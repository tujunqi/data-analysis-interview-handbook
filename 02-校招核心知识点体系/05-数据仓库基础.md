# 数据仓库基础全解：业务数仓的入门地图

> 校招数据分析岗不要求你会搭数仓，但**几乎一定**会问三个问题："数仓分几层、为什么要分层""事实表和维度表是什么""星型和雪花什么区别"。这三个问题答不好，面试官会怀疑你只做过"取数"，没理解数据从哪来、怎么加工。本篇六节：**数仓是什么 → 事实表与维度表 → 星型与雪花 → 数仓分层 → ETL与调度 → 指标口径管理**，最后配一个电商迷你数仓案例把全部概念落地。

---

## 第一节 数仓是什么、为什么需要它

### 1.1 定义与一句话理解

数据仓库（Data Warehouse）：**面向主题的、集成的、相对稳定的、反映历史变化的数据集合，用于支持管理决策**（Inmon定义，四个关键词值得背）。

业务翻译：业务数据库（MySQL）是为"下单要快"设计的——频繁写、只存当前状态；分析需要"看三年趋势、任意维度切"——需要把各业务库的数据**定期抽到一起、按分析主题重组、保留历史**，这个"分析专用的库"就是数仓。

### 1.2 OLTP vs OLAP（必考对比题）

| | OLTP（业务库） | OLAP（数仓） |
|---|---|---|
| 目的 | 支撑交易：快写入、快查单行 | 支撑分析：大范围扫描聚合 |
| 典型操作 | INSERT/UPDATE/按主键查 | 全表/多维聚合、大JOIN |
| 数据量级 | 单次毫秒级小事务 | 亿行级扫描 |
| 数据形态 | 当前状态（库存=100） | 历史+变化（每天库存快照） |
| 典型系统 | MySQL、Oracle | Hive、Spark、ClickHouse、Doris |

**面试口述**："我在业务库里查'我的订单'是OLTP；我在数仓里算'上周各渠道GMV及环比'是OLAP。两者架构差异的根源是读写模式完全不同，所以不能混用一个系统。"

### 1.3 数仓解决的具体痛点（用案例讲）

没有数仓时：运营要"各渠道新客GMV"需要跨订单库、用户库、渠道投放库取三份数据用Excel拼——口径各异、对不齐、每次重算。有了数仓：三库数据统一入ODS，按统一口径在DWD/DWS加工，所有报表都从同一张ADS表出数——**"同一指标只有一个口径、只算一次"**是数仓存在的根本理由。

## 第二节 事实表与维度表：数仓的两块砖

### 2.1 定义

- **事实表（Fact Table）**：记录"发生的事件"，一行=一次业务动作（一笔订单、一次登录、一次点击）。特征：**体量大（亿行）、字段=外键+度量值**，且持续增长。
- **维度表（Dimension Table）**：描述"事件的主体与环境"，回答"是谁/什么/在哪/什么时候"。特征：**体量小（千-百万行）、字段=描述属性**，相对稳定。

### 2.2 度量值的可加性（易被忽略的高频点）

| 类型 | 定义 | 例子 | 注意 |
|---|---|---|---|
| 完全可加 | 任意维度求和都有意义 | 销售额、销量 | 正常SUM |
| 半可加 | 部分维度可加 | **余额、库存**——按时间求和无意义 | 按时间取"快照"，按地区/商品可加 |
| 不可加 | 求和无意义 | 比率（转化率）、年龄均值 | 必须先加总分子分母再相除 |

**【面试高频】** "余额能不能SUM？"——不能按时间SUM（1号余额100、2号余额100，求和200毫无意义），要取期末快照或按日均值处理；但跨账户/跨地区可以加。这一问答出，说明真理解了事实表设计。

### 2.3 事实表的三种类型

1. **事务事实表**：一行=一次原子事件，最细粒度。例：`fact_order_detail`（一笔订单的一个SKU一行）。
2. **周期快照事实表**：按固定间隔拍"状态快照"。例：`fact_user_balance_daily`（每天每账户一行余额）——余额这类半可加度量的标准载体。
3. **累积快照事实表**：一行=一个有起止的过程，随里程碑更新。例：`fact_order_lifecycle`（一行订单：下单时间/支付时间/发货时间/签收时间/取消时间）——分析"各环节时效"的最好载体，因为它把漏斗各步时间放在同一行。

### 2.4 缓慢变化维（SCD）：维度变了怎么办

用户从"普通会员"升级"黑卡"、门店搬迁——维度属性会变，历史怎么记？

| 类型 | 策略 | 例子 |
|---|---|---|
| SCD0 | 不改，保持原值 | 出生年份 |
| SCD1 | 直接覆盖，不留历史 | 修正录入错误 |
| SCD2 | **新增一行**，用生效日期/是否当前标记 | 会员等级变更保留两行——分析"当时等级"必需 |
| SCD3 | 加一列存"上一个值" | 只关心新旧对比时用 |

**【加分点】** 校招能主动讲SCD2并说出"为什么算历史订单归属必须用SCD2"（当时的等级/当时的组织架构），是数仓理解的强信号。

### 2.5 退化维度与事实表其他细节

- **退化维度（Degenerate Dimension）**：订单号这类"没有对应维度表"的维度，直接留在事实表里当主键用——名字唬人，本质是"没有属性的业务编号"。
- **粒度声明**：设计事实表第一件事是声明"一行代表什么"（一笔订单？一个SKU？一次支付尝试？）——粒度混装是数仓设计的第一大忌。

## 第三节 星型模型与雪花模型：维度的两种组织法

### 3.1 结构对比

```
星型模型（Star Schema）              雪花模型（Snowflake Schema）
   Dim_Date   Dim_Product                Dim_Date   Dim_Product ── Dim_Brand
        \        /                              \        /              /
         事实表 ──                              事实表 ──
        /        \                              /        \
   Dim_Store  Dim_User                       Dim_Store  Dim_User ── Dim_City ── Dim_Province
（维度"扁平化"，一层到底）                （维度再范式化，逐层拆表）
```

- **星型**：维度表单层扁平（品牌信息直接放商品表里）。查询少JOIN一层，宽表冗余但**分析查询快、理解直观**——主流选择。
- **雪花**：维度表再拆（品牌单独成表，商品表存品牌ID）。规范化省冗余，但查询多JOIN、维护复杂——出现在维度属性多且强层级、存储极度敏感的场景。

### 3.2 对比表（面试直接背）

| | 星型 | 雪花 |
|---|---|---|
| JOIN次数 | 少（一层） | 多（多层） |
| 冗余 | 高 | 低 |
| 查询性能 | 快 | 慢（JOIN链长） |
| 维护 | 改动常需整表刷 | 改品牌只改一张小表 |
| 业务数仓/BI工具 | **首选** | 少数场景 |

**结论话术**："业务分析场景性能与易用性优先，业界事实标准是星型；雪花省的那点存储在列式存储时代基本可以忽略。"——**【加分点】** 末半句体现对现代列存（冗余成本低）的理解。

### 3.3 总线矩阵与一致性维度（进阶概念，一句加分）

大型数仓里多个业务线共用维度（用户、商品、日期），Kimball提出**总线矩阵**：行=业务过程（下单/支付/退货），列=维度，格子打勾表示该事实表用了该维度。**一致性维度**（同一定义、同一份实现）保证"用户"在订单分析和登录分析里是同一个口径——这是跨主题分析不翻车的根基。

## 第四节 数仓分层：ODS/DWD/DWS/ADS

### 4.1 五层结构（背熟并会画）

```
ODS（操作数据层）→ DWD（明细数据层）→ DWS（汇总数据层）→ ADS（应用数据层）
                     DIM（维度层，横向供各层使用）
```

| 层 | 全称 | 存什么 | 处理内容 | 命名习惯 | 例子 |
|---|---|---|---|---|---|
| ODS | Operational Data Store | 原样同步的业务库数据 | 不做加工，只落库 | ods_库名_表名 | ods_trade_order_detail |
| DIM | Dimension | 一致性维度 | 清洗、SCD处理 | dim_xxx | dim_user、dim_product |
| DWD | Data Warehouse Detail | 明细事实，一行=一次原子事件 | 清洗、去重、脱敏、统一格式、打维度外键 | dwd_业务_动作_粒度 | dwd_trade_order_detail_di（di=日增量） |
| DWS | Data Warehouse Summary | 轻度汇总，按常用维度预聚合 | 聚合出"人/商品/店铺×天"宽表 | dws_主题_粒度 | dws_trade_user_order_1d（用户日汇总） |
| ADS | Application Data Service | 直接喂报表/看板/接口 | 最终口径计算 | ads_xxx | ads_sales_overview_di |

### 4.2 为什么要分层（面试必考，四条理由）

1. **解耦复用**：上游明细只加工一次，N个报表复用DWS，避免每张报表都从明细重算——省算力且口径统一；
2. **职责清晰**：清洗逻辑在DWD、聚合口径在DWS、报表口径在ADS，改哪层清清楚楚，问题定位快；
3. **数据血缘可追溯**：ADS数字有问题，顺着 ADS→DWS→DWD→ODS 逐层核对，像函数调用栈一样排查；
4. **屏蔽上游变化**：业务库改表结构，只需改ODS→DWD的映射，下游DWS/ADS无感——**防腐层**思想。

**一句话总结版**（面试开场先说这个）："分层本质是**用空间和步骤换质量与效率**：每层只做一类加工，公共逻辑下沉，让同一个指标在全公司只有一条生产线。"

### 4.3 分层的判断题（校招爱考的场景问答）

- 问：报表直接从DWD取数行不行？→ 行但不好：每次重算聚合、口径容易各写各的；除非是一次性临时分析。
- 问：DWS会不会造成数据冗余浪费？→ 会有存储成本，但列式存储+分区下成本远低于"每报表全量重算"的计算成本；DWS只建"高频复用"的汇总，不贪多。
- 问：ADS和DWS区别？→ DWS是"通用中间件"（用户×天这种自然粒度），ADS是"面向具体应用"（这张看板这张报表的具体口径）。

## 第五节 ETL与调度：数据每天怎么"流"起来

### 5.1 ETL/ELT 概念

- **ETL**：抽取（Extract）→ 转换（Transform）→ 加载（Load），传统做法在中间服务器转换后入库；
- **ELT**：先原样入库（ODS），用数仓自己的算力（Hive SQL/Spark）转换——大数据时代主流，因为数仓库计算能力强于ETL工具。面试说出"现代大数据链路多为ELT"即加分。

### 5.2 增量 vs 全量（必考）

| 方式 | 做法 | 适用 |
|---|---|---|
| 全量 | 每天整表覆盖 | 小表（维度表、配置表） |
| 增量 | 只抽"今天新增/变更" | 大事实表（订单、日志） |
| 全量快照 | 每天存一份当天全量（分区表） | 需要历史回溯的状态表（库存、会员列表） |

**增量的坑（面试展示细节用）**：业务库物理删除抓不到 → 用update_time水位线+定时校对，或走CDC（Binlog/Canal/Flink CDC）；增量到达延迟/乱序 → 分区重跑机制兜底。

### 5.3 调度依赖与幂等

- **调度**：Airflow/DolphinScheduler/自研调度系统，按DAG管理任务依赖——`ods同步 → dwd清洗 → dws聚合 → ads产出 → 报表刷新` 串联，上游失败下游不跑（避免算出一堆"半成品"）。
- **幂等性**：同一任务重跑N次结果一致——实现靠"先删分区再写"（`INSERT OVERWRITE`）或按分区覆盖。**【面试高频】** "任务失败了怎么办"标准答案：告警 → 定位（看日志/看数据是否到达）→ 修复后**从故障层开始重跑该分区**，下游自动级联重跑——能讲出"只重跑故障分区、下游级联"就是懂生产。
- **数据质量校验**：行数波动监控（昨日/前7日均值±30%报警）、主键唯一性、关键字段非空、指标勾稽（DWS汇总=DWD明细汇总）——**【加分点】** 主动谈质量校验层的候选人凤毛麟角。

## 第六节 指标口径管理：数仓的"翻译规范"

### 6.1 指标的构成

原子指标 + 修饰词 + 时间周期 = 一个完整派生指标：

```
原子指标：支付金额（业务动作的原生度量）
修饰词：  实物订单、线上渠道、华东区
时间周期：近30天
→ 派生指标：近30天线上渠道华东区实物订单支付金额
```

### 6.2 口径不一致的经典案例（必讲故事）

"GMV"三个团队三个数：运营算"已支付"（1000万）、财务算"已支付-退款"（960万）、老板看的报表算"含未支付"（1200万）。根因：没有统一指标定义与唯一生产链路。治理三板斧：

1. **指标字典**：每个指标登记"业务定义/计算公式/统计口径/负责人/更新频率"；
2. **唯一生产线**：同指标只允许从一张ADS表出数，旧口径下线；
3. **口径评审**：新增指标先评审"和现有指标什么关系、能不能复用原子指标"。

### 6.3 命名与文档习惯

- 分区命名 `_di`（日增量）/`_df`（日全量）/`_hi`（小时增量）——看名字知刷新方式；
- 表注释、字段注释、口径备注写全——"数仓里最难的不是写SQL，是半年后还有人看懂你写了什么"。

## 第七节 迷你案例：把一个电商数仓从0搭出来（纸面版）

> 面试官问"如果让你从0搭一个电商数仓，你怎么设计"，按下面的骨架讲即可。

### 7.1 业务过程 → 事实表规划（总线矩阵）

| 业务过程 \ 维度 | 日期 | 用户 | 商品 | 店铺 | 渠道 |
|---|---|---|---|---|---|
| 下单（事务） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 支付（事务） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 退款（事务） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 用户余额（周期快照） | ✓ | ✓ | | | |
| 订单履约（累积快照） | ✓ | ✓ | ✓ | ✓ | |

对应事实表：`dwd_trade_order_detail_di`（下单明细）、`dwd_trade_pay_detail_di`、`dwd_trade_refund_detail_di`、`dws_user_balance_df`（日全量快照）、`dwd_trade_order_flow_di`（履约里程碑）。

### 7.2 各层加工内容举例（以"下单"为例）

- **ODS**：`ods_trade_order_detail_di` —— MySQL订单表每日增量同步原样落Hive分区 `dt=当天`；
- **DWD**：清洗（去重、`status`归一化、金额单位统一为分）、打上 `dim_user/dim_product` 外键、拆出维度列 → `dwd_trade_order_detail_di`；
- **DWS**：按"用户×天"聚合出 `dws_trade_user_order_1d`（首单标记、订单数、GMV、退款额），按"商品×天"出 `dws_trade_item_order_1d`；
- **ADS**：`ads_sales_overview_di`（全站GMV/订单/客单价/新客占比，喂驾驶舱）、`ads_channel_sales_di`（渠道销售明细，喂运营周报）。

### 7.3 一个具体指标的完整链路（口述模板）

"'近30天渠道新客GMV'怎么算？DWD的订单明细在DWS的'用户×天'汇总里打了首单标记，ADS层按渠道聚合：**新客GMV = 当日GMV中'是否首单=是'的部分，近30天滚动求和**。同一原子指标GMV和'全站GMV'共用同一条DWD→DWS生产线，只换修饰词——这就是口径管理。"这段话能同时展示分层、事实表、指标体系三个知识点，是数仓面试的"满分句式"。

## 第八节 收尾：数仓面试高频问答TOP10

1. **数仓为什么分层**——解耦复用/职责清晰/血缘追溯/屏蔽变化（第四节）。
2. **事实表vs维度表**——事件vs主体；粒度声明；可加性三分类（第二节）。
3. **星型vs雪花**——扁平维度vs范式化维度，业务场景选星型（第三节）。
4. **OLTP vs OLAP**——读写模式决定架构分离（第一节）。
5. **全量/增量/快照怎么选**——大表增量+水位线，状态表全量快照，删除靠CDC（第五节）。
6. **任务失败怎么处理**——定位→修复→从故障层重跑分区→下游级联；幂等靠覆盖写（第五节）。
7. **SCD2是什么、为什么需要**——维度历史多行保留，"当时的等级"才能算对（第二节）。
8. **余额能SUM吗**——半可加，按时间不可加、跨账户可加（第二节）。
9. **DWS和ADS的区别**——通用中间汇总vs面向应用的最终口径（第四节）。
10. **指标口径打架怎么治理**——指标字典+唯一生产线+评审机制（第六节）。
