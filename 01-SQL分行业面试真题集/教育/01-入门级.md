## EDU-01 各渠道线索量与有效线索率

### 1. 业务背景

市场部的投放运营专员每月要复盘各获客渠道（抖音信息流、小红书、老带新、百度搜索、线下地推）的线索产出质量。CRM 系统记录每条留资线索的来源渠道，课程顾问在首次电话回访后标记该线索是否"有效"（能联系上、有明确学习意向）。专员需要知道每个渠道带来多少线索、其中多少有效、有效率是多少，用来决定下月预算向哪些渠道倾斜、收缩哪些低质渠道，这是教育机构"招生—教学—续费"链条的最上游环节。**【面试高频】**线索有效率是教培行业面试出现频率最高的入门考题之一，几乎每场数据岗一面都会考到它的变体。

### 2. 表结构说明

线索表 leads（记录所有留资线索）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| lead_id | BIGINT | 线索ID，主键 |
| channel | VARCHAR(32) | 来源渠道：抖音信息流/小红书/老带新/百度搜索/地推 |
| student_name | VARCHAR(64) | 留资人姓名 |
| phone | VARCHAR(20) | 联系电话 |
| is_valid | TINYINT | 是否有效线索：1有效，0无效（回访后标记） |
| created_at | DATETIME | 线索创建时间 |

示例数据：

| lead_id | channel | student_name | phone | is_valid | created_at |
|---|---|---|---|---|---|
| 1001 | 抖音信息流 | 张同学 | 138****1001 | 1 | 2026-09-01 10:23:00 |
| 1002 | 小红书 | 李同学 | 139****1002 | 0 | 2026-09-01 14:05:00 |
| 1003 | 老带新 | 王同学 | 137****1003 | 1 | 2026-09-02 09:40:00 |
| 1004 | 百度搜索 | 赵同学 | 136****1004 | 0 | 2026-09-02 16:12:00 |
| 1005 | 地推 | 刘同学 | 135****1005 | 1 | 2026-09-03 11:30:00 |

### 3. 解题思路

先明确指标口径：①"线索量"指统计周期内 leads 表的全部记录数，不区分有效与否；②"有效线索率 = 有效线索数 / 线索总数"，分母必须是该渠道全部线索，不能只统计有效线索；③入门题可不限定时间范围，若限定需对 created_at 做日期过滤。实现路径：按 channel 分组，线索量用 COUNT(*)，有效数用 SUM(is_valid) 或 SUM(CASE WHEN is_valid=1 ...)，占比用除法并 ROUND 保留两位，最后按线索量降序输出。**【避坑指南】**若 is_valid 存在 NULL，SUM(is_valid) 不受影响，但 AVG 会把 NULL 行剔出分母导致有效率虚高，务必先确认字段无 NULL 或用 COALESCE 兜底；另外除法要注意 MySQL 整数相除会截断小数，分子应乘 100.0 或用 ROUND 显式控制精度。

### 4. 参考解法

解法一：条件聚合 AVG 写法（一个 GROUP BY 直接出占比）

```sql
SELECT
    channel AS `渠道`,                                   -- 渠道分组维度
    COUNT(*) AS `线索总量`,                               -- 该渠道全部线索数（含无效）
    SUM(is_valid) AS `有效线索数`,                        -- is_valid 为 1 的记录求和即有效数
    ROUND(AVG(is_valid) * 100, 2) AS `有效线索率_百分比`   -- AVG(0/1) 等价于有效占比，乘100转百分数
FROM leads
GROUP BY channel                                         -- 按渠道分组
ORDER BY `线索总量` DESC;                                 -- 按线索量降序，先看主渠道
```

结果解读：返回每个渠道一行，可直观看到"抖音信息流线索量最大但有效率偏低、老带新量中等但有效率最高"的典型结构，提示预算应向高质量渠道倾斜。

解法二：SUM(CASE WHEN) 拆列写法（显式拆分有效/无效，口径更稳）

```sql
SELECT
    channel AS `渠道`,                                              -- 渠道维度
    COUNT(*) AS `线索总量`,                                          -- 全部线索数
    SUM(CASE WHEN is_valid = 1 THEN 1 ELSE 0 END) AS `有效线索数`,    -- 逐行判断，有效记1后求和
    SUM(CASE WHEN is_valid = 0 OR is_valid IS NULL THEN 1 ELSE 0 END) AS `无效线索数`, -- 显式统计无效，含 NULL
    ROUND(SUM(CASE WHEN is_valid = 1 THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS `有效线索率_百分比` -- 分子分母显式可控
FROM leads
GROUP BY channel
ORDER BY `有效线索率_百分比` DESC;                                   -- 本题按有效率降序，看质量排名
```

结果解读：把有效、无效两列都拆出来，可与线索总量交叉验证（有效+无效=总量），适合直接进汇报；显式处理 NULL 后分母口径不漂移，是更严谨的报表习惯。

### 5. 性能分析与优化

两种解法都是单表全量扫描+分组聚合，扫描行数相同，代价几乎一样：AVG 写法少一次 CASE 判断、CPU 略省；CASE WHEN 写法多两次列级计算但可读性与口径控制更好。具体优化建议：①对 (channel, is_valid) 建联合索引（ALTER TABLE leads ADD INDEX idx_channel_valid(channel, is_valid)）可实现索引覆盖，避免回表；②线索表达千万级后，按日预聚合到 dws_channel_leads_daily 汇总表，查询只扫汇总层；③若只需本月数据，务必加 created_at 范围条件并对 (created_at, channel) 建索引，避免全表扫描。

### 6. 面试延伸考点

**问：为什么用 AVG(is_valid) 也能算占比？** 回答要点：is_valid 是 0/1 布尔值，AVG = SUM/COUNT，恰好等于有效记录占比，这是条件聚合的经典技巧，但前提是字段无 NULL，否则分母被偷偷改变。

**问：渠道字段有脏数据（大小写混写、多余空格、同义命名）怎么办？** 回答要点：先清洗再分组，如 TRIM(channel)、统一到渠道字典表做映射，规范动作应放在数仓 DWD 层而非每次查询里临时处理。

**问：有效线索率的口径争议在哪里？** 回答要点："有效"依赖销售回访人工标记，存在主观性与滞后性；更客观的口径是回访接通率、7 日内转试听率，可用下游漏斗数据交叉验证线索质量。

### 7. 业务拓展思考

线索渠道质量分析是市场预算分配的核心依据：有效率高的渠道（如老带新）可加大激励与裂变投入，量大质低的渠道要下钻到素材与计划层级继续排查。该指标可延展为"渠道→有效线索→试听→报名→续费"的全链路转化漏斗，进一步计算各渠道线索成本（CPL）与单报名成本（CPA）；还可以按月对比有效率走势，识别渠道流量质量衰退的早期信号，为投放策略调整提供数据依据。

## EDU-02 每月新增学员数

### 1. 业务背景

校区运营负责人在月度经营会上要汇报学员规模的增长趋势：每个月新注册/新报名的学员有多少人，增长在提速还是放缓。这直接决定校区师资排班与编制、下月市场预算盘子，以及是否需要启动老带新活动补量。教务系统里每条学员档案都有建档时间，运营需要一份按月汇总的新增学员数报表，通常还要与上月对比看环比。**【面试高频】**"按月/按周统计新增"是数据岗笔试的第一道热身题，考察日期函数与分组基本功，答得快且口径干净会给面试官留下很好的第一印象。

### 2. 表结构说明

学员表 students（记录所有正式学员档案）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(64) | 学员姓名 |
| age | TINYINT | 年龄 |
| city | VARCHAR(32) | 所在城市 |
| campus_id | BIGINT | 所属校区ID |
| status | VARCHAR(16) | 状态：在读/结课/退费 |
| created_at | DATETIME | 建档（首次报名）时间 |

示例数据：

| student_id | student_name | age | city | campus_id | status | created_at |
|---|---|---|---|---|---|---|
| 2001 | 陈小明 | 9 | 北京 | 1 | 在读 | 2026-08-03 10:15:00 |
| 2002 | 周小雨 | 12 | 北京 | 1 | 在读 | 2026-08-15 18:40:00 |
| 2003 | 吴同学 | 15 | 上海 | 2 | 在读 | 2026-09-01 09:20:00 |
| 2004 | 郑同学 | 8 | 上海 | 2 | 退费 | 2026-09-10 14:55:00 |
| 2005 | 冯同学 | 17 | 广州 | 3 | 在读 | 2026-09-28 20:05:00 |

### 3. 解题思路

先明确口径："新增学员"以建档时间 created_at 为准，按自然月统计，统计对象是全部新建档学员（含后续退费的）。**【避坑指南】**退费学员仍要计入其建档当月的新增数，不能加 status='在读' 过滤，否则历史月份的新增数会被回溯性削减，这是教育行业最常被追问的口径细节。实现路径：把 created_at 格式化成年月字符串，GROUP BY 后 COUNT(*)，按月份升序排列形成趋势序列。易错点：直接 GROUP BY DATE(created_at) 会变成按天统计；忘记 ORDER BY 导致月份乱序；DATETIME 截断到月应使用 DATE_FORMAT 而非 LEFT 字符串截取，后者可读性差且无法利用函数语义。

### 4. 参考解法

解法一：DATE_FORMAT 直接按月分组

```sql
SELECT
    DATE_FORMAT(created_at, '%Y-%m') AS `月份`,   -- 把日期时间格式化成"年-月"字符串
    COUNT(*) AS `新增学员数`                       -- 每个自然月的建档记录数
FROM students
GROUP BY DATE_FORMAT(created_at, '%Y-%m')          -- 按年月分组
ORDER BY `月份`;                                   -- 按月份升序，形成时间趋势
```

结果解读：输出形如 2026-08：2 人、2026-09：3 人的月度序列，运营可直接画折线图看增长趋势与寒暑假淡旺季波动。

解法二：先按天聚合、再按月二次聚合（子查询写法）

```sql
SELECT
    SUBSTRING(stat_date, 1, 7) AS `月份`,          -- 从"年-月-日"截取前 7 位得到年月
    SUM(daily_cnt) AS `新增学员数`                  -- 把当月各天新增数加总
FROM (
    SELECT
        DATE(created_at) AS stat_date,             -- 先把时间戳截断到"日"
        COUNT(*) AS daily_cnt                      -- 统计每天建档学员数
    FROM students
    GROUP BY DATE(created_at)                      -- 按天分组（大表常先按天预聚合）
) t
GROUP BY SUBSTRING(stat_date, 1, 7)                -- 再按月二次汇总
ORDER BY `月份`;
```

结果解读：两阶段聚合与数仓"日汇总表→月汇总"的加工思路一致；当业务已有每日学员快照表时，直接在日汇总层做月度上卷会比扫明细更快。

### 5. 性能分析与优化

解法一一次全表扫描+一次分组，代价最低；解法二多一层派生表物化（MySQL 中会生成临时表），CPU 与临时表开销更高，仅在数据源本身是"按天汇总表"时才更优。具体优化建议：①对 created_at 建索引，当查询限定"近 12 个月"时可走范围扫描减少读取；②大表按月做 RANGE 分区，月度统计只扫相关分区；③结果固化为 ads_month_new_students 月度汇总表，报表与例会材料直接读汇总，不再实时扫明细。

### 6. 面试延伸考点

**问：如何同时输出每月新增与环比增幅？** 回答要点：用窗口函数 LAG(新增学员数) OVER(ORDER BY 月份) 取上月值，再算 (本月-上月)/上月；MySQL 8.0 原生支持，这是本题最常见的追问。

**问：created_at 上建了索引，这条查询能用到索引吗？** 回答要点：不能，因为没有 WHERE 过滤条件且需要全量聚合；索引只在"限定时间范围"的场景下帮助缩小扫描区间，分组聚合本身仍要读全量满足条件的行。

**问：如果"新增"应按首笔已支付订单时间而非建档时间，两者不一致怎么处理？** 回答要点：先与业务确认口径归属，通常以订单表首笔 pay_status=1 的订单时间为准；建档时间与首单时间的差异本身可作为"线索转化周期"单独分析。

### 7. 业务拓展思考

月度新增是校区健康度的第一曲线，通常还要拆校区、拆渠道看结构：哪个校区在涨、哪个渠道贡献了增量。可联动的动作包括：增长放缓的月份提前安排地推与老带新活动、按新增量预测下季度师资缺口并提前招聘。口径上可延展出"净增学员数=新增-退费""年累计新增""同比增速"等指标，与续费率、退费率一起构成校区经营仪表盘的核心面板。

## EDU-03 各课程报名人数与收入

### 1. 业务背景

课程运营经理在每个招生季结束后要复盘产品线表现：每个课程（如"初一数学秋季班""成人 Python 入门"）卖了多少份、带来多少实收。报名数据在订单表里，课程名称与品类在课程表里，需要两表关联才能出报表。这份报表用于决定下季度哪些课程扩班、哪些课程下架，也是老师课时费分摊与市场投放 ROI 核算的基础数据。**【面试高频】**两表 JOIN + 分组求和是入门笔试的绝对核心题型，几乎每场面试都会出现它的变体，必须做到一次写对。

### 2. 表结构说明

课程表 courses：

| 字段名 | 类型 | 含义 |
|---|---|---|
| course_id | BIGINT | 课程ID，主键 |
| course_name | VARCHAR(128) | 课程名称 |
| category | VARCHAR(32) | 品类：K12学科/素质教育/职业考证/语言培训 |
| price | DECIMAL(10,2) | 课程标价（元） |

示例数据：

| course_id | course_name | category | price |
|---|---|---|---|
| 11 | 初一数学秋季班 | K12学科 | 3600.00 |
| 12 | 成人Python入门 | 职业考证 | 1980.00 |
| 13 | 雅思强化6人班 | 语言培训 | 1299.00 |

报名订单表 orders（一笔报名一条记录）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 报名课程ID |
| amount | DECIMAL(10,2) | 实付金额（元） |
| pay_status | TINYINT | 支付状态：1已支付，0未支付/已取消 |
| created_at | DATETIME | 下单时间 |

示例数据：

| order_id | student_id | course_id | amount | pay_status | created_at |
|---|---|---|---|---|---|
| 3001 | 2001 | 11 | 3600.00 | 1 | 2026-09-01 10:00:00 |
| 3002 | 2002 | 11 | 3200.00 | 1 | 2026-09-01 11:20:00 |
| 3003 | 2003 | 12 | 1980.00 | 1 | 2026-09-02 09:10:00 |
| 3004 | 2004 | 12 | 1980.00 | 0 | 2026-09-02 15:30:00 |
| 3005 | 2005 | 11 | 3600.00 | 1 | 2026-09-03 19:45:00 |

### 3. 解题思路

先明确口径：①"报名人数"是已支付订单数还是去重学员数要与面试官确认，本题两个口径同时给出；②"收入"用实付金额 amount 汇总而不是课程标价 price，因为存在优惠、券与差价；③必须过滤 pay_status=1，否则未支付订单会虚增收入。实现路径：orders 关联 courses 拿课程名，按课程分组，分别 COUNT(*)、COUNT(DISTINCT student_id)、SUM(amount)，按收入降序。**【避坑指南】**忘记过滤未支付订单、用标价 price 代替实付金额统计收入，是本题两大失分点；若要求零报名课程也出现在报表中，需改用 LEFT JOIN 并对 NULL 用 IFNULL 补 0。

### 4. 参考解法

解法一：先关联后分组（直观写法）

```sql
SELECT
    c.course_name AS `课程名称`,                        -- 从课程表取课程名
    COUNT(*) AS `报名订单数`,                            -- 已支付订单笔数
    COUNT(DISTINCT o.student_id) AS `报名人数`,          -- 同一学员重复报班只算一次
    SUM(o.amount) AS `实收金额`                          -- 实付金额求和，而非标价
FROM orders o
INNER JOIN courses c                                    -- 订单关联课程补名称
    ON o.course_id = c.course_id
WHERE o.pay_status = 1                                  -- 只统计已支付订单
GROUP BY c.course_id, c.course_name                     -- 按课程分组（带上ID防重名）
ORDER BY `实收金额` DESC;                                -- 按收入降序看主力课程
```

结果解读：课程"初一数学秋季班"3 笔订单贡献 10400 元是当期主力；若订单数明显大于去重人数，说明学员复购/联报行为活跃，可顺势推联报优惠。

解法二：先聚合后关联（子查询写法，保留零销量课程）

```sql
SELECT
    c.course_name AS `课程名称`,                        -- 课程名
    IFNULL(t.order_cnt, 0) AS `报名订单数`,              -- 无订单的课程补 0
    IFNULL(t.pay_amt, 0) AS `实收金额`                   -- 收入同样补 0
FROM courses c
LEFT JOIN (                                             -- 左连接保证没销量的课程也在报表里
    SELECT
        course_id,                                      -- 分组键：课程
        COUNT(*) AS order_cnt,                          -- 已支付订单数
        SUM(amount) AS pay_amt                          -- 已支付实收合计
    FROM orders
    WHERE pay_status = 1                                -- 过滤未支付
    GROUP BY course_id
) t ON c.course_id = t.course_id
ORDER BY `实收金额` DESC;
```

结果解读：该写法能带出零报名的"陪跑课程"，运营据此识别滞销课程；先在子查询里把订单表压缩到课程粒度再关联，宽表大场景下更省资源。

### 5. 性能分析与优化

解法一先 JOIN 后聚合，若 orders 达千万级，JOIN 产生的中间结果集大；解法二先聚合把订单明细压缩到课程粒度（行数=课程数）再 JOIN，通常更快。具体优化建议：①orders 对 (pay_status, course_id) 建联合索引，既做过滤又辅助分组；②两表的 course_id 均需索引，保证 JOIN 走 ref/eq_ref 而非全表嵌套循环；③报表场景建议 T+1 预聚合到 dws_course_sales_daily（课程×日粒度的订单数与金额），看板直接读汇总层。

### 6. 面试延伸考点

**问：COUNT(*) 和 COUNT(DISTINCT student_id) 什么时候差很多？** 回答要点：同一学员一季联报多班（如数学+英语）时订单数远大于去重人数，教育行业联报很常见，两个口径都应提供给业务方并注明含义。

**问：为什么统计收入不用 courses.price？** 回答要点：price 是标价，实收受折扣、优惠券、续费减免影响，财务口径必须以订单实付 amount 为准，否则对不上账。

**问：如果要按品类上卷看收入怎么办？** 回答要点：把分组维度换成 c.category 或同时按品类+课程分组，再按品类 ROLLUP 汇总；本质是同一份明细在不同粒度上的聚合。

### 7. 业务拓展思考

课程维度收入报表是产品线取舍的依据：高收入低人数的大班课与低收入高人数的低价引流课要分开评估，可继续下钻客单价（收入/人数）与毛利率。联动动作包括：滞销课程调整定价或打包进联报优惠、爆款课程提前扩班并锁定师资。口径延展上，可增加"退费金额"列计算净收入，或按品类、按校区、按月上卷，形成课程经营的多维分析立方体，支撑季度产品会决策。

## EDU-04 学员年龄段与城市分布

### 1. 业务背景

市场与教研团队在制定新品课程规划时需要学员画像支持：机构现有学员主要集中在哪个年龄段、分布在哪些城市。年龄段决定课程梯度设计（幼儿启蒙、小学培优、初高中冲刺、成人职教），城市分布决定是否新开校区或加大线上课投放。学员表里只有精确年龄，需要用 SQL 把连续年龄切成"6 岁以下/小学段/中学段/成人段"等分箱，再统计各分箱人数，这是画像分析最基础的一环。**【加分点】**用 CASE WHEN 完成连续值分箱并保证分箱不重不漏，是校招面试的高频基本功考点，边界处理能直接体现逻辑严谨性。

### 2. 表结构说明

学员表 students（与 EDU-02 同源，本题关注年龄与城市字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(64) | 学员姓名 |
| age | TINYINT | 年龄（成人职教学员为 19-45） |
| city | VARCHAR(32) | 所在城市 |
| status | VARCHAR(16) | 状态：在读/结课/退费 |
| created_at | DATETIME | 建档时间 |

示例数据：

| student_id | student_name | age | city | status | created_at |
|---|---|---|---|---|---|
| 2001 | 陈小明 | 9 | 北京 | 在读 | 2026-08-03 10:15:00 |
| 2002 | 周小雨 | 12 | 北京 | 在读 | 2026-08-15 18:40:00 |
| 2003 | 吴同学 | 15 | 上海 | 在读 | 2026-09-01 09:20:00 |
| 2004 | 何同学 | 7 | 广州 | 在读 | 2026-09-10 14:55:00 |
| 2005 | 冯同学 | 24 | 深圳 | 在读 | 2026-09-28 20:05:00 |

### 3. 解题思路

先明确口径：①统计对象建议限定 status='在读' 的活跃学员，也可按全部建档口径，需先与面试官确认；②年龄分箱边界要定义清楚（如小学段为 6-11 岁、中学段为 12-17 岁），CASE WHEN 自上而下短路求值，各分支条件必须不重不漏；③NULL 年龄单独归"未知"档而不是丢弃，否则各档人数加总对不上总人数。实现路径：CASE WHEN 生成年龄段标签，再按年龄段×城市交叉分组 COUNT。易错点：相邻分箱都用 BETWEEN 且边界重叠，导致边界年龄被重复计数；忘记 ELSE 兜底使 NULL 行落入 NULL 分组；分箱规则改动时忘改 GROUP BY 里的同一表达式。

### 4. 参考解法

解法一：CASE WHEN 分箱 + 年龄段×城市交叉分布

```sql
SELECT
    CASE
        WHEN age < 6  THEN '6岁以下'                 -- 学龄前
        WHEN age BETWEEN 6 AND 11  THEN '小学段'      -- 6-11 岁，含两端边界
        WHEN age BETWEEN 12 AND 17 THEN '中学段'      -- 12-17 岁，与上一档不重叠
        ELSE '成人段'                                -- 18 岁及以上兜底
    END AS `年龄段`,
    city AS `城市`,                                  -- 第二个分组维度
    COUNT(*) AS `学员数`                             -- 交叉计数
FROM students
WHERE status = '在读'                                -- 只看在读学员画像
GROUP BY
    CASE
        WHEN age < 6  THEN '6岁以下'
        WHEN age BETWEEN 6 AND 11  THEN '小学段'
        WHEN age BETWEEN 12 AND 17 THEN '中学段'
        ELSE '成人段'
    END,
    city                                             -- 年龄段与城市两维联合分组
ORDER BY `年龄段`, `学员数` DESC;                     -- 段内按人数降序
```

结果解读：一张"年龄段×城市"交叉明细，如北京以小学段为主、深圳成人段占比高，可直接支撑各城市的课程组合与投放定向决策。

解法二：子查询先打年龄标签，外层统计各档总人数与占比

```sql
SELECT
    t.age_group AS `年龄段`,                             -- 子查询中已打好的标签
    COUNT(*) AS `学员数`,                                -- 该档人数
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*)
                              FROM students
                              WHERE status = '在读'), 2) AS `占比_百分比` -- 除以在读总人数
FROM (
    SELECT
        student_id,
        CASE
            WHEN age IS NULL THEN '未知'                 -- NULL 单独归档，保证总数对齐
            WHEN age < 6  THEN '6岁以下'
            WHEN age BETWEEN 6 AND 11  THEN '小学段'
            WHEN age BETWEEN 12 AND 17 THEN '中学段'
            ELSE '成人段'
        END AS age_group
    FROM students
    WHERE status = '在读'
) t
GROUP BY t.age_group
ORDER BY FIELD(t.age_group, '6岁以下', '小学段', '中学段', '成人段', '未知'); -- 按业务顺序输出
```

结果解读：占比列让画像一眼可读（如小学段 45%、中学段 30%），FIELD 函数让分箱按业务逻辑排序而非字母序，是汇报友好的细节。

### 5. 性能分析与优化

解法一交叉分组的输出行数=年龄段数×城市数，分组开销小，但 CASE 表达式在 SELECT 与 GROUP BY 中重复书写、维护成本高；解法二多一层派生表物化，略增开销，但结构清晰且便于计算占比。具体优化建议：①age 允许 NULL 时先在清洗层补齐或打标，避免每次查询都处理；②画像类查询建议夜间跑批写入 dws_student_profile 汇总表，前端直读；③(status, city) 上建联合索引辅助 WHERE 过滤，减少扫描行数。

### 6. 面试延伸考点

**问：BETWEEN 写分箱为什么容易出重复计数？** 回答要点：BETWEEN 两端都含边界，若相邻档写成 BETWEEN 6 AND 12 与 BETWEEN 12 AND 17，12 岁会命中两档；应统一左闭右开（age >= 6 AND age < 12）或让 CASE 自上而下短路保证互斥。

**问：年龄缺失怎么处理更稳妥？** 回答要点：单独归"未知"档保持分母完整，画像占比才有意义；不要删记录，也不要填均值后再分箱，那会制造假的中间档拥挤。

**问：这个分布要按月看趋势怎么办？** 回答要点：加 DATE_FORMAT(created_at,'%Y-%m') 维度，或对建档月份做同期群对比，观察年龄段结构随时间的迁移，判断机构定位是否漂移。

### 7. 业务拓展思考

年龄段与城市分布是课程规划与投放定向的底表：小学段集中的城市主推培优与托管产品，成人段占比高的城市把预算转向职教考证与线上课。可联动动作包括按画像调整试听课排期（匹配家长下班时段）、教研按年龄段重构教材难度梯度。口径延展上，可与报名数据交叉计算"各年龄段客单价与续费率"，把静态人口画像升级为价值画像，指导分层运营与个性化触达。

## EDU-05 试听课排课与实际上课数

### 1. 业务背景

课程顾问的核心过程指标之一是试听课的履约情况：给意向学员约了试听课，学员是否真的来了。试听爽约率高，说明线索质量差或顾问跟进不到位，需要在每周销售例会上按课程、按顾问拆解"排课数、实际上课数、履约率"，找出爽约重灾的时段与人群，进而决定是加强课前提醒（短信/企微）还是收缩低质渠道的约课量。教务系统的排课表记录每一节试听安排及其最终状态，是本题的数据来源。**【面试高频】**"应到 vs 实到"是教育行业数据题的经典母题，后续的直播到课率、正课到课率、续费率分析都是它的变体。

### 2. 表结构说明

试听排课表 trial_classes（每节约一次试听安排）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| schedule_id | BIGINT | 排课记录ID，主键 |
| lead_id | BIGINT | 关联线索ID（意向学员） |
| course_id | BIGINT | 试听课程ID |
| consultant_id | BIGINT | 约课顾问ID |
| scheduled_at | DATETIME | 预约上课时间 |
| attend_status | VARCHAR(16) | 状态：已上/爽约/取消 |

示例数据：

| schedule_id | lead_id | course_id | consultant_id | scheduled_at | attend_status |
|---|---|---|---|---|---|
| 4001 | 1001 | 11 | 801 | 2026-09-05 19:00:00 | 已上 |
| 4002 | 1002 | 11 | 801 | 2026-09-05 19:00:00 | 爽约 |
| 4003 | 1003 | 12 | 802 | 2026-09-06 10:00:00 | 已上 |
| 4004 | 1004 | 12 | 802 | 2026-09-06 10:00:00 | 取消 |
| 4005 | 1005 | 11 | 801 | 2026-09-07 19:00:00 | 已上 |

### 3. 解题思路

先明确口径：①"排课数"= 全部试听安排记录数（含取消），"实际上课数"仅指 attend_status='已上' 的记录；②"履约率"分母有争议：严格口径用"排课数-取消数"（取消多为顾问侧改期，不应记学员爽约），宽松口径用全部排课数，答题时先声明选择；③状态是字符串，比较值必须与库内存储完全一致。实现路径：按课程分组，条件聚合各状态数量并计算履约率。易错点：把"取消"算进爽约虚增流失；履约率分母忘记剔除取消；字符串状态值存在空格或大小写差异导致漏统计，必要时先 TRIM 清洗。

### 4. 参考解法

解法一：按课程条件聚合，一次出全部指标

```sql
SELECT
    course_id AS `课程ID`,                                        -- 课程维度
    COUNT(*) AS `排课总数`,                                        -- 含取消的全部安排
    SUM(attend_status = '已上') AS `实际上课数`,                    -- MySQL 布尔表达式可直接求和
    SUM(attend_status = '爽约') AS `爽约数`,                        -- 学员未到且未提前取消
    ROUND(SUM(attend_status = '已上') /
          (COUNT(*) - SUM(attend_status = '取消')) * 100, 2) AS `履约率_百分比` -- 分母剔除取消
FROM trial_classes
GROUP BY course_id
ORDER BY `排课总数` DESC;
```

结果解读：课程 11 排课 3 节实上 2 节、履约率 66.67%；课程 12 排课 2 节、1 节取消 1 节实上，剔除取消后履约率 100%——取消多但爽约少，说明问题出在顾问改期而非学员爽约，管理动作完全不同。

解法二：先按状态拆列统计，再用 HAVING 过滤小样本

```sql
SELECT
    course_id AS `课程ID`,                                   -- 课程维度
    SUM(CASE WHEN attend_status = '已上' THEN 1 ELSE 0 END) AS `实际上课数`, -- 行转列：已上
    SUM(CASE WHEN attend_status = '爽约' THEN 1 ELSE 0 END) AS `爽约数`,     -- 行转列：爽约
    SUM(CASE WHEN attend_status = '取消' THEN 1 ELSE 0 END) AS `取消数`,     -- 行转列：取消
    COUNT(*) AS `排课总数`                                    -- 三状态之和应等于总数，用于自检
FROM trial_classes
GROUP BY course_id
HAVING COUNT(*) >= 2                                          -- 过滤排课太少的课程，防比率波动误导
ORDER BY `排课总数` DESC;
```

结果解读：三个状态列相加等于排课总数，可当场自检口径；HAVING 过滤掉只有 1 节排课的课程，避免小样本比率（1 爽约即 100% 爽约率）误导决策，是比解法一更严谨的报表习惯。

### 5. 性能分析与优化

两种写法同为单表一次扫描+分组聚合，代价相同；解法一的布尔求和写法少写 CASE 分支、CPU 略优，但仅 MySQL 支持，可移植性差。具体优化建议：①对 (course_id, attend_status) 建联合索引，可覆盖分组与状态判断；②若只看近 7 天，加 scheduled_at 范围条件并建 (course_id, scheduled_at) 索引；③履约率适合按周预聚合固化成 dws_trial_weekly_stat，例会报表直接读取，不再实时扫明细。

### 6. 面试延伸考点

**问：SUM(attend_status='已上') 这个写法的原理是什么？通用吗？** 回答要点：MySQL 中布尔表达式返回 1/0，SUM 即计数；但它不符合标准 SQL，迁移到 PostgreSQL 等库需改写为 SUM(CASE WHEN ...)，跨方言项目建议直接用标准写法。

**问：履约率分母到底该不该剔除"取消"？** 回答要点：建议区分"学员取消"与"顾问/机构取消"两个字段或加取消人标识，前者计入分母、后者剔除，口径说明写进报表脚注。

**问：如何定位爽约学员的共同特征？** 回答要点：把爽约记录关联线索表看渠道、约课时段、约课到试听的间隔时长并做分组对比；常见结论是"约课到试听间隔超过 3 天，爽约率显著上升"，据此把提醒和改期策略前置。

### 7. 业务拓展思考

试听履约是"线索到报名"漏斗的咽喉：履约率每提升 10 个百分点，同等线索量下的报名增量立竿见影。可联动动作包括课前 24 小时与 2 小时双提醒、爽约学员自动进入 48 小时补救召回队列、按履约率而非约课量考核顾问的约课质量。口径延展上可继续计算"试听转报名率"，与履约率连乘得到"线索-报名"整体转化率，作为渠道 ROI 评估与顾问提成设计的统一基础。

| 5003 | 902 | 602 | 2026-10-09 | 3.0 | 已完成 |
| 5004 | 901 | 603 | 2026-10-12 | 2.0 | 已取消 |
| 5005 | 903 | 604 | 2026-09-30 | 2.0 | 已完成 |

### 3. 解题思路

先明确口径：①只统计 session_status='已完成' 的课节，已取消的课不计课时；②时间范围"本月"用 session_date 匹配 2026-10，推荐范围写法 session_date >= '2026-10-01' AND session_date < '2026-11-01'，比 DATE_FORMAT 等值比较更容易走索引；③结果必须包含本月无课的老师且课时显示 0 而非 NULL。实现路径：teachers LEFT JOIN 上课记录，按老师分组 SUM 课时。**【避坑指南】**把 session_status='已完成' 这类右表过滤条件写进 WHERE 而不是 JOIN ON，会把右表为 NULL 的行（0 课时老师）整体剔除，LEFT JOIN 退化成 INNER JOIN，闲置师资从报表里消失——这是本题埋的最深的坑。

### 4. 参考解法

解法一：LEFT JOIN + 过滤条件放 ON（保留无课老师）

```sql
SELECT
    t.teacher_id AS `教师ID`,                            -- 老师维度
    t.teacher_name AS `教师姓名`,                         -- 老师姓名
    IFNULL(SUM(s.duration_hours), 0) AS `本月课时`        -- 无课老师补 0，避免显示 NULL
FROM teachers t
LEFT JOIN class_sessions s
    ON s.teacher_id = t.teacher_id
   AND s.session_status = '已完成'                        -- 状态过滤放 ON：不破坏左连接
   AND s.session_date >= '2026-10-01'                     -- 本月起点，范围写法可走索引
   AND s.session_date <  '2026-11-01'                     -- 左闭右开，避免月末边界问题
GROUP BY t.teacher_id, t.teacher_name
ORDER BY `本月课时` DESC;                                  -- 课时从高到低
```

结果解读：王老师 4.0 课时居首，李老师 3.0，张老师 0 课时也保留在结果里——教务主管可一眼锁定本月闲置、需要排课倾斜的英语师资。

解法二：先聚合子查询，再 LEFT JOIN（先算后关联）

```sql
SELECT
    t.teacher_name AS `教师姓名`,                          -- 教师姓名
    IFNULL(s.total_hours, 0) AS `本月课时`                  -- 子查询无记录时补 0
FROM teachers t
LEFT JOIN (
    SELECT
        teacher_id,                                       -- 按老师分组
        SUM(duration_hours) AS total_hours                -- 已完成课时合计
    FROM class_sessions
    WHERE session_status = '已完成'                       -- 子查询内部先过滤
      AND session_date >= '2026-10-01'                    -- 限定本月
      AND session_date <  '2026-11-01'
    GROUP BY teacher_id
) s ON t.teacher_id = s.teacher_id                         -- 聚合后的小表再关联
ORDER BY `本月课时` DESC;
```

结果解读：与解法一结果完全一致，但子查询先把大课表明细压成"老师×月"小表（行数=老师数）再关联，千万级课时表下性能明显更好，也是数仓开发的惯用手法。

### 5. 性能分析与优化

解法一先 JOIN 后聚合，中间结果为"老师×课节"明细，大课时表下临时结果大；解法二先聚合再 JOIN，参与关联的只有老师数级行，JOIN 代价极低，大表下更优。具体优化建议：①class_sessions 对 (session_status, session_date, teacher_id) 建联合索引，子查询可实现索引覆盖；②课时表按月 RANGE 分区，本月统计只扫当月分区；③结果固化成 dws_teacher_monthly_hours 月度汇总表，薪资核算直接取数并保留历史快照。

### 6. 面试延伸考点

**问：LEFT JOIN 之后又在 WHERE 里写 s.session_status='已完成' 会怎样？** 回答要点：等值条件对 NULL 行判定为假，0 课时老师被全部过滤，LEFT JOIN 退化为 INNER JOIN；正确做法是把条件写进 ON，或用 (条件 OR s.teacher_id IS NULL) 兜底。

**问：课时量能否直接用 COUNT(*) 数节数代替？** 回答要点：不能，一对一与班课的时长不同，绩效按标准课时 duration_hours 结算；若源表只有节数，需乘时长系数折算后再汇总。

**问：怎么衡量老师之间的排班均衡度？** 回答要点：在课时量基础上比较同学科组内的离散程度（极差或标准差），方差过大说明排班失衡；SQL 里可用窗口函数算出组均值后再与个人对比。

### 7. 业务拓展思考

老师课时量是教学产能的核心指标：过低意味着人力闲置与成本浪费，过高则有教学质量下滑与离职风险，通常设置健康区间（如每月 60-90 标准课时）并监控越界人数。联动动作包括排课系统按均衡度自动推荐排班、淡旺季切换前提前储备兼职师资。口径延展上可区分"正课/试听课/教研备课"课时分别计价，或计算"人效=课时收入/老师薪酬"，把工作量报表升级为师资盈利能力分析。

## EDU-07 本月退费申请清单及金额

### 1. 业务背景

学员满意度下降或课程不匹配时家长会提出退费申请；财务与质检团队每月要出一份退费清单：谁、什么时间、因为什么原因、申请退多少、审批处于什么状态。这份清单既是财务打款的依据，也是教学质量复盘的输入——把退费原因归类后，能定位是师资问题、排课问题还是售前过度承诺问题。运营负责人还关心退费金额占当期收入的比例（退费率），作为经营健康度的负向监控指标。**【面试高频】**"明细清单+分类汇总"是笔试最常见的组合题，考察 SELECT 过滤、排序与聚合的综合基本功，也能看出候选人有没有"口径要先声明"的职业习惯。

### 2. 表结构说明

退费申请表 refunds：

| 字段名 | 类型 | 含义 |
|---|---|---|
| refund_id | BIGINT | 退费单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| apply_date | DATE | 申请日期 |
| refund_amount | DECIMAL(10,2) | 申请退费金额（元） |
| refund_reason | VARCHAR(64) | 退费原因：效果不符/时间冲突/搬迁转学/服务态度/其他 |
| status | VARCHAR(16) | 状态：待审核/已通过/已驳回 |

示例数据：

| refund_id | student_id | course_id | apply_date | refund_amount | refund_reason | status |
|---|---|---|---|---|---|---|
| 7001 | 2001 | 11 | 2026-10-05 | 2400.00 | 效果不符 | 已通过 |
| 7002 | 2004 | 12 | 2026-10-07 | 1980.00 | 时间冲突 | 待审核 |
| 7003 | 2006 | 11 | 2026-10-09 | 3600.00 | 搬迁转学 | 已通过 |
| 7004 | 2007 | 13 | 2026-10-12 | 899.00 | 服务态度 | 已驳回 |
| 7005 | 2008 | 12 | 2026-10-15 | 1500.00 | 效果不符 | 待审核 |

### 3. 解题思路

先明确口径：①"本月退费"按申请日期 apply_date 归月，而不是财务实际打款日，两者差异体现审核时长；②清单题要保留明细行并排序（金额降序、日期升序），汇报时另附汇总行；③金额有"申请金额"与"已通过金额"之分，监控经营健康度看已通过口径，清单可两列并出。实现路径：解法一按月过滤明细并 LEFT JOIN 学员、课程补名称；解法二按退费原因分组汇总笔数与金额。易错点：日期范围写 BETWEEN '2026-10-01' AND '2026-10-31'，在字段为 DATETIME 时会漏掉 10-31 当天的记录，应统一用"≥月初 且 <次月月初"的左闭右开写法。

### 4. 参考解法

解法一：本月退费明细清单（过滤 + JOIN + 排序）

```sql
SELECT
    r.refund_id AS `退费单号`,                            -- 明细行：单号
    s.student_name AS `学员姓名`,                         -- 关联学员表补姓名
    c.course_name AS `课程名称`,                          -- 关联课程表补课程名
    r.apply_date AS `申请日期`,                           -- 申请时间
    r.refund_reason AS `退费原因`,
    r.status AS `审批状态`,
    r.refund_amount AS `申请金额`                         -- 保留申请口径金额
FROM refunds r
LEFT JOIN students s ON r.student_id = s.student_id       -- LEFT JOIN 防学员档案缺失时丢行
LEFT JOIN courses  c ON r.course_id  = c.course_id
WHERE r.apply_date >= '2026-10-01'                        -- 左闭右开的月度范围
  AND r.apply_date <  '2026-11-01'
ORDER BY r.refund_amount DESC, r.apply_date;              -- 金额优先降序，同额按日期先后
```

结果解读：5 笔申请合计 10379 元，其中"效果不符"出现 2 笔为最高频原因，提示秋季班教学满意度需要专项回访，质检团队按清单逐单跟进。

解法二：按退费原因分组汇总（聚合 + 状态拆列）

```sql
SELECT
    refund_reason AS `退费原因`,                                   -- 原因维度
    COUNT(*) AS `申请笔数`,                                        -- 全部申请笔数
    SUM(refund_amount) AS `申请金额合计`,                            -- 申请口径金额
    SUM(CASE WHEN status = '已通过' THEN refund_amount ELSE 0 END) AS `已通过金额`, -- 只累加审批通过的
    ROUND(SUM(CASE WHEN status = '已通过' THEN refund_amount ELSE 0 END)
          / SUM(refund_amount) * 100, 2) AS `通过金额占比_百分比`     -- 通过率监控
FROM refunds
WHERE apply_date >= '2026-10-01'                                  -- 本月范围
  AND apply_date <  '2026-11-01'
GROUP BY refund_reason
ORDER BY `申请金额合计` DESC;                                       -- 按金额降序定位主要流失原因
```

结果解读："效果不符"是金额最大的退费原因且审批通过比例高，说明退费诉求合理性强，应优先排查该课程的教学质量与售前承诺一致性，而不是收紧审批。

### 5. 性能分析与优化

解法一为明细查询，扫描行数等于当月退费单数（通常仅数百到数千行），两次 JOIN 均走主键，代价很低；解法二多一层条件聚合，同样轻量。具体优化建议：①refunds 对 (apply_date, refund_reason) 建联合索引，月度过滤可走范围扫描；②退费单达百万级后按月分区；③退费率监控建议与收入表按月 JOIN 后预计算成经营指标表，避免报表端每次实时做除法与跨表对账。

### 6. 面试延伸考点

**问：BETWEEN '2026-10-01' AND '2026-10-31' 有什么隐患？** 回答要点：若 apply_date 是 DATETIME，10-31 当天 00:00 之后的记录会被漏掉；统一用 >= 月初 AND < 次月月初的左闭右开写法，日与月粒度切换都不出错。

**问：退费率怎么算才严谨？** 回答要点：当月已通过退费金额 / 当月确认收入，分子分母同月同口径；申请金额含未通过与待审核项，不能直接做分子，也不应与不同月的收入错配。

**问：如何分析退费学员的历史行为？** 回答要点：把退费学员关联出勤、作业、评分数据，与未退费学员做对比；常见发现是"到课率低于 40% 的学员退费概率显著升高"，从而把退费预警前置到行为信号。

### 7. 业务拓展思考

退费是续费链条的负向信号，逐单归因比看总量更重要：把原因结构化后可以驱动具体动作——"时间冲突"多就增加班次与回放，"效果不符"多就做入学测试分层排班并校准售前话术。口径延展上可监测"申请到打款时长"（服务体验）、"退费学员 90 天回流率"（召回效果），并把退费预警前置到"连续缺课 3 次未请假"等行为信号，变事后处理为事前挽留。

## EDU-08 各班级作业提交率

### 1. 业务背景

教学质检团队每周检查各班级的作业提交情况：布置的作业里学员实际交了多少。提交率低的班级可能意味着课程难度不匹配、班主任督学不到位，甚至是学员流失的前兆。班主任需要一张班级维度的提交率榜单，低于阈值的班级要触发督学动作（电话回访、家长群提醒），榜单也用于班主任绩效考核。作业系统里每条记录代表"某学员在某次作业上的应交与实交状态"，需要在班级粒度汇总。**【避坑指南】**提交率的分母是"应交人次"（每次作业覆盖到的每名学员），分子是"实交人次"，混淆两者或用学员数做分母都会让指标失真，这是本题埋的核心考点。

### 2. 表结构说明

作业提交记录表 homework_records（每条 = 一名学员的一次作业应交记录）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| record_id | BIGINT | 记录ID，主键 |
| class_id | BIGINT | 班级ID |
| student_id | BIGINT | 学员ID |
| homework_id | BIGINT | 作业ID |
| is_submitted | TINYINT | 是否提交：1已交，0未交 |
| submit_time | DATETIME | 提交时间（未交为 NULL） |
| created_at | DATETIME | 作业布置时间 |

示例数据：

| record_id | class_id | student_id | homework_id | is_submitted | submit_time | created_at |
|---|---|---|---|---|---|---|
| 8001 | 601 | 2001 | 31 | 1 | 2026-10-09 20:10:00 | 2026-10-08 19:00:00 |
| 8002 | 601 | 2002 | 31 | 0 | NULL | 2026-10-08 19:00:00 |
| 8003 | 601 | 2001 | 32 | 1 | 2026-10-12 21:00:00 | 2026-10-11 19:00:00 |
| 8004 | 602 | 2003 | 33 | 0 | NULL | 2026-10-09 19:00:00 |
| 8005 | 602 | 2009 | 33 | 1 | 2026-10-13 18:30:00 | 2026-10-09 19:00:00 |

班级表 classes：

| 字段名 | 类型 | 含义 |
|---|---|---|
| class_id | BIGINT | 班级ID，主键 |
| class_name | VARCHAR(64) | 班级名称，如"初一数学秋季3班" |
| head_teacher_id | BIGINT | 班主任ID |

示例数据：

| class_id | class_name | head_teacher_id |
|---|---|---|
| 601 | 初一数学秋季3班 | 811 |
| 602 | 初二英语秋季1班 | 812 |
| 603 | 少儿编程入门A班 | 813 |

### 3. 解题思路

先明确口径：①提交率 = SUM(is_submitted) / COUNT(*)，每条记录都是一次"应交"，分母天然正确；②按班级分组后要 JOIN 班级表拿班级名；③若记录中含已退费学员，是否剔除要在口径确认时说明，本题从督学视角保留全部。实现路径：JOIN 班级表补名称，按班级分组条件聚合计算提交率，用 HAVING 筛出低于 60% 的预警班级。易错点：AVG(is_submitted) 遇到 NULL 会把 NULL 行剔出分母导致比率虚高，应先确认字段无 NULL 或 COALESCE 兜底；WHERE 与 HAVING 混用——过滤聚合后的结果只能用 HAVING，这是本题的语法考点。

### 4. 参考解法

解法一：AVG 条件聚合直接出比率 + HAVING 预警

```sql
SELECT
    c.class_name AS `班级名称`,                          -- 关联班级名
    COUNT(*) AS `应交人次`,                               -- 每条记录即一次应交
    SUM(h.is_submitted) AS `实交人次`,                    -- is_submitted=1 的个数即实交
    ROUND(AVG(h.is_submitted) * 100, 2) AS `提交率_百分比` -- 0/1 字段取平均即提交率
FROM homework_records h
INNER JOIN classes c ON h.class_id = c.class_id           -- 内连接补班级名
GROUP BY c.class_id, c.class_name                         -- 按班级分组（带上ID防重名）
HAVING AVG(h.is_submitted) < 0.6                          -- 只看预警班级：提交率低于 60%
ORDER BY `提交率_百分比`;                                  -- 从差到好排，优先整改
```

结果解读：榜单直接给出需要督学的班级清单，班主任按提交率从低到高逐一整改，配合家长群提醒与电话回访，通常两周内可见提交率回升。

解法二：SUM(CASE WHEN) 拆列 + 显式比率计算

```sql
SELECT
    c.class_name AS `班级名称`,                                        -- 班级名
    COUNT(*) AS `应交人次`,                                            -- 分母：全部应交记录
    SUM(CASE WHEN h.is_submitted = 1 THEN 1 ELSE 0 END) AS `实交人次`,  -- 分子：显式判断提交
    ROUND(SUM(CASE WHEN h.is_submitted = 1 THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS `提交率_百分比`, -- 分子分母显式可控
    ROUND(SUM(CASE WHEN h.is_submitted = 0 THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS `未交率_百分比`  -- 交叉校验：两项相加应为 100
FROM homework_records h
INNER JOIN classes c ON h.class_id = c.class_id
GROUP BY c.class_id, c.class_name
ORDER BY `提交率_百分比` DESC;                                           -- 全量班级榜单
```

结果解读：提交率与未交率互补成 100%，可当场自检口径；相比 AVG 写法，显式 CASE 在 is_submitted 含 NULL 时分母口径不漂移，更适合作为对外发布的正式报表。

### 5. 性能分析与优化

两解法均为一次 JOIN + 单趟分组聚合，数据量等于作业应交记录数（教育场景通常百万级以内），代价可控；差异仅在 CASE 判断的 CPU 开销。具体优化建议：①homework_records 对 (class_id, is_submitted) 建联合索引，聚合可被索引覆盖；②只看近两周时加 created_at 范围条件并建 (class_id, created_at) 索引；③按"班级×周"预聚合提交率写入汇总表，班主任端看板直接读取，避免每次实时扫明细。

### 6. 面试延伸考点

**问：为什么过滤"提交率低于 60% 的班级"必须用 HAVING 而不是 WHERE？** 回答要点：WHERE 在聚合前生效、引用不了聚合函数；HAVING 在聚合后对分组结果过滤，执行顺序决定了只能如此，这是本题的语法核心。

**问：提交率按"人次加权"还是按"学员平均"算，有什么区别？** 回答要点：人次口径即本题（总实交/总应交）；学员平均是先算每人提交率再对学员取均值，两者在作业覆盖次数不一致时结果不同，督学场景通常用人次口径。

**问：未交学员如何自动催交？** 回答要点：查出 is_submitted=0 的记录，关联家长联系方式生成催交名单，按"连续未交次数"分级触发不同话术，避免过度打扰。

### 7. 业务拓展思考

作业提交率是教学过程质量的过程性指标，比考试分数更早反映学员流失风险：连续两周未交作业的学员，退费概率显著上升。联动动作包括班主任按名单分层督学、教研按班级提交率调整作业量与难度、续费期前对高提交率班级优先做续班转化。口径延展上可区分"按时提交率"（submit_time 早于截止时间）与"补交率"，或下钻到学员维度构建作业行为分，纳入学员健康度预警模型。

## EDU-09 每个学员最近一次上课时间

### 1. 业务背景

续费运营团队每天要维护一张"学员活跃度"名单：每个学员最近一次来上课是什么时候。超过 14 天没来上课的学员是流失高危人群，班主任要在其彻底沉默前电话召回；刚上完课的学员则是续班沟通的最佳时机。考勤系统按每节课记录出勤，明细行很多，但名单只要每个学员的最新一条，这是"分组取最新记录"的经典问题。该名单每日更新，是班主任日常工作的第一张表。**【面试高频】**分组取最大值/最新记录是 SQL 笔试 Top3 高频题，MAX 写法与窗口函数写法都必须熟练，且能说清两者的适用差异。

### 2. 表结构说明

上课考勤表 attendance（每名学员每节课一条）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| attendance_id | BIGINT | 考勤ID，主键 |
| student_id | BIGINT | 学员ID |
| class_id | BIGINT | 班级ID |
| class_date | DATE | 上课日期 |
| checkin_status | VARCHAR(16) | 出勤状态：出勤/缺勤/请假 |

示例数据：

| attendance_id | student_id | class_id | class_date | checkin_status |
|---|---|---|---|---|
| 9001 | 2001 | 601 | 2026-10-08 | 出勤 |
| 9002 | 2001 | 601 | 2026-10-15 | 出勤 |
| 9003 | 2002 | 601 | 2026-10-10 | 缺勤 |
| 9004 | 2002 | 601 | 2026-10-17 | 出勤 |
| 9005 | 2003 | 602 | 2026-09-20 | 出勤 |

学员表 students（简版，补姓名用）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(64) | 学员姓名 |
| status | VARCHAR(16) | 学员状态：在读/结课/退费 |

示例数据：

| student_id | student_name | status |
|---|---|---|
| 2001 | 陈小明 | 在读 |
| 2002 | 周小雨 | 在读 |
| 2003 | 吴同学 | 在读 |

### 3. 解题思路

先明确口径：①"最近一次上课"只看 checkin_status='出勤' 的记录，缺勤与请假不算"来上课"；②若只需日期，最近上课日期 = MAX(class_date) 按学员分组即可；③若要连同"上的是哪个班"一起输出，MAX 写法需 JOIN 回原表，窗口写法可一次取整行。实现路径：解法一先按学员 GROUP BY 取 MAX(class_date) 再 JOIN 学员表补姓名；解法二用 ROW_NUMBER() OVER(PARTITION BY student_id ORDER BY class_date DESC) 编号取 rn=1。易错点：JOIN 回原表时同一学员同一天多条出勤会产生重复行；窗口写法要先过滤出勤状态再编号，否则最新一条可能是缺勤记录。

### 4. 参考解法

解法一：GROUP BY + MAX，再关联学员表

```sql
SELECT
    s.student_id AS `学员ID`,                            -- 学员维度
    s.student_name AS `学员姓名`,                         -- 学员姓名
    MAX(a.class_date) AS `最近上课日期`                    -- 每个学员出勤日期的最大值
FROM attendance a
INNER JOIN students s ON a.student_id = s.student_id      -- 关联学员表补姓名
WHERE a.checkin_status = '出勤'                           -- 缺勤/请假不算上课
  AND s.status = '在读'                                   -- 只看在读学员
GROUP BY s.student_id, s.student_name
ORDER BY `最近上课日期`;                                   -- 越久没上课的排越前，优先召回
```

结果解读：名单按"最久没来"升序排列，2003 号学员已一个多月未到课排在最前，班主任从顶部开始 7 天内完成回访即可覆盖全部高危学员。

解法二：窗口函数 ROW_NUMBER 取每人最新整行（含班级信息）

```sql
SELECT
    t.student_id AS `学员ID`,                            -- 学员
    t.student_name AS `学员姓名`,
    t.class_id AS `最近所上班级ID`,                       -- 窗口写法可同时保留整行信息
    t.class_date AS `最近上课日期`
FROM (
    SELECT
        s.student_id,                                    -- 学员ID
        s.student_name,                                  -- 姓名
        a.class_id,                                      -- 班级
        a.class_date,                                    -- 上课日期
        ROW_NUMBER() OVER (                              -- 每个学员内部按日期倒序编号
            PARTITION BY s.student_id
            ORDER BY a.class_date DESC
        ) AS rn
    FROM attendance a
    INNER JOIN students s ON a.student_id = s.student_id
    WHERE a.checkin_status = '出勤'                      -- 先过滤再编号，保证窗口内全是有效出勤
) t
WHERE t.rn = 1                                           -- 每人只保留最新一条
ORDER BY t.class_date;                                   -- 越久没上课的排越前
```

结果解读：相比解法一还能带出"最近上的是哪个班"，方便班主任直接定位课堂与授课老师；同一天多节课时 ROW_NUMBER 保证只取一行不重复，结果更干净。

### 5. 性能分析与优化

解法一聚合后行数=学员数，再与学员表 JOIN，代价低且稳定，是首选写法；解法二窗口函数需对分区排序，内存与临时文件开销高于聚合，千万级考勤表下更慢。具体优化建议：①attendance 对 (student_id, class_date) 建联合索引，解法一可借助松散索引扫描快速取每组最大值；②严格限定"近 90 天出勤"时加日期范围条件缩小扫描量；③高危名单每日跑批物化成 ads_dormant_students，班主任端直查结果表，避免高峰期实时计算。

### 6. 面试延伸考点

**问：MAX 写法 JOIN 回原表为什么会出重复行？怎么解决？** 回答要点：同一学员同一天在多个班出勤时 JOIN 条件命中多行；可改窗口写法一次取整行，或 JOIN 前先对 (student_id, class_date) 去重。

**问：ROW_NUMBER、RANK、DENSE_RANK 取最新记录时有什么区别？** 回答要点："只取一条"场景三者结果看似相同，但语义上必须用 ROW_NUMBER（强制唯一序号）；RANK 并列会出多行导致"取最新"变"取多条"，是常见笔误。

**问：怎么定义"沉睡学员"更科学？** 回答要点：结合排课密度而非固定天数——"连续 N 个应上课节次未出勤"比"14 天没来"更公平，因为周中班与周末班的排课密度不同，固定天数会误伤。

### 7. 业务拓展思考

最近上课时间是学员健康度最简单的信号，可与出勤率、作业提交率组成"活跃三件套"预警模型。联动动作包括沉睡学员自动分配召回任务、召回成功后赠送补课课时、对续班窗口期（结课前一个月）的活跃学员优先触达续班权益。口径延展上可输出"距上次上课天数"的分桶分布（0-7/8-14/15-30/30+ 天），让运营按桶配置差异化召回策略与话术，而非只盯单一阈值。

## EDU-10 各班级人数与满班状态

### 1. 业务背景

校区教务在排班和招生咨询时都需要一张班级容量台账：每个班现在多少在读学员、距离满员还有几个空位、状态是"可报名/即将满班/已满班"。课程顾问接待新学员时据此推荐班级，教务据此决定是否开新班、申请教室。班级人数来自班级学员关系表（在读状态），班级容量在班级表里，两表关联后还要按容量阈值给每个班打状态标签。**【加分点】**把聚合结果（人数）与维度字段（容量）比较后再用 CASE WHEN 打标，考察聚合与条件表达式叠加的综合运用，很多初学者会在这里卡壳或写出 ONLY_FULL_GROUP_BY 报错的 SQL。

### 2. 表结构说明

班级表 classes：

| 字段名 | 类型 | 含义 |
|---|---|---|
| class_id | BIGINT | 班级ID，主键 |
| class_name | VARCHAR(64) | 班级名称 |
| capacity | TINYINT | 满班容量（人） |
| campus_id | BIGINT | 所属校区ID |

示例数据：

| class_id | class_name | capacity | campus_id |
|---|---|---|---|
| 601 | 初一数学秋季3班 | 2 | 1 |
| 602 | 少儿编程入门B班 | 8 | 1 |
| 603 | 雅思强化晚班 | 6 | 2 |

班级学员关系表 class_students（一名学员在一个班一条关系）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| relation_id | BIGINT | 关系ID，主键 |
| class_id | BIGINT | 班级ID |
| student_id | BIGINT | 学员ID |
| status | VARCHAR(16) | 关系状态：在读/已结课/已退费 |
| join_date | DATE | 加入日期 |

示例数据：

| relation_id | class_id | student_id | status | join_date |
|---|---|---|---|---|
| 10001 | 601 | 2001 | 在读 | 2026-08-01 |
| 10002 | 601 | 2002 | 在读 | 2026-08-03 |
| 10003 | 601 | 2003 | 已退费 | 2026-08-05 |
| 10004 | 602 | 2004 | 在读 | 2026-09-01 |
| 10005 | 602 | 2009 | 在读 | 2026-09-02 |

### 3. 解题思路

先明确口径：①班级人数只统计关系状态为"在读"的学员，已结课与已退费不计入，这是当前时点快照口径；②满班规则按容量比例：人数≥容量为"已满班"，达到 80% 为"即将满班"，否则"可报名"；③人数与容量的比较发生在聚合之后，因此 CASE 判断的对象是聚合值。实现路径：解法一先在子查询按班级聚合人数，外层 JOIN 班级表后再 CASE 打标，逻辑最清晰；解法二一次 JOIN 后 GROUP BY，在 SELECT 里直接对 COUNT 结果做 CASE。易错点：一对多 JOIN 后用 COUNT(*) 会把关系行重复计数，必须 COUNT(DISTINCT student_id)；内连接会丢掉 0 人的新开班级。

### 4. 参考解法

解法一：子查询先算人数，外层 JOIN 后打状态标签

```sql
SELECT
    c.class_name AS `班级名称`,                          -- 班级名
    c.capacity AS `满班容量`,                             -- 容量来自维度表
    IFNULL(t.stu_cnt, 0) AS `在读人数`,                   -- 无在读学员的班补 0
    CASE
        WHEN IFNULL(t.stu_cnt, 0) >= c.capacity THEN '已满班'       -- 人数达到容量
        WHEN IFNULL(t.stu_cnt, 0) >= c.capacity * 0.8 THEN '即将满班' -- 达到八成容量
        ELSE '可报名'                                              -- 其余可继续招生
    END AS `满班状态`
FROM classes c
LEFT JOIN (
    SELECT
        class_id,                                        -- 班级维度
        COUNT(DISTINCT student_id) AS stu_cnt            -- 去重统计在读人数
    FROM class_students
    WHERE status = '在读'                                 -- 只算在读关系
    GROUP BY class_id
) t ON c.class_id = t.class_id
ORDER BY `满班状态`, `在读人数` DESC;                     -- 先按状态归类再看人数
```

结果解读：601 班 2/2 已满班、602 班 2/8 可报名；顾问看到"已满班"会推荐 602 或登记候补，"即将满班"标签还能制造稀缺感促进成交。

解法二：一次 JOIN 后 GROUP BY，SELECT 内对聚合值做 CASE

```sql
SELECT
    c.class_name AS `班级名称`,                                      -- 班级名
    COUNT(DISTINCT cs.student_id) AS `在读人数`,                      -- 关联后按学员去重计数
    CASE
        WHEN COUNT(DISTINCT cs.student_id) >= MAX(c.capacity) THEN '已满班'        -- 聚合值之间比较
        WHEN COUNT(DISTINCT cs.student_id) >= MAX(c.capacity) * 0.8 THEN '即将满班' -- 容量用 MAX 聚合包裹
        ELSE '可报名'
    END AS `满班状态`
FROM classes c
LEFT JOIN class_students cs
    ON cs.class_id = c.class_id
   AND cs.status = '在读'                                            -- 过滤放 ON，保留空班
GROUP BY c.class_id, c.class_name, c.capacity                        -- 分组键带上容量
ORDER BY `在读人数` DESC;
```

结果解读：单层查询完成全部逻辑、代码更短；容量经 MAX(c.capacity) 包裹后满足 ONLY_FULL_GROUP_BY 要求，可与人数量化比较，适合临时取数快速出结果。

### 5. 性能分析与优化

解法二只扫一遍关系表+一遍班级表，无派生表物化，通常更快；解法一的子查询结果集只有班级数级行、外层 JOIN 极轻，可读性更好，两者实际差距很小。具体优化建议：①class_students 对 (class_id, status, student_id) 建联合索引，可覆盖分组计数；②两表按 class_id 组织索引时 JOIN 走 ref，代价可控；③满班状态变化低频，可每日跑批把状态冗余进班级表，前端与顾问工作台直查，免去实时计算。

### 6. 面试延伸考点

**问：COUNT(*)、COUNT(1)、COUNT(DISTINCT student_id) 在本题的区别？** 回答要点：一对多 JOIN 后 COUNT(*) 与 COUNT(1) 都按关系行计数，同一学员多条关系会被重复计入；必须 COUNT(DISTINCT student_id) 按学员去重，这是本题最核心的坑。

**问：为什么解法二里容量要写 MAX(c.capacity)？** 回答要点：ONLY_FULL_GROUP_BY 模式下 SELECT 只允许分组键与聚合值；capacity 虽函数依赖于 class_id，但 MySQL 不做函数依赖推断，需加入 GROUP BY 或用 MAX 包裹。

**问：空班（无在读学员）为什么必须 LEFT JOIN？** 回答要点：内连接会让 0 人的新开班从报表消失，而这些班恰恰最需要招生曝光；LEFT JOIN + IFNULL 补 0 才是完整台账。

### 7. 业务拓展思考

满班状态台账连接招生与排班两侧：临近满班的班级要提前申请开新班并锁定教室与老师，长期不满班的老班要评估合并、调价或加大投放。口径延展上可计算"满班率=在读人数/容量"作为教室利用效率指标，按校区汇总后与租金成本对照；也可增加"本周新增人数"观察班级增长速度，识别爆款班级提前扩容，避免因满班拒收而流失意向学员。

## EDU-11 直播课到课人数与到课率

### 1. 业务背景

在线教育的直播大班课每次开播后都要复盘到课情况：该场直播应到多少学员（该课程已支付的在读学员数）、实际到课多少、到课率多少。到课率直接反映课程吸引力与提醒触达效果，低于阈值的场次要复盘开播时间、标题、讲师与提醒链路；未到课名单还会回流给班主任做 48 小时内二次触达。运营每周汇总各场直播的到课率排名，作为后续排期优化的依据。**【避坑指南】**到课率的分母是"应到人数"（课程已支付学员数）而不是平台推流触达数，两者口径混用是新人最常见的错误；同时到课人数必须按学员去重，重复进出直播间不能重复计数。

示例数据：

示例数据：

报名订单表 orders（复用 EDU-03 结构，取关键字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |

| pay_status | TINYINT | 1已支付，0未支付 |

示例数据：

| order_id | student_id | course_id | pay_status |
|---|---|---|---|
| 3001 | 2001 | 11 | 1 |
| 3002 | 2002 | 11 | 1 |
| 3003 | 2003 | 11 | 1 |
| 3004 | 2004 | 12 | 1 |
| 3005 | 2005 | 12 | 0 |

### 3. 解题思路

先明确口径：①应到人数 = 该课程 pay_status=1 的去重学员数（学员重复下单按人去重）；②到课人数 = 到课记录表按场次去重学员数；③到课率 = 到课/应到，分母可能为 0（无报名的测试场），需 NULLIF 防除零。实现路径：解法一先 LEFT JOIN 到课聚合，应到人数用相关子查询按课程取数，写法直观；解法二把到课、报名分别聚合成子查询再 JOIN，纯集合写法性能更好。易错点：忘记 COUNT(DISTINCT) 导致重复进出被多次计数；应到人数把未支付订单也算进去；分母为 0 直接做除法得到 NULL 或报错且未做业务兜底。

### 4. 参考解法

解法一：JOIN 到课聚合 + 相关子查询取应到人数

```sql
SELECT
    l.lesson_id AS `场次ID`,                             -- 直播场次
    l.lesson_title AS `直播标题`,
    COUNT(DISTINCT j.student_id) AS `到课人数`,           -- 重复进出按学员去重
    (SELECT COUNT(DISTINCT o.student_id)                 -- 应到：该课程已支付去重学员数
       FROM orders o
      WHERE o.course_id = l.course_id
        AND o.pay_status = 1) AS `应到人数`,
    ROUND(COUNT(DISTINCT j.student_id) /
          NULLIF((SELECT COUNT(DISTINCT o.student_id)   -- 再次引用子查询算比率
                   FROM orders o
                  WHERE o.course_id = l.course_id
                    AND o.pay_status = 1), 0) * 100, 2) AS `到课率_百分比` -- NULLIF 防除零
FROM live_lessons l
LEFT JOIN live_join_records j
    ON j.lesson_id = l.lesson_id                         -- 左连接：无人到课也保留场次
GROUP BY l.lesson_id, l.lesson_title, l.course_id        -- course_id 供相关子查询使用
ORDER BY l.live_date;                                    -- 按直播日期排序
```

结果解读：场次 21 到课率 100%、场次 22 为 66.67%（学员 2003 缺席）、场次 23 仅 1 人报名且未到课为 0%，运营应优先触达 2003 并复盘场次 23 的提醒链路。

解法二：到课与报名分别聚合后 JOIN（纯集合写法）

```sql
SELECT
    l.lesson_title AS `直播标题`,                                   -- 场次信息
    IFNULL(j.join_cnt, 0) AS `到课人数`,                             -- 无人到课补 0
    e.expect_cnt AS `应到人数`,                                      -- 课程维度应到数
    ROUND(IFNULL(j.join_cnt, 0) / NULLIF(e.expect_cnt, 0) * 100, 2) AS `到课率_百分比` -- 防除零
FROM live_lessons l
LEFT JOIN (
    SELECT lesson_id, COUNT(DISTINCT student_id) AS join_cnt        -- 到课：按场次去重
    FROM live_join_records
    GROUP BY lesson_id
) j ON l.lesson_id = j.lesson_id                                    -- 场次关联到课聚合
LEFT JOIN (
    SELECT course_id, COUNT(DISTINCT student_id) AS expect_cnt      -- 应到：按课程去重已支付学员
    FROM orders
    WHERE pay_status = 1                                            -- 排除未支付
    GROUP BY course_id
) e ON l.course_id = e.course_id                                    -- 课程关联应到聚合
ORDER BY `到课率_百分比`;                                            -- 从差到好排，优先复盘
```

结果解读：每个子查询只聚合一次再 JOIN，语义清晰、无重复计算；到课率从低到高排列，排在尾部的场次连同未到课名单一起交给班主任做召回。

### 5. 性能分析与优化

解法一的相关子查询在 MySQL 8.0 中可能被优化器改写为 JOIN，但同一子查询被引用两次仍可能重复执行，数据量大时不如解法二稳定；解法二每个子查询只聚合一次，再以小结果集 JOIN，代价更低。具体优化建议：①live_join_records 对 (lesson_id, student_id) 建联合索引，去重计数可走索引；②orders 对 (course_id, pay_status, student_id) 建联合索引，覆盖应到人数计算；③按场次预聚合到 dws_live_lesson_stat（到课人数、应到人数、到课率），看板直读汇总层，明细层只在下钻时才查。

### 6. 面试延伸考点

**问：为什么到课人数必须 COUNT(DISTINCT)？** 回答要点：学员可能中途退出再进入产生多条记录，不去重人数会翻倍；若业务定义"观看满 10 分钟才算有效到课"，还要叠加时长条件后再去重。

**问：分母为 0 的场次怎么处理？** 回答要点：用 NULLIF(分母,0) 让结果为 NULL 而不是报错，报表端显示"—"，语义上比 0% 更准确；也要在口径文档中说明测试场不计入考核。

**问：到课率低一定是课程问题吗？** 回答要点：先看提醒触达（短信/企微到达率）、开播时间与学员时段偏好、报名到开课间隔，先归因运营再归因内容，避免误伤教研。

### 7. 业务拓展思考

到课率是线上课交付质量的第一指标，向下游可串联"到课→完课→作业→续费"漏斗，向上游可反推报名后的激活动作（开课提醒、预习资料、班级群预热）是否到位。联动动作包括对未到课学员自动触发回放推送与班主任跟进、把到课率纳入讲师与班主任双线考核。口径延展上可定义"有效到课"（观看满 15 分钟）与"完课率"，并按课程类型（体验课/正课/公开课）分别设阈值，避免一刀切考核引发数据游戏。

## EDU-12 各课程评分分布

### 1. 业务背景

结课后学员会对课程打 1-5 分，教学质量团队每月要看每个课程的评分结构：多少好评（4-5 分）、中评（3 分）、差评（1-2 分），并计算好评率。评分分布比平均分信息量更大——平均 4.2 分的两个课程，一个评分集中在 4-5 分、一个两极分化，教研动作完全不同。差评明细要回流给教研做内容修订，好评则提炼为转介绍话术素材。**【面试高频】**CASE WHEN 分档 + 占比计算是评价类数据的标准处理范式，笔试常以"算好评率"的形式出现，分档边界与分母口径是得分关键。

### 2. 表结构说明

课程评分表 course_reviews：

| 字段名 | 类型 | 含义 |
|---|---|---|
| review_id | BIGINT | 评价ID，主键 |
| course_id | BIGINT | 课程ID |
| student_id | BIGINT | 学员ID |
| score | TINYINT | 评分 1-5 分 |
| created_at | DATETIME | 评价时间 |

示例数据：

| review_id | course_id | student_id | score | created_at |
|---|---|---|---|---|
| 12001 | 11 | 2001 | 5 | 2026-10-20 10:00:00 |
| 12002 | 11 | 2002 | 4 | 2026-10-21 11:30:00 |
| 12003 | 11 | 2003 | 2 | 2026-10-22 09:15:00 |
| 12004 | 12 | 2004 | 3 | 2026-10-23 14:40:00 |
| 12005 | 12 | 2009 | 1 | 2026-10-24 20:05:00 |

课程表 courses（复用，补课程名）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| course_id | BIGINT | 课程ID，主键 |
| course_name | VARCHAR(128) | 课程名称 |
| category | VARCHAR(32) | 课程品类 |

示例数据：

| course_id | course_name | category |
|---|---|---|
| 11 | 初一数学秋季班 | K12学科 |
| 12 | 成人Python入门 | 职业考证 |

### 3. 解题思路

先明确口径：①分档规则：4-5 分好评、3 分中评、1-2 分差评，边界必须先写清；②好评率 = 好评数 / 总评价数，评价通常是小样本，必须同时输出评价数供判断显著性；③只统计 score 在 1-5 之间的有效评价，NULL 与越界值剔除或单列。实现路径：解法一行式明细——按课程×评分档 GROUP BY 输出长表，适合接 BI 与下钻；解法二列式——每门课一行，布尔条件拆列统计各档数量与好评率，适合汇报。易错点：CASE 分档遗漏 ELSE 导致越界值落入 NULL 档；好评率分母漏掉差评；小样本课程好评率 100% 参与排名误导决策。

### 4. 参考解法

解法一：行式分档明细（课程 × 评分档）

```sql
SELECT
    c.course_name AS `课程名称`,                            -- 课程名
    CASE
        WHEN score BETWEEN 4 AND 5 THEN '好评'              -- 4-5 分归好评
        WHEN score = 3 THEN '中评'                          -- 3 分归中评
        WHEN score BETWEEN 1 AND 2 THEN '差评'              -- 1-2 分归差评
        ELSE '异常分'                                       -- 越界值兜底
    END AS `评价档位`,
    COUNT(*) AS `评价数`                                    -- 每档计数
FROM course_reviews r
INNER JOIN courses c ON r.course_id = c.course_id          -- 关联课程名
WHERE r.score BETWEEN 1 AND 5                              -- 只保留有效评分
GROUP BY c.course_name,
         CASE
             WHEN score BETWEEN 4 AND 5 THEN '好评'
             WHEN score = 3 THEN '中评'
             WHEN score BETWEEN 1 AND 2 THEN '差评'
             ELSE '异常分'
         END                                               -- 按课程与档位联合分组
ORDER BY c.course_name, `评价档位`;                         -- 课程内按档位排序
```

结果解读：长表结构便于接入 BI 与继续下钻；课程 11 好评 2 条、差评 1 条，课程 12 中差评居多，教研应优先复核课程 12 的内容难度与讲师表现。

解法二：列式汇总 + 好评率（每课一行）

```sql
SELECT
    c.course_name AS `课程名称`,                             -- 课程名
    COUNT(*) AS `总评价数`,                                  -- 分母：全部有效评价
    SUM(r.score >= 4) AS `好评数`,                           -- 4 分及以上即好评
    SUM(r.score <= 2) AS `差评数`,                           -- 2 分及以下即差评
    ROUND(AVG(r.score), 2) AS `平均分`,                      -- 均分作辅助参考
    ROUND(SUM(r.score >= 4) / COUNT(*) * 100, 2) AS `好评率_百分比` -- 好评占比
FROM course_reviews r
INNER JOIN courses c ON r.course_id = c.course_id
WHERE r.score BETWEEN 1 AND 5                               -- 有效评分范围
GROUP BY c.course_id, c.course_name
HAVING COUNT(*) >= 3                                        -- 评价数过少的课程不参与排名
ORDER BY `好评率_百分比` DESC;
```

结果解读：一课一行的宽表适合汇报；课程 12 只有 2 条评价被 HAVING 过滤，样本不足暂不参与排名，避免"2 条评价全 5 星"这类偶然结果误导决策。

### 5. 性能分析与优化

两种写法同为一次 JOIN + 单趟聚合，代价几乎一致；解法一 GROUP BY 中的 CASE 表达式重复书写、维护成本高，解法二更简洁。具体优化建议：①course_reviews 对 (course_id, score) 建联合索引即可覆盖本题全部聚合；②评分表增长快，按月分区并只聚合近 N 月；③好评率与评价数一起预聚合到 dws_course_rating_daily，看板层不再扫明细，同时保留差评明细表供教研下钻。

### 6. 面试延伸考点

**问：平均分相同的两个课程，为什么还要看分布？** 回答要点：均值会掩盖两极分化，4.2 分可能来自均匀打分也可能是 5 星与 1 星对冲；分布与离散度才能区分"普遍满意"与"体验不稳定"，对应完全不同的教研动作。

**问：SUM(r.score >= 4) 这种布尔求和写法有什么风险？** 回答要点：仅 MySQL 等少数方言支持，可移植性差；score 为 NULL 时表达式为 NULL、SUM 会忽略该行，导致分子分母不一致，应先用 WHERE 过滤 NULL 保证口径一致。

**问：如何识别与处理"刷好评"？** 回答要点：从评价时间聚集度、学员无对应上课记录、文本高度重复等特征识别，建模剔除后再计算；指标可信度比指标好看更重要。

### 7. 业务拓展思考

评分分布是教学质量的外部体温计，差评率上升应先于投诉被感知。联动动作包括差评学员 24 小时内教研回访、好评学员自动推送转介绍激励、评分与续费率交叉验证课程口碑。口径延展上可细分到讲师维度（同一课程不同老师评分差异）、按开班批次追踪评分趋势，定位是内容问题还是交付问题；也可引入 NPS（净推荐值）替代单一星级，提升指标对口碑的解释力。

## EDU-13 报名金额Top10学员

### 1. 业务背景

销售总监每月要公布"学习投入榜"：累计报名金额最高的 10 名学员。这份名单有三个用途：一是给大客户（高投入家长/企业团购）匹配专属顾问做深度服务；二是作为老带新活动的种子用户——高投入学员的转介绍意愿与能力最强；三是监控订单异常，单人金额突增可能对应刷单或内部测试单。数据来自报名订单表按学员汇总实付金额后排序取前 10。**【加分点】**"先聚合排序取 TopN，再回表补明细字段"的两段式写法，以及"金额并列时 LIMIT 截断不稳定"的边界意识，都是面试官想听到的亮点。

### 2. 表结构说明

报名订单表 orders（复用 EDU-03 结构）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| amount | DECIMAL(10,2) | 实付金额（元） |
| pay_status | TINYINT | 1已支付，0未支付 |
| created_at | DATETIME | 下单时间 |

示例数据：

| order_id | student_id | course_id | amount | pay_status | created_at |
|---|---|---|---|---|---|
| 13001 | 2001 | 11 | 3600.00 | 1 | 2026-09-01 10:00:00 |
| 13002 | 2001 | 12 | 1980.00 | 1 | 2026-09-10 14:20:00 |
| 13003 | 2002 | 11 | 3200.00 | 1 | 2026-09-12 09:05:00 |
| 13004 | 2003 | 13 | 899.00 | 0 | 2026-09-15 16:40:00 |
| 13005 | 2002 | 13 | 1299.00 | 1 | 2026-09-20 11:10:00 |

学员表 students：

| 字段名 | 类型 | 含义 |
|---|---|---|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(64) | 学员姓名 |
| phone | VARCHAR(20) | 联系电话 |
| city | VARCHAR(32) | 所在城市 |

示例数据：

| student_id | student_name | phone | city |
|---|---|---|---|
| 2001 | 陈小明 | 138****1001 | 北京 |
| 2002 | 周小雨 | 139****1002 | 北京 |
| 2003 | 吴同学 | 137****1003 | 上海 |

### 3. 解题思路

先明确口径：①只累计 pay_status=1 的已支付订单实付金额，未支付与已取消剔除；②按学员去重汇总（一人多单求和），再按金额降序取前 10；③姓名、电话等明细字段在学员表，应在聚合出 Top10 之后再关联，避免大表过早 JOIN。实现路径：解法一一步到位，JOIN 后分组、排序、LIMIT；解法二先在子查询里聚合出 Top10 的学员与金额，再 JOIN 学员表补姓名。**【避坑指南】**LIMIT 10 在金额并列处会"随机"截断，结果不稳定，严肃场景应改用窗口函数 RANK() 让并列者都保留；忘记过滤未支付订单则会让 899 元的未支付学员错误上榜。

### 4. 参考解法

解法一：JOIN + GROUP BY + ORDER BY + LIMIT 一步到位

```sql
SELECT
    s.student_id AS `学员ID`,                            -- 学员维度
    s.student_name AS `学员姓名`,                         -- 姓名
    s.city AS `城市`,                                    -- 城市
    SUM(o.amount) AS `累计实付金额`                        -- 多笔订单金额求和
FROM orders o
INNER JOIN students s ON o.student_id = s.student_id      -- 一次 JOIN 补齐姓名城市
WHERE o.pay_status = 1                                    -- 只算已支付订单
GROUP BY s.student_id, s.student_name, s.city             -- 按学员分组
ORDER BY `累计实付金额` DESC                               -- 金额降序
LIMIT 10;                                                 -- 取前 10 名
```

结果解读：2001 号学员两单合计 5580 元登顶、2002 号 4499 元紧随，两人均有联报行为；榜单可导出给顾问分配专属服务，城市分布可辅助线下活动选址。

解法二：先聚合取 Top10，再 JOIN 补明细（两段式）

```sql
SELECT
    t.student_id AS `学员ID`,                            -- 子查询筛出的学员
    s.student_name AS `学员姓名`,                         -- 关联补姓名
    t.total_amt AS `累计实付金额`                          -- 子查询算好的金额
FROM (
    SELECT
        student_id,                                      -- 学员维度
        SUM(amount) AS total_amt                         -- 金额合计
    FROM orders
    WHERE pay_status = 1                                 -- 过滤未支付
    GROUP BY student_id                                  -- 按学员聚合
    ORDER BY total_amt DESC                              -- 子查询内先排序
    LIMIT 10                                             -- 截取前 10
) t
INNER JOIN students s ON t.student_id = s.student_id      -- 小结果集再关联明细
ORDER BY t.total_amt DESC;                                -- 最终顺序保持降序
```

结果解读：先在订单表内完成"聚合+截断"，参与 JOIN 的只有 10 行，订单表巨大时明显优于解法一；两段式也更贴近"明细层→汇总层→应用层"的数仓加工习惯。

### 5. 性能分析与优化

解法一 JOIN 的中间结果为"订单×学员"明细，订单表越大越亏；解法二把聚合与截断下推到子查询，JOIN 阶段只有 10 行数据，大表下优势明显。具体优化建议：①orders 对 (pay_status, student_id, amount) 建联合索引，聚合可在索引上覆盖完成；②榜单只看当月时加 created_at 范围条件；③高投入学员名单变化慢，可每日跑批物化；④需要处理并列时改用窗口写法：RANK() OVER(ORDER BY SUM(amount) DESC) 后取 rk <= 10。

### 6. 面试延伸考点

**问：第 10、11 名金额相同，LIMIT 10 会怎样？** 回答要点：数据库返回其中任意一个，结果不稳定；严肃场景应改用 RANK() OVER(ORDER BY 金额 DESC) 取 rk <= 10，让并列者全部保留，规则可预期。

**问：为什么必须先 GROUP BY 再取 TopN，而不是先 LIMIT？** 回答要点：榜单主体是"学员累计金额"而非单笔订单，直接对明细 LIMIT 得到的是"单笔最贵的 10 笔订单"；必须先聚合到学员粒度再排序截断，语义才正确。

**问：大客户名单按金额还是按利润排？** 回答要点：金额只反映投入，大班课与一对一毛利差异大；运营上建议叠加上课消耗与退费记录看净贡献，避免把"高金额低毛利"的客户误判为优质客户。

### 7. 业务拓展思考

高投入学员是机构最稀缺的资产，名单必须转化为动作：专属顾问一对一服务、新品内测邀请、老带新激励包。口径延展上可从"累计金额"升级为"累计净金额（扣除退费）"与"近 90 天活跃投入"，避免把已退费大客户当成种子用户；再与上课频次交叉，区分"高投入高活跃"的真粉丝与"高投入低活跃"的流失风险户，两类人群的服务策略完全不同。

## EDU-14 各校区在读学员数排名

### 1. 业务背景

区域总监每月例会要看各校区的在读学员规模排名，用于资源分配（师资编制、市场预算向头部校区倾斜同时扶持腰部校区）、评估新校区爬坡进度，以及识别规模持续下滑需要整改的校区。学员分布在学员表，校区名称在校区表，两表关联后按校区汇总在读人数并排名。排名本身不难，但"并列名次怎么处理"与"规模要和增长率、满班率同看"是面试与实务的分水岭。**【面试高频】**GROUP BY 汇总 + 排序是基本功必考题，能否顺手指出现代写法窗口函数 RANK 并说清三种排名函数的区别，是明显的加分项。

### 2. 表结构说明

校区表 campuses：

| 字段名 | 类型 | 含义 |
|---|---|---|
| campus_id | BIGINT | 校区ID，主键 |
| campus_name | VARCHAR(64) | 校区名称 |
| city | VARCHAR(32) | 所在城市 |
| open_date | DATE | 开业日期 |

示例数据：

| campus_id | campus_name | city | open_date |
|---|---|---|---|
| 1 | 北京海淀校区 | 北京 | 2020-09-01 |
| 2 | 上海浦东校区 | 上海 | 2021-03-15 |
| 3 | 广州天河校区 | 广州 | 2022-06-01 |

学员表 students（复用，取关键字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(64) | 学员姓名 |
| campus_id | BIGINT | 所属校区ID |
| status | VARCHAR(16) | 状态：在读/结课/退费 |

示例数据：

| student_id | student_name | campus_id | status |
|---|---|---|---|
| 2001 | 陈小明 | 1 | 在读 |
| 2002 | 周小雨 | 1 | 在读 |
| 2003 | 吴同学 | 2 | 在读 |
| 2004 | 郑同学 | 2 | 退费 |
| 2005 | 冯同学 | 3 | 在读 |

### 3. 解题思路

先明确口径：①"在读学员数"只统计 status='在读'，退费与结课剔除，不能拿"累计招生数"冒充"在读"；②排名规则要声明：人数相同是并列同名次（RANK）还是强制顺序（ROW_NUMBER），默认按 RANK；③LEFT JOIN 保留 0 人的校区（新开业校区可能尚未招生）。实现路径：解法一 JOIN 后 GROUP BY 汇总再 ORDER BY 完成基础排名；解法二在汇总结果上叠加 RANK() OVER 窗口函数输出名次列。易错点：内连接丢掉 0 人校区；LEFT JOIN 时把状态过滤误写进 WHERE 导致 0 人校区被过滤；只报规模不看增速导致误判经营趋势。

### 4. 参考解法

解法一：JOIN + GROUP BY + ORDER BY 基础排名

```sql
SELECT
    cp.campus_name AS `校区名称`,                        -- 校区名
    cp.city AS `城市`,                                   -- 城市
    COUNT(s.student_id) AS `在读学员数`                   -- LEFT JOIN 下无学员自然计 0
FROM campuses cp
LEFT JOIN students s
    ON s.campus_id = cp.campus_id
   AND s.status = '在读'                                 -- 状态过滤放 ON，保留 0 人校区
GROUP BY cp.campus_id, cp.campus_name, cp.city           -- 按校区分组
ORDER BY `在读学员数` DESC, cp.campus_name;               -- 人数降序，同数按名称稳定输出
```

结果解读：北京海淀 2 人领先，上海浦东与广州天河各 1 人并列；即使某校区 0 人也会出现在台账里，适合作为例会基础报表与后续增长率计算的底表。

解法二：窗口函数 RANK 输出并列名次

```sql
SELECT
    t.campus_name AS `校区名称`,                         -- 校区名
    t.stu_cnt AS `在读学员数`,                            -- 汇总人数
    RANK() OVER (ORDER BY t.stu_cnt DESC) AS `名次`       -- 并列同名次，后续名次跳号
FROM (
    SELECT
        cp.campus_name,                                  -- 校区维度
        COUNT(s.student_id) AS stu_cnt                   -- 在读人数
    FROM campuses cp
    LEFT JOIN students s
        ON s.campus_id = cp.campus_id
       AND s.status = '在读'
    GROUP BY cp.campus_id, cp.campus_name
) t
ORDER BY `名次`, t.campus_name;                          -- 先按名次再按名称
```

结果解读：RANK 让并列校区共享名次（两个第 2 名之后直接是第 4 名），比手工排序更符合"榜单"语义；若业务要求绝不并列，换成 ROW_NUMBER 即可。

### 5. 性能分析与优化

两解法主体都是一次 LEFT JOIN + 分组计数，校区数只有几十个，窗口函数开销可忽略，性能差异极小。具体优化建议：①students 对 (campus_id, status) 建联合索引，状态过滤与分组都能走索引；②校区表极小，JOIN 代价可忽略；③需要历史趋势时，按月快照在读人数写入 dws_campus_monthly_snapshot，排名与环比都从快照表取，避免每次扫学员全表，也天然保留历史名次变化。

### 6. 面试延伸考点

**问：RANK、DENSE_RANK、ROW_NUMBER 在排名上的区别？** 回答要点：并列时 RANK 跳号（1,2,2,4），DENSE_RANK 不跳号（1,2,2,3），ROW_NUMBER 强制唯一（1,2,3,4）；榜单业务通常选 RANK，需要唯一序号时选 ROW_NUMBER。

**问：为什么状态过滤写 ON 而不是 WHERE？** 回答要点：LEFT JOIN 下 WHERE 中的右表条件会把右表为 NULL 的行过滤掉，0 人校区消失；写在 ON 上只影响匹配结果不影响行的保留，这是 LEFT JOIN 的核心规则。

**问：规模排名之外还应看什么？** 回答要点：环比净增、满班率、续费率与坪效，规模大不代表健康；例会建议"规模+增速+质量"三列同看，避免单指标误导资源分配。

### 7. 业务拓展思考

校区排名是资源调度地图：头部校区要防满班瓶颈（扩容或分流），尾部校区要诊断是选址、师资还是本地投放问题。联动动作包括按排名动态调整市场预算系数、新校区爬坡期设置独立考核阈值、对连续两季度下滑的校区启动专项整改。口径延展上可拆解"在读=期初在读+本月新增-本月流失"做流量归因，或按城市上卷看区域集中度，为开城/关城决策提供依据。

## EDU-15 每个老师带过的学员数

### 1. 业务背景

师资盘点时教学主管需要回答：每位老师累计带过多少名学员。这个数字用于师资介绍页包装（"累计服务 800+ 学员"）、老师等级评定（带教人数是晋升硬指标之一），也用于排课风险评估——带学员过多的老师一旦流失影响面巨大，需要提前配助手或分班分流。学员通过班级与老师产生关系：一个老师带多个班，一个学员可能先后进入同一老师的多个班，统计"带过的学员数"必须按学员去重。**【避坑指南】**三表 JOIN 后直接 COUNT(*) 会把"同一学员报了同老师两个班"重复计数，COUNT(DISTINCT student_id) 是本题的灵魂，也是多表 JOIN 统计类题目的通用铁律。

### 2. 表结构说明

教师表 teachers：

| 字段名 | 类型 | 含义 |
|---|---|---|
| teacher_id | BIGINT | 教师ID，主键 |
| teacher_name | VARCHAR(64) | 教师姓名 |
| subject | VARCHAR(32) | 主教学科 |

示例数据：

| teacher_id | teacher_name | subject |
|---|---|---|
| 901 | 王老师 | 数学 |
| 902 | 李老师 | 编程 |
| 903 | 张老师 | 英语 |

班级表 classes（复用，取关键字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| class_id | BIGINT | 班级ID，主键 |
| class_name | VARCHAR(64) | 班级名称 |
| teacher_id | BIGINT | 授课教师ID |

示例数据：

| class_id | class_name | teacher_id |
|---|---|---|
| 601 | 初一数学秋季3班 | 901 |
| 602 | 初二数学秋季1班 | 901 |
| 603 | 少儿编程入门A班 | 902 |

班级学员关系表 class_students（复用）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| relation_id | BIGINT | 关系ID，主键 |
| class_id | BIGINT | 班级ID |
| student_id | BIGINT | 学员ID |
| status | VARCHAR(16) | 关系状态：在读/已结课/已退费 |

示例数据：

| relation_id | class_id | student_id | status |
|---|---|---|---|
| 15001 | 601 | 2001 | 在读 |
| 15002 | 601 | 2002 | 在读 |
| 15003 | 602 | 2001 | 在读 |
| 15004 | 602 | 2003 | 已结课 |
| 15005 | 603 | 2004 | 在读 |

### 3. 解题思路

先明确口径：①"带过"= 曾经建立教学关系，含已结课与已退费学员（历史累计口径）；若只要"目前在带"则过滤 status='在读'，面试必须先声明口径，本题按历史累计；②关系链是 老师→班级→学员 的两跳 JOIN；③计数必须 COUNT(DISTINCT student_id)。实现路径：解法一三表 JOIN 一气呵成、分组去重计数；解法二先在子查询里 DISTINCT 出"老师×学员"唯一关系对，外层再简单计数，在关系数据存在重复时更抗错。易错点：COUNT(*) 与 COUNT(DISTINCT) 混淆导致虚增；JOIN 链中任一环节的状态过滤位置不同会造成口径漂移；忘记处理没有带班记录的老师。

### 4. 参考解法

解法一：三表 JOIN + COUNT(DISTINCT) 直接去重

```sql
SELECT
    t.teacher_id AS `教师ID`,                                -- 老师维度
    t.teacher_name AS `教师姓名`,                             -- 老师姓名
    COUNT(DISTINCT cs.student_id) AS `带过学员数`              -- 关键：按学员去重
FROM teachers t
INNER JOIN classes c          ON c.teacher_id = t.teacher_id  -- 第一跳：老师 → 其班级
INNER JOIN class_students cs  ON cs.class_id  = c.class_id    -- 第二跳：班级 → 学员关系
GROUP BY t.teacher_id, t.teacher_name
ORDER BY `带过学员数` DESC;                                    -- 按带教人数降序
```

结果解读：901 号王老师两个班去重后带过 3 名学员（2001 在两个班重复只计一次），带教集中度一目了然，可用于流失风险评估与教师主页宣传包装。

解法二：先 DISTINCT 出"老师-学员"对，再计数（先去重后聚合）

```sql
SELECT
    pair.teacher_name AS `教师姓名`,                         -- 老师姓名
    COUNT(*) AS `带过学员数`                                  -- 关系对已去重，直接计数
FROM (
    SELECT DISTINCT
        t.teacher_id,                                        -- 去重核心：老师×学员唯一化
        t.teacher_name,
        cs.student_id
    FROM teachers t
    INNER JOIN classes c          ON c.teacher_id = t.teacher_id -- 老师到班级
    INNER JOIN class_students cs  ON cs.class_id  = c.class_id   -- 班级到学员
) pair
GROUP BY pair.teacher_name
ORDER BY `带过学员数` DESC;                                   -- 按带教人数降序
```

结果解读：子查询先物化"老师×学员"唯一关系对，外层简单 COUNT 即可；即使关系表存在历史重复数据也不会虚增，"先清洗后聚合"的结构在复杂数据源下更抗错。

### 5. 性能分析与优化

解法一在 GROUP BY 内做 DISTINCT，MySQL 通常借助临时表去重，数据量大时开销高于普通计数；解法二多一层派生表物化但逻辑等价，性能差异不大，主要差别在可读性与抗脏数据能力。具体优化建议：①classes 对 (teacher_id, class_id)、class_students 对 (class_id, student_id) 建联合索引，两跳 JOIN 全程走索引；②带教学员数低频变化，按月跑批写入 dws_teacher_stat 汇总表；③若只统计在读口径，把 status='在读' 放在 JOIN 条件里先过滤，减少参与去重的行数。

### 6. 面试延伸考点

**问：COUNT(DISTINCT) 大数据量下为什么慢？有什么替代方案？** 回答要点：去重需要暂存中间结果（临时表/内存），千万级明显变慢；可先按 student_id GROUP BY 预去重再计数，或上游按"老师-学员"粒度预聚合，近似统计可用 HyperLogLog（如 Presto 的 approx_distinct）。

**问：老师 A 在两个校区都带课，怎么拆分统计？** 回答要点：在 JOIN 链中引入班级所属校区字段，按 (teacher_id, campus_id) 分组；同时要确认同一学员跨校区是否仍按人去重，口径不同结果不同。

**问："带过"与"实际上过课"有什么区别？** 回答要点：关系存在但学员可能从未出勤；严谨口径应 JOIN 考勤表限定有出勤记录的学员，两个口径都要能说清并注明用途。

### 7. 业务拓展思考

带教学员数是老师影响力与风险的量化：宣传侧用它建立信任（教师主页、招生海报），管理侧用它做师生比监控与单点依赖预警——某老师带教学员占比超过 20% 就应启动备份师资计划。口径延展上可计算"人均带教收入"（学员实付/老师人数）衡量师资创收能力，或追踪学员随老师的流转率（续班时是否指定同一老师），为师徒制培养与教研组建设提供数据支撑。
