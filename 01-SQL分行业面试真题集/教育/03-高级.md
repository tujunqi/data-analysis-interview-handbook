## EDU-31 线索-试听-报名-续费全漏斗分渠道转化分析

### 1. 业务背景

某K12机构市场部在抖音、美团、地推、转介绍四个渠道持续投放，线索进入CRM后由销售顾问跟进：先约试听课，试听满意后购买正价课，课程到期前再谈续费。市场总监在季度经营会上需要一张"分渠道全漏斗表"：每个渠道各有多少线索、多少试听、多少报名、多少续费，以及相邻环节的转化率，用来判断"哪个渠道量小但质高、哪个渠道量大但漏得厉害"，从而决定下季度预算向哪个渠道倾斜、哪个渠道的线索要重点培训顾问的承接话术。**【面试高频】**全漏斗是教培数据分析的第一道大题，考察的不是JOIN语法而是"漏斗口径"：四层实体不同（线索→试听→订单→续费订单），必须先定义每一层的去重主体和归属渠道规则，再谈实现。

### 2. 表结构说明

leads（线索表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | BIGINT | 线索ID，主键 |
| channel | VARCHAR(32) | 获客渠道：抖音/美团/地推/转介绍 |
| student_key | VARCHAR(64) | 学员唯一键（手机号哈希） |
| created_at | DATETIME | 线索创建时间 |
| trial_date | DATE | 首次试听日期，NULL表示未试听 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |
| order_type | VARCHAR(16) | 订单类型：正价课/续费 |
| amount | DECIMAL(10,2) | 订单金额 |
| pay_date | DATE | 支付日期 |

示例数据：

leads：

| lead_id | channel | student_key | created_at | trial_date |
|---------|---------|-------------|------------|------------|
| 1 | 抖音 | stu_001 | 2024-06-01 10:00:00 | 2024-06-03 |
| 2 | 抖音 | stu_002 | 2024-06-02 11:00:00 | NULL |
| 3 | 美团 | stu_003 | 2024-06-03 09:00:00 | 2024-06-05 |
| 4 | 地推 | stu_004 | 2024-06-05 14:00:00 | 2024-06-06 |
| 5 | 转介绍 | stu_005 | 2024-06-08 16:00:00 | 2024-06-10 |

orders：

| order_id | student_key | order_type | amount | pay_date |
|----------|-------------|------------|--------|----------|
| 901 | stu_001 | 正价课 | 5800.00 | 2024-06-04 |
| 902 | stu_003 | 正价课 | 7200.00 | 2024-06-06 |
| 903 | stu_004 | 正价课 | 3600.00 | 2024-06-07 |
| 904 | stu_005 | 正价课 | 8800.00 | 2024-06-11 |
| 905 | stu_005 | 续费 | 8800.00 | 2024-12-11 |

### 3. 解题思路

先定口径再动手，这是漏斗题拿到高分的前提。第一层"线索"：以lead_id计数，渠道直接取leads.channel；第二层"试听"：trial_date IS NOT NULL的线索数，即"约到并实际上过试听"按线索粒度去重；第三层"报名"：该线索对应student_key在订单表存在order_type='正价课'的订单，且支付日期不早于线索创建日期（排除历史老学员回流的干扰，按"线索激活"口径归属）；第四层"续费"：该学员在正价课之后再产生order_type='续费'的订单。实现路径用四层CTE逐级收窄：第一层算线索与试听，第二层挂上报名（LEFT JOIN聚合后的首单），第三层挂上续费（LEFT JOIN续费学员集合），最外层用NULLIF防除零计算逐级转化率。**【避坑指南】**易错点有三个：一是同一线索表同一student_key可能出现两条（二次回访），需按student_key去重归属首条线索；二是续费订单若直接JOIN orders会把正价课也带进来，必须先过滤order_type；三是转化率分母为0时MySQL直接报错，必须包NULLIF。

### 4. 参考解法

**解法一：多层CTE逐级挂接（推荐，层次清晰）**

```sql
WITH lead_base AS (                       -- 第一层：线索与试听，按线索去重
    SELECT
        lead_id,
        channel,
        student_key,
        created_at,
        trial_date,
        ROW_NUMBER() OVER (               -- 同一student_key多条线索时取最早一条做归属
            PARTITION BY student_key
            ORDER BY created_at
        ) AS rn
    FROM leads
),
funnel1 AS (                              -- 第一、二层：线索数、试听数
    SELECT
        channel,
        COUNT(*) AS lead_cnt,             -- 线索数（漏斗顶层）
        COUNT(trial_date) AS trial_cnt    -- trial_date非空即试听，COUNT忽略NULL
    FROM lead_base
    WHERE rn = 1                          -- 只保留每个学员的首次线索
    GROUP BY channel
),
signup AS (                               -- 第三层：报名学员集合（正价课首单）
    SELECT o.student_key,
           MIN(o.pay_date) AS first_pay   -- 首次正价课支付日，用于窗口校验
    FROM orders o
    WHERE o.order_type = '正价课'
    GROUP BY o.student_key
),
funnel2 AS (                              -- 挂接报名层
    SELECT
        l.channel,
        COUNT(s.student_key) AS signup_cnt
    FROM lead_base l
    LEFT JOIN signup s
        ON l.student_key = s.student_key
       AND s.first_pay >= DATE(l.created_at)  -- 支付不早于线索创建，排除历史学员
    WHERE l.rn = 1
    GROUP BY l.channel
),
renew AS (                                -- 第四层：续费学员集合
    SELECT DISTINCT student_key
    FROM orders
    WHERE order_type = '续费'
),
funnel3 AS (                              -- 挂接续费层
    SELECT
        l.channel,
        COUNT(r.student_key) AS renew_cnt
    FROM lead_base l
    LEFT JOIN renew r
        ON l.student_key = r.student_key
    WHERE l.rn = 1
    GROUP BY l.channel
)
SELECT
    f1.channel,
    f1.lead_cnt,
    f1.trial_cnt,
    f2.signup_cnt,
    f3.renew_cnt,
    ROUND(f1.trial_cnt / NULLIF(f1.lead_cnt, 0), 4)   AS trial_rate,   -- 线索→试听
    ROUND(f2.signup_cnt / NULLIF(f1.trial_cnt, 0), 4) AS pay_rate,     -- 试听→报名
    ROUND(f3.renew_cnt / NULLIF(f2.signup_cnt, 0), 4) AS renew_rate    -- 报名→续费
FROM funnel1 f1
JOIN funnel2 f2 ON f1.channel = f2.channel
JOIN funnel3 f3 ON f1.channel = f3.channel
ORDER BY f3.renew_cnt DESC;
```

结果解读：若转介绍渠道续费率明显高于抖音但线索量只有其十分之一，说明转介绍是"质高价也高"的渠道，预算决策应做"保量提质"而非简单倾斜；抖音若试听率高但报名率低，问题在试听课体验或顾问转化，而非投放本身。

**解法二：条件聚合一步到位（快写法，适合笔试）**

```sql
SELECT
    l.channel,
    COUNT(*) AS lead_cnt,                                  -- 漏斗顶层：线索
    COUNT(l.trial_date) AS trial_cnt,                      -- 第二层：试听
    COUNT(DISTINCT CASE                                    -- 第三层：报名
              WHEN o.order_type = '正价课'
               AND o.pay_date >= DATE(l.created_at)
              THEN l.student_key END) AS signup_cnt,
    COUNT(DISTINCT CASE                                    -- 第四层：续费
              WHEN r.order_type = '续费'
              THEN l.student_key END) AS renew_cnt
FROM leads l
LEFT JOIN orders o                                        -- 正价课订单挂在学员上
    ON l.student_key = o.student_key
LEFT JOIN orders r                                        -- 续费订单再挂一次
    ON l.student_key = r.student_key
   AND r.order_type = '续费'
GROUP BY l.channel;
```

结果解读：条件聚合把四层漏斗压进一条SELECT，代码量减半，但两个LEFT JOIN orders会造成同一线索匹配多行订单的join膨胀，COUNT(DISTINCT)恰好去重兜底；数据量小时是笔试首选，量大时应回到解法一先聚合再JOIN。

### 5. 性能分析与优化

解法一扫描leads和orders各一次，signup与renew子集先按student_key聚合收窄再JOIN，join次数3次但每次都是聚合后的小结果集，代价可控；解法二leads×orders双重LEFT JOIN是"一对多挂两遍"，若某学员有20笔订单，单条线索膨胀为20行，且两个JOIN都是宽匹配，GROUP BY的去重排序开销大。优化建议：orders表建复合索引(student_key, order_type, pay_date)，让两次JOIN都能走索引且覆盖；leads表在(student_key, created_at)建索引支撑ROW_NUMBER分区排序；若渠道维度固定且报表T+1出，可将signup/renew做成按日预聚合的中间表，漏斗层只做渠道粒度SUM；数据量过亿时按created_at月份对leads做RANGE分区，月度复盘只扫当月分区。

### 6. 面试延伸考点

**【面试高频】问：同一学员在两个渠道都有线索，转化算谁的？** 要点：业务上通常按"首触归属"或"末触归属"二选一并写进口径文档，SQL上用ROW_NUMBER取最早/最晚线索；面试时要主动说出多触点归因（如按时间衰减分账）是数据产品而非SQL层面的活。**问：为什么报名层要加pay_date >= created_at？** 要点：老学员回流会在orders里留有历史正价课订单，不校验时序会把"本来就要买的人"记成本渠道转化，高估渠道效果。**问：漏斗的四级转化率中哪一环最值得关注？** 要点：结合行业基准，线索→试听看承接速度，试听→报名看教学与顾问，报名→续费看交付质量；本题续费率最被看重，因为它决定LTV。**问：COUNT(trial_date)和COUNT(*)的区别在这里为什么关键？** 要点：trial_date为NULL表示未试听，COUNT(列)天然跳过NULL，免写一层CASE。

### 7. 业务拓展思考

全漏斗表是教培机构市场部每月经营会的核心报表，直接驱动预算再分配与顾问绩效考核。拿到结果后可联动的动作：试听率低的渠道优化线索承接SLA（30分钟内联系），报名率低的渠道重排试听班型与老师，续费率低的渠道反查招生话术是否过度承诺。口径延展上，可以把漏斗窗口从"无窗口"收紧为"线索后30天内报名"，或加入退费层构成"报名-退费"净漏斗；再进一步，用各层转化率反推"每万元投放的最终续费学员数"，把市场ROI从流量口径升级为LTV口径。

## EDU-32 学员LTV：首单后各期续费收入累计

### 1. 业务背景

某职业教育培训机构的CFO办公室正在做学员生命周期价值（LTV）专项：市场部报价"一个转介绍学员值3000元获客成本贵不贵"，答案是比不了的——必须先知道一个学员平均能贡献多少累计收入。财务分析师需要按学员计算LTV：以首笔正价课订单为起点，把该学员后续所有续费收入逐期累加，得到每个学员的累计贡献收入，再按渠道、班型分组算平均LTV，用于回答"花多少钱获客不亏"的定价问题，以及判断"低价引流班学员的LTV是否显著低于直报正价班学员"。**【加分点】**LTV是面试中最高频的复杂口径题，面试官想听的不是SUM，而是你对"首单起点怎么定、收入按支付日还是服务期归属、未到期学员LTV算到哪天"这三个口径问题的处理。

### 2. 表结构说明

orders（学员订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |
| order_type | VARCHAR(16) | 订单类型：正价课/续费 |
| term_no | INT | 期数：首单为1，后续续费依次为2、3… |
| amount | DECIMAL(10,2) | 订单实付金额 |
| pay_date | DATE | 支付日期 |

示例数据：

| order_id | student_key | order_type | term_no | amount | pay_date |
|----------|-------------|------------|---------|--------|----------|
| 201 | stu_A | 正价课 | 1 | 5800.00 | 2023-03-01 |
| 202 | stu_A | 续费 | 2 | 6200.00 | 2023-09-05 |
| 203 | stu_A | 续费 | 3 | 6600.00 | 2024-03-08 |
| 204 | stu_B | 正价课 | 1 | 3600.00 | 2023-05-10 |
| 205 | stu_C | 正价课 | 1 | 8800.00 | 2024-01-15 |

### 3. 解题思路

明确指标口径是第一步：LTV定义为"该学员所有订单实付金额之和"，起点为首笔订单（term_no=1或pay_date最早者，两者要校验一致，不一致以pay_date为准并标记数据质量问题），观察截止为查询日，因此老学员的LTV天然高于新学员，分组对比时必须注明入组时间差异，或者只对"满观察期（如12个月）"的学员计算可比LTV。实现路径：先用窗口给每笔订单算出该学员的累计收入SUM(amount) OVER (PARTITION BY student_key ORDER BY pay_date)，同时用ROW_NUMBER标记首单，则首单行上的累计值即该学员截至最新一笔订单的全量LTV；再关联渠道/班型维度做分组均值。**【避坑指南】**易错点：一是SUM窗口若忘记按pay_date排序，累计顺序随机导致LTV错误；二是首单识别若用MIN(pay_date)后再JOIN，重复支付日会翻倍，应用ROW_NUMBER取行；三是amount含退费冲销时应改为加退费负向记录或单独扣减。

### 4. 参考解法

**解法一：累积窗口函数（推荐）**

```sql
WITH order_seq AS (                        -- 给每个学员的订单按时间排序并算累计收入
    SELECT
        order_id,
        student_key,
        order_type,
        amount,
        pay_date,
        ROW_NUMBER() OVER (                -- 标记首单：时间最早的那笔
            PARTITION BY student_key
            ORDER BY pay_date, order_id
        ) AS pay_seq,
        SUM(amount) OVER (                 -- 累积窗口：按时间逐笔累加该学员收入
            PARTITION BY student_key
            ORDER BY pay_date, order_id
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS cum_amount
    FROM orders
)
SELECT
    s.student_key,
    s.pay_date            AS first_pay_date,    -- 首单日期
    s.cum_amount          AS ltv,               -- 首单之后的累计收入即全周期LTV
    s.pay_seq             AS term_cnt           -- 该学员已购买期数
FROM order_seq s
WHERE s.pay_seq = 1                        -- 只取首单行：该行的cum_amount即全量LTV
ORDER BY ltv DESC;
```

结果解读：输出每个学员的LTV与购买期数，term_cnt高的学员若LTV并未同步走高，说明该学员续的是低价班，客单价在下滑，值得班主任重点升级班型。

**解法二：自连接偏移聚合（无窗口函数思路）**

```sql
SELECT
    o.student_key,
    MIN(o.pay_date)                 AS first_pay_date,   -- 首单日期
    COUNT(*)                        AS term_cnt,         -- 订单笔数即期数
    SUM(o.amount)                   AS ltv               -- 全量收入即LTV
FROM orders o
GROUP BY o.student_key
HAVING COUNT(*) >= 2                                 -- 可选：只看发生过续费的学员
ORDER BY ltv DESC;

-- 若还需"每期续费收入明细"（第2期、第3期各贡献多少），用自连接：
SELECT
    o1.student_key,
    o1.term_no,                                       -- 期数
    o1.amount AS term_amount,                         -- 该期收入
    SUM(o2.amount) AS cum_ltv                         -- 自连接自身，汇总不晚于该期的收入
FROM orders o1
JOIN orders o2
    ON o1.student_key = o2.student_key
   AND o2.pay_date <= o1.pay_date                      -- 偏移匹配：历史所有笔
GROUP BY o1.student_key, o1.term_no, o1.amount, o1.pay_date
ORDER BY o1.student_key, o1.term_no;
```

结果解读：自连接版本能在不支持窗口的老库上跑，第二段查询给出"LTV增长曲线"每一期的增量与累计，可直接喂给BI画曲线；代价是o2全表按学员自匹配，复杂度O(N²)量级。

### 5. 性能分析与优化

解法一每分区内部排序一次，窗口缓冲为学员订单数（个位数），扫描一次orders即可，代价O(N log K)；解法二第二段是学员内自连接，某学员若极端地有100笔订单，就要生成10000行中间结果，整体代价接近分区行数平方，orders越大越危险。优化建议：orders建复合索引(student_key, pay_date)，窗口排序与自连接匹配都能走索引顺序避免filesort；LTV属典型"读多写少"指标，应做成按日增量刷新的汇总表（student_ltv_daily：学员、累计金额、期数、最新支付日），报表只查汇总表；若按渠道算平均LTV，把渠道冗余进orders或汇总表，避免再JOIN leads；超大表按pay_date年份RANGE分区，计算"满12个月可比LTV"时只扫对应历史分区。

### 6. 面试延伸考点

**【面试高频】问：LTV按支付日归属还是按服务期分摊？** 要点：收付实现制按pay_date一次性计入，权责发生制按课消逐期确认；市场获客决策用前者（现金流视角），财务报表用后者，面试先问清口径再写。**问：新学员LTV天然低，怎么公平对比？** 要点：只对入组满固定观察期（如12个月）的cohort计算可比LTV，或对不满期学员按存活概率外推并标注为预测值。**问：退费学员的LTV怎么处理？** 要点：退费金额作为负向流水冲减LTV，或将LTV拆为毛LTV与净LTV两个指标并分别汇报。**问：LTV与CAC怎么联动？** 要点：LTV/CAC>3是常见健康线，分渠道算"LTV/CAC"而非单看CAC，这是本题最直接的业务出口。

### 7. 业务拓展思考

LTV结论直接决定获客预算上限与渠道定价：若转介绍学员平均LTV达2.4万而抖音学员仅1.1万，市场部应把转介绍激励提至原预算上限。可联动的运营动作：对term_cnt=1且首单即将到期的学员提前触发续费方案，对连续续费学员推高客单价班型。口径延展上，可计算"首单后N个月LTV"（限时窗口LTV）用于快速验证渠道质量，或把LTV拆到班型、老师维度，识别"哪类班型培养出的学员更忠诚"，反向指导排课与产品设计。

## EDU-33 退费原因结构化与高危学员预警名单

### 1. 业务背景

某K12连锁机构的教学质量部发现，最近三个月退费金额环比上升明显，但各部门各说各话：销售说价格太贵，老师说课堂效果差，班主任说家长没时间。负责人需要一份数据结论：把已发生退费按原因结构化拆分（教学效果/时间冲突/价格/转学搬家/其他），并从在读学员中筛出"高危预警名单"——出勤率下滑、作业缺交、曾咨询过退费的学员，让班主任在家长提出退费之前先行介入。这份名单每月输出一次，是续费保卫战的核心弹药。**【面试高频】**这道题考察两件事：一是用条件聚合把文本化的退费原因变成结构化占比；二是把"多信号加权"写成SQL打分逻辑，考察你对预警类指标"宁多勿漏还是宁缺勿滥"的口径权衡。

### 2. 表结构说明

refunds（退费记录表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| refund_id | BIGINT | 退费单ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |

| refund_amount | DECIMAL(10,2) | 退费金额 |
| apply_date | DATE | 退费申请日期 |

attendance（到课记录表，预警信号来源）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| att_id | BIGINT | 记录ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |
| class_id | BIGINT | 班级ID |

| 字段名 | 类型 | 含义 |
|--------|------|------|
| consult_id | BIGINT | 咨询记录ID，主键 |

### 3. 解题思路

分两段任务。第一段退费结构化：对近90天退费单按原因做条件聚合（SUM(CASE WHEN reason=...)）算金额与单数占比，注意口径用金额占比为主、单数为辅，因为一笔大额退费可能抵十笔小额。第二段高危预警：先明确预警口径——"在读且课程未到期"的学员中，满足以下信号者入名单：近30天出勤率低于60%、连续缺勤大于等于2次、近90天有退费咨询记录；三个信号按权重打分（出勤低2分、连续缺勤2分、有咨询3分，咨询是最强信号），总分大于等于4入高危名单，小于4入观察名单。实现路径用四层CTE：学员出勤率 → 连续缺勤判定（用LAG） → 咨询标记 → 汇总打分排序。**【避坑指南】**易错点：一是出勤率分母必须是"应到课次数"（该班排课数），不是实际记录数，否则长期缺勤学员的记录少、出勤率反而虚高；二是已全额退费学员要从预警名单剔除，避免给流失学员打骚扰电话；三是打分阈值要和业务方确认，SQL里用参数化CASE而不是硬编码散落各处。

### 4. 参考解法

**解法一：多层CTE信号打分（推荐，结构清晰）**

```sql
WITH recent_refund AS (                        -- 退费结构化：近90天按原因汇总
    SELECT
        reason,
        COUNT(*)              AS refund_cnt,   -- 退费单数
        SUM(refund_amount)    AS refund_amt,   -- 退费金额
        SUM(refund_amount) * 100.0
            / NULLIF(SUM(SUM(refund_amount)) OVER (), 0) AS amt_pct  -- 金额占比
    FROM refunds
    WHERE apply_date >= CURDATE() - INTERVAL 90 DAY
    GROUP BY reason
),
att_stat AS (                                  -- 信号一：近30天出勤率
    SELECT
        a.student_key,
        COUNT(*) AS should_cnt,                -- 应到课次数（排课记录即应到）
        SUM(a.is_attend) AS attend_cnt,        -- 实到次数
        SUM(a.is_attend) * 1.0 / NULLIF(COUNT(*), 0) AS att_rate
    FROM attendance a
    WHERE a.lesson_date >= CURDATE() - INTERVAL 30 DAY
    GROUP BY a.student_key
),
con_absent AS (                                -- 信号二：最长连续缺勤次数（gaps-and-islands）
    SELECT
        student_key,
        MAX(run_len) AS max_absent_run         -- 每个学员取最长连续缺勤段长度
    FROM (
        SELECT
            student_key,
            lesson_date,
            ROW_NUMBER() OVER (                -- 段内编号：同一缺勤段内第几次缺勤
                PARTITION BY student_key, last_attend_seq
                ORDER BY lesson_date
            ) AS run_len
        FROM (
            SELECT
                student_key,
                lesson_date,
                is_attend,
                SUM(is_attend) OVER (          -- 截至本行的累计到课次数：每到课一次开启新段，
                    PARTITION BY student_key   -- 因此同一段缺勤内该值保持不变，可作段ID
                    ORDER BY lesson_date
                    ROWS UNBOUNDED PRECEDING
                ) AS last_attend_seq
            FROM attendance
            WHERE lesson_date >= CURDATE() - INTERVAL 30 DAY
        ) x
        WHERE is_attend = 0                    -- 只考察缺勤行
    ) y
    GROUP BY student_key
),
consulted AS (                                 -- 信号三：近90天退费咨询
    SELECT DISTINCT student_key
    FROM refund_consult
    WHERE consult_date >= CURDATE() - INTERVAL 90 DAY
),
risk_score AS (                                -- 三个信号加权打分
    SELECT
        s.student_key,
        CASE WHEN s.att_rate < 0.6 THEN 2 ELSE 0 END
            + CASE WHEN COALESCE(c.max_absent_run, 0) >= 2 THEN 2 ELSE 0 END
            + CASE WHEN v.student_key IS NOT NULL THEN 3 ELSE 0 END AS score,
        s.att_rate,
        COALESCE(c.max_absent_run, 0) AS max_absent_run,
        CASE WHEN v.student_key IS NOT NULL THEN 1 ELSE 0 END AS has_consult
    FROM att_stat s
    LEFT JOIN con_absent c ON s.student_key = c.student_key
    LEFT JOIN consulted v ON s.student_key = v.student_key
)
SELECT
    r.student_key,
    r.att_rate,
    r.max_absent_run,
    r.has_consult,
    r.score,
    CASE WHEN r.score >= 4 THEN '高危' ELSE '观察' END AS risk_level
FROM risk_score r
WHERE NOT EXISTS (                             -- 剔除已全额退费学员
    SELECT 1 FROM refunds f WHERE f.student_key = r.student_key
)
ORDER BY r.score DESC, r.att_rate ASC;
```

结果解读：高危名单按score降序即班主任介入优先级，has_consult=1且att_rate低的学员几乎必然流失，应24小时内触达。

**解法二：精简版打分（一条主查询+子查询，笔试快写）**

```sql
SELECT
    s.student_key,
    ROUND(SUM(s.is_attend) * 1.0 / COUNT(*), 2)          AS att_rate,   -- 近30天出勤率
    CASE WHEN SUM(s.is_attend) * 1.0 / COUNT(*) < 0.6
         THEN 2 ELSE 0 END                               AS p_att,      -- 信号一分
    CASE WHEN COUNT(*) >= 2
          AND SUM(CASE WHEN s.is_attend = 0 THEN 1 ELSE 0 END) >= 2
         THEN 2 ELSE 0 END                               AS p_absent,   -- 缺勤信号（简化为次数）
    CASE WHEN c.student_key IS NOT NULL THEN 3 ELSE 0 END AS p_consult, -- 咨询信号分
    (CASE WHEN SUM(s.is_attend) * 1.0 / COUNT(*) < 0.6 THEN 2 ELSE 0 END
     + CASE WHEN SUM(CASE WHEN s.is_attend = 0 THEN 1 ELSE 0 END) >= 2
            THEN 2 ELSE 0 END
     + CASE WHEN c.student_key IS NOT NULL THEN 3 ELSE 0 END) >= 4
        AS is_high_risk                                                  -- 综合判定
FROM attendance s
LEFT JOIN refund_consult c
    ON s.student_key = c.student_key
   AND c.consult_date >= CURDATE() - INTERVAL 90 DAY
WHERE s.lesson_date >= CURDATE() - INTERVAL 30 DAY
GROUP BY s.student_key, c.student_key
HAVING is_high_risk = 1
ORDER BY p_consult DESC, p_att ASC;
```

结果解读：精简版把"连续缺勤"放宽为"缺勤总次数大于等于2"，会多捞一些学员——预警场景下"宁多勿漏"是可接受的口径选择，但要向业务方说明两种口径的名单量差异。

### 5. 性能分析与优化

解法一扫描attendance两次（出勤率一次、连续段一次）、refunds与refund_consult各一次，ATT表是全链路最大的表，两次扫描是主要代价；con_absent内的嵌套窗口排序在学员数百万级时排序缓存压力大。优化建议：attendance建复合索引(lesson_date, student_key, is_attend)，让30天过滤走范围扫描；连续缺勤改为"只看最近10条记录"的取法可把扫描量压缩一个量级（先ROW_NUMBER倒序取每学员最近10条，再判连续）；refunds按apply_date做月分区，结构化只扫近90天；预警名单天然适合离线批任务T+1产出，写入risk_student日表供CRM直接消费，避免业务高峰期在线跑窗口。解法二单次扫描attendance但LEFT JOIN refund_consult可能因一人多次咨询而放大行数，GROUP BY里必须带c.student_key，这在审核时可提示面试官你意识到了join膨胀。

### 6. 面试延伸考点

**【面试高频】问：预警名单的精确率和召回率怎么权衡？** 要点：班主任资源有限，名单越长人均跟进越浅，业务通常要求"名单控制在在读学员的5%以内"，所以宁可提高阈值保精确率；面试要主动说出用历史数据回测：名单学员后续实际退费率是基线的几倍。**问：为什么退费咨询是最强信号？** 要点：家长主动咨询退费说明流失意向已显性化，转化窗口极短，权重给最高；数据上可用"咨询后30天退费率"验证。**问：出勤率的分母还能怎么定？** 要点：应到课次数、剔除请假次数的应到次数两种口径差异很大，病假多的学员不应被打低分，需与业务确认。**问：连续缺勤为什么不能只数总次数？** 要点：一学期缺勤4次但零散分布问题不大，连缺2次往往意味着出了状况，连续性是比频次更强的流失信号。

### 7. 业务拓展思考

预警名单的价值在于把续费保卫从"事后挽单"前移到"事前干预"：班主任按名单优先级逐一沟通，教学部对出勤率低的班级做课程内容复盘，产品部把退费原因Top1反馈给教研迭代。可联动动作还包括对"时间冲突"退费集中的时段做排课调整、对"价格"退费集中的班型做分期或赠课策略。口径延展上，可把打分从线性加权升级为基于历史退费学员的逻辑回归概率分，或加入"同学退费扩散"特征（同班有1人退费，其余学员风险上调），让名单从规则引擎逐步进化为模型引擎。

## EDU-34 完课率异动归因：老师×班型×时段下钻

### 1. 业务背景

某在线教育机构的运营负责人在周会上看到数据：10月大班直播课完课率（到课人数/应到人数）从92%跌到81%，需要数据分析师回答三个问题——跌在哪些老师？跌在哪些班型？跌在哪个时段？这决定了应对动作是约谈老师、调整排课还是优化提醒策略。分析师要做的不是重新报一个总数，而是"异动归因下钻"：把整体完课率的环比变化拆解到"老师×班型×时段"的组合粒度，并计算每个组合对整体降幅的贡献度，排出Top5"罪魁组合"。**【加分点】**异动归因是数分面试压轴高频题，考察加法分解思想——整体变化 = Σ(结构变化) + Σ(组内变化)，能否用SQL把贡献度算出来并排序，是初级与高级分析的分水岭。

### 2. 表结构说明

classes（排课表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lesson_id | BIGINT | 课次ID，主键 |
| teacher_id | BIGINT | 授课老师ID |
| class_type | VARCHAR(32) | 班型：大班直播/小班互动/1对1 |
| time_slot | VARCHAR(16) | 时段：工作日晚间/周末白天/周末晚间 |
| lesson_date | DATE | 上课日期 |
| enroll_cnt | INT | 应到人数（报名该课次的学员数） |

attendance（到课表，按课次汇总）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lesson_id | BIGINT | 课次ID |
| attend_cnt | INT | 实际到课人数 |

（attendance与classes按lesson_id一对一；本题为课次汇总粒度，不需到学员粒度。）

示例数据：

classes：

| lesson_id | teacher_id | class_type | time_slot | lesson_date | enroll_cnt |
|-----------|------------|------------|-----------|-------------|------------|
| 1 | 701 | 大班直播 | 工作日晚间 | 2024-10-08 | 500 |
| 2 | 701 | 大班直播 | 周末晚间 | 2024-10-12 | 480 |
| 3 | 702 | 小班互动 | 工作日晚间 | 2024-10-09 | 30 |
| 4 | 702 | 大班直播 | 周末白天 | 2024-10-13 | 450 |
| 5 | 703 | 1对1 | 工作日晚间 | 2024-10-10 | 1 |

attendance：

| lesson_id | attend_cnt |
|-----------|------------|
| 1 | 460 |
| 2 | 350 |
| 3 | 28 |
| 4 | 405 |
| 5 | 1 |

### 3. 解题思路

先定口径：完课率 = Σ实到 / Σ应到（先加总再相除，绝不能先算每节课率再平均——后者是"课均完课率"，人数加权不同，口径要先说清）。归因分两步：第一步"变化定位"，分别算9月、10月在"老师×班型×时段"粒度的完课率，两期对齐后算差值，筛出降幅最大的组合；第二步"贡献度拆解"，每个组合对整体完课率变化的贡献 = (本月组内率 - 上月组内率) × 本月应到人数占比（组内变化部分），再加上结构变化（各组合应到占比变动带来的影响），简化版面试常只算组内变化贡献。实现路径：CTE按月×组合聚合 → 条件聚合把两月并成一行 → 计算组内差值与贡献度 → 排序取Top。**【避坑指南】**易错点：一是两期JOIN时某些组合上月有课本月没课（或反之），JOIN后差值为NULL，必须决定"无课组合"记为0课次还是剔除并在结论中说明；二是贡献度算完要检验——所有组合贡献之和应约等于整体完课率降幅，面试官常追问这一步自洽性校验；三是时段字段若直接比较中文串，注意口径统一（"工作日晚间"与"周中晚"是两个值）。

### 4. 参考解法

**解法一：CTE两期聚合+条件合并（推荐）**

```sql
WITH month_stat AS (                           -- 按月×老师×班型×时段聚合
    SELECT
        DATE_FORMAT(c.lesson_date, '%Y-%m') AS ym,
        c.teacher_id,
        c.class_type,
        c.time_slot,
        SUM(c.enroll_cnt)  AS enroll_cnt,      -- 应到人数
        SUM(a.attend_cnt)  AS attend_cnt,      -- 实到人数
        SUM(a.attend_cnt) * 1.0
            / NULLIF(SUM(c.enroll_cnt), 0)     AS lesson_rate   -- 组合粒度完课率
    FROM classes c
    JOIN attendance a ON c.lesson_id = a.lesson_id
    WHERE c.lesson_date >= '2024-09-01'
      AND c.lesson_date <  '2024-11-01'         -- 只取9、10两个月
    GROUP BY 1, 2, 3, 4
),
pivot2m AS (                                   -- 两期并排成一行
    SELECT
        teacher_id,
        class_type,
        time_slot,
        SUM(CASE WHEN ym = '2024-09' THEN enroll_cnt ELSE 0 END) AS enroll_m9,
        SUM(CASE WHEN ym = '2024-09' THEN attend_cnt  ELSE 0 END) AS attend_m9,
        SUM(CASE WHEN ym = '2024-10' THEN enroll_cnt ELSE 0 END) AS enroll_m10,
        SUM(CASE WHEN ym = '2024-10' THEN attend_cnt  ELSE 0 END) AS attend_m10
    FROM month_stat
    GROUP BY 1, 2, 3
)
SELECT
    p.teacher_id,
    p.class_type,
    p.time_slot,
    ROUND(p.attend_m9  / NULLIF(p.enroll_m9,  0), 4) AS rate_m9,   -- 上月组合完课率
    ROUND(p.attend_m10 / NULLIF(p.enroll_m10, 0), 4) AS rate_m10,  -- 本月组合完课率
    ROUND(p.attend_m10 / NULLIF(p.enroll_m10, 0)
        - p.attend_m9 / NULLIF(p.enroll_m9, 0), 4)       AS rate_diff, -- 组合内降幅
    ROUND(                                                               -- 贡献度：
        (p.attend_m10 / NULLIF(p.enroll_m10, 0)
         - p.attend_m9  / NULLIF(p.enroll_m9, 0))                        -- 组内率变化
        * p.enroll_m10 / NULLIF(t.total_enroll, 0)                       -- ×本月人数占比
    , 4) AS contribution
FROM pivot2m p
CROSS JOIN (                                   -- 全局10月应到总数，作贡献度分母
    SELECT SUM(enroll_m10) AS total_enroll FROM pivot2m
) t
ORDER BY contribution ASC                      -- 贡献度为负且越小，拖累越大
LIMIT 5;                                       -- Top5拖累组合
```

结果解读：若Top1是"老师701×大班直播×周末晚间"，且该组合率从0.95跌到0.72，而其余组合基本持平，则结论指向具体老师的单场事故（如调课冲突、课程质量滑坡），运营可直接约谈而不是全盘改革。

**解法二：整体两期率+按组合分解的验证写法（自洽校验版）**

```sql
WITH month_stat AS (
    SELECT
        DATE_FORMAT(c.lesson_date, '%Y-%m') AS ym,
        c.teacher_id, c.class_type, c.time_slot,
        SUM(c.enroll_cnt) AS enroll_cnt,
        SUM(a.attend_cnt) AS attend_cnt
    FROM classes c
    JOIN attendance a ON c.lesson_id = a.lesson_id
    WHERE c.lesson_date >= '2024-09-01'
      AND c.lesson_date <  '2024-11-01'
    GROUP BY 1, 2, 3, 4
),
overall AS (                                   -- 整体完课率：两期各算一个总率
    SELECT
        ym,
        SUM(enroll_cnt) AS e,
        SUM(attend_cnt) AS a,
        SUM(attend_cnt) * 1.0 / NULLIF(SUM(enroll_cnt), 0) AS rate
    FROM month_stat
    GROUP BY ym
)
SELECT                                         -- 整体结论行 + 各组合贡献行（UNION自检）
    '整体' AS dim, NULL AS teacher_id, NULL AS class_type, NULL AS time_slot,
    MAX(CASE WHEN ym = '2024-09' THEN rate END) AS rate_m9,
    MAX(CASE WHEN ym = '2024-10' THEN rate END) AS rate_m10,
    MAX(CASE WHEN ym = '2024-10' THEN rate END)
      - MAX(CASE WHEN ym = '2024-09' THEN rate END) AS rate_diff
FROM overall
UNION ALL
SELECT
    '组合贡献' AS dim, teacher_id, class_type, time_slot,
    NULL, NULL,
    (SUM(CASE WHEN ym = '2024-10' THEN attend_cnt ELSE 0 END) * 1.0
       / NULLIF(SUM(CASE WHEN ym = '2024-10' THEN enroll_cnt ELSE 0 END), 0)
     - SUM(CASE WHEN ym = '2024-09' THEN attend_cnt ELSE 0 END) * 1.0
       / NULLIF(SUM(CASE WHEN ym = '2024-09' THEN enroll_cnt ELSE 0 END), 0))
     * SUM(CASE WHEN ym = '2024-10' THEN enroll_cnt ELSE 0 END) * 1.0
     / (SELECT SUM(enroll_cnt) FROM month_stat WHERE ym = '2024-10') AS rate_diff
FROM month_stat
GROUP BY teacher_id, class_type, time_slot
ORDER BY dim, rate_diff ASC;
```

结果解读：整体行的rate_diff就是总降幅，下面各组合行rate_diff加总应近似等于它（差异来自结构变化项），把这条自洽校验讲给面试官，是归因题的压轴加分动作。

### 5. 性能分析与优化

两解法都只扫描classes与attendance各一次（JOIN为lesson_id一对一，无膨胀），month_stat聚合输出行数=月×组合数，规模很小；主要代价在GROUP BY的临时表与排序，若classes无日期索引，9、10月数据全表扫描。优化建议：classes建复合索引(lesson_date, teacher_id, class_type, time_slot)让月份过滤走范围扫描并尽量覆盖；本题是典型周报/月报场景，应把month_stat落成"课次日汇总表"（日粒度增量刷新），归因查询只对两个月×组合粒度的小表做条件聚合，毫秒级返回；若归因维度常变（有时按渠道、有时按城市），把维度字段都冗余进汇总表，避免每次改SQL重扫明细；数据量再大时按月RANGE分区，跨两月查询只触及两个分区。

### 6. 面试延伸考点

**【面试高频】问：你的贡献度之和为什么不等于总降幅？** 要点：完整分解应含"结构变化项"（各组合应到人数占比变动的贡献），简化版只算了组内变化；要把公式写全：Δ总 = Σ(占比变化×上月率) + Σ(本月占比×组内率变化)，并说明残余项很小可忽略时才用简化版。**问：为什么不能按"课均完课率"做归因？** 要点：1对1课和大班课每节人数差500倍，课均会让1对1的波动被放大成主要矛盾，必须人数加权。**问：如果某老师上月没课本月有课怎么处理？** 要点：新组合无基线，贡献度无法计算，应单列为"新增供给"另做分析，不能算进异动拖累。**问：完课率跌了但报名人数涨了，怎么解读？** 要点：警惕辛普森悖论——新涌入的低价渠道学员完课习惯差，结构性拉低整体，此时组合粒度的归因恰好能识别出来。

### 7. 业务拓展思考

归因结论直接对应三类动作：老师维度的异常走向教学质量复盘与磨课，班型维度走向产品调整（大班互动性不足可加测试题、红包激励），时段维度走向排课优化（周末晚间与热门综艺、家庭活动冲突可前移一小时）。指标口径延展上，可把完课率拆成"到课率×课中留存率"两段（进入直播间算到课，观看超80%时长算完课），进一步定位流失发生在"叫不醒"还是"留不住"；也可把归因框架复用到续费率、作业提交率等其他指标，沉淀成机构通用的"指标异动归因模板"。

## EDU-35 连续3次未到课的流失预警识别

### 1. 业务背景

某K12线下机构的班主任团队管理着上千名在读学员，经验法则是"连续缺3次课的学员大概率不会续费"，但班主任不可能每天人工翻考勤。学服负责人要求数据侧每周一输出一份名单：当前正处于"连续缺勤大于等于3次"状态的在读学员，附上最近一次到课日期、已连缺次数、所属班级与班主任，推送给各班主任做本周第一优先级回访。与EDU-33的"多信号打分"不同，本题是单信号的"连续行为识别"，SQL上必须精确判定"连续"——这是gaps-and-islands经典考点。**【面试高频】**连续行为识别（连续打卡/连续到课/连续登录）是校招笔试出场率最高的窗口题之一，面试官会盯着你的分段键写法看是否真正理解。

### 2. 表结构说明

### 3. 解题思路

先定口径："当前连续缺勤大于等于3次"指按该学员该班课次序号排列，从最近一次课往前数，连续为缺勤的课次次数大于等于3——注意是"当前处于连缺状态"，而不是"曾经连缺过"，所以要从尾部向前判定，不能只算历史最长连缺段。实现路径：先取每学员每班的最新课次行作为锚点，向前回溯。两种写法：写法A用"累计到课次数当段ID"的gaps-and-islands，缺勤行的段ID=截至该行的到课累计数，同一段内段ID相同，对"最新一段"（段ID等于该学员总到课数，即最后一段）计段内行数；写法B用自连接偏移：对每个缺勤行问一句"我之前的K行是不是都缺勤"，用NOT EXISTS存在到课行即截断。**【避坑指南】**易错点：一是必须先过滤到"开班中班级+在读学员"，否则结课班的最后几讲缺勤全是误报；二是lesson_no排序要加class_id进分区，学员换班后序号会重新从1开始，跨班混排会把不连续的课次当成连续；三是最新一段的判定若写成MAX(run_len)，会把历史最长段误当当前段，必须锚定"截至最新课次"。

### 4. 参考解法

**解法一：gaps-and-islands段ID法（推荐，一次扫描）**

```sql
WITH att_seq AS (                              -- 第一步：算每行的"累计到课数"作段ID
    SELECT
        a.student_key,
        a.class_id,
        a.lesson_no,
        a.lesson_date,
        a.is_attend,
        SUM(a.is_attend) OVER (                -- 累计到课次数：每到课一次+1
            PARTITION BY a.student_key, a.class_id
            ORDER BY a.lesson_no
            ROWS UNBOUNDED PRECEDING
        ) AS attend_cum
    FROM attendance a
    JOIN students s  ON a.student_key = s.student_key AND s.status = '在读'
    JOIN classes  cl ON a.class_id    = cl.class_id     AND cl.status = '开班中'
),
latest AS (                                    -- 第二步：锚定每个学员每班的最新课次
    SELECT student_key, class_id, MAX(lesson_no) AS max_no
    FROM att_seq
    GROUP BY student_key, class_id
),
current_run AS (                               -- 第三步：只看"最新一段缺勤"的长度
    SELECT
        x.student_key,
        x.class_id,
        COUNT(*) AS cur_absent_run             -- 同一段内缺勤行数即当前连缺次数
    FROM att_seq x
    JOIN latest l
        ON x.student_key = l.student_key
       AND x.class_id    = l.class_id
       AND x.lesson_no   <= l.max_no           -- 不超过最新课次（防御性条件）
    WHERE x.is_attend = 0                      -- 只考察缺勤行
      AND x.attend_cum = (                     -- 段ID=该学员总到课数，即"最后一段"
            SELECT SUM(t.is_attend) FROM att_seq t
            WHERE t.student_key = x.student_key AND t.class_id = x.class_id
      )
    GROUP BY x.student_key, x.class_id
)
SELECT
    r.student_key,
    s.student_name,
    r.class_id,
    cl.class_name,
    ht.head_teacher_id,
    r.cur_absent_run           AS absent_times,        -- 当前连缺次数
    MAX(x.lesson_date)         AS last_absent_date,    -- 最近一次缺勤日期
    (SELECT MAX(t.lesson_date) FROM att_seq t
     WHERE t.student_key = r.student_key
       AND t.class_id = r.class_id AND t.is_attend = 1) AS last_attend_date
FROM current_run r
JOIN students s  ON r.student_key = s.student_key
JOIN classes  cl ON r.class_id = cl.class_id
JOIN attendance x ON x.student_key = r.student_key
                 AND x.class_id = r.class_id
                 AND x.is_attend = 0                 -- 回填最近缺勤日期
WHERE r.cur_absent_run >= 3                          -- 阈值：连缺3次
GROUP BY r.student_key, s.student_name, r.class_id, cl.class_name,
         ht.head_teacher_id, r.cur_absent_run
ORDER BY r.cur_absent_run DESC, last_absent_date ASC;
```

结果解读：名单按连缺次数降序即回访优先级，连缺5次的学员比连缺3次的更紧急；last_attend_date越久远，流失概率越高，可作为次级排序。

**解法二：自连接偏移法（无窗口思路，面试对照）**

```sql
SELECT
    a.student_key,
    a.class_id,
    COUNT(*) AS cur_absent_run                       -- 当前连续缺勤次数
FROM attendance a
JOIN students s  ON a.student_key = s.student_key AND s.status = '在读'
JOIN classes  cl ON a.class_id = cl.class_id       AND cl.status = '开班中'
WHERE a.is_attend = 0
  -- 条件1：该学员该班此后（序号更大）没有到课记录 → 缺勤段一直延续到最新
  AND NOT EXISTS (
        SELECT 1 FROM attendance a2
        WHERE a2.student_key = a.student_key
          AND a2.class_id    = a.class_id
          AND a2.lesson_no   > a.lesson_no
          AND a2.is_attend   = 1
  )
  -- 条件2：该缺勤行往前的3行（序号1/2/3之前）也都是缺勤 → 保证连缺至少3次
  AND NOT EXISTS (
        SELECT 1 FROM attendance a3
        WHERE a3.student_key = a.student_key
          AND a3.class_id    = a.class_id
          AND a3.lesson_no   BETWEEN a.lesson_no - 2 AND a.lesson_no - 1
          AND a3.is_attend   = 1
  )
GROUP BY a.student_key, a.class_id
HAVING COUNT(*) >= 3
ORDER BY cur_absent_run DESC;
```

结果解读：条件1把范围锁定在"延伸到最新课次的缺勤尾段"，条件2确认段内连缺已达3次，两个NOT EXISTS配合完成"当前连续"判定；思路直白、无窗口依赖，适合窗口函数受限的老版本MySQL（5.x）。

### 5. 性能分析与优化

解法一扫描attendance两次（att_seq一次、current_run内关联子查询按学员班再取一次，索引好时可忽略），窗口排序按(学员，班级，课次)分区，代价O(N log K)，整体线性级；解法二每个缺勤行触发两次NOT EXISTS相关子查询，attendance百万行时子查询执行次数巨大，是最坏O(N²)的写法，必须依赖(student_key, class_id, lesson_no)复合索引才能把每次子查询压到索引点查。优化建议：attendance建复合索引(student_key, class_id, lesson_no, is_attend)让覆盖索引同时服务窗口排序与子查询；名单场景天然T+1离线批产，写入absent_warning日表，班主任端只读；若课次数据极长，可先按学员班聚合出"总到课数、最大课次号"的小表再回连明细，避免ATT两次全扫；班级结课后把历史考勤归档到冷表，主表只留开班中班级数据，扫描量随业务状态自然收敛。

### 6. 面试延伸考点

**【面试高频】问：为什么段ID用"累计到课数"而不是"累计缺勤数"？** 要点：到课一次开启新段，同一段缺勤内到课数不变，因此可作为稳定段ID；若用缺勤数递增，段内每行ID都不同，无法分段。**问：如果把口径改成"曾经连缺过3次"呢？** 要点：直接MAX(段内行数)即可，不必锚定最新段；一字之差（当前/曾经）就是两种完全不同的SQL结构，面试要先复述口径。**问：学员请假算缺勤吗？** 要点：考勤表若有leave_type字段，应把"已审批请假"从缺勤口径剔除，否则病假三周的学员会被误拉名单，引发家长投诉。**问：连缺阈值3次怎么定？** 要点：用历史数据回测"连缺N次后最终未续费的概率"随N的变化曲线，选概率跳变点；阈值是业务决策，SQL负责把曲线算出来。

### 7. 业务拓展思考

连缺名单是班主任工作的"作战地图"，直接决定每周回访顺序与话术：连缺3次问课程体验，连缺5次谈学习规划，连缺7次基本进入挽单流程。可联动动作包括教学侧复盘（是否某老师某时段集中导致缺勤）、排课侧调整（与校历考试周冲突的课次顺延）。口径延展上，可把"连缺课次"扩展为"连续N天未登录线上系统"（在线课场景）、"连续N次作业未交"，也可把名单升级为"连缺次数×出勤趋势（近4周出勤率环比）"二维矩阵，让班主任在"高危且恶化"与"高危但好转"之间分配不同精力。

## EDU-36 直播课到课-互动-转化路径漏斗

### 1. 业务背景

某在线教育机构的增长团队运营"0元/低价直播体验课"获客链路：用户报名后进入直播间，课上发言、答题、点赞即算互动，课后运营发优惠券引导下单正价课。增长负责人需要一张"直播体验课转化漏斗"：进入直播间→完成至少1次互动→领取优惠券→7天内下单正价课，各环节人数与相邻转化率，并按老师场次拆分，回答"哪位老师的直播间互动率高但下单率低（说明转化靠运营不靠老师）、哪位老师互动率低（直播内容有问题）"，用于指导老师直播话术培训与优惠券发放策略。**【加分点】**事件漏斗与EDU-31的实体漏斗不同：数据源是行为事件表，同一用户同一事件可能发生多次，漏斗必须"先按用户压缩到每事件的最早时间、再校验事件时序"，漏掉时序校验就会把先领券后进直播间的老用户算成漏斗完成者。

### 2. 表结构说明

events（用户行为事件表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| event_id | BIGINT | 事件ID，主键 |
| user_id | VARCHAR(64) | 用户唯一键 |
| lesson_id | BIGINT | 直播场次ID |
| event_name | VARCHAR(32) | 事件名：进入直播间/发言/答题/点赞/领券/下单 |
| event_time | DATETIME | 事件发生时间 |

lessons（直播场次表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lesson_id | BIGINT | 场次ID，主键 |
| teacher_id | BIGINT | 授课老师ID |
| lesson_title | VARCHAR(64) | 场次主题 |
| start_time | DATETIME | 直播开始时间 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | VARCHAR(64) | 用户唯一键 |
| amount | DECIMAL(10,2) | 订单金额 |
| pay_time | DATETIME | 支付时间 |

（下单行为同时记录在events.event_name='下单'，与orders一一对应，本题漏斗以events为准。）

示例数据：

events：

| event_id | user_id | lesson_id | event_name | event_time |
|----------|---------|-----------|------------|------------|
| 1 | u_001 | 91 | 进入直播间 | 2024-10-12 19:55:00 |
| 2 | u_001 | 91 | 发言 | 2024-10-12 20:10:00 |
| 3 | u_001 | 91 | 领券 | 2024-10-12 20:40:00 |
| 4 | u_002 | 91 | 进入直播间 | 2024-10-12 20:02:00 |
| 5 | u_002 | 91 | 点赞 | 2024-10-12 20:15:00 |

orders：

| order_id | user_id | amount | pay_time |
|----------|---------|--------|----------|
| 701 | u_001 | 4999.00 | 2024-10-14 10:30:00 |
| 702 | u_002 | 4999.00 | 2024-10-19 21:00:00 |

### 3. 解题思路

先定漏斗口径：以"进入直播间"为漏斗入口（必须发生在直播开始时间之后，排除测试账号与回放流量），第二层"互动"=发言/答题/点赞任一事件且时间晚于进入直播间，第三层"领券"晚于互动，第四层"下单"=events中'下单'事件（或orders表）发生在领券后7天内——每一步都要求"时间有序递进"，这是事件漏斗与实体漏斗的本质区别。实现路径：第一层CTE按(user_id, lesson_id, event_name)取MIN(event_time)，把重复行为压成时间轴上的关键节点；第二层用条件聚合+时序比较（CASE WHEN 进直播间时间 < 互动时间 < 领券时间 < 下单时间）逐级计数；第三层按老师场次分组输出漏斗。**【避坑指南】**易错点：一是同一事件多次发生时若不取MIN，JOIN或CASE聚合会重复计数；二是7天窗口必须锚定领券时间而非直播开始时间；三是"点赞"这类轻互动是否计入互动层要先与业务确认，口径不同漏斗量级差数倍。

### 4. 参考解法

**解法一：事件节点压缩+时序条件聚合（推荐）**

```sql
WITH user_nodes AS (                           -- 压缩：每用户每场次每事件取最早时间
    SELECT
        user_id,
        lesson_id,
        MIN(CASE WHEN event_name = '进入直播间' THEN event_time END) AS enter_time,
        MIN(CASE WHEN event_name IN ('发言', '答题', '点赞')
                 THEN event_time END) AS interact_time,   -- 互动任取一次最早
        MIN(CASE WHEN event_name = '领券' THEN event_time END) AS coupon_time,
        MIN(CASE WHEN event_name = '下单'  THEN event_time END) AS order_time
    FROM events
    GROUP BY user_id, lesson_id
),
funnel AS (                                    -- 逐级时序判定：后一步必须晚于前一步
    SELECT
        n.lesson_id,
        l.teacher_id,
        COUNT(*) AS enter_cnt,                 -- 第一层：进入直播间
        COUNT(CASE WHEN n.interact_time > n.enter_time
                   THEN 1 END) AS interact_cnt,-- 第二层：进入后才互动
        COUNT(CASE WHEN n.interact_time > n.enter_time
                    AND n.coupon_time > n.interact_time
                   THEN 1 END) AS coupon_cnt,  -- 第三层：互动后才领券
        COUNT(CASE WHEN n.interact_time > n.enter_time
                    AND n.coupon_time > n.interact_time
                    AND n.order_time <= n.coupon_time + INTERVAL 7 DAY
                   THEN 1 END) AS order_cnt    -- 第四层：领券后7天内下单
    FROM user_nodes n
    JOIN lessons l ON n.lesson_id = l.lesson_id
    WHERE n.enter_time IS NOT NULL              -- 漏斗入口必须有进入事件
      AND n.enter_time >= l.start_time          -- 排除开播前进场（测试/预放）
    GROUP BY n.lesson_id, l.teacher_id
)
SELECT
    lesson_id,
    teacher_id,
    enter_cnt,
    interact_cnt,
    coupon_cnt,
    order_cnt,
    ROUND(interact_cnt / NULLIF(enter_cnt, 0), 4)  AS interact_rate,  -- 到课→互动
    ROUND(coupon_cnt  / NULLIF(interact_cnt, 0), 4) AS coupon_rate,   -- 互动→领券
    ROUND(order_cnt   / NULLIF(coupon_cnt, 0), 4)   AS order_rate     -- 领券→下单
FROM funnel
ORDER BY order_cnt DESC;
```

结果解读：interact_rate高而order_rate低的老师说明直播内容有吸引力但运营转化动作弱，应加强其场次的逼单话术与优惠券面额实验；反之interact_rate低的场次优先优化直播内容而非发券。

**解法二：JOIN逐步收窄法（体现漏斗递进结构）**

```sql
WITH enter AS (                                -- 第一层：进入直播间（含开播过滤）
    SELECT e.user_id, e.lesson_id, e.event_time AS enter_time
    FROM events e
    JOIN lessons l ON e.lesson_id = l.lesson_id
    WHERE e.event_name = '进入直播间'
      AND e.event_time >= l.start_time
),
interact AS (                                  -- 第二层：进入后首次互动
    SELECT n.user_id, n.lesson_id, MIN(x.event_time) AS interact_time
    FROM enter n
    JOIN events x
        ON x.user_id  = n.user_id
       AND x.lesson_id = n.lesson_id
       AND x.event_name IN ('发言', '答题', '点赞')
       AND x.event_time > n.enter_time          -- 时序：晚于进入
    GROUP BY n.user_id, n.lesson_id
),
coupon AS (                                    -- 第三层：互动后首次领券
    SELECT i.user_id, i.lesson_id, MIN(c.event_time) AS coupon_time
    FROM interact i
    JOIN events c
        ON c.user_id  = i.user_id
       AND c.lesson_id = i.lesson_id
       AND c.event_name = '领券'
       AND c.event_time > i.interact_time       -- 时序：晚于互动
    GROUP BY i.user_id, i.lesson_id
),
paid AS (                                      -- 第四层：领券后7天内下单
    SELECT c.user_id, c.lesson_id
    FROM coupon c
    JOIN events o
        ON o.user_id  = c.user_id
       AND o.lesson_id = c.lesson_id
       AND o.event_name = '下单'
       AND o.event_time <= c.coupon_time + INTERVAL 7 DAY
)
SELECT
    e.lesson_id,
    l.teacher_id,
    COUNT(DISTINCT e.user_id) AS enter_cnt,    -- 每层LEFT JOIN回入口做计数
    COUNT(DISTINCT i.user_id) AS interact_cnt,
    COUNT(DISTINCT c.user_id) AS coupon_cnt,
    COUNT(DISTINCT p.user_id) AS order_cnt
FROM enter e
JOIN lessons l ON e.lesson_id = l.lesson_id
LEFT JOIN interact i ON e.user_id = i.user_id AND e.lesson_id = i.lesson_id
LEFT JOIN coupon  c ON e.user_id = c.user_id AND e.lesson_id = c.lesson_id
LEFT JOIN paid    p ON e.user_id = p.user_id AND e.lesson_id = p.lesson_id
GROUP BY e.lesson_id, l.teacher_id;
```

结果解读：JOIN收窄法把"时序递进"显式写在每一层的JOIN条件里，漏斗结构一目了然，适合向业务方解释口径；代价是events表被反复JOIN四次，行数放大明显，COUNT(DISTINCT)兜底去重。

### 5. 性能分析与优化

解法一只扫events一次，GROUP BY (user_id, lesson_id, event_name)后的中间结果是"用户×场次"粒度，规模可控，条件聚合无JOIN膨胀，是最优结构；解法二events被扫四次且逐层JOIN，每层都在user_id上做匹配，events上亿行时代价显著。优化建议：events建复合索引(user_id, lesson_id, event_name, event_time)让节点压缩走索引分组；事件表通常按天分区（PARTITION BY RANGE，按event_time），漏斗限定直播月份后只扫相关分区；直播场次是天然批次，可先按lesson_id圈定用户集合再关联；高频报表场景把user_nodes落成场次结束后的T+1快照表（每场次一次计算），线上查询只做场次级SUM；若互动事件量极大（点赞刷屏），先在入库层把点赞类聚合计数，SQL层只判"是否大于0"即可省去明细扫描。

### 6. 面试延伸考点

**【面试高频】问：漏斗分层窗口为什么锚定领券时间而不是直播开始时间？** 要点：优惠券有效期从发放起算，且领券到下单才是运营动作的作用窗口；锚定开播时间会把"开播前领券"等脏路径混入，口径不纯。**问：用户重复参加三场体验课怎么算？** 要点：按"用户×场次"各算一次会重复计人，按"用户首次进入的场次"归属则每人只计一次；获客漏斗应取后者（首次触达口径），并在SQL用ROW_NUMBER取首场。**问：如何识别"直播内容差"和"运营转化差"？** 要点：拆互动率与领券-下单率两个独立比率，前者归因内容、后者归因运营，交叉四象限定位责任方。**问：事件乱序到达（迟到数据）对漏斗有什么影响？** 要点：MIN(event_time)对乱序天然稳健，但窗口统计（如7天）会因迟到数据晚到而少算，离线任务需设置迟到容忍期重跑近N天分区。

### 7. 业务拓展思考

直播漏斗是增长团队迭代体验课的标准仪表盘：互动率低改内容结构（前15分钟必须有强互动钩子），领券率低改发券时机（互动高峰后即时发券），下单率低改价格锚点与限时逼单。可联动动作还包括按老师维度沉淀"最佳实践场次"供新人复训。口径延展上，可把漏斗延伸到"下单→到课→完课→续费"形成完整LTV前链路，或把互动行为加权成"参与度分"替代二元互动，让漏斗从计数升级为质量度量；再进一步，用漏斗各层转化率反推"每场直播的期望正价课GMV"，把直播排期从经验驱动升级为GMV预算驱动。

## EDU-37 多期续费cohort矩阵：按首购月追踪各期留存

### 1. 业务背景

某职业教育机构的CEO在年度战略会上问了一个问题："我们在2023年各个月招来的学员，质量是不是越来越差？"单看当月续费率回答不了这个问题——不同月份的学员课程进度不同。正确工具是cohort矩阵：把学员按首次购课月份分组（cohort），横向追踪每个cohort在第1期、第2期、第3期……的续费人数与续费率，形成一张"行是首购月、列是续费期数"的三角矩阵。运营副总用它判断招生质量趋势（后进来的cohort续费率是否系统性走低）、定价总监用它评估涨价对留存的影响，财务用它预测未来各期收入。**【面试高频】**cohort分析是校招SQL压轴常客，考察"期数展开+行转列"的组合建模能力，以及你能否讲清"矩阵右上角为什么是空的"（观察期未满）。

### 2. 表结构说明

orders（学员订单表，含期数）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |
| term_no | INT | 期数：1=首购，2=第一次续费，依此类推 |
| amount | DECIMAL(10,2) | 实付金额 |
| pay_date | DATE | 支付日期 |

students（学员表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| student_key | VARCHAR(64) | 学员唯一键，主键 |
| student_name | VARCHAR(50) | 学员姓名 |
| channel | VARCHAR(32) | 获客渠道 |

示例数据：

orders：

| order_id | student_key | term_no | amount | pay_date |
|----------|-------------|---------|--------|----------|
| 401 | stu_201 | 1 | 5800.00 | 2024-01-10 |
| 402 | stu_201 | 2 | 6200.00 | 2024-07-12 |
| 403 | stu_201 | 3 | 6600.00 | 2025-01-15 |
| 404 | stu_202 | 1 | 3600.00 | 2024-01-25 |
| 405 | stu_203 | 1 | 8800.00 | 2024-02-08 |

students：

| student_key | student_name | channel |
|-------------|--------------|---------|
| stu_201 | 张小明 | 抖音 |
| stu_202 | 李小红 | 美团 |
| stu_203 | 王小刚 | 转介绍 |

### 3. 解题思路

先定口径：cohort = 学员首购订单的支付月份（DATE_FORMAT(MIN(pay_date), '%Y-%m')，或直接用term_no=1那笔的pay_date，两者必须校验一致）；矩阵列 = 期数偏移 term_no - 1（0列即首购期人数，1列即第1次续费）；单元格值 = 该cohort在对应期数有订单的学员数，续费率 = 该期人数 / 该cohort首购人数。注意两点：一是"期数"以term_no为准而非按月数日历月，因为课程期长可能不是整数月，按日历月算会把没到续费点的cohort误判为流失；二是矩阵右上角（近期cohort的高期数列）为空是观察期未满，不是留存为零，输出时要保留空单元格并说明。实现路径：CTE算每个学员的cohort月 → 按cohort×term_no聚合人数 → 行转列（CASE WHEN term_no偏移）成矩阵。**【避坑指南】**易错点：一是cohort用MIN(pay_date)后若学员有同日多笔订单，需按订单去重；二是续费率分母必须用"该cohort首购人数"，不是上一期人数（后者算的是期际留存，是另一个指标，两者都要会讲）；三是term_no=2但pay_date早于首单的脏数据要先校验剔除。

### 4. 参考解法

**解法一：cohort标记+行转列矩阵（推荐）**

```sql
WITH first_order AS (                          -- 每个学员的首购信息
    SELECT
        student_key,
        DATE_FORMAT(MIN(pay_date), '%Y-%m') AS cohort_month,  -- 首购月即cohort
        MIN(pay_date) AS first_pay
    FROM orders
    GROUP BY student_key
),
order_flag AS (                                -- 给每笔订单贴上cohort与期数偏移
    SELECT
        o.student_key,
        f.cohort_month,
        o.term_no - 1 AS term_offset,          -- 0=首购期，1=第一次续费
        o.amount
    FROM orders o
    JOIN first_order f ON o.student_key = f.student_key
),
cohort_base AS (                               -- 每个cohort的首购人数（分母）
    SELECT cohort_month, COUNT(DISTINCT student_key) AS base_cnt
    FROM first_order
    GROUP BY cohort_month
)
SELECT
    b.cohort_month,
    b.base_cnt,
    COUNT(DISTINCT CASE WHEN o.term_offset = 0 THEN o.student_key END) AS t0_cnt,
    COUNT(DISTINCT CASE WHEN o.term_offset = 1 THEN o.student_key END) AS t1_cnt,
    COUNT(DISTINCT CASE WHEN o.term_offset = 2 THEN o.student_key END) AS t2_cnt,
    COUNT(DISTINCT CASE WHEN o.term_offset = 3 THEN o.student_key END) AS t3_cnt,
    ROUND(COUNT(DISTINCT CASE WHEN o.term_offset = 1 THEN o.student_key END)
          * 1.0 / NULLIF(b.base_cnt, 0), 4) AS t1_retain_rate,   -- 第1期续费率
    ROUND(COUNT(DISTINCT CASE WHEN o.term_offset = 2 THEN o.student_key END)
          * 1.0 / NULLIF(b.base_cnt, 0), 4) AS t2_retain_rate    -- 第2期续费率
FROM cohort_base b
LEFT JOIN order_flag o                         -- LEFT JOIN保留无人续费的cohort行
    ON b.cohort_month = o.cohort_month
GROUP BY b.cohort_month, b.base_cnt
ORDER BY b.cohort_month;
```

结果解读：横向看单一cohort，t1_rate 65%、t2_rate 40%说明每期流失约三分之一，是课程设计的结构性问题；纵向比较各cohort的t1_rate，若2024年下半年cohort系统性低于上半年，则指向招生质量或涨价影响，而非课程本身。

**解法二：期数偏移自连接法（无行转列，直接长表输出）**

```sql
WITH first_order AS (
    SELECT
        student_key,
        MIN(pay_date) AS first_pay,
        DATE_FORMAT(MIN(pay_date), '%Y-%m') AS cohort_month
    FROM orders
    GROUP BY student_key
),
renew_pair AS (                                -- 自连接：首购行 × 该学员后续每期订单
    SELECT
        f.cohort_month,
        f.student_key,
        o.term_no - 1 AS term_offset,          -- 续费期数偏移
        DATEDIFF(o.pay_date, f.first_pay) AS lag_days  -- 距首购天数（辅助列）
    FROM first_order f
    JOIN orders o
        ON o.student_key = f.student_key
       AND o.pay_date > f.first_pay            -- 只匹配首购之后的订单
)
SELECT
    p.cohort_month,
    p.term_offset,
    COUNT(DISTINCT p.student_key) AS renew_cnt,          -- 该cohort该期续费人数
    ROUND(AVG(p.lag_days), 0) AS avg_lag_days,           -- 平均续费间隔（天）
    ROUND(SUM(o.amount), 2) AS renew_amount              -- 该期续费金额
FROM renew_pair p
JOIN orders o                                  -- 关联订单取金额
    ON o.student_key = p.student_key
   AND o.term_no - 1 = p.term_offset
GROUP BY p.cohort_month, p.term_offset
ORDER BY p.cohort_month, p.term_offset;
```

结果解读：长表输出与矩阵信息等价但更适合程序消费，平均续费间隔能回答"第2期为什么掉得多——是流失还是只是没到期"，避免把"未到期"误读为"流失"，这是cohort矩阵最常见的解读事故。

### 5. 性能分析与优化

解法一扫描orders两次（first_order一次、order_flag一次JOIN），输出行数=cohort月数，极小；主要代价是first_order的GROUP BY全表聚合与JOIN，orders上亿行时建议在(student_key, pay_date)建复合索引让首购识别走索引扫描；解法二的自连接按学员匹配，每学员订单数小（个位数）时可控，但JOIN条件含term_no计算会阻碍索引下推，最好先把term_no-1物化进子查询。优化建议：cohort矩阵是典型月度例行报表，应把first_order落成学员维表字段（首购月、首购日期），增量维护而非每次全量重算；orders按pay_date月分区，新cohort只触及新分区；若矩阵要按渠道再拆一层，把channel冗余进orders或以学员维表JOIN（学员表远小于订单表，代价可忽略）；观察期不足的cohort列可直接在SQL里用CASE屏蔽或标注"未满期"，避免业务误读。

### 6. 面试延伸考点

**【面试高频】问：矩阵右上角为什么是空的？怎么防止业务误读？** 要点：近期cohort尚未到达高期数的续费时点，属结构性缺失；SQL可标注"观察中"，分析时只对"已满期"单元格做比较，这是cohort分析的基本素养。**问：续费率的分母用首购人数还是上一期人数？** 要点：前者是cohort留存率（对首购的累计），后者是期际存活率（对上期的条件概率），两者乘积关系：t2留存 = t1期际 × t2期际；面试要能现场推导。**问：课程期长不同（半年班/年班）怎么对齐期数？** 要点：term_no对齐的是"购买期次"而非时间，若要做时间对齐cohort可改用"首购后N个月"窗口，两种口径并存并各自标注。**问：怎么判断"后期cohort质量差"不是观察期偏差？** 要点：只比较各cohort在同一期数（如都是t1）的表现，并校验各cohort的观察时长一致，必要时按渠道结构标准化后再比。

### 7. 业务拓展思考

cohort矩阵把"续费率"从单点数字变成可追踪的质量趋势线，是机构战略层的核心报表：招生团队据此验证渠道质量是否被牺牲，教研据此评估课程改版后新cohort留存是否改善，财务据此滚动预测未来12个月收入（cohort人数×各期留存率×客单价）。可联动动作：对t1续费率骤降的cohort回查该月招生话术与班型结构，对平均续费间隔拉长的cohort提前启动续费触达。口径延展上，可把单元格从"续费人数"升级为"续费金额"或"课消进度"，形成金额cohort与消耗cohort双矩阵；也可在列上增加"转班型""升班"维度，追踪学员的结构性升级路径。

## EDU-38 老师综合质量分：出勤+评分+续费三指标加权

### 1. 业务背景

某K12机构的师资管理部每季度给全校三百位老师评质量等级，决定课酬系数与排课优先级，但过去只看"学员满意度评分"单一指标，被教师工会质疑不公平：有老师评分高但经常临时调课，有老师评分中庸但学员续费率全校第一。师资总监要求建立综合质量分模型：出勤达标率（按课表实际授课、无临时调课）占30%、学员评分占40%、所带学员续费率占30%，三指标先各自标准化到0-100分再加权合成，最后按分值分S/A/B/C四档输出全量老师排名。HR据此发放课酬系数，教学部据此安排师训。**【加分点】**综合评分题考察"多指标不可直接相加"的敏感性——出勤率是0到1、评分是1到5、续费率是0到1且量纲含义不同，必须先标准化再合成，以及你对分母为零（新老师无续费数据）这类边界情况的处理。

### 2. 表结构说明

### 3. 解题思路

先定三个指标口径：出勤达标率 = 实际授课课次 / 应上课课次（executed=1占比）；学员评分 = 该老师近90天评分均值（剔除开课不满两周的评分，避免首课体验噪声）；续费率 = 所带学员中已到期学员的续费占比——注意分母必须剔除未到期学员（is_renew IS NULL），否则新老师带的新学员会稀释续费率。标准化：用min-max把每个指标线性映射到0-100：(x - min) / (max - min) × 100，max与min取当季全老师范围；合成 = 出勤标准化×0.3 + 评分标准化×0.4 + 续费标准化×0.3；分档 = CASE按分值切S/A/B/C（如≥85/75/60/其余）。**【避坑指南】**易错点：一是min-max对离群值敏感，某位老师出勤率0.5会压缩全体区分度，稳健做法可用NTILE百分位替代；二是MAX=MIN时（如全员出勤率都一样）分母为零，必须包NULLIF并约定给固定分值（如全员100或全员60）；三是无续费数据的老师（新老师）应标记"观察期"而非强行打0分。

### 4. 参考解法

**解法一：min-max标准化加权（推荐，口径透明可解释）**

```sql
WITH att_rate AS (                             -- 指标一：出勤达标率
    SELECT
        teacher_id,
        SUM(executed) * 1.0 / NULLIF(COUNT(*), 0) AS att_rate
    FROM teacher_lessons
    WHERE plan_date >= '2024-09-01'
      AND plan_date <  '2024-12-01'            -- 当季范围
    GROUP BY teacher_id
),
rating_avg AS (                                -- 指标二：近90天学员评分均值
    SELECT
        teacher_id,
        AVG(score) AS avg_score,
        COUNT(*) AS rating_cnt                 -- 评分条数，用于过滤样本不足
    FROM teacher_rating
    WHERE rating_date >= '2024-09-01'
      AND rating_date <  '2024-12-01'
    GROUP BY teacher_id
    HAVING COUNT(*) >= 10                      -- 样本不足老师不参与排名
),
renew_rate AS (                                -- 指标三：已到期学员续费率
    SELECT
        teacher_id,
        SUM(is_renew) * 1.0 / NULLIF(SUM(CASE WHEN is_renew IS NOT NULL
                                              THEN 1 ELSE 0 END), 0) AS rn_rate,
        SUM(CASE WHEN is_renew IS NOT NULL THEN 1 ELSE 0 END) AS due_cnt
    FROM teacher_renew
    GROUP BY teacher_id
),
metric AS (                                    -- 三指标对齐到老师粒度
    SELECT
        t.teacher_id,
        a.att_rate,
        r.avg_score,
        v.rn_rate,
        v.due_cnt
    FROM att_rate a
    LEFT JOIN rating_avg r ON a.teacher_id = r.teacher_id
    LEFT JOIN renew_rate v ON a.teacher_id = v.teacher_id
),
norm AS (                                      -- min-max标准化到0-100
    SELECT
        teacher_id,
        (att_rate - MIN(att_rate) OVER ())
            / NULLIF(MAX(att_rate) OVER () - MIN(att_rate) OVER (), 0) * 100 AS s_att,
        (avg_score - MIN(avg_score) OVER ())
            / NULLIF(MAX(avg_score) OVER () - MIN(avg_score) OVER (), 0) * 100 AS s_score,
        (rn_rate - MIN(rn_rate) OVER ())
            / NULLIF(MAX(rn_rate) OVER () - MIN(rn_rate) OVER (), 0) * 100 AS s_renew
    FROM metric
)
SELECT
    teacher_id,
    ROUND(s_att, 1)    AS att_score,
    ROUND(s_score, 1)  AS score_item,
    ROUND(s_renew, 1)  AS renew_score,
    ROUND(s_att * 0.3 + s_score * 0.4 + s_renew * 0.3, 1) AS total_score,  -- 加权合成
    CASE                                            -- 四档评级
        WHEN s_att * 0.3 + s_score * 0.4 + s_renew * 0.3 >= 85 THEN 'S'
        WHEN s_att * 0.3 + s_score * 0.4 + s_renew * 0.3 >= 75 THEN 'A'
        WHEN s_att * 0.3 + s_score * 0.4 + s_renew * 0.3 >= 60 THEN 'B'
        ELSE 'C'
    END AS grade
FROM norm
ORDER BY total_score DESC;
```

结果解读：S档老师通常是"出勤稳+评分高+续费强"三高，若某老师综合S但出勤分低，说明其教学效果足以抵消排课不稳定，师资部可优先为其配固定助教消除调课影响，而不是简单扣分。

**解法二：NTILE百分位法（稳健替代离群敏感的min-max）**

```sql
WITH att_rate AS (
    SELECT teacher_id,
           SUM(executed) * 1.0 / COUNT(*) AS att_rate
    FROM teacher_lessons
    GROUP BY teacher_id
),
rating_avg AS (
    SELECT teacher_id, AVG(score) AS avg_score
    FROM teacher_rating
    GROUP BY teacher_id
    HAVING COUNT(*) >= 10
),
renew_rate AS (
    SELECT teacher_id,
           SUM(is_renew) * 1.0
               / NULLIF(SUM(CASE WHEN is_renew IS NOT NULL THEN 1 ELSE 0 END), 0)
               AS rn_rate
    FROM teacher_renew
    GROUP BY teacher_id
),
ranked AS (                                    -- 各指标先在老师间排百分位
    SELECT
        m.teacher_id,
        NTILE(100) OVER (ORDER BY m.att_rate)   AS p_att,    -- 百分位1~100
        NTILE(100) OVER (ORDER BY m.avg_score)  AS p_score,
        NTILE(100) OVER (ORDER BY m.rn_rate)    AS p_renew
    FROM (
        SELECT a.teacher_id, a.att_rate, r.avg_score, v.rn_rate
        FROM att_rate a
        LEFT JOIN rating_avg r ON a.teacher_id = r.teacher_id
        LEFT JOIN renew_rate v ON a.teacher_id = v.teacher_id
    ) m
)
SELECT
    teacher_id,
    p_att   AS att_pct,                        -- 百分位天然0-100且对离群稳健
    p_score AS score_pct,
    p_renew AS renew_pct,
    ROUND(p_att * 0.3 + p_score * 0.4 + p_renew * 0.3, 1) AS total_score
FROM ranked
ORDER BY total_score DESC;
```

结果解读：百分位法把"绝对水平"换成"相对排名"，某位老师出勤率离群超高也只拿100分而非拉爆分母，适合指标分布偏斜的场景；代价是丢失绝对值信息（99分只代表"比99%的老师强"，不代表"接近满分"），向HR解释时要说明这一差异。

### 5. 性能分析与优化

两解法主体都是三次按teacher_id的GROUP BY聚合加一次老师粒度JOIN，三次聚合的输出都是老师数（数百行），代价极小，瓶颈在原始表扫描：teacher_lessons与teacher_rating按季度过滤若无日期索引会全表扫。优化建议：teacher_lessons建(plan_date, teacher_id, executed)复合索引、teacher_rating建(rating_date, teacher_id, score)，让季度过滤走范围扫描；综合分是季度例行计算，应落成teacher_quality_q表带季别字段，历史分数留存支持趋势回看；三指标可各自独立增量预聚合（日表→季汇总），评分计算时不碰明细；NTILE(100)需一次全局排序，老师数不大时无碍，若扩展到数万兼职老师，可先按校区分片计算再全局合并；权重0.3/0.4/0.3应写成参数表而非硬编码，便于HR做权重敏感性实验。

### 6. 面试延伸考点

**【面试高频】问：为什么不能直接把出勤率、评分、续费率相加？** 要点：量纲与分布不同，评分4.8/5的"高分"与出勤率0.98/1的"高分"不可通约，直接相加等于隐式加权且权重失真；必须标准化或百分位化。**问：min-max和标准化（z-score）你选哪个，为什么？** 要点：min-max边界明确（0-100）便于分档与业务沟通但受离群影响；z-score对离群稳健但分值含义抽象；评分这种有理论边界的指标常用min-max，分布长尾时用百分位。**问：新老师没有续费数据怎么办？** 要点：标记观察期不参与本期排名，或用"同班型同入职批次均值"填充并单独标注；绝对不能填0，否则新人永远C档，招聘与留任都会被扭曲。**问：续费率高的老师一定教学好吗？** 要点：续费受班主任跟单、班型、渠道学员构成等混杂因素影响，公平做法是按班型分层后组内比较，或引入"续费率相对同班型均值的提升"作指标。

### 7. 业务拓展思考

综合质量分把师资管理从"印象分"升级为数据驱动：课酬系数与S/A档挂钩可留住头部老师，C档老师进入90天师训改进期，连续两季C档再触发汰割流程，形成完整的师资晋升-改进闭环。可联动动作：教学部对出勤分低的老师分析调课原因（外部兼职时间不稳定则改签约方式），对续费分低的老师配班主任跟单SOP。口径延展上，可增加"课消进度分"（老师课时消耗是否达到排课计划）与"学员进步分"（所带学员测验收入提升幅度），把质量分从"服务态度"维度扩展到"教学效果"维度；也可按班型分层出"同型相对分"，消除班型间天然续费率差异对排名的干扰。

### 3. 解题思路

先定口径：满班率 = student_cnt / capacity，只统计开班中班级（结课班满班率无意义）；老师利用率 = 当月已执行课时 / 标准月课时，只统计已执行课次（取消课不算工作量）；两个指标都建议按校区分组呈现，因为合并班级只能在同校区同科目进行。诊断分桶：满班率切为[<40%严重闲置, 40%-70%待优化, 70%-90%健康, ≥90%需扩容]四档，老师利用率切为[<50%闲置, 50%-80%正常, >90%超负荷]三档，输出"班级诊断表"与"老师诊断表"两张结果，并给出合并候选清单（同校区、同科目、低满班率的班级对）。**【避坑指南】**易错点：一是合并候选必须是"同时段可合并"，SQL里没有排课时间就判断合并会闹笑话，需按lesson_date的时段做冲突校验；二是student_cnt若是快照字段要注意统计时点，与课时统计的月份对齐；三是利用率超100%（老师加了课时）要原样输出并在解读中说明是超负荷信号而非数据错误。

### 4. 参考解法

**解法一：双指标分桶诊断（推荐）**

```sql
WITH valid_class AS (                          -- 只看开班中班级
    SELECT
        class_id, class_name, campus, teacher_id,
        capacity, student_cnt,
        student_cnt * 1.0 / NULLIF(capacity, 0) AS fill_rate   -- 满班率
    FROM classes
    WHERE status = '开班中'
),
class_diag AS (                                -- 班级维度诊断
    SELECT
        class_id,
        class_name,
        campus,
        teacher_id,
        ROUND(fill_rate, 2) AS fill_rate,
        CASE
            WHEN fill_rate < 0.4 THEN '严重闲置-建议合并'
            WHEN fill_rate < 0.7 THEN '待优化-补招或并班'
            WHEN fill_rate < 0.9 THEN '健康'
            ELSE '接近满班-考虑扩容'
        END AS fill_action
    FROM valid_class
),
teacher_hours AS (                             -- 老师当月已执行课时
    SELECT
        s.teacher_id,
        SUM(s.hours) AS exec_hours,            -- 已执行课时长合计
        COUNT(DISTINCT s.class_id) AS class_cnt
    FROM teacher_schedule s
    WHERE s.lesson_date >= '2024-10-01'
      AND s.lesson_date <  '2024-11-01'
      AND s.is_executed = 1                    -- 取消课次不计工作量
    GROUP BY s.teacher_id
),
teacher_diag AS (                              -- 老师维度利用率
    SELECT
        h.teacher_id,
        h.exec_hours,
        h.class_cnt,
        ROUND(h.exec_hours / NULLIF(t.std_monthly_hours, 0), 2) AS util_rate,
        CASE
            WHEN h.exec_hours / NULLIF(t.std_monthly_hours, 0) > 0.9 THEN '超负荷-减排或配助教'
            WHEN h.exec_hours / NULLIF(t.std_monthly_hours, 0) >= 0.5 THEN '正常'
            ELSE '闲置-增加排课'
        END AS util_action
    FROM teacher_hours h
    JOIN teacher_std t ON h.teacher_id = t.teacher_id
)
SELECT
    c.campus,
    c.class_name,
    c.fill_rate,
    c.fill_action,
    d.teacher_id,
    d.util_rate,
    d.util_action
FROM class_diag c
LEFT JOIN teacher_diag d ON c.teacher_id = d.teacher_id
ORDER BY c.fill_rate ASC, d.util_rate DESC;    -- 低满班率×高利用率老师优先处理
```

结果解读：若"初一数学B班"满班率0.30但老师801整体利用率0.95，说明该老师的问题不是班级多而是班级空，并班后老师课时数不变但可腾出教室时段给新班，是典型的"合并增效"机会。

**解法二：窗口分位数定位异常（统计视角）**

```sql
WITH valid_class AS (
    SELECT
        campus, class_id, class_name, teacher_id,
        student_cnt * 1.0 / NULLIF(capacity, 0) AS fill_rate
    FROM classes
    WHERE status = '开班中'
),
q AS (                                         -- 满班率的四分位（按校区）
    SELECT
        campus,
        class_id, class_name, teacher_id, fill_rate,
        PERCENT_RANK() OVER (PARTITION BY campus ORDER BY fill_rate) AS pr,
        NTILE(4)    OVER (PARTITION BY campus ORDER BY fill_rate) AS quartile
    FROM valid_class
),
teacher_hours AS (
    SELECT teacher_id, SUM(hours) AS exec_hours
    FROM teacher_schedule
    WHERE lesson_date >= '2024-10-01' AND lesson_date < '2024-11-01'
      AND is_executed = 1
    GROUP BY teacher_id
)
SELECT
    q.campus,
    q.class_name,
    ROUND(q.fill_rate, 2) AS fill_rate,
    q.quartile,                                            -- 校区内四分位档
    ROUND(q.pr, 2) AS percent_rank,                        -- 0~1的相对位置
    ROUND(h.exec_hours / t.std_monthly_hours, 2) AS util_rate,
    CASE WHEN q.pr < 0.25
          AND h.exec_hours / t.std_monthly_hours > 0.9
         THEN '重点合并候选'                               -- 低满班×超负荷交集
         ELSE '-' END AS merge_flag
FROM q
LEFT JOIN teacher_hours h ON q.teacher_id = h.teacher_id
LEFT JOIN teacher_std t   ON q.teacher_id = t.teacher_id
ORDER BY merge_flag DESC, q.fill_rate ASC;
```

结果解读：PERCENT_RANK给出门内相对位置，"重点合并候选"标记的是"满班率处于校区后25%且授课老师超负荷"的交集班级，比固定阈值更贴合各校区的运营水位差异。

### 5. 性能分析与优化

解法一只扫classes、teacher_schedule、teacher_std各一次，聚合输出为班级数与老师数（千级），代价极小；解法二的NTILE/PERCENT_RANK需按校区分区排序一次，量级同样可控。主要风险在teacher_schedule无索引时的全表扫描与classes.status低选择性过滤。优化建议：teacher_schedule建(lesson_date, teacher_id, hours, is_executed)复合索引支持月份范围扫描；班级人数student_cnt若由报名/退班实时更新，确保与报表对齐用同一天快照，或改为从class_student关系表当日COUNT得到，避免快照陈旧；利用率与满班率都是月度指标，应落成campus_util_monthly汇总表；若班级量大（连锁数万班），按campus分区让诊断只扫目标校区；并班冲突校验需要班级×课次时段明细，建议把时段冗余进班级表（如"周二19点"），SQL即可直接判断时段相同才可合并。

### 6. 面试延伸考点

**【面试高频】问：满班率和教室利用率是一回事吗？** 要点：不是，满班率是班级容量口径，教室利用率还要叠加时段维度（同一教室不同时段可排多班），全口径资源诊断应输出"教室×时段"热力表。**问：老师利用率越高越好吗？** 要点：超过90%通常伴随备课质量下滑与离职风险，且没有弹性应对调课，健康区间应设上限；利用率指标要配"课时质量"（学员出勤率、续费率）一起看，防止排满垃圾课时。**问：并班要校验什么？** 要点：同校区同科目同教材、上课时段不冲突、两班进度接近（课次差不超过2讲）、合计人数不超容量，SQL至少能做前两项，进度差需要班级当前课次字段。**问：student_cnt是快照字段有什么风险？** 要点：快照时点与统计月份错位会让满班率失真，尤其月末退费潮；建议用关系表实时COUNT或明确快照日期字段并纳入口径说明。

### 7. 业务拓展思考

满班率与利用率联合诊断直接产出三类运营指令：并班清单释放教室时段用于开新班（同一老师不增课时多收学员）、超负荷老师招募助教或减班、闲置老师跨校区支援。可联动动作还包括招生端把补招资源优先投向40%-70%档班级（边际收益最高）。口径延展上，可把满班率升级为"课时段满班率"（按教室时段算），把利用率升级为"人效"（老师月课时×班均人数，即老师当月服务学员课时总数），后者才是师资成本的真正产出；再进一步，用历史数据回归"满班率-续费率"关系，找到教学质量不因拥挤而下降的最大班容，让扩容决策有数据边界。

## EDU-40 寒暑假班与常规班学员流转矩阵

### 1. 业务背景

某K12机构的商业模式里，暑期班是"引流池"（低价、短周期、大面积招生），秋季常规班是"利润池"（高价、长周期）。暑期班结课后，学员有四个去向：转入秋季常规班（核心目标）、继续等待寒假班、转去竞品、彻底流失。课程顾问团队需要在暑期班结课两周内完成秋季班转化，但不知道该优先跟进谁。运营总监要求输出"暑期班→秋季班流转矩阵"：行是学员暑期班型（如数学暑期衔接班/英语暑期营/物理暑期先修），列是去向类型（转常规班/报寒假班/无后续），单元格是人数与转化率，用来回答"哪类暑期班型的学员最容易转常规班（作为明年主推产品）、哪些班型只是陪跑"，并给顾问生成待跟进名单。**【加分点】**流转矩阵（转移矩阵）是状态机分析在SQL里的落地，考察"用LAG取学员上一状态+条件聚合转置成矩阵"的组合，以及你对"去向窗口"（结课后多少天内算转化）的口径意识。

### 3. 解题思路

先定口径：以"暑期班结课日"为时间锚点，学员暑期班结课后30天内的下一笔报名为"流转去向"（30天是顾问转化窗口，超窗视为自然流失；具体天数要和业务确认）；去向分类：报秋季常规班=转常规班、报寒假班=报寒假班、无任何报名=无后续（矩阵里补齐为默认去向，否则矩阵人数对不上暑期学员总数）。实现路径：第一步圈出暑期学员（JOIN classes过滤class_type为暑期类）；第二步用LAG或"下一笔报名"子查询取每人在锚点窗口内的最早后续报名及其班型；第三步按"暑期班型×去向"条件聚合，行转列输出矩阵。**【避坑指南】**易错点：一是同学员暑期可能报两个班，去重要锚定"最早结课的暑期班"；二是"无后续"学员在INNER JOIN去向表时会整行消失，必须LEFT JOIN+COALESCE兜底，否则矩阵分母缺失；三是转班型口径要把"暑期数学衔接班→秋季数学常规班"和"→秋季英语常规班"区分开，跨科目流转是重要产品信号。

### 4. 参考解法

**解法一：LAG链+条件聚合转置（推荐）**

```sql
WITH summer_enroll AS (                        -- 第一步：圈出暑期班报名（学员×暑期班）
    SELECT
        e.student_key,
        e.class_id,
        c.class_type   AS summer_type,
        c.subject      AS summer_subject,
        c.end_date     AS summer_end,
        ROW_NUMBER() OVER (                   -- 同学员多个暑期班取最早结课的一个
            PARTITION BY e.student_key
            ORDER BY c.end_date, e.enroll_date
        ) AS rn
    FROM enrollments e
    JOIN classes c ON e.class_id = c.class_id
    WHERE c.class_type IN ('暑期衔接班', '暑期营')
),
summer_base AS (                               -- 暑期学员基础表（分母）
    SELECT student_key, summer_type, summer_subject, summer_end
    FROM summer_enroll
    WHERE rn = 1
),
next_enroll AS (                               -- 第二步：锚点窗口内的下一笔报名
    SELECT
        b.student_key,
        b.summer_type,
        MIN(nc.class_type) AS next_type        -- 多笔取最早（先按日期取，再取班型）
    FROM summer_base b
    LEFT JOIN enrollments ne
        ON b.student_key = ne.student_key
       AND ne.enroll_date > b.summer_end       -- 结课之后的报名才算流转
       AND ne.enroll_date <= b.summer_end + INTERVAL 30 DAY   -- 30天转化窗口
    LEFT JOIN classes nc ON ne.class_id = nc.class_id
    GROUP BY b.student_key, b.summer_type
)
SELECT
    summer_type,
    COUNT(*) AS summer_total,                  -- 分母：该暑期班型学员总数
    COUNT(CASE WHEN next_type = '秋季常规班'
               THEN 1 END) AS to_regular,      -- 去向1：转常规班
    COUNT(CASE WHEN next_type = '寒假班'
               THEN 1 END) AS to_winter,       -- 去向2：报寒假班
    COUNT(CASE WHEN next_type IS NULL
               THEN 1 END) AS lost             -- 去向3：窗口内无后续
FROM next_enroll
GROUP BY summer_type
ORDER BY summer_total DESC;
```

结果解读：若"暑期衔接班"转常规班率35%而"暑期营"仅8%，说明衔接班（与秋季课程强衔接）是有效的引流产品，暑期营则更像独立活动，明年应把预算向衔接班倾斜或重做暑期营的课程衔接设计。

**解法二：自连接配对+科目交叉矩阵（无LAG思路）**

```sql
WITH summer_enroll AS (
    SELECT DISTINCT                            -- 学员粒度去重（多班取任一，用MIN聚合兜底）
        e.student_key,
        MIN(c.class_type) AS summer_type,
        MIN(c.subject)    AS summer_subject,
        MIN(c.end_date)   AS summer_end
    FROM enrollments e
    JOIN classes c ON e.class_id = c.class_id
    WHERE c.class_type IN ('暑期衔接班', '暑期营')
    GROUP BY e.student_key
),
pair AS (                                      -- 自连接：暑期报名 × 窗口内后续报名
    SELECT
        s.student_key,
        s.summer_type,
        s.summer_subject,
        nc.class_type   AS next_type,
        nc.subject      AS next_subject
    FROM summer_enroll s
    LEFT JOIN enrollments ne
        ON s.student_key = ne.student_key
       AND ne.enroll_date >  s.summer_end
       AND ne.enroll_date <= s.summer_end + INTERVAL 30 DAY
    LEFT JOIN classes nc ON ne.class_id = nc.class_id
)
SELECT                                          -- 输出"暑型→秋型"科目级交叉矩阵
    summer_subject,
    next_subject,
    CASE WHEN next_type = '秋季常规班' THEN '转常规班'
         WHEN next_type = '寒假班'      THEN '转寒假班'
         ELSE '无后续' END AS flow_type,
    COUNT(DISTINCT student_key) AS stu_cnt
FROM pair
GROUP BY summer_subject, next_subject, flow_type
ORDER BY summer_subject, flow_type, stu_cnt DESC;
```

结果解读：科目交叉矩阵能暴露"暑期学数学、秋季转英语"这类跨科目流转——它不是流失而是产品迁移，若规模可观，说明暑期班在为新科目导流，应设计科目衔接优惠券主动经营这条路径。

### 5. 性能分析与优化

解法一扫描enrollments与classes各两次（圈暑期班一次、找下一笔一次），JOIN条件是student_key等值加日期范围，本质是"学员内取窗口内最小值"，学员数百万级时靠(student_key, enroll_date)复合索引走索引范围扫描可保持高效；解法二LEFT JOIN链与解法一同构，加DISTINCT与MIN聚合去重，多一次GROUP BY。优化建议：enrollments建(student_key, enroll_date)与(class_id, enroll_date)两组索引分别服务"找下一笔"与"圈暑期班"；流转矩阵是季度例行报表，应把"结课锚点+30天窗口"的流转结果落成term_flow表（T+1增量），并按结课批次分区；暑期班通常占全年报名量四成，8-9月的enrollments分区最大，跨表JOIN时可先按class_id IN（暑期班清单）缩小右表；若顾问还要名单明细，把pair结果按consultant_id输出明细表而非矩阵，矩阵只做汇报层。

### 6. 面试延伸考点

**【面试高频】问：为什么去向窗口定结课后30天？依据是什么？** 要点：窗口长短直接改变矩阵数字，定短了漏掉犹豫期学员（流转率被低估），定长了把寒假自然招生算进暑期功劳（被高估）；严谨做法用历史数据看"结课到下一笔报名"的间隔分布，取累计85%分位点。**问：学员暑期结课后先报了竞品又回来报秋季班怎么算？** 要点：内部数据看不到竞品行为，只能按"窗口内是否有我方报名"判定，建议口径文档注明"流转=回流我方"，竞品流失需问卷或第三方数据补充。**问：LEFT JOIN去掉会怎样？** 要点："无后续"学员整行消失，矩阵只剩成功去向，分母与暑期学员总数对不上，这是流转矩阵最常见的翻车点，必须COALESCE补默认去向。**问：怎么把矩阵升级为预测？** 要点：以"暑期班型×科目×出勤率×结课成绩"为特征预测个体转常规班概率，输出TopN高意向名单，SQL算特征、模型算概率，是流转分析的进阶形态。

### 7. 业务拓展思考

流转矩阵回答了"暑期引流是否真的在给秋季供血"这个商业模式的根本问题：转常规班率即引流池的"成材率"，直接决定暑期班可以亏多少（获客成本=暑期亏损/成材学员数）。可联动动作：顾问按"高意向未转化"（出勤高、成绩好但未报名）优先跟进，产品端把低流转班型重构为衔接型课程，市场端按班型流转率调整暑期投放结构。口径延展上，可把矩阵扩展为"暑期→秋季→寒假→春季"多期状态转移链，计算学员的平均存续期与全周期价值；也可在单元格内再拆金额，识别"人数流转高但金额低"（靠大额优惠转化）的产品质量问题。

## EDU-41 学习时长与成绩提升的分组对比

### 1. 业务背景

某在线职教机构的教研负责人要回答一个产品根本问题："多学真的能多提分吗？"销售话术里"每天学1小时，3个月提20分"到底有没有数据支撑？教研分析师需要把学员按"累计有效学习时长"分桶（如0-5小时/5-20小时/20-50小时/50小时以上），对比各桶学员的"入学测验到结课测验的提分幅度"，输出一张"投入-产出"对比表，用于三件事：验证话术是否夸大、评估课程设计是否存在"学了不涨分"的结构问题（某桶提分异常低）、给销售端提供"建议学习时长"的科学依据。**【面试高频】**分组对比题考察提分口径（同科目两次测验可比性）、分桶方式（等频还是业务阈值）以及"相关不等于因果"的分析素养——能主动说出选择偏差的候选人会立刻被区分出来。

### 2. 表结构说明

| 字段名 | 类型 | 含义 |

示例数据：

| 3 | stu_502 | 入学测 | 行测 | 62.0 | 2024-09-01 |

### 3. 解题思路

先定口径：学习时长 = video_minutes + quiz_minutes 按学员累计（是否区分有效学习——单次会话低于5分钟不计——要与教研确认）；提分 = 结课测分数 - 入学测分数，必须同科目配对（跨科目比较无意义），且学员需两次测验齐全；分桶方式二选一：等频NTILE(4)看分布差异，或按业务阈值（0-5h/5-20h/20-50h/50h+）保证桶有业务含义，面试建议两者都提，主用业务阈值。实现路径：CTE一层算学员累计时长，一层把两次测验按科目PIVOT成一行算提分，两表按学员JOIN后GROUP BY时长桶输出人数、平均提分、提分中位数近似（窗口AVG）。**【避坑指南】**易错点：一是两次测验JOIN时若不限定exam_type各取一次，会产生笛卡尔配对；二是只统计"有结课测"的学员会引入幸存者偏差——中途放弃的人学习时长低且无结课测，必须在结论中声明样本范围或单独统计放弃率；三是平均提分对极端值敏感，建议并列输出中位数近似值。

### 4. 参考解法

**解法一：业务阈值分桶对比（推荐，桶有业务含义）**

```sql
WITH study_total AS (                          -- 学员累计学习时长（小时）
    SELECT
        student_key,
        SUM(video_minutes + quiz_minutes) / 60.0 AS total_hours
    FROM study_log
    GROUP BY student_key
),
score_pair AS (                                -- 两次测验按科目配对成一行
    SELECT
        student_key,
        subject,
        MAX(CASE WHEN exam_type = '入学测' THEN score END) AS pre_score,
        MAX(CASE WHEN exam_type = '结课测' THEN score END) AS post_score,
        MAX(CASE WHEN exam_type = '结课测' THEN exam_date END) AS post_date
    FROM exam_score
    GROUP BY student_key, subject
),
analysis_base AS (                             -- 对齐时长与提分
    SELECT
        p.student_key,
        p.subject,
        p.pre_score,
        p.post_score,
        p.post_score - p.pre_score AS score_gain,           -- 提分幅度
        s.total_hours
    FROM score_pair p
    JOIN study_total s ON p.student_key = s.student_key
    WHERE p.pre_score IS NOT NULL
      AND p.post_score IS NOT NULL             -- 两次测验齐全才可比
)
SELECT
    CASE
        WHEN total_hours < 5  THEN '①0-5小时'
        WHEN total_hours < 20 THEN '②5-20小时'
        WHEN total_hours < 50 THEN '③20-50小时'
        ELSE '④50小时以上'
    END AS hours_bucket,
    COUNT(*) AS stu_cnt,                                     -- 各桶样本量
    ROUND(AVG(score_gain), 1) AS avg_gain,                   -- 平均提分
    ROUND(AVG(post_score - pre_score) * 1.0
        / NULLIF(AVG(pre_score), 0), 3) AS gain_rate,        -- 提分相对幅度
    MIN(score_gain) AS min_gain,
    MAX(score_gain) AS max_gain
FROM analysis_base
GROUP BY hours_bucket
ORDER BY hours_bucket;
```

结果解读：若④桶平均提分18分、①桶仅2分且随桶递增单调上升，"多学多提分"成立，话术可用；若③到④桶提分持平，说明50小时后边际收益递减，销售话术应改为"学满20小时即可见显著提升"。

**解法二：NTILE等频分桶+组内分布对比（统计视角）**

```sql
WITH study_total AS (
    SELECT student_key,
           SUM(video_minutes + quiz_minutes) / 60.0 AS total_hours
    FROM study_log
    GROUP BY student_key
),
score_pair AS (
    SELECT student_key, subject,
           MAX(CASE WHEN exam_type = '入学测' THEN score END) AS pre_score,
           MAX(CASE WHEN exam_type = '结课测' THEN score END) AS post_score
    FROM exam_score
    GROUP BY student_key, subject
),
ranked AS (                                    -- 等频四分桶：每桶人数接近
    SELECT
        p.student_key, p.subject,
        p.post_score - p.pre_score AS score_gain,
        s.total_hours,
        NTILE(4) OVER (ORDER BY s.total_hours) AS hour_quartile
    FROM score_pair p
    JOIN study_total s ON p.student_key = s.student_key
    WHERE p.pre_score IS NOT NULL AND p.post_score IS NOT NULL
),
bucket_stat AS (
    SELECT
        hour_quartile,
        MIN(total_hours) AS bucket_min_h,      -- 该桶的时长下界（体现真实分布）
        MAX(total_hours) AS bucket_max_h,
        COUNT(*) AS stu_cnt,
        AVG(score_gain) AS avg_gain
    FROM ranked
    GROUP BY hour_quartile
)
SELECT
    hour_quartile,
    ROUND(bucket_min_h, 1) AS min_h,
    ROUND(bucket_max_h, 1) AS max_h,
    stu_cnt,
    ROUND(avg_gain, 1) AS avg_gain,
    ROUND(avg_gain - LAG(avg_gain) OVER (ORDER BY hour_quartile), 1)
        AS gain_diff_prev                      -- 与上一桶的提分差：看边际收益
FROM bucket_stat
ORDER BY hour_quartile;
```

结果解读：等频桶的min/max列展示真实时长分布边界，gain_diff_prev直接给出相邻桶的边际提分——若第二桶+8分、第三桶+4分、第四桶+1分，边际递减形态一目了然，比绝对平均数更能指导"建议学习时长"的定价。

### 5. 性能分析与优化

两解法都只扫study_log与exam_score各一次，聚合后学员粒度对齐，代价集中在两个GROUP BY全量聚合与一次JOIN；exam_score的配对PIVOT用条件聚合，无JOIN膨胀。优化建议：study_log建(student_key, study_date)复合索引、exam_score建(student_key, exam_type)复合索引，让配对与聚合走索引；学习时长是持续累加指标，应做学员级日增量汇总表（student_study_daily再ROLLUP到student_total），避免每次全表SUM日志；日志表按月分区后"结课学员的历史时长"只触及历史分区；若要按科目分别对比，把科目冗余进study_log（学习行为挂在科目上），避免JOIN放大学员表；输出时附带各桶人数占比，样本不足的桶（<30人）标注"仅供参考"，防止业务过度解读。

### 6. 面试延伸考点

**【面试高频】问：学习时长和提分正相关，能证明是课程带来的提分吗？** 要点：不能，存在选择偏差（基础差的学员更愿意刷题）与混杂因素（自律性强的人既学得久基础又好）；严谨做法是对照实验（随机分组控制学习量）或至少控制入学测分数做分层对比，SQL能做的是按入学分数段再交叉分桶。**问：为什么用业务阈值分桶而不是NTILE？** 要点：NTILE保证各桶样本均衡便于看趋势，但桶边界（如38.7小时）无业务含义无法写进话术；业务阈值桶可直接翻译为运营指令，两者互补，汇报常用阈值、探索先用NTILE。**问：中途退出的学员怎么处理？** 要点：只算有结课测的学员会高估提分（幸存者偏差），应单独统计各时长桶的结课率，或对退出学员按最近一次测验估计；口径必须在汇报开头声明。**问：同一学员考两个科目算两行还是求平均？** 要点：按科目×时长桶分别统计保留差异（不同科目提分效率不同），求平均会掩盖科目问题；面试说出两种口径的适用场景即可。

### 7. 业务拓展思考

投入-产出对比表是教研与销售之间的"信任基础设施"：话术改为数据背书后投诉率下降，教研按"高投入低提分"的桶回查课程结构（可能是题目难度跳档导致刷题无效）。可联动动作：给低时长桶学员推送学习计划提醒（他们最可能流失），给边际收益拐点处设计"效果达成"仪式感（如20小时节点报告）。口径延展上，可把学习时长拆成"看课/刷题/答疑"三类分别对比提分贡献，识别哪种行为最有效；也可把提分升级为"分数段跨越率"（从不及格到及格的人数占比），让结果对家长和学员更有感知力。

## EDU-42 招生目标达成度与缺口拆解（渠道×城市）

### 1. 业务背景

某职教机构Q4的招生目标是8000个正价课名额，总部已按"渠道×城市"拆解到明细：抖音-广州1200、美团-深圳800、地推-武汉600……每周末销售运营负责人要看一张达成度看板：哪些格子超额、哪些格子掉队，并回答"距离季度目标还差多少、缺口主要在哪些渠道哪些城市、按当前进度季末预期能完成多少"，用于决定最后一月是否追加投放、是否把缺口城市的激励政策加码。**【面试高频】**目标达成题是业务SQL的经典复合题，考察三件事：目标表与事实表的粒度对齐（目标按月拆、事实按日来，必须先归一）、LEFT JOIN方向（以目标表为主表，否则没招生的城市直接消失）、缺口贡献度（用每个格子的缺口占整体缺口的比例排序，让"先抓哪个格子"有数据依据）。

### 2. 表结构说明

enroll_target（招生目标表，渠道×城市×月粒度）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| target_id | BIGINT | 目标ID，主键 |
| channel | VARCHAR(32) | 渠道：抖音/美团/地推/转介绍 |
| city | VARCHAR(32) | 城市：广州/深圳/武汉/成都 |
| target_month | CHAR(7) | 目标月份，格式'2024-10' |
| target_cnt | INT | 当月目标报名人数 |

enrollments（报名事实表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| enroll_id | BIGINT | 报名ID，主键 |
| channel | VARCHAR(32) | 报名来源渠道 |
| city | VARCHAR(32) | 报名城市 |
| amount | DECIMAL(10,2) | 报名金额 |
| enroll_date | DATE | 报名日期 |

（要求：报名必须为正价课报名，且渠道口径与目标表一致；渠道若在报名表新增而目标表未设，属于超目标来源，单独列示。）

示例数据：

enroll_target：

| target_id | channel | city | target_month | target_cnt |
|-----------|---------|------|--------------|------------|
| 1 | 抖音 | 广州 | 2024-10 | 400 |
| 2 | 抖音 | 广州 | 2024-11 | 400 |
| 3 | 美团 | 深圳 | 2024-10 | 300 |
| 4 | 地推 | 武汉 | 2024-10 | 200 |
| 5 | 转介绍 | 成都 | 2024-10 | 150 |

enrollments：

| enroll_id | channel | city | amount | enroll_date |
|-----------|---------|------|--------|-------------|
| 1 | 抖音 | 广州 | 5800.00 | 2024-10-03 |
| 2 | 抖音 | 广州 | 6200.00 | 2024-10-05 |
| 3 | 美团 | 深圳 | 3600.00 | 2024-10-07 |
| 4 | 地推 | 武汉 | 4200.00 | 2024-10-09 |
| 5 | 转介绍 | 广州 | 8800.00 | 2024-10-12 |

### 3. 解题思路

先定口径：达成率 = 实际报名数 / 目标数，粒度为渠道×城市×月；季度达成 = 三个月目标合计与实际合计对比；缺口 = 目标 - 实际（可为负即超额）；缺口贡献 = 该格子缺口 / 整体总缺口（只对正缺口格子归一）。实现路径：第一层CTE把报名事实按渠道×城市×月聚合（事实表粒度是日，必须先聚合到月再与目标对齐，直接按日JOIN会因粒度不匹配产生错误乘积）；第二层目标表LEFT JOIN实际（目标为主表，保证没开单的格子不消失）；第三层输出达成率、缺口、缺口贡献并排序。**【避坑指南】**易错点：一是事实表聚合必须GROUP BY到目标粒度后JOIN，若直接JOIN再聚合，多日订单会把目标行复制多份导致SUM重复计数；二是报名表中目标外渠道（如新开的视频号）用LEFT JOIN目标表会被丢弃，应FULL JOIN或单独UNION补齐并标注"未设目标"；三是月份用CHAR(7)字符串对齐时注意格式统一（'2024-10'与'2024-1'是两种值）。

### 4. 参考解法

**解法一：目标主表LEFT JOIN月度实际（推荐）**

```sql
WITH fact_month AS (                           -- 事实聚合到目标粒度：渠道×城市×月
    SELECT
        channel,
        city,
        DATE_FORMAT(enroll_date, '%Y-%m') AS target_month,
        COUNT(*) AS actual_cnt                 -- 报名人数
    FROM enrollments
    WHERE enroll_date >= '2024-10-01'
      AND enroll_date <  '2025-01-01'          -- Q4范围
    GROUP BY channel, city, DATE_FORMAT(enroll_date, '%Y-%m')
),
gap_calc AS (                                  -- 目标为主表挂实际
    SELECT
        t.channel,
        t.city,
        t.target_month,
        t.target_cnt,
        COALESCE(f.actual_cnt, 0) AS actual_cnt,        -- 没开单补0
        t.target_cnt - COALESCE(f.actual_cnt, 0) AS gap_cnt,
        COALESCE(f.actual_cnt, 0) * 1.0
            / NULLIF(t.target_cnt, 0) AS achieve_rate
    FROM enroll_target t
    LEFT JOIN fact_month f
        ON t.channel = f.channel
       AND t.city    = f.city
       AND t.target_month = f.target_month
),
total AS (                                     -- 整体缺口，作贡献度分母
    SELECT SUM(CASE WHEN gap_cnt > 0 THEN gap_cnt ELSE 0 END) AS total_gap,
           SUM(target_cnt) AS total_target,
           SUM(actual_cnt) AS total_actual
    FROM gap_calc
)
SELECT
    g.channel,
    g.city,
    SUM(g.target_cnt) AS target_sum,
    SUM(g.actual_cnt) AS actual_sum,
    ROUND(SUM(g.actual_cnt) * 1.0
        / NULLIF(SUM(g.target_cnt), 0), 4) AS achieve_rate,   -- 季度粒度达成率
    SUM(g.target_cnt) - SUM(g.actual_cnt) AS gap_sum,         -- 季度缺口
    ROUND(SUM(CASE WHEN g.gap_cnt > 0 THEN g.gap_cnt ELSE 0 END) * 1.0
        / NULLIF((SELECT total_gap FROM total), 0), 4) AS gap_share,  -- 缺口贡献
    (SELECT ROUND(total_actual * 1.0 / NULLIF(total_target, 0), 4)
     FROM total) AS overall_rate
FROM gap_calc g
GROUP BY g.channel, g.city
ORDER BY gap_share DESC;                       -- 缺口贡献大的格子优先干预
```

结果解读：若"抖音-广州"缺口贡献占全公司缺口的45%，运营就应把最后一个月的追加投放和定向优惠集中砸向这一个格子，而不是平均分摊——缺口贡献排序正是达成度报表区别于"罗列表"的价值所在。

**解法二：进度透镜+月末预测（窗口累积视角）**

```sql
WITH fact_month AS (
    SELECT
        channel, city,
        DATE_FORMAT(enroll_date, '%Y-%m') AS target_month,
        COUNT(*) AS actual_cnt
    FROM enrollments
    WHERE enroll_date >= '2024-10-01'
      AND enroll_date <  '2025-01-01'
    GROUP BY channel, city, DATE_FORMAT(enroll_date, '%Y-%m')
),
gap_calc AS (
    SELECT
        t.channel, t.city, t.target_month, t.target_cnt,
        COALESCE(f.actual_cnt, 0) AS actual_cnt
    FROM enroll_target t
    LEFT JOIN fact_month f
        ON t.channel = f.channel
       AND t.city = f.city
       AND t.target_month = f.target_month
),
monthly AS (                                   -- 渠道×城市季度累计目标与实际
    SELECT
        channel, city,
        SUM(target_cnt) AS q_target,
        SUM(actual_cnt) AS q_actual,
        SUM(CASE WHEN target_month = '2024-11' THEN target_cnt END) AS nov_target,
        SUM(CASE WHEN target_month = '2024-11' THEN actual_cnt END) AS nov_actual,
        SUM(CASE WHEN target_month = '2024-10' THEN actual_cnt END) AS oct_actual
    FROM gap_calc
    GROUP BY channel, city
)
SELECT
    channel, city,
    q_target, q_actual,
    ROUND(q_actual * 1.0 / NULLIF(q_target, 0), 4) AS achieve_rate,
    q_target - q_actual AS gap_sum,
    ROUND(                                                     -- 季末预测：
        q_actual + GREATEST(nov_actual, 0)                     -- 已完成 + 11月进度外推
        * (DATEDIFF('2024-12-31', '2024-11-30') * 1.0
           / GREATEST(DATEDIFF(CURDATE(), '2024-10-31'), 1))
    , 0) AS forecast_cnt
FROM monthly
ORDER BY gap_sum DESC;
```

结果解读：预测列把"还差多少"升级为"按当前节奏季末能到哪"，负缺口即预期超额；预测公式的天数基准要与业务确认（按11月单月线性外推），并在汇报时说明假设，避免被当成承诺。

### 5. 性能分析与优化

解法一扫描enrollments一次（月度聚合）与enroll_target一次，JOIN键是渠道×城市×月三字段等值匹配，聚合后fact_month行数=格子数×月数，很小；total子查询再扫一次gap_calc（内存小表），整体轻量。主要代价在enrollments无索引时Q4范围全表扫。优化建议：enrollments建(enroll_date, channel, city)复合索引支持季度范围扫描；目标达成是每周例行看板，应把fact_month落成"报名月汇总表"（T+1增量追加），报表只做目标表JOIN小表；若渠道城市组合上千个，按target_month分区目标表、按月分区事实表，逐月对齐；需要"未设目标的新来源"时改用UNION ALL补差集而非FULL JOIN（MySQL 8.0无FULL JOIN），并在聚合前完成补齐，避免口径遗漏；金额口径（人数 vs GMV）要参数化，一张看板两套指标时先说清当前列是哪个。

### 6. 面试延伸考点

**【面试高频】问：为什么不直接目标表JOIN报名明细再GROUP BY？** 要点：一条报名明细会匹配其目标行一次看似没问题，但反过来若先JOIN后聚合，任何粒度不一致（目标月对报名日）都会导致目标被复制或实际被重复计数，规范做法永远是"先各自聚合到公共粒度再JOIN"。**问：实际超出目标很多说明什么？** 要点：先查口径（是否把非正价课或目标外来源计入），再判断是目标定低还是渠道爆发；超额格子应输出"目标校准建议"回馈下季度目标制定，这是达成度报表的反哺价值。**问：达成率100%就健康吗？** 要点：要看结构——可能A城市超额掩盖B城市大幅缺口（整体合成谬误），所以必须保留格子级明细与缺口贡献列。**问：目标中途调整怎么处理？** 要点：目标表应带版本字段（调整日期、调整人），报表取生效版本；直接改数会丢失"调整前达成率"导致复盘失真。

### 7. 业务拓展思考

达成度看板把招生管理从"月尾算总账"变为"周中盯格子"：缺口贡献Top3格子触发专项动作（追加投放、调顾问人力、临时激励），连续两周达成率低于60%的格子升级到总监层面复盘。可联动动作：把缺口城市的线索分配倾斜（线索富余城市支援缺口城市），把超额渠道的素材与话术沉淀复用。口径延展上，可从"人数达成"扩展到"GMV达成"与"有效名单达成"（剔除当天退费的报名），三口径并看识别"凑数报名"；也可加入时间进度线（达成率 vs 日历进度差），把"落后"量化为"落后N天"，让预警更直观。

## EDU-43 续费窗口前置识别：到期前30天高意向学员筛选

### 1. 业务背景

某K12机构的续费率长期卡在60%，班主任的续费动作总是"到期了才打电话"，家长此时往往已被竞品接触。续费项目组把打法改为"前置经营"：每周一从系统筛选出"课程将于未来30天内到期、且尚未产生续费订单"的在读学员，并按意向信号排优先级——近两周出勤率上升、有过课程咨询或资料索取、续费页有浏览记录的学员排前面——分配给班主任做第一波触达。数据组的任务就是把这份"续费前置名单"从人工翻表变成一条可例行执行的SQL。**【加分点】**本题考察"时间窗口前置"的SQL表达（到期日落在NOW到NOW+30天的区间判断）与"排除已续费"的负向条件（NOT EXISTS续费订单），以及多信号意向排序——把运营节奏写进SQL是高级数分的日常工作形态。

### 3. 解题思路

先定圈人口径：主体为"在读学员"，到期日落在[今天， 今天+30天]的半开区间内（今天到期已可谈续费，30天外暂不触达避免打扰），且近60天无续费订单（NOT EXISTS排除已续费，防止重复触达引发投诉）。意向信号三层：信号一出勤走势（近14天出勤率高于近60天出勤率，说明学习投入在加深，续费意愿基础好）；信号二续费页浏览（近14天浏览过续费页，显性意向最强）；信号三资料页/课程页浏览（近14天，隐性意向）。排序列出三个信号命中数与到期紧迫度（剩余天数升序），供班主任按序触达。**【避坑指南】**易错点：一是到期区间必须含边界讨论——到期日=今天是否还来得及（建议含并加"今日到期"紧急标记）；二是排除已续费不能只看renew_order存在与否，要校验续费支付日期晚于本周期课程开始（老订单是上一周期续费，不能误伤）；三是page_view若同一学员反复浏览，信号判定用EXISTS存在即可，不要COUNT导致JOIN膨胀。

### 4. 参考解法

**解法一：多层CTE信号打分排序（推荐）**

```sql
WITH due_window AS (                           -- 第一步：圈定到期窗口内在读学员
    SELECT
        student_key, student_name, class_id, head_teacher_id, expire_date,
        DATEDIFF(expire_date, CURDATE()) AS days_left      -- 剩余天数（可为0）
    FROM students
    WHERE status = '在读'
      AND expire_date >= CURDATE()             -- 今日到期也含（当天可谈）
      AND expire_date <  CURDATE() + INTERVAL 30 DAY
),
not_renewed AS (                               -- 第二步：排除已续费学员
    SELECT d.*
    FROM due_window d
    WHERE NOT EXISTS (
        SELECT 1 FROM renew_order r
        WHERE r.student_key = d.student_key
          AND r.pay_date >= CURDATE() - INTERVAL 60 DAY   -- 近60天无新续费
    )
),
att_trend AS (                                 -- 信号一：出勤走势（近14天 vs 近60天）
    SELECT
        student_key,
        SUM(CASE WHEN lesson_date >= CURDATE() - INTERVAL 14 DAY
                 THEN is_attend END) * 1.0
            / NULLIF(SUM(CASE WHEN lesson_date >= CURDATE() - INTERVAL 14 DAY
                              THEN 1 ELSE 0 END), 0) AS att_14d,
        SUM(is_attend) * 1.0 / NULLIF(COUNT(*), 0) AS att_60d
    FROM attendance
    WHERE lesson_date >= CURDATE() - INTERVAL 60 DAY
    GROUP BY student_key
),
pv_flag AS (                                   -- 信号二/三：页面浏览标记
    SELECT
        student_key,
        MAX(CASE WHEN page_name = '续费页'
                  AND pv_time >= NOW() - INTERVAL 14 DAY THEN 1 ELSE 0 END) AS pv_renew,
        MAX(CASE WHEN page_name IN ('课程页', '资料页')
                  AND pv_time >= NOW() - INTERVAL 14 DAY THEN 1 ELSE 0 END) AS pv_other
    FROM page_view
    GROUP BY student_key
)
SELECT
    n.student_key,
    n.student_name,
    n.head_teacher_id,
    n.expire_date,
    n.days_left,
    ROUND(COALESCE(a.att_14d, 0), 2) AS att_14d,
    ROUND(COALESCE(a.att_60d, 0), 2) AS att_60d,
    COALESCE(p.pv_renew, 0) AS pv_renew,
    COALESCE(p.pv_other, 0) AS pv_other,
    (CASE WHEN COALESCE(a.att_14d, 0) > COALESCE(a.att_60d, 0) THEN 1 ELSE 0 END
     + COALESCE(p.pv_renew, 0)
     + COALESCE(p.pv_other, 0)) AS signal_cnt,             -- 命中信号数
    CASE WHEN COALESCE(p.pv_renew, 0) = 1 THEN 'P0-显性意向'
         WHEN COALESCE(a.att_14d, 0) > COALESCE(a.att_60d, 0) THEN 'P1-投入加深'
         ELSE 'P2-常规触达' END AS touch_priority           -- 触达优先级
FROM not_renewed n
LEFT JOIN att_trend a ON n.student_key = a.student_key
LEFT JOIN pv_flag   p ON n.student_key = p.student_key
ORDER BY touch_priority ASC, n.days_left ASC;              -- 优先级+紧迫度双排序
```

结果解读：P0名单（浏览过续费页）转化概率最高，班主任应在24小时内触达并附专属优惠；P1（出勤上升）适合以学习成果汇报切入；days_left小于7的P0学员标记为"本周必完成"。

**解法二：EXISTS条件串联的精简写法（快筛版）**

```sql
SELECT
    s.student_key,
    s.student_name,
    s.head_teacher_id,
    s.expire_date,
    DATEDIFF(s.expire_date, CURDATE()) AS days_left,
    CASE WHEN EXISTS (                              -- 显性意向：近期浏览续费页
             SELECT 1 FROM page_view p
             WHERE p.student_key = s.student_key
               AND p.page_name = '续费页'
               AND p.pv_time >= NOW() - INTERVAL 14 DAY
         ) THEN 1 ELSE 0 END AS pv_renew,
    (SELECT COUNT(*) FROM attendance a              -- 近14天到课次数（辅助参考）
     WHERE a.student_key = s.student_key
       AND a.lesson_date >= CURDATE() - INTERVAL 14 DAY
       AND a.is_attend = 1) AS attend_14d_cnt
FROM students s
WHERE s.status = '在读'
  AND s.expire_date >= CURDATE()
  AND s.expire_date < CURDATE() + INTERVAL 30 DAY
  AND NOT EXISTS (                                  -- 未续费
        SELECT 1 FROM renew_order r
        WHERE r.student_key = s.student_key
          AND r.pay_date >= CURDATE() - INTERVAL 60 DAY
  )
  AND (                                             -- 至少命中一个意向信号才输出
        EXISTS (SELECT 1 FROM page_view p
                WHERE p.student_key = s.student_key
                  AND p.page_name = '续费页'
                  AND p.pv_time >= NOW() - INTERVAL 14 DAY)
     OR EXISTS (SELECT 1 FROM page_view p
                WHERE p.student_key = s.student_key
                  AND p.page_name IN ('课程页', '资料页')
                  AND p.pv_time >= NOW() - INTERVAL 14 DAY)
     OR (SELECT COUNT(*) FROM attendance a
         WHERE a.student_key = s.student_key
           AND a.lesson_date >= CURDATE() - INTERVAL 14 DAY
           AND a.is_attend = 1) >= 2                -- 近14天到课2次以上
  )
ORDER BY pv_renew DESC, days_left ASC;
```

结果解读：精简版直接把"高意向"翻译成一串EXISTS存在性判断，可读性高、不产生JOIN膨胀，适合名单规模可控的每周执行；与解法一的差异是"出勤走势"被简化为"到课次数"，业务若认可简化口径，性能更优。

### 5. 性能分析与优化

解法一主要代价在attendance按60天窗口的全学员聚合（ATT表大，是扫描大头），page_view全表GROUP BY聚合；解法二的多个EXISTS相关子查询在students候选行（到期窗口内学员，规模已被压缩到很小）上执行，配合(student_key, pv_time)、(student_key, lesson_date)索引时每次子查询都是索引点查，实际代价低于直觉——"先收窄主表再相关子查询"是小名单场景的实用套路。优化建议：renew_order建(student_key, pay_date)索引让NOT EXISTS走索引反连接（MySQL 8.0对NOT EXISTS可优化为anti-join）；attendance按lesson_date月分区，60天窗口只扫两个分区；名单每周例行产出，把due_window（到期学员池）做成学员维表的物化字段，信号计算改为T+1批任务写renew_touch_list表；page_view量大时先在数仓层按"学员×页面×日"预聚合成布尔/计数列，SQL层只读预聚合结果。

### 6. 面试延伸考点

**【面试高频】问：为什么用NOT EXISTS而不是LEFT JOIN ... IS NULL排除已续费？** 要点：两者结果等价，NOT EXISTS语义直白且MySQL 8.0能转成反连接；LEFT JOIN在续费表有重复订单时会放大主表行数，需DISTINCT兜底，易错。**问：到期窗口30天怎么定的？** 要点：太早触达家长无决策动力、太晚被竞品截胡，通常用历史数据看"续费支付日距到期日的分布"，取提前触达有效区间；窗口是运营参数，SQL应写成变量。**问：信号会不会自证预言（浏览续费页本来就因为运营推了券）？** 要点：会，意向信号与运营动作互为因果，严谨做法是A/B对照（推送触达组 vs 不触达对照组）验证名单增量价值，SQL负责按实验分组输出对比。**问：学员有多门课到期怎么处理？** 要点：以最早到期课程为主课程触达，续费话术按"全部持有课程"打包设计，SQL按(student_key, expire_date)取ROW_NUMBER=1锚定主课。

### 7. 业务拓展思考

前置名单把续费从"到期抢救"变为"窗口经营"，直接拉动续费率与现金流的稳定：P0转化率若达40%，整月续费收入可预测性显著增强，财务排期也更从容。可联动动作：出勤下降型学员先由教学侧修复体验再谈续费（硬推易反弹），显性意向学员配限时优惠制造决策闭环。口径延展上，可把信号从三项扩到"课后作业提交率、家长群活跃度、测验成绩趋势"，加权成意向分；也可把名单口径反转为"高意向但被竞品截胡"（窗口结束仍未续费），回溯分析流失原因，持续校准信号权重与触达话术。

## EDU-44 试听未转化学员的行为归因：到课率与互动率对比

### 1. 业务背景

某语培机构每月有约2000条线索被约到试听课，但只有35%试听后购买正价课。顾问团队的直觉归因是"价格贵""竞品便宜"，但运营总监怀疑问题出在试听体验本身。数据组受命做一次对照归因：把近90天试听学员分成"已转化组"（试听后30天内购买正价课）与"未转化组"，对比两组在试听阶段的行为指标——试听到课率（约了试听实际到场）、试听课互动次数（课堂发言/答题）、试听后24小时回访接通率、试听完成度（中途离场与否）——用数据回答"未转化的学员是没来、来了没听懂、还是听完了没被跟进"，把归因从拍脑袋变成动作清单。**【面试高频】**对照归因题考察"对照组构建"（转化口径与窗口）与"多指标组间对比"的SQL表达，以及最重要的分析素养：相关差异不等于原因，要主动讨论混杂与实验设计。

### 2. 表结构说明

leads（试听线索表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | BIGINT | 线索ID，主键 |
| student_key | VARCHAR(64) | 学员唯一键 |
| trial_date | DATE | 试听日期 |
| trial_class_id | BIGINT | 试听班级ID |
| converted | TINYINT | 1试听后30天内报名 0未报名（业务已维护） |

### 3. 解题思路

先定口径：对照分组以converted为准（业务已按"试听后30天内购买"维护），若表里没有该字段则需按orders自行判定——本题按有字段处理但要口头说明判定逻辑；四项对比指标：到场率（到场行为存在为1）、互动次数（发言+答题计数）、中途离场标记、回访接通率（试听后48小时内的首次外呼是否接通）。实现路径：行为表先按lead_id条件聚合成行为宽表（到场/互动数/离场一行搞定），回访表取试听后48小时首次接通标记，最后按converted分组对比两组均值并计算差值与比值。**【避坑指南】**易错点：一是"没到场"学员在行为表无"到场"行，条件聚合天然记0，但不能因此把他们从到场率分母剔除——到场率恰恰要含爽约者；二是回访接通率只统计试听后的外呼，若JOIN时不加call_time > trial_date会混入试听前电话；三是两组样本量差异大时（转化组小），单看均值差易被极端值带偏，应并列输出各指标的分位数或样本量。

### 4. 参考解法

**解法一：行为宽表+分组条件聚合对比（推荐）**

```sql
WITH bhv_wide AS (                             -- 行为明细压成每线索一行宽表
    SELECT
        lead_id,
        MAX(CASE WHEN bhv_type = '到场' THEN 1 ELSE 0 END) AS is_show,     -- 是否到场
        SUM(CASE WHEN bhv_type IN ('课堂发言', '课堂答题')
                 THEN 1 ELSE 0 END) AS interact_cnt,                        -- 互动次数
        MAX(CASE WHEN bhv_type = '中途离场' THEN 1 ELSE 0 END) AS left_early,
        MAX(CASE WHEN bhv_type = '领取资料' THEN 1 ELSE 0 END) AS got_material
    FROM trial_behavior
    GROUP BY lead_id
),
first_connect AS (                             -- 试听后48小时内首次接通标记
    SELECT
        f.lead_id,
        MAX(f.is_connected) AS connected_48h   -- 48h内任一次接通即算触达成功
    FROM followup f
    JOIN leads l ON f.lead_id = l.lead_id
    WHERE f.call_time >= TIMESTAMP(l.trial_date, '00:00:00')
      AND f.call_time <= TIMESTAMP(l.trial_date, '00:00:00') + INTERVAL 48 HOUR
      AND f.call_time > l.created_at           -- 排除试听前的营销电话
    GROUP BY f.lead_id
),
base AS (                                      -- 对齐分组与四项指标
    SELECT
        l.converted,
        l.lead_id,
        COALESCE(b.is_show, 0) AS is_show,     -- 无到场行为=爽约，计0不能丢行
        COALESCE(b.interact_cnt, 0) AS interact_cnt,
        COALESCE(b.left_early, 0) AS left_early,
        COALESCE(c.connected_48h, 0) AS connected_48h
    FROM leads l
    LEFT JOIN bhv_wide b ON l.lead_id = b.lead_id
    LEFT JOIN first_connect c ON l.lead_id = c.lead_id
    WHERE l.trial_date IS NOT NULL             -- 只看已约试听的线索
      AND l.trial_date >= CURDATE() - INTERVAL 90 DAY
)
SELECT
    CASE WHEN converted = 1 THEN '已转化组' ELSE '未转化组' END AS grp,
    COUNT(*) AS lead_cnt,                                    -- 组样本量
    ROUND(AVG(is_show), 4) AS show_rate,                     -- 到场率
    ROUND(AVG(interact_cnt), 2) AS avg_interact,             -- 户均互动次数
    ROUND(AVG(left_early), 4) AS left_early_rate,            -- 中途离场率
    ROUND(AVG(connected_48h), 4) AS connect_rate,            -- 48h接通率
    ROUND(AVG(CASE WHEN is_show = 1 THEN interact_cnt END), 2) AS interact_per_show
                                                             -- 到场者户均互动
FROM base
GROUP BY converted
ORDER BY converted DESC;
```

结果解读：若两组到场率接近（说明约课能力OK）但"到场者户均互动"1组是0组的三倍、且0组中途离场率是1组的两倍，结论指向"试听课堂体验"而非"约课或价格"，动作是重做试听课的前20分钟设计；若0组48小时接通率显著更低，则要优化回访时段与号码质量。

**解法二：个体偏离视角（组均值+离群标记）**

```sql
WITH bhv_wide AS (
    SELECT lead_id,
           MAX(CASE WHEN bhv_type = '到场' THEN 1 ELSE 0 END) AS is_show,
           SUM(CASE WHEN bhv_type IN ('课堂发言', '课堂答题')
                    THEN 1 ELSE 0 END) AS interact_cnt
    FROM trial_behavior
    GROUP BY lead_id
),
base AS (
    SELECT
        l.converted,
        l.lead_id,
        COALESCE(b.is_show, 0) AS is_show,
        COALESCE(b.interact_cnt, 0) AS interact_cnt
    FROM leads l
    LEFT JOIN bhv_wide b ON l.lead_id = b.lead_id
    WHERE l.trial_date IS NOT NULL
),
group_mean AS (                                -- 分组均值
    SELECT
        converted,
        AVG(interact_cnt) AS mean_interact
    FROM base
    GROUP BY converted
),
joined AS (                                    -- 个体对组均值的偏离
    SELECT
        b.converted,
        b.lead_id,
        b.interact_cnt,
        g.mean_interact,
        b.interact_cnt - g.mean_interact AS dev
    FROM base b
    JOIN group_mean g ON b.converted = g.converted
)
SELECT                                          -- 转化组与未转化组各取互动Top模式
    CASE WHEN converted = 1 THEN '已转化组' ELSE '未转化组' END AS grp,
    COUNT(*) AS lead_cnt,
    ROUND(AVG(interact_cnt), 2) AS avg_interact,
    SUM(CASE WHEN interact_cnt >= 3 THEN 1 END) AS hi_interact_cnt,  -- 高互动人数
    ROUND(SUM(CASE WHEN interact_cnt >= 3 THEN 1 END) * 1.0
        / NULLIF(COUNT(*), 0), 4) AS hi_interact_rate,             -- 高互动占比
    ROUND(STDDEV_SAMP(dev), 2) AS interact_std                     -- 组内互动离散度
FROM joined
GROUP BY converted;
```

结果解读：高互动占比比均值更抗极端值——若未转化组中"互动大于等于3次"的学员占比仅5%而转化组达40%，可以粗略推断"互动3次"是转化分水岭，课堂设计目标就是让每个试听者至少互动3次；STDDEV衡量组内一致性，离散小说明体验稳定。

### 5. 性能分析与优化

两解法主体是trial_behavior按lead_id的条件聚合（一次扫描）加leads JOIN，聚合后行数=线索数，代价小；followup的48小时窗口聚合需JOIN leads取trial_date，是第二处扫描。优化建议：trial_behavior建(lead_id, bhv_type)复合索引支持条件聚合与覆盖扫描；followup建(lead_id, call_time)索引让时间窗过滤走范围扫描；行为表通常增长最快（互动明细），按月分区后90天窗口只扫三个分区；归因报表可月度例行化，把bhv_wide落成"试听行为宽表"（线索粒度，含四指标列），后续任何归因分析直接读宽表；若互动事件量大（大班直播弹幕），先在数仓层按"线索×行为类型"聚合计数入宽表，SQL不再碰明细。解法一的AVG(CASE WHEN is_show=1...)注意NULL传播：到场者为0时AVG忽略NULL分母自动缩到到场人数，语义正确但要在注释说明，防止评审误读。

### 6. 面试延伸考点

**【面试高频】问：两组行为差异显著，能说互动少导致了未转化吗？** 要点：不能直接归因，存在反向因果（对课程没兴趣的学员既不互动也不报名）与混杂（班型、老师、时段差异）；正确姿势是控制变量分层对比（同老师同班型内比较），或对未转化组做随机A/B干预实验验证。**问：为什么用"到场率"而不是"试听完成率"做第一指标？** 要点：漏斗顺序决定动作归属——没到场是顾问提醒与时段问题，到场后流失才是课程问题，先看上游才能正确分派责任。**问：爽约学员算进到场率分母吗？** 要点：算，到场率的业务含义就是"约课质量"；但需另列"爽约率"单独分析，两者合并会掩盖问题环节。**问：converted字段由业务维护有什么风险？** 要点：口径漂移（30天窗口被人为放宽）与延迟更新会让归因失真，数据组应具备按orders自行复核的能力，双口径校验一致性后再使用。

### 7. 业务拓展思考

行为归因把"未转化"从模糊的价格问题拆成可执行的三类动作：低到场率优化提醒链路（试听前1小时短信+顾问电话双触达）、低互动率重构试听课互动设计（前20分钟必答题、红包激励）、低接通率调整外呼时段与号码池。可联动动作：给"到场且高互动但未转化"的学员做定向回访（最可惜的一批人），其异议记录反哺话术库。口径延展上，可把对比指标扩到"课后24小时内主动咨询率、试听课观看时长中位数"，构建更完整的行为画像；也可把归因周期从30天放宽到90天追踪"慢转化"学员，识别长周期转化的行为特征，让流失名单避免错杀潜在客户。

## EDU-45 校区月度经营健康度评分卡

### 1. 业务背景

某连锁教培机构在全国有12家直营校区，总部每月要给各校区做一次"经营体检"：单看收入会误判（老校区存量高不代表健康），单看续费会失衡（新校区无历史包袱）。运营中台把健康度拆成五个维度：招生达成率（当月报名/当月目标）、学员续费率、退费率（反向指标）、班级满班率、师资留存率，每个维度按阈值打分（0-100），加权合成"校区健康分"（权重30/25/15/15/15），再映射红黄绿三色灯：绿灯正常经营、黄灯重点关注、红灯总部介入。月度经营会上，红灯校区的校长要用数据说明原因与改进计划。**【面试高频】**评分卡是多源指标综合建模的收官题，考察跨表汇水（招生、续费、退费、排班、人事五张事实表）、阈值打分与加权合成的结构化表达，以及"维度缺失怎么办"（新校区无续费数据）的口径弹性。

### 2. 表结构说明

campus_metrics（校区月度指标宽表，由各业务线T+1汇总产出）：

| refund_rate | DECIMAL(5,4) | 当月退费率（0-1） |
| fill_rate | DECIMAL(5,4) | 平均满班率（0-1） |

### 3. 解题思路

先定打分口径：每个维度按"线性映射"打分——指标值处于[零分线，满分线]之间时按比例落在0-100之间，退费率是反向指标（越低越好），打分前先取负号或交换阈值方向；权重从配置表读取而非硬编码，方便运营调权重不改SQL。灯号规则：总分大于等于80绿灯、60-80黄灯、小于60红灯（阈值与业务方确认）。实现路径：第一步把宽表"逆透视"成长表（每校区×每指标一行），便于统一套用打分公式；第二步JOIN权重配置表算各项得分；第三步按校区加权合成总分并映射灯号。**【避坑指南】**易错点：一是反向指标（退费率）直接套正向公式会得负分或反向排序，必须先归一方向；二是新校区续费率为NULL，合成时NULL会把总分污染为NULL，应COALESCE给中性分（如60）并标记"部分维度缺失"；三是权重配置合计不等于1时总分失真，输出前用窗口校验SUM(weight)=1。

### 4. 参考解法

**解法一：长表化+配置驱动打分（推荐，配置可维护）**

```sql
WITH metric_long AS (                          -- 宽表逆透视：每校区×每指标一行
    SELECT campus, stat_month, '招生达成' AS metric_name,
           enroll_cnt * 1.0 / NULLIF(target_cnt, 0) AS metric_value
    FROM campus_metrics
    UNION ALL
    SELECT campus, stat_month, '续费率', renew_rate FROM campus_metrics
    UNION ALL
    SELECT campus, stat_month, '退费率', refund_rate FROM campus_metrics   -- 反向指标
    UNION ALL
    SELECT campus, stat_month, '满班率', fill_rate FROM campus_metrics
    UNION ALL
    SELECT campus, stat_month, '师资留存', teacher_retain FROM campus_metrics
),
direction AS (                                 -- 指标方向：1正向（越高越好）-1反向
    SELECT metric_name,
           CASE WHEN metric_name = '退费率' THEN -1 ELSE 1 END AS d,
           weight, full_score_line, zero_score_line
    FROM score_weight
),
scored AS (                                    -- 统一线性打分（支持正反向）
    SELECT
        m.campus,
        m.metric_name,
        w.weight,
        ROUND(
            CASE
                WHEN m.metric_value IS NULL THEN 60          -- 缺失维度给中性分
                WHEN (m.metric_value - w.zero_score_line) * w.d
                     / NULLIF(w.full_score_line - w.zero_score_line, 0) >= 1
                    THEN 100                                  -- 达到满分线
                WHEN (m.metric_value - w.zero_score_line) * w.d
                     / NULLIF(w.full_score_line - w.zero_score_line, 0) <= 0
                    THEN 0                                    -- 低于零分线
                ELSE (m.metric_value - w.zero_score_line) * w.d
                     / NULLIF(w.full_score_line - w.zero_score_line, 0) * 100
            END, 1) AS item_score
    FROM metric_long m
    JOIN direction w ON m.metric_name = w.metric_name
    WHERE m.stat_month = '2024-10'
),
campus_score AS (                              -- 按校区加权合成
    SELECT
        campus,
        ROUND(SUM(item_score * weight)
            / NULLIF(SUM(CASE WHEN item_score IS NOT NULL THEN weight END), 0), 1)
            AS health_score                    -- 缺失维度时按实际权重归一
    FROM scored
    GROUP BY campus
)
SELECT
    campus,
    health_score,
    CASE
        WHEN health_score >= 80 THEN '绿灯'
        WHEN health_score >= 60 THEN '黄灯'
        ELSE '红灯'
    END AS light,                              -- 三色灯映射
    RANK() OVER (ORDER BY health_score DESC) AS campus_rank   -- 校区间排名
FROM campus_score
ORDER BY health_score ASC;                     -- 最差的排在最上面先讨论
```

结果解读：珠海校区若红灯，逐项看是招生达成与退费率双低分——招生缺口靠市场动作、退费高企要教学侧复盘，评分卡的价值在于"总分定级别、分项定动作"，输出时应附带各维度得分明细供校长申诉与拆解。

**解法二：宽表CASE直接打分（快写版，适合指标固定）**

```sql
WITH raw AS (
    SELECT
        campus,
        enroll_cnt * 1.0 / NULLIF(target_cnt, 0) AS enroll_achieve,
        renew_rate,
        refund_rate,
        fill_rate,
        teacher_retain
    FROM campus_metrics
    WHERE stat_month = '2024-10'
),
scored AS (
    SELECT
        campus,
        -- 招生达成：0.6以下0分，1.0满分，线性内插
        ROUND(LEAST(GREATEST((enroll_achieve - 0.6) / 0.4, 0), 1) * 100, 1)
            AS s_enroll,
        -- 续费率：0.5以下0分，0.85满分
        ROUND(LEAST(GREATEST((COALESCE(renew_rate, 0.65) - 0.5) / 0.35, 0), 1) * 100, 1)
            AS s_renew,
        -- 退费率（反向）：2%及以下满分，10%及以上0分
        ROUND(LEAST(GREATEST((0.10 - refund_rate) / 0.08, 0), 1) * 100, 1)
            AS s_refund,
        -- 满班率：0.5以下0分，0.9满分
        ROUND(LEAST(GREATEST((fill_rate - 0.5) / 0.4, 0), 1) * 100, 1)
            AS s_fill,
        -- 师资留存：0.7以下0分，0.95满分
        ROUND(LEAST(GREATEST((COALESCE(teacher_retain, 0.85) - 0.7) / 0.25, 0), 1) * 100, 1)
            AS s_retain
    FROM raw
)
SELECT
    campus,
    s_enroll, s_renew, s_refund, s_fill, s_retain,
    ROUND(s_enroll * 0.30 + s_renew * 0.25 + s_refund * 0.15
        + s_fill * 0.15 + s_retain * 0.15, 1) AS health_score,
    CASE
        WHEN s_enroll * 0.30 + s_renew * 0.25 + s_refund * 0.15
             + s_fill * 0.15 + s_retain * 0.15 >= 80 THEN '绿灯'
        WHEN s_enroll * 0.30 + s_renew * 0.25 + s_refund * 0.15
             + s_fill * 0.15 + s_retain * 0.15 >= 60 THEN '黄灯'
        ELSE '红灯'
    END AS light
FROM scored
ORDER BY health_score ASC;
```

结果解读：宽表版把五个维度摊开成五行得分列，会上直接指着列讨论，可读性最好；代价是阈值与权重硬编码进SQL，每次调整都要改代码并回归测试，适合指标稳定的过渡期，成熟后应迁回解法一的配置表模式。

### 5. 性能分析与优化

解法一的数据源campus_metrics已是月度宽表（校区数×月数，行数极小），逆透视UNION ALL五段各扫一遍宽表（宽表小，五次扫描可忽略），JOIN配置表是几行的点查，整体几乎无代价——本题的真正瓶颈在"宽表是怎么来的"：上游招生、续费、退费、排班、人事五张事实表的汇水才是重活。优化建议：把五路汇水做成T+1批任务的campus_metrics日表/月表，评分SQL只读宽表；UNION ALL各段都加WHERE stat_month过滤让分区裁剪生效；score_weight是典型维表，MySQL会自动缓存，无需额外优化；若维度扩到十几个，长表+配置的边际成本不变，而宽表CASE会线性膨胀，这是两种解法架构差异的本质；RANK排名窗口在十几个校区的量级上开销可忽略，扩展到数千加盟校时给health_score建索引或改为物化视图。

### 6. 面试延伸考点

**【面试高频】问：为什么用阈值线性打分而不是min-max标准化？** 要点：评分卡要"对绝对标准负责"——80分必须始终代表"健康"，而min-max的分母随当月各校极值浮动，某月出现超级校区会把其他人分数压扁，灯号失稳；管理层沟通需要分值跨月可比，阈值法是正解。**问：某校区缺续费数据怎么处理？** 要点：不能给0分（新校区会被误判红灯）也不能直接跳过（权重真空导致总分虚高），标准做法是给中性分并在灯号旁标注"部分维度缺失"，或对总分乘以实际权重占比归一——本题两种都写了，要能讲清取舍。**问：总分一样怎么排名次？** 要点：RANK对并列名次跳号，DENSE_RANK不跳；业务上通常并列时看"招生达成"作第一关键字，或干脆并列呈现不硬排名。**问：这套评分卡的公平性怎么向校长保证？** 要点：阈值与权重必须事前公示、按月锁定版本、变动留痕；校长可下钻每个维度的原始值复核，评分卡是工具不是黑箱。

### 7. 业务拓展思考

健康度评分卡把总部对校区的管理从"看结果数字"升级为"看结构健康"：红灯触发总部进驻诊断，黄灯进入校长月度改进跟踪，绿灯经验被提炼成SOP横向复制。可联动动作：把灯号与校长激励挂钩时必须双指标防博弈（总分+分项红线，如退费率超过8%一票黄灯）。口径延展上，可加入"环比改善分"（本月比上月进步加分），让基础差的校区也有上升通道，避免"强者恒强"；也可把评分卡下沉到班级粒度做"班主任健康分"，或上升到集团粒度做"品牌健康分"，同一套长表+配置架构可以直接复用，这正是配置驱动设计的最大红利。
