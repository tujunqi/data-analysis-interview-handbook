## EDU-16 按渠道与顾问统计试听转正价转化率

### 1. 业务背景

某K12机构市场部每月在抖音、美团、地推等渠道投放广告，线索进入CRM后由销售顾问一对一跟进，先约试听课，试听满意后购买正价课。市场总监在月度复盘中需要一张"渠道×顾问"粒度的试听转化率表：看哪些渠道带来的试听线索更容易转正价、哪些顾问的转化能力更强，用于决定下月投放预算在各渠道间的分配，以及顾问的绩效排名与培训安排。**【面试高频】**试听转化率是教培机构最核心的漏斗指标，面试官常用它考察你对"转化窗口"和"分子分母口径"的处理是否严谨：未试听的线索算不算分母、30天窗口怎么定、同一线索买多笔课怎么去重，每一处都是扣分点。

### 2. 表结构说明

leads（试听线索表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | BIGINT | 线索ID，主键 |
| channel | VARCHAR(32) | 获客渠道：抖音/美团/地推/转介绍 |
| consultant_id | BIGINT | 跟进顾问ID |
| student_name | VARCHAR(50) | 学员姓名 |
| created_at | DATETIME | 线索创建时间 |
| trial_date | DATE | 试听日期，NULL表示未约到试听 |

示例数据：

| lead_id | channel | consultant_id | student_name | created_at | trial_date |
|---------|---------|---------------|--------------|------------|------------|
| 1001 | 抖音 | 501 | 张小明 | 2024-06-01 10:00:00 | 2024-06-03 |
| 1002 | 抖音 | 501 | 李小红 | 2024-06-02 11:00:00 | 2024-06-05 |
| 1003 | 美团 | 502 | 王小刚 | 2024-06-03 09:00:00 | NULL |
| 1004 | 地推 | 503 | 赵小丽 | 2024-06-05 14:00:00 | 2024-06-06 |

| amount | DECIMAL(10,2) | 订单金额 |

### 3. 解题思路

先定口径再动手。**【避坑指南】**分母不是全部线索，而是"已试听"的线索（trial_date 非空）：未约到试听的线索连漏斗第二步都没进，混入分母会把转化率严重拉低，也让"渠道线索质量"与"顾问转化能力"两个问题混为一谈。分子是"试听后30天内购买正价课"的线索，即该线索存在一笔 is_trial=0 且 paid_at 落在 [trial_date, trial_date+30天) 区间内的订单；窗口用左闭右开，避免第30天边界被双算。同一线索买了多笔正价课只算1个转化线索，必须按线索去重（如示例中 lead_id=1001 的第二笔订单在30天窗口外，也不影响判定）。实现路径：方案一先把 orders 按 lead_id 预聚合出"最早正价购买时间"，LEFT JOIN 回 leads 后用条件聚合同时算分母与分子；方案二用 EXISTS 相关子查询在行级打"是否转化"标记再 GROUP BY。易错点：一对多 JOIN 导致订单行放大重复计数、忘记过滤 is_trial=0、ROUND 之前分子分母用了错误的粒度。

### 4. 参考解法

解法一：预聚合订单 + LEFT JOIN + 条件聚合（推荐）

```sql
WITH first_paid AS (                 -- CTE：每个线索最早一次正价课购买时间
    SELECT
        lead_id,                     -- 线索ID
        MIN(paid_at) AS first_paid_at  -- 最早正价支付时间（只统计正价课）
    FROM orders
    WHERE is_trial = 0               -- 过滤掉试听课订单，只看正价课
    GROUP BY lead_id                 -- 按线索聚合，保证一线索一行，防止JOIN放大
)
SELECT
    l.channel,                       -- 渠道
    l.consultant_id,                 -- 顾问ID
    COUNT(*) AS trial_cnt,           -- 分母：已试听线索数（见WHERE过滤）
    COUNT(CASE WHEN o.first_paid_at >= l.trial_date          -- 最早正价购买不早于试听日
                AND o.first_paid_at < DATE_ADD(l.trial_date, INTERVAL 30 DAY)  -- 且在30天窗口内（右开区间）
          THEN 1 END) AS conv_cnt,   -- 分子：窗口内转化的线索数（已按线索去重）
    ROUND(COUNT(CASE WHEN o.first_paid_at >= l.trial_date
                AND o.first_paid_at < DATE_ADD(l.trial_date, INTERVAL 30 DAY)
          THEN 1 END) / COUNT(*), 4) AS conv_rate  -- 转化率 = 分子 / 分母
FROM leads l                         -- 线索表为主表
LEFT JOIN first_paid o               -- 左连接预聚合结果，未成单线索o字段为NULL
    ON o.lead_id = l.lead_id
WHERE l.trial_date IS NOT NULL       -- 分母口径：只保留已试听的线索
GROUP BY l.channel, l.consultant_id  -- 渠道×顾问粒度
ORDER BY l.channel, conv_rate DESC;  -- 渠道内按转化率降序，便于看顾问排名
```

结果解读：假设输出"抖音/501：试听120，转化36，转化率30.0%"，说明该顾问在抖音渠道的试听转化能力显著高于渠道均值，可提炼其跟进话术作为标杆经验；若某渠道整体转化率明显偏低，应优先排查线索质量而非归因于顾问。

解法二：EXISTS 相关子查询打转化标记

```sql
SELECT
    l.channel,                       -- 渠道
    l.consultant_id,                 -- 顾问ID
    COUNT(*) AS trial_cnt,           -- 分母：已试听线索数
    SUM(EXISTS (                     -- 相关子查询：当前线索是否存在窗口内的正价订单
        SELECT 1
        FROM orders o
        WHERE o.lead_id = l.lead_id  -- 关联外层当前线索
          AND o.is_trial = 0         -- 只看正价课订单
          AND o.paid_at >= l.trial_date                              -- 购买不早于试听日
          AND o.paid_at < DATE_ADD(l.trial_date, INTERVAL 30 DAY)    -- 30天窗口内（右开）
    )) AS conv_cnt,                  -- EXISTS返回0/1，SUM即转化线索数（天然按线索去重）
    ROUND(SUM(EXISTS (
        SELECT 1 FROM orders o
        WHERE o.lead_id = l.lead_id AND o.is_trial = 0
          AND o.paid_at >= l.trial_date
          AND o.paid_at < DATE_ADD(l.trial_date, INTERVAL 30 DAY)
    )) / COUNT(*), 4) AS conv_rate   -- 转化率
FROM leads l
WHERE l.trial_date IS NOT NULL       -- 分母口径：已试听线索
GROUP BY l.channel, l.consultant_id
ORDER BY l.channel, conv_rate DESC;
```

结果解读：EXISTS 写法把"是否转化"下沉到行级判断，语义接近自然语言"存在一笔30天内的正价订单"，与解法一结果完全等价；orders 按 lead_id 建好索引时，MySQL 8.0 会将 EXISTS 优化为半连接，性能与解法一相当。

### 5. 性能分析与优化

两种解法复杂度均约为 O(线索数 + 订单数)。解法一先对 orders 做 GROUP BY 聚合，JOIN 后每条线索最多匹配1行，中间结果集小；解法二对每条已试听线索做一次索引探测，探测次数等于分母行数，但有半连接（semijoin）优化兜底，线索量在百万级以内差异不大。可执行优化：(1) 为 orders 建复合索引 (lead_id, is_trial, paid_at)，让 EXISTSI 探测与预聚合都走覆盖索引，避免回表；(2) leads 上建 (trial_date) 或 (channel, consultant_id) 索引，辅助过滤与分组；(3) 若该报表每日定时刷新，可把 first_paid 结果物化为中间表，或在订单落库时回写线索表的"是否转化"标记，查询退化为单表条件聚合。

### 6. 面试延伸考点

- **如果业务要求分母包含所有线索（含未试听）怎么办？** 直接改 WHERE 即可，但必须同步改指标名（"线索转化率"与"试听转化率"是两个指标），并在报表上标注口径，避免两套数字在会上打架。
- **为什么分子按线索去重而不是按订单计数？** 一个线索复购多门课属于同一次转化决策，按订单计数会虚增分子；若管理层想衡量报读科目数，应另设"人均报读科数"指标。
- **30天窗口为什么用右开区间？** [trial_date, trial_date+30) 保证与"第30天后的转化"不重叠；若写成 BETWEEN trial_date AND trial_date+30，边界日会被相邻两个窗口重复统计。
- **如何看转化率的月度趋势？** 在 GROUP BY 中追加 DATE_FORMAT(trial_date,'%Y-%m')，注意按试听月归属而非线索创建月，两个归属口径会差几天到几周，全公司必须统一。

### 7. 业务拓展思考

这张转化率表能同时反哺投放与销售两条线。渠道维度上，转化率乘以客单价等于单线索期望价值，倒推可得各渠道可承受的线索成本上限，直接指导投放出价与渠道砍留；顾问维度上，转化率结合人均跟进量可以区分"能力强但线索少"与"线索多但转化差"两类顾问，分别采取加量投放与话术辅导。口径上还可延展出试听后7天/15天/30天的分窗口转化率，观察成单衰减曲线，为"首次回访、二次触达"的跟进SOP节奏提供数据依据。

## EDU-17 到期学员分班型续费率

### 1. 业务背景

教培机构获客成本逐年攀升，续费是收入的基本盘，续一个老学员的成本通常只有招一个新学员的三分之一。校区校长每月月初要在经营分析会上看上月各班型（一对一、小班课、大班课）的到期学员续费率：判断哪类班型用户粘性更强、班主任的续费动作是否到位，据此决定教学资源向哪个班型倾斜、以及给哪些班主任发续费专项奖金。**【面试高频】**续费率最大的坑在分母——"到期学员"必须排除已退费的报名，且按报名记录而非学员去重计数；分子"续费"要有明确的时间窗口，否则考前的流失和考后的续费会算成一笔糊涂账。

### 2. 表结构说明

enrollments（报名表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| enrollment_id | BIGINT | 报名记录ID，主键 |
| student_id | BIGINT | 学员ID |
| class_type | VARCHAR(20) | 班型：一对一/小班课/大班课 |
| course_id | BIGINT | 课程ID |
| start_date | DATE | 开课日期 |
| end_date | DATE | 到期日期 |
| status | VARCHAR(20) | 状态：在读/已结课/已退费 |

示例数据：

| enrollment_id | student_id | class_type | course_id | start_date | end_date | status |
|---------------|------------|------------|-----------|------------|----------|--------|
| 30001 | 801 | 一对一 | 301 | 2024-03-01 | 2024-06-30 | 已结课 |
| 30002 | 802 | 小班课 | 302 | 2024-04-01 | 2024-06-15 | 已结课 |
| 30003 | 803 | 大班课 | 303 | 2024-03-15 | 2024-06-20 | 已退费 |
| 30004 | 801 | 小班课 | 304 | 2024-02-10 | 2024-06-10 | 已结课 |
| 30005 | 804 | 一对一 | 305 | 2024-04-05 | 2024-06-25 | 在读 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| is_trial | TINYINT | 是否试听课订单：1是，0否 |
| amount | DECIMAL(10,2) | 订单金额 |
| paid_at | DATETIME | 支付时间 |

示例数据：

| order_id | student_id | course_id | is_trial | amount | paid_at |
|----------|------------|-----------|----------|--------|---------|
| 40001 | 801 | 306 | 0 | 9600.00 | 2024-06-28 20:10:00 |
| 40002 | 802 | 307 | 0 | 5200.00 | 2024-07-10 11:00:00 |
| 40003 | 802 | 308 | 0 | 4800.00 | 2024-06-16 09:30:00 |
| 40004 | 804 | 309 | 1 | 0.00 | 2024-06-26 15:00:00 |
| 40005 | 805 | 301 | 0 | 9600.00 | 2024-06-05 10:00:00 |

### 3. 解题思路

口径分三步定清楚。第一步定分母：考察月（如2024年6月）内到期的报名记录，且 status 不等于"已退费"；注意按报名记录计数，同一学员两个班先后到期要分别计入分母，因为两次到期对应两次独立的续费决策。第二步定分子：该学员在到期日当天起30天内（[end_date, end_date+30天)）再次购买了任一正价课，即视为该笔报名续费成功；窗口起点用 end_date 而不是 start_date，到期当天续费（提前锁单）也算续费，是否剔除"当天原班续费=转班"的场景需业务确认并在口径文档里写死。第三步定粒度：按班型 GROUP BY，输出分母、分子、续费率三列。实现路径：方案一用 EXISTS 相关子查询在行级判续费；方案二先把窗口内订单按学员预聚合出"到期后最早复购时间"再 LEFT JOIN。易错点：分母误用期末在读学员（那是在读率不是续费率）、JOIN 订单未预聚合导致一单多行、把试听课订单（is_trial=1）算进续费。

### 4. 参考解法

解法一：EXISTS 相关子查询判续费（语义直观）

```sql
SELECT
    e.class_type,                    -- 班型
    COUNT(*) AS expired_cnt,         -- 分母：考察月内到期且未退费的报名记录数
    SUM(EXISTS (                     -- 行级判断：该学员是否在到期后30天内复购正价课
        SELECT 1
        FROM orders o
        WHERE o.student_id = e.student_id   -- 关联外层报名记录的学员
          AND o.is_trial = 0                -- 只认正价课订单
          AND o.paid_at >= e.end_date       -- 从到期日当天起算（含当天提前续费）
          AND o.paid_at < DATE_ADD(e.end_date, INTERVAL 30 DAY)  -- 30天窗口，右开
    )) AS renew_cnt,                 -- 分子：续费成功的报名记录数
    ROUND(SUM(EXISTS (
        SELECT 1 FROM orders o
        WHERE o.student_id = e.student_id AND o.is_trial = 0
          AND o.paid_at >= e.end_date
          AND o.paid_at < DATE_ADD(e.end_date, INTERVAL 30 DAY)
    )) / COUNT(*), 4) AS renew_rate  -- 续费率 = 分子 / 分母
FROM enrollments e
WHERE e.status <> '已退费'                                  -- 排除已退费报名
  AND e.end_date >= '2024-06-01' AND e.end_date < '2024-07-01'  -- 考察月：2024年6月到期
GROUP BY e.class_type
ORDER BY renew_rate DESC;            -- 班型间按续费率降序对比
```

结果解读：假设输出"一对一 82%、小班课 61%、大班课 43%"，说明班型越个性化粘性越高；大班课续费率低可能源于互动感弱，应优先为大班课配置课后答疑与学情反馈动作，而不是简单砍掉该班型。

解法二：预聚合窗口内复购时间 + LEFT JOIN

```sql
WITH renew_first AS (                -- CTE：每笔到期报名对应的"到期后最早复购时间"
    SELECT
        e.enrollment_id,             -- 报名记录ID
        MIN(o.paid_at) AS renew_paid_at  -- 窗口内最早一笔正价复购时间
    FROM enrollments e
    JOIN orders o
        ON o.student_id = e.student_id               -- 按学员关联订单
       AND o.is_trial = 0                            -- 只认正价课
       AND o.paid_at >= e.end_date                   -- 到期日当天起
       AND o.paid_at < DATE_ADD(e.end_date, INTERVAL 30 DAY)  -- 30天窗口
    WHERE e.status <> '已退费'
      AND e.end_date >= '2024-06-01' AND e.end_date < '2024-07-01'
    GROUP BY e.enrollment_id         -- 按报名记录聚合，一笔报名最多一行，防放大
)
SELECT
    e.class_type,                                        -- 班型
    COUNT(*) AS expired_cnt,                             -- 分母：全部到期报名记录
    COUNT(r.enrollment_id) AS renew_cnt,                 -- 分子：能匹配到复购时间的记录数
    ROUND(COUNT(r.enrollment_id) / COUNT(*), 4) AS renew_rate  -- 续费率
FROM enrollments e
LEFT JOIN renew_first r               -- 左连接保留未续费报名
    ON r.enrollment_id = e.enrollment_id
WHERE e.status <> '已退费'
  AND e.end_date >= '2024-06-01' AND e.end_date < '2024-07-01'
GROUP BY e.class_type
ORDER BY renew_rate DESC;
```

结果解读：LEFT JOIN 版本把"是否续费"物化为能否匹配到一行，COUNT(r.enrollment_id) 天然跳过 NULL，适合后续要在同一查询里追加"续费金额"等指标的场景；两解结果一致，可互相校验口径。

### 5. 性能分析与优化

解法一的 EXISTS 会对每条到期报名做一次 orders 索引探测，分母行数=探测次数；解法二先做一次 JOIN 聚合再回连 enrollments，多了一次物化但把随机探测换成了批量 JOIN，分母很大（数十万级）时通常更快。优化建议：(1) orders 上建 (student_id, is_trial, paid_at) 复合索引，两种写法都能走覆盖索引，这是本题性能的决定性因素；(2) enrollments 上建 (end_date, status) 索引加速分母过滤；(3) 续费窗口天数若为全局统一配置（如30天），可把"到期后是否续费"在数仓层固化为标记字段，报表层避免每次现算；(4) 分母过滤条件里对 end_date 用范围而非函数包裹（不要写 DATE_FORMAT(end_date,'%Y-%m')='2024-06'），否则索引失效。

### 6. 面试延伸考点

- **为什么分母按报名记录而不是按学员？** 一个学员同期多个班到期是多次续费决策，按学员去重会低估续费工作量；若管理层要看"学员口径续费率"，需另出一列并标注口径。
- **已退费的报名为什么从分母剔除？** 退费发生在到期前的报名没有走到续费环节，计入分母会让续费率承担退管理的责任，混淆两个问题；如需监控退费另设退费率指标（见 EDU-27）。
- **到期后60天或90天再续的算不算续费？** 这是业务定义问题：窗口越长续费率越高。正确做法是同时输出30/60/90天三档续费率形成曲线，而不是争论单一数字。
- **如何排除"到期当天原班低价续"的水分？** 可在分子判定中加"新订单 course_id <> 原课程"或金额阈值条件，把真正的转班/扩科与防御性续费区分开。

### 7. 业务拓展思考

分班型续费率是排课与人力决策的核心输入：续费率高的班型可以加大师资储备与开班密度，续费率低的班型要先做归因（师资、教材、时段、班主任跟进频次）再决定收缩。可以进一步联动的动作包括：对"到期前30天"的学员按预测续费概率分层，让班主任优先跟进高价值低概率学员；把续费率与班主任绩效挂钩时必须同时考核续费金额，防止刷单笔小额定金。口径延展上，还可以计算"净续费率"（续费收入/到期应续收入），把金额维度引入，避免大量低价课续费虚高人头续费率。

## EDU-18 课程完课率及完课与续费交叉分析

### 1. 业务背景

教学质检负责人每周要向教务总汇报各课程的完课情况：某门课报读学员里有多少人坚持上完了80%以上的课时，即课程完课率。完课率是教学质量的先行指标——完课率低的课程，学员续费几乎必然塌方。因此汇报里还有一张交叉表：同一门课中，完课学员与未完课学员各自的续费率对比，用来验证"完课驱动续费"的业务假设，并决定对哪些课程启动教学干预（增加督学电话、调整难度、更换讲师）。**【加分点】**能在 SQL 里把"完课"这个模糊词翻译成可计算口径（单学员单课出勤节数/应上节数≥80%）的候选人，在面试中会明显加分。

### 2. 表结构说明

attendance（上课考勤表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| att_id | BIGINT | 考勤记录ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| lesson_date | DATE | 上课日期 |
| status | VARCHAR(10) | 状态：出勤/请假/缺勤 |

示例数据：

| att_id | student_id | course_id | lesson_date | status |
|--------|------------|-----------|-------------|--------|
| 50001 | 801 | 301 | 2024-06-01 | 出勤 |
| 50002 | 801 | 301 | 2024-06-08 | 出勤 |
| 50003 | 801 | 301 | 2024-06-15 | 缺勤 |
| 50004 | 802 | 301 | 2024-06-01 | 出勤 |
| 50005 | 802 | 301 | 2024-06-08 | 请假 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| is_trial | TINYINT | 是否试听课订单：1是，0否 |
| amount | DECIMAL(10,2) | 订单金额 |
| paid_at | DATETIME | 支付时间 |

示例数据：

| order_id | student_id | course_id | is_trial | amount | paid_at |
|----------|------------|-----------|----------|--------|---------|
| 60001 | 801 | 301 | 0 | 6800.00 | 2024-05-20 10:00:00 |
| 60002 | 801 | 305 | 0 | 5200.00 | 2024-07-05 19:00:00 |
| 60003 | 802 | 301 | 0 | 6800.00 | 2024-05-21 14:00:00 |
| 60004 | 803 | 301 | 0 | 6800.00 | 2024-05-22 09:00:00 |
| 60005 | 803 | 307 | 0 | 5200.00 | 2024-07-08 20:00:00 |

### 3. 解题思路

先锁两个口径。完课口径：单个学员在单门课程上的出勤率 = 出勤考勤行数 / 该学员该课程全部考勤行数（出勤+请假+缺勤，请假不占便宜），出勤率≥80% 记为完课；课程完课率 = 该课程完课学员数 / 报读学员数。续费口径：本题将"续费"操作化为"学员在考察期内购买了另一门（course_id 不同）正价课"，即发生了跨课复购；实际业务中更严谨的定义是"上一门课到期后窗口内再购"，面试时应主动说明这一简化及升级方向。实现路径：CTE1 按学员×课程算出勤率并打完课标记；CTE2 或相关子查询判定学员是否有另一门课的正价订单；最后按课程聚合，同时输出课程完课率、完课学员续费率、未完课学员续费率三列。易错点：请假是否算入分母、LEFT JOIN 续费标记时 COUNT 误写为 COUNT(*)、完课率分母混入试听课订单。

### 4. 参考解法

解法一：CTE 分层 + 预聚合续费学员集合（推荐）

```sql
WITH stu_course_att AS (             -- CTE1：学员×课程粒度的出勤率
    SELECT
        student_id,                  -- 学员ID
        course_id,                   -- 课程ID
        SUM(CASE WHEN status = '出勤' THEN 1 ELSE 0 END) / COUNT(*) AS att_rate
                                     -- 出勤率 = 出勤行数 / 全部考勤行数（请假计入分母）
    FROM attendance
    GROUP BY student_id, course_id
),
finish_flag AS (                     -- CTE2：打完课标记
    SELECT
        student_id,
        course_id,
        CASE WHEN att_rate >= 0.8 THEN 1 ELSE 0 END AS is_finish
                                     -- 出勤率≥80% 记为完课（口径可按业务调整）
    FROM stu_course_att
),
renew_stu AS (                       -- CTE3：发生跨课复购（续费）的学员集合
    SELECT student_id
    FROM orders
    WHERE is_trial = 0               -- 只看正价课
    GROUP BY student_id
    HAVING COUNT(DISTINCT course_id) >= 2  -- 持有≥2门不同正价课即视为续费
)
SELECT
    f.course_id,                                         -- 课程ID
    COUNT(*) AS stu_cnt,                                 -- 报读学员数（分母）
    ROUND(SUM(f.is_finish) / COUNT(*), 4) AS finish_rate, -- 课程完课率
    ROUND(SUM(CASE WHEN f.is_finish = 1 AND r.student_id IS NOT NULL THEN 1 ELSE 0 END)
        / NULLIF(SUM(f.is_finish), 0), 4) AS renew_rate_finished,   -- 完课学员续费率
    ROUND(SUM(CASE WHEN f.is_finish = 0 AND r.student_id IS NOT NULL THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*) - SUM(f.is_finish), 0), 4) AS renew_rate_unfinished  -- 未完课学员续费率
FROM finish_flag f
LEFT JOIN renew_stu r                -- 左连接续费学员集合，未续费为NULL
    ON r.student_id = f.student_id
GROUP BY f.course_id
ORDER BY finish_rate ASC;            -- 完课率低的课程排前面，优先干预
```

结果解读：若输出"课程301：完课率72%，完课学员续费率65%，未完课学员续费率18%"，巨大的续费率落差验证了完课驱动续费的假设，教学干预应聚焦把出勤率从50%拉到80%的中间层学员，投入产出比最高。

解法二：EXISTS 相关子查询判定"另一门课复购"（口径更精确）

```sql
WITH stu_course_att AS (             -- CTE：学员×课程出勤率与完课标记
    SELECT
        student_id,
        course_id,
        CASE WHEN SUM(CASE WHEN status = '出勤' THEN 1 ELSE 0 END) / COUNT(*) >= 0.8
             THEN 1 ELSE 0 END AS is_finish   -- 完课标记，一步到位
    FROM attendance
    GROUP BY student_id, course_id
)
SELECT
    f.course_id,                                         -- 课程ID
    COUNT(*) AS stu_cnt,                                 -- 报读学员数
    ROUND(SUM(f.is_finish) / COUNT(*), 4) AS finish_rate, -- 课程完课率
    ROUND(SUM(CASE WHEN f.is_finish = 1 AND EXISTS (          -- 完课且存在另一门课的正价订单
            SELECT 1 FROM orders o
            WHERE o.student_id = f.student_id   -- 同一学员
              AND o.course_id <> f.course_id    -- 课程不同（跨课复购）
              AND o.is_trial = 0                -- 正价课
          ) THEN 1 ELSE 0 END)
        / NULLIF(SUM(f.is_finish), 0), 4) AS renew_rate_finished,
    ROUND(SUM(CASE WHEN f.is_finish = 0 AND EXISTS (
            SELECT 1 FROM orders o
            WHERE o.student_id = f.student_id AND o.course_id <> f.course_id AND o.is_trial = 0
          ) THEN 1 ELSE 0 END)
        / NULLIF(COUNT(*) - SUM(f.is_finish), 0), 4) AS renew_rate_unfinished
FROM stu_course_att f
GROUP BY f.course_id
ORDER BY finish_rate ASC;
```

结果解读：EXISTS 版本把续费判定精确到"本课程之外的另一门课"，排除了同课多期报读的干扰，语义比解法一更贴业务；代价是每行一次子查询探测，课程多、学员多时更依赖订单表索引。

### 5. 性能分析与优化

解法一对 renew_stu 一次聚合、一次 JOIN，订单表只扫一遍；解法二对每个学员×课程行做两次 EXISTS 探测（完课/未完课各写一次），探测次数约等于学员×课程组合数的2倍，组合达十万级时建议合并为一个 CASE 内的双 EXISTS 并确保 orders(student_id, is_trial, course_id) 复合索引存在。优化建议：(1) attendance 按 (student_id, course_id) 建索引或直接使用按该粒度预聚合的汇总表，CTE1 是本题最大开销；(2) 若考勤表很大，可将 status='出勤' 的过滤下推为 SUM(status='出勤') 与 COUNT 的条件聚合写法（本解法已采用），避免先过滤再 COUNT 导致分母丢失；(3) 完课率与续费交叉表可固化为日更中间表，供教学周会直接查询。

### 6. 面试延伸考点

- **请假该不该算进完课分母？** 建议计入（请假也是未完成学习），但补课成功后应回补为出勤；口径必须与教务制度一致并写进指标字典。
- **"续费"简化为跨课复购有什么问题？** 无法区分到期续费与提前囤课；升级方案是取学员上一门课的 end_date（窗口函数取最近一期），判断其后30天内是否再购，面试中能说出升级路径即可。
- **为什么用 NULLIF 包住分母？** 完课学员数为0时除法报错或返回NULL，NULLIF(x,0) 是标准防御写法，配合 COALESCE 显示0更友好。
- **交叉表还能怎么扩展？** 可按出勤率分档（<50%/50-80%/≥80%）输出三档续费率，观察续费率随完课深度的梯度，比二分更能定位干预点。

### 7. 业务拓展思考

完课×续费交叉的价值在于把"教学结果"和"经营结果"接通：交叉数据若显示完课学员续费率显著更高，则应把督学资源（班主任电话、缺勤预警、补课安排）前置到出勤率刚跌破60%的学员身上，而不是等续费期到了再做促销。该结论还可反向用于产品设计——把完课率做成课程详情页的"坚持指数"，帮助销售在试听阶段管理家长预期。口径延展上，可把完课定义从出勤率升级为"出勤率×作业提交率"的加权学习完成度，更贴近真实学习投入。

## EDU-19 学员累计学习时长TOP10%名单

### 1. 业务背景

用户运营团队每月初要从学习行为日志里筛出上月"累计学习时长 TOP10%"的学员，给这批人发"学霸勋章"、寄实体奖品，并邀请进入高意向学员社群——这批学员是续费与转介绍转化率最高的人群，激励预算向他们倾斜的ROI最高。运营专员需要一个能直接导出名单的SQL：名单含学员ID、总学习时长、以及"全国排名前10%"的身份说明，用于自动化推送流程。**【面试高频】**"TOP N%"类需求是窗口函数的入门必考题，NTILE、ROW_NUMBER、PERCENT_RANK 三种写法的边界差异（并列值怎么处理、不足10人怎么办）是面试官的高频追问点。

### 2. 表结构说明

study_logs（学习行为日志表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| log_id | BIGINT | 日志ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| study_minutes | INT | 本次学习分钟数 |
| study_date | DATE | 学习日期 |

示例数据：

| log_id | student_id | course_id | study_minutes | study_date |
|--------|------------|-----------|---------------|------------|
| 70001 | 801 | 301 | 45 | 2024-07-01 |
| 70002 | 801 | 302 | 60 | 2024-07-03 |
| 70003 | 802 | 301 | 30 | 2024-07-02 |
| 70004 | 803 | 303 | 90 | 2024-07-01 |
| 70005 | 803 | 303 | 120 | 2024-07-05 |

### 3. 解题思路

指标口径：TOP10% 按"学员上月累计学习时长"从高到低取前10%名学员，时长=SUM(study_minutes)，统计范围限定 study_date 在考察月内；同一学员多课程、多天日志需先聚合到学员粒度。实现路径：先 GROUP BY 学员求总时长（聚合），再在聚合结果上开窗排序取前10%，这是"先聚合后开窗"的两层结构，必须用 CTE 或派生表包裹聚合结果。取法有三种：NTILE(10) 取第1桶、ROW_NUMBER 配合 COUNT(*) OVER() 按比例截断、PERCENT_RANK 阈值法。易错点：直接在明细表上开窗（忘了先聚合）；NTILE 要求行数≥10否则桶数不足；总时长并列时 NTILE 会硬切并列者、ROW_NUMBER 顺序不稳定，需加第二排序键；10%边界四舍五入规则要提前声明。

### 4. 参考解法

解法一：NTILE 十分位法（简洁直观）

```sql
WITH stu_total AS (                  -- CTE1：学员粒度累计学习时长
    SELECT
        student_id,                  -- 学员ID
        SUM(study_minutes) AS total_minutes  -- 上月累计学习分钟数
    FROM study_logs
    WHERE study_date >= '2024-07-01' AND study_date < '2024-08-01'
                                     -- 限定考察月，避免全表聚合
    GROUP BY student_id
),
ranked AS (                          -- CTE2：在聚合结果上开十分位窗口
    SELECT
        student_id,
        total_minutes,
        NTILE(10) OVER (ORDER BY total_minutes DESC) AS decile
                                     -- 按总时长降序切成10桶，第1桶=前10%
    FROM stu_total
)
SELECT
    student_id,                      -- 学员ID
    total_minutes,                   -- 累计学习时长（分钟）
    decile                           -- 十分位桶号，1即TOP10%
FROM ranked
WHERE decile = 1                     -- 只取第一桶
ORDER BY total_minutes DESC;         -- 名单内部按时长降序展示
```

结果解读：假设学员共2000人，输出200人名单，首尾时长从3260分钟降到1180分钟，说明头部学员学习强度远超均值；该名单可直接对接勋章发放与社群邀约流程。

解法二：ROW_NUMBER + 总行数按比例截断（边界可控）

```sql
WITH stu_total AS (                  -- CTE1：学员粒度累计学习时长（同解法一）
    SELECT
        student_id,
        SUM(study_minutes) AS total_minutes
    FROM study_logs
    WHERE study_date >= '2024-07-01' AND study_date < '2024-08-01'
    GROUP BY student_id
),
ranked AS (                          -- CTE2：行号 + 全局总人数窗口
    SELECT
        student_id,
        total_minutes,
        ROW_NUMBER() OVER (ORDER BY total_minutes DESC, student_id) AS rn,
                                     -- 降序行号；追加student_id作次序键，保证并列时结果稳定
        COUNT(*) OVER () AS total_cnt  -- 全部学员数（窗口不分区，即全局计数）
    FROM stu_total
)
SELECT
    student_id,                      -- 学员ID
    total_minutes,                   -- 累计学习时长
    rn,                              -- 全局排名
    ROUND(rn / total_cnt, 4) AS pct_rank  -- 当前排名占总人数比例，便于核对
FROM ranked
WHERE rn <= CEIL(total_cnt * 0.1)    -- 前10%：向上取整，宁多勿漏（口径可调）
ORDER BY total_minutes DESC, rn;
```

结果解读：CEIL(total_cnt*0.1) 让 195 人取 20 人、2000 人取 200 人，边界规则一目了然；相比 NTILE，该写法明确回答了"到底取几个人"，更适合对接自动化流程。

### 5. 性能分析与优化

两种解法都要经历一次 GROUP BY 聚合和一次排序开窗，成本主要是 study_logs 的扫描与排序。优化建议：(1) study_logs 上建 (study_date, student_id, study_minutes) 复合索引，让考察月过滤与聚合走覆盖索引；(2) 若日志量大（千万级），改为预聚合日表：每日跑一次按学员×日的时长汇总，月度TOP10%只对30行的学员×日小表聚合，成本下降一个数量级；(3) NTILE 与 ROW_NUMBER 都需要在内存/磁盘排序，学员数有限（几十万内）问题不大，若在明细行级开窗则务必避免；(4) 名单只用于运营触达时，可加 LIMIT 弹性截断，但10%规则变了要与运营重新对齐。

### 6. 面试延伸考点

- **NTILE(10) 和 ROW_NUMBER 取TOP10%有什么区别？** NTILE 按桶硬切，并列时长可能被拆进不同桶；ROW_NUMBER+CEIL 规则明确但并列者名次仍随机；若要求并列同进退，应改用 RANK/DENSE_RANK 并接受人数不完全等于10%。
- **时长为0或缺失的学员算不算分母？** 只要当月有日志就进分母，无日志学员不在表里；若业务要求含"零活跃学员"，需要与学员维表 LEFT JOIN 补0，两种口径差异巨大。
- **为什么不能在明细表上直接 NTILE？** 明细行是"学员×课程×日期"粒度，直接开窗选出的将是"学习最久的一次记录"而非"累计最久的学员"，必须先聚合。
- **如何验证名单正确性？** 抽查边缘名次的学员，手算其总时长与第10%分位名次的时长对比；同时输出 total_cnt 与入选人数让业务复核比例。

### 7. 业务拓展思考

TOP10%名单只是学习时长的最右尾，更有经营价值的是完整分布：可按十分位输出各桶的续费率与转介绍率，量化"学习投入→商业结果"的梯度关系，为激励预算分配提供依据。运营动作上，除奖励头部外，应把更多精力放在"时长处于中位数且连续两周下滑"的预警人群，因为把他们拉回均值带来的续费增量大于再奖一个头部学员。口径延展上，纯时长会偏向挂机刷时长，可乘以互动系数（作业提交、课堂发言）合成"学习投入分"，让激励更公平。

## EDU-20 转介绍率及转介绍来源学员榜

### 1. 业务背景

转介绍是教培机构成本最低、质量最高的获客渠道：老学员推荐的新线索信任度高、试听到场率与成交率都显著优于投放渠道。增长负责人每月要看两件事：一是整体转介绍率（转介绍渠道线索占全部线索的比例）及各渠道线索结构，判断获客健康度是否在向低成本渠道迁移；二是找出持续带来成交的"超级推荐人"TOP10，为他们设计阶梯奖励（推荐1人送课时、推荐5人升级会员），把口碑变成可运营的资产。**【加分点】**用 GROUP BY WITH ROLLUP 一次性产出渠道明细加总计行、并用窗口占比代替嵌套子查询，是本考点能让面试官眼前一亮的写法。

### 2. 表结构说明

leads（线索表，含推荐人字段）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | BIGINT | 线索ID，主键 |
| channel | VARCHAR(32) | 获客渠道：抖音/美团/地推/转介绍 |
| referrer_student_id | BIGINT | 推荐人学员ID，仅转介绍渠道非空 |
| student_name | VARCHAR(50) | 线索学员姓名 |
| created_at | DATETIME | 线索创建时间 |
| is_converted | TINYINT | 是否已成交：1是，0否 |

示例数据：

| lead_id | channel | referrer_student_id | student_name | created_at | is_converted |
|---------|---------|---------------------|--------------|------------|--------------|
| 11001 | 转介绍 | 801 | 周小雨 | 2024-07-01 10:00:00 | 1 |
| 11002 | 抖音 | NULL | 吴小涛 | 2024-07-02 11:00:00 | 0 |
| 11003 | 转介绍 | 802 | 郑小雪 | 2024-07-05 15:00:00 | 1 |
| 11004 | 转介绍 | 801 | 冯小磊 | 2024-07-08 09:30:00 | 0 |
| 11005 | 美团 | NULL | 陈小蕾 | 2024-07-09 20:00:00 | 0 |

students（学员表）：

| 字段名 | 类型 | 含义 |
|--------|--------|------|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(50) | 学员姓名 |
| mobile | VARCHAR(20) | 联系手机号 |
| enrolled_at | DATE | 首次报名日期 |
| status | VARCHAR(20) | 状态：在读/结课/退费 |

示例数据：

| student_id | student_name | mobile | enrolled_at | status |
|------------|--------------|--------|-------------|--------|
| 801 | 刘一鸣 | 13800000001 | 2023-09-01 | 在读 |
| 802 | 黄一朵 | 13800000002 | 2023-10-15 | 在读 |
| 803 | 徐子墨 | 13800000003 | 2024-01-08 | 结课 |
| 804 | 何雨桐 | 13800000004 | 2024-03-20 | 在读 |
| 805 | 马思远 | 13800000005 | 2024-05-11 | 在读 |

### 3. 解题思路

本题两问，拆成两个口径。第一问转介绍率：分母=考察期内全部新增线索，分子=channel='转介绍'的线索数；同时给出各渠道线索占比看结构，用 GROUP BY channel WITH ROLLUP 一次得到明细行加总计行，占比用"当前计数 / 全局总计数"的聚合窗口 SUM(COUNT(*)) OVER() 计算，避免再嵌一层子查询。第二问超级推荐人榜：只取转介绍且 referrer_student_id 非空的线索，按推荐人聚合"推荐线索数"与"推荐成交数"（is_converted=1），关联 students 拿姓名，按成交数降序 ROW_NUMBER 取前10。易错点：ROLLUP 产生的 NULL 行要用 IFNULL 转成"总计"标签；占比窗口要写在聚合之后；推荐人榜必须过滤 referrer_student_id IS NOT NULL，防止 NULL 被聚合成一个"幽灵推荐人"；奖励只认成交数而非线索数，防止刷未成交线索薅羊毛。

### 4. 参考解法

解法一：WITH ROLLUP + 窗口占比看渠道结构与转介绍率

```sql
SELECT
    IFNULL(channel, '全部渠道') AS channel,          -- ROLLUP总行channel为NULL，转成可读标签
    COUNT(*) AS lead_cnt,                            -- 该渠道线索数（总行=全部线索数）
    ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4) AS lead_ratio
                                                     -- 渠道占比 = 渠道线索数 / 全局线索数（窗口对全结果求和）
FROM leads
WHERE created_at >= '2024-07-01' AND created_at < '2024-08-01'
                                                     -- 考察期：2024年7月新增线索
GROUP BY channel WITH ROLLUP                        -- 聚合出各渠道明细，并追加一行总计
ORDER BY channel IS NULL DESC, lead_cnt DESC;       -- 总行置顶，明细按线索量降序
```

结果解读：假设总行显示转介绍占比28%、抖音41%、美团21%、地推10%，且转介绍行的 is_converted 均值明显更高，说明获客结构健康度尚可但地推性价比存疑；转介绍率即"转介绍"行的 lead_ratio，一行读数，无需再写子查询。

解法二：CTE 聚合推荐成绩 + ROW_NUMBER 生成超级推荐人榜

```sql
WITH referral_stat AS (              -- CTE：按推荐人聚合推荐成绩
    SELECT
        l.referrer_student_id AS referrer_id,        -- 推荐人学员ID
        COUNT(*) AS referred_leads,                  -- 推荐带来的线索总数
        SUM(l.is_converted) AS referred_converted    -- 其中成交数（只认成交，防刷量）
    FROM leads l
    WHERE l.channel = '转介绍'                       -- 只看转介绍渠道
      AND l.referrer_student_id IS NOT NULL         -- 排除无推荐人的脏数据
      AND l.created_at >= '2024-07-01' AND l.created_at < '2024-08-01'
    GROUP BY l.referrer_student_id
),
ranked AS (                          -- CTE：排名并补齐推荐人姓名
    SELECT
        r.referrer_id,
        s.student_name,                              -- 推荐人姓名（关联学员表）
        r.referred_leads,
        r.referred_converted,
        ROW_NUMBER() OVER (ORDER BY r.referred_converted DESC, r.referred_leads DESC) AS rn
                                                     -- 主序按成交数，次序按线索数，保证唯一且稳定
    FROM referral_stat r
    JOIN students s ON s.student_id = r.referrer_id  -- 内连接：推荐人必须是正式学员
)
SELECT
    rn,                              -- 排名
    referrer_id,                     -- 推荐人ID
    student_name,                    -- 推荐人姓名
    referred_leads,                  -- 推荐线索数
    referred_converted               -- 推荐成交数
FROM ranked
WHERE rn <= 10                       -- TOP10推荐人
ORDER BY rn;
```

结果解读：榜首推荐人一个月带来8条线索、5单成交，是典型的超级推荐人，应触发最高档奖励并由班主任做一次感谢回访；榜单同时暴露了"高线索低成交"的推荐人，其线索质量需要渠道侧复核。

### 5. 性能分析与优化

解法一全表单遍聚合加一个窗口求和，成本最低；解法二两次聚合加一次 JOIN，成本略高但仍是线性复杂度。优化建议：(1) leads 上建 (channel, created_at) 复合索引，让两个 CTE 的过滤都走索引范围扫描；(2) referrer_student_id 相关的聚合可加 (referrer_student_id, is_converted) 索引实现覆盖索引；(3) 榜单若每日刷新，可把 referral_stat 物化并按月分区，历史月份不再重算；(4) 占比若需精确到千分位且避免窗口开销，也可用标量子查询取总数，但数据量大时窗口写法更优。

### 6. 面试延伸考点

- **WITH ROLLUP 的总计行还有什么坑？** 总行上再做聚合类表达式（如AVG）不能直接相加，占比列在总行恒为1，需理解 ROLLUP 行只是"多一行分组结果"而非汇总重算。
- **为什么奖励按成交数而不是线索数？** 线索数可被低成本刷量，成交数与收入挂钩；更严格可按"成交且未退费"计数，把退费时点口径（见 EDU-27）引入奖励风控。
- **转介绍率的分母要不要剔除转介绍自身？** 有两种口径：转介绍/全部线索，或转介绍/(全部-转介绍)即"推荐放大系数"；两者含义不同，报表需标注。
- **如何识别刷单推荐人？** 观察其推荐线索的试听到场率、成交间隔（是否秒成交）与设备/手机号聚集度，SQL 上可用推荐人×被推荐人的注册时间间隔分布做异常检测。

### 7. 业务拓展思考

转介绍体系的核心是让超级推荐人持续被看见：榜单不只发奖励，还应联动班主任在班级群公开致谢、给予课堂展示机会，把物质激励与社交荣誉叠加。结构数据上，若转介绍率逐月上升而投放渠道线索质量下滑，应逐步把预算从投放迁移到"老带新"活动与奖学金体系。口径延展上，可计算"推荐漏斗"：推荐人数量→人均推荐线索→线索试听率→成交率→成交后留存，逐层定位转介绍体系的短板究竟在参与人数还是线索质量。

## EDU-21 连续打卡7天学员识别

### 1. 业务背景

打卡是K12在线教育促活的核心手段：学员每天完成单词打卡或口算打卡，坚持满7天可以领取"坚持之星"勋章并解锁续费优惠券。活动运营在每期打卡活动结束次日，需要从打卡流水里捞出"连续打卡≥7天"的学员名单，分两路使用：一路给运营做勋章发放与社群表扬，一路给销售做高意向线索——能连续7天打卡的学员（及背后的家长）配合度极高，是续费转化的黄金人群。**【面试高频】**"连续N天"是SQL面试的经典母题（gaps and islands 连续区间问题），从登录、签到、学习行为到处方依从性都能换皮出现，两种主流解法都必须掌握。

### 2. 表结构说明

checkins（打卡记录表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| checkin_id | BIGINT | 打卡记录ID，主键 |
| student_id | BIGINT | 学员ID |
| checkin_date | DATE | 打卡日期 |
| source | VARCHAR(20) | 打卡来源：单词/口算/阅读 |

示例数据：

| checkin_id | student_id | checkin_date | source |
|------------|------------|--------------|--------|
| 90001 | 801 | 2024-07-01 | 单词 |
| 90002 | 801 | 2024-07-02 | 单词 |
| 90003 | 801 | 2024-07-04 | 单词 |
| 90004 | 801 | 2024-07-05 | 单词 |
| 90005 | 802 | 2024-07-01 | 口算 |

（注：801号学员在07-01至07-05期间还有更多打卡记录，正文中按"07-01、07-02、07-03、07-04、07-05、07-06、07-07"的连续场景理解其判定逻辑。）

### 3. 解题思路

口径界定：连续打卡指日历日连续（中间断一天即断档），同一学员同一天重复打卡（多来源）要去重，活动期内最长连续天数≥7即入选；输出名单及各自的连续区间与天数，便于运营核对。实现路径有两条经典路线：路线一是"日期减行号"分组法——同一学员的打卡日期按升序编号，若日期连续，则 date 减去行号天数的差值恒定，差值相同即属于同一段连续区间，按差值分组后取 MAX-MIN 与 COUNT 判断长度；路线二是"断点累计"法——用 LAG 找到与前一天的间隔，间隔>1 记为断点，对断点做累计求和生成区间编号，再按编号分组统计。易错点：忘记先按学员×日期去重（同日双打卡会让行号法错位）；行号必须在学员分区内按日期排序；分组键必须同时包含学员ID，否则不同学员的区间会被合并。

### 4. 参考解法

解法一：日期减行号分组法（最经典）

```sql
WITH ordered AS (                    -- CTE1：学员内按日期排序并编号
    SELECT
        student_id,                  -- 学员ID
        checkin_date,                -- 打卡日期
        ROW_NUMBER() OVER (PARTITION BY student_id ORDER BY checkin_date) AS rn
                                     -- 学员分区内的日期升序行号（先去重保证一天一行）
    FROM (SELECT DISTINCT student_id, checkin_date FROM checkins) t
                                     -- 同一天多来源打卡去重，一天只留一行
),
grouped AS (                         -- CTE2：计算"日期-行号"分组键
    SELECT
        student_id,
        checkin_date,
        rn,
        DATE_SUB(checkin_date, INTERVAL rn DAY) AS grp_key
                                     -- 日期连续时，日期与行号同步递增，差值恒定 → 同一连续段
)
SELECT
    student_id,                      -- 学员ID
    MIN(checkin_date) AS streak_start,  -- 连续段起始日
    MAX(checkin_date) AS streak_end,    -- 连续段结束日
    COUNT(*) AS streak_days,            -- 连续天数（段内行数）
    DATEDIFF(MAX(checkin_date), MIN(checkin_date)) + 1 AS days_check
                                     -- 校验列：起止日差+1 应等于 COUNT(*)，不一致说明有重复日期
FROM grouped
GROUP BY student_id, grp_key         -- 双键分组：学员 + 连续段
HAVING COUNT(*) >= 7                 -- 只保留连续≥7天的段（口径线）
ORDER BY streak_days DESC, student_id;
```

结果解读：输出如"801号学员：07-01至07-09，连续9天"，运营按 streak_start/streak_end 核对活动期后即可发奖；若 days_check 与 streak_days 不等，说明去重逻辑出了问题，可作为数据质检信号。

解法二：LAG 断点 + 累计求和分组法

```sql
WITH ordered AS (                    -- CTE1：去重排序，并取前一次打卡日期
    SELECT
        student_id,
        checkin_date,
        LAG(checkin_date) OVER (PARTITION BY student_id ORDER BY checkin_date) AS prev_date
                                     -- 同学员内上一次打卡日期，首行为NULL
    FROM (SELECT DISTINCT student_id, checkin_date FROM checkins) t
),
flagged AS (                         -- CTE2：标记断点
    SELECT
        student_id,
        checkin_date,
        CASE WHEN prev_date IS NULL                       -- 首行视为新段起点
              OR DATEDIFF(checkin_date, prev_date) > 1    -- 与前一天间隔>1天即断档
             THEN 1 ELSE 0 END AS is_break
    FROM ordered
),
grouped AS (                         -- CTE3：断点序号累计 = 区间编号
    SELECT
        student_id,
        checkin_date,
        SUM(is_break) OVER (PARTITION BY student_id ORDER BY checkin_date) AS grp_id
                                     -- 每遇到一个断点，累计和+1，同一连续段内 grp_id 恒定
    FROM flagged
)
SELECT
    student_id,                      -- 学员ID
    MIN(checkin_date) AS streak_start,  -- 段起始日
    MAX(checkin_date) AS streak_end,    -- 段结束日
    COUNT(*) AS streak_days             -- 段内天数
FROM grouped
GROUP BY student_id, grp_id          -- 按学员+区间编号分组
HAVING COUNT(*) >= 7                 -- 连续≥7天
ORDER BY streak_days DESC, student_id;
```

结果解读：断点累计法思路更"显式"——先看见断档，再给每段编号，可读性接近业务语言；两解结果完全一致，面试中先写行号法、再口述断点法思路，是展示深度的标准动作。

### 5. 性能分析与优化

两解都要做一次分区排序（去重 DISTINCT 也隐含排序），复杂度约 O(N log N)，N 为去重后的打卡行数。差异在窗口函数个数：行号法只用 ROW_NUMBER 一个窗口，断点法用 LAG 与滑动 SUM 两个窗口，理论上多一趟窗口计算，但都在同一排序结果上进行，实际差距很小。优化建议：(1) checkins 建 (student_id, checkin_date) 唯一索引，既能加速去重又能从源头避免重复打卡入库；(2) 只在活动期内扫描（WHERE checkin_date BETWEEN 活动起止），避免全表排序；(3) 打卡流水巨大时改为按学员预聚合"最长连续天数"的日增任务：每天只需对比昨日是否连续，增量更新，报表查询退化为单表过滤；(4) 需求只问"是否有连续7天"而不要求区间时，可将 HAVING 条件改为 EXISTS 匹配以提前短路，但窗口方案通常已足够。

### 6. 面试延伸考点

- **同一学员同一天多次打卡为什么不影响行号法？** 会影响！若不去重，同日两行使行号+2而日期+0，grp_key 被破坏，段会被错误切断，所以必须先 DISTINCT，这是本题第一坑。
- **如何求"最长连续打卡天数排行榜"而不是只筛7天？** 把每个学员所有连续段取出后按学员再取 MAX(streak_days)，可用窗口或再次聚合，两层结构注意先段后学员。
- **如果打卡带时间戳、按自然日切分？** 先 DATE() 截断到日再 DISTINCT；跨时区业务要统一按机构所在时区切日，否则深夜打卡会被切到两天。
- **大数据量下这两种方法谁更优？** 渐进复杂度相同；工程上更常用"昨日是否打卡"的增量标记维护连续天数，SQL 区间法适合离线批量与面试。

### 7. 业务拓展思考

连续打卡名单的商业价值不止发奖：它是家长投入度的代理变量，连续打卡≥7天的学员家庭对续费、扩科的接受度显著更高，销售应在勋章发放当天跟进，情绪价值最高。可联动的动作包括：断档即提醒（连续中断24小时内推送"补卡"挽回）、连续天数兑换课时券形成沉没成本。指标口径上，"连续7天"之外还可输出"30天内打卡天数分布""最长连续天数中位数"等稳健指标，避免单点名单的随机波动影响运营判断。

## EDU-22 班主任消息响应时长P50/P90分位数

### 1. 业务背景

家长在班级群里最在意的是"老师多久回我消息"，响应速度直接影响满意度与续费。服务质量负责人每月对班主任做响应时长考核：取每位班主任当月所有家长消息的响应时长（家长发送到班主任回复的分钟数），计算中位数P50与P90——用分位数而非平均数，是因为个别深夜未回的长尾消息会把均值拉爆，P50代表典型体验、P90代表最差的那10%体验的底线。考核结果用于续费前的服务预警与班主任绩效评级。**【避坑指南】**MySQL 8.0 没有 PERCENTILE_CONT 这类分位数聚合函数，必须用窗口函数手工近似，面试中能主动指出这一点并给出 NTILE 或行号法实现，是硬核加分项。

### 2. 表结构说明

messages（家校消息表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| msg_id | BIGINT | 消息ID，主键 |
| class_id | BIGINT | 班级ID |
| teacher_id | BIGINT | 班主任ID |
| student_id | BIGINT | 学员ID |
| sent_at | DATETIME | 家长消息发送时间 |
| replied_at | DATETIME | 班主任回复时间，NULL表示超时未回 |

示例数据：

| msg_id | class_id | teacher_id | student_id | sent_at | replied_at |
|--------|----------|------------|------------|---------|------------|
| 12001 | 501 | 601 | 801 | 2024-07-01 09:00:00 | 2024-07-01 09:08:00 |
| 12002 | 501 | 601 | 802 | 2024-07-02 14:00:00 | 2024-07-02 14:35:00 |
| 12003 | 502 | 602 | 803 | 2024-07-03 18:30:00 | 2024-07-03 18:33:00 |
| 12004 | 502 | 602 | 804 | 2024-07-05 22:00:00 | 2024-07-06 07:30:00 |
| 12005 | 501 | 601 | 801 | 2024-07-08 10:00:00 | NULL |

### 3. 解题思路

口径界定：响应时长 = TIMESTAMPDIFF(MINUTE, sent_at, replied_at)，只统计已回复消息（replied_at 非空）且时长≥0（排除乱序脏数据）；超时未回的消息不计入分位数，但必须另列"未回复率"作为配套指标，否则把消息晾着反而"优化"了分位数，这是本指标最危险的博漏洞点。每位班主任输出P50与P90两个数。实现路径：因为 MySQL 8.0 无分位数聚合函数，用窗口近似——解法一在班主任分区内按响应时长排序取行号与分区总数，P50即第 CEIL(n*0.5) 行、P90即第 CEIL(n*0.9) 行的值，用条件聚合把两行折到一行输出；解法二用 NTILE(100) 百分桶，取第50桶与第90桶的最大值作为近似分位数。易错点：分区键必须是 teacher_id；n 较小时 NTILE 桶数会少于100导致桶号错位；同一班主任行数≤1时两分位数相等属正常现象。

### 4. 参考解法

解法一：行号 + 分区总数定位分位（精确可控）

```sql
WITH resp AS (                       -- CTE：清洗后的响应时长 + 排名信息
    SELECT
        teacher_id,                  -- 班主任ID
        TIMESTAMPDIFF(MINUTE, sent_at, replied_at) AS resp_min
                                     -- 响应时长（分钟）= 回复时间 - 发送时间
    FROM messages
    WHERE replied_at IS NOT NULL     -- 只统计已回复消息
      AND replied_at >= sent_at      -- 排除乱序脏数据（回复早于发送）
      AND sent_at >= '2024-07-01' AND sent_at < '2024-08-01'  -- 考察月
),
ranked AS (                          -- CTE：分区内按响应时长升序编号，并记录分区行数
    SELECT
        teacher_id,
        resp_min,
        ROW_NUMBER() OVER (PARTITION BY teacher_id ORDER BY resp_min) AS rn,
                                     -- 升序行号，第k行即第k小的响应时长
        COUNT(*) OVER (PARTITION BY teacher_id) AS cnt
                                     -- 该班主任当月有效消息总数
    FROM resp
)
SELECT
    teacher_id,                      -- 班主任ID
    MAX(CASE WHEN rn = CEIL(cnt * 0.5) THEN resp_min END) AS p50_min,
                                     -- 中位数：第 ceil(n/2) 小的值
    MAX(CASE WHEN rn = CEIL(cnt * 0.9) THEN resp_min END) AS p90_min,
                                     -- P90：第 ceil(n*0.9) 小的值
    COUNT(*) AS msg_cnt              -- 有效消息数，用于判断分位数可信度
FROM ranked
GROUP BY teacher_id
ORDER BY p90_min DESC;               -- P90差的班主任排前面，优先辅导
```

结果解读：假设输出"602号班主任：P50=5分钟，P90=570分钟"，说明其典型响应很快，但深夜消息次日才回拉高了P90，改进方向是夜间值班轮换而非整体提速；msg_cnt 过小（如<20）的班主任分位数波动大，考核时应标注置信度。

解法二：NTILE 百分桶近似

```sql
WITH resp AS (                       -- CTE：清洗后的响应时长
    SELECT
        teacher_id,
        TIMESTAMPDIFF(MINUTE, sent_at, replied_at) AS resp_min
    FROM messages
    WHERE replied_at IS NOT NULL
      AND replied_at >= sent_at
      AND sent_at >= '2024-07-01' AND sent_at < '2024-08-01'
),
bucketed AS (                        -- CTE：分区内按响应时长升序切成100个百分位桶
    SELECT
        teacher_id,
        resp_min,
        NTILE(100) OVER (PARTITION BY teacher_id ORDER BY resp_min) AS bucket
                                     -- 第1桶=最小的1%，第50桶≈中位数，第90桶≈P90
    FROM resp
)
SELECT
    teacher_id,                      -- 班主任ID
    MAX(CASE WHEN bucket = 50 THEN resp_min END) AS p50_min,
                                     -- 第50桶内的最大值作为P50近似
    MAX(CASE WHEN bucket = 90 THEN resp_min END) AS p90_min,
                                     -- 第90桶内的最大值作为P90近似
    MIN(resp_min) AS fastest_min,    -- 附赠：最快响应，用于横向对比服务态度
    MAX(resp_min) AS slowest_min     -- 附赠：最慢响应，观察长尾极值
FROM bucketed
GROUP BY teacher_id
ORDER BY p90_min DESC;
```

结果解读：NTILE 版本顺手输出了最快/最慢两端，便于做完整的服务画像；需注意当某班主任消息数不足100条时，桶数等于消息数，第90桶会退化为接近最大值，此时应改用解法一的行号法。

### 5. 性能分析与优化

两解都需要对每个班主任分区排序，复杂度 O(N log N)。解法一窗口更少（ROW_NUMBER+COUNT 可共用同一排序），解法二 NTILE 同样一次排序，开销接近。优化建议：(1) messages 建 (teacher_id, sent_at) 复合索引，考察月过滤加分区排序都能受益；(2) 未回复消息建议单独打标（replied_at IS NULL 或加 status 字段），"未回复率"用 COUNT(CASE WHEN replied_at IS NULL THEN 1 END)/COUNT(*) 一并输出，避免只考分位数引发晾消息博弈；(3) 消息表为千万级大表时，按月预聚合到"班主任×月"的响应时长明细小表再算分位数，或直接在ETL层用 Iceberg/Spark 的 percentile 函数算好落表；(4) CEIL(cnt*0.9) 在 cnt 很小时对边界敏感，报表需同时展示 cnt。

### 6. 面试延伸考点

- **为什么用P50/P90而不用平均响应时长？** 响应时长右偏严重，均值被极端长尾绑架；分位数稳健，且P90直接对应"最差体验底线"，与考核目标一致。
- **超时未回的消息怎么处理才合理？** 不计入分位数但要单独考核未回复率，或给未回消息赋一个封顶惩罚值（如1440分钟）纳入P90，两种口径都可，关键是全公司统一。
- **分位数还有别的SQL写法吗？** PERCENT_RANK() 窗口找出累计百分比首次≥0.9的行；或对去重后的时长值做 CUME_DIST；MySQL 8.0 之外， Hive/Spark 有 percentile_approx，PostgreSQL 有 percentile_cont 有序集聚合。
- **P50相同怎么比较两个班主任？** 引入P90、未回复率做二级排序，或比较P50与P90的差距（响应稳定性），单一分位数不构成完整评价。

### 7. 业务拓展思考

响应时长数据若与续费率关联，通常能看到"P90<30分钟的班主任其班级续费率显著更高"，从而把服务SLA从感觉变成数字承诺，对外可包装成"30分钟必响应"的服务卖点。运营动作上，对P90超标班主任先看时段分布：若集中在晚间与周末，解法是排班而非批评；若集中在特定家长，则是关系管理问题。口径延展上，可按消息类型（请假/作业疑问/投诉）分别计算分位数，投诉响应的考核权重应远高于常规寒暄，一刀切的P90会误导改进方向。

## EDU-23 渠道ROI：获客成本对比首期收入

### 1. 业务背景

市场部每个季度要向管理层汇报投放效果，核心问题是"每个渠道花出去的钱换回多少首期收入"：ROI = 首期收入 ÷ 获客成本。抖音适合起量、美团流量精准但贵、地推便宜但看人、转介绍几乎零成本——只有把各渠道当季广告花费与该渠道线索带来的首期正价收入摆到一张表上，Q4预算才能砍得有理有据。财务与市场对ROI口径常有分歧，因此SQL里必须写清归因规则。**【加分点】**多来源指标合成类题目，用分层CTE把"成本"与"收入"各自聚合干净再JOIN，并处理"有花费无收入""有收入无花费"的渠道，是体现数据严谨性的最佳机会。

### 2. 表结构说明

ad_spend（广告花费表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| spend_id | BIGINT | 花费记录ID，主键 |
| channel | VARCHAR(32) | 渠道 |
| spend_month | CHAR(7) | 花费月份，如2024-07 |
| cost | DECIMAL(12,2) | 当月花费金额 |

示例数据：

| spend_id | channel | spend_month | cost |
|----------|---------|-------------|------|
| 13001 | 抖音 | 2024-07 | 120000.00 |
| 13002 | 美团 | 2024-07 | 60000.00 |
| 13003 | 地推 | 2024-07 | 15000.00 |
| 13004 | 抖音 | 2024-08 | 100000.00 |
| 13005 | 美团 | 2024-08 | 55000.00 |

leads（线索表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | BIGINT | 线索ID，主键 |
| channel | VARCHAR(32) | 来源渠道 |
| student_name | VARCHAR(50) | 学员姓名 |
| created_at | DATETIME | 线索创建时间 |

示例数据：

| lead_id | channel | student_name | created_at |
|---------|---------|--------------|------------|
| 14001 | 抖音 | 罗小川 | 2024-07-03 10:00:00 |
| 14002 | 抖音 | 高小远 | 2024-07-05 14:00:00 |
| 14003 | 美团 | 谢小楠 | 2024-07-06 19:00:00 |
| 14004 | 地推 | 唐小禾 | 2024-07-07 11:00:00 |
| 14005 | 转介绍 | 曹小易 | 2024-07-09 09:00:00 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| lead_id | BIGINT | 关联线索ID |
| is_trial | TINYINT | 是否试听课订单：1是，0否 |
| amount | DECIMAL(10,2) | 订单金额 |
| paid_at | DATETIME | 支付时间 |

示例数据：

| order_id | lead_id | is_trial | amount | paid_at |
|----------|---------|----------|--------|---------|
| 15001 | 14001 | 0 | 6800.00 | 2024-07-15 20:00:00 |
| 15002 | 14002 | 0 | 4800.00 | 2024-07-20 11:00:00 |
| 15003 | 14003 | 0 | 8800.00 | 2024-07-25 15:00:00 |
| 15004 | 14005 | 0 | 6800.00 | 2024-07-18 19:30:00 |
| 15005 | 14004 | 1 | 0.00 | 2024-07-12 10:00:00 |

### 3. 解题思路

先把归因口径写死，这是本题的灵魂。首期收入口径：线索创建当月内，该线索产生的全部正价课订单金额（is_trial=0），归属到线索的渠道；即"当月投放 → 当月线索 → 当月转化"的同月归因，跨月转化的长周期渠道会被低估，应另出"90天归因"版本对照。获客成本口径：ad_spend 中该渠道当月花费之和。ROI = 首期收入 ÷ 获客成本，成本为0（转介绍）时需用 NULLIF 防除零并显示为"无需投放"。实现路径：CTE1按渠道聚合季度成本，CTE2把线索与订单关联后按渠道聚合首期收入，两表 FULL 对齐——MySQL 没有 FULL OUTER JOIN，用 LEFT JOIN 覆盖"有花费无收入"，再 UNION 补"有收入无花费"（转介绍）的渠道；或以成本表为主 LEFT JOIN 并接受转介绍ROI缺失另列。易错点：先JOIN再聚合导致花费被订单行数放大，ROI虚低；忘记过滤试听课订单；月份用 DATE_FORMAT 匹配导致索引失效。

### 4. 参考解法

解法一：分层CTE + LEFT JOIN + UNION 补齐单边渠道（推荐）

```sql
WITH channel_cost AS (               -- CTE1：季度内各渠道总花费
    SELECT
        channel,                     -- 渠道
        SUM(cost) AS total_cost      -- 季度花费合计
    FROM ad_spend
    WHERE spend_month IN ('2024-07', '2024-08', '2024-09')  -- 考察季度
    GROUP BY channel
),
channel_revenue AS (                 -- CTE2：各渠道首期收入（同月归因）
    SELECT
        l.channel,
        SUM(o.amount) AS first_revenue   -- 正价订单金额合计
    FROM leads l
    JOIN orders o
        ON o.lead_id = l.lead_id
       AND o.is_trial = 0                -- 只算正价课，试听课0元单剔除
    WHERE DATE_FORMAT(l.created_at, '%Y-%m') = DATE_FORMAT(o.paid_at, '%Y-%m')
                                     -- 同月归因：订单支付月份 = 线索创建月份
      AND l.created_at >= '2024-07-01' AND l.created_at < '2024-10-01'
    GROUP BY l.channel
),
merged AS (                          -- CTE3：成本为主左连收入，补齐"有收入无花费"渠道
    SELECT
        c.channel,
        c.total_cost,
        COALESCE(r.first_revenue, 0) AS first_revenue   -- 有花费无收入按0计
    FROM channel_cost c
    LEFT JOIN channel_revenue r ON r.channel = c.channel
    UNION ALL                        -- 追加只有收入没有花费的渠道（如转介绍）
    SELECT
        r.channel,
        0 AS total_cost,             -- 无投放成本
        r.first_revenue
    FROM channel_revenue r
    WHERE r.channel NOT IN (SELECT channel FROM channel_cost)
                                     -- 防止与LEFT JOIN结果重复
)
SELECT
    channel,                         -- 渠道
    total_cost,                      -- 获客成本
    first_revenue,                   -- 首期收入
    ROUND(first_revenue / NULLIF(total_cost, 0), 2) AS roi
                                     -- ROI = 收入/成本；NULLIF防除零（成本0时ROI为NULL）
FROM merged
ORDER BY roi DESC;                   -- ROI降序，预算向高ROI渠道倾斜
```

结果解读：假设抖音ROI 0.61、美团 0.85、地推 1.40、转介绍成本为0收入6800，说明当季各付费渠道首期收入均未回本——但K12的LTV主要来自续费，首期ROI低不一定砍预算，应结合EDU-17续费率看全周期ROI，这层解读正是面试亮点。

解法二：派生表两段聚合后相除（MySQL 5.7 兼容写法）

```sql
SELECT
    c.channel,                                           -- 渠道
    c.total_cost,                                        -- 季度成本
    COALESCE(r.first_revenue, 0) AS first_revenue,       -- 首期收入（无转化补0）
    ROUND(COALESCE(r.first_revenue, 0) / NULLIF(c.total_cost, 0), 2) AS roi
FROM (
    SELECT channel, SUM(cost) AS total_cost              -- 派生表1：成本聚合
    FROM ad_spend
    WHERE spend_month IN ('2024-07', '2024-08', '2024-09')
    GROUP BY channel
) c
LEFT JOIN (
    SELECT l.channel, SUM(o.amount) AS first_revenue     -- 派生表2：收入聚合
    FROM leads l
    JOIN orders o ON o.lead_id = l.lead_id AND o.is_trial = 0
    WHERE DATE_FORMAT(l.created_at, '%Y-%m') = DATE_FORMAT(o.paid_at, '%Y-%m')
      AND l.created_at >= '2024-07-01' AND l.created_at < '2024-10-01'
    GROUP BY l.channel
) r ON r.channel = c.channel
ORDER BY roi DESC;
```

结果解读：派生表版本逻辑与解法一的主体完全一致，只是省去转介绍等"零成本渠道"的补齐分支，适合汇报口径为"付费渠道ROI"的场景；两张派生表各自先聚合再JOIN，杜绝了花费被放大的问题。

### 5. 性能分析与优化

解法一三个CTE各扫一遍源表，规模为成本表行数+线索×订单行数，线性可控；解法二结构相同少一次UNION。优化建议：(1) orders(lead_id, is_trial) 与 leads(created_at) 建索引；月份匹配改写为范围条件（o.paid_at >= l.created_at 当月初 AND < 次月初）可利用索引并避免对两列套 DATE_FORMAT 导致函数计算，精确写法是用 DATE_FORMAT(o.paid_at,'%Y-%m') = DATE_FORMAT(l.created_at,'%Y-%m') 时接受函数开销，或在ETL层预生成"订单月份""线索月份"冗余列；(2) 收入聚合中 leads 与 orders 是一对多，金额 SUM 不会放大（金额属于订单），但要警惕把成本表也JOIN进来后再SUM的错误写法；(3) 季度报表可固化为月度中间表，季度末只做四则运算。

### 6. 面试延伸考点

- **为什么不能把三张表直接JOIN后一次SUM？** 花费行会被线索数、订单数逐级放大，SUM(cost) 变成"花费×订单数"，ROI被系统性低估，必须分源聚合后再JOIN，这是本题主考的放大陷阱。
- **首期收入为什么按线索创建月归因而非支付月？** 与投放月份对齐才能算清"这个月花的钱带来多少收入"；两种归因差异即转化周期，可同时输出对照。
- **转介绍ROI显示为NULL合适吗？** 数学上除零无意义，业务上可显示为无穷大或标注"自然流量"，但把转介绍纳入资源分配时要看规模（收入绝对值）而非只看比率。
- **如何升级为全周期ROI？** 把线索关联学员后续所有续费订单（LTV口径），或用EDU-17的续费率乘首期客单估算，SQL上需打通lead→student的映射链。

### 7. 业务拓展思考

ROI表的价值在于把预算会从"感觉之争"变成"数字之争"：首期ROI低的抖音若续费率高，全周期ROI可能反超，因此建议渠道报表固定输出"首期ROI、90天收入、续费率"三列联动。运营动作上，高ROI渠道应加预算至边际ROI递减点，低ROI渠道先做素材与落地页A/B再决定去留。口径延展上，ROI之外还可输出单线索成本、单成交成本、单试听成本三级漏斗成本，定位渠道问题究竟出在流量质量还是销售转化。

## EDU-24 学员上课间隔天数分布

### 1. 业务背景

学习节奏是留存的生命线：班主任经验表明，两次上课间隔超过一周的学员大概率正在流失，等到期再挽回就晚了。教学运营需要一张"上课间隔天数分布表"——把所有学员相邻两次上课的间隔收集起来，按1-3天、4-7天、8-15天、15天以上分桶统计占比，看整体学习节奏是否健康、以及哪个间隔段的人数在膨胀；同时圈出"最近一次间隔>15天"的学员名单推给班主任做回访。**【面试高频】**LAG取相邻记录再算差值是窗口函数的经典应用，与自连接/相关子查询写法的性能对比是标配追问。

### 2. 表结构说明

attendance（上课出勤表，仅出勤记录）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| att_id | BIGINT | 记录ID，主键 |
| student_id | BIGINT | 学员ID |
| class_date | DATE | 上课日期 |
| status | VARCHAR(10) | 状态：出勤/请假/缺勤 |

示例数据：

| att_id | student_id | class_date | status |
|--------|------------|------------|--------|
| 16001 | 801 | 2024-07-01 | 出勤 |
| 16002 | 801 | 2024-07-03 | 出勤 |
| 16003 | 801 | 2024-07-10 | 出勤 |
| 16004 | 802 | 2024-07-02 | 出勤 |
| 16005 | 802 | 2024-07-20 | 出勤 |

### 3. 解题思路

口径界定：间隔 = 同一学员相邻两次"出勤"上课日期的天数差，只统计出勤（请假缺勤不算真实学习发生）；首次上课没有前序记录，不产生间隔；同一学员同一天多节课压缩为一天。分析路径分两步：先用窗口按学员分区、日期升序，LAG 取上一次上课日期，DATEDIFF 算间隔；再把间隔按业务分桶（1-3天=高频节奏、4-7天=正常周节奏、8-15天=节奏拖慢、15天以上=流失预警），统计各桶间隔次数与占比，并可加 MIN(gap_days) 排序保证桶序。易错点：LAG 的分区键与排序键写反；忘记剔除首行（prev为NULL时DATEDIFF返回NULL需过滤）；同日多节未去重导致间隔0天虚增高频桶；分桶边界（15天以上是否含15）要与业务确认。

### 4. 参考解法

解法一：LAG 窗口 + 条件分桶聚合（推荐）

```sql
WITH ordered AS (                    -- CTE1：学员内按上课日期排序并取前一次日期
    SELECT
        student_id,                  -- 学员ID
        class_date,                  -- 本次上课日期
        LAG(class_date) OVER (PARTITION BY student_id ORDER BY class_date) AS prev_date
                                     -- 同学员上一次出勤上课日期，首次为NULL
    FROM (
        SELECT DISTINCT student_id, class_date
        FROM attendance
        WHERE status = '出勤'        -- 只看出勤，请假缺勤不算学习发生
    ) t                              -- 去重：同日多节课压成一天
),
gaps AS (                            -- CTE2：计算相邻间隔
    SELECT
        student_id,
        DATEDIFF(class_date, prev_date) AS gap_days
                                     -- 间隔天数 = 本次日期 - 上次日期
    FROM ordered
    WHERE prev_date IS NOT NULL      -- 首次上课无前序，不产生间隔
)
SELECT
    CASE WHEN gap_days <= 3  THEN '1-3天'
         WHEN gap_days <= 7  THEN '4-7天'
         WHEN gap_days <= 15 THEN '8-15天'
         ELSE '15天以上' END AS gap_bucket,      -- 业务分桶（左闭右闭，边界已与运营确认）
    COUNT(*) AS interval_cnt,        -- 落在该桶的间隔次数
    ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4) AS ratio  -- 桶占比（窗口求全局总数）
FROM gaps
GROUP BY CASE WHEN gap_days <= 3  THEN '1-3天'
              WHEN gap_days <= 7  THEN '4-7天'
              WHEN gap_days <= 15 THEN '8-15天'
              ELSE '15天以上' END   -- 按分桶表达式分组（与SELECT一致）
ORDER BY MIN(gap_days);              -- 按最小间隔排序，保证桶从短到长排列
```

结果解读：假设输出"1-3天占38%、4-7天占41%、8-15天占14%、15天以上占7%"，说明多数学习节奏健康；若8-15天桶环比翻倍，则是节奏性流失的前兆信号，应触发督学干预。

解法二：相关子查询找前一次上课日期（无LAG写法）

```sql
SELECT
    CASE WHEN gap_days <= 3  THEN '1-3天'
         WHEN gap_days <= 7  THEN '4-7天'
         WHEN gap_days <= 15 THEN '8-15天'
         ELSE '15天以上' END AS gap_bucket,          -- 同样的业务分桶
    COUNT(*) AS interval_cnt,                        -- 各桶间隔次数
    ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4) AS ratio
FROM (
    SELECT
        DATEDIFF(a.class_date,
                 (SELECT MAX(b.class_date)          -- 相关子查询：小于当前日期的最大上课日
                  FROM attendance b
                  WHERE b.student_id = a.student_id -- 同一学员
                    AND b.class_date < a.class_date -- 严格早于当前记录
                 )) AS gap_days                     -- 即"上一次上课日期"，等价于LAG
    FROM (
        SELECT DISTINCT student_id, class_date
        FROM attendance
        WHERE status = '出勤'
    ) a
) g
WHERE gap_days IS NOT NULL          -- 首次上课的学员子查询返回NULL，剔除
GROUP BY CASE WHEN gap_days <= 3  THEN '1-3天'
              WHEN gap_days <= 7  THEN '4-7天'
              WHEN gap_days <= 15 THEN '8-15天'
              ELSE '15天以上' END
ORDER BY MIN(gap_days);
```

结果解读：相关子查询对每行执行一次 MAX 查找，语义与LAG等价、结果一致，适合展示"没有窗口函数的版本"；出勤记录到十万行以上时其逐行探测代价会明显劣于LAG的单一排序，这正是两个版本的差异点。

### 5. 性能分析与优化

解法一一次排序完成去重、LAG与DATEDIFF，整体 O(N log N)；解法二在外层每行触发一次相关子查询，最坏 O(N²)（索引好时 O(N log N)），大表下差距悬殊。优化建议：(1) attendance 建 (student_id, class_date) 复合索引，解法二的 MAX 子查询可走索引范围扫描，解法一的窗口排序可直接利用索引序；(2) 出勤明细大时预聚合"学员×日"出勤表，间隔计算只在小表上做；(3) 若只需预警名单（最近间隔>15天），可加 WHERE class_date >= 近90天 限定窗口，避免扫全历史；(4) 分桶占比用窗口求和代替嵌套子查询取总数，省一次全表扫描。

### 6. 面试延伸考点

- **LAG与自连接取相邻记录怎么选？** LAG一次排序解决，自连接需要先证明"相邻"（b.date<a.date 且不存在中间记录）再连接，写法复杂且易错，窗口函数是首选。
- **同一天两节课怎么算间隔？** 业务上间隔0天无意义，应先按学员×日期去重；若想保留"一天多节"的信息，另设"日上课节数"指标。
- **如何输出每个学员的最近间隔做预警名单？** 对每个学员取日期最大行的 LAG 值，可用窗口 ROW_NUMBER 倒序取第一行，或 MAX(class_date) 配相关子查询。
- **间隔分布要不要按课程/班型拆分？** 要：一对一每周固定与大小班自选节奏完全不同，混在一起的分布会掩盖真实问题，分维度后各看各的基线。

### 7. 业务拓展思考

间隔分布是"学习节奏健康度"的地基指标：把各桶占比做成周趋势，8-15天与15天以上两桶的膨胀几乎总是先于续费率下滑出现，可当作流失预警的领先指标。运营动作上，预警名单应交给班主任在间隔第5天（还没彻底断）时触达，话术聚焦"落下的课怎么补"而非"快来续费"；对高频桶学员则可推荐加课扩科。口径延展上，可把间隔与"完课率"（EDU-18）交叉，区分"来得很勤但没学会"与"来都不来"两类风险，干预策略完全不同。

## EDU-25 月活跃学员统计（上课或作业任一）

### 1. 业务背景

在线教育里"学员活跃"有两个触点：来上课（教学侧）与提交作业（督学侧）。只统计上课会漏掉"本周没排课但天天交作业"的学员，只统计作业会漏掉"上完课从不写作业"的学员，两个单口径都会误导运营判断。运营总监每月1日要上月月活（MAU）报表：月活总数、只上课人数、只交作业人数、双触点人数四列并列，用于判断督学产品渗透率与排课密度是否健康，同时把"连续两月零触点"的学员列为沉默名单交给班主任做召回。**【面试高频】**多来源合并去重计数（UNION ALL + COUNT DISTINCT/条件聚合）是流量统计的母题，电商的"下单或浏览活跃"、社交的"发言或点赞活跃"都是同构题，合并时"来源标签怎么打、去重在哪个粒度做"是面试官必问的两问。

### 3. 解题思路

口径界定：月份取自然月；上课活跃=当月至少一条"出勤"记录（缺勤、请假不算上课触点，但缺勤学员若交了作业仍算活跃）；作业活跃=当月至少一次作业提交；月活=任一触点，且按学员去重——同一学员当月上10节课只算1个活跃。输出：每月的MAU、只上课、只交作业、双触点四列。实现路径：解法一先把两表UNION ALL打上来源标签，聚合到"学员×月"粒度（MAX出两个触点标志），再按月条件聚合拆出四个人群——去重发生在学员月粒度，天然正确；解法二用递归CTE生成月份骨架，逐月用标量子查询统计两来源人数、用EXISTS OR判断学员是否活跃，优点是没有学员的月份也输出0，报表不断行。易错点：用UNION而非UNION ALL，来源标签被跨表去重吃掉且多付一次排序代价；跳过"学员×月"中间粒度直接在UNION行上COUNT(CASE)，双触点学员会被重复计入两个单边人群；把DATE_FORMAT包在WHERE条件里导致索引失效（本题主键聚合场景影响小，但习惯必须正确）。

### 4. 参考解法

解法一：UNION ALL打标 + 学员月粒度去重 + 条件聚合（推荐）

```sql
WITH act AS (                        -- CTE1：两来源合并，打来源标签
    SELECT
        student_id,                  -- 学员ID
        attend_date AS act_date,     -- 行为日期（统一列名）
        1 AS src                     -- 来源标签：1=上课出勤
    FROM attendance
    WHERE status = '出勤'            -- 缺勤请假不算上课触点
    UNION ALL                        -- 不去重，保留全部行与来源信息
    SELECT
        student_id,
        submit_date,                 -- 作业提交日期
        2 AS src                     -- 来源标签：2=作业提交
    FROM homeworks
),
sm AS (                              -- CTE2：聚合到"学员×月"粒度，生成触点标志
    SELECT
        DATE_FORMAT(act_date, '%Y-%m') AS ym,              -- 自然月
        student_id,
        MAX(CASE WHEN src = 1 THEN 1 ELSE 0 END) AS att_flag,
                                     -- 当月是否有出勤（0/1标志）
        MAX(CASE WHEN src = 2 THEN 1 ELSE 0 END) AS hw_flag
                                     -- 当月是否交过作业（0/1标志）
    FROM act
    GROUP BY DATE_FORMAT(act_date, '%Y-%m'), student_id
                                     -- 学员×月去重：一月一学员只留一行
)
SELECT
    ym,                              -- 月份
    COUNT(*) AS mau,                 -- 月活 = 任一触点的学员数
    SUM(CASE WHEN att_flag = 1 AND hw_flag = 0 THEN 1 ELSE 0 END) AS only_att,
                                     -- 只上课人群
    SUM(CASE WHEN hw_flag = 1 AND att_flag = 0 THEN 1 ELSE 0 END) AS only_hw,
                                     -- 只交作业人群
    SUM(CASE WHEN att_flag = 1 AND hw_flag = 1 THEN 1 ELSE 0 END) AS both_cnt,
                                     -- 双触点人群
    ROUND(SUM(CASE WHEN att_flag = 1 AND hw_flag = 1 THEN 1 ELSE 0 END)
        / COUNT(*), 4) AS both_ratio -- 双触点占比，衡量督学渗透率
FROM sm
GROUP BY ym
ORDER BY ym;
```

结果解读：假设输出"2024-07：MAU=420，只上课235，只交作业98，双触点87"，双触点占比20.7%偏低，说明作业督学对上课人群渗透不足；802号学员当月缺勤但交了作业，仍计入月活并落在"只交作业"组，符合"任一触点"口径。

解法二：递归CTE月份骨架 + EXISTS判活（月份不断行）

```sql
WITH RECURSIVE months AS (           -- 递归生成2024年逐月骨架
    SELECT CAST('2024-01-01' AS DATE) AS month_start
                                     -- 骨架起点：2024年1月1日
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH
                                     -- 每次递推加一个月
    FROM months
    WHERE month_start < '2024-12-01' -- 终止条件：递推到12月为止
)
SELECT
    DATE_FORMAT(m.month_start, '%Y-%m') AS ym,         -- 月份标签
    (SELECT COUNT(DISTINCT a.student_id)               -- 当月上课人数
     FROM attendance a
     WHERE a.status = '出勤'
       AND a.attend_date >= m.month_start
       AND a.attend_date < m.month_start + INTERVAL 1 MONTH
                                     -- 月初含、次月初不含的半开区间，可走索引
    ) AS att_users,
    (SELECT COUNT(DISTINCT h.student_id)               -- 当月交作业人数
     FROM homeworks h
     WHERE h.submit_date >= m.month_start
       AND h.submit_date < m.month_start + INTERVAL 1 MONTH
    ) AS hw_users,
    (SELECT COUNT(*)                                   -- 当月MAU：任一触点去重
     FROM students s
     WHERE EXISTS (SELECT 1                            -- 触点一：当月有出勤
                   FROM attendance a
                   WHERE a.student_id = s.student_id
                     AND a.status = '出勤'
                     AND a.attend_date >= m.month_start
                     AND a.attend_date < m.month_start + INTERVAL 1 MONTH)
        OR EXISTS (SELECT 1                            -- 触点二：当月有交作业
                   FROM homeworks h
                   WHERE h.student_id = s.student_id
                     AND h.submit_date >= m.month_start
                     AND h.submit_date < m.month_start + INTERVAL 1 MONTH)
    ) AS mau
FROM months m
ORDER BY ym;
```

结果解读：骨架法每月必有输出，1月还没开学也能给出MAU=0的行，趋势图不会断线；EXISTS的OR会被优化器改写为两个半连接取并，配合(student_id, 日期)索引可控制在毫秒级，但学员规模极大时解法一的一次扫描通常更稳。

### 5. 性能分析与优化

解法一扫两表各一次后做两级聚合，代价约 O(N log N)，N为两表行数之和；解法二对每个月执行三个相关子查询，索引良好时是12×3次范围/半连接扫描，月份跨度拉长到几年时子查询次数线性增长。优化建议：(1) attendance 建 (student_id, attend_date)、homeworks 建 (student_id, submit_date) 复合索引，解法二的EXISTS与标量子查询都可走索引；(2) 两张流水表按月分区或按月归档，报表只碰相关月份的分片；(3) 数仓标准收口是建"学员×日活跃"日增中间表（当天出勤或交作业即写一行），月活查询退化为单表按月COUNT DISTINCT，沉默名单也从这张表反向取；(4) 若只需MAU总数，解法一的CTE2可省略，直接对UNION结果COUNT(DISTINCT student_id)，但要拆四个人群时学员月粒度聚合不可省。

### 6. 面试延伸考点

- **为什么必须UNION ALL而不是UNION？** UNION会跨来源去重，"同一天上课又交作业"的两行被压成一行后来源标签丢失，还要多付一次排序；本题的去重应在"学员×月"粒度用GROUP BY完成，不是在合并阶段。
- **双触点人数能不能分别COUNT两个来源再相加？** 不能，需要容斥（交集难算）；把标签聚合到学员月粒度后用两个布尔标志组合判断，才是稳妥解。
- **"连续N月活跃"怎么算？** 在学员×月粒度上套EDU-21的连续区间法（月份差=行号差），输出连续活跃月数分布，衡量粘性。
- **月活要不要给触点加权？** 运营上可输出加权活跃分（上课权重高于交作业），但主口径MAU必须保持无权去重，两套口径并行时要在报表上分开列示，避免打架。

### 7. 业务拓展思考

月活四分口的运营含义：只上课人群大，说明督学产品渗透不足，作业布置与批改反馈要补课；只交作业人群大，可能是排课密度不足或寒暑假模式，供给端要解决；双触点占比代表"教学闭环完成度"，与续费率高度相关，可作续费预测的输入特征。延伸分析上，把MAU与课耗收入做同环比联动，可识别"活跃涨收入不涨"的虚假繁荣（大量只交作业的赠课学员）；连续两月零触点的沉默学员应自动进入召回队列，召回话术按最后触点类型（缺课型/断作业型）差异化设计。

## EDU-26 低分课程识别（评分低且完课率低）

### 1. 业务背景

课程负责人每季度做课程质量复盘，规则是"双低即整改"：学员平均评分低于4.5分、且完课率低于60%的课程进入整改名单——评分低说明教学体验差，完课率低说明学员用脚投票，双低课程是口碑与续费的隐形杀手，必须限期重做教案、更换主讲或直接下架。数据上需要把"学员评分"（学员粒度）与"上课出勤"（课节×学员粒度）两张不同粒度的数据合并到课程粒度再筛选。**【避坑指南】**本题的核心陷阱是JOIN放大：评分表与出勤表直接JOIN后再各自AVG/SUM，两表会按对方的行数互相复制放大，评分与完课率双双失真——先分源预聚合到课程粒度再JOIN是唯一正确姿势，这与EDU-23渠道ROI的"放大陷阱"是同一母题在质量分析上的变体，面试中能主动点破是重要加分项。

### 2. 表结构说明

### 3. 解题思路

口径界定：课程平均评分=评分表按课程AVG(score)；完课率=出勤人次÷(出勤+缺勤)人次，请假是学员有计划的缺席，剔除分母（口径须与EDU-18、EDU-30全公司统一）；双低=平均评分<4.5且完课率<60%；只保留评分≥10条的课程（样本量门槛），输出评分、完课率、评分人数并按完课率升序。实现路径：解法一用两个CTE分别把评分、出勤聚合到课程粒度，再与课程表JOIN后多条件过滤——聚合已前置到CTE，外层用WHERE写三个条件，若把过滤写在同层聚合之后则等价改写为HAVING多条件，两者语义相同；解法二以课程表为驱动、SELECT列表内放三个相关子查询，天然不产生JOIN放大，课程数少时直观可靠。易错点：把评分表与出勤表同时JOIN进courses再GROUP BY用HAVING筛，AVG(score)被该课程的出勤行数逐行复制加权、评分人数被放大成"评分×课节"，两个指标同时失真；完课率分母漏掉缺勤或误把请假计入；小样本课程均分不稳却进入名单。

### 4. 参考解法

解法一：分源预聚合 + JOIN + 多条件过滤（推荐）

```sql
WITH rating_agg AS (                 -- CTE1：评分聚合到课程粒度
    SELECT
        course_id,                   -- 课程ID
        AVG(score) AS avg_score,     -- 平均评分
        COUNT(*) AS rating_cnt       -- 评分人数（样本量门槛用）
    FROM course_ratings
    GROUP BY course_id
),
att_agg AS (                         -- CTE2：出勤聚合到课程粒度
    SELECT
        course_id,
        SUM(CASE WHEN status = '出勤' THEN 1 ELSE 0 END) AS att_cnt,
                                     -- 出勤人次（完课率分子）
        SUM(CASE WHEN status = '缺勤' THEN 1 ELSE 0 END) AS absent_cnt
                                     -- 缺勤人次（分母=出勤+缺勤，请假剔除）
    FROM attendance
    GROUP BY course_id
)
SELECT
    c.course_id,                     -- 课程ID
    c.course_name,                   -- 课程名
    c.category,                      -- 品类/班型
    ROUND(r.avg_score, 2) AS avg_score,              -- 平均评分
    ROUND(a.att_cnt / NULLIF(a.att_cnt + a.absent_cnt, 0), 4) AS completion_rate,
                                     -- 完课率 = 出勤/(出勤+缺勤)，NULLIF防除零
    r.rating_cnt                     -- 评分人数，判断均分可信度
FROM courses c
JOIN rating_agg r ON r.course_id = c.course_id
                                     -- 聚合后的1:1连接，不会放大
JOIN att_agg a ON a.course_id = c.course_id
WHERE r.rating_cnt >= 10             -- 条件一：样本量门槛（评分≥10条）
  AND r.avg_score < 4.5              -- 条件二：低分线
  AND a.att_cnt / NULLIF(a.att_cnt + a.absent_cnt, 0) < 0.6
                                     -- 条件三：低完课线
ORDER BY completion_rate, avg_score; -- 完课率最差的排最前
```

结果解读：假设输出"2003 大语文写作大班：均分3.92、完课率48%、评分46条"进入整改名单，而"2005 物理竞赛一对一：均分4.30、完课率82%"评分虽低但完课健康，属于内容偏难而非体验差，暂不整改——双低条件的价值就是把"口碑差"与"学不动"两类问题分开，避免一刀切下架。

解法二：标量子查询版（课程表驱动，免JOIN放大）

```sql
SELECT *
FROM (
    SELECT
        c.course_id,                 -- 课程ID
        c.course_name,               -- 课程名
        c.category,                  -- 品类
        (SELECT AVG(r.score)         -- 相关子查询：该课程平均评分
         FROM course_ratings r
         WHERE r.course_id = c.course_id) AS avg_score,
        (SELECT SUM(CASE WHEN a.status = '出勤' THEN 1 ELSE 0 END) /
                NULLIF(SUM(CASE WHEN a.status IN ('出勤', '缺勤') THEN 1 ELSE 0 END), 0)
         FROM attendance a
         WHERE a.course_id = c.course_id) AS completion_rate,
                                     -- 相关子查询：该课程完课率，请假剔除
        (SELECT COUNT(*)             -- 相关子查询：该课程评分人数
         FROM course_ratings r2
         WHERE r2.course_id = c.course_id) AS rating_cnt
    FROM courses c
) t
WHERE t.rating_cnt >= 10             -- 三个筛选条件放外层：
  AND t.avg_score < 4.5              -- 别名不能直接用于同层WHERE
  AND t.completion_rate < 0.6
ORDER BY t.completion_rate, t.avg_score;
```

结果解读：与解法一结果一致；标量子查询按课程逐个求值，两指标各算各的、互不放大，几百门课程规模内清晰可靠，课程多时不如解法一的两次批量聚合高效。

### 5. 性能分析与优化

解法一对两张流水表各做一次全表分组聚合（约 O(N log N)），再在几十行的聚合结果上JOIN，代价集中在前两次扫描；解法二每门课程触发三次相关子查询，有索引时是M×3次索引查找（M=课程数），课程规模大时明显劣于解法一。优化建议：(1) course_ratings 建 (course_id, score)、attendance 建 (course_id, status) 复合索引，两个CTE可走覆盖扫描；(2) 样本量门槛可下沉到rating_agg里先HAVING COUNT(*)>=10，减少参与JOIN的行；(3) 课程质量报表适合固化为日更"课程质量宽表"，季度复盘只查宽表不再碰流水；(4) 反面教材必须点到：直接 courses LEFT JOIN course_ratings LEFT JOIN attendance 后GROUP BY课程并HAVING AVG(r.score)<4.5，评分会被出勤行数加权放大——这就是"先聚到同粒度再JOIN"的铁律。

### 6. 面试延伸考点

- **两表粒度不同又必须JOIN，怎么防放大？** 无法在JOIN后补救，唯一正确做法是各自先聚合到公共粒度（课程）再JOIN；AVG(DISTINCT ...)只能去完全重复值，不能抵消复制放大，不可靠。
- **评分人数很少的课程怎么处理？** 设最低样本门槛（如≥10条），或输出贝叶斯平滑均分（向全局均分收缩），避免两三条评分的偶然低分把课程误送进整改名单。
- **完课率为什么剔除请假？** 请假是学员有计划的缺席，不反映课程质量；若业务认为"请假过多也是吸引力问题"，可输出含请假版本作对照，两版并列不混用。
- **双低之外还要看什么组合？** 四象限：双低=整改，低分高完课=内容枯燥但约束强，高分低完课=偏难或服务拖累，双高=标杆课；每类的干预动作完全不同。

### 7. 业务拓展思考

整改名单落地要接归因：对双低课程先做低分评论关键词聚类与低完课学员访谈，再决定改教案、换主讲或下架；一对一课程的完课率受排课密度影响大，应与大小班分开设基线再比较。延伸方向上，课程质量表可接入老师维度形成"老师×课程"质量矩阵，与EDU-30的出勤率排名、EDU-22的响应时长分位数共同构成教学质量驾驶舱；更进一步，把整改前后90天的评分、完课率、续费率做成对照，用数据证明课程治理对续费的贡献，这是课程运营团队争取资源时最有说服力的闭环证据。

## EDU-27 分班型×学习时长退费率交叉表

### 1. 业务背景

退费是教培收入的直接漏损，但"学员报课后多久退费"比"退了多少"更有诊断价值：7天内退的多是销售过度承诺或冲动消费，8~30天退的是课程适配问题，30天以上退的是效果或服务积累的问题。教学与客服负责人月度复盘需要一张交叉表：行=班型（一对一/小班课/大班课），列=学习时长桶（≤7天/8-30天/31-90天/90天以上），格子=该班型退款单落在各桶的单数与占比，末列附各班型整体退费率——一张表同时看清"哪个班型退得多"和"退费集中在哪个阶段"。**【加分点】**行转列（条件聚合）与退费时点口径是本题双考点，MySQL没有PIVOT函数，条件聚合是行转列的标准姿势，两条实现路线的取舍要能讲清楚。

### 2. 表结构说明

### 3. 解题思路

先把口径写死：退费时点用"退费申请时间"而非到账时间——申请时点是学员决策终点，到账时间混入财务处理周期会虚增学员的实际学习时长；学习时长=TIMESTAMPDIFF(DAY, 支付时间, 退费申请时间)，分桶为≤7天/8-30天/31-90天/90天以上（边界对应冷静期、首月评估点、半学期，须与业务确认）；时长只对退费订单有定义，因此交叉表的格子是"该班型退款单中各桶的单数与占比"，而整体退费率以正价订单数为分母另列——两种分母混在一张表时必须在口径注释里写明。实现路径：CTE1关联退费与订单算出班型与时长桶，解法一在班型分组内用CASE条件聚合把四个桶"转"成列（行转列），退费率通过JOIN订单聚合表取分母；解法二先GROUP BY出"班型×桶"长表，再四次LEFT JOIN拼成宽表，演示无PIVOT时的另一条路。易错点：试听课0元单混进退费率分母；一单多次部分退费时COUNT(*)被放大（本表按全额退费建模，若业务允许部分退费须先按订单聚合）；90天整归属哪个桶未确认；长表桶名不带序号前缀导致拼宽时排序错乱。

### 4. 参考解法

解法一：条件聚合行转列（推荐）

```sql
WITH refund_detail AS (              -- CTE1：退款单明细（班型 + 学习时长）
    SELECT
        o.class_type,                -- 班型
        TIMESTAMPDIFF(DAY, o.paid_at, r.applied_at) AS dur_days
                                     -- 学习时长（天）= 退费申请日 - 支付日
    FROM refunds r
    JOIN orders o ON o.order_id = r.order_id
                                     -- 全额退费一单一退，1:1连接不放大
    WHERE o.is_trial = 0             -- 试听课0元单不进退费分析
      AND r.applied_at >= '2024-01-01' AND r.applied_at < '2025-01-01'
                                     -- 考察年（订单均按同年口径）
),
order_stat AS (                      -- CTE2：各班型正价订单数（退费率分母）
    SELECT
        class_type,
        COUNT(*) AS order_cnt        -- 该班型正价订单总数
    FROM orders
    WHERE is_trial = 0
      AND paid_at >= '2024-01-01' AND paid_at < '2025-01-01'
    GROUP BY class_type
)
SELECT
    d.class_type,                    -- 行：班型
    COUNT(*) AS refund_cnt,          -- 该班型退费单总数
    SUM(CASE WHEN d.dur_days <= 7 THEN 1 ELSE 0 END) AS c_7d,
                                     -- ≤7天桶单数：冲动/过度承诺型
    ROUND(SUM(CASE WHEN d.dur_days <= 7 THEN 1 ELSE 0 END) / COUNT(*), 4) AS r_7d,
    SUM(CASE WHEN d.dur_days BETWEEN 8 AND 30 THEN 1 ELSE 0 END) AS c_8_30,
    ROUND(SUM(CASE WHEN d.dur_days BETWEEN 8 AND 30 THEN 1 ELSE 0 END) / COUNT(*), 4) AS r_8_30,
    SUM(CASE WHEN d.dur_days BETWEEN 31 AND 90 THEN 1 ELSE 0 END) AS c_31_90,
    ROUND(SUM(CASE WHEN d.dur_days BETWEEN 31 AND 90 THEN 1 ELSE 0 END) / COUNT(*), 4) AS r_31_90,
    SUM(CASE WHEN d.dur_days > 90 THEN 1 ELSE 0 END) AS c_90p,
    ROUND(SUM(CASE WHEN d.dur_days > 90 THEN 1 ELSE 0 END) / COUNT(*), 4) AS r_90p,
    ROUND(COUNT(*) / MAX(os.order_cnt), 4) AS refund_rate
                                     -- 末列：整体退费率 = 退费单数/正价订单数
                                     -- order_cnt非分组列，用MAX()包裹满足严格模式
FROM refund_detail d
JOIN order_stat os ON os.class_type = d.class_type
GROUP BY d.class_type
ORDER BY refund_rate DESC;           -- 退费率高的班型排前面
```

结果解读：假设输出"一对一：退费17单，8-30天桶占53%；大班课：退费31单，≤7天桶占48%"，干预方向完全不同——大班课要管住售前承诺、设置冷静期回访，一对一要在首月学习报告上做效果可视化拦截；退费率列则告诉管理层哪个班型收入漏损最严重。

解法二：长表预聚合 + 多次LEFT JOIN拼宽（无窗口/无PIVOT写法）

```sql
WITH refund_detail AS (              -- CTE1：同解法一的退款明细
    SELECT
        o.class_type,
        TIMESTAMPDIFF(DAY, o.paid_at, r.applied_at) AS dur_days
    FROM refunds r
    JOIN orders o ON o.order_id = r.order_id
    WHERE o.is_trial = 0
      AND r.applied_at >= '2024-01-01' AND r.applied_at < '2025-01-01'
),
bucket_agg AS (                      -- CTE2：班型×时长桶的长表
    SELECT
        class_type,
        CASE WHEN dur_days <= 7  THEN '1_7天内'
             WHEN dur_days <= 30 THEN '2_8-30天'
             WHEN dur_days <= 90 THEN '3_31-90天'
             ELSE '4_90天以上' END AS bucket,
                                     -- 桶名带序号前缀，保证排序与JOIN键稳定
        COUNT(*) AS cnt              -- 该班型该桶的退费单数
    FROM refund_detail
    GROUP BY class_type,
             CASE WHEN dur_days <= 7  THEN '1_7天内'
                  WHEN dur_days <= 30 THEN '2_8-30天'
                  WHEN dur_days <= 90 THEN '3_31-90天'
                  ELSE '4_90天以上' END
                                     -- 分组表达式与SELECT保持一致
)
SELECT
    t.class_type,                    -- 行：班型
    COALESCE(b1.cnt, 0) AS c_7d,     -- 各桶单数，无数据补0
    COALESCE(b2.cnt, 0) AS c_8_30,
    COALESCE(b3.cnt, 0) AS c_31_90,
    COALESCE(b4.cnt, 0) AS c_90p,
    COALESCE(b1.cnt, 0) + COALESCE(b2.cnt, 0)
      + COALESCE(b3.cnt, 0) + COALESCE(b4.cnt, 0) AS refund_cnt
                                     -- 退费单总数
FROM (SELECT DISTINCT class_type FROM refund_detail) t
                                     -- 出现过退费的班型清单作驱动行
LEFT JOIN bucket_agg b1 ON b1.class_type = t.class_type AND b1.bucket = '1_7天内'
LEFT JOIN bucket_agg b2 ON b2.class_type = t.class_type AND b2.bucket = '2_8-30天'
LEFT JOIN bucket_agg b3 ON b3.class_type = t.class_type AND b3.bucket = '3_31-90天'
LEFT JOIN bucket_agg b4 ON b4.class_type = t.class_type AND b4.bucket = '4_90天以上'
ORDER BY refund_cnt DESC;
```

结果解读：与解法一同构（少一列退费率）；桶名加序号前缀是长表转宽的实用技巧，ORDER BY bucket 不会因汉字排序乱序；此写法桶数增加时JOIN线性增多，条件聚合仍是首选，本解更适合讲解"长表↔宽表"的转换思想。

### 5. 性能分析与优化

解法一两次聚合加小表JOIN，约 O(N log N)，主代价在退款与订单的连接；解法二多四次LEFT JOIN，但都发生在聚合后的极小结果集（班型×桶）上，代价可忽略，差异主要在可维护性而非性能。优化建议：(1) refunds(order_id)、orders(paid_at, is_trial) 建索引，年份过滤与连接都走索引；(2) 若班型多、桶多，建议在ETL阶段把"时长桶"直接打在退款明细宽表里，报表层只做GROUP BY+条件聚合；(3) 若业务存在部分退费，refunds 增加 refund_type 字段并在CTE里先按订单聚合退费金额再JOIN，防止COUNT(*)与SUM被一单多退放大；(4) 跨年对比时把年份加进分组，同结构输出多年交叉表，比每年跑一遍更可比。

### 6. 面试延伸考点

- **MySQL没有PIVOT，行转列还有哪些写法？** 条件聚合是标准答案；动态列数需在应用层或存储过程拼SQL；BI工具的透视表本质也是条件聚合；反向的列转行用UNION ALL。
- **退费时点为什么用申请时间？** 申请时点是学员决策终点，到账时间混入财务周期会虚增学习时长；但分析资金占用与现金回流时恰恰要用到账时间——口径跟着问题走，没有绝对对错。
- **时长分桶的边界怎么定？** 跟随业务干预节奏：7天≈冷静期/试听保障期，30天≈首月效果评估点，90天≈半学期；边界必须有业务含义，等分四桶是偷懒。
- **退费率的分母还有什么口径之争？** 按订单数、按金额、按学员数三种；建议主口径用单数（运营视角）、辅口径用金额（财务视角）并列输出，口径混用是复盘会上最常见的争吵来源。

### 7. 业务拓展思考

交叉表可以直接翻译成干预动作：≤7天桶高的班型强化售前预期管理（试听课改为与正课同型同师）并设置冷静期回访；8-30天桶高则要排查课程适配与分班测精度；31-90天桶高把阶段学习报告前置到期中，用效果可视化拦截退费念头。延伸上，把退费原因维并入做"班型×时长×原因"三层下钻，可定位到"大班课31-90天的效果不符"这类具体病灶；再把退费时点分布与续费窗口对照——退费高发期往往正是续费转化期，一套干预动作要同时服务挽单与续费两个目标，这也是教培数据分析师最有杠杆的分析场景之一。

## EDU-28 学员持有课程数分布

### 1. 业务背景

扩科（一名学员报多门课）是教培机构提升学员生命周期价值的第二增长曲线：持有2门及以上课程的学员，续费率与转介绍率都显著更高。增长团队每季度要输出"学员持有课程数分布表"：持1门/2门/3门/4门及以上各多少人、占比多少、累计占比到哪——它既是扩科渗透率的直接度量，也用于评估"第二科半价"这类搭售活动的真实效果。**【面试高频】**"先按学员聚合计数、再按计数值二次聚合分布"的两层聚合结构是高频考点，叠加累计占比的窗口写法，一道题能同时考察COUNT(DISTINCT)、两层GROUP BY与累计求和窗口三个知识点。

### 2. 表结构说明

orders（购课订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| course_id | BIGINT | 课程ID |
| amount | DECIMAL(10,2) | 订单金额 |
| is_trial | TINYINT | 是否试听课：1是，0否 |
| status | VARCHAR(10) | 状态：已支付/已退款 |
| paid_at | DATETIME | 支付时间 |

示例数据：

| order_id | student_id | course_id | amount | is_trial | status | paid_at |
|----------|------------|-----------|--------|----------|--------|---------|
| 26001 | 801 | 3001 | 6800.00 | 0 | 已支付 | 2024-03-10 10:00:00 |
| 26002 | 801 | 3002 | 5200.00 | 0 | 已支付 | 2024-06-15 14:00:00 |
| 26003 | 802 | 3001 | 6800.00 | 0 | 已支付 | 2024-04-01 09:00:00 |
| 26004 | 803 | 3003 | 3600.00 | 0 | 已退款 | 2024-05-20 16:00:00 |
| 26005 | 804 | 3001 | 0.00 | 1 | 已支付 | 2024-07-01 11:00:00 |

（注：801号学员持3001、3002两门课程；26004已退款、26005为试听单，均不计入持有。）

### 3. 解题思路

口径界定：有效持有=is_trial=0且status='已支付'的订单；每学员持有课程数=COUNT(DISTINCT course_id)——同一课程续期、升级产生的多笔订单只算一门，这是本题第一坑；分布桶为1门/2门/3门/4门及以上；输出各桶人数、占比、累计占比（从低桶向高桶累计，回答"前两档覆盖了多少人"）。实现路径：三层CTE——CTE1过滤有效订单，CTE2按学员聚合计数，CTE3用LEAST(course_cnt,4)把4及以上归并成一桶并COUNT人数；解法一外层用窗口SUM(stu_cnt) OVER (ORDER BY bucket_no ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)算累计；解法二用相关子查询对dist自累计（bucket_no小于等于当前桶的人数和），演示窗口函数出现前的经典写法。易错点：用COUNT(*)代替COUNT(DISTINCT course_id)导致续费学员被高估持有数；CASE分桶条件顺序错误把"4门及以上"吞进"3门"；累计占比的排序基准与展示顺序不一致；某些桶无学员时缺行，需要时用数字骨架补0。

### 4. 参考解法

解法一：两层聚合 + 窗口累计（推荐）

```sql
WITH valid AS (                      -- CTE1：有效持有订单
    SELECT
        student_id,                  -- 学员ID
        course_id                    -- 课程ID
    FROM orders
    WHERE is_trial = 0               -- 试听课不算持有
      AND status = '已支付'          -- 已退款订单剔除
),
held AS (                            -- CTE2：学员粒度持有课程数
    SELECT
        student_id,
        COUNT(DISTINCT course_id) AS course_cnt
                                     -- 同课程多笔订单（续期/升级）只算一门
    FROM valid
    GROUP BY student_id
),
dist AS (                            -- CTE3：持有数分桶分布
    SELECT
        LEAST(course_cnt, 4) AS bucket_no,   -- ≥4归并为4，桶号1~4天然封顶
        COUNT(*) AS stu_cnt          -- 该桶人数
    FROM held
    GROUP BY LEAST(course_cnt, 4)
)
SELECT
    CASE bucket_no WHEN 1 THEN '1门'
                   WHEN 2 THEN '2门'
                   WHEN 3 THEN '3门'
                   ELSE '4门及以上' END AS cnt_bucket,   -- 桶标签
    stu_cnt,                         -- 该桶人数
    ROUND(stu_cnt / SUM(stu_cnt) OVER (), 4) AS ratio,
                                     -- 桶占比：分子当前桶，分母窗口求全体
    ROUND(SUM(stu_cnt) OVER (ORDER BY bucket_no
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
        / SUM(stu_cnt) OVER (), 4) AS cum_ratio
                                     -- 累计占比：从1门桶累计到当前桶
FROM dist
ORDER BY bucket_no;                  -- 按桶号从低到高展示
```

结果解读：假设输出"1门2860人占71.5%、2门860人占21.5%、3门200人占5%、4门及以上80人占2%"，扩科渗透率（≥2门）=28.5%，与上季度对比即可评估"第二科半价"活动效果；累计占比列直接回答"持有不超过2门的学员占93%"这类管理层追问。

解法二：相关子查询自累计（窗口函数的手工替代）

```sql
WITH valid AS (                      -- CTE1：有效持有订单（同解法一）
    SELECT student_id, course_id
    FROM orders
    WHERE is_trial = 0
      AND status = '已支付'
),
held AS (                            -- CTE2：学员持有课程数（同解法一）
    SELECT student_id, COUNT(DISTINCT course_id) AS course_cnt
    FROM valid
    GROUP BY student_id
),
dist AS (                            -- CTE3：分桶（同解法一）
    SELECT LEAST(course_cnt, 4) AS bucket_no, COUNT(*) AS stu_cnt
    FROM held
    GROUP BY LEAST(course_cnt, 4)
)
SELECT
    CASE d.bucket_no WHEN 1 THEN '1门'
                     WHEN 2 THEN '2门'
                     WHEN 3 THEN '3门'
                     ELSE '4门及以上' END AS cnt_bucket,
    d.stu_cnt,                       -- 该桶人数
    ROUND(d.stu_cnt / t.total, 4) AS ratio,
                                     -- 占比：total来自CROSS JOIN的总数行
    ROUND((SELECT SUM(d2.stu_cnt)    -- 相关子查询：累计到当前桶的人数和
           FROM dist d2
           WHERE d2.bucket_no <= d.bucket_no) / t.total, 4) AS cum_ratio
FROM dist d
CROSS JOIN (SELECT SUM(stu_cnt) AS total FROM dist) t
                                     -- 总人数以CROSS JOIN挂到每一行
ORDER BY d.bucket_no;
```

结果解读：与解法一完全一致；相关子查询+CROSS JOIN总数是窗口函数出现前的经典累计写法，思路可迁移到不支持窗口的引擎（把CTE换成派生表即可在MySQL 5.7运行）；面试中能点出"窗口函数本质是这类自连接累计的语法糖优化"，是理解窗口语义的有力证明。

### 5. 性能分析与优化

两级GROUP BY加一个小结果集上的窗口/子查询，整体代价由订单表扫描与COUNT(DISTINCT)的去重排序主导，约 O(N log N)；dist只有最多4行，窗口与相关子查询开销可忽略。优化建议：(1) orders 建 (student_id, course_id, is_trial, status) 或 (student_id, course_id) 复合索引，让CTE1/CTE2走覆盖扫描，COUNT(DISTINCT)可直接利用索引序去重；(2) 大订单表可日更"学员持有宽表"（学员×持有课程数），分布查询退化为对宽表GROUP BY；(3) 扩科推荐需要明细时，用GROUP_CONCAT(course_id ORDER BY course_id)把每个学员持有的课程一次带出，注意group_concat_max_len默认1024可能截断；(4) 若某桶无学员导致缺行，右连一张1~4数字骨架表补0，保证报表列位稳定。

### 6. 面试延伸考点

- **为什么COUNT(DISTINCT course_id)而不是COUNT(*)？** 同一课程续期/升级产生多笔订单，COUNT(*)把"买一门课付三次"算成持有3门，系统性高估扩科渗透率，这是本题第一坑。
- **累计占比还能怎么写？** 窗口SUM OVER是首选；不支持窗口的环境用相关子查询自累计；若要"从高到低累计"（头部贡献视角），把窗口ORDER BY改为降序即可。
- **热门课程组合怎么统计？** 自连接orders把同学员两两课程配对（a.course_id < b.course_id防重复），GROUP BY配对计数，输出"报数学的人最常再报英语"这类搭售洞察。
- **"4门及以上"为什么要归并？** 长尾桶人数过少会让分布失焦且涉及学员隐私风险，归并到4+既保护隐私又聚焦主结论；CASE条件注意从宽到窄的短路顺序。

### 7. 业务拓展思考

分布表是扩科战略的仪表盘：扩科渗透率的环比趋势直接反映第二增长曲线的健康度，"报数学的人最常再报什么"的组合热力指导第二科优惠券的发放组合；持单科学员是最大的未开发池，应按首科类别与家长投入度分层运营。更进一步，把持有课程数与续费率、完课率交叉，可验证"多科绑定提升留存"的假设——注意相关不等于因果，最好用搭售活动的A/B实验数据佐证；当分布显示4门及以上占比极低时，说明产品供给尚未支撑深度扩科，问题在课程线宽度而非运营力度，这一层判断能把分析从"报表"推到"战略"。

## EDU-29 新老学员收入贡献拆分

### 1. 业务背景

月度经营分析会上，CFO的第一个问题往往是"这个月收入里多少来自新学员、多少来自老学员"：新学员收入反映获客机器的产出，老学员收入（续费+扩科）反映留存健康度，两者结构失衡比总收入下滑更危险——老学员收入占比连续下滑，说明续费出了问题，市场拉新的增长正在被流失抵消。分析师需要按支付月份拆分收入：学员的"首笔正价订单"记为新学员收入，其后的所有订单记为老学员收入，输出每月新学员收入、老学员收入与老学员占比。**【面试高频】**"首单识别"是本题题眼，ROW_NUMBER窗口打标与GROUP BY MIN回JOIN两条路线的口径差异（同日多单算几笔新学员收入）是必被追问的细节。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| student_id | BIGINT | 学员ID |
| amount | DECIMAL(10,2) | 订单金额 |
| is_trial | TINYINT | 是否试听课：1是，0否 |
| status | VARCHAR(10) | 状态：已支付/已退款 |
| paid_at | DATETIME | 支付时间 |

示例数据：

| order_id | student_id | amount | is_trial | status | paid_at |
|----------|------------|--------|----------|--------|---------|
| 27001 | 801 | 6800.00 | 0 | 已支付 | 2024-05-10 10:00:00 |
| 27002 | 801 | 5200.00 | 0 | 已支付 | 2024-07-02 14:00:00 |
| 27003 | 802 | 4800.00 | 0 | 已支付 | 2024-07-05 09:00:00 |
| 27004 | 803 | 3600.00 | 0 | 已支付 | 2024-07-05 09:00:00 |
| 27005 | 801 | 6800.00 | 0 | 已退款 | 2024-07-08 11:00:00 |

（注：801号学员5月的27001是首单，7月的27002算老学员收入；27005已退款不参与；802、803两笔同秒首单用于演示并列场景。）

### 3. 解题思路

口径先行：新老按"学员维度首笔正价订单"定义而非注册时间——教育场景"新学员收入"指首次产生正价付费的订单；只统计is_trial=0且status='已支付'的订单，退款单剔除；首单唯一化用ROW_NUMBER并以order_id决胜同秒并列。实现路径：解法一窗口法——ROW_NUMBER() OVER (PARTITION BY student_id ORDER BY paid_at, order_id)打is_new标志，一次扫描完成，再按月条件聚合；解法二CTE法——GROUP BY student_id取MIN(paid_at)后回JOIN打标，语义直观，但学员同秒多笔订单会全部命中首单时间、都被记为新学员收入（两解的口径差异要写进口径文档二选一）。易错点：先按月聚合再判新老会出错（首单可能在更早月份，窗口必须对全体有效订单先算）；MIN回JOIN法的同秒重复计入；试听课剔除后0元单不再污染首单；被退款的历史首单剔除后，下一笔顺延成为首单，新老标签会漂移，需冻结快照口径。

### 4. 参考解法

解法一：ROW_NUMBER首单打标（推荐）

```sql
WITH valid AS (                      -- CTE1：有效收入订单
    SELECT
        order_id,                    -- 订单ID
        student_id,                  -- 学员ID
        amount,                      -- 订单金额
        paid_at                      -- 支付时间
    FROM orders
    WHERE is_trial = 0               -- 剔除试听课0元单
      AND status = '已支付'          -- 剔除已退款订单
),
tagged AS (                          -- CTE2：窗口打新老标签
    SELECT
        o.order_id,
        o.student_id,
        o.amount,
        o.paid_at,
        CASE WHEN ROW_NUMBER() OVER (
                 PARTITION BY o.student_id
                 ORDER BY o.paid_at, o.order_id) = 1
             THEN 1 ELSE 0 END AS is_new
                                     -- 学员内按支付时间+订单ID升序，
                                     -- 第1笔=首单=新学员收入（order_id决胜同秒并列）
    FROM valid o
)
SELECT
    DATE_FORMAT(paid_at, '%Y-%m') AS ym,
                                     -- 收入归属月（按支付时间）
    SUM(CASE WHEN is_new = 1 THEN amount ELSE 0 END) AS new_revenue,
                                     -- 新学员收入
    SUM(CASE WHEN is_new = 0 THEN amount ELSE 0 END) AS old_revenue,
                                     -- 老学员收入
    ROUND(SUM(CASE WHEN is_new = 0 THEN amount ELSE 0 END)
        / SUM(amount), 4) AS old_ratio,
                                     -- 老学员收入占比（留存健康度）
    COUNT(CASE WHEN is_new = 1 THEN 1 END) AS new_orders,
                                     -- 新学员订单数
    COUNT(DISTINCT CASE WHEN is_new = 1 THEN student_id END) AS new_students
                                     -- 新学员人数（首单学员去重）
FROM tagged
GROUP BY DATE_FORMAT(paid_at, '%Y-%m')
ORDER BY ym;
```

结果解读：假设7月总收入42.6万，其中新学员18.9万、老学员23.7万，老学员占比55.6%且连续三月上升——留存引擎在发力；若老学员占比高但总收入下滑，则问题在拉新端，应回到EDU-23的渠道ROI找原因，两张表拼起来才是完整的增长诊断。

解法二：MIN(paid_at)首单时间回JOIN打标

```sql
WITH valid AS (                      -- CTE1：有效收入订单（同解法一）
    SELECT order_id, student_id, amount, paid_at
    FROM orders
    WHERE is_trial = 0
      AND status = '已支付'
),
first_order AS (                     -- CTE2：学员首单时间
    SELECT
        student_id,
        MIN(paid_at) AS first_paid_at
                                     -- 该学员最早的正价支付时间
    FROM valid
    GROUP BY student_id
),
tagged AS (                          -- CTE3：回JOIN打新老标签
    SELECT
        o.order_id,
        o.student_id,
        o.amount,
        o.paid_at,
        CASE WHEN o.paid_at = f.first_paid_at THEN 1 ELSE 0 END AS is_new
                                     -- 支付时间等于首单时间即记为新学员收入
    FROM valid o
    JOIN first_order f ON f.student_id = o.student_id
                                     -- 1:1连接（每学员一行首单时间）
)
SELECT
    DATE_FORMAT(paid_at, '%Y-%m') AS ym,
    SUM(CASE WHEN is_new = 1 THEN amount ELSE 0 END) AS new_revenue,
    SUM(CASE WHEN is_new = 0 THEN amount ELSE 0 END) AS old_revenue,
    ROUND(SUM(CASE WHEN is_new = 0 THEN amount ELSE 0 END)
        / SUM(amount), 4) AS old_ratio,
    COUNT(CASE WHEN is_new = 1 THEN 1 END) AS new_orders,
    COUNT(DISTINCT CASE WHEN is_new = 1 THEN student_id END) AS new_students
FROM tagged
GROUP BY DATE_FORMAT(paid_at, '%Y-%m')
ORDER BY ym;
```

结果解读：在无同秒订单时与解法一完全一致；当学员同一天连付两笔（如首日连报两科），MIN法把两笔都标为新学员收入，新学员收入被高估——汇报前必须与ROW_NUMBER口径二选一并写进口径文档，这正是两解并存的业务意义。

### 5. 性能分析与优化

解法一一次窗口排序 O(N log N)，无JOIN；解法二一次GROUP BY（MIN可走(student_id, paid_at)索引的松散扫描，聚合本身很快）加一次等值JOIN，大表下两者接近，解法二略优的场景是学员数远小于订单数时。优化建议：(1) orders 建 (student_id, paid_at) 复合索引同时服务两解；(2) 收入月报建议物化为"订单×新老标签"宽表，标签按月末快照冻结、历史月不回溯重算，避免首单退款后历史报表漂移；(3) 需要按渠道/班型细分时，在tagged层之后JOIN维表——先打标后JOIN，防止维表1:N放大破坏ROW_NUMBER的"学员内唯一"语义；(4) 若仅关心占比趋势，可只输出月份×新老收入两列，新学员人数等明细指标放二级报表。

### 6. 面试延伸考点

- **新老定义为什么不用注册时间？** 注册不等于付费，教培转化周期长，用首笔正价订单定义"新学员收入"更贴近经营；按注册月划分是"用户年龄"口径，两者可并列输出但用途不同。
- **同一天两笔订单怎么算？** ROW_NUMBER加order_id决胜只认一笔为首单（解法一）；MIN回JOIN把同刻多笔全标新（解法二）；差异须在口径文档固化，这是本题主考的细节。
- **首单被退款后口径怎么办？** 剔除退款单后首单顺延到下一笔，新老标签随之漂移；稳妥做法是月末快照冻结，历史月不重算，当月用最新口径。
- **如何扩展到"新老×渠道/班型"？** 在tagged层JOIN线索或课程维表后增加分组维度即可；注意先打标后JOIN，避免维表放大破坏首单唯一性。

### 7. 业务拓展思考

新老结构是增长质量的体检表：老学员收入占比是"留存驱动型增长"的核心证据，对投资人叙事与内部预算分配（市场投放vs教学服务）都有一票否决力。延伸上，可把老学员收入再拆为"续费/扩科/加期"三级，定位留存引擎的具体齿轮；把新学员收入按渠道拆分后与EDU-23的渠道ROI打通，形成"获客成本-新学员收入-老学员复购"的完整单位经济模型（LTV/CAC），这是数据分析师在经营会上建立影响力的最佳主线——收入结构分析从来不只是两张饼图，而是资源往哪投的决策依据。

## EDU-30 班级内学员出勤率排名TOP3

### 1. 业务背景

班主任每月在班级群公布"学习之星"，依据就是学员出勤率的班级内前三名——既是激励手段，也是续费前的情感铺垫（被公开表扬的家长续费意愿更高）。教学运营需要一张"班级×学员"出勤榜单：每个班出勤率最高的3名学员及其出勤率，供教务系统批量生成表彰海报。难点在"并列怎么办"：出勤率相同的学员是都表彰（保留并列名次）还是严格只取3人，决定了该用DENSE_RANK、RANK还是ROW_NUMBER。**【面试高频】**三个排名函数的输出差异是窗口函数的第一考题，教育榜单是它最自然的业务载体，决胜键设计则是从"会写"到"写对"的分水岭。

### 2. 表结构说明

students（学员表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| student_id | BIGINT | 学员ID，主键 |
| student_name | VARCHAR(50) | 学员姓名 |
| class_id | BIGINT | 所属班级 |

示例数据：

| student_id | student_name | class_id |
|------------|--------------|----------|
| 801 | 张小明 | 501 |
| 802 | 李小红 | 501 |
| 803 | 王小刚 | 501 |
| 804 | 赵小丽 | 502 |
| 805 | 孙小强 | 502 |

attendance（上课出勤表，每学员每课节一行）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| att_id | BIGINT | 记录ID，主键 |
| class_id | BIGINT | 班级ID |
| student_id | BIGINT | 学员ID |
| lesson_date | DATE | 课节日期 |
| status | VARCHAR(10) | 状态：出勤/缺勤/请假 |

示例数据：

| att_id | class_id | student_id | lesson_date | status |
|--------|----------|------------|-------------|--------|
| 28001 | 501 | 801 | 2024-07-02 | 出勤 |
| 28002 | 501 | 802 | 2024-07-02 | 出勤 |
| 28003 | 501 | 803 | 2024-07-02 | 缺勤 |
| 28004 | 502 | 804 | 2024-07-03 | 出勤 |
| 28005 | 502 | 805 | 2024-07-03 | 请假 |

（注：示例仅5行示意；出勤率口径为出勤节数÷(出勤+缺勤)节数，请假剔除分母，与EDU-18、EDU-26统一。）

### 3. 解题思路

口径界定：考察期为当月；出勤率=出勤节数÷(出勤+缺勤)节数，请假剔除分母；分母小于4节的学员不参与排名（最低课节门槛，防止"只上了2节课恰好全勤"挤掉稳定全勤者）；每班取前三，并列场景由方案决定函数选择：ROW_NUMBER强制取3人（需设计决胜键：出勤率、出勤节数、学员ID依次降序/升序），DENSE_RANK保留前三名次档的所有并列者，RANK介于两者语义之间。实现路径：CTE1按班级×学员条件聚合出出勤率，CTE2按班级开窗排名，外层过滤名次；解法一演示ROW_NUMBER+决胜键的严格版，解法二同时输出RANK与DENSE_RANK两列对比并列差异。易错点：ORDER BY只有出勤率没有决胜键，并列行序不确定、榜单不可复现；PARTITION BY class_id漏写变成全校总榜；用ROUND后的展示值排序导致与原始比值的排序不一致；全缺勤学员在无人达标的班级也会"上榜"，门槛条件就是防这个的。

### 4. 参考解法

解法一：ROW_NUMBER严格取三（决胜键版）

```sql
WITH att_stat AS (                   -- CTE1：班级×学员粒度的出勤统计
    SELECT
        class_id,                    -- 班级ID
        student_id,                  -- 学员ID
        SUM(CASE WHEN status = '出勤' THEN 1 ELSE 0 END) AS att_cnt,
                                     -- 出勤节数（分子）
        SUM(CASE WHEN status IN ('出勤', '缺勤') THEN 1 ELSE 0 END) AS total_cnt
                                     -- 应到节数=出勤+缺勤（请假剔除分母）
    FROM attendance
    WHERE lesson_date >= '2024-07-01' AND lesson_date < '2024-08-01'
                                     -- 考察月（半开区间可走索引）
    GROUP BY class_id, student_id
),
ranked AS (                          -- CTE2：班级内排名
    SELECT
        a.class_id,
        s.student_name,              -- 学员姓名（1:1连接只取名，不放大）
        a.att_cnt,
        a.total_cnt,
        ROUND(a.att_cnt / NULLIF(a.total_cnt, 0), 4) AS att_rate,
                                     -- 出勤率（展示用；排序仍用原始比值）
        ROW_NUMBER() OVER (
            PARTITION BY a.class_id  -- 班级内排名，漏写会变全校总榜
            ORDER BY a.att_cnt / NULLIF(a.total_cnt, 0) DESC,
                     a.att_cnt DESC, a.student_id
                                     -- 主排序键：出勤率原始比值；
                                     -- 决胜键：出勤节数、学员ID，保证结果可复现
        ) AS rn
    FROM att_stat a
    JOIN students s ON s.student_id = a.student_id
    WHERE a.total_cnt >= 4           -- 最低课节门槛，防小样本全勤挤榜
)
SELECT
    class_id,                        -- 班级
    rn,                              -- 班内名次
    student_name,                    -- 姓名
    att_rate,                        -- 出勤率
    att_cnt,                         -- 出勤节数
    total_cnt                        -- 应到节数
FROM ranked
WHERE rn <= 3                        -- 每班严格取3人
ORDER BY class_id, rn;
```

结果解读：501班输出恰好3行（如801张小明1.0、802李小红0.9、803王小刚0.75），即便两人出勤率并列，ROW_NUMBER也凭决胜键只保留一位——适合"勋章只有3枚"的表彰场景；业务若不接受并列被挤掉，改用解法二。

解法二：RANK / DENSE_RANK 并列保留版

```sql
WITH att_stat AS (                   -- CTE1：班级×学员出勤统计（同解法一）
    SELECT
        class_id,
        student_id,
        SUM(CASE WHEN status = '出勤' THEN 1 ELSE 0 END) AS att_cnt,
        SUM(CASE WHEN status IN ('出勤', '缺勤') THEN 1 ELSE 0 END) AS total_cnt
    FROM attendance
    WHERE lesson_date >= '2024-07-01' AND lesson_date < '2024-08-01'
    GROUP BY class_id, student_id
),
ranked AS (                          -- CTE2：同时计算两种并列语义的名次
    SELECT
        a.class_id,
        s.student_name,
        ROUND(a.att_cnt / NULLIF(a.total_cnt, 0), 4) AS att_rate,
        RANK() OVER (
            PARTITION BY a.class_id
            ORDER BY a.att_cnt / NULLIF(a.total_cnt, 0) DESC
        ) AS rk,                     -- RANK：并列同名次，后续跳号（1,1,3）
        DENSE_RANK() OVER (
            PARTITION BY a.class_id
            ORDER BY a.att_cnt / NULLIF(a.total_cnt, 0) DESC
        ) AS drk                     -- DENSE_RANK：并列同名次，后续不跳号（1,1,2）
    FROM att_stat a
    JOIN students s ON s.student_id = a.student_id
    WHERE a.total_cnt >= 4           -- 最低课节门槛
)
SELECT
    class_id,                        -- 班级
    rk,                              -- RANK名次（跳号版，供对照）
    drk,                             -- DENSE_RANK名次（紧凑版）
    student_name,                    -- 姓名
    att_rate                         -- 出勤率
FROM ranked
WHERE drk <= 3                       -- 前三名次档全部保留并列
ORDER BY class_id, drk, student_name;
```

结果解读：若501班两人并列第一，本解可能输出4行以上（并列第一2人+第二名1人+第三名1人）；RANK与DENSE_RANK的差异只在并列后的编号跳不跳，表彰发的是"名次档"用DENSE_RANK、发"固定人数"必须回到ROW_NUMBER——输出行数不同不是Bug而是口径，面试中讲清这句即可收尾。

### 5. 性能分析与优化

先按班级×学员聚合（行数从课节级缩到学员级）再开窗，窗口排序只发生在极小结果集上，整体代价由出勤表扫描主导，约 O(N log N)；解法二多一个排名函数但共用同一排序，增量开销很小。优化建议：(1) attendance 建 (lesson_date, class_id, student_id, status) 复合索引或按月分区，考察月过滤与分组一次完成；(2) students只提供姓名，放在开窗前的CTE里做1:1连接不影响量级，切勿先JOIN大维表再聚合；(3) 榜单类需求可把att_stat固化为月表，前端即查即用，跨月对比"连续上榜"也依赖这张表；(4) 班级数千、学员数万时窗口排序仍线性对数级，无性能之忧，反而要警惕门槛条件缺失导致的业务争议。

### 6. 面试延伸考点

- **ROW_NUMBER/RANK/DENSE_RANK输出差异？** 同样两个并列第一：1,2,3；1,1,3；1,1,2。"严格取N"用ROW_NUMBER，"并列保留名次档"用DENSE_RANK，RANK用于需要跳号语义（如竞赛计分）的场景。
- **ORDER BY里为什么必须加决胜键？** 不加则并列行的顺序由执行计划决定，不同批次跑出的名单可能不同，表彰口径漂移、报表不可复现，这是榜单类SQL评审最常指出的缺陷。
- **最低课节门槛为什么重要？** 只上过2节恰好全勤的学员会以100%挤掉稳定全勤者，小样本极端值是率类指标的通病，门槛值（如≥4节）必须与业务确认。
- **如何输出"连续3月上榜"的学员？** 把月度榜单落表后，按学员对月份做连续区间判断（套用EDU-21的日期减行号法），连续上榜者升级表彰并纳入转介绍邀约池。

### 7. 业务拓展思考

出勤榜单的价值远超表彰：上榜学员家长是续费意愿与转介绍的黄金人群，"连续三月上榜"比"单月上榜"信号强得多，应自动进入EDU-20的转介绍邀约池；长期垫底学员则触发班主任一对一回访而非公开批评，榜单只做内部诊断不做公开惩罚。延伸上，出勤率可与作业提交率、完课率合成"投入度指数"，再与续费结果做分群对照，把班主任的经验判断升级为数据驱动的干预优先级排序；当榜单与续费率在班级层面呈现稳定正相关时，还可以反过来把出勤率承诺写进续费前的服务报告，让数据指标直接参与商业动作——这是教培数据岗从"取数"走向"策略"的典型路径。
