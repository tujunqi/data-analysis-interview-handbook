## WL-31 全链路时效异动的仓×线路×时段三维归因分解

### 1. 业务背景

某快递公司时效运营负责人在月度复盘时发现：全网平均全链路时效（揽收→签收）从4月的47.8小时恶化到5月的53.6小时，管理层要求数据分析师说清楚"恶化到底来自哪里"。分析师需要在始发仓、干线线路、揽收时段三个维度上分解这次异动：每个仓库、每条线路、每个时段各自贡献了多少小时的恶化，从中找出贡献最大的取值（例如"WH03仓恶化3.1小时、占总异动的40%"），用来决定下月时效专项治理的资源投向——是整改某个仓的出库效率、调整某条线路的发车计划，还是优化某个时段的揽收波次。这是网络运营中最典型的异动归因决策场景。

### 2. 表结构说明

waybills（运单时效明细表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| waybill_id | VARCHAR(32) | 运单号，主键 |
| origin_wh | VARCHAR(20) | 始发仓编码（WH01/WH02/WH03…） |
| route_id | VARCHAR(20) | 干线线路编号（R001/R002…） |
| hour_seg | VARCHAR(10) | 揽收时段（凌晨/早高峰/日间/晚间） |
| period | CHAR(7) | 账期月（YYYY-MM） |
| total_hours | DECIMAL(6,1) | 全链路耗时（揽收到签收，小时） |

示例数据：

| waybill_id | origin_wh | route_id | hour_seg | period | total_hours |
|------------|-----------|----------|----------|--------|-------------|
| SF2025050001 | WH01 | R001 | 早高峰 | 2025-05 | 46.5 |
| SF2025050002 | WH01 | R002 | 日间 | 2025-05 | 61.2 |
| SF2025050003 | WH02 | R001 | 晚间 | 2025-05 | 39.8 |
| SF2025050004 | WH03 | R003 | 凌晨 | 2025-04 | 52.4 |
| SF2025050005 | WH02 | R002 | 日间 | 2025-04 | 44.1 |

### 3. 解题思路

先明确指标口径：全链路时效必须用**单量加权均值**（Σ总耗时/Σ单量），不能用各单耗时的简单平均，否则大单量组的权重被低估。总异动 ΔA = 本期全网加权均值 − 基期全网加权均值。对任一维度（如仓库），把总体切成互斥子集后，异动可精确分解为两项之和：**水平效应**（组内均值变化 × 本期单量占比）与**结构效应**（单量占比变化 × 基期组内均值），两项按维度内求和恰好等于 ΔA，可严格对账。实现路径：多层CTE分别按基期/本期分组聚合 → JOIN对齐计算两种效应 → 窗口函数算维度内贡献占比并排序。易错点：①三个维度的贡献直接横向相加——跨维度不可加，只能各自维度内归一化后并列呈现；②权重口径混乱（水平效应用本期占比、结构效应用基期占比，混用会导致重复计算）；③基期存在而本期消失的组贡献为负的结构效应，严格口径需补一条反向UNION ALL。

### 4. 参考解法

**解法一：多层CTE + 水平/结构双效应精确分解（可对账口径）**

```sql
WITH base_grp AS (                                -- 基期(2025-04)按仓库分组的汇总
    SELECT origin_wh        AS grp_val,           -- 分组取值：仓库编码
           SUM(total_hours) AS sum_h,             -- 耗时合计（算加权均值用）
           COUNT(*)         AS cnt                -- 基期该仓单量
    FROM waybills
    WHERE period = '2025-04'                      -- 只扫基期分区/账期
    GROUP BY origin_wh                            -- 按仓库聚合
),
cur_grp AS (                                      -- 本期(2025-05)同口径汇总
    SELECT origin_wh        AS grp_val,
           SUM(total_hours) AS sum_h,
           COUNT(*)         AS cnt
    FROM waybills
    WHERE period = '2025-05'
    GROUP BY origin_wh
),
joined AS (                                       -- 基期/本期按取值对齐
    SELECT c.grp_val,
           c.sum_h / c.cnt                        AS avg_cur,   -- 本期组内加权均值
           COALESCE(b.sum_h / b.cnt, 0)           AS avg_base,  -- 基期组内加权均值（新仓记0）
           c.cnt                                  AS cnt_cur,   -- 本期组内单量
           COALESCE(b.cnt, 0)                     AS cnt_base   -- 基期组内单量
    FROM cur_grp c
    LEFT JOIN base_grp b                          -- 以本期为主表，LEFT JOIN保留新增组
      ON b.grp_val = c.grp_val
),
total AS (                                        -- 全网总量，用于归一化权重
    SELECT SUM(cnt_cur)  AS n_cur,                -- 本期全网单量
           SUM(cnt_base) AS n_base                 -- 基期全网单量
    FROM joined
)
SELECT j.grp_val,                                                                  -- 仓库
       ROUND((j.avg_cur - j.avg_base), 2)                                          AS avg_diff,   -- 组内均值变化(小时)
       ROUND((j.avg_cur - j.avg_base) * j.cnt_cur / t.n_cur, 2)                    AS level_eff,  -- 水平效应=均值差×本期占比
       ROUND((j.cnt_cur / t.n_cur - j.cnt_base / t.n_base) * j.avg_base, 2)        AS mix_eff,    -- 结构效应=占比变化×基期均值
       ROUND((j.avg_cur - j.avg_base) * j.cnt_cur / t.n_cur
           + (j.cnt_cur / t.n_cur - j.cnt_base / t.n_base) * j.avg_base, 2)        AS total_eff   -- 该仓合计贡献(小时)
FROM joined j CROSS JOIN total t                                                   -- 与单行总量表做笛卡尔积
ORDER BY total_eff DESC;                                                           -- 恶化贡献降序，头部即整改优先对象
-- 校验：SUM(total_eff) 应等于 全网加权均值(5月) - 全网加权均值(4月)
```

结果解读：total_eff 排名第一的仓库（如 WH03 贡献 +3.1 小时）就是下月治理的第一优先级；level_eff 大说明该仓自身操作变慢，mix_eff 大说明单量涌向了本来就慢的仓，两者对应完全不同的整改动作。

> **【面试高频】** 追问"为什么你算的贡献加起来正好等于总异动？"——因为水平效应固定用本期权重、结构效应固定用基期均值，两项是恒等变形插入项，数学上严格可加；若两个效应都用本期权重，结构项会漏掉，总和就对不上账了。

**解法二：三维度UNION ALL长表 + 自连接一次算完（归因看板通用骨架）**

```sql
WITH long_t AS (                                  -- 三个维度统一展开为"维度-取值-账期"长表
    SELECT '仓库' AS dim_type, origin_wh AS grp_val, period,
           SUM(total_hours) AS sum_h, COUNT(*) AS cnt
    FROM waybills
    GROUP BY origin_wh, period                    -- 仓库维度聚合
    UNION ALL
    SELECT '线路', route_id, period, SUM(total_hours), COUNT(*)
    FROM waybills
    GROUP BY route_id, period                     -- 线路维度聚合
    UNION ALL
    SELECT '时段', hour_seg, period, SUM(total_hours), COUNT(*)
    FROM waybills
    GROUP BY hour_seg, period                     -- 时段维度聚合
),
pivot AS (                                        -- 基期/本期转列对齐到同一行
    SELECT dim_type, grp_val,
           MAX(CASE WHEN period = '2025-04' THEN sum_h END) AS base_h,   -- 基期耗时合计
           MAX(CASE WHEN period = '2025-04' THEN cnt   END) AS base_n,   -- 基期单量
           MAX(CASE WHEN period = '2025-05' THEN sum_h END) AS cur_h,    -- 本期耗时合计
           MAX(CASE WHEN period = '2025-05' THEN cnt   END) AS cur_n     -- 本期单量
    FROM long_t
    GROUP BY dim_type, grp_val
),
calc AS (                                         -- 计算均值与维度内总量
    SELECT dim_type, grp_val,
           cur_h  / NULLIF(cur_n, 0)              AS cur_avg,   -- 本期加权均值(除0保护)
           base_h / NULLIF(base_n, 0)             AS base_avg,  -- 基期加权均值
           cur_n, base_n,
           SUM(cur_n) OVER (PARTITION BY dim_type) AS dim_n     -- 该维度本期总单量(窗口算分母)
    FROM pivot
)
SELECT dim_type,                                                                    -- 维度
       grp_val,                                                                     -- 取值
       ROUND(cur_avg - COALESCE(base_avg, 0), 2)                                    AS avg_diff,  -- 均值变化
       ROUND((cur_avg - COALESCE(base_avg, 0)) * cur_n / dim_n, 2)                  AS contrib_h, -- 简化贡献(小时)
       ROUND(100 * (cur_avg - COALESCE(base_avg, 0)) * cur_n / dim_n
             / SUM((cur_avg - COALESCE(base_avg, 0)) * cur_n / dim_n)
               OVER (PARTITION BY dim_type), 1)                                     AS contrib_pct -- 维度内贡献占比%
FROM calc
ORDER BY dim_type, contrib_h DESC;                                                  -- 每个维度内部按贡献排序
```

结果解读：一个查询同时输出三个维度的贡献榜，直接可挂异动看板；contrib_pct 在每个维度内加总为100%，方便汇报时说"线路维度里R004贡献了58%的恶化"。**【加分点】** 主动说明该简化口径未拆结构效应，适用于单量结构稳定的月份；若单量结构大幅变化（如大促搬家），必须回到解法一的双效应分解。

### 5. 性能分析与优化

解法一扫描两遍明细表（基期+本期各一次），两次GROUP BY后JOIN，结果集只有几十行，代价集中在明细扫描与聚合排序；解法二扫描三遍（每维度一遍），但每遍都可独立走分区裁剪。优化建议：①按 period 做分区或以 (period, origin_wh) 建联合索引，让两个CTE各自只扫对应分区；②月级归因应基于日级预聚合表（按仓×线路×时段×日预先汇总 sum_h、cnt），把扫描量从亿级运单降到万级日汇总，两种解法SQL骨架不变，只换数据源表；③解法二的UNION ALL三段会触发三次shuffle，Hive/Spark下可先GROUP BY (dim_type, grp_val, period)一次完成（dim_type用常量编码列实现），减少两次作业；④JOIN键 grp_val 与 dim_type 均为短字符串，避免VARCHAR(32)运单号级别的宽键JOIN。

> Hive/Spark SQL差异：Hive中 `NULLIF` 可用但建议显式 `CASE WHEN`；大规模下解法二的三段UNION ALL在Hive会展开成多个MapReduce作业，Spark SQL则共享shuffle，优先用Spark；贡献占比窗口在Hive 2.x以下版本不支持PARTITION BY内的表达式，需先物化贡献列再开窗。

### 6. 面试延伸考点

- **水平效应和结构效应如果都统一用本期占比做权重，会有什么问题？** 回答要点：结构项被错误归一，Σ贡献不再等于总异动，差异恰好是"基期结构×均值变化"的交叉项；小样本或结构剧变时对账误差会被放大，面试官在考察异动分解的数学严谨性。
- **如果要求三个维度的贡献能交叉验证（比如锁定"WH03仓×晚间时段"），SQL怎么改？** 回答要点：把维度组合作为联合分组键（origin_wh, hour_seg）做交叉归因，组数=仓×时段，粒度更细但单组样本量下降，需同时输出单量防止小样本误判；可提卡方检验或最小样本阈值过滤。
- **异动归因时本期新增了一个仓库（基期无量），怎么处理？** 回答要点：解法一LEFT JOIN已兼容，其水平效应=本期均值×本期占比、结构效应为0；同时应单独标注"新增组"，因为对它谈"恶化"无意义，属于增量而非异动。
- **为什么用加权均值而不是中位数看时效？** 回答要点：均值反映全网总工时/总体验成本，便于成本关联；中位数抗极端值适合体验视角，二者差异本身可作为长尾恶化的诊断信号（均值恶化但中位数稳定=长尾单量出问题）。

### 7. 业务拓展思考

三维归因结论可直接转化为时效专项治理的优先级清单：对贡献 top1 的仓库下钻到环节级（出库、装车、交接）定位操作瓶颈，对 top1 线路评估加车或改发车时刻，对 top1 时段调整揽收波次或前置分拣资源。口径可延展为"贡献度×可解决性"二维矩阵排优先级，也可把同样的分解框架复用到破损率、投诉率、成本率等任何加权比率指标上，形成网络运营通用的异动归因方法论；进一步可接入周级自动化预警，贡献超阈值的组合自动触发工单。

## WL-32 干线时效达成率7日滑动窗口与劣化预警

### 1. 业务背景

某快运公司的时效管理团队每天监控各干线线路的时效达成率（当日揽收且在承诺时长内签收的单量占比）。单日达成率噪声很大（天气、临时爆仓都会造成单日抖动），直接用单日数据触发报警会天天"狼来了"。团队的标准做法是：对每条线路维护一个**近7日滑动窗口达成率**，当7日达成率跌破92%的承诺红线，且相较前一日窗口仍在恶化（环比下降≥1.5个百分点）或已连续3天下滑时，触发劣化预警，推送给线路运营经理核查发车准点率与分拨滞留。分析师需要写一条SQL，从线路日粒度汇总表出发，输出当日应触发预警的线路清单。

### 2. 表结构说明

dws_route_timeliness_di（线路×日时效达成汇总表，日级预聚合）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stat_date | DATE | 统计日期 |
| route_id | VARCHAR(20) | 干线线路编号 |
| total_cnt | INT | 当日应达成考核单量 |
| on_time_cnt | INT | 当日按时达成单量 |
| avg_hours | DECIMAL(5,1) | 当日均时效（小时） |

示例数据：

| stat_date | route_id | total_cnt | on_time_cnt | avg_hours |
|-----------|----------|-----------|-------------|-----------|
| 2025-07-01 | R001 | 3200 | 3010 | 41.2 |
| 2025-07-02 | R001 | 3450 | 3150 | 43.8 |
| 2025-07-03 | R001 | 3100 | 2860 | 45.1 |
| 2025-07-01 | R002 | 2800 | 2688 | 38.5 |
| 2025-07-02 | R002 | 2950 | 2790 | 39.0 |

### 3. 解题思路

先定口径：7日滑动达成率 = 窗口内Σon_time_cnt / Σtotal_cnt，必须先加总再相除，绝不能对单日达成率求平均（单量不同权重不同）。预警规则拆成三个可计算条件：①7日达成率 < 92%；②环比前一日窗口下降 ≥ 1.5pct；③近3日窗口值逐日下滑（连续性条件）。实现路径：先在日汇总表上开滑动窗口（ROWS BETWEEN 6 PRECEDING AND CURRENT ROW）算出每天的7日达成率，再在外层用 LAG 取前一日的窗口值算环比，用"下滑标记的3行滚动和=3"判定连续下滑，最后过滤出命中预警的线路。易错点：①窗口行数法（ROWS 6 PRECEDING）要求日期无缺口，缺失日期会导致窗口实际不足7天，需先补齐日期骨架或改用RANGE按天区间；②LAG与滑动聚合在同层互相引用会报错，必须分层CTE；③WHERE过滤日期时要注意保留窗口需要的前6天历史。

### 4. 参考解法

**解法一：滑动窗口 + LAG + 连续下滑判定（推荐写法）**

```sql
WITH win AS (                                         -- 第一层：7日滑动窗口加总
    SELECT stat_date, route_id,
           SUM(on_time_cnt) OVER (PARTITION BY route_id ORDER BY stat_date
               ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)              AS on_7d,  -- 窗口内达成单量
           SUM(total_cnt)   OVER (PARTITION BY route_id ORDER BY stat_date
               ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)              AS tot_7d  -- 窗口内应达单量
    FROM dws_route_timeliness_di
    WHERE stat_date >= '2025-06-24'                   -- 7/1起预警，须多留6天喂窗口
),
rate AS (                                             -- 第二层：算出每天的7日达成率
    SELECT stat_date, route_id,
           on_7d / tot_7d                             AS rate_7d,  -- 先加总再相除=加权达成率
           on_7d / tot_7d
             - LAG(on_7d / tot_7d) OVER (PARTITION BY route_id ORDER BY stat_date)
                                                      AS rate_dod  -- 窗口值环比(与前一日窗口差)
    FROM win
),
flag AS (                                             -- 第三层：构造下滑标记与连续性
    SELECT stat_date, route_id, rate_7d, rate_dod,
           CASE WHEN rate_dod < 0 THEN 1 ELSE 0 END   AS down_flag,  -- 当日窗口值环比下滑记1
           SUM(CASE WHEN rate_dod < 0 THEN 1 ELSE 0 END)
               OVER (PARTITION BY route_id ORDER BY stat_date
                   ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)         AS down_3d  -- 近3日下滑天数
    FROM rate
)
SELECT stat_date, route_id,                           -- 输出预警清单
       ROUND(rate_7d * 100, 2)                        AS rate_7d_pct,  -- 7日达成率%
       ROUND(rate_dod * 100, 2)                       AS dod_pct,      -- 环比变化pct
       down_3d                                        AS down_days     -- 连续下滑天数
FROM flag
WHERE rate_7d < 0.92                                  -- 条件①跌破92%红线
  AND (rate_dod <= -0.015 OR down_3d = 3)             -- 条件②明显恶化 或 条件③连降3天
ORDER BY rate_7d ASC;                                 -- 最差的线路排前面
```

结果解读：输出如"R004，7日达成率89.6%，环比-2.3pct"，线路经理按此优先级排查；rate_dod 与 down_days 两个辅助列帮助区分"突发恶化"与"慢性下滑"两种处置路径。

**解法二：自连接区间聚合（不依赖窗口函数的等价写法）**

```sql
WITH win AS (                                         -- 每个观测日自连接它前面的7天
    SELECT t1.stat_date,
           t1.route_id,
           SUM(t2.on_time_cnt) / SUM(t2.total_cnt)    AS rate_7d  -- 区间内先加总再相除
    FROM dws_route_timeliness_di t1
    JOIN dws_route_timeliness_di t2                    -- 同线路、日期落在[t1-6天, t1]的记录
      ON t2.route_id = t1.route_id
     AND t2.stat_date BETWEEN t1.stat_date - INTERVAL 6 DAY AND t1.stat_date
    WHERE t1.stat_date >= '2025-06-24'
    GROUP BY t1.stat_date, t1.route_id                 -- 按观测日聚合出窗口达成率
),
rate AS (                                             -- 外层再取前一日窗口值
    SELECT stat_date, route_id, rate_7d,
           rate_7d - LAG(rate_7d) OVER (PARTITION BY route_id ORDER BY stat_date) AS rate_dod
    FROM win
)
SELECT stat_date, route_id,
       ROUND(rate_7d * 100, 2)                        AS rate_7d_pct,
       ROUND(rate_dod * 100, 2)                       AS dod_pct
FROM rate
WHERE rate_7d < 0.92                                  -- 同一套预警规则
  AND rate_dod <= -0.015
ORDER BY rate_7d;
```

结果解读：与解法一在日期连续时结果完全一致；自连接写法的好处是天然按**日期区间**取数，即使某天数据缺失，窗口也按真实日期跨度取满7天，不会因行数不足而错算。**【避坑指南】** 解法一按"行数"取窗、解法二按"日期区间"取窗，日汇总表缺数时两者会给出不同结果，面试时能主动指出这一差异是重要加分项。

### 5. 性能分析与优化

解法一只需一次排序（PARTITION BY route_id ORDER BY stat_date）流式聚合，复杂度O(N)；解法二自连接在7天窗口下每行匹配约7条，代价约7N次比较加GROUP BY，且连接键是(route_id, stat_date)双列。数据量为"线路数×天数"（几百条线路×一年≈几十万行）时两者都可接受，数据量上到千万级（票级明细直接算）时必须：①预聚合到日粒度再开窗（本表已是）；②为(route_id, stat_date)建联合索引或按stat_date分区；③滑动窗口若只需最新一天结果，可改为`WHERE stat_date > 当日-7`的固定区间GROUP BY，避免全历史开窗；④连续下滑判定若不需要，可去掉一层窗口减少一次排序。

> Hive/Spark SQL差异：Hive支持ROWS BETWEEN滑动窗口但老版本对RANGE INTERVAL支持差；自连接写法在Hive会触发shuffle join，数据大时建议开窗法；Spark SQL下可将route_id+stat_date编码后用window无需额外索引，物理执行靠AQE优化。

### 6. 面试延伸考点

- **为什么用"先加总再相除"而不是对单日达成率求7日平均？** 回答要点：各日单量不同，平均达成率等于给小单量日过高权重，会产生偏差；加权口径才能反映真实的达成单占比，这是比率型指标滑动窗口的标准做法。
- **如果某线路某天数据缺失，两种写法分别会发生什么？** 回答要点：ROWS行数窗口只取到6行，实际是"近6个有数日"；RANGE/自连接按日期区间取，窗口仍是7天但少算一天单量；生产上应先补齐日期骨架（日历表LEFT JOIN）再开窗。
- **如何把"连续3天下滑"改成"7天内至少5天下滑"？** 回答要点：把窗口从ROWS 2 PRECEDING改为6 PRECEDING，阈值改为down_7d >= 5，体现滑动窗口参数化能力。
- **预警阈值92%和1.5pct是怎么定的？** 回答要点：92%来自对客户承诺的SLA红线，1.5pct来自历史窗口值日波动的标准差（约2倍σ），强调阈值要由数据分布而不是拍脑袋决定。

### 7. 业务拓展思考

滑动窗口预警结论可直接驱动线路运营动作：触发预警的线路自动生成核查工单，关联当日分拨滞留时长与发车准点率做二级归因。口径可延展为分产品分层预警（特快件红线更高）、按始发仓聚合同线路簇预警，以及把7日窗口升级为"7日+14日"双窗口对比以区分短期抖动与趋势性劣化；长期可与排班、运力采购系统打通，实现预警到动作的闭环。

## WL-33 单票成本拆解（仓干配三段）与优化空间定位

### 1. 业务背景

某电商仓配一体的物流公司单票履约成本连续两季上涨，成本分析专员需要把每票快递的履约成本拆成**仓内操作、干线运输、末端配送**三段，回答两个问题：钱花在了哪一段？哪些"产品×区域"组合的单票成本显著高于同类基准、压降空间有多大？结论用于制定季度降本方案——例如发现"大件产品发往西北"的组合末端配送成本比产品均值高40%，就会推动该区域改用落地配或调整计费策略。成本分析师按月出这张"成本地图"，是网络规划会上的核心材料。

### 2. 表结构说明

cost_detail（运单分段子成本表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| waybill_id | VARCHAR(32) | 运单号 |
| seg | VARCHAR(10) | 成本段：仓内操作/干线运输/末端配送 |
| cost_amt | DECIMAL(8,2) | 该段归集成本（元） |

waybill_base（运单主属性表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| waybill_id | VARCHAR(32) | 运单号 |
| product_type | VARCHAR(10) | 产品类型：电商小件/大件/生鲜 |
| dest_region | VARCHAR(10) | 目的区域：华东/华南/华北/西北… |
| bill_weight_kg | DECIMAL(6,2) | 计费重量（kg） |

示例数据（cost_detail）：

| waybill_id | seg | cost_amt |
|------------|-----|----------|
| SF2025060001 | 仓内操作 | 1.80 |
| SF2025060001 | 干线运输 | 3.50 |
| SF2025060001 | 末端配送 | 2.20 |
| SF2025060002 | 仓内操作 | 2.60 |
| SF2025060002 | 干线运输 | 8.90 |

示例数据（waybill_base）：

| waybill_id | product_type | dest_region | bill_weight_kg |
|------------|--------------|-------------|----------------|
| SF2025060001 | 电商小件 | 华东 | 1.20 |
| SF2025060002 | 大件 | 西北 | 28.50 |
| SF2025060003 | 生鲜 | 华东 | 3.80 |
| SF2025060004 | 电商小件 | 华南 | 0.90 |
| SF2025060005 | 大件 | 华北 | 15.00 |

### 3. 解题思路

先定口径：单票成本 = 三段成本之和，段占比 = 段成本/单票总成本；"优化空间"定义为（组合单票均值成本 − 同产品全网基准）×组合单量，基准用同产品类型全网单票均值，保证比较时产品结构不变。实现路径：先把cost_detail用条件聚合成"一票一行"的宽表（三段各一列），关联主属性表后按"产品×区域"网格聚合出单票均值与段占比，再用窗口函数在同一结果集上算出产品级全网基准与差值、排序。易错点：①一票在cost_detail中可能缺某一段记录（如仓储外包单无仓内成本），条件聚合必须用SUM+CASE且缺失段按0处理并单独核查缺失率；②基准如果用"产品×区域"自身均值就失去了对比意义；③优化空间是金额概念，必须乘单量，只看单票差值会误导优先级。

### 4. 参考解法

**解法一：条件聚合转列 + 窗口算基准（行级宽表路径）**

```sql
WITH ticket AS (                                      -- 一票一行：三段成本转列
    SELECT w.waybill_id,
           w.product_type,                            -- 产品类型
           w.dest_region,                             -- 目的区域
           SUM(CASE WHEN c.seg = '仓内操作' THEN c.cost_amt ELSE 0 END) AS wh_cost,   -- 仓内段成本(缺失记0)
           SUM(CASE WHEN c.seg = '干线运输' THEN c.cost_amt ELSE 0 END) AS line_cost, -- 干线段成本
           SUM(CASE WHEN c.seg = '末端配送' THEN c.cost_amt ELSE 0 END) AS last_cost, -- 末端段成本
           SUM(c.cost_amt)                            AS total_cost   -- 单票总成本
    FROM waybill_base w
    JOIN cost_detail c ON c.waybill_id = w.waybill_id -- 运单属性关联分段成本
    GROUP BY w.waybill_id, w.product_type, w.dest_region
),
grid AS (                                             -- 产品×区域网格聚合
    SELECT product_type, dest_region,
           COUNT(*)                          AS cnt,                 -- 组合单量
           AVG(total_cost)                   AS avg_cost,            -- 组合单票均值成本
           AVG(wh_cost)   / NULLIF(AVG(total_cost),0) AS wh_pct,   -- 仓内段占比
           AVG(line_cost) / NULLIF(AVG(total_cost),0) AS line_pct, -- 干线段占比
           AVG(last_cost) / NULLIF(AVG(total_cost),0) AS last_pct  -- 末端段占比
    FROM ticket
    GROUP BY product_type, dest_region
)
SELECT g.product_type, g.dest_region, g.cnt, g.avg_cost,
       ROUND(g.avg_cost
           / AVG(AVG(g.avg_cost)) OVER (PARTITION BY g.product_type), 3) AS cost_index,  -- 成本指数(1=产品全网水平)
       ROUND(AVG(g.avg_cost) OVER (PARTITION BY g.product_type), 2)      AS bench_cost, -- 产品全网基准
       ROUND((g.avg_cost - AVG(g.avg_cost) OVER (PARTITION BY g.product_type)) * g.cnt, 0)
                                                                         AS save_space, -- 优化空间(元)=单票差×单量
       ROUND(g.wh_pct * 100, 1)   AS wh_pct,                             -- 段占比用于定位是哪段贵
       ROUND(g.line_pct * 100, 1) AS line_pct,
       ROUND(g.last_pct * 100, 1) AS last_pct
FROM grid g
ORDER BY save_space DESC;                                             -- 按优化空间降序=降本优先级
-- 注意：AVG(AVG(x)) OVER() 是"先算组均值再对组均值求均值"，即未加权的组均值基准
```

结果解读：首行如"大件×西北，单票18.6元，成本指数1.42，优化空间21万元，末端占比58%"，直接指向该组合的末端配送是降本抓手；成本指数剔除产品结构影响，方便跨组合横向比较。

**解法二：先分段预聚合再三次关联（先聚合后JOIN的减量路径）**

```sql
WITH seg_agg AS (                                     -- 先在"网格×段"粒度聚合，行数远小于明细
    SELECT w.product_type, w.dest_region, c.seg,
           COUNT(DISTINCT c.waybill_id)               AS cnt,    -- 组合票数
           SUM(c.cost_amt)                            AS seg_amt -- 该段成本总额
    FROM cost_detail c
    JOIN waybill_base w ON w.waybill_id = c.waybill_id
    GROUP BY w.product_type, w.dest_region, c.seg
),
grid AS (                                             -- 网格粒度转列：三段各一列
    SELECT product_type, dest_region,
           MAX(cnt)                                   AS cnt,     -- 任一段的票数即组合票数
           MAX(CASE WHEN seg = '仓内操作' THEN seg_amt END) / MAX(cnt) AS wh_cost,   -- 仓内单票均值
           MAX(CASE WHEN seg = '干线运输' THEN seg_amt END) / MAX(cnt) AS line_cost, -- 干线单票均值
           MAX(CASE WHEN seg = '末端配送' THEN seg_amt END) / MAX(cnt) AS last_cost, -- 末端单票均值
           SUM(seg_amt) / MAX(cnt)                    AS avg_cost -- 单票总成本
    FROM seg_agg
    GROUP BY product_type, dest_region
),
bench AS (                                            -- 产品级基准(把网格再加权一次)
    SELECT product_type,
           SUM(avg_cost * cnt) / SUM(cnt)             AS bench_cost  -- 加权基准(按组合单量)
    FROM grid
    GROUP BY product_type
)
SELECT g.product_type, g.dest_region, g.cnt,
       ROUND(g.avg_cost, 2)                           AS avg_cost,
       ROUND(b.bench_cost, 2)                         AS bench_cost,
       ROUND((g.avg_cost - b.bench_cost) * g.cnt, 0)  AS save_space,   -- 优化空间(元)
       ROUND(g.wh_cost / g.avg_cost * 100, 1)         AS wh_pct,       -- 仓内占比%
       ROUND(g.line_cost / g.avg_cost * 100, 1)       AS line_pct,     -- 干线占比%
       ROUND(g.last_cost / g.avg_cost * 100, 1)       AS last_pct      -- 末端占比%
FROM grid g
JOIN bench b ON b.product_type = g.product_type       -- 网格只有几十行，JOIN代价极低
ORDER BY save_space DESC;
```

结果解读：与解法一结论一致，但解法二是"先聚合后关联"——JOIN发生在几十行的网格与几行的基准表之间，而不是千万行明细上；且bench用单量加权均值，比解法一未加权的组均值基准更严格。**【加分点】** 能对比说明：解法一适合需要下钻到单票明细的场景，解法二适合固定报表的批量生产。

### 5. 性能分析与优化

解法一的代价集中在：明细JOIN（千万行级shuffle）、按运单GROUP BY（又一次shuffle）、窗口按product_type分区排序；解法二把转列挪到聚合之后，最终JOIN只有几十行，整体shuffle数据量小一个量级。优化建议：①两表按waybill_id分桶（CLUSTERED BY waybill_id INTO n BUCKETS）可将JOIN转为map-side；②cost_detail按seg建稀疏索引意义不大（只有3个值），按月分区即可；③bill_weight_kg若用于公斤成本（单票成本/计费重量）分析，在ticket层一次算出避免二次扫描；④固定月报建议物化"网格×段"中间表，月度增量刷新。

> Hive/Spark SQL差异：Hive的MAX(CASE WHEN)转列是标准pivot写法；Spark 3.x可直接用PIVOT子句替代条件聚合；千万行JOIN在Hive需开启mapjoin自动转换（bench表很小可broadcast）。

### 6. 面试延伸考点

- **为什么基准用"同产品均值"而不是"全网均值"？** 回答要点：控制产品结构变量——大件与小件成本天然不可比；若用全网均值，某区域大件占比高会被误判为"成本高"，辛普森悖论的经典场景。
- **某段成本缺失（如无仓内记录）时你的SQL会怎么算？怎么防范？** 回答要点：SUM+CASE缺失段记0，总成本被低估；应先输出各组合的段缺失率，缺失率超阈值的组合单独标注或剔除，面试考察数据质量意识。
- **优化空间21万元这个数怎么向业务解释它的置信度？** 回答要点：说明它是"静态差额"——假设组合单量与基准可达性不变的上限估计，实际可达空间要扣除距离基准的合理性因素（如西北末端天然贵），可辅以同组合历史最优月份做第二基准。
- **如果要拆到"每公斤成本"，SQL改动在哪？** 回答要点：ticket层加SUM(bill_weight_kg)，网格层用seg_amt/SUM(weight)，口径变为元/公斤，更能解释大件的干线与末端成本差异。

### 7. 业务拓展思考

单票成本地图可直接支撑三个决策：网络规划会上的线路与分拨调整、商务定价的产品加价策略、大客户合同的阶梯报价测算。口径可延展为"成本×时效"双维象限（又贵又慢的组合优先治理）、与收入联动的单票毛利地图，以及把末端配送段进一步拆到快递员粒度做人力成本归因；持续跟踪成本指数的月度变化还能评估降本专项的真实效果，避免"降本"被产品结构变化掩盖。

## WL-34 大促期间分仓运能缺口与积压测算

### 1. 业务背景

双十一前四周，仓网规划团队需要测算各分仓在大促峰值周的**运能缺口**：预测单量（来自算法团队的下单预测）与分仓可用处理能力（场地分拣产能与干线发运能力的较小值）逐日对比，回答三个问题——哪些仓哪几天会出现当日产能不足？不足的单量会积压到后续日子形成雪球吗？峰值日需要临时增补多少产能（临时工、外包干线车）才能把积压控制在24小时内消化？测算结果直接决定大促前的临时工招聘数量与干线包车合同量，是典型的"预测-能力-缺口-补救"运能规划闭环。

| WH01 | 2025-11-12 | 80000 | 92000 |

### 3. 解题思路

先定口径：有效产能 = LEAST(场地分拣产能, 干线发运能力)——两者是流水线的上下游，瓶颈取小值；当日缺口 g = 预测单量 − 有效产能，g>0 表示当日消化不完。关键在**积压**的口径：当日处理不完的单滚入次日，次日可用产能要先还旧账再接新单，因此积压满足递推 back t = GREATEST(back(t-1) + g_t, 0)。这里有个高频陷阱：**直接对 g 做累积和是错的**——一旦累积值转负（产能富余日），后续正缺口被错误地"抵扣"了历史已清零的积压。实现路径：解法一给出笔试常用的简化口径（累积缺口的峰值，适用产能弹性可调剂的近似），解法二用**递归CTE逐日迭代**精确模拟积压，并输出需增补的峰值产能。易错点：除上述累积陷阱外，还有两表日期未对齐（用JOIN后内连接丢日）、忽略瓶颈取小值导致高估产能。

### 4. 参考解法

**解法一：累积缺口窗口法（快速估算，笔试常用）**

```sql
WITH day_gap AS (                                     -- 逐日缺口
    SELECT f.wh,
           f.forecast_date,
           f.forecast_cnt,                            -- 预测单量
           LEAST(c.process_cap, c.line_cap)           AS eff_cap,  -- 有效产能=两段产能取小(瓶颈)
           f.forecast_cnt - LEAST(c.process_cap, c.line_cap) AS g    -- 当日缺口(正=产能不足)
    FROM forecast_orders f
    JOIN capacity_plan c
      ON c.wh = f.wh AND c.cap_date = f.forecast_date -- 仓+日期双键对齐
)
SELECT wh, forecast_date, forecast_cnt, eff_cap, g,
       SUM(g) OVER (PARTITION BY wh ORDER BY forecast_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)          AS cum_gap,  -- 累积缺口
       MAX(SUM(g) OVER (PARTITION BY wh ORDER BY forecast_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW))
           OVER (PARTITION BY wh)                                     AS peak_gap   -- 该仓峰值累积缺口
FROM day_gap
ORDER BY wh, forecast_date;
-- 峰值累积缺口 ≈ 该仓大促期间需要临时增补的产能规模(简化口径)
```

结果解读：WH01峰值累积缺口若为30000单，规划上即"需按峰值临时增补约3万单/日的处理能力或允许积压"；注意该口径在产能富余日不会清零积压，属于偏保守的上限估计。

**解法二：递归CTE逐日模拟积压（精确口径，含"积压清零"逻辑）**

```sql
WITH RECURSIVE day_gap AS (                           -- 先物化逐日缺口(与解法一同)
    SELECT f.wh, f.forecast_date,
           f.forecast_cnt,
           LEAST(c.process_cap, c.line_cap)           AS eff_cap,
           f.forecast_cnt - LEAST(c.process_cap, c.line_cap) AS g
    FROM forecast_orders f
    JOIN capacity_plan c
      ON c.wh = f.wh AND c.cap_date = f.forecast_date
),
backlog(wh, d, g, back) AS (                          -- 递归表：仓/日期/缺口/期末积压
    SELECT wh, forecast_date, g, GREATEST(g, 0)       -- 锚点：每个仓的第一天,积压=max(缺口,0)
    FROM day_gap
    WHERE (wh, forecast_date) IN (                    -- 取每个仓的起始日
        SELECT wh, MIN(forecast_date) FROM day_gap GROUP BY wh
    )
    UNION ALL
    SELECT d.wh, d.forecast_date, d.g,
           GREATEST(b.back + d.g, 0)                  -- 递推:昨日期末积压+今日缺口,下限0
    FROM backlog b
    JOIN day_gap d
      ON d.wh = b.wh                                  -- 同仓
     AND d.forecast_date = b.d + INTERVAL 1 DAY       -- 按日推进一天
)
SELECT wh, d AS forecast_date, g AS day_gap, back AS end_backlog,
       GREATEST(g + back, 0)                          AS need_extra_cap  -- 当日需增补产能=缺口+期初积压
FROM backlog
ORDER BY wh, d;
-- need_extra_cap 的最大值即该仓临时工/包车签约量的依据
```

结果解读：递归写法精确还原"先还旧账再接新单"的物理过程——若11日缺口35000但12日产能富余5000，解法一会把30000积压永远挂着，解法二则正确显示12日后积压继续滚存或被消化。**【面试高频】** 面试官常追问"为什么不能用窗口累积和替代递归"——正是因为GREATEST(x,0)的非线性截断使递推无法表达为线性窗口运算。

### 5. 性能分析与优化

解法一一次JOIN加一次窗口，代价为O(N log N)；解法二递归CTE在MySQL中按日迭代，深度=大促天数（约15层），每层JOIN day_gap，代价可控但**层数等于日期跨度**，若做全年模拟需注意 `cte_max_recursion_depth`（默认1000）。优化建议：①两张表先按(wh, date)聚合并建立(wh, cap_date)索引，JOIN避免笛卡尔；②day_gap物化为临时表供递归引用，避免每层重复计算JOIN；③若仓库数上千，可在应用层按仓并行；④真正的海量场景（仓×SKU×日）下递归不可用时，用Spark的迭代算子或在数仓用累计+重置段的gaps-and-islands窗口法近似。另外把 forecast 与 capacity 统一日期骨架（日历表驱动），防止内连接丢日导致缺口漏算。

> Hive/Spark SQL差异：Hive不支持RECURSIVE CTE，解法二需改写为"迭代临时表"（INSERT INTO ... SELECT 逐日跑N次）或用Spark Scala/DataFrame的iterate；简化口径解法一则可直接迁移，且Hive下建议把两个窗口合并为一次OVER子句减少shuffle。

### 6. 面试延伸考点

- **为什么有效产能取LEAST(分拣产能, 干线产能)而不是求和？** 回答要点：分拣与发运是串行工序，系统吞吐由瓶颈工序决定，求和会双倍高估产能；这是运营管理中的约束理论（TOC）思想。
- **如果预测本身有±15%误差，测算怎么做得更稳健？** 回答要点：对预测取P90分位情景重跑缺口，或在缺口上叠加安全余量；报告同时给中性与悲观两套缺口值，体现情景规划意识。
- **积压口径为什么必须GREATEST(x,0)截断到非负？** 回答要点：积压是实物未处理单量，物理上不能为负；不截断会把产能富余错误地"预支"给未来缺口，低估峰值增补需求。
- **如何测算"把积压控制在24小时内"需要的产能？** 回答要点：反解递推式——令每日 end_backlog <= 次日eff_cap，求得每日常规产能之外的最小增补序列，SQL上可用窗口LEAD做次日产能比对。

### 7. 业务拓展思考

缺口测算结论直接生成三类执行清单：临时工需求按仓按日的人力排班表、干线包车合同的运力采购量、以及超产能仓的订单迁移方案（把预测单量引导至临近富余仓，即仓间分流）。口径可延展到小时级产能（应对峰值日内波峰）、按产品线拆分产能（大件与小件分拣线互不通用），以及把单量缺口折算为面积、人手、车辆三种资源语言，分别对接场务、人力、运力三个采购团队，让一份SQL产出驱动整条大促备战链路。

## WL-35 破损率根因定位（包装×分拨环节交叉分析）

### 1. 业务背景

某快递公司6月全网破损率从5月的0.42%上升到0.55%，质量管理团队必须在周会前回答"破损到底发生在哪"。破损与两个因素强相关：**包装类型**（纸箱、编织袋、原厂包装、气泡袋）与**发生环节**（始发分拨、干线装卸、中转分拨、末端分拨）。单看包装边际或环节边际都不够——真正的高风险往往是特定组合（例如"编织袋×中转分拨"，可能因编织袋在中转槽口易被传送带夹角钩破）。分析师需要做交叉定位：哪些"包装×环节"组合对总体破损率上升贡献最大、哪些组合存在超出两个因素独立作用预期的**交互放大效应**，用于指导包装规范修订与分拨设备改造的投入方向。

### 2. 表结构说明

damage_log（运单破损记录明细表，一单一行）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| waybill_id | VARCHAR(32) | 运单号 |
| stat_month | CHAR(7) | 账期月（YYYY-MM） |
| package_type | VARCHAR(10) | 包装类型：纸箱/编织袋/原厂包装/气泡袋 |
| hub_node | VARCHAR(10) | 判定破损环节：始发分拨/干线装卸/中转分拨/末端分拨 |
| is_broken | TINYINT | 是否破损（1是/0否），全表均为1的记录+全量单量表配合使用 |

示例数据：

| waybill_id | stat_month | package_type | hub_node | is_broken |
|------------|------------|--------------|----------|-----------|
| SF2025060001 | 2025-06 | 编织袋 | 中转分拨 | 1 |
| SF2025060002 | 2025-06 | 纸箱 | 干线装卸 | 1 |
| SF2025060003 | 2025-06 | 编织袋 | 中转分拨 | 1 |
| SF2025060004 | 2025-05 | 原厂包装 | 末端分拨 | 1 |
| SF2025060005 | 2025-06 | 气泡袋 | 始发分拨 | 1 |

同时需要全量运单分母表（题中用 waybill_cnt 代替：按 stat_month × package_type × hub_node 统计的票数，示例：2025-06、编织袋、中转分拨、182000 票）。

### 3. 解题思路

先定口径：组合破损率 = 该组合破损票数 / 该组合总票数；对总体破损率上升的贡献采用"组合本期破损率 − 基期全网破损率"×"组合本期票数占全网比例"的近似贡献分解（与WL-31同框架但以全网基期率为锚，便于跨组合比较绝对抬升）。第二层分析是**交互效应**：若包装与环节相互独立，组合期望破损率 ≈ 包装边际率 × 环节边际率 / 全网率；实际率/期望率即交互提升度，显著大于1说明该组合存在"1+1>2"的物理性风险，是设备或包装改造的靶点。实现路径：交叉聚合本期/基期组合票数与破损数 → 窗口算边际率 → 贡献分解与提升度两个视角输出。易错点：①破损明细表只有破损单，分母必须从全量表来，直接用破损表内部占比会算错率；②小样本组合（票数低于阈值）的提升度会虚高，必须设最低票数门槛；③环节判定依赖人工登记，存在归因漂移，结论要配合现场复核。

### 4. 参考解法

**解法一：组合贡献分解（对总体破损率上升的归因）**

```sql
WITH denom AS (                                       -- 分母：全量票数(包×环节组合×月份)
    SELECT stat_month, package_type, hub_node,
           COUNT(*) AS n                              -- 该组合当月总票数
    FROM waybill_all                                  -- 全量运单表(含未破损)
    GROUP BY stat_month, package_type, hub_node
),
cur_cell AS (                                         -- 本期组合破损率
    SELECT d.package_type, d.hub_node,
           d.n                                        AS n_cur,        -- 本期组合票数
           COALESCE(br.broken_cnt, 0)                 AS broken_cur,   -- 本期组合破损票数
           COALESCE(br.broken_cnt, 0) / d.n           AS r_cur         -- 组合破损率
    FROM denom d
    LEFT JOIN (SELECT stat_month, package_type, hub_node, COUNT(*) AS broken_cnt
               FROM damage_log WHERE stat_month = '2025-06'
               GROUP BY stat_month, package_type, hub_node) br    -- 破损明细聚合
      ON br.stat_month = '2025-06'
     AND br.package_type = d.package_type
     AND br.hub_node = d.hub_node
    WHERE d.stat_month = '2025-06'
),
base_all AS (                                         -- 基期全网破损率(单值锚)
    SELECT SUM(CASE WHEN stat_month = '2025-05' THEN 1 ELSE 0 END) AS broken_base, -- 5月破损总数
           SUM(CASE WHEN stat_month = '2025-06' THEN 1 ELSE 0 END) AS broken_cur_all   -- 6月破损总数
    FROM damage_log
),
calc AS (
    SELECT c.package_type, c.hub_node, c.n_cur, c.r_cur,
           SUM(c.n_cur) OVER ()                       AS n_all,        -- 本期全网总票数(窗口算分母)
           (SELECT broken_base FROM base_all)         / (SELECT SUM(n) FROM denom WHERE stat_month='2025-05')
                                                      AS r_base_all    -- 基期全网破损率
    FROM cur_cell c
)
SELECT package_type, hub_node,
       n_cur,
       ROUND(r_cur * 100, 3)                                        AS rate_pct,    -- 组合破损率%
       ROUND((r_cur - r_base_all) * n_cur / n_all * 100, 3)         AS contrib_pct, -- 对总体破损率的抬升(百分点)
       ROUND(r_cur / NULLIF(r_base_all, 0), 2)                      AS risk_index   -- 相对全网基期的风险指数
FROM calc
ORDER BY contrib_pct DESC;                                            -- 贡献最大的组合排最前
```

结果解读：若"编织袋×中转分拨"贡献0.08个百分点、占总体上升0.13个百分点的六成，即锁定主因组合；risk_index>1.5的组合同时提示相对风险水平。

**解法二：边际期望法定位交互放大效应（独立性假设下的提升度）**

```sql
WITH cur AS (                                         -- 本期组合粒度：票数与破损数
    SELECT d.package_type, d.hub_node,
           COUNT(*)      AS n,                        -- 组合票数
           SUM(b.is_broken) AS broken                 -- 组合破损数(LEFT JOIN补0)
    FROM waybill_all d
    LEFT JOIN damage_log b
      ON b.waybill_id = d.waybill_id
     AND b.stat_month = '2025-06'
    WHERE d.stat_month = '2025-06'
    GROUP BY d.package_type, d.hub_node
),
marg AS (                                             -- 边际率与全网率(一次开窗全算完)
    SELECT package_type, hub_node, n, broken,
           SUM(n)     OVER (PARTITION BY package_type) AS n_pack,   -- 包装边际票数
           SUM(broken) OVER (PARTITION BY package_type) AS b_pack,  -- 包装边际破损数
           SUM(n)     OVER (PARTITION BY hub_node)     AS n_hub,    -- 环节边际票数
           SUM(broken) OVER (PARTITION BY hub_node)    AS b_hub,    -- 环节边际破损数
           SUM(n)     OVER ()                          AS n_all,    -- 全网票数
           SUM(broken) OVER ()                         AS b_all     -- 全网破损数
    FROM cur
)
SELECT package_type, hub_node, n,
       ROUND(broken / n * 100, 3)                                          AS rate_pct,   -- 实际组合破损率%
       ROUND((b_pack / n_pack) * (b_hub / n_hub) / (b_all / n_all) * 100, 3)
                                                                           AS expect_pct, -- 独立性假设下的期望破损率%
       ROUND((broken / n)
             / NULLIF((b_pack / n_pack) * (b_hub / n_hub) / (b_all / n_all), 0), 2)
                                                                           AS lift        -- 交互提升度=实际/期望
FROM marg
WHERE n >= 10000                                                      -- 最低票数门槛防小样本虚高
ORDER BY lift DESC;                                                   -- 提升度大的组合=交互热点
```

结果解读：lift=1.8 意味着该组合破损率比"包装与环节各自风险独立叠加"高80%，指向组合特异的物理机制（如编织袋在中转槽口被钩破），比单维结论更能指导设备与包装的联合改造。**【避坑指南】** 提升度只对票数足够的组合可信，务必带 n 门槛；且环节字段由人工判定，"破损发生在中转"可能被末端操作员习惯性误填，结论需现场复核校准。

### 5. 性能分析与优化

解法一涉及全量分母表聚合（最大代价）与破损明细聚合再LEFT JOIN，组合数只有16个左右（4包装×4环节），聚合后极小；解法二全在组合粒度上开窗，几乎零额外代价，但LEFT JOIN回明细表取破损标记时注意走waybill_id主键点查。优化建议：①waybill_all按stat_month分区、(package_type, hub_node)建联合索引加速GROUP BY；②若全量表巨大，可月级预聚合"组合×月"的票数与破损数小表，两个解法都只需扫小表；③damage_log里全为is_broken=1的行，聚合时用COUNT(*)而非SUM(is_broken)减少语义混乱；④解法一中相关子查询(base_all)在MySQL会执行一次并缓存，但更稳妥的写法是提为独立CTE CROSS JOIN。

> Hive/Spark SQL差异：Hive下相关子查询支持有限，base_all务必改写为CTE；组合粒度小表开窗在两个引擎都高效；亿级全量表建议按月分区+动态分区裁剪，并在数仓层固化"组合×月"质量小表供质量团队例行取数。

### 6. 面试延伸考点

- **破损表只有破损单，破损率的分母从哪来？如果全量表太大怎么办？** 回答要点：必须用全量票数做分母；太大则用预聚合的组合×月票数小表，或抽样估计并给出置信区间，考察对"率"的分子分母口径完整性意识。
- **交互提升度1.8意味着什么？它和贡献度有什么区别？** 回答要点：提升度衡量"组合相对独立性假设的异常放大"，是机制层面的诊断；贡献度衡量"该组合对总体指标上升的量级"，是优先级层面的排序；高提升度×低票数的组合贡献可能很小。
- **如果包装类型登记不全（30%运单包装未知），分析怎么做？** 回答要点：单独列"未知"组防止选择偏差，比较已知组结论是否稳定；或对登记率高的分拨先做局部结论，并把登记完整度纳入流程整改。
- **如何验证"编织袋×中转分拨"确实是物理因果而非数据假象？** 回答要点：A/B试点——该组合在中转分拨改用缓冲槽口或更换包装，对比试点前后破损率（呼应DID思路），体现从归因到实验验证的闭环。

### 7. 业务拓展思考

交叉归因结论可落地为三项动作：高风险组合的包装规范强制升级（如编织袋在中转环节加装护角）、分拨设备改造排期（槽口加装缓冲条）、以及保险与赔付策略的分组合差异化定价。口径可延展到三维（包装×环节×季节，雨季编织袋破损放大）、与运单体积重量交叉定位"重货压轻货"机制，以及把贡献度框架沉淀为质量月报模板，让每次质量异动都能在一小时内给出"发生在哪、为什么是那里、建议改什么"的完整链路答案。

## WL-36 干线班次合空率分析与拼车合并潜力测算

### 1. 业务背景

某零担快运公司的干线运输部每月分析班次**合空率**（空载浪费率 = 1 − 实载重量/核定载重）。全网约35%的班次装载率不足50%，尤其是非高峰时段的小票数线路，一辆17.5米挂车只拉了4吨货跑干线，油费路桥费却一分不少。运输经理希望分析师回答：哪些线路哪些时段的合空率最严重？如果允许把同线路、发车时间接近的两个班次**合并为一班**（前提是合计实载不超过其中较大车型的核定载重），理论上一个月能省多少个班次、折合多少运输成本？结论用于调整发车时刻表与推行"小票拼车"排班策略，是干线运力成本优化的核心分析。

### 2. 表结构说明

line_trips（干线班次表，一班一行）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| trip_id | VARCHAR(20) | 班次ID |
| route_id | VARCHAR(20) | 线路编号 |
| trip_date | DATE | 发车日期 |
| depart_time | DATETIME | 实际发车时间 |
| truck_type | VARCHAR(10) | 车型：9.6米/17.5米 |
| max_load_kg | INT | 核定载重（kg） |
| actual_load_kg | INT | 实际装载重量（kg） |

示例数据：

| trip_id | route_id | trip_date | depart_time | truck_type | max_load_kg | actual_load_kg |
|---------|----------|-----------|-------------|------------|-------------|----------------|
| T2025060101 | R001 | 2025-06-01 | 2025-06-01 08:00 | 9.6米 | 12000 | 9800 |
| T2025060102 | R001 | 2025-06-01 | 2025-06-01 09:40 | 9.6米 | 12000 | 2100 |
| T2025060103 | R001 | 2025-06-01 | 2025-06-01 14:00 | 17.5米 | 30000 | 11500 |
| T2025060104 | R002 | 2025-06-01 | 2025-06-01 07:30 | 17.5米 | 30000 | 6800 |
| T2025060105 | R002 | 2025-06-01 | 2025-06-01 10:10 | 9.6米 | 12000 | 10400 |

### 3. 解题思路

先定口径：班次装载率 = actual_load_kg / max_load_kg，合空率 = 1 − 装载率；线路×车型月度合空率要按重量加权（Σ实载/Σ核定），不能对班次装载率简单平均。可合并判定规则：同线路同日、两班发车间隔 ≤ 120分钟、合计实载 ≤ 两班中较大核定载重（保守用较小车型核载，保证一定能装下），即认为可以合并省1个班次。实现路径：解法一用LAG在同线路同日内构造"前一班→本班"配对，对满足条件的配对做贪心去重（每班最多参与一次合并）后统计可省班次；解法二用自连接枚举所有可行配对，按线路聚合给出潜在节省与成本折算，并讨论链式合并（三班并两班）的局限。易错点：①配对窗口必须按(route_id, trip_date)分区，跨日跨线路配对在运营上不可行；②贪心去重不等于全局最优（这是装箱问题的近似），结论要说明是保守下限；③成本折算要区分车型（大小车单班成本不同）。

### 4. 参考解法

**解法一：LAG相邻配对 + 贪心去重（推荐写法）**

```sql
WITH ordered AS (                                     -- 同线路同日内按发车时间排序
    SELECT trip_id, route_id, trip_date, depart_time,
           truck_type, max_load_kg, actual_load_kg,
           LAG(trip_id)         OVER (PARTITION BY route_id, trip_date ORDER BY depart_time) AS prev_trip,   -- 前一班ID
           LAG(depart_time)     OVER (PARTITION BY route_id, trip_date ORDER BY depart_time) AS prev_time,   -- 前一班发车时间
           LAG(actual_load_kg)  OVER (PARTITION BY route_id, trip_date ORDER BY depart_time) AS prev_load,  -- 前一班实载
           LAG(truck_type)      OVER (PARTITION BY route_id, trip_date ORDER BY depart_time) AS prev_type   -- 前一班车型
    FROM line_trips
    WHERE trip_date BETWEEN '2025-06-01' AND '2025-06-30'    -- 6月数据
),
pair AS (                                             -- 相邻两班构成候选配对
    SELECT trip_id, prev_trip, route_id, trip_date,
           truck_type, max_load_kg, actual_load_kg,
           prev_load, prev_type,
           TIMESTAMPDIFF(MINUTE, prev_time, depart_time) AS gap_min   -- 两班间隔(分钟)
    FROM ordered
    WHERE prev_trip IS NOT NULL                       -- 首班无前驱，排除
      AND gap_min <= 120                              -- 规则①间隔不超过2小时
      AND prev_load + actual_load_kg <= max_load_kg   -- 规则②合计实载≤后班核载(保守可行)
),
greedy AS (                                           -- 贪心去重：每班只参与一次合并
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY prev_trip ORDER BY gap_min) AS rn_prev,  -- 前班优先配间隔最近的后班
           ROW_NUMBER() OVER (PARTITION BY trip_id    ORDER BY gap_min) AS rn_cur    -- 后班同理只保留一个配对
    FROM pair
)
SELECT route_id,                                      -- 线路
       COUNT(*)                                       AS mergeable_pairs,   -- 可合并对数(去重后)
       COUNT(*)                                       AS trips_saved,       -- 每对合并省1班
       ROUND(AVG(prev_load + actual_load_kg) / 1000, 1) AS avg_merged_load_t,       -- 合并后平均载重(吨)
       COUNT(*) * 1800                                AS est_cost_saving    -- 估算节省(元),按小车单班1800元
FROM greedy
WHERE rn_prev = 1 AND rn_cur = 1                      -- 两端都未被占用的配对才计入
GROUP BY route_id
ORDER BY trips_saved DESC;                            -- 节省班次最多的线路优先改时刻表
```

结果解读：R001若显示28对可合并，即该线路月可减28个班次、节省约5万元；合并后平均载重接近核载说明拼车后装载健康，可放心执行。

**解法二：自连接枚举全部可行配对（全景视角，含车型成本折算）**

```sql
WITH pair AS (                                        -- 自连接枚举同线路同日所有可行配对
    SELECT a.trip_id AS trip_a, b.trip_id AS trip_b,
           a.route_id, a.trip_date,
           a.truck_type AS type_a, b.truck_type AS type_b,
           a.actual_load_kg + b.actual_load_kg AS merged_load,          -- 合并实载
           GREATEST(a.max_load_kg, b.max_load_kg) AS merged_cap,        -- 合并后按大车核载
           CASE WHEN a.truck_type = '9.6米' THEN 1800 ELSE 3200 END
                + CASE WHEN b.truck_type = '9.6米' THEN 1800 ELSE 3200 END
                                              AS merged_cost,           -- 合并后留存班次成本(小车1800/大车3200)
           TIMESTAMPDIFF(MINUTE, a.depart_time, b.depart_time) AS gap_min
    FROM line_trips a
    JOIN line_trips b                                 -- a在前、b在后
      ON b.route_id = a.route_id
     AND b.trip_date = a.trip_date
     AND b.depart_time > a.depart_time                -- 保证时间有序防重复配对
    WHERE TIMESTAMPDIFF(MINUTE, a.depart_time, b.depart_time) <= 120  -- 间隔≤2小时
      AND a.actual_load_kg + b.actual_load_kg
          <= GREATEST(a.max_load_kg, b.max_load_kg)   -- 合计实载≤较大核载
)
SELECT route_id,
       COUNT(*)                                       AS all_pairs,        -- 全部可行配对数(含链式冲突)
       COUNT(DISTINCT trip_a) + COUNT(DISTINCT trip_b) AS involved_trips,  -- 涉及班次(有重叠,非最优)
       ROUND(AVG(merged_load / merged_cap) * 100, 1)  AS avg_merged_load_pct, -- 可行对合并后装载率%
       SUM(CASE WHEN type_a = '9.6米' OR type_b = '9.6米'
                THEN 1800 ELSE 3200 END)              AS upper_saving      -- 节省上限(未去重的乐观值)
FROM pair
GROUP BY route_id
ORDER BY upper_saving DESC;
-- 解读时明确: all_pairs是理论上限, 实际执行需按解法一贪心或排班算法求解
```

结果解读：该查询给线路经理一张"合并机会地图"——每条线路有多少可行配对、合并后装载率多高、节省上限多少；与解法一的去重结果对照，可看出链式合并（三班并两班）的额外空间。**【加分点】** 主动指出配对合并是装箱/车辆调度问题的NP-hard近似，SQL产出的是保守下限与乐观上限的区间，精确解要交给排班算法。

### 5. 性能分析与优化

解法一一次窗口排序（route_id, trip_date, depart_time）加两层ROW_NUMBER去重，复杂度O(N log N)，无JOIN膨胀；解法二自连接在120分钟窗口约束下每个班次平均匹配少量后继班，但若去掉时间条件会退化为O(N²)，必须保留 `b.depart_time > a.depart_time` 与间隔过滤，且最好在(route_id, trip_date, depart_time)上建索引让连接走范围扫描。优化建议：①分析期固定一个月时先按trip_date分区裁剪；②pair结果若被多个报表复用，物化为月表；③车型成本映射建议独立字典表（truck_type, cost_per_trip）JOIN替代CASE硬编码；④大表下解法二可加 `a.actual_load_kg <= GREATEST(a.max_load_kg, b.max_load_kg)` 等谓词下推减少中间结果。

> Hive/Spark SQL差异：TIMESTAMPDIFF在Hive中需改用 unix_timestamp 差值/60；自连接大表在Hive必须开mapjoin或依赖Tez/Spark的shuffle join，建议对route_id+trip_date先聚簇；窗口LAG在两引擎均支持。

### 6. 面试延伸考点

- **贪心去重得到的"可省班次数"是精确最优吗？如果不是，上限和下限各怎么估？** 回答要点：不是，这是区间调度/装箱问题；解法一的互斥贪心是可行解（下限），解法二的配对总数是放松上限，精确最优需整数规划，SQL负责给业务区间。
- **为什么合并判定用"较大核载"而不是"较小核载"？** 回答要点：合并后可以调派较大车型执行，用较大核载判定可行域更大；若车队大小车数量受限，则要用可用车型约束重判，体现约束意识。
- **合空率高就一定要合并班次吗？还要考虑什么？** 回答要点：要考虑时效承诺（合并等货2小时可能延误客户SLA）、货量增长趋势（合并后旺季没有冗余运力）、分拨场到车节奏，分析结论必须附带时效影响评估。
- **如何验证拼车策略上线后真的省了钱？** 回答要点：试点线路与非试点线路做前后对比（DID思路），看班次数、单班成本、时效达成率的联合变化，防止"省了车费、赔了时效"。

### 7. 业务拓展思考

合空率分析可延展为干线网络的系统性装载优化：与货量预测联动做"以货定车"的车型动态调配、按周滚动输出拼车排班建议、把合空率纳入线路经营看板与车队KPI。口径上可细化到"重抛比"（重量/体积）维度，识别"重货压舱+抛货填空"的配载组合；长期与定价联动，对合空率高的线路推出满载折扣或集货产品，从源头改变货量分布，让运能规划从"事后分析"走向"事前设计"。

## WL-37 异常件根因多维聚类（地址/天气/操作归因画像）

### 1. 业务背景

某快递公司的客服与质控团队每天产生大量异常件记录（超时、破损、丢失、地址异常），每条记录由处理员挂一个或多个根因标签：**地址原因**（偏远、模糊地址、错误地址）、**天气原因**（暴雨、暴雪封路）、**操作原因**（分拣野蛮操作、漏扫、装错车）。运营总监要一份异常件"根因画像"：每类异常的主要根因构成是什么？多少比例的异常是多因叠加（比如暴雨天+模糊地址导致的超时）？哪些"异常类型×根因"组合的比例显著高于整体水平？这份画像决定下月资源投向——是推进地址补全产品、购置雨天装备，还是整顿分拨操作规范。

### 2. 表结构说明

exceptions（异常件根因表，一单异常一行，可多因并存）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| exception_id | VARCHAR(24) | 异常记录ID |
| waybill_id | VARCHAR(32) | 运单号 |
| exc_type | VARCHAR(10) | 异常类型：超时/破损/丢失/地址异常 |
| cause_addr | TINYINT | 地址原因标签（1命中/0未命中） |
| cause_weather | TINYINT | 天气原因标签（1命中/0未命中） |
| cause_op | TINYINT | 操作原因标签（1命中/0未命中） |
| hub | VARCHAR(20) | 发生分拨/网点 |
| stat_date | DATE | 异常登记日期 |

示例数据：

| exception_id | waybill_id | exc_type | cause_addr | cause_weather | cause_op | hub | stat_date |
|--------------|------------|----------|------------|---------------|----------|-----|-----------|
| E2025060001 | SF2025060001 | 超时 | 1 | 1 | 0 | HUB03 | 2025-06-12 |
| E2025060002 | SF2025060002 | 破损 | 0 | 0 | 1 | HUB01 | 2025-06-13 |
| E2025060003 | SF2025060003 | 地址异常 | 1 | 0 | 0 | NW05 | 2025-06-14 |
| E2025060004 | SF2025060004 | 超时 | 0 | 1 | 1 | HUB03 | 2025-06-15 |
| E2025060005 | SF2025060005 | 丢失 | 0 | 0 | 1 | NW05 | 2025-06-16 |

### 3. 解题思路

先定口径：因为一票异常可挂多因，各原因的"归因率" = 命中该原因的异常票数 / 该类异常总票数，各原因归因率之和可能超过100%（多因并存），必须向业务说明这不是互斥构成；"多因共现率" = 命中≥2个原因的票数 / 总票数，衡量根因混乱或真实叠加。分析路径：①按异常类型聚合三个原因的命中数与共现数；②用 ROLLUP（或UNION ALL模拟上卷）得到"异常类型小计/全网总计"层级，看每类异常对全网各原因的贡献；③用窗口算每个"异常类型×原因"组合占全网该原因的比例并标记主因。易错点：①把多因命中率当互斥占比求和解释（会超过100%被业务质疑）；②ROLLUP空值行需要用GROUPING()区分"该维度的全部"与"字段本身为NULL"；③共现率高时"主因"概念要慎用，改为输出原因组合画像。

### 4. 参考解法

**解法一：ROLLUP上卷 + GROUPING维度判别（层级画像）**

```sql
SELECT COALESCE(exc_type, '全部异常')                 -- 异常类型(上卷空值转'全部异常')
       AS exc_type_l1,
       CASE GROUPING(exc_type)                        -- 判断该行是否为exc_type的汇总行
            WHEN 1 THEN '总计'
            ELSE '分类型' END                         AS level_name,
       COUNT(*)                                       AS exc_cnt,     -- 异常票数
       SUM(cause_addr)                                AS addr_cnt,    -- 命中地址原因票数
       ROUND(SUM(cause_addr) / COUNT(*) * 100, 1)     AS addr_pct,    -- 地址归因率%(多因可超100总和)
       SUM(cause_weather)                             AS weather_cnt, -- 命中天气原因票数
       ROUND(SUM(cause_weather) / COUNT(*) * 100, 1)  AS weather_pct, -- 天气归因率%
       SUM(cause_op)                                  AS op_cnt,      -- 命中操作原因票数
       ROUND(SUM(cause_op) / COUNT(*) * 100, 1)       AS op_pct,      -- 操作归因率%
       ROUND(SUM(CASE WHEN cause_addr + cause_weather + cause_op >= 2
                      THEN 1 ELSE 0 END) / COUNT(*) * 100, 1)
                                                      AS multi_cause_pct -- 多因共现率%
FROM exceptions
WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30' -- 6月异常
GROUP BY exc_type WITH ROLLUP                        -- 类型小计+全网总计一次输出
ORDER BY GROUPING(exc_type), exc_cnt DESC;           -- 总计行放最后,类型行按票数排
```

结果解读：能看到"超时"异常中天气归因率45%显著高于全网20%，且超时的多因共现率高达30%，说明暴雨叠加地址/操作问题的复合超时是重点；总计行给出全网基线便于对照。

**解法二：UNION ALL模拟多维上卷 + 窗口标记主因（组合贡献视角）**

```sql
WITH long_cause AS (                                  -- 把三个原因标签展开为长表(原因维度)
    SELECT exc_type, '地址原因' AS cause, cause_addr     AS hit FROM exceptions
    WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30'
    UNION ALL
    SELECT exc_type, '天气原因', cause_weather FROM exceptions
    WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30'
    UNION ALL
    SELECT exc_type, '操作原因', cause_op      FROM exceptions
    WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30'
),
agg AS (                                              -- 异常类型×原因 命中聚合
    SELECT exc_type, cause,
           SUM(hit)                                   AS hit_cnt,     -- 该组合命中数
           COUNT(*)                                   AS type_cnt     -- 该异常类型总票数(重复计,仅作分母)
    FROM long_cause
    GROUP BY exc_type, cause
),
type_tot AS (                                         -- 每类异常的真实总票数(去重)
    SELECT exc_type, COUNT(*) AS tot
    FROM exceptions
    WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30'
    GROUP BY exc_type
),
all_tot AS (                                          -- 全网总票数与各原因总命中
    SELECT COUNT(*) AS all_n,                                 -- 全网异常票数
           SUM(cause_addr)    AS all_addr,                    -- 全网地址命中
           SUM(cause_weather) AS all_weather,                 -- 全网天气命中
           SUM(cause_op)      AS all_op                       -- 全网操作命中
    FROM exceptions
    WHERE stat_date BETWEEN '2025-06-01' AND '2025-06-30'
)
SELECT a.exc_type, a.cause,
       a.hit_cnt,
       ROUND(a.hit_cnt / t.tot * 100, 1)                  AS type_hit_pct,  -- 该类异常中此因命中率%
       RANK() OVER (PARTITION BY a.exc_type ORDER BY a.hit_cnt DESC) AS cause_rank, -- 类内原因排名
       ROUND(a.hit_cnt
             / CASE a.cause WHEN '地址原因' THEN x.all_addr
                            WHEN '天气原因' THEN x.all_weather
                            ELSE x.all_op END * 100, 1)   AS cause_share_pct  -- 该原因全网命中中此类型占比%
FROM agg a
JOIN type_tot t ON t.exc_type = a.exc_type            -- 挂真实类内分母
CROSS JOIN all_tot x                                  -- 全网基线
ORDER BY a.exc_type, cause_rank;                      -- 每类异常的原因贡献榜
```

结果解读：cause_rank=1 即该类异常的主因；cause_share_pct 回答"全网操作类根因里，破损占了大头还是丢失占了大头"，两个视角交叉支撑资源分配决策。**【避坑指南】** 长表化后 type_cnt 被原因数放大，类内占比必须回到去重的 type_tot 取分母，这是多因长表最典型的口径错误。

### 5. 性能分析与优化

解法一一次分组聚合加ROLLUP，代价即单次GROUP BY；解法二把三列标签UNION成三倍行数再聚合，扫描量×3但每段都可独立走stat_date分区。优化建议：①在(stat_date, exc_type)建联合索引或按月分区，两解法都受益；②解法二的三个UNION段在MySQL中会物化临时表，可改为一次扫描中三个条件聚合（SUM(cause_addr)、SUM(cause_weather)、SUM(cause_op)）配合UNION输出行结构的混合方案减少扫描；③标签列是0/1 tinyint，聚合开销极低，瓶颈在扫描行数，月度画像建议基于异常事实预聚合表；④hub维度下钻时组合数膨胀，注意先聚合后JOIN。

> Hive/Spark SQL差异：Hive支持GROUP BY ... WITH ROLLUP与GROUPING()（Hive 2.3+），但WITH ROLLUP不能与ORDER BY别名混用时需注意；Spark 3.x推荐GROUPING SETS写法一次完成多维度上卷，比UNION ALL少两轮扫描。

### 6. 面试延伸考点

- **一票异常挂了两个原因，归因率之和超过100%，怎么向业务解释？** 回答要点：明确说明是"归因率"不是"构成比"，多因并存反映真实世界；若业务坚持互斥构成，可定义"第一原因"字段或按处理员判定顺序取首因，但会损失信息，两种口径应同时呈现。
- **多因共现率高达30%，可能有哪些业务解释？** 回答要点：真实叠加（暴雨+模糊地址）、根因判定不严谨（处理员随手多挂）、或异常本身是复合事件；需抽检标签质量，并可用共现矩阵（原因对频次）进一步画像。
- **如果要加"分拨中心"维度做三维上卷（类型×原因×分拨），SQL怎么扩展？** 回答要点：解法一直接把hub加入GROUP BY WITH ROLLUP（层级变多）；解法二在长表加hub列；组合数=类型×原因×分拨，要控制最小票数门槛防小样本。
- **根因标签本身可能不准，如何做标签质量评估？** 回答要点：抽检置信度、对比不同处理员对同类异常的标签一致性（可用混淆矩阵/Kappa思想）、监控"未挂因"比例趋势，体现数据质量意识。

### 7. 业务拓展思考

根因画像直接驱动三类运营动作：地址类占比高的网点上线智能地址补全与电询前置、天气类高发区域配置雨季包装与时效豁免规则、操作类集中的分拨开展规范整顿与设备改造。口径可延展为"根因×网点"的热力矩阵做区域专项、与理赔金额联动把票数画像升级为金额画像，以及建立根因标签的月度漂移监控，当某原因归因率突跳时先查标签质量再下业务结论，让根因体系持续可信。

## WL-38 驿站自提vs送货上门的成本与时效对比（DID评估）

### 1. 业务背景

某电商自营运力的末端配送团队为压降履约成本，于2025年5月在部分小区把默认配送方式从"送货上门"切换为"驿站自提"（用户仍可付费选上门），其余小区维持上门。切换前团队有一场激烈争论：驿站自提单票末端成本更低（批量入驿站、无需逐户派送），但可能拉长"最后一百米"的用户取件时间、抬高投诉率。运营副总裁要求用数据回答：切换到底给末端成本、签收时效、投诉率带来了多大净影响？由于用户不能随机分配（自提比例与小区属性天然相关），必须用**双重差分（DID）**——用未切换小区作为同期对照，剔除"5月行业整体变慢/变贵"等共同冲击，得到切换的净效应，为是否全网推广提供依据。

### 2. 表结构说明

lastmile_did（小区×月末端指标表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| district_id | VARCHAR(20) | 小区ID |
| is_treated | TINYINT | 是否处理组（2025-05切换自提=1，未切换=0） |
| stat_month | CHAR(7) | 统计月（YYYY-MM） |
| waybill_cnt | INT | 该小区当月单量 |
| lastmile_cost | DECIMAL(10,2) | 当月末端配送总成本（元） |
| avg_deliver_hours | DECIMAL(5,1) | 当月下单到可取/签收均时长（小时） |
| complain_cnt | INT | 当月末端投诉单数 |

示例数据：

| district_id | is_treated | stat_month | waybill_cnt | lastmile_cost | avg_deliver_hours | complain_cnt |
|-------------|------------|------------|-------------|---------------|-------------------|--------------|
| D0001 | 1 | 2025-04 | 5200 | 9360.00 | 26.5 | 21 |
| D0001 | 1 | 2025-05 | 5600 | 8960.00 | 30.2 | 35 |
| D0002 | 0 | 2025-04 | 4800 | 9120.00 | 27.1 | 18 |
| D0002 | 0 | 2025-05 | 5100 | 9680.00 | 27.8 | 19 |
| D0003 | 1 | 2025-04 | 6100 | 11590.00 | 25.9 | 24 |

### 3. 解题思路

先定口径：DID的核心思想是（处理组前后变化）−（对照组前后变化），前提假设是**平行趋势**——若无切换，两组指标会平行演化；因此严谨的做法还要做趋势检验（切换前多期两组差值是否稳定）。三个结果指标分别计算：单票末端成本 = lastmile_cost/waybill_cnt、可取/签收时长 avg_deliver_hours、投诉率 = complain_cnt/waybill_cnt，均为比率指标，必须先加总再相除。实现路径：解法一"四格法"——组×期的2×2聚合表算出四个格子再手动差分；解法二"个体差分法"——先算每个小区的前后差值Δ，再比较两组Δ的均值（等价于小区固定效应下的DID），对小区异质性更稳健，还能顺带输出差值的分布。易错点：①比率指标在四格里对月度均值再平均会引入辛普森偏差，应以单量为权重或先算全组总额；②DID回答的是"平均处理效应"，不能直接外推到单量结构差异大的小区；③切换若在月中，4/5两月就不是干净的"前/后"，要确认切换日期取整月。

### 4. 参考解法

**解法一：DID四格法（2×2均值差分，汇报首选）**

```sql
WITH cell AS (                                        -- 组×期四格聚合(比率先加总再相除)
    SELECT is_treated,                                -- 组别
           CASE WHEN stat_month = '2025-04' THEN '前' ELSE '后' END AS phase,  -- 期别(4月前/5月后)
           SUM(waybill_cnt)                          AS n,           -- 单量(作权重)
           SUM(lastmile_cost) / SUM(waybill_cnt)     AS cost_per_pkg, -- 组期单票末端成本
           SUM(avg_deliver_hours * waybill_cnt) / SUM(waybill_cnt) AS hours, -- 加权均时长
           SUM(complain_cnt) / SUM(waybill_cnt)      AS complain_rate -- 投诉率
    FROM lastmile_did
    WHERE stat_month IN ('2025-04', '2025-05')        -- 切换前后各取整月
    GROUP BY is_treated,
             CASE WHEN stat_month = '2025-04' THEN '前' ELSE '后' END
),
pivoted AS (                                          -- 四格转列便于差分
    SELECT is_treated,
           MAX(CASE WHEN phase = '前' THEN cost_per_pkg END)    AS cost_before,
           MAX(CASE WHEN phase = '后' THEN cost_per_pkg END)    AS cost_after,
           MAX(CASE WHEN phase = '前' THEN hours END)           AS hours_before,
           MAX(CASE WHEN phase = '后' THEN hours END)           AS hours_after,
           MAX(CASE WHEN phase = '前' THEN complain_rate END)   AS comp_before,
           MAX(CASE WHEN phase = '后' THEN complain_rate END)   AS comp_after
    FROM cell
    GROUP BY is_treated
)
SELECT t.is_treated                                                        -- 组别
       , ROUND(t.cost_after - t.cost_before, 2)                            AS cost_chg,  -- 处理/对照各自前后变化
       ROUND(t.hours_after - t.hours_before, 1)                            AS hours_chg,
       ROUND(t.comp_after - t.comp_before, 5)                              AS comp_chg
FROM pivoted t;
-- 在此结果上人工取差: DID = 处理组变化 - 对照组变化(也可再包一层两行相减)

SELECT ROUND(
         (SELECT cost_after - cost_before FROM pivoted WHERE is_treated = 1)
       - (SELECT cost_after - cost_before FROM pivoted WHERE is_treated = 0), 2)
       AS did_cost,                                     -- 单票成本的DID净效应(元/单)
       ROUND(
         (SELECT hours_after - hours_before FROM pivoted WHERE is_treated = 1)
       - (SELECT hours_after - hours_before FROM pivoted WHERE is_treated = 0), 1)
       AS did_hours,                                    -- 时长的DID净效应(小时)
       ROUND(
         (SELECT comp_after - comp_before FROM pivoted WHERE is_treated = 1)
       - (SELECT comp_after - comp_before FROM pivoted WHERE is_treated = 0), 5)
       AS did_complain;                                 -- 投诉率的DID净效应
```

结果解读：若 did_cost = −0.45元、did_hours = +2.1小时、did_complain = +0.0021，即"每单省4毛5、取件时长多2小时、投诉率升0.21个百分点"，三个指标放进决策矩阵权衡。

**解法二：个体差分法（小区级Δ再组间对比，抗异质性）**

```sql
WITH wide AS (                                        -- 每小区取前后两期并转列
    SELECT district_id, is_treated,
           MAX(CASE WHEN stat_month = '2025-04' THEN waybill_cnt END)    AS n_b,
           MAX(CASE WHEN stat_month = '2025-05' THEN waybill_cnt END)    AS n_a,
           MAX(CASE WHEN stat_month = '2025-04' THEN lastmile_cost END)  AS cost_b,
           MAX(CASE WHEN stat_month = '2025-05' THEN lastmile_cost END)  AS cost_a,
           MAX(CASE WHEN stat_month = '2025-04' THEN avg_deliver_hours END) AS h_b,
           MAX(CASE WHEN stat_month = '2025-05' THEN avg_deliver_hours END) AS h_a
    FROM lastmile_did
    WHERE stat_month IN ('2025-04', '2025-05')
    GROUP BY district_id, is_treated
),
delta AS (                                            -- 小区级差分: 每个小区自己的前后变化
    SELECT district_id, is_treated,
           cost_a / n_a - cost_b / n_b                AS d_cost,   -- 该小区单票成本变化
           h_a - h_b                                  AS d_hours,  -- 该小区时长变化
           n_a                                        AS n_after   -- 事后单量(加权用)
    FROM wide
    WHERE n_a > 0 AND n_b > 0                         -- 前后都有量的有效小区
)
SELECT is_treated,                                    -- 组别
       COUNT(*)                                       AS districts,  -- 小区数
       ROUND(SUM(d_cost * n_after) / SUM(n_after), 2) AS avg_d_cost, -- 组内单量加权平均Δ成本
       ROUND(AVG(d_hours), 1)                         AS avg_d_hours,-- 组内简单平均Δ时长
       ROUND(STDDEV_SAMP(d_hours), 2)                 AS sd_d_hours, -- Δ时长的标准差(看组内分化)
       MIN(d_hours)                                   AS min_d_hours,-- 最差小区(定位需运营介入的个案)
       MAX(d_hours)                                   AS max_d_hours
FROM delta
GROUP BY is_treated;
-- DID(个体法) = 处理组avg_d - 对照组avg_d, 且标准差/极值暴露了平均数背后的分化
```

结果解读：个体法不仅给出两组Δ的对比，还暴露"处理组内有的小区时长+6小时、有的几乎没变"的分化——提示切换效果与驿站覆盖距离强相关，需要下钻分析；**【加分点】** 主动说明个体差分等价于含小区固定效应的DID回归，对小区间固有差异更稳健，且为后续做梯度分析（Δ对驿站距离回归）准备好了数据形态。

### 5. 性能分析与优化

两解法都作用在"小区×月"预聚合表上（行数=小区数×月数，通常几万到几十万行），代价极低，瓶颈在GROUP BY与CASE转列的物化。优化建议：①对(stat_month, is_treated)建联合索引加速期别过滤；②若从运单明细直接算，必须先按小区×日预聚合成本与时长，避免明细级窗口；③解法二的STDDEV_SAMP在MySQL窗口/聚合均支持，若迁移到老版本Hive可用SQRT(VARIANCE)替代；④DID四格结果建议与平行趋势检验共用同一个"组×周"聚合查询，减少重复扫描。

> Hive/Spark SQL差异：Hive无STDDEV_SAMP聚合名（有stddev_samp小写也可，或用var_pop开方）；IF/CASE转列两引擎通用；样本量大时建议在Spark上跑并把检验输出到BI看板。

### 6. 面试延伸考点

- **DID成立的核心假设是什么？怎么用SQL做平行趋势检验？** 回答要点：平行趋势——处理组与对照若无干预会平行变化；检验方法：取切换前4-6周按周输出两组指标差值序列，若差值平稳则假设成立，切换后差值跳变即为效应，事件研究法（呼应WL-40）是标准工具。
- **为什么不能用"切换小区切换前后对比"直接下结论？** 回答要点：前后对比混入了同期共同冲击（油价、大促、天气）与均值回归；对照组的作用是把这些共同变化差分掉，这是准实验设计的基本逻辑。
- **处理组是"被选择"的（可能本来就选了驿站接受度高的小区），怎么缓解选择偏差？** 回答要点：倾向得分匹配后再DID（PSM-DID）、选多个对照小区做加权、或看切换前两组是否可比（单量、客群画像），至少要在汇报中声明局限。
- **三个指标一升一降，怎么给决策建议？** 回答要点：把指标折算成金额语言（成本省X元 vs 投诉上升折算的客诉处理成本与流失风险），给出净影响区间与试点扩量建议，体现从数据到商业决策的翻译能力。

### 7. 业务拓展思考

DID结论可支撑末端网络的分层策略：成本敏感且驿站可达的小区推自提、老年客群占比高的小区保留上门、并设计付费选择机制让愿付用户补贴上门成本。口径可延展为按用户年龄/单量分层的异质性效应分析、把观察期拉长看取件习惯的动态适应曲线（切换初期投诉高、三个月后回落），以及把末端成本口径细化到快递员人效；更进一步可设计与驿站合作方分成机制联动，让"自提率"成为末端网络规划的核心调节变量。

## WL-39 库存周转与销售预测联动的缺货预警

### 1. 业务背景

某B2C电商的区域仓运营团队管理着上万个SKU的前置仓库存。缺货的代价是销售损失与体验下降，但备太多又推高库存资金占用与滞销风险。团队的标准动作是每天跑一轮**缺货预警**：把每个SKU当前可用库存与其未来7天的销量预测（来自算法团队的SKU×日预测）对比，计算"覆盖天数"（库存能撑几天预测销量），对覆盖不足3天的SKU触发红色预警、不足7天触发黄色关注，并输出建议补货量。这个预警同时服务两个下游：采购补货单的生成优先级、以及大促前的库存调拨决策。分析师要保证口径严谨——预测是"未来"的，库存是"当下"的，两者关联方式是本题主考点。

### 2. 表结构说明

inventory_snapshot（SKU库存日快照表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| wh | VARCHAR(20) | 仓库编码 |
| sku_id | VARCHAR(24) | SKU编码 |
| stat_date | DATE | 快照日期 |
| stock_qty | INT | 当日期末可用库存 |

sku_forecast（SKU销量日预测表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| wh | VARCHAR(20) | 仓库编码 |
| sku_id | VARCHAR(24) | SKU编码 |
| fc_date | DATE | 预测日期 |
| fc_qty | INT | 预测销量 |

示例数据（inventory_snapshot）：

| wh | sku_id | stat_date | stock_qty |
|----|--------|-----------|-----------|
| WH01 | SKU-A | 2025-06-10 | 420 |
| WH01 | SKU-B | 2025-06-10 | 90 |
| WH01 | SKU-C | 2025-06-10 | 1500 |
| WH01 | SKU-A | 2025-06-11 | 380 |
| WH01 | SKU-B | 2025-06-11 | 60 |

示例数据（sku_forecast）：

| wh | sku_id | fc_date | fc_qty |
|----|--------|---------|--------|
| WH01 | SKU-A | 2025-06-11 | 150 |
| WH01 | SKU-A | 2025-06-12 | 160 |
| WH01 | SKU-A | 2025-06-13 | 170 |
| WH01 | SKU-B | 2025-06-11 | 80 |
| WH01 | SKU-B | 2025-06-12 | 85 |

### 3. 解题思路

先定口径：以预警日 T 为锚，覆盖天数 = 当前可用库存 / 未来7日日均预测需求（等价于库存可覆盖预测曲线第几天，精确口径是"累积预测首次超过库存的天数"）；7日需求缺口 = 未来7日累积预测 − 当前库存，缺口>0 即7日内会缺货。预警分级：缺口>0且覆盖<3天为红色、覆盖3~7天为黄色。实现路径：解法一用**前向滑动窗口**（ROWS BETWEEN CURRENT ROW AND 6 FOLLOWING）在预测表上直接算每个SKU每日的"未来7日累积需求"，再与当日库存快照按(wh, sku, date)对齐JOIN；解法二先按SKU聚合7日总需求（嵌套派生表）再JOIN库存，并额外给出"累积预测首次击穿库存"的精确覆盖天数（用窗口MIN定位）。易错点：①快照日期与预测日期必须错位对齐——T日库存对应T+1起的预测，直接同日JOIN会把当天已卖掉的需求重复计入；②预测表缺SKU行（新品无预测）时LEFT JOIN方向要选对；③覆盖天数用简单除法在需求前高后低时会失真，精确口径要用累积击穿法。

### 4. 参考解法

**解法一：前向滑动窗口 + 日期对齐JOIN（推荐写法）**

```sql
WITH fc7 AS (                                         -- 预测表上前向7日累积需求
    SELECT wh, sku_id, fc_date, fc_qty,
           SUM(fc_qty) OVER (PARTITION BY wh, sku_id ORDER BY fc_date
               ROWS BETWEEN CURRENT ROW AND 6 FOLLOWING) AS demand_7d,   -- 含当日起7日累积预测
           AVG(fc_qty) OVER (PARTITION BY wh, sku_id ORDER BY fc_date
               ROWS BETWEEN CURRENT ROW AND 6 FOLLOWING) AS avg_daily    -- 7日日均预测
    FROM sku_forecast
    WHERE fc_date BETWEEN '2025-06-10' AND '2025-06-16'   -- 预警日T=6/10,预测窗口T+1..T+7
),
risk AS (                                             -- 库存与未来需求对齐(库存T日 vs 预测T+1日)
    SELECT i.wh, i.sku_id, i.stat_date,
           i.stock_qty,                                -- T日期末可用库存
           f.demand_7d,                                -- 未来7日总需求
           f.avg_daily,                                -- 日均需求
           f.demand_7d - i.stock_qty                   AS gap_7d,   -- 7日需求缺口
           ROUND(i.stock_qty / NULLIF(f.avg_daily, 0), 1) AS cover_days -- 覆盖天数=库存/日均
    FROM inventory_snapshot i
    JOIN fc7 f                                          -- 错位对齐: 库存stat_date 对 预测fc_date=次日
      ON f.wh = i.wh
     AND f.sku_id = i.sku_id
     AND f.fc_date = i.stat_date + INTERVAL 1 DAY       -- T日库存对应T+1开始的预测
    WHERE i.stat_date = '2025-06-10'                    -- 只跑预警日当天
)
SELECT wh, sku_id, stock_qty, demand_7d, gap_7d, cover_days,
       CASE WHEN gap_7d > 0 AND cover_days < 3 THEN '红色预警'   -- 3天内必缺
            WHEN gap_7d > 0 THEN '黄色关注'                      -- 7日内会缺
            WHEN stock_qty > demand_7d * 2 THEN '绿色偏厚'       -- 备货超2倍周需求
            ELSE '健康' END                     AS alert_level   -- 预警分级
FROM risk
ORDER BY FIELD(alert_level, '红色预警', '黄色关注', '绿色偏厚', '健康'),
         gap_7d DESC;                                            -- 红→黄→绿,红区内按缺口降序
```

结果解读：红色预警清单直接生成当日紧急补货工单；"绿色偏厚"同时输出可反哺滞销清理与仓间调拨（衔接WL-44），一个查询服务补货与调拨两个决策。

**解法二：嵌套派生表聚合 + 累积击穿法算精确覆盖天数**

```sql
SELECT r.wh, r.sku_id, r.stock_qty, r.demand_7d, r.gap_7d,
       r.break_day,                                   -- 精确覆盖: 预测累积首次>库存的第几天
       CASE WHEN r.gap_7d > 0 AND r.break_day <= 3 THEN '红色预警'
            WHEN r.gap_7d > 0 THEN '黄色关注'
            ELSE '健康' END            AS alert_level
FROM (
    SELECT i.wh, i.sku_id, i.stock_qty,               -- 库存快照
           d.demand_7d,
           d.demand_7d - i.stock_qty                  AS gap_7d,
           MIN(CASE WHEN d.cum_qty > i.stock_qty      -- 累积需求首次击穿库存
                    THEN d.day_no END)                AS break_day  -- 击穿发生的相对日
    FROM inventory_snapshot i
    JOIN (                                            -- 派生表: 每SKU未来7日逐日累积需求
        SELECT wh, sku_id, fc_date,
               SUM(fc_qty) OVER (PARTITION BY wh, sku_id ORDER BY fc_date
                   ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_qty, -- 自起点累积
               DATEDIFF(fc_date, '2025-06-10')        AS day_no,    -- 相对预警日的天数
               SUM(fc_qty) OVER (PARTITION BY wh, sku_id)            AS demand_7d  -- 7日总需求(全窗)
        FROM sku_forecast
        WHERE fc_date BETWEEN '2025-06-11' AND '2025-06-17'         -- T+1..T+7
    ) d ON d.wh = i.wh AND d.sku_id = i.sku_id        -- 预测窗口整体挂到库存快照
    WHERE i.stat_date = '2025-06-10'
    GROUP BY i.wh, i.sku_id, i.stock_qty, d.demand_7d, d.gap_7d
) r
ORDER BY r.gap_7d DESC;
```

结果解读：break_day=2 表示"库存只够卖到明天"，比平均覆盖天数更能还原需求曲线形状（前高后低的预测下简单除法会高估可撑天数）；**【面试高频】** 被问"覆盖天数为什么不用简单除法"时，用预测曲线不平坦这一业务事实作答即可。

### 5. 性能分析与优化

解法一窗口按(wh, sku_id)分区排序，SKU数×7行的预测表量级可控；JOIN发生在快照日单日切片（行数=SKU数）与预测窗口之间，代价低；解法二多一层累积窗口但省去日均除法，二者都是秒级。真正的性能挑战在SKU百万级×365天全量回溯：①inventory_snapshot与sku_forecast都按stat_date/fc_date分区，预警日只扫1天快照+7天预测；②(wh, sku_id, stat_date)联合索引或按sku分桶，让JOIN走hash/map-side；③预测表通常稀疏（部分SKU部分日期无预测），先补齐日历骨架防窗口行数不足；④预警逻辑可固化为每日调度任务，只做增量。

> Hive/Spark SQL差异：INTERVAL 1 DAY 在Hive老版本写法为 date_add(fc_date, 1)；FIELD()函数Hive不支持，分级排序改用CASE映射数字列；百万SKU级窗口在Spark更稳，建议开启spark.sql.adaptive确保聚合倾斜时自动拆分。

### 6. 面试延伸考点

- **为什么库存T日要对齐T+1开始的预测，而不是T日？** 回答要点：T日期末库存是当天销售结束后的存量，服务于T+1及以后的需求；同日对齐会把当天已消耗的需求重复扣减，系统性高估缺口。
- **覆盖天数用"库存/日均"和"累积击穿法"何时会给出不同结论？** 回答要点：预测前高后低（如周末峰值）时除法高估可撑天数，击穿法按曲线逐日累积更精确；日常监控可用除法近似，补货决策用击穿法。
- **在途库存（已下单未入库）要不要计入可用库存？** 回答要点：要区分"在手""在途"两个口径，预警用在手+确认到货日在窗口内的在途，避免对已在途的SKU重复下紧急补货单。
- **预测本身有误差，预警如何防止狼来了？** 回答要点：对预测取分位（P70/P90）做保守情景、按SKU历史预测准确率（如WMAPE）给预警加置信度过滤，并把预警命中率纳入闭环复盘。

### 7. 业务拓展思考

缺货预警是库存计划体系的发动机：红色清单驱动紧急采购与仓间调拨，黄色清单进入常规补货批次，绿色偏厚清单触发促销清滞与调出。口径可延展到"库存周转天数"趋势监控（衔接周转与缺货的平衡曲线）、按ABC分类差异化预警阈值（A类商品红线更严）、以及把预测准确率反哺预警置信度；与WL-44的调拨识别、WL-34的运能测算组合，就能构成"预测-库存-运能"一体化的供应链数字看板。

## WL-40 分拨中心网络调整前后时效对比（简化DID与事件研究）

### 1. 业务背景

某快递公司3月第一周完成华东二区分拨中心的整体搬迁（原HUB12迁至新场地HUB12N，路由覆盖的8个城市末端网点全部受影响）。网络规划团队需要在搬迁满一个月后回答：这次调整到底让时效变好还是变坏了？变化中有多少是搬迁造成的、多少是大促后行业单量回落等共同因素？单纯对比华东二区前后时效不够说服力（同期全行业时效都在变），标准做法是选路由结构相似、未做调整的华东一区作为**对照区**，用双重差分剥离共同趋势；再用**事件研究**画出搬迁前后逐周的两区差值曲线，检验平行趋势并展示效应的动态路径（搬迁初期阵痛、爬坡后收益），为"是否复制该方案到其他区"提供证据链。

### 2. 表结构说明

region_timeliness_wk（区域×周时效汇总表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stat_week | DATE | 周起始日期（周一） |
| region_id | VARCHAR(20) | 区域编码（华东一区/华东二区…） |
| is_treated | TINYINT | 是否处理区（华东二区=1） |
| waybill_cnt | INT | 该周单量 |
| avg_hours | DECIMAL(5,1) | 该周加权均时效（小时） |
| on_time_rate | DECIMAL(5,4) | 该周时效达成率 |

示例数据：

| stat_week | region_id | is_treated | waybill_cnt | avg_hours | on_time_rate |
|-----------|-----------|------------|-------------|-----------|--------------|
| 2025-02-03 | 华东二区 | 1 | 182000 | 44.2 | 0.9310 |
| 2025-02-03 | 华东一区 | 0 | 205000 | 42.8 | 0.9402 |
| 2025-03-03 | 华东二区 | 1 | 176000 | 46.9 | 0.9125 |
| 2025-03-03 | 华东一区 | 0 | 201000 | 42.5 | 0.9418 |
| 2025-03-24 | 华东二区 | 1 | 188000 | 41.6 | 0.9455 |

### 3. 解题思路

先定口径：处理区=华东二区，对照区=华东一区（选区标准：路由结构、单量级、客户结构相近，需在汇报中论证）；搬迁周W0=2025-03-03，相对周 rel_week = 周序号 − W0序号，取 −4~+4。DID效应 = （处理区后均值−处理区前均值）−（对照区后均值−对照区前均值），时效为加权均值，前后各取4周并按单量加权。事件研究：输出每周两组的均时效与差值，检验调整前4周差值是否平稳（平行趋势），调整后差值相对基线的跳变与回落即动态效应。实现路径：解法一用2×2四格聚合做DID；解法二按rel_week展开做事件研究（窗口/条件聚合转列），两条证据链互相支撑。易错点：①"前/后"取整月聚合会抹掉搬迁初期与爬坡期的差异，事件研究必须保留周粒度；②时效是加权均值，四格里必须用单量加权，直接AVG(avg_hours)有辛普森风险；③若同期对照区也有轻微网络动作，DID被污染，需换对照或在汇报中声明。

### 4. 参考解法

**解法一：DID四格法（前后4周加权聚合）**

```sql
WITH cell AS (                                        -- 组×期四格(前后各4周,单量加权)
    SELECT is_treated,
           CASE WHEN stat_week < '2025-03-03' THEN '前' ELSE '后' END AS phase,  -- 搬迁周起为"后"
           SUM(waybill_cnt)                                        AS n,      -- 单量
           SUM(avg_hours * waybill_cnt) / SUM(waybill_cnt)         AS hours,  -- 单量加权均时效
           SUM(on_time_rate * waybill_cnt) / SUM(waybill_cnt)      AS otr     -- 加权达成率
    FROM region_timeliness_wk
    WHERE stat_week BETWEEN '2025-02-03' AND '2025-03-31'   -- 前4周+后4周窗口
      AND is_treated IN (0, 1)
    GROUP BY is_treated,
             CASE WHEN stat_week < '2025-03-03' THEN '前' ELSE '后' END
),
piv AS (                                              -- 四格转列
    SELECT is_treated,
           MAX(CASE WHEN phase = '前' THEN hours END) AS h_b,   -- 前期均时效
           MAX(CASE WHEN phase = '后' THEN hours END) AS h_a,   -- 后期均时效
           MAX(CASE WHEN phase = '前' THEN otr END)   AS o_b,
           MAX(CASE WHEN phase = '后' THEN otr END)   AS o_a
    FROM cell GROUP BY is_treated
)
SELECT ROUND(MAX(CASE WHEN is_treated = 1 THEN h_a - h_b END)
           - MAX(CASE WHEN is_treated = 0 THEN h_a - h_b END), 2) AS did_hours,  -- 时效DID(小时),负=变快
       ROUND(MAX(CASE WHEN is_treated = 1 THEN o_a - o_b END)
           - MAX(CASE WHEN is_treated = 0 THEN o_a - o_b END), 4) AS did_otr     -- 达成率DID,正=变好
FROM piv;
-- did_hours<0 说明剔除共同趋势后, 搬迁让处理区时效净改善
```

结果解读：若 did_hours = −1.8 小时、did_otr = +0.021，即在剔除行业共同变化后，搬迁使华东二区均时效净缩短1.8小时、达成率净提升2.1个百分点——这是向管理层汇报的核心数字。

**解法二：事件研究法（逐周差值曲线，平行趋势检验）**

```sql
WITH wk AS (                                          -- 周粒度两区指标
    SELECT stat_week, is_treated, waybill_cnt, avg_hours, on_time_rate,
           ROUND(DATEDIFF(stat_week, '2025-03-03') / 7) AS rel_week  -- 相对搬迁周的周数(-4..+4)
    FROM region_timeliness_wk
    WHERE stat_week BETWEEN '2025-02-03' AND '2025-04-28'   -- 前4周后4周
),
wide AS (                                             -- 两区同周并排
    SELECT w.stat_week, w.rel_week,
           w.avg_hours AS h_treat, w.waybill_cnt AS n_treat,       -- 处理区
           c.avg_hours AS h_ctrl,  c.waybill_cnt AS n_ctrl,        -- 对照区
           c.on_time_rate AS otr_ctrl, w.on_time_rate AS otr_treat
    FROM wk w
    JOIN wk c ON c.stat_week = w.stat_week                 -- 同周自连接对齐
             AND c.is_treated = 0 AND w.is_treated = 1
)
SELECT rel_week, stat_week,
       ROUND(h_treat, 1)                                        AS treat_hours, -- 处理区周时效
       ROUND(h_ctrl, 1)                                         AS ctrl_hours,  -- 对照区周时效
       ROUND(h_treat - h_ctrl, 2)                               AS gap,         -- 两区差值(核心观察列)
       ROUND((h_treat * n_treat + h_ctrl * n_ctrl)
             / (n_treat + n_ctrl), 1)                           AS pooled_hours -- 两区合并参考列
FROM wide
ORDER BY rel_week;
-- 判读: rel_week<0的gap应大致平稳(平行趋势成立);
--       rel_week=0..1 gap跳升(搬迁阵痛), rel_week=3..4 gap转为负值且扩大(爬坡收益)
```

结果解读：gap序列如果呈现"调整前稳定在+1.4左右 → 调整当周+3.5（阵痛）→ 第4周−1.9（反超）"的路径，既验证了平行趋势假设，又讲出了"先痛后快"的动态故事，比单一DID数字更有说服力。**【加分点】** 主动说明事件研究中"处理区−对照区"的调整前均值可作为DID的基线差，调整后各周gap与基线差之差就是逐周动态效应（相当于事件研究系数），这已是学术规范的简化版。

### 5. 性能分析与优化

两解法都基于周级预聚合表（行数=区域数×周数，极小），主要代价是解法二的自连接（同表按周对齐，两区各一行，连接结果=周数）与CASE转列。优化建议：①表上建(stat_week, is_treated)索引或直接以该序聚集存储；②若从运单明细起算，务必先按区域×日预聚合均时效与单量，明细级直接算加权均值的窗口成本很高；③事件研究若扩展到多处理区多对照区，改为按 region_type 标签的三段聚合而非多路JOIN；④把四格与事件研究共用同一份周级切片（物化临时表），避免重复扫描。

> Hive/Spark SQL差异：DATEDIFF参数顺序在Hive为 datediff(end, start)；ROUND(DATEDIFF/7) 在Hive中整除行为不同，建议用 floor()；自连接小表在Spark可broadcast；若需显著性检验（聚类稳健标准误），SQL算出周级面板后交给R/Python完成，SQL负责备料。

### 6. 面试延伸考点

- **选华东一区做对照的依据是什么？如果它的路由结构和二区差很大怎么办？** 回答要点：依据是调整前趋势平行与特征可比（单量、时效水平、客户结构）；差异大时用合成控制思想——多对照区加权拟合出"虚拟二区"，SQL可用调整前各周回归权重近似实现。
- **搬迁效应为什么第1周恶化、第4周才转正？怎么避免误判？** 回答要点：场地搬迁伴随系统切换、人员熟悉期，属正常爬坡；结论要以窗口末端（第3-4周）为准，并把爬坡曲线一并汇报，防止只看首周得出失败结论。
- **DID数字显著吗？SQL能做假设检验吗？** 回答要点：可用周级面板手工算两阶段差分的标准误做粗略t检验，或明确说明SQL产出效应量、显著性交给统计工具；关键是意识到点估计之外要有不确定性表达。
- **如果同期公司在处理区还做了别的动作（如加开航线），DID估计的是什么？** 回答要点：估计的是"一揽子变化"的净效应而非搬迁单独效应；需要控制组内其他动作的时点或选更干净的对照，考察识别策略的严谨性。

### 7. 业务拓展思考

该分析框架可沉淀为公司网络调整的标准评估SOP：任何分拨迁移、路由重排、枢纽新增都预注册对照区与观察窗口，调整后自动产出DID与事件研究报告。口径可延展到成本维度（单票干线成本同法评估）、质量维度（破损率DID），以及把爬坡曲线参数化（周改善斜率）用于预测新方案收益；长期积累多个调整案例后，还能建立"哪类调整在多长时间回本"的经验库，让网络规划从经验决策升级为证据决策。

## WL-41 快递员单量爬坡曲线与入职cohort留存分析

### 1. 业务背景

末端配送网点常年面临快递员高流失：新入职快递员头两个月是流失高峰，而人效又需要时间爬坡——新人首周日均派件往往只有熟练工的一半，网点经理需要在"招人补缺口"和"留人降流失"之间做预算分配。人力运营团队需要一组cohort分析：按入职月把快递员分成队列，画出每个队列入职后第0~8周的**单量爬坡曲线**（周人均派件量的成长路径）与**留存曲线**（第N周仍有作业记录的人数占比），回答三个问题：新人需要几周达到成熟产能（用于设定带教期与计件保护期）；哪几周是流失高危窗口（用于安排关怀动作）；不同入职月份的队列留存是否有差异（用于评估某次计件规则调整的效果）。

| C1002 | 2025-04 | 2025-04-02 | 48 | ST0572 |

### 3. 解题思路

先定口径：cohort队列 = hire_month；每个快递员的"个人时间轴"起点是首次作业日 MIN(work_date)（比入职合同日更贴近实际爬坡，也规避了数据里可能没有合同日的问题）；相对周 wk = FLOOR(DATEDIFF(work_date, 首次作业日)/7)。两个核心指标都按"队列×相对周"聚合：爬坡曲线 = 该队列该周的人均周派件量（活跃者平均，注意口径声明）；留存率 = 该队列该周仍有作业的人数 / 队列总人数。实现路径：先窗口取每人首次作业日 → 计算相对周 → 按(hire_month, wk)双维聚合人数与单量 → 条件聚合透视成"队列为行、周为列"的留存矩阵。易错点：①wk=0必须单独存在（首周可能不足7天），爬坡曲线里首周天然偏低属正常；②分母"队列总人数"固定为该队列出现过的总人数（不随后周衰减），否则留存率恒为100%；③活跃者人均与全体人均（分母含已流失）是两个不同口径，混用会同时高估爬坡与掩盖流失。

### 4. 参考解法

**解法一：窗口定位首次作业日 + 条件聚合透视（一查询出矩阵）**

```sql
WITH base AS (                                        -- 每人每次作业挂上个人时间轴
    SELECT courier_id, hire_month, site_id,
           work_date, delivered_cnt,
           MIN(work_date) OVER (PARTITION BY courier_id) AS first_work_date, -- 个人首次作业日(窗口取每人起点)
           FLOOR(DATEDIFF(work_date,
                          MIN(work_date) OVER (PARTITION BY courier_id)) / 7) AS wk -- 相对周序号0,1,2...
    FROM courier_work_di
    WHERE work_date BETWEEN '2025-03-01' AND '2025-06-30'   -- 观察窗口(覆盖3/4月队列的8周)
),
cohort AS (                                           -- 队列×相对周聚合
    SELECT hire_month, wk,
           COUNT(DISTINCT courier_id)                 AS active_cnt,  -- 该周仍活跃人数(留存分子)
           SUM(delivered_cnt)                         AS sum_cnt,     -- 该周总派件量
           COUNT(DISTINCT courier_id)                 AS den_for_avg  -- 占位: 人均按活跃者
    FROM base
    GROUP BY hire_month, wk
),
tot AS (                                              -- 每队列总人数(固定分母)
    SELECT hire_month, COUNT(DISTINCT courier_id) AS total_cnt
    FROM base
    GROUP BY hire_month
)
SELECT c.hire_month,                                  -- 队列: 入职月
       t.total_cnt,                                   -- 队列总人数(留存分母,固定)
       ROUND(100 * MAX(CASE WHEN c.wk = 0 THEN c.active_cnt END) / t.total_cnt, 1) AS wk0_ret,  -- 首周留存%
       ROUND(100 * MAX(CASE WHEN c.wk = 1 THEN c.active_cnt END) / t.total_cnt, 1) AS wk1_ret,  -- 第1周留存%
       ROUND(100 * MAX(CASE WHEN c.wk = 4 THEN c.active_cnt END) / t.total_cnt, 1) AS wk4_ret,  -- 第4周留存%
       ROUND(100 * MAX(CASE WHEN c.wk = 8 THEN c.active_cnt END) / t.total_cnt, 1) AS wk8_ret,  -- 第8周留存%
       ROUND(MAX(CASE WHEN c.wk = 0 THEN c.sum_cnt / c.active_cnt END), 0) AS wk0_avg,  -- 首周人均派件(活跃者)
       ROUND(MAX(CASE WHEN c.wk = 4 THEN c.sum_cnt / c.active_cnt END), 0) AS wk4_avg,  -- 第4周人均
       ROUND(MAX(CASE WHEN c.wk = 8 THEN c.sum_cnt / c.active_cnt END), 0) AS wk8_avg   -- 第8周人均
FROM cohort c
JOIN tot t ON t.hire_month = c.hire_month             -- 挂固定分母
GROUP BY c.hire_month, t.total_cnt
ORDER BY c.hire_month;                                -- 每行一个入职队列
```

结果解读：若3月队列显示 wk0 人均65件、wk4 人均128件、wk8 140件且 wk4 留存仅55%，说明第4周即达成熟产能的80%、而第2-4周是流失高危窗口，带教激励应集中在 wk1-3。

**解法二：派生入职表JOIN + 长表输出（适合看板/分层下钻）**

```sql
WITH first_day AS (                                   -- 派生"入职事实表":每人首次作业日与队列
    SELECT courier_id, hire_month, site_id,
           MIN(work_date) AS first_work_date          -- 每人起点
    FROM courier_work_di
    GROUP BY courier_id, hire_month, site_id
),
joined AS (                                           -- 作业记录挂队列与相对周
    SELECT f.hire_month, f.site_id,
           FLOOR(DATEDIFF(d.work_date, f.first_work_date) / 7) AS wk,
           d.courier_id, d.delivered_cnt
    FROM first_day f
    JOIN courier_work_di d ON d.courier_id = f.courier_id  -- 一人多日记录展开
    WHERE d.work_date BETWEEN '2025-03-01' AND '2025-06-30'
),
ret AS (                                              -- 长表:队列×周×指标
    SELECT hire_month, site_id, wk,
           COUNT(DISTINCT courier_id) AS active_cnt,  -- 活跃人数
           SUM(delivered_cnt)         AS sum_cnt      -- 派件总量
    FROM joined
    GROUP BY hire_month, site_id, wk
)
SELECT r.hire_month, r.site_id, r.wk,                 -- 不透视,保留长表便于下钻
       r.active_cnt,
       ROUND(r.active_cnt / t.total_cnt * 100, 1)     AS ret_pct,     -- 留存率%
       ROUND(r.sum_cnt / r.active_cnt, 0)             AS avg_cnt,     -- 活跃者人均派件
       ROUND(r.sum_cnt / t.total_cnt, 0)              AS avg_cnt_all  -- 全体人均(含已流失,对比口径)
FROM ret r
JOIN (SELECT hire_month, site_id, COUNT(DISTINCT courier_id) AS total_cnt
      FROM joined GROUP BY hire_month, site_id) t     -- 队列固定分母(可按网点下钻)
  ON t.hire_month = r.hire_month AND t.site_id = r.site_id
ORDER BY r.hire_month, r.site_id, r.wk;               -- 长表直接喂BI折线图
```

结果解读：长表形态可直接在BI中画"每队列一条留存折线"，并按 site_id 下钻定位流失异常网点；avg_cnt 与 avg_cnt_all 两列并排，能同时呈现"留下的人越来越强"与"走了一批人"两个事实。**【加分点】** 说明两种口径的用途——活跃者人均用于算产能爬坡，全体人均用于算网点真实运力，混用是cohort分析最常见的事故。

### 5. 性能分析与优化

解法一的窗口按courier_id分区取MIN，等价于一次按人的排序聚合，日表行数=人数×天数（千人×120天≈十万级），代价低；解法二的JOIN会把每人多日记录展开（自连接性质），行数≈明细行数，主要代价在GROUP BY三键。优化建议：①courier_work_di按work_date分区、(courier_id, work_date)建联合索引；②首次作业日若可由HR入职表提供，直接JOIN事实表替代窗口MIN，省一次全表排序；③透视列（wk0~wk8）固定，适合物化成月度刷新的cohort报表；④百万快递员级（平台众包场景）时在Hive/Spark跑，窗口MIN与JOIN均无压力但注意数据倾斜（超级活跃个体）。

> Hive/Spark SQL差异：FLOOR(DATEDIFF(x,y)/7)在Hive为 floor(datediff(y,x)/7)，参数顺序相反；COUNT(DISTINCT)在Hive大分组下会单reduce倾斜，可先GROUP BY去重再计数；Spark SQL两解法均可直接运行。

### 6. 面试延伸考点

- **留存率的分母为什么必须固定为队列总人数？分子分子口径错会发生什么？** 回答要点：若分母用"该周前仍活跃人数"，留存率恒为100%且失去流失信息；固定分母才能呈现真实衰减曲线，这是cohort分析的铁律。
- **"首次作业日"和"合同入职日"作cohort起点有何差异？** 回答要点：合同日早于实际作业（培训期），用合同日会把培训期算进wk0拉低爬坡起点；用首次作业日贴近产能口径，两者都应记录并声明，考察口径自觉。
- **如何评估3月计件规则调整对留存的影响？** 回答要点：以调整月为界比较相邻队列的同wk留存（类似DID，还可配未调整区域网点做对照），并排除单量季节因素，考察cohort与准实验方法的组合。
- **爬坡曲线何时到顶？怎么定义"成熟产能"？** 回答要点：看人均周单量的边际增幅连续两周低于阈值（如<5%）的wk即为成熟点；同时剔除单量季节影响（对比在岗老人同期单量）。

### 7. 业务拓展思考

爬坡与留存曲线直接支撑三套人力机制：计件保护期长度（新人在wk0-2按保底单量计酬）、带教资源投放（高危窗口安排老带新与关怀动作）、以及招聘节奏（按留存率倒推为维持运力需要每月新招人数）。口径可延展为按网点类型/城市分层的cohort对比、把"流失"细分为主动离职与转岗，以及与派件区域难度挂钩解释个体差异；长期把留存曲线与薪酬、带教、路线分配等干预动作关联，就能形成"什么动作在哪个周最有效"的运营实验平台。

## WL-42 客户维度时效体验分构建（多指标加权合成）

### 1. 业务背景

大客户销售团队与体验运营团队长期争议"哪些客户的时效体验真的差"：有的客户投诉多但时效其实不差（期望高），有的客户从不投诉却默默流失。体验团队决定构建一个**客户时效体验分**（0-100分），综合四个维度：准时率、均时效、破损/异常率、预约时段达成率，按月为每个月单量达标的客户打分，输出分级（红黄绿）名单。销售拿着红色名单做客户安抚与赔偿预案，运营拿着维度拆解定位改善抓手。难点在于四个指标量纲不同、分布各异（准时率挤在90%+，均时长长尾分布），直接加权毫无意义，必须先做**同尺度标准化**——这是本题主考点。

### 2. 表结构说明

customer_timeliness_m（客户×月时效指标表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| customer_id | VARCHAR(24) | 客户ID |
| stat_month | CHAR(7) | 统计月 |
| total_cnt | INT | 当月单量 |
| on_time_cnt | INT | 准时达成单量 |
| avg_hours | DECIMAL(5,1) | 加权均时效（小时） |
| broken_cnt | INT | 破损/异常单量 |
| slot_hit_cnt | INT | 预约时段达成单量 |
| complain_cnt | INT | 投诉单量 |

示例数据：

| customer_id | stat_month | total_cnt | on_time_cnt | avg_hours | broken_cnt | slot_hit_cnt | complain_cnt |
|-------------|------------|-----------|-------------|-----------|------------|--------------|--------------|
| U0001 | 2025-06 | 3200 | 3050 | 39.5 | 12 | 2880 | 8 |
| U0002 | 2025-06 | 850 | 780 | 46.2 | 9 | 700 | 6 |
| U0003 | 2025-06 | 5600 | 5480 | 36.8 | 18 | 5320 | 11 |
| U0004 | 2025-06 | 420 | 360 | 58.0 | 7 | 300 | 5 |
| U0005 | 2025-06 | 1500 | 1440 | 41.0 | 5 | 1350 | 2 |

### 3. 解题思路

先定口径：四个原始指标——准时率=on_time_cnt/total_cnt（正向）、均时效=avg_hours（负向，越小越好）、异常率=broken_cnt/total_cnt（负向）、预约达成率=slot_hit_cnt/total_cnt（正向）；只对月单量≥300的客户打分（防小样本波动）。标准化两种主流做法：①百分位法——对每个指标在客户群体内算 PERCENT_RANK，正向指标得分=百分位×100，负向指标得分=(1−百分位)×100，天然对长尾稳健；②业务分箱法——按业务阈值打档位分（准时率≥95%得100分、90~95%得80分……），可解释性强、便于对客沟通。总分=0.4×准时率分+0.25×时效分+0.2×异常分+0.15×预约分（权重需业务共识）。易错点：①负向指标忘记方向翻转，出现"越慢分越高"的事故；②PERCENT_RANK并列值处理与分位数混淆（它是(排名−1)/(n−1)）；③权重设定要有依据（回归投诉率或专家打分），并在报表中冻结版本防口径漂移。

### 4. 参考解法

**解法一：PERCENT_RANK百分位标准化 + 加权合成（统计稳健版）**

```sql
WITH eligible AS (                                    -- 门槛过滤: 月单量达标的客户
    SELECT customer_id, stat_month, total_cnt,
           on_time_cnt / total_cnt                    AS on_time_rate,  -- 准时率(正向)
           avg_hours,                                                  -- 均时效(负向)
           broken_cnt / total_cnt                     AS broken_rate,   -- 异常率(负向)
           slot_hit_cnt / total_cnt                   AS slot_hit_rate  -- 预约达成率(正向)
    FROM customer_timeliness_m
    WHERE stat_month = '2025-06'
      AND total_cnt >= 300                            -- 小样本客户不打分
),
norm AS (                                             -- 四指标百分位标准化(方向翻转)
    SELECT customer_id, total_cnt, on_time_rate, avg_hours, broken_rate, slot_hit_rate,
           PERCENT_RANK() OVER (ORDER BY on_time_rate)    * 100 AS s_ontime, -- 正向:百分位即得分
           (1 - PERCENT_RANK() OVER (ORDER BY avg_hours)) * 100 AS s_hours,  -- 负向:翻转(越快分越高)
           (1 - PERCENT_RANK() OVER (ORDER BY broken_rate))* 100 AS s_broken,-- 负向:越低分越高
           PERCENT_RANK() OVER (ORDER BY slot_hit_rate)   * 100 AS s_slot    -- 正向
    FROM eligible
)
SELECT customer_id, total_cnt,
       ROUND(s_ontime, 1)  AS score_ontime,           -- 准时率分(0-100)
       ROUND(s_hours, 1)   AS score_hours,            -- 时效分
       ROUND(s_broken, 1)  AS score_broken,           -- 异常分
       ROUND(s_slot, 1)    AS score_slot,             -- 预约达成分
       ROUND(0.40 * s_ontime + 0.25 * s_hours             -- 加权总分
           + 0.20 * s_broken + 0.15 * s_slot, 1)     AS total_score,
       CASE WHEN 0.40 * s_ontime + 0.25 * s_hours
              + 0.20 * s_broken + 0.15 * s_slot < 40 THEN '红色(优先安抚)'
            WHEN 0.40 * s_ontime + 0.25 * s_hours
              + 0.20 * s_broken + 0.15 * s_slot < 60 THEN '黄色(关注)'
            ELSE '绿色(健康)' END                 AS grade       -- 体验分级
FROM norm
ORDER BY total_score ASC;                             -- 最差客户排最前,供销售跟进
```

结果解读：总分是客户在全网客户中的相对位置，天然适合"红黄绿"名单——红色客户即处在全网后40%分位的体验洼地；四个分项并列输出，直接指出短板维度供运营定抓手。

**解法二：业务阈值分箱打分 + 短板定位（可解释版）**

```sql
WITH eligible AS (                                    -- 同解法一的指标计算
    SELECT customer_id, stat_month, total_cnt,
           on_time_cnt / total_cnt                    AS on_time_rate,
           avg_hours,
           broken_cnt / total_cnt                     AS broken_rate,
           slot_hit_cnt / total_cnt                   AS slot_hit_rate
    FROM customer_timeliness_m
    WHERE stat_month = '2025-06' AND total_cnt >= 300
),
binned AS (                                           -- 按业务阈值分箱打分(对客可解释)
    SELECT customer_id, total_cnt, on_time_rate, avg_hours, broken_rate, slot_hit_rate,
           CASE WHEN on_time_rate >= 0.95 THEN 100          -- 准时率:95%以上满分
                WHEN on_time_rate >= 0.90 THEN 80
                WHEN on_time_rate >= 0.85 THEN 60
                ELSE 30 END                     AS s_ontime,
           CASE WHEN avg_hours <= 40 THEN 100             -- 均时效:40小时内满分(负向阈值)
                WHEN avg_hours <= 48 THEN 80
                WHEN avg_hours <= 56 THEN 60
                ELSE 30 END                     AS s_hours,
           CASE WHEN broken_rate <= 0.002 THEN 100        -- 异常率:0.2%以下满分
                WHEN broken_rate <= 0.005 THEN 80
                WHEN broken_rate <= 0.010 THEN 60
                ELSE 30 END                     AS s_broken,
           CASE WHEN slot_hit_rate >= 0.95 THEN 100       -- 预约达成率
                WHEN slot_hit_rate >= 0.90 THEN 80
                WHEN slot_hit_rate >= 0.80 THEN 60
                ELSE 30 END                     AS s_slot
    FROM eligible
)
SELECT customer_id, total_cnt,
       0.40 * s_ontime + 0.25 * s_hours
     + 0.20 * s_broken + 0.15 * s_slot                 AS total_score,  -- 总分(整数档,便于对客)
       CASE                                              -- 定位最低分维度=改善抓手
            WHEN LEAST(s_ontime, s_hours, s_broken, s_slot) = s_ontime THEN '准时率'
            WHEN LEAST(s_ontime, s_hours, s_broken, s_slot) = s_hours  THEN '时效'
            WHEN LEAST(s_ontime, s_hours, s_broken, s_slot) = s_broken THEN '破损'
            ELSE '预约达成' END                     AS weakest_dim,
       on_time_rate, avg_hours, broken_rate, slot_hit_rate   -- 原始值留档备查
FROM binned
ORDER BY total_score ASC;
```

结果解读：每档分数都对应一条业务规则（"准时率92%→80分"），销售对客户解释时无需统计学；weakest_dim 自动给出该客户体验分最大的失分维度。**【避坑指南】** 分箱阈值须每半年随全网分布复核一次，否则全网整体变快后老阈值会让所有人满分、分数失去区分度；百分位法则没有这个问题但分数含义是"相对位置"，跨月比较要谨慎。

### 5. 性能分析与优化

两解法都在月度指标表（行数=客户数，万级）上运行，成本极低；解法一的四个PERCENT_RANK窗口各需一次排序（不同ORDER BY键无法共享窗口），即四次排序万级数据无感知。优化建议：①月度指标表若由明细实时汇总而来，先固化"客户×月"指标表再打分，打分层保持轻量；②门槛过滤（total_cnt>=300）尽量下推到子查询减少窗口输入行数；③阈值分箱若阈值存在配置表，JOIN配置表替代CASE硬编码便于业务自助调整；④全网客户百万级时改在Spark跑，四个窗口可合并为一次shuffle（把ORDER BY键拼接后取模优化或接受四次排序）。

> Hive/Spark SQL差异：PERCENT_RANK在Hive 2.x+可用；FIELD/LEAST中Hive支持least()但注意空值传播；分箱配置表JOIN在Hive需小表mapjoin；对客报表建议最终落Hive结果表由BI读取，避免在线查询压窗口排序。

### 6. 面试延伸考点

- **PERCENT_RANK、CUME_DIST、NTILE三个窗口函数有什么区别？打分场景选哪个？** 回答要点：PERCENT_RANK=(rank−1)/(n−1)对并列值同分；CUME_DIST是累积占比含自身；NTILE是硬等分桶。体验分要"并列同分、连续刻度"选PERCENT_RANK；要强制五档人群选NTILE。
- **权重0.4/0.25/0.2/0.15是怎么定的？被质疑"拍脑袋"怎么回应？** 回答要点：可用投诉率对四指标做逻辑回归取标准化系数、或让业务专家做层次分析法(AHP)两两比较，并做权重敏感性测试（±0.1扰动看红名单稳定性）。
- **体验分是相对分，某月全网整体变差所有人都降分，合理吗？** 回答要点：相对分剥离了共同冲击适合内部分级，但对外承诺要配合绝对SLA指标；可双轨制——内部分级用百分位、对客赔付用绝对阈值。
- **如何验证体验分真的能预测流失/投诉？** 回答要点：回测——用上月分数对本月投诉/流失做提升度或AUC检验，若红色客户投诉率是绿色的5倍以上即有效，考察指标体系的闭环验证意识。

### 7. 业务拓展思考

体验分体系可延展为客户经营的仪表盘：红色名单驱动销售安抚与赔付预案、分项短板驱动运营专项（预约达成低的客户推精准预约产品）、分数趋势用于评估改善动作。口径可细化到客户内部分层（大客户的时效承诺更严，分箱阈值随合同等级浮动）、加入温度敏感等品类因子，以及把打分从月度升级为周度滚动（4周滑动窗口）让运营更早介入；分数沉淀两个大促周期后，还能反哺合同的SLA条款设计。

## WL-43 末端派送时段分布与二次派送率分析

### 1. 业务背景

末端配送的成本大头在"上楼"与"重复跑"：用户不在家导致的一次派送失败，会触发二次甚至三次派送，每次重派都消耗快递员半小时以上的往返时间。末端运营团队计划改造预约派送产品——让用户在下单时选择收货时段，从而把派送集中到"有人"的时段。立项前需要摸清现状：现有派送都集中在哪些时段？各预约时段的**一次完成率**差异多大？"无人接听"失败集中在哪个时段？**二次派送率**（一票需要派送两次及以上的比例）多高、首次失败到二次成功的间隔多久？这些结论决定预约时段选项怎么设、是否对晚间无人时段加收提醒费用，是末端产品设计的量化依据。

### 2. 表结构说明

delivery_attempts（派送尝试明细表，一次尝试一行）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| waybill_id | VARCHAR(32) | 运单号 |
| courier_id | VARCHAR(24) | 执行快递员 |
| slot | VARCHAR(10) | 约定/实际时段：9-11/11-14/14-18/18-21/21-23 |
| attempt_no | INT | 派送尝试序号（1=首派） |
| attempt_date | DATE | 尝试日期 |
| result | VARCHAR(10) | 结果：成功/无人接听/拒收/地址错误 |
| arrive_time | DATETIME | 到达时间 |

示例数据：

| waybill_id | courier_id | slot | attempt_no | attempt_date | result | arrive_time |
|------------|------------|------|------------|--------------|--------|-------------|
| SF2025061001 | C201 | 9-11 | 1 | 2025-06-10 | 无人接听 | 2025-06-10 10:20 |
| SF2025061001 | C201 | 18-21 | 2 | 2025-06-10 | 成功 | 2025-06-10 19:05 |
| SF2025061002 | C202 | 14-18 | 1 | 2025-06-10 | 成功 | 2025-06-10 15:40 |
| SF2025061003 | C203 | 21-23 | 1 | 2025-06-10 | 拒收 | 2025-06-10 21:30 |
| SF2025061003 | C203 | 9-11 | 2 | 2025-06-11 | 成功 | 2025-06-11 09:50 |

### 3. 解题思路

先定口径：时段分布 = 各slot首派票数占比；一次完成率 = 该slot首派result='成功'的票数 / 该slot首派总票数；二次派送率 = 存在attempt_no≥2的运单数 / 运单总数（分子分母都落在"运单"粒度，不在"尝试"粒度）；重派间隔 = 同运单第2次尝试时间 − 第1次尝试时间。实现路径：解法一用票内窗口（COUNT(*)/MAX(attempt_no) OVER PARTITION BY waybill_id）给每票打上"是否二次派送"标记，再按时段聚合；解法二用同票自连接把"首派失败行"与"二次派送行"配对，算重派间隔与"失败原因→二次结果"的转移结构，回答"哪种失败原因最浪费"。易错点：①分母必须先聚到运单粒度再算比率，直接在尝试明细上算会把多派几票的客户权重放大；②slot应取首派的slot（用户约的时段），二次派送slot是补救时段，混用会扭曲时段分布；③attempt_no由系统生成但要校验跳号/重复。

### 4. 参考解法

**解法一：票内窗口标记 + 时段聚合（主分析）**

```sql
WITH first_attempt AS (                               -- 取每票首派记录(含票内总尝试数)
    SELECT waybill_id, courier_id, slot, result, arrive_time, attempt_date,
           MAX(attempt_no) OVER (PARTITION BY waybill_id) AS max_attempt,  -- 票内最大尝试次数
           ROW_NUMBER() OVER (PARTITION BY waybill_id ORDER BY attempt_no) AS rn -- 首派标记
    FROM delivery_attempts
    WHERE attempt_date BETWEEN '2025-06-01' AND '2025-06-30'   -- 6月派送
)
SELECT slot,                                          -- 首派约定时段
       COUNT(*)                                       AS first_cnt,      -- 该时段首派票数
       ROUND(COUNT(*) / SUM(COUNT(*)) OVER () * 100, 1) AS slot_pct,     -- 时段分布占比%
       ROUND(SUM(CASE WHEN result = '成功' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1)
                                                      AS first_ok_pct,   -- 一次完成率%
       ROUND(SUM(CASE WHEN max_attempt >= 2 THEN 1 ELSE 0 END) / COUNT(*) * 100, 1)
                                                      AS redelivery_pct, -- 该时段票的二次派送率%
       SUM(CASE WHEN result = '无人接听' THEN 1 ELSE 0 END) AS nobody_cnt, -- 无人失败票数
       SUM(CASE WHEN result = '拒收'    THEN 1 ELSE 0 END) AS refuse_cnt    -- 拒收票数
FROM first_attempt
WHERE rn = 1                                          -- 只取首派行(分母=票数)
GROUP BY slot
ORDER BY slot_pct DESC;                               -- 按单量分布排序
```

结果解读：若"9-11"时段占首派38%但一次完成率仅72%、二次派送率25%，而"18-21"时段一次完成率93%，说明大量单量被派进了"无人"的上午——预约产品把单量向晚间迁移就有明确的量化空间；失败构成列（无人vs拒收）区分"人不在"与"不想要"两类完全不同的补救策略。

**解法二：同票自连接配对（重派间隔与失败-补救转移分析）**

```sql
WITH f AS (                                           -- 首派行
    SELECT waybill_id, slot AS first_slot, result AS first_result,
           arrive_time AS first_time, attempt_date
    FROM delivery_attempts
    WHERE attempt_no = 1
      AND attempt_date BETWEEN '2025-06-01' AND '2025-06-30'
),
s AS (                                                -- 二次派送行
    SELECT waybill_id, slot AS second_slot, result AS second_result,
           arrive_time AS second_time
    FROM delivery_attempts
    WHERE attempt_no = 2
      AND attempt_date BETWEEN '2025-06-01' AND '2025-06-30'
)
SELECT f.first_slot,                                  -- 首派时段
       f.first_result,                                -- 首派失败原因
       s.second_slot,                                 -- 补救时段(看运营是否自动改约)
       COUNT(*)                                       AS pairs,          -- 该组合票数
       ROUND(AVG(TIMESTAMPDIFF(HOUR, f.first_time, s.second_time)), 1) AS avg_rehours, -- 重派间隔(小时)
       ROUND(SUM(CASE WHEN s.second_result = '成功' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1)
                                                      AS second_ok_pct   -- 二次成功率%
FROM f
JOIN s ON s.waybill_id = f.waybill_id                 -- 同票首派与二次派送配对
WHERE f.first_result <> '成功'                        -- 只看首派失败的补救链路
GROUP BY f.first_slot, f.first_result, s.second_slot
ORDER BY f.first_result, pairs DESC;                  -- 按失败原因聚类看补救模式
```

结果解读："9-11无人接听→18-21成功"若占失败票四成且平均间隔8小时，说明当日二次派送可行，预约改造应默认把失败单自动改约到晚间；"拒收→次日成功"间隔24小时+，提示拒收单要走不同的逆向/沟通流程而非简单重派。**【面试高频】** 追问"为什么不用窗口LAG而用自连接"——LAG也可以（按票内序号取下一行），但自连接在需要按失败原因分组、跨天配对、且二次行可能缺失（没有二次派送）时语义更直观，两种写法都应掌握。

### 5. 性能分析与优化

解法一窗口按waybill_id分区两次（MAX与ROW_NUMBER可合并为同一窗口定义减少一次排序），随后按时段GROUP BY，代价为明细一次排序；解法二自连接在waybill_id等值键上，需(waybill_id, attempt_no)联合索引或按票分桶，否则随机访问代价高。优化建议：①月度分析先按attempt_date分区裁剪；②明细表对(waybill_id)建索引使自连接走hash join；③attempt_no≥3的极少数票不影响主结论，可在窗口层先过滤attempt_no<=2减少数据量，但需在口径中声明；④时段聚合结果建议与快递员人效表联动时物化"票粒度宽表"（首派时段/结果/二次标记/间隔）一表多用。

> Hive/Spark SQL差异：TIMESTAMPDIFF(HOUR,...)在Hive为 (unix_timestamp(t2)-unix_timestamp(t1))/3600；自连接亿级明细在Hive必须分桶(sort by waybill_id)或走Spark shuffle hash join；窗口MAX OVER与ROW_NUMBER在两引擎均可用，Spark下同一窗口定义复用可省shuffle。

### 6. 面试延伸考点

- **二次派送率的分子分母分别落在什么粒度？为什么不能在尝试明细上直接算？** 回答要点：分子=存在attempt_no≥2的票数、分母=总票数，均为票粒度；明细粒度会把多次尝试的票重复计数，比率系统性偏高，考察粒度意识。
- **slot应该用"用户预约时段"还是"实际到达时段"分析？** 回答要点：评估预约产品用预约slot（需求侧），评估快递员执行用实际到达时段（供给侧），两者偏差本身就是"预约履约率"指标；混用会同时误判需求与履约。
- **如何判断"晚间时段加价/提醒"这个产品值得做？** 回答要点：用时段间一次完成率差×迁移单量估算省下的重派成本，与提醒短信/加价带来的流失风险对比，先小流量A/B再推广，体现ROI测算闭环。
- **拒收和无人接听的重派策略为什么必须分开？** 回答要点：无人是"时间不匹配"，改约即可；拒收是"意愿问题"，重派大概率再拒，需电询或转逆向，混在一起会拉低二次成功率、误判时段改造效果。

### 7. 业务拓展思考

时段分布与重派分析可直接生成预约产品方案：时段选项按"一次完成率×单量潜力"排序设计、失败单自动改约规则（无人→默认晚间）、对高频无人地址推驿站自提引导。口径可延展为"预约履约率"（按约送达的比例）反向考核快递员、按小区/楼栋粒度定位无人高发楼（对讲机问题）、以及把重派成本折算进单票末端成本（衔接WL-38的成本口径），让预约产品定价有成本锚；持续监控二次派送率的周趋势还能验证产品上线效果，形成"分析-产品-验证"闭环。

## WL-44 仓库间调拨需求识别与建议量生成（库存分布不均）

### 1. 业务背景

同一位SKU在全国多个前置仓都有库存，但销售分布与铺货分布天然错位——A仓所在区域卖得慢、库存积压，B仓卖得快、即将缺货，而总部补货周期要两周，等不及工厂排产。供应链计划团队的日常动作是**仓间调拨**：把A仓的富余库存调给B仓，既救急又降全网库存。计划员需要一份每日扫描的调拨建议清单：哪些SKU在哪些仓对之间应该调、调多少？判定标准是"覆盖天数"——供给仓库存可覆盖未来N天预测需求的富余量，需求仓的缺口量，两者取小为建议调拨量，并按仓间距离/运费优先近距配对。这份清单直接变成调拨单，调错方向（把快缺货仓的货调走）会造成断货事故，因此口径严谨性是本题主考点。

### 2. 表结构说明

inventory_pos（仓库×SKU当日库存与需求表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| wh | VARCHAR(20) | 仓库编码 |
| sku_id | VARCHAR(24) | SKU编码 |
| stat_date | DATE | 库存快照日期 |
| stock_qty | INT | 当日可用库存 |
| avg_daily_sale | DECIMAL(8,1) | 近7日日均销量 |

wh_distance（仓间距离与调拨成本表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| wh_from | VARCHAR(20) | 调出仓 |
| wh_to | VARCHAR(20) | 调入仓 |
| dist_km | INT | 仓间公路距离（km） |
| transfer_cost_per_unit | DECIMAL(6,2) | 单件调拨成本（元） |

示例数据（inventory_pos）：

| wh | sku_id | stat_date | stock_qty | avg_daily_sale |
|----|--------|-----------|-----------|----------------|
| WH01 | SKU-A | 2025-06-10 | 1200 | 30.0 |
| WH02 | SKU-A | 2025-06-10 | 150 | 75.0 |
| WH03 | SKU-A | 2025-06-10 | 600 | 40.0 |
| WH01 | SKU-B | 2025-06-10 | 80 | 50.0 |
| WH02 | SKU-B | 2025-06-10 | 900 | 25.0 |

示例数据（wh_distance）：

| wh_from | wh_to | dist_km | transfer_cost_per_unit |
|---------|-------|---------|------------------------|
| WH01 | WH02 | 320 | 1.20 |
| WH03 | WH02 | 150 | 0.80 |
| WH01 | WH03 | 210 | 1.00 |

### 3. 解题思路

先定口径：覆盖天数 cover = stock_qty / avg_daily_sale；**供给仓**条件 = cover ≥ 15天（两周补货周期之上）且可调出量 = stock − 15×日均销量 > 0；**需求仓**条件 = cover < 7天且缺口量 = 7×日均销量 − stock > 0（保守覆盖一周，等总部补货到达）；同SKU跨仓配对，建议调拨量 = LEAST(供给可调出, 需求缺口)，多供给仓竞争时按调拨成本（距离）升序优先近配。实现路径：解法一在(wh, sku)粒度用窗口/自连接构造"同SKU供给池×需求池"的配对大表再取最优；解法二分别物化供给表与需求表两个派生表再JOIN，结构更清晰。易错点：①必须按SKU分组配对，跨SKU调拨无意义；②多对一配对时需求缺口会被重复分配（两个供给仓都按满缺口建议），需按成本序给供给仓排ROW_NUMBER并扣减已分配量，或至少输出提示；③日均销量为0的SKU要除零保护；④调拨在途时间内需求仓还会继续卖，缺口口径要把调拨提前期（transit天）乘日均销量加进去。

### 4. 参考解法

**解法一：供给/需求池派生表 + 成本序配对（推荐写法）**

```sql
WITH pos AS (                                         -- 计算每仓每SKU的覆盖与富余/缺口
    SELECT wh, sku_id, stock_qty, avg_daily_sale,
           stock_qty / NULLIF(avg_daily_sale, 0)      AS cover_days,      -- 覆盖天数(除零保护)
           stock_qty - 15 * avg_daily_sale            AS surplus_qty,     -- 可调出量=库存-15天保有
           7 * avg_daily_sale - stock_qty             AS gap_qty          -- 缺口量=7天需求-库存
    FROM inventory_pos
    WHERE stat_date = '2025-06-10'                     -- 当日快照(若表中含日期列)
),
supply AS (                                           -- 供给池: 富余且覆盖达标
    SELECT sku_id, wh AS wh_from, surplus_qty, cover_days
    FROM pos
    WHERE avg_daily_sale > 0                          -- 有动销的仓才有"富余"意义
      AND cover_days >= 15                            -- 自己先安全(覆盖≥15天)
      AND surplus_qty > 0
),
demand AS (                                           -- 需求池: 覆盖不足且存在缺口
    SELECT sku_id, wh AS wh_to, gap_qty, cover_days
    FROM pos
    WHERE avg_daily_sale > 0
      AND cover_days < 7                              -- 缺货风险(覆盖<7天)
      AND gap_qty > 0
),
pair AS (                                             -- 同SKU供给×需求全配对
    SELECT s.sku_id, s.wh_from, d.wh_to,
           LEAST(s.surplus_qty, d.gap_qty)            AS suggest_qty,   -- 建议量=富余与缺口取小
           d.avg_daily_sale                           AS to_ads,        -- 调入仓日均销量(算撑货天数用)
           x.dist_km, x.transfer_cost_per_unit,
           ROW_NUMBER() OVER (PARTITION BY d.sku_id, d.wh_to   -- 每个需求仓按成本选最优供给
                              ORDER BY x.dist_km)     AS rn              -- 距离近者优先
    FROM supply s
    JOIN demand d ON d.sku_id = s.sku_id              -- 同SKU才可调
    JOIN wh_distance x ON x.wh_from = s.wh_from       -- 挂仓间距离成本
                     AND x.wh_to = d.wh_to
)
SELECT sku_id, wh_from, wh_to, suggest_qty,
       dist_km,
       ROUND(suggest_qty * transfer_cost_per_unit, 2) AS transfer_cost,   -- 该笔调拨成本(元)
       ROUND(suggest_qty / NULLIF(to_ads, 0), 1)      AS days_added       -- 调入后可多撑天数
FROM pair
WHERE rn = 1                                          -- 每个需求仓只取成本最优的一笔
ORDER BY transfer_cost / GREATEST(suggest_qty, 1) ASC; -- 按单位调拨效率排序
```

结果解读：示例数据会输出"SKU-A: WH01→WH02 调600件"（WH01覆盖40天富余750、WH02缺口375，取小后受成本序约束选WH03或WH01取决于距离）——清单可直接导入调拨系统生成调拨单，days_added 列帮助计划员确认调完仍不达标时需叠加总部补货。

**解法二：自连接宽表法 + 缺口分配去重（多供给竞争的严谨处理）**

```sql
WITH pos AS (                                         -- 同解法一的覆盖计算
    SELECT wh, sku_id, stock_qty, avg_daily_sale,
           stock_qty / NULLIF(avg_daily_sale, 0) AS cover_days,
           stock_qty - 15 * avg_daily_sale       AS surplus_qty,
           7 * avg_daily_sale - stock_qty        AS gap_qty
    FROM inventory_pos
    WHERE stat_date = '2025-06-10'
),
pair AS (                                             -- 同SKU自连接: 一边当供给一边当需求
    SELECT s.sku_id, s.wh AS wh_from, d.wh AS wh_to,
           s.surplus_qty, d.gap_qty,
           LEAST(s.surplus_qty, d.gap_qty)       AS suggest_qty,
           x.dist_km
    FROM pos s
    JOIN pos d ON d.sku_id = s.sku_id                 -- 同SKU自连接
              AND s.wh <> d.wh                        -- 排除自己调自己
    JOIN wh_distance x ON x.wh_from = s.wh AND x.wh_to = d.wh
    WHERE s.cover_days >= 15 AND s.surplus_qty > 0    -- 供给条件
      AND d.cover_days < 7  AND d.gap_qty > 0         -- 需求条件
),
ranked AS (                                           -- 每个需求仓的候选供给排序
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY sku_id, wh_to ORDER BY dist_km) AS rn,
           SUM(suggest_qty) OVER (PARTITION BY sku_id, wh_to ORDER BY dist_km
               ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS allocated_before  -- 排在我前面的仓已分配量(累计)
    FROM pair
)
SELECT sku_id, wh_from, wh_to,
       GREATEST(LEAST(suggest_qty, gap_qty - COALESCE(allocated_before, 0)), 0)
                                                      AS final_qty,  -- 扣减前面仓已分配后的最终建议量
       dist_km
FROM ranked
ORDER BY sku_id, wh_to, dist_km;                      -- 保留全部候选供计划员复核
```

结果解读：当WH02缺口375而WH01、WH03都富余时，解法一给出距离最近的WH03一笔满配；解法二则展示扣减逻辑——若WH03可调出仅200，剩余175自动落到次优的WH01，这是多供给场景的严谨解。**【加分点】** 主动指出该贪心分配仍非全局最优（供给仓之间也存在竞争），严格解是运输问题线性规划，SQL负责给出可执行的高质量启发解。

### 5. 性能分析与优化

解法一的核心代价是supply×demand按SKU的配对JOIN与一次ROW_NUMBER窗口；解法二的自连接是同表N²潜力，必须靠 `s.sku_id = d.sku_id` 等值条件与wh_distance双键JOIN约束，(sku_id, wh)上的索引/分桶是生命线。优化建议：①inventory_pos当日切片先物化（WHERE stat_date=当日），避免两个CTE各扫全历史；②wh_distance是小表，任何引擎都应broadcast；③SKU数十万级时配对结果可能爆炸（供给仓数×需求仓数），先在仓对层面限制"同大区优先"或对surplus/gap加最小阈值（如≥50件）过滤琐碎调拨；④建议清单每日定时生成，落结果表供调拨系统拉取，而非交互查询。

> Hive/Spark SQL差异：GREATEST/LEAST在Hive中为greatest/least且空值返回NULL，需COALESCE前置；自连接大表在Hive务必开启mapjoin或对(sku_id)分桶排序；窗口累计扣减在Spark上更稳，Hive老版本对ROWS BETWEEN支持不全时可改用两层聚合JOIN模拟。

### 6. 面试延伸考点

- **多供给仓竞争同一需求仓时，你的建议量为什么会超配？怎么修？** 回答要点：每个供给仓都按满缺口建议、叠加后超过缺口；修法是按成本序ROW_NUMBER加累计已分配扣减（解法二），或干脆每需求仓只取最优一笔，考察对配对问题重复计算的敏感度。
- **为什么供给仓要求覆盖≥15天而不是"有富余就行"？** 回答要点：调出后供给仓仍要安全撑过总部补货周期（约两周），否则按下葫芦浮起瓢；15天=补货周期+安全余量，阈值应随实际补货lead time配置。
- **调拨提前期3天，缺口口径要怎么修正？** 回答要点：需求缺口应覆盖"缺口识别日+调拨在途天数"的需求，即(7+3)×日均销量−库存，否则货到之前就断货了，考察补货/调拨模型的基本功。
- **调拨成本1.2元/件，什么情况下宁可让客户等总部补货也不调？** 回答要点：单件毛利低且缺货损失小于调拨成本、调拨量低于整车装载率阈值、或SKU处于退市清库阶段——调拨决策要合并财务与网络视角，不是纯SQL问题。

### 7. 业务拓展思考

调拨建议清单可升级为全网库存平衡引擎：与WL-39缺货预警共用覆盖天数口径，红色预警SKU自动进入调拨候选、并按"调拨成本vs缺货损失"排序生成优先级；口径可延展到考虑在途库存、按箱规取整（调拨量向上取整到整箱）、以及区分紧急调拨（空运/快线）与常规调拨（整车）两档时效；积累调拨执行数据后，还能回测"建议采纳率与缺货率改善"，反向校准15天/7天阈值，让调拨规则数据驱动化。

## WL-45 大促前后退货率走势与逆向件洪峰检测

### 1. 业务背景

618大促带来了单量洪峰，也带来了**逆向件洪峰**——大促冲动消费的退货会在促销结束后1~3周集中涌入仓库，退货处理区爆仓、退款时效恶化、客户投诉激增。逆向物流团队需要回答三个问题：本轮大促的退货率比平时高多少、比上一轮大促呢（衡量选品与营销质量）？退货按"下单日cohort"追踪的曲线长什么样——退款高峰在促销后第几天（决定逆向处理区的人力排班峰值日）？哪些天的逆向入库量构成**异常洪峰**（超出常态基线太多，需要临时加开退货处理线）？结论直接驱动逆向处理区的临时工排班与仓间逆向分流方案，也反哺大促复盘里的"真实成交质量"。

### 2. 表结构说明

sale_returns_di（城市×日订单与退货汇总表，按下单日统计）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stat_date | DATE | 下单日期（cohort日） |
| city | VARCHAR(20) | 城市 |
| order_cnt | INT | 当日下单量 |
| return_cnt | INT | 该批订单最终退货量（按退货归因回下单日） |
| return_amt | DECIMAL(12,2) | 退货金额（元） |
| main_reason | VARCHAR(10) | 当日主要退货原因：尺码/质量/描述不符/七天无理由 |

示例数据：

| stat_date | city | order_cnt | return_cnt | return_amt | main_reason |
|-----------|------|-----------|------------|------------|-------------|
| 2025-06-01 | 杭州 | 52000 | 6240 | 187200.00 | 尺码 |
| 2025-06-18 | 杭州 | 158000 | 33490 | 1105000.00 | 七天无理由 |
| 2025-06-25 | 杭州 | 61000 | 14640 | 480000.00 | 七天无理由 |
| 2025-06-18 | 武汉 | 96000 | 18240 | 590000.00 | 尺码 |
| 2025-07-02 | 杭州 | 55000 | 9900 | 310000.00 | 质量 |

### 3. 解题思路

先定口径：退货率 = return_cnt / order_cnt 按"下单日cohort"计算（return_cnt已按退货归属回下单日，避免用退货日算率造成的口径漂移），城市×日粒度先算率再按单量加权汇总，防辛普森。洪峰检测：对每日逆向入库量（用return_cnt近似）建立**滚动30日基线**（截至前一日的30日均值与标准差，注意基线窗口要落在常态期、且不包含被检测日自身防污染），当日量 > 基线均值 + 2×标准差 即标记洪峰日。实现路径：解法一用窗口（ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING）算滚动基线并标记洪峰，同时输出cohort退货率曲线；解法二用自连接构造30日区间基线（等价但适配基线窗口要排除节假日等自定义场景），并做洪峰日的原因与城市构成拆解。易错点：①基线窗口含大促日本身会抬高σ，洪峰被"合法化"漏检——基线须取促销前常态期或剔除已标洪峰日；②退货率cohort口径要求return_cnt完全归因回下单日，若表是按退货日统计的，必须先做归因映射否则早期cohort被低估；③σ对小样本日敏感，城市×日粒度过细时改在全网粒度检测。

### 4. 参考解法

**解法一：滚动窗口基线 + 2σ洪峰标记（推荐写法）**

```sql
WITH daily AS (                                       -- 全网日粒度(先聚合再检测,防城市小样本噪声)
    SELECT stat_date,
           SUM(order_cnt)                             AS order_cnt,   -- 当日下单量
           SUM(return_cnt)                            AS return_cnt,  -- 归因回下单日的退货量
           SUM(return_cnt) / NULLIF(SUM(order_cnt), 0) AS return_rate  -- cohort退货率
    FROM sale_returns_di
    WHERE stat_date BETWEEN '2025-05-01' AND '2025-07-15'
    GROUP BY stat_date
),
baseline AS (                                         -- 滚动30日基线(截至前一日,不含当日)
    SELECT stat_date, order_cnt, return_cnt, return_rate,
           AVG(return_cnt) OVER (ORDER BY stat_date
               ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING) AS avg_base,  -- 前30日均值
           STDDEV_SAMP(return_cnt) OVER (ORDER BY stat_date
               ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING) AS std_base   -- 前30日标准差
    FROM daily
)
SELECT stat_date, order_cnt, return_cnt,
       ROUND(return_rate * 100, 2)                    AS return_rate_pct,   -- cohort退货率%
       ROUND(avg_base, 0)                             AS base_avg,          -- 基线均值
       ROUND(std_base, 0)                             AS base_std,          -- 基线σ
       ROUND((return_cnt - avg_base) / NULLIF(std_base, 0), 2) AS z_score,  -- 距基线的σ倍数
       CASE WHEN return_cnt > avg_base + 2 * std_base THEN '洪峰'   -- 超2σ判洪峰
            WHEN return_cnt > avg_base + 1 * std_base THEN '偏高'
            ELSE '正常' END                           AS peak_flag          -- 洪峰标记
FROM baseline
ORDER BY stat_date;                                   -- 时序输出可直接画"洪峰检测图"
```

结果解读：若6月25日（大促后第7天）z_score=3.4标记洪峰、7月2日z_score=2.6仍洪峰，则逆向处理区的临时工排班应在6月23日-7月5日拉满，且z_score曲线天然回答了"洪峰持续几天"。

**解法二：自连接基线 + 洪峰日构成拆解（归因加强版）**

```sql
WITH daily AS (                                       -- 全网日粒度
    SELECT stat_date, SUM(order_cnt) AS order_cnt, SUM(return_cnt) AS return_cnt
    FROM sale_returns_di
    WHERE stat_date BETWEEN '2025-05-01' AND '2025-07-15'
    GROUP BY stat_date
),
base AS (                                             -- 自连接构造30日基线窗口
    SELECT t.stat_date,
           AVG(b.return_cnt)                          AS avg_base,   -- 基线均值(截至前一日30天)
           STDDEV_SAMP(b.return_cnt)                  AS std_base,
           AVG(t.return_cnt) OVER ()                  AS all_avg     -- 全期均值(参考)
    FROM daily t
    LEFT JOIN daily b                                 -- b为t之前30天的记录
      ON b.stat_date < t.stat_date
     AND b.stat_date >= t.stat_date - INTERVAL 30 DAY
    GROUP BY t.stat_date
),
peaks AS (                                            -- 标记洪峰日(同时带出当日cohort退货率)
    SELECT d.stat_date, d.return_cnt, d.order_cnt,
           b.avg_base, b.std_base,
           (d.return_cnt - b.avg_base) / NULLIF(b.std_base, 0) AS z,  -- z分数
           d.return_cnt / NULLIF(d.order_cnt, 0)      AS return_rate    -- 当日cohort退货率
    FROM daily d
    JOIN base b ON b.stat_date = d.stat_date
    WHERE d.return_cnt > b.avg_base + 2 * b.std_base  -- 2σ规则
)
SELECT p.stat_date, p.return_cnt,
       ROUND(p.z, 2)                                  AS z_score,
       ROUND(p.return_rate * 100, 2)                  AS cohort_rate_pct,   -- 洪峰日下单cohort的退货率%
       SUM(CASE WHEN s.main_reason = '七天无理由' THEN s.return_cnt ELSE 0 END) AS no_reason_cnt, -- 无理由退货量
       SUM(CASE WHEN s.main_reason = '尺码'      THEN s.return_cnt ELSE 0 END) AS size_cnt,       -- 尺码退货量
       SUM(CASE WHEN s.main_reason = '质量'      THEN s.return_cnt ELSE 0 END) AS quality_cnt,    -- 质量退货量
       COUNT(DISTINCT s.city)                         AS peak_cities        -- 洪峰涉及城市数
FROM peaks p
JOIN sale_returns_di s                                -- 回到城市×日明细拆洪峰构成
  ON s.stat_date = p.stat_date
GROUP BY p.stat_date, p.return_cnt, p.z, p.return_rate
ORDER BY p.stat_date;
```

结果解读：洪峰日若"七天无理由"占六成，说明是冲动消费退回而非质量问题，运营策略应是预售定金筛选与详情页优化；若"质量"占比抬头则是选品事故，两类洪峰的处置完全不同。**【避坑指南】** 自连接基线把"前30天"写成区间条件即可灵活排除大促周（加 `AND b.stat_date NOT IN (促销日列表)`），这是窗口法做不到的弹性——面试中能对比说明两种基线的适用场景是加分项。

### 5. 性能分析与优化

解法一一次日聚合加一次滚动窗口（30行窗口），日粒度数据只有75行，代价可忽略；解法二自连接为每行匹配30天×城市明细（不是日聚合），连接代价约30N，城市×日粒度万行级也无压力，但若从运单明细直接算则必须先预聚合。优化建议：①sale_returns_di按stat_date分区，窗口与自连接都能分区裁剪；②STDDEV_SAMP在窗口中与AVG共享同一窗口定义，一次排序完成；③"退货归因回下单日"的映射表（return→order_date）若需从退货表实时推导，先在数仓层固化为cohort归因日表；④洪峰阈值(2σ)与基线长度(30天)参数化进配置表，避免SQL硬编码。

> Hive/Spark SQL差异：STDDEV_SAMP窗口Hive可用stddev_samp；INTERVAL 30 DAY在Hive老版本用 date_sub(t.stat_date, 30)；自连接在Hive会shuffle两次同表，建议先把daily物化成临时表再连接；Spark下直接运行，结果建议输出到看板做"洪峰检测水位图"。

### 6. 面试延伸考点

- **退货率按"下单日cohort"还是"退货日"算？差别是什么？** 回答要点：cohort口径把退货归属回下单日，能回答"某天卖出去的货最终退了多少"，适合衡量促销质量；退货日口径反映逆向处理负荷，适合排班；两者回答不同问题，混用是典型事故。
- **为什么基线窗口要排除大促日本身？** 回答要点：大促日抬升均值与σ，让随后的真实洪峰落在"均值+2σ"之内被漏检（自我污染）；应取促销前常态期，或用迭代法剔除已标洪峰日重算基线。
- **2σ阈值在退货量不服从正态分布（右偏长尾）时可靠吗？** 回答要点：不完全可靠，右偏分布下可用中位数+MAD（绝对中位差）替代均值+σ，或直接用同期分位数（如超过去90分位）判峰，考察对统计假设的敏感度。
- **如何把洪峰检测从"事后"变"事前"？** 回答要点：用下单cohort量×历史退货时滞分布（下单后第N天退货占比）提前预测未来1-2周的逆向入库曲线，把排班决策从洪峰当日提前到一周前，考察从检测到预测的升级思路。

### 7. 业务拓展思考

退货率与洪峰分析反哺三个环节：大促复盘的"真实GMV"（GMV×(1−退货率)）与选品质量评估、逆向处理区的分周人力与场地预案、营销策略修正（七天无理由占比高提示冲动消费设计过度）。口径可延展为按品类/价格带的分层退货率（服饰与3C的洪峰时滞完全不同）、把退货率分解到"尺码推荐准确率"等产品因子，以及与逆向成本（运费损失、二次包装）联动输出金额口径的洪峰；与WL-34的运能测算框架复用，还能把逆向洪峰纳入大促整体产能规划，避免"正向备足了、逆向被冲垮"。
