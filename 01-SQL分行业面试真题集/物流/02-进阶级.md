## WL-16 一张扫描事件表拆解快件全链路时效

### 1. 业务背景

物流运营分析岗每天都要回答"这票件到底慢在哪一段"。分拨中心运营经理（谁）在大促复盘会上（何时），需要把每票快件从揽收、干线上车、到达目的分拨、末端开始派送到签收，逐段拆出耗时（什么），用来判断瓶颈在始发网点滞留、干线在途还是末端派送，进而决定给哪个环节加车、加人或者调整班次计划（为什么）。**全链路时效拆解是物流数据分析最底层的"读懂一张运单"的能力**，几乎所有时效类KPI都由它衍生。

### 2. 表结构说明

**表1：waybills（运单主表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| waybill_no | VARCHAR(20) | 运单号，主键 |
| order_type | VARCHAR(10) | 单类型：正向 / 退货 |
| origin_site | VARCHAR(20) | 始发网点/仓库编码 |
| dest_city | VARCHAR(20) | 目的城市 |
| create_time | DATETIME | 下单时间 |

示例数据：

| waybill_no | order_type | origin_site | dest_city | create_time |
|---|---|---|---|---|
| WB2026100001 | 正向 | WH001 | 杭州 | 2026-10-20 08:12:00 |
| WB2026100002 | 正向 | WH001 | 杭州 | 2026-10-20 09:30:00 |
| WB2026100003 | 正向 | WH002 | 南京 | 2026-10-20 10:05:00 |
| WB2026100004 | 退货 | WH001 | 苏州 | 2026-10-20 11:40:00 |
| WB2026100005 | 正向 | WH003 | 上海 | 2026-10-20 13:22:00 |

**表2：scan_events（扫描事件表）**，scan_type取值：PICKUP揽收 / LINE_HAUL_OUT干线上车 / ARRIVAL_DEST到达目的分拨 / DELIVERING开始派送 / SIGNED签收

| 字段名 | 类型 | 含义 |
|---|---|---|
| event_id | BIGINT | 事件ID，自增主键 |
| waybill_no | VARCHAR(20) | 运单号 |
| scan_type | VARCHAR(20) | 扫描环节类型 |
| scan_time | DATETIME | 扫描时间 |
| site_id | VARCHAR(20) | 扫描场地编码 |

示例数据：

| event_id | waybill_no | scan_type | scan_time | site_id |
|---|---|---|---|---|
| 1001 | WB2026100001 | PICKUP | 2026-10-20 09:00:00 | ST001 |
| 1002 | WB2026100001 | LINE_HAUL_OUT | 2026-10-20 14:30:00 | WH001 |
| 1003 | WB2026100001 | ARRIVAL_DEST | 2026-10-21 03:10:00 | WH009 |
| 1004 | WB2026100001 | DELIVERING | 2026-10-21 08:40:00 | ST301 |
| 1005 | WB2026100001 | SIGNED | 2026-10-21 10:05:00 | ST301 |

### 3. 解题思路

**【避坑指南】** 动手前先定口径：全链路时效 = 签收时间 − 揽收时间；四个分段 = 揽收→干线上车、干线上车→到达分拨、到达分拨→开始派送、开始派送→签收。统计边界只取"正向单且五个节点齐全、已签收"的票，在途票混入会拉偏分布。同一环节多次扫描（重复扫描、补录）取最早一次，因为首次到达才代表真实节点时刻；事件乱序时必须以 scan_time 排序，绝不能依赖 event_id 写入顺序。实现路径：解法一用条件聚合把多行事件压成一行宽表再逐段相减；解法二先用 ROW_NUMBER 去重，再用 LEAD 窗口在长表上逐行计算相邻扫描间隔。易错点：MIN(CASE...) 若写成 MAX 会取到补录时间；缺节点的票相减结果为 NULL，要在 WHERE 或口径说明里交代。

### 4. 参考解法

**解法一：条件聚合透视成宽表（一单一行，报表友好）**

```sql
WITH node_time AS (          -- 第一步：把每个运单散落多行的扫描事件压成一行"节点宽表"
    SELECT
        w.waybill_no,                                                         -- 运单号
        w.dest_city,                                                          -- 目的地，便于后续按城市下钻
        MIN(CASE WHEN e.scan_type = 'PICKUP'        THEN e.scan_time END) AS pickup_time,      -- 揽收时间：MIN取最早一次扫描
        MIN(CASE WHEN e.scan_type = 'LINE_HAUL_OUT' THEN e.scan_time END) AS linehaul_time,   -- 干线上车时间
        MIN(CASE WHEN e.scan_type = 'ARRIVAL_DEST'  THEN e.scan_time END) AS arrive_dest_time, -- 到达目的分拨时间
        MIN(CASE WHEN e.scan_type = 'DELIVERING'    THEN e.scan_time END) AS delivering_time,  -- 末端开始派送时间
        MIN(CASE WHEN e.scan_type = 'SIGNED'        THEN e.scan_time END) AS signed_time       -- 签收时间
    FROM waybills w                                                           -- 以运单为主表，缺扫描的票也保留
    JOIN scan_events e ON e.waybill_no = w.waybill_no                         -- 关联扫描事件明细
    WHERE w.order_type = '正向'                                               -- 口径边界：退货件走逆向时效口径，不混入
    GROUP BY w.waybill_no, w.dest_city                                        -- 按运单聚合出一行
)
SELECT
    waybill_no,                                                               -- 运单号
    dest_city,                                                                -- 目的地
    ROUND(TIMESTAMPDIFF(MINUTE, pickup_time,     linehaul_time)    /60.0, 1) AS h1_揽收到上车,  -- 段1：揽收后场地滞留时长
    ROUND(TIMESTAMPDIFF(MINUTE, linehaul_time,   arrive_dest_time) /60.0, 1) AS h2_干线在途,    -- 段2：干线运输时长
    ROUND(TIMESTAMPDIFF(MINUTE, arrive_dest_time, delivering_time) /60.0, 1) AS h3_分拨到派送,  -- 段3：目的分拨处理+末端分派
    ROUND(TIMESTAMPDIFF(MINUTE, delivering_time,  signed_time)     /60.0, 1) AS h4_派送到签收,  -- 段4：末端配送时长
    ROUND(TIMESTAMPDIFF(MINUTE, pickup_time,      signed_time)     /60.0, 1) AS h_全链路        -- 全链路：签收减揽收
FROM node_time
WHERE signed_time IS NOT NULL                                                 -- 只统计已签收票，在途票全链路无意义
  AND pickup_time IS NOT NULL                                                 -- 揽收缺失则起点不明，剔除并单独排查
  AND linehaul_time IS NOT NULL                                               -- 四段齐全才输出，避免NULL参与计算
  AND arrive_dest_time IS NOT NULL
  AND delivering_time IS NOT NULL;
```

结果解读：每一行是一票件的完整时效画像，四段之和等于全链路；对 h1、h2、h3、h4 分别求均值即可回答"慢在干线还是末端"，是分拨经理排班决策的直接依据。

**解法二：ROW_NUMBER去重 + LEAD窗口算逐段间隔（保留明细行，可下钻）**

```sql
WITH dedup AS (              -- 第一步：同单同环节可能重复扫描，先按时间取最早一次
    SELECT
        waybill_no, scan_type, scan_time,                                    -- 基础字段
        ROW_NUMBER() OVER (PARTITION BY waybill_no, scan_type                -- 同一运单、同一环节内部
                           ORDER BY scan_time ASC)              AS rn        -- 按时间升序编号，rn=1即最早首扫
    FROM scan_events
),
seq AS (                     -- 第二步：同单内按时间排序，LEAD取"下一跳"
    SELECT
        d.waybill_no,                                                        -- 运单号
        d.scan_type,                                                         -- 当前环节
        d.scan_time,                                                         -- 当前环节时间
        LEAD(d.scan_type) OVER (PARTITION BY d.waybill_no
                                ORDER BY d.scan_time)           AS next_type, -- 下一环节编码
        LEAD(d.scan_time) OVER (PARTITION BY d.waybill_no
                                ORDER BY d.scan_time)           AS next_time  -- 下一环节时间
    FROM dedup d
    WHERE d.rn = 1                                                           -- 只保留去重后的首扫记录
)
SELECT
    s.waybill_no,                                                            -- 运单号
    CASE s.scan_type                                                         -- 把环节编码翻译成业务段名
         WHEN 'PICKUP'        THEN '揽收-干线上车'
         WHEN 'LINE_HAUL_OUT' THEN '干线上车-到达分拨'
         WHEN 'ARRIVAL_DEST'  THEN '到达分拨-开始派送'
         WHEN 'DELIVERING'    THEN '开始派送-签收'
         ELSE '其他' END                                         AS 环节段,   -- 兜底防脏数据
    ROUND(TIMESTAMPDIFF(MINUTE, s.scan_time, s.next_time)/60.0, 1) AS 停留小时 -- 当前扫描到下一扫描的间隔即该段停留
FROM seq s
WHERE s.next_time IS NOT NULL                                                -- 无下一跳的行（签收）为终点，排除
  AND s.scan_type <> 'SIGNED';                                               -- 签收即终点，不构成段
```

结果解读：输出"一票多段"的长表，每行是某票在某段的停留分钟数，可直接对单票做异常定位；若要回到"一单一行"口径，再在外层套一次条件聚合即可。

> **Hive/Spark SQL 差异**：扫描事件表通常上亿行，生产上多用 Hive。Hive 无 TIMESTAMPDIFF，需用 `(unix_timestamp(next_time)-unix_timestamp(scan_time))/60.0`；窗口语法一致，但大表 JOIN 建议开启 mapjoin 并按 dt 分区裁剪。

### 5. 性能分析与优化

解法一是一次 GROUP BY 完成压缩，输出行数等于运单数，适合直接出报表；解法二先去重再开窗，窗口需按运单分区排序，在千万级事件表上排序代价更高，但保留明细行、能顺带发现"回退扫描"等脏数据。优化建议：① scan_events 建复合索引 `(waybill_no, scan_type, scan_time)`，或至少 `(waybill_no, scan_time)`，让去重和开窗走索引有序读；② 事件表按扫描日期 dt 分区，查询必须带分区过滤；③ 若固定产出日报，可先用 GROUP BY 把首扫结果落成中间宽表（节点时间已在行内），下游一律读宽表，避免每次对明细开窗；④ 回传一件货物重复扫描极多时，先按 `scan_time > '1970-01-01'` 与类型白名单过滤，减少参与开窗的行数。

### 6. 面试延伸考点

- **同一环节出现"回退扫描"（先派送又退回分拨重新派）怎么处理？** 要点：LEAD 按时间排序会把回退段也算成一段停留，报表口径上应识别"时间倒挂/环节回退"的行并打异常标记，主口径只保留正向推进序列（可用 ROW_NUMBER 对环节顺序编号后校验单调性）。
- **为什么节点时间取最早一次扫描而不是最新一次？** 要点：首次到达分拨代表货真正到了，补录、复扫往往滞后于实际操作；取最新会把内部处理时长错误地算进上一段。
- **全链路时效汇报用平均数还是中位数？** 要点：时效分布右偏、存在极慢件，平均值会被长尾拉高，业务上通常"均值看总量、中位数看体验"，汇报时两者并报并补充P90。
- **揽收时间用商家下单时间还是快递员揽收扫描时间？** 要点：看指标服务对象，考核快递员用揽收扫描，考核商家履约用下单时间，口径必须在需求阶段对齐。

### 7. 业务拓展思考

全链路拆解是所有时效产品的母指标：向上可以合成"次日达率""承诺时效达成率"，向下可以拆到城市、线路、网点、班次粒度。运营联动上，段1偏长说明揽收或场地交接拥堵，可加前置集货班次；段2偏长应调整干线发车计划或改走高铁/航空资源；段3、段4偏长则需要增加末端派送人手或推广驿站自提。口径延展上，还可以把"开始派送"细化为"出分拨"与"快递员领件"两个节点，进一步定位是分拨内部慢还是末端网点分派慢。

## WL-17 各环节超时率与瓶颈环节定位

### 1. 业务背景

时效质量岗的同学每月要做"全链路环节体检"。质量分析师（谁）在月度经营会上（何时），需要给出揽收-上车、干线运输、分拨-派送、派送-签收四个环节各自的超时率与平均耗时（什么），用来向管理层指认本月最大瓶颈环节、确定下月时效专项治理的投入方向（为什么）。**【面试高频】** 这道题的核心不是算数，而是"分母口径"：某环节的超时率只能以"真实经过该环节起点的票"为分母，用全体运单做分母会把瓶颈环节稀释掉。

### 2. 表结构说明

**表1：scan_events（扫描事件表）**，结构同WL-16（event_id / waybill_no / scan_type / scan_time / site_id），scan_type取值：PICKUP / LINE_HAUL_OUT / ARRIVAL_DEST / DELIVERING / SIGNED。

示例数据：

| event_id | waybill_no | scan_type | scan_time | site_id |
|---|---|---|---|---|
| 2001 | WB2026100011 | PICKUP | 2026-10-21 09:00:00 | ST010 |
| 2002 | WB2026100011 | LINE_HAUL_OUT | 2026-10-21 12:00:00 | WH001 |
| 2003 | WB2026100011 | ARRIVAL_DEST | 2026-10-22 02:00:00 | WH009 |
| 2004 | WB2026100011 | DELIVERING | 2026-10-22 09:00:00 | ST310 |
| 2005 | WB2026100011 | SIGNED | 2026-10-22 18:30:00 | ST310 |

**表2：sla_standard（环节时效标准表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| stage_name | VARCHAR(30) | 环节段名，与统计口径一致 |
| std_hours | DECIMAL(5,1) | 该环节标准时效（小时），超过即算超时 |

示例数据：

| stage_name | std_hours |
|---|---|
| 揽收-上车 | 6.0 |
| 干线运输 | 14.0 |
| 分拨-派送 | 8.0 |
| 派送-签收 | 5.0 |
| 出库-揽收 | 4.0 |

### 3. 解题思路

分三步走：第一步复用WL-16的条件聚合，把事件压成节点宽表并逐段算出耗时；第二步把宽表"逆透视"成（运单、环节、耗时）长表，与 sla_standard 按环节挂上标准小时，逐行打上超时标记 1/0；第三步按环节 GROUP BY，用 AVG(超时标记) 得到超时率，再用 RANK() 找出超时率最高的瓶颈环节。**【避坑指南】** 两个易错点：一是解法二的透视写法里，起止时间任一缺失时 IF 判断必须显式返回 NULL，否则 CASE 比较遇到 NULL 会走 ELSE 0，把缺数据票错误计成"未超时"撑大分母；二是瓶颈判定除超时率外还应看平均耗时与标准值的差值，防止低基数环节（票量极少）超时率虚高误判。

### 4. 参考解法

**解法一：宽表拆长表 + 超时率聚合 + RANK定位瓶颈（可扩展、易维护）**

```sql
WITH node_time AS (          -- 第一步：压宽表（与WL-16解法一相同）
    SELECT
        waybill_no,
        MIN(CASE WHEN scan_type = 'PICKUP'        THEN scan_time END) AS pickup_time,       -- 揽收
        MIN(CASE WHEN scan_type = 'LINE_HAUL_OUT' THEN scan_time END) AS linehaul_time,    -- 干线上车
        MIN(CASE WHEN scan_type = 'ARRIVAL_DEST'  THEN scan_time END) AS arrive_dest_time, -- 到达分拨
        MIN(CASE WHEN scan_type = 'DELIVERING'    THEN scan_time END) AS delivering_time,  -- 开始派送
        MIN(CASE WHEN scan_type = 'SIGNED'        THEN scan_time END) AS signed_time       -- 签收
    FROM scan_events
    WHERE scan_time >= '2026-10-01' AND scan_time < '2026-11-01'               -- 统计月，兼做分区裁剪
    GROUP BY waybill_no
),
stage_long AS (              -- 第二步：宽表拆成"运单-环节-耗时"长表，UNION ALL四个分支
    SELECT waybill_no, '揽收-上车' AS stage,
           TIMESTAMPDIFF(MINUTE, pickup_time,   linehaul_time)   /60.0 AS cost_h
    FROM node_time WHERE pickup_time    IS NOT NULL AND linehaul_time    IS NOT NULL  -- 起止齐全才计入该段
    UNION ALL
    SELECT waybill_no, '干线运输',
           TIMESTAMPDIFF(MINUTE, linehaul_time,   arrive_dest_time)/60.0
    FROM node_time WHERE linehaul_time   IS NOT NULL AND arrive_dest_time IS NOT NULL
    UNION ALL
    SELECT waybill_no, '分拨-派送',
           TIMESTAMPDIFF(MINUTE, arrive_dest_time, delivering_time)/60.0
    FROM node_time WHERE arrive_dest_time IS NOT NULL AND delivering_time  IS NOT NULL
    UNION ALL
    SELECT waybill_no, '派送-签收',
           TIMESTAMPDIFF(MINUTE, delivering_time, signed_time)/60.0
    FROM node_time WHERE delivering_time  IS NOT NULL AND signed_time      IS NOT NULL
),
judge AS (                   -- 第三步：挂标准、打超时标记
    SELECT l.waybill_no, l.stage, l.cost_h,
           CASE WHEN l.cost_h > s.std_hours THEN 1 ELSE 0 END AS is_over      -- 超时=1，正常=0
    FROM stage_long l
    JOIN sla_standard s ON s.stage_name = l.stage                             -- 按环节名关联标准时效
)
SELECT
    stage,                                    -- 环节名
    COUNT(*)                    AS 应到票数,   -- 分母=真实经过该段的票数
    SUM(is_over)                AS 超时票数,   -- 分子=超时标记求和
    ROUND(AVG(is_over) * 100, 2) AS 超时率_pct, -- 0/1变量的AVG即超时率
    ROUND(AVG(cost_h), 1)       AS 平均耗时_h,  -- 平均耗时辅助判断
    RANK() OVER (ORDER BY AVG(is_over) DESC) AS 瓶颈排名  -- 超时率最高者排第1
FROM judge
GROUP BY stage;
```

结果解读：瓶颈排名=1 的环节即本月治理重点；若其平均耗时高出标准值很多而票量不大，还要回看是否个别线路拖累，属"结构性瓶颈"而非"普遍性瓶颈"。

**解法二：条件聚合透视（一段一列，一眼对比四段超时率）**

```sql
WITH node_time AS (          -- 同样先压宽表
    SELECT
        waybill_no,
        MIN(CASE WHEN scan_type = 'PICKUP'        THEN scan_time END) AS pickup_time,
        MIN(CASE WHEN scan_type = 'LINE_HAUL_OUT' THEN scan_time END) AS linehaul_time,
        MIN(CASE WHEN scan_type = 'ARRIVAL_DEST'  THEN scan_time END) AS arrive_dest_time,
        MIN(CASE WHEN scan_type = 'DELIVERING'    THEN scan_time END) AS delivering_time,
        MIN(CASE WHEN scan_type = 'SIGNED'        THEN scan_time END) AS signed_time
    FROM scan_events
    WHERE scan_time >= '2026-10-01' AND scan_time < '2026-11-01'
    GROUP BY waybill_no
),
judge AS (                   -- 在宽表上逐段判超时：任一起止点缺失必须显式给NULL
    SELECT
        n.*,
        IF(pickup_time IS NOT NULL AND linehaul_time IS NOT NULL,             -- 分母口径保护：
           TIMESTAMPDIFF(MINUTE, pickup_time, linehaul_time)/60.0
             > (SELECT std_hours FROM sla_standard WHERE stage_name = '揽收-上车'),
           NULL)                                                 AS over1,    -- 缺数据票不计入该段分子分母
        IF(linehaul_time IS NOT NULL AND arrive_dest_time IS NOT NULL,
           TIMESTAMPDIFF(MINUTE, linehaul_time, arrive_dest_time)/60.0
             > (SELECT std_hours FROM sla_standard WHERE stage_name = '干线运输'),
           NULL)                                                 AS over2,
        IF(arrive_dest_time IS NOT NULL AND delivering_time IS NOT NULL,
           TIMESTAMPDIFF(MINUTE, arrive_dest_time, delivering_time)/60.0
             > (SELECT std_hours FROM sla_standard WHERE stage_name = '分拨-派送'),
           NULL)                                                 AS over3,
        IF(delivering_time IS NOT NULL AND signed_time IS NOT NULL,
           TIMESTAMPDIFF(MINUTE, delivering_time, signed_time)/60.0
             > (SELECT std_hours FROM sla_standard WHERE stage_name = '派送-签收'),
           NULL)                                                 AS over4
    FROM node_time n
)
SELECT
    COUNT(over1)                    AS 段1_应到票数,   -- COUNT忽略NULL，天然实现"齐全才计数"
    ROUND(AVG(over1) * 100, 2)      AS 段1_超时率,     -- AVG同样忽略NULL
    COUNT(over2)                    AS 段2_应到票数,
    ROUND(AVG(over2) * 100, 2)      AS 段2_超时率,
    COUNT(over3)                    AS 段3_应到票数,
    ROUND(AVG(over3) * 100, 2)      AS 段3_超时率,
    COUNT(over4)                    AS 段4_应到票数,
    ROUND(AVG(over4) * 100, 2)      AS 段4_超时率
FROM judge;
```

结果解读：一行四组"票数+超时率"横向铺开，汇报时直观对比哪段最红；短板是段数增多时列爆炸，且找"第1名瓶颈"还得靠人工读表或再套一层行转列。

### 5. 性能分析与优化

解法一的 UNION ALL 长表会让 node_time 结果被"逻辑复制"四份，行数放大约4倍，但结构清晰、加环节只加一个分支；解法二对宽表只扫一遍，输出极小，代价是每列内嵌一次 sla_standard 相关子查询（MySQL 会缓存为常量，代价可接受），列数随环节线性膨胀。优化建议：① scan_events 上按 `(scan_type, waybill_no)` 或 `(waybill_no, scan_time)` 建索引，并对统计月做分区裁剪；② 节点宽表是高频复用中间层，建议落成日增量的 dws 表（每票每日一行节点时间），后续所有时效报表只读宽表；③ 若环节多、标准值常变，把 sla_standard 前置 JOIN 到长表而不是每列子查询；④ MySQL 8.0.18+ 可用 `EXPLAIN ANALYZE` 实测两版本耗时差异后再定稿。

### 6. 面试延伸考点

- **不同体量的环节能直接比超时率吗？** 要点：低票量环节超时率方差大，应同时给出票数，或用"超时率置信区间/加权得分（超时率×票量权重）"兜底，防止小环节误判为瓶颈。
- **标准时效该分线路设还是全网统一？** 要点：干线时长天然受里程影响，统一标准会让远程线路"永远超时"，正确做法是标准表按线路/里程档分别维护，SQL里 JOIN 键相应改为 stage+line_id。
- **如果要按周输出瓶颈趋势，SQL怎么改？** 要点：在最终 GROUP BY 前增加 `DATE_FORMAT(签收时间,'%x-W%v')` 维度，窗口 RANK 改为 `RANK() OVER (PARTITION BY 周 ORDER BY 超时率 DESC)`，看瓶颈是否在不同周之间轮动。

### 7. 业务拓展思考

超时率定位产出的是"治理优先级"：瓶颈是揽收段就推预约揽收和前置集单，是干线段就优化发车班次与路由合并，是末端段就加驿站柜机提高单点派送能力。口径延展上，可以把超时率细分为"轻度超时（1.5倍标准内）"与"严重超时"，治理动作完全不同；也可以把 SLA 标准做成随大促/雨雪天气动态调整的维度表，让"超时"更贴近可达成承诺，避免考核失真。长期看，环节体检表可以固化成质量看板，替代人工月度取数。

## WL-18 分线路×区域妥投率与行转列汇总

### 1. 业务背景

线路运营岗每季度要评估哪些线路、哪些目的省份的末端交付质量最差。线路规划分析师（谁）在制定季度线路优化方案时（何时），需要按"线路×目的省份"两个维度算出妥投率（什么），用来决定哪些线路要收缩改配外包、哪些省份的末端要增开合作驿站（为什么）。妥投率 = 已签收票 / 应妥投票，看似简单，但分母口径（在途、拒收、异常退回算不算）必须先讲清楚，这也是面试官最爱追问的地方。

### 2. 表结构说明

**表1：routes（线路主表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| line_id | VARCHAR(20) | 线路编码，主键 |
| line_name | VARCHAR(50) | 线路名称 |
| origin_city | VARCHAR(20) | 发货城市 |
| dest_city | VARCHAR(20) | 到达城市 |

示例数据：

| line_id | line_name | origin_city | dest_city |
|---|---|---|---|
| L001 | 华东一线 | 上海 | 杭州 |
| L002 | 华东二线 | 上海 | 南京 |
| L003 | 华南一线 | 广州 | 深圳 |
| L004 | 华北一线 | 北京 | 天津 |
| L005 | 西南一线 | 成都 | 重庆 |

**表2：waybills（运单表，含投递结果状态）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| waybill_no | VARCHAR(20) | 运单号，主键 |
| line_id | VARCHAR(20) | 承运线路编码 |
| dest_province | VARCHAR(20) | 目的省份 |
| bill_status | VARCHAR(10) | 终态：妥投 / 拒收 / 异常退回 / 在途 |
| create_time | DATETIME | 下单时间 |

示例数据：

| waybill_no | line_id | dest_province | bill_status | create_time |
|---|---|---|---|---|
| WB2026100021 | L001 | 浙江 | 妥投 | 2026-10-05 09:00:00 |
| WB2026100022 | L001 | 浙江 | 拒收 | 2026-10-05 10:10:00 |
| WB2026100023 | L001 | 江苏 | 妥投 | 2026-10-05 11:20:00 |
| WB2026100024 | L002 | 江苏 | 异常退回 | 2026-10-05 14:00:00 |
| WB2026100025 | L002 | 安徽 | 在途 | 2026-10-20 16:30:00 |

### 3. 解题思路

先定口径：应妥投票 = 终态为妥投、拒收、异常退回的票（在途票未到考核时点，剔除）；分子 = 终态为妥投的票。粒度是"线路×省份"，先 JOIN routes 拿线路名，GROUP BY line_id, dest_province 用 AVG(状态标记) 算妥投率；解法一在外层再套一层条件聚合，把省份转成列（行转列），得到"一行一线路、一列一省份"的汇总矩阵，方便汇报；解法二用 WITH ROLLUP + GROUPING() 输出线路小计与总计的层级汇总。**【避坑指南】** 行转列时省份必须枚举在 CASE 里，新省份上线要同步改SQL，这是维护成本；而 ROLLUP 的合计行上"比率不能直接再平均"，要用分子总和/分母总和重新计算，否则小省份会把大线路的率带偏。

### 4. 参考解法

**解法一：条件聚合行转列（一行一线路，省份成列）**

```sql
WITH rate AS (               -- 第一步：算出每条线路每个省份的妥投率
    SELECT
        r.line_name,                                                          -- 线路名
        w.dest_province,                                                      -- 目的省份
        ROUND(
            AVG(CASE WHEN w.bill_status = '妥投' THEN 1.0 ELSE 0.0 END) * 100
            , 2)                                                  AS 妥投率_pct -- 妥投标记的均值即妥投率
    FROM waybills w
    JOIN routes r ON r.line_id = w.line_id                                    -- 挂线路名称
    WHERE w.create_time >= '2026-10-01' AND w.create_time < '2026-11-01'      -- 统计月
      AND w.bill_status <> '在途'                                             -- 分母口径：剔除未到考核点的在途票
    GROUP BY r.line_name, w.dest_province                                     -- 线路×省份粒度
)
SELECT
    line_name                                            AS 线路,             -- 行维度
    ROUND(MAX(CASE WHEN dest_province = '浙江' THEN 妥投率_pct END), 2) AS 浙江, -- 行转列：浙江列
    ROUND(MAX(CASE WHEN dest_province = '江苏' THEN 妥投率_pct END), 2) AS 江苏, -- 江苏列
    ROUND(MAX(CASE WHEN dest_province = '安徽' THEN 妥投率_pct END), 2) AS 安徽, -- 安徽列
    ROUND(MAX(CASE WHEN dest_province = '广东' THEN 妥投率_pct END), 2) AS 广东, -- 广东列
    ROUND(AVG(妥投率_pct), 2)                            AS 省份均值_仅参考    -- 注意：比率均值仅作速览
FROM rate
GROUP BY line_name;
```

结果解读：矩阵里单元格越低说明该线路在该省交付越差；"省份均值"列只是简单平均，正式汇报应以票量加权的总妥投率为准（见解法二思路）。

**解法二：WITH ROLLUP + GROUPING 层级汇总（自动出小计与总计）**

```sql
SELECT
    IF(GROUPING(r.line_name) = 0, r.line_name, '全部线路')        AS 线路,      -- GROUPING=1表示该列被ROLLUP聚合
    IF(GROUPING(w.dest_province) = 0 AND GROUPING(r.line_name) = 0,
       w.dest_province, '小计/总计')                              AS 省份,      -- 区分省份明细与汇总行
    SUM(CASE WHEN w.bill_status = '妥投' THEN 1 ELSE 0 END)       AS 妥投票数,   -- 分子
    SUM(CASE WHEN w.bill_status <> '在途' THEN 1 ELSE 0 END)      AS 应妥投票数, -- 分母
    ROUND(
        SUM(CASE WHEN w.bill_status = '妥投' THEN 1 ELSE 0 END) * 100.0
        / NULLIF(SUM(CASE WHEN w.bill_status <> '在途' THEN 1 ELSE 0 END), 0)
    , 2)                                                          AS 妥投率_pct -- 汇总行也是"先加总再相除"，口径正确
FROM waybills w
JOIN routes r ON r.line_id = w.line_id
WHERE w.create_time >= '2026-10-01' AND w.create_time < '2026-11-01'
GROUP BY r.line_name, w.dest_province WITH ROLLUP                            -- 生成线路小计与全网总计行
HAVING NOT (GROUPING(r.line_name) = 1 AND GROUPING(w.dest_province) = 0);    -- 剔除"全部线路+具体省份"的无意义组合行
```

结果解读：结果自带"线路小计"与"全网总计"，且每一层的妥投率都是分子/分母重新相除，天然实现票量加权；面试中能主动说出 GROUPING() 用于区分汇总行，是明确加分项。

### 5. 性能分析与优化

解法一两段聚合，内层输出行数=线路×省份数（很小），外层再聚合一次，整体代价集中在 waybills 按月的过滤扫描，需 `(create_time, line_id, bill_status)` 或按月分区索引支撑；解法二 ROLLUP 在 GROUP BY 基础上额外做少量聚合，代价略增但省掉一次报表端拼装。优化建议：① 运单表按 create_time 月分区，查询必须携带时间边界；② 终态字段建议冗余到运单宽表并建索引，避免回扫事件表；③ 若省份列经常变化，可在 BI 层做动态行转列，SQL 只输出长表（线路、省份、妥投率）三列；④ 大表上避免 `bill_status <> '在途'` 这类不等于条件走在索引最左侧，可改写为 `bill_status IN ('妥投','拒收','异常退回')` 以便走索引。

### 6. 面试延伸考点

- **在途票什么时候进入妥投率分母？** 要点：按承诺时效到期日"截账"，到期仍未签收视为逾期未妥投进入分母，SQL里通常用日历表按截止日重算，而不是简单剔除。
- **拒收后客户改址重投最终签收，算妥投吗？** 要点：考核末端交付算妥投，考核商品退货率则要看拒收事件，正确做法是保留"首投结果"与"终态结果"两个字段分别统计。
- **为什么不能用 AVG(各省份妥投率) 当线路妥投率？** 要点：比率的无权平均违背加权逻辑，广东10万票与安徽1千票权重完全不同，必须用 SUM(妥投)/SUM(应妥投) 重算。
- **若要求同时看"线路"与"目的分拨"两个维度的同口径妥投率，SQL如何组织？** 要点：分别聚合两个维度的分子分母，再 UNION ALL 成指标长表，或用两个独立查询避免维度混杂。

### 7. 业务拓展思考

妥投率矩阵直接驱动三类决策：线路层面淘汰或外包长期低妥投线路；省份层面针对差省份增加驿站、快递柜等"最后一百米"基础设施；时效层面把妥投率与WL-17的超时率交叉，识别"又慢又差"的复合问题线路。口径延展上，可以按签收次数拆"一次妥投率/二次妥投率"，一次妥投率才是末端作业质量的真指标；也可以把矩阵扩展为"线路×省份×商品类目"，服务大促前的运力预售决策。

## WL-19 仓库库存周转天数计算

### 1. 业务背景

仓配运营岗的核心资产问题：仓库里的货压了多久才能卖出去。仓储运营经理（谁）在月度库存健康度评审上（何时），需要每个仓库的库存周转天数——即"当前平均库存够支撑多少天的出库"（什么），用来判断哪些仓库积压需要清仓调拨、哪些仓库备货不足需要补货，并直接影响仓储成本与现金流占用（为什么）。周转天数 = 平均库存 ÷ 日均出库量，公式简单，但"平均库存"取期初期末均值还是逐日快照均值，是面试里的经典辨析点。

### 2. 表结构说明

**表1：inventory_daily（库存日快照表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| wh_id | VARCHAR(20) | 仓库编码 |
| sku_id | VARCHAR(20) | 商品SKU编码 |
| stat_date | DATE | 快照日期 |
| end_qty | INT | 当日日末库存件数 |

示例数据：

| wh_id | sku_id | stat_date | end_qty |
|---|---|---|---|
| WH001 | SKU1001 | 2026-10-01 | 1200 |
| WH001 | SKU1001 | 2026-10-02 | 1050 |
| WH001 | SKU1001 | 2026-10-03 | 980 |
| WH001 | SKU1002 | 2026-10-01 | 300 |
| WH001 | SKU1002 | 2026-10-03 | 150 |

**表2：outbound_records（出库流水表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| out_id | BIGINT | 出库单明细ID |
| wh_id | VARCHAR(20) | 仓库编码 |
| sku_id | VARCHAR(20) | SKU编码 |
| out_date | DATE | 出库日期 |
| out_qty | INT | 出库件数 |

示例数据：

| out_id | wh_id | sku_id | out_date | out_qty |
|---|---|---|---|---|
| 1 | WH001 | SKU1001 | 2026-10-02 | 150 |
| 2 | WH001 | SKU1001 | 2026-10-03 | 70 |
| 3 | WH001 | SKU1002 | 2026-10-02 | 80 |
| 4 | WH001 | SKU1002 | 2026-10-03 | 70 |
| 5 | WH002 | SKU2001 | 2026-10-02 | 200 |

### 3. 解题思路

先定口径：统计期为自然月（10-01至10-31），周转天数 = 期间平均库存 ÷ 期间日均出库件数，分子分母单位一致（件）。解法一用"期初期末法"：窗口函数 FIRST_VALUE/LAST_VALUE 按"仓库×SKU"分区取期首、期末快照再加总，平均库存=(期初+期末)/2，计算量小但对月中波动不敏感；解法二用"逐日快照法"：先把库存按仓库×日期加总，再 AVG 得到真实平均库存，同时输出"有快照天数与日期跨度"的断档体检（快照断档须先补数再求均值，否则平均值失真，见延伸考点）。**【避坑指南】** LAST_VALUE 默认窗口帧只到当前行，必须显式声明 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`，这是窗口函数最高频的翻车点；此外出库为0的日期会拉高周转天数，属真实业务信号不应剔除。

### 4. 参考解法

**解法一：期初期末法（FIRST_VALUE/LAST_VALUE 窗口）**

```sql
WITH stock_edge AS (         -- 第一步：窗口给每个"仓库×SKU"附上期首/期末库存
    SELECT
        wh_id, sku_id, stat_date, end_qty,                                  -- 基础字段
        FIRST_VALUE(stat_date) OVER w AS d_first,                            -- 该SKU期首快照日期
        FIRST_VALUE(end_qty)   OVER w AS qty_first,                          -- 该SKU期首日末库存
        LAST_VALUE(stat_date)  OVER w AS d_last,                             -- 期末快照日期
        LAST_VALUE(end_qty)    OVER w AS qty_last                            -- 该SKU期末日末库存
    FROM inventory_daily
    WHERE stat_date BETWEEN '2026-10-01' AND '2026-10-31'                    -- 统计月
    WINDOW w AS (PARTITION BY wh_id, sku_id                                  -- 每个"仓库×SKU"独立开窗
                 ORDER BY stat_date
                 ROWS BETWEEN UNBOUNDED PRECEDING                            -- 帧起点=分区第一行
                      AND UNBOUNDED FOLLOWING)                               -- 帧终点=分区最后一行，缺省帧会让LAST_VALUE取到当前行
),
sku_edge AS (                -- 第二步：SKU粒度去重，每个SKU只留一行期初/期末
    SELECT
        wh_id, sku_id,
        MAX(qty_first) AS begin_qty,                                         -- 期首值被窗口复制到该SKU每一行，MAX取其一
        MAX(qty_last)  AS end_qty,                                           -- 期末值同理
        MAX(d_first)   AS d_first,
        MAX(d_last)    AS d_last
    FROM stock_edge
    GROUP BY wh_id, sku_id
),
wh_inv AS (                  -- 第三步：加总到仓库粒度
    SELECT
        wh_id,
        SUM(begin_qty)                                     AS begin_inv,     -- 各SKU期初库存合计
        SUM(end_qty)                                       AS end_inv,       -- 各SKU期末库存合计
        DATEDIFF(MAX(d_last), MIN(d_first)) + 1            AS days_cnt       -- 统计期自然天数（最早期首~最晚期末）
    FROM sku_edge
    GROUP BY wh_id
),
wh_out AS (                  -- 第四步：期间出库总量
    SELECT wh_id, SUM(out_qty) AS total_out                                  -- 期间累计出库件数
    FROM outbound_records
    WHERE out_date BETWEEN '2026-10-01' AND '2026-10-31'
    GROUP BY wh_id
)
SELECT
    i.wh_id,                                                                  -- 仓库
    ROUND((i.begin_inv + i.end_inv) / 2.0, 0)          AS 平均库存_期初期末法, -- (期初+期末)/2
    ROUND(o.total_out * 1.0 / i.days_cnt, 1)           AS 日均出库,           -- 期间出库/天数
    ROUND(((i.begin_inv + i.end_inv) / 2.0)
          / NULLIF(o.total_out * 1.0 / i.days_cnt, 0), 1) AS 周转天数           -- 平均库存/日均出库，NULLIF防零出库除零
FROM wh_inv i
LEFT JOIN wh_out o ON o.wh_id = i.wh_id                                       -- LEFT JOIN保住零出库仓库
ORDER BY 周转天数 DESC;                                                        -- 周转越慢排越前，积压仓一目了然
```

结果解读：周转天数最大的仓库即积压重灾区；若某仓日均出库趋近0则周转天数会异常巨大，需单独备注"静置仓"。

**解法二：逐日快照均值法（断档体检 + 移动平均看趋势）**

```sql
WITH daily_inv AS (          -- 第一步：逐日逐仓库存合计（快照表无断档时可直接聚合）
    SELECT
        stat_date,                                                          -- 快照日期
        wh_id,                                                              -- 仓库
        SUM(end_qty)             AS inv_qty,                                -- 当日全SKU库存合计
        COUNT(DISTINCT sku_id)   AS sku_cnt                                 -- 当日有快照的SKU数，用于断档体检
    FROM inventory_daily
    WHERE stat_date BETWEEN '2026-10-01' AND '2026-10-31'
    GROUP BY stat_date, wh_id
),
daily_trend AS (             -- 第二步：窗口滑动帧算7日移动平均，并做断档体检
    SELECT
        stat_date, wh_id, inv_qty,
        ROUND(AVG(inv_qty) OVER (PARTITION BY wh_id ORDER BY stat_date
                                 ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 0) AS inv_ma7, -- 近7日移动平均库存
        COUNT(*)     OVER (PARTITION BY wh_id)                       AS snap_days,          -- 该仓有快照的天数
        DATEDIFF(MAX(stat_date) OVER (PARTITION BY wh_id),                                  -- 日期跨度
                 MIN(stat_date) OVER (PARTITION BY wh_id)) + 1       AS span_days
    FROM daily_inv
)
SELECT
    wh_id,                                                                    -- 仓库
    MAX(snap_days)                                  AS 有快照天数,
    MAX(span_days)                                  AS 日期跨度,               -- 有快照天数<日期跨度即存在断档，
                                                                              -- 须先按日历补数（补前值）再求均值
    ROUND(AVG(inv_qty), 0)                          AS 平均库存_逐日法,        -- 期间逐日平均库存，比期初期末法更真实
    ROUND(AVG(inv_ma7), 0)                          AS 平均7日移动库存,        -- 趋势平滑后的均值
    ROUND(MAX(inv_qty), 0)                          AS 峰值库存,               -- 期间最高点
    ROUND(MIN(inv_qty), 0)                          AS 谷值库存                -- 期间最低点
FROM daily_trend
GROUP BY wh_id;
```

结果解读：逐日法的平均库存反映月内真实水位，与解法一的期初期末法相除后对比，两者差异大说明库存月中波动剧烈（如大促前备货），此时应采用逐日法口径；"有快照天数<日期跨度"的仓库要先修复快照缺失，否则平均值系统性失真。

### 5. 性能分析与优化

解法一窗口函数在 `(wh_id, stat_date)` 排序上开销可控，且只读两个边界日附近数据即可（可先 WHERE 过滤出期首/期末两天再聚合，把窗口换成 GROUP BY MAX(CASE) 更快）；解法二需对全月快照逐日聚合，行数=仓库×SKU×天数，代价高一个量级，但趋势信息丰富。优化建议：① 快照表按 stat_date 分区并建 `(wh_id, sku_id, stat_date)` 索引；② 出库流水表大时先按仓库×日期聚合出 dws 日汇总表再参与计算；③ 日历表应为常驻维表而非每查询用序号展开，本题仅为演示；④ 若只关心 TopN 积压仓，外层套 `ORDER BY 周转天数 DESC LIMIT 10`，避免全量导出。

### 6. 面试延伸考点

- **期初期末法与逐日均值法什么时候会给出截然不同的结论？** 要点：月中库存先冲高后清空（大促备货）时差异巨大，前者被期末拉低、后者反映真实占用，对外披露资产口径常用期初期末法，内部运营用逐日法。
- **SKU维度周转天数和仓库维度怎么统一？** 要点：仓库=库存与出库均按仓库汇总后相除；SKU=按SKU汇总；切勿对"各SKU周转天数"求平均得到仓库周转天数。
- **出库口径用销售出库还是含调拨出库？** 要点：考核销售周转必须剔除调拨/报损，否则两个仓之间倒货会"虚增周转"，SQL里要在流水表加出库类型过滤。
- **为什么快照表断档要补0还是补前值？** 要点：业务上仓库没扫快照≠库存为0，正确做法是取最近一次快照值（窗口取 last non-null），补0会人为制造库存暴跌，这是数据质量检查重点。

### 7. 业务拓展思考

周转天数向上支撑补货模型（目标库存=日均出库×目标周转天数+安全库存），向下驱动清仓动作（超期SKU推送促销或仓间调拨）。口径延展上，可以用"库龄分布"（按入库批次算每批货躺了多少天）替代单一周转天数，更能定位"哪些批次压着"；与WL-14的发货等待时长、WL-28的装载率交叉，还能识别"周转快但发货慢"的仓内作业瓶颈。对管理层，建议同时输出周转天数与缺货率双指标，防止一味压库存导致断货。

## WL-20 分班次分拣效率对比（均值/中位数/四分位）

### 1. 业务背景

分拨中心的分拣作业分早、中、晚三个班次。分拨中心主管（谁）在排班优化会上（何时），需要对比各班次分拣员的人均分拣量（UPH口径），并希望看到中位数与四分位而不仅是平均值（什么），用来决定夜班是否需要增补人手、哪个班次的人员需要技能培训（为什么）。**【加分点】** 分拣量分布受"个人熟练度+当天件量结构"双重影响且右偏明显，只看平均会被个别快手拉高，中位数与四分位距才是排班与培训决策的可靠依据。

### 2. 表结构说明

### 3. 解题思路

先把扫描时间映射到班次：早班06:00-14:00、中班14:00-22:00、晚班22:00-次日06:00，用 CASE 表达式实现，注意跨零点的晚班归属。粒度先到"分拣员×班次"得到每人每班件量，再在班次内做分布统计。解法一求平均与精确中位数：中位数用 ROW_NUMBER 排序 + COUNT 窗口取中间一行（奇数）或中间两行均值（偶数）；解法二用 NTILE(4) 做四分位近似（P25/P50/P75），并对比 PERCENT_RANK。**【避坑指南】** 两个坑：一是 GROUP BY 中必须重复写班次 CASE 表达式（或用派生表先算好），直接引用别名在纯 MySQL GROUP BY 里会报错或依赖 only_full_group_by 语义；二是中位数算法在人数很少的班次上不稳定，要设最小样本量门槛。

### 4. 参考解法

**解法一：班次聚合 + ROW_NUMBER 精确中位数**

```sql
WITH sorter_shift AS (       -- 第一步：每个分拣员每个班次的分拣件量
    SELECT
        e.sorter_id,                                                          -- 分拣员工号
        CASE
            WHEN TIME(e.scan_time) >= '06:00' AND TIME(e.scan_time) < '14:00' THEN '早班'
            WHEN TIME(e.scan_time) >= '14:00' AND TIME(e.scan_time) < '22:00' THEN '中班'
            ELSE '晚班'                                                       -- 22:00~次日6:00整体归晚班（跨零点）
        END                                                   AS shift_name,  -- 班次名
        COUNT(*)                                              AS pkg_cnt      -- 该人该班分拣件数
    FROM scan_events e
    WHERE e.scan_type = 'SORT'                                                -- 只要分拣扫描
      AND e.scan_time >= '2026-10-20' AND e.scan_time < '2026-10-27'          -- 统计周
    GROUP BY e.sorter_id,
             CASE                                                             -- MySQL要求GROUP BY重复该表达式
                 WHEN TIME(e.scan_time) >= '06:00' AND TIME(e.scan_time) < '14:00' THEN '早班'
                 WHEN TIME(e.scan_time) >= '14:00' AND TIME(e.scan_time) < '22:00' THEN '中班'
                 ELSE '晚班' END
),
ranked AS (                  -- 第二步：班次内排名并附带人数与百分位
    SELECT
        s.sorter_id, s.shift_name, s.pkg_cnt,
        c.courier_name,                                                       -- 姓名
        c.hire_date,                                                          -- 入职日期，用于区分新老员工
        ROW_NUMBER()   OVER (PARTITION BY s.shift_name ORDER BY s.pkg_cnt) AS rn,   -- 班次内按件量升序的行号
        COUNT(*)       OVER (PARTITION BY s.shift_name)                    AS cnt,     -- 班次内分拣员人数
        PERCENT_RANK() OVER (PARTITION BY s.shift_name ORDER BY s.pkg_cnt) AS pct_r -- 百分位0~1
    FROM sorter_shift s
    LEFT JOIN couriers c ON c.courier_id = s.sorter_id                        -- 挂花名册
)
SELECT
    shift_name                                         AS 班次,                -- 班次
    MAX(cnt)                                           AS 分拣人数,            -- 人数（组内恒定）
    ROUND(AVG(pkg_cnt), 1)                             AS 人均件量,            -- 算术平均
    ROUND(AVG(CASE WHEN rn IN (CEIL(cnt / 2.0), FLOOR(cnt / 2.0) + 1)   -- 奇数取正中一行，偶数取中间两行
                   THEN pkg_cnt END), 1)               AS 中位数件量,          -- 精确中位数
    ROUND(MAX(pct_r), 2)                               AS 最高百分位           -- 校验用：应接近1
FROM ranked
GROUP BY shift_name
HAVING MAX(cnt) >= 5;                                                      -- 样本量门槛，人数过少班次不参与对比
```

结果解读：若晚班中位数明显低于早班而平均数接近，说明晚班存在少数快手掩盖了整体偏慢，排班应按中位数而非平均值做决策。

**解法二：NTILE(4) 四分位近似（一把输出P25/P50/P75）**

```sql
WITH sorter_shift AS (       -- 同解法一：先得到分拣员×班次件量
    SELECT
        e.sorter_id,
        CASE
            WHEN TIME(e.scan_time) >= '06:00' AND TIME(e.scan_time) < '14:00' THEN '早班'
            WHEN TIME(e.scan_time) >= '14:00' AND TIME(e.scan_time) < '22:00' THEN '中班'
            ELSE '晚班'
        END                                                    AS shift_name,
        COUNT(*)                                               AS pkg_cnt
    FROM scan_events e
    WHERE e.scan_type = 'SORT'
      AND e.scan_time >= '2026-10-20' AND e.scan_time < '2026-10-27'
    GROUP BY e.sorter_id,
             CASE WHEN TIME(e.scan_time) >= '06:00' AND TIME(e.scan_time) < '14:00' THEN '早班'
                  WHEN TIME(e.scan_time) >= '14:00' AND TIME(e.scan_time) < '22:00' THEN '中班'
                  ELSE '晚班' END
),
tiled AS (                   -- 班次内按件量切成4桶
    SELECT
        s.*,
        NTILE(4) OVER (PARTITION BY s.shift_name ORDER BY s.pkg_cnt) AS q     -- 1=最低25%，4=最高25%
    FROM sorter_shift s
)
SELECT
    shift_name                                       AS 班次,
    COUNT(*)                                         AS 人数,
    MAX(CASE WHEN q = 1 THEN pkg_cnt END)            AS p25_上限,            -- 第1桶最大值≈P25
    MAX(CASE WHEN q = 2 THEN pkg_cnt END)            AS p50_近似,            -- 第2桶最大值≈中位数
    MAX(CASE WHEN q = 3 THEN pkg_cnt END)            AS p75_上限,            -- 第3桶最大值≈P75
    MAX(CASE WHEN q = 4 THEN pkg_cnt END)            AS 最大件量,            -- 分布上沿
    MAX(CASE WHEN q = 4 THEN pkg_cnt END)
      - MAX(CASE WHEN q = 2 THEN pkg_cnt END)        AS 上半离散度           -- 近似衡量尾部拉伸程度
FROM tiled
GROUP BY shift_name;
```

结果解读：P75 与 P50 的差值反映班次内"优秀梯队"与中间层的差距，差值大的班次更应做师徒制培训，把尾部分拣员的能力拉上来。

> **Hive/Spark SQL 差异**：Hive 提供 `percentile_approx(pkg_cnt, ARRAY[0.25,0.5,0.75])` 一步到位，且大数据量下比 NTILE 更高效；NTILE 在 Hive 同样可用，但本质仍需全排序。

### 5. 性能分析与优化

两种解法都要先做一次"扫描事件→人×班次"的聚合，代价集中在事件表按时间范围过滤后按 sorter_id 分组；窗口层（ROW_NUMBER/NTILE）只作用于聚合后的小结果集（人数×班次），代价可忽略。优化建议：① scan_events 对 `(scan_type, scan_time)` 建复合索引，统计周期分区裁剪；② 若按人×日预聚合（每人每天每班件量）落 dws 表，周报只需对小表再聚合；③ 班次映射建议抽成 shift 维表 JOIN，而不是硬编码 CASE，跨年换班制时不用改SQL；④ 避免在 TIME() 函数结果上建索引（函数索引收益有限），以 scan_time 范围过滤先行缩数。

### 6. 面试延伸考点

- **为什么物流/电商场景偏爱中位数和分位数？** 要点：时效、件量、投诉处理时长都是右偏分布，平均数易被长尾绑架，中位数代表"典型员工/典型订单"体验，P90/P95用于服务承诺。
- **NTILE(4) 与 PERCENT_RANK 求四分位的差别？** 要点：NTILE 是桶切分（每桶人数尽量相等），桶边界是近似分位点；PERCENT_RANK 是值百分位，需再按目标百分位过滤，后者在小样本上更精确但写法更绕。
- **跨零点的晚班怎么归属才不丢数？** 要点：不能用 DATE(scan_time) 切天再简单映射，应该按"班次作业窗口"（22:00至次日06:00）判断，必要时把扫描时间平移4小时后取日期，保证一个班次的量统计在同一行。
- **新员工入职不满月，算进对比公平吗？** 要点：花名册 hire_date 可作为过滤维度，至少拆出"新员工单独看板"，或用同入职批次内排名替代全池排名。

### 7. 业务拓展思考

班次效率对比直接服务三件事：排班（件量波峰配人）、培训（尾部分拣员定向辅导）、设备投入（若人均件量到顶则上自动化分拣线）。口径延展上，可以把"件量"升级为"折合件量"（大件按体积折算成标准件），避免件型结构差异造成班次不公平；还可以按小时切片画分拨曲线，识别班次交接期的效率塌陷区。长期看，把分拣效率与错分率（质量指标）并排展示，防止只追产量牺牲质量。

**表2：trip_waybills（班次配载明细表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| trip_id | VARCHAR(20) | 班次ID |
| waybill_no | VARCHAR(20) | 运单号 |
| weight_kg | DECIMAL(10,2) | 该票计费重量（千克） |

示例数据：

| trip_id | waybill_no | weight_kg |

| T2026102201 | WB2026100041 | 520.50 |
| T2026102201 | WB2026100042 | 1330.00 |
| T2026102202 | WB2026100043 | 205.00 |
| T2026102203 | WB2026100044 | 880.00 |
| T2026102204 | WB2026100045 | 640.50 |

### 3. 解题思路

指标口径先定：班次装载率 = 班次实际载重（配载明细按班次求和）÷ 额定载重；线路级"总装载率" = SUM(实际) ÷ SUM(额定)，即按额定载重加权的口径；同时输出 AVG(班次装载率) 作对照列，用于暴露口径差异。实现路径：解法一两层聚合——先 CTE 按班次聚合出每班实际载重与装载率，再按线路二次聚合；解法二用相关子查询在班次行内直接算实际载重，再外层聚合，写法更贴近"逐班打分"的直觉。易错点：LEFT JOIN 配载表后空车班次的 SUM 为 NULL 要 COALESCE 成 0；装载率>100% 是超载要单独计数并核查计抛口径；计重与计抛（体积重）应说明采用哪种。

### 4. 参考解法

**解法一：两层CTE聚合（班次级→线路级，推荐口径）**

```sql
WITH trip_load AS (          -- 第一步：每个班次的实际载重与装载率
    SELECT
        t.trip_id,                                                            -- 班次ID
        t.line_id,                                                            -- 线路
        t.rated_load_kg,                                                      -- 额定载重
        COALESCE(SUM(tw.weight_kg), 0)                    AS actual_kg,       -- 配载合计，空车班次COALESCE为0
        ROUND(COALESCE(SUM(tw.weight_kg), 0) / t.rated_load_kg, 4) AS load_ratio -- 班次装载率
    FROM trips t
    LEFT JOIN trip_waybills tw ON tw.trip_id = t.trip_id                      -- LEFT JOIN：没配载的班次也算空车
    WHERE t.depart_time >= '2026-10-01' AND t.depart_time < '2026-11-01'      -- 统计月
    GROUP BY t.trip_id, t.line_id, t.rated_load_kg                            -- 班次粒度
)
SELECT
    line_id,                                                                  -- 线路
    COUNT(*)                                         AS 班次数,                -- 该月发车班次数量
    ROUND(SUM(actual_kg) / 1000.0, 1)                AS 总载重_吨,             -- 期间实际运输总量
    ROUND(SUM(rated_load_kg) / 1000.0, 1)            AS 总额定_吨,             -- 期间总运力供给
    ROUND(SUM(actual_kg) / SUM(rated_load_kg), 4)    AS 加权装载率,            -- 总装载/总额定：正确线路口径
    ROUND(AVG(load_ratio), 4)                        AS 简单平均装载率,        -- 班次装载率的无权平均：仅作对照
    SUM(CASE WHEN load_ratio > 1.0 THEN 1 ELSE 0 END) AS 超载班次数,          -- 装载率超100%的班次，需核查
    SUM(CASE WHEN load_ratio < 0.5 THEN 1 ELSE 0 END) AS 低载班次数            -- 不足半载的班次，合并候选
FROM trip_load
GROUP BY line_id
ORDER BY 加权装载率 ASC;                                                      -- 装载率最低的线路排前面，优先治理
```

结果解读：加权装载率低于简单平均的线路，说明低装载发生在"大额定车次"上，合并班次或换小车收益最大；超载班次数>0的线路要先查计抛口径再谈运力优化。

**解法二：相关子查询逐班打分（直觉式写法，作对照）**

```sql
SELECT
    t.line_id,                                                                -- 线路
    COUNT(*)                                        AS 班次数,
    ROUND(
        SUM((SELECT COALESCE(SUM(tw.weight_kg), 0)                            -- 相关子查询：逐班算实际载重
             FROM trip_waybills tw
             WHERE tw.trip_id = t.trip_id))
        / SUM(t.rated_load_kg), 4)                  AS 加权装载率,             -- 分子分母均为班次求和，口径正确
    ROUND(AVG(
        (SELECT COALESCE(SUM(tw.weight_kg), 0)
         FROM trip_waybills tw WHERE tw.trip_id = t.trip_id)
        / t.rated_load_kg), 4)                      AS 简单平均装载率,         -- 每班算比率再平均：暴露口径差异
    MAX((SELECT COALESCE(SUM(tw.weight_kg), 0)
         FROM trip_waybills tw WHERE tw.trip_id = t.trip_id)
        / t.rated_load_kg)                          AS 单班最高装载率          -- 排查超载上限
FROM trips t
WHERE t.depart_time >= '2026-10-01' AND t.depart_time < '2026-11-01'
GROUP BY t.line_id;
```

结果解读：两解法数值应完全一致；解法二把"班次打分"写在子查询里更直观，但对外层每一行都要回配载表聚合，是面试中讲执行计划的绝佳素材。

### 5. 性能分析与优化

解法一是一次 JOIN 后 GROUP BY 的标准两层聚合，trip_waybills 按 trip_id 聚合走索引 `(trip_id)` 时为毫秒级；解法二的相关子查询在 MySQL 8.0 中通常会被改写为等值 JOIN 聚合（优化器物化），但若配载表巨大且无 trip_id 索引则退化为逐班扫描。优化建议：① trip_waybills 必建 `(trip_id)` 索引，大表按发车月分区；② 班次级装载率适合落 dws 表（每班一行），线路级月报直接二次聚合；③ 装载率建议同时给"重量口径"与"体积口径"（额定方量），空抛货（轻抛货）会重量不满而体积满载，只看重量会误判运力浪费；④ 排序输出用 `ORDER BY ... LIMIT` 配合索引 `(line_id, depart_time)` 减少回表。

### 6. 面试延伸考点

- **为什么"比率的平均"和"平均的比率"会不一样？** 要点：AVG(班次装载率)给每个班次相同权重，100公斤的小班车与30吨的挂车话语权一样；SUM/SUM按额定载重加权，才是"总运力被利用了百分之几"，汇报默认用后者。
- **装载率应该按重量还是按体积算？** 要点：干线运力同时受载重与方量约束，重货看重量、轻抛货看体积，规范做法取两者中的"约束利用率"较大值，即 min(重量利用率, 体积利用率) 换算后的实际瓶颈利用率。
- **超载班次在SQL里怎么预警？** 要点：HAVING 或 CASE 标记 load_ratio>1.0 的班次清单，联动安全合规流程，不能只在汇总里给个数。
- **空驶班次（无配载）算进分母吗？** 要点：算，空驶是运力浪费的一部分，LEFT JOIN + COALESCE 保证空车班次以0参与加权，若剔除会美化装载率。

### 7. 业务拓展思考

装载率报表上线后可联动三类动作：线路合并（低载班次并入相邻时段）、车型调换（长期60%装载的17.5米线换9.6米）、外协比例调整（自营运力保干线主峰，波谷用外协）。口径延展上，可以扩展为"去程装载率+回程装载率"双指标识别对流线路，回程满载是干线盈利的关键；再与WL-17的干线段超时率交叉，能识别"装得满但跑得慢"的线路，区分运力紧张与运力过剩两种完全相反的治理方案。

## WL-22 异常件类型分布与处理时长

### 1. 业务背景

异常件（破损、丢失、延误、地址错误等）是客服与运营的日常主战场。客服运营主管（谁）在周度服务质量例会上（何时），需要各异常类型的件量分布、占比与平均处理时长，以及尚未解决的积压件数（什么），用来决定增派哪类异常的处理坐席、对高频异常类型发起源头治理专项（为什么）。**【面试高频】** 这题的核心考点是异常件"状态机"口径：未解决件的时长必须用统计截止时间截断（右删失），否则直接排除未结件会系统性低估处理时长。

### 2. 表结构说明

**表1：exceptions（异常件登记表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| exc_id | BIGINT | 异常记录ID，主键 |
| waybill_no | VARCHAR(20) | 运单号 |
| exc_type | VARCHAR(20) | 异常类型：破损/丢失/延误/地址错误/其他 |
| status | VARCHAR(10) | 状态：未处理/处理中/已解决 |
| report_time | DATETIME | 异常上报时间 |
| resolve_time | DATETIME | 解决时间，未解决为NULL |
| site_id | VARCHAR(20) | 责任场地 |

示例数据：

| exc_id | waybill_no | exc_type | status | report_time | resolve_time | site_id |
|---|---|---|---|---|---|---|
| 5001 | WB2026100051 | 延误 | 已解决 | 2026-10-22 08:30:00 | 2026-10-22 20:10:00 | ST310 |
| 5002 | WB2026100052 | 破损 | 处理中 | 2026-10-22 10:00:00 | NULL | WH009 |
| 5003 | WB2026100053 | 地址错误 | 已解决 | 2026-10-22 11:20:00 | 2026-10-23 09:00:00 | ST310 |
| 5004 | WB2026100054 | 丢失 | 未处理 | 2026-10-23 09:40:00 | NULL | WH001 |
| 5005 | WB2026100051 | 破损 | 已解决 | 2026-10-24 14:00:00 | 2026-10-24 18:30:00 | WH009 |

### 3. 解题思路

先明确两件事：一是"分布"指各异常类型的件数与占比，占比分母是统计期内全部异常件，用聚合窗口 `SUM(COUNT(*)) OVER ()` 实现；二是"处理时长"分两个口径——已结时长（仅已解决件，resolve_time-report_time）与含未结的截断时长（未解决件用统计截止时间兜底，体现真实积压）。同一运单可能多次上报不同类型异常（如先延误后破损），主口径按异常记录条数统计，去重口径按运单数另给一列。**【避坑指南】** 未结件参与平均时 COALESCE(resolve_time, 统计截止时间) 是关键一步；若题目问"闭环时长"，则只能取已解决件并说明样本偏差。

### 4. 参考解法

**解法一：类型分布 + 占比 + 状态透视（聚合窗口算占比）**

```sql
WITH dedup AS (              -- 第一步：同票重复上报去重，保留最新一条记录状态
    SELECT
        exc_id, waybill_no, exc_type, status, report_time, resolve_time, site_id,
        ROW_NUMBER() OVER (PARTITION BY waybill_no                            -- 同一运单的多次上报
                           ORDER BY report_time DESC)            AS rn         -- 取最新一条作当前状态
    FROM exceptions
    WHERE report_time >= '2026-10-01' AND report_time < '2026-11-01'          -- 统计月内上报的异常
)
SELECT
    exc_type                                                AS 异常类型,       -- 类型
    COUNT(*)                                                AS 异常件数,       -- 分母构成
    ROUND(COUNT(*) * 100.0
          / SUM(COUNT(*)) OVER (), 2)                       AS 占比_pct,       -- 聚合窗口：全表总数作分母
    SUM(CASE WHEN status = '已解决' THEN 1 ELSE 0 END)      AS 已解决,
    SUM(CASE WHEN status = '处理中' THEN 1 ELSE 0 END)      AS 处理中,
    SUM(CASE WHEN status = '未处理' THEN 1 ELSE 0 END)      AS 未处理,
    ROUND(SUM(CASE WHEN status IN ('未处理','处理中') THEN 1 ELSE 0 END) * 100.0
          / COUNT(*), 2)                                    AS 未结率_pct,     -- 积压压力指标
    RANK() OVER (ORDER BY COUNT(*) DESC)                    AS 类型排名        -- 件量最多的类型排第1
FROM dedup
WHERE rn = 1                                                                 -- 只统计每票当前最新状态
GROUP BY exc_type;
```

结果解读：延误+地址错误往往占异常总量的大头且未结率高，是坐席增援与源头治理的第一优先级；占比列基于聚合窗口，新增类型时无需改SQL。

**解法二：处理时长双口径（截断时长 + 已结时长对照）**

```sql
WITH dedup AS (              -- 同解法一：先按运单取最新一条异常记录
    SELECT
        exc_id, waybill_no, exc_type, status, report_time, resolve_time,
        ROW_NUMBER() OVER (PARTITION BY waybill_no ORDER BY report_time DESC) AS rn
    FROM exceptions
    WHERE report_time >= '2026-10-01' AND report_time < '2026-11-01'
)
SELECT
    exc_type                                                     AS 异常类型,
    COUNT(*)                                                     AS 样本量,
    ROUND(AVG(                                                   -- 口径A：含未结件的截断平均时长
        TIMESTAMPDIFF(HOUR, report_time,
                      COALESCE(resolve_time, TIMESTAMP('2026-10-26 00:00:00')))) -- 未解决件用统计截止时间兜底（右删失）
        , 1)                                                     AS 平均时长_截断_h,
    ROUND(AVG(CASE WHEN status = '已解决'                        -- 口径B：仅已解决件的纯闭环时长
                   THEN TIMESTAMPDIFF(HOUR, report_time, resolve_time) END), 1) AS 平均时长_已结_h,
    SUM(CASE WHEN resolve_time IS NULL THEN 1 ELSE 0 END)        AS 未结件数,   -- 截断样本规模，辅助解读口径A
    MAX(CASE WHEN status = '已解决'
             THEN TIMESTAMPDIFF(HOUR, report_time, resolve_time) END)            AS 最长闭环_h -- 极端个案排查
FROM dedup
WHERE rn = 1
GROUP BY exc_type
ORDER BY 平均时长_截断_h DESC;                                                 -- 处理最慢的异常类型排前面
```

结果解读：若某类型"截断时长"远大于"已结时长"，说明积压未结件被拖了很久，治理动作是清积压而非提效率；两口径接近则说明流水处理健康。

### 5. 性能分析与优化

两解法都先做 ROW_NUMBER 去重，窗口排序发生在 `(waybill_no, report_time)` 上，索引 `(waybill_no, report_time)` 可让去重走索引避免 filesort；随后按 exc_type 的 GROUP BY 输出行数等于类型数（个位数量级），整体代价集中在异常表按月过滤扫描。优化建议：① 异常表按 report_time 分区，查询强制携带月份边界；② status 与 exc_type 建联合索引加速状态透视的过滤；③ "统计截止时间"应由报表参数传入而非硬编码，避免不同人跑数结果不一致；④ 若异常表上亿，可将"每票最新状态"用 Hive 跑批落成日快照表，MySQL 只做类型聚合层。

> **Hive/Spark SQL 差异**：Hive 中 TIMESTAMPDIFF 不可用，改 `(unix_timestamp(resolve_time)-unix_timestamp(report_time))/3600.0`；聚合窗口 `SUM(COUNT(*)) OVER ()` 语法一致；海量数据去重建议 `ROW_NUMBER() OVER (DISTRIBUTE BY waybill_no SORT BY report_time DESC)` 提升并行度。

### 6. 面试延伸考点

- **为什么未结件的时长要用截止时间截断？** 要点：统计学上的右删失问题，直接剔除未结件只统计"已快速解决"的样本，平均时长被系统性低估，截断后才能反映真实服务压力。
- **同票多类型异常（先延误后破损）怎么归因？** 要点：按记录条数统计体现客服工作量，按运单去重统计体现异常面，两者都要给；归因考核一般取首次异常类型。
- **处理时长从上报起算还是从分派起算？** 要点：上报起算考核整体响应链路（含排队），分派起算考核坐席作业，指标用途不同，SQL只差一个起算字段。
- **异常件的"责任场地"维度怎么用？** 要点：按 site_id 拆分布可以定位高发场地，把异常率与场地件量结合算异常率而非绝对件数，避免大场地背锅。

### 7. 业务拓展思考

异常分布与处理时长是服务质量体系的输入端：高频类型驱动源头专项（地址错误→优化下单地址校验，破损→加固包装规范），处理时长驱动坐席排班与工单系统自动化。口径延展上，可以把处理时长拆成"首次响应时长"与"彻底解决时长"两段，与客服KPI对齐；再与WL-27的投诉率交叉，可识别"异常多但投诉少"（处理兜底好）与"异常少但投诉多"（处理体验差）两类不同问题。长期可建异常预测模型，按线路/天气/大促节奏提前布防。

| event_id | return_id | scan_type | scan_time |
|---|---|---|---|
| 6001 | RT10001 | APPLY | 2026-10-22 10:00:00 |
| 6002 | RT10001 | PICK_UP | 2026-10-22 15:30:00 |
| 6003 | RT10001 | ARRIVE_WH | 2026-10-23 09:10:00 |
| 6004 | RT10001 | QC_DONE | 2026-10-23 14:00:00 |
| 6005 | RT10002 | PICK_UP | 2026-10-23 10:00:00 |

### 3. 解题思路

逆向三段口径：揽收响应 = pickup_time - apply_time（考核取件运力）；退回在途 = arrive_wh_time - pickup_time（考核干线/集货）；质检入库 = qc_time - arrive_wh_time（考核仓内质检），全链路 = qc_time - apply_time。边界上：质检不合格件的全链路"退款完成"口径不同，主口径只统计合格件或单列对比；未取到件的揽收段不可截断到统计日再混入，应剔除并单独统计"未揽收率"。解法一在退货单字段直算（前提是节点时间已冗余成列）；解法二模拟"只有扫描事件表"的情形，用条件聚合取节点再算段，展示同构能力。

### 4. 参考解法

**解法一：退货单字段直算（节点已列化，最直观）**

```sql
SELECT
    r.wh_id,                                                                  -- 退回仓，作为分组维度
    COUNT(*)                                              AS 退货单量,         -- 分母：期内申请的退货单
    SUM(CASE WHEN r.pickup_time IS NULL THEN 1 ELSE 0 END) AS 未揽收单数,       -- 申请了但一直没被取走的单
    ROUND(AVG(CASE WHEN r.pickup_time IS NOT NULL                       -- 揽收段：只统计已揽收单
              THEN TIMESTAMPDIFF(HOUR, r.apply_time, r.pickup_time) END), 1) AS 平均揽收响应_h,
    ROUND(AVG(CASE WHEN r.arrive_wh_time IS NOT NULL
                    AND r.pickup_time IS NOT NULL                       -- 在途段：起止点齐全才计
              THEN TIMESTAMPDIFF(HOUR, r.pickup_time, r.arrive_wh_time) END), 1) AS 平均退回在途_h,
    ROUND(AVG(CASE WHEN r.qc_time IS NOT NULL
                    AND r.arrive_wh_time IS NOT NULL
                    AND r.qc_result = '合格'                            -- 质检段口径：仅合格件，避免不合格申诉拉长时长
              THEN TIMESTAMPDIFF(HOUR, r.arrive_wh_time, r.qc_time) END), 1) AS 平均质检入库_h,
    ROUND(AVG(CASE WHEN r.qc_time IS NOT NULL
                    AND r.apply_time IS NOT NULL
                    AND r.qc_result = '合格'                            -- 全链路：申请到质检完成，限合格件
              THEN TIMESTAMPDIFF(HOUR, r.apply_time, r.qc_time) END), 1) AS 平均全链路_h
FROM returns r
WHERE r.apply_time >= '2026-10-01' AND r.apply_time < '2026-11-01'            -- 按申请月归期，符合"用户发起"视角
GROUP BY r.wh_id
ORDER BY 平均全链路_h DESC;                                                   -- 全链路最慢的仓排前面
```

结果解读：哪个仓的全链路最慢、慢在哪一段一目了然；"未揽收单数"高说明不是仓的问题而是取件运力不足，治理方向完全不同。

**解法二：只有扫描事件表时，条件聚合取节点（自连接对照版）**

```sql
WITH node AS (               -- 第一步：条件聚合把每张退货单的节点时间压成一行
    SELECT
        s.return_id,                                                          -- 退货单号
        MAX(CASE WHEN s.scan_type = 'APPLY'     THEN s.scan_time END) AS apply_time,     -- 申请节点
        MAX(CASE WHEN s.scan_type = 'PICK_UP'   THEN s.scan_time END) AS pickup_time,    -- 揽收节点（MIN取首次亦可）
        MAX(CASE WHEN s.scan_type = 'ARRIVE_WH' THEN s.scan_time END) AS arrive_time,    -- 到仓节点
        MAX(CASE WHEN s.scan_type = 'QC_DONE'   THEN s.scan_time END) AS qc_time         -- 质检节点
    FROM reverse_scans s
    GROUP BY s.return_id
),
seg AS (                     -- 第二步：逐段计算，同时算"下一跳"最小时间做交叉校验
    SELECT
        n.return_id,
        TIMESTAMPDIFF(HOUR, n.apply_time,  n.pickup_time) AS h1_揽收响应,     -- 段1
        TIMESTAMPDIFF(HOUR, n.pickup_time, n.arrive_time) AS h2_退回在途,     -- 段2
        TIMESTAMPDIFF(HOUR, n.arrive_time, n.qc_time)     AS h3_质检入库,     -- 段3
        (SELECT MIN(b.scan_time) FROM reverse_scans b                            -- 相关子查询：该单下一次扫描时间
          WHERE b.return_id = n.return_id AND b.scan_time > n.arrive_time) AS next_after_arrive -- 校验在途与质检段是否断裂
    FROM node n
    WHERE n.pickup_time IS NOT NULL AND n.arrive_time IS NOT NULL              -- 段2/段3需要的前置节点齐全
)
SELECT
    COUNT(*)                                        AS 有效单量,               -- 参与分段统计的单量
    ROUND(AVG(h1_揽收响应), 1)                      AS 平均揽收响应_h,
    ROUND(AVG(h2_退回在途), 1)                      AS 平均退回在途_h,
    ROUND(AVG(h3_质检入库), 1)                      AS 平均质检入库_h,
    SUM(CASE WHEN next_after_arrive IS NULL THEN 1 ELSE 0 END) AS 扫描断链单数  -- 到仓后无质检扫描：漏扫或滞留
FROM seg;
```

结果解读：条件聚合版与解法一数值一致。**【加分点】** "扫描断链单数"暴露漏扫或仓库滞留，是逆向链路数据质量检查的副产品，面试中主动提及这类数据质量副产品往往能让面试官眼前一亮。

### 5. 性能分析与优化

解法一只扫退货单表，字段已列化，代价最低，适合日常报表；解法二多一层事件表 GROUP BY（行数=退货单×4节点），且相关子查询需 reverse_scans 上有 `(return_id, scan_time)` 索引。优化建议：① 事件表按月分区，节点宽表（每退货单一行）落成增量 dws 表，报表读宽表；② 节点取值用 MIN 还是 MAX 要与业务确认——逆向件可能"多次上门失败再取"，揽收节点应取成功那次的 MIN(PICK_UP)，失败上门事件若单独有类型则天然排除；③ 质检不合格件的二次处理流程会产生第二段 qc_time，需用 ROW_NUMBER 区分首次/复检；④ returns 与 orders 的关联键 order_no 建索引，便于延伸到"退货率×品类"分析。

### 6. 面试延伸考点

- **逆向时效的分段起止点与正向有什么本质不同？** 要点：正向以"揽收"为起点、商家履约视角；逆向以"用户申请"为起点、消费者体验视角，申请到上门揽收这段是逆向特有的等待段，往往也是投诉高发段。
- **质检不合格的退货单要计入时效吗？** 要点：主口径剔除并单独统计"不合格率+争议处理时长"，混入会把质检段拉长得看不出仓内作业水平。
- **用户申请后取消退货的单算什么？** 要点：状态机里要有"已取消"终态，在"未揽收率"中区分"运力没接住"与"用户主动取消"，否则高估取件运力缺口。
- **逆向单怎么和正向订单关联做退款时效分析？** 要点：以 order_no/return_id 为键 JOIN 退款流水，把"质检合格→退款到账"段补进全链路，形成"申请→退款到账"的端到端体验指标。

### 7. 业务拓展思考

逆向分段时效直接支撑三个决策：取件运力补贴（揽收响应慢的城市加调度额度）、退货仓选址（在途段长的区域增设前置退回仓）、质检流水线扩容（质检段超标的仓加质检工位）。口径延展上，可按品类拆解——服饰类退货率高且质检慢（需重新熨烫打包），3C类质检流程完全不同，统一口径会掩盖问题；还可与正向WL-16的全链路时效拼接，构成"购-退"完整体验旅程，识别"正向快、逆向慢"的伤害型体验。

## WL-24 快递员人均单量与投诉率交叉矩阵

### 1. 业务背景

末端站点管理者长期面临一个两难：单量压得多，时效好看但服务容易出问题；派得少，服务好但人效不达标。末端运营专员（谁）在月度绩效复盘时（何时），需要把每个快递员的"人均日单量"与"投诉率"交叉分档，形成二×三的矩阵（什么），用来识别"高单量高投诉"的风险人员（需要辅导）与"高单量低投诉"的标杆人员（值得总结经验），并校准派件量定额（为什么）。

### 3. 解题思路

分两个 CTE 各自聚合：C1 每个快递员的派件票数（分母）；C2 每个快递员的投诉条数（分子）。**【避坑指南】** 必须用 couriers 花名册为主表 LEFT JOIN C2，保证"零投诉"快递员不丢行——写成内连接会把最优秀的员工洗掉，这是本题最经典的坑。投诉率 = 投诉条数 / 派件票数。然后 CASE 双分档：日单量档（<150低/150-300中/>300高）、投诉率档（=0零投诉/<0.5%低/≥0.5%高）。解法一用条件聚合输出"行=单量档、列=投诉率档"的人数矩阵；解法二输出分档明细长表并配窗口占比，便于下钻到人。

### 4. 参考解法

**解法一：双CTE聚合 + 条件聚合交叉矩阵**

```sql
WITH courier_vol AS (        -- 第一步：每个快递员的派件票数（分母）
    SELECT courier_id, COUNT(*) AS bill_cnt                                  -- 派件票数
    FROM waybills
    WHERE create_date BETWEEN '2026-10-20' AND '2026-10-26'                   -- 统计周
      AND dest_site_id IN ('ST401','ST402')                                   -- 可按站点收窄
    GROUP BY courier_id
),
courier_cmp AS (             -- 第二步：每个快递员的投诉条数（分子）
    SELECT courier_id, COUNT(*) AS cmp_cnt                                   -- 被投诉次数
    FROM complaints
    WHERE complaint_time >= '2026-10-20 00:00:00'
      AND complaint_time <  '2026-10-27 00:00:00'
    GROUP BY courier_id
),
base AS (                    -- 第三步：花名册为主表拼两个指标，保住零投诉/零单量的人
    SELECT
        c.courier_id,
        c.courier_name,
        COALESCE(v.bill_cnt, 0)                       AS bill_cnt,           -- 无派件记录则为0
        COALESCE(x.cmp_cnt, 0)                        AS cmp_cnt,            -- 关键：LEFT JOIN保住零投诉者
        CASE
            WHEN COALESCE(v.bill_cnt, 0) = 0 THEN '无单量'
            WHEN COALESCE(v.bill_cnt, 0) / 7 < 150 THEN '低单量'          -- 除以7天折算日均
            WHEN COALESCE(v.bill_cnt, 0) / 7 < 300 THEN '中单量'
            ELSE '高单量'
        END                                            AS 单量档,
        CASE
            WHEN COALESCE(v.bill_cnt, 0) = 0 THEN '无单量'                -- 分母为0不计投诉率档
            WHEN COALESCE(x.cmp_cnt, 0) = 0 THEN '零投诉'
            WHEN x.cmp_cnt * 100.0 / v.bill_cnt < 0.5 THEN '低投诉'
            ELSE '高投诉'
        END                                            AS 投诉档
    FROM couriers c
    LEFT JOIN courier_vol v ON v.courier_id = c.courier_id
    LEFT JOIN courier_cmp x ON x.courier_id = c.courier_id
    WHERE c.site_id IN ('ST401','ST402')                                      -- 与运单口径同站点
)
SELECT
    单量档,                                                                    -- 行：单量档
    SUM(CASE WHEN 投诉档 = '零投诉' THEN 1 ELSE 0 END) AS 零投诉人数,           -- 列1
    SUM(CASE WHEN 投诉档 = '低投诉' THEN 1 ELSE 0 END) AS 低投诉人数,           -- 列2
    SUM(CASE WHEN 投诉档 = '高投诉' THEN 1 ELSE 0 END) AS 高投诉人数,           -- 列3
    COUNT(*)                                            AS 小计               -- 行合计
FROM base
WHERE 单量档 <> '无单量'                                                      -- 无单量的人不参与矩阵
GROUP BY 单量档
ORDER BY FIELD(单量档, '低单量', '中单量', '高单量');                          -- 按业务顺序排列而非字母序
```

结果解读："高单量×高投诉"格子里的人是风险名单，"高单量×零投诉"是标杆名单；若矩阵整体随单量升高投诉档上移，说明派件定额已经越过服务承压临界点。

**解法二：分档明细长表 + 窗口占比（可下钻到人）**

```sql
WITH courier_vol AS (
    SELECT courier_id, COUNT(*) AS bill_cnt
    FROM waybills
    WHERE create_date BETWEEN '2026-10-20' AND '2026-10-26'
    GROUP BY courier_id
),
courier_cmp AS (
    SELECT courier_id, COUNT(*) AS cmp_cnt
    FROM complaints
    WHERE complaint_time >= '2026-10-20 00:00:00'
      AND complaint_time <  '2026-10-27 00:00:00'
    GROUP BY courier_id
),
base AS (                    -- 同解法一拼指标并分档
    SELECT
        c.courier_id, c.courier_name,
        COALESCE(v.bill_cnt, 0) AS bill_cnt,
        COALESCE(x.cmp_cnt, 0)  AS cmp_cnt,
        CASE WHEN COALESCE(v.bill_cnt, 0) = 0  THEN '无单量'                  -- 先判零单量，防止0/7落入"低单量"
             WHEN COALESCE(v.bill_cnt, 0)/7 < 150 THEN '低单量'
             WHEN COALESCE(v.bill_cnt, 0)/7 < 300 THEN '中单量'
             ELSE '高单量' END              AS 单量档,
        CASE WHEN COALESCE(v.bill_cnt, 0) = 0 THEN '无单量'
             WHEN COALESCE(x.cmp_cnt, 0) = 0 THEN '零投诉'
             WHEN x.cmp_cnt * 100.0 / v.bill_cnt < 0.5 THEN '低投诉'
             ELSE '高投诉' END              AS 投诉档
    FROM couriers c
    LEFT JOIN courier_vol v ON v.courier_id = c.courier_id
    LEFT JOIN courier_cmp x ON x.courier_id = c.courier_id
),
graded AS (                  -- 在人粒度加窗口：先在分档明细上算每组占比
    SELECT
        b.*,
        COUNT(*) OVER (PARTITION BY 单量档, 投诉档)             AS 组内人数,   -- 每个组合的人数
        COUNT(*) OVER ()                                       AS 总人数      -- 全体人数作占比分母
    FROM base b
    WHERE b.单量档 <> '无单量'
)
SELECT
    courier_id,                                                                -- 工号，可下钻
    courier_name,                                                              -- 姓名
    bill_cnt                                             AS 周派件量,
    cmp_cnt                                              AS 周投诉数,
    单量档,
    投诉档,
    ROUND(组内人数 * 100.0 / 总人数, 1)                   AS 组占比_pct         -- 该组合覆盖多少人
FROM graded
WHERE 投诉档 = '高投诉'                                                       -- 先拉高风险名单
ORDER BY cmp_cnt DESC;                                                       -- 投诉最多的人排最前
```

结果解读：这版直接输出人名单与组占比，运营可以拿去逐人辅导；窗口写法让"人数与占比"在人粒度行上同时呈现，避免再写一层聚合。

### 5. 性能分析与优化

两解法主体都是两次小聚合（快递员数百万级以内）加一次 LEFT JOIN，代价可控；complaints 按时间段过滤需 `(courier_id, complaint_time)` 或按月分区索引。优化建议：① waybills 按 create_date 分区并建 `(courier_id, create_date)` 索引；② 投诉与运单的时间窗要严格对齐（本题用同一周），否则投诉率分子分母错位；③ "零投诉 LEFT JOIN 保行"是必考点，写成 JOIN 会把约一半样本洗掉；④ 若站点人多，先把 waybills 按 courier_id 聚合落周表，矩阵层只处理人级数据；⑤ 分档阈值应参数化存维表，跨城市定额不同时不用改SQL。

### 6. 面试延伸考点

- **为什么必须用 LEFT JOIN 而不是 INNER JOIN？** 要点：投诉表只有出事的人，内连接会丢失零投诉快递员，导致"零投诉"档永远统计不到，矩阵系统性偏悲观。
- **投诉率分母用派件量还是签收量？** 要点：投诉可能发生在未签收阶段，用派件量做分母口径更完整；若考核服务态度类投诉可细分到签收后投诉，分母随之调整。
- **一票多投诉和多人共投一票怎么算？** 要点：按投诉条数算人力压力，按去重运单算涉事票量，SQL分别给 COUNT(*) 与 COUNT(DISTINCT waybill_no)。
- **矩阵阈值怎么定才科学？** 要点：可用 PERCENT_RANK/NTILE 按分布切（如后10%为高投诉档）替代拍脑袋绝对值，但跨站对比时绝对阈值更利于统一管理，两种口径面试都应能说清取舍。

### 7. 业务拓展思考

交叉矩阵是末端人力管理仪表盘的核心页：高单量高投诉人员触发辅导或减量，高单量零投诉人员沉淀话术与路线经验并复制推广，低单量低投诉人员评估是否运力冗余。口径延展上，可以把投诉率换成"差错率"（错投、漏投、虚假签收）做第二面板，防止员工用"少派件"优化投诉率；再与WL-20的班次效率、WL-29的仓库等待时长联动，区分"人不行"与"系统拖累"，避免把上游瓶颈错算成末端责任。

## WL-25 网点单量密度与覆盖评估（含网点归属变更）

### 1. 业务背景

网络规划团队要回答"哪里该开新网点、哪里该合并"。网络规划分析师（谁）在年度网络布局规划时（何时），需要每个网点的单量密度（单量/覆盖面积）与人效（单量/员工数）（什么），用来识别"高密度低人效"（该扩编或拆分）与"低密度低人效"（该合并）的网点（为什么）。**【避坑指南】** 物流网点经常调整管辖归属或覆盖范围，表结构必须带生效区间（effective_date/expire_date），统计任意日期都要先按区间过滤出"当时有效"的归属，否则新旧归属的量会被重复或错算。

### 2. 表结构说明

**表1：outlets（网点主数据表，带生效区间）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| site_id | VARCHAR(20) | 网点编码 |
| site_name | VARCHAR(50) | 网点名称 |
| district | VARCHAR(20) | 所属城市/大区 |
| coverage_km2 | DECIMAL(8,2) | 覆盖面积（平方公里） |
| staff_count | INT | 在岗员工数 |
| effective_date | DATE | 本条归属记录生效日 |
| expire_date | DATE | 失效日，9999-12-31表示当前有效 |

示例数据：

| site_id | site_name | district | coverage_km2 | staff_count | effective_date | expire_date |
|---|---|---|---|---|---|---|
| ST501 | 城东一部 | 杭州 | 12.50 | 18 | 2025-01-01 | 2026-06-30 |
| ST501 | 城东一部 | 杭州 | 8.20 | 15 | 2026-07-01 | 9999-12-31 |
| ST502 | 城东二部 | 杭州 | 6.80 | 10 | 2026-07-01 | 9999-12-31 |
| ST503 | 滨江一部 | 杭州 | 15.00 | 22 | 2025-01-01 | 9999-12-31 |
| ST504 | 城西一部 | 杭州 | 20.30 | 14 | 2025-01-01 | 9999-12-31 |

**表2：waybills（运单表，含派件网点与日期）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| waybill_no | VARCHAR(20) | 运单号，主键 |
| dest_site_id | VARCHAR(20) | 派件网点编码 |
| create_date | DATE | 运单日期 |

示例数据：

| waybill_no | dest_site_id | create_date |
|---|---|---|
| WB2026100071 | ST501 | 2026-10-20 |
| WB2026100072 | ST501 | 2026-10-21 |
| WB2026100073 | ST502 | 2026-10-21 |
| WB2026100074 | ST503 | 2026-10-22 |

### 3. 解题思路

第一步按"统计基准日"过滤网点归属：`effective_date <= 基准日 < expire_date`，基准日取统计期末日，保证 ST501 拆分前后只取当前归属（覆盖8.2平方公里、15人）；第二步把运单按网点聚出统计期单量；第三步计算密度（单量/覆盖面积）与人效（单量/员工数），并用窗口 NTILE/PERCENT_RANK 把两个指标各切成高中低档形成四象限。解法一按基准日快照口径输出网点评估表；解法二演示"跨归属变更期"的口径：运单按其 create_date 落在当时有效的归属上（JOIN 条件改为日期区间匹配），可还原拆分前后各自单量，是归属变更类问题的标准解法。

### 4. 参考解法

**解法一：基准日快照口径（当前归属下的密度与人效评估）**

```sql
WITH site_vol AS (           -- 第一步：统计期各网点单量
    SELECT dest_site_id, COUNT(*) AS bill_cnt                                -- 期间派件量
    FROM waybills
    WHERE create_date BETWEEN '2026-10-01' AND '2026-10-31'                   -- 统计月
    GROUP BY dest_site_id
),
site_now AS (                -- 第二步：按基准日取"当时有效"的网点主数据
    SELECT site_id, site_name, district, coverage_km2, staff_count
    FROM outlets
    WHERE effective_date <= '2026-10-31'                                      -- 生效日在基准日之前
      AND expire_date   >  '2026-10-31'                                       -- 失效日在基准日之后=当前有效
      AND expire_date   >  effective_date                                     -- 防御：过滤异常零长区间
),
scored AS (                  -- 第三步：逐网点算密度与人效（无单量网点保留为0）
    SELECT
        n.site_id, n.site_name, n.district,
        COALESCE(v.bill_cnt, 0)                                   AS bill_cnt,
        COALESCE(v.bill_cnt, 0) * 1.0 / NULLIF(n.coverage_km2, 0) AS density,   -- 密度=单量/覆盖面积
        COALESCE(v.bill_cnt, 0) * 1.0 / NULLIF(n.staff_count, 0)  AS per_capita -- 人效=单量/员工数
    FROM site_now n
    LEFT JOIN site_vol v ON v.dest_site_id = n.site_id                       -- 合并候选恰恰可能是无单量网点
),
ranked AS (                  -- 第四步：NTILE切四分位桶（MySQL无PERCENTILE_CONT，用桶上沿近似分位数）
    SELECT
        s.*,
        NTILE(4) OVER (ORDER BY s.density)                        AS q_dens,  -- 密度4桶，1最低4最高
        NTILE(4) OVER (ORDER BY s.per_capita)                     AS q_per    -- 人效4桶
    FROM scored s
),
cut AS (                     -- 第五步：从桶上沿取近似切线值
    SELECT
        MAX(CASE WHEN q_dens = 3 THEN density   END)   AS dens_p75,           -- 密度第3桶最大值≈P75
        MAX(CASE WHEN q_dens = 1 THEN density   END)   AS dens_p25,           -- 密度第1桶最大值≈P25
        MAX(CASE WHEN q_per  = 1 THEN per_capita END)  AS per_p25             -- 人效第1桶最大值≈P25
    FROM ranked
)
SELECT
    r.site_id,                                                                -- 网点
    r.site_name,                                                              -- 名称
    r.district,                                                               -- 大区
    r.bill_cnt                                          AS 月单量,
    ROUND(r.density, 0)                                 AS 单量密度_每平方公里, -- 密度=单量/覆盖面积
    ROUND(r.per_capita, 0)                              AS 人效_人均单量,       -- 人效=单量/员工数
    CASE                                                              -- 四象限结论标签
        WHEN r.density >= c.dens_p75 AND r.per_capita <= c.per_p25
            THEN '高密度低人效_优先扩编'                                       -- 地盘小件多但人手不足
        WHEN r.density <= c.dens_p25 AND r.per_capita <= c.per_p25
            THEN '低密度低人效_评估合并'                                       -- 双低是合并评估对象
        ELSE '正常区间'
    END                                                  AS 布局结论
FROM ranked r CROSS JOIN cut c                                                -- 切线值一行，CROSS JOIN贴到每行
ORDER BY r.density DESC;
```

结果解读：输出即一张布局决策表——"高密度低人效"说明地盘小件多却没人，应扩编或拆出二部；"低密度低人效"是合并评估对象；注意 ST501 取的是拆分后的8.2平方公里口径。

**解法二：归属变更还原口径（运单按"当时有效归属"落位）**

```sql
WITH vol_hist AS (           -- 第一步：运单按日期JOIN到"当日有效"的网点归属
    SELECT
        w.create_date,                                                        -- 运单日期
        o.site_id,                                                            -- 当时归属网点
        COUNT(*) OVER (PARTITION BY o.site_id)                 AS 该归属总单量, -- 窗口：按归属汇总（演示用）
        w.waybill_no                                                          -- 运单号
    FROM waybills w
    JOIN outlets o                                                            -- 关键：JOIN条件是区间匹配而非等值
      ON o.site_id = w.dest_site_id
     AND w.create_date >= o.effective_date                                    -- 运单日在生效区间内
     AND w.create_date <  o.expire_date
    WHERE w.create_date BETWEEN '2026-01-01' AND '2026-10-31'                 -- 跨越6月底拆分的完整观察期
),
monthly AS (                 -- 第二步：按网点×月聚出单量，还原拆分前后水位
    SELECT
        site_id,
        DATE_FORMAT(create_date, '%Y-%m')               AS 月份,
        COUNT(*)                                        AS 单量
    FROM vol_hist
    GROUP BY site_id, DATE_FORMAT(create_date, '%Y-%m')
)
SELECT
    m.site_id,                                                                -- 网点
    m.月份,                                                                    -- 月份
    m.单量,
    ROUND(m.单量 - LAG(m.单量) OVER (PARTITION BY m.site_id
                                     ORDER BY m.月份), 0) AS 环比变化,          -- 与上月比，看拆分是否分流
    ROUND(100.0 * m.单量 / SUM(m.单量) OVER (PARTITION BY m.site_id), 1) AS 占该网点全年比_pct -- 月度结构
FROM monthly m
ORDER BY m.site_id, m.月份;
```

结果解读：ST501 在2026-06、07两月的环比骤降与 ST502 的首月出现，正是拆分分流的证据；区间JOIN让任何历史日期的单量都能按"当时的归属"复算，是网点归属变更场景的标准套路。

### 5. 性能分析与优化

解法一的 NTILE 切桶需按密度、人效各做一次排序，但只作用于网点级小结果集（行数=网点数，百级），代价可忽略，切线值在 cut CTE 中一次算出后 CROSS JOIN 贴行，无重复扫描；区间 JOIN（解法二）无法走普通等值索引，靠 `(site_id, effective_date)` 复合索引缩小候选后过滤。优化建议：① outlets 主数据每次变更插入新行而非 UPDATE，天然形成拉链表，是物流行业主数据的标准设计；② 单量统计先按月聚合到 `(dest_site_id, 月份)` 的 dws 表，再做区间 JOIN，把大表连接降为小表连接；③ 四象限阈值可改为固定业务阈值（如密度>500票/平方公里），牺牲灵活性换取SQL简化与口径稳定；④ 输出加 `ORDER BY ... LIMIT` 只取决策清单。

### 6. 面试延伸考点

- **拉链表（生效区间）为什么优于每次全量覆盖？** 要点：保留历史快照可复算任意历史日期的口径，覆盖更新会让"当时的世界"不可还原，审计与复盘都无从下手。
- **统计期横跨归属变更日，单量怎么算才不重复？** 要点：每票按其业务日期落在当时有效归属上（解法二），严禁全程按当前归属回刷，否则拆分前单量会被两个网点重复计入。
- **密度和人效矛盾时听谁的？** 要点：密度高人效低说明"地盘养得起但人不够"，先扩编；密度低人效高说明人力偏紧但盘子小，重点是扩覆盖；两者都低才谈合并。
- **覆盖面积怎么校准？** 要点：面积应剔除不可配送区域（水域、工业区），用路网可达面积替代平面面积更贴近真实配送强度，GIS侧维护、SQL只引用。

### 7. 业务拓展思考

密度×人效四象限直接驱动网络布局：扩编、拆分、合并、迁址四类动作各有明确触发条件，并可测算单票成本变化支撑立项。口径延展上，密度分母可换成"覆盖小区数/写字楼数"更贴近末端作业单元；人效可拆"派件人效"与"揽件人效"，揽件密度高的区域才是新网点选址的金矿。再与WL-17的超时率叠加，可识别"密度高、时效差"的过载网点，把布局规划从成本视角升级为体验视角。

## WL-26 大促单量预测偏差与MAPE分析

### 1. 业务背景

大促（双11/618）前，运力、场地、人力都按预测单量准备，预测偏差直接转化为成本浪费或爆仓风险。运力规划分析师（谁）在大促复盘时（何时），需要按网点×日期对比预测单量与实际单量，算出逐日偏差率与各网点大促期间的整体MAPE（平均绝对百分比误差）（什么），用来给预测模型团队反馈哪些网点、哪些大促阶段（预售期/预热期/爆发期）偏差最大，指导下一次大促的预测校准与运力冗余系数设定（为什么）。

### 2. 表结构说明

**表1：forecast_daily（大促单量预测表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| site_id | VARCHAR(20) | 网点编码 |
| stat_date | DATE | 预测目标日期 |
| forecast_qty | INT | 预测派件单量 |
| forecast_ver | VARCHAR(10) | 预测版本：T-30/T-7/T-1 |

示例数据：

| site_id | stat_date | forecast_qty | forecast_ver |
|---|---|---|---|
| ST601 | 2026-11-01 | 1200 | T-7 |
| ST601 | 2026-11-02 | 1500 | T-7 |
| ST601 | 2026-11-03 | 2600 | T-7 |
| ST602 | 2026-11-01 | 800 | T-7 |
| ST602 | 2026-11-03 | 1750 | T-7 |

**表2：waybills（运单表，实际单量的来源）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| waybill_no | VARCHAR(20) | 运单号，主键 |
| dest_site_id | VARCHAR(20) | 派件网点 |
| create_date | DATE | 运单日期 |

示例数据：

| waybill_no | dest_site_id | create_date |
|---|---|---|
| WB2026110001 | ST601 | 2026-11-01 |
| WB2026110002 | ST601 | 2026-11-01 |
| WB2026110003 | ST601 | 2026-11-03 |
| WB2026110004 | ST602 | 2026-11-03 |
| WB2026110005 | ST602 | 2026-11-03 |

### 3. 解题思路

口径先行：偏差率 =（实际−预测）/ 预测，正值即低估（实际超预测，爆仓风险），负值即高估（运力浪费）；MAPE = 各日 ABS(偏差率) 的均值，衡量"整体预测准不准"，而方向拆分衡量"偏大还是偏小"，两者缺一不可。实现路径：解法一先把运单聚成"网点×日期实际量"，与预测表对齐 JOIN，得到逐日偏差明细，再按网点聚合出 MAPE 与"低估天数占比"，并用 RANK 找出偏差最差的网点；解法二把偏差按"方向×幅度"分成六档做条件聚合透视，输出偏差结构而非单一均值。**【加分点】** 两个易错点必须主动讲：一是预测量为0或缺失时 NULLIF 防除零，且缺失预测日期应计入"预测漏排"而不是静默丢弃；二是实际表要先聚合再 JOIN，直接大表 JOIN 会产生笛卡尔级放大。

### 4. 参考解法

**解法一：实际先聚合 → 对齐预测 → 逐日偏差 → 网点级MAPE与排名**

```sql
WITH actual AS (             -- 第一步：运单聚合成"网点×日期"实际单量
    SELECT
        dest_site_id                    AS site_id,                          -- 对齐预测表的键名
        create_date                     AS stat_date,                        -- 日期对齐
        COUNT(*)                        AS actual_qty                        -- 实际单量
    FROM waybills
    WHERE create_date BETWEEN '2026-11-01' AND '2026-11-11'                  -- 大促期间11天
    GROUP BY dest_site_id, create_date
),
daily_dev AS (               -- 第二步：预测左连实际，逐日算偏差
    SELECT
        f.site_id,                                                           -- 网点
        f.stat_date,                                                         -- 日期
        f.forecast_qty,                                                      -- 预测量
        COALESCE(a.actual_qty, 0)      AS actual_qty,                        -- 预测了但0实际也要保留（高估样本）
        ROUND((COALESCE(a.actual_qty, 0) - f.forecast_qty)
              * 100.0 / NULLIF(f.forecast_qty, 0), 1) AS dev_pct,            -- 偏差率，NULLIF防预测0除零
        CASE
            WHEN f.forecast_qty IS NULL OR f.forecast_qty = 0 THEN '预测缺失'
            WHEN a.actual_qty IS NULL THEN '实际缺失'
            ELSE '正常' END                          AS data_flag             -- 数据质量标记，防静默丢数
    FROM forecast_daily f
    LEFT JOIN actual a                                                        -- 以预测为主表：预测有而实际无=高估
      ON a.site_id = f.site_id AND a.stat_date = f.stat_date
    WHERE f.forecast_ver = 'T-7'                                              -- 固定考核T-7版本，多版本会重复计分
),
site_score AS (              -- 第三步：网点级聚合MAPE
    SELECT
        site_id,
        COUNT(*)                                        AS 参评天数,
        ROUND(AVG(ABS(dev_pct)), 1)                     AS MAPE_pct,          -- 平均绝对百分比误差
        SUM(CASE WHEN dev_pct > 10 THEN 1 ELSE 0 END)   AS 低估超10pct天数,    -- 爆仓风险天数
        SUM(CASE WHEN dev_pct < -10 THEN 1 ELSE 0 END)  AS 高估超10pct天数,    -- 运力浪费天数
        ROUND(SUM(CASE WHEN dev_pct > 10 THEN 1 ELSE 0 END) * 100.0
              / NULLIF(SUM(CASE WHEN ABS(dev_pct) > 10 THEN 1 ELSE 0 END), 0), 1) AS 偏差中低估占比_pct
    FROM daily_dev
    WHERE data_flag = '正常'                                                  -- 缺失样本单独排查，不进MAPE
    GROUP BY site_id
)
SELECT
    site_id, 参评天数, MAPE_pct, 低估超10pct天数, 高估超10pct天数, 偏差中低估占比_pct,
    RANK() OVER (ORDER BY MAPE_pct DESC)            AS 偏差排名,              -- MAPE最大=最需校准
    ROW_NUMBER() OVER (ORDER BY MAPE_pct DESC)      AS 严格序号               -- 并列时RANK会重号，ROW_NUMBER唯一
FROM site_score;
```

结果解读：MAPE 高且"低估占比"大的网点是下次大促的爆仓高危点，应上调预测冗余系数；反之高估主导的网点要防止按预测满配导致人力闲置。

**解法二：偏差"方向×幅度"六档分布透视（看结构而非只看均值）**

```sql
WITH actual AS (
    SELECT dest_site_id AS site_id, create_date AS stat_date, COUNT(*) AS actual_qty
    FROM waybills
    WHERE create_date BETWEEN '2026-11-01' AND '2026-11-11'
    GROUP BY dest_site_id, create_date
),
daily_dev AS (               -- 逐日偏差并打六档标签
    SELECT
        f.site_id,
        ROUND((COALESCE(a.actual_qty, 0) - f.forecast_qty)
              * 100.0 / NULLIF(f.forecast_qty, 0), 1) AS dev_pct,
        CASE
            WHEN f.forecast_qty IS NULL OR f.forecast_qty = 0 THEN '预测缺失'   -- 无预测样本不参与分档，防除零误判
            WHEN a.actual_qty IS NULL THEN '实际缺失'                           -- 预测有值但当日无运单记录，单独排查
            WHEN (COALESCE(a.actual_qty, 0) - f.forecast_qty) * 100.0
                 / f.forecast_qty >  30 THEN '严重低估_超30pct'                 -- 实际远超预测（前面已保证预测>0）
            WHEN (COALESCE(a.actual_qty, 0) - f.forecast_qty) * 100.0
                 / f.forecast_qty >  10 THEN '轻度低估_10到30pct'
            WHEN (COALESCE(a.actual_qty, 0) - f.forecast_qty) * 100.0
                 / f.forecast_qty >= -10 THEN '基本准确_±10pct内'               -- 可接受的命中区间
            WHEN (COALESCE(a.actual_qty, 0) - f.forecast_qty) * 100.0
                 / f.forecast_qty >= -30 THEN '轻度高估'
            ELSE '严重高估_超30pct'                                             -- 预测远超实际
        END                                            AS dev_band             -- 分档标签（缺失样本已前置排除）
    FROM forecast_daily f
    LEFT JOIN actual a ON a.site_id = f.site_id AND a.stat_date = f.stat_date
    WHERE f.forecast_ver = 'T-7'
)
SELECT
    site_id,                                                                  -- 网点
    COUNT(*)                                        AS 参评日天次,
    SUM(CASE WHEN dev_band IN ('预测缺失','实际缺失')
             THEN 1 ELSE 0 END)                     AS 缺失日次,               -- 不参与命中率分母
    ROUND(SUM(CASE WHEN dev_band = '基本准确_±10pct内' THEN 1 ELSE 0 END) * 100.0
          / NULLIF(COUNT(*) - SUM(CASE WHEN dev_band IN ('预测缺失','实际缺失')
                                        THEN 1 ELSE 0 END), 0), 1) AS 命中率_pct, -- ±10%内占比：业务最直观的"准头"
    SUM(CASE WHEN dev_band = '严重低估_超30pct' THEN 1 ELSE 0 END) AS 严重低估日次,
    SUM(CASE WHEN dev_band = '轻度低估_10到30pct' THEN 1 ELSE 0 END) AS 轻度低估日次,
    SUM(CASE WHEN dev_band = '轻度高估' THEN 1 ELSE 0 END) AS 轻度高估日次,
    SUM(CASE WHEN dev_band = '严重高估_超30pct' THEN 1 ELSE 0 END) AS 严重高估日次
FROM daily_dev
GROUP BY site_id
ORDER BY 命中率_pct ASC;                                                      -- 命中率最差的网点排前面
```

结果解读：同样是 MAPE=25%，"全部严重低估"与"一半严重高估一半严重低估"的治理动作完全不同——前者校准模型基数，后者排查节奏错位（如预售前置发货），六档结构列让这一眼可见。

### 5. 性能分析与优化

两解法成本相当：运单大表做一次按网点×日期的 COUNT（索引 `(create_date, dest_site_id)` 或按日分区可覆盖扫描），JOIN 的是极小的预测表，主体代价在运单聚合。优化建议：① 运单表大促期间单日千万级，务必携带 create_date 分区裁剪，并提前落"网点×日期"日汇总表，复盘只读聚合层；② 预测表固定 forecast_ver 后建 `(site_id, stat_date, forecast_ver)` 索引，防止多版本重复 JOIN 放大行数；③ MAPE 对小基数千次级网点极不稳定（预测100实际150偏差50%），应设最小预测量门槛或在汇总口径中改用加权 MAPE（以 Σ|误差量|/Σ预测量 替代均值）；④ 复盘常需对比 T-30/T-7/T-1 多版本准确度，把 forecast_ver 提为分组维度即可复用同一套SQL。

### 6. 面试延伸考点

- **MAPE 在什么场景会失真？** 要点：预测量很小或为0时百分比爆炸；单量基数差异大的网点直接平均MAPE会被小网点绑架，应改加权MAPE（Σ|实际−预测|/Σ预测）或对分位数（如P75偏差）考核。
- **为什么低估和高估要分开看？** 要点：低估带来爆仓、延误、投诉等体验损失，高估带来人力车辆闲置等成本损失，业务代价不对称，冗余系数应基于"分方向偏差"而非对称MAPE设定。
- **大促节奏（预售期/爆发期）如何影响偏差分析？** 要点：爆发日单量呈脉冲，按日考核偏严；可按"大促阶段"分组算偏差，或对爆发日单独设容差带，SQL里加阶段维表 JOIN 即可实现。
- **预测多版本（T-30/T-7/T-1）怎么考核？** 要点：固定同一版本横向比网点、多版本纵向比滚动校准效果，SQL 中 forecast_ver 进入 GROUP BY，注意版本间不可混算。

### 7. 业务拓展思考

预测偏差复盘的落点是"预测-运力-成本"闭环：低估主导的网点提高冗余系数与外协备选池，高估主导的网点改"基础运力+爆发补贴"模式；偏差集中的日期（通常是爆发首日）应推动大促节奏与消费者分流。口径延展上，可以把单量预测扩展为"分时段预测"（按小时布人）与"分品类预测"（大件占比影响车辆选型）；与WL-17的超时率、WL-22的异常件交叉后，还能量化"预测低估→超时/异常→投诉"的损失传导链，让预测精度直接挂钩经营结果。

## WL-27 线路投诉率×时效达成率四象限分析

### 1. 业务背景

时效与投诉是线路服务质量的两大侧面：时效差但投诉少的线路可能是客户预期低或货主结构不敏感，时效好但投诉多的线路则可能是派送服务态度问题。质量运营专员（谁）在季度线路评级时（何时），需要每条线路的"48小时时效达成率"与"投诉率"双指标，并按双中位数切成四象限（什么），用来输出线路红黑榜——双差线路进入整改、双优线路进入推荐名录，并识别"时效差投诉高"的最危险线路优先投放资源（为什么）。

### 2. 表结构说明

**表1：waybills（运单表，含揽收与签收时间）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| waybill_no | VARCHAR(20) | 运单号，主键 |
| line_id | VARCHAR(20) | 承运线路 |
| pickup_time | DATETIME | 揽收时间 |
| signed_time | DATETIME | 签收时间，未签收为NULL |
| create_time | DATETIME | 下单时间 |

示例数据：

| waybill_no | line_id | pickup_time | signed_time | create_time |
|---|---|---|---|---|
| WB2026100081 | L001 | 2026-10-22 09:00:00 | 2026-10-23 10:00:00 | 2026-10-22 08:00:00 |
| WB2026100082 | L001 | 2026-10-22 10:00:00 | 2026-10-24 11:30:00 | 2026-10-22 09:30:00 |
| WB2026100083 | L002 | 2026-10-22 11:00:00 | NULL | 2026-10-22 10:00:00 |
| WB2026100084 | L002 | 2026-10-22 14:00:00 | 2026-10-23 16:20:00 | 2026-10-22 13:00:00 |
| WB2026100085 | L003 | 2026-10-22 15:00:00 | 2026-10-22 20:10:00 | 2026-10-22 14:30:00 |

**表2：complaints（投诉表）**，结构与WL-24一致（complaint_id / waybill_no / courier_id / complaint_type / complaint_time）。

示例数据：

| complaint_id | waybill_no | courier_id | complaint_type | complaint_time |
|---|---|---|---|---|
| 8001 | WB2026100082 | CR301 | 延误 | 2026-10-24 15:00:00 |
| 8002 | WB2026100083 | CR302 | 延误 | 2026-10-25 09:00:00 |
| 8003 | WB2026100084 | CR302 | 态度 | 2026-10-24 10:00:00 |
| 8004 | WB2026100085 | CR303 | 其他 | 2026-10-23 12:00:00 |
| 8005 | WB2026100081 | CR301 | 态度 | 2026-10-24 18:00:00 |

### 3. 解题思路

指标口径：时效达成率 = 揽收到签收≤48小时的已签收票 / 已签收票（未签收票不进分母，避免在途票拖累，另列"签收率"补充观察）；投诉率 = 投诉票数 / 派件总票数，分母用全部运单（投诉可发生在签收前）。实现路径：解法一用两个 CTE 分别算线路级达成率与投诉率，JOIN 后以"全样本中位数"为切线（用窗口 AVG 或子查询求中位数），CASE 打四象限标签并统计每象限线路数；解法二用纯多层子查询实现同样逻辑，对比 CTE 的可读性。**【面试高频】** 亮点在于切线取中位数而非拍脑袋绝对值：四象限是相对比较，用 PERCENT_RANK/中位数切分能自适应数据分布。

### 4. 参考解法

**解法一：双CTE + 中位数切线的四象限矩阵**

```sql
WITH line_ontime AS (        -- 第一步：每条线路的48小时时效达成率
    SELECT
        line_id,
        COUNT(*)                                                        AS signed_cnt,      -- 已签收票=分母
        SUM(CASE WHEN TIMESTAMPDIFF(HOUR, pickup_time, signed_time) <= 48
                 THEN 1 ELSE 0 END)                                     AS ontime_cnt,      -- 48h内签收票=分子
        ROUND(SUM(CASE WHEN TIMESTAMPDIFF(HOUR, pickup_time, signed_time) <= 48
                       THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2)        AS ontime_rate_pct  -- 达成率
    FROM waybills
    WHERE create_time >= '2026-10-01' AND create_time < '2026-11-01'
      AND signed_time IS NOT NULL                                             -- 口径：仅已签收票进入达成率
    GROUP BY line_id
),
line_cmp AS (                -- 第二步：每条线路的投诉率（分母=全部运单）
    SELECT
        w.line_id,
        COUNT(DISTINCT w.waybill_no)                                    AS bill_cnt,        -- 分母：去重运单
        COUNT(DISTINCT c.waybill_no)                                    AS cmp_bill_cnt,    -- 被投诉的票数
        ROUND(COUNT(DISTINCT c.waybill_no) * 100.0 / COUNT(DISTINCT w.waybill_no), 2) AS cmp_rate_pct
    FROM waybills w
    LEFT JOIN complaints c ON c.waybill_no = w.waybill_no               -- LEFT JOIN保住零投诉线路
    WHERE w.create_time >= '2026-10-01' AND w.create_time < '2026-11-01'
    GROUP BY w.line_id
),
med AS (                     -- 第三步：窗口行号求中位数切线（MySQL无PERCENTILE_CONT，取中间位近似）
    SELECT
        MAX(CASE WHEN rn_o = CEIL((cnt_all + 1) / 2.0)
                 THEN ontime_rate_pct END)                       AS med_ontime,  -- 达成率中位切线（偶数取上中位近似）
        MAX(CASE WHEN rn_c = CEIL((cnt_all + 1) / 2.0)
                 THEN cmp_rate_pct END)                          AS med_cmp      -- 投诉率中位切线
    FROM (
        SELECT
            o.line_id,
            o.ontime_rate_pct,
            x.cmp_rate_pct,
            ROW_NUMBER() OVER (ORDER BY o.ontime_rate_pct)       AS rn_o,        -- 达成率升序行号
            ROW_NUMBER() OVER (ORDER BY x.cmp_rate_pct)          AS rn_c,        -- 投诉率升序行号
            COUNT(*)     OVER ()                                 AS cnt_all      -- 参评线路总数
        FROM line_ontime o
        JOIN line_cmp x ON x.line_id = o.line_id                                 -- 双指标齐备的线路才参评
    ) t
),
merged AS (                  -- 第四步：双指标贴上切线值
    SELECT
        o.line_id, o.ontime_rate_pct, x.cmp_rate_pct, x.bill_cnt,
        m.med_ontime, m.med_cmp
    FROM line_ontime o
    JOIN line_cmp x ON x.line_id = o.line_id                                 -- 线路内连接：双指标齐备才评级
    CROSS JOIN med m                                                         -- 切线一行，贴到每条线路
)
SELECT
    CASE
        WHEN ontime_rate_pct >= med_ontime AND cmp_rate_pct <= med_cmp THEN '双优_标杆'
        WHEN ontime_rate_pct <  med_ontime AND cmp_rate_pct <= med_cmp THEN '时效差_投诉可控'
        WHEN ontime_rate_pct >= med_ontime AND cmp_rate_pct >  med_cmp THEN '时效好_投诉偏高'
        ELSE '双差_优先整改'                                                  -- 最危险象限
    END                                                  AS 象限,
    COUNT(*)                                             AS 线路数,
    ROUND(AVG(ontime_rate_pct), 2)                       AS 平均达成率_pct,     -- 象限内均值辅助解读
    ROUND(AVG(cmp_rate_pct), 2)                          AS 平均投诉率_pct,
    SUM(bill_cnt)                                        AS 覆盖票量            -- 象限的业务体量权重
FROM merged
GROUP BY 象限
ORDER BY FIELD(象限, '双差_优先整改', '时效差_投诉可控', '时效好_投诉偏高', '双优_标杆');
```

结果解读："双差_优先整改"象限的线路进入季度整改清单，"双优_标杆"沉淀为推荐运力；"覆盖票量"提醒决策者小线路双差不代表全局风险，应乘票量看影响面。

**解法二：多层子查询版（不使用CTE，考核同构改写能力）**

```sql
SELECT
    q.象限, COUNT(*) AS 线路数,
    ROUND(AVG(q.ontime_rate_pct), 2) AS 平均达成率_pct,
    ROUND(AVG(q.cmp_rate_pct), 2)    AS 平均投诉率_pct
FROM (
    SELECT                                                              -- 第二层：贴上切线并打象限标签
        m.line_id, m.ontime_rate_pct, m.cmp_rate_pct,
        CASE
            WHEN m.ontime_rate_pct >= a.med_ontime AND m.cmp_rate_pct <= b.med_cmp THEN '双优_标杆'
            WHEN m.ontime_rate_pct <  a.med_ontime AND m.cmp_rate_pct <= b.med_cmp THEN '时效差_投诉可控'
            WHEN m.ontime_rate_pct >= a.med_ontime AND m.cmp_rate_pct >  b.med_cmp THEN '时效好_投诉偏高'
            ELSE '双差_优先整改'                                                 -- 双指标都落在差的一侧
        END                                              AS 象限
    FROM (                                                              -- 第三层：合并双指标的派生表
        SELECT o.line_id, o.ontime_rate_pct, x.cmp_rate_pct
        FROM (SELECT line_id,                                                  -- 4a：线路级达成率
                     ROUND(SUM(CASE WHEN TIMESTAMPDIFF(HOUR, pickup_time, signed_time) <= 48 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS ontime_rate_pct
              FROM waybills
              WHERE signed_time IS NOT NULL
                AND create_time >= '2026-10-01' AND create_time < '2026-11-01'
              GROUP BY line_id) o
        JOIN (SELECT w.line_id,                                                -- 4b：线路级投诉率
                     ROUND(COUNT(DISTINCT c.waybill_no) * 100.0 / COUNT(DISTINCT w.waybill_no), 2) AS cmp_rate_pct
              FROM waybills w
              LEFT JOIN complaints c ON c.waybill_no = w.waybill_no
              WHERE w.create_time >= '2026-10-01' AND w.create_time < '2026-11-01'
              GROUP BY w.line_id) x ON x.line_id = o.line_id
    ) m
    CROSS JOIN (                                                         -- 3b：达成率中位切线（内部又嵌两层）
        SELECT MAX(CASE WHEN rn_o = CEIL((cnt_all + 1) / 2.0)
                        THEN ontime_rate_pct END)        AS med_ontime   -- 中间位近似中位数
        FROM (SELECT ROW_NUMBER() OVER (ORDER BY ontime_rate_pct) AS rn_o, -- 4c：给达成率清单编行号
                     COUNT(*) OVER ()                        AS cnt_all,
                     ontime_rate_pct
              FROM (SELECT line_id,                                           -- 5a：达成率聚合（与4a重复！无CTE只能重写）
                           ROUND(SUM(CASE WHEN TIMESTAMPDIFF(HOUR, pickup_time, signed_time) <= 48 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS ontime_rate_pct
                    FROM waybills
                    WHERE signed_time IS NOT NULL
                      AND create_time >= '2026-10-01' AND create_time < '2026-11-01'
                    GROUP BY line_id) t1
           ) z1
    ) a
    CROSS JOIN (                                                         -- 3c：投诉率中位切线（同样整体重复一遍）
        SELECT MAX(CASE WHEN rn_c = CEIL((cnt_all + 1) / 2.0)
                        THEN cmp_rate_pct END)           AS med_cmp
        FROM (SELECT ROW_NUMBER() OVER (ORDER BY cmp_rate_pct) AS rn_c,     -- 4d：给投诉率清单编行号
                     COUNT(*) OVER ()                        AS cnt_all,
                     cmp_rate_pct
              FROM (SELECT w2.line_id,                                        -- 5b：投诉率聚合（与4b重复！）
                           ROUND(COUNT(DISTINCT c2.waybill_no) * 100.0 / COUNT(DISTINCT w2.waybill_no), 2) AS cmp_rate_pct
                    FROM waybills w2
                    LEFT JOIN complaints c2 ON c2.waybill_no = w2.waybill_no
                    WHERE w2.create_time >= '2026-10-01' AND w2.create_time < '2026-11-01'
                    GROUP BY w2.line_id) t2
           ) z2
    ) b
) q
GROUP BY q.象限
ORDER BY FIELD(q.象限, '双差_优先整改', '时效差_投诉可控', '时效好_投诉偏高', '双优_标杆');
```

结果解读：数值与解法一完全一致（同一套聚合与同一种中位数近似）；但无 CTE 时"达成率/投诉率"的聚合逻辑被迫在切线子查询里整体重写一遍（5a/5b 与 4a/4b 重复），嵌套五层、别名绕行，可读性与可维护性明显劣于 CTE 版，这正是面试官想听到的对比结论：CTE 分层是复杂指标的默认写法。

### 5. 性能分析与优化

解法一的两个 CTE 各自是线路级小聚合（行数=线路数），med CTE 的窗口排序也只发生在线路级小结果集上，整体代价集中在 waybills 按月过滤后的两次聚合与 complaints 的 LEFT JOIN；解法二无 CTE 可复用，达成率/投诉率聚合逻辑在切线子查询里整体重写了一遍，MySQL 8.0 对相同子查询未必共享物化，存在重复扫描风险。优化建议：① waybills 上建 `(create_time, line_id)` 索引并按月分区，complaints 建 `(waybill_no)` 索引支撑 LEFT JOIN；② 达成率/投诉率的线路日汇总应落 dws 表，评级层只读月级聚合；③ 中位数切线按解法一的方式一次 CTE 物化两行切线值再 CROSS JOIN，消除重复子查询；④ 线路极多时输出改 `WHERE 象限='双差_优先整改'` 直出整改清单。

### 6. 面试延伸考点

- **四象限切线为什么常用中位数而不是固定阈值？** 要点：中位数切分保证每期都有相对红黑榜、自适应分布漂移，适合内评比优汰劣；固定阈值适合对外服务承诺，两种口径服务不同目的，汇报时应说明选择理由。
- **时效达成率的分母含未签收票吗？** 要点：不含，达成率与签收率是两个指标，混入在途票会让新开线路达成率虚低；严谨做法是"已到末端未签收超时"单独列观察。
- **投诉归因到线路还是快递员？** 要点：同一投诉双维度都统计，但用途不同——线路评级看系统性问题（路由、时效），快递员绩效看个体服务，考核表要防止用线路投诉率扣个人绩效。
- **如果要求四象限同时显示散点明细（每条线路一个点），SQL怎么组织？** 要点：输出 line_id + 双指标 + 象限标签的明细长表交给 BI 画散点，SQL 不做矩阵聚合，体现"取数与展示分层"的意识。

### 7. 业务拓展思考

四象限评级是线路全生命周期管理的中枢：双差线路触发整改与备选承运商引入，双优线路获得大客户推荐与运力倾斜，两个过渡象限分别对应"时效专项"与"服务专项"。口径延展上，可加入第三维"单票成本"做九宫格评级，防止只管体验不管成本；按季度滚动评级还能观察线路的象限迁移轨迹，连续两季双差即启动线路重构评审。与WL-21的装载率交叉后，还能识别"低载且双差"的线路，直接给出"整合重组"而非"整改"的更强建议。

## WL-28 每条线路的日均班次与满载班次占比

### 1. 业务背景

线路的运力供给强度由两个数共同刻画：日均班次（跑得勤不勤）与满载班次占比（跑得满不满）。干线调度主管（谁）在排班计划月度校准时（何时），需要每条线路的日均班次数、平均装载率与满载班次占比（什么），用来判断哪些线路该加密班次（单量涨但班次少）、哪些该减班（班次多但普遍不满载）（为什么）。**【避坑指南】** "日均"的分母是运营天数而非自然天数，且应用 COUNT(DISTINCT 日期) 从班次表反推；若线路当月有停运日，用自然天数会人为压低日均班次。

### 2. 表结构说明

**表1：trips（干线班次表）**，结构与WL-21一致（trip_id / line_id / depart_time / vehicle_type / rated_load_kg）。

示例数据：

| trip_id | line_id | depart_time | vehicle_type | rated_load_kg |
|---|---|---|---|---|
| T2026102501 | L001 | 2026-10-25 20:00:00 | 17.5米 | 30000 |
| T2026102502 | L001 | 2026-10-25 23:30:00 | 9.6米 | 15000 |
| T2026102503 | L001 | 2026-10-26 20:10:00 | 17.5米 | 30000 |
| T2026102504 | L002 | 2026-10-25 22:00:00 | 9.6米 | 15000 |
| T2026102505 | L003 | 2026-10-26 21:00:00 | 17.5米 | 30000 |

**表2：trip_waybills（班次配载明细表）**，结构与WL-21一致（trip_id / waybill_no / weight_kg）。

示例数据：

| trip_id | waybill_no | weight_kg |
|---|---|---|
| T2026102501 | WB2026100091 | 27500.00 |
| T2026102502 | WB2026100092 | 5200.00 |
| T2026102503 | WB2026100093 | 18500.00 |
| T2026102504 | WB2026100094 | 9800.00 |
| T2026102505 | WB2026100095 | 26400.00 |

**表3：routes（线路主表）**，结构与WL-18一致（line_id / line_name / origin_city / dest_city）。

示例数据：

| line_id | line_name | origin_city | dest_city |
|---|---|---|---|
| L001 | 华东一线 | 上海 | 杭州 |
| L002 | 华东二线 | 上海 | 南京 |
| L003 | 华南一线 | 广州 | 深圳 |

### 3. 解题思路

分三层：第一层 CTE 按班次聚合实际载重与装载率（复用WL-21逻辑）；第二层按线路聚合出班次总数、有班天数、满载班次数（装载率≥90%记满载）；第三层计算日均班次 = 班次总数 / 有班天数，并给满载占比与平均装载率。解法一用 CTE 分层完成并 JOIN routes 补线路名；解法二用嵌套派生表改写，并额外用窗口 RANK 对线路按"日均班次×满载占比"综合排序，展示"供给强度画像"。易错点：有班天数用 `COUNT(DISTINCT DATE(depart_time))`，若要与日历对齐需 LEFT JOIN 日历表统计停运日；满载阈值90%是业务约定，双口径（重量/体积）时取更紧的那个。

### 4. 参考解法

**解法一：三层CTE（班次级→线路级）+ 线路名JOIN**

```sql
WITH trip_load AS (          -- 第一层：每班次的实际载重与装载率
    SELECT
        t.trip_id, t.line_id, t.rated_load_kg,
        DATE(t.depart_time)                              AS depart_date,     -- 发车日期，用于"有班天数"
        COALESCE(SUM(tw.weight_kg), 0)                   AS actual_kg,       -- 空车按0计
        ROUND(COALESCE(SUM(tw.weight_kg), 0) / t.rated_load_kg, 4) AS load_ratio
    FROM trips t
    LEFT JOIN trip_waybills tw ON tw.trip_id = t.trip_id
    WHERE t.depart_time >= '2026-10-01' AND t.depart_time < '2026-11-01'
    GROUP BY t.trip_id, t.line_id, t.rated_load_kg, DATE(t.depart_time)
),
line_agg AS (                -- 第二层：线路级供给与满载统计
    SELECT
        line_id,
        COUNT(*)                                            AS 班次总数,
        COUNT(DISTINCT depart_date)                         AS 有班天数,        -- 分母口径：只数真实发车的日子
        SUM(CASE WHEN load_ratio >= 0.9 THEN 1 ELSE 0 END)  AS 满载班次数,      -- ≥90%记满载（业务约定阈值）
        ROUND(SUM(actual_kg) / SUM(rated_load_kg), 4)       AS 平均装载率_加权  -- 线路总装载率
    FROM trip_load
    GROUP BY line_id
)
SELECT
    la.line_id,                                                             -- 线路
    r.line_name,                                                            -- 线路名
    la.班次总数,
    la.有班天数,
    ROUND(la.班次总数 * 1.0 / la.有班天数, 2)            AS 日均班次,         -- 核心：班次/有班天数
    la.满载班次数,
    ROUND(la.满载班次数 * 100.0 / la.班次总数, 1)        AS 满载班次占比_pct,  -- 满 不满的结构
    la.平均装载率_加权,
    ROUND(RANK() OVER (ORDER BY la.班次总数 * 1.0 / la.有班天数 DESC), 0) AS 日均班次排名 -- 供给强度排名
FROM line_agg la
JOIN routes r ON r.line_id = la.line_id                                      -- 补线路名
ORDER BY 日均班次 DESC;
```

结果解读：日均班次高但满载占比低的线路是"过度供给"，应减班或换小车；日均班次低且满载占比高的线路是"供给不足"，优先加密班次。

**解法二：嵌套派生表 + 综合画像排序（不依赖CTE的等价改写）**

```sql
SELECT
    p.line_id,                                                              -- 线路
    r.line_name,
    p.班次总数,
    ROUND(p.班次总数 * 1.0 / p.有班天数, 2)              AS 日均班次,
    ROUND(p.满载班次数 * 100.0 / p.班次总数, 1)          AS 满载班次占比_pct,
    p.平均装载率_加权,
    RANK() OVER (ORDER BY (p.班次总数 * 1.0 / p.有班天数) * (p.满载班次数 * 1.0 / p.班次总数) DESC) AS 供给强度综合排名 -- 日均班次×满载占比的乘积画像
FROM (
    SELECT                                                                  -- 第二层：从班次级聚合到线路级
        q.line_id,
        COUNT(*)                                            AS 班次总数,
        COUNT(DISTINCT q.depart_date)                       AS 有班天数,
        SUM(CASE WHEN q.load_ratio >= 0.9 THEN 1 ELSE 0 END) AS 满载班次数,
        ROUND(SUM(q.actual_kg) / SUM(q.rated_load_kg), 4)   AS 平均装载率_加权
    FROM (
        SELECT                                                              -- 第三层：班次级装载率
            t.trip_id, t.line_id,
            DATE(t.depart_time)                             AS depart_date,
            COALESCE(SUM(tw.weight_kg), 0)                  AS actual_kg,
            t.rated_load_kg,
            COALESCE(SUM(tw.weight_kg), 0) / t.rated_load_kg AS load_ratio
        FROM trips t
        LEFT JOIN trip_waybills tw ON tw.trip_id = t.trip_id
        WHERE t.depart_time >= '2026-10-01' AND t.depart_time < '2026-11-01'
        GROUP BY t.trip_id, t.line_id, DATE(t.depart_time), t.rated_load_kg
    ) q
    GROUP BY q.line_id
) p
JOIN routes r ON r.line_id = p.line_id
WHERE p.班次总数 >= 20                                                       -- HAVING语义前置：样本太小的线路不参与排名
ORDER BY 供给强度综合排名;
```

结果解读：综合排名=日均班次×满载占比，乘积高代表"又勤又满"的黄金线路；样本量门槛（≥20班）防止只跑了两班的临时线霸榜。

### 5. 性能分析与优化

两解法结构等价：主体是 trips LEFT JOIN trip_waybills 后的两层 GROUP BY，行数从班次×票收缩到班次再到线路，代价集中在配载表按 trip_id 的聚合；窗口 RANK 作用在个位数的线路行上可忽略。优化建议：① trip_waybills 的 `(trip_id)` 索引必备，trips 的 `(depart_time, line_id)` 支撑月份过滤；② 若线路日均班次是常设报表，可先按 `(line_id, DATE(depart_time))` 聚出"日班次表"再聚合，天然解决"有班天数"口径并便于对齐日历；③ 满载阈值与车型相关（17.5米与9.6米装载习惯不同），可按 vehicle_type 分组设阈值或先分车型统计再汇总；④ 停运日信息若在运营计划表中，应 JOIN 进来把"计划有班未执行"的缺勤班次单列，区分"无需求"与"执行失败"。

### 6. 面试延伸考点

- **日均班次的分母为什么不能直接用 DATEDIFF+1？** 要点：自然天数包含未运营的停运日，会稀释供给强度；正确分母是 COUNT(DISTINCT 发车日期)，若要暴露停运问题，再用日历表对照得出"计划班次日缺勤数"。
- **满载阈值90%怎么来的？要按车型区分吗？** 要点：来自安全余量与装载作业时间约束，大车型与冷链等特殊车型标准不同；SQL中阈值应参数化到维表，硬编码是报表维护隐患。
- **班次延误到次日凌晨发车，日期怎么算？** 要点：按计划发车日期归属班次而非实际 DATE(depart_time)，否则晚点班次会被切到错误的一天，供给统计抖动；实现上以计划发车时间为准。
- **体积满载与重量满载不一致的班次怎么归类？** 要点：与WL-21同源问题，取"利用率较小者"是否达到阈值取决于约束瓶颈口径，通常以发车前核载单的瓶颈维度为准。

### 7. 业务拓展思考

"日均班次×满载占比"矩阵是干线排班的双向调节器：加密度（供给不足象限）要同步评估末端分拨的到车处理能力，防止"上量即爆仓"；减密度（过度供给象限）释放的运力可反哺新开线路。口径延展上，可拆"周中/周末"节奏差异（电商件周末峰谷明显），把日均班次细化为分星期几的班表；再与WL-26的大促预测联动，可在预测低估网点对应的线路上提前加密班次，把预测洞察转化为调度动作。

## WL-29 各仓库发货到揽收等待时长排名

### 1. 业务背景

商家发货后，快递员/揽收车多久来把货取走，是仓储与快递协同的第一段体验，也是商家选择合作快递的重要依据。仓配协同专员（谁）在月度服务复盘时（何时），需要每个仓库"出库扫描→揽收扫描"的平均等待时长，并做全网排名（什么），用来约谈等待时长最长的仓库所在区域的揽收排班、调整揽收车频次，并为商务谈判提供各仓服务水平数据（为什么）。

### 2. 表结构说明

**表1：warehouses（仓库主数据表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| wh_id | VARCHAR(20) | 仓库编码，主键 |
| wh_name | VARCHAR(50) | 仓库名称 |
| region | VARCHAR(20) | 所属大区 |
| city | VARCHAR(20) | 所在城市 |

示例数据：

| wh_id | wh_name | region | city |
|---|---|---|---|
| WH001 | 上海东仓 | 华东 | 上海 |
| WH002 | 上海西仓 | 华东 | 上海 |
| WH003 | 广州南仓 | 华南 | 广州 |
| WH004 | 北京北仓 | 华北 | 北京 |
| WH005 | 成都仓 | 西南 | 成都 |

**表2：scan_events（扫描事件表）**，本题用到 OUTBOUND出库 与 PICKUP揽收 两种类型。

| 字段名 | 类型 | 含义 |
|---|---|---|
| event_id | BIGINT | 事件ID |
| waybill_no | VARCHAR(20) | 运单号 |
| scan_type | VARCHAR(20) | OUTBOUND出库 / PICKUP揽收 等 |
| scan_time | DATETIME | 扫描时间 |
| site_id | VARCHAR(20) | 扫描场地 |

示例数据：

| event_id | waybill_no | scan_type | scan_time | site_id |
|---|---|---|---|---|
| 9001 | WB2026100101 | OUTBOUND | 2026-10-25 10:00:00 | WH001 |
| 9002 | WB2026100101 | PICKUP | 2026-10-25 13:30:00 | ST601 |
| 9003 | WB2026100102 | OUTBOUND | 2026-10-25 10:20:00 | WH001 |
| 9004 | WB2026100102 | PICKUP | 2026-10-25 14:00:00 | ST601 |
| 9005 | WB2026100103 | OUTBOUND | 2026-10-25 11:00:00 | WH003 |

### 3. 解题思路

口径：等待时长 = 该票最早揽收扫描 − 该票最早出库扫描；仅统计两节点齐全的票，缺揽收的票单独统计"漏揽率"而不是静默剔除。粒度先到"仓库×运单"算每票等待，再聚到仓库求平均与P90，最后排名。解法一用条件聚合取节点 + RANK/DENSE_RANK/ROW_NUMBER 三种排名并列输出，借机辨析三者差异；解法二用自连接（出库事件 JOIN 同单揽收事件）取节点，并在仓库排名外按大区用 ROW_NUMBER 取各大区 TopN，展示"分组内TopN"套路。**【面试高频】** 排名方向要主动声明：等待越短越好，所以排名第1应给最短者（升序）。

### 4. 参考解法

**解法一：条件聚合 + 三种排名函数并列辨析**

```sql
WITH bill_wait AS (          -- 第一步：每票的出库→揽收等待（出库扫描发生在仓库场地，可据此映射归属仓）
    SELECT
        e.waybill_no,
        MIN(CASE WHEN e.scan_type = 'OUTBOUND' THEN e.scan_time END) AS outbound_time, -- 最早出库扫描
        MIN(CASE WHEN e.scan_type = 'OUTBOUND' THEN e.site_id   END) AS outbound_site, -- 出库扫描所在场地=归属仓编码
        MIN(CASE WHEN e.scan_type = 'PICKUP'   THEN e.scan_time END) AS pickup_time    -- 最早揽收扫描
    FROM scan_events e
    WHERE e.scan_time >= '2026-10-01' AND e.scan_time < '2026-11-01'         -- 统计月
      AND e.scan_type IN ('OUTBOUND','PICKUP')                                -- 类型白名单，减少参与行数
    GROUP BY e.waybill_no
),
wh_stat AS (                 -- 第二步：按出库场地挂仓库维表，聚到仓库粒度
    SELECT
        w.wh_id, w.wh_name, w.region,                                       -- 仓库与大区
        COUNT(*)                                             AS 有效票数,    -- 分母：两节点齐全
        ROUND(AVG(TIMESTAMPDIFF(MINUTE, b.outbound_time, b.pickup_time))/60.0, 2) AS 平均等待_h,
        SUM(CASE WHEN TIMESTAMPDIFF(MINUTE, b.outbound_time, b.pickup_time) > 240
                 THEN 1 ELSE 0 END)                          AS 超4小时票数 -- 服务红线样本
    FROM bill_wait b
    JOIN warehouses w ON w.wh_id = b.outbound_site                           -- 出库场地即仓库编码
    WHERE TIMESTAMPDIFF(MINUTE, b.outbound_time, b.pickup_time) >= 0         -- 防御：揽收早于出库为倒挂脏数据，剔除
    GROUP BY w.wh_id, w.wh_name, w.region
)
SELECT
    wh_id, wh_name, region, 有效票数, 平均等待_h, 超4小时票数,
    ROW_NUMBER() OVER (ORDER BY 平均等待_h ASC)  AS rn_严格唯一,             -- 升序：等待最短=第1名
    RANK()       OVER (ORDER BY 平均等待_h ASC)  AS rk_可并列跳号,           -- 并列同名次，下一名跳号
    DENSE_RANK() OVER (ORDER BY 平均等待_h ASC)  AS drk_可并列不跳号          -- 并列同名次，连续编号
FROM wh_stat
ORDER BY 平均等待_h ASC;
```

结果解读：三个排名列数值相同但并列行为不同，汇报默认用 RANK；平均等待最长的仓库配合"超4小时票数"判断是普遍慢还是个别爆发，约谈数据更具说服力。

> **Hive/Spark SQL 差异**：出库/揽收双节点聚合在亿级事件表上应先按运单去重再聚合；Hive 中 TIMESTAMPDIFF 换成 unix_timestamp 差值，排名窗口写法一致，大区TopN可借助 `DISTRIBUTE BY region SORT BY` 提升并行度。

**解法二：自连接取节点 + 大区分组内TopN**

```sql
WITH ob AS (                 -- 第一步：出库扫描按票去重（GROUP BY取最早一次，防重复出库放大行数）
    SELECT
        waybill_no,
        MIN(scan_time) AS outbound_time,                                    -- 最早出库时间
        MIN(site_id)   AS outbound_site                                     -- 出库场地即归属仓（多仓出库属脏数据，明细另行核查）
    FROM scan_events
    WHERE scan_type = 'OUTBOUND'
      AND scan_time >= '2026-10-01' AND scan_time < '2026-11-01'
    GROUP BY waybill_no
),
pair AS (                    -- 第二步：相关子查询找同单"不早于出库"的最早揽收（自连接取节点的语义）
    SELECT
        o.waybill_no,
        o.outbound_time,
        o.outbound_site,
        (SELECT MIN(b.scan_time)
           FROM scan_events b
          WHERE b.waybill_no = o.waybill_no                                 -- 同一运单
            AND b.scan_type = 'PICKUP'                                      -- 揽收事件
            AND b.scan_time >= o.outbound_time)             AS pickup_time  -- 必须不早于出库，防倒挂
    FROM ob o
),
clean AS (                   -- 第三步：清洗出有效等待样本
    SELECT
        p.waybill_no,
        p.outbound_site,
        TIMESTAMPDIFF(MINUTE, p.outbound_time, p.pickup_time)/60.0 AS wait_h
    FROM pair p
    WHERE p.pickup_time IS NOT NULL                                          -- 缺揽收的票进"漏揽"口径，不进均值
      AND p.pickup_time >= p.outbound_time                                   -- 双保险防倒挂
),
ranked AS (                  -- 第四步：仓库均值 + 大区内ROW_NUMBER排名
    SELECT
        w.wh_id, w.wh_name, w.region,
        COUNT(*)                          AS 有效票数,
        ROUND(AVG(c.wait_h), 2)           AS 平均等待_h,
        ROW_NUMBER() OVER (PARTITION BY w.region                                 -- 大区内独立排名
                           ORDER BY AVG(c.wait_h) ASC)        AS 大区内排名      -- 升序：等待最短=区内第1名
    FROM clean c
    JOIN warehouses w ON w.wh_id = c.outbound_site                           -- 出库场地挂仓库维表
    GROUP BY w.wh_id, w.wh_name, w.region
)
SELECT wh_id, wh_name, region, 有效票数, 平均等待_h, 大区内排名
FROM ranked
WHERE 大区内排名 <= 2                                                        -- 分组内TopN：每个大区取前2名仓
ORDER BY region, 大区内排名;
```

结果解读：每个大区独立输出最慢的前2个仓，区域负责人各领各的清单；此版完全不依赖条件聚合，用"GROUP BY取首扫 + 相关子查询找下一节点"复现同样结果，但相关子查询对每票都要回事件表定位，索引要求更高。

### 5. 性能分析与优化

解法一整体最优：类型白名单过滤后一次 GROUP BY 压到运单粒度，再聚合到仓库，索引 `(scan_type, scan_time)` 与 `(waybill_no, scan_time)` 双管齐下；解法二的相关子查询对每个出库事件都要在事件表内找 MIN(PICKUP)，依赖 `(waybill_no, scan_type, scan_time)` 复合索引，否则性能塌方。优化建议：① 事件表按月分区并强制时间谓词；② 节点宽表（出库时间、揽收时间已在行内）落日增量 dws 表，报表层零窗口；③ 漏揽票（缺PICKUP）用 LEFT JOIN 单独统计漏揽率，与等待时长并排输出，防止单看均值忽略服务缺失；④ P90等待用窗口法（ROW_NUMBER/COUNT 取第 ceil(0.9n) 位）或 NTILE(10) 桶近似，比均值更贴近商家体验。

### 6. 面试延伸考点

- **RANK、DENSE_RANK、ROW_NUMBER 三者何时选用？** 要点：ROW_NUMBER 保证名次唯一适合取严格TopN；RANK 允许并列且跳号，适合排行榜语义；DENSE_RANK 并列不跳号，适合分档；取"并列都进TopN"时用 RANK 且外层过滤 <=N。
- **揽收扫描早于出库扫描的倒挂数据怎么处理？** 要点：先查数据源（设备时钟漂移、补录），统计口径上剔除并输出倒挂票数做数据质量监控，绝不能静默参与计算产生负等待。
- **等待时长的P90怎么算？** 要点：MySQL 8.0 没有 PERCENTILE_CONT 有序集聚合，可用窗口法（ROW_NUMBER/COUNT 取第 ceil(0.9n) 位）或 NTILE(10) 桶近似，Hive 直接用 percentile_approx；P90比均值更能反映"最差商家体验"。
- **大区内TopN和全网TopN的SQL差异？** 要点：窗口 PARTITION BY region 内 ROW_NUMBER 再外层 <=N 即分组内TopN；全网TopN只需全局 ORDER BY + LIMIT，本质是窗口分区键的有无。

### 7. 业务拓展思考

等待时长排名直接驱动揽收排班与车辆频次调整，并可延伸为商家端可视化产品（发货等待看板），提升商务签约竞争力。口径延展上，等待起点可前移到"商家波形出库完成"，终点可细分为"揽收员到场"与"离场"，区分"人到了装得慢"与"人没来"；与WL-25的网点密度、WL-20的班次效率交叉，能识别"等待长是运力不足还是交接低效"。把排名做成月度趋势后，还可评估揽收改革措施的实际效果，形成服务改进闭环。

## WL-30 运单各环节停留时长明细（每段扫描间隔）

### 1. 业务背景

时效异常工单的处理需要"逐票逐段"的证据链：客户投诉一票件卡了三天，运营要能拿出这票件在哪个场地停了多久。申诉处理专员（谁）在处理时效申诉与异常工单时（何时），需要把单票运单的全部扫描按时间排序，逐段算出相邻扫描的停留时长并标记异常段（什么），用于向客户或商家解释延误责任归属、向责任场地发起考核（为什么）。与WL-16的"聚合拆解"不同，本题要求保留"一票多段"的明细形态，并处理乱序、同秒重复扫描等脏数据。

### 2. 表结构说明

**表1：scan_events（扫描事件表）**，全链路五类扫描 + 任意中间场地扫描均可能出现。

| 字段名 | 类型 | 含义 |
|---|---|---|
| event_id | BIGINT | 事件ID，自增 |
| waybill_no | VARCHAR(20) | 运单号 |
| scan_type | VARCHAR(20) | 扫描类型：PICKUP/LINE_HAUL_OUT/ARRIVAL_DEST/DELIVERING/SIGNED等 |
| scan_time | DATETIME | 扫描时间 |
| site_id | VARCHAR(20) | 扫描场地编码 |

示例数据：

| event_id | waybill_no | scan_type | scan_time | site_id |
|---|---|---|---|---|
| 10001 | WB2026100111 | PICKUP | 2026-10-25 09:00:00 | ST701 |
| 10002 | WB2026100111 | LINE_HAUL_OUT | 2026-10-25 09:00:00 | ST701 |
| 10003 | WB2026100111 | ARRIVAL_DEST | 2026-10-26 02:30:00 | WH009 |
| 10004 | WB2026100111 | LINE_HAUL_OUT | 2026-10-25 15:00:00 | WH001 |
| 10005 | WB2026100111 | SIGNED | 2026-10-26 18:40:00 | ST702 |

**表2：stay_threshold（环节停留阈值表）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| stage_name | VARCHAR(30) | 段名 |
| max_stay_hours | DECIMAL(5,1) | 该段允许的最长停留（小时），超出即异常 |

示例数据：

| stage_name | max_stay_hours |
|---|---|
| 揽收场地停留 | 10.0 |
| 干线在途 | 14.0 |
| 分拨停留 | 8.0 |
| 派送执行 | 5.0 |
| 其他 | 24.0 |

### 3. 解题思路

**【避坑指南】** 三件事必须先做：一是去重——同单同秒重复扫描（批量扫描设备回传）会让"零分钟停留"污染明细，用 ROW_NUMBER 按 (waybill_no, scan_time) 去重；二是纠序——上表示例中 event_id=10004 的扫描时间早于 10003，明细必须按 scan_time 排序重建顺序，LEAD 的下一跳由时间决定而非事件ID；三是终点处理——签收是最后一跳，LEAD 结果为 NULL，段明细里排除或标记为"终态"。段名用 CASE 按当前扫描类型命名，阈值表 LEFT JOIN 判断异常停留。解法一用 LEAD 窗口一行出全段明细；解法二用相关子查询自连接取"严格大于当前时间的最近一跳"，展示无窗口函数时代的等价写法，并附段级汇总验证。

### 4. 参考解法

**解法一：ROW_NUMBER去重 + LEAD窗口逐段明细（推荐）**

```sql
WITH dedup AS (              -- 第一步：按"运单+扫描时间"去重，同秒重复扫描只留一条
    SELECT
        waybill_no, scan_type, scan_time, site_id,
        ROW_NUMBER() OVER (PARTITION BY waybill_no, scan_time                -- 同一秒的多条扫描视为一次操作
                           ORDER BY event_id ASC)                AS rn        -- 保留事件ID最小（最早写入）的一条
    FROM scan_events
    WHERE scan_time >= '2026-10-01' AND scan_time < '2026-11-01'             -- 统计月
),
seq AS (                     -- 第二步：按运单内时间排序，LEAD取下一跳
    SELECT
        d.waybill_no, d.scan_type, d.scan_time, d.site_id,
        LEAD(d.scan_time) OVER (PARTITION BY d.waybill_no
                                ORDER BY d.scan_time, d.site_id) AS next_time, -- 下一扫描时间（时间同值再按场地稳定排序）
        LEAD(d.site_id)   OVER (PARTITION BY d.waybill_no
                                ORDER BY d.scan_time, d.site_id) AS next_site  -- 下一扫描场地
    FROM dedup d
    WHERE d.rn = 1                                                           -- 只留去重后记录
)
SELECT
    s.waybill_no,                                                            -- 运单号
    s.scan_time                                          AS 段开始时间,
    CASE s.scan_type                                                          -- 当前扫描翻译为段名
         WHEN 'PICKUP'        THEN '揽收场地停留'
         WHEN 'LINE_HAUL_OUT' THEN '干线在途'
         WHEN 'ARRIVAL_DEST'  THEN '分拨停留'
         WHEN 'DELIVERING'    THEN '派送执行'
         ELSE '其他' END                                     AS 段名,
    s.site_id                                            AS 起始场地,
    s.next_site                                          AS 下一跳场地,
    ROUND(TIMESTAMPDIFF(MINUTE, s.scan_time, s.next_time)/60.0, 1) AS 停留小时, -- 本段停留=下一跳-当前
    CASE
        WHEN s.next_time IS NULL THEN '终态_无需判断'                         -- 签收后无下一跳
        WHEN ROUND(TIMESTAMPDIFF(MINUTE, s.scan_time, s.next_time)/60.0, 1)
             > COALESCE(t.max_stay_hours, 999)          THEN '异常停留'       -- 超阈值标记，无阈值的段给大值兜底
        ELSE '正常'
    END                                                  AS 停留判定,
    t.max_stay_hours                                     AS 段阈值_h
FROM seq s
LEFT JOIN stay_threshold t                                                    -- 阈值表按段名匹配
  ON t.stage_name = CASE s.scan_type
         WHEN 'PICKUP'        THEN '揽收场地停留'
         WHEN 'LINE_HAUL_OUT' THEN '干线在途'
         WHEN 'ARRIVAL_DEST'  THEN '分拨停留'
         WHEN 'DELIVERING'    THEN '派送执行'
         ELSE '其他' END
WHERE s.next_time IS NOT NULL OR s.scan_type = 'SIGNED';                      -- 保留到签收为止的完整链条
```

结果解读：每一行是"某票在某段从A场地到B场地停了多久"，异常停留列直接给出申诉定责证据；上表示例中 event_id=10004 的乱序记录会被时间排序自动归位到正确链路位置。

**解法二：相关子查询自连接取"最近下一跳"（无窗口等价写法）+ 段级汇总**

```sql
WITH first_hit AS (          -- 第一步：同秒去重——每票每秒只保留最早写入的一条
    SELECT waybill_no, scan_time, MIN(event_id) AS keep_id                  -- 同秒多条取MIN(event_id)，结果可复现
    FROM scan_events
    WHERE scan_time >= '2026-10-01' AND scan_time < '2026-11-01'
    GROUP BY waybill_no, scan_time                                           -- 键=运单+时间，保证后续JOIN唯一
),
base AS (                    -- 第二步：回表取被保留记录的完整字段
    SELECT f.waybill_no, f.scan_time, e.scan_type, e.site_id
    FROM first_hit f
    JOIN scan_events e ON e.event_id = f.keep_id                             -- 用主键回表，毫秒级
),
nxt AS (                     -- 第三步：自连接找每行"严格大于当前时间"的最近一跳
    SELECT a.waybill_no, a.scan_time AS cur_time,
           MIN(b.scan_time) AS next_time                                     -- MIN即最近下一跳（LEAD的等价表达）
    FROM base a
    JOIN base b
      ON b.waybill_no = a.waybill_no
     AND b.scan_time > a.scan_time                                           -- 严格大于，剔除同秒并列
    GROUP BY a.waybill_no, a.scan_time
)
SELECT
    g.waybill_no,                                                            -- 运单号
    g.scan_type,                                                             -- 当前环节
    g.scan_time,                                                             -- 段开始
    n.next_time,                                                             -- 下一跳时间
    ROUND(TIMESTAMPDIFF(MINUTE, g.scan_time, n.next_time)/60.0, 1) AS 停留小时,
    CASE
        WHEN TIMESTAMPDIFF(MINUTE, g.scan_time, n.next_time)/60.0
             > COALESCE((SELECT t.max_stay_hours FROM stay_threshold t        -- 段名映射到阈值
                          WHERE t.stage_name = CASE g.scan_type
                              WHEN 'PICKUP'        THEN '揽收场地停留'
                              WHEN 'LINE_HAUL_OUT' THEN '干线在途'
                              WHEN 'ARRIVAL_DEST'  THEN '分拨停留'
                              WHEN 'DELIVERING'    THEN '派送执行'
                              ELSE '其他' END), 999)       THEN '异常停留'
        ELSE '正常'
    END                                                  AS 停留判定
FROM base g
JOIN nxt n
  ON n.waybill_no = g.waybill_no AND n.cur_time = g.scan_time                -- 终态行无下一跳，自然被排除
ORDER BY g.waybill_no, g.scan_time;                                          -- 按时间还原链路顺序
```

结果解读：与解法一逐行对拍应完全一致；此写法把"找下一跳"表达为自连接+GROUP BY MIN，是理解 LEAD 语义的最佳教具，但自连接的中间结果约为事件数的平方级组合，生产上必须让 waybill_no+scan_time 索引生效并控制单票扫描数。

### 5. 性能分析与优化

解法一的窗口排序在每个运单分区内进行，索引 `(waybill_no, scan_time)` 可让 LEAD 走有序读，代价近似线性；解法二的自连接在"单票扫描数k"下产生 k×(k−1) 组合，个别被反复转寄的运单扫描上百条时会放大明显，相关子查询还随行数递增。优化建议：① 强制 `(waybill_no, scan_time)` 复合索引并按月分区；② 同秒去重优先在入库层（设备侧或ETL）完成，SQL层的去重是兜底；③ 段明细查询通常由工单触发、按单票取数，加 `WHERE waybill_no = ?` 后代价极小，全量跑批则改用解法一并在 dws 层落"段停留明细表"；④ 异常停留标记的阈值表 JOIN 键是表达式，可先在 CTE 中算好段名列再 JOIN，避免重复 CASE。

> **Hive/Spark SQL 差异**：Hive 同样支持 LEAD，但亿级事件表上建议先 `DISTRIBUTE BY waybill_no SORT BY scan_time`；同秒去重可用 `ROW_NUMBER() OVER (PARTITION BY waybill_no, scan_time ORDER BY event_id)`；自连接版在 Hive 上代价更高，基本不用于全量跑批。

### 6. 面试延伸考点

- **LEAD 的第三参数（默认值）在这里怎么用？** 要点：`LEAD(scan_time, 1, NULL)` 显式声明无下一跳返回NULL，避免隐式默认带来的歧义；签收行就是靠 NULL 判定为终态。
- **同秒重复扫描去重为什么按 event_id 取最小而不是任意一条？** 要点：同秒多条记录的 scan_type 可能不同（设备重复上报），取最早写入的事件ID保证结果可复现，任意取行在分布式引擎下结果不稳定。
- **回退扫描（签收后又出现派送扫描）在段明细里长什么样？** 要点：会形成"时间仍递增但环节倒退"的段，停留判定正常但业务异常，需按环节顺序编码校验单调性单独打标，不能只看时间间隔。
- **单票扫描可能上百条，明细查询怎么保证交互式响应？** 要点：按单取数走 `(waybill_no, scan_time)` 索引是点查；全量跑批则分区+窗口一次成型，切忌在循环中逐票查询。

### 7. 业务拓展思考

段级停留明细是时效归因的最细颗粒：向上可聚合复算WL-16的全链路时效与WL-17的环节超时率，保证"总账与明细账"一致；向下支撑自动定责（超时段的最后扫描场地即责任场地）与申诉自动化回复。口径延展上，可把"停留"细分为"工作时段停留"与"非工作时段停留"（夜间入库不算作业慢），剔除节假日效应；再按场地聚合异常停留率，就能生成场地的"拥堵画像"，指导分拨中心的产能扩建与班次错峰。
