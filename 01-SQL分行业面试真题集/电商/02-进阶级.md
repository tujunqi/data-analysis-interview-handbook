## EC-16 每个类目销售额Top3商品

### 1. 业务背景
品类运营每周要做类目资源位盘点：首页各频道的商品坑位有限，需要知道过去一个周期内每个类目下实际销售额最高的前三款商品，形成"类目爆款清单"，用于决定哪些商品进频道页推荐位、哪些商品要优先补货保库存。运营向数据组提需求："给我每个类目卖得最好的3个商品和它们的销售额"。数据分析师需要把订单明细表关联商品维表，按类目分组计算商品净销售额并排名取前三。**【面试高频】**分组内 TopN 是电商 SQL 面试出现率最高的题型之一，几乎是每场笔试的固定开场题，退款口径与并列名次是最常见的扣分点。

### 2. 表结构说明
products（商品维表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sku_id | VARCHAR(32) | 商品ID，主键 |
| sku_name | VARCHAR(128) | 商品名称 |
| category_id | VARCHAR(16) | 类目ID |
| category_name | VARCHAR(64) | 类目名称 |
| shelf_status | TINYINT | 上架状态：1上架，0下架 |

order_items（订单明细表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| item_id | BIGINT | 明细行ID，主键 |
| order_id | VARCHAR(32) | 订单ID |
| sku_id | VARCHAR(32) | 商品ID |
| quantity | INT | 购买件数 |
| pay_price | DECIMAL(10,2) | 成交单价 |
| refund_amount | DECIMAL(10,2) | 该行累计已退款金额 |
| pay_date | DATE | 支付日期 |

示例数据 products：

| sku_id | sku_name | category_id | category_name | shelf_status |
|--------|----------|-------------|---------------|--------------|
| S001 | 无线蓝牙耳机Pro | C01 | 数码 | 1 |
| S002 | 机械键盘87键 | C01 | 数码 | 1 |
| S003 | 降噪头戴耳机 | C01 | 数码 | 1 |
| S004 | 保温杯500ml | C02 | 家居 | 1 |
| S005 | 香薰蜡烛套装 | C02 | 家居 | 1 |

示例数据 order_items：

| item_id | order_id | sku_id | quantity | pay_price | refund_amount | pay_date |
|---------|----------|--------|----------|-----------|---------------|----------|
| 10001 | O20250901001 | S001 | 1 | 299.00 | 0.00 | 2025-09-01 |
| 10002 | O20250901002 | S001 | 2 | 289.00 | 289.00 | 2025-09-01 |
| 10003 | O20250902001 | S002 | 1 | 199.00 | 0.00 | 2025-09-02 |
| 10004 | O20250903001 | S003 | 1 | 499.00 | 0.00 | 2025-09-03 |
| 10005 | O20250903002 | S004 | 3 | 59.00 | 0.00 | 2025-09-03 |

### 3. 解题思路
先统一指标口径：商品销售额 = pay_price × quantity − refund_amount，即扣掉退款的"净销售额"，不扣退款会高估退款率高的爆款；时间边界取 2025-09-01 起的统计周期。实现路径分两层：第一层把 order_items JOIN products 补齐类目信息，按"类目×商品"聚合出净销售额；第二层在聚合结果上用 ROW_NUMBER() OVER(PARTITION BY 类目 ORDER BY 销售额 DESC) 打组内名次，外层筛 rk<=3。**【避坑指南】**必须"先聚合、再开窗"：直接在明细行上开窗会在订单明细粒度产生大量重复名次，这是最常见的错误写法。另两个易错点：ROW_NUMBER 对销售额相同的商品会强制排出先后，并列第三可能被挤掉，需主动说明 DENSE_RANK/RANK 的并列语义；只统计上架商品还是含下架商品，口径要提前与业务确认。

### 4. 参考解法

解法一：CTE 先聚合、再用 ROW_NUMBER 取每组前三（推荐）

```sql
WITH sku_gmv AS (                                 -- 第一层：类目×商品粒度的净销售额
    SELECT
        p.category_id,                            -- 类目ID
        p.category_name,                          -- 类目名称
        oi.sku_id,                                -- 商品ID
        MAX(p.sku_name)                AS sku_name,  -- 维度列用MAX包住以满足ONLY_FULL_GROUP_BY
        SUM(oi.pay_price * oi.quantity - oi.refund_amount) AS gmv  -- 净销售额=成交额-退款
    FROM order_items oi
    JOIN products p                               -- 关联商品维表补类目
      ON oi.sku_id = p.sku_id
    WHERE oi.pay_date >= '2025-09-01'             -- 统计周期起点
    GROUP BY p.category_id, p.category_name, oi.sku_id
),
ranked AS (                                       -- 第二层：在聚合结果上开组内排名窗口
    SELECT
        category_id, category_name, sku_id, sku_name, gmv,
        ROW_NUMBER() OVER (
            PARTITION BY category_id              -- 按类目分区
            ORDER BY gmv DESC                     -- 区内按销售额降序
        ) AS rk                                   -- 组内名次：1,2,3,...
    FROM sku_gmv
)
SELECT category_id, category_name, sku_id, sku_name, gmv, rk
FROM ranked
WHERE rk <= 3                                     -- 只保留每个类目的前三名
ORDER BY category_id, rk;                         -- 按类目、名次输出
```

结果解读：每个类目恰好输出 3 行无并列结果，例如数码类返回 S003、S001、S002 及各自净销售额，可直接作为频道页选品与补货优先级的依据。

解法二：聚合派生表 + 相关子查询过滤（不依赖窗口函数，兼容老版本）

```sql
SELECT
    g.category_id,                                -- 类目ID
    g.sku_id,                                     -- 商品ID
    g.gmv                                         -- 该商品净销售额
FROM (
    SELECT
        p.category_id,
        oi.sku_id,
        SUM(oi.pay_price * oi.quantity - oi.refund_amount) AS gmv
    FROM order_items oi
    JOIN products p ON oi.sku_id = p.sku_id
    WHERE oi.pay_date >= '2025-09-01'
    GROUP BY p.category_id, oi.sku_id             -- 先聚合出所有"类目×商品"
) g
WHERE (
    SELECT COUNT(*)                               -- 同类目里销售额严格更高的商品个数
    FROM (
        SELECT
            p2.category_id,
            oi2.sku_id,
            SUM(oi2.pay_price * oi2.quantity - oi2.refund_amount) AS gmv2
        FROM order_items oi2
        JOIN products p2 ON oi2.sku_id = p2.sku_id
        WHERE oi2.pay_date >= '2025-09-01'
        GROUP BY p2.category_id, oi2.sku_id
    ) g2
    WHERE g2.category_id = g.category_id          -- 只在同类目内比较
      AND g2.gmv2 > g.gmv                         -- 用严格大于保证并列名次一致
) < 3;                                            -- 严格更高的商品不足3个，即处于前三
```

结果解读：这种写法等价于 RANK 语义——若第3、4名销售额并列会同时返回 4 行，保证"并列爆款不遗漏"，比 ROW_NUMBER 更贴合"并列商品都要上资源位"的业务诉求。

### 5. 性能分析与优化
解法一扫描 order_items 一遍完成聚合，窗口排序只在每组内 O(n log n)，sku_gmv 结果集仅为"类目×商品数"，代价低，是首选。解法二的相关子查询会为派生表 g 的每一行重新扫描明细做聚合，代价接近 O(类目商品数 × 明细扫描)，明细表大时急剧恶化。优化建议：给 order_items 建 (pay_date, sku_id) 复合索引让日期过滤和 JOIN 都走索引；明细量极大时先按 (sku_id, pay_date) 预聚合落一张日销汇总 ADS 表，或利用按月分区做分区裁剪；products.sku_id 是主键不会引起 JOIN 膨胀，无需预先去重。

### 6. 面试延伸考点
- **怎么把"并列第三名"也保留下来？** 用 RANK() 或 DENSE_RANK() 替代 ROW_NUMBER()：RANK 并列同名次但跳号（1,1,3），DENSE_RANK 不跳号（1,1,2）；配 WHERE rk<=3 时 DENSE_RANK 可能返回超过 3 行，业务上通常可接受。
- **如果要"每个类目销售额累计占比前80%的商品"呢？** 用累计窗口 SUM(gmv) OVER(PARTITION BY category_id ORDER BY gmv DESC) 除以 SUM(gmv) OVER(PARTITION BY category_id)，取累计占比 <=0.8 的行，即二八法则选品。
- **Hive/Spark SQL 里写法有什么差异？** 窗口语法基本一致，但 Hive 的子查询/CTE 必须有别名；某大类目商品极多时排名会集中在单个 reducer，存在数据倾斜，可先按类目打散预处理。
- **退款金额大于销售额的负数行怎么处理？** 可用 GREATEST(净销售额, 0) 归零，或按业务要求保留负数冲抵GMV，两种口径差异必须在交付文档里写明。

### 7. 业务拓展思考
类目 TopN 不只是一张排名表：把本期 rk 与上周快照对比可得"爆款替换率"，频繁易主说明类目供给不稳或比价严重；把 Top3 商品的加购率、转化率与类目均值对比，可区分"引流款"与"利润款"。运营上可联动频道资源位轮换、库存预警和直播选品。口径延展上，把销售额换成毛利额、动销天数、退货率可做多维 TopN，形成品类健康度矩阵，支撑更精细的品类策略。

## EC-17 用户首单后7日内复购率

### 1. 业务背景
用户增长团队跟踪新客质量：新客完成首单后是否在短期内复购，直接反映商品与履约体验的满足度，也决定后续召回成本。运营想看"2025年9月产生首单的用户中，首单后7日内再次下单的比例"，用于评估新客承接策略（首单礼包、追评返券、物流时效）的效果；若7日复购率偏低，需要拆到品类与渠道做归因，判断是首单体验问题还是品类天然低频。**【面试高频】**"首单+N日留存复购"是电商 BI 新客漏斗报表的标准一层，面试考察点集中在首单口径与时间窗口边界的定义上。

### 2. 表结构说明
orders（订单主表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid已支付/refunded已退款/cancelled已取消 |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250905001 | 10001 | paid | 2025-09-05 10:23:00 | 128.00 |
| O20250909001 | 10001 | paid | 2025-09-09 20:11:00 | 89.00 |
| O20250901001 | 10002 | paid | 2025-09-01 09:15:00 | 299.00 |
| O20250906001 | 10002 | refunded | 2025-09-06 18:40:00 | 59.00 |
| O20250902001 | 10003 | paid | 2025-09-02 21:05:00 | 45.00 |

### 3. 解题思路
先定口径：首单 = 用户第一笔 paid 状态订单（按 pay_time 最早）；7日内复购 = 存在支付时间严格晚于首单、且距首单不超过 7 天的第二笔 paid 订单——首单当天晚些时候再下一单也计入复购，若业务要求"隔日才算"则改为 pay_time >= 首单日期+1 天，必须写进口径文档；退款单（refunded/cancelled）不计入任何一端。实现路径：先按用户求出首单时间，再对每个用户判断窗口内是否存在后续订单，最后对全量用户汇总比例。**【避坑指南】**分母必须是"产生过首单的用户数"而不是"订单数"，且用户维度去重要在判定之前完成，否则同用户多单会把分母放大、复购率被稀释。

### 4. 参考解法

解法一：CTE 求首单 + EXISTS 打复购标记（用户粒度思路，语义直观）

```sql
WITH first_order AS (                             -- 第一层：每个用户的首单支付时间
    SELECT
        user_id,
        MIN(pay_time) AS first_pay_time           -- 最早的支付时间即首单
    FROM orders
    WHERE order_status = 'paid'                   -- 只看成功支付，退款取消剔除
    GROUP BY user_id
),
user_flag AS (                                    -- 第二层：给每个用户打"7日内复购"标记
    SELECT
        f.user_id,
        f.first_pay_time,
        CASE WHEN EXISTS (                        -- 存在一笔满足条件的后续订单即复购
            SELECT 1
            FROM orders o2
            WHERE o2.user_id = f.user_id          -- 同一用户
              AND o2.order_status = 'paid'        -- 也必须是有效支付单
              AND o2.pay_time > f.first_pay_time  -- 严格晚于首单，排除首单本身
              AND o2.pay_time <= f.first_pay_time + INTERVAL 7 DAY  -- 落在首单后7天窗口内
        ) THEN 1 ELSE 0 END AS is_repeat
    FROM first_order f
)
SELECT
    COUNT(*)             AS pay_users,            -- 分母：产生首单的用户数
    SUM(is_repeat)       AS repeat_users,         -- 分子：7日内复购用户数
    ROUND(SUM(is_repeat) / COUNT(*), 4) AS repeat_rate  -- 7日复购率
FROM user_flag;
```

结果解读：示例中 10001 在首单后第 4 天复购计入分子，10002 的第二单为退款单不计入，输出为"首单用户 3 人、复购 1 人、复购率 0.3333"，说明新客短期留存处于待提升区间。

解法二：MIN() 窗口 + 条件去重计数（一次扫描明细，不开用户级子查询）

```sql
WITH t AS (
    SELECT
        user_id,
        pay_time,
        MIN(pay_time) OVER (PARTITION BY user_id) AS first_pay_time  -- 每行订单都挂上该用户首单时间
    FROM orders
    WHERE order_status = 'paid'
)
SELECT
    COUNT(DISTINCT user_id) AS pay_users,           -- 分母：有支付订单的用户数
    COUNT(DISTINCT CASE
            WHEN pay_time > first_pay_time          -- 排除首单本身
             AND pay_time <= first_pay_time + INTERVAL 7 DAY  -- 窗口内
            THEN user_id END)       AS repeat_users,  -- 分子：窗口内还有订单的用户
    ROUND(COUNT(DISTINCT CASE
            WHEN pay_time > first_pay_time
             AND pay_time <= first_pay_time + INTERVAL 7 DAY
            THEN user_id END) / COUNT(DISTINCT user_id), 4) AS repeat_rate
FROM t;
```

结果解读：窗口写法把"判断归属"变成"行级打标后计数"，与解法一同为 0.3333；当报表要同时输出首单时间分布、复购单间隔分布时，这种单层扫描更好扩展。

### 5. 性能分析与优化
解法一的 EXISTS 在 order_status+user_id 有索引时可短路查找，每个用户最多探测索引几层，代价与用户数线性相关；解法二需要一次窗口计算（按 user_id 分区排序），明细行数远大于用户数时窗口排序内存与临时表开销更高。优化建议：给 orders 建 (order_status, user_id, pay_time) 复合索引，两个解法都能受益；明细表按 pay_time 分区以裁剪统计周期；若该指标要按天跑批，建议落一张用户级首单宽表（user_id, first_pay_time），后续所有留存口径直接引用，避免每次全表算 MIN。join 层面两解法都无多表 JOIN，无膨胀风险，重点是避免对同一明细重复扫描两次以上。

### 6. 面试延伸考点
- **7日、30日、90日复购率怎么用一套SQL输出？** 把窗口条件参数化为 DATEDIFF(pay_time, first_pay_time) <= n，用 CASE WHEN 多列并行输出各周期分子，或在 GROUP BY 周期标签后透视。
- **首单退款了算不算有首单？** 严格口径下 refunded 不算"成单"，用户会从分母消失；业务上也常用"首单是否发生支付行为"的宽口径，两种口径的差异要在报表注释中声明。
- **为什么用 LEFT JOIN 思路时分子容易算错？** 若先 JOIN 后再 WHERE 过滤复购条件，会把未复购用户整行过滤掉，分母丢失；正确做法是把复购判定放进聚合表达式（CASE/SUM）而不是 WHERE。
- **Hive 里 INTERVAL 7 DAY 的替代写法？** Hive/Spark 常用 DATE_ADD(first_pay_time, 7) 或 datediff(pay_time, first_pay_time) <= 7，且 datediff 只支持 DATE 粒度，注意时间戳要先 to_date。

### 7. 业务拓展思考
7 日复购率是新客"二次价值"的先行指标，可与首单品类、首单折扣深度交叉：低价引流品首单的复购通常显著低于高匹配度品类，据此可调整拉新出价与首单货品池。产品侧可联动"复购券包"与"到期提醒"的 A/B 实验，用该指标做北极星验证。口径延展上，可把"是否复购"升级为"第 N 单达成时长分布"，输出新客到忠诚用户的转化曲线，为会员体系分层提供输入。

## EC-18 月度复购率

### 1. 业务背景
经营分析团队做月度经营复盘时，固定要产出"月度复购率"：当月有支付订单的用户中，上一个自然月也购买过的用户占比。它衡量存量用户的粘性与月度留存，是 CFO 月报和预算模型里的核心留存参数；当该指标环比走低时，管理层需要进一步拆分新老客，判断是拉新质量下滑还是老客流失加速。与 EC-17 的"首单后 N 日"不同，这是自然月口径，难点在于"上月"的精确计算与用户×月的去重。**【加分点】**能在面试里主动指出"复购要求上一购买月恰好是上个自然月，而不是上一个有购买记录的月份"，是区分度很高的一步。

### 2. 表结构说明
orders（订单主表，与 EC-17 同构，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250715001 | 20003 | paid | 2025-07-15 16:00:00 | 79.00 |
| O20250801001 | 20001 | paid | 2025-08-01 10:00:00 | 99.00 |
| O20250901001 | 20001 | paid | 2025-09-01 12:30:00 | 59.00 |
| O20250905001 | 20002 | paid | 2025-09-05 08:00:00 | 159.00 |
| O20250910001 | 20003 | paid | 2025-09-10 19:00:00 | 120.00 |

### 3. 解题思路
口径定义：分母 = 当月有过 paid 订单的去重用户数；分子 = 其中上一自然月也有 paid 订单的用户数；同月多单只按用户记一次（先做"用户×月"去重），用户 7 月买过、8 月没买、9 月又买，9 月不算复购。实现路径一：先把明细压成用户×月去重表，用 LAG 取每个用户"上一个购买月"，再判断它是否恰好等于上个自然月；实现路径二：本月用户集合 LEFT JOIN 上月用户集合，连上的即为复购。**【避坑指南】**LAG 返回的是"上一个有购买记录的月份"，不是"上个自然月"——跨月断档时两者不相等，必须显式比较月字符串，否则复购率会被高估。

### 4. 参考解法

解法一：用户×月去重 + LAG 判断上一购买月（窗口思路）

```sql
WITH um AS (                                      -- 第一层：用户×自然月去重
    SELECT
        user_id,
        DATE_FORMAT(pay_time, '%Y-%m') AS ym      -- 支付月份字符串
    FROM orders
    WHERE order_status = 'paid'                   -- 只计有效支付
    GROUP BY user_id, DATE_FORMAT(pay_time, '%Y-%m')
),
f AS (                                            -- 第二层：每个购买月带上"上一个购买月"
    SELECT
        user_id,
        ym,
        LAG(ym) OVER (PARTITION BY user_id ORDER BY ym) AS prev_buy_ym  -- 用户上一个有购买的自然月
    FROM um
)
SELECT
    ym AS month,                                  -- 统计月
    COUNT(*) AS buy_users,                        -- 分母：当月购买用户数
    SUM(CASE
            WHEN prev_buy_ym = DATE_FORMAT(       -- 上一购买月恰好等于上个自然月才算复购
                     DATE_SUB(CONCAT(ym, '-01'), INTERVAL 1 MONTH), '%Y-%m')
            THEN 1 ELSE 0 END) AS repeat_users,   -- 分子：月度复购用户数
    ROUND(SUM(CASE
            WHEN prev_buy_ym = DATE_FORMAT(
                     DATE_SUB(CONCAT(ym, '-01'), INTERVAL 1 MONTH), '%Y-%m')
            THEN 1 ELSE 0 END) / COUNT(*), 4) AS repeat_rate
FROM f
GROUP BY ym
ORDER BY ym;
```

结果解读：示例中用户 20001 上个购买月为 8 月、当月 9 月购买，计入 9 月分子；20003 上个购买月是 7 月，9 月购买不计入——输出逐月复购率序列，可直接进月报看趋势。

解法二：本月集合 LEFT JOIN 上月集合（集合运算思路，无窗口函数）

```sql
WITH um AS (                                      -- 同样先做用户×月去重
    SELECT
        user_id,
        DATE_FORMAT(pay_time, '%Y-%m') AS ym
    FROM orders
    WHERE order_status = 'paid'
    GROUP BY user_id, DATE_FORMAT(pay_time, '%Y-%m')
)
SELECT
    cur.ym AS month,                              -- 当月
    COUNT(DISTINCT cur.user_id) AS buy_users,     -- 分母：当月购买用户数
    COUNT(DISTINCT pre.user_id) AS repeat_users,  -- 分子：上月也购买（JOIN不上的pre为NULL不计）
    ROUND(COUNT(DISTINCT pre.user_id) / COUNT(DISTINCT cur.user_id), 4) AS repeat_rate
FROM um cur
LEFT JOIN um pre                                  -- 自连接：本月的他 在上月是否存在
  ON pre.user_id = cur.user_id
 AND pre.ym = DATE_FORMAT(                        -- 精确匹配"上个自然月"
         DATE_SUB(CONCAT(cur.ym, '-01'), INTERVAL 1 MONTH), '%Y-%m')
GROUP BY cur.ym
ORDER BY cur.ym;
```

结果解读：LEFT JOIN 天然保证"上月不存在"的用户以 NULL 出现、仍留在分母中，逻辑与月份对齐都隐式正确，是最不易出错的口径实现，月报落地首选。

### 5. 性能分析与优化
两解法都先做用户×月去重，中间结果只有"活跃用户×月"量级，远小于明细。解法一的 LAG 需按 (user_id, ym) 排序，用户量大时排序文件/临时表开销明显；解法二的自连接在 um 上按 (user_id, ym) 建 hash join 键即可，无排序需求，配合索引 (user_id, ym) 或让 CTE 物化后走 hash 均可。优化建议：为 orders 建 (order_status, pay_time) 索引配合分区裁剪减少扫描；跑批场景把 um 落成"月活跃购买用户"快照表，复购率变成两张快照表的 COUNT 对比，日常查询毫秒级；避免在 JOIN 键上套函数（如对 ym 再做 DATE_SUB）导致索引失效——这里函数作用在常量侧，键侧保持原样是安全写法。

### 6. 面试延伸考点
- **月度复购率与月留存率是一回事吗？** 本题口径是"上月买、本月也买"的活跃留存；还有"首购月 cohort 留存"（按首单月分组看后续各月购买率），两者分子分母定义不同，报表里必须分开命名。
- **如果要同时看连续 N 月购买的用户占比呢？** 在 f 层用 SUM(CASE WHEN 相邻月 THEN 1 END) 累计连续购买月数，或对"月-用户"序列做连续段判定（同 EC-24 思想迁移到月份）。
- **跨年边界怎么处理？** DATE_SUB('2025-01-01', INTERVAL 1 MONTH) 得 2024-12-01，DATE_FORMAT 后为 '2024-12'，用日期函数推导而非字符串截断可自然跨年。
- **大促月复购率会失真吗？** 会——大促把本来下月才买的用户提前到当月，复购率虚高，分析时要叠加"大促月标记"或改用滚动90天口径平滑。

### 7. 业务拓展思考
月度复购率是连接获客与留存的枢纽指标：与新增用户数、新客占比联用，可以把 GMV 增长分解为"拉新贡献"与"存量复购贡献"。运营上可对"上月购买但本月未买"人群做流失预警召回（券包、短信、Push 三级触达）；产品侧可按复购率给品类分层，决定资源向高频刚需品倾斜还是向高毛利低频品倾斜。口径延展上可输出"复购间隔分布"，把复购率升级为可预测"下次购买时间"的输入。

## EC-19 加购到支付的转化率

### 1. 业务背景
交易转化分析师日常监控核心漏斗"浏览→加购→支付"中的加购→支付环节：加购代表用户已有明确购买意向，但从加购到支付存在大量流失（价格犹豫、凑单失败、购物车遗忘、缺货）。运营需要某周期内"加购过的用户-商品组合中，最终在加购之后完成支付的比例"，用于定位购物车流失的规模与分布，并推动购物车降价提醒、到期召回、凑单券等产品策略。行为日志表是这道题的载体，难点在于多步行为的时序配对与去重粒度。**【面试高频】**行为表漏斗题在校招一面中出现率极高，能否主动讨论"先加购后支付"的时间顺序校验是重要的加分信号。

### 2. 表结构说明
user_behavior（用户行为日志表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| log_id | BIGINT | 日志行ID，主键 |
| user_id | BIGINT | 用户ID |
| item_id | BIGINT | 商品ID |
| behavior_type | VARCHAR(10) | 行为类型：view浏览/fav收藏/cart加购/pay支付 |
| behavior_time | DATETIME | 行为发生时间 |

示例数据 user_behavior：

| log_id | user_id | item_id | behavior_type | behavior_time |
|--------|---------|---------|---------------|---------------|
| 90001 | 30001 | 70001 | view | 2025-09-01 10:00:00 |
| 90002 | 30001 | 70001 | cart | 2025-09-01 10:05:00 |
| 90003 | 30001 | 70001 | pay | 2025-09-02 09:00:00 |
| 90004 | 30002 | 70002 | cart | 2025-09-01 11:00:00 |
| 90005 | 30003 | 70001 | cart | 2025-09-03 15:30:00 |

### 3. 解题思路
先定口径：粒度取"用户×商品"（贴近商品维度漏斗，同一用户加购多件分开算）；分母 = 统计周期内发生过 cart 行为的去重用户-商品对；分子 = 其中"支付时间 >= 首次加购时间"的对——先买后加购（历史订单复购导致）不能算进分子，这是最容易漏的时序校验。实现路径一：分别聚合出每个用户-商品的首次加购时间与首次支付时间，LEFT JOIN 后在聚合表达式里判断先后；实现路径二：一次扫描用条件聚合（CASE WHEN 内嵌 MIN）同时取两类时间，单表单扫完成。**【避坑指南】**统计周期只约束加购时间，支付允许延伸到周期结束后，否则漏斗尾部会被人为截断；view 行为量大，扫描时先用 behavior_type IN ('cart','pay') 过滤可省一半以上 IO。

### 4. 参考解法

解法一：两段 CTE 聚合 + LEFT JOIN 时序判断（漏斗标准写法）

```sql
WITH cart AS (                                    -- 第一层：每个用户-商品的首次加购时间
    SELECT
        user_id,
        item_id,
        MIN(behavior_time) AS first_cart_time
    FROM user_behavior
    WHERE behavior_type = 'cart'                  -- 只取加购行为
      AND behavior_time >= '2025-09-01'
      AND behavior_time <  '2025-09-08'           -- 统计周期：一周（左闭右开）
    GROUP BY user_id, item_id
),
pay AS (                                          -- 第二层：每个用户-商品的首次支付时间
    SELECT                                        -- 支付时间只设起点，允许延伸到周期后
        user_id,
        item_id,
        MIN(behavior_time) AS first_pay_time
    FROM user_behavior
    WHERE behavior_type = 'pay'
      AND behavior_time >= '2025-09-01'
    GROUP BY user_id, item_id
)
SELECT
    COUNT(*) AS cart_cnt,                         -- 分母：周期内加购过的用户-商品对
    SUM(p.first_pay_time >= c.first_cart_time) AS convert_cnt,  -- 分子：支付且不早于加购(NULL自动跳过)
    ROUND(SUM(p.first_pay_time >= c.first_cart_time) / COUNT(*), 4) AS cart2pay_rate
FROM cart c
LEFT JOIN pay p                                   -- 左连接保证未支付对留在分母
  ON p.user_id = c.user_id
 AND p.item_id = c.item_id;                       -- 时间先后在SELECT里判断，便于单独拆出"先买后加购"
```

结果解读：示例中 30001-70001 加购后次日支付、计入分子；30002、30003 未支付计入分母，输出为"加购 3 对、转化 1 对、转化率 0.3333"，可直接横向对比各周的购物车流失水平。

解法二：条件聚合一次扫描（单表单遍，无 JOIN）

```sql
SELECT
    COUNT(*) AS cart_cnt,                                   -- 分母：有加购行为的用户-商品对
    SUM(first_pay_time >= first_cart_time) AS convert_cnt,  -- 分子：存在不早于加购的支付(NULL不计)
    ROUND(SUM(first_pay_time >= first_cart_time) / COUNT(*), 4) AS cart2pay_rate
FROM (
    SELECT
        user_id,
        item_id,
        MIN(CASE WHEN behavior_type = 'cart'
                 THEN behavior_time END) AS first_cart_time,  -- 该对首次加购时间
        MIN(CASE WHEN behavior_type = 'pay'
                 THEN behavior_time END) AS first_pay_time    -- 该对首次支付时间
    FROM user_behavior
    WHERE behavior_type IN ('cart', 'pay')          -- 只扫两种行为，减少IO
      AND behavior_time >= '2025-09-01'
      AND behavior_time <  '2025-09-08'
    GROUP BY user_id, item_id                       -- 压到用户×商品粒度
) t
WHERE first_cart_time IS NOT NULL;                  -- 分母只保留确实加购过的对
```

结果解读：与解法一同为 0.3333，但整条 SQL 只扫描行为表一次；当漏斗要扩成"浏览→加购→支付"三步时，只需在 CASE WHEN 里增加一列，扩展性最好。

### 5. 性能分析与优化
行为日志是电商最大的表之一，两解法的差别本质是"扫一遍还是两遍"：解法一分别扫 cart 与 pay 各一遍（有 behavior_type 过滤时代价可控），解法二单遍扫描但 GROUP BY 输入行数更多。优化建议：给 user_behavior 建 (behavior_type, behavior_time) 或 (user_id, behavior_type) 索引/按天分区，配合分区裁剪把扫描压到周期内；如需长期监控，先把行为表预聚合为"日-用户-商品-行为类型-次数"中间层，漏斗查询只需扫聚合层。**【避坑指南】**不要在行为表上对 behavior_time 做 DATE_FORMAT 再过滤，函数包列会使索引与分区裁剪失效，应写成 >= 起点且 < 终点的区间形式。海量日志下 Hive/Spark 中两解法等价可用，注意 cart 大表与 pay 表 JOIN 倾斜时可加盐打散。

### 6. 面试延伸考点
- **漏斗粒度选"用户"还是"用户×商品"？** 用户粒度算人数转化，商品粒度定位具体商品流失；粒度越细越能归因，但跨步匹配的时序校验也越严格，两者数值不能混用。
- **怎么计算"平均加购到支付时长"？** 用 TIMESTAMPDIFF(MINUTE, first_cart_time, first_pay_time) 对转化的对求中位数/均值，中位数更抗极值，可用窗口或自近似。
- **先加购后未支付的用户如何圈选？** 把分子条件反过来（pay IS NULL），输出 user_id+item_id 清单对接推送系统，注意要排除"已买过该商品"的老客避免打扰。
- **Hive/Spark 里这道题的写法差异？** 语法几乎一致；Hive 对 CTE 子查询强制别名，collect_set 可替代部分条件聚合场景，超大日志建议先按 dt 分区裁剪再跑。

### 7. 业务拓展思考
加购→支付转化率是购物车产品迭代的核心北极星：转化率提升1个点对GMV的杠杆远大于浏览端优化。可把该指标与"加购后24/48/72小时未支付率"结合，设计分时段降价提醒与召回 Push；对高价值但低转化商品，联动定价与库存做专项治理。口径延展上，可拆"加入购物车→结算页→提交订单→支付"四级漏斗，定位流失到底发生在结算动线还是支付环节，为产品改版提供证据链。

## EC-20 用户累计消费金额及全站TOP20%分档

### 1. 业务背景
会员运营团队按消费力做人群分层：需要给每个用户算出统计期内的累计实付金额，并按全站分布切档——头部 20%（高消费力）进专属客服与高价品推荐池，中间 40% 做品类渗透，尾部 40% 做唤醒与低价品转化。同时管理层常问"头部 20% 用户贡献了多少 GMV"来验证二八法则，这要求先算出用户级累计消费，再做全站分位分档。**【加分点】**NTILE 与 CUME_DIST 的并列值行为差异、以及"分档必须在用户级聚合之后做，否则订单多的用户会在窗口里被重复计数"，是本题的高分讨论点。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250101001 | 40001 | paid | 2025-01-01 10:00:00 | 299.00 |
| O20250215001 | 40001 | paid | 2025-02-15 11:00:00 | 129.00 |
| O20250301001 | 40002 | paid | 2025-03-01 09:00:00 | 59.00 |
| O20250405001 | 40003 | paid | 2025-04-05 20:00:00 | 899.00 |
| O20250506001 | 40004 | cancelled | 2025-05-06 10:00:00 | 199.00 |

### 3. 解题思路
口径：累计消费 = 统计期内 paid 订单 pay_amount 之和（退款单不计入，退款金额冲减看业务要求）；分档 = 按全站用户累计消费降序，前 20% 为 TOP20% 档。实现路径分两层：第一层 GROUP BY user_id 聚合出每人累计消费（必须先做，否则开窗在订单粒度会把同一用户切进多档）；第二层用 NTILE(5) OVER(ORDER BY 消费额 DESC) 均分五份取第 1 份，或用 CUME_DIST() 判断累计人数占比 <=0.2。**【避坑指南】**NTILE 按行数机械切分，两个消费额完全相同的用户可能被切进不同档（档位边界撕裂），而 CUME_DIST 对并列值给出相同累计占比、天然"同值同档"；用户总数不能被 5 整除时 NTILE 会把余数分给前面的组，档位人数不完全相等，面试要能说清。

### 4. 参考解法

解法一：聚合后 NTILE(5) 均分五档（行数均分，报表常用）

```sql
WITH user_amt AS (                                -- 第一层：用户级累计消费
    SELECT
        user_id,
        SUM(pay_amount) AS total_amt              -- 统计期实付总额
    FROM orders
    WHERE order_status = 'paid'                   -- 只计有效支付单
      AND pay_time >= '2025-01-01'
    GROUP BY user_id
)
SELECT
    user_id,
    total_amt,
    NTILE(5) OVER (ORDER BY total_amt DESC) AS amt_tier  -- 按消费降序切5份：1=最高消费的20%
FROM user_amt
ORDER BY amt_tier, total_amt DESC;                -- 输出：用户、累计消费、消费档位
```

结果解读：示例中 40003（899元）落入第 1 档即 TOP20% 高消费人群；把每档 SUM(total_amt) 汇总即可回答"头部 20% 贡献多少 GMV"，用于二八法则验证。

解法二：CUME_DIST 累计占比分档（并列值同档，分位语义更严谨）

```sql
WITH user_amt AS (                                -- 用户级累计消费（同解法一）
    SELECT
        user_id,
        SUM(pay_amount) AS total_amt
    FROM orders
    WHERE order_status = 'paid'
      AND pay_time >= '2025-01-01'
    GROUP BY user_id
)
SELECT
    user_id,
    total_amt,
    ROUND(CUME_DIST() OVER (ORDER BY total_amt DESC), 4) AS cume_pct,  -- 含当前行的累计人数占比
    CASE
        WHEN CUME_DIST() OVER (ORDER BY total_amt DESC) <= 0.20 THEN 'TOP20%'
        WHEN CUME_DIST() OVER (ORDER BY total_amt DESC) <= 0.60 THEN '腰部40%'
        ELSE '长尾40%'
    END AS tier                                   -- 按累计占比切三档，可按需扩成五档
FROM user_amt
ORDER BY total_amt DESC;
```

结果解读：CUME_DIST 给出"消费不低于该用户的人数占比"，TOP20% 边界上并列的用户会整体归入同一档，避免 NTILE 把同额用户撕开的尴尬，更适合对外发布的人群定义。

### 5. 性能分析与优化
两解法第一层相同：一次 GROUP BY 聚合，用户级结果集小；第二层都需要按 total_amt 全量排序，O(N log N)，N 为用户数（千万级时排序是主要代价）。优化建议：让排序发生在聚合后的小结果集上而非明细上（两解法都已满足）；对 total_amt 建索引意义不大（排序发生在派生表），重点是把 paid 过滤下推、减少聚合输入；跑批时把 user_amt 落成用户资产宽表并按月刷新，分档查询变成对小表开窗。相比解法一，解法二的窗口函数在 SELECT 中出现两次（cume_pct 与 CASE 内）可再套一层 CTE 只算一次，避免重复计算；数据量极大时可先按消费额分桶抽样预估边界值，再用边界值等值过滤代替全量开窗。

### 6. 面试延伸考点
- **NTILE、RANK、CUME_DIST 三者分档结果何时不同？** 消费额有并列且恰好落在切分边界时：NTILE 撕裂并列值，CUME_DIST 同值同档，RANK 配合占比换算也可实现同值同档，需按业务对"档位边界"的敏感度选择。
- **TOP20% 用户贡献的 GMV 占比怎么一步算出？** 在分档结果外再套一层聚合：SUM(CASE WHEN tier=1 THEN total_amt END)/SUM(total_amt)，或用 SUM(total_amt) OVER () 做全局分母。
- **用户数为质数（如 101 人）时 NTILE(5) 怎么分？** 前面的组多分一行：21/20/20/20/20，档位人数不严格相等，对人数敏感的权益活动要改用消费额阈值法。
- **累计消费要不要剔除退款？** 严格口径用 SUM(实付)-SUM(退款)；宽松口径只算 paid。会员权益纠纷常源于此，建议口径与客服赔付规则绑定并文档化。

### 7. 业务拓展思考
消费力分档是会员体系与定价策略的地基：TOP20% 档的留存与品类宽度变化应进入高管周报；对腰部用户设计"升档激励"（差价满赠）比拉新便宜数倍。产品上可联动"档位专属价"与分期免息工具，把消费力转化为转化率。口径延展上，可用 RFM 中的 M 维度替代单一累计金额，或引入"消费力同比变化率"识别上升期用户，把静态分档升级为动态迁移矩阵（档位流转分析），支撑生命周期运营。

## EC-21 同一订单内商品连带组合TopN

### 1. 业务背景
购物篮分析师要回答"哪些商品经常被同一个订单一起买走"：把同一订单内的商品两两配成"连带组合"，统计每对组合的共现订单数，找出全站 TopN 组合，用于搭配套餐设计、凑单推荐位和"买了还买"货架。这是购物篮分析（关联规则）的 SQL 入门版——用共现次数代替支持度。技术难点在于用自连接把一行明细"展开"成商品对，并正确处理自配对、方向重复与同单同商品多行的情况。**【面试高频】**自连接成对组合是窗口之外另一类高频进阶题，与 EC-16 组成"TopN 双题型"，几乎必有一道出现在笔试卷上。

### 2. 表结构说明
order_items（订单明细表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| item_id | BIGINT | 明细行ID，主键 |
| order_id | VARCHAR(32) | 订单ID |
| sku_id | VARCHAR(32) | 商品ID |
| sku_name | VARCHAR(128) | 商品名称 |
| quantity | INT | 购买件数 |
| pay_price | DECIMAL(10,2) | 成交单价 |

示例数据 order_items：

| item_id | order_id | sku_id | sku_name | quantity | pay_price |
|---------|----------|--------|----------|----------|-----------|
| 1 | OD001 | S001 | 无线蓝牙耳机Pro | 1 | 299.00 |
| 2 | OD001 | S005 | 香薰蜡烛套装 | 1 | 79.00 |
| 3 | OD001 | S006 | 编织收纳筐 | 2 | 39.00 |
| 4 | OD002 | S001 | 无线蓝牙耳机Pro | 1 | 299.00 |
| 5 | OD002 | S005 | 香薰蜡烛套装 | 1 | 79.00 |

### 3. 解题思路
口径：组合按"无序商品对"计数，即 (A,B) 与 (B,A) 算同一组合；共现次数 = 同时包含两商品的订单数（DISTINCT order_id）；单订单内同一商品出现多行（拆行促销）只算一次，必须先在 (order_id, sku_id) 上去重，否则对数会被重复放大。实现路径：order_items 自连接，连接键为 order_id 相同且 a.sku_id < b.sku_id——小于号一举解决"自己配自己"和"(A,B)/(B,A) 双计"两个问题；随后按商品对 GROUP BY 计数，再用窗口 ROW_NUMBER 取全局 TopN。易错点：大订单（几十个商品）会产生平方级商品对，是 join 膨胀的主要来源；TopN 是"全局"还是"每类目内"，口径要确认。

### 4. 参考解法

解法一：自连接 + GROUP BY + ROW_NUMBER 取 TopN（标准解法）

```sql
WITH od AS (                                      -- 第零层：订单×商品去重，防拆行重复
    SELECT DISTINCT
        order_id,
        sku_id
    FROM order_items
),
pair AS (                                         -- 第一层：同一订单内两两配对并计数
    SELECT
        a.sku_id AS sku_a,                        -- 组合中的商品A
        b.sku_id AS sku_b,                        -- 组合中的商品B
        COUNT(DISTINCT a.order_id) AS co_cnt      -- 共现订单数（DISTINCT兜底防重复）
    FROM od a
    JOIN od b
      ON a.order_id = b.order_id                  -- 同一订单内才配对
     AND a.sku_id < b.sku_id                      -- 小于号：防自配对、防(A,B)/(B,A)双计
    GROUP BY a.sku_id, b.sku_id
),
ranked AS (                                       -- 第二层：按共现次数全局排名
    SELECT
        sku_a, sku_b, co_cnt,
        ROW_NUMBER() OVER (ORDER BY co_cnt DESC) AS rk
    FROM pair
)
SELECT sku_a, sku_b, co_cnt, rk
FROM ranked
WHERE rk <= 10;                                   -- 全站Top10连带组合
```

结果解读：示例中 S001+S005 在 OD001、OD002 两单共现，输出该组合 co_cnt=2 居榜首；把组合清单交给运营设计"耳机+香薰"套装，可显著提高连带率。

解法二：自连接计数 + 相关子查询过滤 TopN（不用窗口函数）

```sql
WITH od AS (                                      -- 订单×商品去重
    SELECT DISTINCT order_id, sku_id FROM order_items
),
pair AS (                                         -- 商品对共现计数
    SELECT
        a.sku_id AS sku_a,
        b.sku_id AS sku_b,
        COUNT(DISTINCT a.order_id) AS co_cnt
    FROM od a
    JOIN od b ON a.order_id = b.order_id
              AND a.sku_id < b.sku_id
    GROUP BY a.sku_id, b.sku_id
)
SELECT
    p1.sku_a,
    p1.sku_b,
    p1.co_cnt
FROM pair p1
WHERE (
    SELECT COUNT(*)                               -- 共现次数严格更高的组合个数
    FROM pair p2
    WHERE p2.co_cnt > p1.co_cnt                   -- 严格大于保证并列名次一致
) < 10                                            -- 高于它的不足10个，即处于Top10
ORDER BY p1.co_cnt DESC;                          -- 输出Top10连带组合（并列会多出）
```

结果解读：该写法等价 RANK 语义，并列第 10 的组合会全部返回，适合"Top10 组合并列也要全上资源位"的运营诉求；代价是相关子查询对 pair 每行做一次计数。

### 5. 性能分析与优化
自连接是本题的性能核心：一单含 n 个商品产生 n(n-1)/2 个对，30 商品的订单就有 435 对，大促囤货单会直接把中间结果放大数个量级。优化建议：先做 (order_id, sku_id) DISTINCT 压缩输入（两解法已内置）；对订单内商品数设置上限（如剔除 >20 商品的异常囤货单）并在口径文档注明；明细表先按 order_id 分区/聚簇，使自连接两侧都是同键聚簇数据，shuffle 量大幅下降。解法一窗口排序发生在 pair 聚合后的小表上，代价可忽略；解法二相关子查询是 O(pair数²)，pair 上百万时不可接受，可用"只取 co_cnt 前10的阈值"先物化再过滤。**【避坑指南】**若把 COUNT(DISTINCT order_id) 写成 COUNT(*)，同单同商品多行的场景会把共现次数算重，直接改变 TopN 结果。

### 6. 面试延伸考点
- **怎么升级成关联规则的"支持度/置信度/提升度"？** 支持度 = 共现订单数/总订单数；置信度 = P(B|A) = 共现/含A订单数；提升度 = 置信度/P(B)，SQL 上增加两个单商品计数 CTE 即可完成。
- **为什么用 a.sku_id < b.sku_id 而不是 <>？** <> 会让 (A,B) 和 (B,A) 各出现一次导致双计，< 同时排除自配对并固定方向；若商品无序可用 LEAST/GREATEST 归一化后分组。
- **只想要"每类目内的连带TopN"怎么改？** 在 pair 聚合时带上类目维度，ROW_NUMBER 改成 PARTITION BY 类目 ORDER BY co_cnt DESC，再筛 rk<=N。
- **Hive/Spark 里大订单膨胀怎么办？** 可用 collect_set(sku_id) 把订单压成数组后用炸裂函数配对，或直接上 FP-Growth 算子（Spark MLlib）替代手写 SQL。

### 7. 业务拓展思考
连带组合 TopN 是搭配销售的最小可行分析：组合置信度高的商品对可做成固定套装或"加价购"，共现高但客单低的组合适合做凑单推荐。与价格弹性结合，可识别"互补型连带"（买A必买B）与"促销型连带"（同打折才一起买），前者才值得长期固定货架。口径延展上，把"同订单"放宽为"同用户7天内多单"可捕捉跨单连带；再加入品类维度可输出"跨品类连带率"，衡量交叉销售战略的真实进展。

## EC-22 每个品牌月度销售额环比

### 1. 业务背景
品牌运营与招商团队按月复盘各品牌 GMV：需要产出"品牌×月份×净销售额×环比增长率"的月度宽表，识别高增长品牌（追加坑位与营销资源）与衰退品牌（评估清仓、换供应商或招商替换）。环比是最容易被面试官追问细节的指标：月份补齐、缺月处理、环比分母为零的情况都要在 SQL 层面严谨处理。数据分析师通常在月度经营报表中交付该表，并附上 TOP 增长/下滑品牌名单。**【避坑指南】**用 LAG 算环比时，LAG 取的是"上一个有记录的月份"，若某品牌当月断档，环比会拿更早的月份来算，结果完全错误——必须校验两月是否相邻。

### 2. 表结构说明
products（商品维表，含品牌）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sku_id | VARCHAR(32) | 商品ID，主键 |
| sku_name | VARCHAR(128) | 商品名称 |
| brand | VARCHAR(64) | 品牌名 |
| category_name | VARCHAR(64) | 类目名称 |

order_items（订单明细表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| item_id | BIGINT | 明细行ID，主键 |
| order_id | VARCHAR(32) | 订单ID |
| sku_id | VARCHAR(32) | 商品ID |
| quantity | INT | 件数 |
| pay_price | DECIMAL(10,2) | 成交单价 |
| refund_amount | DECIMAL(10,2) | 已退款金额 |
| pay_date | DATE | 支付日期 |

示例数据 products：

| sku_id | sku_name | brand | category_name |
|--------|----------|-------|----------------|
| S101 | 经典拿铁咖啡豆 | 品牌A | 食品 |
| S102 | 挂耳咖啡礼盒 | 品牌A | 食品 |
| S201 | 燕麦奶1L | 品牌B | 食品 |
| S202 | 冷萃随行杯 | 品牌B | 食品 |
| S301 | 不锈钢保温杯 | 品牌C | 家居 |

示例数据 order_items：

| item_id | order_id | sku_id | quantity | pay_price | refund_amount | pay_date |
|---------|----------|--------|----------|-----------|---------------|----------|
| 1 | O20250805 | S101 | 2 | 89.00 | 0.00 | 2025-08-05 |
| 2 | O20250806 | S201 | 1 | 25.00 | 0.00 | 2025-08-06 |
| 3 | O20250901 | S101 | 1 | 89.00 | 0.00 | 2025-09-01 |
| 4 | O20250902 | S201 | 3 | 25.00 | 25.00 | 2025-09-02 |
| 5 | O20250903 | S301 | 1 | 129.00 | 0.00 | 2025-09-03 |

### 3. 解题思路
口径：品牌月销售额 = 明细级 (pay_price × quantity − refund_amount) 按品牌×月求和；环比 = (本月 − 上月) / 上月，上月必须是"上个自然月"，分母为零（上月无销售）时不给环比或标记为新增。实现路径一：先聚合出品牌×月 GMV，LAG 同时取上一行的 gmv 与 ym，再校验 prev_ym 是否恰好是上个自然月，相邻才输出环比；实现路径二：品牌×月聚合表自连接，用 DATE_SUB 精确匹配上月，天然避免错配。易错点：GROUP BY 月份用 DATE_FORMAT(pay_date, '%Y-%m')；断档月不在结果集里，"本月为零"的月根本不会出现，需要用月份日历表补齐才能显示为零。

### 4. 参考解法

解法一：品牌×月聚合 + LAG + 相邻月校验（窗口思路）

```sql
WITH bm AS (                                      -- 第一层：品牌×月净销售额
    SELECT
        p.brand,
        DATE_FORMAT(oi.pay_date, '%Y-%m') AS ym,  -- 支付月份
        SUM(oi.pay_price * oi.quantity - oi.refund_amount) AS gmv  -- 净销售额
    FROM order_items oi
    JOIN products p ON oi.sku_id = p.sku_id       -- 明细挂品牌
    GROUP BY p.brand, DATE_FORMAT(oi.pay_date, '%Y-%m')
),
w AS (                                            -- 第二层：取上一条记录的GMV与月份
    SELECT
        brand, ym, gmv,
        LAG(gmv) OVER (PARTITION BY brand ORDER BY ym) AS prev_gmv,
        LAG(ym)  OVER (PARTITION BY brand ORDER BY ym) AS prev_ym  -- 上一"有记录"月份
    FROM bm
)
SELECT
    brand,
    ym,
    gmv,
    prev_gmv,
    CASE
        WHEN prev_ym = DATE_FORMAT(               -- 校验上一记录月=上个自然月
                 DATE_SUB(CONCAT(ym, '-01'), INTERVAL 1 MONTH), '%Y-%m')
        THEN ROUND((gmv - prev_gmv) / prev_gmv, 4)
        ELSE NULL                                  -- 断档时不出环比，避免误导
    END AS mom_rate
FROM w
ORDER BY brand, ym;
```

结果解读：示例中品牌B 8月GMV 25、9月 (75-25)/25=2.0（其中25元已退款冲减）；品牌C 只有9月记录，prev 为 NULL，环比输出 NULL 而非错误数值，报表消费方不会误读。

解法二：聚合表自连接精确匹配上个自然月（集合思路）

```sql
WITH bm AS (                                      -- 品牌×月聚合（同解法一）
    SELECT
        p.brand,
        DATE_FORMAT(oi.pay_date, '%Y-%m') AS ym,
        SUM(oi.pay_price * oi.quantity - oi.refund_amount) AS gmv
    FROM order_items oi
    JOIN products p ON oi.sku_id = p.sku_id
    GROUP BY p.brand, DATE_FORMAT(oi.pay_date, '%Y-%m')
)
SELECT
    cur.brand,                                    -- 品牌
    cur.ym,                                       -- 当月
    cur.gmv,                                      -- 当月GMV
    pre.gmv AS prev_gmv,                          -- 上个自然月GMV（无则NULL）
    CASE WHEN pre.gmv IS NULL OR pre.gmv = 0
         THEN NULL
         ELSE ROUND((cur.gmv - pre.gmv) / pre.gmv, 4)
    END AS mom_rate                               -- 分母NULL或0都不出环比
FROM bm cur
LEFT JOIN bm pre                                  -- 自连接匹配"上个自然月"
  ON pre.brand = cur.brand
 AND pre.ym = DATE_FORMAT(                        -- 键侧精确等值，天然不会错配
         DATE_SUB(CONCAT(cur.ym, '-01'), INTERVAL 1 MONTH), '%Y-%m')
ORDER BY cur.brand, cur.ym;
```

结果解读：自连接用"上月字符串"做等值键，断档时 pre 为 NULL、环比输出 NULL，逻辑上不可能错配；同时可顺带输出"是否新增品牌"（pre IS NULL 且 cur.gmv>0）。

### 5. 性能分析与优化
解法一聚合后窗口按 (brand, ym) 排序，bm 行数 = 品牌数×月数，极小，排序可忽略；解法二自连接走 hash join，代价同为 bm 量级，两者在合理数据规模下都很快，真正的开销在第一层明细聚合。优化建议：order_items 按 pay_date 分区并用 WHERE 限定统计月范围做分区裁剪；(sku_id, pay_date) 索引加速明细侧；品牌维度稳定时可把 bm 落成"品牌月销快照"，环比查询退化为快照表自连接。**【避坑指南】**若要展示"断档月销售为0"，需生成"品牌×月份"全组合日历表再 LEFT JOIN 明细聚合结果，此时环比才对零值月有定义；直接在明细聚合结果上算环比会系统性漏掉零值月。分母为 0 的月（上月无销售本月有销售）用 NULLIF 或 CASE 显式处理，避免除零报错。

### 6. 面试延伸考点
- **怎么把断档月补成0再算环比？** 构建月份维表（或用递归 CTE 生成连续月份）与品牌做笛卡尔积，LEFT JOIN 明细聚合后 COALESCE(gmv,0)，环比自然覆盖零值月。
- **同比与环比SQL的差异？** 同比把匹配条件换成 DATE_SUB(INTERVAL 1 YEAR)，或 LAG(gmv, 12) 按月序偏移12行——后者前提是月份无断档，否则仍要校验。
- **环比分子分母要剔除退款吗？** 用净销售额口径时退款随发生月冲减，跨月退款会让上月环比被追溯修改；更稳的做法是按"退款发生月"单独一列，GMV 用应计口径。
- **Hive/Spark 中 LAG 环比注意事项？** 语法一致；Hive 无 INTERVAL 月份加减，用 add_months(CONCAT(ym,'-01'),-1) 拼上月，且要防分区字段类型为字符串时的排序问题。

### 7. 业务拓展思考
品牌环比宽表是招商与买手的作战地图：连续两月高增长品牌应追加流量与库存深度，连续下滑品牌要区分是行业 beta 还是运营问题（对比类目大盘环比即可归因）。可进一步叠加"品牌月活买家数、客单、件单"拆解环比，回答"增长靠人多还是靠买贵"。口径延展上，输出品牌同比+环比双列并加"促/非促"标记，能识别大促透支效应；把品牌替换成店铺、供应商可复用同一套 SQL 骨架。

## EC-23 用户RFM粗分

### 1. 业务背景
CRM 运营做人群圈选的经典模型是 RFM：R（Recency，最近一次购买距今天数）、F（Frequency，统计期内购买次数）、M（Monetary，统计期内消费金额）。数据团队需要一次性算出每个用户的 R/F/M 原始值，按业务阈值或分位数打分分档（各维度高/低），再映射成"重要价值客户、重要挽留客户"等 8 类人群包，导出给投放系统定向发券、短信与 Push。该任务通常每月跑批，人群包质量直接影响营销 ROI。**【面试高频】**RFM 是"多指标一次聚合+条件分档"的综合题，考察点是聚合的正确性、打分方式的业务依据（阈值法 vs 分位法）以及 8 类人群的完整映射。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250910001 | 55001 | paid | 2025-09-10 12:00:00 | 899.00 |
| O20250920001 | 55001 | paid | 2025-09-20 18:30:00 | 129.00 |
| O20250301001 | 55002 | paid | 2025-03-01 09:00:00 | 59.00 |
| O20250905001 | 55003 | refunded | 2025-09-05 20:00:00 | 299.00 |
| O20250115001 | 55003 | paid | 2025-01-15 11:00:00 | 199.00 |

### 3. 解题思路
口径：基准日取 '2025-09-30'；统计期为基准日前 12 个月；R = DATEDIFF(基准日, 最近一次 paid 支付日)，越小越好；F = 去重订单数；M = pay_amount 之和；退款单全部剔除。实现路径：第一层 GROUP BY user_id 一次聚合出 R/F/M（MAX/COUNT/SUM 三兄弟同表同扫）；第二层打分——解法一用业务阈值 CASE WHEN（如 R<=30 天给 5 分），好处是人群含义稳定、跨月可比；解法二用 NTILE(5) 按全站分位打分，好处是人群规模可控，但边界随分布漂移。最后按 R/F/M 是否 >=4 映射 8 类人群。易错点：0 单用户不进该表（要另行统计"注册未购人群"）；打分层引用打分层别名需要再包一层查询。

### 4. 参考解法

解法一：一次聚合 + 业务阈值打分（阈值法，口径稳定可解释）

```sql
WITH rfm AS (                                     -- 第一层：一次聚合算出R/F/M原始值
    SELECT
        user_id,
        DATEDIFF('2025-09-30', MAX(pay_time)) AS r_value,  -- R：最近支付距基准日天数
        COUNT(DISTINCT order_id)             AS f_value,      -- F：统计期支付订单数
        SUM(pay_amount)                      AS m_value       -- M：统计期消费总额
    FROM orders
    WHERE order_status = 'paid'                       -- 退款取消单全剔除
      AND pay_time >= '2024-10-01'                    -- 统计期：基准日前12个月
    GROUP BY user_id
),
scored AS (                                       -- 第二层：按业务阈值打1~5分
    SELECT
        user_id, r_value, f_value, m_value,
        CASE WHEN r_value <=  30 THEN 5            -- 30天内买过：近期活跃
             WHEN r_value <=  90 THEN 4
             WHEN r_value <= 180 THEN 3
             WHEN r_value <= 365 THEN 2
             ELSE 1 END                  AS r_score,
        CASE WHEN f_value >= 20 THEN 5             -- 次数越多分越高
             WHEN f_value >= 10 THEN 4
             WHEN f_value >=  5 THEN 3
             WHEN f_value >=  2 THEN 2
             ELSE 1 END                  AS f_score,
        CASE WHEN m_value >= 5000 THEN 5           -- 金额越高分越高
             WHEN m_value >= 2000 THEN 4
             WHEN m_value >=  800 THEN 3
             WHEN m_value >=  200 THEN 2
             ELSE 1 END                  AS m_score
    FROM rfm
)
SELECT                                            -- 第三层：映射8类人群包
    user_id, r_value, f_value, m_value,
    r_score, f_score, m_score,
    CASE
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值客户'
        WHEN r_score <  4 AND f_score >= 4 AND m_score >= 4 THEN '重要保持客户'
        WHEN r_score >= 4 AND f_score <  4 AND m_score >= 4 THEN '重要发展客户'
        WHEN r_score >= 4 AND f_score >= 4 AND m_score <  4 THEN '重要挽留客户'
        WHEN r_score >= 4                                          THEN '一般发展客户'
        WHEN f_score >= 4                                          THEN '一般保持客户'
        WHEN m_score >= 4                                          THEN '一般挽留客户'
        ELSE '流失风险客户'
    END AS customer_group
FROM scored;
```

结果解读：示例中 55001（R=10、F=2、M=1028）得 R5/F2/M3，判为"重要发展客户"，适合推高价品；55002（R=213）落入低 R 档，归入保持/挽留类，运营可分别匹配不同权益。

解法二：一次聚合 + NTILE(5) 分位打分（分布法，人群规模可控）

```sql
WITH rfm AS (                                     -- 第一层：R/F/M原始值（同解法一）
    SELECT
        user_id,
        DATEDIFF('2025-09-30', MAX(pay_time)) AS r_value,
        COUNT(DISTINCT order_id)             AS f_value,
        SUM(pay_amount)                      AS m_value
    FROM orders
    WHERE order_status = 'paid'
      AND pay_time >= '2024-10-01'
    GROUP BY user_id
),
scored AS (                                       -- 第二层：按全站分位打分
    SELECT
        user_id, r_value, f_value, m_value,
        6 - NTILE(5) OVER (ORDER BY r_value ASC) AS r_score,  -- R越小越好：升序切5份后翻转，最小R得5分
        NTILE(5) OVER (ORDER BY f_value ASC)     AS f_score,  -- F升序切5份：最大F落第5组得5分
        NTILE(5) OVER (ORDER BY m_value ASC)     AS m_score   -- M同F
    FROM rfm
)
SELECT                                            -- 第三层：8类人群映射（同解法一）
    user_id, r_value, f_value, m_value, r_score, f_score, m_score,
    CASE
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值客户'
        WHEN r_score <  4 AND f_score >= 4 AND m_score >= 4 THEN '重要保持客户'
        WHEN r_score >= 4 AND f_score <  4 AND m_score >= 4 THEN '重要发展客户'
        WHEN r_score >= 4 AND f_score >= 4 AND m_score <  4 THEN '重要挽留客户'
        WHEN r_score >= 4                                          THEN '一般发展客户'
        WHEN f_score >= 4                                          THEN '一般保持客户'
        WHEN m_value >= 2000 OR m_score >= 4                       THEN '一般挽留客户'
        ELSE '流失风险客户'
    END AS customer_group
FROM scored;
```

结果解读：NTILE 保证每个得分档约 20% 用户，人群包规模稳定便于投放排期；代价是阈值随全站分布每月漂移，跨月对比人群时要说明口径变化。

### 5. 性能分析与优化
第一层聚合只扫 orders 一遍，是本题主体开销，给 orders 建 (order_status, pay_time) 索引或按 pay_time 分区可显著减少输入；R/F/M 三个聚合在同一次 GROUP BY 内完成，不要写成三个子查询各扫一遍。第二层窗口打分发生在用户级小表上，三次 NTILE 排序代价 O(3N log N)，用户千万级时排序是次瓶颈，可改为先物化 rfm 再打分。阈值法与分位法在执行计划上几乎等价（都是一次窗口/一次 CASE），选择依据是业务口径而非性能。**【加分点】**跑批时把 rfm 层落表、打分层按月重算，人群包导出走增量比对（新进档/掉档用户），可把上游投放系统的更新压力降到最低。

### 6. 面试延伸考点
- **阈值法和分位法各自适用什么场景？** 阈值法业务含义固定、跨期可比，适合有明确运营节奏的成熟业务；分位法保证每档人数比例，适合人群规模需要精确控制的投放，但边界漂移。
- **注册从未购买的用户怎么纳入体系？** RFM 只覆盖购买用户，需 LEFT JOIN 用户表补齐，R 设为"注册至今天数"、F/M 记 0，单独成"注册未购人群"。
- **F 为什么用 COUNT(DISTINCT order_id)？** 防止拆行明细或重复记录放大次数；若 F 按购买日数计，还要对 DATE(pay_time) 去重，口径差异要写清。
- **8 类人群的运营动作分别是什么？** 价值客户做会员权益锁客、保持客户做唤回券、发展客户做高价品推荐、挽留客户做流失预警召回——面试能落到动作才证明懂业务。

### 7. 业务拓展思考
RFM 人群包是精准营销的起点而非终点：上线后要跟踪各人群的核销率、复购率与 ROI，反向修正打分阈值。产品侧可把人群包接入自动化营销（journey）工具，实现"掉档即触发"的实时化。口径延展上，可加入品类偏好维度升级为 RFM+P 模型做交叉推荐；用"R 的变化率"替代绝对值可更早捕捉流失信号；电商大促前把 M 换成"大促期消费"可单独建促敏感人群。

## EC-24 连续3天都有下单的用户识别

### 1. 业务背景
活动运营与风控都要用"连续行为"：大促期间"连续 3 天下单送大奖"的活动需要每天自动产出符合资格的用户名单发放奖励；风控侧则要识别"连续多日高频下单"的异常账户（羊毛党、刷单）进入人工复核。数据分析师需要写一条可复用的 SQL：给定统计窗口，输出"窗口内存在连续 3 个自然日都有支付订单"的用户清单。**【面试高频】**"连续 N 天"是 SQL 面试的经典母题，标准解法是"日期减去行号得到连续段分组键"，掌握它可以推广到连续签到、连续登录、连续播放等一切连续判定场景。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250901001 | 50001 | paid | 2025-09-01 09:00:00 | 59.00 |
| O20250902001 | 50001 | paid | 2025-09-02 10:00:00 | 120.00 |
| O20250903001 | 50001 | paid | 2025-09-03 11:00:00 | 45.00 |
| O20250905001 | 50002 | paid | 2025-09-05 12:00:00 | 199.00 |
| O20250906001 | 50002 | refunded | 2025-09-06 13:00:00 | 89.00 |

### 3. 解题思路
口径：连续按"自然日"判定，同一天多单只算一天（先 DISTINCT 到用户×日期粒度）；退款单不算下单；窗口为 2025-09-01 起近 30 天。实现路径一（日期-行号法）：把去重后的日期按用户升序编号，DATE_SUB(日期, INTERVAL 行号 DAY) 作为分组键——日期连续时该值不变，日期断开则跳变；按用户×分组键聚合，段内天数 >=3 即命中。实现路径二（LAG 差值法）：取前一天与前两天的日期，若 DATEDIFF(当天, 前一天)=1 且 DATEDIFF(当天, 前两天)=2，则当天处于一个长度 >=3 的连续段中。**【避坑指南】**忘记先按"用户×日期"去重是最常见错误——同一天的多单会让行号后移、分组键错乱，从而漏判连续段。

### 4. 参考解法

解法一：日期减行号分组法（连续问题万能模板）

```sql
WITH d AS (                                       -- 第一步：压到"用户×日期"粒度
    SELECT DISTINCT
        user_id,
        DATE(pay_time) AS dt                      -- 只保留自然日，同日多单去重
    FROM orders
    WHERE order_status = 'paid'                   -- 退款单不算下单
      AND pay_time >= '2025-09-01'                -- 统计窗口
),
g AS (                                            -- 第二步：日期减组内行号=连续段键
    SELECT
        user_id,
        dt,
        DATE_SUB(dt, INTERVAL ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY dt) DAY) AS grp
        -- 日期逐日+1、行号逐行+1，相减后连续段内grp恒定，断档则跳变
    FROM d
),
streak AS (                                       -- 第三步：每段连续天数
    SELECT
        user_id,
        grp,
        COUNT(*) AS streak_days                   -- 段内天数=该段连续下单天数
    FROM g
    GROUP BY user_id, grp
)
SELECT DISTINCT user_id                           -- 一人可能有多段>=3天，去重输出
FROM streak
WHERE streak_days >= 3;                           -- 存在任意一段连续>=3天即命中
```

结果解读：示例中 50001 在 9/1-9/3 连续三天 grp 相同、streak_days=3 命中；50002 第二单退款后 9/6 不成日、最长连续 1 天未命中，输出名单可直接对接活动发奖系统。

解法二：LAG 差值法（前后参照，代码更短）

```sql
WITH d AS (                                       -- 用户×日期去重（同解法一）
    SELECT DISTINCT user_id, DATE(pay_time) AS dt
    FROM orders
    WHERE order_status = 'paid'
      AND pay_time >= '2025-09-01'
)
SELECT DISTINCT user_id
FROM (
    SELECT
        user_id,
        dt,
        LAG(dt, 1) OVER w AS d1,                  -- 该用户前1个下单日的日期
        LAG(dt, 2) OVER w AS d2                   -- 前2个下单日的日期
    FROM d
    WINDOW w AS (PARTITION BY user_id ORDER BY dt)  -- WINDOW子句：窗口定义只写一次
) t
WHERE DATEDIFF(dt, d1) = 1                        -- 当天与前一天相邻
  AND DATEDIFF(dt, d2) = 2;                       -- 当天与前两天相邻 => 三天连续
```

结果解读：只要存在某一天同时满足"与前一天差1、与前两天差2"，该用户必然有连续3天；输出与解法一完全一致，且把 N 改大只需增加 LAG 偏移量。

### 5. 性能分析与优化
两解法都要按 (user_id, dt) 排序做窗口，输入是去重后的"用户×日"行数（用户数×窗口天数上界），远小于订单明细，排序代价可控。优化建议：先在 WHERE 里限定 pay_time 窗口再 DISTINCT，减少排序输入；orders 按 pay_time 分区裁剪；(order_status, pay_time) 或 (user_id, pay_time) 索引都有帮助。解法一的 COUNT 段聚合多一层 GROUP BY，但语义可扩展（能输出"最长连续天数"）；解法二更短但 N 大时 WHERE 条件线性增长，且只能判定"存在连续 N 天"不能给段长分布。**【加分点】**若需求是"每个用户最长连续下单天数"，解法一在 streak 层再套 MAX(streak_days) 即可，模板复用性是它的核心优势；Hive/Spark 写法一致，注意 DATEDIFF 参数顺序为 (end, start)。

### 6. 面试延伸考点
- **怎么顺便输出每个用户的最长连续天数？** 解法一在 streak 之后 SELECT user_id, MAX(streak_days) GROUP BY user_id；解法二需要改为对每个"段尾"打标再聚合。
- **"连续3个自然日"和"连续3次购买"的区别？** 前者按日历日，后者按订单序列（不管隔几天）；后者只需 ROW_NUMBER 差值=3 的相邻订单判定，不需要日期参与。
- **跨月、跨年的连续怎么保证正确？** DATE_SUB 按日历日加减天然跨月跨年，与"日期字符串拼接+自增计数"的土办法相比更稳，后者在跨年时会错。
- **活动场景要不要把"下单未支付"算进去？** 活动规则通常以支付为准防刷；若含未支付单，需要同步加风控过滤（同设备多账号等），口径差异要和活动规则文档一致。

### 7. 业务拓展思考
连续行为识别是增长玩法与风控共用的底层能力：活动上"连续下单/连续签到"能显著提升 DAU 与购买频次，但要配套奖励成本模型防羊毛；风控上连续天数、连续单量与收货地址聚集度组合可产出刷单嫌疑名单。口径延展上，把"下单"换成登录、观看、打卡即可复用模板；把窗口从固定30天改为滚动7天/14天，可输出"连续行为发生时间点"，支撑实时化触发与归因分析。

## EC-25 每个用户平均下单间隔天数

### 1. 业务背景
用户生命周期运营用"平均下单间隔"预测下次购买时间：某用户平均 15 天买一次奶粉，第 14 天未复购就触发回购提醒；间隔均值与波动也是划分"高频刚需/低频耐用"用户的依据，影响召回频次与优惠券面额。数据团队需要给每个有 2 次及以上购买的用户计算平均下单间隔天数，输出用户级宽表供 CRM 圈选。该题表面简单，实际考察同日多单处理、单次购买用户的除零/空值处理以及"按单间隔"与"按天间隔"的口径选择。**【避坑指南】**只买过一次的用户没有"间隔"可言，分母为 0 会直接报除零错误，必须显式处理而不是祈祷数据里没有这类用户。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250110001 | 60001 | paid | 2025-01-10 09:00:00 | 89.00 |
| O20250125001 | 60001 | paid | 2025-01-25 10:00:00 | 59.00 |
| O20250209001 | 60001 | paid | 2025-02-09 11:00:00 | 45.00 |
| O20250201001 | 60002 | paid | 2025-02-01 12:00:00 | 199.00 |
| O20250501001 | 60002 | paid | 2025-05-01 13:00:00 | 259.00 |

### 3. 解题思路
口径：间隔按"支付自然日"计，同一天多单视为一次购买（先 DISTINCT 用户×日期），否则一天下 5 单会把间隔算成 0 天拉低均值；平均下单间隔 = 相邻两次购买日间隔天数的算术平均，只有 >=2 个购买日才有值。实现路径一：去重后用 LAG 取上一购买日，逐单算 DATEDIFF 再 AVG；实现路径二：利用"相邻间隔之和 = 首末日期之差"的性质，用 (MAX(日期)-MIN(日期))/(购买日数-1) 一步算出，数学上与逐单平均严格相等（裂项相消），但要处理购买日数=1 的除零。易错点：忘记按日去重、除零未处理、把 cancelled 计入。

### 4. 参考解法

解法一：LAG 逐单间隔再平均（直白、可扩展到间隔分布）

```sql
WITH o AS (                                       -- 第一步：用户×购买日去重
    SELECT DISTINCT
        user_id,
        DATE(pay_time) AS dt                      -- 同日多单只算一次购买
    FROM orders
    WHERE order_status = 'paid'                   -- 只计有效支付
),
g AS (                                            -- 第二步：每个购买日带上上一购买日
    SELECT
        user_id,
        dt,
        LAG(dt) OVER (PARTITION BY user_id ORDER BY dt) AS prev_dt  -- 上一次购买日期
    FROM o
)
SELECT
    user_id,
    COUNT(*) AS gap_cnt,                          -- 间隔个数=购买日数-1（WHERE已排除首单行）
    ROUND(AVG(DATEDIFF(dt, prev_dt)), 2) AS avg_gap_days  -- 平均下单间隔天数
FROM g
WHERE prev_dt IS NOT NULL                         -- 首单没有"上次"，剔除后不进分子分母
GROUP BY user_id
HAVING COUNT(*) >= 1;                             -- 至少有1个间隔（即至少买过2天）
```

结果解读：示例中 60001 间隔 15、15 天，均值为 15.0；60002 只有 1 个间隔 89 天——单间隔用户也能输出，CRM 可据此把 89 天间隔的用户归入低频召回池。

解法二：极差公式法 (MAX-MIN)/(COUNT-1)，一次聚合无窗口

```sql
WITH o AS (                                       -- 用户×购买日去重（同解法一）
    SELECT DISTINCT user_id, DATE(pay_time) AS dt
    FROM orders
    WHERE order_status = 'paid'
)
SELECT
    user_id,
    COUNT(*) AS buy_days,                         -- 购买日数
    DATEDIFF(MAX(dt), MIN(dt)) AS span_days,      -- 首末购买日跨度
    CASE WHEN COUNT(*) >= 2                       -- 至少2个购买日才有间隔
         THEN ROUND(DATEDIFF(MAX(dt), MIN(dt)) / (COUNT(*) - 1), 2)
         ELSE NULL                                -- 单次购买：无间隔，给NULL而不是报错
    END AS avg_gap_days
FROM o
GROUP BY user_id
ORDER BY avg_gap_days;                            -- 按间隔升序：高频刚需用户排最前
```

结果解读：60001 为 (2025-02-09 减 2025-01-10)/2 = 15.0，与解法一逐单平均完全一致——因为相邻间隔之和恒等于首末跨度（裂项相消），该公式法可免窗口排序，大表上更快。

### 5. 性能分析与优化
解法一需要按 (user_id, dt) 排序做 LAG，输入为去重后的"用户×日"行；解法二只需一次 GROUP BY 聚合（MAX/MIN/COUNT 都是单遍聚合），无排序、无窗口，在大表上通常更优，代价是无法输出"每个间隔"的明细。优化建议：先 DISTINCT 压粒度再计算（两解法已内置）；orders 上建 (order_status, pay_time) 索引/分区裁剪减少输入；若要同时看间隔分布（中位数、P90），解法一的基础才能支撑，可把 g 层落成中间表复用。**【加分点】**能主动说明"两解法在按日去重后数学等价、但口径改为按订单计间隔时不再等价"（同日多单会产生 0 天间隔），体现口径敏感度。

### 6. 面试延伸考点
- **按"订单间隔"还是"购买日间隔"统计？** 同日多单在订单口径下产生 0 天间隔拉低均值，日口径更符合"回购节奏"的业务含义；口径必须写入报表定义。
- **平均间隔能不能预测"下次购买时间"？** 可以作为基线（上次购买日+平均间隔），但更稳健的是按品类统计间隔分布取中位数，因个体波动大、样本少的用户均值不可靠。
- **只有 1 单的用户怎么处理？** 两种选择：输出 NULL 并在下游排除，或归入"间隔未知"人群；千万不要用 COALESCE 成 0 或极大值，会污染分层边界。
- **间隔的异常值（如两年没买又回来）怎么处理？** 可用 P25-P75 截尾或中位数替代均值；更严格的做法是给间隔加上限（如 >180 天按 180 截断）并在口径中注明。

### 7. 业务拓展思考
平均下单间隔是把"复购率"升级为"回购时间预测"的桥梁：与品类自然消耗周期（奶粉罐数、化妆品毫升数）对照，可验证用户节奏是否被运营节奏（大促、券）扭曲。CRM 上按间隔触发"到期提醒"比固定 30 天群发转化率高数倍；对间隔突然变长的用户做流失预警。口径延展上，可输出"间隔波动系数"（标准差/均值）识别稳定回购者与偶发买家；把间隔分布与会员等级交叉，可检验权益是否真的提高了购买频率。

## EC-26 用券人群与未用券人群客单价对比

### 1. 业务背景
市场部复盘大促满减券的效果：需要对比"使用优惠券的订单"与"未用券订单"的客单价（单均实付金额），回答"券是否真的拉高了客单价、还是只把本来就会买的人便宜卖了"。若用券客单价显著高于未用券，说明满减门槛有效带动凑单；若两者接近甚至倒挂，则要重设门槛或改为品类券。数据分析师需要一条 SQL 同时输出两档客单价与差值，作为券策略迭代的输入。**【加分点】**能在面试中点出"这是描述性对比而非因果结论——用券订单可能本身金额就高（满减门槛筛选效应），严谨结论需 A/B 或倾向得分匹配"，是数据思维的直接体现。

### 2. 表结构说明
orders（订单主表，含优惠信息，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| pay_amount | DECIMAL(10,2) | 券后实付金额 |
| discount_amount | DECIMAL(10,2) | 优惠总金额（0表示未用券） |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |

示例数据 orders：

| order_id | user_id | pay_amount | discount_amount | order_status | pay_time |
|----------|---------|------------|-----------------|--------------|----------|
| O20250901001 | 70001 | 238.00 | 30.00 | paid | 2025-09-01 10:00:00 |
| O20250901002 | 70002 | 99.00 | 0.00 | paid | 2025-09-01 11:00:00 |
| O20250902001 | 70003 | 458.00 | 50.00 | paid | 2025-09-02 12:00:00 |
| O20250902002 | 70004 | 129.00 | 0.00 | refunded | 2025-09-02 13:00:00 |
| O20250903001 | 70005 | 199.00 | 0.00 | paid | 2025-09-03 14:00:00 |

### 3. 解题思路
口径：用券订单 = discount_amount > 0；客单价 = SUM(pay_amount) / COUNT(DISTINCT order_id)，即券后实付的单均；退款单剔除（也可另出一列"用券订单退款率"作补充）；统计期限定 paid 订单。实现路径一：条件聚合——一条扫描里用 CASE WHEN 分别对用券/未用券求和与计数，一行输出两个客单价与差值；实现路径二：先按"是否用券" GROUP BY 聚合出每组的单量与金额，再行转列（MAX+CASE）拼成一行，便于同时保留分组明细。易错点：把客单价算成 SUM/COUNT(*)（把退款单算进分母）；用券判定写成 discount_amount IS NOT NULL（NULL 语义与 0 的区别）；对比口径要用同一时间窗，避免大促期与日常期混比。

### 4. 参考解法

解法一：条件聚合一次扫描，一行输出双指标（推荐，报表友好）

```sql
SELECT
    ROUND(SUM(CASE WHEN discount_amount > 0
                   THEN pay_amount END)
          / NULLIF(COUNT(DISTINCT CASE WHEN discount_amount > 0
                                       THEN order_id END), 0), 2) AS coupon_aov,     -- 用券客单价
    ROUND(SUM(CASE WHEN COALESCE(discount_amount, 0) = 0
                   THEN pay_amount END)
          / NULLIF(COUNT(DISTINCT CASE WHEN COALESCE(discount_amount, 0) = 0
                                       THEN order_id END), 0), 2) AS nocoupon_aov,   -- 未用券客单价
    ROUND(SUM(CASE WHEN discount_amount > 0 THEN pay_amount END)
          / NULLIF(COUNT(DISTINCT CASE WHEN discount_amount > 0
                                       THEN order_id END), 0)
        - SUM(CASE WHEN COALESCE(discount_amount, 0) = 0 THEN pay_amount END)
          / NULLIF(COUNT(DISTINCT CASE WHEN COALESCE(discount_amount, 0) = 0
                                       THEN order_id END), 0), 2) AS aov_diff         -- 两者差值
FROM orders
WHERE order_status = 'paid'                       -- 退款取消单剔除，保证分子分母同口径
  AND pay_time >= '2025-09-01'
  AND pay_time <  '2025-10-01';                   -- 统一大促对比窗口
```

结果解读：示例输出用券客单价 (238+458)/2=348.00、未用券 (99+199)/2=149.00、差值 199.00——用券订单客单价约为未用券的 2.3 倍，支持"满减门槛带动凑单"的初步判断，但仍需剔除品类结构差异再下结论。

解法二：先按是否用券分组聚合，再行转列拼一行（便于保留分组明细）

```sql
WITH aov AS (                                     -- 第一层：按"是否用券"分组聚合
    SELECT
        CASE WHEN discount_amount > 0
             THEN '用券' ELSE '未用券' END AS grp,   -- 二分人群键
        COUNT(DISTINCT order_id) AS ord_cnt,          -- 各组订单数
        SUM(pay_amount)          AS pay_sum           -- 各组实付总额
    FROM orders
    WHERE order_status = 'paid'
      AND pay_time >= '2025-09-01'
      AND pay_time <  '2025-10-01'
    GROUP BY CASE WHEN discount_amount > 0 THEN '用券' ELSE '未用券' END
)
SELECT
    ROUND(MAX(CASE WHEN grp = '用券'   THEN pay_sum / ord_cnt END), 2) AS coupon_aov,    -- 行转列：用券客单价
    ROUND(MAX(CASE WHEN grp = '未用券' THEN pay_sum / ord_cnt END), 2) AS nocoupon_aov,  -- 行转列：未用券客单价
    ROUND(MAX(CASE WHEN grp = '用券'   THEN pay_sum / ord_cnt END)
        - MAX(CASE WHEN grp = '未用券' THEN pay_sum / ord_cnt END), 2)     AS aov_diff    -- 差值
FROM aov;
```

结果解读：与解法一数值一致，但 aov 中间层是标准长表（grp, ord_cnt, pay_sum），要扩展"客单件数、退款率、毛利率"等指标时直接加列，比条件聚合更易维护。

### 5. 性能分析与优化
两解法都只扫 orders 一遍，无 JOIN 无窗口，代价集中在过滤 paid 后的聚合，(order_status, pay_time) 索引或按月分区可把输入压到周期内。解法一 SELECT 列表中 CASE 重复出现多次（可读性差但无额外扫描，MySQL 会复用同一行数据）；解法二多一层 CTE 物化，行数只有 2 行，开销可忽略，换来扩展性。**【避坑指南】**对比必须控制"其他变量相同"：用券与未用券订单的品类结构、新老客比例若差异巨大，客单价差会被结构效应污染；建议再出一列"分品类对比"或按新老客分层对比，防止拿到一个漂亮但误导的总体差值。订单粒度去重用 order_id（主键），无需 COUNT(DISTINCT) 也安全，但若表含拆行明细则必须去重。

### 6. 面试延伸考点
- **怎么把对比升级为因果推断？** 有实验就做大促期间随机发券的 A/B，用发券人群做 ITT 分析；没有实验可用 PSM（倾向得分匹配）控制选券人群的自选择偏差，SQL 能完成匹配前的特征准备。
- **客单价提升会不会是"凑单后退款"？** 用券订单退款率若更高，名义客单价虚高，应并列输出"用券/未用券退款率"与"净客单价（扣退款）"。
- **用券口径除了 discount_amount>0 还有别的吗？** 可按 coupon_id 关联券表区分券类型（满减/折扣/包邮），不同券种对客单的拉动差异才是运营真正要的结论。
- **为什么分母要 COUNT(DISTINCT order_id)？** 若表为订单明细粒度（一单多行），COUNT(*) 会把客单价除小；订单主表粒度下 DISTINCT 是防御性写法，成本极低。

### 7. 业务拓展思考
券效果分析要形成"发放→核销→客单变化→ROI"闭环：用券人群客单价提升带来的毛利增量，减去券成本与自然转化损失，才是券的真实 ROI。产品上可实验差异化门槛（满 99 减 20 vs 满 199 减 40），观察客单价与核销率的弹性曲线找最优点。口径延展上，可把对比下沉到"同用户用券前后"（自对照）削弱结构差异；把用券人群再按新老客拆分，能识别"券到底拉动了新客首单还是补贴了老客"。

## EC-27 各渠道新客首单转化率（注册→首单）

### 1. 业务背景
市场投放团队按渠道评估拉新质量：抖音信息流、应用商店、地推等渠道的注册量与获客成本差异巨大，但"注册→首单"的转化才是质量的试金石——注册多而不买是无效消耗。运营需要按注册渠道统计：注册用户数、其中在注册后 30 天内完成首单（首次支付）的人数、转化率，以及平均首单等待时长，用于动态调整各渠道预算分配与素材策略。该指标通常按周/月分渠道复盘。**【面试高频】**"注册→首单"是双表（用户表+订单表）漏斗，考察 LEFT JOIN 保分母的意识——漏掉从未下单的用户、分母只剩购买用户，转化率会虚高到不可用。

### 2. 表结构说明
users（用户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| user_id | BIGINT | 用户ID，主键 |
| channel | VARCHAR(32) | 注册渠道：抖音信息流/应用商店/地推等 |
| register_time | DATETIME | 注册时间 |

orders（订单主表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 users：

| user_id | channel | register_time |
|---------|---------|----------------|
| 80001 | 抖音信息流 | 2025-09-01 10:00:00 |
| 80002 | 抖音信息流 | 2025-09-02 11:00:00 |
| 80003 | 应用商店 | 2025-09-03 12:00:00 |
| 80004 | 地推 | 2025-09-04 13:00:00 |
| 80005 | 应用商店 | 2025-09-05 14:00:00 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250905001 | 80001 | paid | 2025-09-05 10:00:00 | 128.00 |
| O20250910001 | 80002 | paid | 2025-09-10 11:00:00 | 89.00 |
| O20250920001 | 80003 | paid | 2025-09-20 12:00:00 | 59.00 |
| O20250926001 | 80004 | cancelled | 2025-09-26 13:00:00 | 199.00 |
| O20251101001 | 80003 | refunded | 2025-11-01 15:00:00 | 45.00 |

### 3. 解题思路
口径：分母 = 统计期内注册的去重用户数（按注册渠道）；分子 = 注册后 30 天内产生 paid 订单的用户（首单即用户 MIN(pay_time)，需落在 [注册时间, 注册时间+30天] 区间）；cancelled/refunded 不算成单；30 天窗口外才首单的用户不算转化但要在"30天后转化"另行统计，防止口径混淆。实现路径一：先在用户级求出首单时间 CTE，LEFT JOIN 用户表（保住从未购买的人），按渠道条件聚合；实现路径二：不做预聚合，用 EXISTS 相关子查询在用户行上直接判断"30 天内是否存在 paid 单"，配合 GROUP BY 渠道聚合。易错点：JOIN 后在 WHERE 里过滤订单条件会把未购买用户整行滤掉（分母变小）；转化窗口要用注册时间为锚点而不是固定日期。

### 4. 参考解法

解法一：首单 CTE + LEFT JOIN 条件聚合（漏斗标准写法）

```sql
WITH fo AS (                                      -- 第一层：每个用户的首单支付时间
    SELECT
        user_id,
        MIN(pay_time) AS first_pay_time           -- 首次支付即首单
    FROM orders
    WHERE order_status = 'paid'                   -- 只计有效支付
    GROUP BY user_id
)
SELECT
    u.channel AS channel,                         -- 注册渠道
    COUNT(*) AS reg_users,                        -- 分母：该渠道注册用户数
    SUM(f.first_pay_time IS NOT NULL
        AND f.first_pay_time <= u.register_time + INTERVAL 30 DAY) AS conv_users,  -- 分子：30天内成单
    ROUND(SUM(f.first_pay_time IS NOT NULL
        AND f.first_pay_time <= u.register_time + INTERVAL 30 DAY)
        / COUNT(*), 4) AS conv_rate,              -- 注册→首单转化率
    ROUND(AVG(CASE WHEN f.first_pay_time IS NOT NULL
                     AND f.first_pay_time <= u.register_time + INTERVAL 30 DAY
                    THEN TIMESTAMPDIFF(HOUR, u.register_time, f.first_pay_time)
               END) / 24, 2) AS avg_days_to_first_order  -- 转化用户的平均首单等待天数
FROM users u
LEFT JOIN fo f ON f.user_id = u.user_id           -- LEFT JOIN保住从未购买的用户
WHERE u.register_time >= '2025-09-01'
  AND u.register_time < '2025-10-01'              -- 统计期内注册
GROUP BY u.channel
ORDER BY conv_rate DESC;                          -- 按转化率降序：好渠道排前
```

结果解读：示例中抖音信息流 2 人全在 30 天内成单（转化率 1.0）、应用商店 2 人中 80003 第 17 天成单（0.5）、地推 80004 只有取消单（0.0），预算应向抖音倾斜并对地推做归因排查。

解法二：EXISTS 相关子查询 + 条件聚合（不预聚合，逐用户判定）

```sql
SELECT
    u.channel AS channel,
    COUNT(*) AS reg_users,                        -- 分母：注册用户数
    SUM(EXISTS (                                  -- EXISTS返回0/1，当布尔计数用
            SELECT 1
            FROM orders o
            WHERE o.user_id = u.user_id           -- 该用户的订单
              AND o.order_status = 'paid'         -- 有效支付
              AND o.pay_time >= u.register_time   -- 不早于注册（防脏数据）
              AND o.pay_time <= u.register_time + INTERVAL 30 DAY  -- 30天窗口
    )) AS conv_users,                             -- 分子：30天内完成首单
    ROUND(SUM(EXISTS (
            SELECT 1
            FROM orders o
            WHERE o.user_id = u.user_id
              AND o.order_status = 'paid'
              AND o.pay_time >= u.register_time
              AND o.pay_time <= u.register_time + INTERVAL 30 DAY
    )) / COUNT(*), 4) AS conv_rate
FROM users u
WHERE u.register_time >= '2025-09-01'
  AND u.register_time < '2025-10-01'
GROUP BY u.channel
ORDER BY conv_rate DESC;
```

结果解读：与解法一转化率完全一致；该写法把"是否转化"封装成逐行布尔，SQL 更短，且天然不会因 JOIN 丢分母，适合作为快速取数版本。

### 5. 性能分析与优化
解法一对 orders 聚合一次（fo 为用户级），JOIN 键 user_id 是 users 主键不会膨胀，总代价 = 一次订单表扫描 + 一次 hash join；解法二的 EXISTS 在 (user_id, order_status, pay_time) 索引下每个用户只做索引探测，注册用户数远小于订单数时非常高效，但没有合适索引时会退化为逐用户全表探测。优化建议：orders 建 (order_status, user_id, pay_time) 复合索引；users 按 register_time 分区/过滤减少分母侧扫描；若渠道数固定且报表高频，把 fo 落成用户首单宽表长期复用。**【避坑指南】**绝不能把订单表 INNER JOIN 或把订单条件写进 WHERE——未购买用户会被整行过滤，转化率被系统性高估；这两个解法分别用"LEFT JOIN+聚合表达式"与"EXISTS 布尔"规避了该陷阱。

### 6. 面试延伸考点
- **渠道归因怎么更准确？** 用户表只记"注册渠道"，若用户先被种草后自然搜索注册，会归因偏差；可引入首触/末触归因（需要触点日志表）或归因窗口概念，面试说清层次即可。
- **30天窗口为什么常用？** 电商新客决策周期多在两周内，30天兼顾长决策品类；更严谨可输出 7/15/30 天三条转化率曲线观察收敛速度。
- **转化率和"平均首单等待时长"要一起看吗？** 要——高转化+长等待说明渠道用户犹豫型，适合培育式运营；只看转化率会漏掉节奏差异。
- **Hive/Spark 里 EXISTS 的性能？** 旧版 Hive 对相关子查询支持差，通常改写为 LEFT JOIN+聚合或 IN；Spark 3.x 已支持良好，笔试可主动说明改写能力。

### 7. 业务拓展思考
分渠道"注册→首单"转化是投放预算再分配的核心依据：转化率乘以首单毛利再除以 CAC 即渠道首单 ROI，可排出真实的渠道性价比。产品上可对高注册低转化渠道做落地页与新手动线诊断，区分"流量假"与"承接差"。口径延展上，把首单换成"累计 N 单"或"30 天内 GMV 达标"可构建渠道质量漏斗；叠加注册月份 cohort，能观察渠道质量随时间与素材迭代的漂移，形成投放的反馈闭环。
## EC-28 每个用户购买品类数分布

### 1. 业务背景
交叉销售团队用"购买品类数"（品类宽度）衡量用户的跨品类渗透：经验上买过 3 个及以上品类的用户 LTV 与留存显著更高，而只买过单一品类的用户是最容易流失、也最适合推"跨品类首购券"的人群。运营需要两张产出：一是每个用户的购买品类数明细（对接 CRM 打人群标签），二是全站品类宽度分布（品类数=1/2/3/4+ 的用户数与占比），用于制定交叉销售目标与衡量活动效果。**【面试高频】**"去重计数后再聚合"是两层聚合的经典组合题，MySQL 窗口函数不支持 DISTINCT 聚合这个细节是高频追问点。

### 2. 表结构说明
orders（订单主表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |

order_items（订单明细表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| item_id | BIGINT | 明细行ID，主键 |
| order_id | VARCHAR(32) | 订单ID |
| sku_id | VARCHAR(32) | 商品ID |

products（商品维表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sku_id | VARCHAR(32) | 商品ID，主键 |
| sku_name | VARCHAR(128) | 商品名称 |
| category_id | VARCHAR(16) | 类目ID |
| category_name | VARCHAR(64) | 类目名称 |

示例数据 orders：

| order_id | user_id | order_status | pay_time |
|----------|---------|--------------|----------|
| O20250901001 | 88001 | paid | 2025-09-01 10:00:00 |
| O20250902001 | 88001 | paid | 2025-09-02 11:00:00 |
| O20250903001 | 88002 | paid | 2025-09-03 12:00:00 |
| O20250904001 | 88003 | paid | 2025-09-04 13:00:00 |
| O20250905001 | 88004 | cancelled | 2025-09-05 14:00:00 |

示例数据 order_items 与 products：

| item_id | order_id | sku_id | ←→ | sku_id | sku_name | category_id | category_name |
|---------|----------|--------|----|--------|----------|-------------|----------------|
| 1 | O20250901001 | S201 | | S201 | 燕麦奶1L | C10 | 食品 |
| 2 | O20250901001 | S301 | | S301 | 不锈钢保温杯 | C20 | 家居 |
| 3 | O20250902001 | S101 | | S101 | 经典拿铁咖啡豆 | C10 | 食品 |
| 4 | O20250903001 | S401 | | S401 | 纯棉T恤 | C30 | 服饰 |
| 5 | O20250904001 | S301 | | S301 | 不锈钢保温杯 | C20 | 家居 |

### 3. 解题思路
口径：品类宽度 = 用户在统计期内购买过（paid 订单）的"去重品类数"；同一品类买多次只算 1；退款单剔除；统计期取近一个季度。实现路径分两层：第一层把 orders→order_items→products 三表 JOIN 起来，压到"用户×品类"去重粒度（解法一用 GROUP BY 显式去重，解法二直接 COUNT(DISTINCT category_id)）；第二层按品类宽度分箱（1、2、3、4+）统计用户数与占比。易错点：**【避坑指南】**MySQL 8.0 的窗口聚合里不能写 COUNT(DISTINCT ...) OVER(...)（语法不支持），"先去重子查询、再开窗"是标准规避写法；另外 JOIN 链上 order_items 一单多行会让 orders 行复制，若在订单粒度算指标会重复计数，必须在聚合前想清楚"去重发生在哪一层"。

### 4. 参考解法

解法一：三表 JOIN 显式去重 + 两层聚合（结构清晰，粒度可控）

```sql
WITH uc AS (                                      -- 第一层：用户×品类去重
    SELECT
        o.user_id,
        p.category_id
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id  -- 明细挂订单
    JOIN products p     ON p.sku_id = oi.sku_id      -- 明细挂类目
    WHERE o.order_status = 'paid'                    -- 只计有效支付
      AND o.pay_time >= '2025-07-01'                 -- 统计期：近一季度
    GROUP BY o.user_id, p.category_id                -- 显式去重：一人一品类一行
),
w AS (                                            -- 第二层：每个用户的品类宽度
    SELECT
        user_id,
        COUNT(*) AS cat_cnt                       -- 去重后的品类数
    FROM uc
    GROUP BY user_id
)
SELECT
    CASE WHEN cat_cnt >= 4 THEN '4+'              -- 宽度分箱：4及以上合并
         ELSE CAST(cat_cnt AS CHAR) END AS width_bin,
    COUNT(*) AS user_cnt,                         -- 该档用户数
    ROUND(COUNT(*) / (SELECT COUNT(*) FROM w), 4) AS user_pct  -- 占比：相关子查询求全站分母
FROM w
GROUP BY width_bin                                -- MySQL允许按别名分组
ORDER BY width_bin;
```

结果解读：示例中 88001 买了食品+家居（宽度2）、88002 宽度1、88003 宽度1，输出"宽度1占比高"这类分布；宽度=1 的人群就是跨品类券的核心圈选对象。

解法二：COUNT(DISTINCT) 一步去重 + 窗口函数算占比（代码最短）

```sql
WITH w AS (                                       -- 一步到位：每用户去重品类数
    SELECT
        o.user_id,
        COUNT(DISTINCT p.category_id) AS cat_cnt  -- DISTINCT聚合直接去重
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p     ON p.sku_id = oi.sku_id
    WHERE o.order_status = 'paid'
      AND o.pay_time >= '2025-07-01'
    GROUP BY o.user_id
)
SELECT
    CASE WHEN cat_cnt >= 4 THEN '4+'
         ELSE CAST(cat_cnt AS CHAR) END AS width_bin,
    COUNT(*) AS user_cnt,                         -- 该档用户数
    ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4) AS user_pct  -- 聚合结果上开窗口：全站总数作分母
FROM w
GROUP BY width_bin
ORDER BY width_bin;
```

结果解读：与解法一数值一致；SUM(COUNT(*)) OVER () 用全局窗口免去了相关子查询，占比计算内聚在一层，是 MySQL 8.0 里最优雅的"分组占比"写法。

> Hive/Spark 差异提示：MySQL 8.0 窗口聚合不支持 DISTINCT；Spark SQL 支持 COUNT(DISTINCT) OVER，Hive 不支持，需先在子查询里 DISTINCT 再开窗。三表 JOIN 在 Hive 中要注意小表（products）广播以避免 shuffle。

### 5. 性能分析与优化
三表 JOIN 的基数关系决定代价：orders→order_items 是一对多放大（放大到明细行数），order_items→products 是多对一（products.sku_id 为主键，不放大）。优化建议：三表都走主键/索引等值 JOIN（order_id、sku_id 均为主键），无需担心膨胀；orders 先按 order_status+pay_time 过滤缩小集合再 JOIN，能把放大基数压到最低；若类目层级常变，建议在数仓 DWD 明细里冗余 category_id，去掉一次 JOIN。解法二与解法一的差别只在第二层（DISTINCT 聚合 vs 显式去重再 COUNT），执行上 DISTINCT 聚合在 MySQL 内部同样走去重临时表，两者代价接近；占比侧解法二的 OVER () 是聚合后小表上的窗口，可忽略。数据量极大时把"用户×品类"去重结果落表，分布统计变为毫秒级查询。

### 6. 面试延伸考点
- **MySQL 窗口函数为什么不支持 COUNT(DISTINCT) OVER？** DISTINCT 聚合需要先去重集合再计算，而窗口的滑动帧语义与去重集合维护冲突（帧边界变化时无法增量维护），标准 SQL 也未定义；规避法就是"子查询去重后开窗"。
- **宽度分布用"购买品类数"还是"浏览品类数"？** 购买宽度反映已渗透，浏览宽度反映潜在兴趣；两者对比可发现"看了很多类但只买一类"的决策障碍人群，是推荐系统的重点对象。
- **怎么算"品类宽度对LTV的边际贡献"？** 按宽度分箱聚合人均 GMV/留存，但要注意相关不等于因果（高价值用户本来就爱买多品类），可用同 cohort 前后对比或匹配法修正。
- **GROUP BY 别名 width_bin 在其他数据库通用吗？** MySQL 与 Spark 支持按别名分组；PostgreSQL/老版本 Hive 不允许，稳妥写法是重复 CASE 表达式或在子查询里先算好分箱列。

### 7. 业务拓展思考
品类宽度是交叉销售战略的核心 KPI：把"宽度=1 用户占比"作为北极星指标之一，配合跨品类首购券、组合装、购物车凑单推荐形成打法闭环。产品上可按"第一购买品类"聚类，识别各入口品类的天然延伸路径（如母婴用户向家居延伸），指导货架与推荐策略。口径延展上，可用"月均宽度""宽度增速"衡量渗透速度；把宽度分布与 RFM 交叉，可输出"高价值低宽度"黄金人群——他们有钱、爱买、但只买一类，是跨品类转化率最高的人群。

## EC-29 新老客GMV拆分（首单月判定）

### 1. 业务背景
经营分析月报的固定模块是把每月 GMV 拆成"新客 GMV"与"老客 GMV"：新客 GMV = 该月是这个用户第一个购买月的订单金额，老客 GMV = 其余订单金额。这个拆分回答的是公司增长的本质问题——"增长靠拉新还是靠存量"，并与获客成本（CAC）联用判断增长质量：若 GMV 增长几乎全靠新客，而 CAC 又在上涨，增长模型是不可持续的。数据分析师每月要跑一次该拆分并输出趋势序列。**【加分点】**首单月的判定粒度（按支付月）、退款单是否参与"首单"认定、以及用窗口还是 CTE 两种实现路径的选择，是本题的三个讨论层次。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250801001 | 90001 | paid | 2025-08-01 10:00:00 | 199.00 |
| O20250820001 | 90002 | paid | 2025-08-20 18:00:00 | 89.00 |
| O20250901001 | 90002 | paid | 2025-09-01 09:00:00 | 59.00 |
| O20250905001 | 90003 | paid | 2025-09-05 20:00:00 | 899.00 |
| O20250920001 | 90001 | paid | 2025-09-20 21:00:00 | 45.00 |

### 3. 解题思路
口径：用户首单月 = 该用户最早一笔 paid 订单的支付月份（DATE_FORMAT(pay_time,'%Y-%m')）；订单级判定——订单所在月等于其用户首单月即为"新客GMV"，否则为"老客GMV"；退款单不参与首单认定也不计入 GMV。实现路径一：用 MIN(pay_time) OVER(PARTITION BY user_id) 给每一行订单挂上首单时间，行内比较订单月与首单月后条件求和，一次扫描完成；实现路径二：先聚合出"用户×首单月"CTE，再 JOIN 回订单表打标，逻辑分步、可读性高且首单月可落表复用。易错点：首单跨月退款后首单月会漂移（口径需声明"以支付成功为准"）；DATE_FORMAT 前忘过滤 paid 会把退款单金额计入 GMV；跨年月份用字符串比较恰好正确（'2025-01' > '2024-12'），但不能用 DATE_FORMAT 截断后再做数值运算。

### 4. 参考解法

解法一：MIN() 窗口挂首单时间 + 条件求和（一次扫描）

```sql
WITH t AS (
    SELECT
        user_id,
        pay_time,
        pay_amount,
        DATE_FORMAT(pay_time, '%Y-%m') AS ym,     -- 订单所在月
        MIN(pay_time) OVER (PARTITION BY user_id) AS first_pay_time  -- 该用户首单支付时间（全行标注）
    FROM orders
    WHERE order_status = 'paid'                   -- 退款取消不计GMV也不参与首单认定
)
SELECT
    ym AS month,                                  -- 统计月
    ROUND(SUM(CASE WHEN DATE_FORMAT(first_pay_time, '%Y-%m') = ym
                   THEN pay_amount ELSE 0 END), 2) AS new_user_gmv,  -- 订单月=首单月 → 新客GMV
    ROUND(SUM(CASE WHEN DATE_FORMAT(first_pay_time, '%Y-%m') <> ym
                   THEN pay_amount ELSE 0 END), 2) AS old_user_gmv,  -- 否则 → 老客GMV
    ROUND(SUM(pay_amount), 2) AS total_gmv        -- 合计GMV便于校验勾稽
FROM t
GROUP BY ym
ORDER BY ym;
```

结果解读：示例中 8 月 GMV=288 全部为新客贡献（90001、90002 的首单都在 8 月），9 月 1003 元中仅 90003 的 899 元是新客、154 元是老客复购——9 月增长主要靠新客，存量复购贡献偏弱，需关注。

解法二：首单月 CTE + JOIN 打标（分步可读，首单月可复用）

```sql
WITH fo AS (                                      -- 第一层：每个用户的首单月
    SELECT
        user_id,
        DATE_FORMAT(MIN(pay_time), '%Y-%m') AS first_ym  -- 最早支付时间所属月
    FROM orders
    WHERE order_status = 'paid'
    GROUP BY user_id
)
SELECT
    DATE_FORMAT(o.pay_time, '%Y-%m') AS month,    -- 订单月
    ROUND(SUM(CASE WHEN f.first_ym = DATE_FORMAT(o.pay_time, '%Y-%m')
                   THEN o.pay_amount ELSE 0 END), 2) AS new_user_gmv,  -- JOIN回首单月后打标求和
    ROUND(SUM(CASE WHEN f.first_ym <> DATE_FORMAT(o.pay_time, '%Y-%m')
                   THEN o.pay_amount ELSE 0 END), 2) AS old_user_gmv,
    COUNT(DISTINCT CASE WHEN f.first_ym = DATE_FORMAT(o.pay_time, '%Y-%m')
                        THEN o.user_id END) AS new_user_cnt,  -- 顺带输出当月新客数
    ROUND(SUM(o.pay_amount), 2) AS total_gmv
FROM orders o
JOIN fo f ON f.user_id = o.user_id                -- 每笔订单挂上用户首单月
WHERE o.order_status = 'paid'
GROUP BY DATE_FORMAT(o.pay_time, '%Y-%m')
ORDER BY month;
```

结果解读：与解法一拆分结果一致，并额外给出当月新客人数；fo 层是标准的"用户首单月"维表，可落表供留存、LTV 等多个报表复用，工程上更受数仓团队欢迎。

### 5. 性能分析与优化
解法一扫描 orders 一遍，窗口按 user_id 分区排序，明细千万级时排序是主要开销（可用索引 (order_status, user_id, pay_time) 让窗口数据有序输入，减少 filesort）；解法二先聚合（一次扫描+GROUP BY）再 hash join 回 orders（第二次扫描），总扫描量约两倍，但聚合后 fo 表极小，JOIN 代价低，且 fo 可物化复用。优化建议：报表场景优先把 fo 落成"用户首单月快照"并按月增量刷新，后续新老客拆分退化为一次 JOIN+聚合；解法一胜在单次扫描、无 JOIN，适合临时取数。**【避坑指南】**不要用"订单月 > 用户首单月即老客"的思路直接 GROUP BY 而漏掉"订单月 = 首单月"的新客判定基准——首单月必须来自 paid 订单的 MIN(pay_time)，若把退款单也算进 MIN，首单月会漂移、拆分结果整体错位。

### 6. 面试延伸考点
- **首单被全额退款后，该用户算"新客"还是"老客"？** 严格口径：无有效支付单则未成单，下次成功支付重新成为新客；宽松口径：支付行为发生即认定首单。两种口径对"新客GMV"影响巨大，必须与财务口径对齐。
- **新老客拆分粒度为什么是"月"而不是"日"？** 月粒度与月报、预算口径一致且平滑日常波动；日粒度可用于大促复盘看新客集中爆发，但要做工作日/节假日校正。
- **怎么把拆分延伸成 cohort 留存矩阵？** 以首单月为 cohort 分组，统计各 cohort 在后续第 1/2/3…月的复购 GMV 与人数，形成三角留存矩阵，SQL 上再加一个"订单月-首单月"的月差列即可。
- **新老客GMV与"月度复购率"如何互相验证？** 老客GMV占比升通常伴随复购率升，两者背离（老客GMV升但复购率降）说明是老客客单价在涨而人数在流失，需要拆 GMV=人数×频次×客单验证。

### 7. 业务拓展思考
新老客 GMV 拆分是增长模型的体检表：新客 GMV 除以市场费用得到"新客ROI"，老客 GMV 环比反映存量运营健康度，两者此消彼长能暴露"重投放、轻留存"的结构问题。运营上，新客占比过高的大促要警惕虚假繁荣（一次性羊毛客），老客 GMV 稳定增长的公司才有估值溢价。口径延展上，可把"首单月"升级为"首单品类/首单渠道"，输出分来源的新老客拆分，回答"哪个渠道拉来的新客后续贡献最大"，反哺投放策略。

## EC-30 每个用户近90天购买次数分位数分档

### 1. 业务背景
增长团队每月末做用户活跃分层：以 2025-09-30 为基准日，统计每个用户近 90 天的支付订单数，按全站分布切成四档（Q1-Q4）——最低档进入流失预警与召回流程，最高档进入会员专属服务，中间档做频次提升激励。相比固定阈值（如">=10单算高频"），分位数分档不受业务量自然增长影响：大促后全站单量整体上涨，固定阈值会让"高频"人群虚胖，而四分位始终保证每档约 25% 的人。**【面试高频】**NTILE 与 PERCENT_RANK 的分档对比、并列值是否同档、以及"近90天0单用户根本不出现在结果里"的口径盲区，是这道压轴题的三层考点。

### 2. 表结构说明
orders（订单主表，独立呈现）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | VARCHAR(32) | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| order_status | VARCHAR(16) | 订单状态：paid/refunded/cancelled |
| pay_time | DATETIME | 支付时间 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据 orders：

| order_id | user_id | order_status | pay_time | pay_amount |
|----------|---------|--------------|----------|------------|
| O20250705001 | 95001 | paid | 2025-07-05 10:00:00 | 59.00 |
| O20250720001 | 95001 | paid | 2025-07-20 11:00:00 | 120.00 |
| O20250810001 | 95001 | paid | 2025-08-10 12:00:00 | 45.00 |
| O20250901001 | 95002 | paid | 2025-09-01 13:00:00 | 199.00 |
| O20250915001 | 95003 | refunded | 2025-09-15 14:00:00 | 89.00 |

### 3. 解题思路
口径：近 90 天 = [基准日-89天, 基准日] 即 pay_time >= '2025-07-02' 且 pay_time < '2025-10-01'（左闭右开，防止基准日次日 0 点被误入）；购买次数 = 窗口内 paid 订单数（按订单计，如需按天计先对日期去重）；分档 = 按次数降序切四档，Q1 为最高频档。实现路径一：先聚合出每用户购买次数，再 NTILE(4) OVER(ORDER BY 次数 DESC) 均分四份；实现路径二：PERCENT_RANK() 计算每个用户次数的分位（0~1），用 CASE 按 0.25/0.50/0.75 切档，并列值分位相同、天然同档。易错点：**【避坑指南】**NTILE 按行机械切分，两个次数相同的用户可能被切进不同档（边界撕裂），对"档位即权益"的场景有公平性问题；同时"近90天0单"用户被 WHERE 天然过滤、不出现在任何档位，下游若把四档当成全量人群会漏掉流失用户，需在文档中显式说明并另行圈选。

### 4. 参考解法

解法一：聚合后 NTILE(4) 四分位分档（人数均分，报表常用）

```sql
WITH recent AS (                                  -- 第一层：近90天每用户支付订单数
    SELECT
        user_id,
        COUNT(*) AS ord_cnt                       -- 窗口内paid订单数
    FROM orders
    WHERE order_status = 'paid'                   -- 只计有效支付
      AND pay_time >= '2025-07-02'                -- 基准日2025-09-30往前90天（含首日）
      AND pay_time <  '2025-10-01'                -- 左闭右开：右边界取基准日次日零点
    GROUP BY user_id
)
SELECT
    user_id,
    ord_cnt,
    NTILE(4) OVER (ORDER BY ord_cnt DESC) AS activity_tier,  -- 按次数降序切4份：1=最高频Q1档
    CASE WHEN NTILE(4) OVER (ORDER BY ord_cnt DESC) = 1
         THEN 'Q4高频'                            -- 档位映射（注意NTILE的1是最高档）
         WHEN NTILE(4) OVER (ORDER BY ord_cnt DESC) = 2 THEN 'Q3中高频'
         WHEN NTILE(4) OVER (ORDER BY ord_cnt DESC) = 3 THEN 'Q2中低频'
         ELSE 'Q1低频' END AS tier_label
FROM recent
ORDER BY ord_cnt DESC, user_id;                   -- 输出用户级分档明细
```

结果解读：示例中 95001（3单）进入最高档 Q4，95002（1单）在低档——每档约25%用户，运营可直接按档位对接权益与召回策略；汇总各档人数即为活跃分层分布表。

解法二：PERCENT_RANK 分位 + CASE 切档（并列同值同档，公平性更好）

```sql
WITH recent AS (                                  -- 第一层：近90天购买次数（同解法一）
    SELECT
        user_id,
        COUNT(*) AS ord_cnt
    FROM orders
    WHERE order_status = 'paid'
      AND pay_time >= '2025-07-02'
      AND pay_time <  '2025-10-01'
    GROUP BY user_id
),
pr AS (                                           -- 第二层：算每个用户的次数分位
    SELECT
        user_id,
        ord_cnt,
        PERCENT_RANK() OVER (ORDER BY ord_cnt) AS pct  -- 升序分位0~1：越大越高频，并列值分位相同
    FROM recent
)
SELECT
    user_id,
    ord_cnt,
    ROUND(pct, 4) AS pct_rank,
    CASE WHEN pct >= 0.75 THEN 'Q4高频'           -- 处于全站前25%（按次数升序分位）
         WHEN pct >= 0.50 THEN 'Q3中高频'
         WHEN pct >= 0.25 THEN 'Q2中低频'
         ELSE 'Q1低频' END AS tier_label          -- 并列值pct相同→必然同档，无边界撕裂
FROM pr
ORDER BY ord_cnt DESC, user_id;
```

结果解读：与解法一档位语义一致，但次数并列的用户（如大量 1 单用户）全部落在同一档，权益发放不会出现"同样1单有人有券有人没有"的公平性争议；代价是各档人数不再严格等于 25%。

### 5. 性能分析与优化
第一层是过滤+GROUP BY 聚合，配合 (order_status, pay_time) 索引或按 pay_time 分区可把扫描压到 90 天窗口；第二层窗口按 ord_cnt 排序，输入为用户级小表，代价低。两解法执行代价几乎相同（都是一次排序窗口），差异在语义而非性能。优化建议：该分层按月跑批，把 recent 层落成"用户90天频次快照"，NTILE 结果随快照固化，下游圈选直接查档位表；若用户基数过千万，可在快照表上对 ord_cnt 建统计信息，用"边界值"（如第25/50/75分位的具体次数）预计算并物化，日常查询退化为等值/范围过滤，避免每次全量开窗。**【加分点】**能主动给出"0单用户不在任何档位，需 LEFT JOIN 全量用户表补齐并标为'流失预警'"的处理，是最能打动面试官的口径完备性细节。

### 6. 面试延伸考点
- **NTILE 和 PERCENT_RANK 分档什么时候结果不同？** 次数并列恰好横跨切分点时：NTILE 撕裂并列值、各档人数严格均分；PERCENT_RANK 并列同档、档位人数浮动。权益场景选后者，规模控制场景选前者。
- **"近90天0单"用户怎么纳入分层？** 以全量活跃用户表 LEFT JOIN 频次结果，COALESCE(ord_cnt, 0) 后单独设"Q0流失档"或并入低档，保证人群包覆盖完整。
- **分位数分档每月结果会漂移吗？** 会——档位边界随全站分布浮动，用户可能在两月间"被动掉档"；用于权益时建议叠加缓冲带（如 Q3 下沿 10% 保留权益）或改用滚动多月平滑。
- **Hive/Spark 里写法差异？** NTILE/PERCENT_RANK 语法一致；Hive 需注意窗口内排序数据倾斜（大量相同次数），Spark 可开启 skew join 优化，且两者都建议先 DISTINCT 用户×日再聚合防重复计数。

### 7. 业务拓展思考
频次分位分档是生命周期运营的地基：低档用户推"第二单激励"，中档推"品类拓宽"，高档做会员深耕，档位即策略。与 RFM 联用可交叉出"高F低M"（爱买便宜货，推升客单）与"低F高M"（低频高客单，推频次）两类精准人群。口径延展上，把订单数换成"消费天数""活跃品类数"可构建多维分层；输出各档的档位迁移矩阵（本月档位×下月档位），能量化运营动作对档位跃迁的真实拉动，让分层从静态画像变成可验证的增长杠杆。
