## EC-31 GMV同比环比与渠道×品类贡献度拆解

### 1. 业务背景

小张是某综合电商的经营分析岗，每月3号要向运营负责人输出上月经营月报。老板关心的不只是"上月GMV是多少"，而是三个问题：环比涨没涨、同比涨没涨、涨（跌）的钱具体来自哪些"渠道×品类"组合——是直播渠道的美妆在涨，还是私域渠道的食品在跌。这份拆解直接决定下月投放预算在不同渠道间的再分配，以及品类运营资源的排期。因此除了算出大盘增速，还要输出每个组合对总增量的贡献度排名，让"增长从哪来、拖累从哪来"一眼可见。

### 2. 表结构说明

orders（订单主表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID，主键 |
| pay_time | DATETIME | 支付时间（未支付订单为空或状态标记） |
| order_amount | DECIMAL(12,2) | 订单支付金额 |
| channel | VARCHAR(20) | 下单渠道：app/live/h5/private（直播/私域） |
| category | VARCHAR(30) | 商品类目 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |

示例数据（数据均为虚构）：

| order_id | pay_time | channel | category | order_amount | pay_status |
| --- | --- | --- | --- | --- | --- |
| 100001 | 2025-05-02 10:21:00 | app | 美妆 | 259.00 | 1 |
| 100002 | 2025-05-03 21:45:00 | live | 美妆 | 899.00 | 1 |
| 100003 | 2025-05-05 09:12:00 | app | 食品 | 45.80 | 1 |
| 100004 | 2025-05-05 14:30:00 | h5 | 数码 | 1999.00 | 0 |
| 100005 | 2025-05-06 20:02:00 | private | 家居 | 328.00 | 1 |

### 3. 解题思路

先定口径：GMV=pay_status=1 的订单金额合计，唯一口径出处在聚合层写死。同环比实现的最大坑是"月份不连续"——某月全平台0订单时该月不会出现在聚合结果里，直接 LAG 会把"去年11月"错当"同比基数"，导致增速全错。所以必须先用递归CTE生成连续月份日历，LEFT JOIN 聚合结果补0，再 LAG(gmv,1) 取环比基数、LAG(gmv,12) 取同比基数（前提是日历至少覆盖25个月）。第二层做渠道×品类拆解：按"月×渠道×品类"聚合，用 PARTITION BY 渠道,品类的 LAG 取该组合上月GMV算环比增量；贡献度用"组合增量/大盘总增量"，能直接回答增长来源；总增量为负或0时贡献度失去意义，要切换到占比口径并标注。**【避坑指南】** 分母为0或NULL时直接除会得到NULL或报错，必须用 NULLIF 兜底，并在报告层标注"不可比"而不是显示-100%误导读者。

### 4. 参考解法

**解法一：递归日历 + LAG 窗口（推荐，MySQL 8.0）**

```sql
-- 步骤1：递归生成连续月份日历，保证无订单月份不缺席
WITH RECURSIVE calendar AS (
    SELECT DATE '2023-01-01' AS month_start                 -- 日历起点
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH                   -- 每次推进一个月
    FROM calendar
    WHERE month_start + INTERVAL 1 MONTH <= DATE '2025-06-01'  -- 递归终点
),
-- 步骤2：按 月×渠道×品类 聚合支付成功GMV（口径唯一来源）
monthly AS (
    SELECT CAST(DATE_FORMAT(pay_time, '%Y-%m-01') AS DATE) AS month_start,
           channel, category,
           SUM(order_amount) AS gmv
    FROM orders
    WHERE pay_status = 1                                    -- 口径：仅支付成功
    GROUP BY 1, 2, 3
),
-- 步骤3：日历 CROSS 维度骨架 再左连，无单组合补0，防止LAG错位
filled AS (
    SELECT c.month_start, d.channel, d.category,
           COALESCE(m.gmv, 0) AS gmv
    FROM calendar c
    CROSS JOIN (SELECT DISTINCT channel, category FROM monthly) d  -- 维度骨架
    LEFT JOIN monthly m
           ON m.month_start = c.month_start
          AND m.channel = d.channel
          AND m.category = d.category
),
-- 步骤4：组合内取上月GMV，同时按月汇总大盘
combo AS (
    SELECT month_start, channel, category, gmv,
           LAG(gmv) OVER (PARTITION BY channel, category
                          ORDER BY month_start) AS gmv_lm,      -- 组合上月值
           SUM(gmv) OVER (PARTITION BY month_start) AS total_gmv -- 当月大盘
    FROM filled
),
-- 步骤5：大盘层面再取上月，得到总增量
month_total AS (
    SELECT month_start,
           SUM(gmv) AS total_gmv,
           LAG(SUM(gmv)) OVER (ORDER BY month_start) AS prev_total  -- 大盘上月
    FROM filled
    GROUP BY month_start
)
SELECT c.month_start                                                       AS 月份,
       c.channel                                                           AS 渠道,
       c.category                                                          AS 品类,
       c.gmv                                                               AS 组合GMV,
       ROUND((c.gmv - c.gmv_lm) / NULLIF(c.gmv_lm, 0) * 100, 2)            AS 组合环比,
       ROUND((c.gmv - c.gmv_lm)
             / NULLIF(t.total_gmv - t.prev_total, 0) * 100, 2)             AS 对总增量贡献率,
       ROUND(c.gmv / NULLIF(t.total_gmv, 0) * 100, 2)                      AS 组合GMV占比
FROM combo c
JOIN month_total t USING (month_start)
WHERE c.month_start = '2025-06-01'          -- 拆解看板只看最近一个月
ORDER BY 对总增量贡献率 DESC;
```

结果解读：按"对总增量贡献率"倒序，正值最大的组合就是本月增长引擎，负值最大的就是主要拖累；若大盘总增量为负，贡献率符号含义反转，报告要换成"对降幅的贡献"口径说明。

**解法二：月份键偏移自连接法（不依赖窗口，老版本引擎也适用）**

```sql
-- 先把月度聚合收敛为CTE，MySQL 8.0 对多次引用的CTE只物化一次
WITH agg AS (
    SELECT CAST(DATE_FORMAT(pay_time, '%Y-%m-01') AS DATE) AS ym,
           SUM(order_amount) AS gmv
    FROM orders
    WHERE pay_status = 1                          -- 口径：仅支付成功
    GROUP BY 1
)
SELECT cur.ym                                                     AS 月份,
       cur.gmv                                                    AS 当月GMV,
       ROUND((cur.gmv - prev.gmv) / NULLIF(prev.gmv, 0) * 100, 2) AS 环比增速,
       ROUND((cur.gmv - yoy.gmv)  / NULLIF(yoy.gmv, 0)  * 100, 2) AS 同比增速
FROM agg cur
LEFT JOIN agg prev ON prev.ym = cur.ym - INTERVAL 1 MONTH        -- 偏移1个月匹配上月
LEFT JOIN agg yoy  ON yoy.ym  = cur.ym - INTERVAL 1 YEAR         -- 偏移1年匹配去年同月
ORDER BY cur.ym;
```

结果解读：自连接靠"月份键平移"匹配基数，缺月时 join 不上得到 NULL（比 LAG 错位更安全），但报表需要处理 NULL；渠道×品类组合的环比与贡献度同理，把聚合键扩到三列、join 键多加两列即可实现，不再重复展开。

> Hive/Spark SQL 差异：Hive 不支持 RECURSIVE CTE，日历补齐用日历维表（dim_date）或 `lateral view explode(split(space(n),...))` 造序列；日期偏移用 add_months / date_sub；生产上通常直接读数仓月汇表 dws_trd_order_1m，避免扫明细。

### 5. 性能分析与优化

解法一的代价在明细聚合（一次全扫 orders）与 CROSS JOIN 骨架膨胀：月数×组合数，若组合上千、月份上百，filled 达几十万行，但仍是聚合层小表，窗口排序 O(n log n) 可忽略。解法二聚合后自连接，连接行数=月数级，代价极低；多次引用同一 CTE 在 MySQL 8.0 只物化一次，可控。可执行优化：① orders 按 pay_time 月分区做分区裁剪，或建 (pay_status, pay_time) 复合索引；② 线上月报不要扫明细，落地 dws_trd_channel_category_1d/1m 预聚合表，查询只读聚合层；③ 维度骨架改从品类维表取，避免对明细做 DISTINCT；④ 贡献度看板固定"最近一个月"，WHERE 下推减少窗口参与行数。

### 6. 面试延伸考点

- **某月GMV为0时，环比增速该怎么呈现？** 要点：分母为0没有数学意义，显示"N/A/不可比"，不能算成-100%误导；新渠道首月建议用绝对增量替代增速。
- **同比受春节错月影响怎么处理？** 要点：按农历日期段对齐（春节同档期口径），或叠加"剔除春节周"的调整口径，单看公历同月会误判。
- **贡献度为什么用增量口径而不是GMV占比口径？** 要点：回答"增长从哪来"必须用增量贡献；占比口径回答"结构是什么"，两者互补，月报通常并列展示。
- **GMV、营收、净销售额有什么区别？** 要点：GMV按口径可含未支付/取消单；营收确认需扣退款、按净额或总额法；汇报前先对齐口径。

### 7. 业务拓展思考

这层拆解的价值在于把"大盘涨跌"翻译成"谁在涨、谁在跌"的可执行结论：贡献度Top组合直接对应投放预算再分配与品类坑位调整，拖累组合进入品类负责人的诊断队列。拆解粒度可继续下钻到二级品类/店铺/商品定位根因；口径上可延展为"净GMV（扣退款）""券后实付"多口径并行，观察补贴对结构的影响；把月度改成周度即成经营周报看板，配合阈值预警实现"涨跌先知"。

## EC-32 大促每日GMV的7日滑动均值与峰值预警

### 1. 业务背景

双11大促期间，电商数据组的值班同学要盯实时大屏：单日GMV受预热、爆发、周末效应影响波动剧烈，直接看柱状图容易误判趋势。运营负责人要求在GMV曲线上叠加"7日滑动平均"作为平滑基准，并设定峰值预警规则——当日GMV超过7日滑动均值的150%即触发预警，值班同学据此判断是真实爆量还是异常流量（羊毛党、刷单），第一时间通知库存调拨与客服排班。该组件后来被固化为所有大促屏的标准配置，所以SQL要写成可参数化复用的形态。

### 2. 表结构说明

daily_sales（日销售汇总表，由订单表按日聚合产出）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| stat_date | DATE | 统计日期，每日一行 |
| gmv | DECIMAL(14,2) | 当日支付成功GMV |
| order_cnt | INT | 支付成功订单数 |
| uv | INT | 当日活跃用户数 |

示例数据（数据均为虚构）：

| stat_date | gmv | order_cnt | uv |
| --- | --- | --- | --- |
| 2025-06-01 | 3200000.00 | 12800 | 95000 |
| 2025-06-02 | 2980000.00 | 12100 | 91000 |
| 2025-06-03 | 3050000.00 | 12400 | 93000 |
| 2025-06-04 | 6880000.00 | 26500 | 152000 |
| 2025-06-05 | 3400000.00 | 13500 | 98000 |

### 3. 解题思路

先抠口径：监控场景只能用"截止当日的TRAILING 7日窗口"（未来数据不存在），即 ROWS BETWEEN 6 PRECEDING AND CURRENT ROW；前后各3天的中心窗口只能用于离线复盘，用在监控里就是用未来数据"作弊"。预警规则：gmv ≥ 1.5×avg7 标记峰值。实现路径：确认日期连续（缺日要先补日历，否则均值被稀释）；一条窗口函数出趋势线；CASE 打预警标记；取预警名单需要在外层再包一层查询。**【避坑指南】** MySQL 窗口框架默认 RANGE，当 ORDER BY 列出现重复值（如同一天多行）时 RANGE 会把同日所有行都纳入窗口，必须显式写 ROWS；日粒度唯一键下两者等价，但显式声明 ROWS 是窗口函数的基本功。

### 4. 参考解法

**解法一：ROWS 滑动窗口（推荐）**

```sql
-- 步骤1：先算TRAILING 7日均值（前6天+当天）
WITH w AS (
    SELECT stat_date, gmv,
           AVG(gmv) OVER (ORDER BY stat_date
               ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg7
    FROM daily_sales
),
-- 步骤2：打预警标记（窗口结果不能进WHERE，必须先算后筛）
flag AS (
    SELECT stat_date, gmv, avg7,
           CASE WHEN gmv >= 1.5 * avg7 THEN '峰值预警'
                ELSE '正常' END AS alert
    FROM w
)
SELECT stat_date                    AS 日期,
       gmv                          AS 当日GMV,
       ROUND(avg7, 2)               AS 七日滑动均值,
       ROUND(gmv / NULLIF(avg7, 0), 2) AS 峰值比,
       alert                        AS 预警标记
FROM flag
ORDER BY stat_date;
-- 若只要预警名单：再包一层 SELECT ... WHERE alert='峰值预警'
```

结果解读：6月4日GMV为686万的2.26倍滑动均值，触发预警；解读时结合当日UV同步上涨，判断为活动放量真实爆量，而非刷单（刷单通常GMV涨、UV与转化不涨）。

**解法二：自连接区间法（原理等价，适合无窗口函数的引擎）**

```sql
SELECT a.stat_date                                                       AS 日期,
       a.gmv                                                             AS 当日GMV,
       ROUND(AVG(b.gmv), 2)                                              AS 七日滑动均值,
       CASE WHEN a.gmv >= 1.5 * AVG(b.gmv) THEN '峰值预警'
            ELSE '正常' END                                              AS 预警标记
FROM daily_sales a
JOIN daily_sales b
  ON b.stat_date BETWEEN a.stat_date - INTERVAL 6 DAY AND a.stat_date   -- 每日展开[a-6,a]区间
GROUP BY a.stat_date, a.gmv
HAVING a.gmv >= 1.5 * AVG(b.gmv)                                        -- 直接筛出预警日
ORDER BY a.stat_date;
```

结果解读：HAVING 里直接复用均值表达式，一步只输出预警日名单；原理是把滑动窗口展开成"每行匹配自身前7行"的区间连接，与解法一结果一致，但每行要重扫7行，是讲解窗口函数原理的好教材。

> Hive/Spark SQL 差异：两者均支持 ROWS BETWEEN 写法，Spark SQL 可直接平移；日期断裂时同样要先补日历维表；大促屏的实时版通常在 Flink 里用滑动窗口算，SQL 版用于 T+1 复盘。

### 5. 性能分析与优化

解法一一次排序 O(n log n)，窗口仅驻留7行内存，代价最低；解法二自连接行数放大约7倍，日粒度（数千行）无感，但换成小时粒度（24倍数据）就要谨慎。优化建议：① stat_date 建唯一索引，既保证每日一行又加速窗口排序；② 大促屏把 orders 实时聚合落"小时累计+日汇总"两级预聚合表，本查询只读日表；③ 阈值1.5放进参数配置表而不是硬编码SQL，避免每次调阈值都改代码；④ 缺日数据补0或标注"窗口不满7天"，防止均值偏低造成误报。

### 6. 面试延伸考点

- **为什么监控用TRAILING窗口而不是中心窗口？** 要点：实时监控只能用截至当日的数据，中心窗口需要未来数据，只适合离线平滑复盘。
- **怎么区分真实爆量与刷单？** 要点：GMV预警必须交叉UV、转化率、客单价验证（GMV涨但UV转化不涨→疑似异常），再看支付成功率与退款率。
- **滑动均值和指数平滑（EWMA）怎么选？** 要点：滑动均值对突变的响应滞后约窗口一半，EWMA可用α调节灵敏度；SQL实现EWMA需递归，工程上常放Flink/Python。
- **中间缺一天数据，滑动均值会怎样？** 要点：均值被稀释偏低，可能引发误报；必须补日历或在结果中标注窗口实际天数。

### 7. 业务拓展思考

峰值预警可反向扩展为"谷值预警"（当日GMV低于均值70%提示流量或下单链路事故），形成双向监控；固定1.5倍阈值对不同波动特性的品类并不公平，可升级为"均值±k×标准差"的z-score动态阈值。预警触发的联动动作要写进SOP：通知库存调拨、客服排班、暂停可疑优惠券并启动风控核查；趋势线延展为"GMV/UV人均产出"监控，可剥离流量自然波动，更聚焦经营质量本身。

## EC-33 用户生命周期LTV：首单后1/3/6月累计消费

### 1. 业务背景

增长分析小王在做渠道质量评估：市场部在信息流、应用商店、达人直播三个渠道投放拉新，各渠道获客成本（CAC）差异很大。负责人要求按渠道计算新客LTV：以用户首单日为起点，分别统计首单后1个月、3个月、6个月内的累计支付金额（含首单本身），输出"渠道×三周期"的人均LTV，并用 LTV/CAC 粗估各渠道投产比，作为下季度预算分配的依据。运营侧同时用这份LTV表校准新客礼包面额——LTV低的渠道不敢给高补贴。

### 2. 表结构说明

users（用户表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| channel | VARCHAR(20) | 获客渠道：feed信息流/asm应用商店/liv达人直播 |
| register_date | DATE | 注册日期 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| user_id | channel | register_date |
| --- | --- | --- |
| 9001 | feed | 2025-01-05 |
| 9002 | feed | 2025-01-07 |
| 9003 | asm | 2025-01-09 |
| 9004 | liv | 2025-01-10 |
| 9005 | asm | 2025-01-12 |

| order_id | user_id | pay_amount | pay_status | pay_time |
| --- | --- | --- | --- | --- |
| 200001 | 9001 | 89.00 | 1 | 2025-01-06 12:00:00 |
| 200002 | 9001 | 129.00 | 1 | 2025-02-20 18:30:00 |
| 200003 | 9002 | 39.90 | 1 | 2025-01-08 09:10:00 |
| 200004 | 9003 | 2599.00 | 1 | 2025-03-01 20:11:00 |
| 200005 | 9004 | 59.00 | 0 | 2025-01-11 10:00:00 |

### 3. 解题思路

第一步定口径：首单=首笔支付成功订单（pay_status=1，不含未支付；是否剔除全额退款单需业务确认）；LTV窗口为 [首单日, 首单日+N天) 左闭右开、含首单本身；"1/3/6月"本解法用30/90/180整数天实现（也可用自然月 add_months 语义，两者在2月会差几天，报告必须注明）。第二步路径：CTE1 取每用户 MIN(pay_time) 得首单日；CTE2 明细关联首单日计算 datediff；CTE3 用 SUM(CASE WHEN 窗口条件) 一次聚合出三段累计；CTE4 关联 users 按渠道求人均。第三步易错点：**【避坑指南】** 观察期截断——首单还不到6个月的用户，LTV_6m 天然偏低，必须加"窗口已满"标记（首单日≤今天-180天）后过滤或分层展示；否则近期渠道会被系统性低估，这是LTV渠道对比最常见的翻车点。

### 4. 参考解法

**解法一：CTE首单表 + JOIN + 条件聚合（结构清晰，推荐写法）**

```sql
WITH first_order AS (        -- 每个用户的首单时间
    SELECT user_id, MIN(pay_time) AS first_pay_time
    FROM orders
    WHERE pay_status = 1                 -- 口径：仅支付成功
    GROUP BY user_id
),
user_ltv AS (                -- 用户级：三段窗口累计消费
    SELECT f.user_id, f.first_pay_time,
           SUM(CASE WHEN o.pay_time < f.first_pay_time + INTERVAL 30 DAY
                    THEN o.pay_amount ELSE 0 END) AS ltv_1m,   -- 含首单（窗口左闭）
           SUM(CASE WHEN o.pay_time < f.first_pay_time + INTERVAL 90 DAY
                    THEN o.pay_amount ELSE 0 END) AS ltv_3m,
           SUM(CASE WHEN o.pay_time < f.first_pay_time + INTERVAL 180 DAY
                    THEN o.pay_amount ELSE 0 END) AS ltv_6m
    FROM first_order f
    JOIN orders o
      ON o.user_id = f.user_id AND o.pay_status = 1
    GROUP BY f.user_id, f.first_pay_time
)
SELECT u.channel                                                 AS 渠道,
       COUNT(*)                                                  AS 首购用户数,
       ROUND(AVG(l.ltv_1m), 2)                                   AS 人均LTV_1月,
       ROUND(AVG(l.ltv_3m), 2)                                   AS 人均LTV_3月,
       ROUND(AVG(l.ltv_6m), 2)                                   AS 人均LTV_6月,
       ROUND(AVG(CASE WHEN l.first_pay_time <= CURDATE() - INTERVAL 180 DAY
                      THEN 1.0 ELSE 0 END) * 100, 1)             AS 六月窗口已满占比
FROM user_ltv l
JOIN users u USING (user_id)
GROUP BY u.channel
ORDER BY 人均LTV_6月 DESC;
-- 公平对比时应再加：HAVING 六月窗口已满占比=100 或在WHERE过滤 first_pay_time <= CURDATE()-INTERVAL 180 DAY
```

结果解读：渠道LTV从1月到6月拉开差距才能说明渠道质量；若"六月窗口已满占比"很低，LTV_6m 只是下限估计，比较时要声明口径，避免拿不满6个月的近期渠道和满窗口老渠道硬比。

**解法二：窗口内联法（一次扫描明细，省去GROUP BY+JOIN往返）**

```sql
WITH base AS (       -- 在明细上用窗口直接挂首单时间
    SELECT user_id, pay_amount, pay_time, pay_status,
           MIN(CASE WHEN pay_status = 1 THEN pay_time END)
               OVER (PARTITION BY user_id) AS first_pay_time   -- 窗口版首单：忽略未支付行
    FROM orders
),
user_ltv AS (        -- 条件聚合：未支付行被CASE排除，贡献为0
    SELECT user_id,
           SUM(CASE WHEN pay_status = 1 AND pay_time < first_pay_time + INTERVAL 30 DAY
                    THEN pay_amount ELSE 0 END) AS ltv_1m,
           SUM(CASE WHEN pay_status = 1 AND pay_time < first_pay_time + INTERVAL 90 DAY
                    THEN pay_amount ELSE 0 END) AS ltv_3m,
           SUM(CASE WHEN pay_status = 1 AND pay_time < first_pay_time + INTERVAL 180 DAY
                    THEN pay_amount ELSE 0 END) AS ltv_6m
    FROM base
    GROUP BY user_id
)
SELECT u.channel AS 渠道,
       COUNT(*) AS 首购用户数,
       ROUND(AVG(l.ltv_1m), 2) AS 人均LTV_1月,
       ROUND(AVG(l.ltv_3m), 2) AS 人均LTV_3月,
       ROUND(AVG(l.ltv_6m), 2) AS 人均LTV_6月
FROM user_ltv l
JOIN users u USING (user_id)
GROUP BY u.channel
ORDER BY 人均LTV_6月 DESC;
```

结果解读：MIN(CASE WHEN pay_status=1 ...) OVER (PARTITION BY user_id) 把"首单"内联到每行明细，未支付行因CASE为NULL不参与首单判定、又因条件聚合不计入金额，一条链路完成；与解法一结果完全一致，明细量越大相对优势越明显。

> Hive/Spark SQL 差异：逻辑一致，日期加法改 date_add/add_months；亿级订单按 user_id JOIN 注意数据倾斜（超级用户），可加盐或 skew hint；生产上LTV按月调度落 dws_user_ltv 表，渠道层只做轻聚合。

### 5. 性能分析与优化

解法一扫 orders 两次（GROUP BY 一次、JOIN 回明细一次），解法二一次扫描加窗口排序（PARTITION BY user_id 排序 O(n log n)），避免了中间临时表落盘，大数据量下更优。共同优化：① orders 建 (user_id, pay_time) 复合索引，可同时加速 GROUP BY、JOIN 与窗口排序；② 先过滤 pay_status=1 或单独支付成功分区，扫描量直接减半；③ 用户级LTV先落表（数仓 dws_user_ltv，按首购月分区），渠道汇总读用户级结果，报表查询毫秒级；④ 只取近两年订单可控制窗口排序规模，LTV_6m 口径下更早订单对增量无贡献。

### 6. 面试延伸考点

- **LTV该按GMV还是毛利算？** 要点：品类毛利差异大，GMV口径会高估低毛利渠道；决策用毛利LTV/CAC，GMV口径做规模参考。
- **窗口未满的用户怎么处理更严谨？** 要点：要么截断过滤（首单日≤今天-180天，公平但样本变少），要么按已观测比例外推并标注置信度，不能混着比。
- **退款怎么计入口径？** 要点：净额口径扣全额退款单、部分退款按净实付；券补贴是否还原成原价也要定义。
- **LTV能否做个体预测？** 要点：SQL产出首单特征（品类/金额/渠道/时段），用回归或BG/NBD概率模型预测12个月LTV，SQL负责特征层。

### 7. 业务拓展思考

LTV结论直接驱动两件事：渠道预算再分配（LTV/CAC>1的渠道加投、<1的收缩或优化承接链路）与新客礼包差异化（高LTV渠道可承受更高首单补贴）。口径延展：按获客月份做同期群（cohort）矩阵可观察渠道质量随时间漂移（素材疲劳、假量混入）；把LTV拆成"留存率×频次×客单价"三因子，能定位渠道差在哪个因子；与留存曲线拼接可外推12个月LTV，作为与代理商谈CAC上限的谈判依据。

## EC-34 曝光-点击-加购-下单-支付五步漏斗与分步转化率

### 1. 业务背景

产品分析同学在首页推荐位改版上线一周后做链路体检：把用户在当日内的曝光（impression）、点击（click）、加购（cart）、下单（order）、支付（pay）五类行为串成漏斗，输出每日五步人数与四段分步转化率，回答两个问题——本次改版后哪一步转化率最低、最值得优化；改版相对上周整体转化率提升多少。产品经理用这份漏斗定位最薄弱环节并排定迭代优先级，运营则用"加购→支付"段的流失数据设计购物车催付与凑单券策略。

### 2. 表结构说明

user_behavior（用户行为明细表，按天分区）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| behavior_type | VARCHAR(10) | 行为类型：impression/click/cart/order/pay |
| item_id | BIGINT | 商品ID |
| cate_id | VARCHAR(20) | 商品类目 |
| behavior_time | DATETIME | 行为发生时间 |

示例数据（数据均为虚构）：

| user_id | behavior_type | item_id | cate_id | behavior_time |
| --- | --- | --- | --- | --- |
| 7001 | impression | 501 | 美妆 | 2025-06-10 09:00:05 |
| 7001 | click | 501 | 美妆 | 2025-06-10 09:00:40 |
| 7001 | cart | 501 | 美妆 | 2025-06-10 09:05:10 |
| 7002 | impression | 502 | 数码 | 2025-06-10 10:12:00 |
| 7002 | click | 502 | 数码 | 2025-06-10 10:12:30 |

### 3. 解题思路

两个口径必须先讲清：宽口径=当天发生过该行为的去重用户数，不要求行为先后（生产看板常用，抗乱序、易实现）；严口径=行为必须按链路顺序发生（点击晚于曝光、加购晚于点击……），用于精细归因。实现路径：先按"用户×行为类型"取 MIN(behavior_time) 完成去重并保留首时刻；再用条件聚合（MAX(CASE WHEN...)）把五行拍平成一行五列；逐层相除得分步转化率；严口径在拍平后增加相邻行为时间比较。**【面试高频】** 宽口径下漏斗不强制单调——用户可以不经加购直接下单，因此"加购人数"可能小于"下单人数"，分步转化率可能出现超过100%的形态，报表必须注释口径；严口径则天然单调。另一个易错点：曝光行为占存储90%以上，直接全表聚合代价巨大，必须先分区裁剪再按用户收敛。

### 4. 参考解法

**解法一：宽口径——条件聚合拍平（生产看板标准写法）**

```sql
WITH day_user AS (       -- 用户×行为类型 去重，保留当日首次发生时间
    SELECT behavior_date, user_id, behavior_type,
           MIN(behavior_time) AS first_time
    FROM (SELECT DATE(behavior_time) AS behavior_date,
                 user_id, behavior_type, behavior_time
          FROM user_behavior
          WHERE behavior_time >= '2025-06-10'
            AND behavior_time <  '2025-06-11') t          -- 先做日期分区裁剪
    GROUP BY 1, 2, 3
),
funnel AS (              -- 拍平：每个用户一行，五步是否发生用0/1标记
    SELECT behavior_date, user_id,
           MAX(CASE WHEN behavior_type = 'impression' THEN 1 ELSE 0 END) AS has_imp,
           MAX(CASE WHEN behavior_type = 'click'      THEN 1 ELSE 0 END) AS has_clk,
           MAX(CASE WHEN behavior_type = 'cart'       THEN 1 ELSE 0 END) AS has_cart,
           MAX(CASE WHEN behavior_type = 'order'      THEN 1 ELSE 0 END) AS has_ord,
           MAX(CASE WHEN behavior_type = 'pay'        THEN 1 ELSE 0 END) AS has_pay
    FROM day_user
    GROUP BY behavior_date, user_id
)
SELECT behavior_date                                 AS 日期,
       SUM(has_imp)                                  AS 曝光人数,
       SUM(has_clk)                                  AS 点击人数,
       SUM(has_cart)                                 AS 加购人数,
       SUM(has_ord)                                  AS 下单人数,
       SUM(has_pay)                                  AS 支付人数,
       ROUND(SUM(has_clk)  / NULLIF(SUM(has_imp), 0)  * 100, 2) AS 曝光点击率,
       ROUND(SUM(has_cart) / NULLIF(SUM(has_clk), 0)  * 100, 2) AS 点击加购率,
       ROUND(SUM(has_ord)  / NULLIF(SUM(has_cart), 0) * 100, 2) AS 加购下单率,
       ROUND(SUM(has_pay)  / NULLIF(SUM(has_ord), 0)  * 100, 2) AS 下单支付率,
       ROUND(SUM(has_pay)  / NULLIF(SUM(has_imp), 0)  * 100, 2) AS 整体转化率
FROM funnel
GROUP BY behavior_date
ORDER BY behavior_date;
```

结果解读：这是"总体比值口径"的分步转化率；若要"完成上一步的人中完成下一步"的条件转化率，把分母换成 SUM(has_imp AND has_clk) 这类交叉条件即可；下单支付率长期偏低（90%+属正常，低于85%要查支付通道），是定位问题最快的分段。

**解法二：严口径——行为时间链路校验（保证漏斗单调）**

```sql
WITH day_user AS (       -- 同解法一：用户×行为 首次时间
    SELECT DATE(behavior_time) AS behavior_date, user_id, behavior_type,
           MIN(behavior_time) AS first_time
    FROM user_behavior
    WHERE behavior_time >= '2025-06-10' AND behavior_time < '2025-06-11'
    GROUP BY 1, 2, 3
),
pivot AS (               -- 转置：每用户一行，五类行为的首时刻
    SELECT behavior_date, user_id,
           MAX(CASE WHEN behavior_type = 'impression' THEN first_time END) AS imp_time,
           MAX(CASE WHEN behavior_type = 'click'      THEN first_time END) AS clk_time,
           MAX(CASE WHEN behavior_type = 'cart'       THEN first_time END) AS cart_time,
           MAX(CASE WHEN behavior_type = 'order'      THEN first_time END) AS ord_time,
           MAX(CASE WHEN behavior_type = 'pay'        THEN first_time END) AS pay_time
    FROM day_user
    GROUP BY behavior_date, user_id
),
strict AS (              -- 严口径：相邻步必须时间递增，NULL比较为假自动计0
    SELECT behavior_date,
           CASE WHEN imp_time IS NOT NULL THEN 1 ELSE 0 END AS has_imp,
           CASE WHEN clk_time > imp_time  THEN 1 ELSE 0 END AS has_clk,
           CASE WHEN cart_time > clk_time THEN 1 ELSE 0 END AS has_cart,
           CASE WHEN ord_time > cart_time THEN 1 ELSE 0 END AS has_ord,
           CASE WHEN pay_time > ord_time  THEN 1 ELSE 0 END AS has_pay
    FROM pivot
)
SELECT behavior_date AS 日期,
       SUM(has_imp) AS 曝光人数, SUM(has_clk) AS 顺序点击人数,
       SUM(has_cart) AS 顺序加购人数, SUM(has_ord) AS 顺序下单人数,
       SUM(has_pay) AS 顺序支付人数,
       ROUND(SUM(has_pay) / NULLIF(SUM(has_imp), 0) * 100, 2) AS 严口径整体转化率
FROM strict
GROUP BY behavior_date
ORDER BY behavior_date;
```

结果解读：严口径整体转化率必然不高于宽口径，两者差值反映"乱序完成链路"的用户占比（如直接搜索进入下单的用户）；差值突然扩大常意味着入口结构变化，值得单独归因。

> Hive/Spark SQL 差异：行为明细日增数十亿时，先在ODS层按日聚合出 dwd_user_behavior_1d（user_id×date×type×cnt×first_time）再跑漏斗；Spark SQL 写法与本例一致，Hive 也有自研 funnel UDF 可一步输出；曝光与点击分离存储时注意两表 user_id 口径一致。

### 5. 性能分析与优化

主要代价在行为明细扫描：曝光占90%以上存储，必须按 behavior_time 分区裁剪只扫目标日；先按"用户×行为类型"聚合把数千万行收敛到百万级再拍平。解法二多两层CTE传递，但行数已收敛，代价可忽略。可执行优化：① behavior_time 分区 + 每日预聚合表（用户×日×行为类型×次数×首时刻），看板查询毫秒级；② behavior_type 低基数无索引价值，优化重点在分区与预聚合而非索引；③ 若做长期趋势，把漏斗固定在 dws 层按日调度，保留"宽+严"双口径两列；④ 取数范围只圈定实验周期，避免全历史重算。

### 6. 面试延伸考点

- **用户级漏斗和事件级（次数）漏斗有什么区别？** 要点：用户级贴近"人的体验"，事件级受单人高频行为影响大，适合风控与性能监控；汇报默认用户级。
- **跨天漏斗（7天窗口）怎么做？** 要点：以起点事件（曝光）为锚，LEFT JOIN 窗口内后续行为，注意窗口右截断（最近7天样本不完整要剔除）。
- **加购和收藏要不要合并成一个漏斗步骤？** 要点：合并需在埋点层定义"意向行为"统一事件，避免双计；分开看能区分冲动型与决策型用户。
- **怎么做改版AB组的漏斗对比？** 要点：按实验分组分别出漏斗，各步转化率做卡方检验给出显著性，不只看点值差异。

### 7. 业务拓展思考

漏斗定位出最差环节后要有对应动作闭环：点击→加购差，优化商详页与价格锚点；加购→下单差，上线购物车催付、凑单券、运费门槛调整；下单→支付差，排查支付通道与失败原因码。口径延展：分钟级路径序列可做行为模式挖掘（如"反复比价后流失"剧本）；分品类漏斗能区分生鲜冲动型与数码决策型的链路差异；把"搜索"作为替代入口单建漏斗，可评估推荐位改版是否把用户挤向搜索。

## EC-35 90天滑动窗口复购率曲线

### 1. 业务背景

用户运营团队上线"会员日权益"后，需要一条更稳的复购趋势线向管理层汇报效果：单日复购率受周末与大促扰动噪声太大，因此改用"90天滑动窗口复购率"——以每个自然日为观察点，统计观察点前90天（含当天）内发生过购买的用户中，购买天数≥2天的用户占比。权益上线时间点前后对比这条曲线，比看日度数据更能说明复购行为是否被真实改善，曲线也作为会员项目的北极星指标之一进入双周报。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| order_id | user_id | pay_amount | pay_status | pay_time |
| --- | --- | --- | --- | --- |
| 300001 | 6001 | 79.00 | 1 | 2025-04-10 11:20:00 |
| 300002 | 6001 | 99.00 | 1 | 2025-05-02 20:15:00 |
| 300003 | 6002 | 129.00 | 1 | 2025-05-03 09:40:00 |
| 300004 | 6002 | 45.00 | 1 | 2025-05-03 19:05:00 |
| 300005 | 6003 | 259.00 | 0 | 2025-05-04 12:00:00 |

### 3. 解题思路

口径三件事：窗口=[t-89, t] 共90个自然日（含t）；复购=窗口内"购买自然日≥2天"（按天去重，同日下三单不算复购——另一种按订单数口径会高估高频低质用户，需与业务确认）；分母=窗口内有≥1个购买日的用户。路径：先把订单收敛为"用户×购买日"去重表，这是复购判定的最小单元。**【加分点】** 第二种解法把"窗口内≥2个购买日"转化为"相邻购买日间隔≤89天"的区间覆盖问题：用 LAG 取每对相邻购买日，若间隔≤89天，则该用户在 [后一单日, 前一单日+89] 的每一天都处于"复购状态"，配合 [每单日, 每单日+89] 的"在窗状态"，用日历一次连接聚合即可，避免逐日×90倍的连接膨胀。易错点：无购买日的观察点要补日历输出（区分0%与缺数）；MySQL 窗口 RANGE 不支持日期 INTERVAL 单位，若想用窗口滑动必须把日期转成整数天序号。

### 4. 参考解法

**解法一：日历 × 90天区间自连接（直白可维护）**

```sql
WITH calendar AS (       -- 观察点日历（生产中直接用日历维表）
    SELECT DATE '2025-01-01' AS d
    UNION ALL
    SELECT d + INTERVAL 1 DAY FROM calendar WHERE d < DATE '2025-06-30'
),
user_day AS (            -- 用户×购买日 去重：同日多单只算一个购买日
    SELECT user_id, DATE(pay_time) AS pay_day
    FROM orders
    WHERE pay_status = 1
    GROUP BY user_id, DATE(pay_time)
),
win AS (                 -- 每个观察点×用户：90天窗口内的购买日数
    SELECT c.d, u.user_id, COUNT(*) AS days_in_win
    FROM calendar c
    JOIN user_day u
      ON u.pay_day BETWEEN c.d - INTERVAL 89 DAY AND c.d   -- 窗口[含t]左闭右闭
    GROUP BY c.d, u.user_id
)
SELECT d                                                           AS 观察日,
       COUNT(*)                                                    AS 购买用户数,
       SUM(CASE WHEN days_in_win >= 2 THEN 1 ELSE 0 END)           AS 复购用户数,
       ROUND(SUM(CASE WHEN days_in_win >= 2 THEN 1 ELSE 0 END)
             / COUNT(*) * 100, 2)                                  AS 复购率
FROM win
GROUP BY d
ORDER BY d;
-- 注意：窗口内无任何购买的观察日不会出现在win中，需要0%占位时可最外层再LEFT JOIN日历
```

结果解读：曲线反映"最近90天买过的人里有几个是回头客"；权益上线点若出现抬升并持续，且能排除大促扰动，才可归因给权益；新客涌入期分母膨胀，复购率会被动下降，拆"新客/老客"两条线更稳。

**解法二：相邻对区间覆盖法（把窗口判定转成区间标记）**

```sql
WITH calendar AS (       -- 同解法一
    SELECT DATE '2025-01-01' AS d
    UNION ALL
    SELECT d + INTERVAL 1 DAY FROM calendar WHERE d < DATE '2025-06-30'
),
user_day AS (            -- 用户×购买日 去重
    SELECT user_id, DATE(pay_time) AS pay_day
    FROM orders WHERE pay_status = 1
    GROUP BY user_id, DATE(pay_time)
),
pair AS (                -- LAG取相邻购买日对
    SELECT user_id, pay_day,
           LAG(pay_day) OVER (PARTITION BY user_id ORDER BY pay_day) AS prev_day
    FROM user_day
),
states AS (              -- 两类状态区间：在窗（有购买）与复购（存在间隔<=89的相邻对）
    SELECT user_id, pay_day AS s, pay_day + INTERVAL 89 DAY AS e, 0 AS is_rebuy
    FROM pair                                                -- 每个购买日覆盖[d, d+89]
    UNION ALL
    SELECT user_id, pay_day, prev_day + INTERVAL 89 DAY, 1
    FROM pair
    WHERE DATEDIFF(pay_day, prev_day) <= 89                  -- 间隔<=89才构成复购状态
),
stat AS (                -- 按观察日汇总：区间重叠必须按用户去重
    SELECT c.d,
           COUNT(DISTINCT CASE WHEN is_rebuy = 0 THEN user_id END) AS buyers,
           COUNT(DISTINCT CASE WHEN is_rebuy = 1 THEN user_id END) AS rebuy_users
    FROM states s
    JOIN calendar c ON c.d BETWEEN s.s AND s.e
    GROUP BY c.d
)
SELECT d AS 观察日, buyers AS 购买用户数, rebuy_users AS 复购用户数,
       ROUND(rebuy_users / NULLIF(buyers, 0) * 100, 2) AS 复购率
FROM stat
ORDER BY d;
```

结果解读：**【避坑指南】** 同一用户的多个状态区间会重叠，直接 SUM 会重复计数，必须用 COUNT(DISTINCT user_id) 去重——这是区间覆盖法最容易踩的错。该方法连接基数是"购买对数×区间长度"，通常比解法一的"观察日×窗口内购买日数"小一个量级。

> Hive/Spark SQL 差异：无 RECURSIVE CTE，日历用维表；LAG 与区间连接写法一致；数仓里 user_day 落成按月分区的 dws_user_purchase_day 表后，两条路径都能增量调度（每天只补算最新观察点）。

### 5. 性能分析与优化

解法一的行数膨胀=每个观察日×窗口内"用户×购买日"组合数，最坏接近90倍；解法二膨胀≈状态区间长度均值（≤90天）但基数是购买对数而非观察日组合，通常小一个量级。优化建议：① user_day 先物化（按月分区 + (pay_day, user_id) 索引），两个解法都基于它；② 日历限定观察范围，历史观察点不重算，改为每日增量补算最新点；③ 数仓层把"购买用户数/复购用户数"按日预聚合落 dws_repurchase_daily，看板只读结果表；④ 若必须用窗口滑动（RANGE 89 PRECEDING），需先给日期转整数天序号（DATEDIFF 相对基准日），并接受 MySQL 下 RANGE 仅支持数值的限制。

### 6. 面试延伸考点

- **复购按订单数还是按购买日数算？** 要点：按天去重防同日多单虚增，按订单数反映频次；建议双口径并行，主指标用购买日。
- **为什么用滑动窗口而不是自然月留存？** 要点：滑动窗口逐日可监控、对噪声平滑；自然月对齐业务节奏便于同期群对比，两者结合看。
- **窗口内新客会不会稀释复购率？** 要点：会——新客窗口内大概率只买1次；拆"新客复购/老客复购"或"首购90天复购"两条线更真实。
- **怎么证明权益有效而不是大盘回暖？** 要点：上线时点前后对比+未开通权益用户的对照组趋势对比（简化DID），并排除大促窗口干扰。

### 7. 业务拓展思考

这条曲线的价值在于把"复购"从月度滞后的留存报告变成可日度监控的经营指标：下滑即触发召回队列（窗口内仅1次购买用户自动进入二次转化池），抬升可反推权益与会员日玩法是否值得加码。口径延展：分品类计算（生鲜90天复购远高于家电，统一阈值会误判）；把复购率换成"复购间隔中位数曲线"对异常更稳健；加权GMV复购率（金额维度粘性）可补充"人数粘性"之外的货币化视角。
## EC-36 连续登录7天且下单的活跃用户识别

### 1. 业务背景

活动运营准备上线"七日签到礼"预热：给"连续7天登录App且期间至少下过1单"的高粘性用户发放勋章与专属券。团队需要两份产出——用户名单（含每段连续区间的起止日期）和"每日新增七日连续活跃购买用户数"趋势，用于评估预热效果；同时这个口径被固化为核心活跃指标之一（连续活跃购买用户数），进入周会汇报。相比DAU，"连续且购买"更能代表真实粘性，也是刷量最难伪造的指标形态。

### 2. 表结构说明

user_login（登录记录表，已含原始重复行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| login_date | DATE | 登录日期（同一用户同一天可能多行） |

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_time | DATETIME | 支付时间 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据（数据均为虚构）：

| user_id | login_date |
| --- | --- |
| 8001 | 2025-06-01 |
| 8001 | 2025-06-02 |
| 8001 | 2025-06-03 |
| 8002 | 2025-06-01 |
| 8002 | 2025-06-05 |

| order_id | user_id | pay_time | pay_status | pay_amount |
| --- | --- | --- | --- | --- |
| 400001 | 8001 | 2025-06-02 12:00:00 | 1 | 158.00 |
| 400002 | 8001 | 2025-06-03 09:30:00 | 1 | 89.00 |
| 400003 | 8002 | 2025-06-01 21:10:00 | 1 | 59.00 |
| 400004 | 8003 | 2025-06-02 15:45:00 | 1 | 239.00 |
| 400005 | 8002 | 2025-06-06 11:20:00 | 0 | 99.00 |

### 3. 解题思路

经典"连续问题"两步走。第一步找"连续≥7天的登录段"：**【面试高频】** 通法是"日期减序号"——按用户分组对登录日 ROW_NUMBER 编号，DATE_SUB(login_date, INTERVAL rn DAY) 在连续段内为常量，按该常量分组聚合即得每段起点、终点、天数；另一种等价实现是"断点重置"——LAG 看相邻日期差，断点处组号+1，用 SUM 窗口累加出组键。第二步判"段内是否下过单"：把连续段与订单按 user_id 且 pay_time 落在 [段起点, 段终点+1天) 关联，用 EXISTS 半连接命中即入选。易错点：登录表必须先按"用户×天"去重，否则序号错位、分段全乱；"连续7天"指含首尾7个自然日（段天数≥7）；若题目是"7天内登录且下单"（不要求连续），直接窗口即可，审题必须抠清"连续"二字。

### 4. 参考解法

**解法一：日期减序号法（一次排序+一次分组，工程首选）**

```sql
WITH login_seq AS (      -- 登录日先按用户×天去重，再编号
    SELECT user_id, login_date,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn
    FROM (SELECT DISTINCT user_id, login_date FROM user_login) t
),
segment AS (             -- 连续段内：日期-序号 为常量（组键）
    SELECT user_id, login_date,
           DATE_SUB(login_date, INTERVAL rn DAY) AS grp
    FROM login_seq
),
seg_stat AS (            -- 每段起止与天数，筛出>=7天的段
    SELECT user_id, grp,
           MIN(login_date) AS seg_start,
           MAX(login_date) AS seg_end,
           COUNT(*)        AS seg_days
    FROM segment
    GROUP BY user_id, grp
    HAVING COUNT(*) >= 7                          -- 连续至少7个自然日
)
SELECT s.user_id AS 用户,
       s.seg_start AS 连续起始日,
       s.seg_end   AS 连续结束日,
       s.seg_days  AS 连续天数
FROM seg_stat s
WHERE EXISTS (          -- 段内至少一笔支付成功订单（半连接，命中即停）
    SELECT 1 FROM orders o
    WHERE o.user_id = s.user_id
      AND o.pay_status = 1
      AND o.pay_time >= s.seg_start
      AND o.pay_time <  s.seg_end + INTERVAL 1 DAY
)
ORDER BY s.user_id, s.seg_start;
-- 套一层按 seg_end 聚合 COUNT(DISTINCT user_id)，即得"每日新增"趋势
```

结果解读：用户8001连续登录6-01~6-03只有3天，不会入选；名单按用户×段输出，同一用户可能有多个达标段（历史上多次连续7天），发奖时按用户去重即可；日期减序号法利用了"连续日期差恒为1、序号差也恒为1"的守恒关系，是连续类题目的万能钥匙。

**解法二：断点重置法（LAG找断点，SUM累加组号）**

```sql
WITH login_gap AS (      -- 计算相邻登录日的间隔
    SELECT user_id, login_date,
           DATEDIFF(login_date,
                    LAG(login_date) OVER (PARTITION BY user_id ORDER BY login_date)) AS gap
    FROM (SELECT DISTINCT user_id, login_date FROM user_login) t
),
seg_mark AS (            -- 断点重置：首行或间隔>1天时组号+1，SUM窗口累加
    SELECT user_id, login_date,
           SUM(CASE WHEN gap IS NULL OR gap <> 1 THEN 1 ELSE 0 END)
               OVER (PARTITION BY user_id ORDER BY login_date
                     ROWS UNBOUNDED PRECEDING) AS grp      -- 累加出的连续段组键
    FROM login_gap
),
seg_stat AS (            -- 与解法一相同的分组与筛选
    SELECT user_id, grp,
           MIN(login_date) AS seg_start,
           MAX(login_date) AS seg_end,
           COUNT(*)        AS seg_days
    FROM seg_mark
    GROUP BY user_id, grp
    HAVING COUNT(*) >= 7
)
SELECT s.user_id AS 用户, s.seg_start AS 连续起始日,
       s.seg_end AS 连续结束日, s.seg_days AS 连续天数
FROM seg_stat s
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.user_id = s.user_id AND o.pay_status = 1
                AND o.pay_time >= s.seg_start
                AND o.pay_time <  s.seg_end + INTERVAL 1 DAY)
ORDER BY s.user_id, s.seg_start;
```

结果解读：断点重置法的组号是"从用户首日算起经历过的断点个数"，与日期减序号法在分段结果上完全等价；它多一次窗口计算，但思想可迁移到"连续N次未购""连续N单未用券"等非日期维度连续场景，泛用性更强。

> Hive/Spark SQL 差异：两法 Hive/Spark 均支持；登录日增十亿级时先按月分区 + user_id 分桶，窗口排序在桶内完成；EXISTS 在 Hive 老版本支持不佳，可改 LEFT JOIN + 过滤非空再按段去重。

### 5. 性能分析与优化

两法核心都是一次窗口排序 O(n log n)，无自连接膨胀；EXISTS 半连接在 MySQL 8.0 会被优化为 semi-join，命中即停，优于 JOIN+GROUP BY 去重。可执行优化：① user_login 建 (user_id, login_date) 唯一索引，去重与窗口排序一步完成；② orders 建 (user_id, pay_time) 复合索引支撑 EXISTS 范围探测；③ 登录表百亿级时按月分区裁剪最近周期，历史达标段离线分层计算；④ 名单类需求按天增量跑（只算昨天新完成的段），避免全量重扫；⑤ 若只要名单不要区间，可将 seg_stat 结果直接落到发奖中间表供推送系统消费。

### 6. 面试延伸考点

- **"连续7天登录且每天都要下单"怎么改？** 要点：把 EXISTS 升级为"段内有订单的天数=段天数"——订单也按用户×天去重后与登录段按日比对，COUNT 相等才算达标。
- **日期减序号法与断点重置法是否等价？** 要点：等价——连续段内日期差恒为1 ⇔ 相邻间隔恒为1；前者一次排序一次分组更省，后者适用于非日期连续的泛化场景。
- **自然日连续和滚动24小时连续有什么区别？** 要点：跨午夜会话（23点登录次日1点再登录）在自然日口径算中断，需要产品定义对齐；滚动窗口实现复杂得多。
- **发名单要注意什么运营风险？** 要点：叠加"近7天已触达"频控过滤防打扰，名单时效性（段判定是T+1的）要在活动文案里兼容。

### 7. 业务拓展思考

名单可直接接入Push系统与勋章中心，形成"识别-触达-核销"闭环；指标延展为"连续活跃购买天数分布"（7/14/30天阶梯），刻画粘性结构而非单一阈值人数。进一步可做归因验证：签到功能上线前后连续段人数对比+对照组，量化功能价值；风控视角下，连续登录但零浏览行为、高频率低时长的账号组合特征，可反向用于识别机器刷量账号，让这个指标同时服务增长与反作弊。

## EC-37 首购品类与次月留存交叉分析

### 1. 业务背景

品类运营复盘会上出现争论：一派认为"首单买生鲜的新客留存最好，高频刚需会拽着用户回来"；另一派认为"买数码的客单高但一次就走"。增长团队决定用数据裁决：把2025年5月的新客按首购品类分组，统计各组"次月是否复购"的留存率，输出"首购品类×次月留存"交叉表。结论将决定新客落地页推荐位排序——把用户首购引导向留存更好的品类；同时对高客单低留作品类配"复购券+关联品类推荐"的组合拳，而不是简单放弃。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| category | VARCHAR(30) | 商品类目 |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| --- | --- | --- | --- | --- | --- |

| 500002 | 9101 | 生鲜 | 52.00 | 1 | 2025-06-05 08:30:00 |

| 500005 | 9103 | 家居 | 328.00 | 0 | 2025-05-05 14:40:00 |

### 3. 解题思路

口径上要做三个决定：① 首购品类=首笔支付成功订单的品类，同日多笔取时间最早（并列再取金额大者，tie-break 需业务确认）；② "次月"定义为自然月（首单月+1的整个自然月），而非首单日+30天——自然月口径便于按月同期群滚动，两种口径结论可能不同，报告必须注明；③ 观察对象=首单发生在目标月份的新客（此前无支付成功记录），ROW_NUMBER 取第一笔天然满足。路径：CTE1 窗口取首单；CTE2 用 EXISTS 判定次月是否有复购；CTE3 按首购品类聚合人数与留存率。**【避坑指南】** 最近一个整月之前的月份才可比——次月窗口没走完的月份留存率被人为压低，必须限制首单月≤上上月，否则"留存变差"的假结论会直接影响品类预算。

### 4. 参考解法

**解法一：窗口取首单 + EXISTS 半连接（推荐）**

```sql
WITH first_buy AS (      -- 每用户首笔支付成功订单
    SELECT order_id, user_id, category, pay_amount, pay_time,
           ROW_NUMBER() OVER (PARTITION BY user_id
                              ORDER BY pay_time, pay_amount DESC) AS rn
    FROM orders
    WHERE pay_status = 1                       -- 同刻并列时金额大者优先
),
cohort AS (              -- 2025年5月新客同期群
    SELECT user_id,
           category AS first_cate,             -- 首购品类
           pay_amount AS first_amt,
           DATE_FORMAT(pay_time, '%Y-%m-01') AS first_month
    FROM first_buy
    WHERE rn = 1
      AND DATE_FORMAT(pay_time, '%Y-%m-01') = '2025-05-01'
),
retain AS (              -- 逐人判定：次月（自然月）是否有复购
    SELECT c.user_id, c.first_cate, c.first_amt,
           EXISTS (SELECT 1 FROM orders o
                   WHERE o.user_id = c.user_id AND o.pay_status = 1
                     AND o.pay_time >= c.first_month + INTERVAL 1 MONTH  -- 首单月+1
                     AND o.pay_time <  c.first_month + INTERVAL 2 MONTH) AS is_retain
    FROM cohort c
)
SELECT first_cate                                    AS 首购品类,
       COUNT(*)                                      AS 新客数,
       SUM(is_retain)                                AS 次月复购人数,
       ROUND(AVG(is_retain) * 100, 2)                AS 次月留存率,
       ROUND(AVG(first_amt), 2)                      AS 首单客单价
FROM retain
GROUP BY first_cate
ORDER BY 次月留存率 DESC;
```

结果解读：交叉表同时给出"留存率"与"客单价"两列，避免只看留存就砍掉高客单品类——数码类若留存低但客单高，正确动作是配复购券而非下推荐位；结论显著与否还要看各品类新客数（小样本品类的留存率波动大）。

**解法二：区间 LEFT JOIN 聚合法（不用EXISTS，顺带算复购金额）**

```sql
WITH first_buy AS (      -- 同解法一
    SELECT order_id, user_id, category, pay_amount, pay_time,
           ROW_NUMBER() OVER (PARTITION BY user_id
                              ORDER BY pay_time, pay_amount DESC) AS rn
    FROM orders
    WHERE pay_status = 1
),
cohort AS (              -- 同解法一
    SELECT user_id, category AS first_cate,
           DATE_FORMAT(pay_time, '%Y-%m-01') AS first_month
    FROM first_buy
    WHERE rn = 1
      AND DATE_FORMAT(pay_time, '%Y-%m-01') = '2025-05-01'
)
SELECT c.first_cate                                                       AS 首购品类,
       COUNT(DISTINCT c.user_id)                                          AS 新客数,
       COUNT(DISTINCT CASE WHEN o.order_id IS NOT NULL
                           THEN c.user_id END)                            AS 次月复购人数,
       ROUND(COUNT(DISTINCT CASE WHEN o.order_id IS NOT NULL THEN c.user_id END)
             / COUNT(DISTINCT c.user_id) * 100, 2)                        AS 次月留存率,
       ROUND(COALESCE(SUM(o.pay_amount), 0)
             / COUNT(DISTINCT c.user_id), 2)                              AS 次月人均复购金额
FROM cohort c
LEFT JOIN orders o
       ON o.user_id = c.user_id AND o.pay_status = 1
      AND o.pay_time >= c.first_month + INTERVAL 1 MONTH                 -- 次月区间匹配
      AND o.pay_time <  c.first_month + INTERVAL 2 MONTH
GROUP BY c.first_cate
ORDER BY 次月留存率 DESC;
```

结果解读：LEFT JOIN 会把次月多单用户展开成多行（人数用 COUNT(DISTINCT) 防膨胀失真），但换来了"人均复购金额"这一货币化视角；留存率接近的两个品类，人均复购金额高的才是更优质的首购引导方向。

> Hive/Spark SQL 差异：写法一致；Hive 老版本对相关子查询 EXISTS 支持差，优先 LEFT JOIN 区间法；数仓按月调度时把 first_buy 落成全量首购表（dws_user_first_order），同期群只做轻量 join。

### 5. 性能分析与优化

EXISTS 半连接命中即止、无行膨胀，适合只判"有没有"；LEFT JOIN 膨胀=人均次月订单数（通常个位数），可接受但要用 DISTINCT 防失真，好处是一次关联同时拿到留存与金额。可执行优化：① orders 建 (user_id, pay_time) 复合索引，两条路径都能走索引范围扫描；② first_buy 窗口结果集很小，先物化 cohort 再关联，避免窗口在大明细上重复执行；③ 按月调度用 pay_time 分区裁剪首单月与次月两个分区；④ 品类维表规范化（避免同名不同ID），保证交叉表行列稳定。

### 6. 面试延伸考点

- **首购品类的留存差异是因果还是选择偏差？** 要点：用户自选择进入品类，直接归因有偏；严格验证要用新客推荐位随机分流的A/B实验。
- **首日多单跨品类的用户算哪个品类？** 要点：需定主品类规则（时间最早/金额最大/多品类标记），规则一变结论可能翻转，必须在口径文档里写死。
- **留存口径用7日/30日/次月怎么选？** 要点：跟随品类购买周期——生鲜看7日、家电看90日；统一口径会掩盖周期差异，可按品类定制。
- **"注册月新客"和"首购月新客"有什么区别？** 要点：前者含注册未购，后者只算已转化；漏斗分析用前者，留存同期群用后者，混用会导致分母错配。

### 7. 业务拓展思考

交叉表可扩展为"首购品类×首购渠道"二维矩阵，指导渠道与品类联合投放（什么渠道引流到什么品类承接）；对低留作品类上"复购券+关联品类推荐"组合，验证能否人为改善首购结构。口径延展：留存升级为"次月GMV留存"衡量金额粘性；追踪首购后1-6个月留存曲线，区分"短期回访"与"长期习惯"；进一步把首购品类换成首购品类数（单品类 vs 跨品类首购），检验"跨品类用户更忠诚"的常见假设。

## EC-38 支付成功率异动定位：分渠道分时段环比归因

### 1. 业务背景

某天上午10点，数据值班收到大盘报警：昨日全站支付成功率环比下降1.8个百分点。支付产品经理必须在站会前回答"跌在哪里"——是App端整体问题，还是某个第三方支付通道、某个时段的局部故障。数据同学要按"渠道×小时"两维拆解成功率、计算环比变化，并量化每个单元对大盘的拖累（影响度），把最可疑的3个单元连同样本量一起交给对应技术团队排查。这是典型的异动归因场景：速度比完美更重要，但结论必须可甩锅（有数据依据）。

### 2. 表结构说明

payments（支付流水表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| payment_id | BIGINT | 支付流水号 |
| user_id | BIGINT | 用户ID |
| channel | VARCHAR(20) | 支付渠道：app_wechat/app_aliapp/mini/h5 |
| pay_amount | DECIMAL(10,2) | 支付金额 |
| pay_status | TINYINT | 1=成功，0=失败 |
| create_time | DATETIME | 发起支付时间 |

示例数据（数据均为虚构）：

| payment_id | user_id | channel | pay_amount | pay_status | create_time |
| --- | --- | --- | --- | --- | --- |
| 600001 | 9201 | app_wechat | 128.00 | 1 | 2025-06-19 09:15:00 |
| 600002 | 9202 | app_aliapp | 259.00 | 0 | 2025-06-19 09:16:20 |
| 600003 | 9203 | mini | 45.00 | 1 | 2025-06-19 10:02:00 |
| 600004 | 9204 | h5 | 199.00 | 0 | 2025-06-19 10:05:00 |
| 600005 | 9205 | app_wechat | 88.00 | 1 | 2025-06-20 11:30:00 |

### 3. 解题思路

口径先行：成功率=支付成功笔数/发起笔数（分母含失败；"用户取消"若单独立状态需先剔除，本题两级）；时段按 create_time 的小时切。路径：CTE1 按"日×渠道×小时"聚合发起与成功笔数；CTE2 用 LAG 按（渠道,小时）分区取前一日成功率，计算环比变化（pp）；CTE3 计算影响度并排序定位。**【加分点】** 影响度公式=该单元今日发起笔数占比×(今日成功率-昨日成功率)：低量渠道的大波动天然被降权，排序直接按"对大盘的拉动力"而非绝对变化，避免被凌晨小样本时段带偏。易错点：凌晨笔数少、成功率波动天然大，要加最小样本门槛（如发起<50笔标"低置信"）；渠道×小时单元数固定（4×24），窗口代价极小，重点在只扫两日分区。

### 4. 参考解法

**解法一：分组LAG + 影响度归因（推荐，一步到位）**

```sql
WITH hourly AS (         -- 日×渠道×小时 聚合
    SELECT DATE(create_time) AS pay_date, channel,
           HOUR(create_time) AS hr,
           COUNT(*) AS req_cnt,                 -- 发起笔数（含失败）
           SUM(pay_status) AS ok_cnt            -- 成功笔数
    FROM payments
    WHERE create_time >= CURDATE() - INTERVAL 2 DAY     -- 只扫近两日分区
    GROUP BY 1, 2, 3
),
rate AS (                -- 按(渠道,小时)取昨日与前日成功率
    SELECT channel, hr, pay_date, req_cnt,
           ok_cnt / NULLIF(req_cnt, 0) AS succ_rate,
           LAG(ok_cnt / NULLIF(req_cnt, 0))
               OVER (PARTITION BY channel, hr ORDER BY pay_date) AS prev_rate
    FROM hourly
),
impact AS (              -- 影响度 = 昨日发起占比 × 成功率变化(pp)
    SELECT r.*,
           (r.succ_rate - r.prev_rate) * 100 AS delta_pp,
           r.req_cnt * 1.0
             / SUM(CASE WHEN r.pay_date = CURDATE() - INTERVAL 1 DAY
                        THEN r.req_cnt END) OVER ()     -- 只用昨日量做分母
             * (r.succ_rate - r.prev_rate) * 100 AS impact_pp
    FROM rate r
)
SELECT channel AS 渠道, hr AS 小时, req_cnt AS 发起笔数,
       ROUND(succ_rate * 100, 2) AS 今日成功率,
       ROUND(prev_rate * 100, 2) AS 昨日成功率,
       ROUND(delta_pp, 2) AS 环比变化pp,
       ROUND(impact_pp, 2) AS 对大盘影响pp,
       CASE WHEN req_cnt < 50 THEN '低置信' ELSE '可信' END AS 置信标记
FROM impact
WHERE pay_date = CURDATE() - INTERVAL 1 DAY      -- 只看昨日单元
  AND prev_rate IS NOT NULL
ORDER BY 对大盘影响pp ASC                         -- 负向影响最大的排最前
LIMIT 10;
```

结果解读：影响度把"变化幅度"和"量级"合成一个可排序的数——某渠道10点成功率暴跌20pp但只占大盘3%流量，影响度-0.6pp，远小于占40%流量、跌3pp的app_wechat；值班同学按影响度Top3分派，归因效率最高。

**解法二：两日聚合自连接对比法（不依赖窗口）**

```sql
WITH hourly AS (         -- 同解法一的两日聚合
    SELECT DATE(create_time) AS pay_date, channel, HOUR(create_time) AS hr,
           COUNT(*) AS req_cnt, SUM(pay_status) AS ok_cnt
    FROM payments
    WHERE create_time >= CURDATE() - INTERVAL 2 DAY
    GROUP BY 1, 2, 3
),
d1 AS (SELECT channel, hr, req_cnt, ok_cnt FROM hourly
       WHERE pay_date = CURDATE() - INTERVAL 1 DAY),     -- 昨日
d2 AS (SELECT channel, hr, req_cnt, ok_cnt FROM hourly
       WHERE pay_date = CURDATE() - INTERVAL 2 DAY)      -- 前日
SELECT d1.channel AS 渠道, d1.hr AS 小时,
       d1.req_cnt AS 发起笔数,
       ROUND(d1.ok_cnt / NULLIF(d1.req_cnt, 0) * 100, 2) AS 今日成功率,
       ROUND(d2.ok_cnt / NULLIF(d2.req_cnt, 0) * 100, 2) AS 昨日成功率,
       ROUND((d1.ok_cnt / NULLIF(d1.req_cnt, 0)
            - d2.ok_cnt / NULLIF(d2.req_cnt, 0)) * 100, 2) AS 环比变化pp
FROM d1
LEFT JOIN d2 USING (channel, hr)                         -- 昨日为主表，新增渠道也能出现
WHERE d1.req_cnt >= 50                                   -- 最小样本门槛
ORDER BY 环比变化pp ASC;
```

结果解读：LEFT JOIN 以昨日为主表保证新增渠道不丢行；缺点是按绝对变化排序，小量单元会霸榜，人工看表时须结合发起笔数判断——这正是解法一引入影响度的原因，两种写法对比能讲清"归因排序"的演进。

> Hive/Spark SQL 差异：按天分区扫描两日数据，HOUR 函数与窗口写法一致；大表建议按天分区+channel 分桶；实时化时上游用 Flink 落分钟级渠道汇总表，本SQL退化为读聚合层的轻查询。

### 5. 性能分析与优化

只扫两日分区是最大的优化（WHERE create_time >= 近两日 使分区裁剪生效）；窗口按（渠道，小时）分区排序，行数=天数×96，几乎无代价；解法二两个派生表在 MySQL 8.0 各自物化一次再 JOIN，数据量小无感。可执行优化：① payments 按天分区 + (channel, create_time) 二级索引；② 实时监控场景上游落"分钟×渠道"预聚合表，成功率看板只读聚合层；③ 错误码字段若存在，按错误码再拆一层（余额不足/风控拦截/通道超时）定位技术根因；④ 阈值与样本门槛参数化，做成每小时自动跑的归因脚本。

### 6. 面试延伸考点

- **整体下降但每个渠道都在上升，可能吗？** 要点：辛普森悖论——渠道结构变化（低成功率渠道流量占比暴涨）拉低整体；用固定结构加权的"标准化成功率"对比排查。
- **为什么用笔数不用金额口径？** 要点：成功率衡量通道可用性，笔数等权；金额口径会被大额订单绑架，掩盖普通用户的失败。
- **失败原因（错误码）字段怎么用？** 要点：在渠道×小时定位后按错误码下钻，把问题指到具体系统（银行/风控/网络超时），归因才算闭环。
- **怎么区分渠道问题和用户群体问题？** 要点：交叉"渠道×用户分层"，若只有新客渠道失败率高，可能是风控策略收紧而非通道故障。

### 7. 业务拓展思考

这套模式可固化为"渠道健康分"看板：成功率、失败Top错误码、恢复时长三指标加权打分，联动通道降级/熔断的自动化预案；口径延展：把小时换成分钟可作为秒级熔断依据；加入发卡行/银行维度能定位到"某银行通道拥塞"这类最深层原因。归因脚本每小时输出影响度Top3并@通道负责人，把"人盯监控"变成"监控找人"，是数据分析在支付域最直接的工程化价值。

## EC-39 券核销ROI：用券vs未用券人群GMV增量对比（简化DID）

### 1. 业务背景

市场部6月1日向50万用户发放了"满100减20"的通用券，三天后运营复盘提问：这张券到底带来多少GMV增量？ROI是否为正？由于没有严格的随机实验，数据同学采用简化双重差分（DID）：把"领券且核销"用户作处理组、"领券未核销"用户作对照组，对比发券日前后各7天的人均GMV变化；周末、大盘活动等共同趋势在两组差分中抵消，差值即为券的净效应近似值。最终输出"组×期"四格表、DID人均增量与ROI（增量毛利/券补贴成本），作为下次券预算决策的依据。

### 2. 表结构说明

coupons（发券记录表，每用户每批次一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| coupon_id | BIGINT | 券批次ID |
| issue_time | DATETIME | 发放时间 |
| used_flag | TINYINT | 1=已核销，0=未核销 |
| used_time | DATETIME | 核销时间 |
| discount | DECIMAL(10,2) | 券面额 |

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| user_id | coupon_id | issue_time | used_flag | used_time | discount |
| --- | --- | --- | --- | --- | --- |
| 9301 | 20250601 | 2025-06-01 10:00:00 | 1 | 2025-06-03 20:11:00 | 20.00 |
| 9302 | 20250601 | 2025-06-01 10:00:00 | 0 | NULL | 20.00 |
| 9303 | 20250601 | 2025-06-01 10:00:00 | 1 | 2025-06-05 12:30:00 | 20.00 |
| 9304 | 20250601 | 2025-06-01 10:00:00 | 0 | NULL | 20.00 |
| 9305 | 20250601 | 2025-06-01 10:00:00 | 1 | 2025-06-06 09:05:00 | 20.00 |

| order_id | user_id | pay_amount | pay_status | pay_time |
| --- | --- | --- | --- | --- |

| 700002 | 9301 | 129.00 | 1 | 2025-06-03 20:11:00 |
| 700003 | 9303 | 45.00 | 1 | 2025-06-05 12:30:00 |
| 700004 | 9305 | 268.00 | 1 | 2025-06-06 09:05:00 |
| 700005 | 9302 | 99.00 | 1 | 2025-06-02 13:40:00 |

### 3. 解题思路

先立口径：处理组=used_flag=1；对照组=同批次领券但 used_flag=0（绝不能混入未领券人群）；窗口=发券日前7天 [05-25, 06-01) 与后7天 [06-02, 06-08)，发券日当天因脉冲效应剔除；人均GMV=组×期支付成功金额/组内去重人数（分母用整组人数，不是有订单人数）；DID=(处理组后-处理组前)-(对照组后-对照组前)。**【加分点】** 更稳健的等价写法是"个体一阶差分"：先算每个用户（后7天GMV-前7天GMV），再对两组分别求均值、作差——窗口完整前提下与四格表DID数学等价，且能直接看个体分布、算置信区间。易错点：① 个体差分必须 LEFT JOIN 保留窗口内无订单的沉默用户，内联会改变两组结构、DID失真；② 多张券/多次发券要锁定 coupon_id；③ 核销有效期若覆盖观察窗之外，需按 used_time 校准分组。

### 4. 参考解法

**解法一：四格表DID（组×期聚合，口径一目了然）**

```sql
WITH coupon_users AS (   -- 锁定单批次券的用户与分组
    SELECT user_id, used_flag
    FROM coupons
    WHERE coupon_id = 20250601
),
grp_size AS (            -- 每组人数：人均分母必须用整组人数（含沉默用户）
    SELECT used_flag, COUNT(DISTINCT user_id) AS n
    FROM coupon_users
    GROUP BY used_flag
),
tagged AS (              -- 订单打前后期标签，只保留14天窗口
    SELECT cu.used_flag,
           CASE WHEN o.pay_time >= '2025-06-02' AND o.pay_time < '2025-06-08'
                THEN 'after'
                WHEN o.pay_time >= '2025-05-25' AND o.pay_time < '2025-06-01'
                THEN 'before' END AS period_tag,
           o.pay_amount
    FROM coupon_users cu
    JOIN orders o
      ON o.user_id = cu.user_id AND o.pay_status = 1
    WHERE o.pay_time >= '2025-05-25' AND o.pay_time < '2025-06-08'
),
cell AS (                -- 组×期 GMV
    SELECT used_flag, period_tag, SUM(pay_amount) AS gmv
    FROM tagged
    WHERE period_tag IS NOT NULL
    GROUP BY used_flag, period_tag
),
diff AS (                -- 每组"后-前"人均变化
    SELECT g.used_flag,
           (SUM(CASE WHEN c.period_tag = 'after'  THEN c.gmv ELSE 0 END)
          - SUM(CASE WHEN c.period_tag = 'before' THEN c.gmv ELSE 0 END))
          / g.n AS delta_pc
    FROM cell c
    JOIN grp_size g USING (used_flag)
    GROUP BY g.used_flag, g.n
)
SELECT MAX(CASE WHEN used_flag = 1 THEN delta_pc END) AS 处理组人均变化,
       MAX(CASE WHEN used_flag = 0 THEN delta_pc END) AS 对照组人均变化,
       MAX(CASE WHEN used_flag = 1 THEN delta_pc END)
     - MAX(CASE WHEN used_flag = 0 THEN delta_pc END) AS DID人均增量
FROM diff;
-- ROI = (DID人均增量 × 处理组人数 × 毛利率 - 核销张数×面额) / (核销张数×面额)
```

结果解读：若处理组人均涨15元、对照组涨5元，DID=10元/人才是剔除共同趋势后的券效应；直接拿处理组前后差15元汇报会高估50%。ROI用增量毛利而非增量GMV，否则低毛利品类的券会被误判为划算。

**解法二：个体一阶差分法（先差分再组间对比）**

```sql
WITH coupon_users AS (   -- 同解法一
    SELECT user_id, used_flag
    FROM coupons
    WHERE coupon_id = 20250601
),
user_diff AS (           -- 个体层面：后7天GMV - 前7天GMV
    SELECT cu.user_id, cu.used_flag,
           SUM(CASE WHEN o.pay_time >= '2025-06-02' AND o.pay_time < '2025-06-08'
                    THEN o.pay_amount ELSE 0 END)
         - SUM(CASE WHEN o.pay_time >= '2025-05-25' AND o.pay_time < '2025-06-01'
                    THEN o.pay_amount ELSE 0 END) AS diff_gmv
    FROM coupon_users cu
    LEFT JOIN orders o                       -- 必须LEFT JOIN：沉默用户保留0差分
           ON o.user_id = cu.user_id AND o.pay_status = 1
          AND o.pay_time >= '2025-05-25' AND o.pay_time < '2025-06-08'
    GROUP BY cu.user_id, cu.used_flag
)
SELECT used_flag AS 组,
       COUNT(*) AS 人数,
       ROUND(AVG(diff_gmv), 2) AS 人均GMV变化
FROM user_diff
GROUP BY used_flag
ORDER BY used_flag DESC;
-- 两组人均变化之差即DID增量，与解法一在窗口完整时数学等价
```

结果解读：个体差分保留了每个人的完整前后对照，额外产出"差分分布"——若处理组增量高度集中在少数大户，说明券效应可能是长尾驱动，均值会被拉偏，应补中位数与分位数结论。

> Hive/Spark SQL 差异：逻辑一致；用户级 diff 后可直接接 Spark 做双样本t检验（均值±1.96×SE）评估显著性；50万用户级小表在各引擎均可广播，大表按 pay_time 分区裁剪14天。

### 5. 性能分析与优化

两边都只扫14天订单分区（pay_time 范围条件下推），处理组+对照组50万用户是小表。解法一订单聚合一次+小表关联；解法二 JOIN 后按 user_id 一次 shuffle 聚合，行数=用户数。可执行优化：① coupon_users 先按 coupon_id 收敛再去碰订单大表，避免全表用户JOIN；② orders 建 (user_id, pay_time) 复合索引或按天分区，把14天窗口的扫描压到最低；③ 多批次复盘时把"用户×期"中间表落数仓复用，避免每次重扫订单；④ 对照组与处理组规模悬殊时（核销率低），抽样平衡可加速而不改变均值无偏性。

### 6. 面试延伸考点

- **DID的核心假设是什么？怎么验证？** 要点：平行趋势——发券前两组趋势应平行；拉长前期窗口画逐日人均GMV趋势图，若发券前两组已经分叉，DID估计有偏。
- **"领券未核销"对照组干净吗？** 要点：不干净——领券本身有提醒效应、未核销者可能天然低活跃（选择偏差）；严格方案是随机分流实验，或倾向得分匹配（PSM）后再DID。
- **ROI该用GMV还是毛利？** 要点：补贴决策看增量毛利ROI=（DID×处理组人数×毛利率−补贴成本)/补贴成本；GMV口径会高估低毛利券的效果。
- **券被用于"本来就要买"的订单怎么办？** 要点：这就是DID想剔除的自然转化，但个体层面"必然购买"需uplift模型识别，券应定向发给"发券才买"的边缘人群。

### 7. 业务拓展思考

结论联动三件事：券面额与门槛的弹性测试（多批次小流量实验找性价比拐点）、高潜人群分层发券（把预算从"人人有份"转向边缘人群）、券后追踪（观察核销用户30天留存是否真被拉高）。口径延展：观察窗拉长到30天可区分"短期脉冲"与"真实习惯养成"；按品类拆DID能看券拉动的品类结构是否健康（是否全是低毛利品类凑单）；与A/B平台打通后，DID可作为实验未覆盖人群的准实验补充证据，形成"实验为主、准实验兜底"的效果度量体系。

## EC-40 流失用户最后行为特征：流失前7天vs活跃用户对比

### 1. 业务背景

增长团队的流失预警项目进入特征分析阶段：业务定义"连续30天无任何App行为即流失"（由离线任务在 users 表维护标记）。团队想知道流失用户"走之前"有什么征兆——对比流失用户最后7天与活跃用户同期的行为结构（浏览、搜索、加购、下单、客服投诉的人均次数与构成占比），找出显著差异的行为信号，交给算法同学做流失预测模型的特征候选，并给CRM团队设计挽留话术分级。结论将在双周会上决定先推哪类挽留策略：是补偿型（优惠券）还是服务型（人工回访）。

### 2. 表结构说明

users（用户属性表，流失标记由离线任务维护）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| last_active_date | DATE | 最近一次行为日期 |
| is_churn | TINYINT | 1=流失（30天无行为），0=活跃 |
| register_date | DATE | 注册日期 |

user_behavior（行为明细表，按天分区）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| behavior_type | VARCHAR(10) | 行为：view/search/cart/order/complain |
| behavior_time | DATETIME | 行为时间 |

示例数据（数据均为虚构）：

| user_id | last_active_date | is_churn | register_date |
| --- | --- | --- | --- |
| 9401 | 2025-05-20 | 1 | 2024-11-02 |
| 9402 | 2025-05-25 | 1 | 2025-01-15 |
| 9403 | 2025-06-07 | 0 | 2024-12-20 |
| 9404 | 2025-06-05 | 0 | 2025-03-01 |
| 9405 | 2025-05-28 | 1 | 2024-10-08 |

| user_id | behavior_type | behavior_time |
| --- | --- | --- |
| 9401 | view | 2025-05-15 10:00:00 |
| 9401 | cart | 2025-05-16 21:30:00 |
| 9401 | complain | 2025-05-18 09:12:00 |
| 9403 | order | 2025-06-03 20:05:00 |
| 9403 | search | 2025-06-04 08:40:00 |

### 3. 解题思路

口径：流失用户窗口=流失前7天 [last_active_date-6, last_active_date]；活跃对照组必须用"等长窗口"才可比——取同一自然周（示例取2025-06-01~06-07，生产中应按流失人群的流失时间分布选同期周），并剔除窗口期后才注册的用户；指标用"人均次数+组内构成比"双轨。**【避坑指南】** 不要直接比绝对次数——流失用户最后7天总活跃度下降是必然结果，只有构成比（某行为占总行为比重）才能区分"什么都少了"和"下单/投诉占比特别异常"这两种性质完全不同的流失剧本。路径：CTE1 从 users 圈两组人群并绑定各自窗口；CTE2 关联窗口内行为明细；CTE3 按 组×行为类型 聚合人均次数与窗口占比；CTE4 回连计算占比倍数，按信号强度排序。

### 4. 参考解法

**解法一：UNION ALL 拼两组样本 + 窗口占比对比（一步到位）**

```sql
WITH sample AS (         -- 两组人群与各自的观察窗口
    SELECT user_id, 'churn' AS grp,
           last_active_date - INTERVAL 6 DAY AS win_start,   -- 流失前7天
           last_active_date AS win_end
    FROM users
    WHERE is_churn = 1
    UNION ALL
    SELECT user_id, 'active',
           DATE '2025-06-01',                     -- 活跃组统一取同一自然周
           DATE '2025-06-07'
    FROM users
    WHERE is_churn = 0
      AND register_date < '2025-06-01'            -- 排除窗口期后才注册的用户
),
detail AS (              -- 关联窗口内行为明细
    SELECT s.grp, s.user_id, b.behavior_type
    FROM sample s
    JOIN user_behavior b
      ON b.user_id = s.user_id
     AND b.behavior_time >= s.win_start
     AND b.behavior_time <  s.win_end + INTERVAL 1 DAY
),
stat AS (                -- 组×行为：人数、次数、人均、组内构成比
    SELECT grp, behavior_type,
           COUNT(DISTINCT user_id) AS user_cnt,
           COUNT(*) * 1.0 / COUNT(DISTINCT user_id) AS per_user,       -- 人均次数
           COUNT(*) * 1.0 / SUM(COUNT(*)) OVER (PARTITION BY grp) AS share  -- 构成比
    FROM detail
    GROUP BY grp, behavior_type
)
SELECT c.behavior_type                        AS 行为类型,
       ROUND(c.per_user, 2)                   AS 流失组人均次数,
       ROUND(a.per_user, 2)                   AS 活跃组人均次数,
       ROUND(c.share * 100, 2)                AS 流失组占比,
       ROUND(a.share * 100, 2)                AS 活跃组占比,
       ROUND(c.share / NULLIF(a.share, 0), 2) AS 占比倍数   -- 信号强度
FROM stat c
LEFT JOIN stat a                                    -- CTE可被引用两次
       ON a.behavior_type = c.behavior_type AND a.grp = 'active'
WHERE c.grp = 'churn'
ORDER BY 占比倍数 DESC;
```

结果解读：若"complain占比倍数3.5、cart占比倍数1.8而order占比倍数0.4"，剧本很清晰——流失前"加购不买+投诉激增"，挽留应以服务补救（人工回访+补偿券）为主，而非通用Push。

**解法二：先用户级聚合再对比（两层聚合，Hive大表更友好）**

```sql
WITH sample AS (         -- 同解法一
    SELECT user_id, 'churn' AS grp,
           last_active_date - INTERVAL 6 DAY AS win_start,
           last_active_date AS win_end
    FROM users WHERE is_churn = 1
    UNION ALL
    SELECT user_id, 'active', DATE '2025-06-01', DATE '2025-06-07'
    FROM users WHERE is_churn = 0 AND register_date < '2025-06-01'
),
user_act AS (            -- 先收敛到 用户×组×行为 粒度（Hive减少shuffle的关键）
    SELECT s.grp, s.user_id, b.behavior_type, COUNT(*) AS cnt
    FROM sample s
    JOIN user_behavior b
      ON b.user_id = s.user_id
     AND b.behavior_time >= s.win_start
     AND b.behavior_time <  s.win_end + INTERVAL 1 DAY
    GROUP BY s.grp, s.user_id, b.behavior_type
),
stat AS (                -- 再汇总到 组×行为
    SELECT grp, behavior_type,
           COUNT(DISTINCT user_id) AS user_cnt,
           SUM(cnt) AS act_cnt
    FROM user_act
    GROUP BY grp, behavior_type
)
SELECT c.behavior_type AS 行为类型,
       ROUND(c.act_cnt * 1.0 / c.user_cnt, 2) AS 流失组人均次数,
       ROUND(a.act_cnt * 1.0 / a.user_cnt, 2) AS 活跃组人均次数,
       ROUND(c.act_cnt * 1.0
             / SUM(c.act_cnt) OVER (PARTITION BY c.grp) * 100, 2) AS 流失组占比,
       ROUND(a.act_cnt * 1.0
             / SUM(a.act_cnt) OVER (PARTITION BY a.grp) * 100, 2) AS 活跃组占比
FROM stat c
LEFT JOIN stat a ON a.behavior_type = c.behavior_type AND a.grp = 'active'
WHERE c.grp = 'churn'
ORDER BY 流失组占比 DESC;
```

结果解读：先把明细收敛到用户级再汇总，Shuffle 数据量从"行为明细行数"降到"用户×行为类型"行数，亿级行为表下是数量级差异；结果与解法一一致，工程选择问题。

> Hive/Spark SQL 差异：行为表按天分区，两组窗口各自只裁剪7天分区；users 小表广播；生产上把 user_behavior 预聚合为 dws_user_behavior_1d（用户×日×行为×次数）后，本查询从小时级降到秒级。

### 5. 性能分析与优化

行为明细是最大表：必须按 behavior_time 分区裁剪，两组各扫7天分区；sample 人群先在 users 小表层圈定，JOIN 时才不会全表探测。解法二的两层聚合在 Hive/Spark 下显著减少 shuffle，是大数据量首选。可执行优化：① user_behavior 建 (user_id, behavior_time) 复合索引或按日分区+user 分桶；② 预聚合 dws_user_behavior_1d 是此类特征分析的标准前置；③ 流失标记在 users 表离线维护，SQL 只读不重算，避免在查询里反复定义"30天无行为"；④ 窗口期后注册用户的过滤前置到 sample 层，减少无效关联。

### 6. 面试延伸考点

- **流失阈值30天怎么定才科学？** 要点：用全体用户回访间隔分布的P90，或"错过下一个购买周期概率"来定，比拍脑袋可辩护；阈值变化要回溯验证。
- **两组差异怎么判断是否显著？** 要点：构成比做卡方检验、人均次数做t检验或Mann-Whitney；大样本下微小差异也显著，要看效应量（倍数）而非只看p值。
- **投诉行为要不要单独处理？** 要点：强信号但样本少，单列分析并回流客诉工单系统交叉验证，避免被平均掩盖。
- **活跃对照组怎么选才公平？** 要点：同周期、同注册时段、同品类偏好分层抽样；结构差异会伪装成行为差异，选错对照一切白做。

### 7. 业务拓展思考

信号强度Top行为直接进流失预测模型特征库（配合XGBoost等时序特征），CRM按"流失风险×用户价值"四象限分级挽留——高价值投诉用户优先人工外呼，低价值高流失风险用户仅低成本的Push召回。口径延展：把"最后7天"改为"最后3次会话"可捕捉更临终的信号；增加"最后订单的退款/差评"后缀事件能丰富流失剧本；对比"真流失 vs 休眠后回归"用户的行为差异，还能反向提炼召回成功用户的行为指纹，指导召回文案设计。

## EC-41 品类销售额贡献度排名及月度排名变化

### 1. 业务背景

经营分析双周报新增"品类龙虎榜"板块：展示本月各品类的销售额、占总盘比重（贡献度）与名次，并与上月名次对比，标出"上升2位/下降3位/新上榜/跌出榜"。品类负责人每天盯这张表对齐资源位和招商方向；数据同学要保证并列名次处理规则一致（并列同名次还是紧凑排名）、新上榜与跌出榜的标记清晰，避免运营把长尾品类的名次噪声误读成趋势。榜单同时服务CEO晨会——"本月谁在掉队"需要一个不会引起口径争议的答案。

### 2. 表结构说明

order_items（订单明细表，支付成功口径）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| category | VARCHAR(30) | 品类（一级） |
| sale_amount | DECIMAL(12,2) | 明细实付金额 |
| qty | INT | 购买数量 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| order_id | user_id | category | sale_amount | qty | pay_time |
| --- | --- | --- | --- | --- | --- |
| 800001 | 9501 | 美妆 | 259.00 | 1 | 2025-06-01 10:00:00 |
| 800002 | 9502 | 数码 | 1999.00 | 1 | 2025-06-02 20:30:00 |
| 800003 | 9503 | 食品 | 45.80 | 2 | 2025-06-03 09:12:00 |
| 800004 | 9504 | 美妆 | 129.00 | 1 | 2025-06-04 15:40:00 |
| 800005 | 9505 | 家居 | 328.00 | 1 | 2025-06-05 19:02:00 |

### 3. 解题思路

口径：销售额=支付成功明细金额合计；贡献度=品类销售额/当月大盘；排名用 RANK()（并列同名次、后继跳号），若业务要求"无并列不跳号"换 DENSE_RANK 或 ROW_NUMBER——三种函数的差异是必考题，必须在口径文档写明。路径：CTE1 按"月×品类"聚合并设排名门槛（如月销≥1万，滤长尾噪声）；CTE2 RANK() OVER (PARTITION BY 月 ORDER BY 金额 DESC) 得月内名次；CTE3 用 LAG 按（品类）取上月名次与上月销售额，计算名次变化与占比变化。**【避坑指南】** 两个细节决定榜单可信度：一是小品类不设门槛会导致名次大幅跳变全是噪声；二是"跌出榜"品类（上月有本月无）用 LAG 法会被 WHERE 本月条件直接滤掉，必须以两月品类全集为主表反向补齐，或采用解法二的两月JOIN结构。

### 4. 参考解法

**解法一：RANK + LAG 窗口一气呵成（推荐）**

```sql
WITH monthly AS (        -- 月×品类 销售额，设排名门槛滤长尾
    SELECT CAST(DATE_FORMAT(pay_time, '%Y-%m-01') AS DATE) AS ym,
           category,
           SUM(sale_amount) AS amt
    FROM order_items
    WHERE pay_time >= '2025-05-01' AND pay_time < '2025-07-01'   -- 近两个月
    GROUP BY 1, 2
    HAVING SUM(sale_amount) >= 10000                              -- 门槛：月销≥1万
),
ranked AS (              -- 月内排名 + 当月大盘总额
    SELECT ym, category, amt,
           RANK() OVER (PARTITION BY ym ORDER BY amt DESC) AS rk,
           SUM(amt) OVER (PARTITION BY ym) AS month_total
    FROM monthly
),
delta AS (               -- 按品类取上月名次、上月金额、上月大盘
    SELECT ym, category, amt, rk, month_total,
           LAG(rk)           OVER (PARTITION BY category ORDER BY ym) AS prev_rk,
           LAG(amt)          OVER (PARTITION BY category ORDER BY ym) AS prev_amt,
           LAG(month_total)  OVER (PARTITION BY category ORDER BY ym) AS prev_total
    FROM ranked
)
SELECT ym AS 月份, category AS 品类, amt AS 销售额,
       rk AS 名次, prev_rk AS 上月名次,
       ROUND(amt / NULLIF(month_total, 0) * 100, 2)                       AS 本月占比,
       ROUND(amt / NULLIF(month_total, 0) * 100
           - prev_amt / NULLIF(prev_total, 0) * 100, 2)                   AS 占比变化pp,
       CASE WHEN prev_rk IS NULL THEN '新上榜'
            WHEN rk < prev_rk THEN CONCAT('上升', prev_rk - rk)
            WHEN rk > prev_rk THEN CONCAT('下降', rk - prev_rk)
            ELSE '持平' END                                               AS 名次变化
FROM delta
WHERE ym = '2025-06-01'
ORDER BY rk;
```

结果解读：名次变化回答"相对地位"，占比变化pp回答"结构迁移"，两者结合才能定性——名次下降但占比几乎持平，说明是大盘整体波动而非本品掉队；本月占比与占比变化pp的交叉解读是月报复盘的常规动作。

**解法二：两月分别排名后JOIN对比（可完整标记"跌出榜"）**

```sql
WITH monthly AS (        -- 同解法一
    SELECT CAST(DATE_FORMAT(pay_time, '%Y-%m-01') AS DATE) AS ym,
           category, SUM(sale_amount) AS amt
    FROM order_items
    WHERE pay_time >= '2025-05-01' AND pay_time < '2025-07-01'
    GROUP BY 1, 2
    HAVING SUM(sale_amount) >= 10000
),
m5 AS (                  -- 上月榜单
    SELECT category, amt,
           RANK() OVER (ORDER BY amt DESC) AS rk,
           SUM(amt) OVER () AS total
    FROM monthly WHERE ym = '2025-05-01'
),
m6 AS (                  -- 本月榜单
    SELECT category, amt,
           RANK() OVER (ORDER BY amt DESC) AS rk,
           SUM(amt) OVER () AS total
    FROM monthly WHERE ym = '2025-06-01'
)
SELECT COALESCE(m6.category, m5.category) AS 品类,
       m6.rk AS 本月名次, m5.rk AS 上月名次,
       CASE WHEN m6.category IS NULL THEN '跌出榜'
            WHEN m5.category IS NULL THEN '新上榜'
            WHEN m6.rk < m5.rk THEN CONCAT('上升', m5.rk - m6.rk)
            WHEN m6.rk > m5.rk THEN CONCAT('下降', m6.rk - m5.rk)
            ELSE '持平' END AS 名次变化,
       m6.amt AS 本月销售额,
       ROUND(m6.amt / NULLIF(m6.total, 0) * 100, 2) AS 本月占比
FROM m6
LEFT JOIN m5 ON m5.category = m6.category
UNION ALL
SELECT m5.category, NULL, m5.rk, '跌出榜', NULL, NULL
FROM m5
LEFT JOIN m6 ON m6.category = m5.category
WHERE m6.category IS NULL                   -- 上月在榜、本月被门槛滤掉或归零
ORDER BY 本月名次 DESC;                       -- MySQL中DESC时NULL排最后
```

结果解读：跌出榜的品类要么跌破门槛要么零销售，是品类异常（断货、下架、竞对截流）的高危信号，单独列出比默默消失更利于追责与诊断；该结构两月榜单各自物化再对比，逻辑直白，也便于扩展到同比对比。

> Hive/Spark SQL 差异：RANK/DENSE_RANK/ROW_NUMBER 全支持，写法可直接平移；长尾门槛建议在数仓 dws 层统一；亿级明细先落"日×品类"汇总表，月榜只读聚合层。

### 5. 性能分析与优化

解法一一次扫描明细+两次窗口（月内RANK、品类内LAG），排序行数=品类数×月数（几十到几百），可忽略；真正的代价在明细聚合——按 pay_time 月分区裁剪两个月分区，或直接读 dws 月汇表。解法二两月派生表各物化一次再JOIN，行数极小，MySQL 无 FULL OUTER JOIN 需 UNION 补齐跌出榜行。可执行优化：① order_items 按 pay_time 月分区+(category) 排序键/二级索引；② 报表层固化"本月+上月"增量计算，历史月不再重算；③ 品类维度规范化（ID与名称一一映射），避免同名多行分裂榜单；④ 门槛值可用"GMV的P90分位"动态生成，适应大盘体量变化。

### 6. 面试延伸考点

- **RANK、DENSE_RANK、ROW_NUMBER怎么选？** 要点：RANK并列同名次且跳号，DENSE_RANK并列不跳号，ROW_NUMBER强制唯一；业务汇报常用RANK，发奖与配额场景用DENSE_RANK。
- **销售额变化怎么拆成量、价、结构效应？** 要点：ΔGMV≈销量效应（基期价×销量差）+价格效应（销量×价差）+交叉项；榜单"下降"要能回答是卖得少还是卖得便宜。
- **为什么设1万元排名门槛？** 要点：长尾品类名次跳变是噪声，门槛让榜单稳定可解读；门槛用分位数动态定，避免体量变化后失效。
- **CR5/HHI集中度怎么算、看什么？** 要点：Top5品类占比合计（CR5）与平方和（HHI），监控盘子是否过度依赖头部，配合榜单判断"增长质量"。

### 7. 业务拓展思考

榜单的价值在于驱动资源再配置：上升品类加坑位与流量倾斜、招商侧补供给；下降品类先做量价拆解再定动作（是流量问题、供给问题还是价格力问题）。口径延展：把销售额换成毛利额排名，避免"卖得多亏得多"的品类霸榜；下钻二级品类观察"表面持平、内部此消彼长"的结构变化；叠加同比份额对比可排除季节性，叠加竞品数据则能输出"份额此消彼长"的竞争专题，让榜单从描述工具升级为战略仪表盘。

## EC-42 新客首单金额分层与长期留存关系

### 1. 业务背景

增长团队内部有一场持续争论：给新客的大额首单补贴，拉来的是"薅完就走"还是"高价值用户"？一派主张"首单金额高的用户留存一定更好，应该加大补贴"；另一派反驳"那是相关不是因果，可能只是数码用户天然高客单"。第一步先用数据把关系描述清楚：把2025年Q1首购的新客按首单实付金额分成 <50、50-100、100-200、200+ 四层，对比各层的30日复购留存率与90日人均累计消费，为补贴策略提供事实基础；因果验证交给后续的随机实验或断点回归。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

示例数据（数据均为虚构）：

| order_id | user_id | pay_amount | pay_status | pay_time |
| --- | --- | --- | --- | --- |
| 900001 | 9601 | 39.90 | 1 | 2025-01-05 10:00:00 |
| 900002 | 9601 | 59.00 | 1 | 2025-01-20 18:30:00 |
| 900003 | 9602 | 2599.00 | 1 | 2025-01-08 20:11:00 |
| 900004 | 9603 | 129.00 | 1 | 2025-02-01 09:05:00 |
| 900005 | 9604 | 45.00 | 0 | 2025-02-15 12:00:00 |

### 3. 解题思路

口径四件事：① 新客按"首笔支付成功订单"定义（不是按注册日期——注册很久才首购的用户也是新客，按注册定义会漏掉他们）；② 分层边界左闭右开 [50,100)，CASE 从小到大依次判断；③ 30日留存=首单后 (首单日, 首单日+30天] 内有再次支付成功订单；④ 90日人均累计消费=首单后90天内支付金额的层内均值。**【避坑指南】** 两个截断必须处理：其一，90日窗口未走完的近期首单用户必须剔除（首单日≤今天-90天），否则最近月份的层被系统性压低，分层对比直接失真；其二，每层要输出人数，小样本层的留存率不稳定，不能和大层并列解读。路径：CTE1 ROW_NUMBER 取首单；CTE2 CASE 分层并截断；CTE3 LEFT JOIN 后续订单（窗口条件写在ON里保住无复购用户）条件聚合；CTE4 按层输出。

### 4. 参考解法

**解法一：首单分层 + LEFT JOIN 窗口判定（一次关联同时算留存与LTV）**

```sql
WITH first_order AS (    -- 每用户首笔支付成功订单
    SELECT user_id, pay_amount AS first_amt, pay_time AS first_time,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY pay_time) AS rn
    FROM orders
    WHERE pay_status = 1
),
cohort AS (              -- 2025Q1首购新客，且90日观察窗已走完
    SELECT user_id, first_amt, first_time,
           CASE WHEN first_amt < 50  THEN 'A.<50'
                WHEN first_amt < 100 THEN 'B.50-100'
                WHEN first_amt < 200 THEN 'C.100-200'
                ELSE 'D.200+' END AS amt_band     -- 左闭右开，自下而上判断
    FROM first_order
    WHERE rn = 1
      AND first_time >= '2025-01-01' AND first_time < '2025-04-01'
      AND first_time <= CURDATE() - INTERVAL 90 DAY   -- 截断：窗口已满才可比
),
user_ltv AS (            -- 用户级：30日留存标记 + 90日累计消费
    SELECT c.user_id, c.amt_band,
           MAX(CASE WHEN o.pay_time >  c.first_time
                     AND o.pay_time <= c.first_time + INTERVAL 30 DAY
                    THEN 1 ELSE 0 END) AS retain_30,
           SUM(CASE WHEN o.pay_time >  c.first_time
                     AND o.pay_time <= c.first_time + INTERVAL 90 DAY
                    THEN o.pay_amount ELSE 0 END) AS ltv_90
    FROM cohort c
    LEFT JOIN orders o            -- 窗口条件必须写在ON：无复购用户保留
           ON o.user_id = c.user_id AND o.pay_status = 1
          AND o.pay_time >  c.first_time
          AND o.pay_time <= c.first_time + INTERVAL 90 DAY
    GROUP BY c.user_id, c.amt_band
)
SELECT amt_band                                   AS 首单金额分层,
       COUNT(*)                                   AS 人数,
       ROUND(AVG(retain_30) * 100, 2)             AS 三十日复购留存率,
       ROUND(AVG(ltv_90), 2)                      AS 九十日人均累计消费,
       ROUND(SUM(ltv_90) / NULLIF(SUM(retain_30), 0), 2) AS 复购用户人均贡献
FROM user_ltv
GROUP BY amt_band
ORDER BY amt_band;
```

结果解读：复购用户人均贡献列能区分"留存率高但客单低"和"留存率低但复购者豪掷"两种层型——前者适合养，后者适合精选运营；若A层留存明显低于D层但人数占比高，还要回头查A层的品类与渠道构成，防止品类混杂伪装成金额效应。

**解法二：EXISTS 双窗口判定（半连接，无JOIN膨胀）**

```sql
WITH first_order AS (    -- 同解法一
    SELECT user_id, pay_amount AS first_amt, pay_time AS first_time,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY pay_time) AS rn
    FROM orders
    WHERE pay_status = 1
),
cohort AS (              -- 同解法一（含截断）
    SELECT user_id, first_time,
           CASE WHEN first_amt < 50  THEN 'A.<50'
                WHEN first_amt < 100 THEN 'B.50-100'
                WHEN first_amt < 200 THEN 'C.100-200'
                ELSE 'D.200+' END AS amt_band
    FROM first_order
    WHERE rn = 1
      AND first_time >= '2025-01-01' AND first_time < '2025-04-01'
      AND first_time <= CURDATE() - INTERVAL 90 DAY
),
retained AS (            -- 逐人用相关子查询判两个留存窗口
    SELECT c.user_id, c.amt_band,
           EXISTS (SELECT 1 FROM orders o
                   WHERE o.user_id = c.user_id AND o.pay_status = 1
                     AND o.pay_time >  c.first_time
                     AND o.pay_time <= c.first_time + INTERVAL 30 DAY) AS retain_30,
           EXISTS (SELECT 1 FROM orders o
                   WHERE o.user_id = c.user_id AND o.pay_status = 1
                     AND o.pay_time >  c.first_time
                     AND o.pay_time <= c.first_time + INTERVAL 90 DAY) AS retain_90
    FROM cohort c
)
SELECT amt_band                       AS 首单金额分层,
       COUNT(*)                       AS 人数,
       ROUND(AVG(retain_30) * 100, 2) AS 三十日复购留存率,
       ROUND(AVG(retain_90) * 100, 2) AS 九十日复购留存率
FROM retained
GROUP BY amt_band
ORDER BY amt_band;
```

结果解读：EXISTS 命中即停，无行膨胀，配合 (user_id, pay_time) 索引每人只需两次范围探测；它拿不到金额，适合纯留存口径；与解法一的30日列互为校验，两个写法结果应完全一致，不一致说明某边口径写错（最常见是ON与WHERE里窗口条件的差别）。

> Hive/Spark SQL 差异：Hive 老版本相关子查询支持差，优先 LEFT JOIN 法；数仓按季度调度时把 cohort 层落表（按首购月分区），后续窗口判定读 cohort 表可增量更新。

### 5. 性能分析与优化

解法一 LEFT JOIN 膨胀=人均90日订单数（通常<5，可控），一次关联同时产出留存与LTV，信息/代价比最高；解法二每行两次索引探测、无膨胀，但拿不到金额。可执行优化：① orders 建 (user_id, pay_time) 复合索引是两条路径的共同前提；② 截断条件（first_time≤今天-90）前置，先缩小同期群再关联；③ cohort 与 user_ltv 落表按季刷新，看板只读结果层；④ 分层结果输出时同时给人数与占比，避免小样本层被过度解读；⑤ 若需防单品刷单干扰，可在明细层先过滤异常订单（同用户同秒多单等）。

### 6. 面试延伸考点

- **"首单金额高→留存好"能直接推导"加大补贴"吗？** 要点：不能，相关非因果；验证补贴因果用随机分流A/B，或利用满减门槛附近的断点回归（RDD），观察门槛两侧用户后续行为的跳变。
- **分层边界怎么定？** 要点：等频分层（每层人数相近便于比较）、业务断点（运费线、凑单线、支付方式门槛）、或金额分位数；关键是声明并在迭代中保持稳定。
- **高金额层留存高是不是幸存者偏差？** 要点：不是（首单已发生），但要警惕品类混杂——数码首单用户天然高客单，需层内按品类标准化或二维交叉。
- **要不要用首单品类替代金额分层？** 要点：品类与金额高度相关，二维交叉（品类×金额）信息更全；层数会爆炸，控制在6-8格内并可读。

### 7. 业务拓展思考

这组关系的业务出口是"补贴应该发给谁"：若高金额层LTV优势主要来自自然选择而非补贴拉动，预算应从"人人首单立减"转向"首单后30天流失预警用户的二次唤起"。口径延展：分层维度换成首单品类数、首单渠道或首单时段，可交叉验证"高价值新客画像"；把留存输出为90日LTV分布（P25/中位数/P75）能看层内异质性，防止均值掩盖两极；叠加uplift模型后，"该补多少"可以从分层描述变成个体决策，这是新客补贴精细化的一整条演进路线。

## EC-43 复购周期分布与购买间隔变宽（widening）预警

### 1. 业务背景

CRM团队要升级召回策略：过去用固定"60天未购"圈人，但生鲜用户20天不回来就该唤回，家电用户90天不买很正常，固定阈值既误伤活跃用户又漏掉真流失。新方案是"个体化间隔预警"：统计每个用户历史相邻购买间隔的中位数作为个人基准；当"最近一次间隔"超过个人中位数的2倍，且该用户至少有4次购买（保证中位数稳定）、最后一单距今超过3天（排除刚买用户）时，判定为"间隔变宽（widening）"疑似流失预警。输出预警名单与变宽倍数分层，供短信/Push/优惠券分级触达，相比固定阈值更精准也更省预算。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| pay_time | DATETIME | 支付时间 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

示例数据（数据均为虚构，用户9701的购买间隔为7天/7天后突变为41天）：

| order_id | user_id | pay_time | pay_status | pay_amount |
| --- | --- | --- | --- | --- |
| 110001 | 9701 | 2025-01-05 10:00:00 | 1 | 79.00 |
| 110002 | 9701 | 2025-01-12 11:00:00 | 1 | 85.00 |
| 110003 | 9701 | 2025-01-19 09:30:00 | 1 | 92.00 |
| 110004 | 9702 | 2025-01-01 20:00:00 | 1 | 2599.00 |
| 110005 | 9701 | 2025-03-01 15:00:00 | 1 | 66.00 |

### 3. 解题思路

口径：间隔=相邻两笔支付成功订单的"购买日差"（先按用户×购买日去重——同日多单会让间隔变0并污染中位数）；个体基准=该用户全部历史间隔的中位数；预警=最近间隔≥2×个人中位数 且 购买日数≥4 且 最近购买日距今>3天。**【加分点】** MySQL 8.0 没有中位数函数，用窗口法现算：对间隔序列按 ROW_NUMBER 与 COUNT(*) OVER() 定位中间位置，奇数取中间一行、偶数取中间两行平均（rk IN (FLOOR((n+1)/2), CEIL((n+1)/2)) 再 AVG）——这一步是本题的技术亮点也是高频考点。路径：CTE1 用户×购买日去重并编号；CTE2 LAG 取上一购买日算间隔（首单NULL剔除）；CTE3 窗口法算用户级中位数；CTE4 取每用户最后一行（rn=cnt）的最近间隔，关联中位数做判定输出。易错点：NULL间隔参与中位数会拉偏基准；间隔分布右偏，用均值做基准会被偶发长间隔绑架。

### 4. 参考解法

**解法一：LAG间隔 + 窗口法中位数（推荐）**

```sql
WITH user_day AS (       -- 用户×购买日 去重：同日多单只算一个购买日
    SELECT user_id, DATE(pay_time) AS pay_day
    FROM orders
    WHERE pay_status = 1
    GROUP BY user_id, DATE(pay_time)
),
seq AS (                 -- 编号与总数：rn定位最后一行，cnt做稳定性门槛
    SELECT user_id, pay_day,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY pay_day) AS rn,
           COUNT(*)     OVER (PARTITION BY user_id) AS cnt
    FROM user_day
),
gap AS (                 -- 相邻间隔（天），首单间隔为NULL
    SELECT user_id, pay_day, rn, cnt,
           DATEDIFF(pay_day,
                    LAG(pay_day) OVER (PARTITION BY user_id ORDER BY pay_day)) AS gap_days
    FROM seq
),
gap_valid AS (           -- 剔除首单NULL，防中位数被拉偏
    SELECT user_id, gap_days FROM gap WHERE gap_days IS NOT NULL
),
med AS (                 -- 间隔排序编号：定位中间行
    SELECT user_id, gap_days,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY gap_days) AS rk,
           COUNT(*)     OVER (PARTITION BY user_id) AS n
    FROM gap_valid
),
median AS (              -- 窗口法中位数：奇取中间，偶取两行平均
    SELECT user_id, AVG(gap_days) AS med_gap
    FROM med
    WHERE rk IN (FLOOR((n + 1) / 2), CEIL((n + 1) / 2))   -- 中间1~2行
    GROUP BY user_id
)
SELECT l.user_id AS 用户,
       l.pay_day AS 最近购买日,
       m.med_gap AS 个人中位间隔,
       l.gap_days AS 最近间隔,
       ROUND(l.gap_days / NULLIF(m.med_gap, 0), 2) AS 变宽倍数,
       CASE WHEN l.gap_days >= 3 * m.med_gap THEN 'P0高危'
            ELSE 'P1关注' END AS 预警分级
FROM gap l
JOIN median m USING (user_id)
WHERE l.rn = l.cnt                                   -- 只取每用户最后一行
  AND l.cnt >= 4                                     -- 至少4个购买日，中位数才稳定
  AND l.gap_days >= 2 * m.med_gap                    -- 超个人基准2倍
  AND l.pay_day < CURDATE() - INTERVAL 3 DAY         -- 排除刚买的用户
ORDER BY 变宽倍数 DESC;
```

结果解读：示例用户9701历史间隔7/7天、中位数7天，最近间隔41天=5.86倍，触发P0高危；名单按倍数分级输出，倍数越大流失概率越高，触达资源（短信/外呼/大额券）随之升级，实现"个体化阈值"替代一刀切。

**解法二：自连接"相邻对"匹配法（不依赖LAG的老写法）**

```sql
WITH paid AS (           -- 支付成功的购买日
    SELECT DISTINCT user_id, DATE(pay_time) AS pay_day
    FROM orders
    WHERE pay_status = 1
),
pair AS (                -- 自连接找相邻对：o2必须是o1的"下一单"
    SELECT o1.user_id, o1.pay_day AS d1, o2.pay_day AS d2,
           DATEDIFF(o2.pay_day, o1.pay_day) AS gap_days
    FROM paid o1
    JOIN paid o2
      ON o2.user_id = o1.user_id
     AND o2.pay_day > o1.pay_day
    WHERE NOT EXISTS (SELECT 1 FROM paid o3          -- 中间不能有其他购买日
                      WHERE o3.user_id = o1.user_id
                        AND o3.pay_day > o1.pay_day
                        AND o3.pay_day < o2.pay_day)
),
median AS (              -- 同解法一的窗口中位数
    SELECT user_id, AVG(gap_days) AS med_gap
    FROM (SELECT user_id, gap_days,
                 ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY gap_days) AS rk,
                 COUNT(*)     OVER (PARTITION BY user_id) AS n
          FROM pair) t
    WHERE rk IN (FLOOR((n + 1) / 2), CEIL((n + 1) / 2))
    GROUP BY user_id
),
mx AS (                  -- 每用户最近一次购买日
    SELECT user_id, MAX(d2) AS last_day
    FROM pair
    GROUP BY user_id
)
SELECT p.user_id AS 用户,
       m.med_gap AS 个人中位间隔,
       p.gap_days AS 最近间隔,
       ROUND(p.gap_days / NULLIF(m.med_gap, 0), 2) AS 变宽倍数
FROM pair p
JOIN mx   ON mx.user_id = p.user_id AND p.d2 = mx.last_day   -- 取最近一对
JOIN median m USING (user_id)
WHERE p.gap_days >= 2 * m.med_gap
ORDER BY 变宽倍数 DESC;
```

结果解读：NOT EXISTS 把自连接限定在真正相邻的对上——漏掉它会让中间隔多单的"远亲对"混入中位数计算，基准直接失真；该写法直观但代价高，适合中小数据量或已按用户分桶的表，理解它有助于讲清 LAG 到底省了什么。

> Hive/Spark SQL 差异：Hive 自带 percentile/percentile_approx，可直接算中位数省去窗口法；LAG 与去重逻辑一致；亿级订单先按 pay_time 分区裁剪近18个月，并按 user_id 分桶让相邻对计算本地化。

### 5. 性能分析与优化

解法一是两次窗口排序（同分区键可被引擎合并）加分组聚合，O(n log n)，无膨胀，推荐；解法二自连接在"大户用户订单多"时退化到接近平方级，NOT EXISTS 相关子查询进一步放大，必须依赖 (user_id, pay_day) 索引把匹配压到邻域。可执行优化：① orders 建 (user_id, pay_time) 复合索引或按用户分桶；② 历史间隔与中位数离线预计算落 dws_user_purchase_gap 表（按月增量），线上只算"最近间隔"并join基准表；③ pay_time 分区裁剪近18个月（购买周期超过一年的品类单独处理）；④ 输出层只保留预警名单，结果表直接对接触达系统。

### 6. 面试延伸考点

- **中位数和均值选哪个做基准？** 要点：间隔分布右偏，均值被偶发长间隔拉偏，中位数稳健；阈值倍数也应基于中位数而非均值定义。
- **新客没有历史间隔怎么办（冷启动）？** 要点：用全站或同品类P90兜底，积累≥3个间隔后切换个人基准；分层冷启动比全局阈值保留个性化。
- **怎么验证预警名单真的会流失？** 要点：回测——在历史时点跑规则，对比被预警与未预警用户的实际30天流失率，算精准率/召回率并调整倍数阈值。
- **间隔按订单还是按购买日算？** 要点：同日多单会把间隔压成0并破坏中位数，按购买日去重更贴近"回访节奏"；高频品类尤其要处理。

### 7. 业务拓展思考

名单接入触达系统做分级召回（2-3倍发Push、3倍以上配券或外呼），并跟踪触达后的"回归率"形成规则迭代闭环。口径延展：按"品类×用户"计算基准（用户买生鲜与家电节奏不同，混合基准会失真），或按品类加权得到综合节奏；进一步用生存分析（Cox/KM）输出个体流失概率替代固定倍数，把规则预警升级为模型预警；反向地，"间隔收窄"人群（recently tightening）是加购高潜，可主动推关联品类，让同一张间隔表同时服务挽留与增购。

## EC-44 同SKU多渠道价格一致性核查与异常价识别

### 1. 业务背景

价格风控同学在大促前要做价格一致性体检：同一SKU会同时在App主站、小程序、外部比价平台三个渠道售卖，因活动节奏与优惠叠加不同出现价差。过大的价差有两个风险——高价渠道的用户比价后流失、低价渠道可能是错价或优惠叠加导致资损漏洞。任务：对指定核查日（2025-06-18），找出全量在售SKU中"多渠道价格极差率超过10%"的清单，标明最高价与最低价所在渠道，交由价格运营在活动开始前修正。核查同时输出"疑似错价"（异常低价）与"转化杀手"（异常高价）两类标签，方便分派给不同处理流程。

### 2. 表结构说明

sku_price（价格快照表，每日定时抓取各渠道在售价）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sku_id | BIGINT | SKU ID |
| channel | VARCHAR(20) | 渠道：app/mini/compare（比价平台） |
| price | DECIMAL(10,2) | 抓取到的在售价 |
| collect_time | DATETIME | 快照抓取时间 |
| is_active | TINYINT | 1=在售，0=已下架 |

示例数据（数据均为虚构，12002存在0.01元疑似错价、12003在mini渠道已下架）：

| sku_id | channel | price | collect_time | is_active |
| --- | --- | --- | --- | --- |
| 12001 | app | 199.00 | 2025-06-18 08:00:00 | 1 |
| 12001 | mini | 199.00 | 2025-06-18 08:00:05 | 1 |
| 12001 | compare | 259.00 | 2025-06-18 08:01:00 | 1 |
| 12002 | app | 0.01 | 2025-06-18 08:00:00 | 1 |
| 12003 | mini | 45.90 | 2025-06-18 08:00:10 | 0 |

### 3. 解题思路

口径：以核查日内每渠道"最新一次快照"为准——同渠道一天多次变价取最新而非平均，平均值不代表任何真实时刻的可购价格；只统计 is_active=1 的在售快照（下架渠道的价格会制造假价差）；极差率=(渠道最高价−最低价)/最低价，超过10%标记异常；脏数据先清洗（price≤0 的错价抓取剔除或单列）。路径：CTE1 按"SKU×渠道"用 ROW_NUMBER 取核查日最新在售快照；CTE2 剔除0价脏数据；CTE3 按SKU聚合 MIN/MAX 与极差率（NULLIF 防除零，HAVING 渠道数≥2）；CTE4 用窗口极值把最高/最低价所在渠道带出（**【加分点】**：CASE WHEN price=MAX(price) OVER(PARTITION BY sku) 的归因写法，比再关联一次更简洁）。易错点：并列极值渠道取哪个需定规则；错价与活动价靠活动备案白名单区分，SQL负责圈嫌疑名单。

### 4. 参考解法

**解法一：最新快照 + 分组极差率 + 窗口极值归因（推荐）**

```sql
WITH latest AS (         -- 每SKU×渠道当日最新在售快照
    SELECT sku_id, channel, price,
           ROW_NUMBER() OVER (PARTITION BY sku_id, channel
                              ORDER BY collect_time DESC) AS rn
    FROM sku_price
    WHERE collect_time >= '2025-06-18' AND collect_time < '2025-06-19'
      AND is_active = 1                                 -- 只看在售
),
clean AS (               -- 清洗：取最新一行且剔除0价脏数据
    SELECT sku_id, channel, price
    FROM latest
    WHERE rn = 1 AND price > 0
),
agg AS (                 -- SKU级聚合极值与渠道数
    SELECT sku_id,
           MIN(price) AS min_price,
           MAX(price) AS max_price,
           COUNT(DISTINCT channel) AS chn_cnt
    FROM clean
    GROUP BY sku_id
    HAVING COUNT(DISTINCT channel) >= 2                 -- 单渠道无从谈价差
),
marked AS (              -- 极差率与异常判定
    SELECT sku_id, min_price, max_price,
           ROUND((max_price - min_price) / NULLIF(min_price, 0) * 100, 2) AS diff_rate
    FROM agg
),
attr AS (                -- 窗口极值归因：标出极值所在渠道
    SELECT sku_id, channel, price,
           CASE WHEN price = MAX(price) OVER (PARTITION BY sku_id)
                THEN channel END AS max_channel,
           CASE WHEN price = MIN(price) OVER (PARTITION BY sku_id)
                THEN channel END AS min_channel
    FROM clean
)
SELECT m.sku_id AS SKU,
       m.min_price AS 最低价, MAX(a.min_channel) AS 最低价渠道,
       m.max_price AS 最高价, MAX(a.max_channel) AS 最高价渠道,
       m.diff_rate AS 极差率,
       CASE WHEN m.diff_rate > 10 THEN '异常' ELSE '正常' END AS 核查结论
FROM marked m
JOIN attr a ON a.sku_id = m.sku_id
WHERE m.diff_rate > 10
GROUP BY m.sku_id, m.min_price, m.max_price, m.diff_rate
ORDER BY m.diff_rate DESC;
```

结果解读：SKU 12001 极差率30.15%（199 vs 259），compare渠道高价侧，提示比价平台价格未同步活动价；MAX(a.min_channel) 在并列极值时按字典序取一个，业务上应再对齐活动备案表定责；异常清单按极差率倒序，优先处理资损风险最大的低价侧。

**解法二：自连接配对比较（定位到具体"渠道对"，粒度更细）**

```sql
WITH latest AS (         -- 同解法一：最新在售快照
    SELECT sku_id, channel, price,
           ROW_NUMBER() OVER (PARTITION BY sku_id, channel
                              ORDER BY collect_time DESC) AS rn
    FROM sku_price
    WHERE collect_time >= '2025-06-18' AND collect_time < '2025-06-19'
      AND is_active = 1
),
clean AS (SELECT sku_id, channel, price FROM latest WHERE rn = 1 AND price > 0),
pair AS (                -- 同SKU两两渠道配对：channel字典序防重复对与自配对
    SELECT a.sku_id,
           a.channel AS chn_a, a.price AS price_a,
           b.channel AS chn_b, b.price AS price_b
    FROM clean a
    JOIN clean b
      ON a.sku_id = b.sku_id
     AND a.channel < b.channel
)
SELECT sku_id AS SKU,
       chn_a AS 渠道A, price_a AS 价格A,
       chn_b AS 渠道B, price_b AS 价格B,
       ROUND(ABS(price_a - price_b)
             / NULLIF(LEAST(price_a, price_b), 0) * 100, 2) AS 两渠道差率
FROM pair
WHERE ABS(price_a - price_b) > 0.1 * LEAST(price_a, price_b)
ORDER BY 两渠道差率 DESC;
```

结果解读：配对视角能回答"谁和谁差多少"，直接指派给对应两个渠道的运营核对配置；同一SKU三渠道会输出三对，报告层可再按SKU聚合取最大差率对；它是解法一"SKU级结论"的明细层补充，两者配合使用。

> Hive/Spark SQL 差异：快照表按 collect_time 分区裁剪单日；ROW_NUMBER 与配对自连接写法一致；SKU 数千万级时先过滤"渠道数≥2的SKU"再配对，Spark 下可广播清洗后的小表。

### 5. 性能分析与优化

核查日单日分区扫描是第一优化（collect_time 分区裁剪）；ROW_NUMBER 按 (sku_id, channel) 分区排序，需要 (sku_id, channel, collect_time) 复合索引；解法二的自连接在"渠道数≥2的SKU"上做，先用 HAVING 预聚合收敛再配对可减少一半连接。可执行优化：① 快照抓取失败产生 NULL/0 价格提前剔除，避免极差率被脏数据拉爆；② 大促核查可扩为"近7天每日各跑一次"的增量模式，只对新变价SKU复查；③ 活动备案白名单表 JOIN 后打"合规活动价"标记，减少人工复核量；④ 输出直接写监控告警表，对接企微/钉钉机器人工单闭环。

### 6. 面试延伸考点

- **为什么锚点用最低价而不是均值？** 要点：最低价是用户比价的心理锚点，极差率以最低价为分母最贴近流失风险；均值会被极端值拉动，中位数适合做参考锚。
- **活动价和错价怎么区分？** 要点：对照活动备案表（白名单内差价=合规活动），白名单外才算异常；错价常伴随渠道配置时间差，可用配置流水交叉定位。
- **到手价和划线价用哪个口径？** 要点：用户感知的是券后到手价，风控应以到手价为主、划线价为辅，防止"标价一致、叠加券不同"的漏洞漏检。
- **如何从"事后发现"走向"事前预防"？** 要点：价格发布链路加"跨渠道最低到手价防线"，配置时实时校验差率阈值，超标拦截而非事后追责。

### 7. 业务拓展思考

该核查固化为每日价格巡检看板+告警，联动渠道运营工单形成"发现-指派-修正-复核"闭环；口径延展：加入运费后的成交价口径更贴近用户实付；会员价/学生价分层核查可发现"特权价外溢"漏洞；历史价格曲线监控能识别"先涨后降"的虚假促销（合规风险）；与竞品比价结合可输出价格竞争力指数，让价格风控从"堵漏洞"升级为"定价策略参谋"。

## EC-45 大促透支分析：大促后30天GMV对比大促前基线

### 1. 业务背景

双11结束后一周，CEO在经营会上问：**这次大促是不是把后面的生意都透支了？**经营分析需要给出量化回答：以大促开始前30天（剔除预热期）的日均GMV为基线，对比大促结束后30天的日均GMV，计算"透支系数"（后30天日均/前30天日均−1）；再按品类拆分，区分"囤货型透支"（纸品日化大促后断崖）与"真实增量"（新品类平稳抬升）；最后输出"逐日恢复曲线"——大促结束后第几天GMV回到基线的95%以上，为明年大促节奏、返场活动与客服退换货资源排期提供依据。

### 2. 表结构说明

orders（订单表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| category | VARCHAR(30) | 品类 |
| pay_amount | DECIMAL(12,2) | 实付金额 |
| pay_status | TINYINT | 1=支付成功，0=未支付 |
| pay_time | DATETIME | 支付时间 |

promo_calendar（大促日历维表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| promo_id | VARCHAR(10) | 档期ID |
| promo_name | VARCHAR(50) | 档期名称 |
| start_date | DATE | 开始日期 |
| end_date | DATE | 结束日期 |

示例数据（数据均为虚构）：

| order_id | user_id | category | pay_amount | pay_status | pay_time |
| --- | --- | --- | --- | --- | --- |
| 130001 | 9801 | 美妆 | 259.00 | 1 | 2025-11-11 00:05:00 |
| 130002 | 9802 | 纸品日化 | 89.00 | 1 | 2025-11-11 08:30:00 |
| 130003 | 9803 | 数码 | 3999.00 | 1 | 2025-11-11 21:10:00 |
| 130004 | 9801 | 食品 | 45.00 | 0 | 2025-11-12 10:00:00 |
| 130005 | 9804 | 美妆 | 129.00 | 1 | 2025-11-20 12:20:00 |

| promo_id | promo_name | start_date | end_date |
| --- | --- | --- | --- |
| P001 | 2025双11 | 2025-11-11 | 2025-11-12 |
| P002 | 2025双12 | 2025-12-12 | 2025-12-12 |
| P003 | 2025 618 | 2025-06-18 | 2025-06-18 |

### 3. 解题思路

口径：基线=大促开始前30个自然日的日均GMV（本例10月无大促，不需剔除上一个档期尾巴；若基线期含上一次大促要剔除）；透支窗口=结束后第1~30天；透支系数=后30天日均/前30天日均−1，负值为透支；大促当天及结束日属于"中"不属于"后"。**【加分点】** 更严谨的口径要剔除自然增长趋势：用更早30天（大促前31~60天）估算日均增长斜率，把基线外推到大促后窗口再比较——否则增长期平台会把"正常波动"误判为"透支"，本质是简化DID思想。恢复曲线用固定基线逐日算 GMV/基线比值，取首个≥95%的日期。易错点：**【避坑指南】** 边界必须写死并对齐数仓口径（差一天结论可能反转）；恢复窗若与下一个大促重叠（本例第30天恰是双12）要剔除该日或缩短窗口，否则"恢复"是假象。

### 4. 参考解法

**解法一：档期级三窗口对比（前/中/后打标）**

```sql
WITH promo AS (          -- 档期（单行）
    SELECT start_date, end_date
    FROM promo_calendar
    WHERE promo_name = '2025双11'
),
daily AS (               -- 覆盖"前30天~后30天"的逐日GMV
    SELECT DATE(pay_time) AS d, SUM(pay_amount) AS gmv
    FROM orders
    WHERE pay_status = 1
      AND pay_time >= (SELECT start_date - INTERVAL 30 DAY FROM promo)   -- 基线起点
      AND pay_time <  (SELECT end_date + INTERVAL 31 DAY FROM promo)     -- 恢复窗终点
    GROUP BY DATE(pay_time)
),
tagged AS (              -- 三窗口打标：大促日属于promo，不属于post
    SELECT d.d, d.gmv,
           CASE WHEN d.d <  p.start_date THEN 'pre'
                WHEN d.d <= p.end_date  THEN 'promo'
                ELSE 'post' END AS period_tag
    FROM daily d CROSS JOIN promo p
),
base AS (                -- 前30天基线与后30天日均
    SELECT SUM(CASE WHEN period_tag = 'pre'  THEN gmv ELSE 0 END) / 30.0 AS pre_avg,
           SUM(CASE WHEN period_tag = 'post' THEN gmv ELSE 0 END) / 30.0 AS post_avg
    FROM tagged
)
SELECT ROUND(pre_avg, 0) AS 大促前30天日均,
       ROUND(post_avg, 0) AS 大促后30天日均,
       ROUND((post_avg / NULLIF(pre_avg, 0) - 1) * 100, 2) AS 透支系数,
       CASE WHEN post_avg < pre_avg * 0.95 THEN '明显透支'
            WHEN post_avg < pre_avg       THEN '轻度透支'
            ELSE '无透支' END AS 结论
FROM base;
-- 品类级拆解：daily先按 日×品类 聚合，base再按品类分别算两个窗口，口径完全一致
```

结果解读：透支系数-15%意味着大促后30天日均比大促前低15%，结合品类拆分看是"纸品日化断崖"还是全面回落——前者是囤货透支（正常），后者才是需要警惕的需求透支；分母30.0假设基线期与恢复期都完整30天，缺日数据要先补日历。

**解法二：逐日恢复曲线（固定基线+首个恢复日定位）**

```sql
WITH promo AS (          -- 同解法一
    SELECT start_date, end_date FROM promo_calendar WHERE promo_name = '2025双11'
),
daily AS (               -- 覆盖前30天到后45天的逐日GMV（恢复窗可看更远）
    SELECT DATE(pay_time) AS d, SUM(pay_amount) AS gmv
    FROM orders
    WHERE pay_status = 1
      AND pay_time >= (SELECT start_date - INTERVAL 30 DAY FROM promo)
      AND pay_time <  (SELECT end_date + INTERVAL 45 DAY FROM promo)
    GROUP BY DATE(pay_time)
),
base AS (                -- 固定基线：大促开始前30天日均
    SELECT SUM(gmv) / 30.0 AS pre_avg
    FROM daily
    WHERE d >= (SELECT start_date FROM promo) - INTERVAL 30 DAY
      AND d <  (SELECT start_date FROM promo)
),
post AS (                -- 大促后逐日：相对基线百分比与恢复标记
    SELECT d.d, d.gmv,
           ROUND(d.gmv / NULLIF(b.pre_avg, 0) * 100, 2) AS pct_of_base,
           CASE WHEN d.gmv >= b.pre_avg * 0.95 THEN 1 ELSE 0 END AS recovered
    FROM daily d CROSS JOIN base b
    WHERE d.d > (SELECT end_date FROM promo)
      AND d.d <= (SELECT end_date FROM promo) + INTERVAL 30 DAY
)
SELECT MIN(CASE WHEN recovered = 1 THEN d END) AS 首次回到基线95的日期,
       DATEDIFF(MIN(CASE WHEN recovered = 1 THEN d END),
                (SELECT end_date FROM promo))    AS 恢复天数,
       ROUND(AVG(gmv) / NULLIF((SELECT pre_avg FROM base), 0) * 100, 2) AS 后30天相对基线
FROM post;
```

结果解读：pct_of_base 逐日输出即恢复曲线——第1~5天通常深谷（快递消化+需求真空），首次≥95%的天数是"恢复天数"核心KPI；若30天内始终未恢复到95%，透支结论成立，返场与内容营销要提前布置；曲线若被双12抬升，要剔除该日重算。

> Hive/Spark SQL 差异：档期维表小表广播；pay_time 分区裁剪两个窗口；数仓标准做法是先落 dws_sales_1d（日×品类GMV）再跑本逻辑，查询退化为百行级计算；日期运算用 date_sub/add_days。

### 5. 性能分析与优化

查询窗口约2~3个月订单，按 pay_time 分区裁剪"基线窗+恢复窗"两段即可，无需全表；解法二扫描范围更长（前30到后45天）但换来恢复曲线。可执行优化：① 预聚合"日×品类GMV"表（dws_sales_1d）是大促复盘的标准前置，本查询只读聚合层；② promo_calendar 小表 CROSS JOIN 无代价，多档期批量分析时按档期循环或 GROUP BY 档期一次算完；③ orders (pay_time) 索引或按月分区均可加速明细版；④ 恢复阈值95%与窗口30天参数化，便于敏感性分析（90%/95%/100%三档结论并列展示）。

### 6. 面试延伸考点

- **透支系数为负就一定是坏事吗？** 要点：要先剔除增长趋势与季节（12月有双12），对比去年同期透支系数才有意义；新品类的回落可能是尝鲜回流而非透支。
- **怎么区分"透支"与"需求前置"？** 要点：看大促新客的后续留存（新客结构变化）与囤货品类的消耗周期（纸品30天vs家电一年），消耗周期长的品类"断崖"是正常前置。
- **基线要不要剔除预热期？** 要点：预热期GMV已含定金膨胀，计入基线会抬高基线、放大透支假象；预热期应单列或从基线剔除。
- **用户级透支怎么做？** 要点：对比"大促购买用户vs非大促用户"的后30天人均GMV变化（DID），比大盘口径更能定位透支发生在哪类人群。

### 7. 业务拓展思考

透支结论直接影响经营节奏：透支明显的品类次年缩减大促资源转做日销，恢复慢的品类提前布置返场与内容营销，客服与退换货资源按恢复曲线排班。口径延展：按"首购是否发生在档期"拆新老客透支，识别"大促只薅新人羊毛"的结构问题；按价格带拆（低价囤货vs高价耐用）能解释透支的消费逻辑；把基线升级为"趋势外推基线"或"去年同期基线"输出多口径透支系数，让结论经得起CEO的连环追问——这是高级篇收官题最想考察的口径严谨性。
