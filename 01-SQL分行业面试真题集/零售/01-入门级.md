## RET-01 各门店近7天的日销售额与进店客流

### 1. 业务背景

连锁便利店区域运营经理每周一早会要复盘上周经营情况（谁、何时）：他需要拿到每家门店近7天"每天销售额多少、每天进店客流多少"的对照数据（什么数据结论），用来判断销售额下滑的门店到底是"没人进店"（客流问题）还是"进店不买"（转化/客单问题），进而决定是否调整门店排班、补货优先级或发起拉新活动（为什么）。销售额来自POS小票明细表sales，客流来自门店入口感知设备汇总的日报表store_traffic，两张表来源不同、粒度不同，必须按"门店+日期"对齐后一起呈现。

### 3. 解题思路

先定口径：销售额只统计正向销售（is_return='N'），不含退货；客流按进店人次计；输出粒度为"门店×日"。实现路径分三步：第一步把sales按store_id+sale_date做SUM聚合得到日销售额；第二步把store_traffic按同样粒度对齐（若它本身已是日粒度可直接使用）；第三步两表LEFT JOIN，以销售结果为主表，保证"有销售、无客流记录"的日期不丢行，客流缺失用IFNULL补0，最后连stores补门店名称便于阅读。**【避坑指南】** 连接键必须是"门店+日期"双键，只按门店连接会让所有日期都对上同一天的客流；若选择"明细先连客流再聚合"（写法二），必须确认客流表在门店+日期上唯一，否则销售额会被放大数倍（扇出事故）。日期边界建议写成"大于等于起点且小于终点"，避免BETWEEN在含时间的字段上产生歧义。

### 4. 参考解法

**写法一：先各自聚合，再按"门店+日期"连接（口径清晰，推荐）**

```sql
-- 写法一：先分别聚合销售与客流，再按“门店+日期”双键连接
SELECT
    s.store_id,                                -- 门店ID
    st.store_name,                             -- 门店名称（来自门店主数据）
    s.sale_date,                               -- 日期
    s.sales_amount,                            -- 当日销售额（元）
    IFNULL(t.enter_count, 0) AS enter_count    -- 当日进店客流，无记录补0
FROM (
    -- 第一步：小票明细按 门店+日期 聚合出日销售额
    SELECT
        store_id,
        sale_date,
        SUM(sale_amount) AS sales_amount       -- 该门店当日的销售金额合计
    FROM sales
    WHERE sale_date >= '2024-05-27'            -- 近7天起点（含）
      AND sale_date <  '2024-06-03'            -- 近7天终点（不含），共7天
      AND is_return  = 'N'                     -- 只算正向销售，剔除退货行
    GROUP BY store_id, sale_date               -- 聚合粒度：门店×日
) AS s
LEFT JOIN stores AS st                         -- 连门店表补名称
       ON st.store_id = s.store_id
LEFT JOIN (
    -- 第二步：客流表按 门店+日期 聚合（若已是日粒度可省略此步聚合）
    SELECT
        store_id,
        stat_date,
        SUM(enter_count) AS enter_count        -- 当日进店人次合计
    FROM store_traffic
    WHERE stat_date >= '2024-05-27'
      AND stat_date <  '2024-06-03'
    GROUP BY store_id, stat_date
) AS t ON t.store_id   = s.store_id            -- 双键对齐之一：门店
       AND t.stat_date = s.sale_date           -- 双键对齐之二：日期
ORDER BY s.store_id, s.sale_date;              -- 先门店后日期，便于逐店阅读
```

结果解读：每个门店每天一行，销售额与客流并排可看；某天客流缺失时显示0而不是NULL，报表不会出现空值。若某门店某天整店无小票，该行不会出现（销售侧驱动），需要完整日历时应另补日期维度表。

**写法二：明细直接左连客流表，一次聚合出全部指标（写法更短）**

```sql
-- 写法二：明细粒度先关联客流，再一次聚合
SELECT
    sa.store_id,                                      -- 门店ID
    sa.sale_date,                                     -- 日期
    ROUND(SUM(sa.sale_amount), 2) AS sales_amount,    -- 当日销售额
    MAX(IFNULL(tf.enter_count, 0)) AS enter_count     -- 同店同日客流值相同，用MAX(或MIN)带出
FROM sales AS sa
LEFT JOIN store_traffic AS tf                          -- 明细多行命中同一条客流记录
       ON tf.store_id  = sa.store_id
      AND tf.stat_date = sa.sale_date
WHERE sa.sale_date >= '2024-05-27'
  AND sa.sale_date <  '2024-06-03'
  AND sa.is_return  = 'N'
GROUP BY sa.store_id, sa.sale_date                     -- 聚合到 门店×日
ORDER BY sa.store_id, sa.sale_date;
```

结果解读：**【避坑指南】** 这种"明细连汇总表再聚合"的写法成立的前提，是store_traffic在（store_id, stat_date）上唯一——如果客流按小时存了多条，SUM(sale_amount)会被放大数倍，这就是经典的JOIN扇出事故；拿不准粒度时优先用写法一。

### 5. 性能分析与优化

写法一需要两次聚合、两次JOIN，多一次中间结果物化，但每一步逻辑独立、可分别核对，且JOIN发生在已收缩的小结果集上；写法二只扫一遍明细，SQL更短，但JOIN发生在明细层，每行小票都要对客流表做一次探测，明细行数越大代价越高。优化建议：其一，给sales建复合索引 (sale_date, store_id, is_return)，让日期过滤走索引范围扫描；其二，把store_traffic的(store_id, stat_date)建成唯一键，既是正确性保障也是索引；其三，长期方案是T+1调度生成日汇总表 dws_store_sales_daily(store_id, sale_date, sales_amount, receipt_cnt)，报表直接读汇总表，把查询从"亿级明细"降到"万级汇总"。

### 6. 面试延伸考点

- **追问：为什么用LEFT JOIN而不是INNER JOIN？** 回答要点：以销售侧为主表，保证有销售但无客流记录的日期不丢行；INNER JOIN会静默丢数据；报表口径讲究"宁补0、不丢行"，缺失值用IFNULL兜底并标注数据来源异常。
- **追问：如果客流表同一门店同一天有多条记录（如按小时存储），写法二会出什么问题？** 回答要点：JOIN后明细行数膨胀（扇出），SUM(sale_amount)翻倍；正确做法是先把客流聚合到门店×日粒度再连接，即"先对齐粒度、再JOIN"。
- **追问：销售额口径要不要含退货？** 回答要点：看分析目的——经营复盘通常"正销售"与"净销售"双口径并行，净销售=正销售+退货（负数直接SUM）；本题取正销售口径，面试时要主动声明。

### 7. 业务拓展思考

"销售额=客流×进店转化率×客单价"是零售运营的基本漏斗模型，本题为该模型提供了前两个原料：客流来自感知设备、销售额来自POS。拿到结果后，运营可以对"客流高但销售低"的门店做陈列与动线优化、试吃试用等转化动作，对"客流持续走低"的门店投入地推、社群与外卖平台引流；采购侧可联动把爆款商品优先补给高客流门店。口径上还可延展出"进店转化率=小票数/客流""坪效=销售额/营业面积"，分别对应RET-02与门店经营分析题。

## RET-02 计算每天的小票数与客单价

### 1. 业务背景

门店店长每天早上要看昨天的日报（谁、何时）：小票数代表"一天做了多少单生意"，客单价代表"一单平均花多少钱"（什么数据结论）。两者结合才能判断生意变好还是变坏——小票数涨但客单价跌，可能是引流品拉动；客单价涨但小票数跌，可能是少数大单撑起来。店长依据这两个指标调整促销商品组合、堆头陈列和连带推荐话术（为什么）。这两个指标都来自POS小票明细表sales，按天汇总即可。

### 2. 表结构说明

**销售小票明细表 sales**（同RET-01，口径不变：一张小票多行商品共用receipt_no，退货行sale_amount为负且is_return='Y'）

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | BIGINT | 流水行ID，主键 |
| receipt_no | VARCHAR(20) | 小票号 |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| member_id | BIGINT | 会员ID，非会员为NULL |
| staff_id | INT | 收银员工号 |
| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |
| is_return | CHAR(1) | 是否退货行：Y/N |

| 20001 | R20240601S001 | 1 | 3001 | M10023 | 12 | 2024-06-01 | 09:15:00 | 2 | 3.50 | 7.00 | N |
| 20002 | R20240601S001 | 1 | 3105 | M10023 | 12 | 2024-06-01 | 09:15:00 | 1 | 12.80 | 12.80 | N |
| 20003 | R20240601S002 | 1 | 4502 | NULL | 15 | 2024-06-01 | 12:30:00 | 1 | 25.00 | 25.00 | N |
| 20004 | R20240601S003 | 1 | 6108 | NULL | 15 | 2024-06-01 | 18:40:00 | 1 | 0.00 | 0.00 | N |
| 20005 | R20240601S004 | 1 | 5201 | M10188 | 12 | 2024-06-01 | 19:20:00 | 1 | 35.00 | 35.00 | N |

（sale_id=20004为0元赠品行，本题口径中要剔除，否则拉低客单价。）

### 3. 解题思路

先定口径：客单价=期间销售额÷期间小票数；小票数按receipt_no去重（一张小票无论几行商品只算1单）；统计区间取一周便于观察趋势；只算正向销售且剔除0元赠品行。实现路径：按sale_date分组，用COUNT(DISTINCT receipt_no)数小票、SUM(sale_amount)算销售额，两者相除即客单价。写法二换一种思路：先把明细"卷"到小票级（每张小票一行、一个金额），再对小票金额求AVG，数学上与写法一等价，但中间层还能顺带看小票金额分布。**【避坑指南】** 最大陷阱是把COUNT(receipt_no)写成不去重的COUNT(*)——那是商品行数（件数）不是小票数，客单价会被算成"件单价"，结果直接错档；另外分子分母必须来自同一套过滤条件，否则账对不上。

### 4. 参考解法

**写法一：一次聚合直接算出小票数、销售额与客单价（推荐）**

```sql
-- 写法一：按天分组，去重数小票、求和算销售额，相除得客单价
SELECT
    sale_date,                                            -- 日期
    COUNT(DISTINCT receipt_no)           AS receipt_cnt,  -- 去重小票数（一张小票多行只算1）
    ROUND(SUM(sale_amount), 2)           AS sales_amount, -- 当日销售额
    ROUND(SUM(sale_amount) / COUNT(DISTINCT receipt_no), 2) AS avg_ticket -- 客单价=销售额/小票数
FROM sales
WHERE sale_date >= '2024-06-01'
  AND sale_date <  '2024-06-08'       -- 统计一周
  AND is_return   = 'N'               -- 正向销售口径
  AND sale_amount > 0                 -- 剔除0元赠品行，避免拉低客单价
GROUP BY sale_date                    -- 按天分组
ORDER BY sale_date;                   -- 按日期升序看趋势
```

结果解读：每行一天三个指标，客单价波动大的一天通常对应促销或大单；业务上更关心客单价与小票数的同向/反向关系，而非单点数值。

**写法二：先把明细卷到小票级，再对小票金额求平均**

```sql
-- 写法二：两段式——先小票级汇总，再按天对小额求均值
SELECT
    t.sale_date,                                     -- 日期
    COUNT(*)                     AS receipt_cnt,     -- 中间层每行就是一张小票，直接计数
    ROUND(AVG(t.receipt_amount), 2) AS avg_ticket,   -- 小票金额均值=客单价
    ROUND(SUM(t.receipt_amount), 2) AS sales_amount  -- 二次校验：合计应与写法一完全一致
FROM (
    -- 子查询：按 小票号 汇总出每张小票的金额
    SELECT
        sale_date,
        receipt_no,
        SUM(sale_amount) AS receipt_amount           -- 单张小票金额
    FROM sales
    WHERE sale_date >= '2024-06-01'
      AND sale_date <  '2024-06-08'
      AND is_return   = 'N'
      AND sale_amount > 0
    GROUP BY sale_date, receipt_no                   -- 小票级粒度
) AS t
GROUP BY t.sale_date                                 -- 再按天聚合
ORDER BY t.sale_date;
```

结果解读：两种写法结果应完全一致，可互相验证；写法二的小票级中间层是"小票宽表"的雏形，能继续算最高单笔、金额分位数等分布指标。

### 5. 性能分析与优化

写法一一次扫描明细，代价主要在COUNT(DISTINCT receipt_no)——去重需要内存或临时表保存已见小票号，小票量极大时开销上升；写法二扫描两遍并物化一次中间结果，但COUNT(*)与AVG都是流式聚合，单步更便宜。数据量千万级以内两者差异不大。优化建议：给sales建索引 (sale_date, is_return, receipt_no)或按sale_date分区，让一周数据剪枝到单个分区；若日报每天固定跑，把"小票级汇总"固化成日增量的中间表（每日只算当天新小票），历史天数直接累加，避免每天全量重算；小票号设计成含日期前缀（如R20240601S001）有利于分区裁剪与去重排序。

### 6. 面试延伸考点

- **追问：客单价为什么常用"销售额/小票数"，和小票金额的平均值是一回事吗？** 回答要点：数学上等价（总额÷票数=单票均值），但前提是分子分母来自同一过滤集合；若0元票只在一侧被剔除，两种算法结果就分叉，所以口径必须成对声明。
- **追问：客单价和件单价有什么区别？** 回答要点：件单价=销售额/商品件数，客单价=销售额/小票数；两者相除可得连带率（每单件数），连带率才是衡量陈列与推荐效果的核心。
- **追问：某天客单价突然翻倍，你怎么排查？** 回答要点：先看是否团购/大宗采购大单拉动（看Top小票），再看是否系统口径变化（如赠品行是否入账），最后看是否正常消费结构变化；用分位数比用均值更抗极端值。
- **追问：COUNT(DISTINCT)在超大数据量下有什么问题？** 回答要点：需维护去重集合，内存与shuffle开销大；可预聚合到小票级、或用近似计数（如HyperLogLog思路）换取速度。

### 7. 业务拓展思考

客单价是衡量门店商品结构与连带销售能力的核心KPI：便利店通过"饭团+饮料"组合、商超通过"满减凑单"拉客单，效果都直接反映在这张日报上。把客单价按会员/非会员拆开（利用member_id是否为NULL），可以评估会员权益是否真的拉高了会员钱包份额；再按时段拆开（呼应RET-06），能定位"早高峰票多客单低、晚市票少客单高"之类的结构性问题，指导分时段促销。口径延展上，剔除赠品与员工购物小票是零售日报的标准动作，面试时主动提出会明显加分。

## RET-03 各门店会员消费金额占比

### 1. 业务背景

连锁超市的会员运营岗每月初要评估各门店的会员经营健康度（谁、何时）：需要算出每家门店上月"会员消费金额占总销售额的比例"（什么数据结论）。占比高说明会员粘性强、私域运营有效；占比低的门店则是会员日、储值赠礼、企业微信拉新等资源的优先投放对象（为什么）。数据来自POS小票明细：顾客结账时报手机号或扫会员码，小票上会记录member_id，未报会员的散客单member_id为NULL。

### 2. 表结构说明

**销售小票明细表 sales**（同前，本题重点使用member_id与sale_amount）

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | BIGINT | 流水行ID，主键 |
| receipt_no | VARCHAR(20) | 小票号 |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| member_id | BIGINT | 会员ID，非会员支付为NULL |
| staff_id | INT | 收银员工号 |
| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |
| is_return | CHAR(1) | 是否退货行：Y/N |

示例数据：

| sale_id | receipt_no | store_id | product_id | member_id | staff_id | sale_date | sale_time | qty | unit_price | sale_amount | is_return |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 30001 | R20240602S011 | 1 | 3001 | M10023 | 12 | 2024-06-02 | 10:05:00 | 2 | 3.50 | 7.00 | N |
| 30002 | R20240602S011 | 1 | 4502 | M10023 | 12 | 2024-06-02 | 10:05:00 | 1 | 25.00 | 25.00 | N |
| 30003 | R20240602S012 | 1 | 6108 | NULL | 12 | 2024-06-02 | 11:20:00 | 1 | 39.90 | 39.90 | N |
| 30004 | R20240602S013 | 2 | 3001 | M10188 | 21 | 2024-06-02 | 15:40:00 | 4 | 3.50 | 14.00 | N |
| 30005 | R20240602S014 | 2 | 3105 | NULL | 22 | 2024-06-02 | 16:10:00 | 1 | 12.80 | 12.80 | N |

### 3. 解题思路

先定口径：只要小票行上member_id非空，该行金额就计入"会员消费"；占比=会员销售额÷门店总销售额×100%；剔除退货行；分母为0的门店要防护。实现路径首选条件聚合：在SUM里嵌CASE WHEN，一次扫描同时得到总额、会员额和占比（写法一）。另一种思路是把"总销售额"和"会员销售额"拆成两个子查询分别聚合，再按门店连接（写法二），逻辑更直白但要小心连接类型。**【避坑指南】** NULL判断必须用member_id IS NOT NULL，写成member_id != ''或member_id <> 0在MySQL里对NULL永远不成立（NULL与任何值比较结果都是NULL），会把会员消费全部漏掉；写法二若用INNER JOIN，当月"零会员消费"的门店会因子查询无行而被整店丢弃，应改LEFT JOIN并补0。

### 4. 参考解法

**写法一：条件聚合，一次扫描同时算出总额、会员额与占比（推荐）**

```sql
-- 写法一：SUM里嵌CASE WHEN，一遍扫描出三个指标
SELECT
    store_id,                                                    -- 门店ID
    ROUND(SUM(sale_amount), 2) AS total_amount,                  -- 门店总销售额
    ROUND(SUM(CASE WHEN member_id IS NOT NULL
                   THEN sale_amount ELSE 0 END), 2) AS member_amount,   -- 会员消费金额
    ROUND(SUM(CASE WHEN member_id IS NOT NULL
                   THEN sale_amount ELSE 0 END)
          / SUM(sale_amount) * 100, 2) AS member_ratio_pct       -- 会员占比（%）
FROM sales
WHERE sale_date >= '2024-06-01'
  AND sale_date <  '2024-07-01'        -- 统计2024年6月
  AND is_return   = 'N'                -- 正向销售口径
GROUP BY store_id                      -- 按门店分组
HAVING SUM(sale_amount) > 0            -- 防护：剔除分母为0或异常的门店
ORDER BY member_ratio_pct DESC;        -- 占比从高到低
```

结果解读：一行一店三个数，占比降序即"会员经营最强门店"榜单；配合门店客流看，能区分"会员多但总量小"与"总量大但散客为主"两类不同打法的门店。

**写法二：总额与会员额分别聚合，再按门店连接**

```sql
-- 写法二：两个子查询分别算总量与会员量，按门店对齐
SELECT
    s.store_id,                                        -- 门店ID
    ROUND(s.total_amt, 2) AS total_amount,             -- 门店总销售额
    ROUND(IFNULL(m.member_amt, 0) / s.total_amt * 100, 2) AS member_ratio_pct -- 会员占比
FROM (
    -- 子查询1：全量销售额
    SELECT store_id, SUM(sale_amount) AS total_amt
    FROM sales
    WHERE sale_date >= '2024-06-01' AND sale_date < '2024-07-01'
      AND is_return = 'N'
    GROUP BY store_id
) AS s
LEFT JOIN (
    -- 子查询2：仅会员行（member_id非空）的销售额
    SELECT store_id, SUM(sale_amount) AS member_amt
    FROM sales
    WHERE sale_date >= '2024-06-01' AND sale_date < '2024-07-01'
      AND is_return = 'N'
      AND member_id IS NOT NULL                        -- 会员判定放在子查询内
    GROUP BY store_id
) AS m ON m.store_id = s.store_id                      -- LEFT JOIN保留零会员消费的门店
ORDER BY member_ratio_pct DESC;
```

结果解读：**【加分点】** 这里刻意用LEFT JOIN加IFNULL——某店当月若没有任何会员消费，子查询2不产生该店行，INNER JOIN会把它整店丢掉，而LEFT JOIN能把它保留并显示占比0，这才是运营想看到的完整名单。

### 5. 性能分析与优化

写法一只扫一遍sales，聚合全部在内存/临时表完成，通常是更优解；写法二扫两遍sales并多一次JOIN，代价约为写法一的2倍扫描量，但每个子查询逻辑单一、便于分别加过滤和复用。优化建议：索引上建 (store_id, sale_date, is_return) 复合索引，或至少 (sale_date) 让月度范围先剪枝；member_id的选择性低（大量NULL），单独给它建索引意义不大；若该报表月月都跑，建议按月生成"门店×会员标记"的预聚合表 dws_store_member_sales(月份, store_id, member_flag, amount)，把占比计算变成对汇总表的一次除法；查询里避免对member_id做函数包裹（如IFNULL(member_id,0)再比较），会导致索引失效。

### 6. 面试延伸考点

- **追问：member_id为NULL和为空字符串有什么区别？SQL里怎么区分？** 回答要点：NULL是"未知"，空串是"已知为空"；判断用IS NULL/IS NOT NULL，IFNULL(x,0)只兜NULL不兜空串；入库规范上应统一一种，面试时点出数据质量一致性意识。
- **追问：为什么不用"会员小票数占比"代替金额占比？** 回答要点：金额占比反映钱包份额，票数占比反映到店频次；会员客单通常高于散客，两个占比不等，汇报时用哪个要说清。
- **追问：如果还要区分金卡/普卡会员怎么办？** 回答要点：JOIN会员主数据表members取等级字段，条件聚合里再加一层CASE WHEN member_level='金卡'；属于三表聚合，入门后即可进阶。
- **追问：HAVING和WHERE的区别？** 回答要点：WHERE在分组前过滤行、不能用聚合函数；HAVING在分组后过滤组、可以对SUM/COUNT设条件，本题用HAVING剔除分母为0的门店。

### 7. 业务拓展思考

会员占比是会员经济模式的体温计：占比持续走高的门店可以减少无差别折扣、转向会员精准权益；占比低的门店优先做"结账报手机号"话术培训与首单立减，把散客转成会员。与采购联动时，会员购买集中的品类可加大会员价商品采购量。口径延展上，同一结构可以算"会员小票占比""会员人数占比""新会员（当月注册且消费）贡献占比"；若把时间窗拉长到季度，还能观察会员占比的趋势拐点，为年度会员战略复盘提供证据。

## RET-04 生成低于安全库存的商品补货清单

### 1. 业务背景

连锁便利店每天早上开店前，采购专员与门店店长要跑一份补货清单（谁、何时）：列出所有"当前可用库存低于安全库存"的商品，按缺口大小排序（什么数据结论），采购系统据此生成建议订货量、仓库据此安排当日配送波次（为什么）。安全库存safety_stock是按商品周转速度配置的补货触发线，低于它意味着按当前动销可能在下次到货前卖断货，造成缺货销售损失。

### 2. 表结构说明

**门店商品库存表 inventory**

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| stock_qty | INT | 当前可用库存（不含在途） |
| safety_stock | INT | 安全库存阈值 |
| update_time | DATETIME | 库存更新时间 |

示例数据：

| --- | --- | --- | --- | --- |
| 1 | 3001 | 18 | 30 | 2024-06-03 06:00:00 |
| 1 | 6108 | 5 | 12 | 2024-06-03 06:00:00 |
| 2 | 4502 | 40 | 25 | 2024-06-03 06:00:00 |
| 2 | 5201 | 8 | 15 | 2024-06-03 06:00:00 |
| 3 | 3001 | 120 | 80 | 2024-06-03 06:00:00 |

**商品主数据表 products（多题复用）**

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| product_id | INT | 商品ID，主键 |
| product_name | VARCHAR(50) | 商品名称 |
| category_id | INT | 品类ID |
| category_name | VARCHAR(30) | 品类名称 |
| unit | VARCHAR(10) | 售卖单位 |
| sale_price | DECIMAL(10,2) | 标准零售价 |

示例数据：

| product_id | product_name | category_id | category_name | unit | sale_price |
| --- | --- | --- | --- | --- | --- |
| 3001 | 鲜牛奶950ml | 10 | 乳制品 | 盒 | 3.50 |
| 3105 | 全麦吐司400g | 11 | 烘焙 | 袋 | 12.80 |
| 4502 | 照烧鸡便当 | 50 | 生鲜 | 份 | 25.00 |
| 5201 | 冷鲜猪肉500g | 50 | 生鲜 | 盒 | 35.00 |

**门店主数据表 stores**（同RET-01，字段store_id/store_name/city/store_type/open_date，示例数据同前，此处不再重复）

### 3. 解题思路

先定口径：缺货判定为stock_qty严格小于safety_stock（等于不算缺，刚触线）；输出"补货缺口=safety_stock−stock_qty"并按缺口降序，缺口大的优先配送；清单要带商品名、门店名，方便仓配人工核对。实现路径：inventory事实表LEFT JOIN products与stores两张维度表补名称，WHERE过滤缺口，ORDER BY排序。**【避坑指南】** 有个高频小坑：MySQL的WHERE子句里不能直接引用SELECT定义的列别名（如WHERE gap_qty>0会报错），因为WHERE先于SELECT执行——解法二是把带别名的计算放进子查询，外层再用别名过滤，这也是"聚合/计算结果再过滤"的通用套路；另外连维度表建议用LEFT JOIN，防止个别商品主数据缺失导致整行静默丢失。

### 4. 参考解法

**写法一：JOIN后直接WHERE过滤缺口（最常用）**

```sql
-- 写法一：三表连接，WHERE直接比较两列
SELECT
    inv.store_id,                                    -- 门店ID
    st.store_name,                                   -- 门店名称
    inv.product_id,                                  -- 商品ID
    p.product_name,                                  -- 商品名称
    inv.stock_qty,                                   -- 当前可用库存
    inv.safety_stock,                                -- 安全库存
    inv.safety_stock - inv.stock_qty AS gap_qty      -- 补货缺口=安全库存-现有库存
FROM inventory AS inv
LEFT JOIN products AS p ON p.product_id = inv.product_id   -- 补商品名称
LEFT JOIN stores   AS st ON st.store_id  = inv.store_id    -- 补门店名称
WHERE inv.stock_qty < inv.safety_stock              -- 缺货判定：库存严格小于安全库存
ORDER BY gap_qty DESC;                              -- 缺口大的排前面，优先补
```

结果解读：结果即当日补货工作清单；若按门店分组查看，店长只关注自己门店的行，采购则看全量按缺口调度配送波次。

**写法二：先在子查询里算出缺口列，外层用别名过滤排序**

```sql
-- 写法二：子查询产出gap_qty，外层再过滤——演示WHERE不能用SELECT别名的替代写法
SELECT
    t.store_id,
    t.store_name,
    t.product_name,
    t.stock_qty,
    t.safety_stock,
    t.gap_qty
FROM (
    SELECT
        inv.store_id,                                   -- 门店ID
        st.store_name,                                  -- 门店名称
        p.product_name,                                 -- 商品名称
        inv.stock_qty,                                  -- 当前库存
        inv.safety_stock,                               -- 安全库存
        inv.safety_stock - inv.stock_qty AS gap_qty     -- 计算列别名
    FROM inventory AS inv
    LEFT JOIN products AS p ON p.product_id = inv.product_id
    LEFT JOIN stores   AS st ON st.store_id  = inv.store_id
) AS t
WHERE t.gap_qty > 0                -- 与 stock_qty < safety_stock 完全等价
ORDER BY t.gap_qty DESC;
```

结果解读：结果与写法一一致；**【加分点】** 这种"先算列、再引用列"的写法在缺口还要参与二次运算（如缺口×建议订货倍数）时可读性明显更好。

### 5. 性能分析与优化

本题主表是inventory，行数=门店数×商品数（如500店×8000SKU=400万行），两次LEFT JOIN都走主键，代价可控；写法二多物化一层子查询，MySQL 8.0优化器通常会对派生表做合并或物化，差别很小。优化建议：inventory建复合索引 (store_id, stock_qty) 或 (product_id, store_id)，覆盖连接列；若清单里大部分商品并不缺货，可考虑"缺货位图/标志列"由库存事务维护，查询直接WHERE is_short=1，把比较从运行时挪到写入时；更大的量级则按store_id分表或分区，让店长端查询只扫本店分区；切勿在WHERE里对stock_qty包函数（如IFNULL(stock_qty,0)<safety_stock会放弃索引）。

### 6. 面试延伸考点

- **追问：为什么WHERE里不能用SELECT的列别名？** 回答要点：SQL逻辑执行顺序是FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY，WHERE先于SELECT执行，别名尚未产生；ORDER BY可以用别名因为它在SELECT之后。
- **追问：安全库存相等时算缺货吗？两种口径差别是什么？** 回答要点：严格小于（<）与小于等于（<=）取决于业务——等于安全线时是否已触发补货流程；面试要点是主动向业务确认边界，并在口径文档中写死。
- **追问：如果想按品类汇总缺货商品数，怎么改？** 回答要点：保留JOIN products，GROUP BY category_name后COUNT(*)，HAVING COUNT(*)>0；或按门店×品类二维汇总，给区域经理看缺货集中度。
- **追问：LEFT JOIN维度表时若商品主数据缺失，金额类指标会怎样？** 回答要点：商品名为NULL但行保留；若误用INNER JOIN则该商品从清单消失，缺货风险被静默掩盖——数据完整性优先于美观。

### 7. 业务拓展思考

补货清单是零售供应链的日常起跑线：缺口直接换算成建议订货量（缺口×目标覆盖天数÷日均销量），再考虑在途与整箱起订量修正。把本题结果与销售速度（呼应RET-05品类排名）联动，可以区分"卖得快导致缺货"与"滞销后安全库存虚高"两类问题，前者加订、后者调低安全线并清理库存。口径延展上，还可算"缺货商品占比""缺货持续天数"，作为门店运营考核指标；库存快照若按日留存，还能做缺货与销售额损失的归因分析。

## RET-05 各品类销售额排名

### 1. 业务背景

连锁商超的品类经理每月初要做品类复盘（谁、何时）：需要上月各品类的销售额与排名（什么数据结论），用来决定货架与堆头资源分配——头部品类保陈列面、腰部品类做主题促销、尾部品类评估汰换（为什么）。品类归属在商品主数据products里，销售额要从小票明细sales按商品聚合后归到品类，属于典型的事实表连维度表的聚合排名场景。

### 2. 表结构说明

**销售小票明细表 sales**（同RET-01，本题使用product_id、sale_amount、sale_date、is_return）

| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |

| 40001 | R20240605S001 | 1 | 3001 | M10023 | 12 | 2024-06-05 | 09:15:00 | 2 | 3.50 | 7.00 | N |

**商品主数据表 products**（同RET-04：product_id/product_name/category_id/category_name/unit/sale_price，示例数据同前，本题连表取category_id与category_name）

### 3. 解题思路

先定口径：品类归属以商品主数据为准（商品只归属一个主品类，暂不考虑多品类标签）；销售额为正向销售合计，不含退货；排名按金额降序。实现路径：sales按product_id JOIN products取品类，GROUP BY品类后SUM金额，ORDER BY降序即排名（写法一）；写法二在聚合结果上用窗口函数ROW_NUMBER()显式生成名次列，方便前端直接展示"第1名/第2名"，并可无缝换成RANK()/DENSE_RANK()处理并列。**【避坑指南】** GROUP BY要同时带category_id和category_name——只按名称分组时，若存在不同ID的同名品类（如"熟食"分属两个部门），会被错误合并；另外先GROUP BY品类再JOIN并不是必须的，正确顺序是先JOIN再聚合，若先把sales按商品聚合再连商品表，反而多一次聚合且容易漏掉无主数据商品的处理。

### 4. 参考解法

**写法一：JOIN维度表+GROUP BY+ORDER BY（最朴素的排名）**

```sql
-- 写法一：明细连商品表，按品类聚合后金额降序
SELECT
    p.category_id,                                   -- 品类ID
    p.category_name,                                 -- 品类名称
    ROUND(SUM(sa.sale_amount), 2) AS sales_amount    -- 品类月销售额
FROM sales AS sa
JOIN products AS p ON p.product_id = sa.product_id   -- 事实表连商品维度表
WHERE sa.sale_date >= '2024-06-01'
  AND sa.sale_date <  '2024-07-01'                   -- 统计2024年6月
  AND sa.is_return  = 'N'                            -- 正向销售口径
GROUP BY p.category_id, p.category_name              -- ID+名称一起分组，防同名合并
ORDER BY sales_amount DESC;                          -- 金额降序即排名
```

结果解读：结果天然按名次排列，头部两三个品类通常贡献过半销售额（二八分布）；品类的绝对值与份额环比变化比名次本身更有运营含义。

**写法二：聚合子查询+ROW_NUMBER()生成显式名次列（MySQL 8.0）**

```sql
-- 写法二：先聚合出名次候选，再用窗口函数打名次标签
SELECT
    t.category_id,
    t.category_name,
    t.sales_amount,
    ROW_NUMBER() OVER (ORDER BY t.sales_amount DESC) AS rank_no  -- 按金额降序生成连续名次
FROM (
    SELECT
        p.category_id,                                -- 品类ID
        p.category_name,                              -- 品类名称
        SUM(sa.sale_amount) AS sales_amount           -- 品类销售额
    FROM sales AS sa
    JOIN products AS p ON p.product_id = sa.product_id
    WHERE sa.sale_date >= '2024-06-01'
      AND sa.sale_date <  '2024-07-01'
      AND sa.is_return  = 'N'
    GROUP BY p.category_id, p.category_name
) AS t
ORDER BY rank_no;                                    -- 最终按名次输出
```

结果解读：**【加分点】** rank_no列可直接贴到报表；若两个品类金额并列，ROW_NUMBER会硬分先后，讲究公平时应换成RANK()（并列同号、下一名跳号）或DENSE_RANK()（并列同号、不跳号），这也是面试必问的三兄弟区别。

### 5. 性能分析与优化

两写法都要扫一遍月度sales并按品类做哈希聚合，写法二多一层窗口排序（品类数通常只有几十个，排序代价可忽略），性能几乎等价，选择依据主要是可读性与下游需求。优化建议：sales建 (product_id, sale_date) 或 (sale_date) 索引，让JOIN与日期过滤走索引；products.product_id是主键天然有索引；月度品类销售额属于稳定指标，应固化为预聚合表 dws_category_sales(月份, category_id, sales_amount)，大盘页直接读；若只看Top品类，可在子查询里先LIMIT再开窗，减少窗口输入；切勿SELECT *后再在前端过滤品类，要把谓词下推到SQL里。

### 6. 面试延伸考点

- **追问：ROW_NUMBER、RANK、DENSE_RANK的区别？** 回答要点：ROW_NUMBER连续且唯一；RANK并列同号但下一名跳号（1,1,3）；DENSE_RANK并列同号不跳号（1,1,2）；选哪个取决于"并列时名额怎么占"的业务规则。
- **追问：想看每个品类内部的商品排名怎么办？** 回答要点：窗口加PARTITION BY category_name，即ROW_NUMBER() OVER (PARTITION BY category_name ORDER BY SUM(sale_amount) DESC)，可在每个品类内取Top商品做陈列优化。
- **追问：退货要怎么体现？** 回答要点：若只看正销售则过滤is_return='N'；若要看净额，把退货负数一起SUM即可；两个口径的品类排名可能不同，汇报时必须注明。
- **追问：为什么GROUP BY要同时带ID和名称？** 回答要点：防止不同ID同名品类被合并，也满足ONLY_FULL_GROUP_BY对非聚合列的要求；只用名称分组是常见的数据正确性事故源。

### 7. 业务拓展思考

品类排名是货架资源与采购预算的分配依据：头部品类谈年度联采与供应商费用，腰部品类做节令主题档期，尾部品类进汰换清单。与RET-10的动销率联动，可以识别"排名高但动销窄"（靠少数爆款支撑）与"排名低但动销宽"（长尾均衡）两类品类，采取完全不同的促销策略。口径延展上，同一框架换成qty即"品类销量排名"（金额与销量排名背离说明客单结构差异），加上毛利字段可升级为"品类毛利贡献排名"，那是采购谈判的真正弹药。

## RET-06 门店时段销售分布（早市/午市/晚市）

### 1. 业务背景

连锁便利店的店长与督导排班前要回答一个问题：一天的生意集中在哪些时段（谁、何时、什么数据结论）？便利店通常把营业时间切成早市（07:00-11:59，通勤早餐）、午市（12:00-17:59，午餐与下午茶）、晚市（18:00-22:59，下班晚餐与夜购）三段。拿到各时段的销售额与小票数后，店长据此决定高峰时段加派收银与关东煮补货人手、低谷时段安排理货与盘点（为什么）。数据来自POS小票明细，按sale_time的小时数分桶统计。

### 2. 表结构说明

**销售小票明细表 sales**（同前，本题重点使用sale_time的时、分信息）

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | BIGINT | 流水行ID，主键 |
| receipt_no | VARCHAR(20) | 小票号 |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| member_id | BIGINT | 会员ID，非会员为NULL |
| staff_id | INT | 收银员工号 |
| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |
| is_return | CHAR(1) | 是否退货行：Y/N |

示例数据：

| sale_id | receipt_no | store_id | product_id | member_id | staff_id | sale_date | sale_time | qty | unit_price | sale_amount | is_return |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 50001 | R20240607S001 | 1 | 3105 | M10023 | 12 | 2024-06-07 | 08:20:00 | 1 | 12.80 | 12.80 | N |
| 50002 | R20240607S002 | 1 | 3001 | NULL | 12 | 2024-06-07 | 09:05:00 | 2 | 3.50 | 7.00 | N |
| 50003 | R20240607S003 | 1 | 4502 | M10245 | 15 | 2024-06-07 | 12:40:00 | 1 | 25.00 | 25.00 | N |
| 50004 | R20240607S004 | 1 | 3001 | NULL | 15 | 2024-06-07 | 19:15:00 | 3 | 3.50 | 10.50 | N |
| 50005 | R20240607S005 | 1 | 4502 | NULL | 12 | 2024-06-07 | 23:10:00 | 1 | 25.00 | 25.00 | N |

（sale_id=50005发生在23:10，落在"其他时段"兜底桶，用于演示边界处理。）

### 3. 解题思路

先定口径：时段按sale_time的小时数HOUR(sale_time)划分，边界采用左闭右开（[7,12)、[12,18)、[18,23)），23点后与7点前的零星交易归入"其他时段"兜底，保证CASE WHEN覆盖全部时间；统计粒度可以先做全店单日或一周合计，也可加store_id看分店分布。实现路径有两种：写法一用CASE WHEN生成"时段标签"列，再按该列GROUP BY，输出多行；写法二用条件聚合（SUM CASE WHEN）把三个时段拍平成一行三列，并顺带算占比。**【避坑指南】** 最大的坑是CASE WHEN分支不封闭——忘了ELSE兜底时，23:10的交易会落入NULL组且报表上看不出来；其次是GROUP BY时MySQL虽然允许写SELECT别名，但把完整表达式重写一遍跨数据库更稳；如果sale_time是DATETIME类型，HOUR()同样适用，但跨天营业（如24小时店）要定义清楚"营业日"归属。

### 4. 参考解法

**写法一：CASE WHEN生成时段标签后分组（多行输出，最通用）**

```sql
-- 写法一：用CASE WHEN把小时映射成时段标签，再按标签聚合
SELECT
    CASE
        WHEN HOUR(sa.sale_time) >= 7  AND HOUR(sa.sale_time) < 12 THEN '早市(07-11点)'
        WHEN HOUR(sa.sale_time) >= 12 AND HOUR(sa.sale_time) < 18 THEN '午市(12-17点)'
        WHEN HOUR(sa.sale_time) >= 18 AND HOUR(sa.sale_time) < 23 THEN '晚市(18-22点)'
        ELSE '其他时段'                                   -- 兜底分支，必须存在
    END AS time_slot,                                     -- 时段标签
    COUNT(DISTINCT sa.receipt_no) AS receipt_cnt,         -- 时段小票数
    ROUND(SUM(sa.sale_amount), 2) AS sales_amount         -- 时段销售额
FROM sales AS sa
WHERE sa.sale_date = '2024-06-07'      -- 单日分布，也可换成一周区间
  AND sa.is_return  = 'N'
GROUP BY CASE
        WHEN HOUR(sa.sale_time) >= 7  AND HOUR(sa.sale_time) < 12 THEN '早市(07-11点)'
        WHEN HOUR(sa.sale_time) >= 12 AND HOUR(sa.sale_time) < 18 THEN '午市(12-17点)'
        WHEN HOUR(sa.sale_time) >= 18 AND HOUR(sa.sale_time) < 23 THEN '晚市(18-22点)'
        ELSE '其他时段'
    END                                                  -- MySQL支持GROUP BY别名，写全表达式跨库更稳
ORDER BY FIELD(time_slot, '早市(07-11点)', '午市(12-17点)', '晚市(18-22点)', '其他时段'); -- 按业务顺序而非金额排序
```

结果解读：输出四行按营业时间排列，一眼看出"早市票多客单低、晚市票少客单高"之类的结构；FIELD()函数让结果按早晚顺序展示，而不是按金额大小忽上忽下。

**写法二：条件聚合，一行输出三时段金额与晚市占比**

```sql
-- 写法二：SUM CASE WHEN把时段拍平成列，一行看全天
SELECT
    ROUND(SUM(CASE WHEN HOUR(sa.sale_time) >= 7  AND HOUR(sa.sale_time) < 12
                   THEN sa.sale_amount ELSE 0 END), 2) AS morning_amt,    -- 早市销售额
    ROUND(SUM(CASE WHEN HOUR(sa.sale_time) >= 12 AND HOUR(sa.sale_time) < 18
                   THEN sa.sale_amount ELSE 0 END), 2) AS afternoon_amt,  -- 午市销售额
    ROUND(SUM(CASE WHEN HOUR(sa.sale_time) >= 18 AND HOUR(sa.sale_time) < 23
                   THEN sa.sale_amount ELSE 0 END), 2) AS evening_amt,    -- 晚市销售额
    ROUND(SUM(sa.sale_amount), 2) AS total_amt,                           -- 全天合计，用于对账
    ROUND(SUM(CASE WHEN HOUR(sa.sale_time) >= 18 AND HOUR(sa.sale_time) < 23
                   THEN sa.sale_amount ELSE 0 END)
          / SUM(sa.sale_amount) * 100, 2) AS evening_pct                  -- 晚市占比（%）
FROM sales AS sa
WHERE sa.sale_date = '2024-06-07'
  AND sa.is_return  = 'N';
```

结果解读：**【加分点】** 单行宽表最适合塞进日报卡片；total_amt等于三段之和加其他时段，可用作自检；若要分门店，加GROUP BY store_id即可把两种写法升级为分组版。

### 5. 性能分析与优化

两写法同样只扫一遍明细，差异在输出形态：写法一按表达式分组需为每行计算CASE并按结果哈希分组；写法二的每个SUM(CASE)都在同一遍扫描中累加，列数增加不增加扫描次数。真正的代价在于HOUR(sale_time)这类函数计算无法走索引——但它作用在聚合内部而非过滤条件上，问题不大；要避免的是把时段过滤写成WHERE HOUR(sale_time)=9（对索引列包函数导致全表扫描），应改成WHERE sale_time >= '09:00:00' AND sale_time < '10:00:00'。优化建议：sales建 (sale_date, is_return) 索引先做日期剪枝；数据量大时预建 dws_store_hourslot_sales(日期, 门店, 时段, 金额, 小票数) 小时级汇总表，既服务本题也服务客流对照；营业日跨午夜的场景在ETL层打好"营业日"标签列，避免查询端反复推导。

### 6. 面试延伸考点

- **追问：CASE WHEN各分支的求值顺序是怎样的？** 回答要点：自上而下短路命中，命中即返回，所以把最可能、或范围更窄的条件放前面；重叠条件会被前面的分支"截胡"，这是隐性疾病式的口径bug。
- **追问：如果想按小时输出24行明细分布，怎么写？** 回答要点：GROUP BY HOUR(sale_time)即可；要补齐无销售的0点小时，需要关联一张小时维表（数字辅助表）再LEFT JOIN。
- **追问：24小时便利店怎么定义"一天"？** 回答要点：业务上用"营业日"（如04:00结转到次日04:00），ETL打营业日标签比查询端用DATE_SUB拼逻辑更可靠；面试时主动问清口径会加分。
- **追问：时段分布怎么和客流联动？** 回答要点：客流感知设备若也是小时粒度，同样按时段分桶后JOIN，得到各时段"进店人数vs成交小票数"的转化漏斗。

### 7. 业务拓展思考

时段分布直接驱动排班与鲜食补货节奏：早市高峰前鲜食面包必须上架完毕，晚市高峰前要补关东煮与便当；低谷时段则安排收银培训与陈列改造。把时段销售与时段客流（呼应RET-01）相除得到分时段转化率，能进一步区分"人多不买"与"人少但必买"的时段属性，前者做试吃促销、后者保库存深度。口径延展上，时段可细到半小时用于高峰预警；连续观察一个月的时段分布还能识别雨天/周末效应，为动态排班模型提供特征。

## RET-07 各门店退货小票数与退货率

### 1. 业务背景

连锁商超的防损与品控岗每周要复盘退货情况（谁、何时）：统计各门店当周退货小票数、退货金额与退货率（什么数据结论），用来定位异常门店——退货率突然升高可能是生鲜品质问题、临期管理不到位或收银误操作，也可能是职业退货团伙（为什么）。零售POS的通用做法是：退货也作为小票写入同一张sales表，退货行is_return='Y'且sale_amount记录为负数，这样"净销售额"可以直接对全表SUM得到。

### 2. 表结构说明

**销售小票明细表 sales**（同前；本题关键约定：退货行is_return='Y'、sale_amount为负数）

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | BIGINT | 流水行ID，主键 |
| receipt_no | VARCHAR(20) | 小票号（退货生成新的退货小票号） |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| member_id | BIGINT | 会员ID，非会员为NULL |
| staff_id | INT | 经手员工工号 |
| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 数量（退货行为正数，方向由is_return标识） |
| unit_price | DECIMAL(10,2) | 成交单价 |

（60003、60005为退货行：小票号以RT开头、金额为负，模拟真实POS的退货记账方式。）

### 3. 解题思路

先定口径：退货金额=退货行负数金额的绝对值（取负或ABS）；退货小票数=退货行receipt_no去重计数；退货率=退货金额÷正销售额×100%（分母明确用正销售额而非净销售额，两种定义都可以但要声明）。实现路径有两种：写法一只筛退货行（is_return='Y'）单独统计退货侧指标，简单直接但拿不到退货率分母；写法二对全量行做条件聚合，一次算出正销售额、退货金额、退货率三项，是报表的标准做法。**【避坑指南】** 最容易犯的错是SUM(sale_amount)后忘记退货是负数——直接把结果当"退货金额"会得到负值且看不出来；另外退货率排序时，销售额基数极小的门店退货率容易虚高，解读时要同时看金额绝对值，不能只看比率排名。

### 4. 参考解法

**写法一：只取退货行，单独统计退货侧指标**

```sql
-- 写法一：WHERE筛出退货行，只算退货小票数与退货金额
SELECT
    sa.store_id,                                         -- 门店ID
    COUNT(DISTINCT sa.receipt_no) AS return_receipt_cnt, -- 退货小票数（一张退货小票多行只算1）
    ROUND(-SUM(sa.sale_amount), 2) AS return_amount      -- 退货金额：负数取反变正数
FROM sales AS sa
WHERE sa.sale_date >= '2024-06-03'
  AND sa.sale_date <  '2024-06-10'      -- 统计一周
  AND sa.is_return  = 'Y'               -- 只看退货行
GROUP BY sa.store_id
ORDER BY return_amount DESC;            -- 退货金额大的门店排前面
```

结果解读：清单给出"谁退得多"，但要判断异常还缺一个相对刻度——同样是退货2000元，对日销10万和日销1万的门店意义完全不同，于是需要写法二的退货率。

**写法二：全量行条件聚合，一次算出销售额、退货额与退货率（推荐）**

```sql
-- 写法二：同一遍扫描同时产出正销售、退货、退货率
SELECT
    sa.store_id,                                                                  -- 门店ID
    ROUND(SUM(CASE WHEN sa.is_return = 'N' THEN sa.sale_amount ELSE 0 END), 2) AS sales_amount, -- 正销售额
    ROUND(-SUM(CASE WHEN sa.is_return = 'Y' THEN sa.sale_amount ELSE 0 END), 2) AS return_amount,-- 退货金额（负转正）
    ROUND(-SUM(CASE WHEN sa.is_return = 'Y' THEN sa.sale_amount ELSE 0 END)
          / SUM(CASE WHEN sa.is_return = 'N' THEN sa.sale_amount ELSE 0 END) * 100, 2) AS return_rate_pct -- 退货率%
FROM sales AS sa
WHERE sa.sale_date >= '2024-06-03'
  AND sa.sale_date <  '2024-06-10'
GROUP BY sa.store_id                    -- 按门店分组
HAVING SUM(CASE WHEN sa.is_return = 'N' THEN sa.sale_amount ELSE 0 END) > 0 -- 分母防护，避免除零
ORDER BY return_rate_pct DESC;          -- 退货率高的排前面，便于排查
```

结果解读：**【面试高频】** 这张三列报表是防损周会的标准材料：先看退货率Top门店，再下钻到品类与小票定位原因；金额与比率同时呈现，避免小基数门店误导。

### 5. 性能分析与优化

写法一扫描时谓词is_return='Y'选择性高（退货行通常不到1%），若有 (sale_date, is_return) 复合索引可快速定位，代价很低；写法二要处理全量行但只扫一遍，量级大时反而更省——判断标准是"退货行占比"：低于10%时写法一更轻，退货侧还要反复分析时写法二一次成型。优化建议：复合索引 (sale_date, is_return) 让周窗口先剪枝；由于退货分析固定按周跑，可预聚合 dws_store_return_weekly(周, store_id, return_amount, return_receipt_cnt)；分母防护除了HAVING也可在SELECT里用NULLIF(x,0)配合除法；极端情况下若退货率按品类下钻，同理把product_id纳入GROUP BY即可，索引相应调整为 (sale_date, is_return, product_id)。

### 6. 面试延伸考点

- **追问：退货率分母用正销售额还是净销售额？** 回答要点：正销售额口径（退货额/正销售）放大问题便于监控，净口径（退货额/净额）更贴近真实损耗；两者数值差异随退货率升高而放大，关键是全公司统一并写进口径字典。
- **追问：一张小票既买了又退了，小票数怎么算？** 回答要点：POS上退货通常生成独立退货小票（新单号），所以销售票数与退货票数天然分离；若系统允许原票冲销（同号负行），则COUNT(DISTINCT receipt_no)会把两张混在一起，必须先与业务确认记账方式。
- **追问：想看退货率的时间趋势怎么写？** 回答要点：把GROUP BY换成sale_date或周标签，按日/周输出退货率序列；配LAG算环比属进阶内容，入门阶段口头说明思路即可。
- **追问：退货金额为负数，为什么报表里要转正？** 回答要点：负数入账保证SUM全表直接得净销售额（财务口径），而运营看板的"退货金额"是业务量概念，习惯用正数展示并标注方向，避免读者误读。

### 7. 业务拓展思考

退货率是商品品质、门店执行与顾客体验三者的交集指标：生鲜品类退货率高要查冷链与订货量，日百品类高则可能假货/质量投诉，整店高且集中在夜间要防收银误操作甚至内部舞弊。与采购联动，高退货SKU进汰换评审；与运营联动，退货集中的门店安排品控飞行检查。口径延展上，可拆"退货率=退货票数占比"与"退货金额占比"两个维度（票数反映频次、金额反映严重度）；再关联member_id还能识别"职业退货人"账户，那已经是风控建模的入口。

## RET-08 当月店员销售额排名

### 1. 业务背景

### 3. 解题思路

### 4. 参考解法

**写法一：JOIN聚合+ORDER BY+LIMIT取Top10（最直接）**

```sql
-- 写法一：连员工表聚合销售额，降序取前10
SELECT
    st.staff_id,                                      -- 工号
    st.staff_name,                                    -- 姓名
    st.store_id,                                      -- 所属门店
    ROUND(SUM(sa.sale_amount), 2) AS sales_amount     -- 当月经手销售额
FROM sales AS sa
JOIN staff AS st ON st.staff_id = sa.staff_id         -- 明细连员工表补姓名
WHERE sa.sale_date >= '2024-06-01'
  AND sa.sale_date <  '2024-07-01'                    -- 统计6月
  AND sa.is_return  = 'N'                             -- 正向销售口径
GROUP BY st.staff_id, st.staff_name, st.store_id      -- 非聚合列全部进入GROUP BY
ORDER BY sales_amount DESC
LIMIT 10;                                             -- 取前10名
```

结果解读：榜单回答"谁卖得最多"，但LIMIT截断在并列时不公平；用于公示的绩效榜更推荐写法二的显式名次。

**写法二：窗口函数RANK()生成全员名次，正确处理并列**

```sql
-- 写法二：先聚合，再在聚合结果上用RANK()排名
SELECT
    t.staff_name,                                     -- 姓名
    t.sales_amount,                                   -- 销售额
    t.rank_no                                         -- 名次：并列同名次，下一名跳号
FROM (
    SELECT
        st.staff_id,                                  -- 工号
        st.staff_name,                                -- 姓名
        ROUND(SUM(sa.sale_amount), 2) AS sales_amount,
        RANK() OVER (ORDER BY SUM(sa.sale_amount) DESC) AS rank_no -- 直接对聚合结果开窗排名
    FROM sales AS sa
    JOIN staff AS st ON st.staff_id = sa.staff_id
    WHERE sa.sale_date >= '2024-06-01'
      AND sa.sale_date <  '2024-07-01'
      AND sa.is_return  = 'N'
    GROUP BY st.staff_id, st.staff_name               -- 分组列覆盖SELECT非聚合列
) AS t
ORDER BY t.rank_no;                                   -- 按名次输出完整榜单
```

结果解读：**【加分点】** RANK()让并列第1名的两人都显示1、下一位显示3，符合体育比赛直觉；若只要前3名，外层WHERE t.rank_no<=3即可，且并列者不会像LIMIT那样被随机挤掉。

### 5. 性能分析与优化

两写法都要扫当月sales并按员工做哈希聚合，写法二多一次窗口排序（员工数顶多几千，代价可忽略）；写法一LIMIT 10配合ORDER BY在聚合后只需要 Top-N 堆排序，内存友好。优化建议：sales建 (staff_id, sale_date, is_return) 或 (sale_date, staff_id) 复合索引，先按月剪枝再按员工聚合；若绩效系统每天看进度，应建日增预聚合表 dws_staff_sales_daily(日期, staff_id, amount)，月榜=对汇总表二次SUM，避免每天扫全月明细；门店维度的榜单则在GROUP BY加store_id并把索引首列设为store_id；不要在JOIN前对staff_id做函数处理（如CAST），会破坏索引使用。

### 6. 面试延伸考点

- **追问：LIMIT 10和RANK()<=10取Top10有什么本质区别？** 回答要点：LIMIT是"取10行"，并列时按排序的稳定性和执行计划随机截断；RANK是"排名后按名次筛"，并列者同进退；涉及奖励名额时必须用后者或明确并列规则。
- **追问：员工中途调店，销售额算给哪家店？** 回答要点：按小票上的store_id（交易发生地）还是staff表的当前store_id（人事归属）会得出不同结果，历史归属要用慢变化维表；这是维表设计的经典问题。
- **追问：怎么算每个门店内部的销售额冠军？** 回答要点：窗口加PARTITION BY st.store_id，ROW_NUMBER() OVER (PARTITION BY st.store_id ORDER BY SUM(sale_amount) DESC)=1即为店内第一。
- **追问：经手销售额能直接当KPI吗？** 回答要点：收银员销售额受排班时段客流影响大，公平时段差异需要按时段折算；考核通常组合会员招募、客单提升率等多指标，体现分析师的口径批判意识。

### 7. 业务拓展思考

员工销售榜的价值不在排名本身，而在解释差距：结合班表可以看出"高峰班多的员工天然额高"，从而把考核修正为时段调整后的相对贡献；结合品类结构能发现谁更会卖高毛利商品，把其话术提炼成培训素材。与会员数据联动（看各员工经手小票的会员注册率），能评出"拉新之星"；口径延展上，"人效=销售额/排班工时"比绝对额更科学，那是排班系统数据与销售数据的联合分析，也是零售HR Analytics的入门题。

### 3. 解题思路

先定口径：店均销售额=城市总销售额÷该城市门店数，分母必须包含当月"零销售门店"——刚开业或已停业的门店也是真实经营单元；统计区间取当月；正销售口径。实现路径的层次感是本题考点：写法一先在子查询里把明细聚到门店级得到每店销售额，再与stores按城市GROUP BY后对店均额做AVG（零销售店用IFNULL补0参与平均）；写法二不分层，直接LEFT JOIN明细到城市级聚合，用"SUM金额÷COUNT(DISTINCT store_id)"一步算店均。**【避坑指南】** 面试最经典的陷阱是直接对明细AVG(sale_amount)——那是"每行小票的平均金额"，与"每店平均销售额"风马牛不相及，数值可能差几个数量级；另一个坑是LEFT JOIN后把日期过滤写进WHERE（会把无销售门店的行过滤掉，等于变相INNER JOIN），必须写在ON子句里。

### 4. 参考解法

**写法一：两级聚合——先门店级SUM，再城市级AVG（层次最清晰）**

```sql
-- 写法一：子查询先聚到门店级，外层再聚到城市级
SELECT
    st.city,                                             -- 城市
    COUNT(*) AS store_cnt,                               -- 城市门店数（主表所有行都计数）
    ROUND(AVG(IFNULL(t.store_amount, 0)), 2) AS avg_store_amount -- 店均销售额：零销售店按0参与平均
FROM stores AS st
LEFT JOIN (
    -- 第一级聚合：明细 → 门店级月销售额
    SELECT
        store_id,
        SUM(sale_amount) AS store_amount
    FROM sales
    WHERE sale_date >= '2024-06-01'
      AND sale_date <  '2024-07-01'
      AND is_return  = 'N'
    GROUP BY store_id
) AS t ON t.store_id = st.store_id                       -- LEFT JOIN保留无销售的门店
GROUP BY st.city                                        -- 第二级聚合：门店 → 城市
ORDER BY avg_store_amount DESC;                         -- 店均产出高的城市排前
```

结果解读：COUNT(*)数的是主表stores的行，所以零销售门店也被计入门店数与分母；AVG在"门店级金额"上求均值，语义正确。深圳若有店但整月无销售，店均会被拉低——这正是业务想要的信号。

**写法二：单层聚合，SUM金额÷COUNT(DISTINCT门店)一步算店均**

```sql
-- 写法二：明细直接LEFT JOIN到城市，一层GROUP BY算店均
SELECT
    st.city,                                             -- 城市
    COUNT(DISTINCT st.store_id) AS store_cnt,            -- 门店数：LEFT JOIN产生NULL也按店去重
    ROUND(SUM(IFNULL(sa.sale_amount, 0))
          / COUNT(DISTINCT st.store_id), 2) AS avg_store_amount -- 总额÷门店数=店均
FROM stores AS st
LEFT JOIN sales AS sa
       ON sa.store_id = st.store_id
      AND sa.sale_date >= '2024-06-01'                   -- 日期与退货条件必须写在ON里！
      AND sa.sale_date <  '2024-07-01'
      AND sa.is_return  = 'N'
GROUP BY st.city
ORDER BY avg_store_amount DESC;
```

结果解读：**【避坑指南】** 这里的过滤条件全部放在ON而非WHERE——放WHERE会把无销售门店的NULL行清掉，COUNT(DISTINCT store_id)与SUM都随之缩水，"零销售门店"就从报表里消失了；这是LEFT JOIN的必修考点。

### 5. 性能分析与优化

写法一先聚后连，JOIN发生在"门店级"小结果集（几百行）上，代价主要是一次全量明细聚合；写法二把明细行直接带入城市分组，JOIN发生在明细层，探测与shuffle的行数等于明细行数，通常比写法一慢，但少一次子查询物化。优化建议：sales建 (sale_date, store_id, is_return) 复合索引做月份剪枝；stores按主键连接天然高效；若城市分析按月例行，建 dws_store_sales_monthly(月份, store_id, amount) 后本题变成对汇总表的两次轻量GROUP BY；若城市数多、需要同时看业态交叉（城市×业态店均），把GROUP BY扩展为两列即可，索引相应补store_type维度无需变更。

### 6. 面试延伸考点

- **追问：为什么AVG(sale_amount)直接算店均是错的？** 回答要点：AVG作用于JOIN后的明细行，得到的是"每行小票平均金额"；店均的分母是门店数不是明细行数，必须"先聚到门店级再AVG"或用SUM÷COUNT(DISTINCT门店)，这是聚合层次错误的典型案例。
- **追问：LEFT JOIN时过滤条件写ON和写WHERE有什么区别？** 回答要点：写ON在连接时过滤右表、左表全保留；写WHERE在连接后过滤，会把右表为NULL的左表行清掉，等价于INNER JOIN；本题要保留零销售门店，必须写ON。
- **追问：刚开业3天的门店要不要计入店均？** 回答要点：计入会拉低店均（经营天数不满），不计入会高估；更公平的口径是"日均销售额=销售额/经营天数"或限定开业满N天门店，体现口径设计的业务思维。
- **追问：怎么同时看城市×业态的店均？** 回答要点：GROUP BY city, store_type，门店数与店均按交叉组计算；注意小样本组（如某业态仅1家店）的店均波动大，解读要谨慎。

### 7. 业务拓展思考

"门店数×店均产出"矩阵是拓展部的选址罗盘：高店均低密度城市（如新一线首店城市）优先加密，低店均高密度城市转向存量优化甚至关店止损。与RET-01的门店客流联动可判断低店均是选址人流问题还是经营问题；与开业日期联动可剔除爬坡期门店看成熟店店均。口径延展上，店均可换算为"店均日销""坪效（销售额/面积）""人效（销售额/员工数）"，其中坪效是零售上市公司披露的核心经营指标，把stores里的面积字段加进来即可实现，非常适合在面试中主动延伸。

## RET-10 促销商品动销率统计

### 1. 业务背景

连锁超市的促销运营岗在每档活动结束后要做复盘（谁、何时）：活动档期内报名了N个促销商品，但真正"动起来"（至少卖出过一单）的只有一部分，动销率=动销商品数÷促销商品总数（什么数据结论）。动销率低说明选品与顾客需求错位或陈列位置太差，下次选品会就要调整；配合动销商品的销量贡献，还能识别"促销靠少数爆款撑场"的结构问题（为什么）。促销商品清单来自商品主数据的is_promo标志，销售事实来自小票明细。

### 3. 解题思路

先定口径：动销=活动期内该商品存在有效销售记录（本题取is_return='N'且sale_amount>0，0元赠品行不算动销）；分母=主数据中is_promo='Y'的商品总数；动销率=动销数÷总数×100%。实现路径的关键是"以商品清单为左表"：写法一先把活动期销售明细去重成"动销商品清单"子查询，再LEFT JOIN到促销商品上，COUNT(*)数分母、COUNT(sa.product_id)数动销数——这里用到"COUNT(列)自动忽略NULL"的性质，未动销商品右表为NULL不计入；写法二不JOIN，对每个促销商品用EXISTS逐个判断是否存在销售记录。**【避坑指南】** 高频错误是把促销商品INNER JOIN销售明细后COUNT(DISTINCT product_id)——分子对但分母没了，未动销商品在JOIN中消失，算出的"动销率"恒等于100%；必须保证分母来自"活动报名清单"而不是销售事实。

### 4. 参考解法

**写法一：促销商品LEFT JOIN去重销售子查询，双计数相除（推荐）**

```sql
-- 写法一：以促销商品为左表LEFT JOIN动销清单，用COUNT性质同时得分母与分子
SELECT
    COUNT(*)                        AS promo_cnt,        -- 分母：促销商品总数（LEFT JOIN不改变左表行数）
    COUNT(sa.product_id)            AS sold_cnt,         -- 分子：有销售的促销商品数（COUNT列名自动跳过NULL）
    ROUND(COUNT(sa.product_id) / COUNT(*) * 100, 2) AS sell_through_pct -- 动销率%
FROM products AS p
LEFT JOIN (
    -- 先把明细收缩成“动销商品清单”：一商品最多一行
    SELECT DISTINCT product_id
    FROM sales
    WHERE sale_date >= '2024-06-01'
      AND sale_date <  '2024-06-20'                      -- 活动档期
      AND is_return  = 'N'
      AND sale_amount > 0                                -- 0元赠品行不算动销
) AS sa ON sa.product_id = p.product_id
WHERE p.is_promo = 'Y'               -- 只统计本期促销商品
```

结果解读：假设3个促销商品中鲜牛奶和洗衣液动了销、吐司仅0元赠出，动销率约66.7%；两个COUNT的差值就是"未动销商品数"，直接进下次选品的优化清单。

**写法二：EXISTS逐商品判断是否有销售记录**

```sql
-- 写法二：不JOIN明细，用EXISTS判断每个促销商品是否动销
SELECT
    COUNT(*) AS promo_cnt,                                  -- 分母：促销商品总数
    SUM(CASE WHEN EXISTS (                            -- 逐行探测：是否存在销售记录
            SELECT 1
            FROM sales AS s
            WHERE s.product_id = p.product_id          -- 与外层商品关联
              AND s.sale_date >= '2024-06-01'
              AND s.sale_date <  '2024-06-20'
              AND s.is_return  = 'N'
              AND s.sale_amount > 0
        ) THEN 1 ELSE 0 END) AS sold_cnt,              -- 动销记1、未动销记0，SUM即动销数
    ROUND(SUM(CASE WHEN EXISTS (
            SELECT 1
            FROM sales AS s
            WHERE s.product_id = p.product_id
              AND s.sale_date >= '2024-06-01'
              AND s.sale_date <  '2024-06-20'
              AND s.is_return  = 'N'
              AND s.sale_amount > 0
        ) THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS sell_through_pct -- 动销率%
FROM products AS p
WHERE p.is_promo = 'Y';
```

结果解读：**【加分点】** EXISTS是"存在性判断"，找到一条就短路返回，不会产生JOIN扇出，语义上也更贴近"有没有卖过"的业务问题；两种写法结果一致，可互为验证。

### 5. 性能分析与优化

写法一需扫描档期内全部销售明细做DISTINCT去重（临时表开销），随后是商品级小表JOIN；写法二对每个促销商品做一次索引探测，探测次数=促销商品数，若sales的product_id上有索引且促销商品不多（几百个），EXISTS非常高效，反之商品数上万时探测次数过多会劣化。优化建议：sales建 (product_id, sale_date, is_return) 复合索引，让EXISTS的探测走索引区间；或反向构造"档期动销商品临时表"再JOIN，兼顾两种场景；长期方案是商品级日汇总表 dws_product_sales_daily(日期, product_id, amount)，动销判断退化为对汇总表的EXISTS，扫描量骤降；无论哪种写法，分母永远从主数据取，切勿从销售事实反推促销清单。

### 6. 面试延伸考点

- **追问：为什么COUNT(sa.product_id)能统计动销数？** 回答要点：COUNT(列名)只数非NULL值，LEFT JOIN未动销商品右表为NULL不计入；写成COUNT(*)会把所有左表行都数进去，分子等于分母——这是LEFT JOIN计数的核心性质。
- **追问：INNER JOIN后COUNT(DISTINCT product_id)算出的比率是什么？** 回答要点：是"动销商品占动销商品的比例"，恒为100%，属于分子分母同源的逻辑错误；正确做法是分母必须来自活动报名清单。
- **追问：动销率高就代表促销成功吗？** 回答要点：还要看动销深度（户均销量）、毛利变化与对非促销品的分流（ cannibalization ）；动销率是广度指标，需与销量提升率组合解读。
- **追问：如果促销按“门店×商品”报名，怎么改？** 回答要点：分母变成products与活动门店清单的笛卡尔组合，动销判断加store_id维度，即以(门店,商品)为最小分析单元重做LEFT JOIN。

### 7. 业务拓展思考

动销率是选品质量的体检表：连续多档动销率低的品类要重新审视顾客画像与价格带；"永远不动销"的商品可能是谈判来的强制搭售品，需要与采购对齐退出机制。与库存联动（呼应RET-04），未动销促销商品还占用了货架与资金，应转入清仓档期；与门店联动可下钻"某商品只在部分城市动销"，反推区域口味差异。口径延展上，"动销率"之外还有"售罄率"（销量/配货量）与"促销弹性"（促销期销量/日常销量），三者组合才是完整的促销复盘框架。

## RET-11 每月新增会员数统计

### 1. 业务背景

连锁便利公司的市场部每月初复盘拉新效果（谁、何时）：需要2024年每个月的新增会员数曲线（什么数据结论），对照当月的拉新活动（扫码送鸡蛋、首单立减、企业微信裂变）评估哪档活动有效，并据此分配下月的拉新预算与门店拉新指标（为什么）。会员在门店收银台或小程序注册，注册时间记录在会员主数据members的register_date字段，是典型的按时间粒度分组统计题。

### 2. 表结构说明

**会员主数据表 members**

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| member_id | BIGINT | 会员ID，主键 |
| member_name | VARCHAR(20) | 会员姓名（脱敏） |
| gender | CHAR(1) | 性别：M/F/U（未知） |
| phone | VARCHAR(11) | 手机号，唯一 |
| register_store_id | INT | 注册门店ID |
| register_date | DATE | 注册日期 |

示例数据：

| member_id | member_name | gender | phone | register_store_id | register_date |
| --- | --- | --- | --- | --- | --- |
| M10023 | 张* | F | 13800000023 | 1 | 2023-11-15 |
| M10188 | 李* | M | 15900000188 | 2 | 2024-01-20 |
| M10245 | 王* | F | 13700000245 | 1 | 2024-02-11 |
| M10301 | 赵* | M | 18600000301 | 3 | 2024-03-08 |
| M10366 | 陈* | F | 15000000366 | 2 | 2024-10-05 |

### 3. 解题思路

先定口径：新增会员=按register_date落在对应月份的会员计数；一个会员只注册一次，无重复风险，COUNT(*)即可；统计范围限定2024自然年，防止把历史年份卷进来。实现路径是把DATE类型"降粒"到月再分组：写法一用DATE_FORMAT(register_date,'%Y-%m')直接产出'2024-03'样式的年月字符串，字典序与时间序一致，ORDER BY ym即时间序；写法二用YEAR()+MONTH()分组、CONCAT拼接输出，是理解格式化本质的等价写法。**【避坑指南】** 经典的坑是拼接时月份不补零——CONCAT(YEAR,'-',MONTH)会产出'2024-10'和'2024-2'，按字符串排序时'2024-10'排在'2024-2'前面，全年曲线直接错乱；所以要么用DATE_FORMAT，要么用LPAD把月份补到两位。另外若register_date是DATETIME，按月分组前先DATE()或直接DATE_FORMAT都没问题，但WHERE范围仍推荐半开区间写法。

### 4. 参考解法

**写法一：DATE_FORMAT格式化年月后分组（最常用）**

```sql
-- 写法一：DATE_FORMAT把日期降粒到“年月”再分组
SELECT
    DATE_FORMAT(register_date, '%Y-%m') AS ym,       -- 年月标签，如2024-03
    COUNT(*)                            AS new_member_cnt -- 当月新增会员数
FROM members
WHERE register_date >= '2024-01-01'
  AND register_date <  '2025-01-01'      -- 限定2024全年，半开区间不漏不重
GROUP BY DATE_FORMAT(register_date, '%Y-%m')  -- 按年月字符串分组
ORDER BY ym;                             -- 'YYYY-MM'字典序=时间序，天然排对
```

结果解读：输出12行（有注册的月份）构成拉新曲线；结合活动日历标注异常峰谷（如3月峰值对应扫码送鸡蛋），是月度运营复盘的第一张图。

**写法二：YEAR/MONTH分组+CONCAT/LPAD手工拼年月（理解降粒本质）**

```sql
-- 写法二：按年、月两个表达式分组，输出时补零拼接
SELECT
    CONCAT(YEAR(register_date), '-',
           LPAD(MONTH(register_date), 2, '0')) AS ym,  -- 月份用LPAD补到两位，保证排序正确
    COUNT(*) AS new_member_cnt                         -- 当月新增会员数
FROM members
WHERE register_date >= '2024-01-01'
  AND register_date <  '2025-01-01'
GROUP BY YEAR(register_date), MONTH(register_date)     -- 按年、月两个整数分组
ORDER BY ym;                                           -- 补零后字典序正确
```

结果解读：**【加分点】** GROUP BY YEAR(),MONTH()而SELECT里做拼接，两者由相同表达式派生，满足ONLY_FULL_GROUP_BY；这个写法揭示了"时间降粒"的本质是按日期的某个成分分组，换成QUARTER()、DAYOFWEEK()即可做季度/星期分布。

### 5. 性能分析与优化

两写法都是全表（或年份范围内）扫描后的哈希分组，会员表量级通常百万到千万，单次查询代价不大；差异在写法一调用一次DATE_FORMAT，写法二在分组键上调用YEAR/MONTH两个函数，函数开销相近。优化建议：members建 (register_date) 索引，让WHERE的年份范围走索引区间扫描（注意GROUP BY里的函数不影响WHERE的索引使用）；若拉新看板按月自动刷新，建议ETL每天追加一行到 dws_member_register_monthly(年月, 注册门店, 新增数)，把查询变成对汇总表的读取；按注册门店拆分时把register_store_id纳入GROUP BY并相应建 (register_store_id, register_date) 复合索引；手机号唯一约束在库层建唯一索引，防重复注册比事后SQL去重更可靠。

### 6. 面试延伸考点

- **追问：为什么'2024-10'会排在'2024-2'前面？怎么避免？** 回答要点：字符串比较逐字符进行，'1'<'2'导致10月排在2月前；用DATE_FORMAT('%Y-%m')或LPAD补零，让字典序与时间序对齐；这题几乎每月考一次。
- **追问：怎么同时看每个月各门店的拉新贡献？** 回答要点：GROUP BY DATE_FORMAT(...), register_store_id，输出月×门店矩阵；再配窗口SUM() OVER (PARTITION BY 年月) 算各店占比。
- **追问：新增会员多就代表拉新成功吗？** 回答要点：还要看"注册后30天内有消费"的转化率与次月留存，否则可能拉来羊毛党；口径上"有效新增=注册且30天内消费"，面试时主动区分注册量与有效拉新是重要加分点。
- **追问：DATE_FORMAT函数在WHERE里能用吗？有什么风险？** 回答要点：能用但对列包函数会让索引失效（如WHERE DATE_FORMAT(register_date,'%Y-%m')='2024-03'全表扫描），应改写成范围条件register_date>='2024-03-01' AND <'2024-04-01'。

### 7. 业务拓展思考

月度拉新曲线要与活动日历对照解读：峰值对应的活动可以固化成月度机制，谷值月份则安排门店竞赛补位。与RET-03的会员消费占比联动，可以验证"新增会员是否转化为销售额"；与RET-14的消费会员数联动可算月活率。口径延展上，把register_date换成首次消费日期即"激活口径的新增"；再往后看LTV（会员生命周期价值）与RFM分层，都需要本题这张按月粒度的基础表作为起点，是会员分析体系的地基。

## RET-12 各支付方式的分布与占比

### 1. 业务背景

连锁超市的收银运营与财务岗每季度要分析支付方式结构（谁、何时）：微信、支付宝、现金、银行卡、储值卡各占多少小票与金额（什么数据结论）。现金占比高意味着找零成本与资金安全风险高、需要加铺自助收银；储值卡占比反映会员储值业务的健康度；支付通道费率不同，结构变化直接影响结算成本，也是与支付渠道谈判费率的依据（为什么）。约定每张小票只会以一种方式支付，pay_type在小票的各行上重复记录。

### 2. 表结构说明

**销售小票明细表 sales**（同前，本题重点使用pay_type字段，假定其为小票级属性）

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | BIGINT | 流水行ID，主键 |
| receipt_no | VARCHAR(20) | 小票号 |
| store_id | INT | 门店ID |
| product_id | INT | 商品ID |
| member_id | BIGINT | 会员ID，非会员为NULL |
| staff_id | INT | 收银员工号 |
| sale_date | DATE | 销售日期 |
| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |
| pay_type | VARCHAR(10) | 支付方式：微信/支付宝/现金/银行卡/储值卡 |
| is_return | CHAR(1) | 是否退货行：Y/N |

示例数据：

| sale_id | receipt_no | store_id | product_id | member_id | staff_id | sale_date | sale_time | qty | unit_price | sale_amount | pay_type | is_return |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 110001 | R20240622S001 | 1 | 3001 | M10023 | 12 | 2024-06-22 | 09:15:00 | 2 | 3.50 | 7.00 | 微信 | N |
| 110002 | R20240622S001 | 1 | 3105 | M10023 | 12 | 2024-06-22 | 09:15:00 | 1 | 12.80 | 12.80 | 微信 | N |
| 110003 | R20240622S002 | 1 | 4502 | NULL | 15 | 2024-06-22 | 12:30:00 | 1 | 25.00 | 25.00 | 支付宝 | N |
| 110004 | R20240622S003 | 2 | 5201 | M10188 | 21 | 2024-06-22 | 15:40:00 | 1 | 35.00 | 35.00 | 储值卡 | N |

（同一张小票R20240622S001的两行pay_type一致，均为微信，符合小票级属性的约定。）

### 3. 解题思路

先定口径：因为pay_type是小票级属性且在明细行重复，小票数必须用COUNT(DISTINCT receipt_no)而不是COUNT(*)，否则分母被商品行数灌水；金额同理先按小票归集或直接SUM行金额（行金额求和不受pay_type重复影响，因为每行只计一次）；占比=该方式小票数÷总小票数，分子分母过滤条件必须完全一致。实现路径：写法一按pay_type分组统计后，用CROSS JOIN一个"总数子查询"提供分母；写法二用窗口函数SUM() OVER()在分组结果上生成总分母，少一次自连接。**【避坑指南】** 两个子查询（分子与分母）的WHERE条件必须一字不差——一边含退货过滤一边不含，占比总和就不等于100%，这是占比类指标的头部错误来源；另外pay_type若存在NULL或"其他"脏值，分组结果会多出一行，应先与业务确认是否纳入统计。

### 4. 参考解法

**写法一：GROUP BY+CROSS JOIN总数子查询（不依赖窗口函数）**

```sql
-- 写法一：分子按支付方式分组，分母用CROSS JOIN的总数子查询
SELECT
    s.pay_type,                                          -- 支付方式
    s.receipt_cnt,                                       -- 该方式小票数
    ROUND(s.receipt_cnt / t.total_cnt * 100, 2) AS pct   -- 占比=该方式票数/总票数
FROM (
    -- 分子：按支付方式去重数小票
    SELECT
        pay_type,
        COUNT(DISTINCT receipt_no) AS receipt_cnt
    FROM sales
    WHERE sale_date >= '2024-06-16'
      AND sale_date <  '2024-06-23'
      AND is_return  = 'N'
    GROUP BY pay_type
) AS s
CROSS JOIN (
    -- 分母：同口径的总小票数（注意过滤条件与分子完全一致）
    SELECT COUNT(DISTINCT receipt_no) AS total_cnt
    FROM sales
    WHERE sale_date >= '2024-06-16'
      AND sale_date <  '2024-06-23'
      AND is_return  = 'N'
) AS t
ORDER BY s.receipt_cnt DESC;                             -- 票数多的支付方式排前
```

结果解读：输出每个支付方式的票数与占比，占比合计应为100%（可自检）；微信/支付宝通常合计超七成，现金占比按业态差异明显。

**写法二：先分组，再用窗口SUM() OVER()生成总分母（MySQL 8.0）**

```sql
-- 写法二：窗口函数在聚合结果上补一列总票数，避免第二次扫描
SELECT
    t.pay_type,                                                          -- 支付方式
    t.receipt_cnt,                                                       -- 该方式小票数
    ROUND(t.receipt_cnt * 100.0 / SUM(t.receipt_cnt) OVER (), 2) AS pct  -- OVER()空窗口=对全部分组求和
FROM (
    SELECT
        pay_type,
        COUNT(DISTINCT receipt_no) AS receipt_cnt
    FROM sales
    WHERE sale_date >= '2024-06-16'
      AND sale_date <  '2024-06-23'
      AND is_return  = 'N'
    GROUP BY pay_type
) AS t
ORDER BY t.receipt_cnt DESC;
```

结果解读：**【加分点】** SUM(...) OVER()不带分区即"对当前结果集所有行求和"，一行SQL同时得到分子与分母；理解它就理解了窗口函数与GROUP BY的叠加顺序——先分组聚合、再在聚合结果上开窗。

### 5. 性能分析与优化

写法一扫描sales两遍（分子一遍、分母一遍），分母子查询还会对同批数据再做一次COUNT(DISTINCT)去重，代价约为写法二的两倍；写法二只扫一遍，去重与分组后窗口求和都在小结果集上进行。优化建议：sales建 (sale_date, is_return) 复合索引先做周窗口剪枝；若支付分析要按月/按城市例行，预聚合 dws_paytype_sales(月份, 城市, pay_type, 小票数, 金额) 把查询变成轻量汇总；另一个思路是把pay_type规范化到"小票头表"（一张小票一行），从根上消除COUNT(DISTINCT)的去重开销，同时保证pay_type与金额口径天然一致；脏值治理上给pay_type加CHECK约束或字典表外键。

### 6. 面试延伸考点

- **追问：为什么小票数必须COUNT(DISTINCT receipt_no)？** 回答要点：pay_type与金额在明细行上重复，COUNT(*)数的是商品行数；除非先把数据卷到小票级，否则去重计数是唯一正确解。
- **追问：各支付方式“金额占比”和“票数占比”会一样吗？** 回答要点：通常不一样——现金多为小额即时支付、储值卡多为大额采购，金额占比更能反映资金与通道费影响，汇报时两个维度都要给。
- **追问：占比加起来不是100%可能是什么原因？** 回答要点：分子分母过滤条件不一致、存在NULL或未知支付方式被各自处理、四舍五入误差；排查顺序是先对分子分母总量再查脏值。
- **追问：不用窗口函数怎么一行算占比？** 回答要点：写法一的CROSS JOIN；或在MySQL里用子查询标量(SELECT COUNT...)作分母；窗口函数是8.0后的简洁写法，三者语义等价。

### 7. 业务拓展思考

支付结构是门店数字化程度的镜像：现金占比高的社区店要评估老年客群的保留方案与自助收银的适老化改造；储值卡占比高说明会员预付体系健康，可加大充值满赠。财务侧结合费率可算"综合支付成本率"，为通道谈判提供数据；风控侧现金占比异常波动的门店是资金稽核的重点对象。口径延展上，支付方式×时段的交叉分布（呼应RET-06）能发现早晚高峰通道瓶颈；支付方式×客单价的分层则直接服务"满多少推什么支付工具"的运营策略。

## RET-13 单笔金额Top10小票明细

### 1. 业务背景

连锁超市的大客户与防损岗每天收盘后要筛出当日金额最高的10张小票（谁、何时、什么数据结论）：金额异常大的订单可能是企事业单位团购线索（安排客户经理回访转化大客户），也可能是促销套利或内外勾结的异常交易（触发防损复核）（为什么）。单笔金额以小票为单位（一张小票多行商品合计），需要先把明细卷到小票级再排序取Top，是"先聚合后排名"的入门必练题。

### 2. 表结构说明

**销售小票明细表 sales**（同前，本题使用receipt_no、store_id、sale_date、sale_amount）

| 字段名 | 类型 | 含义 |

| sale_time | TIME | 销售时间 |
| qty | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 成交单价 |
| sale_amount | DECIMAL(10,2) | 该行销售金额，退货行为负数 |
| is_return | CHAR(1) | 是否退货行：Y/N |

示例数据：

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 120001 | R20240625S001 | 1 | 3001 | M10023 | 12 | 2024-06-25 | 09:15:00 | 2 | 3.50 | 7.00 | N |

（R20240625S002含两行商品合计562.80元，是典型的团购型大单样本。）

### 3. 解题思路

先定口径：单笔金额=同一receipt_no下正向销售金额合计（退货小票不含，退货是负向事件要单独分析）；Top10指金额降序的前10张。实现路径：第一步GROUP BY receipt_no把明细卷到小票级并SUM金额；第二步排序取前10——写法一用ORDER BY加LIMIT，最短最快；写法二用ROW_NUMBER()在聚合结果上编号再筛rn<=10，为后续"并列同名次""Top N百分比"等变体打好基础。**【避坑指南】** LIMIT 10遇到金额并列时会机械截断到恰好10行，第10名与第11名并列时谁上榜取决于排序的稳定性，防损与奖励场景都要用DENSE_RANK()明确并列规则；另外SELECT里若要带store_id等属性，要么它函数依赖于分组键（同小票同店），要么用MAX()聚合带出，直接写非聚合列在ONLY_FULL_GROUP_BY下会报错。

### 4. 参考解法

**写法一：按小票聚合+ORDER BY+LIMIT 10（最短路径）**

```sql
-- 写法一：先把明细卷到小票级，再按金额降序取前10
SELECT
    receipt_no,                                     -- 小票号
    MAX(store_id)  AS store_id,                     -- 小票所属门店（同小票相同，MAX带出）
    MAX(sale_date) AS sale_date,                    -- 销售日期
    COUNT(*)       AS line_cnt,                     -- 该小票商品行数，辅助判断是否团购
    ROUND(SUM(sale_amount), 2) AS receipt_amount    -- 单笔金额=小票各行合计
FROM sales
WHERE sale_date = '2024-06-25'      -- 当日
  AND is_return  = 'N'              -- 只看正向销售
GROUP BY receipt_no                 -- 卷到小票级
ORDER BY receipt_amount DESC
LIMIT 10;                           -- 金额最高的前10张
```

结果解读：榜单直接给出当日大单线索；line_cnt与member_id是否为空能辅助判断"团购嫌疑"（行数多且无会员登记的整箱采购），是防损复核的入参。

**写法二：聚合后用ROW_NUMBER()编号，外层筛前10（可扩展）**

```sql
-- 写法二：在聚合结果上开窗编号，再按名次过滤
SELECT
    t.receipt_no,                                   -- 小票号
    t.store_id,                                     -- 门店
    t.sale_date,                                    -- 日期
    t.receipt_amount,                               -- 单笔金额
    t.rn                                            -- 名次（1=最大）
FROM (
    SELECT
        receipt_no,                                 -- 小票号
        MAX(store_id)  AS store_id,                 -- 门店属性用MAX带出
        MAX(sale_date) AS sale_date,
        ROUND(SUM(sale_amount), 2) AS receipt_amount,
        ROW_NUMBER() OVER (ORDER BY SUM(sale_amount) DESC) AS rn -- 对聚合值降序编号
    FROM sales
    WHERE sale_date = '2024-06-25'
      AND is_return  = 'N'
    GROUP BY receipt_no
) AS t
WHERE t.rn <= 10                   -- 取前10名
ORDER BY t.rn;                     -- 按名次正序输出
```

结果解读：**【面试高频】** 与写法一结果一致，但把"取前10"变成了"按名次过滤"，改并列规则只需换窗口函数（DENSE_RANK并列不跳号），改"Top 10%"只需rn<=总数10%，扩展成本几乎为零。

### 5. 性能分析与优化

两写法都要扫当日明细并按receipt_no哈希聚合，差异在取Top的方式：ORDER BY+LIMIT在聚合后只需维护10个元素的Top-N堆，内存极小；ROW_NUMBER需要对全部分组排序后再过滤，当日小票量在几十万级别时窗口排序代价仍可接受，但明显大于LIMIT。优化建议：sales建 (sale_date, receipt_no) 复合索引，让当日过滤先走索引；若大单监控每天跑，可在ETL层维护小票级汇总表 dws_receipt_daily(日期, receipt_no, 门店, 金额)，Top10退化为对单日小票表排序；进一步想覆盖并列场景，用DENSE_RANK并接受"并列可能超过10行"的业务约定；绝不要为了取Top把全表数据拉到应用层排序，数据库内完成是底线。

### 6. 面试延伸考点

- **追问：第10名与第11名金额并列时，LIMIT和窗口函数分别怎么表现？** 回答要点：LIMIT 10只返回10行，并列者被随机丢弃；DENSE_RANK会给两者同名次，WHERE rn<=10返回11行，"宁可多给不漏公平"，奖励与风控场景应选后者并提前约定。
- **追问：怎么把Top10小票展开成商品明细？** 回答要点：把本题结果作为筛选集合，再JOIN回sales按receipt_no取行，即"两段式：先定位小票、再拉明细"；也可用窗口在明细级先标小票名次再过滤。
- **追问：大单一定要按绝对金额吗？** 回答要点：可换成"小票金额的99分位以上"作为异常阈值，或按"该店当日均值×N倍"做相对判定，绝对榜单在大小门店间不可比。
- **追问：为什么SELECT里能直接用MAX(store_id)带出属性？** 回答要点：store_id在receipt_no上函数依赖（一张小票只属于一家店），MAX不改变值只是满足聚合语法；若属性不函数依赖（如商品名），MAX会取任意一个值造成误导。

### 7. 业务拓展思考

Top小票是大客户运营与防损的双入口：连续多日出现相似大单且会员留档，应主动建团购档案并提供批量价；高频"整数金额、整箱数量、夜间结账"的订单则要抽小票复核。与库存联动，大单往往瞬间击穿单店库存（呼应RET-04），补货模型应考虑"大单预占"；与会员联动，大单会员的复购周期决定回访时点。口径延展上，把Top N扩展为"金额分布直方图"（0-50元、50-100元等区间的小票数），比榜单更能刻画客群结构，用CASE WHEN分桶即可实现，是本题的自然进阶。

## RET-14 各门店注册会员数与当月消费会员数

### 1. 业务背景

### 3. 解题思路

先定口径：注册会员数=members按register_store_id分组的会员计数；消费会员数=当月sales中member_id非空的去重数按消费store_id分组；两口径的"门店"含义不同，输出表要注明（本题按注册门店归属展示，即"本店注册的会员有多少、他们当月在本店体系消费的有多少"可选其一，实现上写清即可）。实现路径：写法一用两个聚合子查询（注册侧、消费侧）分别GROUP BY门店，再以stores为主表LEFT JOIN对齐，零值补0；写法二以members为主表LEFT JOIN当月销售明细，一次分组对两列分别COUNT(DISTINCT)。**【避坑指南】** 写法二的明细JOIN会让每位会员膨胀成多行（会员有N条消费就有N行），但COUNT(DISTINCT)天然消化扇出，此时绝不能用COUNT(*)或COUNT(s.member_id)直接计数——后者会把多行算多次；消费侧的时间与退货条件必须写在LEFT JOIN的ON里，写进WHERE会把"当月未消费会员"的行清空，活跃率恒为100%。

### 4. 参考解法

**写法一：注册侧与消费侧分别聚合，再以门店主表对齐（层次清晰）**

```sql
-- 写法一：两个子查询各自聚合，主表用门店串起两侧口径
SELECT
    st.store_id,                                    -- 门店ID
    st.store_name,                                  -- 门店名称
    IFNULL(r.reg_cnt, 0) AS registered_cnt,         -- 注册会员数（无注册补0）
    IFNULL(c.buy_cnt, 0) AS consumed_cnt,           -- 当月消费会员数
    ROUND(IFNULL(c.buy_cnt, 0) / IFNULL(r.reg_cnt, 0) * 100, 2) AS active_rate_pct -- 活跃率%
FROM stores AS st
LEFT JOIN (
    -- 注册侧：按注册门店计数
    SELECT register_store_id AS store_id, COUNT(*) AS reg_cnt
    FROM members
    GROUP BY register_store_id
) AS r ON r.store_id = st.store_id
LEFT JOIN (
    -- 消费侧：按消费门店去重数会员
    SELECT sa.store_id, COUNT(DISTINCT sa.member_id) AS buy_cnt
    FROM sales AS sa
    WHERE sa.sale_date >= '2024-06-01'
      AND sa.sale_date <  '2024-07-01'
      AND sa.is_return  = 'N'
      AND sa.member_id IS NOT NULL                   -- 只算会员消费
    GROUP BY sa.store_id
) AS c ON c.store_id = st.store_id
ORDER BY active_rate_pct DESC;                       -- 活跃率低的门店排前，即召回重点
```

结果解读：registered_cnt与consumed_cnt的差是"当月未活跃会员池"；活跃率排序让运营一眼锁定召回优先门店，注意小基数门店（注册会员个位数）的活跃率波动大，解读需结合绝对数。

**写法二：会员表LEFT JOIN当月销售，一次分组双去重计数**

```sql
-- 写法二：以会员为主表连消费明细，COUNT(DISTINCT)双列计数
SELECT
    m.register_store_id AS store_id,                     -- 门店（按注册门店归属）
    COUNT(DISTINCT m.member_id) AS registered_cnt,       -- 该店注册会员总数
    COUNT(DISTINCT s.member_id) AS consumed_cnt          -- 其中当月有消费的会员数（全NULL时结果为0）
FROM members AS m
LEFT JOIN sales AS s
       ON s.member_id = m.member_id                      -- 会员连其消费明细，一位会员可能膨胀成多行
      AND s.sale_date >= '2024-06-01'                    -- 时间条件写在ON里！
      AND s.sale_date <  '2024-07-01'
      AND s.is_return  = 'N'
GROUP BY m.register_store_id                          -- 按注册门店分组
ORDER BY registered_cnt DESC;
```

结果解读：**【加分点】** 明细JOIN造成扇出，但COUNT(DISTINCT m.member_id)与COUNT(DISTINCT s.member_id)分别按"注册事实"与"消费事实"去重，结果不受行数膨胀影响；consumed_cnt自动忽略NULL，未消费会员不计入——两个COUNT的语义差正是本题要的差值。

### 5. 性能分析与优化

写法一扫members一遍、sales一遍，JOIN都发生在门店级小结果集上，整体代价低且每段口径可独立复用；写法二把会员表与当月明细JOIN，中间结果行数≈会员当月消费行数，扇出明显但DISTINCT去重有额外哈希开销，数据量大时慢于写法一。优化建议：members建 (register_store_id) 索引、sales建 (store_id, sale_date, member_id) 复合索引，让消费侧子查询按门店+月份剪枝；会员月活跃属于例行指标，应建 dws_store_member_active(月份, 门店, 注册数, 消费会员数) 每日增量维护；若要按"消费门店"口径另出一版，把消费侧子查询的GROUP BY换到sa.store_id即可（写法一已是如此），体现口径分离的好处；避免在JOIN键上包函数（如UPPER(member_id)），会破坏索引与合并连接机会。

### 6. 面试延伸考点

- **追问：写法二里COUNT(DISTINCT s.member_id)在全店会员都未消费时返回什么？** 回答要点：返回0（COUNT忽略NULL），而不是NULL或报错，正好满足"未活跃显示0"的报表需求；若换COUNT(s.member_id)同样是0，但一旦有消费行就会因扇出多算，必须加DISTINCT。
- **追问：注册门店口径和消费门店口径，业务上分别怎么用？** 回答要点：注册口径衡量"拉新属地"，用于拉新考核与召回短信投放（按注册地触达）；消费口径衡量"用卡行为"，用于门店服务评价；两者差异大的门店说明会员跨店流动明显，适合做商圈分析。
- **追问：为什么消费侧的时间条件必须写在ON里？** 回答要点：写在WHERE里会把LEFT JOIN产生的NULL行过滤掉，未消费会员整行消失，活跃率恒为100%；LEFT JOIN的右表过滤写ON是固定套路。
- **追问：想看连续3个月都活跃的会员数怎么办？** 回答要点：对"会员×月份"活跃事实做按会员的月份计数（COUNT(DISTINCT月份)=3）或用窗口连续判断，属于中级内容，入门阶段说明思路即可。

### 7. 业务拓展思考

"注册-消费"的落差池是会员运营的弹药库：对注册后从未消费的会员做首单礼激活，对曾经活跃但近期沉默的做品类定向召回，两套策略对应的SQL条件不同（累计消费=0 vs 近90天消费=0）。与采购联动，活跃会员集中的门店加大会员价商品备货；与RET-11的月度拉新联动可算"注册到首购的中位时长"，衡量会员旅程效率。口径延展上，活跃率可按"30天/90天/累计"三档并行，分别服务短期召回、中期经营与长期资产评估，把口径选择写进指标字典是数据团队的职责。

### 3. 解题思路

先定口径：覆盖数=统计期内该商品有过有效销售记录的门店去重数（卖过一次即算覆盖，不看销量）；覆盖率=覆盖数÷在营门店总数；分母用stores全表计数而不是销售明细里出现过的门店数（后者会把零销售门店漏掉，覆盖率虚高）；只考核is_on_sale='Y'的在售商品。实现路径：写法一先把明细聚成"商品×覆盖门店数"，再LEFT JOIN商品主数据并用标量子查询提供分母算覆盖率；写法二反过来，以商品主数据为左表LEFT JOIN聚合子查询，无销售商品补0，再连总数。**【避坑指南】** 核心是COUNT(store_id)必须加DISTINCT——同一商品在同一门店有几十行明细，不去重会把覆盖数放大几十倍；另一个隐性错误是分母写成"(SELECT COUNT(DISTINCT store_id) FROM sales)"，零销售门店被剔除，覆盖率高估，业务决策就会失真。

### 4. 参考解法

**写法一：聚合子查询算覆盖数，标量子查询提供总门店数分母**

```sql
-- 写法一：先按商品聚合覆盖数，再连商品表并用标量子查询补分母
SELECT
    p.product_id,                                        -- 商品ID
    p.product_name,                                      -- 商品名称
    IFNULL(s.store_cnt, 0) AS store_cnt,                 -- 销售门店覆盖数（无销售补0）
    ROUND(IFNULL(s.store_cnt, 0)
          / (SELECT COUNT(*) FROM stores) * 100, 1) AS coverage_pct -- 覆盖率=覆盖数/全部门店数
FROM products AS p
LEFT JOIN (
    -- 明细 → 商品级覆盖门店数（关键：门店去重）
    SELECT
        product_id,
        COUNT(DISTINCT store_id) AS store_cnt            -- 同店多行只算一次
    FROM sales
    WHERE sale_date >= '2024-06-01'
      AND sale_date <  '2024-07-01'
      AND is_return  = 'N'
    GROUP BY product_id
) AS s ON s.product_id = p.product_id                    -- LEFT JOIN保留零销售商品
WHERE p.is_on_sale = 'Y'                                 -- 只考核在售商品
ORDER BY store_cnt DESC, p.product_id;                   -- 覆盖数降序，同数按ID稳定排序
```

结果解读：鲜牛奶覆盖3/5店=60%，洗衣液仅1店=20%；榜单尾部（覆盖率低但公司战略权重高）的商品就是铺货推动的目标清单，头部商品则进入全渠道合同谈判。

**写法二：以商品为左表，标量子查询逐行探测覆盖数（思路对偶）**

```sql
-- 写法二：不预聚合，用相关标量子查询逐商品探测覆盖门店数
SELECT
    p.product_id,                                        -- 商品ID
    p.product_name,                                      -- 商品名称
    (SELECT COUNT(DISTINCT sa.store_id)                  -- 相关子查询：该商品销售过的门店数
     FROM sales AS sa
     WHERE sa.product_id = p.product_id                  -- 与外层商品关联
       AND sa.sale_date >= '2024-06-01'
       AND sa.sale_date <  '2024-07-01'
       AND sa.is_return  = 'N') AS store_cnt,
    (SELECT COUNT(*) FROM stores) AS total_store_cnt,    -- 分母：在营门店总数
    ROUND((SELECT COUNT(DISTINCT sa.store_id)
     FROM sales AS sa
     WHERE sa.product_id = p.product_id
       AND sa.sale_date >= '2024-06-01'
       AND sa.sale_date <  '2024-07-01'
       AND sa.is_return  = 'N')
          / (SELECT COUNT(*) FROM stores) * 100, 1) AS coverage_pct -- 覆盖率%
FROM products AS p
WHERE p.is_on_sale = 'Y'
ORDER BY store_cnt DESC;
```

结果解读：**【加分点】** 相关子查询把"每个商品各自数门店"的语义写得直白，可读性好；但外层每一行都要探测一遍sales，商品数上万时代价显著，生产环境优先用写法一的"先聚合后JOIN"。

### 5. 性能分析与优化

写法一扫描一遍月度明细做分组聚合，再与商品表按主键JOIN，标量子查询COUNT(*) FROM stores是常量级代价，整体为线性扫描，是两写法中更优的形态；写法二对每个在售商品执行一次sales探测，复杂度≈商品数×索引查找，商品少且(product_id, sale_date)索引良好时可接受，商品多则劣化明显。优化建议：sales建 (product_id, sale_date, is_return) 复合索引服务分组与探测；覆盖率报表按月例行时，预聚合 dws_product_coverage(月份, product_id, store_cnt)，分母常量在ETL写入；若同时要"覆盖门店明细清单"下钻，把COUNT(DISTINCT)换成GROUP_CONCAT(DISTINCT store_id)可一并列出门店ID（注意长度上限）；停售商品过滤放在主数据侧而非销售侧，保持两个集合的语义清晰。

### 6. 面试延伸考点

- **追问：COUNT(DISTINCT store_id)和COUNT(store_id)差在哪？** 回答要点：后者数行数，同一门店多行重复计入，覆盖数被放大到"明细行数"量级；凡是"多少个X"的问题都要条件反射地检查是否需要DISTINCT。
- **追问：覆盖率的分母为什么不能用销售明细里的门店数？** 回答要点：零销售门店不出现在明细里，用它做分母会把"全体都没卖"的商品也算出高覆盖率；分母必须来自门店主数据全量，这是覆盖率类指标的分母纪律。
- **追问：想看每个品类平均覆盖率怎么写？** 回答要点：把本题结果作为子查询，外层按category_name分组AVG(coverage_pct)——注意是对商品级覆盖率求均值，与"品类总覆盖/品类应覆盖"的组合口径不同，属于比率再聚合的经典陷阱。
- **追问：覆盖数高但销售额低的商品说明什么？** 回答要点：铺得广但卖不动，问题在动销与陈列而非分销；要结合RET-10的动销率与单店产出（销售额/覆盖数）拆解，三个指标构成分销质量三角。

### 7. 业务拓展思考

覆盖率是分销管理的核心KPI：新品上市按周追踪覆盖率爬坡曲线，未覆盖门店清单直接下发给业代执行铺货；区域限定品则考核"目标区域覆盖率"而非全网。与采购联动，高覆盖商品谈判年度返利与陈列费，低覆盖高毛利商品用铺货奖励推动；与RET-04库存联动可发现"系统有货但不卖"的上架执行漏洞。口径延展上，"覆盖"可升级为"连续N周有销售才算覆盖"（剔除一次性团购的虚覆盖），或按业态分层计算（便利店覆盖与大卖场覆盖分开考核），让指标贴合真实的分销结构。

**结语**

入门级的15道题覆盖了SELECT基本功的全部高频考点：过滤与排序（RET-01/04/13）、去重与聚合（RET-02/10/14/15）、条件聚合与CASE WHEN（RET-03/06/07）、两表JOIN与扇出（RET-01/09/14）、子查询与分母纪律（RET-09/15）、时间函数与降粒（RET-06/11）、窗口函数入门（RET-05/08/12）。面试答题时请保持两个习惯：先声明指标口径（是否含退货、分母是谁、边界怎么切），再写SQL；写完检查GROUP BY是否覆盖非聚合列、LEFT JOIN的右表过滤是否写在ON里、COUNT是否需要DISTINCT。这些口径意识与踩坑经验，是通往中级（多表复杂关联、窗口进阶、漏斗留存）题型的地基。
