## RET-16 门店同店销售额同比增长

### 1. 业务背景

你是区域连锁超市总部经营分析组的专员。每月月初经营例会前，运营总监要一份上个月各门店销售额同比增速表：如果直接拿全量销售额算同比，2023年下半年新开的门店去年同期没有销售，既算不出增速，其爬坡期的高增长还会掩盖老店的真实经营状况。因此需要按"同店口径"（开业时间早于去年同期、即开业满一年以上）计算2024年3月各门店销售额同比增长率，用来识别真正经营向好的老店、支撑门店评优与区域资源投放决策，并在汇报中与全量增速并列展示增长质量。

### 3. 解题思路

先明确三个口径边界：一是"同店"定义，通常取开业日期早于去年同期月初（本题为 open_date < '2023-03-01'）的门店，新店和转改店都剔除；二是退货处理，amount 退货为负数，SUM 天然完成冲减，不需要额外过滤；三是时间边界，统一用左闭右开区间 `>= '2024-03-01' AND < '2024-04-01'`，避免手工拼月末日期出错。实现路径有两条：解法一对本期与去年同期分别聚合成两个结果集再 JOIN，这是同期对比最通用、最稳的写法；解法二把13个月的月度销售额排成序列，用 LAG(amt, 12) 上溯12行取去年同期，代码更短但强依赖"门店每个月都有数据"的连续性。**【避坑指南】**LAG 偏移量按"行数"而非"月份"回退，某店某月缺数就会整体错位，生产环境应先补齐月份维度或改用解法一；另外同比分母为去年同期销售额，若去年无销售则除零，用内连接排除或 NULLIF 保护。

### 4. 参考解法

解法一：两段聚合 + JOIN（同期对比的通用标准写法）

```sql
WITH cur_sales AS (                                  -- CTE1：2024年3月各门店销售额
    SELECT store_id,
           SUM(amount) AS cur_amt                    -- 退货金额为负，SUM自动冲减退货
    FROM sales
    WHERE sale_date >= '2024-03-01'
      AND sale_date <  '2024-04-01'                  -- 左闭右开区间，防止边界重复或遗漏
    GROUP BY store_id
),
prev_sales AS (                                      -- CTE2：2023年3月（去年同期）销售额
    SELECT store_id,
           SUM(amount) AS prev_amt
    FROM sales
    WHERE sale_date >= '2023-03-01'
      AND sale_date <  '2023-04-01'
    GROUP BY store_id
)
SELECT s.store_id,                                   -- 门店ID
       s.store_name,                                 -- 门店名称
       c.cur_amt,                                    -- 本期销售额
       p.prev_amt,                                   -- 去年同期销售额
       ROUND((c.cur_amt - p.prev_amt) / p.prev_amt * 100, 2) AS yoy_pct  -- 同比增长率（%）
FROM cur_sales c
JOIN prev_sales p ON p.store_id = c.store_id         -- 内连接：去年同期无销售的门店自然排除
JOIN stores s ON s.store_id = c.store_id             -- 关联门店属性取名称
WHERE s.open_date < '2023-03-01';                    -- 同店口径：去年同期前已开业
```

结果解读：输出的是"老店名单"上的同比增速，新开门店不参与计算。业务上若同店增速为正但全量增速明显更高，说明增长主要靠开新店驱动，存量门店经营质量需要警惕。

解法二：月度序列 + LAG 窗口函数（一次扫表取同期）

```sql
WITH monthly AS (                                    -- 各门店按自然月的销售额序列
    SELECT store_id,
           DATE_FORMAT(sale_date, '%Y-%m') AS ym,    -- 年月键，作为排序依据
           SUM(amount) AS amt
    FROM sales
    WHERE sale_date >= '2023-03-01'                  -- 覆盖2023-03至2024-03共13个月
      AND sale_date <  '2024-04-01'
    GROUP BY store_id, DATE_FORMAT(sale_date, '%Y-%m')
),
lagged AS (                                          -- 上溯12行得到去年同期值
    SELECT store_id, ym, amt,
           LAG(amt, 12) OVER (PARTITION BY store_id  -- 每个门店独立一条时间线
                              ORDER BY ym) AS prev_amt
    FROM monthly
)
SELECT s.store_id,
       s.store_name,
       l.amt AS cur_amt,                             -- 2024年3月销售额
       l.prev_amt,                                   -- LAG取到的2023年3月销售额
       ROUND((l.amt - l.prev_amt) / l.prev_amt * 100, 2) AS yoy_pct
FROM lagged l
JOIN stores s ON s.store_id = l.store_id
WHERE l.ym = '2024-03'                               -- 只保留目标月
  AND s.open_date < '2023-03-01';                    -- 同店口径过滤
```

结果解读：与解法一数值一致，但省去了一次扫表。前提是每个门店13个月数据完整，若某店某月停业无销售，LAG 会取到错误月份，必须先补齐空月或回退到解法一。

### 5. 性能分析与优化

解法一扫表两遍（各扫1个月），数据量为"2个月明细"；解法二扫表一遍但覆盖13个月明细，还需对 (store_id, ym) 排序做窗口，排序代价约为 O(N·logN)。当月度明细远大于目标月时，解法一反而更快，且不受缺月影响，是首选。优化建议：给 sales 建 (sale_date, store_id, amount) 复合索引或按月做 RANGE 分区，让日期过滤直接裁剪分区；两段聚合先 GROUP BY 再 JOIN，驱动表是聚合后的小结果集（门店数级别），远小于明细行数；只 SELECT 需要的列，避免回表取整行；若报表固定按月出，可预聚合一张 store_month_sales 汇总表，同比查询退化为对汇总表的两次小扫描。

### 6. 面试延伸考点

- **为什么同比一定要用同店口径？直接算全量同比会有什么问题？** 回答要点：新店爬坡期基数低、增速虚高，会夸大全量增速；老店衰退会被开店红利掩盖；同店增速衡量存量经营质量，全量增速衡量规模扩张，两者必须并列披露。
- **如果门店发生过搬迁或面积改造，同店口径怎么处理？** 回答要点：一般以"经营主体+地址+业态连续经营满一年"为可比标准，改造停业超一定天数（如30天）的门店当年移出同店池，口径必须在报表附录中固化并保持一致。
- **退货冲减在同比计算中还有什么隐藏问题？** 回答要点：退货常滞后发生，3月销售对应的退货可能发生在4月，严格口径应按"业务发生制"把退货冲回原销售月，否则月度增速会受当月退货随机性干扰。
- **LAG 与自连接取同期，各自的适用场景？** 回答要点：LAG 适合序列连续、偏移量固定的场景，写法简洁；自连接（或两段聚合）适合维度不连续、可能缺行的情况，稳健性更好。

### 7. 业务拓展思考

同店同比是零售经营质量的第一指标，但单看增速容易误判：应联动客单价、客流、连带率拆解增长来源（量价拆分），区分"人多花"还是"人少买贵"。运营上，同店下滑门店可触发陈列调整、社区团品引流、会员唤醒等动作；采购上，下滑品类的订单量与安全库存需要同步下调。口径可延展出"同店同品类同比""同店可比口径毛利率同比"，并进一步建立同店池的白名单维护机制，作为集团层面统一的可比口径底座。

## RET-17 门店坪效与人效双维排名

### 1. 业务背景

你是连锁超市区域运营部的数据分析师。季度复盘会上，区域经理要对比辖区5家门店的资源使用效率：同样一个亿的销售，是开大店摊出来的还是小店高密度做出来的？坪效（每平方米营业面积产出的销售额）和人效（每名在册店员产出的销售额）是两个最常用的效率标尺。运营需要在2024年第二季度维度上计算各门店坪效、人效并给出排名，找出"面积大但坪效垫底"或"人员冗余人效偏低"的门店，作为下季度缩编排班、面积调改或汰换评估的量化依据。

### 3. 解题思路

先定口径：统计区间取2024年4月1日至6月30日整个季度；坪效 = 区间销售额 ÷ 营业面积，人效 = 区间销售额 ÷ 在册店员数，两个指标都在门店粒度先聚合销售额再与门店主数据 JOIN 计算比值，比值算完再做窗口排名。**【面试高频】**排名函数三兄弟 RANK、DENSE_RANK、ROW_NUMBER 的区别必须讲清：销售额并列时 RANK 会跳号（1,1,3），DENSE_RANK 不跳号（1,1,2），ROW_NUMBER 强制唯一（1,2,3），做门店评优一般用 RANK 或 DENSE_RANK，取"前3名门店"则必须用 ROW_NUMBER 去重。易错点：新店（如科技园店2月开业）季度不满会有爬坡干扰，严格口径应剔除或单独标注；JOIN 时若门店某季无销售，内连接会静默丢行，建议 LEFT JOIN 保留并 COALESCE 补0。

### 4. 参考解法

解法一：先聚合后JOIN，双指标一次输出并排名

```sql
WITH store_sales AS (                                -- CTE：2024Q2各门店销售额
    SELECT store_id,
           SUM(amount) AS total_amt                  -- 区间总销售额
    FROM sales
    WHERE sale_date >= '2024-04-01'
      AND sale_date <  '2024-07-01'                  -- 2024年第二季度，左闭右开
    GROUP BY store_id
)
SELECT s.store_id,                                   -- 门店ID
       s.store_name,                                 -- 门店名称
       t.total_amt,                                  -- 季度销售额
       s.area_m2,                                    -- 营业面积
       s.staff_cnt,                                  -- 在册店员数
       ROUND(t.total_amt / s.area_m2, 2) AS amt_per_m2,                       -- 坪效=销售额/面积
       RANK() OVER (ORDER BY t.total_amt / s.area_m2 DESC) AS pm_rank,        -- 坪效排名（并列跳号）
       ROUND(t.total_amt / s.staff_cnt, 2) AS amt_per_staff,                  -- 人效=销售额/店员数
       RANK() OVER (ORDER BY t.total_amt / s.staff_cnt DESC) AS staff_rank    -- 人效排名
FROM store_sales t
JOIN stores s ON s.store_id = t.store_id             -- 门店主数据提供面积与人数
ORDER BY pm_rank;                                    -- 按坪效排名升序展示
```

结果解读：两个排名并列输出后，"坪效高、人效低"的门店大概率是人员冗余或排班结构问题，"坪效低、人效高"则可能是面积过大动线浪费，两条线索指向不同的整改方向。

解法二：CTE分层 + DENSE_RANK + 聚合窗口对比区域均值

```sql
WITH store_sales AS (                                -- 第一步：门店季度销售额
    SELECT store_id, SUM(amount) AS total_amt
    FROM sales
    WHERE sale_date >= '2024-04-01' AND sale_date < '2024-07-01'
    GROUP BY store_id
),
calced AS (                                          -- 第二步：JOIN主数据并计算两个效率指标
    SELECT s.store_id, s.store_name, t.total_amt,
           ROUND(t.total_amt / s.area_m2, 2)   AS amt_per_m2,   -- 坪效
           ROUND(t.total_amt / s.staff_cnt, 2) AS amt_per_staff -- 人效
    FROM store_sales t
    JOIN stores s ON s.store_id = t.store_id
)
SELECT c.*,
       DENSE_RANK() OVER (ORDER BY c.amt_per_m2 DESC) AS pm_dense_rank,        -- 不跳号排名
       ROUND(c.amt_per_m2 - AVG(c.amt_per_m2) OVER (), 2) AS pm_gap_vs_avg,    -- 坪效与区域均值差
       ROUND(c.amt_per_staff - AVG(c.amt_per_staff) OVER (), 2) AS staff_gap_vs_avg -- 人效与均值差
FROM calced c
ORDER BY pm_dense_rank;
```

结果解读：均值差比名次更能表达"差多少"，负值门店即低于区域平均线，是复盘会上最直观的问责依据。**【加分点】**主动说明 DENSE_RANK 与 RANK 的并列处理差异，并按业务需要选择，是面试中的稳定加分项。

### 5. 性能分析与优化

两种解法都是"明细聚合一次 + 小表JOIN + 窗口排序"，代价集中在：sales 按3个月明细做 GROUP BY 的哈希聚合，以及窗口排序（5家门店极小，真实几千家门店也可接受）。优化建议：sales 上建 (store_id, sale_date, amount) 复合索引可走覆盖索引免回表；若门店数上千，先在 CTE 中聚合把行数压缩到门店级再 JOIN，杜绝大明细直接 JOIN 主数据；窗口函数基于同一份排序结果，MySQL 8.0 会复用窗口分区排序，但 ORDER BY 表达式完全一致才可复用，尽量统一表达式写法；季度报表可预聚合月度汇总表，把明细扫描量降一个数量级。

### 6. 面试延伸考点

- **RANK、DENSE_RANK、ROW_NUMBER 在评优场景里怎么选？** 回答要点：并列名次要保留用 RANK/DENSE_RANK；要严格取N名（如发3个奖）用 ROW_NUMBER 并指定唯一排序键；排名键加次级键（如销售额、门店号）保证结果可复现。
- **坪效排名能直接跨业态比较吗？** 回答要点：不能简单比较，大卖场、社区店、便利店的坪效基准差异极大，应分业态内排名，或改用坪效达成率（实际/内部预算）。
- **为什么人效用"在册店员数"可能失真？** 回答要点：在册人数不等于实际出勤工时，兼职、排班波峰、外包保洁都会扭曲人效，精细口径应改用"总工时"算每小时销售额。
- **如果要求"坪效前3名门店"，SQL怎么写最稳？** 回答要点：CTE里用 ROW_NUMBER() OVER (ORDER BY 坪效 DESC, total_amt DESC) 保证并列时唯一，外层 WHERE rn <= 3。

### 7. 业务拓展思考

坪效与人效是"资产效率"和"人力效率"的交叉验证：两者同低说明选址或经营模型有问题，单边低则指向局部资源错配，可与租金坪效（销售额/租金）合并成单店盈利预警模型。运营动作上，坪效垫底门店优先做品类结构与动线调改，人效垫底门店优先优化排班与自动收银渗透率。口径可延展为"日坪效（剔除营业天数差异）""可比口径坪效同比"，把规模差异和时间差异同时拉平，让排名更公平。

## RET-18 分品类连带率（每小票平均商品件数）

### 1. 业务背景

你是便利店总部商品部的数据分析师。门店近期在收银台旁做了"口香糖+饮料"关联陈列试点，运营想用数据验证效果：连带率（每张小票平均购买的商品件数）是最常用的衡量指标——顾客不会只为一件商品进店，小票上件数越多，说明关联陈列、组合促销的"顺带购买"越成功。现在需要按品类计算2024年6月的连带率，找出连带率最低的品类，作为关联陈列调整和第二件优惠选品的输入，并在试点店与对照店之间做对比复盘。

### 2. 表结构说明

| --- | --- | --- |

### 3. 解题思路

先定口径：连带率 = 品类销售总件数 ÷ 含该品类商品的小票数，衡量"买了这个品类的人平均顺带买几件"；它有一个必须与面试官确认的对照口径——分母换成"全部小票数"时，指标含义变成"每张小票平均贡献该品类几件"（渗透×深度），两个口径数值和业务解读完全不同，动手前先问清楚。**【避坑指南】**一张小票同一商品可能出现多行（不同批次、不同价格），所以件数要 SUM(qty)、小票数必须 COUNT(DISTINCT sale_id)，直接 COUNT(*) 会把重复行当多张小票；退货小票（金额为负）若混入会把件数拉低甚至为负，应按口径约定剔除或保留冲减。实现路径：解法一先按"小票×品类"聚合出每张小票在每个品类的件数，再按品类求平均，逻辑分层最清晰；解法二一层聚合直接用 SUM/COUNT(DISTINCT) 完成，并附全量小票口径对照。

### 4. 参考解法

解法一：小票×品类两级聚合（分母=含该品类的小票数）

```sql
WITH ticket_cat AS (                                 -- 第一层：每张小票在每个品类上的件数
    SELECT s.sale_id,
           p.category,
           SUM(s.qty) AS qty                         -- 同品类多行商品件数合并
    FROM sales s
    JOIN products p ON p.product_id = s.product_id   -- 挂上品类维度
    WHERE s.sale_date >= '2024-06-01'
      AND s.sale_date <  '2024-07-01'
    GROUP BY s.sale_id, p.category                   -- 小票×品类粒度
)
SELECT category,                                     -- 品类
       SUM(qty) AS total_qty,                        -- 该品类被购买的总件数
       COUNT(*) AS ticket_cnt,                       -- 含该品类的小票数（每行=一张含该品类的小票）
       ROUND(SUM(qty) / COUNT(*), 2) AS attach_rate  -- 连带率=总件数/含该品类小票数
FROM ticket_cat
GROUP BY category
ORDER BY attach_rate DESC;                           -- 连带率低的品类排前面看
```

结果解读：日配、粮油这类"目的性购买"品类连带率通常偏低，休闲食品偏高。低连带品类是关联陈列和组合促销的重点试验田。

解法二：一层聚合 + 全量小票口径对照

```sql
SELECT p.category,                                                   -- 品类
       SUM(s.qty) AS total_qty,                                      -- 品类总件数
       COUNT(DISTINCT s.sale_id) AS cat_ticket_cnt,                  -- 含该品类的小票数（去重防多行）
       ROUND(SUM(s.qty) / COUNT(DISTINCT s.sale_id), 2) AS attach_rate,      -- 口径A：品类内连带率
       ROUND(SUM(s.qty) / (SELECT COUNT(DISTINCT sale_id)            -- 口径B对照：全店小票总数
                            FROM sales
                            WHERE sale_date >= '2024-06-01'
                              AND sale_date <  '2024-07-01'), 2) AS per_ticket_share -- 每张小票平均贡献该品类件数
FROM sales s
JOIN products p ON p.product_id = s.product_id
WHERE s.sale_date >= '2024-06-01' AND s.sale_date < '2024-07-01'
GROUP BY p.category;
```

结果解读：口径A高说明"买这个品类的人买得深"，口径B高说明"该品类渗透广且贡献件数多"。**【加分点】**能当场把两个分母口径的差别讲透，比写出SQL本身更能体现数据 sense。

### 5. 性能分析与优化

解法一两次聚合、写 CTE 分层，中间结果集是"小票×品类"笛卡尔级组合（小票数×品类数上限），行数可控；解法二一层聚合，但子查询里又扫了一遍 sales 求全量小票数，等于明细扫两遍。优化建议：全量小票数可改用窗口 `COUNT(DISTINCT sale_id) OVER ()` 或先在 CTE 里算一次供两处引用，避免重复扫表；JOIN products 只取 product_id 与 category 两列，配合 (sale_date, store_id) 过滤索引减少扫描；如需按门店下钻，把 store_id 加入两级 GROUP BY 即可，代价线性增长；历史月度连带率建议物化成汇总表供看板直接查询。

### 6. 面试延伸考点

- **连带率用"件数"还是"单品SKU数"做分子？有什么区别？** 回答要点：件数口径受多件促销影响大，SKU数口径衡量"买了几个不同商品"，两者要一起看；SKU口径需在件数聚合前对 (sale_id, product_id) 去重。
- **退货小票要不要算进分母？** 回答要点：看分析目的，评估真实购买行为应剔除退货小票；评估净销售额口径则保留负数冲减，关键是团队内统一并写进指标字典。
- **连带率提升就一定好吗？** 回答要点：不一定，强行捆绑可能拉高客单但伤复购与体验，要配合复购率、毛利率一起评估。
- **小票跨品类时，"含该品类的小票数"在SQL里怎么保证不重复计数？** 回答要点：先按 (sale_id, category) 聚合把粒度压实到每小票每品类一行，再 COUNT(*)，或直接 COUNT(DISTINCT sale_id)。

### 7. 业务拓展思考

连带率是"购物篮分析"的入口指标，可与购物篮关联规则（支持度/置信度/提升度）联动，把"哪些商品放在一起卖"从经验变成数据。运营上，低连带品类可与高连带品类做收银台交叉陈列、满件折（第二件半价）；采购上，组合装 SKU 的开发优先级可由连带缺口量化。口径延展方向：分时段连带率（早晚高峰差异）、分门店业态连带率、会员与非会员连带率对比，逐步形成"人-货-场"三维连带诊断体系。

## RET-19 会员与非会员客单价对比

### 1. 业务背景

你是连锁超市会员运营团队的分析师。公司刚做完"办卡送礼"活动，市场部宣称会员客单价显著高于散客，但 CFO 要求拿出严谨的数据：2024年5月，会员小票与非会员小票的客单价各是多少、差异多大、会员贡献了多大比例的销售额？这个结论将决定是否继续投入办卡补贴预算。需要注意销售明细里 member_id 为空即代表非会员交易，一张小票要么整体是会员单要么整体是散客单，必须在"小票粒度"上归并后再对比，而不是在商品行粒度直接分组。

| 字段名 | 类型 | 含义 |
| --- | --- | --- |

| gender | CHAR(1) | 性别：M/F |

### 3. 解题思路

客单价的正确定义是"总销售额 ÷ 总小票数"（即平均每张小票金额），等价于对每张小票金额求平均，但绝不能在商品行粒度直接对 amount 求平均，那会把"多商品小票"拆碎严重低估客单价。**【避坑指南】**必须先把数据压实到小票粒度（一行=一张小票），再按会员/非会员分群；归并 member_id 时用 MAX 或 MIN 均可（同一小票会员号唯一），但绝不能用 SUM。实现路径：解法一用 CTE 先做小票级聚合，再 CASE WHEN 分群求客单价，逻辑最清晰、可扩展门店下钻；解法二在明细层直接 GROUP BY 分群并用 COUNT(DISTINCT sale_id) 做分母，配合聚合套窗口 `SUM(SUM(amount)) OVER ()` 计算会员销售额占比。易错点：一张小票内 member_id 必须一致，若出现脏数据（同小票不同会员号）要先按小票仲裁；退货小票口径需与业务确认。

### 4. 参考解法

解法一：CTE压实到小票粒度再分群（推荐的标准流程）

```sql
WITH ticket AS (                                     -- 第一层：把明细压实成"一张小票一行"
    SELECT sale_id,
           store_id,
           MAX(member_id) AS member_id,              -- 同一小票会员号唯一，MAX归并；NULL不受影响
           SUM(amount) AS ticket_amt                 -- 小票金额=各行金额求和
    FROM sales
    WHERE sale_date >= '2024-05-01'
      AND sale_date <  '2024-06-01'
    GROUP BY sale_id, store_id
)
SELECT CASE WHEN member_id IS NULL THEN '非会员'      -- 小票级判群，而不是行级
            ELSE '会员' END AS cust_type,
       COUNT(*) AS ticket_cnt,                        -- 小票数（此时每行就是一张小票）
       ROUND(SUM(ticket_amt), 2) AS total_amt,        -- 分群销售额
       ROUND(SUM(ticket_amt) / COUNT(*), 2) AS avg_ticket -- 客单价=销售额/小票数
FROM ticket
GROUP BY CASE WHEN member_id IS NULL THEN '非会员'
              ELSE '会员' END;
```

结果解读：得到会员、非会员两组的小票数、销售额与客单价。会员客单价高出非会员的部分，扣除办卡与权益成本后才是会员体系的真实增量价值。

解法二：明细层直接分群 + 聚合套窗口算销售占比

```sql
SELECT IF(member_id IS NULL, '非会员', '会员') AS cust_type,    -- 行级判群（口径见思路说明）
       COUNT(DISTINCT sale_id) AS ticket_cnt,                   -- 小票数：必须DISTINCT去重
       ROUND(SUM(amount) / COUNT(DISTINCT sale_id), 2) AS avg_ticket, -- 客单价
       ROUND(SUM(amount) * 100.0
             / SUM(SUM(amount)) OVER (), 1) AS amt_share_pct   -- 分群销售额占总销售额比例（聚合套窗口）
FROM sales
WHERE sale_date >= '2024-05-01' AND sale_date < '2024-06-01'
GROUP BY IF(member_id IS NULL, '非会员', '会员');
```

结果解读：在客单价之外直接给出"会员贡献了百分之几的销售额"，这是预算决策最需要的证据。**【加分点】**`SUM(SUM(amount)) OVER ()` 这种"聚合结果再开窗"的写法，体现对 MySQL 8.0 聚合与窗口混合执行顺序的理解。

### 5. 性能分析与优化

解法一两次聚合（明细→小票→分群），中间结果集是小票级，行数远小于明细行，后续计算成本可忽略；解法一只扫一遍明细，但 COUNT(DISTINCT sale_id) 需要去重结构，大表上内存与临时表开销略高。优化建议：先按日期过滤把扫描量压到单月；在 (sale_date) 或 (sale_date, store_id) 上建索引辅助范围裁剪；小票级聚合阶段只保留 sale_id、store_id、member_id、amount 四列走覆盖索引；如果小票粒度表本身已存在于数仓（常见做法），直接在小票表上算客单价，避免每次从行明细重算；历史趋势需求可按月物化"客群×门店"客单价汇总表。

### 6. 面试延伸考点

- **为什么必须先压到小票粒度，不能直接对明细行分组？** 回答要点：一张小票多个商品行，行级平均会被"多行小票"稀释，把客单价算成"行均价"；分子分母必须同粒度。
- **客单价提升就代表会员运营成功吗？** 回答要点：不一定，可能是会员买了更贵的东西（结构效应），也可能是大额采购者恰好都注册了会员（自选择偏差），更严谨的是对比会员办卡前后的自身客单变化（前后对照）。
- **如果要按门店看会员/非会员客单价差异，SQL怎么扩展？** 回答要点：GROUP BY 里加 store_id，或先算"门店×客群"客单价再用窗口对比该门店整体客单，注意小门店小票数过少要加 HAVING 样本量保护。
- **同一小票出现两个不同会员号（脏数据）怎么办？** 回答要点：按业务规则仲裁（如取下单时扫码的最后一个会员），或整单标记为数据异常剔除并反馈给收银系统排查。

### 7. 业务拓展思考

### 3. 解题思路

先定口径：贡献度 = 品类当月销售额 ÷ 全品类当月总销售额，用占比而非绝对额衡量可以剔除月度大促、天数差异的干扰；排名按销售额降序。名次变化有两种取上月的方式：自连接同表（按品类 join 两个月份）与 LAG 窗口（按品类分区按月排序取上一行），前者不依赖月份连续，后者代码更紧凑。占比的计算用聚合窗口 `SUM(amt) OVER (PARTITION BY ym)` 在品类聚合结果上直接求当月总量，避免再写一层子查询。**【面试高频】**这里会追问 RANK 与 DENSE_RANK 的选择：品类销售额并列时 RANK 跳号会导致"名次变化"忽大忽小，DENSE_RANK 更平滑，需与业务确认；另一个易错点是占比的分母必须是"同月总销售额"，PARTITION BY ym 不能丢，否则分母变成全部月份总和。

### 4. 参考解法

解法一：占比窗口 + RANK，再用自连接比较两个月份

```sql
WITH monthly AS (                                    -- 第一层：月×品类销售额
    SELECT DATE_FORMAT(s.sale_date, '%Y-%m') AS ym,  -- 年月键
           p.category,
           SUM(s.amount) AS amt
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2024-04-01' AND s.sale_date < '2024-06-01'
    GROUP BY DATE_FORMAT(s.sale_date, '%Y-%m'), p.category
),
ranked AS (                                          -- 第二层：算占比与排名
    SELECT ym, category, amt,
           ROUND(amt * 100.0 / SUM(amt) OVER (PARTITION BY ym), 2) AS pct, -- 当月品类占比（分母=同月总量）
           RANK() OVER (PARTITION BY ym ORDER BY amt DESC) AS rk           -- 当月名次（并列跳号）
    FROM monthly
)
SELECT cur.category,                                 -- 品类
       cur.pct  AS pct_may,                          -- 5月占比
       cur.rk   AS cur_rank,                         -- 5月名次
       prev.rk  AS prev_rank,                        -- 4月名次
       prev.rk - cur.rk AS rank_change               -- 名次变化：正数=上升，负数=下滑
FROM ranked cur
JOIN ranked prev                                     -- 自连接同一CTE：拿上月名次
  ON prev.category = cur.category
 AND prev.ym = '2024-04'
WHERE cur.ym = '2024-05'
ORDER BY cur.rk;                                     -- 按5月名次展示
```

结果解读：rank_change 为负且连续两月为负的品类要重点排查，是价格、缺货还是竞争分流导致失守。

解法二：LAG 窗口跨月对比（不写自连接）

```sql
WITH ranked AS (                                     -- 与解法一相同的占比与排名层
    SELECT DATE_FORMAT(s.sale_date, '%Y-%m') AS ym,
           p.category,
           SUM(s.amount) AS amt,
           ROUND(SUM(s.amount) * 100.0
                 / SUM(SUM(s.amount)) OVER (PARTITION BY DATE_FORMAT(s.sale_date, '%Y-%m')), 2) AS pct,
           RANK() OVER (PARTITION BY DATE_FORMAT(s.sale_date, '%Y-%m')
                        ORDER BY SUM(s.amount) DESC) AS rk
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2024-04-01' AND s.sale_date < '2024-06-01'
    GROUP BY DATE_FORMAT(s.sale_date, '%Y-%m'), p.category
)
SELECT category, ym, pct, rk,
       LAG(rk) OVER (PARTITION BY category ORDER BY ym) AS prev_rank,   -- 同品类上一月名次
       rk - LAG(rk) OVER (PARTITION BY category ORDER BY ym) AS rank_change -- 名次变化
FROM ranked
WHERE ym = '2024-05';                                -- 只展示目标月的变化
```

结果解读：LAG 按品类分区取上一月名次，与自连接等价但避免了重复引用 CTE。**【避坑指南】**LAG 依赖"品类每月都有数据"的连续性，某品类整月无销售会错位，稳健做法是先补齐月×品类维度框架或用解法一。

### 5. 性能分析与优化

两种解法都先做"月×品类"聚合，中间结果只有几十行，主要代价在明细扫描与 GROUP BY。解法一自连接发生在极小的 ranked 结果上，代价可忽略；解法二少一次 CTE 引用但窗口嵌套在聚合之上，MySQL 需先完成 GROUP BY 再开窗，逻辑计划更复杂但通常无差异。优化建议：sales 上建 (sale_date, product_id, amount) 索引，日期先过滤；products 的主键 JOIN 是小表查找；月度品类销售额建议物化到 category_month_summary 汇总表，把此类报表从明细级降为汇总级查询；若品类数多、月份跨度大，考虑给汇总表建 (category, ym) 联合索引加速 LAG 排序。

### 6. 面试延伸考点

- **用占比还是绝对销售额看品类贡献？** 回答要点：绝对额受月度天数、大促节奏影响，占比剔除规模波动更适合看结构性变化；汇报时常两者并列，占比看趋势、绝对额看盘子。
- **排名并列时 RANK 和 DENSE_RANK 对"名次变化"的影响？** 回答要点：RANK 并列跳号会让变化值不稳定（1,1,3中第3名升1位显示+2），DENSE_RANK 变化更连续，业务上若关心"超过了几家对手"用 DENSE_RANK 更贴切。
- **某品类整月无销售，LAG 会发生什么？怎么补救？** 回答要点：该品类当月没有行，下月 LAG 取到的是更早月份造成错位；补救用日历表/品类维度表 LEFT JOIN 补齐空月（销售额填0）再开窗。
- **如何把品类占比变化归因到具体门店？** 回答要点：在聚合粒度中加入 store_id 下钻，或计算各门店对该品类占比变化的贡献分解（门店销售额变化×门店权重）。

### 7. 业务拓展思考

品类贡献度排名是商品预算与货架资源分配的依据：名次持续上升的品类可争取端架、堆头资源与更多新品配额，下滑品类则要区分"趋势性衰退"与"执行性缺货"，分别对应汰换与补货动作。口径延展上，可从销售额占比延展到毛利占比（防止单纯冲量）、从月度延展到周度观察短期节奏、引入"品类角色"框架（引流/利润/形象品类）让排名变化与品类战略对齐，避免为了占比牺牲整体毛利结构。
## RET-21 会员30天内二次到店复购率

### 1. 业务背景

你是连锁超市会员运营中心的数据分析师。公司2024年6月投放了"新会员开卡礼包"，市场部想知道：6月首次到店消费的新会员里，有多少人在30天内又来了一次？"30天复购率"是衡量拉新质量与首购体验的核心指标——只来一次的会员大概率是"薅完羊毛即流失"，而30天内二次到店的会员其年消费额通常数倍于单次客群。该指标将决定下季度开卡礼包的预算加码还是叫停。需要注意口径：以"首次到店日期"为起点，观察其之后30个自然日内是否产生第二笔消费，且观察窗必须完整落在数据范围内，否则会低估复购率。

### 3. 解题思路

先定三个口径：一是"人群"，2024年6月1日至6月30日产生第一笔消费的会员（以消费首店而非注册日期定义，注册了但没消费的不算）；二是"复购"，首店日期之后、30个自然日内（含第30天）再次产生消费即算复购，同一张小票不算、同一天再来第二次按"当日复购"口径另行确认；三是"观察窗完整性"，6月30日首次到店的会员要观察到7月30日，因此数据范围必须取到7月底，避免窗口截断造成低估。实现路径：解法一先用 MIN 聚合出首店日期，再左连接该会员首店后30天内的小票打复购标记，最后按人群聚合比例；解法二用窗口 `MIN(sale_date) OVER (PARTITION BY member_id)` 在明细层直接给每行打上首店日期，一层扫描完成标记，再在聚合层用条件计数求比率。**【避坑指南】**复购判定必须是 `sale_date > first_dt` 的严格大于，否则首店当天自己就被算成"复购"，复购率直接虚高到100%。

### 4. 参考解法

解法一：MIN聚合首店日期 + LEFT JOIN 打复购标记

```sql
WITH first_visit AS (                                -- CTE1：6月首次到店会员及其首店日期
    SELECT member_id,
           MIN(sale_date) AS first_dt                -- 首次到店日（按消费口径，非注册口径）
    FROM sales
    WHERE member_id IS NOT NULL                      -- 非会员小票不参与
      AND sale_date >= '2024-06-01'
      AND sale_date <  '2024-07-01'                  -- 6月内首店的人群
    GROUP BY member_id
),
repeat_flag AS (                                     -- CTE2：判断30天内是否二次到店
    SELECT f.member_id,
           f.first_dt,
           MAX(CASE WHEN s.sale_date > f.first_dt    -- 严格大于：排除首店当天
                     AND s.sale_date <= DATE_ADD(f.first_dt, INTERVAL 30 DAY)  -- 30天观察窗（含第30天）
                    THEN 1 ELSE 0 END) AS is_repeat  -- 窗口内任一天有消费即标记1
    FROM first_visit f
    LEFT JOIN sales s                                -- LEFT JOIN：不复购的会员也要保留在人群里
      ON s.member_id = f.member_id
     AND s.sale_date >  f.first_dt
     AND s.sale_date <= DATE_ADD(f.first_dt, INTERVAL 30 DAY)
    GROUP BY f.member_id, f.first_dt
)
SELECT COUNT(*) AS cohort_cnt,                       -- 6月首到店会员总数
       SUM(is_repeat) AS repeat_cnt,                 -- 30天内复购人数
       ROUND(AVG(is_repeat) * 100, 2) AS repeat_pct  -- 复购率=复购人数/人群数
FROM repeat_flag;
```

结果解读：假设输出复购率38%，即每10个新会员有近4人一个月内回流。低于行业基准（如45%）时应排查首购体验：缺货率、收银排队、礼包核销门槛。

解法二：窗口 MIN 在明细层打首店标记，条件计数求比率

```sql
WITH tagged AS (                                     -- 每行小票都带上该会员的首店日期
    SELECT member_id,
           sale_date,
           MIN(sale_date) OVER (PARTITION BY member_id) AS first_dt -- 窗口MIN：该会员在本区间最早到店日
    FROM sales
    WHERE member_id IS NOT NULL
      AND sale_date >= '2024-06-01'
      AND sale_date <  '2024-08-01'                  -- 数据范围覆盖到7月底，保证30天观察窗完整
)
SELECT COUNT(DISTINCT CASE WHEN first_dt < '2024-07-01'        -- 限定6月首到店人群
                            THEN member_id END) AS cohort_cnt, -- 人群数
       COUNT(DISTINCT CASE WHEN first_dt < '2024-07-01'        -- 人群内
                            AND sale_date >  first_dt          -- 二次到店
                            AND sale_date <= DATE_ADD(first_dt, INTERVAL 30 DAY) -- 30天内
                            THEN member_id END) AS repeat_cnt, -- 复购人数
       ROUND(COUNT(DISTINCT CASE WHEN first_dt < '2024-07-01'
                                  AND sale_date >  first_dt
                                  AND sale_date <= DATE_ADD(first_dt, INTERVAL 30 DAY)
                                  THEN member_id END) * 100.0
             / COUNT(DISTINCT CASE WHEN first_dt < '2024-07-01'
                                   THEN member_id END), 2) AS repeat_pct -- 复购率（%）
FROM tagged;
```

结果解读：与解法一同值，但只扫一遍明细。**【加分点】**能主动说明"数据取到7月底是为了让6月末首店会员的观察窗完整"，体现对窗口截断（censoring）的敏感度。

### 5. 性能分析与优化

解法一扫两遍明细（首店聚合一次、JOIN取窗口内小票一次），且JOIN条件是会员号+日期区间，索引可用 (member_id, sale_date) 完美命中；解法一只扫一遍但窗口 MIN 需要按 member_id 分区排序，大表上排序内存开销高。优化建议：sales 上建 (member_id, sale_date) 复合索引，两种写法都能从"索引扫描+松散聚合"中获益；人群先在 CTE 里收缩到"6月活跃会员"再做连接，避免全量会员参与；数据量大时按月分桶，把标记阶段限制在6月+7月两个分区；若指标常态化，可维护 member_first_visit 维度表（会员号、首店日期），每次只算增量会员的复购标记。

### 6. 面试延伸考点

- **复购率分母为什么用"首到店会员数"而不是"注册会员数"？** 回答要点：注册未到店会员从未产生消费，混入分母会把拉新漏斗的两个阶段混在一起；应拆成"注册→首购转化率"和"首购→30天复购率"两段分别考核。
- **观察窗截断怎么处理？** 回答要点：只统计"首店日期+30天"落在数据末尾之前的会员；或对最近 cohorts 标记"观察中"，出数时按完整窗口的 cohort 滚动更新。
- **如果要求"按首次到店门店拆解复购率"，哪里要小心？** 回答要点：复购可能发生在其他门店，分子判定是"该会员30天内任意门店再次消费"，分母才是首店归属，避免把跨店复购漏掉。
- **同一天多张小票算几次到店？** 回答要点：到店按自然日去重（COUNT(DISTINCT sale_date)），交易次数是另一个口径，需在指标字典里明确。

### 7. 业务拓展思考

30天复购率是会员生命周期管理的第一道闸口：可延展为7天/30天/90天复购曲线，定位最佳唤醒时机；可按首购品类分层，生鲜引流客与百货尝鲜客的复购路径完全不同，运营上对未复购会员在首店后第7、14天触发分层券包，采购上对复购高的品类加大囤货装开发。口径延展：以"到店日"可切换为"跨店复购率""线上小程序复购率"，进一步构建 omni-channel 会员旅程看板。

## RET-22 促销期与日常销售对比（分品类）

### 1. 业务背景

你是超市总部市场部与商品部共用的数据分析师。"五一焕新周"大促（2024年5月1日~5月5日）刚结束，采购总监想知道：这次全店满减大促对每个品类的拉动有多大——休闲食品应该弹性最大，生鲜可能只是自然客流带动，粮油可能几乎没反应甚至被囤货透支。需要计算各品类"促销期日均销售额"相对"当月非促销日日均销售额"的提升率，用于评估促销资源（堆头、DM档期、补贴）在品类间的分配效率，并识别被透支的品类（大促后销量明显回落）。

### 3. 解题思路

先定口径：促销日=小票日期落在 promotions 任一活动区间内；基线=当月非促销日的日均销售额。**【避坑指南】**对比必须用"日均"而不是"促销期总额"——5天促销对26个日常日，直接比总额会得出"暴涨5倍"的荒谬结论；分母促销天数按"品类实际有销售的自然日数"计（COUNT(DISTINCT sale_date)），防止无销售日记入分母。提升率 = 促销日均/日常日均 - 1。实现路径：解法一用 LEFT JOIN 促销日历按日期区间连接打 is_promo 标记，再按"品类×是否促销"聚合求日均，最后行转列对比；解法二用 EXISTS 子查询打标，避免促销日历若有重叠活动时区间连接造成的行扇出重复计数。易错点：多活动区间重叠时 JOIN 连接会一单多行、销售额翻倍，EXISTS 或先对日历去重才安全；品类无促销销售时提升率除零需 NULLIF。

### 4. 参考解法

解法一：LEFT JOIN 促销日历打标 + 行转列求日均提升率

```sql
WITH detail AS (                                     -- 第一步：明细打上促销标记
    SELECT p.category,
           s.sale_date,
           s.sale_id,
           s.amount,
           CASE WHEN pr.promo_id IS NOT NULL         -- 能连上促销日历即落在活动区间
                THEN 1 ELSE 0 END AS is_promo
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    LEFT JOIN promotions pr                          -- LEFT JOIN：非促销日保留且标记0
      ON s.sale_date >= pr.start_date
     AND s.sale_date <= pr.end_date                  -- 日期区间连接（日历不重叠时安全）
    WHERE s.sale_date >= '2024-05-01'
      AND s.sale_date <  '2024-06-01'                -- 统计2024年5月
),
agg AS (                                             -- 第二步：品类×是否促销 聚合
    SELECT category, is_promo,
           SUM(amount) AS amt,                       -- 该组销售额
           COUNT(DISTINCT sale_date) AS days         -- 该组有销售的自然日数（日均分母）
    FROM detail
    GROUP BY category, is_promo
)
SELECT category,
       MAX(CASE WHEN is_promo = 1 THEN ROUND(amt / days, 2) END) AS promo_daily,  -- 促销期日均
       MAX(CASE WHEN is_promo = 0 THEN ROUND(amt / days, 2) END) AS daily_avg,    -- 日常日均
       ROUND(MAX(CASE WHEN is_promo = 1 THEN amt / days END)
             / MAX(CASE WHEN is_promo = 0 THEN amt / days END) * 100 - 100, 2) AS lift_pct -- 日均提升率%
FROM agg
GROUP BY category
ORDER BY lift_pct DESC;                              -- 拉动最大的品类排前面
```

结果解读：lift_pct 越大促销弹性越高；若某品类 lift_pct 为负，说明促销反而扰乱了正常销售节奏（如消费者把日常购买推迟到大促囤货）。

解法二：EXISTS 打标（防促销日历重叠导致的扇出）

```sql
WITH detail AS (                                     -- 用EXISTS打标：只判断"是否落在任一活动区间"
    SELECT p.category,
           s.sale_date,
           s.sale_id,
           s.amount,
           CASE WHEN EXISTS (SELECT 1                -- 半连接：存在即真，不产生额外行
                              FROM promotions pr
                              WHERE s.sale_date BETWEEN pr.start_date AND pr.end_date)
                THEN 1 ELSE 0 END AS is_promo
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2024-05-01' AND s.sale_date < '2024-06-01'
),
agg AS (
    SELECT category, is_promo,
           SUM(amount) AS amt,
           COUNT(DISTINCT sale_date) AS days
    FROM detail
    GROUP BY category, is_promo
)
SELECT a.category,
       MAX(CASE WHEN a.is_promo = 1 THEN ROUND(a.amt / a.days, 2) END) AS promo_daily,
       MAX(CASE WHEN a.is_promo = 0 THEN ROUND(a.amt / a.days, 2) END) AS daily_avg,
       ROUND(MAX(CASE WHEN a.is_promo = 1 THEN a.amt / a.days END)
             / NULLIF(MAX(CASE WHEN a.is_promo = 0 THEN a.amt / a.days END), 0) * 100 - 100, 2) AS lift_pct
FROM agg a
GROUP BY a.category
ORDER BY lift_pct DESC;
```

结果解读：与解法一同值，但当促销日历存在重叠活动（如全场满减叠加品类折扣）时结果仍然正确。**【加分点】**能指出"日期区间JOIN在活动重叠时会让小票翻倍"这一数据正确性风险，是把SQL写对和写稳的分水岭。

### 5. 性能分析与优化

解法一区间连接在促销日历极小（几行到几十行）时代价可忽略，MySQL 会把它转成小表驱动；解法二 EXISTS 走半连接（semijoin），每行明细做一次探测，但优化器可将 promotions 缓存在内存中，两者差距不大。主要代价仍是5月明细的扫描与两次聚合。优化建议：sales (sale_date, product_id, amount) 索引先裁剪月份；promotions 的 (start_date, end_date) 建索引辅助 EXISTS 探测；促销日历先在 CTE 中按月份预过滤，缩小连接集；若促销评估是固定月度动作，建议建 fact_sales_with_promo_flag 宽表（ETL阶段打标），查询侧免连接；促销期与日常的对比还可按门店下钻，注意保持"先聚合后对比"的顺序。

### 6. 面试延伸考点

- **为什么用日均而不是总额做基线对比？** 回答要点：促销期与日常天数不等，总额对比混入了时长效应；日均剥离时长后才是纯粹的销售强度差异。
- **怎么判断一个品类被大促"透支"了？** 回答要点：看大促后7~14天的日常日均是否低于大促前基线，即"前基线-促销期-后基线"三段对比，后基线显著回落即透支。
- **促销日历有两场活动时间重叠，解法一会发生什么？** 回答要点：同一张小票连上两行促销日历，SUM(amount) 翻倍；要么 EXISTS 打标，要么先对日历按日展开去重再连接。
- **提升率应该按销售额还是销量（件数）算？** 回答要点：两者结合，销售额提升可能只来自降价（件单价下滑），件数提升才是真实需求拉动；毛利率变化用于判断促销是否在赔本赚吆喝。

### 7. 业务拓展思考

促销对比的终点是"促销弹性档案"：为每个品类沉淀常态弹性系数，预测下次投入产出。运营上，高弹性品类可加大档期频率、低弹性品类改做形象展示或换购；采购上，被透支品类要在大促后下调补货计划防积压。口径延展：可从"日均销售额提升率"延展到"日均毛利额提升率""新增客流贡献占比""会员召回贡献"，并把"是否有竞对同期大促"作为归因控制变量，避免把外部节奏误读为自身促销效果。

## RET-23 门店分时段进店-成交转化率

### 1. 业务背景

你是便利店运营部的数据分析师。门店客流系统按小时记录每天各时段的进店人次与成交小票数。店长例会上要回答一个"排班与陈列"问题：一天中哪些时段"进店的人多但买单的人少"？例如午后14~16点进店不少但成交稀疏，可能是白领进来吹空调买杯咖啡就走；而晚间18~20点转化率高但常因收银排长队流失。需要按小时计算全网及各门店的进店-成交转化率，找出转化率显著低于同时段均值的门店-时段组合，作为精准排班、收银动线优化和时段促销的依据。

### 2. 表结构说明

store_traffic（门店客流统计表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| store_id | INT | 门店ID |
| stat_date | DATE | 统计日期 |
| hour_slot | INT | 时段（小时），如8表示8:00~8:59 |
| enter_cnt | INT | 进店人次 |
| deal_cnt | INT | 成交小票数 |

| store_id | stat_date | hour_slot | enter_cnt | deal_cnt |
| --- | --- | --- | --- | --- |
| 1001 | 2024-05-03 | 8 | 120 | 66 |
| 1001 | 2024-05-03 | 14 | 95 | 30 |
| 1001 | 2024-05-03 | 19 | 210 | 150 |
| 1002 | 2024-05-03 | 8 | 80 | 52 |
| 1002 | 2024-05-03 | 14 | 110 | 28 |

### 3. 解题思路

先定口径：转化率 = 成交小票数 ÷ 进店人次。**【避坑指南】**这是典型的"比率型指标"，聚合时必须"先加总分子分母、再相除"（加权口径），绝不能先算各店各天的转化率再对转化率求平均——一天3人次成交1人次的门店（33%）和一家3000人次成交1500人次的门店（50%）简单平均会严重失真；同时要与人效、客单等指标互查，确认 enter_cnt 是"人次"而 deal_cnt 是"小票笔数"，一人多票或多人同票的系统性偏差要向面试官说明假设（一人次进店至多一张成交小票）。实现路径：解法一按时段全网聚合，直接算各小时转化率并排名找最差时段；解法二下沉到"门店×时段"粒度，用聚合窗口 `SUM() OVER (PARTITION BY hour_slot)` 计算同时段全网基准，筛出低于基准2个百分点以上的门店-时段组合做归因。

### 4. 参考解法

解法一：按时段全网加权聚合 + 排名定位最差时段

```sql
SELECT t.hour_slot,                                        -- 小时时段
       SUM(t.enter_cnt) AS enter_cnt,                      -- 该时段全网进店人次（先加总）
       SUM(t.deal_cnt)  AS deal_cnt,                       -- 该时段全网成交小票数
       ROUND(SUM(t.deal_cnt) / SUM(t.enter_cnt) * 100, 2) AS conv_pct, -- 转化率=加总后再相除（加权口径）
       RANK() OVER (ORDER BY SUM(t.deal_cnt) / SUM(t.enter_cnt) ASC) AS bad_rank -- 转化率从差到好排名
FROM store_traffic t
WHERE t.stat_date >= '2024-05-01'
  AND t.stat_date <  '2024-06-01'                          -- 统计2024年5月
GROUP BY t.hour_slot
ORDER BY t.hour_slot;                                      -- 按时间轴展示一天节奏
```

结果解读：输出一天24小时的转化曲线，午后低谷段与晚间高峰段一目了然，是"时段运营"的第一张图。

解法二：门店×时段粒度 + 聚合窗口求同时段基准，筛低效组合

```sql
WITH slot AS (                                             -- 第一层：门店×时段的月度加总
    SELECT hour_slot,
           store_id,
           SUM(enter_cnt) AS enter_cnt,                    -- 该店该时段进店人次
           SUM(deal_cnt)  AS deal_cnt                      -- 该店该时段成交小票数
    FROM store_traffic
    WHERE stat_date >= '2024-05-01' AND stat_date < '2024-06-01'
    GROUP BY hour_slot, store_id
),
calc AS (                                                  -- 第二层：算各组合转化率与时段基准
    SELECT hour_slot, store_id, enter_cnt, deal_cnt,
           ROUND(deal_cnt / enter_cnt * 100, 2) AS conv_pct,             -- 组合转化率
           ROUND(SUM(deal_cnt)  OVER (PARTITION BY hour_slot)            -- 该时段全网成交合计
                 / SUM(enter_cnt) OVER (PARTITION BY hour_slot) * 100,   -- 该时段全网进店合计
                 2) AS slot_avg_pct                                      -- 时段全网加权基准
    FROM slot
)
SELECT c.hour_slot,
       c.store_id,
       c.enter_cnt,
       c.deal_cnt,
       c.conv_pct,
       c.slot_avg_pct,
       ROUND(c.conv_pct - c.slot_avg_pct, 2) AS gap_pct             -- 与同时段全网基准的差距
FROM calc c
WHERE c.conv_pct < c.slot_avg_pct - 2                                 -- 低于基准2个百分点以上
  AND c.enter_cnt >= 500                                              -- 排除小样本门店的噪音
ORDER BY c.gap_pct;                                                   -- 差距最大的排前面
```

结果解读：输出"哪里、几点、差多少"的低效清单，比全网时段曲线更可直接派发整改工单。**【加分点】**`SUM(deal_cnt) OVER (PARTITION BY hour_slot) / SUM(enter_cnt) OVER (...)` 先加总再相除，天然规避"比率的比率"陷阱。

### 5. 性能分析与优化

解法一粒度最粗，聚合结果只有24行，代价几乎全在月度明细的扫描与分组；解法二多一层"门店×时段"中间结果（门店数×24行），窗口按 hour_slot 分区排序开销很小。优化建议：store_traffic 建万级日行小表，性能压力不大，但可加 (stat_date, hour_slot) 或 (hour_slot, store_id) 索引加速两种分组；enter_cnt/deal_cnt 若来自客流设备，采集层先按日聚合落表，避免查询层处理小时级原始流水；低效组合筛查中 enter_cnt 阈值（如500）能滤掉大量噪音行，越早过滤越省；若做实时时段看板，改按最近7天滚动窗口计算，进一步压缩扫描量。

### 6. 面试延伸考点

- **为什么不能对各家门店的转化率直接求平均？** 回答要点：转化率是比值，简单平均等价于给小店和大店同权重；必须加权（总成交/总进店），或用加权平均公式 SUM(p_i×w_i)/SUM(w_i)。
- **进店人次和小票数口径不一致会怎样？** 回答要点：一人多次进店只被计数一次、或一次进店买多张小票，都会让转化率系统性偏高或偏低，需要与客流设备口径核对并在报表注明假设。
- **转化率低就是坏事吗？怎么结合业务判断？** 回答要点：不绝对，引流型业态（便利店的早餐咖啡客流）天然低转化高客单频次，应结合客单价、进店目的调研一起看；异常低的组合才是整改对象。
- **如果要加"工作日/周末"维度，SQL怎么扩展？** 回答要点：用 DAYOFWEEK 或自定义日历表打 workday_flag，把该标志加入 GROUP BY 与窗口 PARTITION BY，注意周末时段结构差异大必须分开基准。

### 7. 业务拓展思考

时段转化率是"人效排班"和"时段营销"的连接器：低转化高进店时段可安排试吃、秒杀把人流转成单，高转化低进店时段则做引流投放。延展口径有"入店-深逛-成交"三段漏斗（需要动线传感数据）、时段转化率×客单价的时段产出矩阵（决定黄金档期）、以及雨天/节假日的转化弹性，逐步把排班模型从经验表升级为时段产出预测模型。

## RET-24 商品ABC分级（帕累托80/15/5）

### 1. 业务背景

你是超市商品部的SKU管理分析师。全店SKU上万，但贡献高度集中：通常20%的SKU贡献80%销售额（A类），中间30%贡献15%（B类），剩余一半长尾SKU只贡献5%（C类）。季度选品会上要按2024年第二季度销售额对全部商品做ABC分级：A类保障库存与陈列永不缺货，B类观察优化，C类进入汰换清单释放货架与资金。分级规则采用帕累托累计法：按销售额从高到低排序后，累计占比不超过80%的为A，80%~95%为B，其余为C。这个分级每季度滚动一次，是货架谈判与库存资金分配的基础表。

### 2. 表结构说明

sales（小票明细表）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| sale_id | VARCHAR(20) | 小票号 |
| store_id | INT | 门店ID |
| sale_date | DATE | 销售日期 |
| product_id | INT | 商品ID |
| member_id | VARCHAR(20) | 会员号 |
| qty | INT | 购买件数 |
| amount | DECIMAL(10,2) | 实付金额，退货为负 |

### 3. 解题思路

ABC分级的本质是"排序 + 累计求和 + 累计占比分档"，三个动作都可下推到窗口函数：先在 CTE 里按商品聚合季度销售额；再按销售额降序排序，用 `SUM(amt) OVER (ORDER BY ... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` 求累计销售额，用 `SUM(amt) OVER ()` 求总销售额，两者相除即累计占比；最后 CASE WHEN 按 0.80/0.95 两个断点分档。**【避坑指南】**两个细节决定结果可复现：一是排序键必须加唯一次级键（如 product_id），否则销售额并列的两款商品跨断点时每次执行分级结果都可能不同；二是窗口框架要用 ROWS 而不是默认的 RANGE——RANGE 在并列值上会把"整个并列组"一起计入累计，导致同分商品的累计占比跳变，这正是需要显式声明窗口框架的原因。

### 4. 参考解法

解法一：窗口累计和 + CASE 分档（标准帕累托写法）

```sql
WITH sku_amt AS (                                    -- 第一层：各SKU季度销售额
    SELECT product_id,
           SUM(amount) AS amt                        -- 退货负数自动冲减
    FROM sales
    WHERE sale_date >= '2024-04-01'
      AND sale_date <  '2024-07-01'                  -- 2024年第二季度
    GROUP BY product_id
),
sorted AS (                                          -- 第二层：排序并算累计占比
    SELECT product_id, amt,
           ROW_NUMBER() OVER (ORDER BY amt DESC, product_id) AS rn,  -- 次级键保证并列时顺序唯一
           SUM(amt) OVER (ORDER BY amt DESC, product_id
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_amt, -- 逐行累计销售额（ROWS防并列跳变）
           SUM(amt) OVER () AS total_amt             -- 全部SKU总销售额（无排序的窗口）
    FROM sku_amt
)
SELECT product_id,
       amt,                                          -- SKU销售额
       rn,                                           -- 销售排名
       ROUND(cum_amt / total_amt * 100, 2) AS cum_pct,   -- 累计销售额占比
       CASE WHEN cum_amt / total_amt <= 0.80 THEN 'A'    -- 累计到80%为止都是A
            WHEN cum_amt / total_amt <= 0.95 THEN 'B'    -- 80%~95%为B
            ELSE 'C' END AS abc_class                    -- 其余长尾为C
FROM sorted
ORDER BY rn;                                         -- 按销售排名展示
```

结果解读：A类SKU清单是库存与陈列的"保护名单"，C类清单是汰换候选。注意断点是"累计占比首次越过80%的那一行"即截止，A类SKU数量占比通常远小于80%。

解法二：相关子查询算累计（兼容不支持窗口函数的旧库的思路对照）

```sql
WITH sku_amt AS (                                    -- 各SKU季度销售额（同解法一）
    SELECT product_id, SUM(amount) AS amt
    FROM sales
    WHERE sale_date >= '2024-04-01' AND sale_date < '2024-07-01'
    GROUP BY product_id
),
ranked AS (                                          -- 用相关子查询求"排在它前面（含自己）"的累计值
    SELECT a.product_id, a.amt,
           (SELECT SUM(b.amt)                        -- 累计：所有排序不晚于当前行的销售额之和
              FROM sku_amt b
             WHERE b.amt > a.amt                     -- 销售额更大的排前面
                OR (b.amt = a.amt AND b.product_id <= a.product_id) -- 并列时按product_id定序，含自身
           ) AS cum_amt
    FROM sku_amt a
),
total AS (                                           -- 总销售额单独算，避免重复聚合
    SELECT SUM(amt) AS total_amt FROM sku_amt
)
SELECT r.product_id,
       r.amt,
       ROUND(r.cum_amt / t.total_amt * 100, 2) AS cum_pct,
       CASE WHEN r.cum_amt / t.total_amt <= 0.80 THEN 'A'
            WHEN r.cum_amt / t.total_amt <= 0.95 THEN 'B'
            ELSE 'C' END AS abc_class
FROM ranked r
CROSS JOIN total t                                   -- 一行的总额广播到每行SKU
ORDER BY r.amt DESC, r.product_id;
```

结果解读：与解法一结果一致，但相关子查询对每个SKU都要回扫一遍排序后的结果，是 O(N²) 代价。**【加分点】**能讲清"窗口函数就是优化器对这类自累计子查询的向量化重写"，体现对 SQL 演进的理解。

### 5. 性能分析与优化

解法一：明细 GROUP BY 一次 + 窗口排序一次，复杂度 O(N·logN)，N 为SKU数（万级），整体毫秒到秒级；解法二相关子查询在 sku_amt 上对每行执行一次聚合扫描，O(N²)，SKU上万时可能需要数十秒。优化建议：sales (sale_date, product_id, amount) 索引压缩扫描；sku_amt 物化成季度汇总表后，解法二在小表上也勉强可用，但生产环境一律用解法一；排序键 (amt DESC, product_id) 上若建索引，MySQL 可免排序直接走索引序；分级结果按季度物化成 sku_abc_tag 维度表，供库存、陈列系统反查，避免每次实时计算；若按门店分别分级，把 store_id 加入聚合与所有窗口 PARTITION BY。

### 6. 面试延伸考点

- **为什么窗口框架要显式写 ROWS 而不是用默认 RANGE？** 回答要点：默认 RANGE 在 ORDER BY 键并列时把整个并列组计入累计，导致同分商品累计占比一起跳变；ROWS 按物理行逐行累计，语义才符合"逐个SKU累加"。
- **ABC用销售额分级有什么盲区？** 回答要点：销售额忽略毛利与周转，高销低毛利的引流品和占资金的滞销高销品会被同等保护；常用双维（销售额×毛利额）分级或四象限修正。
- **断点80/15/5是铁律吗？** 回答要点：不是，要看品类结构，长尾极长的便利店可能是70/20/10；关键是口径固定、滚动可比，并在报告标注所用断点。
- **某款SKU季度中只上架了半个月，直接参与分级公平吗？** 回答要点：不公平，可按"日均销售额"或"在架天数加权"修正，或单独标记为"新SKU观察期"不参与汰换。

### 7. 业务拓展思考

ABC分级是库存与货架资源分配的总开关：A类设定更高安全库存与自动补货优先级、端架陈列保护；C类按"销售额×毛利×周转"三因子复核后进汰换清单，把释放的排面让给B类中上升最快的新品。延展口径包括分门店ABC（总部A类未必是每家店的A类）、分渠道ABC，以及用"毛利额"替换销售额的第二套平行分级，双名单交叉后形成"销高利高保、销高利低谈、销低利低汰"的精细化选品策略。

### 3. 解题思路

先定口径：周转天数 = 期末库存件数 ÷ 日均销售件数（数量口径；若用金额口径，分子库存成本额、分母日均销售成本额，两者必须同口径）。日均销量 = 6月总销量 ÷ 30，固定除以自然月天数而非"有销售天数"，否则淡季品类会被高估周转速度。实现路径：解法一是标准的两段聚合——库存表按品类汇总件数、销售表按品类汇总月销量并换算日均，再按品类 JOIN 相除，注意用 LEFT JOIN 保留"有库存无销售"的品类并用 NULLIF 防除零；解法二换一个思路，把库存与销量用 UNION ALL 压成"品类-指标-数值"长表，再一次 GROUP BY 行转列并计算周转天数，适合指标会持续增多（库存额、缺货天数等）的可扩展报表。**【避坑指南】**绝对不能先把 inventory 与 sales 按商品 JOIN 成明细再聚合——库存行会被销售行放大、销售行会被批次行放大，两侧都重复计数，这是本题最大的坑。

### 4. 参考解法

解法一：两段聚合 + JOIN + NULLIF 除零保护（标准写法）

```sql
WITH stock AS (                                      -- 各品类期末库存件数
    SELECT p.category,
           SUM(i.stock_qty) AS stock_qty             -- 各批次库存按品类加总
    FROM inventory i
    JOIN products p ON p.product_id = i.product_id
    GROUP BY p.category
),
sold AS (                                            -- 各品类6月销量与日均
    SELECT p.category,
           SUM(s.qty) AS qty_30d,                    -- 6月总销量（退货为负自动冲减）
           ROUND(SUM(s.qty) / 30.0, 2) AS qty_per_day -- 日均销量：固定除以自然月30天
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2024-06-01'
      AND s.sale_date <  '2024-07-01'
    GROUP BY p.category
)
SELECT st.category,                                  -- 品类
       st.stock_qty,                                 -- 期末库存件数
       COALESCE(sd.qty_per_day, 0) AS qty_per_day,   -- 日均销量，无销售记0
       ROUND(st.stock_qty / NULLIF(sd.qty_per_day, 0), 1) AS turn_days, -- 周转天数=库存/日均销量（除零返回NULL）
       CASE WHEN sd.qty_per_day IS NULL OR sd.qty_per_day = 0
            THEN '滞销预警(零动销)'
            WHEN st.stock_qty / NULLIF(sd.qty_per_day, 0) > 30 THEN '压货预警'
            WHEN st.stock_qty / NULLIF(sd.qty_per_day, 0) < 3  THEN '断货预警'
            ELSE '正常' END AS risk_flag             -- 按周转天数分风险档
FROM stock st
LEFT JOIN sold sd ON sd.category = st.category       -- LEFT JOIN：零动销品类不丢行
ORDER BY turn_days DESC;                             -- 周转最慢的排前面
```

结果解读：turn_days 超过品类基准（日配3天、粮油30天）即压货，为 NULL 或被标记零动销的品类要立即排查是真实滞销还是缺货断档导致的"假滞销"。

解法二：UNION ALL 长表 + 行转列（可扩展的多指标写法）

```sql
WITH metric AS (                                     -- 把两个指标压成"品类-指标-数值"长表
    SELECT p.category, 'stock_qty' AS metric,        -- 指标1：期末库存
           SUM(i.stock_qty) AS val
    FROM inventory i
    JOIN products p ON p.product_id = i.product_id
    GROUP BY p.category
    UNION ALL
    SELECT p.category, 'sold_qty_30d' AS metric,     -- 指标2：6月总销量
           SUM(s.qty)
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2024-06-01' AND s.sale_date < '2024-07-01'
    GROUP BY p.category
)
SELECT category,                                     -- 品类
       MAX(CASE WHEN metric = 'stock_qty'    THEN val END) AS stock_qty,          -- 列1：库存
       ROUND(MAX(CASE WHEN metric = 'sold_qty_30d' THEN val END) / 30.0, 2) AS qty_per_day, -- 列2：日均销量
       ROUND(MAX(CASE WHEN metric = 'stock_qty'    THEN val END)
             / NULLIF(MAX(CASE WHEN metric = 'sold_qty_30d' THEN val END) / 30.0, 0), 1) AS turn_days -- 周转天数
FROM metric
GROUP BY category                                    -- 一个品类两行并成一行
ORDER BY turn_days DESC;
```

结果解读：与解法一同值。**【加分点】**长表结构的优势是加指标只加一段 UNION ALL 而不动主查询，适合指标不断膨胀的库存健康度报表，这是数仓建模里"行转列前置到查询侧"的常见套路。

### 5. 性能分析与优化

解法一两段聚合各自扫一遍表，JOIN 发生在品类级小结果上，代价最低、语义最清晰；解法二多一次 UNION ALL 的数据搬运，但仍是品类级小表操作，差异可忽略，扩展性更好。两者共同的性能要点：inventory 与 sales 都先按品类聚合再连接，严禁明细级 JOIN 后聚合（会双重放大且可能内存溢出）；products 按主键 JOIN 开销小；sales (sale_date, product_id, qty) 索引、inventory (product_id, store_id) 索引可走覆盖扫描；库存若来自多仓多店日快照大表，先按快照日分区裁剪；月度周转报表建议由数仓按"品类周"预聚合，查询侧只做最后一步除法。

### 6. 面试延伸考点

- **为什么不能用"期末库存÷有销售天数"算日均？** 回答要点：会高估周转速度（分母变小），且不同品类销售天数不同导致横向不可比；标准做法固定除以自然月天数或营业天数。
- **金额口径和数量口径的周转天数什么时候会矛盾？** 回答要点：涨价促销期数量周转快但金额库存占用大，两者背离提示价格结构变化；常规监控用数量口径看运营、金额口径看资金。
- **库存表按批次记录，为什么不能直接和销售明细JOIN？** 回答要点：批次行×销售行产生笛卡尔放大，库存被销售行数复制、销量被批次数复制，两边都错；必须各自聚合到同一粒度再连接。
- **周转天数短就一定好吗？** 回答要点：过短可能意味着安全库存不足、断货风险高，要结合缺货率、到货周期（订货提前期）设定品类基准带，而不是一味求短。

### 7. 业务拓展思考

周转天数要转化为"资金与货龄"双视角：结合 in_date 计算库龄分布，长周转+长库龄即双重压货，优先促销清库；短周转+短库龄但到货周期长的品类要提高订货频次。采购动作上，压货品类下调下月订单并申请档期支持，断货预警品类启用供应商直送。口径延展：分门店周转（门店间调拨机会）、批次级先到期先出（FEFO）执行率、以及"周转天数×毛利率"矩阵定位既压货又不赚钱的品类，作为清库优先级排序。

### 3. 解题思路

先定口径：以统计基准日（示例固定为 '2024-06-30'，生产中可用 CURDATE()）计算每批次的剩余保质期天数 `DATEDIFF(expire_date, 基准日)`；**临期判定不能一刀切天数**——保质期7天的鲜牛奶剩3天和保质期365天的矿泉水剩3天完全是两回事，必须用"剩余天数 ÷ 总保质期天数"的比例口径，剩余不足1/3即临期。分级规则：剩余占比 ≤1/6（或剩余≤2天）为红色立即折价，1/6~1/3为黄色促销预警，已过期为"过期-下架"，另仓处理。实现路径：解法一 JOIN 商品表后在 SELECT 中用嵌套 CASE 分级，利用 MySQL 允许在 HAVING 中引用列别名的特性过滤掉正常批次；解法二用 CTE 先算剩余比例，再过滤 + 用 ROW_NUMBER() OVER (PARTITION BY store_id ORDER BY days_left) 给每家店生成"紧急度序号"，让店长按序处理。易错点：只统计 stock_qty > 0 的批次； INTERVAL 表达式里的 shelf_life_days/3 要 FLOOR 取整；除法结果为小数，比较时注意类型。

### 4. 参考解法

解法一：条件分级 + HAVING 别名过滤（MySQL 特性写法）

```sql
SELECT i.store_id,                                   -- 门店ID
       i.product_id,                                 -- 商品ID
       p.product_name,                               -- 商品名称
       p.category,                                   -- 品类
       i.batch_no,                                   -- 批次号
       i.stock_qty,                                  -- 该批次剩余库存
       p.shelf_life_days,                            -- 总保质期天数
       DATEDIFF(i.expire_date, '2024-06-30') AS days_left,                      -- 剩余保质期天数
       ROUND(DATEDIFF(i.expire_date, '2024-06-30') / p.shelf_life_days, 2) AS life_ratio, -- 剩余比例
       CASE
           WHEN DATEDIFF(i.expire_date, '2024-06-30') <= 0                    THEN '过期-立即下架'  -- 已到期
           WHEN DATEDIFF(i.expire_date, '2024-06-30') / p.shelf_life_days <= 1/6 THEN '红色-立即折价' -- 剩余不足1/6
           WHEN DATEDIFF(i.expire_date, '2024-06-30') / p.shelf_life_days <= 1/3 THEN '黄色-促销预警' -- 剩余不足1/3
           ELSE '正常'                                                        -- 其余不预警
       END AS warn_level
FROM inventory i
JOIN products p ON p.product_id = i.product_id       -- 挂上保质期与商品信息
WHERE i.stock_qty > 0                                -- 只看还有库存的批次
HAVING warn_level <> '正常'                          -- MySQL允许HAVING引用别名：过滤掉正常批次
ORDER BY days_left;                                  -- 最先到期的排最前
```

结果解读：清单按"距离过期最近"排序，店长从上往下贴折价签即可。红色批次当天必须动作，黄色批次列入近三天促销计划。

解法二：CTE过滤 + ROW_NUMBER 生成门店内紧急度序号

```sql
WITH danger AS (                                     -- 第一层：筛出临期批次并算好剩余指标
    SELECT i.store_id, i.product_id, p.product_name, p.category,
           i.batch_no, i.stock_qty, p.shelf_life_days,
           DATEDIFF(i.expire_date, '2024-06-30') AS days_left,               -- 剩余天数
           DATEDIFF(i.expire_date, '2024-06-30') / p.shelf_life_days AS life_ratio -- 剩余比例
    FROM inventory i
    JOIN products p ON p.product_id = i.product_id
    WHERE i.stock_qty > 0
      AND i.expire_date > '2024-06-30'                -- 已过期批次另行下架流程，不进促销清单
      AND i.expire_date <= DATE_ADD('2024-06-30',     -- 到期日早于"今天+保质期/3天"
            INTERVAL FLOOR(p.shelf_life_days / 3) DAY) -- FLOOR取整天数，等价于剩余不足1/3
)
SELECT d.*,
       CASE WHEN d.life_ratio <= 1/6 THEN '红色'      -- 二级判定：红/黄
            ELSE '黄色' END AS warn_level,
       ROW_NUMBER() OVER (PARTITION BY d.store_id     -- 每家门店独立编号
                          ORDER BY d.days_left, d.stock_qty DESC) AS urg_no -- 先到期、量大的排前面
FROM danger d
ORDER BY d.store_id, urg_no;                         -- 门店内按紧急度输出
```

结果解读：urg_no 让"先处理哪一批"有了明确顺序（先到期优先，同到期日先清大批量）。**【加分点】**把"剩余比例"而非"剩余天数"作为临期判定依据，并解释为什么不同保质期商品不能共用一个天数阈值，是效期管理题的核心得分点。

### 5. 性能分析与优化

两种解法都是 inventory×products 的主键 JOIN 加日期计算，行数受门店批次量控制（单店数千行级别），代价很小。注意点与优化建议：判定条件 `expire_date <= DATE_ADD(基准日, INTERVAL ...)` 中若含 product 关联列则无法对 expire_date 直接用简单索引区间，可先在 CTE/子查询里按 `expire_date <= 基准日 + 最大可能提前量` 粗筛（如90天）再精确判断，让 expire_date 索引生效；每日跑批时把基准日参数化（SET @stat_date），避免SQL里散落日期字面量；效期清单是典型"日更小结果集"，可落成 daily_expiry_alert 表供 POS 与打标设备直读；如果批次表过大，按门店或月分区并保留近3个批次周期。

### 6. 面试延伸考点

- **为什么临期判定用"剩余比例"而不是"剩余天数"？** 回答要点：长保与短保商品的风险节奏完全不同，比例口径自动适配；工程上常设"比例阈值+最短天数下限"双条件，避免365天保质期商品剩120天就被标红。
- **临期预警和"先进先出/先到期先出"（FEFO）是什么关系？** 回答要点：FEFO 是出库执行策略，决定先卖哪一批；预警是滞销诊断，决定要不要降价。批次表必须同时支持两者的查询。
- **同款商品多个批次库存，预警该怎么合并展示？** 回答要点：按 (store_id, product_id) 汇总临期总量、取最早到期批次为处置代表，门店按批次执行，报表按商品汇总，两个粒度都保留。
- **如果基准日要支持"每天自动跑"，SQL里怎么写最规范？** 回答要点：用 CURDATE() 或调度系统传入的统计日期变量，统一时间基准，禁止查询中混用系统时间与字面日期。

### 7. 业务拓展思考

临期预警的价值在于把损耗从事后报废变成事前干预：清单联动动态定价系统（按剩余比例自动生成折扣梯度）、员工内购通道与社区团购"临期专场"，能显著降低报损率。采购端，反复出现临期的SKU说明订货批量与动销不匹配，应缩小起订量或改为高频小批量补货；不同门店的临期结构差异还能识别陈列与订货的门店个性问题。口径延展：损耗率=报废金额/销售额可按品类与门店做基准对比，"预警→促销→动销"转化率则衡量清单本身是否真的被门店执行。

### 1. 业务背景

### 3. 解题思路

先定口径：分子是 register_store_id 归属门店、register_date 落在2024年6月的新增会员数（按注册门店考核，而不是按会员后来消费的门店）；分母是同门店同月进店人次 SUM(enter_cnt)。**【避坑指南】**两个指标来自不同的表、粒度不同（会员是注册事件、客流是小时统计），必须各自先聚合到"门店月"粒度再 JOIN；用 LEFT JOIN 以客流表为主表保留全部门店，注册数为0的门店用 COALESCE 补0后计算招募率，否则内连接会把"零招募"的差店静默丢掉，恰好漏掉最需要帮扶的对象。实现路径：解法一 CTE 两段聚合再 JOIN，并附 RANK 排名；解法二用相关标量子查询在门店维度上直接取注册数，展示另一种不写 JOIN 的取数方式。易错点：招募率是比率型指标，全网汇总时同样要"先加总再相除"；极小客流门店的招募率会剧烈波动，可加最低客流门槛。

### 4. 参考解法

解法一：两段CTE聚合 + LEFT JOIN + 排名（标准漏斗写法）

```sql
WITH reg AS (                                        -- CTE1：各店6月新注册会员数
    SELECT register_store_id AS store_id,
           COUNT(*) AS reg_cnt                       -- 注册事件计数
    FROM members
    WHERE register_date >= '2024-06-01'
      AND register_date <  '2024-07-01'              -- 2024年6月注册
    GROUP BY register_store_id
),
traffic AS (                                         -- CTE2：各店6月进店人次
    SELECT store_id,
           SUM(enter_cnt) AS enter_cnt               -- 小时级客流加总到门店月
    FROM store_traffic
    WHERE stat_date >= '2024-06-01'
      AND stat_date <  '2024-07-01'
    GROUP BY store_id
)
SELECT s.store_id,                                   -- 门店ID
       s.store_name,                                 -- 门店名称
       t.enter_cnt,                                  -- 当月进店人次
       COALESCE(r.reg_cnt, 0) AS reg_cnt,            -- 新注册会员数，零招募补0
       ROUND(COALESCE(r.reg_cnt, 0) / t.enter_cnt * 100, 2) AS reg_rate_pct, -- 招募率%
       RANK() OVER (ORDER BY COALESCE(r.reg_cnt, 0) / t.enter_cnt DESC) AS rk -- 招募率排名（高在前）
FROM traffic t                                       -- 以客流表为主表：有客流才有考核意义
JOIN stores s ON s.store_id = t.store_id
LEFT JOIN reg r ON r.store_id = t.store_id           -- LEFT JOIN：零招募门店不被丢掉
ORDER BY rk;                                         -- 按名次输出
```

结果解读：招募率高的门店通常收银台话术与礼品动线做得好；排名靠后且客流不小的门店，优先复盘办卡流程是否繁琐、员工是否被培训到位。

解法二：相关标量子查询取数 + 汇总行对比门店与全网

```sql
SELECT s.store_id,
       s.store_name,
       t.enter_cnt,                                   -- 当月进店人次
       (SELECT COUNT(*)                               -- 标量子查询：该店6月注册数
          FROM members m
         WHERE m.register_store_id = s.store_id
           AND m.register_date >= '2024-06-01'
           AND m.register_date <  '2024-07-01') AS reg_cnt,
       ROUND((SELECT COUNT(*)
                FROM members m
                WHERE m.register_store_id = s.store_id
                  AND m.register_date >= '2024-06-01'
                  AND m.register_date <  '2024-07-01') / t.enter_cnt * 100, 2) AS reg_rate_pct, -- 招募率%
       ROUND(t.enter_cnt / SUM(t.enter_cnt) OVER () * 100, 1) AS traffic_share_pct -- 该店客流占全网比重（辅助判断小客流噪音）
FROM (SELECT store_id,                               -- 内层：客流先聚合到门店月
             SUM(enter_cnt) AS enter_cnt
        FROM store_traffic
        WHERE stat_date >= '2024-06-01' AND stat_date < '2024-07-01'
        GROUP BY store_id) t
JOIN stores s ON s.store_id = t.store_id
ORDER BY reg_rate_pct DESC;
```

结果解读：traffic_share_pct 用于识别"低客流高招募率"的偶然领先，避免用小样本门店通报表彰。**【加分点】**能指出标量子查询在老版本MySQL可能逐行执行，并说明现代优化器的半连接改写与索引 (register_store_id, register_date) 的配合，是从"会写"到"会调"的标志。

### 5. 性能分析与优化

解法一两次聚合产生门店级小表，JOIN 代价可忽略，是首选；解法二标量子查询理论上每行执行一次 COUNT，但若 members 上存在 (register_store_id, register_date) 复合索引，MySQL 8.0 会将其物化/半连接化，代价可接受，门店数很多时仍建议回归解法一。优化建议：members 的 (register_store_id, register_date) 与 store_traffic 的 (stat_date, store_id) 索引覆盖两个过滤与分组；客流表先按月分区再聚合；若考核指标常态化，可建 store_month_kpi 宽表由调度任务月度刷新，报表只做展示层；招募质量线（注册当月有消费）需要再 JOIN sales，建议在 reg CTE 中用 EXISTS 追加一列，避免第三次扫全表。

### 6. 面试延伸考点

- **招募率分子按注册门店还是按会员消费门店统计？** 回答要点：考核招募效率必须按注册门店归因，激励才能落到执行动作上；会员价值分析则按消费门店/常购门店归因，两个口径用途不同。
- **怎么识别"僵尸会员"拉高的虚假招募？** 回答要点：跟踪新会员的注册后首购率、30天复购率，把"注册→首购→复购"三段漏斗与招募率并列考核，防止门店刷注册。
- **全网整体招募率怎么算才是对的？** 回答要点：先加总各店注册数与进店人次再相除（加权），不能对各店招募率求平均；分母还应剔除设备故障导致的异常客流。
- **如果要求环比招募率变化，要注意什么？** 回答要点：注册与客流都要对齐自然月边界，节假日大促月要标注，避免把"5月大促高客流稀释招募率"误读为执行力下降。

### 7. 业务拓展思考

招募率只是会员漏斗第一环，应与注册→首购转化、首购→复购串联成完整的"会员健康度"记分卡，让门店从"冲注册量"转向"经营会员质量"。运营动作上，高招募低首购的门店检查礼包核销流程，低招募高客流的门店做收银台动线与员工话术专项；礼品预算按"有效新客成本（礼品成本/首购新客数）"分配更有杠杆。口径延展：分渠道招募（小程序自助、收银台引导、企微地推）拆解效率差异，并按客群画像（年龄带、时段）识别最容易转化的进店人群，把招募从全员任务变成精准动作。

## RET-28 门店×品类销售交叉矩阵（行转列）

### 1. 业务背景

你是连锁超市总部的报表开发分析师。经营周报的第一张表是一张经典的"门店×品类"交叉矩阵：行是各门店，列是生鲜、酒水饮料、休闲食品、日配、粮油五大品类，单元格是当月销售额，最后一列是门店合计、便于横向比较门店体量；部分版本还要求在每列后再附"该品类占本店销售额比例"。业务方习惯在 Excel 里按列比较"哪家店的生鲜做得最强"，所以必须把行状明细"转"成宽表。这是报表开发面试里最经典的行转列题：既考 SUM(CASE WHEN) 的基本功，也考品类不固定时动态生成列的工程化思路。

### 3. 解题思路

行转列的标准动作是：按行维度（门店）GROUP BY，对每个列维度取值（品类）写一个 `SUM(CASE WHEN category='xx' THEN amount ELSE 0 END)` 生成一列。**【避坑指南】**三个细节最容易翻车：一是 ELSE 必须写 0（或 NULL 配合 COALESCE 语义），漏写 ELSE 时未命中行返回 NULL，SUM 会跳过导致数值碰巧正确但口径含混，而外层做除法时 NULL 会传染；二是列名用中文时加反引号；三是"列取值写死"与"品类变化"的矛盾——品类新增时固定写法要改SQL，工程上用 GROUP_CONCAT(DISTINCT category) 拼接动态SQL再 PREPARE/EXECUTE 执行，这也是面试区分初级与中高级的延伸点。实现路径：解法一固定列写法，加合计列与窗口占比列；解法二演示动态行转列的完整拼装与执行。

### 4. 参考解法

解法一：SUM(CASE WHEN) 固定列 + 合计列与占比

```sql
SELECT s.store_id,                                   -- 行维度：门店ID
       st.store_name,                                -- 门店名称
       ROUND(SUM(CASE WHEN p.category = '生鲜'     THEN s.amount ELSE 0 END), 2) AS `生鲜`,     -- 列1
       ROUND(SUM(CASE WHEN p.category = '酒水饮料' THEN s.amount ELSE 0 END), 2) AS `酒水饮料`, -- 列2
       ROUND(SUM(CASE WHEN p.category = '休闲食品' THEN s.amount ELSE 0 END), 2) AS `休闲食品`, -- 列3
       ROUND(SUM(CASE WHEN p.category = '日配'     THEN s.amount ELSE 0 END), 2) AS `日配`,     -- 列4
       ROUND(SUM(CASE WHEN p.category = '粮油'     THEN s.amount ELSE 0 END), 2) AS `粮油`,     -- 列5
       ROUND(SUM(s.amount), 2) AS `合计`,            -- 行合计：门店总销售额
       ROUND(SUM(CASE WHEN p.category = '生鲜' THEN s.amount ELSE 0 END) * 100.0
             / NULLIF(SUM(s.amount), 0), 1) AS `生鲜占比%` -- 示例占比列：生鲜占本店比重
FROM sales s
JOIN products p ON p.product_id = s.product_id       -- 取品类维度
JOIN stores st ON st.store_id = s.store_id           -- 取门店名称
WHERE s.sale_date >= '2024-06-01'
  AND s.sale_date <  '2024-07-01'                    -- 2024年6月
GROUP BY s.store_id, st.store_name                   -- 行维度分组
ORDER BY `合计` DESC;                                -- 按门店体量排序
```

结果解读：一行一个门店、一列一个品类，业务方可以横向比较"谁的生鲜强、谁的粮油弱"。合计列与分列之和严格相等（ELSE 0 保证不漏不重），可直接对账。

解法二：GROUP_CONCAT 拼动态SQL + PREPARE 执行（品类可扩展）

```sql
-- 第一步：把"每个品类一列"的CASE表达式动态拼出来
SELECT CONCAT(
    'SELECT s.store_id, ',                                        -- 行维度开头
    GROUP_CONCAT(
        DISTINCT CONCAT(
            'SUM(CASE WHEN p.category = ''', c.category, '''',    -- 单列表达式模板
            ' THEN s.amount ELSE 0 END) AS `', c.category, '`')
        ORDER BY c.category SEPARATOR ', '),                      -- 多列用逗号拼接
    ', ROUND(SUM(s.amount), 2) AS `合计`',
    ' FROM sales s JOIN products p ON p.product_id = s.product_id',
    ' WHERE s.sale_date >= ''2024-06-01'' AND s.sale_date < ''2024-07-01''',
    ' GROUP BY s.store_id ORDER BY `合计` DESC'
) INTO @sql                                                        -- 完整SQL存入变量
FROM (SELECT DISTINCT category FROM products) c;                   -- 品类清单来自数据本身

-- 第二步：预编译并执行动态SQL
PREPARE stmt FROM @sql;                                            -- 预处理语句
EXECUTE stmt;                                                      -- 执行
DEALLOCATE PREPARE stmt;                                           -- 释放
```

结果解读：品类无论增删都不需要改查询代码，列由数据驱动生成。**【加分点】**能说明动态SQL的适用边界——固定看板用解法一（可被BI工具解析、可加索引提示），元数据易变的自助分析用解法二，并提示拼接SQL要防注入（品类值来自受控维表）。

### 5. 性能分析与优化

解法一只扫一遍6月明细 + 两次小表JOIN，SUM(CASE WHEN) 是分支表达式，对行数线性、不产生额外扫描，5个品类列一次 GROUP BY 全部算完，是最高效的形态；解法二多一次元数据查询与 PREPARE 开销，列数极多时表达式数量增加解析成本，但扫描次数不变。优化建议：sales (sale_date, store_id, product_id, amount) 复合索引让月度过滤与分组走索引；若门店×品类矩阵是固定周报，物化到汇总表 store_category_month 并建 (ym, store_id) 索引；需要同时给出行合计与列合计时，可用 GROUPING 集合（ROLLUP）一次产出，注意 MySQL 的 `GROUP BY s.store_id WITH ROLLUP` 会附加合计行，前端要识别 NULL 行；大表上避免在 CASE 表达式里再嵌套子查询，一切条件先在过滤层完成。

### 6. 面试延伸考点

- **ELSE 0 和 ELSE NULL 对后续计算有什么影响？** 回答要点：SUM 忽略 NULL 两者结果相同，但对"列"做 AVG、或把 CASE 结果放入除法时 NULL 会传播成空值，报表出现空洞；宽表场景统一 ELSE 0 更稳。
- **MySQL 没有 PIVOT 关键字，动态行转列有哪几种方案？** 回答要点：应用层拼SQL（最常见）、GROUP_CONCAT+PREPARE（本例）、ETL/BI工具的透视节点；列数极多或不定时不建议在库内硬转，可交由前端透视表。
- **矩阵里出现"某门店某品类无销售"怎么展示？** 回答要点：ELSE 0 显示0更符合报表习惯；若0与"未经营该品类"是两回事，需要额外标记维度，避免把"没卖"和"没得卖"混为一谈。
- **要同时输出行合计与列合计，怎么写？** 回答要点：行合计在 SELECT 里 SUM(amount)；列合计可用 WITH ROLLUP 生成汇总行，或单独一条按品类 GROUP BY 的查询 UNION 起来，注意 ROLLUP 的 NULL 行识别。

### 7. 业务拓展思考

交叉矩阵是零售经营分析的最小完整模型：横向比较门店可发现"品类结构异常店"（如生鲜占比显著低于同规模门店），纵向比较品类可支撑采购谈判与货架配比。延展形态包括把单元格从销售额换成毛利率、周转天数、缺货率，形成多张同构矩阵拼成的经营驾驶舱；再加上同比列（去年同期矩阵）可一眼看出结构迁移。口径上要注意"占比列"的分母是本店合计还是全网合计需明确，跨店比较时用全网占比、店内诊断时用本店占比，一张表两种读法。

## RET-29 会员月均到店频次分档

### 1. 业务背景

你是连锁超市 CRM 团队的数据分析师。会员体系有几十万注册会员，但活跃度高度分化：有人一周来三次，有人办卡后再没出现。权益与营销资源有限，必须分层运营：把会员按"月均到店次数"分成高频活跃（月均≥8次）、一般活跃（3~8次）、低频（1~3次）、沉睡（0次）四档，高频会员推专享价与新品优先购，沉睡会员走大额唤醒券与召回短信。现在需要基于2024年第二季度（4~6月）消费数据输出各档位会员数、占比与平均月均频次，作为下季度分层权益方案的基线。口径上"到店"按有消费的自然日去重，月均=到店天数÷3个月。

### 2. 表结构说明

| M40012 | M | 1003 | 2024-03-20 |
| M50066 | F | 1001 | 2024-05-02 |

| sale_id | store_id | sale_date | product_id | member_id | qty | amount |
| --- | --- | --- | --- | --- | --- | --- |
| TK20240402001 | 1001 | 2024-04-02 | 5001 | M10023 | 2 | 25.80 |
| TK20240402002 | 1001 | 2024-04-02 | 5003 | M10023 | 1 | 2.00 |
| TK20240510003 | 1002 | 2024-05-10 | 5002 | M30077 | 2 | 21.00 |
| TK20240608004 | 1001 | 2024-06-08 | 5004 | M10023 | 3 | 23.94 |
| TK20240620005 | 1004 | 2024-06-20 | 5005 | M40012 | 1 | 49.90 |

### 3. 解题思路

先定口径：统计区间2024-04-01至2024-06-30共3个自然月；单会员"到店次数"= 该区间内有消费的自然日数（COUNT(DISTINCT sale_date)），一天来两次买两单只算到店1次；月均频次 = 到店天数 ÷ 3.0（用小数除法，避免整数除法把 5/3 砍成 1）。分档规则按业务阈值用 CASE WHEN 落档，沉睡会员（区间零消费）必须通过 members LEFT JOIN 消费统计保留并落档，**【避坑指南】**只从 sales 出发统计会天然丢掉零消费会员，导致"沉睡档"永远为空、唤醒动作没有目标人群，这是本题材最常见的翻车点。实现路径：解法一是"消费统计→LEFT JOIN全量会员→CASE分档→GROUP BY 汇总"四层结构，并给出各档占比；解法二用 NTILE(4) 按到店天数四分位分档，展示统计分位分档与业务规则分档的差异及适用场景。

### 4. 参考解法

解法一：LEFT JOIN 保留零消费会员 + 业务阈值 CASE 分档（标准写法）

```sql
WITH visits AS (                                     -- 第一层：各会员Q2到店天数
    SELECT member_id,
           COUNT(DISTINCT sale_date) AS visit_days   -- 按自然日去重：一天多单算一次到店
    FROM sales
    WHERE member_id IS NOT NULL
      AND sale_date >= '2024-04-01'
      AND sale_date <  '2024-07-01'                  -- 2024年第二季度
    GROUP BY member_id
),
tier AS (                                            -- 第二层：全量会员落档
    SELECT m.member_id,
           COALESCE(v.visit_days, 0) AS visit_days,  -- 零消费会员补0
           COALESCE(v.visit_days, 0) / 3.0 AS monthly_freq, -- 月均=到店天数/3个月（3.0保证小数除法）
           CASE
               WHEN COALESCE(v.visit_days, 0) >= 24 THEN '高频活跃'  -- 月均≥8次
               WHEN COALESCE(v.visit_days, 0) >= 9  THEN '一般活跃'  -- 月均3~8次
               WHEN COALESCE(v.visit_days, 0) >= 3  THEN '低频'      -- 月均1~3次
               ELSE '沉睡'                                           -- Q2零消费
           END AS freq_tier
    FROM members m
    LEFT JOIN visits v ON v.member_id = m.member_id  -- LEFT JOIN：沉睡会员不丢
)
SELECT freq_tier,                                    -- 档位
       COUNT(*) AS member_cnt,                       -- 档内会员数
       ROUND(AVG(monthly_freq), 2) AS avg_freq,      -- 档内平均月均频次
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS pct -- 档位占比（聚合套窗口）
FROM tier
GROUP BY freq_tier
ORDER BY FIELD(freq_tier, '高频活跃', '一般活跃', '低频', '沉睡'); -- 按业务顺序而非字母序展示
```

结果解读：假设沉睡档占比过半，说明会员池虚胖，唤醒预算应优先于拉新预算；高频档规模与占比是会员体系健康度的核心读数。

解法二：NTILE(4) 统计分位分档（对照写法）

```sql
WITH visits AS (                                     -- 仅含有消费的会员及其到店天数
    SELECT member_id,
           COUNT(DISTINCT sale_date) AS visit_days
    FROM sales
    WHERE member_id IS NOT NULL
      AND sale_date >= '2024-04-01' AND sale_date < '2024-07-01'
    GROUP BY member_id
),
tiered AS (                                          -- 按到店天数四分位分箱
    SELECT member_id,
           visit_days,
           NTILE(4) OVER (ORDER BY visit_days DESC, member_id) AS quartile -- 高到低四等份；加次级键保证确定性
    FROM visits
)
SELECT CASE quartile WHEN 1 THEN 'Q1-高'
                     WHEN 2 THEN 'Q2-中高'
                     WHEN 3 THEN 'Q3-中低'
                     ELSE 'Q4-低' END AS tier,       -- 分位档名
       COUNT(*) AS member_cnt,                       -- 档内人数（各档人数近似相等）
       MIN(visit_days) AS min_days,                  -- 档内最低到店天数
       MAX(visit_days) AS max_days                   -- 档内最高到店天数
FROM tiered
GROUP BY quartile
ORDER BY quartile;
```

结果解读：NTILE 保证各档人数均衡（各25%），适合做"相对分层"（如砍掉最底部25%的预算），但档位边界随分布漂移、不可跨期比较。**【加分点】**能对比"业务阈值分档（可跨期追踪、可配置权益）"与"NTILE分位分档（人群均衡、适合A/B实验分组）"的适用场景，说明为什么正式权益体系用前者、实验分流用后者。

### 5. 性能分析与优化

解法一扫一遍Q2明细做去重计数，再与 members 全量 LEFT JOIN，代价主要是 sales 的 GROUP BY 与 (member_id, sale_date) 的 DISTINCT；解法二在此基础上多一个窗口排序，但 visits 结果集是会员级（几十万行内），可接受。优化建议：sales 建 (member_id, sale_date) 复合索引，COUNT(DISTINCT sale_date) 可走索引松散扫描；members 按 register_date/状态先过滤出"在册且注册满一个季度"的会员再 JOIN，避免新注册会员稀释沉睡档（注册3天就进沉睡档不公平，应设"在册满90天"门槛）；分层结果是典型月度批产物，物化成 member_freq_tier 表并打上统计月份，供营销系统圈人直查；会员量极大时可按 member_id 哈希分片并行计算。

### 6. 面试延伸考点

- **"到店次数"按小票数还是按自然日去重？各适合什么场景？** 回答要点：自然日口径衡量"来店里多少回"，适合权益与频次分层；小票数口径衡量交易笔数，适合交易强度分析，两者都要在指标字典命名清楚。
- **为什么沉睡会员必须从 members 表 LEFT JOIN 出来？** 回答要点：sales 只有发生过消费的会员，零消费会员在消费数据里"不存在"，只查 sales 会系统性漏掉沉睡人群，导致分档结果偏乐观。
- **新注册会员要不要参与分档？** 回答要点：在册不满一个统计周期的会员观察窗不完整，应单独标记"新客观察期"或按注册月对齐口径，否则沉睡档被低估。
- **分档阈值怎么科学设定？** 回答要点：参考分布（分位数）+ 业务经验 + 权益成本测算，阈值改动要留存历史版本保证跨期可比。

### 7. 业务拓展思考

频次分档是分层运营的地基：往下可叠加客单价形成"频次×客单"九宫格，识别"高频低客单"（推凑单券）与"低频高客单"（品类唤醒）两类策略人群；往上可结合RFM做更细的生命周期管理。运营动作上，沉睡档先做召回实验（券面额、触达渠道A/B），一般活跃档推"频次挑战"任务制权益；采购端，高频档的购物篮结构决定常购品类的库存深度。口径延展：分档指标可从到店频次扩展到"全渠道触点频次"（含线上小程序浏览），把到店分层升级为全渠道活跃分层。

## RET-30 店员连带率与客单价对比

### 1. 业务背景

你是连锁超市门店运营部的数据分析师，支持店长做收银/导购团队的绩效复盘。同一门店里不同收银员经手的小票质量差异很大：有人结账时会主动推荐促销装和关联商品，有人只做被动扫码。店长需要一张2024年6月的店员对比表：每位店员（按收银工号）的连带率（其经手小票的平均商品件数）与客单价（其经手小票的平均金额），在门店内排名，并与本店均值对比。这张表用于识别需要辅导的店员、提炼优秀话术案例，而不是直接扣罚——所以必须有小票量样本保护，避免兼职少票店员被偶然数据冤枉或错奖。

### 3. 解题思路

先定口径：连带率 = 店员经手小票的总件数 ÷ 其小票数；客单价 = 总金额 ÷ 小票数。**【避坑指南】**必须先把数据压实到"小票粒度"（一张小票一行、件数金额预先汇总），再按店员聚合——因为一张小票包含多行商品，若直接在行明细上按店员算 `AVG(amount)` 会得到"行均价"而非客单价，连带率同理会被多行小票稀释；分母用 COUNT(DISTINCT sale_id) 防同一小票多行重复计数。样本保护用 HAVING COUNT(DISTINCT sale_id) >= 50（示例阈值），少票店员不参与排名但在明细中保留。实现路径：解法一"小票级→店员级"两级聚合加双 RANK 门店内排名；解法二一层聚合用聚合套窗口 `AVG(SUM(...)) OVER (PARTITION BY store_id)` 计算店员指标与本店均值的差，突出"对比均值"的辅导视角。易错点：退货小票（负金额、负件数）会扭曲个人指标，需按口径约定剔除或单列。

### 4. 参考解法

解法一：两级聚合 + 门店内双排名（标准写法）

```sql
WITH ticket AS (                                     -- 第一层：压实到小票粒度（一张小票一行）
    SELECT cashier_id,
           store_id,
           sale_id,
           SUM(qty) AS qty,                          -- 小票总件数
           SUM(amount) AS amt                        -- 小票总金额
    FROM sales
    WHERE sale_date >= '2024-06-01'
      AND sale_date <  '2024-07-01'                  -- 2024年6月
      AND amount > 0                                 -- 剔除退货小票（口径示例，需与业务确认）
    GROUP BY cashier_id, store_id, sale_id           -- 小票粒度去重
),
staff AS (                                           -- 第二层：店员级指标
    SELECT store_id,
           cashier_id,
           SUM(qty) AS total_qty,                    -- 经手总件数
           SUM(amt) AS total_amt,                    -- 经手总金额
           COUNT(*) AS ticket_cnt                    -- 小票数（此层每行即一张小票）
    FROM ticket
    GROUP BY store_id, cashier_id
    HAVING COUNT(*) >= 50                            -- 样本量保护：少于50张小票不参与排名
)
SELECT store_id,                                     -- 门店
       cashier_id,                                   -- 员工号
       ticket_cnt,                                   -- 小票量（判断工时负荷）
       ROUND(total_qty / ticket_cnt, 2) AS attach_rate,  -- 连带率=件数/小票数
       ROUND(total_amt / ticket_cnt, 2) AS avg_ticket,   -- 客单价=金额/小票数
       RANK() OVER (PARTITION BY store_id ORDER BY total_qty / ticket_cnt DESC) AS attach_rank, -- 门店内连带率排名
       RANK() OVER (PARTITION BY store_id ORDER BY total_amt / ticket_cnt DESC) AS ticket_rank   -- 门店内客单价排名
FROM staff
ORDER BY store_id, attach_rank;                      -- 门店内按连带率名次展示
```

结果解读：attach_rank 与 ticket_rank 的组合能识别两种典型店员——"连带高手"（两榜皆前）与"高价低连"（客单价高但件数少，可能靠推大单品），对应不同辅导方案。

解法二：一层聚合 + 聚合套窗口与本店均值对比（辅导视角写法）

```sql
SELECT s.store_id,                                   -- 门店
       s.cashier_id,                                 -- 员工号
       COUNT(DISTINCT s.sale_id) AS ticket_cnt,      -- 小票数（DISTINCT防小票多行重复计数）
       ROUND(SUM(s.qty)    / COUNT(DISTINCT s.sale_id), 2) AS attach_rate, -- 连带率
       ROUND(SUM(s.amount) / COUNT(DISTINCT s.sale_id), 2) AS avg_ticket,  -- 客单价
       ROUND(SUM(s.qty) / COUNT(DISTINCT s.sale_id)
             - AVG(SUM(s.qty) / COUNT(DISTINCT s.sale_id)) OVER (PARTITION BY s.store_id), 2) AS attach_gap, -- 连带率与本店均值差
       ROUND(SUM(s.amount) / COUNT(DISTINCT s.sale_id)
             - AVG(SUM(s.amount) / COUNT(DISTINCT s.sale_id)) OVER (PARTITION BY s.store_id), 2) AS ticket_gap  -- 客单价与本店均值差
FROM sales s
WHERE s.sale_date >= '2024-06-01' AND s.sale_date < '2024-07-01'
  AND s.amount > 0                                   -- 口径同解法一：剔除退货
GROUP BY s.store_id, s.cashier_id                    -- 店员粒度分组
HAVING COUNT(DISTINCT s.sale_id) >= 50               -- 样本量保护
ORDER BY s.store_id, attach_gap DESC;                -- 高于均值最多的排前面
```

结果解读：gap 值直接量化"比同事强多少/差多少"，负值超阈值的店员进入辅导名单。**【加分点】**`AVG(SUM(x)) OVER (PARTITION BY ...)` 先按店员聚合、再对聚合结果按门店求均值的写法，展示对"聚合函数嵌套窗口函数"执行顺序（先分组聚合、后开窗）的掌握。

### 5. 性能分析与优化

解法一两次聚合：明细→小票（行数压缩到小票级）→店员（几十行），成本集中在第一层的 GROUP BY；解法二一层聚合直接到店员级，扫一遍明细，配合 COUNT(DISTINCT sale_id) 的去重开销，通常更快，但两级聚合版在需要小票级中间结果（如剔除异常小票、按小票打标）时更灵活。优化建议：sales 建 (store_id, sale_date, cashier_id) 或 (cashier_id, sale_date) 索引辅助过滤与分组；先按日期与 amount>0 过滤再聚合；店员绩效月度化后建议按月物化 staff_kpi 表，季度复盘直接取数；若一条小票理论上有多个收银员字段冲突，聚合前先做小票级仲裁（如取扫码时间最晚者），把数据质量修复放在最内层 CTE。

### 6. 面试延伸考点

- **为什么店员指标必须在"小票粒度"上先聚合？直接在行明细算AVG会怎样？** 回答要点：多行商品的小票权重被放大、单行小票被稀释，AVG(amount) 是行均价而非客单价；分子分母同粒度是一切均值口径的第一原则。
- **连带率高的店员一定是优秀店员吗？** 回答要点：不一定，可能是班次集中在生鲜高峰（件数天然多）或过多推销引发投诉；要结合班次结构、客群构成、投诉率做归因，指标用于辅导而非单一奖惩。
- **兼职店员小票量很少，直接排名有什么问题？** 回答要点：小样本方差大，排名噪音高；用 HAVING 最小样本量门槛，或改用贝叶斯收缩（向门店均值收缩）处理小样本估计。
- **退货怎么处理才公平？** 回答要点：退货冲减会让被退单店员指标虚低，可按"退货归因到原销售店员"或单列退货率指标，关键是与HR确认口径并全员公示。

### 7. 业务拓展思考

店员级连带率与客单价是"能力复制"的起点：把 Top 店员的结账话术整理成SOP并培训，往往比改陈列更见效；指标还可与排班联动，让高连带店员驻守高峰时段放大价值。延展口径包括分品类连带（谁擅长推酒水、谁擅长推日配）、会员招募数（收银员兼拉新考核）、以及服务分（满意度/投诉率）组成的均衡记分卡，避免单一销售指标带来的行为扭曲。长期看，店员指标数据可与培训系统打通，形成"数据识别短板—定向培训—指标复测"的闭环。
