## RET-31 门店销售额异动三因子归因（客流×转化×客单）

### 1. 业务背景

某连锁商超运营总监在周一晨会前发现：华东区S001门店上月销售额同比明显下滑，需要数据分析师在会上把下滑拆解清楚——到底是进店的人少了（客流）、进店后买的人少了（转化率），还是买的人花得少了（客单价）。这三类问题对应完全不同的干预手段：客流不足要加大引流投放与周边推广，转化率下滑要检查动线陈列、缺货与服务体验，客单价下降则要审视商品结构与价格带。销售分析的黄金公式是：销售额 = 进店客流 × 成交转化率 × 客单价，分析师需要用SQL把同比销售额差值精确分解到三个因子上，并给出各因子贡献金额。

### 2. 表结构说明

门店日客流成交汇总表 store_traffic_daily（由闸机/WiFi探针客流系统与POS汇总生成）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stat_date | DATE | 统计日期 |
| store_id | VARCHAR(10) | 门店编号 |
| enter_uv | INT | 当日进店人次 |
| deal_uv | INT | 当日成交人次（有实付大于0小票的人数） |
| gmv | DECIMAL(12,2) | 当日实付销售额 |

示例数据：

| stat_date | store_id | enter_uv | deal_uv | gmv |
|-----------|----------|----------|---------|-----|
| 2026-03-01 | S001 | 3200 | 1120 | 186400.00 |
| 2026-03-02 | S001 | 2950 | 1092 | 168200.00 |
| 2026-03-03 | S001 | 3050 | 1150 | 175900.00 |
| 2026-03-01 | S002 | 4100 | 1353 | 210500.00 |
| 2026-03-02 | S002 | 3880 | 1280 | 198700.00 |

### 3. 解题思路

先明确指标口径：转化率 = deal_uv / enter_uv（成交人次占进店人次），客单价 = gmv / deal_uv（实付金额除以成交人次），对比周期用同比（本期2026年3月 vs 上期2025年3月）。实现路径分两步：第一步用两层CTE分别聚合出两个期间每个门店的三个因子值，再JOIN拼成一行；第二步做差值分解。经典方法是连环替代法——按业务因果顺序（客流→转化→客单）逐个把因子从上期值替换成本期值，每次替换产生的差额记为该因子的贡献。更优雅的方法是对数分解法：因为销售额等于三因子乘积，取对数后加法关系成立，每个因子按 LN(本期/上期) 占总对数变化的比例分摊总变动额，权重之和恒为1。**【加分点】** 对数分解法天然无残差且与因子顺序无关，连环替代法则依赖替代顺序，面试中能主动对比两种方法的差异是明显加分项。易错点：转化率、客单价是比率因子，直接把"转化率变化额×客单价"算贡献会漏掉交互项；enter_uv 为0或因子为0时对数无定义需过滤。

### 4. 参考解法

解法一：连环替代法（多层CTE，按因果顺序逐因子替代）。

```sql
WITH cur AS (                                        -- 本期因子：2026年3月
    SELECT store_id,
           SUM(enter_uv) AS uv,                      -- 客流因子：进店人次
           SUM(deal_uv)  AS deal_uv,                 -- 成交人次
           SUM(gmv)      AS gmv                      -- 销售额
    FROM store_traffic_daily
    WHERE stat_date BETWEEN '2026-03-01' AND '2026-03-31'
    GROUP BY store_id
),
prev AS (                                            -- 上期因子：2025年3月（同比）
    SELECT store_id,
           SUM(enter_uv) AS uv,
           SUM(deal_uv)  AS deal_uv,
           SUM(gmv)      AS gmv
    FROM store_traffic_daily
    WHERE stat_date BETWEEN '2025-03-01' AND '2025-03-31'
    GROUP BY store_id
),
factor AS (                                          -- 拼接两期，计算三个因子
    SELECT c.store_id,
           c.uv AS uv1, p.uv AS uv0,                 -- 客流：本期/上期
           c.deal_uv / c.uv AS conv1,                -- 本期转化率 = 成交/进店
           p.deal_uv / p.uv AS conv0,                -- 上期转化率
           c.gmv / c.deal_uv AS ticket1,             -- 本期客单价 = GMV/成交人次
           p.gmv / p.deal_uv AS ticket0,             -- 上期客单价
           c.gmv AS gmv1, p.gmv AS gmv0
    FROM cur c
    JOIN prev p ON c.store_id = p.store_id           -- 两期都有数据的门店
)
SELECT store_id,
       ROUND(gmv1 - gmv0, 2)                       AS gmv_diff,       -- 销售额总变动
       ROUND((uv1 - uv0) * conv0 * ticket0, 2)     AS uv_effect,      -- 客流效应：只替换客流，其余用上期
       ROUND(uv1 * (conv1 - conv0) * ticket0, 2)   AS conv_effect,    -- 转化效应：客流已替换为本期
       ROUND(uv1 * conv1 * (ticket1 - ticket0), 2) AS ticket_effect,  -- 客单效应：前两项均取本期
       ROUND((uv1 - uv0) * conv0 * ticket0
           + uv1 * (conv1 - conv0) * ticket0
           + uv1 * conv1 * (ticket1 - ticket0), 2) AS check_sum       -- 校验列：三项之和应等于总变动
FROM factor;
```

三项效应之和恒等于销售额总变动（替代法在此顺序下无残差）。结果解读：若 uv_effect 为-5.2万、conv_effect 为-1.8万、ticket_effect 为-0.6万，说明下滑主要来自客流，动作应投向引流而非降价。

解法二：对数分解法（按对数权重分摊总变动额，顺序无关）。

```sql
WITH cur AS (
    SELECT store_id, SUM(enter_uv) AS uv, SUM(deal_uv) AS deal_uv, SUM(gmv) AS gmv
    FROM store_traffic_daily
    WHERE stat_date BETWEEN '2026-03-01' AND '2026-03-31'
    GROUP BY store_id
),
prev AS (
    SELECT store_id, SUM(enter_uv) AS uv, SUM(deal_uv) AS deal_uv, SUM(gmv) AS gmv
    FROM store_traffic_daily
    WHERE stat_date BETWEEN '2025-03-01' AND '2025-03-31'
    GROUP BY store_id
),
factor AS (
    SELECT c.store_id,
           c.uv AS uv1, p.uv AS uv0,
           c.deal_uv / c.uv AS conv1, p.deal_uv / p.uv AS conv0,
           c.gmv / c.deal_uv AS ticket1, p.gmv / p.deal_uv AS ticket0,
           c.gmv AS gmv1, p.gmv AS gmv0
    FROM cur c
    JOIN prev p ON c.store_id = p.store_id
)
SELECT store_id,
       ROUND(gmv1 - gmv0, 2) AS gmv_diff,
       -- 各因子对数变化占总对数变化的比例 × 总变动额 = 该因子贡献
       ROUND(LN(uv1 / uv0) / LN(gmv1 / gmv0) * (gmv1 - gmv0), 2)        AS uv_effect,
       ROUND(LN(conv1 / conv0) / LN(gmv1 / gmv0) * (gmv1 - gmv0), 2)    AS conv_effect,
       ROUND(LN(ticket1 / ticket0) / LN(gmv1 / gmv0) * (gmv1 - gmv0), 2) AS ticket_effect
FROM factor
WHERE gmv1 <> gmv0                                  -- 排除销售额不变（分母对数为0）
  AND uv0 > 0 AND uv1 > 0                           -- 对数要求因子为正
  AND conv0 > 0 AND ticket0 > 0;                    -- 上期因子为0无法取对数
```

由于 LN(gmv1/gmv0) 恰好等于三个因子对数变化之和，三项权重之和恒为1，效应之和精确等于总变动额，且调换因子顺序结果不变。对比解法一：替代法三项效应会随替代顺序略有差异，对数法则唯一确定，适合对外汇报口径。

### 5. 性能分析与优化

两种解法都只需扫描两段日期范围的日表数据，先按门店聚合（分组数最多为门店数，代价很小），再做一次小表JOIN，区别仅在于解法二多计算三个 LN（开销可忽略）。优化建议：日表按 stat_date 做按月分区，查询裁剪到两个月分区；在 (store_id, stat_date) 上建联合索引覆盖聚合列；若门店量大、异动分析高频，可预聚合出门店×月份的因子宽表（uv、deal_uv、gmv），归因查询退化为对月表的简单计算；Hive/Spark SQL 下两种写法均支持（LN为内置函数），大数据量时把两期聚合结果分别落成临时表再JOIN，避免一次查询内重复扫描明细。

### 6. 面试延伸考点

1. **为什么用对数分解而不是连环替代法？** 要点：连环替代法结果依赖因子替代顺序（先换客流与先换客单得到的三项分配不同），对数分解法权重和为1、无残差、顺序无关；缺点是对数法因子必须为正且不能解释方向相反的复杂情形。
2. **进店人次的口径怎么定？** 要点：人次（含重复进出）还是去重人数、是否剔除员工与配送员、闸机计数与WiFi探针的误差校准，口径变更会造成同比不可比，必须冻结口径或双轨跑一段。
3. **如果销售额下滑但三个因子都只小幅变化怎么办？** 要点：说明存在交互效应或数据口径问题，可下钻到品类/周内日别找结构性原因，单因子归因解释不了的部分要补充维度下钻。
4. **转化率的分子用人数还是人次？** 要点：分子分母必须同口径（人次对人次、去重对去重），混用会系统性高估或低估转化率，尤其一人多单场景。

### 7. 业务拓展思考

三因子归因结论直接映射三类资源动作：客流效应主导时增加地推、线上到家引流与广告投放；转化效应主导时优化动线、补齐货架缺货、加强导购；客单效应主导时调整价格带与关联陈列、推动凑单满减。指标口径可延展为"毛利三因子"（客流×转化×毛利率），避免只盯销售额导致的低毛利冲量；也可以从同比扩展到对标同商圈竞对门店的横截面归因，定位是行业性下滑还是门店自身问题。

## RET-32 购物篮关联分析（支持度/置信度/提升度）与货架陈列优化

### 1. 业务背景

某便利店公司商品部要做季度货架陈列调优：把顾客经常一起购买的商品（如卤味与饮料、泡面与火腿肠）调整到相邻货位，利用连带消费提升客单。分析师需要从一个月的小票明细中挖掘商品关联规则，对每个商品对输出三个指标：支持度（两商品同时出现在一张小票的概率）、置信度（买了A的人同时买B的条件概率）、提升度（置信度除以B的购买概率，大于1才说明A的出现真正带动了B）。最终按提升度排序输出Top规则清单给陈列组和采购组，同时要过滤掉支持度过低的偶然规则，避免被小样本巧合误导。**【面试高频】** 购物篮三指标是零售数据分析笔试的经典压轴题型，考察自连接去对称与口径设计能力。

### 2. 表结构说明

小票明细表 sales（POS流水）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sale_id | BIGINT | 流水号 |
| store_id | VARCHAR(10) | 门店编号 |
| receipt_no | VARCHAR(20) | 小票号（同一单购物唯一） |
| member_id | VARCHAR(20) | 会员号（可为NULL） |
| product_id | INT | 商品编号 |
| sale_date | DATE | 销售日期 |
| qty | INT | 数量 |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| cost_amount | DECIMAL(10,2) | 成本金额 |

商品主数据表 products：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| product_id | INT | 商品编号 |
| product_name | VARCHAR(50) | 商品名称 |
| category_name | VARCHAR(20) | 所属品类 |
| is_private_label | TINYINT | 是否自有品牌（1是0否） |

示例数据（sales）：

| sale_id | store_id | receipt_no | member_id | product_id | sale_date | qty | pay_amount | cost_amount |
|---------|----------|------------|-----------|------------|-----------|-----|------------|-------------|
| 1001 | S001 | R20260901001 | M1001 | 3001 | 2026-09-01 | 1 | 32.80 | 18.50 |
| 1002 | S001 | R20260901001 | M1001 | 4002 | 2026-09-01 | 2 | 12.60 | 6.00 |
| 1003 | S001 | R20260901002 | NULL | 2005 | 2026-09-01 | 1 | 89.00 | 55.00 |
| 1004 | S001 | R20260901002 | NULL | 4002 | 2026-09-01 | 1 | 6.30 | 3.00 |
| 1005 | S001 | R20260901003 | M1002 | 3001 | 2026-09-02 | 2 | 65.60 | 37.00 |

### 3. 解题思路

先固定三个指标的口径定义（以小票为"购物篮"单位）：支持度 Support(A,B) = 同时含A与B的小票数 / 总小票数；置信度 Confidence(A→B) = 同含AB的小票数 / 含A的小票数；提升度 Lift = Confidence(A→B) / P(B)，P(B) = 含B的小票数 / 总小票数。实现路径：先把小票明细按 (receipt_no, product_id) 去重（同一小票同商品买多件只算一次关联），再用小票号自连接构造商品对，用 a.product_id < b.product_id 去掉对称重复与自我配对，最后分别聚合出成对计数、单品计数、总小票数三个量再组合出三指标。**【避坑指南】** 自连接时若不加 < 去对称，(啤酒,卤味) 和 (卤味,啤酒) 会重复计数且置信度方向混淆；不做小票内去重会让多件购买虚增支持度；不设最小支持度阈值，低频组合会产出大量提升度虚高的垃圾规则。解法一做全量两两组合，解法二针对指定目标商品做定向挖掘，计算量骤减，适合日常迭代。

### 4. 参考解法

解法一：自连接成对法（全量商品对，一次聚合出三指标）。

```sql
WITH basket AS (                                     -- 第一步：小票-商品去重，同票同商品只留一行
    SELECT DISTINCT receipt_no, product_id
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30'
      AND store_id = 'S001'                          -- 货架以单店为单位，先锁定门店
),
pair_cnt AS (                                        -- 第二步：小票内商品两两配对
    SELECT a.product_id AS pa,
           b.product_id AS pb,
           COUNT(*)     AS ab_cnt                      -- 同时含两商品的小票数
    FROM basket a
    JOIN basket b
      ON  a.receipt_no = b.receipt_no                  -- 同一张小票
     AND a.product_id  < b.product_id                  -- 去对称：只保留 A<B 一对，防重复与自配
    GROUP BY a.product_id, b.product_id
),
single AS (                                          -- 第三步：单品出现的小票数
    SELECT product_id, COUNT(*) AS cnt
    FROM basket
    GROUP BY product_id
),
total AS (                                           -- 第四步：总小票数 N
    SELECT COUNT(DISTINCT receipt_no) AS n
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30'
      AND store_id = 'S001'
),
direction AS (                                       -- 第五步：展开 A→B 与 B→A 两个方向
    SELECT pa AS antecedent, pb AS consequent, ab_cnt FROM pair_cnt
    UNION ALL
    SELECT pb AS antecedent, pa AS consequent, ab_cnt FROM pair_cnt
),
rules AS (                                           -- 计算三指标
    SELECT d.antecedent, d.consequent, d.ab_cnt,
           s1.cnt AS a_cnt, s2.cnt AS b_cnt, t.n AS total_receipts
    FROM direction d
    JOIN single s1 ON s1.product_id = d.antecedent   -- P(A)
    JOIN single s2 ON s2.product_id = d.consequent   -- P(B)
    CROSS JOIN total t
    WHERE d.ab_cnt >= 30                             -- 最小支持度门槛：过滤小样本巧合
)
SELECT f1.product_name AS antecedent_name,           -- 前项商品名
       f2.product_name AS consequent_name,           -- 后项商品名
       ROUND(ab_cnt / total_receipts, 5) AS support,                                  -- 支持度
       ROUND(ab_cnt / a_cnt, 4)          AS confidence,                               -- 置信度 A→B
       ROUND((ab_cnt / a_cnt) / (b_cnt / total_receipts), 3) AS lift                   -- 提升度
FROM rules
JOIN products f1 ON f1.product_id = rules.antecedent
JOIN products f2 ON f2.product_id = rules.consequent
WHERE (ab_cnt / a_cnt) / (b_cnt / total_receipts) > 1                -- 只保留正相关规则
ORDER BY lift DESC, support DESC
LIMIT 20;
```

结果解读：如输出"卤味拼盘→冰咖啡，置信度0.31、提升度2.8"，说明买卤味的顾客买冰咖啡的概率是无卤味顾客的2.8倍，陈列组可将两者相邻摆放并在卤味货架端头放冰咖啡二次陈列位。

解法二：定向规则挖掘（只算指定目标商品作为前项的规则，避免全量组合爆炸）。

```sql
WITH basket AS (
    SELECT DISTINCT receipt_no, product_id
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30'
      AND store_id = 'S001'
),
target AS (                                          -- 目标商品（如新品卤味3001）出现过的小票
    SELECT receipt_no
    FROM basket
    WHERE product_id = 3001
),
co AS (                                              -- 与目标同篮共现的其他商品计数
    SELECT b.product_id,
           COUNT(*) AS co_cnt                        -- 共现小票数
    FROM basket b
    JOIN target t ON b.receipt_no = t.receipt_no     -- 与目标商品同小票
    WHERE b.product_id <> 3001                       -- 排除自身
    GROUP BY b.product_id
),
single AS (
    SELECT product_id, COUNT(*) AS cnt
    FROM basket
    GROUP BY product_id
),
total AS (
    SELECT COUNT(DISTINCT receipt_no) AS n
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30' AND store_id = 'S001'
)
SELECT p.product_name AS consequent_name,
       c.co_cnt,
       ROUND(c.co_cnt / t.n, 5) AS support,                            -- 支持度
       ROUND(c.co_cnt / (SELECT cnt FROM target_count_alias), 4) AS placeholder -- 见下方说明
FROM co c
JOIN single s ON s.product_id = c.product_id
JOIN products p ON p.product_id = c.product_id
CROSS JOIN total t;
```

实际执行时把置信度分母替换为目标商品的小票数（target CTE 的 COUNT(*)），例如先算 `SELECT COUNT(*) FROM target` 存入变量或在子查询中引用。结果解读：定向法把计算从 O(全量商品对) 降为 O(单商品×其他商品)，适合每周为每个新品/主推品生成一条"最佳邻居商品"清单。注：示例中 placeholder 处应替换为 `c.co_cnt / (SELECT COUNT(*) FROM target)`，完整可运行写法见性能分析中给出的最终形态。

> Hive/Spark SQL 差异：全量自连接在Hive上会产生大规模shuffle，建议先对 basket 按 receipt_no 分桶（CLUSTERED BY），或改用 collect_set 把每张小票聚成商品数组后用 explode 展开下标组合（posexplode 两次+过滤 i<j），能显著减少自连接代价；Spark SQL 可直接用 sameSelfJoin 优化或 cubic cube 预聚合。

### 5. 性能分析与优化

解法一的代价集中在 pair_cnt 自连接：设平均每票 n 个SKU、月票数 m，中间行数约 m×n²，是典型的join膨胀；解法二只有 m×n 的共现计数，代价低一个数量级。优化建议：自连接前先在 basket 内用 `WHERE product_id IN (SELECT product_id FROM single WHERE cnt >= 50)` 预过滤低频商品（低频商品不可能产出过阈值的规则）；把最小支持度条件下推到 pair_cnt 的 HAVING 提前裁剪；在 sales (store_id, sale_date, receipt_no) 建联合索引加速范围过滤；规模大时改为按周分片计算再合并。最终可运行的定向法置信度写法：`ROUND(c.co_cnt * 1.0 / (SELECT COUNT(*) FROM target), 4) AS confidence`，提升度为该置信度除以 `(s.cnt / t.n)`。

### 6. 面试延伸考点

1. **提升度接近1但置信度很高的规则有意义吗？** 要点：提升度≈1说明A的出现不改变B的购买概率（如米和油这类家常组合），摆在一起不会产生增量连带，陈列优化只应投给提升度显著大于1且支持度足够的规则。
2. **为什么不直接用共现次数排序？** 要点：共现次数被单品自身热度污染，热销品和任何商品共现都多；提升度归一化掉了基线概率，才能识别真正的关联。
3. **如何防止把"促销导致的临时关联"当成稳定规律？** 要点：剔除大促周期数据、拉长观察窗口、跨月验证规则稳定性，只有持续多期出现的规则才进陈列调整。
4. **关联分析和购物路径分析的区别？** 要点：小票只保留"同篮"关系丢失先后顺序，路径分析需要带时间戳的动线/加购序列数据，能回答"先看什么后买什么"。

### 7. 业务拓展思考

关联规则清单可直接落地为三类动作：货架相邻陈列、收银台 impulse 商品组合、线上加购推荐与满减凑单池设计。指标口径可延展为品类级关联（卤味→饮料的品类连带率）、跨时段关联（早餐时段 vs 夜宵时段规则不同）以及关联增量验证（调改货架后对比实验组与对照组的连带率变化）。进一步可以把提升度与两品的毛利率相乘得到"连带毛利贡献"，让陈列位分配同时服务销售额与毛利目标，而不是单纯追求规则强度。

## RET-33 会员RFM分层与到店频次变化追踪

### 1. 业务背景

会员运营负责人要在季度初做一轮会员唤醒：把存量会员按经典RFM三维分层——R（最近一次到店距今天数）、F（近90天到店频次）、M（近90天消费金额），识别出"高价值沉睡会员"（历史上买得多买得勤、但最近很久没来）单独投放唤醒券，并把普通会员与流失会员区分开避免预算浪费。同时需要追踪每个分层会员"本月 vs 上月"的到店频次变化，验证上月发的唤醒短信是否真的把人拉回了门店。输出物是分层层级的人数分布表和各层频次变化表，支撑CRM预算分配。**【面试高频】** RFM是会员运营必考题，考察分位数打分与业务阈值两套口径的设计能力。

### 2. 表结构说明

会员主表 members：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| member_id | VARCHAR(20) | 会员编号 |
| join_date | DATE | 入会日期 |
| gender | VARCHAR(4) | 性别 |
| age_band | VARCHAR(10) | 年龄段 |
| register_store_id | VARCHAR(10) | 注册门店 |

小票明细表 sales（复用RET-32结构，此处取 member_id、sale_date、pay_amount 三列）。

示例数据（members）：

| member_id | join_date | gender | age_band | register_store_id |
|-----------|-----------|--------|----------|-------------------|
| M1001 | 2024-03-15 | 女 | 26-35 | S001 |
| M1002 | 2024-07-02 | 男 | 36-45 | S001 |
| M1003 | 2025-01-20 | 女 | 18-25 | S002 |
| M1004 | 2023-11-08 | 男 | 46-55 | S002 |
| M1005 | 2025-05-30 | 女 | 26-35 | S001 |

示例数据（sales，节选会员消费行）：

| member_id | sale_date | pay_amount |
|-----------|-----------|------------|
| M1001 | 2026-09-28 | 156.50 |
| M1001 | 2026-09-12 | 88.20 |
| M1002 | 2026-05-19 | 230.00 |
| M1003 | 2026-09-30 | 45.80 |
| M1004 | 2026-08-21 | 312.40 |

### 3. 解题思路

口径先定清楚：R = 基准日（9月30日）减最近一次消费日期的天数；F = 近90天按天去重的到店天数（一天买三单只算1天，防止拆单虚高频次）；M = 近90天累计实付金额。打分有两条路线：分位数路线用 NTILE(5) 窗口把会员五等分打1-5分，优点是任何分布都能拉开层次；业务阈值路线用绝对标准（如R≤30天记5分），优点是跨期可比、业务好解释。分层用CASE组合R/F/M得分，重点圈出"重要挽留会员"（R差但F、M好）。频次追踪用条件聚合分别统计本月与上月到店天数作差。**【避坑指南】** R的打分方向最容易写反：R值是"距今天数"，越大越差，NTILE排序必须倒序；入会不满90天的新会员F天然偏低，要提前剔除或单独成层，否则会污染分位数切点。

### 4. 参考解法

解法一：分位数打分路线（NTILE窗口打分 + CASE分层 + 频次变化一并输出）。

```sql
WITH base AS (                                       -- 第一步：近90天消费明细
    SELECT s.member_id, s.sale_date, s.pay_amount
    FROM sales s
    WHERE s.sale_date >= '2026-07-02'
      AND s.sale_date <  '2026-10-01'
),
rfm AS (                                             -- 第二步：按会员聚合 R/F/M 及频次变化原料
    SELECT member_id,
           DATEDIFF('2026-09-30', MAX(sale_date)) AS r_value,              -- R：最近到店距基准日天数
           COUNT(DISTINCT DATE(sale_date))        AS f_value,              -- F：到店天数（按天去重）
           SUM(pay_amount)                        AS m_value,              -- M：累计实付
           COUNT(DISTINCT CASE WHEN sale_date >= '2026-09-01'
                               THEN DATE(sale_date) END) AS cur_days,      -- 本月到店天数
           COUNT(DISTINCT CASE WHEN sale_date <  '2026-09-01'
                               THEN DATE(sale_date) END) AS prev_days      -- 上月（8月+7月末段）到店天数
    FROM base
    GROUP BY member_id
),
scored AS (                                          -- 第三步：五分位打分（分值越大越优）
    SELECT *,
           NTILE(5) OVER (ORDER BY r_value DESC) AS r_score,                -- R倒序：越久没来分越低
           NTILE(5) OVER (ORDER BY f_value)      AS f_score,                -- F正序：越勤快分越高
           NTILE(5) OVER (ORDER BY m_value)      AS m_score                 -- M正序：花得越多分越高
    FROM rfm
)
SELECT member_id, r_value, f_value, m_value,
       cur_days - prev_days AS freq_delta,                                -- 频次变化：正=回暖，负=恶化
       CONCAT(r_score, f_score, m_score) AS rfm_code,                     -- RFM编码便于圈人
       CASE
         WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值会员'  -- 高分三项：核心客群
         WHEN r_score <= 2 AND f_score >= 4 AND m_score >= 4 THEN '重要挽留会员'  -- 高价值沉睡：唤醒重点
         WHEN r_score >= 4 AND f_score <= 2                   THEN '重要发展会员'  -- 新客潜力：提频
         WHEN r_score <= 2 AND f_score <= 2                   THEN '流失预警会员'  -- 双低：低成本触达
         ELSE '一般保持会员'
       END AS member_layer
FROM scored;
```

结果解读：假设输出中"重要挽留会员"占8%但M贡献占比22%，说明这是最值得投入唤醒预算的人群；若该层 freq_delta 均值为正，说明上月唤醒动作有效。

解法二：业务阈值路线（派生表分别算 R/F/M 再JOIN，用绝对阈值打分，跨月可比）。

```sql
WITH r_calc AS (                                     -- R 单独计算：全部存量会员的最近到店
    SELECT member_id,
           DATEDIFF('2026-09-30', MAX(sale_date)) AS r_value
    FROM sales
    WHERE sale_date >= '2025-10-01'                  -- 观察窗口取近12个月，避免把长期会员误判为流失
    GROUP BY member_id
),
fm_calc AS (                                         -- F/M 用近90天窗口
    SELECT member_id,
           COUNT(DISTINCT DATE(sale_date)) AS f_value,
           SUM(pay_amount)                 AS m_value
    FROM sales
    WHERE sale_date >= '2026-07-02' AND sale_date < '2026-10-01'
    GROUP BY member_id
)
SELECT COALESCE(r.member_id, f.member_id) AS member_id,
       CASE
         WHEN r.r_value IS NULL THEN '已流失'                       -- 12个月内零消费
         WHEN r.r_value <= 30 AND f.f_value >= 9 AND f.m_value >= 600 THEN '重要价值会员'
         WHEN r.r_value >  45 AND f.f_value >= 9 AND f.m_value >= 600 THEN '重要挽留会员'
         WHEN r.r_value <= 30 AND f.f_value <  9                    THEN '重要发展会员'
         WHEN r.r_value >  60 AND f.f_value <  3                    THEN '流失预警会员'
         ELSE '一般保持会员'
       END AS member_layer
FROM r_calc r
LEFT JOIN fm_calc f ON f.member_id = r.member_id;
```

结果解读：阈值版每月跑数时切点不动，9月与10月的分层结果可以直接对比观察会员迁移（如从"重要价值"滑落到"重要挽留"的人数），这是它比分位数版更适合做迁移追踪的原因；分位数版每月切点随分布漂移，层间不可比。

### 5. 性能分析与优化

解法一全程只有一次明细扫描加三次窗口排序，排序代价 O(N log N)，N 为活跃会员数，通常几十万级，MySQL单机可承受；解法二对 sales 扫描两次（12个月窗口与90天窗口），扫描量更大但无窗口排序。优化建议：在 sales (member_id, sale_date) 建联合索引，让两个聚合都能走索引范围扫描；窗口打分前先把 rfm 聚合结果收窄到会员粒度（本方案已做到），切忌把 NTILE 直接套在明细行上再聚合；若会员千万级（Hive/Spark），NTILE 需单 reducer 全排序，应改用 PERCENT_RANK 或近似分位数（分桶取样估算切点），并把 R/F/M 预计算成日增量的会员标签表，避免每次全量回溯90天明细。

### 6. 面试延伸考点

1. **F为什么按天去重而不是按小票数？** 要点：零售场景一天多单常是拆单（午市晚市、忘带东西二次进店），按小票数会虚高频次；按天去重更接近"到店行为"本质，具体口径要与运营对齐并冻结。
2. **分位数打分和业务阈值打分怎么选？** 要点：一次性圈人用分位数（无需拍阈值），跨期迁移追踪必须用固定阈值；折中方案是按季度评审一次阈值。
3. **怎么验证唤醒短信的效果？** 要点：不能只看唤醒层到店率回升，要用未触达的同类会员做对照组对比频次变化（双重差分思想，见RET-42），排除季节性自然回暖。
4. **RFM的M用销售额还是毛利？** 要点：高M会员可能是靠促销冲量的羊毛客，用毛利口径打分能识别真金白银的价值客，条件允许应双口径并行。

### 7. 业务拓展思考

RFM分层结果可联动：挽留层定向发高门槛券（满减拉客单）、发展层发提频券（限次周券）、流失层只做低成本短信召回。口径延展上有三个方向：把F扩展为"到店天数+到家订单天数"的全渠道频次；把R按品类分开（生鲜R短、百货R长，混合R会误判）；在分层之上叠加品类偏好标签形成"分层×品类"矩阵，指导选品与货架。长期看RFM应沉淀为会员标签宽表的固定分区，供营销系统每日圈人调用。

## RET-34 大促备货缺口测算（预测销量 vs 现有库存）

### 1. 业务背景

618大促开卖前一周，连锁商超采购部的计划员要完成最后一批补货决策：每个门店×每个参与促销的单品，大促期间预计能卖多少、现在手里有多少可用库存、缺口有多少金额。预测口径由商品部给出（近30天日均销量×促销弹性倍数×大促天数），可用库存要同时考虑门店在手库存、供应商在途货量并扣掉安全库存。缺口金额按成本价折算后汇总给采购总监，用于决定向供应商追加订单的优先级——缺口大且供应商交期赶不上开卖日的SKU要立刻转加急物流或调拨其他门店库存。输出物是SKU级缺口明细表和按缺口金额排序的补货优先级清单。

### 2. 表结构说明

|--------|------|------|

| base_daily_qty | DECIMAL(10,2) | 近30天日均销量 |
| promo_lift | DECIMAL(5,2) | 大促销量提升倍数（历史大促回归得到） |

| 2005 | 精酿啤酒6罐装 | 55.00 | 12 |

### 3. 解题思路

先把口径钉死：大促预测销量 = base_daily_qty × promo_lift × promo_days；可用库存 = 在手 + 在途 − 安全库存（安全库存是应对需求波动的缓冲，不能拿去卖）；缺口数量 = GREATEST(预测 − 可用， 0)，注意是"截断到0"而不是直接相减——库存过剩的SKU产生负缺口，若直接求和会让过剩与缺口互相抵消，掩盖真实补货需求，这是本题最大陷阱；缺口金额 = 缺口数量 × 成本价（对采购而言按成本衡量资金占用）。实现路径：三张表按门店×商品JOIN，缺口算出后分两个视角交付——SKU明细视角直接输出缺口与加急标记（供应商交期是否超过距开卖日剩余天数）；汇总视角用窗口按缺口金额降序累计占比做帕累托分析，锁定贡献80%缺口金额的头部SKU。**【避坑指南】** LEFT JOIN 库存表时无库存记录的门店×商品要按0处理，用 COALESCE 防止缺口被 NULL 吞掉。

### 4. 参考解法

解法一：SKU明细直算法（多表JOIN + GREATEST截断）。

```sql
WITH need AS (                                       -- 第一步：大促需求量测算
    SELECT store_id, product_id,
           CEIL(base_daily_qty * promo_lift * promo_days) AS forecast_qty   -- 预测销量，向上取整留余量
    FROM promo_forecast
),
avail AS (                                           -- 第二步：可用库存 = 在手 + 在途 - 安全库存
    SELECT store_id, product_id,
           stock_qty + in_transit_qty - safety_stock AS available_qty
    FROM inventory
    WHERE snapshot_date = '2026-05-25'               -- 只取最新快照
),
gap AS (                                             -- 第三步：缺口计算
    SELECT n.store_id, n.product_id, n.forecast_qty,
           GREATEST(n.forecast_qty - COALESCE(a.available_qty, 0), 0) AS gap_qty,  -- 无库存记录按0，负缺口截断
           p.cost_price,
           p.lead_time_days
    FROM need n
    LEFT JOIN avail a                                -- LEFT JOIN：预测有但库存表无记录的也要算缺口
      ON  a.store_id   = n.store_id
     AND  a.product_id = n.product_id
    JOIN products p ON p.product_id = n.product_id
)
SELECT g.store_id, g.product_id, p.product_name,
       g.forecast_qty,                               -- 大促预测销量
       g.gap_qty,                                    -- 缺口数量
       ROUND(g.gap_qty * g.cost_price, 2) AS gap_amount,                     -- 缺口金额（成本口径）
       CASE WHEN g.lead_time_days > 7                -- 交期是否超过距6月1日开卖的剩余7天
            THEN '加急催单' ELSE '正常下单' END   AS action_note
FROM gap g
JOIN products p ON p.product_id = g.product_id
ORDER BY gap_amount DESC;                            -- 缺口金额降序，采购从上往下看
```

结果解读：S001的精酿啤酒预测1800件、可用150件、缺口1650件、金额9万以上且交期12天超剩余7天，必须立刻加急或从S002（可用1000件）调拨。鲜牛奶交期1天可直接正常补货。

解法二：帕累托优先级视角（窗口累计占比，锁定头部补货清单）。

```sql
WITH need AS (
    SELECT store_id, product_id,
           CEIL(base_daily_qty * promo_lift * promo_days) AS forecast_qty
    FROM promo_forecast
),
avail AS (
    SELECT store_id, product_id,
           stock_qty + in_transit_qty - safety_stock AS available_qty
    FROM inventory
    WHERE snapshot_date = '2026-05-25'
),
gap AS (
    SELECT n.store_id, n.product_id,
           GREATEST(n.forecast_qty - COALESCE(a.available_qty, 0), 0) AS gap_qty,
           p.cost_price,
           ROUND(GREATEST(n.forecast_qty - COALESCE(a.available_qty, 0), 0)
                 * p.cost_price, 2) AS gap_amount    -- 缺口金额提前算好，供窗口引用
    FROM need n
    LEFT JOIN avail a
      ON  a.store_id = n.store_id AND a.product_id = n.product_id
    JOIN products p ON p.product_id = n.product_id
)
SELECT store_id, product_id, gap_qty, gap_amount,
       ROUND(SUM(gap_amount) OVER (ORDER BY gap_amount DESC)
             / NULLIF(SUM(gap_amount) OVER (), 0), 4) AS cum_share,         -- 按金额降序的累计占比
       CASE WHEN SUM(gap_amount) OVER (ORDER BY gap_amount DESC)
                 / NULLIF(SUM(gap_amount) OVER (), 0) <= 0.8
            THEN 'P0优先补货' ELSE 'P1次优' END     AS priority_tag          -- 覆盖前80%金额的为P0
FROM gap
ORDER BY gap_amount DESC;
```

结果解读：输出中 cum_share 首次越过0.8的那一行以上的SKU构成P0清单——通常不到20%的SKU贡献80%的缺口金额，采购只需要紧盯P0清单的供应商交期，避免在长尾SKU上分散谈判资源。

### 5. 性能分析与优化

两解法的主体代价相同：三表JOIN按 (store_id, product_id) 键进行，参与行数等于参与促销的SKU×门店数，通常几万到几十万级，均为小表JOIN，代价很低；解法二多了两个窗口排序（对 gap_amount 排序两次，实际优化器可合并）。优化建议：inventory 快照表按 snapshot_date 分区，查询裁剪到单日分区；在 (store_id, product_id, snapshot_date) 建联合索引；promo_forecast 与 inventory 最好预关联成"日库存×预测"宽表供大促期间每天刷新；Hive/Spark 下若 forecast 来自模型批量输出，建议按 store_id 分桶后与 inventory 分桶JOIN，避免shuffle；GREATEST 在各引擎均支持，注意 Hive 旧版本 NULL 传播行为（任一参数为NULL结果为NULL），需 COALESCE 预处理。

### 6. 面试延伸考点

1. **为什么缺口要用 GREATEST(x,0) 截断而不是直接相减？** 要点：过剩SKU的负缺口与缺货SKU的正缺口求和会互相抵消，总量看似平衡但结构上缺货依旧；正确做法是正负分开统计，负缺口单独作为"滞销风险清单"反馈给促销选品。
2. **在途库存什么情况下不应计入可用？** 要点：要按"预计到货日早于大促需求日"过滤在途（需要到货计划表），交期晚于开卖日的在途货赶不上销售窗口，计入会低估缺口。
3. **promo_lift 这个弹性倍数怎么来的？** 要点：用历史大促的（大促日均/日常日均）按品类回归，需剔除缺货导致的人为压低、控制价格折扣深度，否则弹性被低估。
4. **门店间调拨的SQL怎么写？** 要点：把正缺口与负缺口（过剩）按品类配对，生成"从X店调Y店Z件"建议表，需叠加调拨成本与时效约束。

### 7. 业务拓展思考

备货缺口测算的更大价值在于打通"预测—库存—订单"闭环：缺口清单直接生成采购建议单，加急标记驱动物流排程。口径延展：缺口可从数量口径升级为"服务水平口径"——不追求100%满足预测，而是按品类目标有货率（如生鲜98%、百货95%）反推安全库存与补货量；预测端可引入天气因子（见RET-45）与节假日因子（见RET-44）修正 promo_lift；负缺口清单应回流给商品部做促销力度或陈列位调整，形成"多备了少促销、缺货了加库存"的双向联动。

## RET-35 滞销品折扣清理ROI测算（折扣深度 vs 毛利损失）

### 1. 业务背景

季度末，连锁商超品类经理面对一批滞销SKU：库存周转天数远超品类均值，占压仓库与资金，部分商品保质期剩余不足两个月，再不清仓就要整批报废。清仓要打折——折扣越深动销越快、资金回笼越早，但单位毛利损失越大。经理需要一张SKU级清理决策表：每个滞销SKU按滞销程度匹配建议折扣档位，测算"折价清仓的让利成本"与"不清仓的预期损失（资金占用成本+预计报废损失）"之比（清理ROI），按ROI从高到低排清理优先级，ROI明显小于1的SKU宁可少打折慢慢卖或直接报废，避免"越清越亏"。输出物直接用于季度末清仓促销选品会。

### 2. 表结构说明

库存快照表 inventory：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| store_id | VARCHAR(10) | 门店编号 |
| product_id | INT | 商品编号 |
| snapshot_date | DATE | 快照日期 |
| stock_qty | INT | 库存数量 |
| last_inbound_date | DATE | 最近入库日期（用于推算剩余保质期） |

商品主数据表 products：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| product_id | INT | 商品编号 |
| product_name | VARCHAR(50) | 商品名称 |
| cost_price | DECIMAL(10,2) | 成本价 |
| list_price | DECIMAL(10,2) | 原价（正常售价） |
| shelf_life_days | INT | 保质期天数 |

销售明细表 sales（复用RET-32结构，此处取 product_id、sale_date、qty 计算近30天日销）。

示例数据（inventory，快照日2026-09-30）：

| store_id | product_id | snapshot_date | stock_qty | last_inbound_date |
|----------|------------|---------------|-----------|-------------------|
| S001 | 6001 | 2026-09-30 | 480 | 2026-06-10 |
| S001 | 6002 | 2026-09-30 | 260 | 2026-08-01 |

示例数据（products）：

| product_id | product_name | cost_price | list_price | shelf_life_days |
|------------|--------------|------------|------------|-----------------|
| 6001 | 芝士饼干礼盒 | 22.00 | 45.00 | 270 |
| 6002 | 冷榨果汁1L | 9.80 | 19.90 | 90 |
| 6003 | 冬季羽绒被 | 180.00 | 399.00 | 1825 |
| 6004 | 南瓜拿铁饮料 | 6.50 | 12.90 | 120 |

### 3. 解题思路

口径分四步钉死。第一步滞销判定：周转天数 = 库存量 ÷ 近30天日均销量，超过品类阈值（本例60天）判为滞销；**【避坑指南】** 近30天完全零动销的SKU日均销量为NULL或0，直接用除法会把这批"最该清理"的SKU在HAVING里悄悄过滤掉，必须用COALESCE+CASE把零动销的周转天数置为极大值（如999）。第二步折扣档位：按周转深度分档（>120天打5折、>90天打6.5折、其余8.5折），用CASE实现，不做连续线性折扣假设——需求价格弹性非线性，深折带来的动销加速远超线性外推。第三步两头算账：清仓的让利成本 =（原价−清仓价）×库存量（滞销品默认继续持有几乎不再正价售出，故让利按全额折扣差额计）；不清仓的预期损失 = 库存成本×资金月费率2%×预计再滞销3个月 + 库存成本×预计报废比例（剩余保质期≤30天按100%、≤60天按50%、其余按10%）。第四步清理ROI = 避免的损失 ÷ 让利成本，ROI大于1清仓划算。实现上多层CTE：日销聚合→滞销清单→档位与报废比例→ROI输出，另用窗口给ROI排序并NTILE(4)分批执行，避免一次性深折冲击整体毛利。

### 4. 参考解法

解法一：CASE分档 + 条件聚合直算ROI（SKU明细决策表）。

```sql
WITH daily_sale AS (                                 -- 第一步：近30天单品日均销量
    SELECT product_id, SUM(qty) / 30.0 AS avg_daily_qty
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30'
    GROUP BY product_id
),
slow AS (                                            -- 第二步：滞销SKU清单（按商品聚合全部门店）
    SELECT i.product_id,
           SUM(i.stock_qty) AS stock_qty,            -- 合计库存
           MAX(i.last_inbound_date) AS last_inbound, -- 取最早入库更保守，示例用最近入库列名
           MAX(p.cost_price)  AS cost_price,
           MAX(p.list_price)  AS list_price,
           MAX(p.shelf_life_days) AS shelf_life,
           CASE WHEN COALESCE(MAX(d.avg_daily_qty), 0) = 0 THEN 999          -- 零动销：周转置999天
                ELSE SUM(i.stock_qty) / MAX(d.avg_daily_qty) END AS turn_days
    FROM inventory i
    LEFT JOIN daily_sale d ON d.product_id = i.product_id   -- LEFT JOIN保住零动销SKU
    JOIN products p ON p.product_id = i.product_id
    WHERE i.snapshot_date = '2026-09-30'
    GROUP BY i.product_id
    HAVING CASE WHEN COALESCE(MAX(d.avg_daily_qty), 0) = 0 THEN 999
                ELSE SUM(i.stock_qty) / MAX(d.avg_daily_qty) END > 60        -- 滞销判定阈值
),
plan AS (                                            -- 第三步：折扣档位与预计报废比例
    SELECT s.*,
           CASE WHEN s.turn_days > 120 THEN 0.50     -- 深度滞销：5折
                WHEN s.turn_days > 90  THEN 0.65     -- 中度滞销：6.5折
                ELSE 0.85 END                        -- 轻度滞销：8.5折
                AS discount,
           CASE WHEN DATEDIFF(DATE_ADD(s.last_inbound, INTERVAL s.shelf_life DAY),
                              DATE '2026-09-30') <= 30 THEN 1.0             -- 临期30天内：预计全报废
                WHEN DATEDIFF(DATE_ADD(s.last_inbound, INTERVAL s.shelf_life DAY),
                              DATE '2026-09-30') <= 60 THEN 0.5             -- 半年内到期：半数报废
                ELSE 0.1 END                         -- 保质期充裕：仅少量损耗
                AS writeoff_ratio
    FROM slow s
)
SELECT product_id,
       stock_qty,
       ROUND(turn_days, 1) AS turn_days,
       discount,
       ROUND(list_price * discount, 2) AS clear_price,                     -- 清仓单价
       ROUND(stock_qty * list_price * (1 - discount), 2) AS margin_loss,   -- 让利成本=原价与折价差额×库存
       ROUND(stock_qty * cost_price * (0.02 * 3 + writeoff_ratio), 2) AS avoid_loss,  -- 避免损失=资金占用(2%×3月)+报废
       ROUND(stock_qty * cost_price * (0.02 * 3 + writeoff_ratio)
             / NULLIF(stock_qty * list_price * (1 - discount), 0), 2) AS clear_roi  -- 清理ROI
FROM plan
ORDER BY clear_roi DESC;
```

结果解读：芝士饼干礼盒周转200天、打5折，让利1.1万但避免损失约2.3万，ROI约2.1，优先清仓；羽绒被虽滞销但保质期长、报废比例低，ROI可能小于1，宁可减慢折扣节奏。

解法二：窗口打分分批清理（在ROI基础上输出执行节奏）。

```sql
WITH daily_sale AS (
    SELECT product_id, SUM(qty) / 30.0 AS avg_daily_qty
    FROM sales
    WHERE sale_date BETWEEN '2026-09-01' AND '2026-09-30'
    GROUP BY product_id
),
slow AS (
    SELECT i.product_id,
           SUM(i.stock_qty) AS stock_qty,
           MAX(i.last_inbound_date) AS last_inbound,
           MAX(p.cost_price) AS cost_price, MAX(p.list_price) AS list_price,
           MAX(p.shelf_life_days) AS shelf_life,
           CASE WHEN COALESCE(MAX(d.avg_daily_qty), 0) = 0 THEN 999
                ELSE SUM(i.stock_qty) / MAX(d.avg_daily_qty) END AS turn_days
    FROM inventory i
    LEFT JOIN daily_sale d ON d.product_id = i.product_id
    JOIN products p ON p.product_id = i.product_id
    WHERE i.snapshot_date = '2026-09-30'
    GROUP BY i.product_id
    HAVING CASE WHEN COALESCE(MAX(d.avg_daily_qty), 0) = 0 THEN 999
                ELSE SUM(i.stock_qty) / MAX(d.avg_daily_qty) END > 60
),
ranked AS (                                          -- 综合ROI与滞销深度排清理优先级
    SELECT s.*,
           ROW_NUMBER() OVER (ORDER BY
                CASE WHEN s.turn_days > 120 THEN 0.50 WHEN s.turn_days > 90 THEN 0.65 ELSE 0.85 END ASC,  -- 折扣深者先清
                s.turn_days DESC) AS clear_rank,                            -- 同档位内滞销越久越先
           NTILE(4) OVER (ORDER BY
                CASE WHEN s.turn_days > 120 THEN 0.50 WHEN s.turn_days > 90 THEN 0.65 ELSE 0.85 END ASC,
                s.turn_days DESC) AS batch_no                               -- 均分4批，分周执行
    FROM slow s
)
SELECT product_id, stock_qty, ROUND(turn_days, 1) AS turn_days,
       clear_rank, batch_no,
       CASE batch_no WHEN 1 THEN '第1周执行' WHEN 2 THEN '第2周执行'
                     WHEN 3 THEN '第3周执行' ELSE '第4周执行' END AS exec_plan
FROM ranked
ORDER BY clear_rank;
```

结果解读：批次1是折扣最深、滞销最久的SKU，第一周集中上清仓端头并短信触达；分批执行可避免同一品类多品同时深折互相蚕食销量，也平滑了毛利损失的月度波动。

### 5. 性能分析与优化

两解法主体代价相同：inventory 单日快照（行数=门店×SKU，万级）与日销聚合表（SKU粒度，千级）JOIN，均为小表；HAVING里的重复CASE表达式会让优化器各算一遍，可在下一层CTE先算 turn_days 再过滤以省一次计算。优化建议：日销聚合可预计算为 product_daily_sales 汇总表并按月刷新，清理分析变成纯小表运算；inventory 在 (snapshot_date, product_id) 建索引；Hive/Spark下若库存快照是全量分区表，务必按 snapshot_date 分区裁剪到单日；零动销SKU的999哨兵值只用于排序与分档，不要参与任何金额乘除，避免污染输出。

### 6. 面试延伸考点

1. **零动销SKU为什么会被HIVING条件误杀？** 要点：avg_daily_qty 为NULL或0时除法结果为NULL/报错，NULL>60为假，SKU被过滤；必须COALESCE后用CASE显式置哨兵值，这是滞销分析最高频的隐藏bug。
2. **让利成本为什么按全额折扣差额而不是按实际少卖的部分算？** 要点：前提假设是滞销品继续持有基本卖不动，清仓价卖出的每一件都放弃了原价收入；若部分商品正价仍可动销，该口径会高估让利，需用"清仓期预估正价销量"做修正。
3. **报废比例1.0/0.5/0.1怎么定更科学？** 要点：用历史同保质期档位商品的实际报废率统计替换拍脑袋常数，样本不足时按品类先验。
4. **ROI小于1的SKU怎么办？** 要点：分两种情况——资金占用主导的（保质期长）放慢折扣做常规动销；报废主导但折价后ROI仍小于1的（深度临期且需求极弱），直接报废回收货架与仓容，或转员工内购/公益捐赠减税。

### 7. 业务拓展思考

清理ROI表的上游是滞销预警（周转天数连续两周上升即预警），下游联动三件事：清仓档期排期、促销位资源分配、供应商退换货谈判（未拆封商品争取退供）。口径延展：ROI可从"避免损失/让利"扩展为现金流视角（清仓回款现值 vs 持有期资金占用现值），对现金流紧张的门店更有说服力；折扣档位可结合价格弹性试验（对同类SKU随机施放不同折扣观察动销响应）持续校准，把拍档位变成回归定价。
## RET-36 会员生命周期价值LTV与权益成本对比

### 1. 业务背景

公司拟扩大会员权益投入（付费会员卡的运费补贴、会员价折扣、积分返利），财务要求会员部先回答一个问题：一个会员在我们这里整个生命周期贡献的毛利（LTV），到底能不能覆盖他为公司消耗的权益成本？会员部需要按入会月份分组（cohort视角），追踪每批会员入会后第1个月、第2个月……的累计毛利贡献曲线（LTV曲线），再叠加同期的累计权益成本，算出各阶段的净贡献；同时对比付费会员与普通会员两条LTV曲线的差异，判断付费会员体系的权益投入是否带来了超额回报。输出物是"入会后第N月 × 会员类型"的人均累计LTV与人均累计权益成本对照表，作为下一年度会员预算的决策依据。**【加分点】** LTV分析必须用毛利口径而非GMV口径，并正确处理"未消费月份缺行"的问题，这两点最能区分候选人是否真做过会员分析。

### 2. 表结构说明

会员主表 members：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| member_id | VARCHAR(20) | 会员编号 |
| member_type | VARCHAR(10) | 会员类型（付费会员/普通会员） |
| join_date | DATE | 入会日期 |
| annual_fee | DECIMAL(8,2) | 付费会员年费（普通会员为0） |

销售明细表 sales（复用RET-32结构，此处取 member_id、sale_date、pay_amount、gross_profit）。

权益成本明细表 member_benefit_cost（按月归集）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| member_id | VARCHAR(20) | 会员编号 |
| cost_month | VARCHAR(7) | 成本归属月份（YYYY-MM） |
| benefit_cost | DECIMAL(10,2) | 当月权益成本（运费补贴+折扣让利+积分成本） |

示例数据（members）：

| member_id | member_type | join_date | annual_fee |
|-----------|-------------|-----------|------------|
| M1001 | 付费会员 | 2025-02-10 | 88.00 |

|-----------|------------|--------------|

| M1001 | 2025-03 | 6.20 |
| M1002 | 2025-03 | 0.00 |
| M1003 | 2025-04 | 2.80 |
| M1005 | 2025-06 | 4.10 |

### 3. 解题思路

口径三件事：第一，LTV用毛利口径（gross_profit 累计）而非销售额，因为权益成本是真金白银，必须用同量纲对比；第二，观察单位是"入会后第N月"（month_no），把不同入会时间的会员对齐到生命周期坐标轴上，按cohort月份与会员类型分组求人均；第三，权益成本按月累计后与累计LTV同轴对比，净贡献 = 人均累计毛利 − 人均累计权益成本。实现路径的核心难点在"补齐零消费月"：会员没有消费的月份在 sales 里没有行，直接按明细聚合再累积窗口，LTV曲线会出现断点（某月没消费就缺一行，之后的累计值看似跳变）。**【避坑指南】** 正确做法是先造"月历主轴"（递归CTE生成月份序列），与会员CROSS JOIN展开成"会员×月"全组合，LEFT JOIN消费毛利补零后再做累积窗口；MySQL 8.0 没有 IGNORE NULLS 的LAG/LAST_VALUE，缺行补齐是绕不开的前置步骤。易错点：新会员前期LTV低于权益成本是正常曲线，不能用第一个月的数据否定会员体系；流失会员与活跃会员混算会拉低曲线，汇报时要区分总体LTV与存活会员LTV。

### 4. 参考解法

解法一：递归CTE月历主轴 + 累积窗口（口径严谨版）。

```sql
WITH RECURSIVE month_spine AS (                      -- 第一步：递归生成月历主轴 2025-01 ~ 2026-09
    SELECT DATE '2025-01-01' AS month_start
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH            -- 每次推进一个月
    FROM month_spine
    WHERE month_start < DATE '2026-09-01'
),
cohort AS (                                          -- 第二步：选定观察 cohort（入会满12个月以上）
    SELECT member_id, member_type,
           DATE_FORMAT(join_date, '%Y-%m') AS cohort_month
    FROM members
    WHERE join_date BETWEEN '2025-01-01' AND '2025-06-30'
),
member_month AS (                                    -- 第三步：会员×月 全组合（含零消费月）
    SELECT c.member_id, c.member_type, c.cohort_month,
           DATE_FORMAT(m.month_start, '%Y-%m') AS sale_month
    FROM cohort c
    CROSS JOIN month_spine m                         -- 与月历交叉展开
    WHERE DATE_FORMAT(m.month_start, '%Y-%m') >= c.cohort_month   -- 只看入会后的月份
),
gp AS (                                              -- 第四步：每月实际毛利
    SELECT member_id,
           DATE_FORMAT(sale_date, '%Y-%m') AS sale_month,
           SUM(gross_profit) AS gp
    FROM sales
    GROUP BY member_id, DATE_FORMAT(sale_date, '%Y-%m')
),
filled AS (                                          -- 第五步：零消费月补0
    SELECT mm.member_id, mm.member_type, mm.cohort_month, mm.sale_month,
           COALESCE(g.gp, 0) AS gp
    FROM member_month mm
    LEFT JOIN gp g
      ON g.member_id = mm.member_id AND g.sale_month = mm.sale_month
),
ltv AS (                                             -- 第六步：累积窗口算LTV + 生命周期序号
    SELECT f.*,
           SUM(gp) OVER (PARTITION BY member_id ORDER BY sale_month
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS ltv_cum,  -- 累计毛利
           PERIOD_DIFF(CAST(REPLACE(sale_month, '-', '') AS SIGNED),
                       CAST(REPLACE(cohort_month, '-', '') AS SIGNED)) AS month_no   -- 入会后第N月
    FROM filled f
),
cost_cum AS (                                        -- 第七步：权益成本按月累计（先月聚合再累积）
    SELECT member_id, cost_month,
           SUM(SUM(benefit_cost)) OVER (PARTITION BY member_id ORDER BY cost_month) AS cost_cum
    FROM member_benefit_cost
    GROUP BY member_id, cost_month                   -- 窗口在GROUP BY之后执行，可套SUM(SUM())
)
SELECT l.member_type, l.month_no,
       COUNT(DISTINCT l.member_id) AS mem_cnt,                                   -- 该序号仍可观测的会员数
       ROUND(SUM(l.ltv_cum) / COUNT(DISTINCT l.member_id), 2) AS avg_ltv,        -- 人均累计LTV（毛利）
       ROUND(AVG(COALESCE(cc.cost_cum, 0)), 2) AS avg_cost,                      -- 人均累计权益成本
       ROUND(SUM(l.ltv_cum) / COUNT(DISTINCT l.member_id)
             - AVG(COALESCE(cc.cost_cum, 0)), 2) AS avg_net                     -- 人均净贡献
FROM ltv l
LEFT JOIN cost_cum cc
  ON cc.member_id = l.member_id AND cc.cost_month = l.sale_month
GROUP BY l.member_type, l.month_no
ORDER BY l.member_type, l.month_no;
```

结果解读：若付费会员在第7个月人均净贡献转正（14.5元）而普通会员天然无权益成本，且付费会员12个月人均LTV比普通会员高60元以上（超过88元年费），说明权益投入回报成立；若两条毛利曲线几乎平行，说明高价值人群本来就倾向办卡，权益只是选择效应而非增量。

解法二：自连接区间累计（老版本/无窗口函数环境的兼容写法）。

```sql
WITH gp AS (                                         -- 每月毛利（未补零，仅在有消费月份计算）
    SELECT member_id,
           DATE_FORMAT(sale_date, '%Y-%m') AS sale_month,
           SUM(gross_profit) AS gp
    FROM sales
    GROUP BY member_id, DATE_FORMAT(sale_date, '%Y-%m')
)
SELECT a.member_id, a.sale_month,
       SUM(b.gp) AS ltv_cum                          -- 自连接小于等于当前月的所有月份求和=累计LTV
FROM gp a
JOIN gp b
  ON  b.member_id  = a.member_id
 AND  b.sale_month <= a.sale_month                   -- 区间条件：b月不晚于a月
GROUP BY a.member_id, a.sale_month
ORDER BY a.member_id, a.sale_month;
```

结果解读：结果与解法一在有消费月份的取值完全一致，但零消费月份缺行，LTV曲线不连续，做cohort透视前需要再补轴。业务含义相同，适合快速验证或在窗口函数不可用的老环境迁移。对比提示：该写法是解释"为什么窗口函数值得用"的活教材——同一逻辑，自连接是 O(N²) 的行对行膨胀，窗口是 O(N log N) 的排序。

> Hive/Spark SQL 差异：Hive 不支持 WITH RECURSIVE，月历主轴可用 explode(sequence(to_date('2025-01-01'), to_date('2026-09-01'), interval 1 month)) 生成；窗口累积 SUM OVER 语法一致；Spark SQL 3.x 支持递归CTE与 IGNORE NULLS。

### 5. 性能分析与优化

解法一的代价主要是 member_month 的CROSS JOIN：cohort会员数×月数（如10万会员×21个月=210万行），行数可控但LEFT JOIN gp 需按 (member_id, sale_month) 排序或哈希，累积窗口再排一次序；cost_cum 的GROUP BY+窗口同理。优化建议：把 gp 与 cost_cum 先按月物化（月度会员汇总表），把JOIN收窄到必要月份；month_spine 建成永久日历维表，避免每次递归；递归深度受 cte_max_recursion_depth 限制（默认1000），跨年月数远小于该值无需调整；Hive/Spark下按 member_id 分桶可以让累积窗口的分区排序在本地完成，大幅减少shuffle；若只需 cohort 级曲线，可先在会员×月粒度聚合，再上卷到 cohort×month_no，最后一步才除以人数，避免在明细行上做重复除法。

### 6. 面试延伸考点

1. **LTV用GMV还是毛利？折中方案是什么？** 要点：与权益成本对比必须同量纲用毛利；若毛利数据缺失，可用GMV乘以品类毛利率近似，但要声明假设；严格版还应扣掉履约成本。
2. **为什么必须补齐零消费月？** 要点：累积窗口按存在行累积，缺行月份之后取到的累计值仍正确（因为值是累积的），但"第N月人均LTV"的分母与时间对齐会错——缺行月份会员根本不出现，该月人均被高估；cohort透视要求每个会员在第N月都有一行。
3. **存活LTV和总体LTV怎么区分？** 要点：总体LTV把流失会员的冻结曲线摊进人均，会低估活跃会员价值；存活LTV只在"当月仍活跃"的会员上平均，两者并排看才能同时回答获客质量与留存问题。
4. **付费会员LTV高，怎么证明是权益带来的增量而不是筛选效应？** 要点：办卡前的消费水平匹配（倾向得分或分桶匹配，见RET-42思路）、办卡前后自身对照、或利用权益改版的自然实验做双重差分。

### 7. 业务拓展思考

LTV×权益成本对照表的直接用途是会员预算分配：把权益成本从"无差别发放"改为按"边际LTV响应"投放——对LTV曲线仍在爬升的会员加码权益，对曲线已平台化的会员降本。口径延展：LTV可加入推荐价值（老客拉新数折算）、续卡率（付费会员年费收入应并入LTV）；cohort维度可叠加获客渠道，回答"哪个渠道来的会员更值钱"，反哺投放预算；还可把LTV曲线斜率突变点与运营动作日历对齐，识别真正影响留存的关键动作时点。

## RET-37 门店开业销售爬坡曲线对比

### 1. 业务背景

拓展部今年新开了8家社区超市，运营标准要求新店在开业后第6个月销售额达到同城市标杆店中位水平的80%，第12个月持平。现在需要把每家新店的销售表现换算到"开业后第N月"的生命周期坐标上，与历史标杆门店的爬坡曲线对比，输出每家新店的爬坡达成率、首次达标月序，识别爬坡明显偏慢的门店——这些门店要么选址有硬伤（客流不足）、要么开业营销透支（前3个月虚高后断崖），需要拓展部在下一家店选址复盘和当前门店运营干预中分别处理。由于各家门店开业时间不同，绝对日历月份的对比没有意义，必须做时间对齐。**【面试高频】** "不同起点的时间对齐"是窗口与日期函数的典型综合考察。

### 2. 表结构说明

门店主表 stores：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| store_id | VARCHAR(10) | 门店编号 |
| store_name | VARCHAR(50) | 门店名称 |
| open_date | DATE | 开业日期 |
| is_benchmark | TINYINT | 是否标杆店（1是0否） |
| close_date | DATE | 闭店日期（NULL为营业中） |

门店日销售额宽表 store_daily_gmv（POS按日汇总）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| store_id | VARCHAR(10) | 门店编号 |
| stat_date | DATE | 统计日期 |
| gmv | DECIMAL(12,2) | 当日实付销售额 |

示例数据（stores）：

| store_id | store_name | open_date | is_benchmark | close_date |
|----------|------------|-----------|--------------|------------|
| S001 | 幸福里店 | 2024-05-18 | 1 | NULL |
| S002 | 学院路店 | 2024-09-01 | 1 | NULL |
| S101 | 梧桐苑店 | 2025-03-15 | 0 | NULL |
| S102 | 康桥店 | 2025-05-08 | 0 | NULL |
| S103 | 滨江新天地店 | 2025-06-01 | 0 | NULL |

示例数据（store_daily_gmv）：

|----------|-----------|-----|
| S101 | 2025-03-16 | 52300.00 |
| S101 | 2025-03-17 | 48100.00 |
| S101 | 2025-04-16 | 61700.00 |
| S102 | 2025-05-09 | 44200.00 |
| S103 | 2025-06-02 | 58900.00 |

### 3. 解题思路

第一步做时间对齐：给每行月度销售计算"开业后第N月"，用 PERIOD_DIFF(本月的YYYYMM， 开业月的YYYYMM) 得到月序，开业当月为第0月。**【避坑指南】** 开业当月几乎必然不完整（如15日开业只算了半个月），直接纳入对比会让第0月系统性偏低，标准做法是把第0月剔除或按"开业日起的剩余天数/当月总天数"折算，方案里明确写出所选口径。第二步造对比基准：标杆店（is_benchmark=1）在每个月序上的销售额中位数作为爬坡基准线——用中位数而非均值，防止单个超级门店把基准拉高；MySQL 8.0 没有 MEDIAN 函数，用 ROW_NUMBER + COUNT 的经典行号法近似（取第⌈(N+1)/2⌉个附近的一或两行求平均）。第三步算达成率与首次达标月：每家新店各月序GMV除以基准中位数，达标线80%，用 MIN(CASE WHEN 达标 THEN month_no END) 取首次达标月序。易错点：PERIOD_DIFF 的入参是YYYYMM整数不是日期；新店样本在各月序上数量不同（刚开业的店没有第7月数据），达成率均值不能跨月直接平均。

### 4. 参考解法

解法一：中位数基准曲线（行号法近似中位数 + 全体新店分月序分布）。

```sql
WITH ms AS (                                         -- 第一步：门店×月份的GMV
    SELECT g.store_id, st.open_date,
           DATE_FORMAT(g.stat_date, '%Y-%m') AS ym,
           SUM(g.gmv) AS gmv
    FROM store_daily_gmv g
    JOIN stores st ON st.store_id = g.store_id
    WHERE st.open_date >= '2025-01-01'               -- 只看今年新店
      AND st.close_date IS NULL                      -- 排除已闭店
    GROUP BY g.store_id, st.open_date, DATE_FORMAT(g.stat_date, '%Y-%m')
),
ramp AS (                                            -- 第二步：换算“开业后第N月”，剔除不完整开业月
    SELECT store_id, ym, gmv,
           PERIOD_DIFF(CAST(REPLACE(ym, '-', '') AS SIGNED),
                       CAST(DATE_FORMAT(open_date, '%Y%m') AS SIGNED)) AS month_no  -- 月序，开业当月=0
    FROM ms
    HAVING month_no >= 1                             -- 开业当月（第0月）不完整，剔除
),
med AS (                                             -- 第三步：标杆店各月序中位数（行号法）
    SELECT month_no, AVG(gmv) AS median_gmv
    FROM (SELECT r.month_no, r.gmv,
                 ROW_NUMBER() OVER (PARTITION BY r.month_no ORDER BY r.gmv) AS rn,   -- 组内按GMV排名
                 COUNT(*)     OVER (PARTITION BY r.month_no)             AS cnt      -- 组内样本数
          FROM ramp r
          JOIN stores s ON s.store_id = r.store_id
          WHERE s.is_benchmark = 1                                   -- 只用标杆店造基准
         ) t
    WHERE rn IN (FLOOR((cnt + 1) / 2), CEIL((cnt + 1) / 2))           -- 奇数取中间1行，偶数取中间2行
    GROUP BY month_no                                -- 中间两行取平均即中位数
)
SELECT r.month_no,
       COUNT(*) AS store_cnt,                        -- 该月序在对比的门店数
       ROUND(m.median_gmv, 0) AS benchmark_median,   -- 标杆中位爬坡线
       ROUND(MIN(r.gmv), 0) AS min_gmv,              -- 最弱新店
       ROUND(MAX(r.gmv), 0) AS max_gmv               -- 最强新店
FROM ramp r
JOIN med m ON m.month_no = r.month_no
GROUP BY r.month_no, m.median_gmv
ORDER BY r.month_no;
```

结果解读：假设基准曲线从第1月的58万爬到第6月的92万，若某月序区间 min_gmv 只有31万，说明尾部新店爬坡严重掉队，需要下钻到具体门店。

解法二：逐店达成率与首次达标月（对齐基准后的窗口判断）。

```sql
WITH ms AS (
    SELECT g.store_id, st.open_date,
           DATE_FORMAT(g.stat_date, '%Y-%m') AS ym,
           SUM(g.gmv) AS gmv
    FROM store_daily_gmv g
    JOIN stores st ON st.store_id = g.store_id
    WHERE st.open_date >= '2025-01-01' AND st.close_date IS NULL
    GROUP BY g.store_id, st.open_date, DATE_FORMAT(g.stat_date, '%Y-%m')
),
ramp AS (
    SELECT store_id, gmv,
           PERIOD_DIFF(CAST(REPLACE(ym, '-', '') AS SIGNED),
                       CAST(DATE_FORMAT(open_date, '%Y%m') AS SIGNED)) AS month_no
    FROM ms
    HAVING month_no >= 1
),
bench AS (                                           -- 标杆店各月序均值作基准（此处用均值简化，也可换成中位数）
    SELECT r.month_no, AVG(r.gmv) AS bench_gmv
    FROM ramp r
    JOIN stores s ON s.store_id = r.store_id
    WHERE s.is_benchmark = 1
    GROUP BY r.month_no
),
cmp AS (                                             -- 新店逐月对齐标杆
    SELECT r.store_id, r.month_no, r.gmv,
           b.bench_gmv,
           ROUND(r.gmv / NULLIF(b.bench_gmv, 0), 3) AS reach_rate   -- 达成率=新店GMV/标杆
    FROM ramp r
    JOIN bench b ON b.month_no = r.month_no
)
SELECT store_id,
       MIN(CASE WHEN reach_rate >= 0.8 THEN month_no END) AS first_ok_month,       -- 首次达成≥80%的月序
       MAX(CASE WHEN reach_rate >= 0.8 THEN month_no END) AS latest_ok_month,      -- 最近一次达标月序
       ROUND(AVG(CASE WHEN month_no <= 6 THEN reach_rate END), 3) AS avg_reach_6m, -- 前6月平均达成率
       CASE WHEN MIN(CASE WHEN reach_rate >= 0.8 THEN month_no END) IS NULL
                 OR MIN(CASE WHEN reach_rate >= 0.8 THEN month_no END) > 6
            THEN '爬坡预警' ELSE '正常' END AS ramp_flag                            -- 超6个月未达标即预警
FROM cmp
GROUP BY store_id
ORDER BY ramp_flag DESC, avg_reach_6m;               -- 预警店置顶，按达成率升序
```

结果解读：first_ok_month 为3且逐月保持达标的是健康店；若 latest_ok_month 小于最大月序（先达标后跌破），提示开业促销透支后的回落，要区分于选址硬伤型的从未达标。

### 5. 性能分析与优化

两解法都先做日表→月表聚合（扫描量=新店开业以来的日行数，万级），再做多路JOIN与窗口排序，代价都很低。解法一的行号法中位数需要按 month_no 分区排序，窗口分区数等于月序数（十几个），排序开销小。优化建议：store_daily_gmv 按 stat_date 分区并在 (store_id, stat_date) 建索引；月度GMV可物化为 store_monthly_gmv 表，爬坡监控从"算一次"变成"每月增量追加"；标杆基准曲线一年重算一次即可落成配置表 bench_ramp_curve(month_no, median_gmv)；Hive/Spark下可用 percentile_approx 直接求近似中位数，省掉行号法嵌套，语义也更清晰。

### 6. 面试延伸考点

1. **为什么用开业后第N月而不是日历月对齐？** 要点：爬坡是生命周期行为，与季节、日历无关或弱相关；用日历月对比会把"开业早晚"与"爬坡快慢"两个效应混在一起；若季节性强（如冬季开业店），可进一步用同比季节指数调整。
2. **MySQL 8.0 怎么求中位数？** 要点：无MEDIAN函数，用 ROW_NUMBER 排序后取第⌈(N+1)/2⌉与⌈N/2+1⌉位置的均值；或 PERCENT_RANK 近似；Hive用percentile/percentile_approx。
3. **开业当月的半月数据怎么处理更严谨？** 要点：两种口径——剔除第0月（简单稳健）或按营业天数折算成日均再乘标准月天数（保留信息但对促销集中开业敏感），要在方案里声明并全期统一。
4. **爬坡慢的店怎么区分"选址问题"还是"运营问题"？** 要点：拆客流与客单（复用RET-31三因子），客流曲线平的偏选址，客流正常但转化/客单低的偏运营；再看商圈入店率与周边竞对动/static数据。

### 7. 业务拓展思考

爬坡曲线的价值在于把"新店评估"从拍脑袋变成基准管理：爬坡快的门店画像反哺选址模型（商圈类型、面积、竞对距离），爬坡慢的门店触发干预包（加大地推、调整开业档期、品类结构复核）。口径延展：爬坡指标可从GMV扩展到会员招募爬坡、到家业务渗透爬坡；基准线可细分为"同商圈类型标杆"，避免社区店对标购物中心店；更长期可以把爬坡期SKU动销率纳入，识别"销售额达标但结构单薄"的虚胖门店。

## RET-38 缺货导致销售损失估算（缺货时段销量外推）

### 1. 业务背景

供应链分析师做月度缺货复盘：门店货架单品断货期间销量为零，但这不等于"没有需求"——顾客想买买不到就去了竞对，这部分销售是真实流失的。采购部需要知道每个缺货事件"本应卖出的量"，作为安全库存设置、补货频次与供应商履约考核的依据。缺货时段来自巡检与收银系统的库存核销记录（stock_status 表的起止时间）。估算口径：用缺货前的历史销量外推缺货时段的"应有销量"，减去实际销量（断货期通常为零）即为损失。关键设计是基准的选择——**【加分点】** 直接用前一天做基准会被星期效应污染（周五断货用周四做基准低估损失），正确做法是取"最近4个相同星期几"的平均销量做基准，把周内节律剥离出来。

### 2. 表结构说明

### 3. 解题思路

口径设计分三步。第一步定基准：对每个缺货事件，取缺货开始日之前、与缺货开始日相同星期几的最近4天，计算该商品的日平均销量作为"基准日销"。第二步算损失：损失销量 = 基准日销 ×（缺货小时数/24），毛利损失 = 损失销量 ×（售价−成本）。第三步汇总到门店×商品粒度。两条实现路径：解法一是"日基准×时长"的粗估法，不展开缺货时段，逻辑简单、计算量小，适合月度复盘的量级判断；解法二是"逐小时展开+同时段基准"的精细法，用递归CTE把缺货时段展开成逐小时行，再对每个小时取历史同时段（同小时钟点）的平均销量，能捕捉日内节律（早高峰的鲜牛奶和深夜的啤酒完全不同），适合高价值单品的精确索赔测算。**【避坑指南】** 递归CTE默认深度上限 cte_max_recursion_depth=1000，跨多天的长缺货事件展开行数超限会直接报错，需要调参或改用日历表JOIN；缺货时段若与促销重叠，基准销量被促销抬高会高估损失，应剔除促销期样本或加标记。

### 4. 参考解法

解法一：同星期几日基准 × 缺货时长（粗估法）。

```sql
WITH daily AS (                                      -- 第一步：单品日销量
    SELECT store_id, product_id, stat_date, SUM(qty) AS day_qty
    FROM sales_hour
    GROUP BY store_id, product_id, stat_date
),
wk AS (                                              -- 第二步：按“门店×商品×星期几”取最近样本排序
    SELECT d.*,
           ROW_NUMBER() OVER (PARTITION BY store_id, product_id, WEEKDAY(stat_date)
                              ORDER BY stat_date DESC) AS rn      -- 同星期几内按日期倒序
    FROM daily d
),
baseline AS (                                        -- 第三步：最近4个同星期几的平均日销作基准
    SELECT store_id, product_id,
           WEEKDAY(stat_date) AS wd,                 -- 0=周一 … 6=周日
           AVG(day_qty) AS base_qty
    FROM wk
    WHERE rn <= 4
    GROUP BY store_id, product_id, WEEKDAY(stat_date)
),
loss AS (                                            -- 第四步：外推损失
    SELECT o.store_id, o.product_id,
           TIMESTAMPDIFF(HOUR, o.oos_start, o.oos_end) AS oos_hours,               -- 缺货时长（小时）
           b.base_qty,
           ROUND(TIMESTAMPDIFF(HOUR, o.oos_start, o.oos_end) / 24.0 * b.base_qty) AS lost_qty,  -- 按比例外推
           p.price - p.cost_price AS unit_gp                                        -- 单件毛利
    FROM stock_status o
    JOIN baseline b
      ON  b.store_id   = o.store_id
     AND  b.product_id = o.product_id
     AND  b.wd = WEEKDAY(DATE(o.oos_start))          -- 基准星期几 = 缺货起始日星期几
    JOIN products p ON p.product_id = o.product_id
)
SELECT store_id, product_id,
       SUM(oos_hours) AS total_oos_hours,            -- 累计缺货时长
       SUM(lost_qty)  AS lost_qty,                   -- 外推损失销量
       ROUND(SUM(lost_qty * unit_gp), 2) AS lost_gp  -- 毛利损失
FROM loss
GROUP BY store_id, product_id
ORDER BY lost_gp DESC;
```

结果解读：S001鲜牛奶在周五白天断货12小时，若近4个周五日均卖144瓶，外推损失72瓶、毛利约108元；月度汇总后按 lost_gp 排序即得"缺货损失Top清单"，通常头部20%事件贡献大部分损失。

解法二：递归CTE逐小时展开 + 同时段小时基准（精细法）。

```sql
WITH RECURSIVE oos_hour AS (                         -- 第一步：缺货时段展开成逐小时
    SELECT store_id, product_id,
           DATE_FORMAT(oos_start, '%Y-%m-%d %H:00:00') AS hr,   -- 对齐到整点
           oos_end
    FROM stock_status
    UNION ALL
    SELECT store_id, product_id,
           DATE_ADD(hr, INTERVAL 1 HOUR),            -- 递归推进一小时
           oos_end
    FROM oos_hour
    WHERE DATE_ADD(hr, INTERVAL 1 HOUR) < oos_end    -- 未到结束时间则继续展开
),
base_hour AS (                                       -- 第二步：历史同时段的平均小时销量
    SELECT store_id, product_id, stat_hour AS hh,
           AVG(qty) AS base_hour_qty
    FROM sales_hour
    WHERE stat_date BETWEEN '2026-09-01' AND '2026-09-14'   -- 取缺货前的两周历史
    GROUP BY store_id, product_id, stat_hour
),
lost AS (                                            -- 第三步：逐小时损失=该小时基准
    SELECT h.store_id, h.product_id,
           COALESCE(b.base_hour_qty, 0) AS lost_qty
    FROM oos_hour h
    LEFT JOIN base_hour b
      ON  b.store_id   = h.store_id
     AND  b.product_id = h.product_id
     AND  b.hh = HOUR(h.hr)                          -- 历史同一钟点做基准
)
SELECT store_id, product_id,
       COUNT(*) AS oos_hours,                        -- 展开后的小时数=缺货时长
       ROUND(SUM(lost_qty)) AS lost_qty              -- 逐小时基准求和=损失销量
FROM lost
GROUP BY store_id, product_id
ORDER BY lost_qty DESC;
```

结果解读：精细法能识别出"断在早高峰"与"断在深夜"的差异——同样断12小时，鲜牛奶断在8-20点损失约是断在0-12点的3倍以上；该口径适合用于向供应商索赔与安全库存参数校准。注意：递归展开需关注 cte_max_recursion_depth，长时段事件建议先 `SET SESSION cte_max_recursion_depth = 10000;` 或改用日历小时表JOIN。

> Hive/Spark SQL 差异：Hive 不支持递归CTE，逐小时展开可用 explode(split(space(小时数), ' ')) 配合 row_number 构造偏移、或 posexplode(sequence(0, 小时数-1)) 生成小时序列后 DATE_ADD(oos_start, pos 小时)；Spark SQL 可用 explode(sequence(oos_start, oos_end - 1 hour, interval 1 hour)) 一行完成，语法最简洁。

### 5. 性能分析与优化

解法一只需两次聚合加一次小表JOIN，扫描量为 sales_hour 全表一次，代价最低；解法二的递归展开行数等于总缺货小时数（月度复盘通常数千到数万行，可控），但 LEFT JOIN base_hour 按四列等值关联，需 (store_id, product_id, stat_hour) 索引或聚簇。优化建议：base_hour 的两周历史基准可物化为周期任务表并每周刷新；sales_hour 按 stat_date 分区，基准计算裁剪到所需分区；若做全天候实时缺货监控，把基准表预计算到"门店×商品×星期几×小时"粒度，损失估算退化为纯查表；对超长缺货事件（数天以上）建议直接切换日粒度口径，避免递归深度风险。Hive场景下优先用 sequence+explode 方案替代递归。

### 6. 面试延伸考点

1. **为什么不用前一天同时段做基准？** 要点：星期效应会让基准系统性偏离（工作日与周末销量差异可达50%），取最近4个同星期几平均能把周内节律平均掉；更精细可再剔除节假日。
2. **外推得到的是点估计，怎么给出区间？** 要点：对4个同星期几样本取分位数（P25-P75）作为损失区间，汇报"损失72瓶（52-89瓶）"比单一数字更可信；样本不足时降级为两周全日均并加宽区间。
3. **缺货期间替代品销量上升，要不要扣减？** 要点：需求转移让全口径损失被高估，可按品类级"缺货期替代品类销量增量"折算净损失；但如果替代品毛利更低，毛利口径损失依然成立，口径要讲清楚。
4. **库存为零但系统仍有过账销售，说明什么？** 要点：负库存问题（先卖后入库未冲销），说明 stock_status 的时段边界不可靠，需先做库存账实校正再算损失，否则时段两端会重复计损。

### 7. 业务拓展思考

缺货损失清单是供应链改进的"证据链"：按损失金额排序锁定问题门店与SKU，追溯是补货频次不足、供应商交期波动还是门店订货习惯问题；把估算损失与安全库存提升成本对比，能算出"多备一件货的成本 vs 少丢一单毛利"的最优安全库存。口径延展：损失可从毛利扩展到"顾客流失的长期价值"（缺货体验导致的会员流失，联动RET-36的LTV）；基准外推可升级为含天气与促销因子的回归预测，让"应有销量"更贴近真实需求曲线。

## RET-39 自有品牌渗透率量化路径（结构效应 vs 渗透效应）

### 1. 业务背景

商品部总经理把"自有品牌销售额占比提升到15%"写进年度OKR。季度复盘时，BI不能只报一个总占比数字，还要回答两个问题：占比的提升（或没提升）到底来自哪里——是各品类内部自有品牌卖得更多了（渗透效应），还是销售结构向自有品牌强的品类倾斜了（结构效应）？以及下一步资源往哪投——哪些品类"销售盘子大但自有品牌渗透率低"，是最值得重点开发的自有品牌洼地。输出物两张表：一是分品类的渗透率同比变化及两因子效应拆解表，二是按"权重×渗透缺口"排序的自有品牌开发优先级清单，直接决定下季度自有品牌开发部门的SKU立项顺序。

### 2. 表结构说明

小票明细表 sales（复用RET-32结构，此处取 product_id、sale_date、pay_amount）。

商品主数据表 products（含自有品牌标识）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| product_id | INT | 商品编号 |
| product_name | VARCHAR(50) | 商品名称 |
| category_name | VARCHAR(20) | 所属品类 |
| is_private_label | TINYINT | 是否自有品牌（1是0否） |

示例数据（products）：

| product_id | product_name | category_name | is_private_label |
|------------|--------------|---------------|------------------|
| 3001 | 优选卤味拼盘500g | 熟食卤味 | 1 |
| 4002 | 鲜牛奶950ml | 乳品饮品 | 0 |
| 5001 | 优选纸巾24包 | 家清纸品 | 1 |
| 2005 | 精酿啤酒6罐装 | 酒水饮料 | 0 |
| 6002 | 优选冷榨果汁1L | 乳品饮品 | 1 |

示例数据（sales，节选）：

| product_id | sale_date | pay_amount |
|------------|-----------|------------|
| 3001 | 2026-09-01 | 656.00 |
| 4002 | 2026-09-01 | 2250.00 |
| 5001 | 2026-09-02 | 1188.00 |
| 2005 | 2026-09-02 | 1780.00 |
| 6002 | 2026-09-03 | 398.00 |

### 3. 解题思路

先定口径：品类渗透率 = 该品类自有品牌销售额 / 该品类总销售额；品类权重 = 该品类销售额 / 全公司销售额；总渗透率 = Σ(权重×渗透率)。关键一步是精确的两因子分解恒等式：总渗透变化 ΔP = Σ[(w1−w0)×p0] + Σ[w1×(p1−p0)]，其中第一项是结构效应（品类权重变化、按去年渗透率计价），第二项是渗透效应（品类内渗透变化、按今年权重计价），两项相加精确等于总变化、无残差。**【加分点】** 能现场推导这个恒等式（把 Σw1p1 − Σw0p0 拆成两项）并说明"与RET-31对数分解的适用场景差异"（两因子加权和用恒等式更直观，乘积因子用对数分解），是让面试官认可的关键。实现路径：两期分别按品类条件聚合出自有品牌额与总额→算两期权重与渗透率→窗口 SUM OVER 求总权重→输出两效应。优先级矩阵则用"品类权重 ×（目标渗透25% − 当前渗透）"作为开发优先级得分排序。易错点：件数口径会虚高自有品牌渗透（自有品牌通常单价低），必须统一金额口径；新品类没有去年同期数据，JOIN会丢行，要用LEFT JOIN并单独标注。

### 4. 参考解法

解法一：两因子精确分解（结构效应+渗透效应，无残差）。

```sql
WITH cur AS (                                        -- 本期（2026Q3）分品类销售额与自有品牌额
    SELECT p.category_name,
           SUM(s.pay_amount) AS gmv,
           SUM(CASE WHEN p.is_private_label = 1
                    THEN s.pay_amount ELSE 0 END) AS pl_gmv    -- 条件聚合：自有品牌部分
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date BETWEEN '2026-07-01' AND '2026-09-30'
    GROUP BY p.category_name
),
prev AS (                                            -- 去年同期（2025Q3）
    SELECT p.category_name,
           SUM(s.pay_amount) AS gmv,
           SUM(CASE WHEN p.is_private_label = 1
                    THEN s.pay_amount ELSE 0 END) AS pl_gmv
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date BETWEEN '2025-07-01' AND '2025-09-30'
    GROUP BY p.category_name
),
calc AS (                                            -- 两期权重与渗透率
    SELECT COALESCE(c.category_name, p.category_name) AS category_name,   -- 防新品类/停售品类丢行
           COALESCE(c.pl_gmv,0) / NULLIF(c.gmv, 0) AS pen1,               -- 本期品类渗透率
           COALESCE(p.pl_gmv,0) / NULLIF(p.gmv, 0) AS pen0,               -- 去年品类渗透率
           COALESCE(c.gmv, 0) / NULLIF((SELECT SUM(gmv) FROM cur), 0)  AS w1,  -- 本期品类权重
           COALESCE(p.gmv, 0) / NULLIF((SELECT SUM(gmv) FROM prev), 0) AS w0   -- 去年品类权重
    FROM cur c
    LEFT JOIN prev p ON p.category_name = c.category_name
)
SELECT category_name,
       ROUND(pen1, 4) AS cur_pen,                     -- 本期渗透率
       ROUND(pen0, 4) AS prev_pen,                    -- 去年渗透率
       ROUND((w1 - w0) * COALESCE(pen0, 0), 5) AS mix_effect,        -- 结构效应=(w1-w0)×p0
       ROUND(w1 * (COALESCE(pen1, 0) - COALESCE(pen0, 0)), 5) AS pen_effect,  -- 渗透效应=w1×(p1-p0)
       ROUND((w1 - w0) * COALESCE(pen0, 0)
           + w1 * (COALESCE(pen1, 0) - COALESCE(pen0, 0)), 5) AS total_effect,  -- 两项之和=该品类对总变化贡献
       (SELECT ROUND(SUM(COALESCE(pl_gmv,0)) / NULLIF(SUM(gmv),0), 4)
        FROM cur) AS total_pen                        -- 总渗透率对照
FROM calc
ORDER BY total_effect DESC;
```

结果解读：若熟食卤味 pen_effect 贡献了总提升的六成，说明OKR进度主要靠品类内渗透（选品与陈列动作有效）；若 mix_effect 反而是负的（销售结构向渗透率低的生鲜倾斜抵消了渗透努力），需要在汇报中明确"结构拖累"，避免误判执行不力。

解法二：开发优先级矩阵（权重×渗透缺口排序，窗口给名次）。

```sql
WITH cur AS (
    SELECT p.category_name,
           SUM(s.pay_amount) AS gmv,
           SUM(CASE WHEN p.is_private_label = 1
                    THEN s.pay_amount ELSE 0 END) AS pl_gmv
    FROM sales s
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date BETWEEN '2026-07-01' AND '2026-09-30'
    GROUP BY p.category_name
),
matrix AS (                                          -- 渗透率×权重的优先级矩阵
    SELECT category_name,
           pl_gmv / NULLIF(gmv, 0) AS cur_pen,       -- 当前品类渗透率
           gmv / (SELECT SUM(gmv) FROM cur) AS weight,   -- 品类销售权重
           gmv
    FROM cur
)
SELECT category_name,
       ROUND(cur_pen, 4) AS cur_pen,
       ROUND(weight, 4) AS weight,
       ROUND(weight * (0.25 - cur_pen), 5) AS priority_score,   -- 得分=权重×(目标25%-当前渗透)
       ROW_NUMBER() OVER (ORDER BY weight * (0.25 - cur_pen) DESC) AS dev_rank,  -- 开发优先名次
       ROUND(gmv * (0.25 - cur_pen), 0) AS potential_gmv        -- 达到目标渗透对应的自有品牌销售额空间
FROM matrix
WHERE cur_pen < 0.25                                 -- 已达标品类不进入开发清单
ORDER BY dev_rank;
```

结果解读：priority_score 把"大而低"的品类排到最前，potential_gmv 给出该品类的渗透空间金额，商品部可据此把有限的开发资源（供应商谈判、OEM打样）集中到前3个品类。

### 5. 性能分析与优化

两解法都先把明细聚合到品类粒度（几十行），主体代价在明细扫描：两期各扫一遍 sales，按 (product_id, sale_date) 过滤聚合。优化建议：在 sales (sale_date, product_id) 建联合索引，或预聚合为"日×品类×自有品牌标记"的中间表（把 is_private_label 在打宽表时带上），渗透分析退化为对日表的轻量汇总；products 的 is_private_label 变更要走拉链表（历史标记可回溯），否则去年同期口径会失真；Hive/Spark下两期可 UNION ALL 成一段带期别标记的数据一次扫描聚合，减少一次全表扫描。

### 6. 面试延伸考点

1. **结构效应和渗透效应为什么这样计价（一个用p0一个用w1）？** 要点：拆分必须选一个"锚"避免交叉项——结构效应用去年渗透计价、渗透效应用今年权重计价，恰好各取一次且无重复无遗漏；若都用w1或都用p0会出现交叉项残留，用对数分解则自动消掉交叉项。
2. **渗透率用金额还是件数口径？** 要点：自有品牌多走高性价比路线、单价偏低，件数渗透天然高于金额渗透；对外汇报建议双口径并列，OKR一般锚定金额口径因为对应收入。
3. **自有品牌占比是不是越高越好？** 要点：不是——自有品牌毛利高但供应链重、试错成本高，且部分品类消费者强品牌偏好（如名酒），渗透天花板不同；应看品类级目标渗透而非全域追高。
4. **为什么新品类JOIN会丢行？怎么处理？** 要点：INNER JOIN会把只有单侧数据的品类排除，导致分解不完整；用LEFT JOIN+COALESCE并给"新增品类"打标签单独汇报。

### 7. 业务拓展思考

渗透率拆解体系可以横向扩展到"到家业务占比""会员销售占比"等结构性指标的归因，同一套两因子框架直接复用。运营联动上：mix_effect 为负说明要调品类结构（给高渗透品类更多货架与流量位）或调OKR口径；pen_effect 跟踪具体品类动作（自有品牌端架、试吃、与一线品牌并排陈列）的效果。延展方向：把优先级矩阵从静态季度表升级为"渗透爬坡曲线"（每个新自有品牌SKU上市后逐月渗透率，类比RET-37新店爬坡），用爬坡速度而非单期占比评估开发成功率。

## RET-40 促销频次与毛利率的边际关系（分箱对比）

### 1. 业务背景

定价委员会察觉一个危险信号：各门店促销越打越频繁，"不打折就没客流"，怀疑毛利正在被"促销上瘾"侵蚀。但要说服老板给促销频次设红线，必须拿出量化证据：把门店-月份按"促销强度"（当月促销天数占营业天数比例）分箱（0-10%、10-20%、20-30%、30%以上），对比各箱的平均毛利率与促销销售占比，看毛利率是否随促销强度递减、递减的斜率在哪一箱变陡（边际拐点），为"促销天数占比不超过X%"的红线提供依据。分析师还要警惕两个统计陷阱：一是品类结构混杂（促销多的店可能恰好在推高毛利品类，掩盖侵蚀），二是相关不等于因果（选促销多的店可能本身经营就弱）。

### 2. 表结构说明

小票明细表 sales（扩展促销标记）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sale_id | BIGINT | 流水号 |
| store_id | VARCHAR(10) | 门店编号 |
| receipt_no | VARCHAR(20) | 小票号 |
| sale_date | DATE | 销售日期 |
| promo_flag | TINYINT | 本单是否促销交易（1是0否） |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| cost_amount | DECIMAL(10,2) | 成本金额 |

示例数据：

| sale_id | store_id | receipt_no | sale_date | promo_flag | pay_amount | cost_amount |
|---------|----------|------------|-----------|------------|------------|-------------|
| 2001 | S001 | R20260901001 | 2026-09-01 | 1 | 98.50 | 71.00 |
| 2002 | S001 | R20260901002 | 2026-09-01 | 0 | 45.80 | 30.20 |
| 2003 | S002 | R20260901003 | 2026-09-01 | 0 | 128.00 | 88.00 |
| 2004 | S002 | R20260901004 | 2026-09-02 | 1 | 66.60 | 52.00 |
| 2005 | S001 | R20260902001 | 2026-09-02 | 1 | 152.30 | 120.00 |

### 3. 解题思路

口径三步。第一步定义门店-月粒度的两个变量：促销强度 = 当月有促销交易的天数 / 当月营业天数（营业天数用"当日有小票"近似，口径需与门店排班表核对）；毛利率 =（Σpay_amount − Σcost_amount）/ Σpay_amount，同时算促销销售占比（promo_flag=1的销售额/总销售额）作为依赖度参考。第二步分箱：CASE显式分箱或 INTERVAL+ELT 函数分箱，边界口径要声明（本例含下限）。第三步对比与边际：各箱的门店-月数、平均毛利率、平均促销销售占比；再用 LAG 在箱序列上做差分，得到"促销强度每上一档，毛利率掉多少"的边际斜率，斜率突然放大的那一箱就是红线候选位置。**【避坑指南】** 分箱只回答相关性，汇报时必须说明混杂：促销强度受门店自主决策影响，可用"同一门店跨月的变化"（固定效应思想）替代横截面对比，或至少控制品类结构；毛利率下滑也可能是大促引流品占比升高的机械结果，建议同时看剔除引流品后的毛利率。

### 4. 参考解法

解法一：CASE显式分箱 + 条件聚合（可读性最好，边界清晰）。

```sql
WITH sm AS (                                         -- 第一步：门店×月汇总
    SELECT store_id,
           DATE_FORMAT(sale_date, '%Y-%m') AS ym,
           COUNT(DISTINCT DATE(sale_date)) AS open_days,               -- 营业天数（有销售即营业）
           SUM(pay_amount) AS gmv,                                     -- 月销售额
           SUM(pay_amount - cost_amount) AS gp,                        -- 月毛利额
           SUM(CASE WHEN promo_flag = 1 THEN pay_amount ELSE 0 END) AS promo_gmv,   -- 促销销售额
           COUNT(DISTINCT CASE WHEN promo_flag = 1
                               THEN DATE(sale_date) END) AS promo_days -- 有促销交易的天数
    FROM sales
    WHERE sale_date BETWEEN '2026-07-01' AND '2026-09-30'
    GROUP BY store_id, DATE_FORMAT(sale_date, '%Y-%m')
),
binned AS (                                          -- 第二步：按促销强度分箱
    SELECT *,
           CASE WHEN promo_days / open_days < 0.1 THEN '1_0-10%'
                WHEN promo_days / open_days < 0.2 THEN '2_10-20%'
                WHEN promo_days / open_days < 0.3 THEN '3_20-30%'
                ELSE '4_30%以上' END AS promo_bin,   -- 前缀数字保证字符串排序正确
           gp / NULLIF(gmv, 0) AS gp_rate,           -- 门店月毛利率
           promo_days / open_days AS promo_ratio,    -- 促销强度（复核用）
           promo_gmv / NULLIF(gmv, 0) AS promo_gmv_share   -- 促销销售占比
    FROM sm
)
SELECT promo_bin,
       COUNT(*) AS store_months,                     -- 各箱门店-月样本数
       ROUND(AVG(gp_rate), 4) AS avg_gp_rate,        -- 平均毛利率
       ROUND(AVG(promo_gmv_share), 4) AS avg_promo_share,   -- 平均促销销售占比
       MIN(gp_rate) AS min_gp_rate,                  -- 箱内最差情形
       MAX(gp_rate) AS max_gp_rate
FROM binned
GROUP BY promo_bin
ORDER BY promo_bin;
```

结果解读：若四箱平均毛利率依次为0.212、0.198、0.181、0.163，呈现单调递减且第四箱跌幅加深，初步支持"促销强度与毛利率负相关"，红线候选在20%档。

解法二：INTERVAL函数分箱 + LAG边际斜率（自动算递减幅度，定位拐点）。

```sql
WITH sm AS (
    SELECT store_id,
           DATE_FORMAT(sale_date, '%Y-%m') AS ym,
           COUNT(DISTINCT DATE(sale_date)) AS open_days,
           SUM(pay_amount) AS gmv,
           SUM(pay_amount - cost_amount) AS gp,
           COUNT(DISTINCT CASE WHEN promo_flag = 1
                               THEN DATE(sale_date) END) AS promo_days
    FROM sales
    WHERE sale_date BETWEEN '2026-07-01' AND '2026-09-30'
    GROUP BY store_id, DATE_FORMAT(sale_date, '%Y-%m')
),
agg AS (                                             -- 先分箱再聚合出各箱指标
    SELECT ELT(INTERVAL(promo_days / NULLIF(open_days, 0) * 100, 0, 10, 20, 30),
               '1_0-10%', '2_10-20%', '3_20-30%', '4_30%以上') AS promo_bin,   -- INTERVAL返回0..4，ELT映射箱名
           COUNT(*) AS store_months,
           AVG(gp / NULLIF(gmv, 0)) AS avg_gp_rate
    FROM sm
    GROUP BY 1
)
SELECT promo_bin, store_months,
       ROUND(avg_gp_rate, 4) AS avg_gp_rate,
       ROUND(avg_gp_rate - LAG(avg_gp_rate) OVER (ORDER BY promo_bin), 4) AS marginal_drop,  -- 相邻箱毛利率差=边际
       ROUND(AVG(avg_gp_rate) OVER (ORDER BY promo_bin
               ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING), 4) AS prev_avg    -- 前序箱均值（复核）
FROM agg
ORDER BY promo_bin;
```

结果解读：marginal_drop 列即促销强度每上一档的毛利率边际变化，若前三档差值稳定在-0.015左右而第四档达到-0.032，说明超过30%后毛利侵蚀加速，红线应设在30%；LAG在聚合结果上做差分，比手算相邻行差值更不易错。

### 5. 性能分析与优化

两解法主体都是一次明细扫描聚合成门店×月（行数千级），分箱与窗口均在聚合后的小结果集上进行，代价很低；INTERVAL+ELT 写法比多层CASE少一次全行条件判断但可读性略差。优化建议：促销强度与毛利率是月度监控指标，应固化为 store_month_promo 汇总表（ETL日更），分析层只做分箱与差分；sales 在 (sale_date, store_id) 建索引加速月度范围聚合；若要控制品类结构混杂，先聚合到"门店×月×品类"粒度再上卷，可用品类权重标准化的毛利率（固定品类权重加权平均）替代简单平均；样本少于10个门店-月的箱要标注"样本不足"，防止管理层拿噪声当结论。

### 6. 面试延伸考点

1. **分箱对比能证明因果关系吗？怎么设计更接近因果？** 要点：不能，横截面分箱受门店自选择混杂；更接近因果的做法是门店内固定效应（对比同一门店促销强度升降前后的毛利率变化）、双重差分（对触碰红线的门店与未触碰门店对比，见RET-42思路）或随机化的促销强度试验。
2. **INTERVAL函数的边界语义是什么？** 要点：INTERVAL(N, v1, v2, ...) 返回"最后一个不大于N的参数的位置"，边界值归入下界箱（含下限），与CASE的<边界写法要在口径文档里对齐，否则两解法结果在临界值上不一致。
3. **毛利率下滑还可能有哪些机械原因？** 要点：促销本身把高毛利商品打折（结构性毛利稀释）、引流品占比升高、供应商返利未冲减成本，需拆"促销期毛利率"与"非促销期毛利率"对照并追踪返利。
4. **如果各箱毛利率没有单调关系呢？** 要点：可能存在混杂掩盖（强店促销多）、或关系是非单调的U型（适度促销拉客流提升周转反哺毛利），应加入品类结构控制、看分位数而非均值，并延长观察期。

### 7. 业务拓展思考

边际曲线一旦确认，可直接输出三条管理动作：促销天数占比红线（拐点箱的下界）、超线门店的促销审批加签、以及对"高促销强度+低毛利率"门店的专项经营诊断。口径延展：促销强度可区分"全店档期"与"单品促销天数"两套；毛利率可换成"促销增量毛利ROI"（大促期毛利减去自然销量的反事实毛利，思路同RET-38外推），直接回答"这场促销到底赚没赚"；长期可建促销强度与会员复购的联合面板，验证促销频次对顾客价格预期（无券不买）的长期伤害。
## RET-41 区域品类结构季度迁移矩阵

### 1. 业务背景

季度经营复盘会上，大区总经理要回答一个结构问题：华东区的销售盘子正在从哪个品类流向哪个品类？生鲜占比还在升、百货是不是在被到家渠道蚕食、酒水饮料占比的季节波动有多大？分析师需要输出一张"品类×季度"的销售占比迁移矩阵：每个品类在本季与上季的占比、迁移的百分点数，并对变化超过±2个百分点的品类打上"显著上升/显著下滑"标记，辅助判断是主动调改（品类策略生效）还是被动滑坡（竞品冲击、客群变化），最终支撑下季度的品类预算与货架资源再分配。**【面试高频】** 行列转换（宽表）与相邻期对比（LAG）是数仓面试的双高频考点，本题把两者放在同一业务问题里对比考察。

### 2. 表结构说明

小票明细表 sales（复用RET-32结构，此处取 store_id、product_id、sale_date、pay_amount）。

门店主表 stores（补充大区字段）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| store_id | VARCHAR(10) | 门店编号 |
| store_name | VARCHAR(50) | 门店名称 |
| region | VARCHAR(20) | 所属大区 |
| open_date | DATE | 开业日期 |

商品主数据表 products（复用RET-32/39结构，此处取 product_id、category_name）。

示例数据（stores）：

| store_id | store_name | region | open_date |
|----------|------------|--------|-----------|
| S001 | 幸福里店 | 华东 | 2024-05-18 |
| S002 | 学院路店 | 华东 | 2024-09-01 |
| S003 | 中山路店 | 华南 | 2024-06-20 |
| S004 | 金融街店 | 华东 | 2025-04-10 |
| S005 | 环球港店 | 华南 | 2024-11-11 |

示例数据（sales，节选）：

| store_id | product_id | sale_date | pay_amount |
|----------|------------|-----------|------------|
| S001 | 3001 | 2026-08-15 | 65.60 |
| S001 | 5001 | 2026-08-15 | 49.50 |
| S004 | 2005 | 2026-08-16 | 89.00 |
| S002 | 4002 | 2026-08-16 | 15.00 |
| S003 | 3001 | 2026-08-17 | 32.80 |

### 3. 解题思路

口径先行：品类季度占比 = 品类季度GMV / 区域季度总GMV；迁移幅度 = 本季占比 − 上季占比（单位为百分点）；标记阈值±2个百分点。实现有两条路线：路线一是条件聚合宽表——把两个季度的GMV用CASE展开成两列，占比用 SUM OVER 窗口在行间求分母，一行输出一个品类的两期占比与迁移值，SQL最短、结果即矩阵；路线二是长表+LAG——先把"季度×品类"聚合成长表（QUARTER函数生成季度标签），再用窗口 LAG(PARTITION BY 品类 ORDER BY 季度) 取上一季占比作差，优点是天然支持任意多季度的连续迁移链（Q1→Q2→Q3一路对比），加新季度不用改SQL。**【避坑指南】** 占比变化的解读不能直接看品类自身增速——分母不同，某品类增速10%但大盘增速15%，占比其实是在下滑；此外新开门店（如S004）会造成结构性迁移，严谨版要用同店口径（开业满两个季度的门店）重算一遍做对照，防止把"新店带来的结构"误读为"老客结构迁移"。

### 4. 参考解法

解法一：条件聚合宽表（两季同框，结果即矩阵）。

```sql
WITH qs AS (                                         -- 第一步：分品类聚合两季GMV（条件聚合一扫完成）
    SELECT p.category_name,
           SUM(CASE WHEN s.sale_date BETWEEN '2026-07-01' AND '2026-09-30'
                    THEN s.pay_amount ELSE 0 END) AS q3_gmv,        -- 本季（2026Q3）
           SUM(CASE WHEN s.sale_date BETWEEN '2026-04-01' AND '2026-06-30'
                    THEN s.pay_amount ELSE 0 END) AS q2_gmv         -- 上季（2026Q2）
    FROM sales s
    JOIN stores st ON st.store_id = s.store_id
    JOIN products p ON p.product_id = s.product_id
    WHERE st.region = '华东'                          -- 只看华东大区
      AND (s.sale_date BETWEEN '2026-04-01' AND '2026-09-30')   -- 扫描范围覆盖两季
    GROUP BY p.category_name
)
SELECT category_name,
       q3_gmv, q2_gmv,
       ROUND(q3_gmv / SUM(q3_gmv) OVER (), 4) AS q3_share,           -- 本季占比（窗口求区域总GMV做分母）
       ROUND(q2_gmv / SUM(q2_gmv) OVER (), 4) AS q2_share,           -- 上季占比
       ROUND(q3_gmv / SUM(q3_gmv) OVER () - q2_gmv / SUM(q2_gmv) OVER (), 4) AS shift_pp,  -- 迁移百分点
       CASE WHEN q3_gmv / SUM(q3_gmv) OVER () - q2_gmv / SUM(q2_gmv) OVER () >=  0.02 THEN '显著上升'
            WHEN q3_gmv / SUM(q3_gmv) OVER () - q2_gmv / SUM(q2_gmv) OVER () <= -0.02 THEN '显著下滑'
            ELSE '平稳' END AS move_flag               -- ±2个百分点阈值标记
FROM qs
ORDER BY shift_pp DESC;                              -- 迁移幅度降序：上升品类在前
```

结果解读：若熟食卤味 shift_pp=+0.013、家清纸品=+0.021（显著上升）、百货=−0.025（显著下滑），说明华东结构正从百货向高频刚需品类迁移，预算应向后者倾斜并复盘百货客流下滑原因。

解法二：长表 + LAG 相邻季度对比（支持任意长度的迁移链）。

```sql
WITH quarter_gmv AS (                                -- 第一步：季度×品类长表
    SELECT CONCAT(YEAR(s.sale_date), 'Q', QUARTER(s.sale_date)) AS q_label,   -- 季度标签如 2026Q3
           p.category_name,
           SUM(s.pay_amount) AS gmv
    FROM sales s
    JOIN stores st ON st.store_id = s.store_id AND st.region = '华东'
    JOIN products p ON p.product_id = s.product_id
    WHERE s.sale_date >= '2026-01-01'                -- 从年初起，可看连续三个季度
    GROUP BY CONCAT(YEAR(s.sale_date), 'Q', QUARTER(s.sale_date)), p.category_name
),
share AS (                                           -- 第二步：每季度内的品类占比
    SELECT q_label, category_name,
           gmv / SUM(gmv) OVER (PARTITION BY q_label) AS share   -- 窗口求当季总GMV
    FROM quarter_gmv
)
SELECT category_name, q_label,
       ROUND(share, 4) AS share,
       ROUND(share - LAG(share) OVER (PARTITION BY category_name ORDER BY q_label), 4) AS shift_pp,  -- 与上一季比
       ROUND(AVG(share) OVER (PARTITION BY category_name
                              ORDER BY q_label
                              ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 4) AS share_ma3   -- 近3季占比均值，平滑季节波动
FROM share
ORDER BY category_name, q_label;
```

结果解读：每个品类输出一条跨季度的时间序列与逐季迁移值，share_ma3 平滑了单季噪声，若某品类连续三季 shift_pp 为负且低于3季均值，可判定为趋势性下滑而非季节波动；加新季度数据时SQL无需改动，这是长表方案的核心优势。

> Hive/Spark SQL 差异：两方案语法均兼容；数据量大时长表方案可按 q_label 分区，LAG 在品类分区排序内完成；条件聚合宽表在Hive上两季数据量翻倍扫描，建议改用 WHERE 季别过滤 + UNION ALL 后统一聚合，或预建 dws 层"季度×区域×品类"汇总表。

### 5. 性能分析与优化

解法一扫描两个季度的明细并做一次GROUP BY，窗口分母 SUM OVER 在品类行数（几十行）上完成，代价极小；解法二扫描区间更长（可到全年），LAG 需按品类分区排序，行数同样在品类×季度量级，主要成本都在明细聚合一步。优化建议：把明细聚合下沉到数仓 dws 层的"日×区域×品类"汇总表，分析层从汇总表再聚合，扫描量从亿级明细降到千级汇总；stores/products 维表JOIN在明细层完成一次即可；分区裁剪上 sales 按 stat_date 分区，两方案都只扫相关分区；若报表高频刷新，宽表方案可物化为"迁移矩阵视图"，长表方案则保留为底层，供下钻与可视化工具共用。

### 6. 面试延伸考点

1. **宽表（条件聚合）和长表（LAG）怎么选？** 要点：固定两期对比、出报表矩阵用宽表，直观且SQL短；期数可变、要连续迁移链或下钻时间序列用长表，扩展零改SQL；生产上常见做法是长表为底、按需透视。
2. **为什么不能只看品类自身增速判断结构变化？** 要点：占比是相对指标，品类增速必须减去大盘增速才有结构含义；等价关系是"占比变化≈(品类增速−大盘增速)/(1+大盘增速)×上期占比"，口径要向业务讲清。
3. **新开门店对结构矩阵的干扰怎么处理？** 要点：用同店口径（开业早于对比期起点且未闭店）重算对照版，两版差异大的品类说明变化主要来自渠道扩张而非客群偏好，汇报时两版并列。
4. **占比各品类相加不等于100%是怎么回事？** 要点：ROUND逐行四舍五入的累计误差，或品类归属变更（商品改品类）导致两期口径不一致；前者展示层处理，后者必须用拉链表冻结历史归属。

### 7. 业务拓展思考

迁移矩阵是品类战略的仪表盘：显著上升品类加大货架与库存深度、显著下滑品类启动原因排查（竞对开业、电商替代、客群搬迁）。口径延展：矩阵可从"销售额占比"扩展到"毛利占比""会员消费占比"，识别销售额平移但毛利恶化的结构性风险；时间粒度可细到月并叠加同比（今年Q3 vs 去年Q3），区分季节迁移与趋势迁移；再往下钻一层是"门店×品类"的迁移热力图，定位结构变化是全区域一致还是个别门店拉动，直接指派责任门店。

## RET-42 社群运营与到店行为交叉分析（双重差分）

### 1. 业务背景

用户增长团队在20家门店运营"福利社群"（企业微信群，每日发限时券与到店活动），老板在复盘会上质疑："进群的人本来就会来买，别把自然到店算成社群功劳。"要回应这个质疑，不能简单对比入群会员与未入群会员的到店频次——愿意进群的本来就是高活跃会员，存在严重的自选择偏差。分析师需要用双重差分（DID）框架：对比入群会员"入群前后30天"的到店频次变化，减去同期未入群会员的前后变化，差值才是社群的增量贡献；再辅以"按入群前消费额分桶"的匹配对照，检查高活跃与低活跃人群内部结论是否一致。输出物是DID结果表与分桶对照表，直接决定社群运营预算是扩大还是收缩。**【避坑指南】** 面试中若直接说"对比入群组与未入群组的到店率"，等于当场暴露不懂得选择偏差，这是本题最核心的考察点。

### 2. 表结构说明

会员主表 members（含社群入群时间）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| member_id | VARCHAR(20) | 会员编号 |
| join_date | DATE | 入会日期 |
| register_store_id | VARCHAR(10) | 注册门店 |
| community_join_date | DATE | 入群日期（NULL为未入群） |

小票明细表 sales（复用RET-32结构，此处取 member_id、sale_date、pay_amount）。

示例数据（members）：

| member_id | join_date | register_store_id | community_join_date |
|-----------|-----------|-------------------|---------------------|
| M1001 | 2024-03-15 | S001 | 2026-06-08 |
| M1002 | 2024-07-02 | S001 | NULL |
| M1003 | 2025-01-20 | S002 | 2026-06-20 |
| M1004 | 2023-11-08 | S002 | NULL |
| M1005 | 2025-05-30 | S001 | 2026-06-25 |

示例数据（sales，节选）：

| member_id | sale_date | pay_amount |
|-----------|-----------|------------|
| M1001 | 2026-05-20 | 88.20 |
| M1001 | 2026-06-30 | 156.50 |
| M1002 | 2026-05-25 | 45.80 |
| M1003 | 2026-07-01 | 230.00 |
| M1004 | 2026-06-10 | 12.90 |

### 3. 解题思路

口径设计四步。第一步分组与锚点：入群会员以 community_join_date 为锚点，未入群会员没有真实锚点，统一指定期中锚点（如2026-06-15）构造"伪锚点"，保证两组的观察窗口在日历上可比（避开季节性错位）。第二步前后窗计算：锚点前30天与后30天各算到店天数（按天去重）与消费额。第三步DID：入群组变化量 Δ1 = after−before，对照组变化量 Δ0 = after−before，社群增量 = Δ1 − Δ0。第四步稳健性：把两组会员按"锚点前90天消费额"分成10个分位桶，在每个桶内再做组间对比——如果每个桶内入群组的提升都为正，结论对人群结构稳健；如果提升集中在高消费桶，说明社群主要激活了本就活跃的人，增量要打折。易错点：观察窗口要与入群动作错开（入群当天发的欢迎券立即可用，前后窗各30天足够）；对照组要剔除"窗口期内后来才入群"的人，避免处理污染；M确实大于0才能谈归因，还要确认前后窗内没有全店级大促干扰。

### 4. 参考解法

解法一：双重差分DID（前后窗×分组，条件聚合一次成型）。

```sql
WITH mem AS (                                        -- 第一步：分组与锚点
    SELECT member_id,
           CASE WHEN community_join_date IS NOT NULL
                THEN '入群组' ELSE '对照组' END AS grp,
           COALESCE(community_join_date, DATE '2026-06-15') AS anchor_date  -- 对照组统一用期中伪锚点
    FROM members
    WHERE join_date < '2026-01-01'                   -- 老会员，保证前窗行为可观察
      AND (community_join_date IS NULL
           OR community_join_date BETWEEN '2026-06-01' AND '2026-06-30')  -- 只取6月入群批次；未入群者为对照
),
act AS (                                             -- 第二步：锚点前后各30天的行为
    SELECT m.member_id, m.grp,
           CASE WHEN s.sale_date < m.anchor_date THEN 'before' ELSE 'after' END AS period_tag,
           COUNT(DISTINCT s.sale_date) AS visit_days,                -- 到店天数（按天去重）
           COALESCE(SUM(s.pay_amount), 0) AS amt
    FROM mem m
    LEFT JOIN sales s                                -- LEFT JOIN保住窗口内零到店会员
      ON s.member_id = m.member_id
     AND s.sale_date BETWEEN m.anchor_date - INTERVAL 30 DAY
                          AND m.anchor_date + INTERVAL 30 DAY
    GROUP BY m.member_id, m.grp,
             CASE WHEN s.sale_date < m.anchor_date THEN 'before' ELSE 'after' END
),
piv AS (                                             -- 第三步：前后并排（行转列）
    SELECT grp, member_id,
           SUM(CASE WHEN period_tag = 'before' THEN visit_days ELSE 0 END) AS before_days,
           SUM(CASE WHEN period_tag = 'after'  THEN visit_days ELSE 0 END) AS after_days
    FROM act
    GROUP BY grp, member_id
),
agg AS (                                             -- 第四步：各组前后变化
    SELECT grp,
           COUNT(*) AS mem_cnt,
           AVG(before_days) AS avg_before,
           AVG(after_days)  AS avg_after,
           AVG(after_days - before_days) AS delta    -- 组内前后差（一阶差分）
    FROM piv
    GROUP BY grp
)
SELECT a.grp, a.mem_cnt,
       ROUND(a.avg_before, 2) AS avg_before,
       ROUND(a.avg_after, 2) AS avg_after,
       ROUND(a.delta, 3) AS delta,
       ROUND(a.delta - (SELECT delta FROM agg WHERE grp = '对照组'), 3) AS did_value  -- 双重差分=增量效应
FROM agg a
ORDER BY a.grp;
```

结果解读：若入群组 delta=+0.42、对照组 delta=+0.11（同期自然回暖），DID=+0.31 即社群带来人均每月约0.3次的增量到店；再乘以客单价与社群人力成本即可算社群ROI。

解法二：分桶匹配对照（按入群前消费额分位桶，检验结论稳健性）。

```sql
WITH mem AS (
    SELECT member_id,
           CASE WHEN community_join_date IS NOT NULL
                THEN '入群组' ELSE '对照组' END AS grp,
           COALESCE(community_join_date, DATE '2026-06-15') AS anchor_date
    FROM members
    WHERE join_date < '2026-01-01'
      AND (community_join_date IS NULL
           OR community_join_date BETWEEN '2026-06-01' AND '2026-06-30')
),
pre_amt AS (                                         -- 匹配变量：锚点前90天消费额
    SELECT m.member_id, m.grp,
           COALESCE(SUM(CASE WHEN s.sale_date < m.anchor_date
                              AND s.sale_date >= m.anchor_date - INTERVAL 90 DAY
                             THEN s.pay_amount END), 0) AS pre_amt   -- 前窗无消费记0
    FROM mem m
    LEFT JOIN sales s ON s.member_id = m.member_id
    GROUP BY m.member_id, m.grp
),
bucketed AS (                                        -- 混合两组后按消费额分10桶
    SELECT p.*,
           CASE WHEN p.pre_amt = 0 THEN 0                                   -- 零消费单独一桶
                ELSE NTILE(10) OVER (PARTITION BY (p.pre_amt > 0)
                                     ORDER BY p.pre_amt) END AS amt_bucket  -- 仅在正消费组内做分位
    FROM pre_amt p
),
after AS (                                           -- 锚点后30天到店天数
    SELECT b.member_id, b.grp, b.amt_bucket,
           COUNT(DISTINCT s.sale_date) AS after_days
    FROM bucketed b
    LEFT JOIN sales s
      ON s.member_id = b.member_id
     AND s.sale_date BETWEEN b.anchor_date + INTERVAL 1 DAY
                          AND b.anchor_date + INTERVAL 30 DAY
    GROUP BY b.member_id, b.grp, b.amt_bucket
),
cmp AS (                                             -- 桶内组间对比
    SELECT amt_bucket, grp,
           COUNT(*) AS n,
           AVG(after_days) AS avg_after_days
    FROM after
    GROUP BY amt_bucket, grp
)
SELECT amt_bucket,
       MAX(CASE WHEN grp = '入群组' THEN n END) AS treat_n,
       MAX(CASE WHEN grp = '对照组' THEN n END) AS ctrl_n,
       ROUND(MAX(CASE WHEN grp = '入群组' THEN avg_after_days END)
           - MAX(CASE WHEN grp = '对照组' THEN avg_after_days END), 3) AS bucket_gap  -- 桶内增量差
FROM cmp
GROUP BY amt_bucket
ORDER BY amt_bucket;
```

结果解读：若0-3号低消费桶的 bucket_gap 接近0.25、且各桶方向一致，说明社群对低活跃会员的唤醒作用真实存在（回应了"只是活跃的人本来就来"的质疑）；若提升只出现在高消费桶，应把社群定位从"拉新促活"改为"高客维护"。

### 5. 性能分析与优化

两解法主体都是会员表（万级）LEFT JOIN 明细的窗口范围聚合，明细扫描按会员键分布，JOIN后聚合行数为会员×2（前后两期），代价可控；解法二的NTILE需对全量会员按消费额排序一次。优化建议：sales 在 (member_id, sale_date) 建联合索引，让范围JOIN走索引；先把明细按会员预聚合到"会员×日"粒度（每日到店标记），前后窗统计变成对标记求和，避免大表直接JOIN；对照组要剔除窗口后入群者的过滤条件要前置在 members 筛选阶段；Hive/Spark下会员千万级时，先按 member_id 分桶让JOIN与窗口本地化，DID与分桶统计全部可在聚合后的小表完成。注意本设计是"单期DID"，若社群分批入群（多期），可升级为交错DID或事件研究（按入群后第N月对齐，思路同RET-37）。

### 6. 面试延伸考点

1. **为什么不能用入群组与未入群组的截面均值差？** 要点：入群是自选择行为，活跃会员更可能扫码进群，截面差混入了人群固有差异；DID用"各自与自身过去比"消掉了组间固定差异，剩下的才是时间上的增量差。
2. **对照组的伪锚点怎么选才公平？** 要点：取处理组锚点日期的分布中心（或按注册门店/消费额分层后分别配锚点），保证两组的日历窗口重叠，否则季节与促销效应会污染差分。
3. **DID的平行趋势假设怎么验证？** 要点：把前后窗拉长，画两组在锚点前多个周期的到店频次趋势线，处理前两条线大致平行才满足假设；若入群前入群组就在加速，说明存在预期效应或趋势分歧，DID高估。
4. **入群当天发券会不会让"前窗"被行为反噬？** 要点：会员知道马上进群有券可能抑制前窗消费（囤着），属于预期效应，可用更早的安慰剂锚点检验，或把欢迎券改为入群次日生效。

### 7. 业务拓展思考

DID框架可以直接复用到零售各类运营动作的效果评估：改版会员权益、上新到家服务、调整营业时间、重摆货架，只需要替换"处理事件"与结果变量。口径延展：结果变量从到店频次扩展到客单、品类渗透（社群券核销带动了哪些品类）、社群活跃度（发言/领券）与到店的漏斗关系；样本足够时可做剂量效应（领券次数分箱看响应曲线），识别社群触达的边际递减点，指导"每天发几条"的运营节奏。长期应把社群效果沉淀为AB实验平台的标准流程，避免每次复盘都重新洗数据。

## RET-43 门店间客群重叠与分流分析（会员跨店消费）

### 1. 业务背景

城市经理发现：新开的B店（S002，2026年6月开业）销售额不错，但同商圈老店A店（S001）销售额同比掉了8%。B店的GMV到底有多少是从A店"搬"过来的自然分流，有多少是商圈外新客的真实增量？这关系到两件事：一是B店的考核口径（分流部分不应计入新店开拓成绩），二是A店的应对策略（是竞对抢客还是自家左右手互搏）。分析师要用会员跨店消费数据量化：近90天同时消费过A、B两店的会员数（重叠客群）、其中"开业前主消费A店、开业后主消费转向B店"的分流会员数与分流金额占比，输出给选址委员会与新店考核组。**【面试高频】** 自连接构造"实体对"（门店对/商品对/门店-商品对）的套路与RET-32购物篮同源，面试常借此考察举一反三能力。

### 2. 表结构说明

小票明细表 sales（此处取 member_id、store_id、sale_date、pay_amount，仅会员消费行）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| sale_id | BIGINT | 流水号 |
| member_id | VARCHAR(20) | 会员编号 |
| store_id | VARCHAR(10) | 门店编号 |
| sale_date | DATE | 销售日期 |
| pay_amount | DECIMAL(10,2) | 实付金额 |

门店主表 stores（复用RET-37结构，此处取 store_id、store_name、open_date）。

示例数据（sales）：

| sale_id | member_id | store_id | sale_date | pay_amount |
|---------|-----------|----------|-----------|------------|
| 3001 | M1001 | S001 | 2026-07-05 | 88.20 |
| 3002 | M1001 | S002 | 2026-07-20 | 156.50 |
| 3003 | M1002 | S001 | 2026-07-08 | 45.80 |
| 3004 | M1003 | S002 | 2026-07-25 | 230.00 |
| 3005 | M1001 | S002 | 2026-08-15 | 99.00 |

示例数据（stores）：

| store_id | store_name | open_date |
|----------|------------|-----------|
| S001 | 幸福里店（老店A） | 2024-05-18 |
| S002 | 康桥店（新店B） | 2026-06-01 |
| S003 | 中山路店 | 2024-06-20 |
| S004 | 金融街店 | 2025-04-10 |
| S005 | 环球港店 | 2024-11-11 |

### 3. 解题思路

口径分四层。第一层重叠客群：近90天消费门店数≥2的会员为跨店会员，其中同时含A、B两店的是A-B重叠客群。第二层主店判定：按近90天累计消费金额最大者为主消费门店（ROW_NUMBER取第一），金额并列时用频次破平。第三层分流判定：分流会员 = 开业前6个月主消费A店 + 开业后主消费转为B店的会员——**【避坑指南】** 只看"开业后B店消费占比高"就判分流会误伤两类人：会员搬家（居住地变化）与顺路消费（B店在通勤路上），必须把主店迁移与B店开业时点对齐才能称其为分流。第四层量化：分流率 = 分流会员数 / A店开业前活跃会员数，分流金额 = 分流会员在B店的消费额，占B店GMV比重即"B店成绩单里的分流水分"。实现路径：近期消费按会员×门店聚合→窗口判主店与门店数→条件聚合判A/B重叠→再取开业前窗口重复判"前主店"，两段对齐出分流清单。

### 4. 参考解法

解法一：主店迁移判定法（聚合+窗口+条件聚合，输出分流会员清单）。

```sql
WITH recent AS (                                     -- 第一步：近90天会员×门店消费额
    SELECT member_id, store_id, SUM(pay_amount) AS amt
    FROM sales
    WHERE sale_date >= '2026-07-01'
      AND member_id IS NOT NULL
    GROUP BY member_id, store_id
),
flag AS (                                            -- 第二步：窗口判主店 + 消费门店数
    SELECT r.member_id, r.store_id, r.amt,
           ROW_NUMBER() OVER (PARTITION BY r.member_id ORDER BY r.amt DESC) AS rk,   -- 金额最大为主店
           COUNT(*) OVER (PARTITION BY r.member_id) AS store_cnt                     -- 该会员消费门店数
    FROM recent r
),
ab AS (                                              -- 第三步：圈出A-B重叠会员并记录其现主店
    SELECT member_id,
           MAX(CASE WHEN store_id = 'S001' THEN 1 ELSE 0 END) AS visit_a,
           MAX(CASE WHEN store_id = 'S002' THEN 1 ELSE 0 END) AS visit_b,
           MAX(CASE WHEN rk = 1 THEN store_id END) AS main_now       -- 当前主店
    FROM flag
    GROUP BY member_id
    HAVING MAX(CASE WHEN store_id = 'S001' THEN 1 ELSE 0 END) = 1
       AND MAX(CASE WHEN store_id = 'S002' THEN 1 ELSE 0 END) = 1    -- 同时消费过A、B
),
pre_main AS (                                        -- 第四步：B店开业前6个月的主店
    SELECT member_id,
           MAX(CASE WHEN rk = 1 THEN store_id END) AS main_before
    FROM (SELECT s.member_id, s.store_id,
                 ROW_NUMBER() OVER (PARTITION BY s.member_id
                                    ORDER BY SUM(s.pay_amount) DESC) AS rk   -- 开业前主店排名
          FROM sales s
          WHERE s.sale_date BETWEEN '2025-12-01' AND '2026-05-31'     -- B店2026-06-01开业前
          GROUP BY s.member_id, s.store_id) t
    GROUP BY member_id
)
SELECT COUNT(*) AS overlap_members,                                  -- A-B重叠会员数
       SUM(CASE WHEN pm.main_before = 'S001' AND ab.main_now = 'S002'
                THEN 1 ELSE 0 END) AS diverted_members,              -- A主店→B主店：分流会员
       SUM(CASE WHEN pm.main_before = 'S001' AND ab.main_now = 'S001'
                THEN 1 ELSE 0 END) AS retained_members,              -- 主店未变：B店只是顺路
       ROUND(SUM(CASE WHEN pm.main_before = 'S001' AND ab.main_now = 'S002'
                      THEN 1 ELSE 0 END) * 1.0 / COUNT(*), 4) AS divert_ratio   -- 分流会员占重叠客群比
FROM ab
LEFT JOIN pre_main pm ON pm.member_id = ab.member_id;
```

结果解读：若重叠会员320人中分流会员145人、retained 175人，说明B店四成以上重叠客群已把"主店"从A迁走，A店的下滑主要是自家分流而非竞对，应对策略是差异化A、B店的品类与营业时间而非加大对抗性促销。

解法二：门店对自连接矩阵（量化任意两店重叠度，输出分流网络）。

```sql
WITH recent AS (                                     -- 近90天会员×门店消费
    SELECT member_id, store_id, SUM(pay_amount) AS amt
    FROM sales
    WHERE sale_date >= '2026-07-01' AND member_id IS NOT NULL
    GROUP BY member_id, store_id
),
store_total AS (                                     -- 各店活跃会员数（作分母）
    SELECT store_id, COUNT(DISTINCT member_id) AS member_cnt,
           SUM(amt) AS store_amt
    FROM recent
    GROUP BY store_id
),
pair AS (                                            -- 会员的门店两两组合（自连接，a<b去对称）
    SELECT a.store_id AS store_a, b.store_id AS store_b,
           COUNT(*) AS overlap_members,              -- 两店都消费的会员数
           SUM(LEAST(a.amt, b.amt)) AS shared_amt    -- 两店消费较低值≈该会员的"共享钱包"
    FROM recent a
    JOIN recent b
      ON  a.member_id = b.member_id
     AND a.store_id  < b.store_id                    -- 去对称，与购物篮分析同一套路
    GROUP BY a.store_id, b.store_id
)
SELECT p.store_a, p.store_b, p.overlap_members,
       ROUND(p.shared_amt, 2) AS shared_amt,
       ROUND(p.overlap_members / NULLIF(t1.member_cnt, 0), 4) AS overlap_rate_a,  -- 重叠会员占A店会员比
       ROUND(p.overlap_members / NULLIF(t2.member_cnt, 0), 4) AS overlap_rate_b,  -- 重叠会员占B店会员比
       CASE WHEN p.store_b = 'S002' AND t2.store_amt / NULLIF((SELECT store_amt
                FROM store_total WHERE store_id = 'S002'), 0) >= 0
            THEN '新店B相关' ELSE '老店间重叠' END AS pair_type      -- 标记涉及新店的门店对
FROM pair p
JOIN store_total t1 ON t1.store_id = p.store_a
JOIN store_total t2 ON t2.store_id = p.store_b
ORDER BY p.overlap_members DESC;                     -- 重叠最多的门店对在前
```

结果解读：矩阵中 (S001,S002) 行的 overlap_rate_a=0.35 说明A店35%的会员在B店也有消费，而其他老店对之间普遍低于0.08，验证B店对A店的分流强度远超正常水平；该矩阵还可用于全城门店网络规划（重叠度过高的两店考虑合并或差异化定位）。

### 5. 性能分析与优化

解法一的成本在两次窗口排序（近90天与开业前窗口各一次），明细扫描量=会员消费行数；解法二的自连接是 join 膨胀点：每会员消费 k 家门店产生 k(k−1)/2 行，人均门店数低（多在2-4家），膨胀可控，但跨店频繁的会员会放大行数。优化建议：recent 聚合先收窄到"会员×门店"再自连接（已做到，切忌直接在明细行上自连接）；在 sales (member_id, sale_date) 建索引加速范围过滤；对全城分析可预建"会员×月×门店"汇总表，滚动90天从月表叠加；Hive/Spark下按 member_id 分桶再做自连接可本地化shuffle；门店对矩阵若只关心Top门店，可先按门店GMV取Top20再连对，行数骤减。

### 6. 面试延伸考点

1. **主店判定用金额还是频次？** 要点：金额口径贴近价值贡献但被大单扭曲，频次口径贴近习惯但被小额高频扭曲；稳妥做法金额为主、频次破平，或双口径都算、只把两种口径下主店一致的会员计入分流（更严格）。
2. **跨店消费一定是分流吗？还有什么解释？** 要点：搬家、通勤路线变化、陪家人购物、B店有A店没有的品类（如B店有生鲜）；用品类结构对比可区分——若会员在B店主要买A店没有的品类，属于品类互补而非分流。
3. **新店GMV怎么拆"增量"与"分流"？** 要点：分流部分=分流会员在B店的消费额，增量=B店GMV−分流额；更精细可对分流会员的B店消费打折计（他们不来B店也不会把这部分钱全花在A店）。
4. **非会员顾客的分流怎么估？** 要点：会员数据是样本，可按会员渗透率把分流率外推到全体客流，或用客流系统（WiFi探针）的跨店到访数据交叉验证，口径声明"会员近似"。

### 7. 业务拓展思考

客群重叠矩阵是城市门店网络规划的底图：重叠率高的门店对提示选址过密或定位同质，应做品类/时段差异化；分流分析结果直接写进新店开业复盘，考核上把"净增量GMV"替代"总GMV"，避免门店为冲成绩互相抢客。口径延展：主店可扩展为"全渠道主店"（含到家订单归属）；时序上可做"主店迁移流"（Sankey思路：每个季度各会员主店流转矩阵），持续监控网络内客群流动；再叠加会员LTV（RET-36）可回答"被分走的会员价值有多高"，让网络决策同时看人数与价值。

## RET-44 节假日效应剥离后的真实同店增长

### 1. 业务背景

经营分析会上财务与运营对增长数字吵了起来：运营报"五一档销售额同比增长18%"，财务指出今年五一假期5天而去年只有3天，多出来的两天本身就是增量，日历结构不同导致同比虚高，"真实增长"可能只有个位数。要终结争论，必须剥离节假日效应：把日历分成节假日、调休补班日、普通日三种类型，分别计算两年"同类型日的日均销售额"，再按去年的日历结构（各类型天数）把今年的日均合成回去，得到"日历结构对齐后的同比增速"——它回答的是"如果今年假期长度和去年一样，增长是多少"。同店口径还需剔除开业不满一年与已闭店的门店。输出物是真实同店增速及其与"裸同比"的差值解释，供管理层定调。**【避坑指南】** 只比总量（被天数差污染）和只比日均（被类型结构污染）都不对，正确答案是"类型日均×去年类型天数"的加权合成。

### 2. 表结构说明

日历维表 calendar（运营部维护，标注法定节假日）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stat_date | DATE | 日期 |
| day_type | VARCHAR(10) | 日历类型（节假日/调休补班/普通日） |

门店日销售宽表 store_daily_gmv（复用RET-37结构，此处取 store_id、stat_date、gmv）。

门店主表 stores（复用RET-37结构，含 open_date、close_date）。

示例数据（calendar）：

| stat_date | day_type |
|-----------|----------|
| 2026-05-01 | 节假日 |
| 2026-05-02 | 节假日 |
| 2026-04-26 | 调休补班 |
| 2026-05-07 | 普通日 |
| 2025-05-01 | 节假日 |

示例数据（store_daily_gmv）：

| store_id | stat_date | gmv |
|----------|-----------|-----|
| S001 | 2026-05-01 | 186400.00 |
| S001 | 2026-05-02 | 172300.00 |
| S001 | 2026-04-26 | 121500.00 |
| S001 | 2025-05-01 | 148900.00 |
| S002 | 2026-05-01 | 210500.00 |

### 3. 解题思路

口径设计三步。第一步圈定同店集合：开业日期早于对比期起点一年以上、且未闭店的门店，两年口径一致才叫同店。第二步类型日均：把对比区间（如4月20日-5月10日，覆盖假期与补班日）的日销售额按"年份×日历类型"分组求日均——节假日日均、补班日均、普通日日均各算各的；**【加分点】** 调休补班日必须单独一类，它名义上是工作日但作息被打乱（周末补班反而像工作日，工作日补休像周末），混进普通日会污染普通日日均。第三步合成真实增速：真实增速 = Σ_type(今年该类型日均 × 去年该类型天数) / Σ_type(去年该类型日均 × 去年该类型天数) − 1——分子是"今年日均、去年日历"的合成GMV，分母是去年真实GMV，日历结构被固定在去年，剩下的差异全部来自经营本身。同时输出"裸同比"（今年GMV/去年GMV−1）作对照，两者的差值即"日历红利"。易错点：两年类型集合可能不完全对应（去年没有某类型），JOIN缺失类型要按0处理并在汇报中说明；区间要对称覆盖两年同期。

### 4. 参考解法

解法一：类型日均×去年天数加权合成法（主口径）。

```sql
WITH same_store AS (                                 -- 第一步：同店口径过滤
    SELECT store_id
    FROM stores
    WHERE open_date <= '2025-04-20'                  -- 开业早于对比区间起点（保证两年都有数据）
      AND close_date IS NULL                         -- 未闭店
),
day_gmv AS (                                         -- 第二步：同店日销售额贴上日历类型
    SELECT YEAR(g.stat_date) AS yr,
           c.day_type,
           g.stat_date,
           SUM(g.gmv) AS gmv
    FROM store_daily_gmv g
    JOIN same_store ss ON ss.store_id = g.store_id
    JOIN calendar c ON c.stat_date = g.stat_date
    WHERE (g.stat_date BETWEEN '2025-04-20' AND '2025-05-10')     -- 去年同期区间
       OR (g.stat_date BETWEEN '2026-04-20' AND '2026-05-10')     -- 今年区间
    GROUP BY YEAR(g.stat_date), c.day_type, g.stat_date
),
type_stat AS (                                       -- 第三步：各年×类型的日均与天数
    SELECT yr, day_type,
           AVG(gmv) AS avg_daily,                    -- 该类型日均销售额
           COUNT(*) AS days                          -- 该类型天数
    FROM day_gmv
    GROUP BY yr, day_type
),
join2 AS (                                           -- 第四步：两年度同类型对齐
    SELECT a.day_type,
           a.avg_daily AS avg25, a.days AS days25,   -- 去年
           b.avg_daily AS avg26                      -- 今年
    FROM type_stat a
    LEFT JOIN type_stat b
      ON b.day_type = a.day_type AND b.yr = 2026
    WHERE a.yr = 2025                                -- 以去年类型集合为基准（LEFT JOIN防今年缺类型）
)
SELECT ROUND(SUM(COALESCE(avg26, 0) * days25)
             / NULLIF(SUM(avg25 * days25), 0) - 1, 4) AS true_growth,   -- 真实同店增速（日历结构=去年）
       ROUND(SUM(avg25 * days25), 0) AS base_gmv_2025,                   -- 去年GMV（分母）
       ROUND(SUM(COALESCE(avg26, 0) * days25), 0) AS adj_gmv_2026,       -- 结构对齐后的合成GMV
       SUM(days25) AS calendar_days_2025                                 -- 去年日历天数合计
FROM join2;
```

结果解读：若裸同比+18%而 true_growth=+7.2%，则11个点的差距来自"假期多2天+少1个补班日"的日历红利；汇报中应把 true_growth 作为经营定调数字，裸同比只用于解释。

解法二：普通日剔除法（简单口径作交叉验证）。

```sql
WITH same_store AS (
    SELECT store_id
    FROM stores
    WHERE open_date <= '2025-04-20' AND close_date IS NULL
),
day_gmv AS (
    SELECT YEAR(g.stat_date) AS yr,
           c.day_type,
           g.stat_date,
           SUM(g.gmv) AS gmv
    FROM store_daily_gmv g
    JOIN same_store ss ON ss.store_id = g.store_id
    JOIN calendar c ON c.stat_date = g.stat_date
    WHERE (g.stat_date BETWEEN '2025-04-20' AND '2025-05-10')
       OR (g.stat_date BETWEEN '2026-04-20' AND '2026-05-10')
    GROUP BY YEAR(g.stat_date), c.day_type, g.stat_date
),
type_stat AS (
    SELECT yr, day_type, AVG(gmv) AS avg_daily, COUNT(*) AS days
    FROM day_gmv
    GROUP BY yr, day_type
)
SELECT '普通日口径' AS method,
       ROUND(MAX(CASE WHEN yr = 2026 THEN avg_daily END)
             / NULLIF(MAX(CASE WHEN yr = 2025 THEN avg_daily END), 0) - 1, 4) AS growth_normal,  -- 只用普通日日均比
       MAX(CASE WHEN yr = 2026 THEN days END) AS days_2026,
       MAX(CASE WHEN yr = 2025 THEN days END) AS days_2025
FROM type_stat
WHERE day_type = '普通日';
```

结果解读：普通日口径实现最简单（直接比两年普通日日均），但其隐含假设"普通日增长能代表全部"——若今年促销集中砸在假期、平日促销减少，普通日增速会低估整体；与解法一的 true_growth 并排出现，两者差距本身就是一个诊断信号（差距大=增长依赖假期运营）。

### 5. 性能分析与优化

两解法主体都是对约三周×两年的日粒度数据（同店数×42天，万级行）做两级聚合，代价极小；主要JOIN是 calendar 维表等值关联。优化建议：calendar 提前物化"日期×类型×年份"宽表，并把 day_type 的历史值冻结（法定假期安排公布后补录）；store_daily_gmv 按 stat_date 分区使区间扫描只触两个分区；若同店增长是月度例行指标，建议把口径固化为视图（同店清单×类型日均），每次只刷新增量分区；Hive/Spark下数据量大时，可把"年×类型"聚合下推到 dws 日汇总层，分析层只处理几十行；LEFT JOIN 缺失类型的COALESCE处理在两引擎行为一致。

### 6. 面试延伸考点

1. **为什么"总量同比"和"日均同比"都不对？** 要点：总量被日历天数污染，日均被类型结构污染（今年假期日均高但假期天数结构不同），只有"今年类型日均×去年类型天数"的合成才把日历固定住；本质是指数里的"拉氏数量指数"思想。
2. **调休补班日为什么必须单独分类？** 要点：补班日作息错位使消费行为既不像普通工作日也不像周末（有的家庭补班孩子没人带反而到店少），混入普通日会扭曲普通日基准；至少分三类，精细化可加"假期前一日/后一日"（备货与返程效应）。
3. **同店口径怎么定义才无争议？** 要点：开业满完整对比期（常见满12个月）且未闭店、未大改造（面积变化超阈值剔除）；口径写进制度并全公司统一，否则各部门数字打架。
4. **如果管理层只想看"五一档"增长怎么办？** 要点：给出两版——日历对齐版（真实经营）与裸同比版（预算达成视角），并明确标注差异来源；切忌只报对己方有利的口径，口径一致性是分析公信力的底线。

### 7. 业务拓展思考

日历剥离能力可推广到所有受日历结构影响的指标：月度销售考核（每月工作日数不同，可算"日历调整后的月销"）、年同比（闰年多一天、春节错月）、周末效应分析。运营联动上，真实增速低于裸同比的年份提示"增长靠假期"，应加强平日的日常经营（会员日、工作日特惠）降低日历依赖；高于裸同比则说明平日基本盘在变强。延展方向：把日历类型再叠加天气（RET-45）与促销日历，构建"可解释的销售基准模型"，让每一期销售波动都能拆成日历、天气、促销、经营四个来源，真正实现归因式经营分析。

## RET-45 天气/温度与品类销售弹性分析

### 1. 业务背景

供应链计划部想建立"看天备货"机制：气温超过30℃时冷饮凉品动销翻倍，寒潮来袭时火锅食材与暖贴走俏，若能在天气预报出现极端温度前2-3天完成门店调货，既能抓住销售高峰又能减少报废。第一步是量化：各品类的日销量对日均温度有多敏感？分析师需要输出"品类×温度区间"的平均日销量曲线（温度分箱对比），并计算相邻温度箱之间的销量变化率（每升温10℃的弹性），识别高敏感品类与敏感拐点温度，形成"温度-备货系数表"给采购。难点在于剥离混杂：周末与工作日的到店结构不同、促销日销量被人为抬高，不控制这些因素，弹性估计会严重失真。**【加分点】** 能主动提出"按星期几分层/剔除促销日再算弹性"并解释为什么，比算出弹性数字本身更能体现分析素养。

### 2. 表结构说明

### 3. 解题思路

口径三步。第一步构造分析单元：品类×日期的销量（把 sales_hour 按日聚合到商品再映射品类，门店经 stores 挂接城市，再按城市JOIN当天天气），同时打上两个控制变量——星期几（工作日/周末标记）与是否促销日（LEFT JOIN促销日历，命中则剔除）。第二步温度分箱：按温度分四箱（<5℃、5-15℃、15-25℃、≥25℃，箱距10℃便于弹性解读），每箱内按"品类×工作日/周末"分别求平均日销量，保证箱间对比在同一星期结构下进行。第三步弹性差分：相邻箱的平均日销量取变化率，除以箱距10℃得到"每升温10℃的销量弹性"；样本少于15天的箱打上"样本不足"标记，防止小样本噪声混进备货系数。**【避坑指南】** 不控制星期效应的典型事故：夏天的高温日恰好多逢周末，直接分箱会得出"高温让所有品类都大涨"的假结论（其实是周末效应）；相关不等于因果——温度升高也伴随整体客流变化，严谨结论应表述为"同店同星期条件下"的品类弹性，并可交叉验证雨天（weather_type）的独立效应。

### 4. 参考解法

解法一：温度分箱 + 星期分层条件聚合（弹性曲线版）。

```sql
WITH day_cat AS (                                     -- 第一步：品类×城市×日期销量
    SELECT st.city,
           p.category_name,
           sh.stat_date,
           SUM(sh.qty) AS qty
    FROM sales_hour sh
    JOIN stores st ON st.store_id = sh.store_id       -- 门店挂接城市
    JOIN products p ON p.product_id = sh.product_id   -- 商品挂接品类
    WHERE sh.stat_date BETWEEN '2026-06-01' AND '2026-08-31'   -- 夏季样本期
    GROUP BY st.city, p.category_name, sh.stat_date
),
tw AS (                                               -- 第二步：贴上温度、星期与促销标记
    SELECT d.city, d.category_name, d.stat_date, d.qty,
           w.avg_temp,
           CASE WHEN WEEKDAY(d.stat_date) >= 5 THEN '周末' ELSE '工作日' END AS day_kind,   -- 星期效应控制
           w.weather_type                                    -- 保留天气类型，可作交叉验证维度
    FROM day_cat d
    JOIN weather w ON w.city = d.city AND w.stat_date = d.stat_date
    WHERE NOT EXISTS (                                -- 剔除促销日，防止促销抬量污染弹性
        SELECT 1 FROM promo_days pd                   -- promo_days为促销日历表(城市,促销日)，结构从略
        WHERE pd.stat_date = d.stat_date AND pd.city = d.city
    )
)
SELECT category_name, day_kind,
       CASE WHEN avg_temp < 5  THEN '1_<5℃'
            WHEN avg_temp < 15 THEN '2_5-15℃'
            WHEN avg_temp < 25 THEN '3_15-25℃'
            ELSE '4_≥25℃' END AS temp_bin,           -- 温度四箱（箱距10℃）
       COUNT(*) AS sample_days,                       -- 样本天数（小样本诊断用）
       ROUND(AVG(qty), 0) AS avg_qty                  -- 分箱平均日销量
FROM tw
GROUP BY category_name, day_kind,
         CASE WHEN avg_temp < 5  THEN '1_<5℃'
              WHEN avg_temp < 15 THEN '2_5-15℃'
              WHEN avg_temp < 25 THEN '3_15-25℃'
              ELSE '4_≥25℃' END
ORDER BY category_name, day_kind, temp_bin;
```

结果解读：冷饮冰品"工作日"列从15-25℃箱的日均180件升到≥25℃箱的310件，曲线随温度陡升；速食暖食曲线则相反；两条曲线的交点温度即"冷暖品切换线"，可直接写进季节陈列切换SOP。分箱表达式统一放在外层SELECT与GROUP BY中，输出按品类×星期×温度箱排列，可直接画成分箱曲线图。

解法二：分箱聚合 + LAG差分算弹性（直接输出备货系数表）。

```sql
WITH day_cat AS (
    SELECT st.city, p.category_name, sh.stat_date, SUM(sh.qty) AS qty
    FROM sales_hour sh
    JOIN stores st ON st.store_id = sh.store_id
    JOIN products p ON p.product_id = sh.product_id
    WHERE sh.stat_date BETWEEN '2026-06-01' AND '2026-08-31'
    GROUP BY st.city, p.category_name, sh.stat_date
),
tw AS (
    SELECT d.category_name, d.qty, w.avg_temp,
           CASE WHEN WEEKDAY(d.stat_date) >= 5 THEN '周末' ELSE '工作日' END AS day_kind,
           CASE WHEN w.avg_temp < 5  THEN 1            -- 箱号用数字，便于排序与温度插值
                WHEN w.avg_temp < 15 THEN 2
                WHEN w.avg_temp < 25 THEN 3
                ELSE 4 END AS bin_no,
           CASE WHEN w.avg_temp < 5  THEN 0            -- 箱中值（近似代表温度，供弹性归一）
                WHEN w.avg_temp < 15 THEN 10
                WHEN w.avg_temp < 25 THEN 20
                ELSE 30 END AS bin_mid
    FROM day_cat d
    JOIN weather w ON w.city = d.city AND w.stat_date = d.stat_date
),
agg AS (                                              -- 品类×星期×温度箱聚合
    SELECT category_name, day_kind, bin_no, bin_mid,
           COUNT(*) AS sample_days,
           AVG(qty) AS avg_qty
    FROM tw
    GROUP BY category_name, day_kind, bin_no, bin_mid
)
SELECT category_name, day_kind, bin_no,
       CONCAT(CASE bin_no WHEN 1 THEN '<5℃' WHEN 2 THEN '5-15℃'
                          WHEN 3 THEN '15-25℃' ELSE '≥25℃' END) AS temp_bin,
       sample_days,
       ROUND(avg_qty, 0) AS avg_qty,
       ROUND(avg_qty / NULLIF(LAG(avg_qty) OVER (PARTITION BY category_name, day_kind ORDER BY bin_no), 0) - 1,
             4) AS qty_chg_rate,                      -- 相邻箱销量变化率
       ROUND((avg_qty / NULLIF(LAG(avg_qty) OVER (PARTITION BY category_name, day_kind ORDER BY bin_no), 0) - 1) / 10,
             4) AS elasticity_per_1c,                 -- 每升温1℃的销量弹性（箱距10℃归一）
       CASE WHEN sample_days < 15 THEN '样本不足' ELSE '可用' END AS quality_flag   -- 小样本标记
FROM agg
ORDER BY category_name, day_kind, bin_no;
```

结果解读：冷饮冰品工作日从箱3到箱4的 elasticity_per_1c≈0.013（每升温1℃日销约+1.3%），备货系数表据此写成"预报高温日按基准×(1+0.013×温度距平)上调冷饮调拨量"；sample_days 不足的箱在输出中降级为参考值，避免采购拿噪声当系数。

### 5. 性能分析与优化

两解法主体都是明细按"城市×品类×日"聚合（行数=品类数×天数，万级），JOIN天气维表（日期数行）后分箱聚合，代价很低。优化建议：sales_hour 按月分区，扫描裁剪到样本期；day_cat 可物化为"日×品类×城市"汇总表供天气、节假日、促销多因子分析共用；weather 表补充湿度、降水量后同一框架直接扩展多因子分箱；Hive/Spark下若做全国多城市，按 city 分区并让弹性计算在各城市分区内完成；更严格的弹性应升级为对数线性回归 ln(qty)=α+β×temp+星期哑变量+促销哑变量（SQL可手工实现最小二乘或导出到Spark ML），分箱法是其非参数近似，面试中能讲出这层关系即是加分。

### 6. 面试延伸考点

1. **不控制星期效应会发生什么？** 要点：高温日与周末、夏季档期高度相关，混合样本会把周末效应、促销效应错记到温度头上，弹性被系统性高估；分层（工作日/周末分别算）或回归加哑变量是标准解法。
2. **为什么用分箱而不是直接算相关系数？** 要点：温度与销量的关系常是非线性且有拐点（超过30℃冷饮增速放缓甚至下降），相关系数只给单调性一个数；分箱曲线能暴露拐点与阈值，直接服务于备货规则。
3. **温度对销量的影响有滞后吗？SQL怎么验证？** 要点：有——持续高温第三天比第一天影响大（累积效应），可用 LAG 取前1-3天温度作滞后特征，分别分箱对比当期与滞后特征的解释力。
4. **弹性系数怎么落地到调拨？** 要点：把弹性换算成"温度距平×品类基准日销"的加量系数，叠加在途与安全库存（RET-34）生成提前3天的调拨建议单，并在高温日后复盘预测偏差持续校准。

### 7. 业务拓展思考

温度弹性表是"看天经营"的基石：短期驱动极端天气前的应急调拨与陈列切换（冷饮端头提前上岗），中期支撑季节性选品与仓网布局（南方仓冷饮库容扩容）。口径延展：可加入降水、湿度、空气质量多因子并区分"晴天高温"与"闷雨高温"的不同弹性；把弹性细化到SKU级（单价带、品牌）支持精细化订货；与会员数据交叉还能识别"天气敏感客群"（高温日转向到家的会员），推动到家运力按天气预报弹性排班，让天气从分析报表变成调度参数。
