## FIN-01 各渠道注册客户数与占比

### 1. 业务背景

零售银行市场部渠道运营岗的同学，在季度渠道复盘会上需要向管理层汇报：各注册渠道（手机银行APP、官网、线下网点、第三方合作平台）分别带来了多少客户、各占总客量的比例。这张报表直接决定下个季度的获客预算怎么分：占比高且转化质量好的渠道追加投放，长期低产的渠道收缩预算。作为面向客户信息的报表，输出前必须遵循合规要求：手机号等敏感字段脱敏展示，分析只取最小必要字段，明细数据严禁外发给无权限人员。

### 2. 表结构说明

客户主表 customers（本例使用其中部分字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户唯一编号（主键） |
| cust_name | VARCHAR(50) | 客户姓名（报表输出时脱敏为姓+*） |
| phone_no | CHAR(11) | 手机号（展示时脱敏为`138****1234`） |
| channel | VARCHAR(20) | 注册渠道：APP/官网/网点/第三方合作 |
| city | VARCHAR(20) | 开户城市 |
| risk_level | CHAR(2) | 客户风险等级 R1~R5 |
| open_date | DATE | 开户日期 |
| created_at | DATETIME | 系统注册时间 |

示例数据（5行）：

| customer_id | cust_name | phone_no | channel | city | risk_level | open_date |
|---|---|---|---|---|---|---|
| 100001 | 张* | `138****1234` | APP | 杭州 | R2 | 2024-01-05 |
| 100002 | 李* | `159****8877` | 网点 | 上海 | R1 | 2024-02-11 |
| 100003 | 王* | `186****3321` | 第三方合作 | 北京 | R3 | 2024-02-18 |
| 100004 | 赵* | `131****9090` | 官网 | 深圳 | R2 | 2024-03-02 |
| 100005 | 钱* | `177****5656` | APP | 成都 | R4 | 2024-03-15 |

### 3. 解题思路

先明确口径："注册客户数"按客户主表一客户一条记录的特点，直接对渠道分组计数即可，无需去重；占比 = 渠道客户数 ÷ 全量客户数，分母必须是同一时点的全表客户数，避免分子分母口径不一致。实现路径有两种：一是先用 GROUP BY 汇总各渠道人数，占比用标量子查询再取一次总数；二是利用窗口函数 SUM(COUNT(*)) OVER()，在分组聚合结果之上对"各渠道计数"再求总和，一步得到分母，只扫一遍表。易错点有三个：一是整数除法——MySQL 中 COUNT(*) 除以 COUNT(*) 结果按整数截断，必须乘 100.0 转为小数；二是占比保留两位小数要用 ROUND；三是渠道字段可能存在历史脏数据（如"APP "尾部带空格），必要时先 TRIM 再分组，否则同一渠道被拆成两行。

**【面试高频】** 为什么乘 100.0 而不是 100？因为整数与整数相除在 MySQL 中结果仍是整数，小数部分被直接截断，占比会全部变成 0 或 1。

### 4. 参考解法

解法一：GROUP BY 汇总 + 标量子查询求占比

```sql
SELECT
    c.channel,                                    -- 渠道名
    COUNT(*) AS cust_cnt,                         -- 该渠道注册客户数
    ROUND(
        COUNT(*) * 100.0 / (SELECT COUNT(*) FROM customers), 2
    ) AS pct                                      -- 渠道客户数除以全量客户数；乘100.0避免整数除法丢失小数
FROM customers c
GROUP BY c.channel                                -- 按注册渠道分组
ORDER BY pct DESC;                                -- 占比从高到低，便于汇报阅读
```

结果解读：若 APP 渠道占比接近一半，说明线上自助注册已是主入口；第三方合作占比虽小，但要结合户均AUM看质量，不能只看数量。

解法二：窗口函数一次聚合完成

```sql
SELECT
    channel,                                      -- 渠道名
    COUNT(*) AS cust_cnt,                         -- 各渠道客户数
    ROUND(
        COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2
    ) AS pct                                      -- SUM(COUNT(*)) OVER ()：对各分组的计数再求和，等价于总客户数
FROM customers
GROUP BY channel                                  -- 按渠道分组
ORDER BY pct DESC;                                -- 占比降序
```

结果解读：两种写法结果一致；解法二只扫描一遍表，把"总数"内联到聚合里，省掉一次子查询，是 MySQL 8.0 之后更推荐的写法。

### 5. 性能分析与优化

解法一需要访问 customers 两次（一次分组计数、一次子查询取总数）；解法二只扫描一次，数据量越大差距越明显。优化建议：一是 channel 区分度低，单独建索引帮助不大，全表分组本身不慢；二是该报表按天/季固定产出，建议用定时任务把结果落到汇总表，查询时只读结果表；三是渠道取值有限，可加渠道维度表 channel_dim 用 JOIN 补齐渠道中文名与上级渠道，避免在 SQL 里硬编码枚举；四是若报表还要按月份拆分，把日期列纳入 GROUP BY 后建 (channel, open_date) 复合索引才有意义。

### 6. 面试延伸考点

**问：占比加总不等于100%怎么办？** 回答要点：四舍五入所致，可用最大余额法调整余数，或汇报时注明"因四舍五入合计略有误差"。

**问：如果只统计最近一个季度注册的客户怎么改？** 回答要点：WHERE 加 created_at >= 季度起始日的范围条件，不要对字段套 DATE_FORMAT 之类的函数，以免索引失效。

**问：渠道质量除了人数还应看什么？** 回答要点：结合开户转化率、30天动户率、户均AUM、风险等级分布等后链路指标，量质并重评估渠道。

### 7. 业务拓展思考

渠道占比是投放决策的基础盘，但单一数量指标容易误导：若某第三方渠道客户多但风险等级集中在 R4/R5、动户率低，反而摊薄产能。可将本结果与"渠道×30天动户率""渠道×户均AUM"做交叉表，形成量质二维矩阵；同时把口径固化为"注册口径"与"开户口径"两条线，剔除注册未开户的水分。合规上，明细层仅限授权岗位访问，对外只输出汇总数，敏感字段一律脱敏。

## FIN-02 每日交易笔数与交易金额统计

### 1. 业务背景

银行运营监控中心的值班分析师每天早上要出"前一交易日交易日报"：全行每天发生了多少笔交易、总金额多少，按天排列成趋势供晨会监控异常波动。当某一天交易金额环比激增（例如超过近28天均值的3倍标准差），需要第一时间与风控团队联动排查是否存在欺诈、大额套现或系统重复扣款。因此该统计必须只统计"成功"状态的交易——失败、冲正交易混入会污染监控基线，这是金融数据统计最基本的风控口径意识。

### 2. 表结构说明

交易流水表 transactions：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号（主键） |
| customer_id | BIGINT | 客户编号 |
| account_id | BIGINT | 账户编号 |
| txn_type | VARCHAR(10) | 交易类型：存款/取款/转账/购买理财 |
| amount | DECIMAL(18,2) | 交易金额（元） |
| txn_status | VARCHAR(10) | 交易状态：成功/失败/冲正 |
| txn_time | DATETIME | 交易时间 |

示例数据（5行）：

| txn_id | customer_id | txn_type | amount | txn_status | txn_time |
|---|---|---|---|---|---|
| 202403010001 | 100001 | 存款 | 5000.00 | 成功 | 2024-03-01 09:12:33 |
| 202403010002 | 100002 | 转账 | 120000.00 | 成功 | 2024-03-01 10:05:11 |
| 202403010003 | 100003 | 取款 | 800.00 | 失败 | 2024-03-01 11:40:07 |
| 202403010004 | 100004 | 购买理财 | 30000.00 | 成功 | 2024-03-01 14:22:50 |
| 202403010005 | 100005 | 存款 | 200.00 | 成功 | 2024-03-02 08:55:40 |

金额字段说明：金额必须用 DECIMAL(18,2) 而不是 FLOAT/DOUBLE。FLOAT 是二进制浮点，无法精确表示 0.1 这类十进制小数，累加后会出现 0.30000000000000004 之类的误差，对金额对账和风控限额判断不可接受；DECIMAL 按十进制存储，精确无误。

### 3. 解题思路

口径先行：第一，"每天"以交易日 txn_time 的自然日为准，跨零点交易归入实际发生日；第二，只统计 txn_status='成功' 的交易，失败/冲正必须剔除，否则笔数与金额双虚高；第三，金额汇总用 SUM(amount)，笔数用 COUNT(*)，两者分组维度保持一致。实现路径：把 DATETIME 转换到日期粒度再分组，MySQL 可用 DATE() 或 DATE_FORMAT(txn_time, '%Y-%m-%d')，两者分组效果等价。**【避坑指南】** WHERE 条件里对 txn_time 套函数（如 DATE(txn_time)='2024-03-01'）会使索引失效，应写成左闭右开的范围条件 txn_time >= 起始日 AND txn_time < 截止日；另外注意统计区间含头不含尾，DECIMAL 汇总无需再担心精度，但若源表是 FLOAT 则 SUM 结果不可信。

### 4. 参考解法

解法一：DATE() 提取日期分组（区间过滤，走索引友好）

```sql
SELECT
    DATE(t.txn_time) AS txn_date,                 -- 把DATETIME截断到自然日，作为分组键
    COUNT(*) AS txn_cnt,                          -- 成功交易笔数
    SUM(t.amount) AS total_amt                    -- 成功交易金额合计，DECIMAL保证精确累加
FROM transactions t
WHERE t.txn_status = '成功'                        -- 只统计成功交易，剔除失败/冲正
  AND t.txn_time >= '2024-03-01'                   -- 统计区间起点（含）
  AND t.txn_time < '2024-03-08'                    -- 统计区间终点（不含），左闭右开避免边界重复或遗漏
GROUP BY DATE(t.txn_time)                          -- 按自然日分组
ORDER BY txn_date;                                 -- 日期升序形成时间趋势
```

结果解读：若 3 月 5 日金额突增数倍而笔数变化不大，大概率是少数大额转账所致，应立即下钻交易明细并与反欺诈团队核对。

解法二：DATE_FORMAT 格式化为字符串分组（便于直接出报表标签）

```sql
SELECT
    DATE_FORMAT(t.txn_time, '%Y-%m-%d') AS txn_date,  -- 格式化成'2024-03-01'样式的日期标签
    COUNT(*) AS txn_cnt,                              -- 成功交易笔数
    ROUND(SUM(t.amount), 2) AS total_amt              -- 金额合计，ROUND兜底统一两位小数输出
FROM transactions t
WHERE t.txn_status = '成功'                          -- 风控口径：仅成功交易
  AND t.txn_time >= '2024-03-01'                     -- 区间起点
  AND t.txn_time < '2024-03-08'                      -- 区间终点（不含）
GROUP BY DATE_FORMAT(t.txn_time, '%Y-%m-%d')         -- 按格式化后的日期字符串分组
ORDER BY txn_date;                                   -- 日期升序
```

结果解读：DATE_FORMAT 返回字符串，分组等价于 DATE()，但输出标签可直接贴进日报模板；日报场景务必带时间区间条件，否则会全表分组。

### 5. 性能分析与优化

两种写法分组粒度相同，WHERE 均为范围条件：若在 txn_time 上建索引 idx_txn_time(txn_time)，可走索引范围扫描后再分组，代价可控；解法二若省略时间条件则需全表扫描后分组，大表上明显更慢。优化建议：一是建复合索引 (txn_status, txn_time)，状态等值+时间范围可同时命中；二是大表按月/按日分区，日报查询只扫对应分区；三是固定日报需求下用 T+1 预聚合表（txn_date, txn_cnt, total_amt），晨会查询毫秒级返回；四是金额汇总在 SQL 层用 DECIMAL 出结果，应用层不要再用浮点二次加工。

### 6. 面试延伸考点

**问：为什么时间条件用 < 次日零点而不是 BETWEEN 当日 00:00:00 到 23:59:59？** 回答要点：DATETIME 带时分秒，写 23:59:59 会漏掉 23:59:59.5 这类记录，左闭右开最稳妥且不怕字段精度变化。

**问：要同时统计成功率和失败笔数怎么写？** 回答要点：条件聚合，SUM(CASE WHEN txn_status='失败' THEN 1 ELSE 0 END) 与 COUNT(*) 相除。

**问：冲正交易应该怎么算？** 回答要点：冲正表示原交易被撤销，通常原交易与冲正都不计入有效交易或按净额口径，必须与业务确认并写入口径文档。

### 7. 业务拓展思考

日报的下一步是自动预警：把每日金额与滚动 28 天均值、标准差对比，偏离超阈值自动推送值班群并联动风控排查。还可按 txn_type、渠道、分行拆维度出结构化日报，快速定位波动来源。口径延展上可定义"有效交易"（剔除 0.01 元测试单等羊毛行为），防止刷量干扰监控基线；对金额维度另设"借贷净流量"口径，支持流动性管理视角。

## FIN-03 逾期超过30天的客户名单

### 1. 业务背景

消费金融部贷后管理岗每月初要产出催收名单：把逾期超过 30 天的客户筛出来交给催收团队分级处置，同时报备风控委员会。30 天是重要的风险分水岭——逾期超过 30 天（进入 M2+）后，贷款大概率向不良迁徙，需要升级为电话催收、上门催收甚至启动担保代偿。名单输出必须合规：仅包含必要的身份与逾期信息，通过加密通道下发到催收系统并留痕，且要剔除已结清/已核销的贷款，避免对正常客户错误催收引发投诉与监管处罚。

### 2. 表结构说明

贷款表 loans：

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | VARCHAR(20) | 贷款合同号（主键） |
| customer_id | BIGINT | 客户编号 |
| product_name | VARCHAR(50) | 贷款产品名：信用贷/房贷/车贷/消费贷等 |
| loan_amount | DECIMAL(18,2) | 合同金额 |
| outstanding_principal | DECIMAL(18,2) | 剩余未还本金 |
| due_date | DATE | 当期应还日 |
| overdue_days | INT | 逾期天数（已扣除3天宽限期后的口径） |
| loan_status | VARCHAR(10) | 贷款状态：正常/逾期/结清/核销 |

示例数据（5行）：

| loan_id | customer_id | product_name | loan_amount | outstanding_principal | due_date | overdue_days | loan_status |
|---|---|---|---|---|---|---|---|
| L20230001 | 100003 | 信用贷 | 100000.00 | 85000.00 | 2024-01-15 | 45 | 逾期 |
| L20230002 | 100007 | 信用贷 | 80000.00 | 76000.00 | 2024-02-01 | 28 | 逾期 |
| L20230003 | 100010 | 房贷 | 1200000.00 | 980000.00 | 2024-03-20 | 0 | 正常 |
| L20230004 | 100012 | 消费贷 | 30000.00 | 29500.00 | 2024-01-30 | 36 | 逾期 |
| L20230005 | 100015 | 车贷 | 150000.00 | 149000.00 | 2024-02-25 | 5 | 逾期 |

### 3. 解题思路

先定口径："逾期超过30天"指 overdue_days > 30；本行口径已扣除 3 天宽限期（到期后 3 天内不算逾期），所以 overdue_days=31 才算进入 M2+。若面试中没给现成字段，可用 DATEDIFF(CURDATE(), due_date) 现算，但必须同时排除宽限期影响与已结清状态。实现路径是单表多条件过滤，输出客户编号、合同号、产品、剩余本金、逾期天数，按逾期天数降序排列，最严重的排最前便于催收分诊。**【避坑指南】** 一是忘记排除 loan_status IN ('结清','核销') 的记录，会对已还清客户错误催收；二是用 DATEDIFF 现算时，跑批快照日与"今天"不一致会引入偏差，生产环境应优先使用表内快照字段 overdue_days；三是边界"超过30天"是 >30 还是 >=30，要和业务白纸黑字确认。

### 4. 参考解法

解法一：直接使用逾期天数快照字段（生产推荐）

```sql
SELECT
    l.customer_id,                                -- 客户编号
    l.loan_id,                                    -- 贷款合同号
    l.product_name,                               -- 产品名称
    l.outstanding_principal,                      -- 剩余本金，催收谈判的金额依据
    l.overdue_days                                -- 逾期天数（已扣宽限期口径）
FROM loans l
WHERE l.overdue_days > 30                          -- 逾期超过30天（M2+），边界已与业务确认
  AND l.loan_status NOT IN ('结清', '核销')         -- 排除已结清/已核销，避免错误催收
ORDER BY l.overdue_days DESC;                      -- 逾期最久的排最前，优先处置
```

结果解读：名单按逾期严重度排序，L20230001（45天）最先外呼；28 天与 5 天的不入名单，分别留在 M1 催缴池与宽限期观察池。

解法二：用 DATEDIFF 现算逾期天数（无快照字段时）

```sql
SELECT
    l.customer_id,                                -- 客户编号
    l.loan_id,                                    -- 合同号
    l.outstanding_principal,                      -- 剩余本金
    DATEDIFF(CURDATE(), l.due_date) AS calc_days  -- 当前日期减应还日，现场计算逾期天数
FROM loans l
WHERE DATEDIFF(CURDATE(), l.due_date) > 30         -- 逾期超过30天
  AND l.loan_status = '逾期'                        -- 状态为逾期的才参与计算，避免结清单被误算
ORDER BY calc_days DESC;                           -- 逾期天数降序
```

结果解读：适合临时取数与面试白板推演；但 due_date 可能因展期被更新，且"今天"与数据快照日不同会带来口径漂移，生产必须用快照字段。

### 5. 性能分析与优化

解法一条件简单，建复合索引 (loan_status, overdue_days) 后可先按状态等值过滤再按天数范围定位，效率高；解法二对 due_date 套 DATEDIFF 后再比较无法使用 due_date 索引，可改写为等价范围条件 due_date < CURDATE() - INTERVAL 33 DAY（把 30 天逾期加 3 天宽限期换算到日期端），即可走索引。更系统的优化：每月固定跑批，把逾期名单落到催收中间表，催收系统只读中间表，避免业务高峰期反复扫全量贷款表；同时给 customer_id 建索引，方便后续关联客户信息表取联系方式。

### 6. 面试延伸考点

**问：逾期30天含不含宽限期？两种口径差在哪？** 回答要点：含宽限期则到期第 4 天才计逾期 1 天；监管与五级分类通常用不含宽限口径，对客告知用含宽限口径，报表必须写明用的是哪个。

**问：怎么统计各逾期桶（1-30/31-60/61-90天）的户数与金额？** 回答要点：CASE WHEN 分桶 + GROUP BY，金额用 SUM(outstanding_principal)，桶边界左闭右开保持一致。

**问：为什么生产上不要用 CURDATE() 现算而要用表内快照字段？** 回答要点：快照日与查询日不一致会造成同一天两次查询结果不同、历史报表无法复现，且现算无法利用索引。

### 7. 业务拓展思考

该名单是贷后管理的起点：按逾期天数分桶后可配置差异化催收策略（M2 短信+外呼、M3 委外、M4+ 法诉），催收结果回流向风控模型提供违约标签。口径可延展为迁徙率（上月 M1 本月滚入 M2 的比例）与 Vintage 曲线，用于评估各放款批次质量；合规上要控制名单可见范围、留存外呼录音、禁止向无关第三方泄露客户欠款信息，确保催收行为全程可审计。

## FIN-04 各理财产品总余额汇总

### 1. 业务背景

财富管理条线的经营分析师每周一出一份"理财产品存续规模周报"：每只理财产品当前有多少客户持有、总余额（存续规模）是多少。产品经理用它判断产品规模是否达标、是否面临集中赎回压力；销售管理层用它做网点与客户经理的业绩归因。口径上"总余额"以估值日 T-1 的持有余额快照为准，不含在途申购；客户级持仓属于敏感信息，汇总额之外的明细仅在授权范围内使用，对外披露必须走合规审批。

### 2. 表结构说明

产品表 products：

| 字段名 | 类型 | 含义 |
|---|---|---|
| product_id | VARCHAR(10) | 产品编码（主键） |
| product_name | VARCHAR(50) | 产品名称 |
| product_type | VARCHAR(20) | 产品类型：货币基金/固收理财/混合理财/养老理财/私募专户 |
| risk_level | CHAR(2) | 产品风险等级 R1~R5 |
| expected_return | DECIMAL(5,2) | 业绩比较基准（%） |

持有表 holdings：

| 字段名 | 类型 | 含义 |
|---|---|---|
| holding_id | BIGINT | 持仓记录号（主键） |
| customer_id | BIGINT | 客户编号 |
| product_id | VARCHAR(10) | 产品编码（外键） |
| balance | DECIMAL(18,2) | 当前持有余额（元，T-1估值快照） |
| purchase_date | DATE | 首次申购日期 |

示例数据（products，5行）：

| product_id | product_name | product_type | risk_level | expected_return |
|---|---|---|---|---|
| P001 | 稳盈90天 | 固收理财 | R2 | 3.20 |
| P002 | 现金管家 | 货币基金 | R1 | 2.10 |
| P003 | 慧盈混合 | 混合理财 | R3 | 4.50 |
| P004 | 安享养老5年 | 养老理财 | R2 | 3.80 |
| P005 | 高端专享 | 私募专户 | R4 | 6.00 |

示例数据（holdings，5行）：

| holding_id | customer_id | product_id | balance | purchase_date |
|---|---|---|---|---|
| H0001 | 100001 | P001 | 50000.00 | 2023-12-05 |
| H0002 | 100002 | P002 | 12000.50 | 2024-01-10 |
| H0003 | 100003 | P001 | 80000.00 | 2023-11-20 |
| H0004 | 100001 | P003 | 30000.00 | 2024-02-15 |
| H0005 | 100005 | P005 | 500000.00 | 2024-01-28 |

### 3. 解题思路

口径明确：总余额 = 同一估值时点下该产品所有客户余额之和，本题以 holdings 表当前余额快照为准；同时顺带产出"持有客户数"，必须用 COUNT(DISTINCT customer_id)——一个客户对同一产品可能有多笔持仓，COUNT(*) 会把人数算多。实现路径：holdings 按 product_id 聚合后关联 products 取产品名。**【加分点】** 这里推荐 LEFT JOIN 从 products 出发，保证"还没有人持有"的新发产品也出现在报表中（余额显示 0），这对募集期监控非常关键——能主动指出"INNER JOIN 会静默丢掉零持有产品"是明显的加分信号。易错点：LEFT JOIN 后 SUM 结果为 NULL 需要 COALESCE 兜底，否则报表出现空单元格；金额列坚持 DECIMAL 精度，SUM 后不再有浮点误差。

### 4. 参考解法

解法一：从产品表 LEFT JOIN 持仓聚合（保留零持有产品）

```sql
SELECT
    p.product_id,                                 -- 产品编码
    p.product_name,                               -- 产品名称
    COUNT(DISTINCT h.customer_id) AS holder_cnt,  -- 持有客户数，去重防止一人多笔被重复计数
    COALESCE(SUM(h.balance), 0) AS total_balance  -- 总余额；无持仓的产品用0填充而非NULL
FROM products p
LEFT JOIN holdings h                               -- 左连接：主表是产品，保证零持有新产品不丢失
       ON p.product_id = h.product_id
GROUP BY p.product_id, p.product_name              -- 按产品分组（编码+名称一起列出更稳妥）
ORDER BY total_balance DESC;                       -- 规模从大到小排
```

结果解读：P004 没有客户持有，LEFT JOIN 下仍显示一行、余额 0，提示产品条线关注募集进度；若用 INNER JOIN 它会被悄悄吞掉，规模报表"少一只产品"很难被发现。

解法二：先聚合持仓、再关联产品（先聚合后JOIN）

```sql
SELECT
    p.product_name,                               -- 产品名称
    t.holder_cnt,                                 -- 持有客户数（来自聚合子查询）
    t.total_balance                               -- 总余额（来自聚合子查询）
FROM (
    SELECT
        h.product_id,                             -- 产品编码
        COUNT(DISTINCT h.customer_id) AS holder_cnt,  -- 去重客户数
        SUM(h.balance) AS total_balance           -- 余额合计
    FROM holdings h
    GROUP BY h.product_id                         -- 先在持仓表内部聚合，行数压缩成每产品一行
) t
INNER JOIN products p                              -- 再与产品表关联取名称等属性
        ON p.product_id = t.product_id
ORDER BY t.total_balance DESC;                     -- 规模降序
```

结果解读：先把 holdings 聚合成每产品一行再 JOIN，参与连接的行数少，大数据量下是常用的优化改写；代价是零持有产品不会出现在结果里，适合内部规模分析而非募集监控。

### 5. 性能分析与优化

解法一先 JOIN 后聚合，连接的中间结果行数等于持仓明细行数；解法二先聚合后 JOIN，中间行数只有产品数量级，通常更省内存与临时表空间。优化建议：一是 holdings 上建复合索引 (product_id, balance)，聚合可走覆盖索引不回表；二是 products.product_id 为主键，JOIN 侧无压力；三是持仓表按日更新且体量大时，建日终快照汇总表 product_balance_daily(product_id, stat_date, holder_cnt, balance_sum)，周报直接读汇总；四是需要产品类型、风险等级维度时，在解法二的子查询里 JOIN products 后再按多字段 GROUP BY 即可。

### 6. 面试延伸考点

**问：COUNT(DISTINCT customer_id) 和 COUNT(*) 差在哪？** 回答要点：后者数行数，一人多笔会重复计数；统计"多少个客户"必须先按客户去重。

**问：COALESCE(SUM(h.balance),0) 为什么需要？** 回答要点：LEFT JOIN 未匹配时 balance 为 NULL，SUM 全 NULL 结果是 NULL，报表出现空单元格，用 0 语义更明确。

**问：产品规模是时点数还是区间数？** 回答要点：余额是时点数（某估值日快照），与"本周销售额"这类区间流量数不能混用，汇报要标注估值日。

### 7. 业务拓展思考

规模周报可以继续下钻：按产品类型、风险等级分层看结构，若 R3 以上产品占比快速上升，需评估客户适当性（KYC 风险匹配）是否跟得上；按持有人集中度看前十大持有人占比，防止单一机构客户赎回引发规模闪崩。口径延展：增加"日均余额"平滑时点波动、"周环比赎回额"作为流失预警，联动客户经理对大额持仓客户做到期回访与留存挽留。

## FIN-05 客户年龄段分布与人均AUM

### 1. 业务背景

零售条线做客群分层经营，需要一张"客户年龄画像"报表：全行客户按年龄段（30岁以下、30-45岁、45-60岁、60岁以上）分布如何，各段的人均管理资产规模（AUM，Assets Under Management）是多少。年轻客群人均资产低但成长性强，适合推信用卡、消费贷与基金定投；中老年客群资产厚，主打养老理财与保险。营销预算与权益设计据此分配。年龄与资产均属个人敏感信息，报表只输出分组统计值，禁止落到个人明细级外发，这是数据合规的底线。

### 2. 表结构说明

客户主表 customers（本例使用生日与资产快照字段）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户编号（主键） |
| cust_name | VARCHAR(50) | 客户姓名（脱敏） |
| birth_date | DATE | 出生日期 |
| total_assets | DECIMAL(18,2) | 客户总资产AUM快照（存款+理财+基金，元，日终跑批） |
| city | VARCHAR(20) | 城市 |
| risk_level | CHAR(2) | 风险等级 R1~R5 |

示例数据（5行）：

| customer_id | cust_name | birth_date | total_assets | city | risk_level |
|---|---|---|---|---|---|
| 100001 | 张* | 1996-04-12 | 85000.00 | 杭州 | R2 |
| 100002 | 李* | 1972-09-30 | 560000.00 | 上海 | R1 |
| 100003 | 王* | 1985-01-20 | 150000.00 | 北京 | R3 |
| 100004 | 赵* | 2003-11-08 | 8000.00 | 深圳 | R2 |
| 100005 | 钱* | 1965-06-25 | 1200000.00 | 成都 | R4 |

### 3. 解题思路

口径先定：年龄用 TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) 按周岁计算，不能用当前年份减出生年份——那会把未过生日的人算大一岁；AUM 用 total_assets 日终快照，人均 AUM = SUM(total_assets)/COUNT(*)，也可直接 AVG(total_assets)。分箱规则写死在 CASE WHEN 里：30岁以下 / 30-45岁 / 45-60岁 / 60岁以上，边界归属（30 岁整归哪档）必须全组统一。实现路径：先在派生表里算出每人的年龄段标签，外层再按标签 GROUP BY 统计人数与人均资产。**【避坑指南】** birth_date 为 NULL 的客户不会落入任何一档，分组计数加总与全量对不上，必须显式归入"未知"档兜底；AVG 会静默忽略 NULL，容易掩盖生日缺失的数据质量问题。

### 4. 参考解法

解法一：派生表先打年龄段标签，外层聚合（含未知档兜底）

```sql
SELECT
    t.age_band,                                   -- 年龄段标签
    COUNT(*) AS cust_cnt,                         -- 该段客户数
    ROUND(AVG(t.total_assets), 2) AS avg_aum      -- 该段人均AUM，AVG自动忽略NULL
FROM (
    SELECT
        customer_id,
        total_assets,
        CASE
            WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 30 THEN '30岁以下'  -- 按周岁算年龄再分箱
            WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 45 THEN '30-45岁'   -- 上一档已排除<30，此处即30~44
            WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 60 THEN '45-60岁'   -- 45岁整的归属需与业务确认
            WHEN birth_date IS NOT NULL            THEN '60岁以上'                 -- 有生日且年龄>=60
            ELSE '未知'                                                            -- 生日缺失的兜底档，防止计数丢失
        END AS age_band
    FROM customers
) t
GROUP BY t.age_band                                -- 按年龄段分组
ORDER BY FIELD(t.age_band, '30岁以下', '30-45岁', '45-60岁', '60岁以上', '未知');
                                                   -- FIELD按业务习惯顺序排列，而非字母/拼音序
```

结果解读：60 岁以上段人均 AUM 通常最高，验证"资产随年龄积累"；30 岁以下人多钱少，是低成本获客与长期经营的战略客群。

解法二：直接 GROUP BY CASE 别名（MySQL 8.0 支持按别名分组）

```sql
SELECT
    CASE
        WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 30 THEN '30岁以下'  -- 与解法一相同的分箱规则
        WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 45 THEN '30-45岁'
        WHEN TIMESTAMPDIFF(YEAR, birth_date, CURDATE()) < 60 THEN '45-60岁'
        ELSE '60岁及以上（含未知）'                                             -- 简化处理：未知年龄并入最后一档
    END AS age_band,                              -- 分箱表达式直接写在SELECT里
    COUNT(*) AS cust_cnt,                         -- 客户数
    ROUND(SUM(total_assets) / COUNT(*), 2) AS avg_aum  -- 人均AUM：总和除以人数，等价于AVG但更显式
FROM customers
GROUP BY age_band                                  -- MySQL允许按SELECT别名分组
ORDER BY MIN(age_band);                            -- 简化排序，正式报表可用FIELD自定义顺序
```

结果解读：写法更短，适合快速取数；但"未知"档被并入 60 岁以上，该段人数虚高，且分箱逻辑散落在 SELECT 里，正式报表建议用解法一并保留未知档。

### 5. 性能分析与优化

两种解法都是全表扫描 + 一次聚合，量级相当，主要开销在对每行计算 TIMESTAMPDIFF。优化建议：一是表很大时物化一列 age 或 age_band（跑批时维护），查询退化为普通列分组，代价骤降；二是 birth_date 索引对本题（全量分布）帮助有限，但对下游"筛某年龄段名单"有用；三是 AUM 坚持用日终快照字段，若现场关联账户明细实时 SUM 会重一个量级；四是分箱边界参数化到维度表 age_band_dim(min_age, max_age, band_name)，口径变更不用改 SQL；五是更稳健的分析建议补充中位数（窗口函数 NTILE/PERCENT_RANK），避免富豪客户拉高均值。

### 6. 面试延伸考点

**问：为什么用 TIMESTAMPDIFF 而不是 YEAR(CURDATE())-YEAR(birth_date)？** 回答要点：后者把没过生日的也算大一岁，口径错误；TIMESTAMPDIFF(YEAR,...) 才是精确周岁。

**问：AUM 为 0 的客户算客户吗？** 回答要点：看经营定义，通常"零资产户"单独统计，且要区分"从未有资产"与"资产流失为 0"，两者的运营动作完全不同。

**问：人均 AUM 会被什么扭曲？如何更稳健？** 回答要点：极少数高净值客户拉高均值；更稳健用中位数或分位数（NTILE(10) 看十等分），并配合分层占比描述分布。

### 7. 业务拓展思考

年龄×AUM 二维交叉可升级为经典的客户分层九宫格，驱动差异化权益：年轻低资产客群推首绑卡与定投，高资产长者推私行与养老规划。画像还与适当性管理联动——向高龄客户销售 R4 产品需额外的风控提示与双录。口径延展：AUM 可细分为存款/理财/基金/保险结构占比，观察客群"存款搬家"与财富迁移趋势；年龄分箱也可替换为代际标签（Z世代/千禧一代），让营销语言与活动设计对齐。

## FIN-06 近30天有交易的活跃客户数

### 1. 业务背景

手机银行运营团队刚结束一轮"交易打卡"促活活动，需要评估效果：看板的北极星指标是"近30天有交易行为的客户数"（月活跃交易客户），它比登录日活更贴近真实经营价值——登录不算活跃，动了钱才算。运营总监每周要看这个数及其环比变化，判断活动带来的交易转化是否可持续，并据此调整下阶段投放。注意与风控口径区分：本指标只统计"成功"交易，失败交易不算活跃；同时活跃客户明细属于内部经营数据，输出仅限汇总数，明细名单只能给到有权限的精准营销岗位。

| txn_status | VARCHAR(10) | 交易状态：成功/失败/冲正 |

示例数据（5行）：

| txn_id | customer_id | amount | txn_status | txn_time |
|---|---|---|---|---|
| 202409200001 | 100001 | 500.00 | 成功 | 2024-09-20 09:10:00 |
| 202409250002 | 100002 | 1200.00 | 成功 | 2024-09-25 12:30:00 |
| 202409280003 | 100001 | 300.00 | 失败 | 2024-09-28 18:45:00 |
| 202410010004 | 100003 | 8000.00 | 成功 | 2024-10-01 10:05:00 |
| 202410150005 | 100002 | 66.00 | 成功 | 2024-10-15 20:12:00 |

### 3. 解题思路

口径是本题灵魂："近30天"指包含今天在内的最近30个自然日，即 txn_time >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)；"有交易"指至少一笔成功交易；"活跃客户数"是客户去重计数，一个客户30天内交易 100 笔也只算 1 个。实现路径两条：一是 COUNT(DISTINCT customer_id) 一步到位；二是先 SELECT DISTINCT customer_id 取出去重客户集合，再外套 COUNT(*)，逻辑等价但分步清晰，且派生表可直接复用为"活跃客户清单"。**【加分点】** 能主动指出"活跃"必须写明口径——交易口径与登录口径是两个不同的数，汇报时混用会被面试官扣分。易错点：把 CURDATE() 换成 NOW() 会连时分秒一起比较导致窗口边界偏移；COUNT(DISTINCT) 误写成 COUNT(*) 会把人数虚高；失败交易必须过滤，否则失败重试的客户也被算成活跃。

### 4. 参考解法

解法一：COUNT(DISTINCT) 一步到位

```sql
SELECT
    COUNT(DISTINCT t.customer_id) AS active_cust  -- 近30天有成功交易的客户去重数
FROM transactions t
WHERE t.txn_time >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)  -- 最近30天窗口，含今天
  AND t.txn_status = '成功';                        -- 风控口径：失败/冲正交易不算活跃
```

结果解读：返回一个数（如 48231），与上一个30天窗口对比即得环比，是运营周会的核心汇报指标。

解法二：先去重取客户集合，再计数（便于扩展名单）

```sql
SELECT
    COUNT(*) AS active_cust                       -- 对去重后的客户集合计数
FROM (
    SELECT DISTINCT
        t.customer_id                             -- 每个活跃客户只保留一行
    FROM transactions t
    WHERE t.txn_time >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)  -- 同样的30天窗口
      AND t.txn_status = '成功'                 -- 只认成功交易
) d;                                              -- 派生表d：近30天活跃客户清单
```

结果解读：结果与解法一完全一致；去掉外层 COUNT 就能直接导出活跃客户名单给精准营销用，一份 SQL 两用，复用性强。

### 5. 性能分析与优化

COUNT(DISTINCT) 需要在内存/临时表中维护去重结构，客户量到千万级时是主要开销；解法二本质相同，仅多一层子查询，优化器通常会合并执行。优化建议：一是建复合索引 (txn_status, txn_time, customer_id)，过滤与去重走覆盖索引，避免回表；二是 txn_time 保持裸字段范围比较（不要 DATE(txn_time) >= ...），才能命中索引；三是亿级流水改走数仓预聚合：日终先算每日活跃客户集合，30 天指标由 30 个日集合合并去重得到（Bitmap/去重合并思路），查询从分钟级降到秒级；四是结果落活跃看板表，历史值固化，避免每次重算。

### 6. 面试延伸考点

**问：活跃口径用"有交易"还是"有登录"？** 回答要点：登录活跃看产品粘性，交易活跃看经营价值；汇报必须写明口径，本行北极星指标用交易口径。

**问：怎么同时输出近30天和上一个30天的对比？** 回答要点：条件聚合写两个窗口各 COUNT(DISTINCT ...)，或两个子查询分别算再 JOIN，注意窗口不重叠。

**问：客户量到亿级，COUNT(DISTINCT) 还能用吗？** 回答要点：单机压力大会超时，可改近似算法（HyperLogLog类）、位图或预聚合，用可接受的精度损失换性能。

### 7. 业务拓展思考

活跃客户数是转化漏斗的中间层：向上接"注册客户数"看注册→动户转化率，向下接"交易金额"看活跃深度。运营动作上，对"近30天活跃但近7天沉默"的客户触发挽留推送；对连续 3 个窗口活跃的客户升级为忠诚客群给权益倾斜。口径延展：把总活跃拆成"首交易客户数"（新增动户）与"复交易客户数"两个分量，涨跌归因立刻清晰——是新客驱动还是存量唤醒，策略完全不同。

## FIN-07 各城市交易量排名（Top10 城市）

### 1. 业务背景

分行条线经营分析例会上，管理层要看"哪些城市贡献了全行最多的交易笔数"，以此评估区域运营强度与渠道布局：交易量持续领先的城市考虑增设网点与本地化营销，垫底城市则诊断是客群基数问题还是产品适配问题。交易笔数来自全渠道流水，客户归属城市取自客户信息表的常住城市——交易表里没有城市字段，必须两表关联。口径与合规要点：统计成功交易并限定统计期；城市取客户最新有效地址，避免历史迁居造成归属漂移；城市级汇总可对外汇报，客户级明细不出内网。

### 2. 表结构说明

客户表 customers：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户编号（主键） |
| cust_name | VARCHAR(50) | 姓名（脱敏） |
| city | VARCHAR(20) | 常住城市 |
| risk_level | CHAR(2) | 风险等级 |
| open_date | DATE | 开户日期 |

交易表 transactions：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 流水号（主键） |
| customer_id | BIGINT | 客户编号 |
| txn_type | VARCHAR(10) | 交易类型 |
| amount | DECIMAL(18,2) | 交易金额 |
| txn_status | VARCHAR(10) | 交易状态 |
| txn_time | DATETIME | 交易时间 |

示例数据（customers，5行）：

| customer_id | cust_name | city | risk_level | open_date |
|---|---|---|---|---|
| 100001 | 张* | 杭州 | R2 | 2024-01-05 |
| 100002 | 李* | 上海 | R1 | 2024-02-11 |
| 100003 | 王* | 北京 | R3 | 2024-02-18 |
| 100004 | 赵* | 深圳 | R2 | 2024-03-02 |
| 100005 | 钱* | 杭州 | R4 | 2024-03-15 |

示例数据（transactions，5行）：

| txn_id | customer_id | txn_type | amount | txn_status | txn_time |
|---|---|---|---|---|---|
| 900001 | 100001 | 转账 | 2000.00 | 成功 | 2024-10-01 08:00:00 |
| 900002 | 100002 | 存款 | 500.00 | 成功 | 2024-10-01 09:00:00 |
| 900003 | 100005 | 购买理财 | 10000.00 | 成功 | 2024-10-02 10:00:00 |
| 900004 | 100003 | 取款 | 300.00 | 失败 | 2024-10-02 11:00:00 |
| 900005 | 100004 | 转账 | 700.00 | 成功 | 2024-10-02 12:00:00 |

### 3. 解题思路

先定口径：交易量按"成功交易笔数"计，时间限定一个自然月；城市归属以客户表 city 为准，需要 transactions JOIN customers ON customer_id 后按 city GROUP BY 计数，再降序取前 10。实现路径两条：一是 ORDER BY + LIMIT 直接截断；二是窗口函数 RANK() OVER (ORDER BY COUNT(*) DESC) 生成名次后取 rk<=10。**【面试高频】** 两种取 Top10 的方式差异在哪——LIMIT 遇到并列第 10 名会按隐式顺序随机截断，RANK 会把并列名次全部保留，对需要稳定可复现结果的业务报表，窗口写法更严谨。易错点：JOIN 键类型或编码不一致导致漏匹配；失败交易未过滤；客户表 city 为 NULL 的交易会从 INNER JOIN 结果中消失，需归入"未知"档兜底。

### 4. 参考解法

解法一：JOIN + GROUP BY + ORDER BY + LIMIT

```sql
SELECT
    c.city,                                       -- 城市名
    COUNT(*) AS txn_cnt                           -- 成功交易笔数
FROM transactions t
INNER JOIN customers c                             -- 内连接：流水挂上客户的城市属性
        ON t.customer_id = c.customer_id
WHERE t.txn_status = '成功'                        -- 只统计成功交易
  AND t.txn_time >= '2024-10-01'                   -- 统计起始日（含）
  AND t.txn_time < '2024-11-01'                    -- 统计截止日（不含），恰好一个自然月
GROUP BY c.city                                    -- 按城市分组计数
ORDER BY txn_cnt DESC                              -- 笔数降序
LIMIT 10;                                          -- 取前10名城市
```

结果解读：示例数据中杭州两笔成功交易居首；实际业务中一线城市通常领跑。LIMIT 简单直接，但第 10、11 名笔数相同时截断有随机性，两次执行结果可能不同。

解法二：窗口函数 RANK 处理并列

```sql
SELECT
    city,                                         -- 城市名
    txn_cnt,                                      -- 交易笔数
    txn_rank                                      -- 名次（并列同名次）
FROM (
    SELECT
        c.city,                                   -- 城市名
        COUNT(*) AS txn_cnt,                      -- 各城市成功交易笔数
        RANK() OVER (ORDER BY COUNT(*) DESC) AS txn_rank  -- 对聚合结果排名，并列取相同名次
    FROM transactions t
    INNER JOIN customers c ON t.customer_id = c.customer_id  -- 流水关联客户城市
    WHERE t.txn_status = '成功'                   -- 成功交易口径
    GROUP BY c.city                               -- 先按城市聚合
) ranked                                           -- 派生表：城市级聚合结果
WHERE txn_rank <= 10;                              -- 名次不超过10的全部保留，并列不遗漏
```

结果解读：若两个城市并列第 10，会同时保留、输出 11 行，比 LIMIT 更符合"Top10 城市"的业务语义；RANK 与 DENSE_RANK 的差别在并列后是否跳号，需按汇报习惯选择。

### 5. 性能分析与优化

两解法主体都是一次 JOIN + 一次 GROUP BY，解法二多一个窗口排序，聚合结果只有城市量级（几十到几百行），代价可忽略。性能关键在 JOIN 与前置过滤：一是在 transactions(txn_time, txn_status, customer_id) 建复合索引做时间裁剪，先缩小流水再 JOIN；二是 customers.customer_id 为主键，连接侧无压力；三是客户表远大于近期活跃客户时，可改为"先在交易侧按 customer_id 聚合、再 JOIN 客户取城市、再按城市二次聚合"的两段式改写，减少参与连接的行数；四是月度城市交易量可预聚合到 city_txn_monthly 表，历年趋势直接读汇总。

### 6. 面试延伸考点

**问：RANK、DENSE_RANK、ROW_NUMBER 的区别？** 回答要点：并列时 RANK 跳号（1,1,3），DENSE_RANK 不跳号（1,1,2），ROW_NUMBER 强制连续唯一（1,2,3）；选哪个取决于并列语义。

**问：交易笔数排名和交易金额排名会一致吗？** 回答要点：不一定，小额高频城市笔数高、金额低，两口径要并排看，避免单一指标误导资源投放。

**问：客户城市缺失怎么处理？** 回答要点：INNER JOIN 会丢掉 city 为 NULL 的交易，应归入"未知"城市档兜底，并推动地址信息治理，长期看占比要收敛。

### 7. 业务拓展思考

城市排名可细化为"城市×交易类型×金额分层"三维矩阵，识别各城市的主导交易行为：转账型城市侧重代发与缴费场景运营，理财型城市侧重财富队伍建设。指标延展：人均交易频次（笔数÷活跃客户数）比绝对笔数更能反映经营深度，避免"人多量大自然高"的错觉。风控视角下，交易量异常激增的城市要同步排查是否涉赌涉诈资金流，经营报表与反诈监测联动，防止只看增长不看风险。

## FIN-08 每个客户最近一次交易时间与交易次数

### 1. 业务背景

客户经理每月要做客户盘点：手上的客户最近什么时候交易过、本季度交易了几笔。最近交易时间距今越久，流失风险越高，是"唤醒名单"的核心字段；交易次数反映活跃深度，用于筛选高互动客户做交叉销售。这张表会下发到一线，因此字段最小化：只带客户编号、最近交易时间、交易次数，不带交易金额与联系方式明细；客户手机号由 CRM 系统按权限实时拉取并脱敏展示，避免敏感信息随报表扩散。这是 RFM 客户分层中 R（Recency）与 F（Frequency）两个维度的取数基础。

### 2. 表结构说明

交易流水表 transactions：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号（主键） |
| customer_id | BIGINT | 客户编号 |
| txn_type | VARCHAR(10) | 交易类型 |
| amount | DECIMAL(18,2) | 交易金额（元） |
| txn_status | VARCHAR(10) | 交易状态 |
| txn_time | DATETIME | 交易时间 |

示例数据（5行）：

| txn_id | customer_id | txn_type | amount | txn_status | txn_time |
|---|---|---|---|---|---|
| 880001 | 100001 | 存款 | 3000.00 | 成功 | 2024-10-01 09:00:00 |
| 880002 | 100001 | 转账 | 500.00 | 成功 | 2024-10-10 14:30:00 |
| 880003 | 100002 | 购买理财 | 20000.00 | 成功 | 2024-09-28 10:15:00 |
| 880004 | 100003 | 取款 | 200.00 | 成功 | 2024-08-30 16:40:00 |
| 880005 | 100001 | 存款 | 100.00 | 失败 | 2024-10-12 11:00:00 |

### 3. 解题思路

口径：只统计成功交易；"最近一次交易时间"= MAX(txn_time)，"交易次数"= COUNT(*)，都按 customer_id 分组，统计区间两列必须一致（同一个 WHERE）。若只要这两列，GROUP BY 聚合一步到位；若业务还要最近那笔交易的类型与金额（方便客户经理开场切入），就要用窗口函数 ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY txn_time DESC) 给每个客户的交易按时间倒序编号，外层取 rn=1 保留整行明细，同时用 COUNT(*) OVER 窗口带上次数。**【加分点】** 窗口写法一次扫描同时拿到"聚合值+明细行"，是"分组取Top1"类需求的标准解法。易错点：忘记过滤失败交易会把失败重试时间当成最近活跃；窗口函数结果不能直接写在 WHERE 里过滤，必须包一层派生表。

### 4. 参考解法

解法一：GROUP BY + MAX + COUNT（两列指标一步出）

```sql
SELECT
    t.customer_id,                                -- 客户编号
    MAX(t.txn_time) AS last_txn_time,             -- 最近一次成功交易时间
    COUNT(*) AS txn_cnt                           -- 统计区间内成功交易次数
FROM transactions t
WHERE t.txn_status = '成功'                        -- 失败/冲正不计入活跃口径
  AND t.txn_time >= '2024-10-01'                   -- 限定统计区间（示例为10月）
  AND t.txn_time < '2024-11-01'
GROUP BY t.customer_id                             -- 每个客户一行
ORDER BY last_txn_time DESC;                       -- 最近活跃的客户排前面
```

结果解读：客户 100001 最近交易为 10-10、区间内 2 笔（10-12 那笔失败已剔除）；100003 上次交易停在 8 月底，应进入流失预警名单。

解法二：ROW_NUMBER 窗口取最近一笔明细 + 窗口计数

```sql
SELECT
    customer_id,                                  -- 客户编号
    last_txn_time,                                -- 最近交易时间
    txn_cnt,                                      -- 该客户交易总次数
    last_txn_type,                                -- 最近一笔交易类型（补充业务信息）
    last_amount                                   -- 最近一笔交易金额
FROM (
    SELECT
        t.customer_id,
        t.txn_time AS last_txn_time,              -- 保留原始交易时间
        t.txn_type AS last_txn_type,              -- 最近一笔的类型
        t.amount   AS last_amount,                -- 最近一笔的金额
        COUNT(*) OVER (PARTITION BY t.customer_id) AS txn_cnt,
                 -- 窗口计数：该客户在过滤后结果集中的总笔数，不改变行粒度
        ROW_NUMBER() OVER (
            PARTITION BY t.customer_id            -- 按客户分组编号
            ORDER BY t.txn_time DESC              -- 时间倒序，最新一笔编号为1
        ) AS rn
    FROM transactions t
    WHERE t.txn_status = '成功'                   -- 成功交易口径，与解法一一致
) ranked
WHERE rn = 1;                                     -- 每个客户只保留最新一笔整行
```

结果解读：除最近时间与次数外，还带出最近一笔的类型和金额，客户经理可直接据此切入（如"您上月购买的理财即将到期"），信息密度比纯聚合更高。

### 5. 性能分析与优化

解法一是标准聚合，建复合索引 (customer_id, txn_status, txn_time) 或 (txn_status, customer_id, txn_time) 后可走索引分组，代价低；解法二需要窗口排序，内存与临时表开销更大，但一次扫描同时产出明细与聚合，避免"先聚合一次、再回头查明细一次"的两趟查询。优化建议：一是不需要明细列时坚决用解法一；二是大表按月分区，WHERE 裁剪分区后窗口排序范围大幅缩小；三是该需求高频出现时，日终跑批维护 customer_txn_stat(customer_id, last_txn_date, txn_cnt_30d) 宽表供 CRM 直读；四是"取每组最新一条"在 8.0 优先用窗口函数，不要用效率与可读性都差的相关子查询。

### 6. 面试延伸考点

**问：为什么窗口函数不能直接写在 WHERE 里？** 回答要点：SQL 逻辑执行顺序中 WHERE 先于窗口计算，必须用派生表/CTE 包一层再过滤 rn=1。

**问：想要"最近一次交易距今多少天"怎么写？** 回答要点：DATEDIFF(CURDATE(), MAX(txn_time))；注意快照日与当前日的差异，正式报表用数据日期而非系统日期。

**问：怎么筛出"从未交易"的客户？** 回答要点：交易表里根本没有他们的记录，必须从全量客户表 LEFT JOIN 交易统计，统计列为 NULL 的即沉默客户；只查交易表会全部漏掉。

### 7. 业务拓展思考

"最近交易时间"是 RFM 模型的 R 维度，加上次数 F 与金额 M 即可做客户价值分层：R 近 F 高的重点维护，R 远 F 高的优先唤醒，R 远 F 低的自然衰退观察。该统计还能反哺风控：长期沉默账户突然恢复大额交易，是账户出借、买卖的典型特征，应触发尽职调查。口径延展：输出"30/60/90天分层沉默天数分布"，为唤醒策略的触达频次与渠道选择提供依据。

## FIN-09 交易类型分布（存款/取款/转账/购买理财）

### 1. 业务背景

产品与渠道运营团队做季度用户行为分析：全行客户的交易都花在什么类型上——存款、取款、转账、购买理财各占多少笔、多少金额。这个分布决定资源投向：理财占比高说明财富管理心智强，应加投投顾服务；存款占比畸高说明资金沉淀但未转化，需要理财转化活动。风控同样紧盯该分布：某客群取款/转账占比突然抬升，可能是电诈资金转移的前兆。输出为汇总分布表，不含个人明细，满足最小可用与合规要求；类型字段如有枚举外脏数据要如实呈现而非静默丢弃。

### 2. 表结构说明

交易流水表 transactions：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 流水号（主键） |
| customer_id | BIGINT | 客户编号 |
| txn_type | VARCHAR(10) | 交易类型：存款/取款/转账/购买理财（可能存在枚举外值） |
| amount | DECIMAL(18,2) | 交易金额（元） |
| txn_status | VARCHAR(10) | 交易状态 |
| txn_time | DATETIME | 交易时间 |

示例数据（5行）：

| txn_id | customer_id | txn_type | amount | txn_status | txn_time |
|---|---|---|---|---|---|
| 770001 | 100001 | 存款 | 5000.00 | 成功 | 2024-10-03 09:00:00 |
| 770002 | 100002 | 转账 | 15000.00 | 成功 | 2024-10-03 10:10:00 |
| 770003 | 100003 | 购买理财 | 50000.00 | 成功 | 2024-10-04 11:20:00 |
| 770004 | 100004 | 取款 | 800.00 | 成功 | 2024-10-05 15:00:00 |
| 770005 | 100005 | 生活缴费 | 120.00 | 成功 | 2024-10-05 16:30:00 |

### 3. 解题思路

笔数分布与金额分布要一起看：笔数占比代表行为频次偏好，金额占比代表资金流向，二者可能完全背离——转账可能笔数少金额大。口径上先过滤成功交易；类型字段可能存在枚举外脏数据（如示例"生活缴费"，或带空格、大小写混写），要么 GROUP BY 后如实展示，要么 CASE WHEN 归一到"其他"，关键是不能丢。实现路径：解法一 GROUP BY txn_type 竖表输出并配窗口占比；解法二条件聚合把四类横排成一行五列（四类+其他兜底），适合放日报卡片。**【避坑指南】** CASE WHEN 漏写某个类型会把该类笔数金额静默归入 ELSE 或直接丢进 0，正式统计前应先用 GROUP BY 摸底字段全部取值，再写透视。

### 4. 参考解法

解法一：竖表分布 + 窗口占比

```sql
SELECT
    t.txn_type,                                   -- 交易类型
    COUNT(*) AS txn_cnt,                          -- 该类型成功笔数
    SUM(t.amount) AS total_amt,                   -- 该类型成功金额合计（DECIMAL精确）
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS cnt_pct,
                 -- 笔数占比：分组计数除以全部分组计数之和（乘100.0避免整数除法）
    ROUND(SUM(t.amount) * 100.0 / SUM(SUM(t.amount)) OVER (), 2) AS amt_pct
                 -- 金额占比：分组金额和除以总金额和
FROM transactions t
WHERE t.txn_status = '成功'                        -- 成功交易口径
  AND t.txn_time >= '2024-10-01' AND t.txn_time < '2024-11-01'  -- 限定10月区间
GROUP BY t.txn_type                                -- 按类型分组
ORDER BY txn_cnt DESC;                             -- 笔数降序
```

结果解读：转账可能"笔数第二、金额第一"，说明大额资金迁徙频繁，运营与风控都要关注；枚举外类型（生活缴费）如实进入分布，同时暴露字段字典需要治理。

解法二：条件聚合横排一行（汇报卡片式）

```sql
SELECT
    SUM(CASE WHEN t.txn_type = '存款' THEN 1 ELSE 0 END) AS dep_cnt,       -- 存款笔数
    SUM(CASE WHEN t.txn_type = '取款' THEN 1 ELSE 0 END) AS wdr_cnt,       -- 取款笔数
    SUM(CASE WHEN t.txn_type = '转账' THEN 1 ELSE 0 END) AS trf_cnt,       -- 转账笔数
    SUM(CASE WHEN t.txn_type = '购买理财' THEN 1 ELSE 0 END) AS wm_cnt,    -- 购买理财笔数
    SUM(CASE WHEN t.txn_type NOT IN ('存款','取款','转账','购买理财')
             THEN 1 ELSE 0 END) AS oth_cnt                        -- 枚举外类型兜底列，防止脏数据被吞
FROM transactions t
WHERE t.txn_status = '成功'                        -- 成功口径
  AND t.txn_time >= '2024-10-01' AND t.txn_time < '2024-11-01';  -- 10月区间
```

结果解读：一行五列直接可贴进日报；专门保留"其他"列让枚举外数据可见而不是被 CASE 静默吞掉——若 oth_cnt 持续增长，说明上游类型字典失控，应推动治理。

### 5. 性能分析与优化

解法一扫描一次表做分组，窗口占比是轻量操作；解法二同样单次扫描，CASE 多分支在行数大时 CPU 略高，但省去 GROUP BY 临时表。优化建议：一是 (txn_status, txn_time) 复合索引先裁剪状态与时间；二是类型列取值有限，应外键约束到类型字典表 txn_type_dim，脏数据在 ETL 层拦截而不是在报表层兜底；三是该分布月度稳定，适合预聚合 type_dist_monthly 供 BI 看板直连；四是金额维度坚持 DECIMAL 汇总，应用层不做浮点累加。

### 6. 面试延伸考点

**问：CASE WHEN 里漏了一个类型会怎样？** 回答要点：该类型的行落入 ELSE 0 或被忽略，结果静默偏小；对策是先 GROUP BY 摸底枚举值，或保留 ELSE 兜底列让异常可见。

**问：怎么算各类型的户均笔数？** 回答要点：COUNT(*)/COUNT(DISTINCT customer_id)，分母必须是去重客户数。

**问：金额口径用成功笔还是含冲正？** 回答要点：统计行为分布用成功笔；若做资金净流量口径，取款/转出记负向，需单独立口径并写清说明。

### 7. 业务拓展思考

类型分布的下一步是结构迁移分析：对比逐月分布看"存款→理财"转化趋势，评估财富中收战略进度。运营上，对"只存不理"客群推理财新手引流，对"只转账"客群用缴费、信用卡场景提升粘性。风控延展：为每个客群建立类型基线分布，偏离检测（如某城市取款占比突增）可作涉诈预警信号；口径可细化到"渠道×类型"二维，观察线下柜台被手机端替代的进度，指导网点转型。

## FIN-10 风险等级 R1-R5 客户数量分布

### 1. 业务背景

反洗钱与风控条线每季度向合规负责人汇报客户风险等级分布：全量客户按洗钱/信用风险划分为 R1（低）到 R5（高）五级。R4/R5 客户需执行强化尽职调查（EDD）、限制非柜面交易额度，其占比变化直接反映客群风险结构，也是监管检查的必查报表。这类报表有一个区别于普通经营报表的硬要求：R1~R5 五级必须全部呈现——即使某级客户数为 0 也要显示 0，否则审阅者无法区分"确实没有"和"漏统计了"，这在监管问询时是自证清白的关键。新客户尚未评级跑批的，还须单列"未评级"档。

### 2. 表结构说明

客户主表 customers：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户编号（主键） |
| cust_name | VARCHAR(50) | 姓名（脱敏） |
| risk_level | CHAR(2) | 风险等级 R1~R5（反洗钱评级跑批维护，可能为NULL） |
| risk_level_date | DATE | 评级日期 |
| id_type | VARCHAR(10) | 证件类型：身份证/护照等 |
| open_date | DATE | 开户日期 |

示例数据（5行）：

| customer_id | cust_name | risk_level | risk_level_date | id_type | open_date |
|---|---|---|---|---|---|
| 100001 | 张* | R2 | 2024-06-30 | 身份证 | 2024-01-05 |
| 100002 | 李* | R1 | 2024-06-30 | 身份证 | 2024-02-11 |
| 100003 | 王* | R5 | 2024-06-30 | 护照 | 2024-02-18 |
| 100004 | 赵* | R3 | 2024-06-30 | 身份证 | 2024-03-02 |
| 100005 | 钱* | NULL | 2024-06-30 | 身份证 | 2024-03-15 |

### 3. 解题思路

口径要点：一是统计对象为全量在册客户（本表无状态字段，按业务约定；有状态字段时排除销户）；二是 risk_level 可能为 NULL（新客户未评级），必须显式归入"未评级"档，不能因为分组或计数函数把它无声丢掉；三是输出固定 R1~R5 五级加未评级，逐级计数并给占比。实现路径：解法一 GROUP BY risk_level 直接分组（简单但缺级不显示）；解法二用条件聚合对五个等级各写一列 SUM(CASE WHEN...)，保证五级全部出现、为 0 也可见，并附全量列做勾稽校验。**【面试高频】** 为什么风控报表宁可多一行"0"也不要缺行——因为缺行无法证明是"无"还是"漏"，审计上说不清。易错点：等级值大小写/空格不一致导致 R2 拆成两行；COUNT(risk_level) 会跳过 NULL，与 COUNT(*) 混用造成分母不齐。

### 4. 参考解法

解法一：GROUP BY 直接分组（NULL 转未评级兜底）

```sql
SELECT
    COALESCE(c.risk_level, '未评级') AS risk_lvl, -- NULL等级转成'未评级'标签，避免该档被静默丢弃
    COUNT(*) AS cust_cnt,                         -- 各等级客户数（COUNT(*)不漏NULL行）
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS pct  -- 占全量客户比例
FROM customers c
GROUP BY COALESCE(c.risk_level, '未评级')          -- 按转换后的等级表达式分组
ORDER BY risk_lvl;                                 -- 按等级排序（R1~R5、未评级）
```

结果解读：若 R1 占七成、R4/R5 合计不足一成，说明客群风险结构健康；"未评级"行偏高则提示评级跑批积压，是必须上报的数据质量问题。

解法二：条件聚合固定五级 + 未评级（一行展示，缺级显示0）

```sql
SELECT
    SUM(CASE WHEN c.risk_level = 'R1' THEN 1 ELSE 0 END) AS r1_cnt,       -- R1人数（没有则为0）
    SUM(CASE WHEN c.risk_level = 'R2' THEN 1 ELSE 0 END) AS r2_cnt,       -- R2人数
    SUM(CASE WHEN c.risk_level = 'R3' THEN 1 ELSE 0 END) AS r3_cnt,       -- R3人数
    SUM(CASE WHEN c.risk_level = 'R4' THEN 1 ELSE 0 END) AS r4_cnt,       -- R4人数
    SUM(CASE WHEN c.risk_level = 'R5' THEN 1 ELSE 0 END) AS r5_cnt,       -- R5人数
    SUM(CASE WHEN c.risk_level IS NULL THEN 1 ELSE 0 END) AS unrated_cnt, -- 未评级人数，必须单列可见
    COUNT(*) AS total_cnt                          -- 全量客户数，用于核对前六列加总一致
FROM customers c;                                  -- 无WHERE：统计全量，含未评级
```

结果解读：五级与未评级共六列加总应等于 total_cnt，报表自带勾稽校验；某级为 0 也明示为 0，满足风控报表"缺级可见"的合规要求。

### 5. 性能分析与优化

解法一一次全表分组，代价低；解法二单次扫描带六个条件表达式，行数大时 CPU 略高但仍远优于分六趟查询。优化建议：一是 risk_level 区分度极低，单独建索引无意义；二是若需"等级×城市"等交叉维度，可建 (city, risk_level) 复合索引或直接预聚合；三是评级取值应外键约束到等级字典表，防止脏枚举混入；四是季度监管报表走 T-1 快照表（含评级日期版本），保证监管问询时能精确还原"当时看到什么"；五是超大客户表可按评级跑批日增量维护分布汇总表。

### 6. 面试延伸考点

**问：为什么风控报表要求空等级也显示0？** 回答要点：区分"确实没有"与"统计漏了"，缺行在审计上无法自证，这是风控报表的严谨性要求。

**问：评级过期（超过一年未重评）的客户算什么？** 回答要点：合规上应触发重评，报表可按 risk_level_date 单列"评级过期"档，不能混入正常等级。

**问：GROUP BY 会把 NULL 分到一组吗？** 回答要点：会，NULL 单独成组且 COUNT(*) 能计到；会丢数的是 JOIN 匹配与 COUNT(字段) 场景，三者要分清。

### 7. 业务拓展思考

等级分布是风控资源配置的仪表盘：R4/R5 客户池规模决定 EDD 团队编制与名单化系统容量，占比抬升要区分是模型阈值调整还是客群真实恶化。可延展为等级迁移矩阵（上季 R2 本季流向哪级），迁徙率恶化通常早于绝对分布恶化，是更灵敏的预警指标；再联动限额系统，对 R5 客户自动收紧非柜面额度，形成"报表—策略—管控"闭环。合规上，等级明细涉及监管报送标准，任何口径调整需留档并报备。

## FIN-11 单笔金额 Top10 的交易明细

### 1. 业务背景

反洗钱中心每日需要复核大额交易：按单笔金额取全行当日 Top10，逐笔确认交易背景，判断是否达到人民银行大额交易报告标准（如单笔人民币 50 万以上的非现金转账等），并决定是否上报或转反欺诈深挖。这份明细要求字段完整——交易时间、类型、金额、客户、账户，供调查人员直接阅读，属于涉密报表，仅在反洗钱系统内流转。金额门槛类业务天然关心"并列"问题：两笔金额完全相同的交易都排在第 10 名附近时，漏掉任何一笔都可能造成漏报，这是合规场景下 LIMIT 与窗口函数取舍的现实依据。

### 2. 表结构说明

交易流水表 transactions：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 流水号（主键） |
| customer_id | BIGINT | 客户编号 |
| account_id | BIGINT | 账户编号 |
| txn_type | VARCHAR(10) | 交易类型 |
| amount | DECIMAL(18,2) | 交易金额（元） |
| txn_status | VARCHAR(10) | 交易状态 |
| txn_time | DATETIME | 交易时间 |

示例数据（5行）：

| txn_id | customer_id | account_id | txn_type | amount | txn_status | txn_time |
|---|---|---|---|---|---|---|
| 660001 | 100002 | `622202****0002` | 转账 | 980000.00 | 成功 | 2024-10-10 09:01:00 |
| 660002 | 100005 | `622202****0005` | 取款 | 500000.00 | 成功 | 2024-10-10 09:35:00 |
| 660003 | 100001 | `622202****0001` | 存款 | 200000.00 | 成功 | 2024-10-10 10:20:00 |
| 660004 | 100003 | `622202****0003` | 转账 | 200000.00 | 成功 | 2024-10-10 11:05:00 |
| 660005 | 100004 | `622202****0004` | 存款 | 150.00 | 成功 | 2024-10-10 12:00:00 |

### 3. 解题思路

口径：当日、成功状态、按 amount 降序取前 10。关键决策点是并列处理：ORDER BY amount DESC LIMIT 10 在第 10/11 名金额相同时会按隐式顺序随机截断，对合规场景不可接受；用 DENSE_RANK() OVER (ORDER BY amount DESC) 编号后取 rk<=10，并列名次全部保留，可能输出多于 10 行——这正是业务想要的"宁多勿漏"。实现路径：先 WHERE 裁剪当日成功交易，再排序取数。**【避坑指南】** 一是 ORDER BY 只按 amount 排序时，同金额的行顺序不稳定，必须补次级排序键（如 txn_time ASC）保证结果可复现；二是金额若用 FLOAT 存储，会出现"看起来相等实际不等"的排序事故，DECIMAL 是底线；三是失败交易混入大额榜会造成误报，浪费调查人力。

### 4. 参考解法

解法一：ORDER BY + LIMIT（快速查看）

```sql
SELECT
    t.txn_id,                                     -- 流水号
    t.customer_id,                                -- 客户编号
    t.txn_type,                                   -- 交易类型
    t.amount,                                     -- 交易金额，DECIMAL保证精确比较
    t.txn_time                                    -- 交易时间
FROM transactions t
WHERE t.txn_status = '成功'                        -- 剔除失败交易，避免误报
  AND t.txn_time >= '2024-10-10'                   -- 当日0点起（含）
  AND t.txn_time < '2024-10-11'                    -- 次日0点前（不含），左闭右开
ORDER BY t.amount DESC, t.txn_time ASC             -- 金额降序；同金额按时间先后，保证结果稳定可复现
LIMIT 10;                                          -- 取前10行
```

结果解读：快速给出当日金额最大的 10 笔；若第 10、11 名金额相同，被截掉的那笔是否该报需要人工复核，合规场景存在漏报风险。

解法二：DENSE_RANK 窗口，并列全部保留

```sql
SELECT
    txn_id, customer_id, txn_type, amount, txn_time, amt_rank  -- 输出明细与名次
FROM (
    SELECT
        t.txn_id, t.customer_id, t.txn_type, t.amount, t.txn_time,
        DENSE_RANK() OVER (ORDER BY t.amount DESC) AS amt_rank
                 -- 对当日成功交易按金额降序密集排名：并列同名次且不跳号
    FROM transactions t
    WHERE t.txn_status = '成功'                   -- 成功交易口径
      AND t.txn_time >= '2024-10-10'               -- 当日起
      AND t.txn_time < '2024-10-11'                -- 当日止（不含）
) ranked
WHERE amt_rank <= 10;                             -- 名次不超过10的全部保留，并列不遗漏
```

结果解读：两笔 20 万并列第 3 时会同时输出，名次为 3、3，第 4 名不跳号；对大额报告而言"并列全保留"比"凑够 10 行"更符合合规精神。

### 5. 性能分析与优化

数据范围已被当日条件裁剪，两解法都只对当日数据操作：解法一 LIMIT 10 可用优先队列，只需维护 10 个元素的堆，代价 O(n)；解法二需对全量当日行完整排名，当日流水千万级时窗口开销明显更高。优化建议：一是建复合索引 (txn_time, amount) 或按日分区，WHERE 先走分区/索引裁剪；二是把次级排序键 txn_time 一并纳入索引可消除 filesort；三是大额监控更适合流式方案——入仓时按金额阈值（如 ≥50 万）预筛一张大额事件表，Top10 只在极小集合上排序；四是解法一若用于正式交付，务必补齐次级排序键保证稳定输出。

### 6. 面试延伸考点

**问：LIMIT 10 与 DENSE_RANK<=10 的输出行为差异？** 回答要点：LIMIT 固定 10 行、遇并列随机截断；DENSE_RANK 并列同名次全保留、可能超过 10 行，合规场景优先后者。

**问：RANK 和 DENSE_RANK 在这里选哪个？** 回答要点：都保留并列；RANK 并列后跳号（3,3,5），DENSE_RANK 不跳（3,3,4），按报告展示与考核规则选择。

**问：大额交易标准是单笔还是日累计？** 回答要点：监管口径两者都有且区分现金额度与非现金额度；SQL 上需按客户按日 SUM 累计后再判断，只看单笔会漏掉分拆交易。

### 7. 业务拓展思考

TopN 复核是人工抽样的最小闭环，工程化方向是阈值触发的实时大额监测：金额或当日累计超阈值即生成待核任务，而不是每日事后取 Top10。指标延展：对 Top 客户做"近 30 日大额频次"画像，频繁贴线交易（刚好低于报告标准）是分拆逃报的典型特征，值得建模识别；联动名单核查系统，命中制裁/涉诈名单的交易直接进入冻结复核流程，把事后报表升级为事中拦截。

## FIN-12 2024年Q1每月新增开户客户数

### 1. 业务背景

零售行长季度经营分析会需要回答：2024 年一季度各月新开了多少户？开户是零售业务的起点，月度走势反映网点获客节奏与开门红活动效果：1 月冲高、2 月春节回落、3 月回升是常见形态，若 3 月未反弹则要复盘渠道投放与网点执行。口径上"新增开户"以 open_date（开户完成日）为准，不含预约未办结；统计对象是客户主表新插入记录，一人一行无重复问题。报表要求三个月份齐全——即使某月为 0 也要显示 0，否则折线图出现断点，管理层会误以为数据缺失。

### 2. 表结构说明

客户主表 customers：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户编号（主键） |
| cust_name | VARCHAR(50) | 姓名（脱敏） |
| id_no_masked | VARCHAR(18) | 证件号（脱敏展示） |
| channel | VARCHAR(20) | 开户渠道：APP/官网/网点等 |
| branch_id | INT | 开户网点编号（线上开户可为NULL） |
| open_date | DATE | 开户日期 |

示例数据（5行）：

| customer_id | cust_name | id_no_masked | channel | branch_id | open_date |
|---|---|---|---|---|---|
| 100001 | 张* | `3301**********0012` | APP | 101 | 2024-01-08 |
| 100002 | 李* | `3101**********0034` | 网点 | 102 | 2024-01-26 |
| 100003 | 王* | `1101**********0056` | 网点 | 101 | 2024-02-03 |
| 100004 | 赵* | `4403**********0078` | APP | NULL | 2024-02-29 |
| 100005 | 钱* | `5101**********0090` | APP | 103 | 2024-03-15 |

### 3. 解题思路

口径：按 open_date 落入 2024-01-01 至 2024-03-31 的客户逐月计数；月粒度用 DATE_FORMAT(open_date, '%Y-%m') 提取。边界写法有两种：字符串范围 open_date >= '2024-01-01' AND open_date < '2024-04-01'（推荐，可走索引且覆盖 3 月 31 日全天），或 YEAR()/MONTH() 函数过滤（索引失效，且 MONTH=3 不区分年份，跨年数据会混入）。难点在"月份补齐"：GROUP BY 只会输出有数据的月份，某月开户为 0 时整行消失；要保证 Q1 三行齐全，需构造月份骨架表（UNION ALL 三个字符串）再 LEFT JOIN 统计结果，空月用 COALESCE 补 0。**【避坑指南】** 月份维度报表"缺月"是最常见的翻车点，被追问"2月去哪了"就很被动；骨架表+LEFT JOIN 是标准解法，进阶可换成日历维表。

### 4. 参考解法

解法一：范围过滤 + DATE_FORMAT 分组

```sql
SELECT
    DATE_FORMAT(c.open_date, '%Y-%m') AS ym,      -- 开户日期格式化为'2024-01'月份标签
    COUNT(*) AS new_cust                          -- 当月新增开户客户数
FROM customers c
WHERE c.open_date >= '2024-01-01'                 -- Q1起点（含），范围条件可走索引
  AND c.open_date <  '2024-04-01'                 -- 4月1日0点前（不含），完整覆盖3月31日
GROUP BY DATE_FORMAT(c.open_date, '%Y-%m')        -- 按月分组
ORDER BY ym;                                      -- 月份升序
```

结果解读：得到 1/2/3 月各行计数，可直接画折线；但若某月开户数为 0，该月整行不出现，这是本写法的盲区。

解法二：月份骨架表 LEFT JOIN 补零

```sql
SELECT
    m.ym,                                         -- 骨架月份，保证Q1三个月都在结果里
    COALESCE(t.new_cust, 0) AS new_cust           -- 无开户的月份补0，避免折线断点
FROM (
    SELECT '2024-01' AS ym                        -- 骨架行：1月
    UNION ALL SELECT '2024-02'                    -- 骨架行：2月
    UNION ALL SELECT '2024-03'                    -- 骨架行：3月
) m
LEFT JOIN (
    SELECT
        DATE_FORMAT(c.open_date, '%Y-%m') AS ym,  -- 与骨架同口径的月份标签
        COUNT(*) AS new_cust                      -- 每月新增客户数
    FROM customers c
    WHERE c.open_date >= '2024-01-01'             -- 与解法一相同的Q1范围条件
      AND c.open_date <  '2024-04-01'
    GROUP BY DATE_FORMAT(c.open_date, '%Y-%m')    -- 按月聚合
) t ON m.ym = t.ym                                -- 骨架左连统计，保留无数据月份
ORDER BY m.ym;                                    -- 按月升序
```

结果解读：三个月恒有三行，0 也是有效经营信号（如 2 月春节假期网点歇业）；骨架法可扩展为连续日历表驱动，是时间序列报表的标准姿势。

### 5. 性能分析与优化

两解法统计部分相同，解法二多一次极小结果集（3行）的 JOIN，代价可忽略。性能关键在 WHERE 走索引：open_date 上建索引后范围条件做索引区间扫描；避免 YEAR(open_date)=2024 AND MONTH(open_date)<=3 这类函数包裹字段的写法，会退化为全表扫描。优化建议：一是季度报表可在数仓按月预聚合 open_cust_monthly(ym, channel, branch_id, cnt)，多维度会上一查直读；二是骨架表升级为日历维度表 calendar_dim，支持任意区间自动补零；三是亿级客户表按 open_date 分区，Q1 查询只扫三个分区；四是结果中补一列环比增幅（LAG 窗口），减少会后再算。

### 6. 面试延伸考点

**问：为什么用 open_date < '2024-04-01' 而不是 BETWEEN '2024-01-01' AND '2024-03-31'？** 回答要点：open_date 是 DATE 时两者等价，但字段若演化为 DATETIME，BETWEEN 会漏掉 3 月 31 日 0 点之后的记录，左闭右开对类型演化更稳健。

**问：月环比怎么写进同一结果？** 回答要点：LAG(new_cust) OVER (ORDER BY ym) 取上月值再算增幅，注意首行为 NULL 的处理。

**问：开户数和动户数是什么关系？** 回答要点：开户是流量入口，动户（首次交易）是质量校验；只考核开户会催生"冲量开户"，两个指标联立才能评估获客水分。

### 7. 业务拓展思考

月度开户数应拆渠道与网点：线上 APP 开户成本远低于网点，结构变化直接指导渠道预算；某网点连续三月挂零要现场督导。该指标与获客成本（CAC）联用才有决策意义——高开户但高销户或零动户说明"冲量"行为，应把考核从开户数切换为"90 天动户率"。口径延展：区分Ⅰ类户/Ⅱ类户分别计数（监管对电子账户有功能限额与数量约束），避免把低价值电子户混入总量造成虚增。

## FIN-13 余额低于1000元的低效账户清单

### 1. 业务背景

银行每个账户都有维护成本（系统资源、对账、反洗钱监测），大量长期小额且不动的"低效账户"挤占成本并抬高风控扫描基数。运营部每季度要输出低效账户清单：活期余额低于 1000 元、且长期无交易的正常状态账户，用于推动客户归并账户或进入睡眠户清理流程。合规要求非常关键：清理前必须履行告知义务（公告+客服通知）并保留申诉通道；有贷款代扣、社保代发、代发工资等关联功能的账户一律不得纳入限制；SQL 结果只是初筛，须人工复核后才可执行任何动作。

### 2. 表结构说明

账户表 accounts：

| 字段名 | 类型 | 含义 |
|---|---|---|
| account_id | BIGINT | 账户号（主键） |
| customer_id | BIGINT | 客户编号 |
| acct_type | VARCHAR(10) | 账户类型：活期/定期 |
| balance | DECIMAL(18,2) | 当前余额（元） |
| acct_status | VARCHAR(10) | 状态：正常/休眠/销户 |
| last_txn_date | DATE | 最近一次交易日期（从未交易则为NULL） |
| open_date | DATE | 开户日期 |

示例数据（5行）：

| account_id | customer_id | acct_type | balance | acct_status | last_txn_date | open_date |
|---|---|---|---|---|---|---|
| 62010001 | 100001 | 活期 | 320.50 | 正常 | 2023-05-01 | 2022-03-10 |
| 62010002 | 100002 | 活期 | 58.00 | 正常 | NULL | 2021-11-20 |
| 62010003 | 100003 | 活期 | 25000.00 | 正常 | 2024-10-08 | 2023-06-01 |
| 62010004 | 100004 | 定期 | 500.00 | 正常 | 2024-01-15 | 2024-01-15 |
| 62010005 | 100005 | 活期 | 999.99 | 休眠 | 2022-08-12 | 2020-07-07 |

### 3. 解题思路

口径逐条定：①"低于1000元"= balance < 1000，严格不含等于；②只看"活期"账户——定期余额低是正常业务形态，不属低效（该取舍要与业务确认）；③状态为"正常"，休眠户走另一条清理流程、销户账户直接排除；④"低效"还要叠加不动户条件：last_txn_date 早于阈值（如约180天前）或 last_txn_date IS NULL（从未交易）。实现路径：解法一单表多条件初筛；解法二 JOIN 客户表带出脱敏姓名与手机号、计算沉睡天数，方便运营直接触达。**【避坑指南】** last_txn_date IS NULL 必须单独用 OR 判断——NULL 与任何值比较结果都是 UNKNOWN，"从未交易"的账户会被 WHERE 静默漏掉，而这类恰恰是最典型的低效账户。

### 4. 参考解法

解法一：单表多条件初筛

```sql
SELECT
    a.account_id,                                 -- 账户号
    a.customer_id,                                -- 客户编号
    a.balance,                                    -- 当前余额
    a.last_txn_date                               -- 最近交易日期，NULL代表从未交易
FROM accounts a
WHERE a.acct_type = '活期'                        -- 只筛活期，定期低余额属正常形态
  AND a.acct_status = '正常'                      -- 休眠/销户走其他流程，不进本清单
  AND a.balance < 1000                            -- 严格小于1000，不含等于
  AND (a.last_txn_date < '2024-04-28'             -- 最近交易早于阈值日（约180天前）
       OR a.last_txn_date IS NULL);               -- 从未交易的账户必须单独用IS NULL判断，否则整类被漏掉
```

结果解读：初筛出"小额+长期不动"的活期正常户；62010002（从未交易）是漏网高危点，OR IS NULL 条件保证其入选。

解法二：JOIN 客户表补充脱敏联系信息

```sql
SELECT
    a.account_id,                                 -- 账户号
    c.cust_name,                                  -- 客户姓名（库内已脱敏）
    CONCAT(LEFT(c.phone_no, 3), '****', RIGHT(c.phone_no, 4)) AS phone_masked,
                 -- 手机号脱敏：保留前3后4，中间四位打码，满足输出合规
    a.balance,                                    -- 余额
    a.last_txn_date,                              -- 最近交易日期
    DATEDIFF('2024-10-25', a.last_txn_date) AS idle_days  -- 距最近交易的天数，量化"沉睡深度"
FROM accounts a
INNER JOIN customers c                            -- 关联客户表取姓名与手机号
        ON a.customer_id = c.customer_id
WHERE a.acct_type = '活期'                        -- 活期口径
  AND a.acct_status = '正常'                      -- 正常状态
  AND a.balance < 1000                            -- 低于1000元（不含）
  AND (a.last_txn_date < '2024-04-28' OR a.last_txn_date IS NULL)  -- 长期不动或从未交易
ORDER BY a.balance ASC;                           -- 余额越低越靠前，优先处理
```

结果解读：清单多了姓名、脱敏手机号与沉睡天数，可直接转入客户经理触达队列；注意 DATEDIFF 对 NULL 行返回 NULL，展示时需 COALESCE 处理或单列标注"从未交易"。

### 5. 性能分析与优化

解法一纯单表过滤：建索引 (acct_status, acct_type, balance) 后两个等值条件走索引再按余额过滤，选择性尚可；但 last_txn_date 的"OR IS NULL"组合条件会让优化器难以用单一索引，可拆成两条 UNION ALL 分别走 (acct_status, acct_type, last_txn_date) 索引再合并。优化建议：一是清单季度化跑批，落地 low_activity_accounts 中间表并加处理状态标记，避免重复触达同一客户；二是账户表亿级时按 acct_status 分区或维护"活跃账户白名单"反向缩小扫描面；三是 JOIN 只按 customer_id 主键关联，代价可控；四是导出文件加密传输、字段最小化，落实数据分级管理。

### 6. 面试延伸考点

**问：为什么 last_txn_date IS NULL 必须单独写？** 回答要点：NULL 与任何值比较结果都是 UNKNOWN 不会命中 WHERE，"从未交易"的账户会静默漏掉，直接破坏清单完整性。

**问：低效账户清理有什么合规红线？** 回答要点：公告与通知到位、保留申诉通道、有代发/代扣/社保等功能的账户不得纳入，执行前人工复核，全过程留痕可审计。

**问：沉睡判定用 last_txn_date 还是账户状态字段？** 回答要点：优先系统休眠标记（流程系统权威），last_txn_date 作补充维度；两者冲突时以流程系统为准并排查数据链路。

### 7. 业务拓展思考

低效账户治理既是成本题也是体验题：可按"余额分层×沉睡时长"二维分桶制定梯度策略（短信唤回→降级限额→归并提示），唤回成功即转化一笔沉睡 AUM。风控视角下，低效账户被收购用于跑分的风险更高，清理同时要监测"唤回即大额进出"的异常模式。口径延展：把"低效"扩展为"低余额+低频次+低产品持有数"的三低评分，比单一余额阈值更能准确定位治理对象，减少误伤正常客户。

## FIN-14 关联查询：逾期客户的姓名、手机号与逾期金额

### 3. 解题思路

```sql
    SUM(l.overdue_amount) AS total_overdue,       -- 该客户所有逾期贷款的逾期金额合计
    COUNT(*) AS overdue_loan_cnt,                 -- 逾期贷款笔数
    MAX(l.overdue_days) AS max_overdue_days       -- 最长逾期天数，决定催收分案等级
FROM loans l
INNER JOIN customers c                            -- 明细先连客户，带出身份信息
        ON l.customer_id = c.customer_id
WHERE l.loan_status = '逾期'                      -- 状态为逾期
  AND l.overdue_days > 0                          -- 双保险：排除逾期天数为0的异常记录
GROUP BY c.customer_id, c.cust_name, c.phone_no   -- 按人汇总，非聚合列必须全部列入GROUP BY
ORDER BY total_overdue DESC;                      -- 逾期金额大的优先催收
```

结果解读：客户 100001 两笔贷款合计逾期 10300 元、最长逾期 38 天，按 M2+ 高优先级分案；按人聚合保证一个客户一个任务，避免重复外呼引发投诉。

解法二：先按人聚合贷款，再 JOIN 客户（先聚合后连接）

```sql
SELECT
    c.cust_name,                                  -- 姓名
    CONCAT(LEFT(c.phone_no, 3), '****', RIGHT(c.phone_no, 4)) AS phone_masked,  -- 脱敏手机号
    t.total_overdue,                              -- 逾期金额合计（来自聚合子查询）
    t.overdue_loan_cnt,                           -- 逾期笔数
    t.max_overdue_days                            -- 最长逾期天数
FROM (
    SELECT
        l.customer_id,                            -- 按客户分组
        SUM(l.overdue_amount) AS total_overdue,   -- 逾期金额求和
        COUNT(*) AS overdue_loan_cnt,             -- 逾期笔数
        MAX(l.overdue_days) AS max_overdue_days   -- 最长逾期天数
    FROM loans l
    WHERE l.loan_status = '逾期'                  -- 逾期口径在子查询内先过滤
      AND l.overdue_days > 0                      -- 排除异常0天记录
    GROUP BY l.customer_id                        -- 每个客户聚合为一行
) t
INNER JOIN customers c                            -- 聚合结果（每人一行）再连客户表
        ON c.customer_id = t.customer_id
ORDER BY t.total_overdue DESC;                    -- 逾期金额降序
```

结果解读：连接发生在"每人一行"的聚合结果上，行数远小于明细 JOIN，客户表大时性能优势明显；结果与解法一完全一致。

### 5. 性能分析与优化

解法一以贷款明细行数参与 JOIN，明细百万级时临时表与哈希连接开销可观；解法二把 JOIN 推迟到聚合之后，连接行数等于逾期客户数，通常少一个量级。优化建议：一是 loans 上建复合索引 (loan_status, overdue_days, customer_id)，逾期过滤可走索引；二是 customers.customer_id 为主键，连接侧天然高效；三是催收名单每日跑批固化到 collection_task 表供催收系统高频读取，不直连业务库；四是脱敏在 SQL 出口统一完成（或由数据权限层统一掩码），禁止裸字段进导出文件；五是大清单分页导出按 customer_id 切片，避免一次性全量拉取造成内存与安全风险。

### 6. 面试延伸考点

**问：如果客户表里没有该客户（数据缺失），两种写法分别什么行为？** 回答要点：INNER JOIN 直接丢行、逾期客户从清单消失，催收场景不可接受；应 LEFT JOIN 保留明细并检查 NULL，推动身份数据补全。

**问：逾期金额口径包括罚息吗？** 回答要点：本表 overdue_amount 已含本息罚；若只有本金字段，需明确口径并联动利息计算规则，不能拍脑袋按比例估。

**问：为什么 GROUP BY 里要放 cust_name 和 phone_no？** 回答要点：SELECT 中的非聚合列必须出现在 GROUP BY（ONLY_FULL_GROUP_BY 强制），否则报错或产生不确定结果。

### 7. 业务拓展思考

该清单驱动的不只是外呼：逾期金额分层（小额提醒/中额协商/大额委外）配合最长逾期天数形成二维分案矩阵，回收率与人力成本最优。风控延展：把催收响应回写为行为标签（承诺还款/失联/部分还款）供风控模型迭代；对多平台共债客户可接入征信查询辅助决策。合规上，名单字段最小化、外呼录音留存、禁止向第三方泄露欠款信息，是口径之外必须写进流程的红线。

## FIN-15 各支行网点的存款余额排名

### 1. 业务背景

分行计划财务部每月初统计所辖支行网点的存款余额时点数并排名，这是"存款立行"导向下的核心 KPI：排名靠前的网点获得费用与人力倾斜，连续垫底的网点触发帮扶或布局调整。数据链路是账户表（含余额与归属网点）关联网点维表取网点名称。口径要点：时点余额取月末日终快照；存款口径含活期与定期存款账户，不含理财与基金（它们是受托资产不是银行负债，混入即口径事故）；撤并网点的存量余额需按业务规则并入承接网点，防止历史编号漂移导致总额对不上。

### 2. 表结构说明

账户表 accounts：

| 字段名 | 类型 | 含义 |
|---|---|---|
| account_id | BIGINT | 账户号（主键） |
| customer_id | BIGINT | 客户编号 |
| acct_type | VARCHAR(10) | 账户类型：活期/定期 |
| balance | DECIMAL(18,2) | 账户余额（元，月末时点快照） |
| acct_status | VARCHAR(10) | 状态：正常/休眠/销户 |
| branch_id | INT | 归属网点编号 |

网点维表 branches：

| 字段名 | 类型 | 含义 |
|---|---|---|
| branch_id | INT | 网点编号（主键） |
| branch_name | VARCHAR(50) | 网点名称 |
| city | VARCHAR(20) | 所在城市 |
| open_date | DATE | 网点开业日期 |

示例数据（accounts，5行）：

| account_id | customer_id | acct_type | balance | acct_status | branch_id |
|---|---|---|---|---|---|
| 62010001 | 100001 | 活期 | 85000.00 | 正常 | 101 |
| 62010002 | 100002 | 定期 | 300000.00 | 正常 | 102 |
| 62010003 | 100003 | 活期 | 1200.00 | 正常 | 101 |
| 62010004 | 100004 | 活期 | 50000.00 | 正常 | 103 |
| 62010005 | 100005 | 定期 | 200000.00 | 正常 | 102 |

示例数据（branches，5行）：

| branch_id | branch_name | city | open_date |
|---|---|---|---|
| 101 | 城东支行 | 杭州 | 2015-04-01 |
| 102 | 城西支行 | 杭州 | 2018-09-10 |
| 103 | 滨江支行 | 杭州 | 2021-06-20 |
| 104 | 城北支行 | 上海 | 2012-01-15 |
| 105 | 高新支行 | 深圳 | 2019-03-30 |

### 3. 解题思路

口径：只统计 acct_status='正常' 的存款账户（活期+定期都算，销户账户排除）；余额是月末时点数，直接 SUM(balance)；输出按余额降序的名次。实现路径：accounts JOIN branches ON branch_id 取网点名，GROUP BY 网点求和；解法一 ORDER BY 排序输出（名次靠位置人工读）；解法二用 RANK() OVER (ORDER BY SUM(balance) DESC) 在聚合结果上生成名次列，并列余额取同名次。**【避坑指南】** 账户表可能残留已撤并网点的失效 branch_id，INNER JOIN 会把这些余额静默丢弃、总分对不上——应 LEFT JOIN 排查"孤儿数据"，或在维表维护承接映射。易错点：把理财/基金余额误算进存款口径；并列名次用 RANK 还是 DENSE_RANK 要与考核细则一致；GROUP BY 需同时列出 SELECT 的所有非聚合列。

### 4. 参考解法

解法一：JOIN + GROUP BY + ORDER BY（排序即排名）

```sql
SELECT
    b.branch_name,                                -- 网点名称
    b.city,                                       -- 所在城市
    SUM(a.balance) AS deposit_total               -- 该网点全部正常存款账户余额合计
FROM accounts a
INNER JOIN branches b                             -- 账户挂上网点名称
        ON a.branch_id = b.branch_id
WHERE a.acct_status = '正常'                      -- 排除休眠/销户，口径干净
GROUP BY b.branch_id, b.branch_name, b.city       -- 按网点分组（编号+名称+城市一起列出）
ORDER BY deposit_total DESC;                      -- 余额降序即排名
```

结果解读：城西支行以 50 万居首（示例数据），城东支行 8.62 万次之；该写法简单可靠，但结果表没有显式名次列，正式发文时需人工补序号。

解法二：聚合 + RANK 窗口生成名次列

```sql
SELECT
    branch_name,                                  -- 网点名
    city,                                         -- 城市
    deposit_total,                                -- 存款余额合计
    RANK() OVER (ORDER BY deposit_total DESC) AS deposit_rank
                 -- 对聚合结果按余额降序排名：并列余额取相同名次，后一名跳号
FROM (
    SELECT
        b.branch_name,                            -- 网点名
        b.city,                                   -- 城市
        SUM(a.balance) AS deposit_total           -- 存款余额合计
    FROM accounts a
    INNER JOIN branches b ON a.branch_id = b.branch_id  -- 账户关联网点
    WHERE a.acct_status = '正常'                  -- 正常账户口径
    GROUP BY b.branch_id, b.branch_name, b.city   -- 按网点聚合
) t                                               -- 派生表：网点级余额
ORDER BY deposit_rank;                            -- 按名次输出
```

结果解读：名次作为一列直接可贴进考核通报；若两网点余额并列第 1，RANK 给出 1、1、3，考核细则若要求"并列不跳号"则改用 DENSE_RANK。

### 5. 性能分析与优化

主体代价是一次 JOIN + 一次分组，聚合结果只有网点量级（百行内），瓶颈在账户表扫描。优化建议：一是 accounts 建复合索引 (acct_status, branch_id, balance)，等值过滤后分组求和走覆盖索引、不回表；二是账户表按 branch_id 或变动日期分区，月度报表走分区裁剪；三是月末余额本来自日终跑批，直接在数仓建 branch_deposit_monthly(branch_id, stat_month, balance_sum) 预聚合表，排名在百行结果上瞬时完成；四是考核结果落快照表留档，保证季度末可复核当月通报数，防止口径调整后历史无法追溯。

### 6. 面试延伸考点

**问：时点余额和日均余额有什么区别？考核该用哪个？** 回答要点：时点是月末一瞬、日均是全月平均，后者能防"月末冲量月初转出"，考核应逐步转向日均口径。

**问：账户表里 branch_id=999 在网点维表查不到会怎样？** 回答要点：INNER JOIN 丢行、总额少算；应 LEFT JOIN 排查孤儿数据，或用外键约束与撤并承接映射从源头治理。

**问：想拆出"活期/定期"两个子榜怎么改？** 回答要点：GROUP BY 增加 acct_type，窗口加 PARTITION BY acct_type 分别排名，一次查询输出两张榜。

### 7. 业务拓展思考

存款排名背后是区域资金生态：可叠加网点所在商圈人口、代发工资企业数做归因，识别"低余额高潜力"网点。管理动作上，排名与增量并重——存量大的老网点防流失，新网点看增速；风控联动方面，需监测排名突变（单月暴增）是否来自大额时点资金冲量或异常资金归集，防止考核指标被资金掮客套利。口径延展：将存款细分为对公/零售、活期/定期结构，评价负债成本质量，而不是只看规模总量。
