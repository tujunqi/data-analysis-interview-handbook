## FIN-16 注册到开户的渠道转化漏斗

### 1. 业务背景
某股份制银行数字金融部在季度复盘会上要回答一个核心问题：本季度信息流、应用商店、异业合作三个渠道买来的注册用户，有多少完成了实名认证、多少最终开立了银行账户、开户后账户状态是否正常。零售条线的获客成本核算、下季度渠道预算分配、产品侧开户流程优化（如实名环节流失偏高就要简化OCR校验）都依赖这条漏斗。渠道运营经理需要分析师从注册埋点表和开户表里，按渠道把每一层转化率算准、算可比，并指出最需要抢救的环节。

### 2. 表结构说明
user_register（注册用户表，一人一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | BIGINT | 用户ID |
| register_date | DATE | 注册日期 |
| channel | VARCHAR(32) | 获客渠道：info_feed/app_store/co_brand |
| is_realname | TINYINT | 是否完成实名认证（1是/0否） |

示例数据：

| user_id | register_date | channel | is_realname |
|---|---|---|---|
| 10001 | 2026-07-03 | info_feed | 1 |
| 10002 | 2026-07-05 | app_store | 1 |
| 10003 | 2026-07-08 | info_feed | 0 |
| 10004 | 2026-07-12 | co_brand | 1 |
| 10005 | 2026-07-15 | info_feed | 1 |

account_open（开户表，一次开户一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| open_id | BIGINT | 开户流水号 |
| user_id | BIGINT | 用户ID |
| open_date | DATE | 开户日期 |
| acct_type | VARCHAR(16) | 账户类型：一类户/二类户 |
| acct_status | VARCHAR(16) | 当前状态：正常/冻结/销户 |

示例数据：

| open_id | user_id | open_date | acct_type | acct_status |
|---|---|---|---|---|
| 90001 | 10001 | 2026-07-04 | 二类户 | 正常 |
| 90002 | 10002 | 2026-07-06 | 二类户 | 冻结 |
| 90003 | 10004 | 2026-07-13 | 一类户 | 正常 |
| 90004 | 10005 | 2026-07-20 | 二类户 | 销户 |
| 90005 | 10005 | 2026-08-01 | 二类户 | 正常 |

### 3. 解题思路
先定口径：漏斗四层为"注册→实名→开户→正常状态户"，前两层看 is_realname，后两层要用开户表判断；转化率有"逐级口径"（以上一层为分母）与"全链路口径"（统一以注册为分母）两种，动手前应与面试官确认要哪种，最好两个都给。实现路径上，用注册表做左连接主表保证分母不丢人；因为一人可能多次开户（示例中10005开了两户），必须先按 user_id 去重打标再做渠道聚合。**【避坑指南】** 直接 JOIN 后 COUNT 会让多开户用户重复计数，转化率可能超过100%；另外"正常户"要判断 acct_status='正常'，只看"是否开户"会把冻结、销户也算成有效获客。

### 4. 参考解法

**解法一：CTE打标 + 条件聚合，一次算出宽表漏斗（适合直接进报表）**

```sql
WITH base AS (                              -- CTE：先把每位用户压缩成一行，完成漏斗打标
    SELECT
        r.user_id,                                                    -- 用户ID，去重粒度
        r.channel,                                                    -- 渠道维度
        MAX(r.is_realname)           AS is_realname,                  -- 是否实名（1/0）
        MAX(o.open_date IS NOT NULL) AS is_opened,                    -- 是否发生过开户行为
        MAX(o.acct_status = '正常')  AS is_valid_open                 -- 是否为正常状态户
    FROM user_register r
    LEFT JOIN account_open o                   -- 左连接：未开户用户也要保留作分母
      ON r.user_id = o.user_id
    GROUP BY r.user_id, r.channel              -- 按人去重，一人多户只算一次
)
SELECT
    channel                                                    AS 渠道,
    COUNT(*)                                                   AS 注册用户数,
    SUM(is_realname)                                           AS 实名用户数,
    SUM(is_opened)                                             AS 开户用户数,
    SUM(is_valid_open)                                         AS 正常状态户数,
    ROUND(AVG(is_realname) * 100, 2)                           AS 注册到实名率,
    ROUND(SUM(is_opened) / NULLIF(SUM(is_realname), 0) * 100, 2)    AS 实名到开户率,     -- 逐级口径
    ROUND(SUM(is_valid_open) / NULLIF(SUM(is_opened), 0) * 100, 2)  AS 开户到正常户率,   -- 逐级口径
    ROUND(SUM(is_valid_open) * 100.0 / COUNT(*), 2)            AS 注册到正常户全链路率  -- 全链路口径
FROM base
GROUP BY channel;
```

结果解读：若信息流渠道"实名到开户率"明显低于应用商店，说明注册后的开户引导环节在该渠道失效，问题在转化路径而非获客质量；"开户到正常户率"低则往往指向风控拦截或身份资料不齐。

**解法二：UNION ALL 竖表 + LAG/FIRST_VALUE 窗口，漏斗通用框架（环节可插拔）**

```sql
WITH step_cnt AS (                  -- 每个漏斗环节输出一行(渠道,环节,人数)，先竖后算
    SELECT channel, '1_注册' AS step, COUNT(*) AS cnt
    FROM user_register
    GROUP BY channel
    UNION ALL
    SELECT channel, '2_实名', COUNT(*)
    FROM user_register
    WHERE is_realname = 1                    -- 第二层：完成实名
    GROUP BY channel
    UNION ALL
    SELECT r.channel, '3_开户', COUNT(DISTINCT r.user_id)
    FROM user_register r
    JOIN account_open o ON o.user_id = r.user_id        -- 内连接即"发生过开户"
    GROUP BY r.channel
    UNION ALL
    SELECT r.channel, '4_正常户', COUNT(DISTINCT r.user_id)
    FROM user_register r
    JOIN account_open o ON o.user_id = r.user_id AND o.acct_status = '正常'
    GROUP BY r.channel
)
SELECT
    channel                                            AS 渠道,
    step                                               AS 环节,
    cnt                                                AS 人数,
    ROUND(cnt * 100.0 / LAG(cnt) OVER (
              PARTITION BY channel ORDER BY step), 2)  AS 逐级转化率,   -- 除以上一环节，首行自然为NULL
    ROUND(cnt * 100.0 / FIRST_VALUE(cnt) OVER (
              PARTITION BY channel ORDER BY step
              ROWS BETWEEN UNBOUNDED PRECEDING
                       AND UNBOUNDED FOLLOWING), 2)      AS 全链路转化率   -- 统一除以注册人数
FROM step_cnt
ORDER BY channel, step;
```

结果解读：该框架把漏斗从"写死四列"变成"环节可插拔"，后续新增绑卡、首购环节只需再 UNION 一段；逐级与全链路两个口径同表输出，方便跨渠道横向对标。

### 5. 性能分析与优化
解法一在注册表上做一次 LEFT JOIN + 一次 GROUP BY，代价约为两表连接加一次聚合，线性于数据量；解法二要扫描注册表多次（每个 UNION 分支各一次）且开户表被 JOIN 两次，数据量大时代价约为解法一的2-3倍，但换来框架的可扩展性。优化建议：① user_register(user_id)、account_open(user_id, acct_status) 建索引，连接键必须有序；② 若注册表数千万行，可先按渠道预聚合出各层人数中间表（Hive/Spark 日调度落表），查询层只做除法；③ 只统计近N个季度时，先按 register_date 分区裁剪再 JOIN。

> Hive/Spark SQL 差异：海量埋点数据建议在 Spark 上跑；布尔表达式 `MAX(o.acct_status = '正常')` 在旧版 Hive 需改写为 `MAX(CASE WHEN ... THEN 1 ELSE 0 END)`；UNION ALL 分支可并行执行，解法二在 Spark 上代价反而更可控。

### 6. 面试延伸考点
- **同一用户先后走了两个渠道注册，渠道归属怎么算？** 要点：通常按"首次触点归因"取首条注册记录，或按业务约定"末次触点归因"；主动指出归因规则是口径的一部分，并说明用 ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY register_date) 取首/末条去重。
- **转化率分母要不要限定观察窗口（如注册后30天内开户）？** 要点：不限窗口会把半年后才回流的用户算进当期漏斗，高估当期转化；限定窗口则低估长决策链渠道。银行开户多为即期行为，通常取注册后30/60天窗口，并把口径写进报表注释。
- **如果注册表和开户表都是十亿级，怎么改？** 要点：分区裁剪（按注册日期）、连接键先去重预聚合（先 user 级打标落临时表再JOIN）、避免 JOIN 后再去重，可提 Spark 广播小表优化。

### 7. 业务拓展思考
这条漏斗是零售条线所有"获客-激活"分析的母版：把"开户"替换为"首笔理财申购"就是财富条线激活漏斗，替换为"首次支用额度"就是信贷转化漏斗。结论可直接联动动作——渠道层转化率低砍投放、实名环节流失推流程优化、正常户率低反馈风控策略。口径上还可延展为"渠道×城市层级"的二维漏斗，或引入"注册到开户间隔天数中位数"衡量渠道质量而不只是数量。

## FIN-17 信用卡分期通过率的渠道×客群交叉分析

### 1. 业务背景
信用卡中心风险政策团队每季度要输出分期业务的"渠道×客群"通过率矩阵：电销、App弹窗、电子账单三大进件渠道，面对青年客群、工薪客群、高净值客群的审批通过率差异很大。审批策略团队据此决定哪些渠道对哪些客群要收紧授信政策；渠道经理则关注通过率虚高但后期逾期偏高的组合需要回溯。月度经营例会上，这个矩阵是渠道经理与风险经理对齐"量与质平衡"的核心依据——渠道经理背件均核准金额与放款规模，风险经理背通过率与资产质量，一张矩阵让两个团队的对话有了共同语言。

### 2. 表结构说明
installment_application（信用卡分期申请表，一次申请一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| app_id | BIGINT | 申请流水号 |
| customer_id | BIGINT | 客户ID |
| apply_date | DATE | 申请日期 |
| channel | VARCHAR(32) | 进件渠道：telesales电销/app_push弹窗/ebill账单 |
| cust_segment | VARCHAR(32) | 客群分层：青年客群/工薪客群/高净值客群 |
| approve_result | TINYINT | 审批结果：1核准/0拒绝 |
| approve_amount | DECIMAL(14,2) | 核准分期金额（拒绝为0） |

示例数据：

| app_id | customer_id | apply_date | channel | cust_segment | approve_result | approve_amount |
|---|---|---|---|---|---|---|
| 70001 | 20011 | 2026-08-02 | telesales | 工薪客群 | 1 | 50000.00 |
| 70002 | 20012 | 2026-08-03 | app_push | 青年客群 | 0 | 0.00 |
| 70003 | 20013 | 2026-08-05 | ebill | 高净值客群 | 1 | 200000.00 |
| 70004 | 20014 | 2026-08-09 | app_push | 青年客群 | 1 | 30000.00 |
| 70005 | 20015 | 2026-08-11 | telesales | 青年客群 | 0 | 0.00 |

### 3. 解题思路
口径明确：通过率=核准笔数/申请笔数，用 AVG(approve_result) 对0/1型标记直接求均值最不易错；件均金额只对核准样本求均值。分析维度是"渠道×客群"两维交叉，输出既可以是长表（每行一个组合，便于筛选排序），也可以是行转列宽表（渠道为行、客群为列，便于例会展示）。**【面试高频】** 小样本组合（如某渠道青年客群只来了8笔申请）通过率波动极大，必须用 HAVING 设置样本量门槛再谈通过率，这是面试官反复设置的陷阱。易错点还有：拒绝件的 approve_amount=0 会拉低件均金额，求均值前要用 IF 过滤；时间范围过滤要先于聚合下推。

### 4. 参考解法

**解法一：长表条件聚合 + RANK 窗口定位最差组合**

```sql
WITH seg_stat AS (                      -- 第一层：渠道×客群粒度聚合
    SELECT
        channel,                                                    -- 进件渠道
        cust_segment,                                               -- 客群分层
        COUNT(*)                          AS 申请笔数,
        SUM(approve_result)               AS 核准笔数,               -- 0/1直接求和即计数
        ROUND(AVG(approve_result) * 100, 2) AS 通过率,              -- 0/1的均值就是通过率
        ROUND(SUM(IF(approve_result = 1, approve_amount, 0))
              / NULLIF(SUM(approve_result), 0), 2)  AS 件均核准金额    -- 只对核准件求均值，拒绝件排除
    FROM installment_application
    WHERE apply_date >= '2026-08-01'        -- 限定统计区间，先过滤再聚合
    GROUP BY channel, cust_segment
    HAVING COUNT(*) >= 50                   -- 样本量门槛：小于50笔的组合不进榜
)
SELECT
    *,
    RANK() OVER (ORDER BY 通过率 ASC)       AS 通过率排名     -- 全局升序，最差组合排最前
FROM seg_stat
ORDER BY 通过率 ASC;
```

结果解读：通过率最低的组合并不一定是坏渠道——若件均金额高，可能是政策有意收紧大额进件；必须结合件均核准金额与放款后逾期率一起读，单看一个指标都会误判。

**解法二：行转列宽表（渠道为行、客群为列），直接可用于例会汇报**

```sql
SELECT
    channel                                                AS 渠道,
    COUNT(*)                                               AS 总申请笔数,
    ROUND(AVG(CASE WHEN cust_segment = '青年客群'
                   THEN approve_result END) * 100, 2)      AS 青年客群通过率,   -- CASE不匹配返回NULL，AVG自动忽略
    ROUND(AVG(CASE WHEN cust_segment = '工薪客群'
                   THEN approve_result END) * 100, 2)      AS 工薪客群通过率,
    ROUND(AVG(CASE WHEN cust_segment = '高净值客群'
                   THEN approve_result END) * 100, 2)      AS 高净值客群通过率,
    ROUND(AVG(approve_result) * 100, 2)                    AS 整体通过率        -- 不分客群的全渠道对照列
FROM installment_application
WHERE apply_date >= '2026-08-01'
GROUP BY channel;
```

结果解读：宽表一眼能看出"同一客群跨渠道"与"同一渠道跨客群"两个方向的差异，通常高净值客群通过率最高、青年客群在电销渠道被拒最多，这与收入核验难度的业务直觉一致。

### 5. 性能分析与优化
两解法都是单表一次扫描加聚合，代价差异极小：解法一按渠道×客群分组，中间结果行数等于组合数；解法二按渠道分组但每行要做三次 CASE 判断，CPU 略高。优化建议：① WHERE apply_date 走分区裁剪或 (apply_date, channel) 复合索引；② 客群分层若由客户表计算而来，应提前物化为申请表的冗余字段，避免查询时再 JOIN 客户宽表；③ 固定月报建议按"日×渠道×客群"增量聚合落中间表，例会查询只读结果表；④ 若加 RANK 排序，组合数通常只有个位数到几十个，排序代价可忽略。

### 6. 面试延伸考点
- **通过率高就代表渠道质量好吗？** 要点：要通过率×件均金额×放款后逾期率三个指标联合判断；可顺势提"审批后表现回溯"（见FIN-21的vintage逾期率），体现风险口径闭环意识。
- **如果要按月看各渠道通过率趋势怎么写？** 要点：GROUP BY 月份+渠道，或用窗口 LAG 计算环比变化；补一句"趋势比截面更能暴露策略调整的影响"即可加分。
- **approve_result 存的是'核准'/'拒绝'/'取消'三种字符串怎么改写？** 要点：先明确取消件是否计入分母（口径问题），再写 SUM(CASE WHEN approve_result='核准' THEN 1 ELSE 0 END) / NULLIF(COUNT(*),0)，体现对脏口径的敏感度。

### 7. 业务拓展思考
通过率矩阵是差异化授信政策的起点：对高通过×高逾期的组合收紧额度，对低通过×低逾期的优质组合放宽准入或提高预授信额度，直接创造营收。口径延展上，可加入"自动审批通过率 vs 转人工通过率"拆分衡量策略引擎效率；运营侧可联动"被拒客户再营销白名单"——被拒但评分临界的客户在补齐收入证明后二次进件的挽回率，往往能贡献可观的增量放款。

## FIN-18 客户AUM分组排名与TOP10%客户资产占比

### 1. 业务背景
财富管理条线的核心经营指标是AUM（管理客户资产总额），而"二八效应"的量化版本——TOP10%客户贡献了多少比例资产——直接决定零售条线的服务资源配置：私人银行中心建在哪里、客户经理人力怎么分、哪些临界客户（离TOP10%门槛一步之遥）值得重点提升。财富管理部的季度经营分析需要分析师给出：全体客户的AUM十分位分组、每组户数与资产占比、TOP10%客户的资产集中度，以及组间户均资产的悬殊程度，为"分层经营"策略提供数据底座，并向管理层解释为什么预算要向头部倾斜。

### 2. 表结构说明
holdings（客户资产持仓表，客户×产品粒度，月末快照）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| product_type | VARCHAR(32) | 产品类型：存款/理财/基金/保险/贵金属 |
| market_value | DECIMAL(16,2) | 期末市值 |
| as_of_date | DATE | 快照日期 |

示例数据：

| customer_id | product_type | market_value | as_of_date |
|---|---|---|---|
| 30001 | 存款 | 85000.00 | 2026-09-30 |
| 30001 | 理财 | 320000.00 | 2026-09-30 |
| 30002 | 存款 | 12000.00 | 2026-09-30 |
| 30003 | 基金 | 1500000.00 | 2026-09-30 |
| 30004 | 理财 | 680000.00 | 2026-09-30 |

### 3. 解题思路
口径先行：AUM=客户名下所有产品期末市值之和，必须在客户粒度先聚合；"TOP10%"是按客户数取前10%，不是按金额切分，两者含义完全不同。实现路径：第一步CTE把持仓聚合到客户级AUM；第二步用窗口函数做分位——NTILE(10)按AUM降序切成十组（第1组即Top10%），或用 ROW_NUMBER 配合 COUNT(*) OVER () 动态算出前10%的排名阈值；第三步对Top组求资产占比（SUM(aum)/全体SUM(aum)）。**【加分点】** 主动指出 NTILE 与 ROW_NUMBER+CEIL 在客户总数不能被10整除时的边界差异，并说明聚合窗口 SUM(aum) OVER () 在分布式引擎下会把数据拉到单节点，是性能面试的隐藏考点。

### 4. 参考解法

**解法一：NTILE 十分位分组 + 组级汇总（最直观的分位写法）**

```sql
WITH cust_aum AS (                      -- 第一层：客户粒度AUM
    SELECT customer_id, SUM(market_value) AS aum
    FROM holdings
    WHERE as_of_date = '2026-09-30'     -- 月末快照日，保证口径唯一
    GROUP BY customer_id
),
decile AS (                             -- 第二层：按AUM降序切十分位
    SELECT
        customer_id,
        aum,
        NTILE(10) OVER (ORDER BY aum DESC) AS decile,   -- 1=Top10% ... 10=Bottom10%
        SUM(aum) OVER () AS total_aum                   -- 聚合窗口：全体客户总资产
    FROM cust_aum
)
SELECT
    decile                                              AS 资产十分位,
    CONCAT('D', decile)                                 AS 分组标签,
    COUNT(*)                                            AS 客户数,
    ROUND(SUM(aum), 2)                                  AS 组内总资产,
    ROUND(SUM(aum) * 100.0 / MAX(total_aum), 2)         AS 资产占比,     -- total_aum为组内常量，用MAX取出
    ROUND(AVG(aum), 2)                                  AS 户均AUM
FROM decile
GROUP BY decile
ORDER BY decile;
```

结果解读：D1组的资产占比通常在40%-60%之间，与D10组的户均资产差距可达三个数量级；把D2组（紧邻Top10%）单独标出来，就是下季度"临界客户提升"专项行动的客群。

**解法二：ROW_NUMBER + COUNT 动态阈值求Top10%占比（精确控制人数比例）**

```sql
WITH cust_aum AS (
    SELECT customer_id, SUM(market_value) AS aum
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
),
ranked AS (
    SELECT
        customer_id,
        aum,
        ROW_NUMBER() OVER (ORDER BY aum DESC) AS rn,    -- 资产降序排名
        COUNT(*) OVER ()                      AS total_cnt   -- 客户总数（聚合窗口）
    FROM cust_aum
)
SELECT
    COUNT(*)                                    AS top10客户数,
    ROUND(COUNT(*) * 100.0 / MAX(total_cnt), 2) AS 客户数占比,
    ROUND(SUM(aum) * 100.0
          / (SELECT SUM(aum) FROM cust_aum), 2) AS top10资产占比,   -- 标量子查询给分母，避免重复扫描歧义
    ROUND(MIN(aum), 2)                          AS top10门槛AUM    -- 第10%名客户的资产即分界线
FROM ranked
WHERE rn <= CEIL(total_cnt * 0.1);              -- 动态取前10%名；CEIL防止总数不足10人时取0人
```

结果解读：top10门槛AUM是业务上最有行动力的数字——客户经理按这条线筛出"差一点的客户"，配合理财转介就能把客户推过分位线，实现AUM与中收双升。

### 5. 性能分析与优化
两解法都要先做一次全量 GROUP BY（客户级聚合），窗口函数在此基础上多一次排序：NTILE 与 ROW_NUMBER 的排序代价相同，均为 O(N logN)。优化建议：① holdings 按 (as_of_date, customer_id) 建索引或按 as_of_date 分区，先裁剪快照日再聚合；② 客户数千万级时窗口排序内存压力大，可在 Spark 上先按 customer_id 聚合再重分区开窗，或预先生成月度客户AUM表；③ SUM(aum) OVER () 这类无分区聚合窗口在 Spark 中会把全量数据收进单个 partition，改用独立汇总 CTE 再 CROSS JOIN 更稳。

> Hive/Spark SQL 差异：Hive 支持 NTILE 与聚合窗口，但老版本 Hive 不支持 WHERE 中的标量子查询，需改为 CROSS JOIN 汇总子查询；Spark SQL 建议对 cust_aum 先 CACHE 再开窗，避免重复扫描同一CTE。

### 6. 面试延伸考点
- **NTILE(10) 和 ROW_NUMBER 取前10%有什么区别？** 要点：NTILE是等分组数，组内人数可能差1且组边界与"恰前10%"有偏差；ROW_NUMBER+CEIL是精确人数口径；数据量不能被10整除时两者结果不同，能主动说明即可加分。
- **AUM应不应该包含负债（如房贷欠款怎么处理）？** 要点：AUM是资产管理口径，负债走"金融资产减负债"的净金融资产口径；强调口径必须与财富条线对齐并全行统一，防止跨部门数字打架。
- **如何看Top10%占比的趋势而非单期截面？** 要点：按月快照循环计算或按月份分区开窗排名，输出集中度时间序列；趋势陡升提示客群分化加剧，可能伴随长尾客户流失。

### 7. 业务拓展思考
资产集中度是财富条线经营稳健度的体检表：占比过高说明收入依赖少数客户，市场波动时AUM回撤风险大；占比过低说明高净值经营能力不足。联动动作包括：对D2临界客群做理财到期承接提醒、对D1客户配置私行专属权益、对D9-D10长尾客户引导线上化以降低服务成本。口径可延展为"户均AUM中位数与均值对比"，中位数远低于均值即是长尾分布的直接证据，比占比更能说服管理层配置普惠客群资源。

## FIN-19 产品持有数分布与理财基金交叉持有分析

### 1. 业务背景
零售银行做"客群深耕"时绕不开两个问题：我的客户平均持有几类产品？持有理财的客户里有多少同时买了基金？前者衡量客户绑定深度（持有产品数≥2的客户流失率远低于单产品客户），后者是交叉销售的直接成果指标。财富条线在制定"基金进理财客群"专项营销计划前，需要分析师给出：全量客户的产品持有数分布（1类/2类/3类及以上各占多少）、理财与基金的交叉持有率、以及"持有存款但未持理财"的待转化客群规模——这份名单就是营销活动的底层输入，直接决定活动预算的盘子大小。

### 2. 表结构说明
holdings（客户产品持仓表，客户×产品粒度，月末快照）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| product_type | VARCHAR(32) | 产品类型：存款/理财/基金/保险 |
| market_value | DECIMAL(16,2) | 期末市值 |
| as_of_date | DATE | 快照日期 |

示例数据：

| customer_id | product_type | market_value | as_of_date |
|---|---|---|---|
| 40001 | 存款 | 50000.00 | 2026-09-30 |
| 40001 | 理财 | 200000.00 | 2026-09-30 |
| 40002 | 存款 | 30000.00 | 2026-09-30 |
| 40003 | 基金 | 120000.00 | 2026-09-30 |
| 40003 | 理财 | 80000.00 | 2026-09-30 |

### 3. 解题思路
先打标再统计是本题的关键结构：持仓表是客户×产品粒度，任何"客户持有什么"的判断都要先用 MAX(CASE WHEN ...) 或 MAX(product_type='理财') 把宽表压成客户级0/1标记，否则后续 JOIN 或聚合会产生重复计数。两个产出：一是持有数分布（COUNT(DISTINCT product_type) 后按数量分组，配聚合窗口算占比）；二是交叉矩阵（理财与基金的交叉持有率=同时持有两类的客户数除以指定分母）。**【避坑指南】** 交叉率分母用"全体客户"还是"持有理财客户"结论完全不同，必须先问业务目的；GROUP_CONCAT 匹配产品集合的写法在产品名有包含关系（如"理财"与"结构化理财"）时会误判，生产环境慎用。

### 4. 参考解法

**解法一：客户级0/1打标 + 布尔条件聚合求交叉持有率**

```sql
WITH cust_flag AS (                     -- 客户级产品持有标记（宽表化）
    SELECT
        customer_id,
        MAX(product_type = '理财')   AS has_licai,   -- MySQL布尔表达式返回1/0，MAX=是否持有
        MAX(product_type = '基金')   AS has_jj,
        MAX(product_type = '存款')   AS has_ck,
        COUNT(DISTINCT product_type) AS hold_cnt     -- 持有产品类别数
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
)
SELECT
    COUNT(*)                                   AS 客户数,
    SUM(has_licai)                             AS 持有理财客户数,
    SUM(has_jj)                                AS 持有基金客户数,
    SUM(has_licai AND has_jj)                  AS 双持有客户数,      -- AND结果仍为0/1，直接求和
    ROUND(AVG(has_licai AND has_jj) * 100, 2)  AS 全体交叉持有率,    -- 分母=全体客户
    ROUND(SUM(has_licai AND has_jj) * 100.0
          / NULLIF(SUM(has_licai), 0), 2)      AS 理财客群内基金渗透率,  -- 分母=理财客户，口径不同
    ROUND(AVG(hold_cnt), 2)                    AS 户均持有产品数
FROM cust_flag;
```

结果解读：理财客群内基金渗透率是"基金进理财客群"专项的基线值，专项上线后该指标的增量就是营销成果；全体交叉持有率则用于管理层层面的交叉销售能力披露，两个口径要并列披露防止误读。

**解法二：持有数分布 + GROUP_CONCAT 热门组合榜（长尾组合一目了然）**

```sql
-- 语句1：持有产品数分布
WITH cust_products AS (
    SELECT
        customer_id,
        COUNT(DISTINCT product_type) AS hold_cnt
    FROM holdings
    WHERE as_of_date = '2026-09-30'          -- 快照日过滤先行
    GROUP BY customer_id
)
SELECT
    hold_cnt                                     AS 持有产品数,
    COUNT(*)                                     AS 客户数,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS 占比   -- 窗口套聚合：全体客户作分母
FROM cust_products
GROUP BY hold_cnt
ORDER BY hold_cnt;

-- 语句2：热门持有组合TOP5（CTE作用域仅限单条语句，需随语句重复定义）
WITH cust_products AS (
    SELECT
        customer_id,
        GROUP_CONCAT(DISTINCT product_type
                     ORDER BY product_type SEPARATOR '+') AS combo  -- 产品集合拼成"存款+理财"
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
)
SELECT combo AS 持有组合, COUNT(*) AS 客户数
FROM cust_products
GROUP BY combo
ORDER BY COUNT(*) DESC
LIMIT 5;
```

结果解读：持有1类产品的客户占比若超过60%，说明交叉销售空间巨大；组合榜里"存款+理财"通常最多，"理财+基金"组合的客户数可与解法一的交叉持有率互相验证，两套口径对得上才敢上会。

### 5. 性能分析与优化
两解法都只需一次 holdings 扫描加一次客户级 GROUP BY，代价线性；解法二的 GROUP_CONCAT 会产生字符串拼接，分组基数（组合数）最高为 2^k 减1（k为产品类数），本例k=4只有15种组合代价可忽略，若用SKU级产品编号代替大类则组合数爆炸，必须先归并到大类。优化建议：① holdings 按 (as_of_date, customer_id) 建索引，快照日过滤先行；② 0/1打标结果可物化为月度客户产品标志宽表，供FIN-26渗透率矩阵等多场景复用；③ GROUP_CONCAT 默认1024字节上限，长集合需调大 group_concat_max_len 参数。

### 6. 面试延伸考点
- **交叉持有率的分母怎么选？** 要点：衡量全员交叉销售能力用全体客户，评估理财客群向上销售用理财客户数；面试时先问清业务目的，最好两个口径都给出并说明差异。
- **怎么找"持有存款但未持理财"的待转化名单？** 要点：WHERE has_ck=1 AND has_licai=0 输出 customer_id 清单，再按AUM和交易活跃度排序圈选优先级，体现"分析输出直连营销名单"的闭环意识。
- **GROUP_CONCAT 方案有什么坑？** 要点：产品名包含关系误匹配、group_concat_max_len 长度上限、集合内排序不稳定；更稳的替代是回到0/1打标或 COUNT(DISTINCT ...) 判断。

### 7. 业务拓展思考
持有数分布是客户生命周期管理的标尺：新客户普遍单产品，绑定到2-3类产品后留存率显著抬升，因此"首年新客第二产品渗透率"常被设为支行KPI。联动动作上，双持有率低的分行可复制高渗透分行的理财经理话术，基金渗透率低的理财客群定向推送基金定投体验金。口径延展：把"持有"升级为"活跃持有"（近6个月有该类产品交易），剔除僵尸持仓后交叉率更真实，也更能反映交叉销售的真实缺口。

## FIN-20 贷款申请-审批-授信-放款四环节漏斗及流失率

### 1. 业务背景
消费金融公司信贷运营部每月要向管理层汇报进件漏斗：本月新增贷款申请多少笔，多少通过审批，多少完成授信签约，多少最终放款成功。四个环节分别由不同团队负责——审批环节看风控策略通过率，授信签约环节看产品与法务流程（合同签署、绑卡验证），放款环节看支付通道成功率。漏斗各环节流失率要定位到环节责任人：审批流失率高要复盘策略松紧，签约流失高要优化合同流程，放款失败高要排查银行卡维护或支付渠道故障。这张漏斗表是信贷条线月度经营分析的第一张表，也是渠道进件质量评估的基准。

### 2. 表结构说明
loan_applications（贷款申请表，一次申请一行，状态时间戳法建模）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| apply_id | BIGINT | 申请单号 |
| customer_id | BIGINT | 客户ID |
| channel | VARCHAR(32) | 进件渠道：app/h5/telesales |
| apply_date | DATE | 申请日期 |
| approve_date | DATE | 审批通过日期（NULL=未通过/未审批） |
| credit_date | DATE | 授信签约日期（NULL=未签约） |
| disburse_date | DATE | 放款日期（NULL=未放款） |
| credit_limit | DECIMAL(14,2) | 授信额度 |
| disburse_amount | DECIMAL(14,2) | 放款金额 |

示例数据：

| apply_id | customer_id | channel | apply_date | approve_date | credit_date | disburse_date | credit_limit | disburse_amount |
|---|---|---|---|---|---|---|---|---|
| 80001 | 50011 | app | 2026-09-01 | 2026-09-01 | 2026-09-02 | 2026-09-02 | 80000.00 | 50000.00 |
| 80002 | 50012 | h5 | 2026-09-03 | NULL | NULL | NULL | 0.00 | 0.00 |
| 80003 | 50013 | app | 2026-09-05 | 2026-09-05 | NULL | NULL | 60000.00 | 0.00 |
| 80004 | 50014 | telesales | 2026-09-08 | 2026-09-09 | 2026-09-15 | NULL | 100000.00 | 0.00 |
| 80005 | 50015 | app | 2026-09-10 | 2026-09-10 | 2026-09-11 | 2026-09-12 | 50000.00 | 30000.00 |

### 3. 解题思路
状态时间戳法（一表多列记录各环节完成时间）是漏斗建模的主流方式，比状态机法（单列status流转）更利于SQL分析。口径要点：四层漏斗=申请→审批通过（approve_date非空）→完成签约（credit_date非空）→放款成功（disburse_date非空）；按申请月份（cohort）分组看，避免月末申请下月放款导致的口径漂移。**【面试高频】** "状态时间戳法与状态字段法怎么选"是信贷数据岗的经典追问。易错点：授信环节判定用 credit_date IS NOT NULL 而非 credit_limit>0（存在已批额度但未签约的中间态）；分母必须固定为申请笔数或上一环节笔数，混用会让各环节流失率加总不等于全链路流失率。

### 4. 参考解法

**解法一：按申请月cohort的条件聚合宽表（月度经营例会标准形态）**

```sql
SELECT
    DATE_FORMAT(apply_date, '%Y-%m')                            AS 申请月份,
    COUNT(*)                                                    AS 申请笔数,
    SUM(approve_date IS NOT NULL)                               AS 审批通过笔数,   -- 布尔表达式直接求和
    SUM(credit_date  IS NOT NULL)                               AS 签约笔数,
    SUM(disburse_date IS NOT NULL)                              AS 放款笔数,
    ROUND(SUM(approve_date IS NOT NULL) * 100.0 / COUNT(*), 2)  AS 审批通过率,
    ROUND(SUM(credit_date IS NOT NULL) * 100.0
          / NULLIF(SUM(approve_date IS NOT NULL), 0), 2)        AS 审批到签约率,   -- 逐级口径
    ROUND(SUM(disburse_date IS NOT NULL) * 100.0
          / NULLIF(SUM(credit_date IS NOT NULL), 0), 2)         AS 签约到放款率,   -- 逐级口径
    ROUND(SUM(disburse_amount) * 100.0
          / NULLIF(SUM(credit_limit), 0), 2)                    AS 额度支用率      -- 金额口径补充指标
FROM loan_applications
GROUP BY DATE_FORMAT(apply_date, '%Y-%m')
ORDER BY 申请月份;
```

结果解读：三个逐级转化率连乘即全链路放款率；额度支用率低说明"批了不用"，这部分客户是唤醒营销的机会客群，额度有效期内推送利率券常有立竿见影的效果。

**解法二：UNION ALL 竖表 + LAG，通用漏斗框架（环节可插拔、可带渠道维度）**

```sql
WITH step_cnt AS (                      -- 每个环节一行：渠道×环节×笔数
    SELECT channel, '1_申请' AS step, COUNT(*) AS cnt
    FROM loan_applications
    WHERE apply_date >= '2026-09-01'
    GROUP BY channel
    UNION ALL
    SELECT channel, '2_审批通过', COUNT(*)
    FROM loan_applications
    WHERE apply_date >= '2026-09-01' AND approve_date IS NOT NULL
    GROUP BY channel
    UNION ALL
    SELECT channel, '3_完成签约', COUNT(*)
    FROM loan_applications
    WHERE apply_date >= '2026-09-01' AND credit_date IS NOT NULL
    GROUP BY channel
    UNION ALL
    SELECT channel, '4_放款成功', COUNT(*)
    FROM loan_applications
    WHERE apply_date >= '2026-09-01' AND disburse_date IS NOT NULL
    GROUP BY channel
)
SELECT
    channel                                             AS 渠道,
    step                                                AS 环节,
    cnt                                                 AS 笔数,
    ROUND(cnt * 100.0 / LAG(cnt) OVER (
              PARTITION BY channel ORDER BY step), 2)   AS 逐级转化率,
    ROUND(100.0 - COALESCE(ROUND(cnt * 100.0 / LAG(cnt) OVER (
              PARTITION BY channel ORDER BY step), 2), 100), 2)
                                                        AS 环节流失率   -- 100减转化率；首环节无上游记0
FROM step_cnt
ORDER BY channel, step;
```

结果解读：流失率把"少的部分"直接呈现给对应环节负责人；带渠道维度后可定位"哪个渠道在哪个环节漏得最多"，例如电销渠道常见签约流失偏高，因为客户被动进件、意愿弱，需要话术与产品设计双管齐下。

### 5. 性能分析与优化
解法一单次全表扫描加一次聚合，最优；解法二扫描表4次（每个 UNION 分支一次），代价约为解法一的4倍，但分支可并行（Spark 天然并行，MySQL 需靠硬件余量）。优化建议：① 四个分支的过滤条件是层层包含关系，可改为一次扫描用条件聚合输出"渠道×环节"竖表再 LAG，兼顾两者优点；② apply_date 与 (apply_date, approve_date) 建索引支持分区裁剪；③ 月度报表建议按申请月预聚合落表，漏斗层只做比率计算；④ 时间戳列全部建索引意义不大（NULL多、选择性低），分析型查询优先考虑分区而非索引。

### 6. 面试延伸考点
- **状态时间戳法和状态字段法（status列）各有什么优劣？** 要点：时间戳法天然支持漏斗与时延分析（如审批耗时 DATEDIFF），状态法省存储但只能看当前态、无法回溯历史漏斗；成熟数仓常两者兼存，能主动说出这一点即是加分。
- **审批通过但没有签约的客户，还算流失吗？** 要点：算，且是"可挽回流失"——额度已批、只差签约动作，运营挽回成本最低；可提"签约流失客户7日回访名单"的运营用法。
- **如何计算每个环节的平均耗时？** 要点：AVG(DATEDIFF(credit_date, approve_date))，配合中位数（ROW_NUMBER 取中间值）防极端值误导；耗时突增往往对应流程改造或系统故障。

### 7. 业务拓展思考
四环节漏斗向上接渠道获客成本（CPA）就是"放款件均成本"——管理层最关心的单位经济模型；向下接 FIN-21 的 vintage 逾期率，构成"量-质"闭环：通过率放宽带来的增量放款，要用来期 vintage 验证是否稀释了资产质量。运营联动：签约环节流失客户推送"签约立减利率券"，放款环节失败客户自动触发换卡引导与客服外呼。口径延展：把放款金额替换为"首期还款金额"可评估净投放，剔除提前结清对投放规模的干扰。
## FIN-21 按放款月份的账龄逾期率（vintage入门）

### 1. 业务背景
风险政策团队评审"是否收紧某渠道准入"时，最忌讳用单期逾期率下结论——因为近期放款的贷款还没来得及暴露风险。vintage分析把不同放款月的贷款分开跟踪：每笔贷款放款后第N个月（MOB，Month on Book）处于逾期30天以上的比例，画成一张"放款月×账龄"的矩阵，曲线越早翘头的放款月风险越差。信贷部用这张表判断：某渠道收紧策略上线后，新放款vintage是否真的变好；财务部用它计提拨备；它也是信贷风控数据分析岗面试中出现频率最高的口径题，答不好会直接暴露风控数据功底不足。

### 2. 表结构说明
loans（放款主表，一笔放款一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | BIGINT | 贷款单号 |
| customer_id | BIGINT | 客户ID |
| disburse_date | DATE | 放款日期 |
| loan_amount | DECIMAL(14,2) | 放款金额 |

示例数据：

| loan_id | customer_id | disburse_date | loan_amount |
|---|---|---|---|
| 60001 | 70001 | 2025-01-10 | 20000.00 |
| 60002 | 70002 | 2025-01-25 | 15000.00 |
| 60003 | 70003 | 2025-02-08 | 30000.00 |
| 60004 | 70004 | 2025-02-20 | 12000.00 |
| 60005 | 70005 | 2025-03-05 | 25000.00 |

repayment_snapshot（每月末贷款状态快照，贷款×账期一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | BIGINT | 贷款单号 |
| stat_month | DATE | 账期（当月月末日期） |
| balance | DECIMAL(14,2) | 期末剩余本金 |
| overdue_days | INT | 期末逾期天数 |

示例数据：

| loan_id | stat_month | balance | overdue_days |
|---|---|---|---|
| 60001 | 2025-02-28 | 18500.00 | 0 |
| 60001 | 2025-05-31 | 17000.00 | 35 |
| 60002 | 2025-02-28 | 14500.00 | 0 |
| 60003 | 2025-04-30 | 28500.00 | 62 |
| 60005 | 2025-06-30 | 23000.00 | 0 |

### 3. 解题思路
vintage三要素：cohort（放款月）、MOB（观察月减放款月的自然月差）、表现指标（逾期30+的金额或户数占比）。口径决定一切：金额口径的vintage分子应为"该放款月贷款在MOB=N时逾期30+的当期剩余本金"，分母固定为"该放款月放款总额"，两者必须同源对齐。实现路径：先把主表与快照表按 loan_id 连接并算出 MOB（PERIOD_DIFF 按自然月差），再按放款月×MOB聚合出长表，最后行转列成矩阵。**【面试高频】** "vintage分母为什么用放款金额而不是在贷余额"几乎必问。易错点：MOB必须按自然月对齐（1月25日放款，2月末观察即MOB=1，不能按30天折算）；表现期未到的格子要留空而不是填0；放款总额要单独去重聚合，直接在JOIN结果里SUM会随快照行数翻倍。

### 4. 参考解法

**解法一：宽表矩阵版——行转列直接输出vintage矩阵（适合汇报展示）**

```sql
WITH loan_mob AS (                      -- 每笔贷款在每个账期的逾期标记
    SELECT
        l.loan_id,
        DATE_FORMAT(l.disburse_date, '%Y-%m') AS 放款月,
        PERIOD_DIFF(DATE_FORMAT(s.stat_month, '%Y%m'),
                    DATE_FORMAT(l.disburse_date, '%Y%m')) AS mob,   -- 自然月差即账龄MOB
        (s.overdue_days >= 30)          AS is_m2,                       -- 是否逾期30天以上（0/1）
        s.balance                                                       -- 当期剩余本金
    FROM loans l
    JOIN repayment_snapshot s ON s.loan_id = l.loan_id
    WHERE l.disburse_date >= '2025-01-01'
),
amt AS (                                -- 各放款月的放款总额（独立聚合，防止JOIN后重复求和）
    SELECT DATE_FORMAT(disburse_date, '%Y-%m') AS 放款月,
           SUM(loan_amount) AS 放款总额
    FROM loans
    WHERE disburse_date >= '2025-01-01'
    GROUP BY DATE_FORMAT(disburse_date, '%Y-%m')
)
SELECT
    a.放款月,
    a.放款总额,
    ROUND(SUM(CASE WHEN mob = 3  THEN IF(is_m2, b.balance, 0) END)
          / NULLIF(a.放款总额, 0) * 100, 2)  AS MOB3逾期率,    -- 分子=逾期贷款当期剩余本金
    ROUND(SUM(CASE WHEN mob = 6  THEN IF(is_m2, b.balance, 0) END)
          / NULLIF(a.放款总额, 0) * 100, 2)  AS MOB6逾期率,
    ROUND(SUM(CASE WHEN mob = 9  THEN IF(is_m2, b.balance, 0) END)
          / NULLIF(a.放款总额, 0) * 100, 2)  AS MOB9逾期率,
    ROUND(SUM(CASE WHEN mob = 12 THEN IF(is_m2, b.balance, 0) END)
          / NULLIF(a.放款总额, 0) * 100, 2)  AS MOB12逾期率    -- 表现期未到的cohort该格为NULL而非0
FROM amt a
LEFT JOIN loan_mob b ON b.放款月 = a.放款月
GROUP BY a.放款月, a.放款总额
ORDER BY a.放款月;
```

结果解读：矩阵中同一MOB列纵向对比是"同账龄跨cohort"比较，横向看单个cohort曲线的翘头速度；若新cohort在MOB3就超过老cohort的MOB6水平，即是准入策略恶化的强信号。

**解法二：长表版（放款月×MOB逐格输出，通用且便于接BI热力图）**

```sql
WITH loan_mob AS (                      -- 与解法一相同的贷款×账期粒度底表
    SELECT
        l.loan_id,
        DATE_FORMAT(l.disburse_date, '%Y-%m') AS 放款月,
        PERIOD_DIFF(DATE_FORMAT(s.stat_month, '%Y%m'),
                    DATE_FORMAT(l.disburse_date, '%Y%m')) AS mob,
        (s.overdue_days >= 30)          AS is_m2,
        s.balance
    FROM loans l
    JOIN repayment_snapshot s ON s.loan_id = l.loan_id
    WHERE l.disburse_date >= '2025-01-01'
),
amt AS (
    SELECT DATE_FORMAT(disburse_date, '%Y-%m') AS 放款月,
           SUM(loan_amount) AS 放款总额
    FROM loans
    WHERE disburse_date >= '2025-01-01'
    GROUP BY DATE_FORMAT(disburse_date, '%Y-%m')
),
long_vintage AS (                       -- 长表聚合：每个cohort×MOB一格
    SELECT
        放款月,
        mob,
        COUNT(DISTINCT loan_id)         AS 在贷笔数,
        SUM(is_m2)                      AS 逾期笔数,
        SUM(IF(is_m2, balance, 0))      AS 逾期余额
    FROM loan_mob
    GROUP BY 放款月, mob
)
SELECT
    v.放款月,
    v.mob                               AS 账龄MOB,
    ROUND(v.逾期余额 * 100.0 / NULLIF(a.放款总额, 0), 2) AS vintage逾期率_金额口径,  -- 分母=放款额
    ROUND(v.逾期笔数 * 100.0 / NULLIF(v.在贷笔数, 0), 2) AS 逾期率_当期在贷户数口径        -- 分母=在贷笔数
FROM long_vintage v
JOIN amt a ON a.放款月 = v.放款月
ORDER BY v.放款月, v.mob;
```

结果解读：长表同时给出两种口径便于对照——vintage口径（分母=放款额）用于跨cohort比较风险暴露，当期在贷口径（分母=在贷余额）用于观察存量资产质量，用途不同不可混用。

### 5. 性能分析与优化
两表JOIN（loans×snapshot）是主要代价：快照表按贷款×月份增长，一笔一年期贷款即12行，亿级放款×24个月即数百亿行，必须依赖分区与预聚合。优化建议：① snapshot 按 stat_month 分区，查询限定 MOB 上限时先做账期分区裁剪；② loans 按 disburse_date 分区，cohort 过滤下推；③ 把"放款月×MOB×逾期余额"粒度的结果先落汇总表（日调度增量），报表层直接查汇总表，这是生产环境的标准做法；④ MySQL 中 JOIN 键 loan_id、(stat_month, loan_id) 建索引。

> Hive/Spark SQL 差异：百亿行快照务必在 Spark 上跑；Hive 无 PERIOD_DIFF，改用 months_between(stat_month, disburse_date) 取整；大表JOIN建议先按放款月过滤再JOIN，或对两表按 loan_id 分桶（bucketing）避免 shuffle。

### 6. 面试延伸考点
- **vintage逾期率的分母为什么用放款金额而不是在贷余额？** 要点：放款额固定，cohort间可比；在贷余额随还款递减且受提前结清影响，会把"还得好"误判成"风险低"；两种口径都存在但用途不同——vintage看风险暴露过程，余额逾期率看当期资产质量。
- **MOB从0还是1起算？逾期30+还是M2+？** 要点：业内常用口径必须固定并在报表标注，如M2+（逾期30天以上）、MOB按放款次月末起算；面试主动声明假设比答案本身更重要。
- **表现期不足的cohort怎么处理？** 要点：矩阵中MOB未到的格子留空（NULL）而不是填0，否则会严重低估近期cohort风险；报表上用灰色或NA标识，并把最长可用MOB标注出来。

### 7. 业务拓展思考
vintage是信贷风控的"时光机"：准入策略调整、催收资源变化、宏观波动都会在曲线形态上留痕。联动动作：新cohort翘头即触发渠道准入复核与额度策略回调；M2+余额率环比抬升推动催收分段外包与拨备重估。口径延展：从"逾期30+金额"扩展到"首逾率（首期还款即逾期）"衡量欺诈风险，形成FPD30 vintage与信用风险vintage两条观察线；也可按渠道、产品、额度档拆分vintage，定位风险的维度来源。

## FIN-22 理财客户与纯存款客户的AUM与活跃对比

### 1. 业务背景
零售银行数字化转型的核心命题是"存款客户财富化迁移"：只存存款的客户贡献低价负债但粘性弱、易被他行高息存款挖走；持有理财的客户AUM高、中收贡献大、留存率显著更好。零售条线总经理在年度策略会上需要一张对比表：理财客户与纯存款客户在户均AUM、月交易活跃度上的差距到底有多大，以此论证投入理财经理人力与投资者教育预算的必要性；同时"纯存款且AUM达标"的客户规模，就是下季度财富转化的目标盘子，直接决定专项营销的预算与人力安排。

### 2. 表结构说明
holdings（客户产品持仓表，客户×产品粒度，月末快照）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| product_type | VARCHAR(32) | 产品类型：存款/理财/基金/保险 |
| market_value | DECIMAL(16,2) | 期末市值 |
| as_of_date | DATE | 快照日期 |

示例数据：

| customer_id | product_type | market_value | as_of_date |
|---|---|---|---|
| 40001 | 存款 | 50000.00 | 2026-09-30 |
| 40001 | 理财 | 200000.00 | 2026-09-30 |
| 40002 | 存款 | 30000.00 | 2026-09-30 |
| 40004 | 存款 | 600000.00 | 2026-09-30 |
| 40005 | 理财 | 150000.00 | 2026-09-30 |

transactions（交易流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| product_type | VARCHAR(32) | 交易产品：存款/理财/基金（NULL=非产品交易） |
| amount | DECIMAL(14,2) | 交易金额 |

示例数据：

| txn_id | customer_id | trade_date | product_type | amount |
|---|---|---|---|---|
| 100001 | 40001 | 2026-09-02 | 理财 | 50000.00 |
| 100002 | 40002 | 2026-09-05 | 存款 | 10000.00 |
| 100003 | 40004 | 2026-08-15 | 存款 | 200000.00 |
| 100004 | 40001 | 2026-09-20 | 存款 | 2000.00 |
| 100005 | 40005 | 2026-09-18 | 理财 | 30000.00 |

### 3. 解题思路
口径先行：客群定义要有互斥边界——理财客户=持有理财（不论是否持其他产品），纯存款客户=只持有存款、无理财也无基金；剩下的归"其他客户"，三类必须互斥且完备。指标两个：户均AUM（持仓快照聚合）、户均近30天交易次数（流水聚合），两表粒度不同必须分别预聚合到客户级再JOIN，这是本题最核心的结构考点。**【避坑指南】** 直接 holdings JOIN transactions 会让AUM随交易笔数翻倍；纯存款判断必须"无理财且无基金且有存款"三个条件齐全，漏掉基金条件会把基金客误划进纯存款；未交易客户要用 IFNULL 补0再求均值，否则活跃均值只反映交易客户。

### 4. 参考解法

**解法一：双CTE预聚合 + 客群CASE互斥分类（标准分层写法）**

```sql
WITH cust_aum AS (                      -- 客户级持仓打标与AUM
    SELECT
        customer_id,
        SUM(market_value)          AS aum,
        MAX(product_type = '理财') AS has_licai,     -- 布尔转0/1标记
        MAX(product_type = '基金') AS has_jj,
        MAX(product_type = '存款') AS has_ck
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
),
cust_type AS (                          -- 客群互斥分类：顺序决定优先级
    SELECT
        customer_id,
        aum,
        CASE
            WHEN has_licai = 1 THEN '理财客户'
            WHEN has_licai = 0 AND has_jj = 0 AND has_ck = 1 THEN '纯存款客户'
            ELSE '其他客户'
        END AS 客群
    FROM cust_aum
),
act AS (                                -- 客户级近30天交易计数
    SELECT customer_id, COUNT(*) AS txn_cnt_30d
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 30 DAY)
    GROUP BY customer_id
)
SELECT
    t.客群,
    COUNT(*)                                AS 客户数,
    ROUND(AVG(t.aum), 2)                    AS 户均AUM,
    ROUND(AVG(IFNULL(a.txn_cnt_30d, 0)), 2) AS 户均近30天交易次数,   -- 未交易客户计0
    ROUND(SUM(IFNULL(a.txn_cnt_30d, 0) > 0) * 100.0 / COUNT(*), 2) AS 交易活跃率
FROM cust_type t
LEFT JOIN act a ON a.customer_id = t.customer_id
WHERE t.客群 IN ('理财客户', '纯存款客户')      -- 聚焦两类对比，其他客户单独分析
GROUP BY t.客群;
```

结果解读：理财客户户均AUM通常是纯存款客户的3-5倍、活跃率高出一截，这组对比是"财富转型"汇报的核心论据；交易活跃率同时暴露纯存款客群的睡眠户比例，是激活活动的基线。

**解法二：GROUP_CONCAT 集合匹配分类（少一层CASE，写法轻巧但有边界）**

```sql
WITH cust_prod AS (                     -- 把每个客户持有的产品集合压成字符串
    SELECT
        customer_id,
        GROUP_CONCAT(DISTINCT product_type ORDER BY product_type) AS prod_set,
        SUM(market_value) AS aum
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
),
act AS (
    SELECT customer_id, COUNT(*) AS txn_cnt_30d
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 30 DAY)
    GROUP BY customer_id
)
SELECT
    CASE
        WHEN prod_set LIKE '%理财%' THEN '理财客户'
        WHEN prod_set = '存款'      THEN '纯存款客户'   -- 集合恰只有一个元素才算"纯"
        ELSE '其他客户'
    END AS 客群,
    COUNT(*)                                AS 客户数,
    ROUND(AVG(c.aum), 2)                    AS 户均AUM,
    ROUND(AVG(IFNULL(a.txn_cnt_30d, 0)), 2) AS 户均近30天交易次数
FROM cust_prod c
LEFT JOIN act a ON a.customer_id = c.customer_id
GROUP BY 客群
ORDER BY 户均AUM DESC;
```

结果解读：三客群全量对比后，"其他客户"（持基金或保险但无理财）往往是最好的理财转化候选，因其风险偏好已被验证；集合匹配写法在产品名存在包含关系时会误判（如"理财"匹配"结构化理财"），生产环境更推荐解法一的显式打标。

### 5. 性能分析与优化
两解法结构相同：holdings 一次聚合、transactions 一次聚合、客户级 JOIN，代价线性于两表行数。优化建议：① transactions 按 trade_date 分区，30天窗口先裁剪；② holdings 快照日过滤走 (as_of_date, customer_id) 索引；③ 客群标签（理财/纯存款/其他）建议物化为客户标签宽表字段，供FIN-26、FIN-30复用，避免每张报表重算；④ 大表JOIN前先把 act 限制在目标客群内（先过滤 cust_type 再JOIN），减少JOIN行数。

### 6. 面试延伸考点
- **"理财客户"要不要区分"活跃理财客户"？** 要点：持仓不等于活跃，可叠加"近90天有理财申购或赎回"条件；主动区分存量口径与动量口径是加分项。
- **AUM对比用均值还是中位数？** 要点：AUM右偏严重，均值会被大户拉高，建议同时给中位数；可用 ROW_NUMBER 排序取中间行求中位数，并说明MySQL 8.0无内置 PERCENTILE_CONT。
- **纯存款客户里如何圈出高优先转化名单？** 要点：AUM超过理财起购门槛若干倍＋近期交易活跃＋存款到期临近，多条件打分排序输出TOP清单，体现从分析到名单的闭环。

### 7. 业务拓展思考
这组对比的价值在于把"财富转型"从口号变成可量化、可追踪的迁移工程：目标客群规模×预期转化率×客均AUM增量=季度中收机会测算，预算申请就有了依据。联动动作包括理财体验金投放、存款到期承接外呼、基金客向理财的升级路径设计。口径延展：可按AUM分层（如10-50万/50-100万）交叉客群，识别"高存款低理财"的错配富矿；也可引入时间维度做客群迁移矩阵（上月纯存款、本月购买理财的流转率），衡量迁移工程的真实速度。

## FIN-23 客户开户到首笔交易的平均间隔天数

### 1. 业务背景
新客经营团队把开户后30天内是否发生首笔交易称为"激活"，激活客户的次月留存与AUM增长远好于未激活客户，因此"开户到首笔交易的间隔天数"是衡量获客质量与新客运营效率的第一指标。渠道经理用它复盘：应用商店渠道用户平均3天激活，而异业合作渠道平均21天——后者的补贴ROI必须重算。月度新客经营会需要的是：分开户月份的平均激活天数、7日内激活率、以及未激活客户的规模，作为新客触达节奏（T+1、T+7、T+30三个波次）设计的依据，波次资源按激活漏斗的衰减速度分配。

### 2. 表结构说明
customers（客户主表，一人一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| open_date | DATE | 开户日期 |
| cust_level | VARCHAR(16) | 客户等级：普通/金卡/白金 |

示例数据：

| customer_id | open_date | cust_level |
|---|---|---|
| 80001 | 2026-06-01 | 普通 |
| 80002 | 2026-06-03 | 普通 |
| 80003 | 2026-06-10 | 金卡 |
| 80004 | 2026-06-15 | 普通 |
| 80005 | 2026-06-20 | 白金 |

transactions（交易流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| amount | DECIMAL(14,2) | 交易金额 |

示例数据：

| txn_id | customer_id | trade_date | amount |
|---|---|---|---|
| 200001 | 80001 | 2026-06-02 | 500.00 |
| 200002 | 80001 | 2026-07-10 | 1200.00 |
| 200003 | 80003 | 2026-06-25 | 8000.00 |
| 200004 | 80005 | 2026-06-20 | 300.00 |
| 200005 | 80004 | 2026-08-01 | 100.00 |

### 3. 解题思路
口径先行：间隔天数=DATEDIFF(首笔交易日, 开户日)，且只承认开户日之后的交易（含当日，当日交易算0天）；"平均激活天数"只在已激活客户上计算，未激活客户单独统计占比，混在一起会拉低均值且语义混乱。实现路径两条：一是客户表左连流水（连接条件限定开户后）再聚合出首笔；二是先聚合每客户首笔交易日期再JOIN回客户表。**【加分点】** 主动指出"上月开户cohort激活率随观察截止日推移会天然上升"的表现期不足问题——这与vintage口径同源，能跨题迁移的候选人非常出彩。易错点：忘记过滤开户前的历史交易（换卡重开客户）；LEFT JOIN 后未激活客户间隔为NULL，AVG 自动忽略但 COUNT 不会，两个指标的分子分母要分开处理。

### 4. 参考解法

**解法一：左连流水限制开户后交易 + 条件聚合（分母完整，能算未激活占比）**

```sql
WITH first_txn AS (                     -- 每位客户在"开户后"的首笔交易日期
    SELECT
        c.customer_id,
        c.open_date,
        MIN(t.trade_date) AS first_date             -- 只看开户后的交易，LEFT JOIN保住未激活客户
    FROM customers c
    LEFT JOIN transactions t
      ON t.customer_id = c.customer_id
     AND t.trade_date >= c.open_date                -- 口径：当日交易算激活，间隔0天
    GROUP BY c.customer_id, c.open_date
)
SELECT
    DATE_FORMAT(open_date, '%Y-%m')                     AS 开户月份,
    COUNT(*)                                            AS 开户客户数,   -- LEFT JOIN保证分母完整
    SUM(first_date IS NOT NULL)                         AS 激活客户数,
    ROUND(AVG(DATEDIFF(first_date, open_date)), 2)      AS 平均激活天数, -- NULL自动忽略，只对已激活求均值
    ROUND(SUM(DATEDIFF(first_date, open_date) <= 7) * 100.0
          / NULLIF(SUM(first_date IS NOT NULL), 0), 2)  AS 7日内激活率,  -- 分母=已激活客户
    ROUND(SUM(first_date IS NULL) * 100.0 / COUNT(*), 2) AS 未激活占比
FROM first_txn
GROUP BY DATE_FORMAT(open_date, '%Y-%m')
ORDER BY 开户月份;
```

结果解读：平均激活天数下降且7日激活率抬升，说明新客触达波次起效；未激活占比若超40%，问题通常出在开户后的产品引导页与权益发放，而非渠道本身质量。

**解法二：MIN() OVER 窗口直接在连接结果上取首笔（少一层GROUP BY，展示窗口功底）**

```sql
WITH joined AS (                        -- 只保留开户后的交易（含当日）
    SELECT
        c.customer_id,
        c.open_date,
        t.trade_date
    FROM customers c
    JOIN transactions t
      ON t.customer_id = c.customer_id
     AND t.trade_date >= c.open_date    -- 连接条件即口径过滤
),
first_flag AS (
    SELECT
        customer_id,
        open_date,
        MIN(trade_date) OVER (PARTITION BY customer_id) AS first_date   -- 聚合窗口：不改变行粒度
    FROM joined
),
per_cust AS (                           -- 关键一步：收敛到客户粒度，防止重复行污染AVG
    SELECT customer_id, open_date, first_date
    FROM first_flag
    GROUP BY customer_id, open_date, first_date
)
SELECT
    DATE_FORMAT(open_date, '%Y-%m')                     AS 开户月份,
    COUNT(*)                                            AS 激活客户数,   -- 内连接后只剩激活客户
    ROUND(AVG(DATEDIFF(first_date, open_date)), 2)      AS 平均激活天数,
    ROUND(AVG(DATEDIFF(first_date, open_date) <= 7) * 100, 2) AS 7日内激活率
FROM per_cust
GROUP BY DATE_FORMAT(open_date, '%Y-%m')
ORDER BY 开户月份;
```

结果解读：窗口函数不改变行粒度，同一客户的多笔交易会携带相同的 first_date，若不去重直接 AVG 会向交易笔数多的客户加权——这是窗口函数最经典的坑；本解法因内连接丢失未激活客户，适合只看激活客群的画像分析，与解法一互补。

### 5. 性能分析与优化
解法一以 customers 为主表左连 transactions，JOIN 行数约为客户数（每客户至多展开到其开户后首笔聚合前的流水行数），GROUP BY 在连接结果上完成；解法二先内连再开窗，窗口排序发生在连接后的宽结果上，交易多的客户会放大排序行数。优化建议：① customers(customer_id) 主键、transactions(customer_id, trade_date) 复合索引，让每客户的交易按日期有序读取；② 千万级流水建议把"客户首笔交易日期"做成日增量标签表（T+1更新），分析层直接取用；③ 求中位数激活天数时用窗口排序，且只对激活客户计算；④ 观察期按开户月份分区裁剪，避免全历史扫描。

### 6. 面试延伸考点
- **平均激活天数会被什么扭曲？中位数怎么求？** 要点：少数几个月才激活的客户拉高均值，建议报中位数；用 ROW_NUMBER 按间隔排序取中间行，或 PERCENT_RANK 定位；主动说明MySQL 8.0没有内置 PERCENTILE_CONT 是方言素养。
- **当日开户当日交易算0天还是1天？** 要点：口径题，通常算0天（当日激活），但必须全行统一并写进报表注释，体现"先对口径再动手"的职业习惯。
- **观察截止日对指标的影响？** 要点：越早的cohort激活天数越完整，近期cohort激活率被系统性低估——与vintage"表现期不足"同源，能跨题迁移的候选人非常加分。

### 7. 业务拓展思考
激活间隔是新客生命周期管理的起点指标：T+1未激活推首绑微信提醒，T+7推小额体验金，T+30未激活转入沉睡唤醒池，波次设计直接以间隔分位数曲线为依据。把指标从"均值"升级为"分渠道×分客群的分位数曲线"，能精确指导触达时点与内容。口径延展：把"首笔交易"按业务含义细分为"首笔消费/首笔理财/首笔代发"，不同激活定义对应不同条线的经营目标，同名指标必须挂口径标签，避免跨部门汇报时数字打架。

## FIN-24 连续3个月购买理财产品的客户识别

### 1. 业务背景
财富条线做客户培育时有个经典命题：连续性是忠诚度的前兆——连续3个月申购理财的客户，次年留存率与AUM增速远高于间断购买客户，因此"连续N月购买"客群是理财经理重点维护名单，也是"定投式理财"产品的目标客群。与之配套的是"断签预警"：上两月连续购买、本月未购的客户要在月初名单里出现，供理财经理第一时间挽留。数据团队需要一条可复用的SQL：输入任意连续月数阈值，输出当前处于连续购买状态的客户及其连续起始月，支撑两个运营场景共用一套底层逻辑。

### 2. 表结构说明
transactions（交易流水表，含产品交易类型）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| txn_type | VARCHAR(32) | 交易类型：理财申购/理财赎回/消费/转账等 |
| product_type | VARCHAR(32) | 产品类型：理财/基金/存款（NULL=非产品交易） |
| amount | DECIMAL(14,2) | 交易金额 |

示例数据：

| txn_id | customer_id | trade_date | txn_type | product_type | amount |
|---|---|---|---|---|---|
| 300001 | 90001 | 2026-07-05 | 理财申购 | 理财 | 10000.00 |
| 300002 | 90001 | 2026-08-06 | 理财申购 | 理财 | 10000.00 |
| 300003 | 90001 | 2026-09-07 | 理财申购 | 理财 | 12000.00 |
| 300004 | 90002 | 2026-07-15 | 理财申购 | 理财 | 5000.00 |
| 300005 | 90002 | 2026-09-16 | 理财申购 | 理财 | 5000.00 |

（示例中90001为7-9月连续3个月购买；90002在7月与9月购买、8月断签，不满足连续3个月）

### 3. 解题思路
核心是"月度去重+连续段识别"两步走。第一步把流水收敛到客户×月份粒度（DISTINCT 或 GROUP BY），一月多次申购只算一个月；第二步判连续，两大流派：① 行号错位法——按月排序的行号 rn 与月份同步递增，若"月初日期减rn个月"的值恒定则为同一段连续区间，这是 gaps-and-islands 的经典变形；② 自连接存在性法——对每个客户月，检查 m+1、m+2 月是否也有记录。**【面试高频】** "为什么日期减行号能标识连续段"是本题主追问，必须能推导。易错点：忘记先按月去重（同月两笔会被当成两个月）；月份连续要用日历月差（PERIOD_DIFF=1 或月初日期加 INTERVAL）而不是行相邻；日期必须先规整为月初日期，否则减rn个月会错位。

### 4. 参考解法

**解法一：行号错位法（gaps-and-islands，可输出每段连续的起止与长度）**

```sql
WITH licai_month AS (                   -- 第一步：收敛到客户×月份，日期规整为月初
    SELECT DISTINCT
        customer_id,
        CAST(DATE_FORMAT(trade_date, '%Y-%m-01') AS DATE) AS month_start
    FROM transactions
    WHERE txn_type = '理财申购'          -- 口径：申购才算购买，赎回不算
),
seq AS (                                -- 第二步：客户内按月初日期排序编号
    SELECT
        customer_id,
        month_start,
        ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY month_start) AS rn
    FROM licai_month
),
grp AS (                                -- 第三步：错位构造分组键——连续段内该值相同
    SELECT
        customer_id,
        month_start,
        rn,
        DATE_SUB(month_start, INTERVAL rn MONTH) AS grp_key  -- 月份每前进1、行号也前进1，连续则差值不变
    FROM seq
),
seg AS (                                -- 第四步：每段连续区间的起止与长度
    SELECT
        customer_id,
        MIN(month_start) AS seg_start,
        MAX(month_start) AS seg_end,
        COUNT(*)         AS seg_len
    FROM grp
    GROUP BY customer_id, grp_key
)
SELECT
    customer_id,
    DATE_FORMAT(seg_start, '%Y-%m') AS 连续起始月,
    DATE_FORMAT(seg_end,   '%Y-%m') AS 连续结束月,
    seg_len                         AS 连续月数
FROM seg
WHERE seg_len >= 3                      -- 阈值参数化：改一个数字即可查连续N月
ORDER BY customer_id, seg_start;
```

结果解读：输出即"连续购买在册名单"；把过滤条件改为 seg_end 等于当前月且 seg_len 大于等于2，就变成断签预警的前序名单，一套SQL服务"维护"与"挽留"两个运营场景。

**解法二：自连接存在性判断（思路最直白，适合快速验证与老环境）**

```sql
WITH licai_month AS (
    SELECT DISTINCT
        customer_id,
        CAST(DATE_FORMAT(trade_date, '%Y-%m-01') AS DATE) AS month_start
    FROM transactions
    WHERE txn_type = '理财申购'
)
SELECT DISTINCT
    a.customer_id,
    DATE_FORMAT(a.month_start, '%Y-%m') AS 连续起始月
FROM licai_month a
JOIN licai_month b                                -- 次月也购买
  ON b.customer_id = a.customer_id
 AND b.month_start = a.month_start + INTERVAL 1 MONTH
JOIN licai_month c                                -- 第三个月也购买
  ON c.customer_id = a.customer_id
 AND c.month_start = a.month_start + INTERVAL 2 MONTH
ORDER BY a.customer_id, a.month_start;
```

结果解读：自连接版本无法直接给出连续长度（要数到几就连几个表），但胜在零窗口函数、任何环境可跑；当需求升级为连续4月、5月时，行号错位法只需改一个 HAVING 阈值，扩展成本远低于继续堆JOIN。

### 5. 性能分析与优化
解法一：DISTINCT 收敛 O(T)，窗口排序 O(M logM)（M=客户×月数，远小于流水数T），整体最优且只扫一遍流水；解法二三次自JOIN，代价取决于月粒度表的连接选择性，月粒度表通常很小实际可接受，但客户月记录大时连接次数膨胀。优化建议：① 先 WHERE txn_type 过滤再 DISTINCT，减少进入窗口的行数；② (txn_type, trade_date) 或 (customer_id, trade_date) 建索引；③ 月粒度中间表（客户×月×是否申购）建议物化，连续签到、连续活跃等所有连续性指标全部复用；④ 千万级流水放 Spark 跑，窗口按 customer_id 重分区。

### 6. 面试延伸考点
- **为什么 DATE_SUB(month_start, INTERVAL rn MONTH) 能标识连续段？** 要点：连续月份序列减去同步递增的行号会落到同一个锚点日期，断签则锚点跳跃；它与"相邻差值法"（LAG判断差值是否为1，再用断点累计 SUM(is_break) OVER 分段）是两大主流解法，两种都要会写。
- **一个月内赎回又申购算连续吗？** 要点：口径题——按"有申购行为"算连续（本解法），或按"月末净持有"算；前者衡量行为粘性，后者衡量资产留存，先问业务目的再定口径。
- **怎么同时输出"本月断签"名单？** 要点：取每客户最近一段（seg_end 最大），判断 seg_end 早于当前月且 seg_len≥2；或用 LAG 判断"本月无记录、上月有记录"，窗口方案更简洁。

### 7. 业务拓展思考
连续性识别是行为忠诚度建模的原料：连续月数本身可作为特征进入理财持有期预测与流失预警模型。运营联动：连续3月客户推送"理财到期自动续接"服务与专属费率，断签客户触发理财经理24小时回访，把挽回窗口压缩到最短。口径延展：把"连续3月"推广为"近6月内购买≥4月"的覆盖度口径，能抗偶尔断签的噪声；也可对每个连续段计算段内申购金额趋势，区分"加仓型"与"减仓型"连续客户，运营话术随之分化。

## FIN-25 客户近90天交易频次与金额分层

### 1. 业务背景
零售条线做客户分层运营（RFM的简化版）时，第一刀切的就是"近90天交易频次×交易金额"四象限：高频高额是核心客户（专属客户经理维护）、低频高额是潜力客户（激活频次）、高频低额是活跃大众（交叉销售）、低频低额是长尾客户（线上化服务降成本）。私行部与财富部每季度要用这套分层重新分配名单归属，营销费用跟着象限走。分析师要给出：每位客户近90天的交易笔数与总金额、四象限归属、以及各象限客户数与户均指标，输出直接驱动名单再分配与服务资源配置。

### 2. 表结构说明
transactions（交易流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| txn_type | VARCHAR(32) | 交易类型：消费/转账/缴费/申购等 |
| amount | DECIMAL(14,2) | 交易金额 |

示例数据：

| txn_id | customer_id | trade_date | txn_type | amount |
|---|---|---|---|---|
| 400001 | 60001 | 2026-08-10 | 消费 | 300.00 |
| 400002 | 60001 | 2026-09-01 | 消费 | 800.00 |
| 400003 | 60002 | 2026-07-15 | 转账 | 200000.00 |
| 400004 | 60003 | 2026-09-20 | 缴费 | 50.00 |
| 400005 | 60003 | 2026-09-21 | 消费 | 60.00 |

### 3. 解题思路
口径先行：统计窗口"近90天"以数据日（2026-09-30）为终点往回推90天，含端点；频次=交易笔数，金额=交易总额，若有冲正/退款标记要先剔除。分层阈值两种流派：固定业务阈值（笔数≥6为高频、金额≥5万为高额，可解释性强、跨期可比）与动态分位阈值（各取客户中位数，随大盘自适应但含义漂移）；面试先给固定阈值版本并说明可替换。**【加分点】** 进阶写法用 RANGE 时间窗口帧直接在流水上算滚动90天指标——必须用 RANGE（按日期值范围）而非 ROWS（按行数），否则"90天"变成"90笔"，这一字之差是窗口函数理解深度的试金石。易错点：窗口帧需要预取双倍时间跨度的数据，窗口内再嵌 ROW_NUMBER 取每客户最新行时要注意去重。

### 4. 参考解法

**解法一：客户级聚合 + CASE 四象限分层（生产最常用）**

```sql
WITH cust_90d AS (                      -- 客户级近90天交易画像
    SELECT
        customer_id,
        COUNT(*)    AS txn_cnt,
        SUM(amount) AS txn_amt
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 90 DAY)  -- 左开右闭窗口，报表可复现
      AND trade_date <= '2026-09-30'
    GROUP BY customer_id
),
tiered AS (                             -- 四象限打标：阈值可整体替换为分位数
    SELECT
        customer_id,
        txn_cnt,
        txn_amt,
        CASE
            WHEN txn_cnt >= 6 AND txn_amt >= 50000 THEN '高频高额'
            WHEN txn_cnt >= 6 AND txn_amt <  50000 THEN '高频低额'
            WHEN txn_cnt <  6 AND txn_amt >= 50000 THEN '低频高额'
            ELSE '低频低额'
        END AS 客户分层
    FROM cust_90d
)
SELECT
    t.客户分层,
    COUNT(*)                                                    AS 客户数,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)          AS 客户数占比,  -- 窗口套聚合求总占比
    ROUND(AVG(t.txn_cnt), 2)                                    AS 户均笔数,
    ROUND(AVG(t.txn_amt), 2)                                    AS 户均金额
FROM tiered t
GROUP BY t.客户分层
ORDER BY 户均金额 DESC;
```

结果解读：低频高额象限是最值得投入的"潜力客"——有钱但不常来，激活频次的抓手是场景绑定（缴费、代发工资）；高频低额则适合做交叉销售提升单客价值。

**解法二：RANGE 时间窗口帧计算滚动90天指标（任意历史日快照可复现）**

```sql
WITH w AS (                             -- 在每笔交易上计算"截至该日的近90天"滚动指标
    SELECT
        customer_id,
        trade_date,
        COUNT(*)   OVER (PARTITION BY customer_id ORDER BY trade_date
                         RANGE BETWEEN INTERVAL 89 DAY PRECEDING AND CURRENT ROW) AS cnt_90d,
        SUM(amount) OVER (PARTITION BY customer_id ORDER BY trade_date
                         RANGE BETWEEN INTERVAL 89 DAY PRECEDING AND CURRENT ROW) AS amt_90d
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 180 DAY)   -- 预取双倍窗口供滚动
),
latest AS (                             -- 取每位客户最近一行的滚动值=截至数据日的90天画像
    SELECT
        customer_id,
        cnt_90d,
        amt_90d,
        ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY trade_date DESC) AS rn
    FROM w
)
SELECT
    customer_id,
    cnt_90d                             AS 近90天笔数,
    amt_90d                             AS 近90天金额,
    CASE
        WHEN cnt_90d >= 6 AND amt_90d >= 50000 THEN '高频高额'
        WHEN cnt_90d >= 6                      THEN '高频低额'
        WHEN amt_90d >= 50000                  THEN '低频高额'
        ELSE '低频低额'
    END                                 AS 客户分层
FROM latest
WHERE rn = 1
ORDER BY amt_90d DESC
LIMIT 20;                               -- 示例输出Top20，实际可全量落表
```

结果解读：RANGE帧版本的价值在于"任意一天快照可查"——把排序键换成任意历史日期即可复现当时的分层，支撑事后归因与口径审计；生产上更常把解法一做成日调度增量表，两者是灵活性与效率的取舍。

### 5. 性能分析与优化
解法一一次扫描加一次 GROUP BY，代价 O(T)；解法二窗口排序 O(T logT) 且中间结果膨胀（每笔交易携带两个窗口聚合值），内存压力显著更大。优化建议：① (customer_id, trade_date) 复合索引或按 trade_date 分区；② 解法二的 WHERE 必须先裁剪到窗口最大跨度，避免全表开窗；③ 若只需要数据日快照，坚决用解法一；④ 亿级流水在 Spark 上跑解法二时按 customer_id repartition，控制单分区窗口规模。

> Hive/Spark SQL 差异：Hive/Spark 支持 RANGE BETWEEN INTERVAL 89 DAY PRECEDING（要求 ORDER BY 为日期型）；老版本 Hive 不支持 INTERVAL 帧时，可退化为自连接 trade_date BETWEEN d-89 AND d 再聚合，语义等价但代价更高。

### 6. 面试延伸考点
- **ROWS 与 RANGE 帧的区别？** 要点：ROWS按物理行数取帧，RANGE按排序键的值范围取帧；本题"90天"必须RANGE，答成ROWS会把窗口变成"最近90笔"，这是窗口函数最经典的追问。
- **阈值用固定值还是分位数？** 要点：固定阈值跨期可比、业务可解释；分位数自适应但每期含义漂移，客户会"被动升级/降级"引发投诉；折中方案是固定阈值加季度校准。
- **金额口径要不要剔除转账？** 要点：转账金额大但非消费能力，混入会让"高额"失真；应按业务目的选择口径（评估消费能力则剔除转账，评估资金活跃度则保留），并全行统一。

### 7. 业务拓展思考
四象限分层是名单分配的起点而非终点：象限间流转率（如上季高频高额、本季低频高额）才是预警核心，核心客户降档必须触发客户经理干预。口径延展：频次可替换为"活跃天数"（去重日期数）防止单日爆量虚高频次；金额可替换为AUM增量，形成"交易行为×资产变化"双维矩阵，直接对接支行KPI；再叠加上期分层做流转矩阵，分层就从一个静态快照升级为动态经营仪表盘。
## FIN-26 不同风险等级客户的产品渗透率矩阵

### 1. 业务背景
银行在"卖适当的产品给适当的人"上受投资者适当性管理约束：风险等级R1到R5的客户能购买的产品风险档位不同，但业务上仍要回答——每个风险等级的客户里，存款、理财、基金、保险的渗透率各是多少？合规视角要验证高风险产品是否只卖给了匹配等级的客户；营销视角要找到"低风险等级但资产充足"客户的合规替代产品（如R2档理财）。产品部季度会上，这张"风险等级×产品渗透率"矩阵决定各产品线下一季的客群定向策略，也是适当性检查报告的必备数据附件，合规与营销两套人马共用同一张底表。

### 2. 表结构说明
customers（客户主表，一人一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| risk_level | VARCHAR(8) | 风险测评等级：R1-R5（R1最低） |
| open_date | DATE | 开户日期 |

示例数据：

| customer_id | risk_level | open_date |
|---|---|---|
| 20001 | R1 | 2024-03-01 |
| 20002 | R3 | 2024-05-12 |
| 20003 | R2 | 2025-01-20 |
| 20004 | R4 | 2023-11-08 |
| 20005 | R5 | 2024-08-25 |

holdings（客户产品持仓表，客户×产品粒度，月末快照）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| product_type | VARCHAR(32) | 产品类型：存款/理财/基金/保险 |
| market_value | DECIMAL(16,2) | 期末市值 |
| as_of_date | DATE | 快照日期 |

示例数据：

| customer_id | product_type | market_value | as_of_date |
|---|---|---|---|
| 20002 | 存款 | 40000.00 | 2026-09-30 |
| 20002 | 基金 | 60000.00 | 2026-09-30 |
| 20003 | 存款 | 100000.00 | 2026-09-30 |
| 20004 | 理财 | 300000.00 | 2026-09-30 |
| 20005 | 基金 | 800000.00 | 2026-09-30 |

### 3. 解题思路
渗透率=持有该产品客户数/该风险等级客户总数，分母是"全体客户"（含未持任何产品的），因此必须以 customers 为主表 LEFT JOIN 持仓打标，不能用持仓表反向统计，否则零持仓客户直接消失、渗透率被系统性高估。实现路径：先客户级0/1打标（防JOIN翻倍），再按风险等级条件聚合出宽表矩阵；第二种写法输出长表（等级×产品×渗透率），用 CROSS JOIN 产品维度表补全零值单元格，便于BI作图与合规筛查。**【避坑指南】** 客户持有多个产品时直接 JOIN 会重复计数，渗透率可能超过100%；另外风险测评有有效期，"分母要不要只用测评在有效期的客户"是合规口径要点，两个版本都要能算。

### 4. 参考解法

**解法一：客户级打标 + 条件聚合宽表矩阵**

```sql
WITH cust_flag AS (                     -- 客户级产品持有0/1标记
    SELECT
        customer_id,
        MAX(product_type = '存款') AS has_ck,
        MAX(product_type = '理财') AS has_lc,
        MAX(product_type = '基金') AS has_jj,
        MAX(product_type = '保险') AS has_bx
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
)
SELECT
    c.risk_level                             AS 风险等级,
    COUNT(*)                                 AS 客户数,        -- 分母：全体客户（含零持仓）
    ROUND(AVG(IFNULL(f.has_ck, 0)) * 100, 2) AS 存款渗透率,    -- 未持仓客户补0参与均值
    ROUND(AVG(IFNULL(f.has_lc, 0)) * 100, 2) AS 理财渗透率,
    ROUND(AVG(IFNULL(f.has_jj, 0)) * 100, 2) AS 基金渗透率,
    ROUND(AVG(IFNULL(f.has_bx, 0)) * 100, 2) AS 保险渗透率
FROM customers c
LEFT JOIN cust_flag f ON f.customer_id = c.customer_id
GROUP BY c.risk_level
ORDER BY c.risk_level;
```

结果解读：理论上风险等级越高、中高风险产品渗透率越高；若R1客户出现基金渗透率异常，大概率是适当性执行漏洞或测评过期未更新，需转合规核查，这张表因此兼具营销与风控双重身份。

**解法二：长表 + CROSS JOIN 产品维度补零（零渗透组合也出现在结果里）**

```sql
WITH prod_dim AS (                      -- 产品维度表：想看哪些产品就列哪些
    SELECT '存款' AS product_type
    UNION ALL SELECT '理财'
    UNION ALL SELECT '基金'
    UNION ALL SELECT '保险'
),
lvl AS (                                -- 各风险等级客户总数（分母）
    SELECT risk_level, COUNT(*) AS cust_cnt
    FROM customers
    GROUP BY risk_level
),
hold AS (                               -- 等级×产品的持有客户数（分子）
    SELECT c.risk_level, h.product_type,
           COUNT(DISTINCT h.customer_id) AS hold_cnt
    FROM customers c
    JOIN holdings h ON h.customer_id = c.customer_id
    WHERE h.as_of_date = '2026-09-30'
    GROUP BY c.risk_level, h.product_type
)
SELECT
    l.risk_level                                  AS 风险等级,
    d.product_type                                AS 产品类型,
    l.cust_cnt                                    AS 客户数,
    IFNULL(h.hold_cnt, 0)                         AS 持有客户数,  -- CROSS JOIN保证零值也成行
    ROUND(IFNULL(h.hold_cnt, 0) * 100.0 / NULLIF(l.cust_cnt, 0), 2) AS 渗透率
FROM lvl l
CROSS JOIN prod_dim d
LEFT JOIN hold h
  ON h.risk_level = l.risk_level AND h.product_type = d.product_type
ORDER BY l.risk_level, d.product_type;
```

结果解读：长表里"持有客户数=0"的格子不再消失，合规筛查可直接加过滤条件（产品为基金或保险、等级为R1或R2、持有客户数大于0）定位违规敞口，比宽表更适合做例外检查。

### 5. 性能分析与优化
解法一一次打标聚合加一次 LEFT JOIN，宽表输出行数等于等级数，最省；解法二多一次 CROSS JOIN（5等级×4产品=20行，代价可忽略）但省掉了打标步骤，两法整体同量级。优化建议：① customers(risk_level)、holdings(as_of_date, customer_id) 建索引；② 渗透率矩阵是季度固定报表，建议把客户产品标志宽表日级物化，多张报表共用一份打标结果；③ 客户千万级时瓶颈在打标聚合，可预聚合到 (as_of_date, customer_id, product_type) 粒度的持有标志表；④ 维度表（prod_dim）用 UNION ALL 常量表在Spark中可改为广播维度表。

### 6. 面试延伸考点
- **分母该不该排除"风险测评已过期"的客户？** 要点：合规口径通常要求测评在有效期内才算可销售客群；经营口径与合规口径分母不同，输出时要标注版本，避免同一指标两个数。
- **渗透率矩阵和FIN-19交叉持有分析是什么关系？** 要点：同源数据（客户×产品打标）不同视角——FIN-19看客户维度的绑定深度，本题看产品维度的客群覆盖；一份数据双份产出正是数仓分层价值的直接体现。
- **如果产品有上百个SKU怎么输出？** 要点：宽表列数爆炸，应改长表加产品层级表（大类-小类），按大类出矩阵、SKU级明细下钻；体现报表设计与粒度选择的工程意识。

### 7. 业务拓展思考
渗透率矩阵把"适当性合规"与"销售机会"放进同一张表：R3客户存款渗透率高但理财渗透率低，即R2档理财的定向推广池；R1高资产客户的合规替代方案是大额存单，既守住合规又留住资金。口径延展：渗透率可按"近12个月曾持有"算动量口径识别流失产品线；也可叠加AUM分层做三维矩阵（等级×产品×资产段），给分行下达分客群渗透率KPI，让矩阵从分析品变成考核品。

## FIN-27 月活跃率（当月交易且前3月内至少2月有交易）

### 1. 业务背景
运营部发现"当月有交易"的月活（MAU）太宽松——羊毛党与薅完红包即走的客户也算活跃，月活跃率在大型促销月虚高、次月又断崖下跌，无法指导预算决策。于是定义了严口径月活跃：当月有交易，且前3个自然月内至少有2个月也有交易，即"持续性活跃"。该指标用于考核月度运营活动质量、剔除一次性激励虚增，也是App运营团队与分行零售条线对齐的"真实活跃"标准。月度运营复盘会上，分析师要给出近12个月严口径月活跃率趋势，并解释口径切换后MAU下降的部分有多少来自"挤水分"。

### 2. 表结构说明
transactions（交易流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| amount | DECIMAL(14,2) | 交易金额 |

示例数据：

| txn_id | customer_id | trade_date | amount |
|---|---|---|---|
| 500001 | 11001 | 2026-05-08 | 200.00 |
| 500002 | 11001 | 2026-06-15 | 350.00 |
| 500003 | 11001 | 2026-09-01 | 500.00 |
| 500004 | 11002 | 2026-09-03 | 80.00 |
| 500005 | 11003 | 2026-07-20 | 600.00 |

（示例中11001在9月有交易，但前3个自然月6/7/8月中只有6月有交易，不满足"至少2月"，属严口径下的非活跃；11002仅9月一笔，同样非活跃）

### 3. 解题思路
先把"有交易月份"收敛为客户×月份去重集合，这是所有月度活跃类指标的地基。判定"前3个月内至少2个月有交易"两条路径：① LAG偏移法——取每位客户最近3个有交易月份，逐个判断与当月的日历距离是否小于等于3，计数大于等于2即活跃（必须校验日历距离，不能只数行数）；② 自连接计数法——对每个客户月，统计其前1到3个日历月内的有交易月份数。**【面试高频】** "为什么取最近3个有交易月份就等价于统计前3个日历月"是本题主追问。易错点：月份字符串直接相减没有意义，必须转成 YYYYMM 后用 PERIOD_DIFF 求日历月差；分母是"当月有交易客户数"，若换成全体客户数则变成另一种口径，要先对齐。

### 4. 参考解法

**解法一：LAG偏移取最近3个交易月 + 日历距离校验**

```sql
WITH cm AS (                            -- 客户×有交易月份（去重，指标地基）
    SELECT DISTINCT
        customer_id,
        CAST(DATE_FORMAT(trade_date, '%Y-%m-01') AS DATE) AS month_start  -- 规整为月初日期
    FROM transactions
),
seq AS (                                -- 每位客户最近3个有交易月份
    SELECT
        customer_id,
        month_start,
        LAG(month_start, 1) OVER (PARTITION BY customer_id ORDER BY month_start) AS prev1,
        LAG(month_start, 2) OVER (PARTITION BY customer_id ORDER BY month_start) AS prev2,
        LAG(month_start, 3) OVER (PARTITION BY customer_id ORDER BY month_start) AS prev3
    FROM cm
),
flag AS (                               -- 统计"前3个日历月内"的有交易月份数
    SELECT
        customer_id,
        month_start,
        (prev1 IS NOT NULL AND PERIOD_DIFF(DATE_FORMAT(prev1, '%Y%m'),
             DATE_FORMAT(month_start, '%Y%m')) <= 3)
      + (prev2 IS NOT NULL AND PERIOD_DIFF(DATE_FORMAT(prev2, '%Y%m'),
             DATE_FORMAT(month_start, '%Y%m')) <= 3)
      + (prev3 IS NOT NULL AND PERIOD_DIFF(DATE_FORMAT(prev3, '%Y%m'),
             DATE_FORMAT(month_start, '%Y%m')) <= 3)
        AS recent_cnt                   -- 结果0~3；日历距离超过3的最近月份不计入
    FROM seq
)
SELECT
    DATE_FORMAT(month_start, '%Y-%m')                   AS 月份,
    COUNT(*)                                            AS 当月有交易客户数,
    SUM(recent_cnt >= 2)                                AS 严口径活跃客户数,
    ROUND(SUM(recent_cnt >= 2) * 100.0 / COUNT(*), 2)   AS 严口径月活跃率
FROM flag
GROUP BY DATE_FORMAT(month_start, '%Y-%m')
ORDER BY 月份;
```

结果解读：严口径活跃率通常比普通MAU率低10-20个百分点，差值即"激励虚增活跃"；口径切换初期务必双口径并行披露，向管理层解释差异来源，避免被质疑数据造假。

**解法二：自连接统计前1-3个日历月内的交易月份数**

```sql
WITH cm AS (
    SELECT DISTINCT
        customer_id,
        CAST(DATE_FORMAT(trade_date, '%Y-%m-01') AS DATE) AS month_start
    FROM transactions
),
recent AS (                             -- 每个客户月：前1~3个日历月内的有交易月份数
    SELECT
        a.customer_id,
        a.month_start,
        COUNT(b.month_start) AS recent_cnt   -- b落在a的前1~3个自然月内则计1
    FROM cm a
    LEFT JOIN cm b
      ON b.customer_id = a.customer_id
     AND PERIOD_DIFF(DATE_FORMAT(a.month_start, '%Y%m'),
                     DATE_FORMAT(b.month_start, '%Y%m')) BETWEEN 1 AND 3
    GROUP BY a.customer_id, a.month_start
)
SELECT
    DATE_FORMAT(month_start, '%Y-%m')                   AS 月份,
    COUNT(*)                                            AS 当月有交易客户数,
    SUM(recent_cnt >= 2)                                AS 严口径活跃客户数,
    ROUND(SUM(recent_cnt >= 2) * 100.0 / COUNT(*), 2)   AS 严口径月活跃率
FROM recent
GROUP BY DATE_FORMAT(month_start, '%Y-%m')
ORDER BY 月份;
```

结果解读：自连接版本逻辑一目了然、易向业务同事解释，适合做口径评审材料；代价是月粒度集合的自连接，数据量约为客户×月数的平方级，客户规模大时优先用解法一。

### 5. 性能分析与优化
解法一：一次去重加一次窗口排序，代价 O(M logM)（M=客户×月数，一年期千万客户约1.2亿行，窗口只有4列，内存可控）；解法二自连接是潜在爆炸点，靠 (customer_id, month_start) 索引与连接谓词下推缓解，客户越多越危险。优化建议：① 先 DISTINCT 收敛到月粒度再开窗或连接，绝不能在流水粒度直接算；② cm 结果物化为月度客户活跃明细表，月活、季活、连续活跃等多个指标共用；③ Spark 上解法二按 customer_id 分桶（bucketing）可把自连接退化为 map 端连接。

### 6. 面试延伸考点
- **为什么 LAG 取"最近3个有交易月份"就等价于"前3个日历月内有几个交易月"？** 要点：3个日历月内最多3个不同交易月，且它们必然是按时间排序后最近的前缀；理解这层等价关系是窗口思维成熟的标志，答不出会被追问到穿。
- **口径改成"前3月内至少1月"或"前6月内至少3月"怎么改？** 要点：LAG 的偏移档位与日历距离阈值两个参数联动修改，最好把窗口大小与阈值做成报表参数，体现可复用意识。
- **要不要把"开户未满3个月"的新客剔除出分母？** 要点：新客天然无法满足严口径，会永久拉低活跃率；成熟做法是新客单独cohort观察，或给出"满3月客户活跃率"对照口径。

### 7. 业务拓展思考
严口径活跃是运营投入产出的"照妖镜"：活动后的月活跃率弹性才是真实拉动，MAU虚高会误导预算加码，最终形成"买量-虚活-再买量"的循环。联动动作：严口径跌出活跃的客户进入唤醒旅程（Push加权益包），连续3月严口径活跃客户升级为"稳定活跃"标签享受费率优惠。口径延展：把"有交易"替换为"登录App"或"资产变动"，得到行为深浅不同的活跃层级（登录活跃、交易活跃、资产活跃），构成活跃金字塔，逐层递减的漏斗本身就是运营诊断报告。

## FIN-28 客户余额变动的期初-发生-期末流水重构

### 1. 业务背景
财务对账与客户账单场景要求把客户存款账户还原成会计三栏式月度报表：期初余额、本期收入发生额、本期支出发生额、期末余额，四者满足恒等式"期末=期初+收入-支出"。运营侧用它做客户账单月报（类似信用卡月账单），财务侧用它核对核心系统余额与数仓流水加工结果是否一致——差额一分钱都要出工单追查。数据分析师常被要求用交易流水表反推出逐月余额链条，既验证数据质量，又支撑"余额变动归因"分析：哪个月的大额流出导致了AUM下滑、客户资金去了哪里，这是客户经理挽留谈话的弹药。

### 2. 表结构说明
transactions（存款账户交易流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户ID |
| trade_date | DATE | 交易日期 |
| direction | VARCHAR(8) | 方向：收入/支出 |
| amount | DECIMAL(14,2) | 交易金额 |
| account_type | VARCHAR(16) | 账户类型：活期/定期 |

示例数据（假定期初余额为0，即观察期内所有余额均由流水累积）：

| txn_id | customer_id | trade_date | direction | amount | account_type |
|---|---|---|---|---|---|
| 700001 | 12001 | 2026-01-10 | 收入 | 50000.00 | 活期 |
| 700002 | 12001 | 2026-02-05 | 支出 | 12000.00 | 活期 |
| 700003 | 12001 | 2026-03-18 | 收入 | 8000.00 | 活期 |
| 700004 | 12002 | 2026-02-11 | 收入 | 30000.00 | 活期 |
| 700005 | 12002 | 2026-03-25 | 支出 | 5000.00 | 活期 |

### 3. 解题思路
会计恒等式拆两步实现：第一步把流水聚合成"客户×月份"的发生额（收入与支出分列或合并为净额）；第二步构造期初——期初=截至上月的累计净额，期末=截至本月的累计净额。累计净额用窗口 SUM(...) OVER (PARTITION BY customer_id ORDER BY ym)，期初用 LAG(上月累计值) 取得。**【避坑指南】** MySQL 不允许窗口函数嵌套窗口函数，直接写 LAG(SUM(x) OVER ...) 会报语法错，必须拆成多层CTE；另外无交易月份不产生行，若下游要求逐自然月连续，需用日历维度表补齐空月；有历史期初余额时第一行要用 COALESCE 接入初始值，不能默认从0开始。

### 4. 参考解法

**解法一：累计窗口求期末 + LAG取期初（两层CTE规避窗口嵌套）**

```sql
WITH monthly AS (                       -- 第一步：客户×月净发生额
    SELECT
        customer_id,
        DATE_FORMAT(trade_date, '%Y-%m') AS ym,
        SUM(IF(direction = '收入', amount, -amount)) AS net_flow
    FROM transactions
    WHERE account_type = '活期'
    GROUP BY customer_id, DATE_FORMAT(trade_date, '%Y-%m')
),
cum AS (                                -- 第二层：逐月累计净额 = 期末余额
    SELECT
        customer_id,
        ym,
        net_flow,
        SUM(net_flow) OVER (PARTITION BY customer_id ORDER BY ym
                            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_net
    FROM monthly
)
SELECT
    customer_id,
    ym                                              AS 月份,
    COALESCE(LAG(cum_net) OVER (PARTITION BY customer_id ORDER BY ym), 0)
                                                    AS 期初余额,     -- 上月期末即本月期初
    net_flow                                        AS 本月净发生额,
    cum_net                                         AS 期末余额,
    (COALESCE(LAG(cum_net) OVER (PARTITION BY customer_id ORDER BY ym), 0)
      + net_flow = cum_net)                         AS 恒等式校验    -- 为1则流水自洽
FROM cum
ORDER BY customer_id, ym;
```

结果解读：恒等式校验列全为1即流水自洽；若核心系统提供官方余额，与 cum_net 的差异行就是数据质量工单，这套"用恒等式验数"的思路在银行数仓对账场景天天要用。

**解法二：相关子查询求期初（收入支出分列，兼容无窗口函数的老环境）**

```sql
WITH monthly AS (
    SELECT
        customer_id,
        DATE_FORMAT(trade_date, '%Y-%m') AS ym,
        SUM(IF(direction = '收入', amount, 0)) AS inflow,
        SUM(IF(direction = '支出', amount, 0)) AS outflow
    FROM transactions
    WHERE account_type = '活期'
    GROUP BY customer_id, DATE_FORMAT(trade_date, '%Y-%m')
)
SELECT
    m.customer_id,
    m.ym                                AS 月份,
    IFNULL((SELECT SUM(m2.inflow - m2.outflow)       -- 相关子查询：本月之前所有月的累计净额
            FROM monthly m2
            WHERE m2.customer_id = m.customer_id
              AND m2.ym < m.ym), 0)     AS 期初余额,
    m.inflow                            AS 收入发生额,
    m.outflow                           AS 支出发生额,
    IFNULL((SELECT SUM(m2.inflow - m2.outflow)
            FROM monthly m2
            WHERE m2.customer_id = m.customer_id
              AND m2.ym < m.ym), 0) + m.inflow - m.outflow
                                        AS 期末余额   -- 期初+收入-支出，恒等式显式呈现
FROM monthly m
ORDER BY m.customer_id, m.ym;
```

结果解读：收入与支出分列版可直接贴进客户月度账单；相关子查询每行触发一次累计扫描，客户月份数多时代价高，仅适合小数据量或MySQL 5.7等无窗口函数的环境，是理解窗口函数"替我们做了什么"的最佳对照。

### 5. 性能分析与优化
解法一两次轻量窗口（累计SUM加LAG），均是对有序分区的线性扫描，总体 O(N logN)；解法二相关子查询最坏 O(N²)（每行扫描该客户此前所有月份），数据量增长后不可用。优化建议：① monthly 聚合阶段把月份规整为 YYYYMM 数值型，排序更快且避免字符串月份比较；② (customer_id, trade_date) 复合索引；③ 窗口帧显式写 ROWS UNBOUNDED PRECEDING，避免默认 RANGE 帧在排序键并列值时的语义意外；④ 对账场景建议把期末余额与核心系统余额逐月比对落差异表，作为数仓数据质量监控项常态化运行。

### 6. 面试延伸考点
- **客户某个月没有任何交易，期初链条怎么保持连续？** 要点：稀疏行会让 LAG 取到"上一个有交易的月份"而非上一自然月，期初语义从"上月末余额"漂移为"上次有交易时的累计"；下游要求逐月连续时，用日历维度表 LEFT JOIN 补齐空月（净发生额为0）。
- **客户有历史期初余额（开户时存量）怎么办？** 要点：把初始余额并入第一行——COALESCE(LAG(cum_net), 初始余额)，或构造一条"期初建账"流水；口径上必须明确观察起点，否则对账永远差一笔。
- **窗口函数嵌套报错怎么破？** 要点：MySQL不支持窗口内嵌窗口，拆成多层CTE是标准解法；顺带说明聚合嵌套（如 AVG(SUM(x)) OVER ()）同理需分层，能讲清"为什么"而不是背结论才算过关。

### 7. 业务拓展思考
三栏式重构是客户账单月报、AUM归因、余额预测特征工程的公共底座：期末减期初就是当月资金净流入，连成序列即"客户资金流向画像"，大额流出预警可直接对接客户经理挽留动作。口径延展：把 direction 细分为代发、消费、理财申购等交易类型，发生额就从两栏扩展为多栏构成分析（类似现金流量表结构），支撑"钱从哪来、到哪去"的经营叙事，也是向管理层讲清AUM波动原因的标准框架。

## FIN-29 逾期客户回收情况分布（已还清/部分还款/无还款）

### 1. 业务背景
催收与资产管理团队每季度要向风险委员会汇报逾期资产的回收结构：进入逾期状态的贷款中，多少笔已全额还清，多少笔部分还款（回收意愿存在但能力不足），多少笔毫无还款动作（需要强催收或核销评估）。三类客群对应完全不同的处置策略——已还清客户做关系修复防止二次流失，部分还款客户是分期重组的最佳候选，无还款客户评估诉讼与核销路径。回收率同时按户数与金额两个口径披露：金额口径决定拨备与利润表影响，户数口径指导催收人力与外呼资源的排布，两个口径缺一不可。

### 2. 表结构说明
loans（逾期贷款现状表，每笔在逾期中的贷款一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | BIGINT | 贷款单号 |
| customer_id | BIGINT | 客户ID |
| overdue_amount | DECIMAL(14,2) | 当前逾期金额（含本息） |
| overdue_days | INT | 当前逾期天数 |

示例数据：

| loan_id | customer_id | overdue_amount | overdue_days |
|---|---|---|---|
| 61001 | 13001 | 5000.00 | 45 |
| 61002 | 13002 | 12000.00 | 120 |
| 61003 | 13003 | 8000.00 | 20 |
| 61004 | 13004 | 3000.00 | 200 |
| 61005 | 13005 | 20000.00 | 60 |

repayments（还款流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| repay_id | BIGINT | 还款流水号 |
| loan_id | BIGINT | 贷款单号 |
| repay_date | DATE | 还款日期 |
| repay_amount | DECIMAL(14,2) | 还款金额 |

示例数据：

| repay_id | loan_id | repay_date | repay_amount |
|---|---|---|---|
| 91001 | 61001 | 2026-08-15 | 5000.00 |
| 91002 | 61003 | 2026-09-01 | 3000.00 |
| 91003 | 61005 | 2026-09-10 | 8000.00 |
| 91004 | 61005 | 2026-09-20 | 2000.00 |
| 91005 | 61002 | 2026-07-30 | 1500.00 |

### 3. 解题思路
口径先行：回收状态以"逾期后累计还款额"对比"当前逾期金额"判定——累计还款大于等于逾期金额为已还清，大于0且小于逾期金额为部分还款，无还款记录为无还款；还款流水必须先聚合到贷款粒度再JOIN，避免一笔多期还款导致主表行数翻倍。产出两层：总体三分类分布（笔数、占比、金额占比），以及逾期账龄段×回收状态交叉矩阵（账龄越老回收越差是规律，交叉看才有处置建议）。**【加分点】** 主动指出"已还清"严格应对比合同应还总额而非当前逾期金额，并说明本例用逾期金额近似的简化边界，这是风控数据岗口径素养的直接体现。易错点：LEFT JOIN 还款表保证无还款客户在场；SUM(COUNT(*)) OVER () 这类"窗口套聚合"要写在聚合查询里才合法。

### 4. 参考解法

**解法一：LEFT JOIN 预聚合 + CASE 分类 + 总体分布（含金额口径占比）**

```sql
WITH repay_agg AS (                     -- 还款流水聚合到贷款粒度，防止JOIN翻倍
    SELECT loan_id, SUM(repay_amount) AS total_repay
    FROM repayments
    GROUP BY loan_id
),
cls AS (                                -- 逐笔回收分类
    SELECT
        l.loan_id,
        l.overdue_amount,
        CASE
            WHEN IFNULL(r.total_repay, 0) >= l.overdue_amount THEN '已还清'
            WHEN IFNULL(r.total_repay, 0) > 0                 THEN '部分还款'
            ELSE '无还款'
        END AS 回收状态
    FROM loans l
    LEFT JOIN repay_agg r ON r.loan_id = l.loan_id    -- 左连：无还款记录的贷款也保留
    WHERE l.overdue_amount > 0
)
SELECT
    回收状态,
    COUNT(*)                                                AS 笔数,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)      AS 笔数占比,   -- 窗口套聚合求总占比
    ROUND(SUM(overdue_amount), 2)                           AS 逾期金额,
    ROUND(SUM(overdue_amount) * 100.0
          / SUM(SUM(overdue_amount)) OVER (), 2)            AS 金额占比    -- 金额口径分布
FROM cls
GROUP BY 回收状态
ORDER BY 笔数 DESC;
```

结果解读：无还款占比高说明催收前置动作缺失或进件客群质量差；金额口径占比通常比户数口径更向"无还款"倾斜——大额欠款更难回收，这正是必须双口径披露的原因。

**解法二：账龄段×回收状态交叉矩阵（行转列，定位哪个账龄段最急需处置）**

```sql
WITH repay_agg AS (
    SELECT loan_id, SUM(repay_amount) AS total_repay
    FROM repayments
    GROUP BY loan_id
),
cls AS (
    SELECT
        CASE WHEN overdue_days <= 30  THEN '1_逾期30天内'
             WHEN overdue_days <= 90  THEN '2_逾期31-90天'
             WHEN overdue_days <= 180 THEN '3_逾期91-180天'
             ELSE '4_逾期180天以上' END AS 账龄段,
        CASE
            WHEN IFNULL(r.total_repay, 0) >= l.overdue_amount THEN '已还清'
            WHEN IFNULL(r.total_repay, 0) > 0                 THEN '部分还款'
            ELSE '无还款'
        END AS 回收状态
    FROM loans l
    LEFT JOIN repay_agg r ON r.loan_id = l.loan_id
    WHERE l.overdue_amount > 0
)
SELECT
    账龄段,
    COUNT(*)                                    AS 总笔数,
    SUM(回收状态 = '已还清')                    AS 已还清,
    SUM(回收状态 = '部分还款')                  AS 部分还款,
    SUM(回收状态 = '无还款')                    AS 无还款,
    ROUND(AVG(回收状态 = '已还清') * 100, 2)    AS 还清率,
    ROUND(AVG(回收状态 <> '无还款') * 100, 2)   AS 有回收动作率   -- 部分还款也算回收意愿信号
FROM cls
GROUP BY 账龄段
ORDER BY 账龄段;
```

结果解读：逾期30天内的"有回收动作率"通常最高，是提醒还款与分期重组的黄金窗口；180天以上还清率趋近于零，资源应转向诉讼与核销评估，交叉矩阵直接对应催收分段策略。

### 5. 性能分析与优化
还款聚合（GROUP BY loan_id）加主表 LEFT JOIN 加一次分组，两解法同构，瓶颈在 repayments 的聚合，其行数约为贷款数的3-5倍。优化建议：① repayments(loan_id, repay_date) 复合索引让聚合走索引；② 还款流水上亿时先按 loan_id 维护累计还款汇总表（还款事件触发增量更新），主查询退化为单表扫描；③ 账龄段映射建议做成维度表 JOIN 而非硬编码 CASE，段定义调整时不用改SQL；④ 金额口径若需精确，引入还款计划表比对"应还本息"，SQL结构不变只换对比基准。

### 6. 面试延伸考点
- **"已还清"的判定为什么用累计还款对比逾期金额不严谨？** 要点：严格口径应比较"逾期后累计还款与逾期时点应还总额"，还要处理还款冲正、费用减免；主动指出简化并给出精确方案是风控数据岗的核心素养。
- **部分还款客户按什么顺序催？** 要点：按"剩余逾期额×还款意愿信号×账龄窗口"打分排序，账龄30-90天且有还款记录的优先，实现回收概率与回收金额的期望最大化。
- **回收状态会不会随时间变化，怎么追踪？** 要点：状态是时点快照，正式分析要按月快照留存，输出"回收状态迁徙矩阵"（上月部分还款、本月还清的迁徙率），与vintage思路同源。

### 7. 业务拓展思考
回收结构分布直接对接资产质量预期与拨备计提：无还款占比抬升预示核销规模上行，董事会层面要提前沟通利润影响。运营联动：部分还款客群推"余息分期重组"方案，已还清客群推送免抵押小额产品做关系修复，把风险处置与客户经营衔接起来。口径延展：把回收细分为"正常回收/折价回收/代偿回收"，或输出M1-M6各阶段的滚动回收率曲线，为催收外包定价与律所委案策略提供数据基准。

## FIN-30 各客户经理名下客户的AUM与交易活跃排名

### 1. 业务背景
支行零售条线的绩效管理绕不开分组排名：每位客户经理名下挂着几十到几百名客户，支行行长要看两份榜单——每位经理AUM最高与交易最活跃的前3名客户（用于月度重点客户服务检视），以及经理之间的管户数量、户均AUM与活跃客户占比横向对比（用于绩效分配与辅导对象识别）。分组内TopN是SQL面试的经典题型，而银行业务语境还叠加真实约束：客户可能更换管户经理（按当前归属统计）、无交易客户也要参与活跃排名（挂零管理），这些约束正是面试官考察业务细腻度的地方。

### 2. 表结构说明
customer_manager（管户关系表，记录客户当前归属，一人一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| manager_id | BIGINT | 客户经理工号 |
| manager_name | VARCHAR(32) | 客户经理姓名 |
| assign_date | DATE | 归属生效日期 |

示例数据：

| customer_id | manager_id | manager_name | assign_date |
|---|---|---|---|
| 30001 | M001 | 张伟 | 2025-01-01 |
| 30002 | M001 | 张伟 | 2025-03-15 |
| 30003 | M002 | 李娜 | 2025-02-01 |
| 30004 | M002 | 李娜 | 2025-06-10 |
| 30005 | M003 | 王强 | 2025-04-20 |

holdings（客户资产持仓表，客户×产品粒度，月末快照）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户ID |
| product_type | VARCHAR(32) | 产品类型：存款/理财/基金/保险 |

示例数据：

| 30001 | 存款 | 100000.00 | 2026-09-30 |

|---|---|---|
| txn_id | BIGINT | 交易流水号 |

### 3. 解题思路
三层结构：① 指标层——持仓聚AUM、流水聚近30天交易次数，各自聚合到客户粒度；② 归属层——管户关系 LEFT JOIN 两个指标，无持仓无交易的客户补0，保证经理名下名单完整；③ 排名层——RANK() OVER (PARTITION BY manager_id ORDER BY aum DESC) 取组内TopN，再配经理级汇总（户数、户均AUM、活跃客户占比）形成"客户明细+经理汇总"双层报表。**【面试高频】** RANK并列会跳号（两个第1之后直接是第3），取Top3可能返回多于3行，ROW_NUMBER 则强制截断为3行——用哪个取决于业务要不要看到并列，能主动对比三者即可拿下此题。易错点：管户关系若存历史归属记录，要先按 assign_date 取最新一条；LEFT JOIN 后指标为NULL要补0再排名，否则NULL排序位置不定。

### 4. 参考解法

**解法一：RANK 窗口分组排名（保留并列名次，符合绩效语境）**

```sql
WITH cust_aum AS (                      -- 指标层1：客户AUM
    SELECT customer_id, SUM(market_value) AS aum
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
),
cust_act AS (                           -- 指标层2：客户近30天交易次数
    SELECT customer_id, COUNT(*) AS txn_cnt
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 30 DAY)
    GROUP BY customer_id
),
base AS (                               -- 归属层：经理×客户×指标（补零保名单完整）
    SELECT
        cm.manager_id,
        cm.manager_name,
        cm.customer_id,
        IFNULL(a.aum, 0)     AS aum,
        IFNULL(t.txn_cnt, 0) AS txn_cnt
    FROM customer_manager cm
    LEFT JOIN cust_aum a ON a.customer_id = cm.customer_id
    LEFT JOIN cust_act t ON t.customer_id = cm.customer_id
),
ranked AS (                             -- 排名层：经理内双榜排名
    SELECT
        *,
        RANK() OVER (PARTITION BY manager_id ORDER BY aum DESC)     AS aum_rank,
        RANK() OVER (PARTITION BY manager_id ORDER BY txn_cnt DESC) AS act_rank
    FROM base
)
SELECT
    manager_name                        AS 客户经理,
    customer_id                         AS 客户ID,
    aum                                 AS AUM,
    txn_cnt                             AS 近30天交易次数,
    aum_rank                            AS AUM排名,
    act_rank                            AS 活跃排名
FROM ranked
WHERE aum_rank <= 3                     -- 每位经理的AUM Top3客户
ORDER BY manager_name, aum_rank;
```

结果解读：榜单供支行月度重点客户检视会使用；RANK并列意味着两位客户AUM并列第2时Top3会输出4行——绩效场景通常希望并列都被看到，这正是选RANK而非ROW_NUMBER的业务理由。

**解法二：相关子查询取组内TopN + 经理级汇总（无窗口函数环境可用）**

```sql
WITH cust_aum AS (
    SELECT customer_id, SUM(market_value) AS aum
    FROM holdings
    WHERE as_of_date = '2026-09-30'
    GROUP BY customer_id
),
cust_act AS (
    SELECT customer_id, COUNT(*) AS txn_cnt
    FROM transactions
    WHERE trade_date > DATE_SUB('2026-09-30', INTERVAL 30 DAY)
    GROUP BY customer_id
),
base AS (
    SELECT
        cm.manager_id,
        cm.manager_name,
        cm.customer_id,
        IFNULL(a.aum, 0)     AS aum,
        IFNULL(t.txn_cnt, 0) AS txn_cnt
    FROM customer_manager cm
    LEFT JOIN cust_aum a ON a.customer_id = cm.customer_id
    LEFT JOIN cust_act t ON t.customer_id = cm.customer_id
)
-- 语句1：组内AUM Top3（相关子查询法：组内严格比它大的个数<3 即Top3，并列全取）
SELECT
    b.manager_name                      AS 客户经理,
    b.customer_id                       AS 客户ID,
    b.aum                               AS AUM
FROM base b
WHERE (SELECT COUNT(*)
       FROM base b2
       WHERE b2.manager_id = b.manager_id
         AND b2.aum > b.aum) < 3
ORDER BY b.manager_name, b.aum DESC;

-- 语句2：经理级横向对比（CTE需随语句重复定义，此处仅展示查询体）
SELECT
    manager_name                        AS 客户经理,
    COUNT(*)                            AS 管户数量,
    ROUND(AVG(aum), 2)                  AS 户均AUM,
    ROUND(AVG(txn_cnt > 0) * 100, 2)    AS 近30天活跃客户占比
FROM base
GROUP BY manager_id, manager_name
ORDER BY 户均AUM DESC;
```

结果解读：相关子查询的语义是"组内严格比我AUM大的客户不足3个"，并列时全部入选，与RANK行为一致；经理级汇总里活跃占比低的经理优先安排外呼团队支援，而不是简单增加名单，体现了排名结果如何反哺资源调配。

### 5. 性能分析与优化
解法一：两次预聚合加两次 LEFT JOIN 加一次窗口排序，O(N logN)；解法二相关子查询对每行执行一次组内计数，最坏 O(N²)，仅在分组数小（几百经理×几百客户）时可行。优化建议：① customer_manager(customer_id) 唯一约束保证一人一归属，若存历史记录先用 ROW_NUMBER 按 assign_date DESC 取最新；② 客户级月度AUM与月度交易次数预聚合表是支行报表的公共底座，务必物化；③ 窗口排序按 manager_id 分区，Spark 上先 repartition(manager_id)；④ MySQL 8.0 也可用 LATERAL 派生表按经理取前3，语义等价于 ROW_NUMBER 截断。

### 6. 面试延伸考点
- **RANK、DENSE_RANK、ROW_NUMBER 取Top3有什么区别？** 要点：RANK并列跳号可能返回多于3行、DENSE_RANK并列不跳号、ROW_NUMBER严格3行；绩效榜单一般用RANK保留并列，限量抽奖类场景用ROW_NUMBER，回答时给出各自的业务场景才算完整。
- **客户换了管户经理，历史业绩怎么算？** 要点：归属表按 assign_date 取时点快照，AUM增量归属通常按"贡献期是否在管"切分；能主动提出管户切换对指标连续性的影响即是业务理解加分。
- **经理间对比要不要看管户规模差异？** 要点：户均指标消除规模影响，但也要看高价值客户数的绝对值；建议人均与结构双指标并列，防止单一均值掩盖分布差异。

### 7. 业务拓展思考
分组排名把绩效管理从"凭印象"变成"看数据"：AUM排名靠后但活跃排名靠前的客户是经理投入度不足的信号，活跃排名靠后的大额客户则是流失预警名单，双榜交叉比单榜更能定位问题。口径延展：TopN可换成"分位线以上客户占比"衡量经理客群质量结构；联动动作包括标杆经理话术萃取、落后经理的名单调配（把长期低活跃客户调给外呼团队），让排名直接驱动资源再分配，形成"排名-诊断-干预"的闭环。
