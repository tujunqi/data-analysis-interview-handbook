## FIN-31 AUM同比环比与客群结构贡献拆解

### 1. 业务背景
某股份制银行零售财富管理条线，每月经营分析会前，分行财富管理部负责人（谁）需要拿到本月AUM（管理客户资产规模）的环比、同比增速，并按客群等级（大众、富裕、私行）拆解增长来源（何时/什么）：判断增长主要由"客户数扩张"驱动还是由"户均资产提升/结构升级"驱动（为什么）。该结论直接决定下季度预算是投向新客获取，还是聚焦存量客户升级与流失挽留；这是财富条线KPI归因的标准动作，也是向管理层汇报时"规模效应 vs 结构效应"的经典分析框架，口径错误会直接误导资源投放方向。

### 2. 表结构说明
表名：customer_aum_snapshot（客户AUM月度快照表，每月末全量快照一次）

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户编号 |
| stat_month | DATE | 统计月份（月末快照日，如2025-06-30） |
| segment | VARCHAR(20) | 客群等级：大众/富裕/私行 |
| aum | DECIMAL(18,2) | 月末AUM余额（元） |
| branch | VARCHAR(50) | 所属支行 |

示例数据：

| customer_id | stat_month | segment | aum | branch |
|---|---|---|---|---|
| 10001 | 2025-05-31 | 大众 | 86000.00 | 城东支行 |
| 10001 | 2025-06-30 | 大众 | 91500.00 | 城东支行 |
| 10002 | 2025-05-31 | 富裕 | 820000.00 | 城西支行 |
| 10002 | 2025-06-30 | 私行 | 1050000.00 | 城西支行 |
| 10003 | 2025-06-30 | 大众 | 15000.00 | 城南支行 |

（10002 由富裕升级为私行，是"结构效应"的典型载体。）

### 3. 解题思路
先定口径：环比增速=（本月AUM−上月AUM）/上月AUM；同比增速=（本月−去年同期）/去年同期。贡献拆解用两因素分解：设C=客户数、A=户均AUM，则 ΔAUM = C1×A1 − C0×A0 = (C1−C0)×A0 + C1×(A1−A0)，前者为"规模效应"（客户数变化按上期户均折算），后者为"结构效应"（户均变化按本期客户数放大），两项之和严格等于总变化、不重不漏。实现路径分三层：第一层CTE按"月份×客群"聚合出总AUM与客户数；第二层用LAG或自连接取上月、去年同期基准；第三层计算增速与两项效应。**【避坑指南】** LAG(x,12) 算同比的前提是12个月快照连续无缺，缺月时会静默错位相减得出荒谬增速，稳妥做法是先校验快照完整性，或用自连接按月份键精确匹配；另外月末日期直接加1个月会溢出（1-31加1月变2-28），统一转"月初键"再运算可规避。

### 4. 参考解法

**解法一：LAG 窗口函数（快照连续时最简）**

```sql
WITH seg_month AS (                              -- 第一层：按月份×客群聚合
    SELECT stat_month,
           segment,
           SUM(aum) AS total_aum,                -- 该客群当月AUM合计
           COUNT(DISTINCT customer_id) AS cust_cnt  -- 该客群当月客户数
    FROM customer_aum_snapshot
    GROUP BY stat_month, segment
),
seg_calc AS (                                    -- 第二层：窗口取环比与同比基准
    SELECT stat_month,
           segment,
           total_aum,
           cust_cnt,
           LAG(total_aum, 1)  OVER (PARTITION BY segment ORDER BY stat_month) AS prev_aum,   -- 上月AUM
           LAG(cust_cnt, 1)   OVER (PARTITION BY segment ORDER BY stat_month) AS prev_cnt,   -- 上月客户数
           LAG(total_aum, 12) OVER (PARTITION BY segment ORDER BY stat_month) AS yoy_aum,    -- 去年同期AUM（要求快照连续12个月）
           LAG(cust_cnt, 12)  OVER (PARTITION BY segment ORDER BY stat_month) AS yoy_cnt     -- 去年同期客户数
    FROM seg_month
)
SELECT stat_month,                                                     -- 统计月
       segment,                                                        -- 客群等级
       ROUND(total_aum / 10000, 2)                                     AS aum_wan,     -- 当期AUM（万元）
       ROUND((total_aum - prev_aum) / NULLIF(prev_aum,0) * 100, 2)     AS mom_pct,     -- 环比增速%
       ROUND((total_aum - yoy_aum)  / NULLIF(yoy_aum,0)  * 100, 2)     AS yoy_pct,     -- 同比增速%
       ROUND((cust_cnt - prev_cnt) * (prev_aum / NULLIF(prev_cnt,0)) / 10000, 2)      AS scale_wan,    -- 规模效应：户数变化×上期户均（万元）
       ROUND(cust_cnt * (total_aum / NULLIF(cust_cnt,0) - prev_aum / NULLIF(prev_cnt,0)) / 10000, 2) AS structure_wan  -- 结构效应：本期户数×户均变化（万元）
FROM seg_calc
WHERE stat_month = '2025-06-30'        -- 只看最新月份
ORDER BY segment;
-- 规模效应+结构效应恰等于AUM总变化，可直接做瀑布图拆解
```

结果解读：若"富裕"客群规模效应为正而结构效应为负，说明客户数在增加但户均被新客摊薄，经营重点应从拉新转向存量户均提升；两效应同正才是健康增长。

**解法二：自连接按月精确匹配（不依赖快照连续）**

```sql
WITH seg_month AS (                                    -- 聚合时统一转“月初键”，规避月末加减溢出
    SELECT DATE_FORMAT(stat_month, '%Y-%m-01') AS month_key,  -- 月初日期作为连接键
           segment,
           SUM(aum) AS total_aum,
           COUNT(DISTINCT customer_id) AS cust_cnt
    FROM customer_aum_snapshot
    GROUP BY month_key, segment               -- MySQL 8.0 允许按别名分组
),
joined AS (                                            -- 三份自连接：当期×上月×去年同期
    SELECT c.month_key, c.segment, c.total_aum, c.cust_cnt,
           m.total_aum AS prev_aum, m.cust_cnt AS prev_cnt,      -- 上月值
           y.total_aum AS yoy_aum,  y.cust_cnt AS yoy_cnt        -- 去年同期值
    FROM seg_month c
    LEFT JOIN seg_month m
           ON m.segment = c.segment
          AND m.month_key = DATE_SUB(c.month_key, INTERVAL 1 MONTH)    -- 上月 = 当期月减1
    LEFT JOIN seg_month y
           ON y.segment = c.segment
          AND y.month_key = DATE_SUB(c.month_key, INTERVAL 12 MONTH)   -- 同比 = 当期月减12
)
SELECT month_key, segment,
       ROUND((total_aum - prev_aum) / NULLIF(prev_aum,0) * 100, 2) AS mom_pct,   -- 环比
       ROUND((total_aum - yoy_aum)  / NULLIF(yoy_aum,0)  * 100, 2) AS yoy_pct,   -- 同比
       ROUND((cust_cnt - prev_cnt) * (prev_aum / NULLIF(prev_cnt,0)) / 10000, 2)       AS scale_wan,     -- 规模效应
       ROUND(cust_cnt * (total_aum / NULLIF(cust_cnt,0) - prev_aum / NULLIF(prev_cnt,0)) / 10000, 2) AS structure_wan  -- 结构效应
FROM joined
WHERE prev_aum IS NOT NULL            -- 剔除无上月基准的月份（缺月时不误算）
ORDER BY month_key DESC, segment;
```

结果解读：自连接版对快照缺月免疫——缺月时基准为NULL被过滤，而不是像LAG那样错位相减；适合快照完整性无法保证的多分行环境。

> Hive/Spark SQL 差异：Hive 中月份增减用 `add_months(month_key, -1)`；GROUP BY 不支持别名需重复书写聚合表达式；LAG语法一致，亿级快照表按 stat_month 分区后只扫所需分区。

### 5. 性能分析与优化
解法一单次扫描+窗口排序，代价 O(N log N)，逻辑最简；解法二对聚合后的中间结果（月×客群粒度，通常仅几百行）做两次自连接，代价可忽略，但明细表可能被引用三次，数据量大时建议把 seg_month 落成月度汇总表。具体优化：① customer_aum_snapshot 建 (stat_month, segment) 复合索引，或按 stat_month RANGE 分区；② 建立"月度客群AUM汇总表"供经营看板复用，避免每次扫亿级客户快照；③ 两解法都需 NULLIF 防除零（新客群上月户均为0）；④ 若快照连续性经校验有保障，优先解法一，少一层JOIN。

### 6. 面试延伸考点
- **为什么客户跨等级迁移会同时影响规模效应与结构效应？** 要点：迁移客户在原等级户数减少、新等级户数增加，且两档户均不同，故两项都有贡献；严格归因可再做"等级内变化+等级间迁移"三维拆解。
- **AUM用时点值还是日均值？差异说明什么？** 要点：时点值可被月末冲量操纵（月末转入次月初转出）；日均值反映真实粘性，考核与监管口径常用日均AUM，两者背离越大说明"冲时点"越严重。
- **如果上月某客群客户数为0（新设客群），环比怎么算？** 要点：分母为0无意义，应展示绝对增量而非增速，或注明"基数不可比"，硬算会得到天文数字误导汇报。
- **同比为负但环比为正，怎么向行长解释？** 要点：短期改善但未恢复至去年同期水平，需结合去年高基数事件（如集中赎回、大额资金搬家）归因，避免单月解读。

### 7. 业务拓展思考
该拆解框架可直接迁移到存款余额、基金保有量、保险新单价值等指标：把"客户数×户均"换成"户数×件均"或"户数×持有产品数"即可复用。联动动作上，规模效应为正但结构效应为负时启动"大众客群升级计划"（工资理财绑定、资产归集礼遇）；结构效应为正时复制高等级客户打法下沉。口径延展：可加入"新增AUM/流失AUM"净流入双列拆解，或用"有效AUM"（剔除低收益产品）与中收贡献挂钩，让归因结论直接对接利润表。

## FIN-32 M0-M3逾期迁徙率矩阵

### 1. 业务背景
某消费金融公司资产质量月度复盘会上，风险政策与资产质量团队（谁）每月初需要基于月末贷快照计算M0-M4+迁徙率矩阵——例如"5月末M1余额中，6月末有多少比例滚入M2"（何时/什么）。迁徙率是坏账准备计提、12期vintage损失率预测和催收资源配置的核心输入（为什么）：M1→M2迁徙率抬升通常意味着催收前端失守，需立即加派外呼产能；M2→M3抬升则指向诉前处置能力不足。同时监管报送要求按逾期期限段披露资产分类与迁徙情况，口径必须严谨可复核，因此这道题是信贷风控SQL的最高频考题之一。

### 2. 表结构说明
表名：loan_monthly_snapshot（借据月度快照表，每月末对全量在贷借据快照一次）

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | BIGINT | 借据号 |
| customer_id | BIGINT | 客户号 |
| stat_month | DATE | 快照月末日期 |
| overdue_days | INT | 月末逾期天数 |
| dpd_bucket | VARCHAR(10) | 逾期桶：M0(0-29天)/M1(30-59)/M2(60-89)/M3(90-119)/M4plus(120+) |
| outstanding_amt | DECIMAL(16,2) | 月末剩余应还本金 |
| is_written_off | TINYINT | 是否已核销：1是/0否 |

示例数据：

| loan_id | customer_id | stat_month | overdue_days | dpd_bucket | outstanding_amt | is_written_off |
|---|---|---|---|---|---|---|
| L2001 | 8001 | 2025-05-31 | 35 | M1 | 12000.00 | 0 |
| L2001 | 8001 | 2025-06-30 | 64 | M2 | 11500.00 | 0 |
| L2002 | 8002 | 2025-05-31 | 5 | M0 | 30000.00 | 0 |
| L2002 | 8002 | 2025-06-30 | 0 | M0 | 0.00 | 0 |
| L2003 | 8003 | 2025-05-31 | 45 | M1 | 8800.00 | 0 |

（L2002六月末还清结清、余额归0；L2003若6月无快照行则按"结清"处理。）

### 3. 解题思路
口径先行：迁徙率=分母为上月末某桶（如M1）的余额（剔除已核销），分子为其中本月末滚入下一桶（M2）的余额；同时关注"回正率"（滚回M0）与"结清率"（本月无快照记录）。**【面试高频】** 余额口径与户数口径必须先声明——余额口径反映风险暴露但受大额单笔影响剧烈，户数口径稳定但会低估大额风险，严谨的月报两者都算。实现路径：解法一用相邻两月快照自连接+条件聚合做行转列矩阵；解法二用LEAD窗口在整张快照表上一次性生成"本月桶→下月桶"配对，避免大表自连接且可一次回溯多月。易错点：①本月结清的借据无快照行，必须LEFT JOIN保留在分母，否则迁徙率虚高；②LEAD取到的"下一份快照"可能是隔月的（借据中途断档），须校验相邻自然月才计入；③核销件要剔除；④M4plus通常设为吸收态不再细分。

### 4. 参考解法

**解法一：相邻两月快照自连接 + 条件聚合（行转列矩阵）**

```sql
WITH cur AS (                                   -- 基准月（上月末）快照
    SELECT loan_id, dpd_bucket, outstanding_amt
    FROM loan_monthly_snapshot
    WHERE stat_month = '2025-05-31'
      AND is_written_off = 0                    -- 剔除已核销借据
),
nxt AS (                                        -- 目标月（本月末）快照
    SELECT loan_id, dpd_bucket
    FROM loan_monthly_snapshot
    WHERE stat_month = '2025-06-30'
      AND is_written_off = 0
)
SELECT cur.dpd_bucket                                                       AS from_bucket,   -- 上月所在桶（矩阵行）
       ROUND(SUM(cur.outstanding_amt)/10000, 2)                             AS base_amt_wan,  -- 分母：上月该桶余额（万元）
       ROUND(SUM(CASE WHEN n.dpd_bucket='M0'    THEN cur.outstanding_amt ELSE 0 END)
             / SUM(cur.outstanding_amt) * 100, 2)                           AS to_m0_pct,     -- 回正：滚入M0占比
       ROUND(SUM(CASE WHEN n.dpd_bucket='M1'    THEN cur.outstanding_amt ELSE 0 END)
             / SUM(cur.outstanding_amt) * 100, 2)                           AS to_m1_pct,     -- 维持M1占比
       ROUND(SUM(CASE WHEN n.dpd_bucket='M2'    THEN cur.outstanding_amt ELSE 0 END)
             / SUM(cur.outstanding_amt) * 100, 2)                           AS to_m2_pct,     -- 恶化：滚入M2占比
       ROUND(SUM(CASE WHEN n.dpd_bucket IN ('M3','M4plus') THEN cur.outstanding_amt ELSE 0 END)
             / SUM(cur.outstanding_amt) * 100, 2)                           AS to_m3p_pct,    -- 跳档：直入M3及以上
       ROUND(SUM(CASE WHEN n.loan_id IS NULL THEN cur.outstanding_amt ELSE 0 END)
             / SUM(cur.outstanding_amt) * 100, 2)                           AS settled_pct    -- 结清：本月无快照记录
FROM cur
LEFT JOIN nxt n ON n.loan_id = cur.loan_id      -- 左连接：本月结清的借据也必须留在分母
GROUP BY cur.dpd_bucket
ORDER BY FIELD(cur.dpd_bucket,'M0','M1','M2','M3','M4plus');   -- 按桶序输出矩阵行
```

结果解读：M1行的to_m2_pct即教科书口径的"M1→M2迁徙率"，环比抬升3个百分点以上即触发催收策略复查；settled_pct高说明该桶回款能力强。

**解法二：LEAD 窗口一次成型（适合逐月滚动监控）**

```sql
WITH pair AS (                                  -- 每条借据按快照月排序，取下一份快照状态
    SELECT stat_month,
           dpd_bucket AS from_bucket,                               -- 本月末状态
           LEAD(dpd_bucket) OVER (PARTITION BY loan_id ORDER BY stat_month) AS to_bucket,    -- 下份快照状态
           LEAD(stat_month) OVER (PARTITION BY loan_id ORDER BY stat_month) AS next_month,   -- 下份快照月份
           outstanding_amt                                          -- 分母用本月末余额
    FROM loan_monthly_snapshot
    WHERE is_written_off = 0
),
valid AS (                                      -- 只保留“下一份快照恰为相邻自然月”的配对
    SELECT from_bucket, to_bucket, outstanding_amt
    FROM pair
    WHERE next_month = DATE_ADD(stat_month, INTERVAL 1 MONTH)   -- 防止借据中途断档导致跨月错配
      AND stat_month = '2025-05-31'                             -- 本期只算5月→6月
)
SELECT from_bucket,
       ROUND(SUM(CASE WHEN to_bucket='M1' THEN outstanding_amt ELSE 0 END)
             / NULLIF(SUM(outstanding_amt),0) * 100, 2) AS to_m1_pct,   -- 结清件to_bucket为NULL，自然不计入分子
       ROUND(SUM(CASE WHEN to_bucket='M2' THEN outstanding_amt ELSE 0 END)
             / NULLIF(SUM(outstanding_amt),0) * 100, 2) AS to_m2_pct,   -- 核心指标：M1→M2等
       ROUND(SUM(CASE WHEN to_bucket='M3' THEN outstanding_amt ELSE 0 END)
             / NULLIF(SUM(outstanding_amt),0) * 100, 2) AS to_m3_pct,
       ROUND(SUM(outstanding_amt)/10000, 2)       AS base_amt_wan       -- 分母余额（万元）
FROM valid
GROUP BY from_bucket;
```

结果解读：窗口法一次扫描即可产出任意月份的迁徙矩阵，把WHERE里的 stat_month 参数化就能批量回溯12个月迁徙率序列，适合做趋势看板与vintage建模取数。

> Hive/Spark SQL 差异：Hive 中 `DATE_ADD(stat_month,1)` 是加天，月份校验改用 `add_months(stat_month,1)=next_month`；亿级快照按 stat_month 分区后取两个月分区即可；Spark 3 支持 `RANGE BETWEEN INTERVAL` 时间帧，可做更灵活的时点状态分析（MySQL 不支持 INTERVAL 帧）。

### 5. 性能分析与优化
解法一取两个月分区后自连接，代价=两分区扫描+一次哈希连接，百万级借据秒级完成；解法二需对全表（所有月份）做窗口排序，单月统计时代价反而更高，但一次扫描可产出全部月份，滚动监控更划算。优化建议：①快照表按 stat_month RANGE 分区（Hive/Spark）或建 (stat_month, loan_id) 复合索引（MySQL）；②结清件在快照表保留"余额0+状态结清"记录，可把LEFT JOIN退化为等值JOIN；③月度迁徙结果预计算写入 vintage 结果表，看板只查结果；④dpd_bucket 由 overdue_days 派生时建议在快照写入时物化，避免查询期CASE重算。

### 6. 面试延伸考点
- **迁徙率用余额口径还是户数口径？各有什么问题？** 要点：余额口径反映风险暴露但受大额单笔扰动；户数口径稳定但低估大额风险；月报双口径并报并注明用途。
- **如何用迁徙率推导vintage最终损失率？** 要点：沿M1→M2→M3→M4→核销逐段迁徙率连乘再乘净损失率，得到边际损失假设，用于新放款资产的拨备计提与定价。
- **M0→M1迁徙率突升但M1→M2正常，先查什么？** 要点：区分"进来的多"（进件质量、出账异常）与"催回的少"（首催触达率），先查前端再查催收，避免误下结论。
- **客户月内部分还款导致桶内跳变，怎么处理？** 要点：以月末时点状态为准（快照口径），不用月内最低逾期天数，防止美化资产质量。

### 7. 业务拓展思考
迁徙矩阵是信贷资产质量管理的"心电图"：向上支撑vintage损失曲线与拨备假设，向下定位催收各环节效能。联动动作：M1→M2超阈值时触发外呼产能扩容与机器人外呼优先级调整；M2→M3抬升时评估诉前调解与批量法诉模型。口径延展：可细分到产品线、获客渠道、额度档的迁徙矩阵，或引入"回正后30天再逾期率"衡量回正质量，防止用无实质还款能力的展期冲短期回正率，这也是监管套利检查的关注点。

## FIN-33 催收回收率账龄×渠道×坐席多维分析

### 1. 业务背景
某消费金融公司催收运营部（谁）每月初复盘上月委案回收表现（何时/什么）：案件按账龄段（M1/M2/M3）分派至电话、短信、外访三类渠道和具体坐席，需要输出"账龄×渠道"回收率矩阵与"账龄内坐席回收率排名"（为什么）。业务背景是催收资源有限：M1案件回收弹性大、适合电话与短信批量触达；M3案件指向法诉与外访，坐席技能差异显著。多维交叉分析避免"把接手M1好收案件的坐席误判为全能、把背M3烂账的坐席误判为低能"的考核不公；同时监管对催收频次与外访行为有红线要求，回收率分析必须与合规指标并跑。

### 2. 表结构说明
表名：collections（催收案件月度回收汇总表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| case_id | BIGINT | 案件号 |
| loan_id | BIGINT | 关联借据号 |
| aging_bucket | VARCHAR(10) | 委案时账龄段：M1/M2/M3 |
| channel | VARCHAR(20) | 催收渠道：电话/短信/外访 |
| agent_id | INT | 坐席编号（短信批量案件为NULL） |
| assigned_amt | DECIMAL(16,2) | 委案金额 |
| recovered_amt | DECIMAL(16,2) | 当月回收金额 |
| collect_month | DATE | 统计月（月末） |

示例数据：

| case_id | loan_id | aging_bucket | channel | agent_id | assigned_amt | recovered_amt | collect_month |
|---|---|---|---|---|---|---|---|
| 90001 | L2001 | M1 | 电话 | 101 | 12000.00 | 6000.00 | 2025-06-30 |
| 90002 | L2010 | M1 | 短信 | NULL | 8000.00 | 800.00 | 2025-06-30 |
| 90003 | L2021 | M2 | 电话 | 102 | 25000.00 | 5000.00 | 2025-06-30 |
| 90004 | L2030 | M3 | 外访 | 103 | 60000.00 | 18000.00 | 2025-06-30 |
| 90005 | L2031 | M1 | 电话 | 101 | 15000.00 | 9000.00 | 2025-06-30 |

### 3. 解题思路
指标口径：回收率=SUM(recovered_amt)/SUM(assigned_amt)，按账龄×渠道矩阵输出；坐席排名必须在同账龄段内比较（不同账龄难度不可比），且回收率要与回收规模双指标联看，防止"小案高率"刷榜。**【面试高频】** 坐席排名若不控制账龄变量，M1坐席天然霸榜、M3坐席天然垫底，考核结论完全失真——面试官常以此考察"控制变量"意识。实现路径：解法一用 GROUP BY ... WITH ROLLUP 配合 GROUPING() 函数一次输出"明细→渠道小计→账龄小计→总计"多层级；解法二先按坐席×账龄聚合，再用窗口 RANK() 在账龄组内排名产出效能榜并打标签。易错点：短信渠道坐席为NULL不能丢行；委案金额为0的脏数据要过滤；并列名次用RANK而非ROW_NUMBER；回收率必须配金额列一起看。

### 4. 参考解法

**解法一：WITH ROLLUP + GROUPING() 多层级汇总**

```sql
SELECT
    COALESCE(aging_bucket, '全部账龄')  AS aging_bucket,   -- 账龄维度（汇总行置空，用COALESCE打标）
    COALESCE(channel, CASE WHEN GROUPING(channel)=1 THEN '全部渠道' ELSE '渠道小计' END) AS channel, -- 渠道维度
    ROUND(SUM(recovered_amt) / NULLIF(SUM(assigned_amt),0) * 100, 2) AS recovery_pct,  -- 回收率%
    ROUND(SUM(assigned_amt)/10000, 2)                                AS assigned_wan,   -- 委案金额（万元）
    ROUND(SUM(recovered_amt)/10000, 2)                               AS recovered_wan,  -- 回收金额（万元）
    GROUPING(aging_bucket) AS g_aging,                               -- 1表示该维度是汇总行
    GROUPING(channel)      AS g_channel
FROM collections
WHERE collect_month = '2025-06-30'
  AND assigned_amt > 0                                  -- 过滤零委案脏数据
GROUP BY aging_bucket, channel WITH ROLLUP             -- 一条SQL输出：明细→渠道→账龄→总计
ORDER BY GROUPING(aging_bucket), aging_bucket,
         GROUPING(channel), channel;                   -- GROUPING()=1的汇总行排到各组末尾
```

结果解读：矩阵显示M1短信回收率虽低但近乎零成本，M3外访回收率最高且集中于个别坐席，提示M3案件应向头部坐席倾斜、M1继续放量短信。

**解法二：坐席效能榜（窗口排名 + 规模约束）**

```sql
WITH agent_stat AS (                                    -- 坐席×账龄粒度聚合
    SELECT aging_bucket,
           agent_id,
           SUM(assigned_amt)  AS assigned_amt,          -- 委案金额
           SUM(recovered_amt) AS recovered_amt,         -- 回收金额
           ROUND(SUM(recovered_amt)/NULLIF(SUM(assigned_amt),0)*100, 2) AS recovery_pct  -- 回收率
    FROM collections
    WHERE collect_month = '2025-06-30'
      AND agent_id IS NOT NULL                          -- 短信批量案件无坐席，排除出人工榜
      AND assigned_amt > 0
    GROUP BY aging_bucket, agent_id
),
ranked AS (                                             -- 账龄组内双指标排名
    SELECT *,
           RANK() OVER (PARTITION BY aging_bucket ORDER BY recovery_pct DESC)  AS rate_rank,  -- 回收率排名（并列同名次）
           RANK() OVER (PARTITION BY aging_bucket ORDER BY recovered_amt DESC) AS size_rank  -- 回收规模排名
    FROM agent_stat
)
SELECT aging_bucket, agent_id,
       ROUND(assigned_amt/10000, 2)  AS assigned_wan,   -- 委案规模（万元）
       ROUND(recovered_amt/10000, 2) AS recovered_wan,  -- 回收规模（万元）
       recovery_pct,
       rate_rank, size_rank,
       CASE WHEN rate_rank <= 3 AND size_rank <= 3 THEN '核心坐席'
            WHEN rate_rank <= 3               THEN '高率小案型'
            WHEN size_rank <= 3               THEN '走量型'
            ELSE '待提升' END                 AS agent_tag   -- 双指标联看的坐席标签
FROM ranked
ORDER BY aging_bucket, rate_rank;
```

结果解读："高率小案型"坐席适合承接M1小额案件走人海战术，"走量型"坐席适合M3大案专项清收，实现人案匹配而非一刀切考核。

> Hive/Spark SQL 差异：Hive 支持 WITH ROLLUP 但老版本无 GROUPING() 函数，可改用 GROUPING SETS((aging_bucket,channel),(aging_bucket),()) 显式声明汇总层级；大案件量下先按 collect_month 分区裁剪再聚合。

### 5. 性能分析与优化
解法一单次扫描完成，ROLLUP 在聚合阶段同步产出多层级，几乎无额外代价；解法二多一层窗口排序（坐席通常几百人，开销可忽略）。瓶颈都在明细表扫描：优化建议——① collections 按 collect_month 分区或建 (collect_month, aging_bucket, channel, agent_id) 复合索引，查询裁剪后只扫当月；② 建立"月度坐席效能"预聚合表供考核系统读取，避免实时SUM亿级回收流水；③ 案件明细与回收流水分表时，先按案件日粒度合并成月度宽表再分析；④ 委案/回收金额用DECIMAL并校验负值冲正记录，防止回收率超100%。

### 6. 面试延伸考点
- **坐席排名还有哪些混淆变量？如何消除？** 要点：账龄、额度大小、客户地域、案件新旧批次都影响难度；严格考核用同层随机分派实验，或按历史难度系数标准化后排名。
- **回收率高就代表坐席能力强吗？** 要点：可能承接了易收案件，或用高强度催收换回收但投诉率飙升；应加入投诉率、回退率（回收后撤销）作约束指标。
- **如何验证"外访对M3更有效"？** 要点：对同质M3案件随机分派外访与电话做AB实验，比较回收率差异并做显著性检验，避免用观察数据自证。
- **COUNT(agent_id)与COUNT(*)在短信案件上的差异？** 要点：COUNT(agent_id)不计NULL行，统计"人工坐席案件量"用前者、统计"总案件量"用后者，口径混淆会虚增或漏计。

### 7. 业务拓展思考
该多维框架可延展为"催收ROI"口径：渠道ROI=(回收金额−渠道人力成本)/成本，短信成本近零但回收率低，外访成本高需看边际回收。联动动作：按账龄×渠道矩阵动态调整分案引擎权重；连续两月垫底坐席触发培训或调岗；M3+存量建立"委外vs自催"对比分析。合规延展：回收率看板与通话频次、夜间外呼次数、投诉率并跑，任一合规指标越线的坐席回收额不计入考核，防止为指标达标触碰催收监管红线。

## FIN-34 客户90天未交易流失预警特征对比

### 1. 业务背景
某股份制银行零售条线数字化团队（谁）在搭建流失预警模型前先做特征区分度盘点（何时/什么）：将"最近一笔任何交易距今超过90天"定义为流失，对比流失组与活跃组在月均交易笔数、笔均金额、渠道线上化率等行为特征上的均值差异，差异显著的特征才有资格进入预警模型（为什么）。这道题的隐蔽陷阱是"观察窗错位"：若统一用"最近6个月"算特征，流失客户窗口内几乎没有交易，组间差异是定义使然而非行为信号，模型上线后会"完美复述定义、毫无预测力"；正确做法是把特征回溯窗口锚定在各自"最后交易日"向前推6个月，比较两组都在"行为活跃期"内的表现。

### 2. 表结构说明
表名：transactions（交易流水表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户号 |
| txn_date | DATE | 交易日期 |
| txn_type | VARCHAR(20) | 交易类型：消费/转账/取现/缴费 |
| txn_amt | DECIMAL(16,2) | 交易金额 |
| txn_channel | VARCHAR(20) | 渠道：APP/网银/柜面/POS |

示例数据：

| txn_id | customer_id | txn_date | txn_type | txn_amt | txn_channel |
|---|---|---|---|---|---|
| 50001 | 30001 | 2025-01-15 | 消费 | 350.00 | APP |
| 50002 | 30001 | 2025-03-10 | 转账 | 5000.00 | APP |
| 50003 | 30002 | 2025-06-20 | 消费 | 128.00 | POS |
| 50004 | 30002 | 2025-06-28 | 缴费 | 200.00 | APP |
| 50005 | 30003 | 2024-12-05 | 取现 | 1000.00 | 柜面 |

（约定基准日为 2025-06-30，用固定日期代替NOW()保证结果可复现：30001与30003为流失组，30002为活跃组。）

### 3. 解题思路
口径：流失=MAX(txn_date)<基准日−90天，以"最近一次任何类型交易"计。解法一是反面教材版：特征窗口统一锚定基准日前6个月，流失组特征必然趋近于零，用它向面试官说明"为什么错"；解法二是正确版：每人的特征窗口锚定在其"最后交易日"向前推6个月，两组都在各自活跃期内比较。实现路径：第一层CTE求每客户最后交易日并打流失标记；第二层JOIN流水取"最后交易日前6个月"窗口内明细聚合特征（月均笔数、笔均金额、线上化率）；第三层按组聚合对比。**【加分点】** 观察窗对齐是流失分析的灵魂——面试中主动指出"统一窗口下的组间差异是结果不是原因"，并给出对齐方案，是区分初级与高级候选人的关键信号。易错点：流失客户窗口内交易为空导致AVG为NULL需COALESCE；"恰好90天"的边界归属要约定；活跃组的幸存者偏差要在结论中声明。

### 4. 参考解法

**解法一：统一基准窗（常见错误写法，用于对比说明）**

```sql
WITH cust_last AS (                                  -- 每位客户的最后交易日与流失标记
    SELECT customer_id,
           MAX(txn_date) AS last_txn_date,           -- 最近一次交易
           CASE WHEN MAX(txn_date) < DATE_SUB('2025-06-30', INTERVAL 90 DAY)
                THEN '流失' ELSE '活跃' END AS grp   -- 90天未交易即流失
    FROM transactions
    GROUP BY customer_id
),
feat AS (                                            -- 统一取基准日前6个月窗口（错误示范）
    SELECT t.customer_id,
           COUNT(*) AS txn_cnt,                      -- 窗口内交易笔数
           AVG(t.txn_amt) AS avg_amt,                -- 笔均金额
           AVG(CASE WHEN t.txn_channel IN ('APP','网银') THEN 1.0 ELSE 0 END) AS online_rate  -- 线上化率
    FROM transactions t
    WHERE t.txn_date BETWEEN DATE_SUB('2025-06-30', INTERVAL 6 MONTH) AND '2025-06-30'
    GROUP BY t.customer_id
)
SELECT c.grp,                                        -- 流失/活跃分组
       COUNT(*) AS cust_cnt,                         -- 组内人数
       ROUND(AVG(COALESCE(f.txn_cnt,0)), 2)     AS win_txn_cnt,    -- 窗口内笔数均值（流失组恒为0）
       ROUND(AVG(COALESCE(f.avg_amt,0)), 2)     AS avg_amount,
       ROUND(AVG(COALESCE(f.online_rate,0)), 4) AS avg_online_rate
FROM cust_last c
LEFT JOIN feat f ON f.customer_id = c.customer_id    -- 流失客户窗口内无交易，特征补0
GROUP BY c.grp;
-- 该写法下流失组交易特征恒为0，“巨大区分度”只是口径造成的假象
```

结果解读：流失组各项特征≈0、活跃组正常，看似差异巨大但毫无模型价值——它只是"流失"定义的重复表达，这就是观察窗错位谬误，保留此版是为了演示识别错误的能力。

**解法二：锚定最后交易日的对齐窗口（正确做法）**

```sql
WITH cust_last AS (                                        -- 第一步：最后交易日 + 流失标记
    SELECT customer_id,
           MAX(txn_date) AS last_txn_date,
           CASE WHEN MAX(txn_date) < DATE_SUB('2025-06-30', INTERVAL 90 DAY)
                THEN '流失' ELSE '活跃' END AS grp
    FROM transactions
    GROUP BY customer_id
),
win_txn AS (                                               -- 第二步：把每人的观察窗锚定在其最后交易日前6个月
    SELECT c.customer_id, c.grp,
           COUNT(*) AS txn_cnt,                            -- 活跃期6个月交易笔数
           AVG(t.txn_amt) AS avg_amt,                      -- 笔均金额
           AVG(CASE WHEN t.txn_channel IN ('APP','网银') THEN 1.0 ELSE 0 END) AS online_rate,
           COUNT(DISTINCT DATE_FORMAT(t.txn_date,'%Y-%m')) AS active_months  -- 有交易的月份数
    FROM cust_last c
    JOIN transactions t
      ON t.customer_id = c.customer_id
     AND t.txn_date BETWEEN DATE_SUB(c.last_txn_date, INTERVAL 6 MONTH) AND c.last_txn_date
    GROUP BY c.customer_id, c.grp
)
SELECT grp,
       COUNT(*) AS cust_cnt,                                              -- 组人数
       ROUND(AVG(txn_cnt/NULLIF(active_months,0)), 2) AS avg_txn_per_month,  -- 活跃月均笔数（剔除空月稀释）
       ROUND(AVG(avg_amt), 2)                         AS avg_amount,      -- 笔均金额对比
       ROUND(AVG(online_rate), 4)                     AS avg_online_rate, -- 线上化率对比
       ROUND(AVG(active_months), 2)                   AS avg_active_months-- 平均活跃月数（粘性）
FROM win_txn
GROUP BY grp
ORDER BY grp;
-- 两组都取“各自最后活跃期内”的行为，均值差异才具备进入预警模型的资格
```

结果解读：对齐后若流失组笔均金额更低、线上化率更弱、活跃月更少，可提炼"低频、低粘性、低线上"三低画像作为预警规则候选特征，并按差异幅度排优先级。

> Hive/Spark SQL 差异：亿级流水按 txn_date 分区，锚定窗口过滤尽量下推到分区裁剪；DATE_SUB 在 Hive 中是天数减法，月份回溯用 add_months；客户上亿时 cust_last 聚合先按 customer_id 分桶避免数据倾斜。

### 5. 性能分析与优化
解法一一次聚合+一次LEFT JOIN代价低，但结论无效；解法二JOIN流水会放大行数（每客户6个月明细），流水重度用户（数万笔）下代价高。优化建议：① transactions 建 (customer_id, txn_date) 复合索引，使锚定窗口检索走索引范围扫描；② 更优做法是先建"客户×月"预聚合表（月笔数、月金额、月线上笔数），第二层改为对月表取"最后交易日前6个自然月"，完全不碰明细；③ 千万级以上迁移Hive按月分区，锚定过滤与分区裁剪结合；④ 基准日参数化传入，避免硬编码导致脚本不可复用。

### 6. 面试延伸考点
- **为什么观察窗必须对齐到各自最后交易日？** 要点：两组必须在可比的生命周期阶段取特征，否则差异是"结果"不是"原因"，模型会把定义复述一遍、上线即失效。
- **流失用90天未交易定义合理吗？如何验证？** 要点：统计历史上"90天未交易客户"的后续回流量，回流高则阈值太紧；结合业务周期（代发客群看工资到账间隔）分客群定阈值。
- **活跃组幸存者偏差如何影响结论？** 要点：活跃组是"被市场验证留存"的群体，特征差异被放大；可用cohort视角按注册月分层再对比，或限制两组开户时长一致。
- **如何用SQL直接产出预警名单？** 要点：筛 last_txn_date 落在"距今60-90天"（即将流失）且满足低频低粘性特征的客户，输出客户号与建议动作供营销触达。

### 7. 业务拓展思考
该对比是流失预警模型的特征前置筛选环节：差异不显著直接剔除，显著特征再进模型算IV值。联动动作：对"即将流失"（60-90天）客群配置App权益推送、代发客群工资到账提醒等挽留策略，并做AB实验验证挽回率提升；对已流失高AUM客户转入客户经理电话挽回队列。口径延展：流失定义可按客群分层（高AUM用180天宽口径、年轻客群用60天紧口径），特征可扩展交易金额变异系数、渠道迁移轨迹（柜面→APP迁移停滞常是流失前兆）。

## FIN-35 大额与高频异常交易识别

### 1. 业务背景
某商业银行反洗钱中心（谁）按《金融机构大额交易和可疑交易报告管理办法》开展可疑交易筛查（何时/什么）：规则一，单笔转账≥50万元且发生在夜间（22:00-6:00）或为跨行交易；规则二，同一客户同一天发生3笔及以上相同金额的转账（疑似拆单规避大额申报）且当日合计≥30万元（为什么）。命中线索输出给反洗钱专岗人工排查：漏报面临监管处罚，误报过多则排查成本失控，因此SQL既要口径准确，又要能支撑亿级流水的T+1日常批跑。这道题综合考察复合规则拆解、时间条件处理与大数据量下的写法取舍，是风控数据岗的高频笔试压轴。

### 2. 表结构说明
表名：transactions（交易流水表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 交易流水号 |
| customer_id | BIGINT | 客户号 |
| txn_time | DATETIME | 交易时间（精确到秒） |
| txn_type | VARCHAR(20) | 类型：转账/消费/取现 |
| txn_amt | DECIMAL(16,2) | 交易金额 |
| counterparty | VARCHAR(64) | 对方账户 |
| is_cross_bank | TINYINT | 是否跨行：1是/0否 |

示例数据：

| txn_id | customer_id | txn_time | txn_type | txn_amt | counterparty | is_cross_bank |
|---|---|---|---|---|---|---|
| 70001 | 40001 | 2025-06-18 23:15:00 | 转账 | 620000.00 | 6222...881 | 1 |
| 70002 | 40002 | 2025-06-18 10:02:00 | 转账 | 290000.00 | 6222...332 | 0 |
| 70003 | 40002 | 2025-06-18 10:05:00 | 转账 | 290000.00 | 6222...774 | 0 |
| 70004 | 40002 | 2025-06-18 10:09:00 | 转账 | 290000.00 | 6222...915 | 0 |
| 70005 | 40003 | 2025-06-19 02:40:00 | 转账 | 80000.00 | 6222...126 | 0 |

（40002当日三笔等额各29万、合计87万≥30万命中规则二；40001命中规则一。）

### 3. 解题思路
两条规则性质不同：规则一是单行过滤（金额阈值+时间/跨行条件）；规则二需要"分组计数"维度。解法一按"客户+日期+金额"GROUP BY聚合识别同日等额多笔，输出线索级汇总，天然适合批跑；解法二用窗口 COUNT(*) OVER(PARTITION BY 客户, 日期, 金额) 直接在明细行打标，保留每笔明细供排查报告，并把两条规则合成一份清单。**【避坑指南】** DATE(txn_time) 包裹索引列会使时间索引失效、退化为全表扫描，亿级流水必须改为半开区间谓词（txn_time >= '日 00:00:00' AND < '次日 00:00:00'）或冗余交易日期列；夜间时段跨午夜（22:00-次日6:00）要写成 HOUR 双分支；金额等额比较用DECIMAL防浮点误差；代发工资分批等合法等额场景需白名单豁免，避免误伤。

### 4. 参考解法

**解法一：聚合汇总法（输出线索级结果）**

```sql
WITH split_risk AS (                                -- 规则二：同日同额多笔聚合识别
    SELECT customer_id,
           DATE(txn_time)          AS txn_day,      -- 交易自然日（聚合键，非索引过滤位）
           txn_amt,                                 -- 相同金额作为分组键之一
           COUNT(*)                AS same_amt_cnt, -- 当日同额笔数
           SUM(txn_amt)            AS day_amt       -- 当日该额合计
    FROM transactions
    WHERE txn_type = '转账'
      AND txn_time >= '2025-06-18 00:00:00'         -- 半开区间写法：可走时间索引
      AND txn_time <  '2025-06-20 00:00:00'
    GROUP BY customer_id, DATE(txn_time), txn_amt
    HAVING COUNT(*) >= 3                            -- 疑似拆单：3笔及以上等额
       AND SUM(txn_amt) >= 300000                   -- 且当日合计达30万阈值
)
SELECT '规则二-同日等额拆分' AS rule_name,           -- 线索类型
       customer_id,
       txn_day    AS hit_date,                       -- 命中日
       txn_amt    AS typical_amt,                    -- 典型单笔金额
       same_amt_cnt,
       ROUND(day_amt/10000,2) AS amount_wan          -- 涉案金额（万元）
FROM split_risk
UNION ALL                                            -- 两条规则纵向合并为一份线索清单
SELECT '规则一-大额敏感交易' AS rule_name,
       customer_id,
       DATE(txn_time),
       txn_amt,
       1,
       ROUND(txn_amt/10000,2)
FROM transactions
WHERE txn_type = '转账'
  AND txn_amt >= 500000                              -- 大额阈值50万
  AND ( HOUR(txn_time) >= 22 OR HOUR(txn_time) < 6   -- 夜间时段（跨午夜用HOUR双分支）
        OR is_cross_bank = 1 )                       -- 或跨行交易
  AND txn_time >= '2025-06-18 00:00:00'
  AND txn_time <  '2025-06-20 00:00:00';
```

结果解读：清单按规则类型区分来源，专岗优先排查"规则二且涉案金额高"的线索；拆单行为通常伴随对手方分散，可再按 counterparty 聚合做团伙挖掘。

**解法二：窗口打标法（保留明细行，两类规则一次输出）**

```sql
WITH flagged AS (                                   -- 在明细行上直接打规则标
    SELECT t.*,
           DATE(txn_time) AS txn_day,
           COUNT(*) OVER (PARTITION BY customer_id, DATE(txn_time), txn_amt)     AS same_amt_cnt,  -- 同日同额计数窗口
           SUM(txn_amt) OVER (PARTITION BY customer_id, DATE(txn_time), txn_amt) AS same_amt_sum,  -- 同日同额合计
           CASE WHEN txn_amt >= 500000
                 AND (HOUR(txn_time) >= 22 OR HOUR(txn_time) < 6 OR is_cross_bank = 1)
                THEN 1 ELSE 0 END AS hit_rule1      -- 规则一行级标记
    FROM transactions t
    WHERE txn_type = '转账'
      AND txn_time >= '2025-06-18 00:00:00'
      AND txn_time <  '2025-06-20 00:00:00'
)
SELECT txn_id, customer_id, txn_time, txn_amt,
       CASE WHEN hit_rule1 = 1 THEN '规则一-大额敏感交易'
            WHEN same_amt_cnt >= 3 AND same_amt_sum >= 300000 THEN '规则二-同日等额拆分'
       END AS rule_name,                            -- 行级命中类型（规则一优先标注）
       same_amt_cnt                                 -- 携带等额笔数上下文供排查参考
FROM flagged
WHERE hit_rule1 = 1
   OR (same_amt_cnt >= 3 AND same_amt_sum >= 300000) -- 命中任一规则即保留明细
ORDER BY customer_id, txn_time;
```

结果解读：窗口法保留每笔明细，排查报告可直接附交易清单；同一拆单事件的3笔会各自带出，落线索表时需按"客户+日期"去重生成线索号。

> Hive/Spark SQL 差异：亿级流水按 txn_day 分区批跑，窗口函数分布式执行无需自连接；Hive 用 to_date(txn_time) 与 hour()；MySQL 的生成列方案在Hive不可用，冗余日期列靠ETL写入。

### 5. 性能分析与优化
解法一聚合后数据量骤减，引擎负担小，适合T+1批跑；解法二窗口需按三键排序且输出明细行数多，落表与传输成本高。优化建议：①建 (txn_time) 分区+ (customer_id, txn_day) 复合结构，把DATE()转换前置到写入层（冗余日期列或生成列）；②金额以"分"为单位用BIGINT存储，既防浮点误差又加速等值比较；③规则一先 WHERE txn_amt>=500000 剪枝（占比极低）再判时段，过滤顺序影响巨大；④窗口分区键以 customer_id 打头利用排序复用；⑤命中结果写入可疑线索表并带处理状态字段，支撑排查闭环与规则效果回溯。

### 6. 面试延伸考点
- **拆单识别为什么限定"相同金额"而不是"相近金额"？** 要点：等额是最强信号、误报低；相近金额需聚类或分桶（如千元档），复杂度与误报率上升，可作为二期规则迭代。
- **HOUR(txn_time)能走索引吗？怎么改？** 要点：对列包函数使索引失效；改为时间戳区间谓词（22:00与次日6:00换算成完整时间戳），或写入时冗余 is_night 标志列。
- **如何评估该规则的误报率？** 要点：人工排查结论回填，计算命中线索中确认可疑的占比；或用"命中客户后续是否涉案"做滞后验证，定期淘汰低精度规则。
- **工资分批发放是合法等额场景，怎么豁免？** 要点：规则引擎加白名单层（对公代发对手方、代发协议客户），SQL输出时带上下文字段供人工判断，而不是在SQL里硬编码豁免。

### 7. 业务拓展思考
线索识别是反洗钱"规则引擎→人工排查→模型升级"闭环的第一环：人工确认结论回流为标注样本后，可训练监督模型替代低精度规则。联动动作：高频拆单命中客户触发额度管控与尽调升级；对手方网络用于团伙图谱挖掘与账户关联管控。口径延展：等额窗口可放宽到"3日内等额多笔"，并与快进快出特征（见FIN-45）组合成多特征评分；同时按监管要求区分"大额报告"（机械报送）与"可疑报告"（主观研判）两类输出，避免混为一谈。

## FIN-36 客户LTV估算与渠道获客ROI对比

### 1. 业务背景
某互联网信贷平台市场部与财务部（谁）做年度获客预算复盘（何时/什么）：信息流广告、应用商店、老客推荐三个渠道的新客，其注册后12个月贡献的综合利润（LTV）差异悬殊，需要按渠道计算"LTV/获客成本"的ROI排序，决定下年预算向哪个渠道倾斜（为什么）。行业背景是获客成本逐年抬升，单看注册CPA会严重误判——推荐渠道CPA高但客群质量好、坏账低；信息流CPA低但首逾高、生命周期短。LTV口径必须按注册月做cohort对齐：把每位客户"注册后第N个月"的利润对齐后累加，才能剔除各渠道放款节奏差异，这同时是财务口径与风险口径的衔接题。

### 2. 表结构说明
表一：customers（客户注册表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户号 |
| register_date | DATE | 注册日期 |
| channel | VARCHAR(20) | 获客渠道：信息流/应用商店/老客推荐 |

表二：customer_month_profit（客户月度综合利润表，利息+手续费−资金成本−坏账）

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户号 |
| stat_month | DATE | 月份（月末日期） |
| profit | DECIMAL(14,2) | 当月综合利润（负数为亏损） |

表三：channel_cost（渠道获客成本表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| channel | VARCHAR(20) | 渠道名 |
| cpa | DECIMAL(10,2) | 单客获客成本 |

示例数据（customers）：

| customer_id | register_date | channel |
|---|---|---|
| 60001 | 2024-07-05 | 信息流 |
| 60002 | 2024-07-18 | 老客推荐 |
| 60003 | 2024-07-22 | 应用商店 |
| 60004 | 2024-08-01 | 信息流 |
| 60005 | 2024-08-10 | 老客推荐 |

示例数据（customer_month_profit）：

| customer_id | stat_month | profit |
|---|---|---|
| 60001 | 2024-08-31 | 45.00 |
| 60001 | 2024-10-31 | 60.00 |
| 60002 | 2024-08-31 | 120.00 |
| 60003 | 2024-09-30 | -30.00 |
| 60005 | 2025-01-31 | 150.00 |

示例数据（channel_cost）：

| channel | cpa |
|---|---|
| 信息流 | 180.00 |
| 应用商店 | 95.00 |
| 老客推荐 | 220.00 |

（60001注册后第2、4个月有利润；60003当月亏损（坏账）；60004注册后12个月内无利润，是"零利润客户"，必须计入分母。）

### 3. 解题思路
口径：LTV=客户注册后第0~11月（cohort月龄）综合利润之和；渠道ROI=渠道LTV合计/(CPA×客户数)，或人均LTV/CPA。关键动作是"月龄对齐"：用 PERIOD_DIFF(利润月, 注册月) 计算 month_offset，只保留0≤offset≤11的记录，保证每个cohort的每一列都是同质的"注册后第N月"。解法一为直接汇总法：每客户SUM窗口内利润→按渠道汇总→关联成本表算ROI，简单可靠；解法二为cohort留存摊薄法：按渠道×月龄把利润对cohort总人数摊薄后累加，输出期望LTV曲线，可外推尚未满12个月的新cohort。**【避坑指南】** 统计客户LTV时必须以客户表为左表LEFT JOIN利润表——只JOIN利润明细会把"12个月零利润客户"（注册未动账）丢掉，系统性高估渠道质量，这是最常见的口径事故；同时负利润（坏账月份）必须保留不能截断，否则LTV虚高。

### 4. 参考解法

**解法一：直接汇总法（已实现LTV）**

```sql
WITH pnl AS (                                        -- 第一步：对齐月龄，取注册后12个月利润
    SELECT c.customer_id,
           c.channel,
           p.profit,
           PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM p.stat_month),       -- 利润月转YYYYMM
                       EXTRACT(YEAR_MONTH FROM c.register_date))    -- 减注册月YYYYMM
                     AS month_offset            -- 月龄：注册当月为0
    FROM customers c
    JOIN customer_month_profit p
      ON p.customer_id = c.customer_id
    WHERE PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM p.stat_month),
                      EXTRACT(YEAR_MONTH FROM c.register_date)) BETWEEN 0 AND 11
),
cust_ltv AS (                                        -- 第二步：客户级12个月累计利润（零利润客户也保留）
    SELECT c.customer_id, c.channel,
           COALESCE(SUM(p.profit), 0) AS ltv         -- LEFT JOIN补零：未动账客户按0计
    FROM customers c
    LEFT JOIN pnl p ON p.customer_id = c.customer_id
    GROUP BY c.customer_id, c.channel
)
SELECT ch.channel,                                   -- 渠道
       COUNT(l.customer_id)                          AS cust_cnt,      -- 该渠道客户数（含零利润）
       ROUND(AVG(l.ltv), 2)                          AS avg_ltv,       -- 人均12个月LTV
       MAX(ch.cpa)                                   AS cpa,           -- 单客获客成本
       ROUND(AVG(l.ltv) / MAX(ch.cpa), 2)            AS ltv_cpa_ratio, -- LTV/CPA（>1回本，>1.5健康）
       ROUND(SUM(l.ltv) - COUNT(l.customer_id) * MAX(ch.cpa), 2) AS total_value  -- 渠道净贡献（元）
FROM channel_cost ch
JOIN cust_ltv l ON l.channel = ch.channel
GROUP BY ch.channel
ORDER BY ltv_cpa_ratio DESC;
```

结果解读：老客推荐CPA虽最高，若LTV/CPA仍显著大于1.5，说明客群质量优势足以覆盖高成本，预算应加码推荐激励而非单纯压CPA；LTV/CPA<1的渠道直接进入收缩观察名单。

**解法二：cohort 留存摊薄法（可外推的期望LTV曲线）**

```sql
WITH pnl AS (                                        -- 月龄对齐（同解法一）
    SELECT c.customer_id, c.channel,
           PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM p.stat_month),
                       EXTRACT(YEAR_MONTH FROM c.register_date)) AS month_offset,
           p.profit
    FROM customers c
    JOIN customer_month_profit p ON p.customer_id = c.customer_id
    WHERE PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM p.stat_month),
                      EXTRACT(YEAR_MONTH FROM c.register_date)) BETWEEN 0 AND 11
),
cohort AS (                                          -- 每渠道cohort总人数（摊薄分母）
    SELECT channel, COUNT(*) AS cohort_cnt
    FROM customers
    GROUP BY channel
),
curve AS (                                           -- 渠道×月龄：人均摊薄利润（流失与休眠自然折算进去）
    SELECT p.channel, p.month_offset,
           SUM(p.profit) / MAX(co.cohort_cnt) AS avg_profit_per_head  -- 当月总利润÷cohort总人数
    FROM pnl p
    JOIN cohort co ON co.channel = p.channel
    GROUP BY p.channel, p.month_offset
)
SELECT channel,                                      -- 渠道
       month_offset,                                 -- 月龄0~11
       ROUND(avg_profit_per_head, 4)                 AS avg_profit_per_head,  -- 该月龄人均贡献
       ROUND(SUM(avg_profit_per_head) OVER (PARTITION BY channel ORDER BY month_offset
             ROWS UNBOUNDED PRECEDING), 2)           AS cumulative_ltv        -- 累计LTV曲线
FROM curve
ORDER BY channel, month_offset;
-- cumulative_ltv 首次超过CPA的月龄即“回本月龄”，是现金流排布的关键参数
```

结果解读：信息流若回本月龄>9个月则现金流压力大，需要配合复借周期前移放款；对未满12个月的新cohort，可用成熟cohort曲线按月龄截断外推并注明置信区间。

> Hive/Spark SQL 差异：PERIOD_DIFF 是MySQL函数，Hive 用 (year(stat_month)*12+month(stat_month)) − (year(register_date)*12+month(register_date)) 计算月龄；利润表按 stat_month 分区、客户表按 channel 分桶，亿级cohort人数先落汇总表再算曲线。

### 5. 性能分析与优化
两解法都只触及"客户×月"粒度表（远小于交易流水），核心代价在 pnl 的JOIN与月龄函数计算。优化建议：① customers 按 channel 建索引、profit 表建 (customer_id, stat_month) 复合索引；② month_offset 在ETL写入时物化为实体列，省去查询期EXTRACT+PERIOD_DIFF计算；③ 渠道ROI月报落"渠道×注册月×月龄"预聚合表，SQL只做最后一层汇总与曲线展开；④ 解法二窗口按渠道分区排序，渠道数个位数，开销可忽略；⑤ 未满观察期的cohort要打"成熟度"标记列，防止报表把截断cohort与成熟cohort直接平均。

### 6. 面试延伸考点
- **为什么用月龄对齐而不是自然月对齐？** 要点：自然月对齐会把"注册晚、观察期短"误判为价值低；cohort月龄对齐保证每列都是"注册后第N月"的同质比较，这是cohort分析的标准动作。
- **未满12个月的cohort怎么估LTV？** 要点：用成熟cohort的月龄曲线外推剩余月龄并给置信区间；或全渠道统一缩短口径为LTV6再比较，注明口径差异。
- **坏账集中在第7个月爆发，对LTV曲线形态有什么影响？** 要点：前6个月曲线虚高、风险后置，容易高估早期渠道；成熟度不足时改用"风险调整利润"（预期损失口径）作分子。
- **ROI为负的渠道应立即砍掉吗？** 要点：看边际与战略价值——新渠道有学习期、推荐渠道有生态外溢，应结合LTV趋势、客群质量迁移与增长期权综合决策。

### 7. 业务拓展思考
LTV-CPA框架是增长预算的标准语言：可延展为渠道×客群×产品的多维矩阵（信息流×安卓/iOS、推荐×新老客交叉），或把LTV拆为"利润率×单客在贷余额×生命周期"三因子定位改进杠杆。联动动作：高ROI渠道加预算同时监控首逾率防质量劣化；低ROI渠道先做素材/定价实验而非直接关停。口径延展：引入折现率得NPV口径LTV，或按"风险调整后利润"对齐财务口径；再叠加推荐裂变系数（老客推荐带来的次级新客价值），市场与财务才能坐在同一张表上对话。

## FIN-37 基金定投留存与断投节点漏斗

### 1. 业务背景
某基金销售平台用户运营团队（谁）复盘定投业务的续投表现（何时/什么）：定投用户按周/月扣款，运营需要还原"第1期→第2期→…→第12期"的逐期留存漏斗，定位断投最集中的期数节点，并区分"扣款失败"（余额不足等可挽回性原因）与"主动终止计划"两类断投原因（为什么）。业务价值在于：行业经验显示第2-4期是断投高发区，第2期留存每提升5个百分点，全年AUM增量可观；挽留手段（扣款前余额提醒、自动垫付、降档扣款）必须按断投原因精准投放，"漏斗×原因"交叉表就是投放依据，也是向产品团队论证定投体验优化的数据基础。

### 2. 表结构说明
表名：fund_deduct（定投扣款流水表，每次扣款尝试一行）

| 字段名 | 类型 | 含义 |
|---|---|---|
| deduct_id | BIGINT | 扣款流水号 |
| customer_id | BIGINT | 客户号 |
| plan_id | BIGINT | 定投计划号 |
| deduct_date | DATE | 扣款日 |
| period_no | INT | 计划内期数（从1开始） |
| deduct_status | VARCHAR(10) | 扣款结果：成功/失败 |
| fail_reason | VARCHAR(20) | 失败原因：余额不足/银行拒绝/系统异常 |
| deduct_amt | DECIMAL(12,2) | 扣款金额 |

示例数据：

| deduct_id | customer_id | plan_id | deduct_date | period_no | deduct_status | fail_reason | deduct_amt |
|---|---|---|---|---|---|---|---|
| 80001 | 50001 | P001 | 2025-01-10 | 1 | 成功 | NULL | 500.00 |
| 80002 | 50001 | P001 | 2025-02-10 | 2 | 失败 | 余额不足 | 500.00 |
| 80003 | 50001 | P001 | 2025-02-12 | 2 | 成功 | NULL | 500.00 |
| 80004 | 50002 | P002 | 2025-01-15 | 1 | 成功 | NULL | 1000.00 |
| 80005 | 50002 | P002 | 2025-02-15 | 2 | 失败 | 余额不足 | 1000.00 |

（50001第2期重试后成功，仍算留存；50002第2期失败且无后续记录，断投于第2期。）

### 3. 解题思路
口径：计划级期数留存——某计划第k期留存=该计划存在第k期"成功"扣款记录（失败重试成功也算）；漏斗=各期留存计划数/第1期成功计划数，用条件聚合一次展开12期。断投节点识别：用LEAD(period_no)看相邻扣款记录的期数跳变——"本期成功、下一动作失败且此后再无成功"即断投于下一期，并结合最后动作归因（失败→扣款失败断投；成功后无记录→主动终止/计划结束近似）。**【避坑指南】** 漏斗分母必须锚定"第1期成功"的计划数——若用"建计划数"做分母，首期即失败的无效计划会混入，分母虚高导致留存率被稀释；同时失败重试会产生同期多行，统计前必须按"计划×期数"去重，否则同一期被重复计数。易错点：期数跳跃（1→3缺2）要识别为"第2期断投"而非线性外推；客户级与计划级口径要分开。

### 4. 参考解法

**解法一：条件聚合漏斗（12期一次展开）**

```sql
WITH plan_success AS (                               -- 计划×期数去重：同期多行取“是否有过成功”
    SELECT plan_id, customer_id, period_no,
           MAX(CASE WHEN deduct_status = '成功' THEN 1 ELSE 0 END) AS is_success  -- 失败重试成功也算成功
    FROM fund_deduct
    GROUP BY plan_id, customer_id, period_no
),
base AS (                                            -- 锚定分母：第1期成功的计划数
    SELECT COUNT(*) AS base_cnt
    FROM plan_success
    WHERE period_no = 1 AND is_success = 1
)
SELECT
    ROUND(SUM(CASE WHEN p.period_no = 1  AND p.is_success=1 THEN 1 ELSE 0 END) / MAX(b.base_cnt) * 100, 2) AS p1_pct,  -- 第1期（100%基准）
    ROUND(SUM(CASE WHEN p.period_no = 2  AND p.is_success=1 THEN 1 ELSE 0 END) / MAX(b.base_cnt) * 100, 2) AS p2_pct,  -- 第2期留存
    ROUND(SUM(CASE WHEN p.period_no = 3  AND p.is_success=1 THEN 1 ELSE 0 END) / MAX(b.base_cnt) * 100, 2) AS p3_pct,  -- 第3期留存
    ROUND(SUM(CASE WHEN p.period_no = 6  AND p.is_success=1 THEN 1 ELSE 0 END) / MAX(b.base_cnt) * 100, 2) AS p6_pct,  -- 半年留存
    ROUND(SUM(CASE WHEN p.period_no = 12 AND p.is_success=1 THEN 1 ELSE 0 END) / MAX(b.base_cnt) * 100, 2) AS p12_pct, -- 一年留存
    MAX(b.base_cnt) AS base_plans                     -- 分母：首期成功计划数
FROM plan_success p
CROSS JOIN base b
WHERE p.period_no BETWEEN 1 AND 12;                   -- 只看前12期
-- 横表漏斗：p2−p1、p3−p2 的落差即各节点的流失规模
```

结果解读：若p2到p3的落差最大，说明"熬过前两期"是关键节点，运营资源应投放在第2期扣款前的余额提醒与降档弹窗。

**解法二：LEAD 跳变识别断投节点与原因**

```sql
WITH seq AS (                                        -- 每个计划内按期数+时间排序，取下一记录
    SELECT plan_id, period_no, deduct_status, fail_reason, deduct_date,
           LEAD(period_no)     OVER (PARTITION BY plan_id ORDER BY period_no, deduct_date) AS next_period,  -- 下一记录期数
           LEAD(deduct_status) OVER (PARTITION BY plan_id ORDER BY period_no, deduct_date) AS next_status,  -- 下一记录状态
           LEAD(fail_reason)   OVER (PARTITION BY plan_id ORDER BY period_no, deduct_date) AS next_reason   -- 下一记录失败原因
    FROM fund_deduct
),
break_events AS (                                    -- 断投事件：成功期之后，下一个动作没有成功
    SELECT plan_id, period_no AS last_success_period,               -- 最后成功期
           COALESCE(next_period, period_no + 1) AS dropped_at,      -- 断投期（成功后无记录则视为下一期）
           CASE WHEN next_period IS NULL THEN '主动终止/结束'
                WHEN next_status = '失败' THEN COALESCE(next_reason,'扣款失败')
                ELSE '其他' END AS drop_type                        -- 断投原因归类
    FROM seq
    WHERE deduct_status = '成功'                                    -- 只从成功记录出发找断点
      AND (next_period IS NULL                                      -- 成功后无任何记录：计划终止
           OR (next_status = '失败' AND next_period = period_no + 1))  -- 下一期首扣即失败
      AND NOT EXISTS (                                              -- 排除断点后重试成功的计划（已自动挽回）
            SELECT 1 FROM fund_deduct r
            WHERE r.plan_id = seq.plan_id
              AND r.deduct_status = '成功'
              AND r.period_no > seq.period_no )
)
SELECT dropped_at AS drop_period,                    -- 断投发生的期数
       drop_type,                                    -- 断投原因
       COUNT(DISTINCT plan_id) AS plan_cnt           -- 断投计划数
FROM break_events
GROUP BY dropped_at, drop_type
ORDER BY drop_period, plan_cnt DESC;
```

结果解读：断投分布若集中在第2-4期且原因以"余额不足"为主，说明抓手是扣款前提醒与低门槛降档，而非产品吸引力问题；"主动终止"占比高则需要挽留问卷定位体验痛点。

> Hive/Spark SQL 差异：NOT EXISTS 关联子查询在 Hive 旧版本支持有限，改写为"窗口取最后成功期 + LEFT JOIN ... IS NULL 反连接"；扣款流水大表按 deduct_date 分区，复盘只扫相关区间。

### 5. 性能分析与优化
解法一两次聚合代价线性，最优；解法二窗口+关联子查询反查，计划数千万时逐行探测代价高。优化建议：① fund_deduct 建 (plan_id, period_no, deduct_date) 复合索引支撑窗口排序与子查询探测；② ETL层预生成"计划×期数成功标志"宽表，漏斗查询退化为单表条件聚合；③ 解法二的"是否有后续成功"改为窗口倒排（row_number倒序+最后成功期标记）后用LEFT JOIN反连接，避免关联子查询；④ 只取近24个月分区数据计算，历史断投已无挽留价值。

### 6. 面试延伸考点
- **漏斗分母用"第1期成功"还是"建计划数"？差异说明什么？** 要点：建计划后首期即失败说明开通流程有强推嫌疑，两口径差值=无效计划率，本身是渠道质量指标。
- **失败重试成功算留存吗？** 要点：算，但重试成功率本身是重要运营指标；口径要在指标字典中固化，避免跨团队报表打架。
- **如何区分"主动终止"与"扣款失败断投"？数据不够时怎么办？** 要点：需要计划状态变更表；缺失时用"最后动作类型"近似并声明口径局限，不臆断。
- **漏斗显示第12期留存率反而高于第6期，可能吗？** 要点：不可能（留存单调不增），出现即口径错误——分母混用不同cohort或期数去重逻辑不一致，这是排查数据管道的信号。

### 7. 业务拓展思考
定投漏斗的价值在于把"留存率"翻译成"节点×原因"的运营指令：余额不足→扣款前提醒/余额理财自动赎回；主动终止→挽留问卷+降档方案。联动动作：对第2期即将扣款客户做自动化提醒AB实验验证留存提升；断投客户30天召回窗口内推送"重启计划费率立减"。口径延展：留存可加权扣款金额（金额留存vs期数留存），或引入"降档续投"作为软留存状态；再叠加扣款日与发薪日错配分析，把断投归因从"意愿问题"细化到"现金流问题"。

## FIN-38 黑名单规则命中率与误伤率分析

### 1. 业务背景
某银行信用卡中心风控策略部（谁）上线三条黑名单规则（R001多头借贷、R002失联、R003历史严重逾期），规则命中后审批引擎按策略拒绝部分申请（何时/什么）。策略复盘要回答两个问题：各规则的命中率（命中申请/总申请）与误伤率——被拒申请人中，其未来重新申请、获批且12个月全程正常还款的比例，这些人本可以被批准，是真实的收益损失（为什么）。误伤率过高的规则要放松阈值，命中率低且误伤高的规则直接下线；同时监管要求自动化拒绝决策可解释，规则级量化证据是合规留痕。本题考察"决策时点→未来表现"的时间序列回看关联，是风控SQL的灵魂题型。

### 2. 表结构说明
表一：risk_events（规则命中事件表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| event_id | BIGINT | 事件号 |
| application_id | BIGINT | 申请件号 |
| customer_id | BIGINT | 客户号 |
| rule_id | VARCHAR(10) | 命中规则：R001/R002/R003 |
| hit_date | DATE | 命中日期 |
| action | VARCHAR(10) | 决策动作：拒绝/人工复核/通过 |

表二：loans（申请与借据表现表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| loan_id | BIGINT | 借据号 |
| application_id | BIGINT | 申请件号 |
| customer_id | BIGINT | 客户号 |
| apply_date | DATE | 申请日期 |
| is_approved | TINYINT | 是否获批：1是/0否 |
| is_normal_12m | TINYINT | 放款后12个月是否全程正常（观察期未满为NULL） |

示例数据（risk_events）：

| event_id | application_id | customer_id | rule_id | hit_date | action |
|---|---|---|---|---|---|
| 1 | 30001 | 70001 | R001 | 2024-07-01 | 拒绝 |
| 2 | 30002 | 70002 | R001 | 2024-07-03 | 拒绝 |
| 3 | 30003 | 70003 | R002 | 2024-07-05 | 拒绝 |
| 4 | 30004 | 70004 | R003 | 2024-07-08 | 人工复核 |
| 5 | 30005 | 70001 | R003 | 2024-07-20 | 拒绝 |

示例数据（loans）：

| loan_id | application_id | customer_id | apply_date | is_approved | is_normal_12m |
|---|---|---|---|---|---|
| L9001 | 30006 | 70001 | 2024-10-15 | 1 | 1 |
| L9002 | 30007 | 70002 | 2024-11-01 | 1 | 0 |
| L9003 | 30008 | 70005 | 2024-12-10 | 1 | NULL |
| L9004 | 30009 | 70006 | 2024-09-01 | 1 | 1 |
| L9005 | 30010 | 70003 | 2025-06-20 | 1 | NULL |

（70001被R001拒后10月重新申请获批且12个月正常——对R001是一笔"误伤"证据；70002复借却逾期，不算误伤；L9003/L9005观察期未满为NULL。）

### 3. 解题思路
口径：命中率=命中规则的申请数/规则扫描申请总数，本题按规则分别统计命中量与拒绝量；误伤率=被拒客户中"hit_date之后重新申请、获批、且12个月表现正常"的占比。**【面试高频】** 观察期不足12个月的借据必须剔除（is_normal_12m IS NULL 不参与判定），而不能当0处理——右删失样本若按0算，近期被拒客户占比越高，误伤率被压得越低，会产生"规则越来越好"的系统性假象，这是面试官最爱追问的统计陷阱。实现路径：解法一事件级自关联（被拒事件×该客户后续获批借据，apply_date>hit_date）；解法二先聚后连（按客户×规则收敛后挂标签），防多对多膨胀。易错点：同一客户命中多条规则会重复计数（规则级分析可接受，总量须去重）；apply_date早于hit_date的历史借据绝不能算"未来表现"。

### 4. 参考解法

**解法一：事件×后续借据自关联（直观版）**

```sql
WITH rejected AS (                                   -- 被拒事件明细
    SELECT event_id, customer_id, rule_id, hit_date
    FROM risk_events
    WHERE action = '拒绝'
      AND hit_date >= '2024-07-01'                   -- 规则上线日（复盘周期下界）
),
future_loan AS (                                     -- 被拒客户的后续获批借据（严格晚于被拒日）
    SELECT r.event_id, r.rule_id,
           MAX(l.apply_date)    AS next_apply_date,  -- 最近一次后续申请日
           MAX(l.is_normal_12m) AS has_good_loan     -- 任一后续借据12个月正常=1（MAX自动忽略NULL=观察期不足）
    FROM rejected r
    JOIN loans l
      ON l.customer_id = r.customer_id
     AND l.apply_date > r.hit_date                   -- 时间序列约束：必须是“之后”的申请
     AND l.is_approved = 1                           -- 且获批
    GROUP BY r.event_id, r.rule_id
),
rule_stat AS (                                       -- 规则级命中与拒绝量
    SELECT rule_id,
           COUNT(*) AS hit_cnt,                                            -- 命中申请数
           SUM(CASE WHEN action='拒绝' THEN 1 ELSE 0 END) AS reject_cnt    -- 其中被拒数
    FROM risk_events
    GROUP BY rule_id
)
SELECT s.rule_id,
       s.hit_cnt,
       s.reject_cnt,
       ROUND(s.reject_cnt * 100.0 / s.hit_cnt, 2)     AS reject_rate_pct,   -- 命中即拒率%
       COUNT(f.event_id)                              AS false_hit_cnt,     -- 误伤数：被拒后复借且表现正常
       ROUND(COUNT(f.event_id) / s.reject_cnt * 100, 2) AS false_reject_pct,-- 误伤率%
       ROUND(AVG(CASE WHEN f.has_good_loan = 0 THEN 1 ELSE 0 END) * 100, 2) AS confirmed_bad_pct -- 反证：复借确实逾期占比
FROM rule_stat s
LEFT JOIN future_loan f ON f.rule_id = s.rule_id     -- 事件级误伤证据挂回规则
GROUP BY s.rule_id, s.hit_cnt, s.reject_cnt
ORDER BY false_reject_pct DESC;
```

结果解读：若R002（失联规则）误伤率显著高于R003，考虑把R002从"直接拒绝"降级为"人工复核"，用观察期收益对冲风险；confirmed_bad_pct是规则的"抓对率"，两列相加即"复借率"。

**解法二：先聚后连（客户口径防膨胀版）**

```sql
WITH rejected_cust AS (                              -- 先按“客户×规则”收敛：取每人首次被拒
    SELECT customer_id, rule_id,
           MIN(hit_date) AS first_reject_date,       -- 首次被拒日（时间锚）
           COUNT(*)      AS reject_times             -- 被拒次数（重复进件强度）
    FROM risk_events
    WHERE action = '拒绝'
    GROUP BY customer_id, rule_id
),
good_after AS (                                      -- 被拒之后是否有12个月正常的获批借据
    SELECT rc.customer_id, rc.rule_id,
           MAX(CASE WHEN l.is_approved = 1 AND l.is_normal_12m = 1
                    THEN 1 ELSE 0 END) AS ever_good  -- 任一后续好借据=1
    FROM rejected_cust rc
    JOIN loans l
      ON l.customer_id = rc.customer_id
     AND l.apply_date > rc.first_reject_date         -- 时间约束在这里完成
     AND l.is_normal_12m IS NOT NULL                 -- 右删失：观察期不足的不参与判定
    GROUP BY rc.customer_id, rc.rule_id
),
merged AS (                                          -- 客户×规则粒度合并
    SELECT rc.rule_id, rc.customer_id, rc.reject_times,
           COALESCE(g.ever_good, 0) AS ever_good     -- 无后续借据=0（未复借）
    FROM rejected_cust rc
    LEFT JOIN good_after g
           ON g.customer_id = rc.customer_id
          AND g.rule_id = rc.rule_id
)
SELECT rule_id,
       COUNT(*) AS rejected_cust_cnt,                -- 被拒客户数（客户口径）
       SUM(ever_good) AS false_reject_cnt,           -- 误伤客户数
       ROUND(SUM(ever_good) / COUNT(*) * 100, 2) AS false_reject_pct,  -- 客户口径误伤率%
       ROUND(AVG(reject_times), 2) AS avg_reject_times  -- 平均被拒次数（观察重复进件）
FROM merged
GROUP BY rule_id;
```

结果解读：客户口径把"同一客户反复被拒"收敛为一条，误伤率不会被频繁进件客户放大，适合向管理层汇报；事件口径保留决策粒度，适合引擎调参，两口径并列输出更严谨。

> Hive/Spark SQL 差异：相关子查询 Hive 支持有限，解法二可改为窗口 MIN(apply_date) OVER 或先求每客户被拒后首借再JOIN；risk_events 按 hit_date 分区，复盘只扫对应区间；客户级标签建议离线T+7固化。

### 5. 性能分析与优化
解法一事件×借据JOIN后按事件聚合，行放大可控（每人后续借据通常≤3笔）；解法二先聚后连但含JOIN条件下的范围匹配。优化建议：① risk_events 建 (rule_id, hit_date)、loans 建 (customer_id, apply_date) 复合索引，让"后续申请"检索走范围扫描；② 把"客户级未来表现"做成离线标签表（T+7更新is_normal_12m回填），策略复盘只做规则表×标签表轻量JOIN；③ 观察期判定改为硬过滤 apply_date <= 基准日−365，避免NULL语义在引擎间漂移；④ 千万级事件表迁Hive时用LEFT JOIN反连接替代相关子查询，并按 rule_id 分桶。

### 6. 面试延伸考点
- **观察期不足的借据为什么必须剔除而不是当0？** 要点：右删失偏差——近期被拒客户占比随时间上升，当0会系统性压低估伤率，制造"规则持续变好"的假象。
- **被拒后复借成功且正常还款，就一定是误伤吗？** 要点：不一定——客户资质可能随时间改善，或复借时规则已调整；严格归因要用"规则豁免随机放行"的冠军挑战实验。
- **命中率与误伤率冲突时怎么权衡？** 要点：货币化比较——每误伤一人的收益损失 vs 每放过一个坏人的预期损失（PD×LGD×EAD），阈值定在边际收益=边际损失处。
- **同一申请命中多条规则导致计数重复，怎么处理？** 要点：规则级分析按规则分别计数合理；分析总拒绝率时按申请件去重，并输出"规则组合分布"定位叠加拦截。

### 7. 业务拓展思考
规则误伤分析把风控从"只看坏账"推向"风险收益平衡"：可与评分卡分数交叉，找"规则拒绝但评分优质"的灰区客群做豁免白名单。联动动作：误伤率超阈值的规则降级为人工复核并灰度观察；"命中即拒率×误伤率"四象限决定规则上下线节奏。口径延展：误伤可细分为"误伤金额"（后续正常借据的利息贡献）使损失货币化；也可引入反事实口径——被拒客户在他行的征信表现回溯，作为更客观的外部标签，弥补本平台无借据无法验证的盲区。

## FIN-39 存款到期日分布与续存率

### 1. 业务背景
某城商行支行零售条线与资产负债管理岗（谁）做存款到期承接管理（何时/什么）：未来90天内到期的大额定期存款需按周排布承接计划，客户经理要在"到期前30天"联系客户做续存营销，支行按周统计续存率（到期本息转入新定期或自动转存的比例）评估挽留效果（为什么）。存款是负债端压舱石，大额存单集中到期而未续存会冲击流动性指标（核心负债依存度）、推高同业负债成本，因此到期分布表是司库与支行的共同语言；续存率则按周、按产品、按客户经理三个粒度同时考核，口径不统一会直接引发考核争议。

### 2. 表结构说明
表名：deposits（定期存单表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| deposit_id | BIGINT | 存单号 |
| customer_id | BIGINT | 客户号 |
| open_date | DATE | 起存日 |
| term_months | INT | 期限（月）：3/6/12/36 |
| maturity_date | DATE | 到期日 |
| principal | DECIMAL(16,2) | 存入本金 |
| rate | DECIMAL(6,4) | 年利率 |
| status | VARCHAR(10) | 状态：存续/自动转存/续存/支取 |
| renew_deposit_id | BIGINT | 续存生成的新存单号（未续存为NULL） |

示例数据：

| deposit_id | customer_id | open_date | term_months | maturity_date | principal | rate | status | renew_deposit_id |
|---|---|---|---|---|---|---|---|---|
| D1001 | 20001 | 2024-07-01 | 12 | 2025-07-01 | 500000.00 | 0.0215 | 存续 | NULL |
| D1002 | 20002 | 2024-06-20 | 12 | 2025-06-20 | 200000.00 | 0.0205 | 续存 | D2001 |
| D1003 | 20003 | 2024-05-15 | 6 | 2024-11-15 | 100000.00 | 0.0190 | 支取 | NULL |
| D1004 | 20004 | 2024-04-01 | 36 | 2027-04-01 | 800000.00 | 0.0290 | 存续 | NULL |
| D1005 | 20001 | 2025-07-01 | 12 | 2026-07-01 | 510000.00 | 0.0185 | 存续 | NULL |

（D1002到期后续存为D2001；D1003到期支取；D1001临近到期仍在存续，属于30天营销名单范围；D1005是D1001到期后同客户新开单。）

### 3. 解题思路
三块产出：①到期分布——status='存续'且maturity_date在[基准日,基准日+90]的存单按周聚合本金，输出承接排期；②到期前30天营销名单——maturity_date落在基准日+30内的存续存单及客户；③续存率——对已到期存单，用renew_deposit_id非空（或status IN('续存','自动转存')）判定续存，按到期周分组算金额口径与笔数口径续存率。**【加分点】** renew_deposit_id 依赖系统回填，数据不完整时用"同一客户到期后14日内新开定期"的时间匹配做兜底口径——两种口径的差额本身就是数据质量的度量，面试中主动提出双口径校验是重要加分项。易错点：自动转存是系统行为不算流失，要区分于人工续存；金额口径与笔数口径差异（大额单笔主导）；跨行转出在本表无记录，需资金流向数据交叉；14天宽限期用历史分布P95校准而非拍脑袋。

### 4. 参考解法

**解法一：到期分布 + 30天名单 + 精确关联续存率**

```sql
-- 第一段：未来90天到期分布与30天营销名单
WITH due AS (                                        -- 基准日口径下90天内到期的存续存单
    SELECT deposit_id, customer_id, maturity_date, principal,
           CEIL(DATEDIFF(maturity_date, '2025-06-30') / 7) AS due_week_no   -- 到期周序号（1=第1周）
    FROM deposits
    WHERE status = '存续'
      AND maturity_date BETWEEN '2025-06-30' AND DATE_ADD('2025-06-30', INTERVAL 90 DAY)
)
SELECT CONCAT('第', due_week_no, '周') AS due_week,   -- 到期周
       COUNT(*) AS deposit_cnt,                      -- 到期笔数
       ROUND(SUM(principal)/10000, 2) AS due_amt_wan,-- 到期金额（万元）
       SUM(CASE WHEN maturity_date <= DATE_ADD('2025-06-30', INTERVAL 30 DAY)
                THEN 1 ELSE 0 END) AS need_contact_cnt,  -- 30天内到期、需进营销名单的笔数
       SUM(CASE WHEN maturity_date <= DATE_ADD('2025-06-30', INTERVAL 30 DAY)
                THEN principal ELSE 0 END)/10000 AS need_contact_wan  -- 名单对应金额（万元）
FROM due
GROUP BY due_week_no
ORDER BY due_week_no;

-- 第二段：近4个月到期存单的续存率（精确关联口径）
SELECT DATE_FORMAT(d.maturity_date, '%x-W%v') AS maturity_week,       -- 到期自然周
       COUNT(*) AS matured_cnt,                                      -- 到期笔数
       ROUND(SUM(d.principal)/10000, 2) AS matured_amt_wan,          -- 到期金额（万元）
       ROUND(SUM(CASE WHEN d.status IN ('续存','自动转存') THEN d.principal ELSE 0 END)/10000, 2) AS renewed_amt_wan,  -- 续存金额
       ROUND(SUM(CASE WHEN d.status IN ('续存','自动转存') THEN d.principal ELSE 0 END)
             / NULLIF(SUM(d.principal),0) * 100, 2) AS renew_rate_amt_pct,   -- 金额口径续存率%
       ROUND(SUM(CASE WHEN d.status IN ('续存','自动转存') THEN 1 ELSE 0 END)
             / COUNT(*) * 100, 2) AS renew_rate_cnt_pct                       -- 笔数口径续存率%
FROM deposits d
WHERE d.status IN ('续存','自动转存','支取')          -- 已到期的三类去向（存续=未到期）
  AND d.maturity_date BETWEEN '2025-03-01' AND '2025-06-30'
GROUP BY maturity_week
ORDER BY maturity_week;
-- renew_deposit_id 可作二次校验：续存新单本金是否≥原本金（识别降额续存）
```

结果解读：若第3-4周出现到期高峰且30天名单笔数集中，司库需提前安排同业置换额度；金额口径续存率显著低于笔数口径时，说明流失集中在大额客户，应转客户经理一对一维护。

**解法二：renew字段缺失时的时间匹配兜底口径**

```sql
WITH matured AS (                                    -- 近期到期存单（不依赖renew回填）
    SELECT d1.deposit_id, d1.customer_id, d1.maturity_date, d1.principal
    FROM deposits d1
    WHERE d1.maturity_date BETWEEN '2025-03-01' AND '2025-05-31'
      AND d1.status <> '自动转存'                    -- 自动转存系统内已闭环，直接视为续存
),
renewed_by_time AS (                                 -- 兜底判定：同客户到期后14天内新开定期即视为续存
    SELECT m.deposit_id,
           MAX(d2.deposit_id) AS matched_new_id,     -- 匹配到的新存单
           MAX(d2.open_date)  AS matched_open_date   -- 新单起存日（验证宽限期分布用）
    FROM matured m
    JOIN deposits d2
      ON d2.customer_id = m.customer_id
     AND d2.open_date  >  m.maturity_date            -- 必须在到期之后
     AND d2.open_date  <= DATE_ADD(m.maturity_date, INTERVAL 14 DAY)  -- 14天宽限期
     AND d2.deposit_id <> m.deposit_id               -- 排除自身
    GROUP BY m.deposit_id
)
SELECT DATE_FORMAT(m.maturity_date, '%x-W%v') AS maturity_week,
       COUNT(*) AS matured_cnt,
       ROUND(SUM(CASE WHEN r.deposit_id IS NOT NULL THEN m.principal ELSE 0 END)/10000, 2) AS renewed_amt_wan,
       ROUND(SUM(CASE WHEN r.deposit_id IS NOT NULL THEN m.principal ELSE 0 END)
             / NULLIF(SUM(m.principal),0) * 100, 2) AS renew_rate_approx_pct   -- 时间匹配口径续存率%（近似）
FROM matured m
LEFT JOIN renewed_by_time r ON r.deposit_id = m.deposit_id
GROUP BY maturity_week
ORDER BY maturity_week;
```

结果解读：时间匹配口径通常略高于精确关联口径，差额是把"资金短暂挪用后回流"误判为续存的部分；两口径并报并注明版本，汇报口径才站得住。

> Hive/Spark SQL 差异：存单表百万级差异不大；若按 open_date 分区，时间匹配JOIN的连接键在 maturity_date 上会导致分区裁剪失效，可改广播JOIN（d2为小表）或按 customer_id 分桶后桶内匹配。

### 5. 性能分析与优化
两解法均为单表聚合+一次JOIN，存单表千万级内无压力。优化建议：① (maturity_date, status) 复合索引直接覆盖到期分布查询；② renew_deposit_id 建索引加速精确关联；③ 续存率周报落预聚合表，按周增量更新；④ 14天时间匹配是范围JOIN，MySQL 8.0 无 range join 优化，客户量大时先按 customer_id 哈希分桶再桶内匹配（或迁Spark）；⑤ 到期名单需关联客户经理归属表分派，归属关系按月固化快照，防止当月人员调动导致名单错派。

### 6. 面试延伸考点
- **自动转存算续存吗？对口径有什么影响？** 要点：算，但它是无人工触达的被动续存；评估营销有效性时应单独报"主动续存率"，两个口径混用会高估营销效果。
- **金额口径和笔数口径差很多说明什么？** 要点：大额单笔主导金额口径，差额指向"大户流失"还是"广撒网失败"，两者对应完全不同的挽留策略。
- **14天宽限期怎么定的？** 要点：用历史已续存客户实际转存日分布的P95校准，避免拍脑袋；宽限期越长续存率高估越严重，需在口径文档中固化。
- **如何评估到期前营销的真实增量？** 要点：对30天名单随机留白做对照组，比较"触达组续存率−对照组"，防止把自然续存记为营销功劳。

### 7. 业务拓展思考
到期承接是负债成本管理的抓手：续存率按期限、利率档交叉后可指导"到期定价"——对价格敏感度低的客户降点续接，直接节约付息成本。联动动作：30天名单分派客户经理并按周跟踪触达率、App到期提醒自动化、对他行高息对比客户启用挽留话术。口径延展：可做"续存金额保持率"（新存单本金/原本金）识别降额续存；结合客户AUM变化区分"到期离行"还是"内部搬家"（转理财/基金），后者对全行中收反而是利好，不能一刀切算流失。

## FIN-40 信用卡分期每期回收计划表

（F001第3期只回收4000/10000，达成率40%，是催收线索；F002第1期只还5000，可能部分还款。）

### 3. 解题思路
核心是"期数展开"：MySQL 8.0 无 generate_series，两种办法——递归CTE逐期生成，或数字辅助表（两张0-9小表笛卡尔构造1..100序列）。展开后每期计划本金=principal_total/total_periods，末期用"总额−前N−1期之和"吸收四舍五入尾差；每期手续费按总额×每期费率简化（等额本息真实IRR口径见延伸考点）。再LEFT JOIN实际回收按(installment_id, period_no)双键对齐，产出每期达成率与状态机（已回收/逾期未收/未到期/提前结清）。**【避坑指南】** 逐期ROUND的累计尾差会让计划合计≠总额，对账必然不平——末期兜底法是标准解；递归CTE受 cte_max_recursion_depth（默认1000）限制，期数虽小但要知道这个参数的存在；实际还款未按期数归集（还款冲抵顺序）时，对齐口径必须先与账务系统确认，这是业务对齐能力考点。

### 4. 参考解法

**解法一：递归CTE 展开期数**

```sql
WITH RECURSIVE period_list AS (                      -- 递归生成1..24的期数序列
    SELECT 1 AS period_no                            -- 递归种子：第1期
    UNION ALL
    SELECT period_no + 1 FROM period_list WHERE period_no < 24   -- 递归体：最长24期
),
plan AS (                                            -- 合约×期数 = 每期计划行
    SELECT i.installment_id, i.customer_id, i.total_periods, i.principal_total, i.fee_rate_month,
           p.period_no,
           DATE_ADD(i.first_repay_month, INTERVAL p.period_no - 1 MONTH) AS due_month,  -- 该期应还月
           ROUND(i.principal_total / i.total_periods, 2) AS plan_principal,             -- 每期计划本金（等额）
           ROUND(i.principal_total * i.fee_rate_month, 2) AS plan_fee                   -- 每期计划手续费（总额×费率）
    FROM installments i
    JOIN period_list p ON p.period_no <= i.total_periods          -- 只展开到合约期数
),
actual AS (                                          -- 实际回收按合约×期数聚合
    SELECT installment_id, period_no,
           SUM(actual_principal) AS act_principal,
           SUM(actual_fee)       AS act_fee,
           MAX(repay_date)       AS last_repay_date,
           MAX(is_early_settle)  AS is_early_settle
    FROM repayment_actuals
    GROUP BY installment_id, period_no
)
SELECT pl.installment_id,
       pl.period_no,                                                  -- 期数
       pl.due_month,                                                  -- 应还月
       pl.plan_principal,                                             -- 计划本金
       pl.plan_fee,                                                   -- 计划手续费
       COALESCE(a.act_principal, 0) AS act_principal,                 -- 实收本金
       ROUND(COALESCE(a.act_principal,0) / NULLIF(pl.plan_principal,0) * 100, 1) AS period_rate_pct, -- 当期本金达成率%
       CASE WHEN a.is_early_settle = 1 THEN '提前结清'
            WHEN a.last_repay_date IS NULL AND pl.due_month < '2025-06-30' THEN '逾期未收'  -- 应还月已过仍无回收
            WHEN a.last_repay_date IS NULL THEN '未到期'
            ELSE '已回收' END AS period_status                         -- 期级状态机
FROM plan pl
LEFT JOIN actual a
       ON a.installment_id = pl.installment_id
      AND a.period_no     = pl.period_no              -- 合约+期数双键对齐
ORDER BY pl.installment_id, pl.period_no;
```

结果解读：期级"逾期未收"行就是催收工作清单的种子；把达成率按期数透视可发现"第N期断崖"（12期分期常在第6-8期达成率骤降，与持卡人资金周期相关）。

**解法二：数字辅助表法（无递归开销）**

```sql
WITH digits AS (                                     -- 0-9十个数字的小表
    SELECT 0 AS n UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
    UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9
),
period_list AS (                                     -- d1.n + d2.n*10 + 1 构造 1..100 序列
    SELECT d1.n + d2.n * 10 + 1 AS period_no
    FROM digits d1 CROSS JOIN digits d2
),
plan AS (                                            -- 带费率的最终计划行
    SELECT i.installment_id, p.period_no,
           CASE WHEN p.period_no = i.total_periods
                THEN i.principal_total - ROUND(i.principal_total / i.total_periods, 2) * (i.total_periods - 1)
                ELSE ROUND(i.principal_total / i.total_periods, 2)
           END AS plan_principal,
           ROUND(i.principal_total * i.fee_rate_month, 2) AS plan_fee
    FROM installments i
    JOIN period_list p ON p.period_no <= i.total_periods
)
SELECT pl.installment_id, pl.period_no,
       pl.plan_principal, pl.plan_fee,
       COALESCE(SUM(a.actual_principal), 0) AS act_principal,          -- 同期多笔还款流水合并
       ROUND(COALESCE(SUM(a.actual_principal),0) / NULLIF(pl.plan_principal,0) * 100, 1) AS period_rate_pct
FROM plan pl
LEFT JOIN repayment_actuals a
       ON a.installment_id = pl.installment_id
      AND a.period_no     = pl.period_no
GROUP BY pl.installment_id, pl.period_no, pl.plan_principal, pl.plan_fee
ORDER BY pl.installment_id, pl.period_no;
```

结果解读：辅助表法把递归变普通JOIN，计划层零递归开销，合约量千万级时更快；代价是序列上限需预留（期数>100要扩容数字表），并把尾差逻辑固化在计划生成层。

> Hive/Spark SQL 差异：Hive 可用 split+explode/lateral view 展开期数序列，Spark 3 有 sequence(1, total_periods) 内置函数，均比递归CTE自然；递归CTE在Hive老版本不可用，数字辅助表是通用兜底。

### 5. 性能分析与优化
解法一递归生成的期数序列仅≤24行，递归开销可忽略；解法二辅助表100行常驻内存，两者计划层代价相同，真正代价在 repayment_actuals 关联聚合。优化建议：① repayment_actuals 建 (installment_id, period_no) 复合索引，把LEFT JOIN变成索引查找；② 合约×期数计划行物化为"分期计划表"（数仓标准宽表），还款流水T+1增量更新达成率，避免每次全量展开；③ 按 bill_month 分区，现金流预测只取未到期合约分区；④ 提前结清与账单日调整走事件表打补丁（计划行带版本号），不重算全量；⑤ 尾差在计划生成时统一处理，避免下游对账不平。

### 6. 面试延伸考点
- **计划本金除不尽（如10000元分3期）怎么办？** 要点：末期兜底=总额−前N−1期，保证合计恒等；分摊方式（等额/递减）以与账务系统一致为准，SQL不自创口径。
- **"总额固定费率"与"等额本息真实利率"差异是什么？** 要点：名义月费率0.6%×12期对应实际IRR约13%，消费者保护与营销宣传用IRR口径；SQL负责展开，IRR换算交给专门函数/对照表。
- **客户提前结清剩余手续费怎么算？** 要点：看合同——"剩余手续费一次性收取"或"减免"，计划表必须支持事件触发的重算，这就是计划行要带版本号的原因。
- **为什么对齐键是(合约号,期数)而不是还款日期？** 要点：账单日调整、宽限期会让日期漂移，期数是合约的稳定属性；日期只用于逾期天数计算。

### 7. 业务拓展思考
计划vs实际对比表向上支撑现金流预测（计划回收×历史达成率=预测回收），向下驱动催收策略（期级逾期清单）。联动动作：达成率连续两期低于80%的合约提前进入soft collection；提前结清高峰月提示价格策略复盘（费率过高诱发提前结清）。口径延展：加"提前结清率、展期率"组成分期健康度仪表盘；现金分期与账单分期分开建模——两者还款来源（薪资vs额度循环）行为特征不同，混合平均会掩盖各自的期数断崖。

## FIN-41 客户资产等级季度迁移矩阵

### 1. 业务背景
某银行私人银行/财富管理部（谁）按季度末AUM对客户重新评定资产等级（普通/白银/黄金/钻石），等级决定客户经理配比、权益发放与费率档位（何时/什么）。季度经营会需要输出"等级迁移矩阵"：上季度各等级客户本季度流向哪里，升级/降级/持平的比例各是多少（为什么）。降级矩阵是预警重点——黄金降白银往往领先于资产流失与销户，提前干预可挽留；升级矩阵则是客群培育成果的度量。矩阵还是等级策略的模拟器：若把黄金门槛从50万提到80万，用历史迁移矩阵可以快速估算各档受影响人数与AUM规模，为策略调整提供量化依据。

### 2. 表结构说明
表名：customer_level_snapshot（客户等级季度快照表，每季度末全量快照）

| 字段名 | 类型 | 含义 |
|---|---|---|
| customer_id | BIGINT | 客户号 |
| stat_quarter | VARCHAR(8) | 快照季度：2025Q1/2025Q2... |
| level_name | VARCHAR(10) | 等级：普通/白银/黄金/钻石 |
| aum | DECIMAL(18,2) | 季末AUM |

示例数据：

| customer_id | stat_quarter | level_name | aum |
|---|---|---|---|
| 11001 | 2025Q1 | 黄金 | 620000.00 |
| 11001 | 2025Q2 | 白银 | 430000.00 |
| 11002 | 2025Q1 | 白银 | 250000.00 |
| 11002 | 2025Q2 | 黄金 | 550000.00 |
| 11003 | 2025Q1 | 普通 | 80000.00 |

（11001降级、11002升级、11003的Q2无快照——视为流失或数据缺失，矩阵中应显式呈现。）

### 3. 解题思路
口径：矩阵行=上季度等级、列=本季度等级，单元格=客户数（或AUM）及行占比；两季度都有快照才进入矩阵，仅上季度有→"流失"、仅本季度有→"新进入"，两者都要显式补全，否则行占比合计不为100%造成误读。实现：相邻季度配对是关键——解法一自连接（季度字符串'2025Q1'<'2025Q2'字典序可比），解法二LAG窗口按客户时间序取上季度等级，一次扫描产出全季度迁移对，便于回溯任意季度。**【避坑指南】** 阈值边界抖动客户（AUM在门槛±10%徘徊）会高估降级规模，严格口径应加缓冲带或要求连续两季度越线才认定降级（与FIN-44临界预警联动）；季度字符串若'25Q1'与'2025Q1'混用会配对失败，先做格式校验。易错点：流失列必须保留在分母；等级顺序排序用FIELD或维度表，避免字母序错乱。

### 4. 参考解法

**解法一：相邻季度自连接（行转列矩阵）**

```sql
WITH cur AS (                                        -- 本季度快照（2025Q2）
    SELECT customer_id, level_name, aum
    FROM customer_level_snapshot
    WHERE stat_quarter = '2025Q2'
),
prev AS (                                            -- 上季度快照（2025Q1）
    SELECT customer_id, level_name
    FROM customer_level_snapshot
    WHERE stat_quarter = '2025Q1'
)
SELECT p.level_name                                                       AS from_level,    -- 上季度等级（矩阵行）
       ROUND(SUM(CASE WHEN c.level_name='普通' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS to_normal_pct,   -- 流向普通占比%
       ROUND(SUM(CASE WHEN c.level_name='白银' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS to_silver_pct,   -- 流向白银占比%
       ROUND(SUM(CASE WHEN c.level_name='黄金' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS to_gold_pct,     -- 流向黄金占比%
       ROUND(SUM(CASE WHEN c.level_name='钻石' THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS to_diamond_pct,  -- 流向钻石占比%
       ROUND(SUM(CASE WHEN c.customer_id IS NULL THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS churned_pct,   -- 流失：本季度无快照
       COUNT(*)                                                               AS from_cnt,      -- 上季度该等级客户数（分母）
       ROUND(SUM(CASE WHEN c.level_name='黄金' THEN c.aum ELSE 0 END)/10000, 2) AS to_gold_aum_wan  -- 流入黄金的资产规模（万元）
FROM prev p
LEFT JOIN cur c ON c.customer_id = p.customer_id      -- 左连接：本季度流失的客户留在分母
GROUP BY p.level_name
ORDER BY FIELD(p.level_name,'普通','白银','黄金','钻石');   -- 按业务等级序输出
```

结果解读：黄金行若to_silver_pct超过20%即触发降级预警专项；churned_pct高企说明该等级的权益与客户资产规模不匹配，需与产品部复盘权益设计。

**解法二：LAG 窗口法（一次扫描回溯全季度）**

```sql
WITH ordered AS (                                    -- 客户内按季度字典序排序
    SELECT customer_id, stat_quarter, level_name, aum,
           LAG(level_name)   OVER (PARTITION BY customer_id ORDER BY stat_quarter) AS prev_level,    -- 上季度等级
           LAG(stat_quarter) OVER (PARTITION BY customer_id ORDER BY stat_quarter) AS prev_quarter   -- 上季度名（校验相邻）
    FROM customer_level_snapshot
),
pairs AS (                                            -- 校验“相邻季度”防止快照断档错配
    SELECT prev_level, level_name AS curr_level, aum
    FROM ordered
    WHERE prev_level IS NOT NULL
      AND CAST(SUBSTRING(stat_quarter,1,4) AS UNSIGNED) * 4
        + CAST(SUBSTRING(stat_quarter,6,1) AS UNSIGNED)                            -- 本季度序号 = 年×4+季
      = CAST(SUBSTRING(prev_quarter,1,4) AS UNSIGNED) * 4
        + CAST(SUBSTRING(prev_quarter,6,1) AS UNSIGNED) + 1                        -- 恰为上季度序号+1
)
SELECT prev_level,                                    -- 上季度等级
       curr_level,                                    -- 本季度等级
       COUNT(*)                                   AS cust_cnt,     -- 迁移客户数
       ROUND(SUM(aum)/10000, 2)                   AS aum_wan,      -- 迁移资产规模（万元）
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY prev_level), 1) AS row_pct  -- 行占比（窗口行归一化）
FROM pairs
GROUP BY prev_level, curr_level
ORDER BY FIELD(prev_level,'普通','白银','黄金','钻石'), cust_cnt DESC;
```

结果解读：长表矩阵便于继续下钻（按支行/客户经理切片），行占比用窗口分区归一化，省去再套一层子查询；一次运行可回溯全部历史季度的迁移对。

> Hive/Spark SQL 差异：季度序号换算可用 substr+cast 同理；亿级快照按 stat_quarter 分区后，解法一只读两个分区、解法二需全表窗口，按场景选择；FIELD 函数 Hive 无，用 CASE 或 map 构造排序键替代。

### 5. 性能分析与优化
解法一只扫两个季度分区+一次JOIN，是季度会报表的最优解；解法二全表窗口，适合一次产出历史所有季度迁移对后落表复用。优化建议：①快照表 (customer_id, stat_quarter) 唯一索引防重复快照；②迁移对落"季度迁移明细表"，矩阵查询退化为单表透视；③客户千万级时快照只保留等级与AUM窄列，减少IO；④输出时与等级维表JOIN补齐空单元格（如某季度无钻石流失也要有行），避免业务方把"没数据"误读为"零流失"；⑤缓冲带认定逻辑（连续两季越线）建议在明细表加标记列固化。

### 6. 面试延伸考点
- **降级一定代表流失风险吗？如何排除"阈值抖动"？** 要点：AUM在门槛附近波动属正常，可设缓冲带（连续2季度低于门槛×0.9才认定）或看迁移后30天资金动向再定性。
- **矩阵用什么值加权：户数、AUM还是中收贡献？** 要点：看用途——客群培育看户数、资产负债管理看AUM、利润分析看中收；三者背离时说明结构异质，需分层展示。
- **新客与流失客不在矩阵里，怎么补全画面？** 要点：增加"新进入"行与"流失"列构成带边界的完整迁移表，行合计守恒可核对，避免占比读错。
- **如何用迁移矩阵估算提门槛的影响？** 要点：把历史迁移对按新门槛重新映射等级算反事实矩阵，新旧矩阵之差即受影响人群与AUM，作为策略模拟。

### 7. 业务拓展思考
迁移矩阵是客群经营的"流体力学"：连续多季度观察可识别"升降级通道"（普通→黄金的常见路径与停留时长），指导培育动作的投放时点。联动动作：降级客户触发资产归集礼遇与专属理财额度；升级客户即时推送权益升级通知放大获得感；连续两季降级客户转客户经理深度维护。口径延展：可扩展为"等级×产品持有"联合迁移（降级且赎回理财是高危组合）；或引入等级停留时长半衰期概念，为权益预算ROI测算提供参数，把定性挽留变成定量预算。

## FIN-42 授信额度使用率分布与逾期率交叉分析

### 1. 业务背景
某银行信用卡中心风险政策部（谁）验证"额度使用率—逾期风险"曲线形态（何时/什么）：把存量账户按授信使用率（已用额度/总额度）分箱，统计各箱的当前逾期率、户均透支余额与户数（为什么）。业务预期呈U型或阶梯型：低使用率客群不活跃、风险低但贡献低；中段是健康层；使用率>90%的客群资金链紧张、逾期率陡升，是降额与预警重点。若曲线与预期不符（如高使用率逾期率反而低），往往是客群结构混淆——代发优质客群习惯性高使用但低风险，需要分层验证。这种"预期违背时的解读能力"与"分箱方法选择"正是面试深挖点，也是额度管理策略的数据地基。

### 2. 表结构说明
表名：credit_accounts（授信账户月度状态表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| account_id | BIGINT | 账户号 |
| customer_id | BIGINT | 客户号 |
| total_limit | DECIMAL(14,2) | 总授信额度 |
| used_amt | DECIMAL(14,2) | 当前已用额度 |
| is_overdue | TINYINT | 当前是否逾期：1是/0否 |
| open_date | DATE | 开户日期 |
| segment | VARCHAR(20) | 客群：代发/商旅/学生/年轻白领 |

示例数据：

| account_id | customer_id | total_limit | used_amt | is_overdue | open_date | segment |
|---|---|---|---|---|---|---|
| C001 | 12001 | 50000.00 | 48000.00 | 1 | 2023-05-01 | 年轻白领 |
| C002 | 12002 | 200000.00 | 40000.00 | 0 | 2022-11-15 | 代发 |
| C003 | 12003 | 30000.00 | 6000.00 | 0 | 2024-01-20 | 学生 |
| C004 | 12004 | 80000.00 | 76000.00 | 0 | 2021-08-08 | 商旅 |
| C005 | 12005 | 20000.00 | 19900.00 | 1 | 2023-12-01 | 年轻白领 |

（C001与C005满额且逾期，验证"高使用率高风险"假设；C004高使用但商旅客群暂未逾期，提示需分层看。）

### 3. 解题思路
口径：使用率=used_amt/total_limit，total_limit≤0（僵尸/异常户）剔除；逾期率=箱内逾期账户/账户数，同时必报户均余额（风险敞口）与户数（置信度），只看逾期率会把"小额高频逾期"与"大额沉睡逾期"混为一谈。分箱两法：解法一业务固定分箱（CASE WHEN：0/0-30/30-60/60-90/90-100%/超限），可解释可复现，是策略文档语言；解法二数据驱动分箱（NTILE(10)十分位+LAG找拐点），能暴露曲线细节但边界随样本漂移。**【面试高频】** NTILE分箱的边界每月随样本变化、线上无法复现同一客户的箱归属，探索用NTILE、上线必须固化为固定边界——"探索分箱"与"策略分箱"的分离是面试官高频追问点。易错点：分箱边界左闭右开约定要明确；小样本箱要合并或标置信度；超限（>100%）与零额度异常要单独兜底。

### 4. 参考解法

**解法一：CASE WHEN 业务分箱（固定口径版）**

```sql
WITH acct AS (                                       -- 清洗：剔除零额度与负值脏数据
    SELECT account_id,
           CASE WHEN total_limit <= 0 THEN NULL
                ELSE used_amt / total_limit END AS util,          -- 使用率
           is_overdue,
           used_amt
    FROM credit_accounts
    WHERE total_limit > 0
)
SELECT CASE
         WHEN util IS NULL      THEN '00_异常(空)'
         WHEN util <= 0         THEN '01_未使用(0%)'
         WHEN util <  0.30      THEN '02_低使用(0-30%)'   -- 边界约定：左闭右开
         WHEN util <  0.60      THEN '03_中使用(30-60%)'
         WHEN util <  0.90      THEN '04_高使用(60-90%)'
         WHEN util <= 1.00      THEN '05_满额(90-100%)'
         ELSE '06_超限(>100%)'                            -- 临时额度/超限兜底
       END AS util_bin,                                 -- 使用率分箱（前缀序号保证排序）
       COUNT(*)                                AS acct_cnt,            -- 户数（样本量）
       SUM(is_overdue)                         AS od_cnt,              -- 逾期户数
       ROUND(SUM(is_overdue)/COUNT(*)*100, 2)  AS overdue_pct,         -- 逾期率%
       ROUND(AVG(used_amt)/10000, 2)           AS avg_used_wan,        -- 户均透支（万元，敞口）
       ROUND(SUM(used_amt)/10000, 2)           AS total_exposure_wan   -- 箱内总敞口（万元）
FROM acct
GROUP BY util_bin
ORDER BY util_bin;
```

结果解读：若'05_满额'箱逾期率是'03_中使用'的5倍以上且总敞口占比高，"高使用率降额"策略即有数据支撑；'01_未使用'占比>30%时，睡眠户激活与清理应同步提上日程。

**解法二：NTILE 十分位 + LAG 找拐点（数据驱动版）**

```sql
WITH acct AS (                                       -- 同样先清洗
    SELECT account_id, used_amt / total_limit AS util, is_overdue, used_amt
    FROM credit_accounts
    WHERE total_limit > 0 AND used_amt >= 0
),
tiled AS (                                            -- 按使用率升序切十分位
    SELECT *,
           NTILE(10) OVER (ORDER BY util, account_id) AS decile  -- 尾键account_id打散并列值
    FROM acct
),
bin_range AS (                                        -- 箱级聚合并回填边界
    SELECT decile,
           COUNT(*)                                AS acct_cnt,
           SUM(is_overdue)                         AS od_cnt,
           ROUND(SUM(is_overdue)/COUNT(*)*100, 2)  AS overdue_pct,
           ROUND(AVG(used_amt)/10000, 2)           AS avg_used_wan,
           MIN(util) AS bin_min,                   -- 箱内最小使用率
           MAX(util) AS bin_max                    -- 箱内最大使用率
    FROM tiled
    GROUP BY decile
)
SELECT decile,
       CONCAT(ROUND(bin_min*100,1),'%~',ROUND(bin_max*100,1),'%') AS util_range,  -- 数据驱动的箱区间
       acct_cnt, overdue_pct, avg_used_wan,
       ROUND(overdue_pct - LAG(overdue_pct) OVER (ORDER BY decile), 2) AS pct_jump  -- 与低一箱的逾期率差：识别陡增拐点
FROM bin_range
ORDER BY decile;
```

结果解读：pct_jump在某一分位骤然放大即为风险拐点（如第9→第10箱跳增3个百分点），比固定分箱更精准地圈定自动降额线（拐点上方使用率区间）。

> Hive/Spark SQL 差异：NTILE与LAG语法一致；千万级账户表按 segment 预分组跑分箱或先落月状态宽表；NTILE对大量并列值（util=0）切分不稳定，排序键尾部必须拼接唯一键打散，否则同分位客户集合漂移。

### 5. 性能分析与优化
两解法均为单表一次扫描+分组/窗口，千万行内秒级。优化建议：① (total_limit, used_amt, is_overdue) 覆盖索引或列存（ORC/Parquet）减少IO；② 使用率与固定分箱在账户日快照ETL时物化为 util、util_bin 实体列，报表直接GROUP BY；③ 逾期率月度监控需留历史快照，账户状态表按月分区，交叉分析只取月末分区；④ 分箱边界存维表（bin_config表）参数化，策略调整不改SQL；⑤ 解法二十分位结果只用于探索报告，不要落业务表，防止边界漂移污染下游。

### 6. 面试延伸考点
- **为什么使用率与逾期率可能不是单调关系？** 要点：高使用率混有"代发客群惯性高使用"（低风险）与"资金链紧张"（高风险），需按客群/收入来源分层后曲线才显形。
- **固定分箱和NTILE各适合什么场合？** 要点：固定箱可解释、可写进策略文档、跨期可比；NTILE用于探索拐点但边界随样本漂移，上线前必须固化边界。
- **使用率用时点值还是月均值更合理？** 要点：时点值受账单日影响（刚出账单利用率天然高），月均值平滑但滞后；风险模型常用"近3个月最高使用率"捕捉资金紧张峰值。
- **小样本箱的逾期率能直接比较吗？** 要点：不能，需卡方检验或展示置信区间，户数<300的箱先合并，否则把随机波动当规律。

### 7. 业务拓展思考
该交叉分析是额度管理的证据链：拐点箱决定自动降额线，低使用箱决定激活预算投放。联动动作：满额箱客户推送账单分期与临时额度（做收益）同时监控共债信号（多头借贷数据）；逾期率抬升的箱触发策略复查工单与人工抽检。口径延展：使用率可换为"近6月平均使用率""现金分期余额占比"等变体对比稳健性；交叉维度扩展到账龄×使用率、客群×使用率三维透视，定位风险集中象限，把降额从"一刀切"升级为"象限化精准管控"。

## FIN-43 反欺诈规则串联路径分析

### 1. 业务背景
某消费金融公司反欺诈部（谁）分析审批引擎的规则命中序列（何时/什么）：一份申请进入引擎后依次流经多条规则（如R01身份异常→R04设备关联→R07多头集中申请），"命中路径"刻画了欺诈团伙的作案手法与引擎拦截逻辑（为什么）。分析目的有二：统计被拒申请件的高频命中路径TOP5，识别团伙模式并前置拦截；评估新增规则的"叠加度"——若新规则的命中件几乎都已被旧规则拦截，其净增量有限，不值得为此承担误杀成本。同时引擎编排顺序影响审批时效，路径统计还能回答"哪条规则该前置"。这是典型的"序列拼接+模式统计"题，GROUP_CONCAT与自连接两大流派的取舍是核心考点。

### 2. 表结构说明
表名：rule_hits（审批规则命中流水表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| hit_id | BIGINT | 命中记录号 |
| application_id | BIGINT | 申请件号 |
| rule_id | VARCHAR(10) | 规则编号：R01/R04/R07... |
| hit_time | DATETIME | 命中时间（引擎执行序） |
| rule_stage | VARCHAR(10) | 规则环节：准入/反欺诈/授信 |
| is_reject_rule | TINYINT | 该规则是否可直接致拒：1是/0否 |

示例数据：

| hit_id | application_id | rule_id | hit_time | rule_stage | is_reject_rule |
|---|---|---|---|---|---|
| 1 | A1001 | R01 | 2025-06-01 09:00:01 | 准入 | 0 |
| 2 | A1001 | R04 | 2025-06-01 09:00:02 | 反欺诈 | 1 |
| 3 | A1002 | R07 | 2025-06-01 09:01:10 | 反欺诈 | 1 |
| 4 | A1003 | R01 | 2025-06-01 09:02:00 | 准入 | 0 |
| 5 | A1003 | R04 | 2025-06-01 09:02:01 | 反欺诈 | 1 |

（A1001与A1003命中同一路径R01→R04，若该路径频次异常高且设备ID集中，即是团伙线索。）

### 3. 解题思路
口径：路径=同一申请件按hit_time排序的规则序列以"→"连接（如R01→R04→R07），统计对象限定被拒件（存在is_reject_rule=1），路径长度即命中规则数。解法一用GROUP_CONCAT(rule_id ORDER BY hit_time, hit_id)一次拼接，按路径串GROUP BY计数排名，叠加度用FIND_IN_SET判序列包含；解法二用自连接展开"相邻两跳"转移对（下一跳=时间上最近的后继记录），产出规则间转移矩阵，不依赖字符串、可移植Hive。**【避坑指南】** GROUP_CONCAT默认1024字节上限，长路径会被静默截断成错误结论，必须先SET group_concat_max_len；同秒命中的排序不稳定，ORDER BY必须带hit_id次序键；GROUP_CONCAT里DISTINCT与ORDER BY表达式不一致会直接报错，这是MySQL的知名坑。两跳法必须定义"相邻"（最近后继），否则两两JOIN统计的是共现而非转移，路径语义失真。

### 4. 参考解法

**解法一：GROUP_CONCAT 路径拼接（路径TOP榜+叠加度）**

```sql
SET SESSION group_concat_max_len = 65535;             -- 放大拼接上限，防长路径被1024截断

WITH path AS (                                        -- 每个被拒申请件拼出完整命中路径
    SELECT h.application_id,
           GROUP_CONCAT(h.rule_id ORDER BY h.hit_time, h.hit_id SEPARATOR '→') AS hit_path,  -- 时间序拼接（hit_id做次序键防同秒乱序）
           COUNT(*) AS hit_cnt,                       -- 命中规则数=路径长度
           MAX(h.is_reject_rule) AS is_rejected       -- 是否含致拒规则
    FROM rule_hits h
    WHERE h.hit_time >= '2025-06-01' AND h.hit_time < '2025-07-01'   -- 复盘月
    GROUP BY h.application_id
    HAVING MAX(h.is_reject_rule) = 1                  -- 只统计最终被拒的申请件
)
SELECT hit_path,                                      -- 命中路径串
       COUNT(*) AS path_cnt,                          -- 路径频次
       ROUND(AVG(hit_cnt), 2) AS avg_hit_len,         -- 平均命中数（异常长的路径值得人工看）
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS path_pct  -- 占全部被拒件比例（窗口全表归一化）
FROM path
GROUP BY hit_path
ORDER BY path_cnt DESC
LIMIT 5;                                              -- 高频路径TOP5
```

结果解读：TOP路径若集中在"R01→R04"（身份异常+设备关联），提示团伙批量伪造身份绑定同批设备，可从设备指纹维度增设聚合拦截规则；叠加度评估再按下式拆分：

```sql
-- 新旧规则叠加度：R07命中件中已被R04拦截的比例（衡量新规则净增量）
SELECT SUM(CASE WHEN FIND_IN_SET('R04', REPLACE(hit_path,'→',',')) THEN 1 ELSE 0 END) AS covered_by_old_cnt,  -- 被旧规则R04覆盖
       SUM(CASE WHEN FIND_IN_SET('R07', REPLACE(hit_path,'→',',')) THEN 1 ELSE 0 END) AS r07_cnt                   -- 命中新规则R07总数
FROM (SELECT GROUP_CONCAT(rule_id ORDER BY hit_time, hit_id SEPARATOR '→') AS hit_path
      FROM rule_hits
      GROUP BY application_id) t;
-- covered_by_old_cnt / r07_cnt 越接近1，新规则的独立拦截价值越低，不值得引入误杀成本
```

结果解读：若R07命中件的90%已被R04覆盖，R07应作为R04的补充条件而非独立拒绝规则，避免双重误杀同一批正常客户。

**解法二：自连接相邻两跳转移（可移植版）**

```sql
WITH ordered AS (                                     -- 申请件内按命中时间排序并打序号
    SELECT application_id, rule_id, hit_time,
           ROW_NUMBER() OVER (PARTITION BY application_id ORDER BY hit_time, hit_id) AS hit_seq  -- 相邻定义的序号键
    FROM rule_hits
),
transition AS (                                       -- 相邻两跳配对：seq与seq+1自连接
    SELECT a.rule_id AS rule_1st,                     -- 首条命中规则
           b.rule_id AS rule_2nd,                     -- 紧随其后的规则
           a.application_id
    FROM ordered a
    JOIN ordered b
      ON b.application_id = a.application_id
     AND b.hit_seq = a.hit_seq + 1                    -- 序号相邻=时间相邻，杜绝两两组合爆炸
)
SELECT rule_1st,                                      -- 首条规则
       rule_2nd,                                      -- 第二条规则
       COUNT(*) AS transition_cnt,                    -- 转移频次
       ROUND(COUNT(*) * 100.0
             / SUM(COUNT(*)) OVER (PARTITION BY rule_1st), 1) AS trans_pct  -- 行归一化：首规则流向分布%
FROM transition
GROUP BY rule_1st, rule_2nd
ORDER BY rule_1st, transition_cnt DESC;
```

结果解读：转移矩阵显示"R01之后84%流向R04"，说明身份异常件在设备维度被集中再拦截、两规则串联有效；若某首规则大量"无第二跳"，说明它多为单点拦截，需评估其前置价值。

> Hive/Spark SQL 差异：Hive 无 GROUP_CONCAT，用 concat_ws('→', collect_list(rule_id))，但 collect_list 无序，须先用 ROW_NUMBER 打序号排序后再collect；序号自连接法在Hive/Spark通用，是跨平台首选写法。

### 5. 性能分析与优化
解法一单次GROUP BY+字符串拼接为O(N)，但长路径与放大后的拼接上限有内存开销；解法二序号自连接为O(N)等值JOIN，优于老式"最小后继"相关子查询的O(N·k)。优化建议：① (application_id, hit_time, hit_id) 复合索引覆盖窗口排序；② 路径拼接在数仓ETL日批固化为"申请件路径宽表"，在线查询只做计数与TOP榜；③ 分区裁剪只扫复盘月；④ GROUP_CONCAT结果若要入库，路径串字段按最长规则数预留长度并加CHECK，防静默截断；⑤ 叠加度分析在大数据量下改为两列存在标志（MAX(CASE WHEN rule_id='R04')）聚合，避免REPLACE+FIND_IN_SET逐行字符串运算。

### 6. 面试延伸考点
- **为什么"相邻两跳"要用序号相邻而不是时间两两JOIN？** 要点：两两JOIN产出组合数爆炸且统计的是"共现"而非"转移"，路径语义失真；序号法把相邻关系显式化、复杂度线性。
- **GROUP_CONCAT拼路径有哪些工程隐患？** 要点：1024长度截断、分隔符转义、同秒排序不稳定、Hive不兼容；生产更常用窗口序号+collect_list或数组类型。
- **如何量化新规则的增量价值？** 要点：命中件中"未被任何旧规则拦截"的比例=净拦截率，乘单件预期损失节约，再对比误杀客户的收益损失与投诉成本。
- **团伙识别只看路径够吗？** 要点：不够——需结合设备ID、IP段、紧急联系人图谱做社区发现；路径是时序特征、图谱是关系特征，互补而非替代。

### 7. 业务拓展思考
路径分析把反欺诈从"单点规则"升级为"链路视角"：高频路径反向指导规则编排顺序（高区分度规则前置可节省引擎算力与客户等待时间）。联动动作：TOP路径团伙特征导入设备指纹黑产库并做关联账户管控；新路径冒头接入实时告警与周报监控。口径延展：路径可加权命中间隔时长（两规则间隔秒数反映引擎串行深度与客户流失风险）；被拒件路径与人工调查结论（确认欺诈/误杀）关联标注，为每条路径赋予"确认欺诈率"先验，指导新规则的准入阈值设定。

## FIN-44 财富客户升级降级预警（阈值边界客户）

### 1. 业务背景
某银行财富管理部的等级体系按季度AUM评定：黄金50万、钻石100万门槛（何时/什么）。客户AUM月度自然波动，季度评定时点才"定格"，因此客户经理需要在评定前锁定"临界客户"——AUM处于某门槛±10%区间且连续两个月贴近门槛的客户，提前2个月做资产归集（升级潜力）或流失挽留（降级风险）（为什么）。等评定结果出来再行动就晚了：升级客户错过权益感知、降级客户流失后再挽回成本翻倍。等级既是服务资源的分配器也是客户心理锚点，临界客群的干预时点与方向判定直接决定权益预算的转化效率，本题核心是"临近阈值的连续状态识别"。

（13001连续两月落在黄金门槛±10%[45万,55万]内且6月越线→升级预警；13002贴钻石门槛下方→降级预警。）

### 3. 解题思路
口径：临界=存在门槛T使AUM∈[T×0.9, T×1.1]（缓冲带±10%）；方向判定：AUM<T为"临降级"（当前档保不住），AUM≥T为"临升级"；连续性=最近连续≥2个自然月处于临界带，且最新月份仍临界才预警。实现三步：①每行"客户×月"与阈值维表做区间关联打临界标志与方向；②连续月计数两种写法——gaps-and-islands断代法（ROW_NUMBER差值分组）或滑动窗口SUM(flag) OVER(ROWS 1 PRECEDING)=2；③筛选"当月仍临界且连续≥2月"输出名单。**【加分点】** gaps-and-islands（断代法）是连续行为识别的通用范式，从"连续临界"到"连续登录""连续逾期"都能复用，面试中能主动写出"ROW_NUMBER−月份索引=断代键"的推导过程是重要加分项。易错点：AUM恰在两档之间的双重临界要按更高档优先；断代法要求快照月份连续（缺月时差值键失效，先校验）；窗口法忘记限定"最新月仍临界"会把历史波动客户也报出来。

### 4. 参考解法

**解法一：gaps-and-islands 断代法（通用性最强）**

```sql
WITH flagged AS (                                    -- 第一步：区间关联打临界标志与方向
    SELECT a.customer_id, a.stat_month, a.aum, t.level_name,
           CASE WHEN a.aum BETWEEN t.min_aum * 0.9 AND t.min_aum * 1.1
                THEN 1 ELSE 0 END AS near_flag,      -- 是否落入该门槛±10%缓冲带
           CASE WHEN a.aum <  t.min_aum THEN '临降级'
                ELSE '临升级' END AS warn_dir         -- 方向：门槛下=保级边缘，门槛上=够到上一档
    FROM customer_aum_monthly a
    JOIN level_thresholds t                           -- 区间JOIN：每行AUM对照三档门槛（同时完成过滤）
      ON a.aum BETWEEN t.min_aum * 0.9 AND t.min_aum * 1.1
),
streak AS (                                          -- 第二步：断代法构造连续段键
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY stat_month)
             - (YEAR(stat_month) * 12 + MONTH(stat_month)) AS grp_key
           -- 全序号 − 月份索引：同一连续临界段内该差值恒定，段断裂则跳变（要求月份无缺）
    FROM flagged
    WHERE near_flag = 1
),
seg AS (                                              -- 第三步：段聚合：起止月与连续长度
    SELECT customer_id, level_name, warn_dir, grp_key,
           MIN(stat_month) AS streak_start,
           MAX(stat_month) AS streak_end,
           COUNT(*)        AS streak_months             -- 连续临界月数
    FROM streak
    GROUP BY customer_id, level_name, warn_dir, grp_key
)
SELECT s.customer_id, s.level_name, s.warn_dir,       -- 客户/门槛档/预警方向
       s.streak_start, s.streak_end, s.streak_months,
       ROUND(f.aum/10000, 2) AS latest_aum_wan        -- 段末（最新月）AUM
FROM seg s
JOIN flagged f
  ON f.customer_id = s.customer_id
 AND f.stat_month = s.streak_end                       -- 回表取段末明细
WHERE s.streak_end = '2025-06-30'                      -- 段末=最新月：当前仍临界才预警
  AND s.streak_months >= 2                             -- 且连续≥2个月
ORDER BY s.warn_dir, s.streak_months DESC;
```

结果解读：名单按方向分组推送客户经理：临降级（13002贴钻石下沿）优先挽留，临升级（13001越线）推送升级权益锁定感知，连续月数越长紧迫度越高。

**解法二：滑动窗口计数（简洁版）**

```sql
WITH flagged AS (                                     -- 同样先打临界标志（区间关联阈值表）
    SELECT a.customer_id, a.stat_month, a.aum, t.level_name,
           CASE WHEN a.aum BETWEEN t.min_aum * 0.9 AND t.min_aum * 1.1 THEN 1 ELSE 0 END AS near_flag,
           CASE WHEN a.aum < t.min_aum THEN '临降级' ELSE '临升级' END AS warn_dir
    FROM customer_aum_monthly a
    JOIN level_thresholds t
      ON a.aum BETWEEN t.min_aum * 0.9 AND t.min_aum * 1.1
),
slide AS (                                            -- 滑动两月窗口：本月+上月标志求和
    SELECT customer_id, stat_month, aum, level_name, warn_dir,
           SUM(near_flag) OVER (PARTITION BY customer_id
                                ORDER BY stat_month
                                ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS flag_2m  -- =2即连续两月临界
    FROM flagged
)
SELECT customer_id, level_name, warn_dir,
       stat_month AS latest_month,                    -- 命中月（即最新月）
       ROUND(aum/10000, 2) AS latest_aum_wan,
       flag_2m                                        -- 连续临界月数（此处=2）
FROM slide
WHERE flag_2m = 2                                     -- 近两月连续临界
  AND stat_month = '2025-06-30';                      -- 且最新月仍临界（否则是历史波动）
-- 需要改“连续3月”时把窗口帧改为 2 PRECEDING、判据改=3，参数化非常轻
```

结果解读：滑动窗口版代码量小、参数易改，适合预警阈值快速迭代；局限是只能回答固定N的连续性，要输出"任意长度连续段分布"仍需断代法。

> Hive/Spark SQL 差异：区间JOIN在大表上是笛卡尔风险，AUM表亿级时把缓冲带判断改写为CASE常量表达式消除JOIN；窗口帧语法一致；按 customer_id 分桶（CLUSTERED BY）可显著降低窗口排序的shuffle代价。

### 5. 性能分析与优化
解法一两次窗口排序+段聚合，客户千万级时排序内存敏感；解法二单窗口+过滤更轻。优化建议：① flagged 的区间JOIN实为每行×3档常量比较，可改写为CASE表达式消除JOIN开销；② (customer_id, stat_month) 唯一索引保证快照唯一，Hive按customer_id分桶收益明显（窗口局部化）；③ 预警名单月批固化成结果表，客户经理系统只读结果，不直连明细库；④ 断代法前置"月份连续性校验"（每客户快照月数=自然月数），缺月客户改用窗口法兜底，这是正确性保障；⑤ 缓冲带比例、连续月数做成参数表，便于AB不同灵敏度。

### 6. 面试延伸考点
- **缓冲带±10%怎么定？** 要点：看AUM月度波动分位数（如P60波动幅度）与权益成本预算权衡；缓冲过窄名单周转快但动作不精准，过宽则名单过大失焦。
- **AUM同时满足两档临界（贴黄金下沿又超白银上沿）怎么处理？** 要点：按对客户影响最大的档优先（可升可降的最高档），或一人多档预警分行输出由业务侧判断，关键是口径固化。
- **为什么必须要求"最新月仍临界"才预警？** 要点：连续临界但最新月已越线的客户状态已变化（升级祝贺或降级关怀流程），继续报警会重复触达骚扰客户。
- **预警名单的转化率如何闭环验证？** 要点：跟踪触达后下季度等级变化与AUM增量，与未触达的相似客群对比做净增量评估，反推缓冲带与名单规模的最优配置。

### 7. 业务拓展思考
临界预警把等级经营从"事后统计"变成"事前干预"：升级侧联动资产归集（他行资金转入礼遇、工资卡绑定），降级侧联动留存挽留（专属理财、费用减免）。口径延展：预警特征可加入"AUM趋势斜率"（连续下滑vs波动企稳）区分紧急度，斜率为负的临界客户优先级最高；或对临界客群做"等级敏感度"建模，估计资产提升1万元带来的权益价值与行为改变，指导礼遇预算上限；再叠加资金来源分析（他行转入vs内部产品腾挪），把"临升级"细分为真增长与结构腾挪。

## FIN-45 流水游资识别（资金快进快出）

### 1. 业务背景
某商业银行反洗钱中心（谁）日常监测"过账账户"（何时/什么）：部分账户呈现快进快出特征——大额资金流入后极短时间内近乎等额流出，账户留存余额极低、交易对手分散，疑似洗钱通道、跑分平台或过桥资金池（为什么）。监管可疑交易模型中"资金快进快出+余额归零"是典型特征，漏报面临监管问责，全量人工排查成本又不可承受，因此需要SQL先从亿级流水中筛出线索：以"单笔≥20万流入"为锚，检查其后2小时内同账户流出合计是否达到流入额的80%。本题综合考察时间区间自连接与分层筛查的工程取舍，是高级篇的压轴综合题。

### 2. 表结构说明
表名：txn_flow（账户交易流水表）

| 字段名 | 类型 | 含义 |
|---|---|---|
| txn_id | BIGINT | 流水号 |
| account_id | VARCHAR(32) | 本方账号 |
| txn_time | DATETIME | 交易时间 |
| direction | TINYINT | 方向：1流入/2流出 |
| txn_amt | DECIMAL(18,2) | 交易金额 |
| balance_after | DECIMAL(18,2) | 交易后余额 |
| counterparty | VARCHAR(32) | 对方账号 |

示例数据：

| txn_id | account_id | txn_time | direction | txn_amt | balance_after | counterparty |
|---|---|---|---|---|---|---|
| 90001 | ACC01 | 2025-06-10 09:05:00 | 1 | 500000.00 | 501200.00 | 622...001 |
| 90002 | ACC01 | 2025-06-10 10:30:00 | 2 | 480000.00 | 21200.00 | 622...777 |
| 90003 | ACC01 | 2025-06-10 10:50:00 | 2 | 20000.00 | 1200.00 | 622...889 |
| 90004 | ACC02 | 2025-06-10 11:00:00 | 1 | 300000.00 | 301500.00 | 622...333 |
| 90005 | ACC02 | 2025-06-11 09:00:00 | 2 | 290000.00 | 11500.00 | 622...555 |

（ACC01流入50万后2小时内流出合计50万（96%+4%）、余额归零，命中；ACC02流出在23小时后，不命中。）

### 3. 解题思路
口径：对每笔"流入≥20万"的交易（锚点），统计"同账户、锚点后2小时内"的流出合计R；R≥0.8×流入额记为一次快进快出事件；账户级线索=按账户×日汇总命中事件数与涉及金额。解法一：区间自连接（流入行×其后的流出行，时间差∈(0,2小时]）按锚点聚合判比例——精确但连接代价高；解法二：分层筛查（工程思路）——先按"账户×日"粗筛（当日流出/当日流入≥0.85且有大额流入），把候选量压缩数个数量级，再对候选做明细级区间验证。**【面试高频】** 80%覆盖率阈值不是拍的——要用历史已确认案件回测校准（100%过严漏报手续费与截留场景，70%误报暴涨），"阈值如何来"是面试官对规则类题目的必问项。易错点：时间差用TIMESTAMPDIFF或区间谓词；一笔流出可同时服务多个锚点（金额重叠计数），事件级允许重叠、日级汇总须声明口径；冲正/负金额流水先清洗；窗口允许跨日。

### 4. 参考解法

**解法一：区间自连接精确识别（事件级）**

```sql
WITH inflow AS (                                      -- 锚点：大额流入
    SELECT txn_id, account_id, txn_time, txn_amt
    FROM txn_flow
    WHERE direction = 1
      AND txn_amt >= 200000                           -- 单笔≥20万
      AND txn_time >= '2025-06-10 00:00:00'
      AND txn_time <  '2025-06-11 00:00:00'           -- 锚点日（半开区间）
),
outflow AS (                                          -- 候选流出（覆盖锚点日+2小时跨日余量）
    SELECT txn_id, account_id, txn_time, txn_amt
    FROM txn_flow
    WHERE direction = 2 AND txn_amt > 0
      AND txn_time >= '2025-06-10 00:00:00'
      AND txn_time <  '2025-06-11 02:00:00'
),
event AS (                                            -- 锚点×同账户流出的区间配对聚合
    SELECT i.txn_id AS anchor_id, i.account_id, i.txn_time, i.txn_amt AS inflow_amt,
           SUM(CASE WHEN o.txn_time > i.txn_time
                     AND o.txn_time <= DATE_ADD(i.txn_time, INTERVAL 2 HOUR)
                    THEN o.txn_amt ELSE 0 END) AS out_in_2h      -- 锚点后2小时窗口内流出合计
    FROM inflow i
    JOIN outflow o ON o.account_id = i.account_id     -- 同账户才配对（时间窗口在CASE内判定）
    GROUP BY i.txn_id, i.account_id, i.txn_time, i.txn_amt
)
SELECT account_id,                                    -- 账户
       DATE(txn_time) AS event_day,                   -- 锚点日（窗口可跨日）
       COUNT(*) AS hit_events,                        -- 命中事件数
       ROUND(SUM(inflow_amt)/10000, 2) AS inflow_wan, -- 涉及流入金额（万元，事件级允许重叠）
       ROUND(SUM(out_in_2h)/SUM(inflow_amt), 3) AS outflow_ratio  -- 平均流出覆盖比
FROM event
WHERE out_in_2h >= inflow_amt * 0.8                   -- 80%覆盖判据
GROUP BY account_id, DATE(txn_time)
ORDER BY inflow_wan DESC;
```

结果解读：命中账户按涉及金额排序交反洗钱岗；ACC01式"当日清零"形态得分最高，可再叠加 balance_after 低留存校验（日末余额<1万）增强置信度，降低专岗排查量。

**解法二：分层筛查（先粗后精的工程优化版）**

```sql
WITH day_agg AS (                                     -- 第一层粗筛：账户×日 收支汇总（扫描一遍即可）
    SELECT account_id,
           DATE(txn_time) AS txn_day,
           SUM(CASE WHEN direction = 1 THEN txn_amt ELSE 0 END) AS day_in,   -- 当日流入合计
           SUM(CASE WHEN direction = 2 THEN txn_amt ELSE 0 END) AS day_out,  -- 当日流出合计
           SUBSTRING_INDEX(GROUP_CONCAT(balance_after ORDER BY txn_time DESC), ',', 1) AS last_balance  -- 日内最后一笔余额（技巧：拼接后取首段）
    FROM txn_flow
    WHERE txn_time >= '2025-06-10 00:00:00'
      AND txn_time <  '2025-06-11 00:00:00'
      AND txn_amt > 0                                  -- 剔除冲正等非正向流水
    GROUP BY account_id, DATE(txn_time)
    HAVING day_in >= 200000                            -- 当日有大额流入
       AND day_out >= day_in * 0.85                    -- 且当日流出≥流入85%（快进快出日形态）
),
suspect AS (                                          -- 候选账户日（量级通常缩小3个数量级）
    SELECT account_id, txn_day
    FROM day_agg
),
verify AS (                                           -- 第二层精筛：只对候选账户做明细区间验证
    SELECT i.txn_id AS anchor_id, i.account_id, i.txn_amt AS inflow_amt,
           SUM(CASE WHEN o.txn_time > i.txn_time
                     AND o.txn_time <= DATE_ADD(i.txn_time, INTERVAL 2 HOUR)
                    THEN o.txn_amt ELSE 0 END) AS out_in_2h
    FROM txn_flow i
    JOIN suspect s
      ON s.account_id = i.account_id
     AND DATE(i.txn_time) = s.txn_day                 -- 锚点只取候选账户日
    JOIN txn_flow o
      ON o.account_id = i.account_id
     AND o.direction = 2 AND o.txn_amt > 0
     AND o.txn_time > i.txn_time                      -- 区间条件下推到JOIN，缩小配对规模
     AND o.txn_time <= DATE_ADD(i.txn_time, INTERVAL 2 HOUR)
    WHERE i.direction = 1 AND i.txn_amt >= 200000
    GROUP BY i.txn_id, i.account_id, i.txn_amt
)
SELECT v.account_id,
       s.txn_day,
       COUNT(*) AS hit_cnt,                            -- 命中锚点数
       ROUND(SUM(v.inflow_amt)/10000, 2) AS inflow_wan -- 涉及流入金额（万元）
FROM verify v
JOIN suspect s ON s.account_id = v.account_id
WHERE v.out_in_2h >= v.inflow_amt * 0.8
GROUP BY v.account_id, s.txn_day
ORDER BY inflow_wan DESC;
```

结果解读：粗筛把亿级流水压缩到千级候选，精筛自连接代价可忽略；粗筛命中量与精筛命中量的比值本身是"日形态≈快进快出"假设的校准数据，比值稳定后可只用粗筛做日常预警。

> Hive/Spark SQL 差异：区间自连接在Hive代价高，Spark 3 可用 `RANGE BETWEEN INTERVAL 2 HOUR` 时间帧窗口直接聚合窗口内流出（免自连接）；两表按 account_id 分桶（CLUSTERED BY）可把JOIN变为shuffle-free；亿级流水按 txn_time 日分区批跑。

### 5. 性能分析与优化
解法一自连接规模=流入笔数×该账户当日流出笔数，正常账户小、可疑账户放大，最坏退化明显；解法二多一轮扫描但把精筛连接压缩到候选集，总量上更快。优化建议：① txn_flow 按 txn_time 日分区+ (account_id, txn_time) 复合索引，两解法都依赖账户+时间定位；② 流水亿级迁Hive/Spark并按 account_id 分桶join；③ 低留存标志（balance_after<阈值）在写入层物化为行级标志列，粗筛阶段即可用；④ 事件结果按日增量落库，同一账户连续多日命中生成"持续性"字段供线索优先级排序；⑤ 冲正/冲账流水（负金额或冲正标志）先剔除，防止配对错乱。

### 6. 面试延伸考点
- **为什么用"2小时内流出≥80%"而不是"100%"？** 要点：留出手续费、税费、部分截留的真实空间，100%过严漏报；阈值用历史确认样本回测校准，是精度与召回的平衡。
- **一笔流出金额被多个锚点重复计入，怎么处理？** 要点：事件级统计允许重叠（各锚点独立成案）；日级汇总须声明口径，严格去重需按时间轴做资金分摊（复杂流水匹配问题）。
- **快进快出与正常经营户（批零商户日结）如何区分？** 要点：看对手方集中度、余额留存天数、时段分布与行业白名单，多特征交叉降误报，不能单指标定罪。
- **该规则如何在流式场景落地？** 要点：锚点事件到达后做2小时滚动聚合（Flink CEP/滑动窗口），批SQL是离线回溯版本，两套引擎的口径必须对齐并定期对账。

### 7. 业务拓展思考
快进快出线索是反洗钱"资金链路图"的起点：账户级命中后向上追对手方二跳三跳，构建资金网络识别团伙中枢账户。联动动作：命中账户触发加强尽调（KYC更新）、非柜面渠道限额、必要时临时止付并按流程上报可疑交易报告。口径延展：可加入"余额留存率"（日终余额/日流入）与"对手方离散度"（当日去重对手方数）构成多特征评分卡，替代单一阈值规则；监管趋势强调可疑报告质量而非数量，线索分级（高/中/低危）与回溯准确率监控比全量报送更可持续。
