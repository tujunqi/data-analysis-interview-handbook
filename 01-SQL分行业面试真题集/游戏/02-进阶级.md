## GAME-16 分渠道统计新增用户的次日留存与7日留存

### 1. 业务背景

手游买量团队在月度渠道复盘中，投放经理需要按注册渠道拆分新增用户的次日留存率与7日留存率，以判断各渠道买来的用户质量差异：某渠道新增量大但留存差，往往意味着素材跑偏或假量，需要削减预算；留存高且稳定的渠道则可加大投放。场景是每月初的买量效率评估会，核心是把"新增口径"统一到首次登录日，避免设备号重复计数导致分母虚高。本题为后续渠道付费质量对比（GAME-17）提供同一套 cohort 分析框架，是留存类面试题的母题。

### 2. 表结构说明

user_login（登录流水表，一次登录会话一行，需按玩家×天去重）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家账号ID（跨服唯一，多服账号已归并） |
| channel | VARCHAR(32) | 注册渠道：tiktok / bilibili / huawei / xiaomi |
| server_id | INT | 区服ID |
| login_date | DATE | 登录日期 |

示例数据：

| player_id | channel | server_id | login_date |
|---|---|---|---|
| 10001 | bilibili | 1 | 2024-06-01 |
| 10001 | bilibili | 1 | 2024-06-02 |
| 10001 | bilibili | 1 | 2024-06-03 |
| 10002 | huawei | 2 | 2024-06-01 |
| 10003 | tiktok | 1 | 2024-06-01 |

### 3. 解题思路

口径先行：留存率的分母是"某日首次登录（即新增）的玩家数"，分子是该 cohort 玩家恰好在第 N 天（first_date+1 / +7）仍有登录记录的人数；渠道归属取首登日的渠道（视为注册渠道），而不是后续登录渠道，否则玩家跨渠道行为会重复计数。实现路径分三步：第一步用 CTE 的 MIN(login_date) 求每个玩家的首登日；第二步关联首登记录取得渠道；第三步 LEFT JOIN 第 1 天、第 7 天的登录记录作为"是否留存"标记，最后按新增日期×渠道分组聚合。**【避坑指南】** 登录流水同一天往往多行（每次启动一行），所有计数必须配 COUNT(DISTINCT)，否则分母虚高、留存被系统性低估。另有两个易错点：7 日留存对"最近 7 天内新增"的 cohort 尚未成熟，报表要剔除或标注；用"≥N 天内登录过"算的是 N 日内留存，与"第 N 日留存"口径不同，面试时要主动说清用的是哪一种。

### 4. 参考解法

解法一：CTE 求首登 + 双 LEFT JOIN 标记（留存类经典框架）

```sql
WITH first_login AS (                      -- CTE①：每个玩家的首次登录日期，即"新增日"
    SELECT player_id,
           MIN(login_date) AS first_date   -- 最小登录日期 = 首登日
    FROM user_login
    GROUP BY player_id                     -- 按玩家聚合，多服账号已归并到 player_id
)
SELECT  f.first_date,                      -- 新增日期（cohort 基准日）
        fl.channel,                        -- 渠道取首登当日渠道，视为注册渠道
        COUNT(DISTINCT f.player_id)        AS new_cnt,     -- 分母：当日新增玩家数（去重）
        COUNT(DISTINCT CASE WHEN d1.login_date IS NOT NULL
                            THEN f.player_id END) AS ret1_cnt,  -- 分子：第1日有登录的玩家数
        COUNT(DISTINCT CASE WHEN d7.login_date IS NOT NULL
                            THEN f.player_id END) AS ret7_cnt,  -- 分子：第7日有登录的玩家数
        ROUND(COUNT(DISTINCT CASE WHEN d1.login_date IS NOT NULL THEN f.player_id END)
              / COUNT(DISTINCT f.player_id), 4) AS ret1_rate,   -- 次日留存率
        ROUND(COUNT(DISTINCT CASE WHEN d7.login_date IS NOT NULL THEN f.player_id END)
              / COUNT(DISTINCT f.player_id), 4) AS ret7_rate    -- 7日留存率
FROM first_login f
JOIN user_login fl                                        -- 关联首登记录以取得渠道
  ON fl.player_id  = f.player_id
 AND fl.login_date = f.first_date                         -- 只取首登日的记录
LEFT JOIN user_login d1                                   -- 次日登录记录，命中即留存
  ON d1.player_id  = f.player_id
 AND d1.login_date = DATE_ADD(f.first_date, INTERVAL 1 DAY)  -- 精确第1天
LEFT JOIN user_login d7                                   -- 第7日登录记录
  ON d7.player_id  = f.player_id
 AND d7.login_date = DATE_ADD(f.first_date, INTERVAL 7 DAY)
GROUP BY f.first_date, fl.channel                         -- 按 新增日期×渠道 输出
ORDER BY f.first_date, fl.channel;
```

结果解读：ret1_rate 反映渠道买量的首日体验质量，若 bilibili 稳定高于 tiktok 3 个百分点以上，说明素材吸引来的用户与玩法匹配度更高，可支持对其提价抢量。

解法二：窗口函数打标 + 一次聚合（先去重再开窗）

```sql
WITH daily AS (                            -- CTE①：玩家×日期去重，规避一天多行干扰
    SELECT DISTINCT player_id, channel, login_date
    FROM user_login
),
tagged AS (                                -- CTE②：开窗给每行打上首登日与注册渠道
    SELECT player_id,
           login_date,
           FIRST_VALUE(channel) OVER (     -- 取首登那天的渠道作为注册渠道
               PARTITION BY player_id ORDER BY login_date) AS reg_channel,
           MIN(login_date)      OVER (     -- 窗口 MIN 直接得到首登日，免再 GROUP BY 一层
               PARTITION BY player_id)     AS first_date
    FROM daily
)
SELECT reg_channel,
       first_date,
       SUM(login_date = first_date)               AS new_cnt,   -- MySQL 布尔表达式求和=新增数
       SUM(DATEDIFF(login_date, first_date) = 1)  AS ret1_cnt,  -- 第1天登录的行数（去重后每人每天至多一行）
       SUM(DATEDIFF(login_date, first_date) = 7)  AS ret7_cnt,  -- 第7天登录的行数
       ROUND(SUM(DATEDIFF(login_date, first_date) = 1) / SUM(login_date = first_date), 4) AS ret1_rate,
       ROUND(SUM(DATEDIFF(login_date, first_date) = 7) / SUM(login_date = first_date), 4) AS ret7_rate
FROM tagged
GROUP BY reg_channel, first_date
ORDER BY first_date, reg_channel;
```

结果解读：窗口法只扫一遍去重数据、代码更短；布尔求和依赖 MySQL 的 1/0 隐式转换，跨库迁移需改写为标准 CASE WHEN。

### 5. 性能分析与优化

解法一对 user_login 做 1+2 次关联，LEFT JOIN 的 d1/d7 按 (player_id, login_date) 等值匹配，有联合索引时代价可控，但大表上仍是三遍扫描；解法二先 DISTINCT 去重一次、再两个同分区的窗口（可共享一次排序），通常更省。优化建议：给 user_login 建 (player_id, login_date) 联合索引，让 DISTINCT 与窗口排序走索引避免 filesort；留存分子也可不用 JOIN，改写为对"玩家×日期"中间表的 IN 子查询聚合；报表高频时把"玩家×日期"去重结果落成数仓中间表，上层查询退化为轻量 JOIN。

> Hive/Spark 差异：十亿级登录日志下，先用 GROUP BY player_id, login_date 去重落盘，再用窗口或 JOIN 计算留存；Hive 的 FIRST_VALUE/MIN 窗口语法一致，但大表 JOIN 需注意数据倾斜，可按渠道加盐或预聚合。

### 6. 面试延伸考点

- **【面试高频】同一设备注册了多个账号，怎么去重？** 回答要点：先声明口径以谁为准（设备 or 账号）；设备维度需引入 device_id 映射表，按设备取最早注册账号为主账号再聚合；防刷场景还要结合 IP 与设备指纹识别模拟器假量。
- **7 日留存为什么要做"成熟期"处理？** 回答要点：最近 7 天新增的 cohort 观察窗未满、分子必然偏低，应只统计 first_date <= 当前日期-7 的 cohort，或对未成熟 cohort 标注"未定值"，否则趋势图会出现假性下滑。
- **留存能不能不用 JOIN 实现？** 回答要点：可以，把每人登录日集合先去重为"玩家×日期"表，再用窗口 MIN 打首登标记后条件聚合；大表场景预计算 cohort 中间表是标准工程做法。
- **多服游戏统计时角色与账号怎么处理？** 回答要点：角色→账号→设备三层映射，出报告前声明统计层级；跨服搬砖账号按账号归并，避免同一玩家在多服重复计入分母。

### 7. 业务拓展思考

留存是买量 ROI 模型的第一道闸门：把渠道级留存接入 LTV 预测后，投放第 3 天即可预估 30 日回收率，大幅缩短预算决策周期。口径上可延展出"新增活跃留存"与"新增付费留存"两条曲线——付费用户留存通常高 10~20 个点，若某渠道整体留存尚可但付费留存差，说明其用户被首充礼包吸引后即流失，应调整礼包策略而非继续加投。联动动作上，留存数据可直接对接投放平台的 oCPM 回传，把"次留"作为优化目标替换浅层的"激活"，从源头改善买量质量。

## GAME-17 各渠道付费率与 ARPPU 对比

### 1. 业务背景

渠道运营每周与商务团队对齐渠道质量，需要对比各渠道活跃用户的付费率与 ARPPU（付费用户人均充值额），判断"量价关系"：有的渠道量大但付费率低（泛用户），有的渠道量小但 ARPPU 高（核心玩家聚集），两者的组合决定渠道的报价上限与预算倾斜方向。场景是周报的渠道质量矩阵，结论直接写进季度商务谈判材料。难点在于活跃与充值分属两张表，且"当日付费玩家必当日活跃"的假设在补单、延迟到账时会被打破，口径必须提前声明，这也是面试官爱追问的地方。

### 2. 表结构说明

user_active（日活跃表，数仓已按 玩家×日期 去重）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| stat_date | DATE | 统计日期 |
| player_id | BIGINT | 玩家ID |
| channel | VARCHAR(32) | 注册渠道 |
| server_id | INT | 区服 |

orders（充值订单表，一笔订单一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | VARCHAR(64) | 订单号（唯一） |
| player_id | BIGINT | 玩家ID |
| amount | DECIMAL(10,2) | 实付金额（元） |
| product_id | VARCHAR(64) | 商品ID（礼包/月卡/钻石） |
| pay_date | DATE | 支付日期 |

示例数据：

user_active：

| stat_date | player_id | channel | server_id |
|---|---|---|---|
| 2024-06-01 | 10001 | bilibili | 1 |
| 2024-06-01 | 10002 | huawei | 2 |
| 2024-06-01 | 10003 | tiktok | 1 |
| 2024-06-02 | 10001 | bilibili | 1 |
| 2024-06-02 | 10004 | xiaomi | 3 |

orders：

| order_id | player_id | amount | product_id | pay_date |
|---|---|---|---|---|
| O1001 | 10001 | 68.00 | pack_68 | 2024-06-01 |
| O1002 | 10001 | 328.00 | pack_328 | 2024-06-01 |
| O1003 | 10003 | 6.00 | diamond_6 | 2024-06-01 |
| O1004 | 10004 | 30.00 | month_card | 2024-06-02 |
| O1005 | 10002 | 98.00 | pack_98 | 2024-06-01 |

### 3. 解题思路

指标口径：付费率 = 当日付费人数 / 当日活跃人数；ARPPU = 当日充值总额 / 当日付费人数。特别注意 ARPPU 分母是付费人数而非活跃人数，若算错分母就变成了 ARPU，这是本题型最常见的口误。粒度取 渠道×日期。实现路径两条：方案 A 把活跃表与订单表按 玩家×日期 LEFT JOIN，条件聚合一次算齐，订单缺失时 COALESCE 补零；方案 B 两侧各自聚合后再 JOIN，可读性更好、也便于兼容"补单玩家当日未活跃"的场景。易错点：LEFT JOIN 后活跃人数必须 COUNT(DISTINCT)，因为一笔订单一行会让主表行膨胀；SUM(amount) 遇全 NULL 返回 NULL 要补 0；除法分母用 NULLIF 防零除；跨天补单按 pay_date 还是订单创建时间归日，需与财务口径对齐后再写 SQL。

### 4. 参考解法

解法一：LEFT JOIN + 条件聚合（一表到底）

```sql
SELECT  a.channel,                                            -- 渠道
        a.stat_date,                                          -- 统计日期
        COUNT(DISTINCT a.player_id)              AS active_users, -- 分母：当日活跃（JOIN膨胀后必须去重）
        COUNT(DISTINCT o.player_id)              AS pay_users,     -- 分子：当日有订单的玩家数
        ROUND(COALESCE(SUM(o.amount), 0), 2)     AS pay_amount,    -- 当日充值总额（无订单补0）
        ROUND(COUNT(DISTINCT o.player_id) / COUNT(DISTINCT a.player_id), 4) AS pay_rate,  -- 付费率
        ROUND(COALESCE(SUM(o.amount), 0)
              / NULLIF(COUNT(DISTINCT o.player_id), 0), 2)        AS arppu      -- 付费用户人均（分母防0）
FROM user_active a
LEFT JOIN orders o                                            -- LEFT JOIN：不付费的活跃玩家也要保留
       ON o.player_id = a.player_id
      AND o.pay_date  = a.stat_date                           -- 按 玩家×日期 对齐，只算当日订单
GROUP BY a.channel, a.stat_date
ORDER BY a.stat_date, pay_rate DESC;                          -- 按付费率倒序便于看渠道差异
```

结果解读：若 tiktok 付费率 2.1% 且 ARPPU 18 元，bilibili 付费率 3.8%、ARPPU 45 元，则 bilibili 属"量价双优"渠道，谈判中可优先争取量级并接受更高单价。

解法二：分表聚合 + LEFT JOIN（先各自算清再对接）

```sql
WITH act AS (                                 -- CTE①：活跃侧按 渠道×日期 聚合
    SELECT channel, stat_date,
           COUNT(DISTINCT player_id) AS active_users
    FROM user_active
    GROUP BY channel, stat_date
),
pay AS (                                      -- CTE②：付费侧以活跃表为骨架聚合
    SELECT a.channel, a.stat_date,
           COUNT(DISTINCT o.player_id) AS pay_users,
           SUM(o.amount)               AS pay_amount
    FROM user_active a
    JOIN orders o ON o.player_id = a.player_id    -- INNER JOIN：默认"付费必当日活跃"
                 AND o.pay_date  = a.stat_date
    GROUP BY a.channel, a.stat_date
)
SELECT a.channel,
       a.stat_date,
       a.active_users,                                              -- 活跃人数
       COALESCE(p.pay_users, 0)  AS pay_users,                      -- 无付费的渠道补0
       COALESCE(p.pay_amount, 0) AS pay_amount,
       ROUND(COALESCE(p.pay_users, 0) / a.active_users, 4)          AS pay_rate,
       ROUND(COALESCE(p.pay_amount, 0) / NULLIF(p.pay_users, 0), 2) AS arppu
FROM act a
LEFT JOIN pay p
       ON p.channel = a.channel AND p.stat_date = a.stat_date        -- 同粒度对接
ORDER BY a.stat_date, a.channel;
```

结果解读：两段式把"活跃"与"付费"解耦，若存在离线补单，把 pay CTE 的主表换成 orders 再 LEFT JOIN active 校验即可，工程上更稳、可解释性更强。

### 5. 性能分析与优化

解法一 JOIN 后的中间结果 = 活跃行数 × 当日订单数，单玩家多单会放大中间集；解法二两侧各自 GROUP BY 后再 JOIN，中间结果只剩 渠道×日期 粒度，通常更快。优化建议：orders 按 (pay_date, player_id) 建分区/索引，JOIN 时裁剪分区；若只看周/月粒度，先在 CTE 里把日期收敛到周再 JOIN，减少分组键组合；渠道维度的月度透视（渠道转列）建议在报表层动态生成，SQL 内可用条件聚合写死列或 GROUP_CONCAT 拼 JSON；数仓侧把"玩家×日期×渠道"活跃与付费预聚合到 ADS 层，查询端只做轻量拼接。

> Hive/Spark 差异：可用 date_trunc 收敛粒度、GROUPING SETS 一次输出多粒度；Spark SQL 支持 PIVOT 子句直接做渠道转列，MySQL 需条件聚合模拟。

### 6. 面试延伸考点

- **【面试高频】付费率和 ARPPU 哪个优先看？** 回答要点：看决策目的——提客单优先 ARPPU，促转化优先付费率；两者相乘才是 ARPU，渠道对比要三指标同看，防止"高 ARPPU 低付费率"的幸存者偏差误导预算分配。
- **【避坑指南】LEFT JOIN 之后 COUNT(DISTINCT a.player_id) 的 DISTINCT 为什么不能省？** 回答要点：一笔订单一行，JOIN 后主表行数膨胀，不去重会把多单付费玩家在分母里重复计数，付费率被人为抬高，这是本题型最高频的写错点。
- **退款订单怎么处理？** 回答要点：财务口径先在数仓层冲销（生成负向订单），SQL 只聚合已结算金额；需要毛流水口径时单列展示，不与净流水混算，报表注明口径。
- **如何扩展为渠道×档位交叉透视？** 回答要点：条件聚合写 N 列或 GROUP_CONCAT 拼接，Hive/Spark 用 PIVOT；列数不定时在报表层动态生成 SQL，避免硬编码枚举。

### 7. 业务拓展思考

付费质量矩阵可直接驱动买量出价：以渠道×7 日付费率作为 oCPM 优化目标分组，高价值渠道抬高目标成本上限、低效渠道压缩预算。延展口径上，可把 ARPPU 拆成"首充 ARPPU"与"复充 ARPPU"，若复充占比低说明付费深度靠礼包堆砌，大版本后收入容易回落；也可按 6/30/98/328 档位拆分订单结构，联动运营调整礼包上架节奏。给策划侧的输入是：付费率低的渠道用户更吃"低门槛首充"，礼包定价与首充奖励应随渠道质量差异化配置，而不是全渠道一刀切。

## GAME-18 注册到首充转化率与间隔分布

### 1. 业务背景

用户增长运营在新手期转化专项中，需要回答两个问题：新注册玩家有多大比例完成首充？从注册到首充平均间隔多久？首充是免费玩家走向付费的关键跃迁，间隔分布直接决定首充礼包与推送的触发时机——若 80% 的首充发生在注册后 48 小时内，运营的自动化触达窗口就要前移到第一天，而不是温吞地按周推送。该结论用于设计"注册后 N 小时未首充"的触达策略，也是评估新手商业化改版（如 6 元首充礼包）效果前必须先钉住的基线指标，改版前后 cohort 的转化率与间隔要可对比。

### 2. 表结构说明

user_register（注册表，一次注册一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| register_time | DATETIME | 注册时间（精确到秒） |
| channel | VARCHAR(32) | 注册渠道 |
| device_id | VARCHAR(64) | 设备号 |

orders（充值订单表，一笔订单一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | VARCHAR(64) | 订单号 |
| player_id | BIGINT | 玩家ID |
| amount | DECIMAL(10,2) | 实付金额 |
| pay_time | DATETIME | 支付完成时间 |

示例数据：

user_register：

| player_id | register_time | channel | device_id |
|---|---|---|---|
| 20001 | 2024-06-01 10:15:00 | tiktok | d_aaa1 |
| 20002 | 2024-06-01 10:20:00 | bilibili | d_aaa2 |
| 20003 | 2024-06-01 11:00:00 | tiktok | d_aaa3 |
| 20004 | 2024-06-02 09:00:00 | huawei | d_aaa4 |
| 20005 | 2024-06-02 14:30:00 | tiktok | d_aaa5 |

orders：

| order_id | player_id | amount | pay_time |
|---|---|---|---|
| O2001 | 20001 | 6.00 | 2024-06-01 12:00:00 |
| O2002 | 20003 | 68.00 | 2024-06-03 20:10:00 |
| O2003 | 20001 | 328.00 | 2024-06-05 21:00:00 |
| O2004 | 20004 | 30.00 | 2024-06-02 10:00:00 |
| O2005 | 20002 | 6.00 | 2024-06-30 19:40:00 |

### 3. 解题思路

先定口径：转化率 = 完成首充的注册玩家数 / 总注册玩家数，按注册日分组输出 cohort 曲线，分母是注册玩家而非新增设备，同一设备多账号要归并；间隔 = 首次支付时间 - 注册时间，常用 TIMESTAMPDIFF 按小时/天双粒度输出。实现路径：第一步对 orders 按玩家 MIN(pay_time) 得首充时间，一人多单只取最早一笔；第二步注册表 LEFT JOIN 首充表，未转化玩家间隔为 NULL；第三步聚合转化率、对已转化玩家算平均间隔；第四步再做一份间隔分桶分布（24h/72h/7d/更久/未转化），用 SUM(COUNT(*)) OVER () 算占比与累计占比。**【避坑指南】** 平均间隔只对已转化玩家有意义，切勿把 NULL 当 0 拉低均值；同时"窗口内还未转化"不等于"永不转化"，近端 cohort 转化率天然偏低，必须设成熟期（如注册满 14 天才纳入统计），否则转化曲线会出现假性连续下跌。

### 4. 参考解法

解法一：MIN 求首充 + LEFT JOIN 聚合（cohort 视角）

```sql
WITH first_pay AS (                       -- CTE①：每个玩家的首充时间
    SELECT player_id, MIN(pay_time) AS first_pay_time
    FROM orders
    GROUP BY player_id                    -- 一人多单只保留最早一笔
)
SELECT  DATE(r.register_time) AS register_date,                 -- 注册日期（cohort 基准）
        COUNT(*)                                AS reg_users,    -- 分母：当日注册玩家数
        COUNT(fp.player_id)                     AS fp_users,     -- 分子：已首充玩家（JOIN命中即非空）
        ROUND(COUNT(fp.player_id) / COUNT(*), 4) AS fp_conv,      -- 首充转化率
        ROUND(AVG(DATEDIFF(fp.first_pay_time, r.register_time)), 2) AS avg_gap_days,  -- 已转化者平均间隔（天）
        ROUND(SUM(CASE WHEN TIMESTAMPDIFF(HOUR, r.register_time, fp.first_pay_time) <= 48
                       THEN 1 ELSE 0 END) / NULLIF(COUNT(fp.player_id), 0), 4)        AS gap48_pct  -- 48h内转化占已转化比例
FROM user_register r
LEFT JOIN first_pay fp
       ON fp.player_id = r.player_id
GROUP BY DATE(r.register_time)
ORDER BY register_date;
```

结果解读：AVG 只作用于 fp 非空的行，得到的是"已转化用户"的平均间隔；若 reg 三天前的 cohort 转化率仍明显偏低，才可判断真实下滑，否则优先怀疑观察窗截断。

解法二：间隔分桶分布（CASE 分桶 + 占比与累计窗口）

```sql
WITH first_pay AS (                      -- CTE①：首充时间（口径与解法一一致）
    SELECT player_id, MIN(pay_time) AS first_pay_time
    FROM orders GROUP BY player_id
),
bucketed AS (                            -- CTE②：给每个注册玩家打转化间隔标签
    SELECT r.player_id,
           CASE WHEN fp.first_pay_time IS NULL                                     THEN '01_未转化'
                WHEN TIMESTAMPDIFF(HOUR, r.register_time, fp.first_pay_time) < 24  THEN '02_24h内'
                WHEN TIMESTAMPDIFF(HOUR, r.register_time, fp.first_pay_time) < 72  THEN '03_1-3天'
                WHEN TIMESTAMPDIFF(HOUR, r.register_time, fp.first_pay_time) < 168 THEN '04_3-7天'
                ELSE '05_7天以上' END    AS gap_bucket,   -- 前缀编号保证字符串排序与语义一致
           CASE WHEN fp.first_pay_time IS NOT NULL THEN 1 ELSE 0 END AS converted  -- 是否转化标记
    FROM user_register r
    LEFT JOIN first_pay fp ON fp.player_id = r.player_id
)
SELECT gap_bucket,
       COUNT(*)                                                    AS users,     -- 各桶人数
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)          AS users_pct, -- 占全部注册比例（聚合结果再开窗）
       ROUND(SUM(COUNT(*)) OVER (ORDER BY gap_bucket) * 100.0
             / SUM(COUNT(*)) OVER (), 2)                           AS cum_pct    -- 从"未转化"起的累计占比
FROM bucketed
GROUP BY gap_bucket
ORDER BY gap_bucket;
```

结果解读：若 02_24h内 占已转化的 65%，说明首充冲动集中在首日，礼包倒计时与推送应在注册后 24 小时内完成首次曝光；未转化桶占比则是触达策略的总盘子上限。

### 5. 性能分析与优化

两个解法都要先对 orders 全量 GROUP BY，订单表亿级时这是主要代价。优化建议：先按 pay_time 过滤观察窗（如近 90 天）再聚合；orders 有 (player_id, pay_time) 索引时 MIN 可走松散索引扫描（MySQL 8.0 对 MIN/MAX 的 loose index scan 优化）；注册表与首充表都先收敛到 player_id 粒度再 JOIN，避免大表直连；周期性报表建议数仓把 first_pay_time 固化为玩家属性表（每日刷新），查询退化为单表统计。窗口分桶查询在注册表百万级时秒出，无需额外优化。

> Hive/Spark 差异：MIN 聚合在 Map 端预聚合、代价平摊；TIMESTAMPDIFF 需换成 unix_timestamp 差值换算；Hive 中 datediff(a,b) 只返回天数，小时级间隔要用 (unix_timestamp(a)-unix_timestamp(b))/3600。

### 6. 面试延伸考点

- **【面试高频】为什么不能对全量注册玩家直接 AVG 间隔？** 回答要点：未转化玩家间隔为 NULL，AVG 忽略 NULL 后得到"已转化者均值"；若把 NULL 替换成观察期长度再平均，口径又变成含截断的伪均值，两者含义完全不同，必须先声明口径再写 SQL。
- **中位数间隔怎么求？** 回答要点：MySQL 8.0 可用 ROW_NUMBER/NTILE 配合计数定位中位行，或 PERCENT_RANK 排序筛选；Hive 有 percentile() 与 percentile_approx()；标准 SQL 的 PERCENTILE_CONT 在 MySQL 尚未内置。
- **【避坑指南】近端 cohort 转化率为什么看起来在跌？** 回答要点：观察窗截断，注册越晚可转化时间越短；修正方法是限定"注册满 N 天"的 cohort 或按注册后时长对齐画生存曲线，而不是拿原始日转化率直接环比。
- **设备级去重怎么做？** 回答要点：同一 device_id 多账号取最早注册账号为主账号，或按设备聚合首充标记再算转化，防止工作室刷号拉高分母、扭曲转化率。

### 7. 业务拓展思考

注册-首充间隔分布是商业化节奏设计的直接输入：若 24 小时内转化占绝对大头，首充礼包应在新手引导 3~5 步内露出并配限时倒计时；间隔长的品类（如 SLG）则把大额礼包后置到第 3~7 天，避免吓跑前期用户。口径延展上，可分别统计自然量与买量用户的转化曲线，识别买量素材带来的"首充羊毛党"；也可将间隔与首充金额交叉，验证"早转化用户客单更高"的假设，进而指导投放平台以"48 小时内首充"作为付费深度回传事件，提升模型找人的精度。

## GAME-19 新手引导 1-10 步漏斗转化

### 1. 业务背景

新手策划与数据分析在版本改版验收时，需要把新手引导的 1~10 步做成漏斗：每一步的到达人数、逐步转化率与最大流失点。新手引导决定玩家是否理解核心玩法，第 3 步（战斗教学）或第 7 步（抽卡教学）往往是流失悬崖；识别卡点后，策划会缩短文案、增加跳过按钮或调整奖励发放位置。漏斗还要按版本与渠道对比，验证改版是否真的把第 10 步完成率拉高了，这要求 SQL 能灵活切换统计窗口与分母口径，并在步数扩展时保持代码可维护——这正是行转列与数字辅助表两种写法的用武之地。

### 2. 表结构说明

tutorial_events（新手引导事件表，玩家每完成一步写一行，step_id 表示完成的步骤号）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| step_id | INT | 完成的引导步骤 1~10 |
| event_time | DATETIME | 事件时间 |
| app_version | VARCHAR(16) | 客户端版本 |

示例数据：

| player_id | step_id | event_time | app_version |
|---|---|---|---|
| 30001 | 1 | 2024-06-10 20:01:05 | 2.4.0 |
| 30001 | 2 | 2024-06-10 20:01:40 | 2.4.0 |
| 30001 | 3 | 2024-06-10 20:02:15 | 2.4.0 |
| 30002 | 1 | 2024-06-10 20:05:00 | 2.4.0 |
| 30002 | 2 | 2024-06-10 20:05:30 | 2.4.0 |

### 3. 解题思路

口径：漏斗第 k 步到达人数 = 统计窗口内出现过 step_id >= k 事件的玩家数（事件在完成该步时上报，因此 >= 等价于"到达过第 k 步"）；转化率输出两种：相对第一步的总转化（step_k/step_1）与相邻步转化（step_k/step_{k-1}）。实现路径：方案 A 用条件聚合把 10 步转成一行宽表，COUNT(DISTINCT CASE WHEN step_id >= k THEN player_id END)，直观但列数固定；方案 B 构造 1~10 的数字辅助表 CROSS JOIN 玩家最大步，输出长表，步数可配置，还能顺势接 LAG 算相邻步转化。**【避坑指南】** 若事件表同时包含"开始"与"完成"两类事件，必须先过滤完成事件，否则到达人数虚高；且绝不能写 COUNT(step_id = 5) 当第 5 步人数——等于 5 只统计"恰好停在第 5 步"的玩家，会把漏斗算成停留分布，必须用 >= 聚合"到达过第 5 步及以后"的所有人。

### 4. 参考解法

解法一：条件聚合 + 宽表行转列（一步一列）

```sql
SELECT COUNT(DISTINCT CASE WHEN step_id >= 1  THEN player_id END) AS s01,  -- 完成第1步人数（漏斗分母）
       COUNT(DISTINCT CASE WHEN step_id >= 2  THEN player_id END) AS s02,
       COUNT(DISTINCT CASE WHEN step_id >= 3  THEN player_id END) AS s03,
       COUNT(DISTINCT CASE WHEN step_id >= 4  THEN player_id END) AS s04,
       COUNT(DISTINCT CASE WHEN step_id >= 5  THEN player_id END) AS s05,
       COUNT(DISTINCT CASE WHEN step_id >= 6  THEN player_id END) AS s06,
       COUNT(DISTINCT CASE WHEN step_id >= 7  THEN player_id END) AS s07,
       COUNT(DISTINCT CASE WHEN step_id >= 8  THEN player_id END) AS s08,
       COUNT(DISTINCT CASE WHEN step_id >= 9  THEN player_id END) AS s09,
       COUNT(DISTINCT CASE WHEN step_id >= 10 THEN player_id END) AS s10,  -- 全流程完成人数
       ROUND(COUNT(DISTINCT CASE WHEN step_id >= 10 THEN player_id END) * 100.0
             / COUNT(DISTINCT CASE WHEN step_id >= 1 THEN player_id END), 2) AS total_rate_pct  -- 首尾总转化率
FROM tutorial_events
WHERE event_time >= '2024-06-01' AND event_time < '2024-07-01'   -- 统计窗口：6月到达玩家
  AND app_version = '2.4.0';                                     -- 版本条件可切换做改版对比
```

结果解读：s05 到 s06 的绝对掉幅最大即第 6 步为卡点；总转化率 42% 意味着近六成玩家没走出引导，其优先级高于任何后期付费优化——新手期的问题放大会传导到全漏斗。

解法二：数字辅助表 + 玩家最大步（长表漏斗，可接 LAG）

```sql
WITH user_max AS (                       -- CTE①：每个玩家在窗口内到达的最大步数
    SELECT player_id, MAX(step_id) AS max_step
    FROM tutorial_events
    WHERE event_time >= '2024-06-01' AND event_time < '2024-07-01'
    GROUP BY player_id
),
steps AS (                               -- CTE②：1~10 数字辅助表（替代写死的10列）
    SELECT 1 AS step_id UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
    UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8
    UNION ALL SELECT 9 UNION ALL SELECT 10
),
reach AS (                               -- CTE③：每步到达人数
    SELECT st.step_id,
           SUM(CASE WHEN u.max_step >= st.step_id THEN 1 ELSE 0 END) AS reach_users
    FROM steps st
    CROSS JOIN user_max u                -- 步骤×玩家网格，明细只需聚合一次
    GROUP BY st.step_id
)
SELECT step_id,
       reach_users,
       ROUND(reach_users * 100.0
             / (SELECT reach_users FROM reach WHERE step_id = 1), 2)             AS total_rate_pct,  -- 相对第1步的总转化
       ROUND(reach_users * 100.0
             / LAG(reach_users) OVER (ORDER BY step_id), 2)                      AS step_rate_pct    -- 相邻步转化率
FROM reach
ORDER BY step_id;
```

结果解读：长表一步一行可直接画漏斗图；step_rate_pct 首行为 NULL（无上一步），其最低值所在步即最大流失点，配合 user_max 里 max_step 的众数还能看"玩家集体停在哪一步"。

### 5. 性能分析与优化

解法一只扫一遍表、聚合粒度极粗，是首选；解法二多一层"按玩家聚合"（明细→玩家），但 CROSS JOIN 发生在聚合后的小结果集（玩家数×10）上，可接受。优化建议：tutorial_events 按 event_time 分区，窗口裁剪后只扫当月分区；若需限定"本期新增玩家"，先用半连接（player_id IN 注册名单）缩小范围，避免老玩家的历史引导事件混入；步数扩展到几十步时把 steps 辅助表固化为 dim_step 维表；Hive 下用 LATERAL VIEW explode(sequence(1,10)) 展开辅助表，避免低效 CROSS JOIN。

> Hive/Spark 差异：explode(sequence(1,10)) 生成数字序列是惯用法；COUNT(DISTINCT) 在 Hive 大分组下会触发单 reducer，可改为先 GROUP BY player_id 打标再二次聚合。

### 6. 面试延伸考点

- **【面试高频】严格漏斗（要求事件按时间有序发生）怎么写？** 回答要点：给每人的步进事件按时间排序打序号，校验相邻步 event_time 递增，或用自连接/窗口比较"第 k 步完成时间晚于第 k-1 步"；乱序补传事件会污染宽松口径，严格口径才是产品真实漏斗。
- **漏斗分母用"注册人数"还是"完成第 1 步人数"？** 回答要点：前者衡量"引导触达率"（含没进引导的流失），后者衡量"引导内流转"，两者都该输出；管理层看触达率，策划看步间转化。
- **【避坑指南】为什么 COUNT(step_id = 5) 是错的？** 回答要点：等于 5 只数"恰好完成第 5 步"的玩家，漏掉已完成 6~10 步者，画出来的是"停留分布"不是漏斗；必须用 >= 表达"到达过第 k 步"。
- **小渠道样本太稀怎么办？** 回答要点：按周聚合拉长窗口或合并渠道组，输出人数与置信区间辅助判断，避免用单日几个样本的转化率波动做改版结论。

### 7. 业务拓展思考

新手漏斗是版本验收的北极星链路：把每步转化与次留做相关分析，常能发现"完成第 3 步战斗教学"与次留相关最强，从而把买量落地页、商店素材与引导首屏对齐到核心玩法。策划侧联动包括：对卡点步骤做 A/B 测试（跳过按钮、自动化战斗）、把首次抽卡奖励前置到卡点之前；运营侧可对卡在固定步骤的玩家配置客服外呼或补偿邮件。口径延展上，漏斗可加"每步平均耗时"列（窗口取每人每步 MAX-MIN 时间差再平均），耗时陡增而转化未跌的步骤往往是合理的阅读学习段，不能一刀切优化掉。

## GAME-20 通过率低于 60% 的卡点关卡识别

### 1. 业务背景

关卡数值策划在每周难度例会上，需要从关卡挑战明细里筛出通过率低于 60% 的"卡点关卡"，作为下一版数值调优清单：过难的关卡会劝退普通玩家、拖累次留，但过易又失去挑战感与付费动机。分析时要同时给出"挑战次数口径"与"玩家口径"两个通过率——前者衡量该关的整体难度，后者衡量有多少玩家最终被拦住；两者背离（整体通过率不低但玩家通过率低）说明少数肝帝反复挑战拉高了均值，这正是 SQL 口径功底的试金石。结论直接决定哪些关卡进热修名单，以及推荐战力提示线的调整幅度。

### 2. 表结构说明

level_attempts（关卡挑战流水，每次挑战一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| level_id | INT | 关卡ID（主线关卡 1001 起连续递增） |
| attempt_time | DATETIME | 挑战时间 |
| is_win | TINYINT | 1 通关 / 0 失败 |
| power_value | BIGINT | 挑战时战力 |

示例数据：

| player_id | level_id | attempt_time | is_win | power_value |
|---|---|---|---|---|
| 40001 | 1001 | 2024-06-11 21:00:10 | 1 | 15200 |
| 40001 | 1002 | 2024-06-11 21:05:30 | 0 | 15200 |
| 40001 | 1002 | 2024-06-11 21:09:45 | 0 | 15200 |
| 40001 | 1002 | 2024-06-11 21:14:02 | 1 | 15350 |
| 40002 | 1002 | 2024-06-11 21:20:00 | 0 | 9800 |

### 3. 解题思路

两种口径要并行输出：挑战通过率 = SUM(is_win)/COUNT(*)（每次挑战权重相同，反映单次难度）；玩家通过率 = 通过玩家数/挑战玩家数（按 玩家×关卡 去重，每人只算一次"是否最终通关"，反映拦截面）。实现路径：方案 A 单层 GROUP BY level_id + HAVING AVG(is_win) < 0.6 直接筛挑战口径，并补 COUNT(DISTINCT player_id) 与人均尝试次数；方案 B 先按 玩家×关卡 聚合出 ever_win、首战即胜标记，再按关卡聚合筛玩家口径。**【面试高频】** 通过率是对聚合结果的过滤，必须用 HAVING 而不是 WHERE——WHERE 在分组前过滤行、不能使用聚合函数，这是本题型必考的语法语义点。其余易错点：AVG(is_win) 依赖 0/1 编码，字段是字符串时先 CASE 转换；新关上线初期样本少，阈值应叠加最小样本量（如挑战数 >= 100）防误报。

### 4. 参考解法

解法一：挑战口径 + HAVING 筛选（最短路）

```sql
SELECT level_id,                                            -- 关卡ID
       COUNT(*)                                 AS attempts,    -- 总挑战次数
       COUNT(DISTINCT player_id)                AS players,     -- 参与玩家数（去重）
       ROUND(AVG(is_win) * 100, 2)              AS win_rate_pct, -- 挑战口径通过率（0/1均值）
       ROUND(COUNT(*) / COUNT(DISTINCT player_id), 1) AS avg_tries -- 人均尝试次数（受挫/重试热度）
FROM level_attempts
WHERE attempt_time >= '2024-06-01'                          -- 观察窗，排除历史难度版本干扰
GROUP BY level_id
HAVING AVG(is_win) < 0.6                                    -- 聚合后过滤：只留通过率<60%的关卡
   AND COUNT(*) >= 100                                      -- 叠加最小样本量，防新关误报
ORDER BY win_rate_pct;                                      -- 越低越优先调
```

结果解读：若 1025 关通过率 41% 且人均尝试 6.8 次，说明该关不仅难且玩家反复受挫，调优优先级最高；若通过率低但人均尝试只有 1~2 次，更可能是玩家直接弃关流失而非"卡关磨练"。

解法二：玩家口径（先按玩家聚合，再按关卡聚合）

```sql
WITH player_level AS (                      -- CTE①：收敛到 玩家×关卡 粒度
    SELECT level_id,
           player_id,
           MAX(is_win)                                         AS ever_win,   -- 是否最终通关
           MIN(attempt_time)                                   AS first_try,  -- 首次挑战时间
           MIN(CASE WHEN is_win = 1 THEN attempt_time END)     AS first_win,  -- 首次通关时间（未通关为NULL）
           COUNT(*)                                            AS try_cnt     -- 该玩家本关总尝试次数
    FROM level_attempts
    WHERE attempt_time >= '2024-06-01'
    GROUP BY level_id, player_id
)
SELECT level_id,
       COUNT(*)                                              AS players,        -- 挑战该关的玩家数
       SUM(ever_win)                                         AS win_players,    -- 最终通关玩家数
       ROUND(AVG(ever_win) * 100, 2)                         AS player_win_pct, -- 玩家口径通过率
       ROUND(SUM(CASE WHEN first_win = first_try THEN 1 ELSE 0 END)
             / COUNT(*) * 100, 2)                            AS first_try_win_pct, -- 首战即胜率
       ROUND(AVG(CASE WHEN ever_win = 0 THEN try_cnt END), 1) AS avg_tries_of_fail  -- 未通关者放弃前的平均尝试次数
FROM player_level
GROUP BY level_id
HAVING AVG(ever_win) < 0.6                                  -- 玩家口径低于60%
ORDER BY player_win_pct;
```

结果解读：玩家口径比挑战口径更贴近"多少人被卡死"；两口径差值大说明少量高战玩家多次通关拉高了挑战口径，数值调整应以玩家口径为准，first_try_win_pct 则反映关卡"上手即难度"的设计意图是否达成。

### 5. 性能分析与优化

解法一是单遍聚合，代价最低；解法二多一层 玩家×关卡 CTE，明细表亿级时中间结果可达千万行。优化建议：按 attempt_time 分区并用 WHERE 先裁剪；CTE 里只保留聚合所需列，避免 SELECT *；把 玩家×关卡 的聚合结果物化成中间表供"难度报表"多场景复用；若关卡数在万级以内、需要逐关看趋势，可用 AVG(is_win) OVER (PARTITION BY level_id) 一次输出全部关卡通过率再外层过滤，但窗口版本无法下推 HAVING，需外层 WHERE 包裹子查询。Hive 下两层 GROUP BY 触发两次 shuffle，可用 GROUPING SETS 合并或先 DISTRIBUTE BY level_id 预聚集。

> Hive/Spark 差异：AVG(is_win) 语义一致；Spark SQL 支持 GROUPING SETS/ROLLUP/CUBE 输出多维汇总；亿级明细建议落"关卡×日 通过率"ADS 表后再筛卡点。

### 6. 面试延伸考点

- **【面试高频】HAVING 和 WHERE 的区别，为什么通过率过滤必须用 HAVING？** 回答要点：WHERE 在分组前过滤原始行、不能用聚合函数；HAVING 在分组后过滤聚合结果，AVG(is_win) < 0.6 只能放 HAVING；两者可同时出现，注意谓词下推顺序对性能的影响。
- **【加分点】如何识别"付费绕过卡点"？** 回答要点：把 level_attempts 关联 orders，比较卡点期间通关与未通关玩家的付费差异；未通关玩家付费率显著升高说明"卖数值"生效，但要同时评估受挫流失的长期代价，输出给策划权衡。
- **60% 阈值应对所有关卡一致吗？** 回答要点：教学关、精英关、BOSS 关设计目标不同，应按关卡类型分层设阈值，或用全体关卡通过率的中位数/分位数动态划线，避免"一刀切"误伤高难度内容。
- **战力与通过率怎么关联分析？** 回答要点：按 power_value 分桶算各战力段的通过率，"战力达标仍高失败"的区间即数值异常；可据此输出推荐战力线（如 90% 玩家通关所需战力的 P50）给策划调推荐值。

### 7. 业务拓展思考

卡点清单的价值不止调难度：把卡点关卡与广告观看（看广告复活/领体力）交叉，可以判断卡点是"健康挑战"还是"流失点"——卡点后广告复活占比高，说明卡点同时是广告变现点，调松难度前要先算广告收入损失。口径延展上，输出"卡点关卡 7 日通过率趋势"，热修上线后通过率应在 1~2 天内回升，形成数值调优的闭环验证。运营侧联动：对卡点玩家推送限时补给礼包，把挫败情绪转化为付费场景；若卡点玩家次留显著低于同战力已通关玩家，则优先级应从"卖礼包"切换为"快修复"。

## GAME-21 大 R 玩家流水占比（帕累托分析）

### 1. 业务背景

发行商务负责人在季度经营分析会上，需要量化"头部玩家依赖度"：流水 Top 10% 的玩家贡献了总流水的百分之多少？累计到 80% 流水最少需要多少人？这是典型的帕累托分析，直接决定三件事：客服资源分配（VIP 专属客服名额）、版本商业化方向（大 R 定制外观与专属玩法）、以及风险预警——若 1% 玩家贡献 50% 流水，头部玩家流失将造成收入断崖，必须建立大 R 流失预警与专属维护机制。SQL 的难点在于"排序后累计占比"必须用窗口函数实现，且并列值会让默认帧口径跳变，是窗口函数入门后最常被追问的进阶题。

### 2. 表结构说明

orders（季度充值订单表，一笔订单一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | VARCHAR(64) | 订单号 |
| player_id | BIGINT | 玩家ID |
| amount | DECIMAL(10,2) | 实付金额 |
| pay_date | DATE | 支付日期 |
| product_type | VARCHAR(16) | 商品类型：直充/礼包/月卡 |

示例数据：

| order_id | player_id | amount | pay_date | product_type |
|---|---|---|---|---|
| O3001 | 50001 | 648.00 | 2024-04-02 | 礼包 |
| O3002 | 50001 | 328.00 | 2024-04-15 | 礼包 |
| O3003 | 50002 | 6.00 | 2024-04-03 | 直充 |
| O3004 | 50003 | 648.00 | 2024-04-20 | 礼包 |
| O3005 | 50004 | 30.00 | 2024-04-21 | 月卡 |

### 3. 解题思路

先收敛口径：总流水用退款冲销后的净额；按玩家聚合出期内累计充值，再排序累计。实现路径：方案 A 用 NTILE(10) 按付费降序切十分位，GROUP BY 十分位后用 SUM(SUM(amount)) OVER () 对聚合结果再开窗求全局占比，输出"每层人数、流水、占比"，Top10% 贡献率一目了然；方案 B 用累计求和窗口 SUM() OVER (ORDER BY amount DESC, player_id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) 逐行算累计占比，外层筛选累计占比首次 >= 80% 的行，即"二八线人数"。**【面试高频】** 窗口 ORDER BY 遇并列金额时默认帧是 RANGE，会把同金额的行并入同一帧，累计占比一次性跳过所有并列行；要逐行累计必须显式写 ROWS 帧，并追加唯一键（如 player_id）打破平局。另有一个必错点：NTILE 必须作用在"玩家粒度"上，直接对订单明细分桶会让多单玩家出现在多个桶，人数与流水口径全部失真。

### 4. 参考解法

解法一：NTILE 十分位 + 聚合外开窗（结构视角）

```sql
WITH user_pay AS (                        -- CTE①：收敛到玩家粒度的期内累计充值
    SELECT player_id, SUM(amount) AS total_amt
    FROM orders
    WHERE pay_date BETWEEN '2024-04-01' AND '2024-06-30'   -- 季度口径
    GROUP BY player_id                     -- 先聚合再分桶，保证一人只进一个桶
),
deciled AS (                              -- CTE②：按付费降序切十分位（1=Top10%）
    SELECT player_id, total_amt,
           NTILE(10) OVER (ORDER BY total_amt DESC) AS decile
    FROM user_pay
)
SELECT decile,                                          -- 十分位组号（1为最高）
       COUNT(*)                              AS users,      -- 该层人数
       ROUND(SUM(total_amt), 2)              AS amt,        -- 该层流水
       ROUND(AVG(total_amt), 2)              AS avg_amt,    -- 该层人均流水
       ROUND(SUM(total_amt) * 100.0
             / SUM(SUM(total_amt)) OVER (), 2) AS amt_pct    -- 层内流水占全局比（对聚合结果再开窗）
FROM deciled
GROUP BY decile
ORDER BY decile;
```

结果解读：看 decile=1 一行的 amt_pct 即 Top10% 玩家的流水贡献率；若第 1 层占比 62%、第 2~3 层合计仅 18%，头部依赖显著，收入预测应按"大 R 存量"而非"全体 ARPU"建模。

解法二：累计求和窗口定位"二八线"（人数视角）

```sql
WITH user_pay AS (
    SELECT player_id, SUM(amount) AS total_amt
    FROM orders
    WHERE pay_date BETWEEN '2024-04-01' AND '2024-06-30'
    GROUP BY player_id
),
cum AS (                                   -- CTE②：按流水降序计算累计占比
    SELECT player_id,
           total_amt,
           ROW_NUMBER() OVER (ORDER BY total_amt DESC, player_id) AS rn,  -- 追加player_id打破并列，保证顺序确定
           SUM(total_amt) OVER (ORDER BY total_amt DESC, player_id
                                ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_amt,  -- 逐行累计流水（ROWS帧）
           SUM(total_amt) OVER () AS grand_total,             -- 全体总流水（无ORDER BY即全帧）
           COUNT(*)       OVER () AS total_users              -- 全体付费玩家人数
    FROM user_pay
)
SELECT MIN(rn)                          AS users_to_80,      -- 累计达到80%流水所需的最少人数
       ROUND(MIN(cum_amt), 2)           AS cum_amt_at_80,    -- 对应累计流水
       ROUND(MIN(rn) * 100.0 / MIN(total_users), 2) AS users_pct  -- 占全体付费玩家的比例
FROM cum
WHERE cum_amt / grand_total >= 0.8;                          -- 累计占比单调递增，首个跨线行即二八点
```

结果解读：若 3.2% 的玩家贡献 80% 流水，依赖度偏高：客服与运营资源向该人群倾斜的同时，应开发中腰部付费点（战令、月卡）稀释集中度；users_pct 的月度趋势比绝对值更重要，抬升即风险信号。

### 5. 性能分析与优化

解法一只需一次排序（NTILE 的 ORDER BY）加一层轻聚合，复杂度 O(n log n)；解法二的窗口累计同样依赖一次排序，但 ROW_NUMBER 与 SUM 窗口的 ORDER BY 完全一致，优化器可共享排序，整体可控。需警惕的自连接写法（JOIN b ON b.total_amt >= a.total_amt 再 GROUP BY 计累计）是 O(n²)，亿级订单必然超时，仅适合教学演示。优化建议：玩家级累计充值若已有 ADS 属性表，直接查表省掉大聚合；订单表按 pay_date 分区先裁剪季度；只关心 TopN 大 R 明细时用 ROW_NUMBER() <= N 提前裁剪，避免全量累计；排序内存不足时调大 sort buffer 或在数仓层完成排序输出。

> Hive/Spark 差异：NTILE、SUM() OVER 语法一致；老版本 Hive 不支持 ROWS 帧，默认 RANGE 行为下并列值会整帧累计，务必显式测试；大数据量建议 DISTRIBUTE BY player_id SORT BY total_amt DESC 预排序后再开窗，减少单点排序压力。

### 6. 面试延伸考点

- **【面试高频】窗口 ORDER BY 遇到并列值会怎样？** 回答要点：默认帧是 RANGE，并列行属于同一帧，SUM 累计会一次性加上所有并列值导致占比跳变；需要逐行累计时用 ROWS 帧 + 唯一排序键（player_id），并解释两者结果差异。
- **NTILE 和 PERCENT_RANK 的区别？** 回答要点：NTILE 均分成 N 桶返回桶号，适合分位数分组与人群切分；PERCENT_RANK 返回 (rank-1)/(n-1) 的相对位置，适合连续占比；按阈值圈人用 NTILE + WHERE 更直观。
- **【避坑指南】为什么不能直接对订单明细做 NTILE？** 回答要点：多单玩家会出现在多个分位桶，人数与流水口径全部失真；必须先 GROUP BY player_id 收敛到玩家粒度再分桶，这考查的是"分析粒度先于分析函数"的意识。
- **头部集中度多少算危险？** 回答要点：结合品类基准（SLG 大 R 依赖普遍高于休闲），常用阈值 Top1% > 40% 或 Top10% > 80% 触发预警，更重要的是监控集中度的月度趋势与头部玩家的登录/充值异动。

### 7. 业务拓展思考

帕累托结论可直接拆解收入风险敞口：把 Top 玩家的登录频次与流水趋势做成月度监控，头部玩家连续 7 天未登录即触发 VIP 团队外呼挽回。对策划的输入是设计"中腰部付费成长线"（战令、基金、月卡）稀释集中度；对买量的输入是以高 ARPPU 人群做 lookalike 定向。口径延展上，可区分"累计口径"与"当季新增付费口径"（存量依赖 vs 增量质量），并区分付费集中度与活跃时长集中度——两者背离说明大 R 时间投入低、纯付费驱动，商业化设计应偏"减负型"商品而非堆肝度玩法。

## GAME-22 活动参与率与付费提升对比

### 1. 业务背景

活动运营在端午限时活动（6/8~6/14）结束后一周内复盘，需要回答：活动参与率多少？参与玩家活动期间人均付费比未参与玩家高多少？比其自身活动前基线提升多少？这些结论决定活动是否纳入常态轮换、奖励力度是否加码。分析要点是三重对比：参与 vs 未参与的横截面、参与者自身的前后对比、活动期大盘 vs 平销期。**【面试高频】** 参与是自愿行为，存在选择偏差——高意愿玩家本来就更活跃更付费，SQL 算出的是相关性而非因果，汇报时必须说明，理想方案是灰度 A/B。未参与组还要限定"活动期活跃但未参与"，否则从不登录的玩家会稀释对照组均值，让对比失去意义。

### 2. 表结构说明

activity_join（活动参与明细，一人一活动一行）：

### 3. 解题思路

口径：活动窗口 2024-06-08~06-14，基线取活动前等长 7 天（05-25~05-31，周期结构对齐）；参与率 = 参与人数 / 活动期活跃人数；付费提升 = 活动期人均付费 / 基线期人均付费 - 1，参与、未参与两组分别计算后相减才是"净提升"的近似。实现路径：方案 A 以活动期活跃玩家为主表 LEFT JOIN 参与名单打参与标记，再 LEFT JOIN 订单做分段条件聚合，一组 GROUP BY 输出两组对比；方案 B 对两组玩家独立聚合成玩家粒度明细后分别汇总，再 UNION 一个"整体参与率"总览行，其中未参与组用 NOT IN 反连接圈出。易错点：参与名单必须先 DISTINCT，一人多条参与记录会膨胀 JOIN；**【避坑指南】** 订单 JOIN 后组内人数必须 COUNT(DISTINCT player_id)，直接 COUNT(*) 会按订单行数计人头；人均提升率在两组人数固定的条件下等于总额比（分母约掉），写法上用总额比更简洁，但要注释说明等价原因，防止面试官误读。

### 4. 参考解法

解法一：活跃主表打标 + 条件聚合（一组 SQL 出两组对比）

```sql
WITH act_users AS (                          -- CTE①：参与名单去重
    SELECT DISTINCT player_id
    FROM activity_join
    WHERE activity_id = 'A2024Dragon'
),
base AS (                                    -- CTE②：活动期活跃玩家打参与标记
    SELECT a.player_id,
           CASE WHEN u.player_id IS NOT NULL THEN 1 ELSE 0 END AS joined
    FROM (SELECT DISTINCT player_id FROM user_active
          WHERE stat_date BETWEEN '2024-06-08' AND '2024-06-14') a  -- 活动期活跃人群
    LEFT JOIN act_users u ON u.player_id = a.player_id
)
SELECT CASE WHEN b.joined = 1 THEN '参与组' ELSE '未参与组' END AS grp,   -- 分组标签
       COUNT(DISTINCT b.player_id)                             AS users,     -- 组内人数（订单JOIN膨胀后必须去重）
       ROUND(SUM(CASE WHEN o.pay_date BETWEEN '2024-05-25' AND '2024-05-31'
                      THEN o.amount ELSE 0 END)
             / COUNT(DISTINCT b.player_id), 2)                 AS avg_amt_before,  -- 基线期人均付费
       ROUND(SUM(CASE WHEN o.pay_date >= '2024-06-08'
                      THEN o.amount ELSE 0 END)
             / COUNT(DISTINCT b.player_id), 2)                 AS avg_amt_during,  -- 活动期人均付费
       ROUND((SUM(CASE WHEN o.pay_date >= '2024-06-08' THEN o.amount ELSE 0 END)
              / NULLIF(SUM(CASE WHEN o.pay_date BETWEEN '2024-05-25' AND '2024-05-31'
                                 THEN o.amount ELSE 0 END), 0) - 1) * 100, 2) AS lift_pct  -- 人均付费提升率（组内人数固定，总额比=人均比）
FROM base b
LEFT JOIN orders o
       ON o.player_id = b.player_id
      AND o.pay_date BETWEEN '2024-05-25' AND '2024-06-14'     -- 一次带上基线+活动期订单
GROUP BY b.joined
ORDER BY grp;
```

结果解读：参与组 lift 85%、未参与组 12%，差值 73 个点是活动"净提升"的上界估计（含选择偏差）；参与率可看参与组 users 除以两组合计，或用 WITH ROLLUP 补一个合计行直接读。

解法二：分组独立聚合 + UNION 总览（含参与率与反连接）

```sql
WITH act_users AS (                          -- CTE①：参与名单
    SELECT DISTINCT player_id FROM activity_join WHERE activity_id = 'A2024Dragon'
),
grp_stats AS (                               -- CTE②：玩家粒度的基线/活动期付费
    SELECT u.grp, u.player_id,
           SUM(CASE WHEN o.pay_date BETWEEN '2024-05-25' AND '2024-05-31'
                    THEN o.amount ELSE 0 END) AS amt_before,
           SUM(CASE WHEN o.pay_date >= '2024-06-08'
                    THEN o.amount ELSE 0 END) AS amt_during
    FROM (
        SELECT player_id, '参与组' AS grp FROM act_users
        UNION ALL
        SELECT DISTINCT a.player_id, '未参与组'
        FROM user_active a
        WHERE a.stat_date BETWEEN '2024-06-08' AND '2024-06-14'
          AND a.player_id NOT IN (SELECT player_id FROM act_users)   -- 反连接：活跃但未参与
    ) u
    LEFT JOIN orders o ON o.player_id = u.player_id
         AND o.pay_date BETWEEN '2024-05-25' AND '2024-06-14'
    GROUP BY u.grp, u.player_id
)
SELECT grp,
       COUNT(*)                                   AS users,        -- 此时已是玩家粒度，无需DISTINCT
       ROUND(SUM(amt_before) / COUNT(*), 2)       AS avg_amt_before,
       ROUND(SUM(amt_during) / COUNT(*), 2)       AS avg_amt_during,
       ROUND((SUM(amt_during) / NULLIF(SUM(amt_before), 0) - 1) * 100, 2) AS lift_pct
FROM grp_stats
GROUP BY grp
UNION ALL
SELECT '00_整体参与率(%)',                                  -- 总览行：参与人数/活动期活跃人数×100
       ROUND((SELECT COUNT(*) FROM act_users) * 100.0
             / NULLIF((SELECT COUNT(DISTINCT player_id) FROM user_active
                       WHERE stat_date BETWEEN '2024-06-08' AND '2024-06-14'), 0), 2),
       NULL, NULL, NULL;
```

结果解读：若整体参与率仅 31%，说明活动入口触达或参与门槛有问题，应优先优化参与率再看提升幅度；lift_pct 两行的差值是活动效果的粗估，最终结论需结合参与者自身基线与灰度实验验证。

### 5. 性能分析与优化

解法一 JOIN 一次、聚合一次，代价最低；解法二的 UNION 分支里 NOT IN 反连接在大表上可能被物化执行而变慢，亿级数据建议改写为 LEFT JOIN ... IS NULL 或 NOT EXISTS。优化建议：act_users 先去重并落临时表，多处引用免重复扫描；user_active 与 orders 均按日期分区，CTE 内先裁剪日期；活动期活跃名单可复用 DAU 中间表；多活动批量复盘时，把 activity_join 先聚合为 玩家×活动 宽表一次跑完。

> Hive/Spark 差异：NOT IN 的子查询含 NULL 时整个结果为空，务必先过滤 NULL 或使用 Spark SQL 的 LEFT ANTI JOIN（Hive 2.3+ 也支持）；大表 JOIN 小表自动 mapjoin 可缓解倾斜。

### 6. 面试延伸考点

- **【面试高频】参与组付费更高，能直接说活动提升了付费吗？** 回答要点：不能直接归因，自愿参与存在自选择偏差；正确做法是参与者自身前后对比做差分、按活跃度分层匹配（PSM 思路），有条件时上灰度 A/B 实验拿因果结论。
- **基线期为什么要等长？** 回答要点：消除周期性（周末/节假日效应），等长对比才可比；若基线期含节日需顺延或改用上周同期、滚动中位数基线，并在报告中注明。
- **【加分点】活动目标完成率怎么算？** 回答要点：finish_flag=1 人数 / 参与人数，配合"曝光-点击-参与-完成"四级漏斗，区分是触达问题（参与率低）还是任务难度问题（完成率低），对应完全不同的优化动作。
- **未参与组的分母为什么限定"活动期活跃"？** 回答要点：完全不登录的玩家没有付费行为，纳入只会稀释未参与组均值、制造虚假的组间差异，对照实验要求两组"同处可付费状态"。

### 7. 业务拓展思考

复盘结论应直接落到活动轮换策略：参与率与付费提升双高的活动进常驻轮换；参与率低的先优化入口曝光与任务门槛，而非盲目加码奖励。可把活动 cohort 接入 LTV 归因模型，观察其后 30 日留存与付费衰减，判断活动是"透支未来付费"还是"真增量拉动"。口径延展上，参与深度（完成任务数分层）比参与与否更能解释付费弹性，可输出"参与任务数-付费提升"的剂量曲线；对买量侧，把高参与意愿人群特征回传投放平台定向相似人群，让活动素材与买量素材互相校准。

## GAME-23 金币产出消耗平衡表

### 1. 业务背景

经济系统策划与数据分析师在每周经济监控里，需要产出金币产出/消耗平衡表：各系统（主线副本、每日任务、商城、抽卡、装备强化）每日产出与消耗多少金币，全服净投放多少。金币是游戏内核心货币，产出持续大于消耗会通胀、交易行物价失控、老玩家囤币贬值；消耗过大则玩家通缩、养成停滞，产生负反馈弃坑。平衡表是数值调参的第一手依据：若发现"装备强化"单日消耗突然归零，往往意味着玩家养成材料被新活动吸走或金币不够，需要立即回调产出点或开设金币回收活动，防止经济系统在版本迭代中悄悄失衡。

### 2. 表结构说明

coin_flow（金币流水表，每笔变动一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| scene | VARCHAR(32) | 变动场景：主线副本/每日任务/商城/抽卡/装备强化 |
| flow_type | VARCHAR(8) | income 产出 / expense 消耗 |
| coin_amount | BIGINT | 变动数量（恒为正数） |
| flow_date | DATE | 变动日期 |

示例数据：

| player_id | scene | flow_type | coin_amount | flow_date |
|---|---|---|---|---|
| 70001 | 主线副本 | income | 12000 | 2024-06-14 |
| 70001 | 装备强化 | expense | 8000 | 2024-06-14 |
| 70002 | 每日任务 | income | 5000 | 2024-06-14 |
| 70002 | 抽卡 | expense | 20000 | 2024-06-14 |
| 70003 | 商城 | expense | 15000 | 2024-06-14 |

### 3. 解题思路

平衡表有两种粒度：按日期（看趋势，产消比逐日监控）或按场景（看结构，谁在产谁在耗）。核心指标：产出 = SUM(income)、消耗 = SUM(expense)、净投放 = 产出 - 消耗、产消比 = 产出/消耗（>1 有通胀压力）。实现路径：方案 A 日期粒度的条件聚合行转列，一行一天，除总量三列外再拆关键场景列（副本产出、任务产出、强化消耗、抽卡消耗），监控最直观；方案 B 场景粒度横截面，输出每场景产出、消耗、净差与产出/消耗结构占比，占比用 SUM(SUM(...)) OVER () 对聚合结果开窗。**【避坑指南】** 条件聚合的 ELSE 0 不能漏——SUM 会忽略 NULL 但净投放表达式 ELSE -coin_amount 与漏写 ELSE 的结果完全不同；另外要校验脏数据：若 expense 流水的 coin_amount 混入负数，会导致"双倍扣减"，SQL 前先做符号一致性校验或在查询中包一层 ABS。

### 4. 参考解法

解法一：日期粒度行转列（趋势监控）

```sql
SELECT flow_date,                                                     -- 日期
       SUM(CASE WHEN flow_type = 'income'  THEN coin_amount ELSE 0 END) AS total_income,   -- 当日总产出
       SUM(CASE WHEN flow_type = 'expense' THEN coin_amount ELSE 0 END) AS total_expense,  -- 当日总消耗
       SUM(CASE WHEN flow_type = 'income'  THEN coin_amount ELSE -coin_amount END) AS net_flow,  -- 净投放=产出-消耗
       ROUND(SUM(CASE WHEN flow_type = 'income' THEN coin_amount ELSE -coin_amount END)
             / NULLIF(SUM(CASE WHEN flow_type = 'expense' THEN coin_amount ELSE 0 END), 0), 3)
             AS pce_ratio,                                            -- 产消比（>1 通胀压力，<1 通缩）
       SUM(CASE WHEN scene = '主线副本' AND flow_type = 'income'  THEN coin_amount ELSE 0 END) AS dungeon_in,   -- 副本产出
       SUM(CASE WHEN scene = '每日任务' AND flow_type = 'income'  THEN coin_amount ELSE 0 END) AS task_in,      -- 任务产出
       SUM(CASE WHEN scene = '装备强化' AND flow_type = 'expense' THEN coin_amount ELSE 0 END) AS enhance_out,  -- 强化消耗
       SUM(CASE WHEN scene = '抽卡'     AND flow_type = 'expense' THEN coin_amount ELSE 0 END) AS gacha_out     -- 抽卡消耗
FROM coin_flow
WHERE flow_date BETWEEN '2024-06-01' AND '2024-06-14'
GROUP BY flow_date
ORDER BY flow_date;
```

结果解读：产消比连续 3 天 > 1.3 需触发通胀预警；若强化消耗列突然归零而其他消耗正常，优先排查养成线是否被新活动截流，而非直接调产出数值。

解法二：场景粒度横截面 + 结构占比窗口

```sql
SELECT scene,                                                        -- 场景
       SUM(CASE WHEN flow_type = 'income'  THEN coin_amount ELSE 0 END) AS income,    -- 该场景总产出
       SUM(CASE WHEN flow_type = 'expense' THEN coin_amount ELSE 0 END) AS expense,   -- 该场景总消耗
       SUM(CASE WHEN flow_type = 'income' THEN coin_amount ELSE -coin_amount END) AS net,  -- 场景净差（产出口/消耗口）
       ROUND(SUM(CASE WHEN flow_type = 'income' THEN coin_amount ELSE 0 END) * 100.0
             / SUM(SUM(CASE WHEN flow_type = 'income' THEN coin_amount ELSE 0 END)) OVER (), 2) AS income_pct,   -- 产出结构占比
       ROUND(SUM(CASE WHEN flow_type = 'expense' THEN coin_amount ELSE 0 END) * 100.0
             / SUM(SUM(CASE WHEN flow_type = 'expense' THEN coin_amount ELSE 0 END)) OVER (), 2) AS expense_pct   -- 消耗结构占比
FROM coin_flow
WHERE flow_date BETWEEN '2024-06-01' AND '2024-06-14'
GROUP BY scene
ORDER BY net DESC;                                                   -- 净投放最大的场景排最前
```

结果解读：产出集中在前两个系统说明经济来源单一，一旦该系统被工作室刷穿会加速通胀；某新系统消耗占比过低说明设计未达预期，需回到玩法侧排查而不是单纯调数值。

### 5. 性能分析与优化

两种解法都是单遍聚合；行转列在场景多达几十个时表达式冗长，但计算开销本身不大。优化建议：coin_flow 按 flow_date 分区，报表只扫近期分区；场景枚举频繁新增时改用 GROUP_CONCAT 动态输出（CONCAT(scene,'_',flow_type,':',SUM(...))）或由数仓固化宽表；高频报表先按 玩家×场景×日 预聚合，去掉 player_id 后数据量降两到三个数量级；对账场景用抽样明细核对总量，避免全量重扫。

> Hive/Spark 差异：Spark SQL 支持 PIVOT 子句直接行列互换；Hive 可用 collect_list 拼接或多层条件聚合；SUM(SUM(x)) OVER () 的"聚合外开窗"写法三家方言均支持，是行转列求占比的标准姿势。

### 6. 面试延伸考点

- **【面试高频】行转列有哪几种写法？** 回答要点：条件聚合（通用、单遍扫描，MySQL 首选）、标准 PIVOT 语法（SQL Server/Spark）、GROUP_CONCAT 动态拼接（列不固定时）、数仓宽表固化（高频报表）；能说清各自适用场景即是加分。
- **【避坑指南】如果 coin_amount 直接带正负号，SQL 要怎么改？** 回答要点：SUM(coin_amount) 即净投放，但产出/消耗拆分要用 SUM(CASE WHEN coin_amount > 0 ...)，并校验符号与 flow_type 一致，脏数据会让同一笔钱被产出列和消耗列各算一次。
- **产消比的合理区间是多少？** 回答要点：随版本阶段变化——开荒期产出略大于消耗（1.1~1.3），长草期应接近 1；持续 >1.5 或 <0.7 都要触发数值复核，且要区分大 R 与全体玩家分开看。
- **怎么定位通胀是谁造成的？** 回答要点：按场景净差排名后下钻到玩家层（该场景净投放 Top 玩家），区分"设计漏洞"（副本可无限刷）与"正常肝帝"；漏洞走热修复，肝帝看是否在规则边界内。

### 7. 业务拓展思考

平衡表应扩展为多货币面板（金币、钻石、体力），并叠加玩家分层——大 R 的产消比通常远高于小 R（产出上限更高），单一全服均值会掩盖分层通胀。联动动作：产出过热时策划收紧副本奖励或增设消耗点（新装备槽、外观强化），运营上抛限时消耗活动回收金币；通缩时上调日常产出并做"补给邮件"。口径延展上，可加"人均产出/消耗"与"产出中位数"对照，识别产出集中度——若 Top1% 玩家拿走 40% 产出，通胀压力集中在头部，应优先做产出封顶（如每日副本次数上限）而不是全服普调。

## GAME-24 版本更新前后留存对比

### 1. 业务背景

项目组在 7 月 1 日发布 2.5 大版本，主策划需要知道：本版的留存改动（新手引导精简、日常任务减负）是否真的改善了留存。数据分析师要在上线后第 10 天的版本验收会上，对比"版本前 vs 版本后"新增用户的次日留存与 3 日留存。坑在版本边界：7 月 1 日当天新增的玩家可能装的是旧包或新包（分包灰度），老玩家会陆续更新，"登录时版本"不等于"注册时版本"；必须以"首登日 + 首登版本"锁定 cohort，否则新旧用户混在一起，结论失真。同时对比窗口要等长、强更带来的活跃回补要剔除，这些边界处理正是本题考察核心。

### 2. 表结构说明

app_release（版本发布表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| version | VARCHAR(16) | 版本号 |
| release_date | DATE | 发布日期 |

user_login_v（登录流水表，含版本信息）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| login_date | DATE | 登录日期 |
| app_version | VARCHAR(16) | 当次登录客户端版本 |
| is_new_device | TINYINT | 是否新设备首登 |

示例数据：

app_release：

| version | release_date |
|---|---|
| 2.4.0 | 2024-06-03 |
| 2.5.0 | 2024-07-01 |

user_login_v：

| player_id | login_date | app_version | is_new_device |
|---|---|---|---|
| 80001 | 2024-06-28 | 2.4.0 | 1 |
| 80001 | 2024-06-29 | 2.4.0 | 0 |
| 80002 | 2024-07-01 | 2.5.0 | 1 |
| 80002 | 2024-07-02 | 2.5.0 | 0 |
| 80003 | 2024-07-01 | 2.4.0 | 1 |

（80003 表示发布日当天仍有旧包新增，正是版本边界坑的体现）

### 3. 解题思路

口径：cohort = 玩家首登日；版本归属有两种口径——其一用 app_release 表推断"首登日当时的线上版本"（release_date <= 首登日的最新版本），其二直接取玩家首登记录的 app_version 埋点。方案 A 用不等 JOIN（r.release_date <= f.first_date）匹配所有已发布版本，再 ROW_NUMBER 取发布日最近的一条，最后按留存框架算次留/3 日留；方案 B 直接取首登埋点版本，并用"更新前 7 天 vs 更新后 7 天"等长窗口对比。**【避坑指南】** 版本发布日当天的新增要单独剔除或标注——分包灰度下新旧包并存，默认归入任何一侧都会污染均值；另外版本号字符串比较是深坑（'2.10.0' < '2.5.0' 按字典序错误），应按发布日期排序而不是字符串比较，或维护版本维表。留存计算与 GAME-16 同框架（LEFT JOIN 第 1/3 日登录记录）。

### 4. 参考解法

解法一：版本表推断归属（不等 JOIN + 窗口取最新）

```sql
WITH first_login AS (                        -- CTE①：每人首登日
    SELECT player_id, MIN(login_date) AS first_date
    FROM user_login_v
    GROUP BY player_id
),
versioned AS (                               -- CTE②：为每个首登日匹配"当时最新版本"
    SELECT f.player_id, f.first_date, r.version,
           ROW_NUMBER() OVER (PARTITION BY f.player_id
                              ORDER BY r.release_date DESC) AS rn   -- 发布日最近的即当时线上版本
    FROM first_login f
    JOIN app_release r
      ON r.release_date <= f.first_date      -- 不等连接：只匹配"已发布"的版本
)
SELECT v.version,                                        -- 版本归属（按发布日期推断，规避版本号字符串比较）
       v.first_date,
       COUNT(DISTINCT v.player_id) AS new_users,         -- 该版本当日新增
       COUNT(DISTINCT CASE WHEN n.login_date IS NOT NULL
                           THEN v.player_id END) AS ret1_users,   -- 第1日留存人数
       COUNT(DISTINCT CASE WHEN n3.login_date IS NOT NULL
                           THEN v.player_id END) AS ret3_users,   -- 第3日留存人数
       ROUND(COUNT(DISTINCT CASE WHEN n.login_date IS NOT NULL THEN v.player_id END)
             / COUNT(DISTINCT v.player_id), 4) AS ret1_rate,
       ROUND(COUNT(DISTINCT CASE WHEN n3.login_date IS NOT NULL THEN v.player_id END)
             / COUNT(DISTINCT v.player_id), 4) AS ret3_rate
FROM versioned v
LEFT JOIN user_login_v n  ON n.player_id  = v.player_id
                          AND n.login_date  = DATE_ADD(v.first_date, INTERVAL 1 DAY)  -- 次日登录
LEFT JOIN user_login_v n3 ON n3.player_id = v.player_id
                          AND n3.login_date  = DATE_ADD(v.first_date, INTERVAL 3 DAY)  -- 第3日登录
WHERE v.rn = 1                                           -- 每个玩家只保留最新匹配版本
GROUP BY v.version, v.first_date
ORDER BY v.first_date;
```

结果解读：若 2.5.0 各日 ret1 均值 34.2%、2.4.0 尾周 31.8%，提升 2.4 个点且逐日方向一致，可初步判定改动有效；仍需按渠道分层复算并做显著性检验，防止渠道 mix 变化冒充版本效果。

解法二：埋点版本直取 + 等长窗口对比

```sql
WITH first_login AS (                        -- CTE①：每人首登日
    SELECT player_id, MIN(login_date) AS first_date
    FROM user_login_v
    GROUP BY player_id
),
tagged AS (                                  -- CTE②：直接取首登记录上的版本埋点
    SELECT f.player_id, f.first_date, fl.app_version AS reg_version
    FROM first_login f
    JOIN user_login_v fl ON fl.player_id = f.player_id
                        AND fl.login_date = f.first_date          -- 首登当日记录（可能多行，版本一致）
),
cohort_agg AS (                              -- CTE③：按"日期分界版本组"聚合（等长窗口）
    SELECT CASE WHEN t.first_date >= '2024-07-01' THEN '2.5.0'
                ELSE '2.4.x' END        AS ver_grp,               -- 用日期分界，不用版本号字符串比较
           COUNT(DISTINCT t.player_id) AS new_users,
           COUNT(DISTINCT CASE WHEN n.login_date IS NOT NULL
                               THEN t.player_id END) AS ret1_users
    FROM tagged t
    LEFT JOIN user_login_v n ON n.player_id = t.player_id
                            AND n.login_date = DATE_ADD(t.first_date, INTERVAL 1 DAY)
    WHERE (t.first_date BETWEEN '2024-06-24' AND '2024-06-30')    -- 旧版观察窗：更新前7天
       OR (t.first_date BETWEEN '2024-07-02' AND '2024-07-08')    -- 新版观察窗：发布次日起7天（7/1混合日剔除）
    GROUP BY 1
)
SELECT ver_grp,
       new_users,
       ret1_users,
       ROUND(ret1_users / new_users, 4) AS ret1_rate
FROM cohort_agg
ORDER BY ver_grp;
```

结果解读：两行 7 天等长窗口的 ret1 直接可比；发布日 7/1 被显式排除，规避旧包新包混合 cohort；此口径依赖埋点版本准确，报表上应与解法一的推断口径交叉校验。

### 5. 性能分析与优化

两解法主体都是"首登 CTE + 两次 LEFT JOIN"，与 GAME-16 同构；解法一多了不等 JOIN，app_release 只有几十行时 MySQL 以小表驱动，代价可忽略，但不等 JOIN 无法走等值索引，版本表大时先物化收敛。优化建议：把"玩家×日期"去重中间表沉淀复用（留存类题目通用）；版本归属可在数仓层固化为 player_cohort 表（player_id, first_date, reg_version），查询退化为单表统计；强更日的版本×日 DAU 交叉表单独监控，识别更新回补；版本对比建议输出逐日 ret1 曲线而非只给均值，检查发布日的异常尖刺。

> Hive/Spark 差异：不等 JOIN 在 Hive 仅限 mapjoin 小表场景，大表需改写为 JOIN 后窗口过滤；版本号比较建议 SPLIT + CAST 逐段数值化，或维护版本维表用发布日期排序。

### 6. 面试延伸考点

- **【面试高频】为什么对比留存要用"新增 cohort"而不是全量用户的留存？** 回答要点：全量留存混入老玩家，版本改动（尤其新手相关）只作用于新用户；老玩家的更新回补会制造虚假提升，新增 cohort 才是干净对照，老玩家体验用"版本前后活跃玩家留存"单独看。
- **版本号字符串比较有什么坑？** 回答要点：'2.10.0' < '2.5.0' 按字典序是错的，需按点分段转数值比较，或维护版本维表用 release_date 排序；SQL 里用日期分界最稳。
- **【避坑指南】发布日当天的新增算旧版还是新版？** 回答要点：分包灰度下两者都有，用首登埋点版本拆分；无埋点时应把发布日剔除或单独标注，避免污染两侧均值——漏掉这一步是版本验收报告最常见的翻车点。
- **如何排除买量节奏变化的干扰？** 回答要点：版本前后投放结构可能不同，按渠道分层对比或固定渠道权重加权，防止渠道 mix 变化被误读为版本效果；也可只看自然量 cohort 做交叉验证。

### 7. 业务拓展思考

版本留存对比应固化为发布验收流程：上线 T+7 出初版结论、T+14 复核 3 日/7 日留存，并配合新手漏斗解释留存变化的来源——次留升但漏斗不变，提升可能来自买量质量而非版本。策划联动：若新版次留升、7 留持平，说明改动改善了首日体验但长线内容未变，下一版应聚焦中期玩法；运营联动：版本期配合回流活动时，回流用户必须单独 cohort，不能混入新增。口径延展上，可做"版本×渠道×机型"三维留存，识别低端机在重资源版本下的留存恶化，为包体优化与机型适配排期提供依据。

## GAME-25 抽卡保底触发次数分布

### 1. 业务背景

数值策划在抽卡系统调优时，需要验证保底机制的实际表现：玩家触发保底时的抽数分布是否符合设计预期（如 90 抽硬保底、50 抽起软保底概率递增），以及"提前出金"（欧皇体验）与"吃满保底"（非酋体验）各占多少。分布若明显右偏（大量玩家吃满 90 抽才出金），体验崩坏并易引发舆情；若过度提前，期望抽数下降会压缩付费深度。结论直接决定是否调整软保底参数——这是商业化收入与玩家体验的平衡点，也常出现在数值向数据岗位的面试里，考察 LAG 窗口与取模分轮两种建模思路。

### 2. 表结构说明

gacha_record（抽卡流水表，每抽一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| draw_seq | BIGINT | 该玩家第几抽（从 1 递增） |
| item_rarity | TINYINT | 品质：5=五星 4=四星 |
| is_pity | TINYINT | 该抽是否触发保底（1=吃满保底出金） |
| draw_date | DATE | 抽卡日期 |

示例数据：

| player_id | draw_seq | item_rarity | is_pity | draw_date |
|---|---|---|---|---|
| 90001 | 1 | 4 | 0 | 2024-06-10 |
| 90001 | 62 | 5 | 0 | 2024-06-10 |
| 90001 | 63 | 4 | 0 | 2024-06-11 |
| 90001 | 152 | 5 | 1 | 2024-06-12 |
| 90002 | 90 | 5 | 1 | 2024-06-10 |

（90001 第 62 抽提前出金并重置计数，第 152 抽距上次出金 90 抽即吃满硬保底；90002 一次吃满）

### 3. 解题思路

口径：保底间隔 = 相邻两次"出金并重置"之间的抽数差（含端点），首个间隔 = 第一次出金的序号；分布输出 间隔值 × 发生次数 × 占比。实现路径：方案 A 先过滤五星出金记录（出金即重置），用 LAG 取同玩家上一次出金序号，差值即间隔，COALESCE(..., 0) 兜底首个间隔；方案 B 不依赖 is_pity 字段，用抽卡序号对 90 取模划分"名义轮次"，取每轮首次出金的轮内位置，验证概率曲线的前段表现。**【避坑指南】** 两种口径必须区分——方案 A 是玩家真实体验（提前出金会重置轮次），方案 B 是设计概率曲线（固定 90 抽切轮）；若用 B 的名义轮次去回答"玩家体验分布"就会答错。其余易错点：出金重置而四星不重置，过滤条件必须与产品规则一致；draw_seq 跨会话断档时 LAG 差值会虚高，需先校验序号连续性；首个间隔的分母（至少出过金的玩家）要在报告里声明。

### 4. 参考解法

解法一：LAG 相邻保底间隔（真实体验口径）

```sql
WITH gold AS (                              -- CTE①：过滤出重置保底的出金记录
    SELECT player_id, draw_seq
    FROM gacha_record
    WHERE item_rarity = 5                   -- 五星出金即重置保底计数（含提前出金与吃满保底）
),
gapped AS (                                 -- CTE②：与上一次出金做差
    SELECT player_id, draw_seq,
           draw_seq - COALESCE(LAG(draw_seq) OVER (PARTITION BY player_id ORDER BY draw_seq), 0) AS gap
    FROM gold                               -- 首次出金时LAG为NULL，取0后gap=首金序号（从0起算的口径）
)
SELECT gap,                                 -- 保底间隔（第几抽出金）
       COUNT(*)                             AS times,     -- 该间隔发生次数
       COUNT(DISTINCT player_id)            AS players,   -- 涉及玩家人数
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS pct  -- 占全部出金事件的比例
FROM gapped
GROUP BY gap
ORDER BY gap;
```

结果解读：gap=90 的占比若超过 35%，说明多数玩家吃满硬保底，软保底参数可能未生效或力度不足；gap<=10 的占比反映"欧皇体验"，过高会压低期望抽数与付费深度。

解法二：序号取模划分名义轮次（设计曲线口径）

```sql
WITH numbered AS (                          -- CTE①：按90抽一轮做名义切分
    SELECT player_id, draw_seq, item_rarity,
           FLOOR((draw_seq - 1) / 90)      AS round_id,     -- 第几轮（0起）：硬保底固定90抽切轮
           MOD(draw_seq - 1, 90) + 1       AS seq_in_round  -- 轮内第几抽（1~90）
    FROM gacha_record
    WHERE draw_seq <= 900                  -- 只看前10轮，控制规模并保证轮次完整
),
gold_in_round AS (                          -- CTE②：每轮首次出金的轮内位置
    SELECT player_id, round_id, MIN(seq_in_round) AS gold_seq
    FROM numbered
    WHERE item_rarity = 5
    GROUP BY player_id, round_id
)
SELECT gold_seq,                                        -- 轮内首次出金抽数
       COUNT(*) AS rounds,                              -- 出现次数（轮数）
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS pct  -- 占比
FROM gold_in_round
GROUP BY gold_seq
ORDER BY gold_seq;
```

结果解读：口径 A 反映玩家真实体验、口径 B 反映概率曲线设计；若 B 显示 60 抽附近出现概率凸起（软保底生效）而 A 的分布无对应改善，说明凸起被"提前出金重置"稀释，属机制正常现象而非参数失效。

### 5. 性能分析与优化

解法一先用 item_rarity=5 把集合缩到约 2% 再开窗，窗口规模小、代价低；解法二要对全量抽卡流水开窗编号后再过滤，明细亿级时 shuffle 与排序压力大。优化建议：优先走解法一的"先过滤后开窗"路径；draw_seq 连续性可用 player_id 粒度 COUNT(*) 与 MAX(draw_seq) 对账校验，断档数据先修复再分析；名义轮次法可改为只对五星记录 FLOOR 定轮（出金位置本身携带轮信息），避免全量开窗；按月物化"玩家×轮次"中间表供趋势报表复用。

> Hive/Spark 差异：LAG 语法一致；亿级窗口先 DISTRIBUTE BY player_id SORT BY draw_seq 预排序可降低单 reducer 排序压力；Spark 的 AQE 可自动处理玩家数倾斜（ whale 玩家抽数极多时）。

### 6. 面试延伸考点

- **【面试高频】LAG 的 COALESCE 兜底为什么重要？** 回答要点：窗口首行 LAG 为 NULL，直接相减会把"首次出金"样本整体丢成 NULL，分布头部缺失；COALESCE(...,0) 让首个间隔等于首金序号，与"从 0 开始计数"的口径一致，这是窗口题的高频送分/送命点。
- **小保底歪了大保底怎么建模？** 回答要点：引入"是否歪"标记（is_up 字段），间隔分布按 歪/不歪 分层统计，分别验证 UP 概率与综合概率；两段保底（歪后必中）会把间隔分布切成双峰，画图时要在同一张图分层标注。
- **【避坑指南】draw_seq 断档会怎样？** 回答要点：LAG 差值会把两个会话之间（甚至数月间）的抽数算进一个间隔，分布出现超长尾；处理是先校验连续性、剔除断档样本或改用逐抽累计计数器而非回填序号。
- **如何区分概率异常与脚本刷抽？** 回答要点：分布异常叠加"单位时间抽数"监控——脚本账号抽数密集且间隔分布畸变；先在样本层剔除脚本与工作室账号，再看真实玩家的概率表现，否则结论被污染。

### 7. 业务拓展思考

保底分布是抽卡商业化的"体温计"：分布健康时可推算每位付费玩家的期望抽数成本，校准礼包定价与保底档位促销（如 90 抽礼包）的毛利。体验侧联动：对即将吃满保底的玩家推送"再抽必得"提示可提升临门一脚的转化，但概率公示与保底规则须符合合规要求。口径延展上，可按玩家付费层级拆分布——大 R 更多靠提前出金还是吃满保底，直接影响"倍率卡池"与定向补给的设计；再监控"吃满保底玩家的次月流失率"，把非酋体验量化成留存风险，为软保底参数调整提供硬证据。

## GAME-26 连续 3 日登录玩家识别

### 1. 业务背景

用户运营在每周活跃维护专项里，需要圈出"连续 3 日及以上登录"的玩家，发放连续登录奖励并推送回流礼包。连续登录是活跃质量信号：这类玩家次周留存与付费意愿显著更高，运营资源应优先投给他们；同时该人群规模本身是版本健康度指标——版本更新后连续登录人数若下滑，说明日常玩法吸引力下降，需要与策划联动调整日常任务结构。SQL 上这是经典的"连续性问题"，考察日期序列的切分技巧与窗口函数功底，面试官常在此基础上追问"最长连续天数""连续付费天数"等变体，一题多练。

### 2. 表结构说明

daily_login（每日登录去重表，数仓已按 玩家×日期 收敛）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| login_date | DATE | 登录日期 |
| channel | VARCHAR(32) | 注册渠道 |
| is_pay_today | TINYINT | 当日是否付费 |

示例数据：

| player_id | login_date | channel | is_pay_today |
|---|---|---|---|
| 11001 | 2024-06-01 | tiktok | 0 |
| 11001 | 2024-06-02 | tiktok | 1 |
| 11001 | 2024-06-03 | tiktok | 0 |
| 11001 | 2024-06-06 | tiktok | 0 |
| 11002 | 2024-06-01 | huawei | 0 |

（11001 在 06-01~06-03 连续 3 天，06-06 为断档后的新段）

### 3. 解题思路

方案 A 经典"日期减序号"法：同一玩家内按日期排序编号 rn，连续登录段的日期每天 +1、rn 每天 +1，因此 DATE_SUB(login_date, INTERVAL rn DAY) 在同一段内是常数——以此为分组键即可把连续段切开，GROUP BY 段键 + HAVING COUNT(*) >= 3 筛出目标。方案 B LAG 法：对每行取前 1 天、前 2 天的登录日期，若恰好都相差 1 天，则该玩家存在连续 3 日，DISTINCT 收敛输出名单。**【避坑指南】** 两法的前提都是表已按 玩家×日期 去重——若同一天存在多条登录记录，ROW_NUMBER 会把同日编成多个号，日期减序号的差值逐行变化，一个自然日被拆成"伪多天"，连续段被错误延长或切断，这是本题最常见的翻车点。另外 ROW_NUMBER 必须以 player_id 分区，漏写分区会全表串号；"连续 N 日"是否允许补签卡也要先与产品规则对齐。

### 4. 参考解法

解法一：日期减序号分组（连续段切分标准解）

```sql
WITH numbered AS (                          -- CTE①：玩家内按日期编号
    SELECT player_id, login_date,
           ROW_NUMBER() OVER (PARTITION BY player_id ORDER BY login_date) AS rn
    FROM daily_login
    WHERE login_date BETWEEN '2024-06-01' AND '2024-06-30'   -- 观察窗（月初边界配合解法二说明）
),
grp AS (                                    -- CTE②：日期减序号=段键
    SELECT player_id, login_date,
           DATE_SUB(login_date, INTERVAL rn DAY) AS grp_key   -- 连续日期+1、rn+1，差值在同段内恒定
    FROM numbered
)
SELECT player_id,
       MIN(login_date) AS streak_start,     -- 段起点
       MAX(login_date) AS streak_end,       -- 段终点
       COUNT(*)        AS streak_days       -- 段长（连续天数）
FROM grp
GROUP BY player_id, grp_key                 -- 段键+玩家，一段一行
HAVING COUNT(*) >= 3                        -- 连续3日及以上
ORDER BY player_id, streak_start;
```

结果解读：输出的是"每个连续段"，同一玩家可能命中多段；发放奖励类场景要"存在 >=3 天段"的名单，再包一层按玩家去重即可；要评"最长连续天数"时在外层取 MAX(streak_days)。

解法二：LAG 双前日判断（存在性检测）

```sql
WITH lagged AS (                            -- CTE①：取前1日与前2日的登录日期
    SELECT player_id, login_date,
           LAG(login_date, 1) OVER (PARTITION BY player_id ORDER BY login_date) AS d1,  -- 前一天
           LAG(login_date, 2) OVER (PARTITION BY player_id ORDER BY login_date) AS d2   -- 前两天
    FROM daily_login
    WHERE login_date BETWEEN '2024-05-30' AND '2024-06-30'   -- 起点提前2天，保证6月1日的连续性可判
)
SELECT DISTINCT player_id                   -- 连续5天会命中多行，DISTINCT 收敛成名单
FROM lagged
WHERE DATEDIFF(login_date, d1) = 1          -- 昨天恰好是今天的前一天
  AND DATEDIFF(d1, d2) = 1;                 -- 前天恰好是昨天的前一天，两者同时成立即存在3连
```

结果解读：解法二直接输出"存在连续 3 日的玩家名单"，代码最短，但拿不到段长与段数；运营要按连续天数分档（3/7/14 天梯度奖励）时必须用解法一。两法在观察窗边界上要注意：LAG 需要提前读取窗前 2 天的数据，否则月初的连续性判断会失真。

### 5. 性能分析与优化

两解法都需要一次窗口排序；解法一多一层 GROUP BY，解法二少分组但 DISTINCT 也要去重，代价相近，数据量决定差异。优化建议：daily_login 建 (player_id, login_date) 主键或联合索引，窗口排序可走索引免 filesort；观察窗内分区裁剪；圈人场景高频调用时，把"玩家最长连续段/当前连续天数"预计算进用户标签表每日增量更新，查询端零计算；"最长连续天数 TopN"在解法一外层套 ROW_NUMBER 即可，不要拉到应用层二次处理。

> Hive/Spark 差异：Hive 中 DATE_SUB(login_date, rn) 需先用 to_date/date_format 统一格式；大表开窗前 DISTRIBUTE BY player_id SORT BY login_date 可减少单点排序压力；连续段也可用 LAG 断点累加（SUM(CASE WHEN 断点 THEN 1 ELSE 0 END) OVER 累计）实现段编号。

### 6. 面试延伸考点

- **【面试高频】"日期减序号"法的原理是什么？** 回答要点：连续日期公差为 1、行号公差也为 1，两者相减在同段内为常数、跨段跳变，因此差值即段键；该技巧可推广到任何"连续事件段"切分——连续付费、连续胜场、连续打卡。
- **如何求每个玩家的最长连续登录天数？** 回答要点：解法一外层再包一层 GROUP BY player_id 取 MAX(streak_days)；注意窗口 MAX 不能直接引用同层聚合别名，需两层嵌套，这是聚合与窗口混用的经典语法边界。
- **【避坑指南】同一天多条登录记录会发生什么？** 回答要点：ROW_NUMBER 把同日编成多个号，日期减序号差值逐行递减，一天被拆成"伪多天"，连续段被错误延长或切断；必须先按 玩家×日期 去重，或在窗口前先 SELECT DISTINCT。
- **补签/挂机算不算连续？** 回答要点：口径贴产品规则——有补签功能时把补签流水并入登录事实表并打来源标记，输出"含补签/不含补签"两版；纯挂机登录建议用"有效活跃"（在线时长阈值）口径过滤。

### 7. 业务拓展思考

连续登录人群是运营金矿：可按连续天数分档（3/7/14/30）设计阶梯奖励，并对"断签前一日"玩家做挽留推送——断签预测比流失预测更前置、干预成本更低。策划联动：签到系统改版（补签卡、连续奖励加码）后，用连续段分布的前后对比验证效果；买量联动：连续 3 日率高的渠道质量更优，可把它作为 oCPM 的深度回传事件替代浅层激活。口径延展上，"连续活跃"可升级为"连续有效活跃"（当日在线 >= 15 分钟或完成日常任务），过滤挂机与灌水登录，让圈人更精准、奖励成本更可控。

## GAME-27 公会活跃度排名

### 1. 业务背景

公会运营每周一发布公会活跃榜，前 10 名公会发放专属奖励，连续垫底的公会触发合并预警。活跃度不是单一指标：在编人数、周活跃人数、活跃率（周活跃/在编）、人均在线时长共同刻画公会健康度，需要加权合成一个分数再排名。榜单直接影响生态：活跃公会吸引新玩家入驻，死公会拖累社交留存与公会玩法参与率。SQL 难点是"多指标聚合 + 加权打分 + 排名"的分层组织，以及并列名次的处理（RANK 与 DENSE_RANK 的业务选择）、无活跃成员公会的空值兜底——这些细节恰是面试官区分"背窗口函数"与"真会用"的地方。

### 2. 表结构说明

guild_info（公会主表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| guild_id | INT | 公会ID |
| guild_name | VARCHAR(64) | 公会名 |
| server_id | INT | 区服 |

guild_member（成员表，在编名单）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| guild_id | INT | 公会ID |
| player_id | BIGINT | 成员ID |
| join_date | DATE | 入会日期 |

user_active（日活跃表，玩家×日期去重）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| stat_date | DATE | 日期 |
| player_id | BIGINT | 玩家ID |
| online_minutes | INT | 当日在线分钟 |

示例数据：

guild_info：

| guild_id | guild_name | server_id |
|---|---|---|
| 1 | 王者之师 | 1 |
| 2 | 悠然小筑 | 1 |
| 3 | 峡谷先锋 | 2 |

guild_member：

| guild_id | player_id | join_date |
|---|---|---|
| 1 | 12001 | 2024-01-10 |
| 1 | 12002 | 2024-02-11 |
| 2 | 12003 | 2024-03-05 |
| 3 | 12004 | 2024-03-20 |
| 3 | 12005 | 2024-04-01 |

user_active：

| stat_date | player_id | online_minutes |
|---|---|---|
| 2024-06-03 | 12001 | 95 |
| 2024-06-04 | 12001 | 60 |
| 2024-06-05 | 12003 | 30 |
| 2024-06-06 | 12004 | 120 |
| 2024-06-07 | 12005 | 15 |

### 3. 解题思路

口径：观察窗取自然周（周一~周日）；周活跃人数 = 窗口内有登录的成员数；活跃率 = 周活跃人数/在编人数；人均时长 = 周总在线分钟/周活跃人数。加权分应先对各指标归一化（除以全服最大值或用分位数）再加权，避免"人数"与"比率"量纲打架；示例用简化加权（活跃人数 0.5 + 活跃率 0.3 + 人均小时 0.2）并在注释说明。实现路径：方案 A 四层结构——成员周活跃明细 → 公会指标聚合 → 打分层 → RANK/DENSE_RANK 窗口排名，注意窗口不能引用同层聚合别名，必须拆 CTE；方案 B 打分后用相关子查询 COUNT(比它高分的行)+1 实现排名，展示无窗口函数的降级写法。易错点：成员整周未登录时 LEFT JOIN 聚合出 NULL，要 COALESCE 记 0；无人活跃的公会人均时长分母为 0，需 NULLIF 防零除；发奖取前 N 时 RANK 并列跳号会导致实际发奖人数不足，应按业务选择 DENSE_RANK。

### 4. 参考解法

解法一：分层 CTE + RANK/DENSE_RANK 窗口（标准解）

```sql
WITH member_week AS (                       -- CTE①：成员级周活跃明细
    SELECT gm.guild_id, gm.player_id,
           COALESCE(SUM(ua.online_minutes), 0) AS week_minutes,   -- 整周未登录记0
           COUNT(DISTINCT ua.stat_date)        AS active_days     -- 有登录的天数（未登录为0）
    FROM guild_member gm
    LEFT JOIN user_active ua
           ON ua.player_id = gm.player_id
          AND ua.stat_date BETWEEN '2024-06-03' AND '2024-06-09' -- 自然周窗口
    GROUP BY gm.guild_id, gm.player_id
),
guild_metric AS (                           -- CTE②：公会级指标聚合
    SELECT guild_id,
           COUNT(*)                                          AS member_cnt,   -- 在编人数
           SUM(CASE WHEN active_days > 0 THEN 1 ELSE 0 END)  AS active_users, -- 周活跃人数
           SUM(week_minutes)                                 AS total_minutes -- 周总在线时长
    FROM member_week
    GROUP BY guild_id
),
scored AS (                                 -- CTE③：加权打分（简化权重，生产建议先归一化）
    SELECT guild_id, member_cnt, active_users, total_minutes,
           ROUND(active_users * 0.5                                    -- 活跃人数（量纲大，权重压低意图）
                 + active_users / member_cnt * 100 * 0.3               -- 活跃率×100，拉到百分位量纲
                 + total_minutes / NULLIF(active_users, 0) / 60 * 0.2  -- 人均小时数，NULLIF防无人活跃除零
                 , 2) AS score
    FROM guild_metric
)
SELECT s.guild_id,
       gi.guild_name,
       s.member_cnt,
       s.active_users,
       ROUND(s.active_users / s.member_cnt, 4)               AS active_rate,  -- 活跃率
       ROUND(s.total_minutes / NULLIF(s.active_users, 0), 1) AS avg_minutes,  -- 人均在线分钟
       s.score,
       RANK()       OVER (ORDER BY s.score DESC) AS rk,        -- 并列同名次、后续跳号（1,1,3）
       DENSE_RANK() OVER (ORDER BY s.score DESC) AS dense_rk    -- 并列同名次、后续不跳号（1,1,2）
FROM scored s
JOIN guild_info gi ON gi.guild_id = s.guild_id
ORDER BY rk;
```

结果解读：rk 与 dense_rk 的差异在并列时显现——Top10 发奖若按 RANK，出现"并列第 3 后直接第 5"，实际只发 4 家；要发满 10 家应取 dense_rk 前 10，这是业务语义而非语法偏好。

解法二：相关子查询排名（无窗口函数的降级写法）

```sql
WITH member_week AS (
    SELECT gm.guild_id, gm.player_id,
           COALESCE(SUM(ua.online_minutes), 0) AS week_minutes,
           COUNT(DISTINCT ua.stat_date)        AS active_days
    FROM guild_member gm
    LEFT JOIN user_active ua
           ON ua.player_id = gm.player_id
          AND ua.stat_date BETWEEN '2024-06-03' AND '2024-06-09'
    GROUP BY gm.guild_id, gm.player_id
),
scored AS (
    SELECT guild_id,
           ROUND(SUM(CASE WHEN active_days > 0 THEN 1 ELSE 0 END) * 0.5
                 + SUM(CASE WHEN active_days > 0 THEN 1 ELSE 0 END) / COUNT(*) * 100 * 0.3
                 + SUM(week_minutes) / NULLIF(SUM(CASE WHEN active_days > 0 THEN 1 ELSE 0 END), 0) / 60 * 0.2
                 , 2) AS score
    FROM member_week
    GROUP BY guild_id
)
SELECT s1.guild_id,
       s1.score,
       (SELECT COUNT(*) + 1                       -- 比自己分高的行数+1 = 名次（并列同名次跳号）
        FROM scored s2
        WHERE s2.score > s1.score)                AS rk
FROM scored s1
ORDER BY rk, s1.guild_id;
```

结果解读：相关子查询的排名结果与 RANK() 完全一致（并列跳号），可作为窗口函数不可用环境（老版本 MySQL 5.x）的降级方案，也是理解排名语义的好教具；但每行触发一次计数，公会上万时性能急剧恶化。

### 5. 性能分析与优化

解法一两层聚合加一次窗口排序，复杂度 O(n log n)；解法二对每行执行一次子查询计数，O(n²)，公会在千级尚可、万级即明显变慢，且 CTE 被引用两次可能物化两份。优化建议：guild_member×user_active 关联前先对 user_active 按窗口裁剪分区；member_week 物化成周表（数仓例行任务），榜单查询退化为单层聚合；加权分若要归一化，用 MAX() OVER () 求全服最大值再相除，注意除零；只取前 10 名时可先 ORDER BY score DESC LIMIT 10（分数已在 scored 层算好），避免全量排序输出。

> Hive/Spark 差异：Hive 对相关子查询支持有限，排名一律用窗口函数；多指标归一化可用 PERCENT_RANK() 或 max() OVER ()；Spark SQL 支持 ANTI JOIN 与窗口函数，写法与 MySQL 基本对齐。

### 6. 面试延伸考点

- **【面试高频】RANK、DENSE_RANK、ROW_NUMBER 的区别与选型？** 回答要点：并列时 RANK 跳号（1,1,3）、DENSE_RANK 不跳（1,1,2）、ROW_NUMBER 强制唯一（1,2,3）；"取前 N 名发奖"用 DENSE_RANK 保证名额发满，"生成唯一序号/去重取一条"用 ROW_NUMBER。
- **【加分点】指标量纲不一致时怎么合成总分？** 回答要点：min-max 归一化或 z-score 标准化，或直接用分位数打分（PERCENT_RANK）；权重由业务定，最好做敏感性分析展示排名对权重的稳定性，防止"调权重即调榜单"的质疑。
- **无人活跃的公会分数怎么算？** 回答要点：人均时长分母为 0，NULLIF 使整式为 NULL；MySQL ORDER BY DESC 时 NULL 排最后，建议显式 COALESCE(score, 0) 并在业务上标记"休眠公会"进入合并观察名单。
- **如何防止 3 人小公会全勤霸榜？** 回答要点：设置最低在编门槛（HAVING member_cnt >= 20），或按公会规模分层排名、引入人数上限截断（活跃人数按 min(活跃, 上限) 计），避免小样本高比率扭曲榜单。

### 7. 业务拓展思考

公会榜可扩展为"公会健康度雷达"：活跃率、成员次周回访率、公会副本参与率多维合成，识别"人数虚胖但活跃低"的公会做合并引导。运营联动：榜单奖励之外，对连续两周活跃率下滑的公会触发"公会维护包"与会长回访；策划联动：把公会玩法（公会战）参与深度纳入打分，牵引玩法迭代方向。口径延展上，应区分"自然活跃"与"任务驱动活跃"（只为公会任务奖励上线）——后者在奖励停发后衰减快，榜单要看连续四周趋势而非单周快照，避免被短期激励冲榜误导资源投放。

## GAME-28 玩家最高关卡进度分布

### 1. 业务背景

关卡策划与发行团队在月度内容消耗报告里，需要玩家"最高关卡进度"的分布：多少玩家停在第 5 章、多少人已通关当前版本最后一关。进度分布反映内容消耗速度——玩家推进太快说明内容储备不足（长草期提前到来），卡在固定区间说明难度曲线异常；同时进度分布是付费点设计依据：付费墙通常设在进度中段，分布右尾（最快玩家）的到达日期直接指导新章节的上线排期。这题考察"两层聚合"的意识：先收敛到玩家粒度，再做分布聚合，很多候选人会一步 GROUP BY level_id 而把进度分布做成通关流量，正是面试要筛掉的典型错误。

### 2. 表结构说明

level_pass（关卡通关流水，每次通关一行，关卡全局递增）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| chapter_id | INT | 章节ID |
| level_id | INT | 关卡ID（全局唯一递增） |
| pass_time | DATETIME | 通关时间 |

示例数据：

| player_id | chapter_id | level_id | pass_time |
|---|---|---|---|
| 13001 | 3 | 301 | 2024-06-01 20:10:00 |
| 13001 | 3 | 305 | 2024-06-03 21:30:00 |
| 13002 | 1 | 105 | 2024-06-02 19:00:00 |
| 13002 | 2 | 201 | 2024-06-10 20:15:00 |
| 13003 | 1 | 102 | 2024-06-05 21:05:00 |

### 3. 解题思路

口径：最高关卡 = 每玩家通关记录中 level_id 的最大值（关卡全局递增时 MAX 即最高进度，若章节内重置需先拼接 chapter_id 与 level_id 构造全局序号）；分布 = 对"每人最高关"再做一次聚合；若要"到达该关及以上"的累计占比（漏斗式读法），用按关卡降序的累计求和窗口。实现路径：方案 A 双层聚合——第一层 GROUP BY player_id 求 MAX(level_id)，第二层对 top_level 求人数、占比与降序累计占比；方案 B"最新记录法"——ROW_NUMBER 按 pass_time DESC 取每人最近一次通关记录代表"当前推进位置"，适合存在资料片重置、进度回退的产品，与"历史最高"口径形成对照。易错点：两层聚合不能合并成一层；累计窗口 ORDER BY top_level DESC 时默认 RANGE 帧会把并列关卡值整帧累计（恰好是我们想要的"该关及以上"语义，需在注释里说清）；分母是"有通关记录的玩家"，未进入关卡的玩家要单独说明。

### 4. 参考解法

解法一：双层聚合 + 降序累计占比（历史最高口径）

```sql
WITH user_top AS (                          -- CTE①：每人最高关卡（先收敛到玩家粒度）
    SELECT player_id, MAX(level_id) AS top_level
    FROM level_pass
    GROUP BY player_id
)
SELECT top_level,                                                        -- 最高关卡
       COUNT(*)                                                          AS users,    -- 停在该关的人数
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)                AS pct,      -- 该层占比
       ROUND(SUM(COUNT(*)) OVER (ORDER BY top_level DESC) * 100.0
             / SUM(COUNT(*)) OVER (), 2)                                 AS cum_pct   -- 到达该关及以上的累计占比（RANGE帧含并列值）
FROM user_top
GROUP BY top_level
ORDER BY top_level;
```

结果解读：cum_pct 在某一关出现断崖（如 40%→12%）即"大关卡墙"；分布右尾稀疏说明头部玩家内容消耗快，新章节排期要前移，否则流失先于内容枯竭发生。

解法二：最新记录法（当前进度口径，适配进度重置）

```sql
WITH latest AS (                            -- CTE①：每人最近一次通关记录
    SELECT player_id, chapter_id, level_id, pass_time,
           ROW_NUMBER() OVER (PARTITION BY player_id ORDER BY pass_time DESC) AS rn
    FROM level_pass
)
SELECT chapter_id,                                       -- 当前所在章节
       COUNT(*)                                          AS users,       -- 玩家数（每人仅一条，无需去重）
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS pct,        -- 章节分布占比
       MAX(pass_time)                                    AS latest_pass_time  -- 该章节最近一次仍有玩家通关（内容新鲜度）
FROM latest
WHERE rn = 1                                             -- 每人只保留最新一条记录
GROUP BY chapter_id
ORDER BY chapter_id;
```

结果解读：与"历史最高"口径的差异在于能识别"资料片重置"——重置后玩家最新记录回到低章，运营可据此区分"真停滞"与"重新开荒"，避免把重置误判为进度倒退流失。

### 5. 性能分析与优化

解法一第一层聚合后行数 = 玩家数，第二层极轻，是亿级明细下的稳妥路径；解法二的 ROW_NUMBER 需对全明细排序，通关流水亿级时开销显著。优化建议：通关流水按 pass_time 分区，报表只取报告期或最新分区快照；数仓维护 player_progress 主键属性表（每日更新最高关），报表层免窗口；若需要"最快玩家到达日期"分布，在解法一的 user_top 上再带 MIN(pass_time) 分桶；章节级分布可由关卡级分布上卷（rollup）得到，避免重复扫明细。

> Hive/Spark 差异：取最新记录时 Hive 可用 MAX(struct(pass_time, level_id)) 的 max-by 技巧避免窗口排序，Spark SQL 提供 max_by()；双层聚合在 Hive 是两次 shuffle，先 GROUP BY player_id 落临时表能显著降本。

### 6. 面试延伸考点

- **【面试高频】"各关卡通关人数"和"最高关卡分布"是一回事吗？** 回答要点：不是——前者对明细按关卡聚合，一人多关会被重复计数，画出的是通关流量；后者先收敛到玩家再聚合，才是存量进度分布；混淆会让管理层把"第 5 章通关人数多"误读为"多数人卡在第 5 章"。
- **【加分点】如何计算"平均推进速度"？** 回答要点：每人 (MAX(pass_time)-MIN(pass_time)) / 推进关卡数，或到固定关卡的天数取分位数；速度分布比均值更能反映肝帝与休闲玩家的两极，直接服务内容排期。
- **关卡号章节内重置时怎么求最高进度？** 回答要点：构造全局关卡序号（chapter_id * 1000 + level_id）或关联关卡维表的 sort_order 字段再取 MAX；直接 MAX(level_id) 会把 3-1 排到 2-9 之后出错。
- **没打过任何关卡的玩家在哪？** 回答要点：通关流水只见活跃推进者，完整分布要 LEFT JOIN 新增/活跃名单补"0 进度"人群，否则整体进度被高估，新手卡点会被隐藏。

### 7. 业务拓展思考

进度分布应与内容排期联动：当 90 分位玩家距最新关卡不足 7 天内容量时触发"内容饥饿预警"，推动开发加急或上线复刻活动缓冲。付费联动：观察付费金额按进度段的分布，验证付费墙位置——付费集中在墙前 1~2 关说明设计有效，集中在墙后说明玩家绕过了付费点（靠肝或广告），需重新设计门槛。口径延展上，可按注册周 cohort 画进度曲线，对比新旧版本推进速度，作为关卡难度调参的量化依据；也可输出"进度-留存"交叉表，找出留存骤降的进度区间，与关卡通过率数据互相印证定位流失关卡。

## GAME-29 各渠道付费用户 ARPU 分档

### 1. 业务背景

买量团队在季度渠道复盘时，需要按注册渠道拆分付费用户的档位结构：小 R（累计 < 30 元）、中 R（30~300 元）、大 R（>= 300 元）各占多少、各渠道 ARPPU 差多少。不同渠道的用户付费结构差异巨大：有的渠道大 R 浓度高、收入靠氪金玩法支撑，有的渠道全是 6 元首充党；结构决定后续投什么素材、接什么联动、礼包怎么配。**【避坑指南】** 口径上必须显式声明两件事：渠道归属用注册渠道还是首充渠道、档位边界是左闭右开还是双闭——恰好 30 元的玩家只能归一档，若两处都写 >= 会出现双计或漏计，商务对数时口径不一致就会"数字打架"。

### 2. 表结构说明

user_login（登录流水表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| player_id | BIGINT | 玩家ID |
| channel | VARCHAR(32) | 注册渠道 |
| login_date | DATE | 登录日期 |

orders（充值订单表，一笔订单一行）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | VARCHAR(64) | 订单号 |
| player_id | BIGINT | 玩家ID |
| amount | DECIMAL(10,2) | 金额 |
| pay_date | DATE | 支付日期 |

示例数据：

user_login：

| player_id | channel | login_date |
|---|---|---|
| 14001 | bilibili | 2024-05-01 |
| 14001 | bilibili | 2024-05-03 |
| 14002 | huawei | 2024-05-02 |
| 14003 | tiktok | 2024-05-02 |
| 14004 | xiaomi | 2024-05-05 |

orders：

| order_id | player_id | amount | pay_date |
|---|---|---|---|
| O4001 | 14001 | 68.00 | 2024-05-03 |
| O4002 | 14001 | 328.00 | 2024-06-01 |
| O4003 | 14002 | 6.00 | 2024-05-04 |
| O4004 | 14003 | 98.00 | 2024-05-10 |
| O4005 | 14004 | 30.00 | 2024-06-05 |

### 3. 解题思路

口径：档位按"统计期内累计充值"划分，边界左闭右开（[0,30)、[30,300)、[300,∞)），SQL 用 CASE 自上而下短路实现（先判 >=300 再判 >=30）；渠道取首登渠道（ROW_NUMBER 取最早登录行）。实现路径：方案 A 三层 CTE——注册渠道 → 玩家累计付费（先 GROUP BY 收敛）→ CASE 分档，最后渠道粒度条件聚合成宽表（各档人数列 + 大 R 流水占比）；方案 B 在订单明细上用 SUM(amount) OVER (PARTITION BY player_id) 直接给每行打上该玩家的累计额与档位，免先聚合，但**【面试高频】** 行级打档后同一玩家出现多行，直接 COUNT(*) 会按订单数计人头、档位人数虚高数倍，必须 DISTINCT 或再收敛一层；组内占比用 SUM(COUNT(*)) OVER (PARTITION BY channel) 窗口。退款是否从累计额扣减需与财务对齐。

### 4. 参考解法

解法一：先聚合后分档（CTE 分层 + 行转列宽表）

```sql
WITH reg_channel AS (                       -- CTE①：每人注册渠道（首登渠道）
    SELECT player_id, channel
    FROM (SELECT player_id, channel,
                 ROW_NUMBER() OVER (PARTITION BY player_id ORDER BY login_date) AS rn
          FROM user_login) t
    WHERE rn = 1                            -- 最早一次登录的渠道即注册渠道
),
user_pay AS (                               -- CTE②：期内累计充值（先收敛到玩家粒度）
    SELECT player_id, SUM(amount) AS total_amt
    FROM orders
    WHERE pay_date BETWEEN '2024-05-01' AND '2024-06-30'
    GROUP BY player_id
),
tiered AS (                                 -- CTE③：关联渠道并分档
    SELECT rc.channel, up.player_id, up.total_amt,
           CASE WHEN up.total_amt >= 300 THEN '3_大R'     -- 从高档往低档判，CASE短路天然实现左闭右开
                WHEN up.total_amt >= 30  THEN '2_中R'
                ELSE '1_小R' END        AS tier
    FROM user_pay up
    JOIN reg_channel rc ON rc.player_id = up.player_id      -- 付费玩家必有首登记录
)
SELECT channel,
       COUNT(*)                                              AS pay_users,    -- 该渠道付费人数
       ROUND(AVG(total_amt), 2)                              AS arppu,        -- 渠道付费人均
       SUM(CASE WHEN tier = '1_小R' THEN 1 ELSE 0 END)       AS small_r,      -- 小R人数（行转列）
       SUM(CASE WHEN tier = '2_中R' THEN 1 ELSE 0 END)       AS mid_r,        -- 中R人数
       SUM(CASE WHEN tier = '3_大R' THEN 1 ELSE 0 END)       AS whale_r,      -- 大R人数
       ROUND(SUM(CASE WHEN tier = '3_大R' THEN total_amt ELSE 0 END)
             * 100.0 / SUM(total_amt), 2)                    AS whale_amt_pct -- 大R流水占该渠道比
FROM tiered
GROUP BY channel
ORDER BY arppu DESC;
```

结果解读：bilibili 若大 R 流水占比 55%、tiktok 仅 20%，说明前者聚集核心玩家，适合投深度玩法素材；tiktok 应配轻量礼包策略并评估广告变现的补充空间。

解法二：订单明细窗口打档 + 长表组内占比

```sql
WITH reg_channel AS (                       -- CTE①：注册渠道（口径同解法一）
    SELECT player_id, channel
    FROM (SELECT player_id, channel,
                 ROW_NUMBER() OVER (PARTITION BY player_id ORDER BY login_date) AS rn
          FROM user_login) t
    WHERE rn = 1
),
tagged AS (                                 -- CTE②：窗口在明细行上直接算累计并打档
    SELECT o.player_id,
           SUM(o.amount) OVER (PARTITION BY o.player_id) AS total_amt,   -- 该玩家累计充值冗余到每行
           CASE WHEN SUM(o.amount) OVER (PARTITION BY o.player_id) >= 300 THEN '3_大R'
                WHEN SUM(o.amount) OVER (PARTITION BY o.player_id) >= 30  THEN '2_中R'
                ELSE '1_小R' END          AS tier
    FROM orders o
    WHERE o.pay_date BETWEEN '2024-05-01' AND '2024-06-30'
),
dedup AS (                                  -- CTE③：同一玩家各行档位/累计一致，DISTINCT收敛到玩家粒度
    SELECT DISTINCT player_id, tier, total_amt
    FROM tagged
)
SELECT rc.channel,
       d.tier,
       COUNT(*)                                                            AS users,     -- 渠道×档位人数
       ROUND(COUNT(*) * 100.0
             / SUM(COUNT(*)) OVER (PARTITION BY rc.channel), 2)            AS users_pct, -- 渠道内档位人数占比
       ROUND(AVG(d.total_amt), 2)                                          AS avg_amt    -- 该档人均累计
FROM dedup d
JOIN reg_channel rc ON rc.player_id = d.player_id
GROUP BY rc.channel, d.tier
ORDER BY rc.channel, d.tier;
```

结果解读：长表输出 渠道×档位 结构，users_pct 直接可贴报表；与解法一相比少一次明细级 GROUP BY、多一次 DISTINCT，数据量小时差异不大；关键都在于"行级打档后必须收敛"，漏掉则人数按订单膨胀。

### 5. 性能分析与优化

解法一先 GROUP BY 玩家（明细→玩家，降一到两个数量级）再聚合，中间结果小，是亿级订单下的稳妥路径；解法二的窗口要保留全部明细行参与排序与去重，内存与临时表压力大。优化建议：reg_channel 固化成维表（注册渠道通常不变，玩家级维表复用率极高）；大表先按 pay_date 分区裁剪；档位阈值参数化（应用层传参或配置表 JOIN），防止阈值调整时全量改 SQL；输出渠道小计与总计可用 GROUP BY channel, tier + WITH ROLLUP；Hive 下优先解法一的预聚合路径，窗口全明细 shuffle 代价高。

> Hive/Spark 差异：窗口 SUM OVER PARTITION 需全量 shuffle 到玩家桶，大表先用 GROUP BY 收敛更稳；DISTINCT 多列在 Hive 按整行去重，也可 GROUP BY player_id 收敛后取 MAX(tier)（档位单调时等价）。

### 6. 面试延伸考点

- **【面试高频】档位边界"左闭右开"为什么重要？怎么在 SQL 里保证？** 回答要点：恰好 30 元的玩家只能归一档，两处都写 >= 会双计；CASE 自上而下短路，从高档开始判断天然实现左闭右开，并在报告注明 [30,300) 这类边界记法。
- **渠道归属用注册渠道还是首充渠道？** 回答要点：注册渠道衡量"买量拉来谁"，首充渠道衡量"谁在变现"；换机重装导致的渠道迁移要在报告中说明，买量复盘通常固定用注册渠道并固化维表。
- **【避坑指南】订单行级打档后为什么必须去重？** 回答要点：窗口把玩家累计冗余到每一行，直接 COUNT(*) 会按订单数计人头、档位人数虚高数倍；DISTINCT 或先 GROUP BY player_id 收敛均可，这考查"分析粒度"意识。
- **档位阈值怎么定更科学？** 回答要点：用期内累计充值的分位数（如 P50/P90/P99）而非拍脑袋整数，并保持季度内稳定以便跨期对比；阈值调整时要做迁移矩阵看人数流动，避免档位结构突变误判为业务变化。

### 7. 业务拓展思考

档位结构是商业化健康度的结构化视图：大 R 占比过高的渠道要建流失预警（大 R 断充即预警外呼），小 R 占比高的渠道考验"首充到复充"的转化设计（连续订阅、战令）。买量联动：把档位结构回传投放平台做价值分层优化（VO），用大 R 信号定向高价值相似人群；运营联动：中 R 是承上启下的核心盘，礼包与月卡的主目标群。口径延展上，可把"期内累计档位"换成"月度档位转移矩阵"（本月档位→下月档位的迁移概率），识别升级/降级流动，评估大版本与付费活动对付费深度的真实拉动力，而非只看档位快照。

## GAME-30 活动期间 DAU 与流水弹性分析

### 1. 业务背景

发行负责人在月度经营会上，需要评估周年庆活动（6/1~6/14）对大盘的拉动：活动期 DAU 相比前期基线提升多少？流水提升多少？流水增幅中有多少来自 DAU 增长、多少来自人均付费上升？"弹性"指流水增幅与 DAU 增幅的比值：弹性 >1 说明活动不仅拉人也拉付费深度，值得常态化复用；弹性 <1 说明拉来的多是白嫖流量，要复盘活动设计。**【面试高频】** 流水的乘法分解（流水 = DAU × 付费率 × ARPPU）是经营分析的基本功，SQL 要输出三率让归因一目了然；基线选择（等长、同周期结构、无其他活动）与 ARPU 的加权口径（SUM/SUM 而非日均均值）是本题的两个隐藏扣分点。

### 2. 表结构说明

daily_overview（数仓 ADS 层日汇总表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| stat_date | DATE | 日期 |
| dau | INT | 日活跃用户数 |
| new_users | INT | 新增用户数 |
| pay_amount | DECIMAL(14,2) | 当日总流水 |
| pay_users | INT | 当日付费人数 |

activity_schedule（活动日程表）：

| 字段名 | 类型 | 含义 |
|---|---|---|
| activity_id | VARCHAR(32) | 活动ID |
| activity_name | VARCHAR(64) | 活动名 |
| start_date | DATE | 开始日期 |
| end_date | DATE | 结束日期 |

示例数据：

daily_overview：

| stat_date | dau | new_users | pay_amount | pay_users |
|---|---|---|---|---|
| 2024-05-25 | 512000 | 38000 | 1860000.00 | 41000 |
| 2024-05-26 | 498000 | 35500 | 1720000.00 | 39500 |
| 2024-06-01 | 615000 | 52000 | 3250000.00 | 66000 |
| 2024-06-02 | 640000 | 55000 | 3580000.00 | 70500 |
| 2024-06-03 | 598000 | 47000 | 2760000.00 | 58000 |

activity_schedule：

| activity_id | activity_name | start_date | end_date |
|---|---|---|---|
| A2024Anniv | 周年庆典 | 2024-06-01 | 2024-06-14 |

### 3. 解题思路

口径：基线取活动前等长 14 天（5/18~5/31），并注明是否含节假日差异；指标：DAU 均值提升率、日均流水提升率、ARPU（SUM(流水)/SUM(DAU)）提升率；弹性 = 流水提升率 / DAU 提升率；恒等关系为 流水增幅 ≈ (1+DAU 增幅) × (1+ARPU 增幅) - 1，三率互相印证。实现路径：方案 A LEFT JOIN 活动日程表给每天打 is_act 标记，再条件聚合一次输出活动期/基线期指标与提升率，日程变化时 SQL 不用改（活动日期由表驱动）；派生指标（ARPU 提升率、弹性）再包一层 CTE 计算，因为同层 SELECT 不能引用聚合别名。方案 B 对基线期、活动期、活动后 7 天三段独立聚合后 UNION 成对比行，简单直观并顺带观察"活动后回落"。易错点：**【避坑指南】** ARPU 必须 SUM(pay_amount)/SUM(dau)——对日均 ARPU 再求平均是等权平均，会放大低 DAU 日的权重，口径错误会把弹性算歪；多活动档期重叠时 BETWEEN JOIN 一对多膨胀，需先按日聚合日程或定优先级。

### 4. 参考解法

解法一：日程表 JOIN 打标 + 条件聚合（表驱动，活动可配置）

```sql
WITH marked AS (                            -- CTE①：给每一天打活动标记
    SELECT d.stat_date, d.dau, d.pay_amount,
           CASE WHEN a.activity_id IS NOT NULL THEN 1 ELSE 0 END AS is_act
    FROM daily_overview d
    LEFT JOIN activity_schedule a
           ON d.stat_date BETWEEN a.start_date AND a.end_date   -- 命中活动日程即标记为1
    WHERE d.stat_date BETWEEN '2024-05-18' AND '2024-06-14'      -- 基线14天 + 活动14天
),
core AS (                                   -- CTE②：条件聚合一次算出两期指标与提升率
    SELECT SUM(CASE WHEN is_act = 1 THEN dau ELSE 0 END) / NULLIF(SUM(is_act), 0)      AS act_avg_dau,   -- 活动期平均DAU（除以天数）
           SUM(CASE WHEN is_act = 0 THEN dau ELSE 0 END) / NULLIF(SUM(1 - is_act), 0)  AS base_avg_dau,  -- 基线期平均DAU
           SUM(CASE WHEN is_act = 1 THEN pay_amount ELSE 0 END)
             / NULLIF(SUM(CASE WHEN is_act = 1 THEN dau ELSE 0 END), 0)                 AS act_arpu,      -- 活动期ARPU（SUM/SUM加权）
           SUM(CASE WHEN is_act = 0 THEN pay_amount ELSE 0 END)
             / NULLIF(SUM(CASE WHEN is_act = 0 THEN dau ELSE 0 END), 0)                 AS base_arpu,     -- 基线期ARPU
           (SUM(CASE WHEN is_act = 1 THEN dau ELSE 0 END)
              / NULLIF(SUM(CASE WHEN is_act = 0 THEN dau ELSE 0 END), 0) - 1) * 100     AS dau_lift_pct,  -- DAU提升率
           (SUM(CASE WHEN is_act = 1 THEN pay_amount ELSE 0 END)
              / NULLIF(SUM(CASE WHEN is_act = 0 THEN pay_amount ELSE 0 END), 0) - 1) * 100 AS pay_lift_pct -- 流水提升率
    FROM marked
)
SELECT ROUND(act_avg_dau, 0)   AS act_avg_dau,
       ROUND(base_avg_dau, 0)  AS base_avg_dau,
       ROUND(act_arpu, 4)      AS act_arpu,
       ROUND(base_arpu, 4)     AS base_arpu,
       ROUND(dau_lift_pct, 2)  AS dau_lift_pct,
       ROUND(pay_lift_pct, 2)  AS pay_lift_pct,
       ROUND((act_arpu / base_arpu - 1) * 100, 2)          AS arpu_lift_pct,   -- ARPU提升率（付费深度变化）
       ROUND(pay_lift_pct / NULLIF(dau_lift_pct, 0), 2)    AS elasticity       -- 弹性=流水增幅/DAU增幅（>1为深度拉动）
FROM core;
```

结果解读：若 DAU +22%、流水 +74%、ARPU +43%，弹性 3.4，说明活动同时拉升人数与付费深度、且主要增量来自付费深度（大额礼包），可评估常态化；若弹性 <1，则增量主要靠拉人，要复盘付费点设计。

解法二：分段独立聚合 + UNION 对比（附活动后回落观察）

```sql
WITH base AS (                              -- 基线期指标
    SELECT '01_基线期(5/18-5/31)' AS period,
           COUNT(*)                             AS days,
           ROUND(AVG(dau))                      AS avg_dau,
           ROUND(SUM(pay_amount) / SUM(dau), 4) AS arpu          -- 加权ARPU，不用AVG(日ARPU)
    FROM daily_overview
    WHERE stat_date BETWEEN '2024-05-18' AND '2024-05-31'
),
act AS (                                    -- 活动期指标
    SELECT '02_活动期(6/1-6/14)' AS period,
           COUNT(*)                             AS days,
           ROUND(AVG(dau))                      AS avg_dau,
           ROUND(SUM(pay_amount) / SUM(dau), 4) AS arpu
    FROM daily_overview
    WHERE stat_date BETWEEN '2024-06-01' AND '2024-06-14'
),
post AS (                                   -- 活动后7天回落观察
    SELECT '03_活动后7天(6/15-6/21)' AS period,
           COUNT(*)                             AS days,
           ROUND(AVG(dau))                      AS avg_dau,
           ROUND(SUM(pay_amount) / SUM(dau), 4) AS arpu
    FROM daily_overview
    WHERE stat_date BETWEEN '2024-06-15' AND '2024-06-21'
)
SELECT period, days, avg_dau, arpu FROM base
UNION ALL
SELECT period, days, avg_dau, arpu FROM act
UNION ALL
SELECT period, days, avg_dau, arpu FROM post;
```

结果解读：三段并排后可直接读出提升与回落——活动后 7 天 DAU 若回到基线的 95%、ARPU 回到基线的 110%，说明存在小幅透支但整体净增；跌破基线（<100%）则透支明显，需评估是否用回流活动托底。

### 5. 性能分析与优化

两解法都在日粒度汇总表（ADS 层）上运行，一年仅几百行，性能不是瓶颈——这本身就是要点：ADS 预聚合让经营查询变轻，明细计算下沉到数仓例行任务。若需从明细现算：login/orders 按 stat_date 分区裁剪后先聚合成日粒度再套用上述框架；多活动重叠时把日程表按日期展开成日历表（spine）再一对一 JOIN，避免一对多膨胀；弹性、ARPU 等派生指标可固化成 VIEW 供 BI 直接取数；节假日效应修正可维护节假日维表参与打标。

> Hive/Spark 差异：ADS 日汇总通常在 Hive 按天分区、MySQL 只承载结果；跨期对比直接按日期切片聚合即可，无需窗口；Spark SQL 中若要单 SQL 出三段对比，也可用 GROUP BY period + CASE 日期段实现，语义与 UNION 等价。

### 6. 面试延伸考点

- **【面试高频】流水提升率怎么拆解成"拉人"与"提付费"？** 回答要点：流水 = DAU × 付费率 × ARPPU，取对数后增幅可加，或做逐项替代分析（固定其他因子看单项贡献）；弹性只是总览，细拆要回到用户级明细按 新/老、付费/未付费 分层。
- **基线期选择有什么讲究？** 回答要点：等长、周期结构对齐（同样含两个周末）、不含其他活动；节日冲突时用去年同期或滚动中位数基线，并在报告注明基线区间与理由，这是结论可信度的前提。
- **【避坑指南】为什么 ARPU 用 SUM(pay)/SUM(dau) 而不是 AVG(日ARPU)？** 回答要点：各日 DAU 不同，日均 ARPU 的简单平均是等权，会放大低 DAU 日的权重；总量比才是按 DAU 加权的正确人均口径，两个口径在 DAU 波动大时可能差出几个百分点。
- **活动后回落幅度怎么定义？** 回答要点：活动后 7 天均值相对基线的偏差；跌破基线即透支，需结合回流活动与版本节奏补救；更精细的做法观察逐日回落曲线而非单一均值，区分"急跌"与"缓降"。

### 7. 业务拓展思考

弹性分析应沉淀为活动评估模板：每次大活动后自动输出"DAU/流水/ARPU 三率 + 回落曲线"，跨活动横向对比形成活动效果基准库，让"这个活动值不值得再做"有历史依据。运营联动：弹性高的活动类型（周年庆签到 + 限时卡池）排进大版本节点，弹性低但参与率高的活动定位为"留存型活动"考核留存而非收入；买量联动：活动期加投时用弹性预估增量 ROI，防止把自然波动算成买量效果。口径延展上，按新/老用户拆弹性——老用户 ARPU 弹性与新用户 DAU 弹性对应完全不同的活动模块（礼包设计 vs 拉新素材），混在一起只会得出模糊结论。
