## GAME-01 每日新增账号与设备数

### 1. 业务背景

市场部买量投放团队每天上午要核对前一天的买量效果：投放同学在抖音、快手等渠道充值投放后，需要数据同学用游戏自有的注册数据统计「每日新增账号数」与「新增设备数」两个指标，用来计算单个账号获取成本（CPA=渠道消耗/新增账号数），并判断渠道是否有刷量嫌疑——正常情况下账号数与设备数接近，若设备数远小于账号数，说明同一台设备在批量注册小号，渠道数据可能掺水。这是游戏公司数据分析师入职后接手的第一类日常取数需求，也是考察基础功的标准开场题。

### 2. 表结构说明

用户注册表 user_register（一行代表一个新注册账号）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID，注册成功即生成，全局唯一 |
| device_id | VARCHAR(64) | 设备唯一标识（安卓为OAID，iOS为IDFA） |
| channel | VARCHAR(32) | 注册来源渠道，如 tiktok（买量）、organic（自然量） |
| register_time | DATETIME | 注册完成时间 |

示例数据：

| user_id | device_id | channel | register_time |
| --- | --- | --- | --- |
| 100001 | dev_a1b2c3 | tiktok | 2026-10-20 09:12:35 |
| 100002 | dev_a1b2c3 | tiktok | 2026-10-20 09:15:02 |
| 100003 | dev_d4e5f6 | organic | 2026-10-20 11:40:18 |
| 100004 | dev_g7h8i9 | kuaishou | 2026-10-20 20:05:44 |
| 100005 | dev_j0k1l2 | tiktok | 2026-10-21 00:23:09 |

### 3. 解题思路

先定口径：新增账号数=注册表记录数（一行一个新账号，直接COUNT(*)）；新增设备数=当日出现过的device_id去重计数，注意「当日口径」只要求当天内去重，不做全生命周期去重（全周期去重需要设备首现表，属于进阶话题，可主动向面试官说明）。边界上：统计区间用「左闭右开」写法（大于等于当日0点且小于次日0点），避免BETWEEN在毫秒级数据上漏数或多数。实现路径：按DATE(register_time)分组，一条SELECT同时输出两个计数。易错点有三：一是COUNT(*)与COUNT(DISTINCT device_id)混用导致口径错误；二是对列套DATE()函数会让register_time上的索引失效；三是忘记按日期排序，输出顺序混乱不便看趋势。

### 4. 参考解法

写法一：单层聚合，按天分组直接计数（推荐，最直观）

```sql
SELECT
    DATE(register_time)          AS stat_date,   -- DATE() 提取日期部分，按天统计
    COUNT(*)                     AS new_users,   -- 注册表一行即一个新账号，直接计数
    COUNT(DISTINCT device_id)    AS new_devices  -- 当日 device_id 去重，得到新增设备数
FROM user_register
WHERE register_time >= '2026-10-20'              -- 左闭：从当日 0 点起
  AND register_time <  '2026-10-22'              -- 右开：到第三日 0 点前，避免毫秒遗漏
GROUP BY DATE(register_time)                     -- 按注册日期分组
ORDER BY stat_date;                              -- 日期升序，方便观察趋势
```

结果解读：示例数据中2026-10-20新增账号4、新增设备3，说明有1台设备注册了2个账号，比例健康；若某日设备数只有账号数的一半，就要警惕渠道刷量并联动反作弊核查。

写法二：先按「天+设备」聚合，再汇总（先聚后总的两层思路）

```sql
SELECT
    t.stat_date,                        -- 统计日期（来自内层派生表）
    SUM(t.dev_user_cnt) AS new_users,   -- 各设备账号数求和 = 新增账号总数
    COUNT(*)            AS new_devices  -- 内层每行是一个去重设备，直接计数
FROM (
    SELECT
        DATE(register_time) AS stat_date,   -- 按天截断注册时间
        device_id,                          -- 设备维度
        COUNT(*)            AS dev_user_cnt -- 该设备当天注册的账号数
    FROM user_register
    WHERE register_time >= '2026-10-20'
      AND register_time <  '2026-10-22'
    GROUP BY DATE(register_time), device_id -- 先按「天+设备」聚合去重
) t
GROUP BY t.stat_date
ORDER BY t.stat_date;
```

结果解读：两种写法结果完全一致；写法二虽然多绕一层，但内层结果可以直接复用——比如追问「单设备最多注册几个账号」时只需在内层加ORDER BY，面试中体现思路灵活性。

### 5. 性能分析与优化

两种写法都要扫描统计区间的注册数据：写法一一次扫描加一次分组；写法二多一次中间结果物化（派生表），在百万行以上数据量时明显更慢，优先写法一。优化建议：（1）在register_time上建普通索引，配合本例的范围条件写法可走索引；MySQL 8.0.13起也支持对DATE(register_time)建函数索引；（2）报表每日固定产出，可建「天+渠道」粒度日汇总表，定时任务增量写入，查询直接打汇总表；（3）channel与register_time建联合索引，可同时服务按渠道筛选的场景。

> Hive/Spark SQL 差异：注册流水入仓后通常按天分区，应写 WHERE dt='2026-10-20' 利用分区裁剪；COUNT DISTINCT 语法兼容，但超大规模去重建议先 GROUP BY 去重再计数，避免单 Reducer 瓶颈；Spark SQL 可用 approx_count_distinct 以精度换性能。

### 6. 面试延伸考点

**【面试高频】为什么设备数会远小于账号数？** 回答要点：一机多号（玩家养小号）、模拟器批量注册、渠道刷量三类原因，需结合单设备注册账号数的分布进一步定位，而不是只看总量比值。

**【面试高频】COUNT(*)、COUNT(1)、COUNT(列)、COUNT(DISTINCT 列)有什么区别？** 回答要点：前两者等价统计行数；COUNT(列)不统计NULL；COUNT(DISTINCT 列)先去重再计数，代价最高。

**【加分点】如何统计全周期去重的新增设备？** 回答要点：需要设备维度的首现口径——按device_id取MIN(register_time)归属到首现日，或维护设备首现表，再按首现日聚合。

### 7. 业务拓展思考

这组指标是渠道ROI分析的地基：新增账号配合渠道消耗可算CPA，再接次留、7留可算LTV与回收周期，直接决定投放预算在渠道间的分配。设备数/账号数比值异常可作为反作弊监控的告警规则，联动市场部门暂停可疑渠道投放；口径上还能继续拆到「渠道×素材」粒度，帮助投放同学定位跑量的素材方向。

## GAME-02 DAU按天与按服统计

### 1. 业务背景

DAU（日活跃用户数）是游戏数据日报的第一个数字。制作人、发行负责人每天早上的数据例会要两条信息：全项目DAU趋势（判断版本、活动对大盘的影响），以及分服DAU（运营同学据此判断哪些服务器进入衰退期需要合服、哪些新服首日流量超预期需要扩容）。登录日志是游戏数据量最大的流水表之一，一天几千万行很常见，分析师既要写对去重口径，也要有分区与性能意识，这道题同时考察「业务口径+工程意识」两个维度。

### 2. 表结构说明

登录日志表 login（每次登录记一行流水，一天数千万行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 玩家ID |
| server_id | VARCHAR(16) | 服务器编号，如 S101 |
| login_time | DATETIME | 登录时间 |
| platform | VARCHAR(10) | 平台：ios / android / pc |

示例数据：

| log_id | user_id | server_id | login_time | platform |
| --- | --- | --- | --- | --- |
| 20261020001 | 100001 | S101 | 2026-10-20 08:02:11 | ios |
| 20261020002 | 100001 | S101 | 2026-10-20 12:30:45 | ios |
| 20261020003 | 100002 | S101 | 2026-10-20 09:15:00 | android |
| 20261020004 | 100003 | S102 | 2026-10-20 21:44:37 | android |
| 20261020005 | 100001 | S101 | 2026-10-21 07:58:03 | ios |

### 3. 解题思路

口径先行：DAU=当日去重登录用户数，即COUNT(DISTINCT user_id)；同一玩家一天登录多次只算1个（示例中100001登录两次），这是与「登录人次」最容易混淆的地方。边界：活跃通常按自然日切分，手游行业常用凌晨4点切日（防熬夜跨天玩家被低估），面试时主动说明口径会加分。实现路径：先写按天全项目DAU，再扩展为GROUP BY日期+服得到分服DAU，并可用WITH ROLLUP输出小计。易错点：用COUNT(*)当DAU（那统计的是登录人次）；分服DAU直接相加不一定等于全项目DAU（跨服玩家会被重复计数），要主动点出这一口径差异，这是重要的加分意识。

### 4. 参考解法

写法一：全项目按天DAU

```sql
SELECT
    DATE(login_time)        AS stat_date,  -- 登录日期
    COUNT(DISTINCT user_id) AS dau         -- 当日去重用户数，即DAU
FROM login
WHERE login_time >= '2026-10-20'           -- 区间左闭右开，可走索引
  AND login_time <  '2026-10-22'           -- 统计两天
GROUP BY DATE(login_time)                  -- 按登录日期分组
ORDER BY stat_date;                        -- 日期升序输出
```

结果解读：示例数据10-20当天登录流水有4条但去重后只有100001、100002、100003三人，DAU=3，这正是「人次不等于人数」的直观体现，也是本题的第一个采分点。

写法二：按天+按服统计，并用 WITH ROLLUP 输出小计

```sql
SELECT
    IFNULL(DATE(login_time), '总计')      AS stat_date, -- ROLLUP 汇总行日期为 NULL，翻译成“总计”
    IFNULL(server_id, '全部服务器')       AS server_id, -- 服维度的小计行
    COUNT(DISTINCT user_id)               AS dau        -- 该天该服的去重活跃人数
FROM login
WHERE login_time >= '2026-10-20'
  AND login_time <  '2026-10-22'
GROUP BY DATE(login_time), server_id WITH ROLLUP    -- 按天、按服分组，并附加各级汇总行
ORDER BY stat_date, server_id;                      -- 按日期与服排序，汇总行自然归位
```

结果解读：ROLLUP在每个日期下追加一行「全部服务器」小计、最后追加全表总计，一张表同时给出明细与汇总；注意小计是「该天各服去重人数直接相加」，若玩家跨服登录会略高于全项目真实DAU，汇报时需注明口径。

> Hive/Spark SQL 差异：Hive 不支持 WITH ROLLUP，可改写为 GROUP BY dt, server_id GROUPING SETS ((dt), (dt, server_id))；生产登录日志按 dt 分区，查询必须带分区条件；超大规模下 COUNT DISTINCT 效率低，可先按用户 GROUP BY 去重再聚合计数。

### 5. 性能分析与优化

写法一扫描两天分区的全部流水做一次去重聚合；写法二额外做ROLLUP排序，代价略高但仍在一次扫描内完成。优化建议：（1）MySQL线上库对login_time建索引，或数仓按天分区裁剪；（2）COUNT(DISTINCT user_id)需要维护去重集合，内存开销随当日活跃用户数增长，超大表可先按user_id去重落临时表再计数，或用Spark的approx_count_distinct近似计数；（3）日报场景应预聚合出「天+服」粒度的汇总表，DAU查询变成对汇总表的单表扫描，毫秒级返回；（4）若要精确的全项目DAU，应在账号（user_id）粒度全量去重，而不是分服结果简单相加。

### 6. 面试延伸考点

**【面试高频】为什么分服DAU加总会大于全项目DAU？** 回答要点：玩家可在多服创建角色并登录，跨服登录造成重复计数；全项目口径应按user_id全量去重，分服数据只用于定位问题。

**【面试高频】DAU突然下跌10%，你怎么排查？** 回答要点：先分渠道/分服/分平台/分版本下钻定位跌幅来源，再排查技术因素（登录服务异常、埋点丢失）、运营因素（活动结束、假期结束）、外因（竞品大版本、渠道政策），按「先定位再归因」的顺序作答。

**【加分点】游戏行业为什么常用凌晨4点作为自然日切点？** 回答要点：重度玩家熬夜至凌晨，按0点切日会把跨夜会话拆到两天、低估其活跃与黏性，4点切日更贴近玩家体感，是行业惯例口径。

### 7. 业务拓展思考

DAU是绝大多数游戏指标的分母：付费率=付费人数/DAU，留存以新增日为基准计算。分服DAU长期下行触发合服评估，合服前后的DAU变化又反过来衡量合服收益；DAU减新增可推老用户活跃规模，结合版本节点观察大盘弹性，是发行排期与买量节奏判断的基础数据，值得在面试中主动展开。

## GAME-03 各渠道注册量与占比

### 1. 业务背景

买量市场部每月做渠道复盘：市场负责人要对比抖音、快手、B站等渠道给游戏带来的注册量与占比，决定下月预算向哪些渠道倾斜。分析师从注册表按渠道聚合，输出渠道排序列表；运营同学同时关心「自然量占比」——自然量健康说明产品口碑与商店推荐位有效，买量依赖度过高则获客成本容易随投放规模上涨。这道题看似只是最基础的GROUP BY加ORDER BY，但面试官往往会追加「再加一列占比」「把渠道归成自然量/买量两大类」，考察你能否一次把口径写全。

### 2. 表结构说明

用户注册表 user_register（与GAME-01同源，完整独立呈现）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID，注册即生成 |
| device_id | VARCHAR(64) | 设备唯一标识 |
| channel | VARCHAR(32) | 注册渠道：tiktok / kuaishou / bili / organic（自然量） |
| register_time | DATETIME | 注册时间 |

示例数据：

| user_id | device_id | channel | register_time |
| --- | --- | --- | --- |
| 100001 | dev_a1b2c3 | tiktok | 2026-10-20 09:12:35 |
| 100002 | dev_d4e5f6 | bili | 2026-10-20 11:40:18 |
| 100003 | dev_g7h8i9 | kuaishou | 2026-10-20 20:05:44 |
| 100004 | dev_j0k1l2 | organic | 2026-10-20 22:18:51 |
| 100005 | dev_m3n4o5 | tiktok | 2026-10-21 00:23:09 |

### 3. 解题思路

口径：注册量=COUNT(*)（注册表一行一个账号）；占比=该渠道注册量/统计周期总注册量，总数可用窗口COUNT(*) OVER()在聚合结果上直接取得，避免再写子查询扫一次表。实现路径分两步：第一步GROUP BY渠道聚合并按注册量降序输出排行；第二步扩展为「自然量/买量」大类归组（CASE WHEN channel='organic' THEN '自然量' ELSE '买量' END）并同步输出占比。易错点：占比计算建议统一乘1.0或100.0——MySQL的/运算会返回小数，但Hive与部分数据库整数相除会截断，写明倍率更稳；大类归组的CASE WHEN必须用ELSE兜底，否则未知渠道值会落入NULL被遗漏；GROUP BY里的表达式必须与SELECT里的完全一致，否则ONLY_FULL_GROUP_BY模式下直接报错。

### 4. 参考解法

写法一：渠道明细排行+同行占比（窗口写法，推荐）

```sql
SELECT
    channel,                     -- 渠道名
    COUNT(*)          AS reg_cnt,-- 该渠道注册账号数
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS reg_pct
                                 -- 窗口 COUNT(*) OVER() 取统计周期总数，在同行算出占比
FROM user_register
WHERE register_time >= '2026-10-01'
  AND register_time <  '2026-11-01'      -- 统计整个10月
GROUP BY channel                         -- 按渠道分组
ORDER BY reg_cnt DESC;                   -- 注册量降序排行
```

结果解读：一条SQL直接给出「哪个渠道量最大」的排序与占比，示例数据中tiktok 2单占40%；若头部渠道占比超过六成，说明大盘高度依赖单一买量渠道，预算风险集中。

写法二：自然量/买量大类归组（口径升级版）

```sql
SELECT
    CASE WHEN channel = 'organic' THEN '自然量' ELSE '买量' END AS channel_type,
                                            -- 把渠道二分为自然量与买量两大类
    COUNT(*)                              AS reg_cnt,      -- 大类注册量
    ROUND(COUNT(*) * 100.0 / (SELECT COUNT(*)
                              FROM user_register
                              WHERE register_time >= '2026-10-01'
                                AND register_time <  '2026-11-01'), 1) AS reg_pct
                                          -- 用标量子查询取总数算占比（对比写法一的窗口写法）
FROM user_register
WHERE register_time >= '2026-10-01'
  AND register_time <  '2026-11-01'
GROUP BY CASE WHEN channel = 'organic' THEN '自然量' ELSE '买量' END
                                          -- ONLY_FULL_GROUP_BY 下 GROUP BY 表达式须与 SELECT 一致
ORDER BY reg_cnt DESC;
```

结果解读：大类视角下若买量占八成以上，说明产品自然增长乏力，市场策略要从「买量冲量」转向「提升自然量」（品牌广告、ASO、口碑运营），这是管理层视角的结论。

### 5. 性能分析与优化

两种写法均为单表一次扫描加聚合，百万行内无压力。写法一的窗口总数在聚合结果上直接计算，通常比写法二的标量子查询少一次独立扫描（优化器不一定总能消除子查询），推荐窗口写法。优化建议：（1）对(channel, register_time)或(register_time, channel)建联合索引，按月统计可走索引范围扫描；（2）渠道取值有限，适合沉淀渠道日汇总表供报表直接读取；（3）若表带账号状态字段（测试号、封禁号标记），务必在WHERE中过滤——这属于比SQL调优更重要的「数据正确性优化」，主动提出是加分项。

### 6. 面试延伸考点

**【面试高频】占比计算有哪几种写法，各有什么优劣？** 回答要点：窗口SUM(COUNT(*)) OVER()一次扫描最优；标量子查询可读性好但可能多扫一次；也可先CTE算总数再JOIN，Hive低版本无窗口函数时用交叉JOIN兜底。

**【加分点】渠道注册数据如何与投放消耗联动？** 回答要点：按渠道+日期JOIN渠道消耗表得CPA/CAC，再接留存表算LTV，形成「消耗-注册-留存-回收」完整漏斗，回答时给出漏斗链条即可。

**【避坑指南】GROUP BY的表达式与SELECT里的CASE WHEN不一致会怎样？** 回答要点：在ONLY_FULL_GROUP_BY模式下直接报错1064/3064类错误，两处表达式必须逐字一致，或先在派生表里算好标签再分组。

### 7. 业务拓展思考

渠道注册分布是发行策略的仪表盘：自然量占比下滑往往早于大盘下滑出现，可作为预警指标；进一步做「渠道×新增7留」的二维评估，低质量渠道即使量大也应削减预算。口径上可延展出「有效注册」（完成新手引导或达到X级才计入），过滤羊毛党注册，让渠道之间的对比更公平，这也是面试中展示口径意识的好素材。

## GAME-04 付费订单金额区间分布

### 1. 业务背景

商业化团队（商业分析师+主策划）每月分析玩家付费结构：本月成功充值订单集中在哪些金额档位？6元、30元、98元、328元、648元是手游常见定价档（对应首充礼包、月卡、战令、皮肤礼包、大额礼包）。小额订单占比高说明付费门槛低、覆盖面广；流水集中在大额档说明营收靠少数大R玩家支撑，风险集中。这份分布直接指导定价策略（是否抬首充档位、是否新增中间档礼包）与礼包上架节奏，是CASE WHEN分档统计的标准面试题。

### 2. 表结构说明

充值订单表 orders（支付成功才产生有效流水）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | VARCHAR(32) | 订单号，全局唯一 |
| user_id | BIGINT | 玩家ID |
| product_name | VARCHAR(64) | 商品名，如 首充礼包 |
| amount | DECIMAL(10,2) | 实付金额（元） |
| pay_status | VARCHAR(16) | 订单状态：SUCCESS成功 / PENDING待支付 / REFUND已退款 |
| pay_time | DATETIME | 支付完成时间 |

示例数据：

| order_id | user_id | product_name | amount | pay_status | pay_time |
| --- | --- | --- | --- | --- | --- |
| R20261020001 | 100001 | 首充礼包 | 6.00 | SUCCESS | 2026-10-20 09:20:11 |
| R20261020002 | 100002 | 月卡 | 30.00 | SUCCESS | 2026-10-20 12:05:40 |
| R20261020003 | 100003 | 大额礼包 | 648.00 | PENDING | 2026-10-20 13:44:02 |
| R20261020004 | 100004 | 战令 | 98.00 | SUCCESS | 2026-10-20 18:22:33 |
| R20261020005 | 100001 | 节日礼包 | 328.00 | REFUND | 2026-10-21 10:11:09 |

### 3. 解题思路

口径与边界第一步：只统计pay_status='SUCCESS'的订单，PENDING未支付、REFUND已退款都不能算流水（退款是否要从营收口径中扣减，需与需求方确认，本例按「成功支付口径」不含退款单，面试要主动说明）。第二步用CASE WHEN把amount切成五个档位：6元以下、6-30元、30-98元、98-328元、328元及以上，边界值归属要明确（本例用「低于下一档下限」的写法，保证区间不重不漏）。实现路径：解法一在GROUP BY中直接复用CASE WHEN表达式一气呵成；解法二先用派生表把档位标签算好，外层再分组并加占比。易错点：CASE WHEN忘写ELSE导致NULL档位行悄悄消失；各分支条件重叠导致重复计数；把订单数当人数（人数要COUNT(DISTINCT user_id)）。

### 4. 参考解法

写法一：CASE WHEN 直接分组（一气呵成版）

```sql
SELECT
    CASE
        WHEN amount <  6   THEN '01_6元以下'      -- 档位名加01_/02_前缀，让字典序等于业务顺序
        WHEN amount <  30  THEN '02_6-30元'       -- CASE 从上到下命中即返回，天然互斥
        WHEN amount <  98  THEN '03_30-98元'
        WHEN amount <  328 THEN '04_98-328元'
        ELSE '05_328元及以上'                     -- ELSE 兜底，避免出现 NULL 档
    END                        AS amount_range,  -- 金额档位标签
    COUNT(*)                   AS order_cnt,     -- 订单数
    SUM(amount)                AS amount_sum     -- 该档位流水金额
FROM orders
WHERE pay_status = 'SUCCESS'                     -- 只统计支付成功订单
  AND pay_time >= '2026-10-01'
  AND pay_time <  '2026-11-01'                   -- 10月区间，左闭右开
GROUP BY CASE
        WHEN amount <  6   THEN '01_6元以下'
        WHEN amount <  30  THEN '02_6-30元'
        WHEN amount <  98  THEN '03_30-98元'
        WHEN amount <  328 THEN '04_98-328元'
        ELSE '05_328元及以上'
    END                                          -- ONLY_FULL_GROUP_BY 下须与 SELECT 表达式一致
ORDER BY amount_range;                           -- 前缀命名保证输出顺序即档位顺序
```

结果解读：示例数据中成功订单落在6元、30元、98元三个档位，648元单为待支付、328元单为退款，均不计入；真实大盘若「05_328元及以上」订单数占比不足5%但流水占比超60%，就是典型的大R依赖型营收结构。

写法二：派生表先打标签，再聚合出订单数、金额与占比

```sql
SELECT
    t.amount_range,                        -- 档位标签
    COUNT(*)      AS order_cnt,            -- 订单数
    SUM(t.amount) AS amount_sum,           -- 流水金额
    ROUND(SUM(t.amount) * 100.0 / SUM(SUM(t.amount)) OVER (), 1) AS amount_pct
                                           -- 该档位流水占全部流水的百分比（窗口取总额）
FROM (
    SELECT
        amount,                            -- 金额透传给外层聚合
        CASE
            WHEN amount <  6   THEN '01_6元以下'
            WHEN amount <  30  THEN '02_6-30元'
            WHEN amount <  98  THEN '03_30-98元'
            WHEN amount <  328 THEN '04_98-328元'
            ELSE '05_328元及以上'
        END AS amount_range                -- 内层只负责打档位标签
    FROM orders
    WHERE pay_status = 'SUCCESS'
      AND pay_time >= '2026-10-01'
      AND pay_time <  '2026-11-01'
) t
GROUP BY t.amount_range                   -- 标签已物化，直接按列分组
ORDER BY t.amount_range;
```

结果解读：内层打标签、外层聚合的结构可读性更好，档位逻辑只写一遍不易改漏，外层还能继续叠加占比、与目标档位维表JOIN等扩展，是数据工程师更推荐的写法。

### 5. 性能分析与优化

两种写法都只扫一遍成功订单数据，差异在代码结构而非执行计划：写法一的CASE要写两遍，存在「分组与显示口径改漏一处」的低级风险（面试会扣分），写法二结构更稳。优化建议：（1）对(pay_status, pay_time)或(pay_time)建索引，订单表极大且常按月统计时按月分区收益明显；（2）档位边界若频繁调整（策划调价），把边界维护成档位配置维表用JOIN代替硬编码CASE，改口径不改代码；（3）金额求和在数仓用DECIMAL计算，避免浮点误差；（4）需要「人数」口径时改用COUNT(DISTINCT user_id)，同一玩家多单归并，避免用订单数冒充人数。

### 6. 面试延伸考点

**【面试高频】退款订单应该怎么处理？** 回答要点：先确认口径——分析「支付行为」可含退款、分析「营收」要剔除甚至记负向流水；iOS渠道退款有滞后性，还要说明T+N的统计时点口径，体现口径意识。

**【面试高频】CASE WHEN不写ELSE会怎样？** 回答要点：不满足任何条件返回NULL，GROUP BY时NULL单独成组或被下游过滤，造成档位遗漏，必须ELSE兜底或显式处理NULL组。

**【加分点】如何同时输出订单数分布与人数分布？** 回答要点：同一SELECT里并列COUNT(*)（订单数）与COUNT(DISTINCT user_id)（人数），并解释两者差异来自同一玩家多笔订单，比值即人均订单数。

### 7. 业务拓展思考

金额档位分布是商业化健康度的体检表：小额档订单多但流水贡献低，可尝试「小额升档」（如6元首充礼包升级为12元双倍返利）提升客单；大R集中度可用帕累托分析量化（前1%玩家流水占比），超过80%就要设计大R留存专项（VIP客服、专属礼包、线下活动）。口径延展：按「角色等级×档位」交叉分析能发现低等级大额充值订单，这是代充与黑产的重要信号，可联动风控。

## GAME-05 各关卡通过人数与通过率

### 1. 业务背景

关卡策划每次上新版本后都要用数据验证关卡难度曲线是否合理：若第5关通过率骤降到30%以下，玩家会在新手期大量卡关流失，需要下调怪物数值；若通过率接近100%，说明关卡缺乏挑战，复活道具等付费点卖不动。分析师从关卡行为流水统计每个关卡的「挑战人数」（发起挑战的去重人数）与「通过人数」，算出通过率输出给策划调整难度。通过率是PVE游戏最核心的漏斗指标之一，本题考察条件聚合、比率计算与除零保护三个基本功。

### 2. 表结构说明

关卡行为表 level_events（玩家每发起或通过一次关卡记一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 玩家ID |
| level_id | INT | 关卡编号，1表示第1关 |
| event_type | VARCHAR(10) | 行为类型：START发起挑战 / PASS通关 |
| event_time | DATETIME | 事件时间 |

示例数据：

| log_id | user_id | level_id | event_type | event_time |
| --- | --- | --- | --- | --- |
| 1 | 100001 | 1 | START | 2026-10-20 09:00:00 |
| 2 | 100001 | 1 | PASS | 2026-10-20 09:01:32 |
| 3 | 100002 | 1 | START | 2026-10-20 09:05:10 |
| 4 | 100002 | 2 | START | 2026-10-20 09:10:00 |
| 5 | 100003 | 1 | START | 2026-10-20 09:12:40 |

### 3. 解题思路

口径界定是本题灵魂：同一玩家同一关可能反复挑战（失败重打），所以「通过人数」必须按user_id去重，直接数PASS行得到的是通过人次，会虚高；通过率=去重通过人数/去重挑战人数。此外PASS行的user_id理论上必先有START（脏数据除外），分母为零的关卡（无人挑战的新关）要做除零保护。实现路径：解法一单表条件聚合，用COUNT(DISTINCT CASE WHEN ...)把两类人数一行算出；解法二把START与PASS分别聚合成两张子查询结果再JOIN，结构更直白。易错点：JOIN后重复行放大计数；分母为零除法报错；忘记按关卡编号排序导致「难度曲线」看不出顺序。

### 4. 参考解法

写法一：单表条件聚合（推荐）

```sql
SELECT
    level_id,                                            -- 关卡编号
    COUNT(DISTINCT CASE WHEN event_type = 'START'
                        THEN user_id END) AS start_users,-- 发起挑战的去重人数（分母）
    COUNT(DISTINCT CASE WHEN event_type = 'PASS'
                        THEN user_id END) AS pass_users, -- 通关的去重人数（分子）
    ROUND(
        COUNT(DISTINCT CASE WHEN event_type = 'PASS' THEN user_id END) * 100.0
        / NULLIF(COUNT(DISTINCT CASE WHEN event_type = 'START' THEN user_id END), 0)
    , 1) AS pass_rate_pct                                -- 通过率(%)，NULLIF 将 0 分母转为 NULL 防除零
FROM level_events
WHERE event_time >= '2026-10-20'
  AND event_time <  '2026-10-27'                         -- 统计一周数据
GROUP BY level_id
ORDER BY level_id;                                       -- 按关卡顺序输出难度曲线
```

结果解读：示例数据第1关3人挑战、1人通关（100002与100003只START未PASS），通过率33.3%；第1关作为新手首关应接近100%，33.3%意味着新手开门杀，需策划立即复核数值。

写法二：两次聚合再JOIN（子查询拼接版）

```sql
SELECT
    s.level_id,                                  -- 关卡编号（以发起表为基准保留全部关卡）
    s.start_users,                               -- 挑战人数
    IFNULL(p.pass_users, 0)     AS pass_users,   -- 无通关记录的关卡补0
    ROUND(IFNULL(p.pass_users, 0) * 100.0 / s.start_users, 1) AS pass_rate_pct
                                                 -- 通过率(%)：分母来自发起表，不为0
FROM (
    SELECT level_id,
           COUNT(DISTINCT user_id) AS start_users -- 各关卡发起挑战人数
    FROM level_events
    WHERE event_type = 'START'
      AND event_time >= '2026-10-20'
      AND event_time <  '2026-10-27'
    GROUP BY level_id
) s
LEFT JOIN (                                      -- 左连接保证零通关关卡不丢行
    SELECT level_id,
           COUNT(DISTINCT user_id) AS pass_users  -- 各关卡通关人数
    FROM level_events
    WHERE event_type = 'PASS'
      AND event_time >= '2026-10-20'
      AND event_time <  '2026-10-27'
    GROUP BY level_id
) p ON s.level_id = p.level_id                   -- 以关卡编号对齐
ORDER BY s.level_id;
```

结果解读：LEFT JOIN写法天然保留「有人挑战但无人通关」的关卡（pass_users补0）；若误用INNER JOIN，这些关卡整行消失——恰好掩盖最严重的卡关点，这是本题最经典的追问。

### 5. 性能分析与优化

写法一只扫描一遍事件表；写法二扫两遍并做JOIN，代价约两倍，事件表上亿行时差距明显，推荐写法一。优化建议：（1）建(event_time, level_id, event_type)联合索引或按天分区，减少扫描量；（2）只关心新手期时加level_id<=10的WHERE条件做谓词下推；（3）更工程化的做法是数仓维护关卡粒度日汇总表（level_id, start_users, pass_users），报表直接读汇总；（4）除零保护除NULLIF外，也可在WHERE中过滤无挑战的关卡，但会丢失「零通关」信息，需按业务目的取舍。

> Hive/Spark SQL 差异：COUNT(DISTINCT CASE WHEN ...) 在 Hive 可用但多组去重并行度差，大表建议先 GROUP BY level_id, event_type 聚合，再在汇总层做条件展开，两阶段聚合性能更佳。

### 6. 面试延伸考点

**【面试高频】通过率的分子分母还可以有哪些口径？** 回答要点：人次口径（不去重，反映重复挑战强度）、首通率（每玩家只算第一次通过，按user_id+level_id取MIN(event_time)）、当日通过率与观察期截止通过率（截止时仍卡关的记为未通过），口径不同结论不同。

**【面试高频】为什么写法二要用LEFT JOIN而不是INNER JOIN？** 回答要点：以挑战为基准保留全部关卡；INNER JOIN会把零通关关卡整行丢弃，恰好掩盖最严重的卡关问题。

**【加分点】如何定位「卡关后流失」的玩家？** 回答要点：关卡事件与登录流水按user_id关联，找出「连续N次挑战未通过且之后再未登录」的群体，量化卡关流失对次留的贡献。

### 7. 业务拓展思考

通过率曲线是难度数值化调优的依据：策划按目标通过率反推怪物血量与伤害数值，分析师持续监控版本更新后的曲线漂移。可进一步联动付费：卡关点的复活道具、养成材料销量应同步上升，若关卡卡住但付费未涨，说明付费点设计错位。口径延展：通过率可拆到「玩家等级段/付费段」，对比付费玩家与免费玩家的难度体验差异，为动态难度调节（DDA）的立项提供数据论证。

## GAME-06 道具销量排行榜

### 1. 业务背景

商城运营每周复盘道具销售情况：需要一份「销量TOP10道具榜单」（按销售件数），同时关注销售额，用来决定下周商城推荐位排序与限购调整——卖得动的道具给曝光，滞销道具考虑打折或下架。主策划同时关心道具收入结构：低价高频道具（体力、复活币）与高价低频道具（皮肤、宝箱）的比例是否健康。这道题是最基础的聚合排序题，但面试官通常会追问「并列销量怎么办」「销量和销售额哪个口径先看」，考察ORDER BY LIMIT与窗口排名函数的差异，以及多口径并行的意识。

道具购买流水表 item_orders（商城每次成交记一行）：

| unit_price | DECIMAL(8,2) | 道具单价（元） |

示例数据：

| I2026102001 | 100001 | 301 | 体力药水 | 2 | 1.00 | 2026-10-20 09:15:00 |
| I2026102002 | 100002 | 302 | 复活币 | 1 | 6.00 | 2026-10-20 10:02:33 |
| I2026102003 | 100001 | 301 | 体力药水 | 5 | 1.00 | 2026-10-20 21:40:12 |

| I2026102005 | 100004 | 302 | 复活币 | 3 | 6.00 | 2026-10-21 20:30:08 |

### 3. 解题思路

口径：销量=SUM(quantity)（注意不是COUNT(*)，一次购买可能含多件）；销售额=SUM(quantity*unit_price)（先乘后加，不是件数与单价各自求和）；统计周期按需求限定为自然周或自然月。实现路径：按道具分组聚合，ORDER BY销量降序，LIMIT取TOP10；解法二在聚合结果上用ROW_NUMBER()窗口给出严格名次列，再在外层过滤名次。易错点：把COUNT(*)当销量（那是订单数）；销售额公式写成SUM(quantity)+unit_price之类的低级错误；并列销量时LIMIT 10的截断顺序不确定，可能随机丢掉并列道具，而RANK/DENSE_RANK能显式处理并列名次——这是本题最高频的追问点。

### 4. 参考解法

写法一：聚合+排序+LIMIT（最常用）

```sql
SELECT
    item_id,                                  -- 道具ID
    item_name,                                -- 道具名
    SUM(quantity)              AS sales_qty,  -- 销量 = 件数求和（不是订单行数）
    SUM(quantity * unit_price) AS gmv,        -- 销售额 = 件数×单价后求和
    COUNT(*)                   AS order_cnt   -- 订单数（与销量口径区分并列输出）
FROM item_orders
WHERE buy_time >= '2026-10-20'
  AND buy_time <  '2026-10-27'                -- 自然周区间
GROUP BY item_id, item_name                  -- 按道具分组，名称随ID保证一一对应
ORDER BY sales_qty DESC                      -- 按销量降序
LIMIT 10;                                    -- 取TOP10
```

结果解读：示例数据中体力药水2笔订单共7件排第一，体现低价高频道具撑销量；GMV列同时提醒「销量王」未必是「收入王」——皮肤宝箱1件就是98元，运营决策时两个榜单都要看。

写法二：窗口函数输出严格名次

```sql
SELECT
    t.rk,                 -- 名次
    t.item_id,            -- 道具ID
    t.item_name,          -- 道具名
    t.sales_qty,          -- 销量
    t.gmv                 -- 销售额
FROM (
    SELECT
        item_id,
        item_name,
        SUM(quantity)              AS sales_qty,               -- 销量
        SUM(quantity * unit_price) AS gmv,                     -- 销售额
        ROW_NUMBER() OVER (ORDER BY SUM(quantity) DESC) AS rk  -- 对聚合结果按销量降序编号
    FROM item_orders
    WHERE buy_time >= '2026-10-20'
      AND buy_time <  '2026-10-27'
    GROUP BY item_id, item_name
) t
WHERE t.rk <= 10;     -- 窗口函数不能写在 WHERE 里，必须先包派生表再过滤名次
```

结果解读：ROW_NUMBER给出连续唯一名次；若业务要求「同销量同名次」，把ROW_NUMBER换成RANK（并列跳号：1,1,3）或DENSE_RANK（并列不跳号：1,1,2），三者区别是窗口函数面试的经典考点。

### 5. 性能分析与优化

两种写法都要全量聚合后再排序，但道具数量级（几百到几千）很小，TOP-N排序本身代价可忽略，瓶颈在流水表扫描。优化建议：（1）buy_time建索引或按天分区，缩小扫描范围；（2）GROUP BY item_id, item_name时排序宽度受名称字段影响，若只需ID可内层按item_id分组、外层再关联名称维表；（3）数仓沉淀日汇总表（天×道具：销量、GMV），周榜变成对7天汇总表再聚合，快且结果稳定；（4）MySQL线上库跑大表时只取聚合列，避免SELECT *带来的回表开销。

### 6. 面试延伸考点

**【面试高频】ROW_NUMBER、RANK、DENSE_RANK的区别？** 回答要点：ROW_NUMBER恒唯一连续；RANK并列同名次且跳号（1,1,3）；DENSE_RANK并列不跳号（1,1,2）；按业务是否允许并列、榜单是否严格N行来选择。

**【面试高频】窗口函数为什么不能直接写在WHERE里？** 回答要点：SQL逻辑执行顺序中WHERE先于SELECT的窗口计算，窗口结果还不存在，必须包一层派生表或CTE再过滤。

**【加分点】销量榜会不会被工作室刷量污染？** 回答要点：结合去重购买人数、单用户购买频次分布识别异常（如某道具九成订单来自同一批账号），必要时按「去重购买人数」另出一版榜单交叉验证。

### 7. 业务拓展思考

销量榜直接驱动商城推荐位与限购策略：高频低价道具考验转化率运营，高价低频道具考验付费深度设计。榜单结合「去重购买人数」可算人均购买件数，识别「少数人囤货」型道具，为背包清理与道具回收玩法提供依据。口径延展：区分「付费货币购买」与「游戏内货币购买」两个口径，只有前者构成真实营收；活动期榜单要标注活动加成背景，避免把运营资源误判为自然需求。

## GAME-07 在线峰值按时段统计

### 1. 业务背景

运维与运营共同关注服务器在线人数曲线：运维根据「每小时在线峰值」安排开新服时间、评估扩容与合服时机；运营用时段曲线决定开服时刻（晚8点是登录高峰，新服常选18:00开启承接流量）、维护窗口与限时活动开启点。在线人数数据来自服务端定时快照（如每5分钟采集一次全服在线数），分析师要按小时取最大值输出「时段峰值表」。本题考察HOUR函数分组与MAX聚合，更考察「先加总还是先取最大」的口径理解，是入门题里最容易暴露思维漏洞的一道。

### 2. 表结构说明

在线人数快照表 online_snapshot（每5分钟每个服一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| snapshot_id | BIGINT | 快照自增ID |
| server_id | VARCHAR(16) | 服务器编号 |
| snapshot_time | DATETIME | 快照采集时间 |
| online_cnt | INT | 该时刻该服在线人数 |

示例数据：

| snapshot_id | server_id | snapshot_time | online_cnt |
| --- | --- | --- | --- |
| 1 | S101 | 2026-10-20 12:00:00 | 8200 |
| 2 | S101 | 2026-10-20 12:05:00 | 8450 |
| 3 | S101 | 2026-10-20 20:00:00 | 15200 |
| 4 | S102 | 2026-10-20 20:00:00 | 5100 |
| 5 | S102 | 2026-10-20 20:05:00 | 4980 |

### 3. 解题思路

两个口径必须分清：（1）单服各小时峰值——直接GROUP BY小时取MAX(online_cnt)；（2）全服合计峰值——必须先把同一snapshot_time的各服在线数SUM成全服在线序列，再在合计序列上取最大值；若对每服各自取MAX再相加，会高估全服峰值（各服峰值不在同一时刻，不可能同时发生）。实现路径：解法一按HOUR分组输出各小时最大在线（单服视角）；解法二先按时刻SUM出全服合计在线，再用子查询找出合计峰值及出现时刻。易错点：跨服口径「先MAX后SUM」的错误；HOUR()返回0-23的整数；主动说明「峰值精度受快照采样频率限制」，5分钟快照得到的峰值只是采样点峰值，是重要的口径意识加分项。

### 4. 参考解法

写法一：按小时看单服在线峰值

```sql
SELECT
    HOUR(snapshot_time) AS hour_of_day,  -- 提取小时（0-23）
    MAX(online_cnt)     AS max_online    -- 该小时内该服最大在线
FROM online_snapshot
WHERE server_id = 'S101'                 -- 单服视角
  AND snapshot_time >= '2026-10-20'
  AND snapshot_time <  '2026-10-21'      -- 只看10-20一天
GROUP BY HOUR(snapshot_time)             -- 按小时分组
ORDER BY hour_of_day;                    -- 按小时顺序输出全天曲线
```

结果解读：示例数据中20点峰值15200远高于12点的8450，晚间是明显高峰；运维据此把例行维护放在19:30之前完成，运营把限时活动排在20:00开启承接流量。

写法二：先算全服合计在线，再找峰值时刻（子查询版）

```sql
SELECT
    t.snapshot_time,        -- 快照时刻
    t.total_online          -- 全服合计在线
FROM (
    SELECT
        snapshot_time,                     -- 同一时刻各服对齐
        SUM(online_cnt) AS total_online    -- 先把该时刻所有服在线数求和
    FROM online_snapshot
    WHERE snapshot_time >= '2026-10-20'
      AND snapshot_time <  '2026-10-21'
    GROUP BY snapshot_time                 -- 得到全服合计在线的时间序列
) t
WHERE t.total_online = (
    SELECT MAX(m.total_online)             -- 再在合计序列中找最大值
    FROM (
        SELECT SUM(online_cnt) AS total_online
        FROM online_snapshot
        WHERE snapshot_time >= '2026-10-20'
          AND snapshot_time <  '2026-10-21'
        GROUP BY snapshot_time
    ) m
)
ORDER BY t.snapshot_time;                  -- 峰值若有多个并列时刻，全部列出
```

结果解读：全服合计峰值出现在20:00的20300（S101的15200+S102的5100），而不是「各服峰值简单相加」的虚高值——先对齐时刻再求和的口径避免了高估；并列峰值时刻全部输出，方便运维核对是否存在瞬时抖动。

### 5. 性能分析与优化

写法一有单服过滤条件，走(server_id, snapshot_time)联合索引后数据量小、效率高；写法二对同一数据聚合两次，可改用窗口函数一步完成（在合计序列上用MAX() OVER()做标记），避免重复扫描。优化建议：（1）快照表按天分区+联合索引(server_id, snapshot_time)；（2）若采样粒度细化到1分钟，可先把「时刻-全服合计」聚合成5分钟粒度落表，峰值查询读聚合表；（3）只要峰值时刻时，可用ORDER BY total_online DESC LIMIT 1代替自比较子查询，语义等价更简洁；（4）跨天高峰（深夜挂机服）要明确统计边界，避免00:05的峰值被算进「前一天」。

### 6. 面试延伸考点

**【面试高频】为什么各服峰值相加不等于全服峰值？** 回答要点：各服峰值出现在不同时刻，相加得到的是「不可能同时发生」的虚高值；全服峰值必须先按时刻对齐求和再取MAX，考察的是聚合顺序意识。

**【面试高频】怎么估算真正的同时在线峰值（PCU）？** 回答要点：快照只能得到采样点峰值，采样间隔越短越接近真实PCU；也可用登录/登出事件流重建在线曲线，或对快照做插值后取上界。

**【加分点】时段峰值曲线还能指导什么？** 回答要点：广告分时段出价、客服排班、维护窗口选择、新手引导客服介入时段，说明同一份数据可服务多个职能。

### 7. 业务拓展思考

在线曲线是游戏的「作息表」：午休12-14点与晚间20-23点双峰是典型形态，周末峰值更高、假期全天高位。运营据此排活动（晚间开限时副本）、运维排容量（按峰值乘安全系数扩容）、市场排广告（高峰前一小时加价抢量）。口径延展：在线曲线下面积即总在线时长，可估算人均在线时长；峰值与均值的比值反映在线稳定度，比值异常升高常对应活动抢量或掉线重连风暴，是运维告警的信号。

## GAME-08 新手引导各步骤流失人数

### 1. 业务背景

新玩家前30分钟决定留存：新手引导把玩家从「下载注册」带到「核心玩法体验」，每一步都有人离开。版本上线后，策划需要一张「引导步骤漏斗表」：每一步到达多少人、比上一步流失多少人、流失率多少，从中定位流失最严重的步骤（往往是操作过于复杂、强制战斗失败或加载卡顿的步骤），推动UI与数值调整。漏斗分析是数据分析最经典的题型之一，新手引导是它在游戏业务里最贴身的载体，也是校招面试的高频题。

### 2. 表结构说明

新手引导事件表 tutorial_events（玩家每完成一步记一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 玩家ID |
| step_id | INT | 引导步骤编号，1为第一步 |
| step_name | VARCHAR(64) | 步骤名称，如 选择职业 |
| event_time | DATETIME | 完成该步的时间 |

示例数据：

| log_id | user_id | step_id | step_name | event_time |
| --- | --- | --- | --- | --- |
| 1 | 100001 | 1 | 选择职业 | 2026-10-20 09:00:10 |
| 2 | 100001 | 2 | 基础移动教学 | 2026-10-20 09:02:40 |
| 3 | 100001 | 3 | 首次战斗 | 2026-10-20 09:06:15 |
| 4 | 100002 | 1 | 选择职业 | 2026-10-20 09:05:00 |
| 5 | 100003 | 1 | 选择职业 | 2026-10-20 09:08:20 |

### 3. 解题思路

口径：到达人数=完成该步骤的去重玩家数（COUNT(DISTINCT user_id)，防止同一玩家重复上报多条日志被重复计数）；流失人数=上一步到达人数−本步到达人数；第N步流失率=该段流失人数/上一步到达人数。实现路径：解法一用条件聚合把各步骤到达人数放进同一行（列转行），流失人数直接做减法，一行SQL输出完整漏斗；解法二先GROUP BY step_id得到每步人数，再自连接（当前步编号=上一步编号+1）拼接上一步人数求流失，输出长表。易错点：玩家乱序或跳步上报会令「=编号」的统计失真，可用「大于等于编号」的写法保证漏斗单调；同一步骤多条日志必须去重；漏斗人数理论上单调递减，出现回升即说明有脏数据，要先查数再出报表。

### 4. 参考解法

写法一：条件聚合一行输出完整漏斗

```sql
SELECT
    COUNT(DISTINCT CASE WHEN step_id >= 1 THEN user_id END) AS s1_users,
    -- 到达第1步人数；用 >= 而非 =，即使日志乱序、跳步也能保证漏斗单调递减
    COUNT(DISTINCT CASE WHEN step_id >= 2 THEN user_id END) AS s2_users,
    -- 到达第2步人数
    COUNT(DISTINCT CASE WHEN step_id >= 3 THEN user_id END) AS s3_users,
    -- 到达第3步人数
    COUNT(DISTINCT CASE WHEN step_id >= 1 THEN user_id END)
      - COUNT(DISTINCT CASE WHEN step_id >= 2 THEN user_id END) AS lose_1to2,
    -- 第1到2步流失人数 = 第1步人数 - 第2步人数
    COUNT(DISTINCT CASE WHEN step_id >= 2 THEN user_id END)
      - COUNT(DISTINCT CASE WHEN step_id >= 3 THEN user_id END) AS lose_2to3
    -- 第2到3步流失人数
FROM tutorial_events
WHERE event_time >= '2026-10-20'
  AND event_time <  '2026-10-27';   -- 统计近一周新玩家的引导数据
```

结果解读：示例数据一周内3人完成第1步、仅1人走完第3步，第1到2步流失2人；真实场景中若某一步流失率突然升高，策划应优先复现该步骤的操作流程，排查操作复杂度与卡顿。

写法二：分组聚合+自连接求逐步流失（长表，可扩展任意步骤数）

```sql
SELECT
    cur.step_id,                                -- 当前步骤编号
    cur.step_name,                              -- 步骤名
    cur.reach_users,                            -- 当前步骤到达人数
    prev.reach_users - cur.reach_users AS lose_users,
    -- 流失人数 = 上一步人数 - 本步人数；第1步无上一步，prev为NULL结果也为NULL
    ROUND((prev.reach_users - cur.reach_users) * 100.0 / prev.reach_users, 1)
                                      AS lose_rate_pct  -- 步骤间流失率(%)
FROM (
    SELECT
        step_id,
        MAX(step_name)          AS step_name,   -- 步骤名（组内取确定值）
        COUNT(DISTINCT user_id) AS reach_users  -- 该步骤去重到达人数
    FROM tutorial_events
    WHERE event_time >= '2026-10-20'
      AND event_time <  '2026-10-27'
    GROUP BY step_id
) cur
LEFT JOIN (                                     -- 自连接同一份聚合结果取「上一步」
    SELECT
        step_id,
        COUNT(DISTINCT user_id) AS reach_users
    FROM tutorial_events
    WHERE event_time >= '2026-10-20'
      AND event_time <  '2026-10-27'
    GROUP BY step_id
) prev ON cur.step_id = prev.step_id + 1        -- 当前步的上一步 = 编号减1
ORDER BY cur.step_id;
```

结果解读：长表结构可容纳任意多的引导步骤，适合步骤经常增删的版本迭代；第1步作为漏斗头没有上一步（LEFT JOIN未命中、流失列为NULL），报表层需单独处理漏斗头部展示。

### 5. 性能分析与优化

写法一只扫一遍表、输出一行，效率最高，但步骤数变化时要改SQL（列固定）；写法二扫两遍加自连接，步骤数动态可扩展。优化建议：（1）建(step_id, user_id)或(event_time, step_id)联合索引；（2）引导数据只属于新玩家，可先JOIN注册表限定「注册7日内玩家」缩小扫描量；（3）数仓按天沉淀引导漏斗汇总表（dt×step_id的到达人数），周/月漏斗对汇总表再聚合；（4）若引导步骤存在支线（非线性流程），自连接的编号加1模型失效，应改用parent_step字段建映射，或按玩家行为序列用窗口函数重建漏斗（可作为进阶话题主动提及）。

### 6. 面试延伸考点

**【面试高频】漏斗的「到达」和「完成」口径有什么区别？** 回答要点：到达=触发该步骤（看到引导界面），完成=完成该步骤，两者之差是「步骤内流失」；本表记录的是完成事件，若要到达口径需另取曝光事件表。

**【面试高频】漏斗人数出现回升说明什么？** 回答要点：漏斗是包含关系必须单调递减，回升说明存在跳步上报、重复注册或埋点错位等脏数据，应先做数据质量核查再出报表。

**【加分点】如何把引导流失和次留关联？** 回答要点：按「是否完成引导」把同期新增分群，对比两群的次日留存，量化引导完成对次留的提升，推动策划优先修补关键流失步骤。

### 7. 业务拓展思考

引导漏斗连接产品体验与留存指标：定位流失步骤后，对改造方案（缩短步骤、跳过动画、失败免罚）做A/B测试，用数据验证改版收益；长期建立「引导完成率—次留—7留」的传导链，作为版本验收的硬指标。口径延展：漏斗可按渠道与平台拆分（低端机型的引导卡顿更严重）、按玩家来源拆分（自然量与买量用户的耐心不同），精细化定位问题人群，避免用一个大盘漏斗掩盖局部问题。

## GAME-09 各活动参与人数统计

### 1. 业务背景

活动运营在大型版本活动（如国庆签到+限时副本合集）结束后做复盘，需要每个活动的「参与人数」来评估活动吸引力：参与率过低（参与人数/活动期间活跃人数）说明入口太深或奖励不吸引人，下期要优化；同时必须把「已上架但零参与」的活动也列出来——这类活动往往是入口配置故障或埋点丢失，比低参与更紧急。本题考察LEFT JOIN保留零行的意义、COUNT(DISTINCT)与COUNT(*)的区别，是两表JOIN的入门标准题。

### 2. 表结构说明

活动主表 activities（每个已配置活动一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| activity_id | INT | 活动ID，主键 |
| activity_name | VARCHAR(64) | 活动名称 |
| activity_type | VARCHAR(16) | 类型：签到 / 限时副本 / 充值返利 |
| start_time | DATETIME | 开始时间 |
| end_time | DATETIME | 结束时间 |

活动参与流水表 activity_records（玩家每次参与记一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| record_id | BIGINT | 流水自增ID |
| activity_id | INT | 参与的活动ID |
| user_id | BIGINT | 参与玩家ID |
| join_time | DATETIME | 参与时间 |

activities 示例数据：

| activity_id | activity_name | activity_type | start_time | end_time |
| --- | --- | --- | --- | --- |
| 1 | 国庆七日签到 | 签到 | 2026-10-01 00:00:00 | 2026-10-07 23:59:59 |
| 2 | 亡灵副本挑战 | 限时副本 | 2026-10-01 00:00:00 | 2026-10-07 23:59:59 |
| 3 | 充值返利翻倍 | 充值返利 | 2026-10-01 00:00:00 | 2026-10-07 23:59:59 |
| 4 | 中秋灯谜 | 签到 | 2026-09-15 00:00:00 | 2026-09-17 23:59:59 |
| 5 | 万圣节预热 | 限时副本 | 2026-10-25 00:00:00 | 2026-10-31 23:59:59 |

activity_records 示例数据：

| record_id | activity_id | user_id | join_time |
| --- | --- | --- | --- |
| 1 | 1 | 100001 | 2026-10-01 08:10:00 |
| 2 | 1 | 100001 | 2026-10-02 09:00:00 |
| 3 | 1 | 100002 | 2026-10-01 12:30:00 |
| 4 | 2 | 100003 | 2026-10-02 20:15:00 |
| 5 | 1 | 100002 | 2026-10-03 08:05:00 |

### 3. 解题思路

口径：参与人数=COUNT(DISTINCT user_id)，一人多次参与（如连续7天签到）只算1人，COUNT(*)会把签到7天算成7人；需求要求包含「零参与活动」，所以必须以活动主表LEFT JOIN流水表，计数用COUNT(DISTINCT r.user_id)——LEFT JOIN未命中时r.user_id为NULL，COUNT(列)自动跳过NULL，恰好得到0。实现路径：解法一直接LEFT JOIN后分组计数；解法二先在流水表内按活动聚合出参与人数，再LEFT JOIN回活动主表并用IFNULL补零。易错点：误用INNER JOIN丢掉零参与活动（充值返利活动3恰好无记录，是测试这个点的关键）；右表过滤条件误放WHERE导致LEFT JOIN退化；活动5尚未开始，区分「未开始」与「已结束零参与」需结合活动时间字段。

### 4. 参考解法

写法一：LEFT JOIN + 去重计数（推荐）

```sql
SELECT
    a.activity_id,                           -- 活动ID
    a.activity_name,                         -- 活动名称
    COUNT(DISTINCT r.user_id) AS join_users  -- 参与人数：NULL不计数，零参与活动自动为0
FROM activities a
LEFT JOIN activity_records r                -- LEFT JOIN：无参与记录的活动保留主表行
       ON a.activity_id = r.activity_id
WHERE a.start_time >= '2026-10-01'           -- 只复盘10月及以后上架的活动（过滤主表放WHERE安全）
GROUP BY a.activity_id, a.activity_name
ORDER BY join_users DESC;                    -- 按参与人数降序
```

结果解读：充值返利活动join_users=0仍然出现在结果里——要么真没人参与，要么入口配置故障或埋点丢失，需要运营第一时间确认；LEFT JOIN的价值正是让「沉默活动」浮出水面。

写法二：先聚合后JOIN（子查询补零版）

```sql
SELECT
    a.activity_id,                             -- 活动ID
    a.activity_name,                           -- 活动名称
    IFNULL(p.join_users, 0) AS join_users      -- 无参与记录的活动用0填充
FROM activities a
LEFT JOIN (
    SELECT
        activity_id,
        COUNT(DISTINCT user_id) AS join_users  -- 先在流水表内按活动去重计数
    FROM activity_records
    WHERE join_time >= '2026-10-01'            -- 提前过滤，减小JOIN输入
    GROUP BY activity_id
) p ON a.activity_id = p.activity_id           -- 与活动主表对齐
WHERE a.start_time >= '2026-10-01'
ORDER BY join_users DESC;
```

结果解读：先聚合再JOIN让参与表在JOIN前就缩成每活动一行，JOIN代价更小；IFNULL补0后与写法一结果完全一致，两种写法可互为校验，这种「同口径双实现对数」的习惯在实习期非常受用。

### 5. 性能分析与优化

写法一先JOIN后聚合，签到类活动单人参与记录多（一人7行），JOIN后中间结果膨胀，去重计数开销大；写法二先聚合，JOIN输入是每活动一行的小结果集，通常更快。优化建议：（1）activity_records建(activity_id, user_id)联合索引，覆盖分组去重；（2）参与流水按天分区，查询先做时间裁剪；（3）活动数量有限（几百内），聚合结果很小，两种写法差距在流水大时才明显；（4）若还要算参与率，与DAU汇总表再JOIN一次即可，注意分母口径取「活动期间活跃人数」而非「全月活跃人数」。

### 6. 面试延伸考点

**【面试高频】过滤右表的条件放ON里和WHERE里有什么区别？** 回答要点：LEFT JOIN下右表条件放ON只影响匹配结果（不匹配仍保留主表行），放WHERE会把右表为NULL的行过滤掉，LEFT JOIN退化成INNER JOIN，零参与活动消失。

**【面试高频】为什么COUNT(DISTINCT r.user_id)在LEFT JOIN未命中时是0而不是1？** 回答要点：未命中时r.user_id为NULL，COUNT(列)跳过NULL值，结果为0；这也是不能用COUNT(*)的原因——COUNT(*)会计数NULL行，未命中的活动会被算成1人。

**【加分点】如何计算活动渗透率？** 回答要点：join_users/活动期间DAU加和去重，分母按活动生命周期聚合而非固定自然月，并说明「参与人数」与「领奖人数」的口径差异。

### 7. 业务拓展思考

参与人数只是活动漏斗第一层，完整复盘要看「曝光→参与→完成→付费转化」四级：签到活动看7日全勤率，副本活动看通关率，充值返利看达标率。零参与活动要联动客户端排查入口埋点是否丢失，属于数据质量事件，应走告警流程。口径延展：区分「参与人数」与「参与人次」，区分「参与人数」与「领奖人数」（领奖才是有效参与）；跨活动可计算互相分流效应，指导活动排期避免同档期活动自相竞争。

## GAME-10 各服玩家数与负载预警

### 1. 业务背景

滚服是手游常用开服模式：每个新服承载一波玩家，随时间自然衰减，玩家数超过服务器设计承载量会造成卡顿、排队甚至崩溃。运维与发行运营每周查看「各服注册玩家数/设计承载上限」的负载率：负载率超过80%的服要预警（考虑开新服导流或扩容），长期低于10%的服要评估合服以节约成本。本题把两表JOIN、GROUP BY聚合与HAVING对聚合结果的过滤串成一条完整业务链，是JOIN+HAVING组合的典型考题。

### 2. 表结构说明

服务器维表 servers（每个服一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| server_id | VARCHAR(16) | 服务器编号，主键 |
| server_name | VARCHAR(64) | 服名称，如 电信一区-青龙 |
| open_time | DATE | 开服日期 |
| max_load | INT | 设计最大承载玩家数 |

玩家表 players（每个注册玩家一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 玩家ID |
| server_id | VARCHAR(16) | 所属服务器 |
| register_time | DATETIME | 注册时间 |
| level | INT | 当前等级 |

servers 示例数据：

| server_id | server_name | open_time | max_load |
| --- | --- | --- | --- |
| S101 | 电信一区-青龙 | 2026-09-01 | 100000 |
| S102 | 电信二区-白虎 | 2026-09-15 | 100000 |
| S103 | 电信三区-朱雀 | 2026-10-10 | 80000 |
| S104 | 电信四区-玄武 | 2026-10-20 | 80000 |

players 示例数据：

| user_id | server_id | register_time | level |
| --- | --- | --- | --- |
| 100001 | S101 | 2026-09-01 10:00:00 | 45 |
| 100002 | S101 | 2026-09-02 11:30:00 | 38 |
| 100003 | S102 | 2026-09-15 09:20:00 | 22 |
| 100004 | S103 | 2026-10-10 18:05:00 | 12 |
| 100005 | S103 | 2026-10-11 20:40:00 | 9 |

### 3. 解题思路

口径：负载率=注册玩家数/max_load；玩家数来自players按服计数（滚服模型下一人一号一服，注册即入服）。需求要「预警」，即对聚合后的负载率做筛选——聚合后的条件必须用HAVING而不是WHERE，这是本题第一考点；同时要以servers为基准LEFT JOIN，让「还没有玩家的预备服」也出现在报表中（玩家数为0）而不是消失。实现路径：解法一LEFT JOIN+GROUP BY+HAVING；解法二用相关标量子查询逐服计算玩家数，在外层WHERE过滤。易错点：在WHERE里写聚合条件直接报错；分母max_load为0或NULL要做除零保护；LEFT JOIN后计数要用COUNT(p.user_id)（主表行保留、右表NULL不计数）而非COUNT(*)（会把未命中行也计成1）。

### 4. 参考解法

写法一：LEFT JOIN + GROUP BY + HAVING（标准写法）

```sql
SELECT
    s.server_id,                          -- 服务器编号
    s.server_name,                        -- 服务器名称
    s.max_load,                           -- 设计承载上限
    COUNT(p.user_id)       AS player_cnt, -- 各服注册玩家数（LEFT JOIN未命中为0，不计数NULL）
    ROUND(COUNT(p.user_id) * 100.0 / NULLIF(s.max_load, 0), 1) AS load_rate_pct
                                          -- 负载率(%)，NULLIF防止上限为0或NULL时除零报错
FROM servers s
LEFT JOIN players p                     -- LEFT JOIN保留尚无玩家的预备服
       ON s.server_id = p.server_id
GROUP BY s.server_id, s.server_name, s.max_load   -- 维表字段全部进GROUP BY（ONLY_FULL_GROUP_BY要求）
HAVING COUNT(p.user_id) >= 0.8 * s.max_load       -- 聚合后过滤：玩家数达承载80%即预警
ORDER BY load_rate_pct DESC;                       -- 最拥挤的服排最前
```

结果解读：返回的服务器进入「开新服导流或扩容」评估流程；示例数据中S103只有2人、上限8万，负载率0.003%不会出现在结果里——预警列表为空本身也是重要信息，说明当前容量充足，运维可以安心。

写法二：相关标量子查询（以服为驱动行）

```sql
SELECT
    s.server_id,                       -- 服务器编号
    s.server_name,                     -- 服务器名称
    s.max_load,                        -- 设计承载上限
    (SELECT COUNT(*)                   -- 相关子查询：逐服统计玩家数
     FROM players p
     WHERE p.server_id = s.server_id) AS player_cnt,
    ROUND((SELECT COUNT(*) FROM players p
           WHERE p.server_id = s.server_id) * 100.0 / NULLIF(s.max_load, 0), 1)
      AS load_rate_pct,                -- 同口径计算负载率(%)
FROM servers s
WHERE (SELECT COUNT(*) FROM players p
       WHERE p.server_id = s.server_id) >= 0.8 * s.max_load  -- 相关子查询结果可在外层WHERE过滤
ORDER BY load_rate_pct DESC;
```

结果解读：相关子查询版本与写法一结果一致，但子查询表达式重复出现三次，可读性与维护性差；演示它的意义在于理解「HAVING过滤」与「把聚合值放进外层WHERE过滤」是同一需求的两种表达，面试能说清两者关系即可。

### 5. 性能分析与优化

写法一一次JOIN加一次分组，players(server_id)有索引时为索引扫描或hash join，效率高；写法二的相关子查询在旧优化器下可能逐行执行（N个服跑N次子查询），服数量少时影响不大，但风格上不推荐。优化建议：（1）players(server_id)建索引，JOIN与子查询都受益；（2）滚服模式下玩家表持续增长，可维护各服玩家数汇总表（定时或触发更新），运维监控直接读汇总；（3）若关注的是真实压力而非注册总量，把口径换成「最近7日活跃玩家数/max_load」，即活跃负载；（4）GROUP BY后若只保留server_id，其余维表字段需全部加入GROUP BY以满足ONLY_FULL_GROUP_BY模式。

### 6. 面试延伸考点

**【面试高频】HAVING和WHERE的区别？** 回答要点：WHERE在分组前过滤原始行、不能使用聚合函数；HAVING在分组后过滤聚合结果；本题「负载率≥80%」是对聚合值的筛选，必须HAVING，或先聚合到派生表再用WHERE。

**【面试高频】为什么用LEFT JOIN？INNER JOIN会怎样？** 回答要点：INNER JOIN会丢掉零玩家的预备服；监控报表需要全量服视角，故以servers为主表LEFT JOIN，未命中计数为0。

**【加分点】滚服游戏合服后数据要怎么处理？** 回答要点：合服需迁移players归属并在维表记录合服映射历史（旧server_id到新server_id的对照表），历史指标按「当前服+并入主体」双口径回溯，否则趋势断裂。

### 7. 业务拓展思考

负载率是服务器成本与玩家体验的平衡器：高负载影响卡顿率与付费体验，低负载浪费成本并稀释社交生态。可延展出三级口径：注册负载（总量）、活跃负载（7日活跃/上限）、峰值在线负载（联动GAME-07的PCU），三者结合决定扩容或合服的优先级；开服节奏（每日开几个服）由新增导流与负载率共同决定，是发行ROI模型的重要变量，面试中主动串起这条业务链非常加分。

## GAME-11 每日活跃时段分布

### 1. 业务背景

运营排活动、客服排班、买量分时段出价，都需要回答同一个问题：玩家都在几点上线？分析师把最近一周的登录流水按小时聚合，输出「各时段活跃人数分布」——典型的手游双峰形态（午休12-14点、晚间20-23点）会直接决定限时活动开启时间、商店刷新时刻与推送时机。与GAME-07不同，本题看的是「玩家活跃行为」（登录去重人数）而非「服务器压力」（在线人数快照）：同样是HOUR()函数分组，业务口径完全不同，面试官常借这两题连问来区分候选人是否真的理解业务。

### 2. 表结构说明

登录日志表 login（与GAME-02同源，完整独立呈现；一行一次登录）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 玩家ID |
| server_id | VARCHAR(16) | 服务器编号 |
| login_time | DATETIME | 登录时间 |
| platform | VARCHAR(10) | 平台：ios / android / pc |

示例数据：

| log_id | user_id | server_id | login_time | platform |
| --- | --- | --- | --- | --- |
| 1 | 100001 | S101 | 2026-10-20 08:02:11 | ios |
| 2 | 100002 | S101 | 2026-10-20 12:30:45 | android |
| 3 | 100001 | S101 | 2026-10-20 12:35:02 | ios |
| 4 | 100003 | S102 | 2026-10-20 21:44:37 | android |
| 5 | 100002 | S101 | 2026-10-20 21:50:19 | android |

### 3. 解题思路

口径：各时段「活跃人数」应按HOUR(login_time)分组后COUNT(DISTINCT user_id)；若用COUNT(*)得到的是登录人次——同一个午休登录两次的玩家会被算两次（示例中100001与100002都是一天内多次登录）。统计周期明确为近7天，跨天聚合时同一玩家在不同天重复出现属正常（口径为「周期内出现在该时段的去重人数」）。实现路径：解法一按24小时细粒度分组，人数与人次两列对照输出；解法二用CASE WHEN把24小时归并为四个业务时段（凌晨/上午/下午/晚间），输出更适合进周报的四行结论。易错点：忘记去重把人次当人数；HOUR()必须作用于DATETIME类型；0点附近的会话归属（23:59登录算前一天）要说明按登录时刻归属。

### 4. 参考解法

写法一：24小时细粒度分布

```sql
SELECT
    HOUR(login_time)         AS hour_of_day,  -- 提取登录小时（0-23）
    COUNT(DISTINCT user_id)  AS active_users, -- 该时段去重活跃人数
    COUNT(*)                 AS login_times   -- 登录人次，与人数口径对照
FROM login
WHERE login_time >= '2026-10-14'
  AND login_time <  '2026-10-21'             -- 近7天窗口，左闭右开
GROUP BY HOUR(login_time)
ORDER BY hour_of_day;                        -- 从0点排到23点
```

结果解读：对照active_users与login_times两列，比值接近1说明玩家上线次数少而集中（休闲向），比值大说明重度玩家高频登录；示例数据12点时段2人3次，双列并排一眼可辨口径差异。

写法二：CASE WHEN归并四大业务时段

```sql
SELECT
    CASE
        WHEN HOUR(login_time) BETWEEN 0  AND 5  THEN '凌晨(0-6点)'    -- 深夜挂机与熬夜党
        WHEN HOUR(login_time) BETWEEN 6  AND 11 THEN '上午(6-12点)'   -- 通勤早高峰
        WHEN HOUR(login_time) BETWEEN 12 AND 17 THEN '下午(12-18点)'  -- 午休双峰之一
        ELSE '晚间(18-24点)'                                          -- 手游最大峰值
    END                      AS time_slot,      -- 业务时段标签
    COUNT(DISTINCT user_id)  AS active_users    -- 时段去重活跃人数
FROM login
WHERE login_time >= '2026-10-14'
  AND login_time <  '2026-10-21'
GROUP BY CASE
        WHEN HOUR(login_time) BETWEEN 0  AND 5  THEN '凌晨(0-6点)'
        WHEN HOUR(login_time) BETWEEN 6  AND 11 THEN '上午(6-12点)'
        WHEN HOUR(login_time) BETWEEN 12 AND 17 THEN '下午(12-18点)'
        ELSE '晚间(18-24点)'
    END                                          -- ONLY_FULL_GROUP_BY 下须与 SELECT 表达式一致
ORDER BY active_users DESC;                      -- 直接按时段热度排序，结论前置
```

结果解读：四行结论可直接进周报——若晚间占比超过40%，运营把签到奖励领取引导、限时商店刷新都安排在晚间，把触达效率做到最大。

### 5. 性能分析与优化

两种写法均为一次扫描加轻量分组；HOUR()包裹列会使login_time索引失效，但近7天窗口小、按天分区裁剪后代价可控；若要查全历史则应改写为「范围条件+预聚合」结构。优化建议：（1）数仓按天分区，查询只扫7个分区；（2）沉淀天×小时粒度汇总表，时段分布对7天汇总表再聚合，秒级返回；（3）Hive下可先按user_id+小时去重再计数，减轻单Reducer压力；（4）需要分平台/分服对比时把维度加入GROUP BY即可，注意输出行数膨胀后排序与展示的成本。

> Hive/Spark SQL 差异：Hive 提供 hour() 函数语义一致；全历史分析务必基于分区表并带分区过滤；大规模去重先 GROUP BY 去重再聚合计数是标准优化手段。

### 6. 面试延伸考点

**【面试高频】人数口径和人次口径分别什么时候用？** 回答要点：看触达面（活动排期、推送时机）用人数，看使用强度（服务器压力、频次运营）用人次；两者之比即人均登录次数，反映登录黏性。

**【面试高频】登录时段分布和在线时段分布有什么区别？** 回答要点：登录是离散事件（每次上线记一点），在线是持续状态（快照重建曲线）；重度玩家一次长会话在登录分布只贡献1次、在在线分布持续贡献时长，两条曲线形态不同。

**【加分点】如何识别「凌晨挂机工作室」？** 回答要点：凌晨时段（0-6点）活跃且登录时间高度规律（整点或固定间隔）的账号群，结合设备聚集度与行为同质性判断脚本行为，联动风控处理。

### 7. 业务拓展思考

时段分布是运营日历的底图：活动开启、商店刷新、推送文案都贴着峰值时段设计；分时段出价买量可压低低效时段的成本。进一步可按玩家分层看时段（新玩家偏晚间、上班族午休峰明显），支撑差异化推送；口径延展：把「登录时段分布」升级为「会话时长×时段」矩阵，能识别碎片时间玩家与沉浸玩家两类人群，反过来指导玩法的单局时长设计。

## GAME-12 首充玩家列表

### 1. 业务背景

首充（第一次充值）是玩家从免费到付费的质变节点。商业化运营每天要拉出「昨日首充玩家名单」：首充转化率（首充人数/同期新增）、首充金额档位、首充距注册的时长，都是评估首充引导设计是否有效的核心数据；名单还会同步给用户运营做付费新手关怀（首充后跟进礼包与客服回访）。技术难点在于「每个玩家的第一笔成功订单」要同时取时间与金额两个配对字段——直接MIN(pay_time)配MIN(amount)会取到两笔不同订单的字段，这是本题最经典的坑。

### 2. 表结构说明

充值订单表 orders（与GAME-04同源，完整独立呈现）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | VARCHAR(32) | 订单号 |
| user_id | BIGINT | 玩家ID |
| product_name | VARCHAR(64) | 商品名 |
| amount | DECIMAL(10,2) | 实付金额（元） |
| pay_status | VARCHAR(16) | SUCCESS成功 / PENDING待支付 / REFUND已退款 |
| pay_time | DATETIME | 支付完成时间 |

示例数据：

| order_id | user_id | product_name | amount | pay_status | pay_time |
| --- | --- | --- | --- | --- | --- |
| R20261001001 | 100001 | 首充礼包 | 6.00 | SUCCESS | 2026-10-01 09:20:11 |
| R20261005002 | 100001 | 月卡 | 30.00 | SUCCESS | 2026-10-05 12:00:00 |
| R20261002003 | 100002 | 大额礼包 | 328.00 | SUCCESS | 2026-10-02 21:10:45 |
| R20261003004 | 100003 | 首充礼包 | 6.00 | PENDING | 2026-10-03 18:30:22 |
| R20261004005 | 100003 | 首充礼包 | 6.00 | SUCCESS | 2026-10-04 10:05:40 |

### 3. 解题思路

口径：首充=第一笔pay_status='SUCCESS'的订单，PENDING不算（尚未支付成功）；同一玩家同一秒多单时用order_id做次序兜底。难点：首充时间与首充金额必须来自同一行订单。实现路径：解法一先GROUP BY user_id取MIN(pay_time)得到首充时间，再JOIN回订单表用「玩家+时间」两键配对取该行的金额与商品；解法二用ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY pay_time, order_id)给每人订单编号，取rn=1，一次扫描干净利落。易错点：SELECT MIN(pay_time), MIN(amount)想当然配对——金额取的是该玩家全场最小金额而非首充那单的金额；忘记过滤pay_status导致待支付单抢先成为「首充」；退款后重新充值的口径要提前与需求方确认。

### 4. 参考解法

写法一：MIN取首充时间 + JOIN回表取配对金额

```sql
SELECT
    f.user_id,                        -- 玩家ID
    f.first_pay_time,                 -- 首充时间
    o.amount        AS first_amount,  -- 首充金额（与首充时间来自同一行订单）
    o.product_name  AS first_product  -- 首充商品名
FROM (
    SELECT
        user_id,
        MIN(pay_time) AS first_pay_time  -- 每个玩家最早的成功支付时间
    FROM orders
    WHERE pay_status = 'SUCCESS'         -- 只认支付成功订单，PENDING/REFUND剔除
    GROUP BY user_id                     -- 按玩家分组取首次
) f
JOIN orders o                           -- 回订单表配对
  ON o.user_id    = f.user_id
 AND o.pay_time   = f.first_pay_time    -- 用「玩家+时间」两键定位首充那一行
 AND o.pay_status = 'SUCCESS';          -- 再次限定成功状态，防止匹配到异常单
```

结果解读：玩家100001的首充是10-01的6元首充礼包，而不是10-05的30元月卡——两键配对保证了金额与时间同源；若同一玩家同一秒存在两笔成功订单，该写法会输出两行，严谨处理需再按order_id取最小，或直接使用写法二。

写法二：ROW_NUMBER窗口取每人第一单（推荐）

```sql
SELECT
    t.user_id,           -- 玩家ID
    t.first_pay_time,    -- 首充时间
    t.first_amount,      -- 首充金额
    t.first_product      -- 首充商品名
FROM (
    SELECT
        user_id,
        pay_time     AS first_pay_time,  -- 时间透传
        amount       AS first_amount,    -- 金额透传
        product_name AS first_product,   -- 商品名透传
        ROW_NUMBER() OVER (
            PARTITION BY user_id             -- 每个玩家一组
            ORDER BY pay_time, order_id      -- 组内按支付时间排序，订单号兜底防并列
        ) AS rn                              -- 组内序号，1即第一笔成功订单
    FROM orders
    WHERE pay_status = 'SUCCESS'             -- 先过滤成功订单再编号，减少排序数据量
) t
WHERE t.rn = 1;                              -- 只保留每人的第一单
```

结果解读：窗口写法一次扫描完成「分组内排序+取首行」，order_id兜底天然规避同秒并列问题；后续要扩展「首充距注册时长」时只需多JOIN一张注册表，工程上更推荐。

### 5. 性能分析与优化

写法一是聚合加JOIN回原表，orders数据量大时回表JOIN代价高，且需要(user_id, pay_time)联合索引支撑；写法二一次扫描加窗口排序，排序发生在每个user_id分区内，代价可控。优化建议：（1）orders建(user_id, pay_status, pay_time)联合索引，两种写法都受益；（2）窗口写法中先WHERE pay_status再编号，缩小参与排序的数据量；（3）首充标记是典型增量需求，数仓可维护玩家首充表（user_id, first_pay_time, first_amount）每日增量刷新，名单查询退化为单表过滤；（4）**【避坑指南】**昨日有充值不代表是昨日首充——首充判定必须回查玩家全部历史订单，只扫昨日分区的写法会把「老玩家复购」误判为首充，这是真实业务里最常见的线上事故之一。

### 6. 面试延伸考点

**【面试高频】为什么MIN(pay_time)不能直接配MIN(amount)？** 回答要点：MIN是列级聚合，两列各自取最小值、可能来自不同订单；要取「首充那一行的金额」必须按行配对——JOIN回表或窗口函数取组内首行。

**【面试高频】退款玩家还算首充玩家吗？** 回答要点：口径确认题——按支付行为口径算，退款前已完成首充；按营收口径可剔除并标记「首充退回」；关键是口径定义先行并在报表注明。

**【加分点】如何计算首充距注册的时长分布？** 回答要点：首充结果JOIN注册表，DATEDIFF(first_pay_time, register_time)后按「当日/3日内/7日后」分层，转化越早说明首充引导越有效，也预示更高LTV。

### 7. 业务拓展思考

首充名单是付费转化漏斗的起点：首充转化率反映6元高性价比档的设计效果；首充时间距注册越短，玩家付费习惯养成越早、长期LTV越高。运营动作上，注册24小时未首充玩家触发定向推送与礼包召回，首充玩家进入付费成长关怀池；口径延展：可分析首充档位分布（全部6元说明档位引导成功）、首充来源场景（弹窗/商城/活动页），定位最有效的首充转化路径，反哺商业化埋点设计。

## GAME-13 各道具使用人数与次数

### 1. 业务背景

道具策划调平衡性时要看道具的真实消耗：体力药水是全员刚需还是少数人囤积？复活币是不是集中在高难副本玩家手里？分析师需要按道具同时输出三个口径——使用人数（多少不同玩家用过）、使用次数（发生了多少次使用行为）、消耗数量（一共吃掉多少个），三者组合才能判断道具定位：人数多说明普及率高，次数远超人数说明重度依赖，数量口径则受单次批量使用影响。只看单一口径极易误判，本题核心考察COUNT(DISTINCT)与COUNT(*)/SUM的口径区分。

### 2. 表结构说明

道具使用流水表 item_use_logs（每次使用记一行，一次可消耗多件）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 使用玩家ID |
| item_id | INT | 道具ID |
| item_name | VARCHAR(64) | 道具名称 |
| use_cnt | INT | 本次消耗件数 |
| use_time | DATETIME | 使用时间 |

示例数据：

| log_id | user_id | item_id | item_name | use_cnt | use_time |
| --- | --- | --- | --- | --- | --- |
| 1 | 100001 | 301 | 体力药水 | 1 | 2026-10-20 09:15:00 |
| 2 | 100001 | 301 | 体力药水 | 2 | 2026-10-20 12:40:00 |
| 3 | 100002 | 301 | 体力药水 | 1 | 2026-10-20 13:02:11 |
| 4 | 100001 | 302 | 复活币 | 1 | 2026-10-20 20:05:44 |
| 5 | 100003 | 302 | 复活币 | 3 | 2026-10-21 10:22:30 |

### 3. 解题思路

三个口径一次分清：使用人数=COUNT(DISTINCT user_id)（玩家去重）；使用次数=COUNT(*)（一行一次使用行为，即使一次批量用多件也只算1次）；消耗数量=SUM(use_cnt)（件数求和）。统计周期按需限定为本周或版本周期。实现路径：解法一单层聚合，三个口径并列输出并附人均次数；解法二先在派生表按「玩家×道具」聚合去重，外层再汇总到道具粒度，结构上便于继续扩展浅度/重度用户拆分。易错点：把COUNT(*)说成人数；SUM列出现NULL时自动跳过不参与求和；MySQL支持COUNT(DISTINCT user_id, item_id)多列组合去重（统计「玩家×道具」组合数），这个冷知识是面试加分项。

### 4. 参考解法

写法一：单层聚合三口径并列

```sql
SELECT
    item_id,                                 -- 道具ID
    item_name,                               -- 道具名
    COUNT(DISTINCT user_id) AS user_cnt,     -- 使用人数：去重玩家数
    COUNT(*)                AS use_times,    -- 使用次数：使用行为行数
    SUM(use_cnt)            AS use_amount,   -- 消耗数量：件数求和
    ROUND(COUNT(*) / COUNT(DISTINCT user_id), 2) AS avg_times_per_user
                                             -- 人均使用次数=次数/人数，衡量使用集中度
FROM item_use_logs
WHERE use_time >= '2026-10-20'
  AND use_time <  '2026-10-27'               -- 近一周
GROUP BY item_id, item_name
ORDER BY user_cnt DESC;                      -- 按普及率排序
```

结果解读：示例数据体力药水2人3次4件（人均1.5次），复活币2人2次4件（人均1次但单次批量更大）；若某道具use_times/user_cnt高达10以上，说明被少数玩家重度依赖，平衡性调整优先关注。

写法二：先按「玩家×道具」去重聚合，再汇总（结构化写法）

```sql
SELECT
    t.item_id,                         -- 道具ID
    t.item_name,                       -- 道具名
    COUNT(*)          AS user_cnt,     -- 内层每行=一个「玩家×道具」组合，计数即人数
    SUM(t.use_times)  AS use_times,    -- 各玩家使用次数求和=总次数
    SUM(t.use_amount) AS use_amount    -- 各玩家消耗件数求和=总消耗
FROM (
    SELECT
        user_id,                        -- 玩家维度
        item_id,                        -- 道具维度
        MAX(item_name)    AS item_name, -- 名称随道具取值（组内取确定值）
        COUNT(*)          AS use_times, -- 该玩家对该道具的使用次数
        SUM(use_cnt)      AS use_amount -- 该玩家对该道具的消耗件数
    FROM item_use_logs
    WHERE use_time >= '2026-10-20'
      AND use_time <  '2026-10-27'
    GROUP BY user_id, item_id           -- 先聚合到「玩家×道具」粒度
) t
GROUP BY t.item_id, t.item_name         -- 再汇总到道具粒度
ORDER BY user_cnt DESC;
```

结果解读：结果与写法一完全一致；两层结构的价值在于内层结果可继续加工——比如先筛掉使用次数小于3的浅度用户再统计「重度使用人数」，复杂口径下比单层COUNT(DISTINCT)更易维护。

### 5. 性能分析与优化

写法一一次扫描，但COUNT(DISTINCT)需在内存维护去重集合，玩家×道具组合大时内存开销上升；写法二两次聚合多一次物化，但每层输入更小，「玩家×道具」粒度先行压缩在登录类大表上常常反而更快（Hive尤其明显）。优化建议：（1）建(item_id, user_id, use_time)联合索引或按天分区；（2）数仓沉淀道具日汇总表（天×道具：人数、次数、数量），周报对汇总表再聚合；（3）超大规模去重可用近似算法（Spark的approx_count_distinct）以精度换性能；（4）需要精确人均次数时，「先按玩家×道具预聚合」即写法二，是标准解法。

> Hive/Spark SQL 差异：Hive 2.x 之前不支持多列 COUNT(DISTINCT a, b)，写法需改为 COUNT(DISTINCT concat_ws('_', user_id, item_id)) 或采用写法二的两层聚合；两层聚合也是 Hive 大表去重的经典优化手段。

### 6. 面试延伸考点

**【面试高频】人数、次数、数量三个口径分别怎么算、什么时候用？** 回答要点：COUNT(DISTINCT user_id)看普及率、COUNT(*)看行为频次、SUM(use_cnt)看资源消耗；混用三者是新手最常见口径错误，答出「普及-频次-强度」的对应关系即可。

**【面试高频】MySQL的COUNT(DISTINCT a, b)是什么语义？** 回答要点：对a、b组合去重计数，任一列为NULL则该行不计入；可用来统计「玩家×道具」组合数。

**【加分点】如何识别道具囤积行为？** 回答要点：对比获取量与使用量，长期「获取远大于使用」的道具是背包沉睡资产，提示投放过量或价值感不足，可联动数值策划调整产出。

### 7. 业务拓展思考

道具消耗数据直接服务数值策划与商业化：体力类道具消耗高峰对应玩法开放时段，可反推体力恢复速度与上限设计是否合理；消耗品销量下滑往往早于「内容荒」出现（玩家没有消耗需求等于没有追求目标），是版本内容储备的预警信号。口径延展：按玩家生命周期阶段（新手/成长/成熟）拆分使用结构，或按副本/玩法场景拆分（需要日志带场景字段），支撑「道具-玩法」配套调优。

## GAME-14 玩家累计登录天数与最近登录

### 1. 业务背景

用户运营维护玩家分层名单时，需要每个玩家的「累计登录天数」（衡量黏性）与「最近一次登录时间」（判断是否流失）。典型场景是流失召回：拉出「历史登录30天以上、但最近14天未登录」的高黏性流失玩家，推送召回礼包——这类玩家回归概率远高于轻度玩家，召回ROI最高。登录日志一人一天可能多条，累计天数必须按「天」去重，而最近登录用MAX即可；两个口径一去重一取最值，是聚合函数综合运用的入门必考题。

### 2. 表结构说明

登录日志表 login（与GAME-02/GAME-11同源，完整独立呈现）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志自增主键 |
| user_id | BIGINT | 玩家ID |
| server_id | VARCHAR(16) | 服务器编号 |
| login_time | DATETIME | 登录时间 |
| platform | VARCHAR(10) | 登录平台 |

示例数据：

| log_id | user_id | server_id | login_time | platform |
| --- | --- | --- | --- | --- |
| 1 | 100001 | S101 | 2026-10-01 08:00:00 | ios |
| 2 | 100001 | S101 | 2026-10-01 21:30:00 | ios |
| 3 | 100001 | S101 | 2026-10-03 09:10:00 | ios |
| 4 | 100002 | S101 | 2026-10-20 12:00:00 | android |
| 5 | 100003 | S102 | 2026-10-05 19:45:00 | android |

### 3. 解题思路

口径：累计登录天数=COUNT(DISTINCT DATE(login_time))，一天登录两次只算1天（示例中100001在10-01登录两次）；最近登录=MAX(login_time)；距今天数=DATEDIFF(当前统计日, MAX(login_time))。召回条件「累计≥30天且最近14天未登录」都是聚合后才能判断的条件，必须写在HAVING里。实现路径：解法一单层GROUP BY直接输出三口径；解法二先按「玩家×天」去重成派生表，外层再COUNT与MAX，结构上可平滑升级为连续登录天数等进阶口径。易错点：用COUNT(*)当天数（把登录次数当天数，多登录玩家严重虚高）；DATEDIFF两个参数的顺序（MySQL是前者减后者）；「当前日期」用CURDATE()会导致不同时间跑数结果漂移，正式报表应固定统计日期参数。

### 4. 参考解法

写法一：单层聚合（推荐）

```sql
SELECT
    user_id,                                            -- 玩家ID
    COUNT(DISTINCT DATE(login_time)) AS total_login_days, -- 累计登录天数：按天去重
    MAX(login_time)                  AS last_login_time,  -- 最近一次登录时间
    DATEDIFF(CURDATE(), MAX(login_time)) AS idle_days     -- 距今天数，超过14即流失候选
FROM login
GROUP BY user_id                                         -- 按玩家聚合
HAVING COUNT(DISTINCT DATE(login_time)) >= 30            -- 高黏性：累计≥30天
   AND MAX(login_time) <  CURDATE() - INTERVAL 14 DAY    -- 流失：最近14天未登录
ORDER BY idle_days DESC;                                 -- 流失越久越靠前，优先召回
```

结果解读：命中名单的玩家是「曾经重度、当前沉默」的核心召回对象；名单为空说明暂无双条件满足者，运营可放宽为「7天未登录」先做观察，而不是直接推翻口径。

写法二：先按「玩家×天」去重，再聚合（两层结构）

```sql
SELECT
    t.user_id,                                -- 玩家ID
    COUNT(*)         AS total_login_days,     -- 内层每行=一个活跃日，直接计数
    MAX(t.login_day) AS last_login_day,       -- 最近活跃日期（天粒度）
    DATEDIFF(CURDATE(), MAX(t.login_day)) AS idle_days  -- 距今天数
FROM (
    SELECT DISTINCT
        user_id,                              -- 玩家
        DATE(login_time) AS login_day         -- 登录时间截断到天
    FROM login
) t                                           -- 「玩家×天」去重后的活跃日明细
GROUP BY t.user_id
HAVING COUNT(*) >= 30                         -- 高黏性条件
   AND MAX(t.login_day) < CURDATE() - INTERVAL 14 DAY  -- 流失条件
ORDER BY idle_days DESC;
```

结果解读：DISTINCT先压掉同日多条日志，外层逻辑更轻；该结构可平滑升级为「最长连续登录天数」等进阶口径（配合窗口函数做日期差分），面试聊到延伸方向时是很好的伏笔。

### 5. 性能分析与优化

写法一一次扫描加COUNT(DISTINCT)去重，玩家量大时去重集合内存开销大；写法二先DISTINCT压缩行数再聚合，对「登录次数远多于活跃天数」的重度高频游戏收益明显。优化建议：（1）数仓登录日志按天分区，先裁剪时间范围再统计；（2）沉淀玩家档案宽表（user_id, total_login_days, last_login_time等）每日增量刷新，召回名单退化为单表查询；（3）MySQL侧建(user_id, login_time)联合索引加速分组与MAX；（4）CURDATE()依赖跑数时间，正式报表应使用固定统计日期参数保证可复现。

> Hive/Spark SQL 差异：Hive 无 CURDATE()，用 current_date()；DATEDIFF(d1, d2) 语义为 d1 减 d2 的天数，与 MySQL 一致；全量玩家档案应优先在 ads 层玩家维表上操作，避免直接扫明细日志。

### 6. 面试延伸考点

**【面试高频】累计登录天数和累计登录次数的区别与计算？** 回答要点：天数按DATE去重COUNT(DISTINCT DATE(...))，次数直接COUNT(*)；次数/天数为日均登录频次，反映登录强度而非广度。

**【面试高频】「流失」的口径一般怎么定？** 回答要点：常用「连续N天未登录」（N随品类取14或30天），更严谨用分位数法（如75%分位玩家最大登录间隔）定义，关键是与运营共识后固化，避免每份报表口径漂移。

**【加分点】如何计算连续登录天数？** 回答要点：经典gaps-and-islands问题——按用户对登录日期去重排序，用日期减去行号生成「连续组标识」，同组内日期连续，再取组内最大跨度。

### 7. 业务拓展思考

玩家档案（天数+最近登录）是分层运营的地基：与累计付费JOIN后可输出「高黏高付/高黏低付/低黏高付/低黏低付」四象限，分别匹配召回礼包、促付引导、防流失干预与观察策略。口径延展：累计天数可限定为自然周/月（周活跃天数WAD反映黏性结构）；最近登录升级为「近7/14/30日活跃标记」矩阵即可构建RFM式玩家分层模型，直接驱动推送与礼包策略，是数据分析师最常交付的名单类需求。

## GAME-15 各渠道玩家等级分布

### 1. 业务背景

发行复盘各渠道用户质量时，等级是最粗但最快的质量代理指标：注册一周后仍停留在10级以下的渠道用户，大概率是羊毛党或广告误点人群；等级分布整体右移（高等级占比高）说明渠道用户与产品匹配。分析师需要把注册表（渠道归属）与玩家档案（当前等级）JOIN起来，按渠道输出等级段分布，供市场部在渠道结算谈判与素材定向时使用。作为入门篇收官题，本题综合考察两表JOIN、CASE WHEN分桶与行转列输出三种能力。

### 2. 表结构说明

用户注册表 user_register（渠道归属）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 玩家ID |
| channel | VARCHAR(32) | 注册渠道：tiktok / bili / organic / kuaishou |
| register_time | DATETIME | 注册时间 |

玩家档案表 user_profile（当前进度快照，每人一行）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 玩家ID，主键 |
| level | INT | 当前角色等级，0表示未创建角色或未升级 |
| last_login_date | DATE | 最近登录日期 |

user_register 示例数据：

| user_id | channel | register_time |
| --- | --- | --- |
| 100001 | tiktok | 2026-10-01 09:12:35 |
| 100002 | bili | 2026-10-01 11:40:18 |
| 100003 | tiktok | 2026-10-02 20:05:44 |
| 100004 | organic | 2026-10-02 22:18:51 |
| 100005 | kuaishou | 2026-10-03 00:23:09 |

user_profile 示例数据：

| user_id | level | last_login_date |
| --- | --- | --- |
| 100001 | 42 | 2026-10-24 |
| 100002 | 3 | 2026-10-02 |
| 100003 | 17 | 2026-10-23 |
| 100004 | 0 | 2026-10-02 |
| 100005 | 8 | 2026-10-04 |

### 3. 解题思路

口径：等级段用CASE WHEN划分（1-10新手/11-30成长/31-60进阶/60以上核心，level=0或NULL归入「未进游戏」）；分布=各渠道×各等级段的去重人数；跨渠道对比建议同时给出「渠道内占比」而非只有绝对量（渠道量级不同，绝对量没有可比性）。实现路径：解法一两表JOIN后按渠道+等级段GROUP BY输出长表（适合入库与继续下钻）；解法二行转列——每个渠道一行、各等级段各一列（SUM(CASE WHEN ... THEN 1 ELSE 0 END)），适合直接贴进汇报表格。易错点：JOIN两侧键类型不一致（如VARCHAR对BIGINT）触发隐式转换使索引失效；档案表缺失的玩家（未创建角色）会被INNER JOIN静默丢掉，必须以注册表为基准LEFT JOIN；占比分母用窗口按渠道分区取总数。

### 4. 参考解法

写法一：JOIN后按渠道×等级段分组（长表）

```sql
SELECT
    r.channel,                               -- 渠道
    CASE
        WHEN p.level BETWEEN 1  AND 10 THEN '01_新手(1-10级)'
        WHEN p.level BETWEEN 11 AND 30 THEN '02_成长(11-30级)'
        WHEN p.level BETWEEN 31 AND 60 THEN '03_进阶(31-60级)'
        WHEN p.level > 60              THEN '04_核心(60级以上)'
        ELSE '00_未进游戏'                    -- level为0或NULL（档案缺失）归入未进游戏
    END                            AS level_band,   -- 等级段标签
    COUNT(DISTINCT r.user_id)      AS user_cnt,     -- 该渠道该段去重人数
    ROUND(COUNT(DISTINCT r.user_id) * 100.0
          / SUM(COUNT(DISTINCT r.user_id)) OVER (PARTITION BY r.channel), 1) AS pct_in_channel
                                   -- 渠道内占比：窗口按渠道分区取该渠道总人数作分母
FROM user_register r
LEFT JOIN user_profile p          -- LEFT JOIN：未创建角色的注册玩家也必须保留
       ON r.user_id = p.user_id
WHERE r.register_time >= '2026-10-01'
  AND r.register_time <  '2026-11-01'      -- 统计10月注册的同期群
GROUP BY r.channel,
         CASE
             WHEN p.level BETWEEN 1  AND 10 THEN '01_新手(1-10级)'
             WHEN p.level BETWEEN 11 AND 30 THEN '02_成长(11-30级)'
             WHEN p.level BETWEEN 31 AND 60 THEN '03_进阶(31-60级)'
             WHEN p.level > 60              THEN '04_核心(60级以上)'
             ELSE '00_未进游戏'
         END                                      -- ONLY_FULL_GROUP_BY 下表达式须一致
ORDER BY r.channel, level_band;
```

结果解读：长表适合入库与继续下钻；示例数据中bili用户100002停在3级、organic用户100004等级为0，若某渠道「00_未进游戏」占比异常高，应优先排查该渠道的包体与SDK问题，而不是直接归咎用户质量。

写法二：行转列，每渠道一行（宽表）

```sql
SELECT
    r.channel,                                            -- 渠道
    COUNT(*) AS total_users,                              -- 渠道总人数（一人一行，作占比分母）
    SUM(CASE WHEN p.level BETWEEN 1 AND 10 THEN 1 ELSE 0 END)     AS lv_1_10,
           -- 新手段人数：对每个玩家判断是否落在该段，命中记1否则记0，SUM即人数
    SUM(CASE WHEN p.level BETWEEN 11 AND 30 THEN 1 ELSE 0 END)    AS lv_11_30,
           -- 成长段人数
    SUM(CASE WHEN p.level BETWEEN 31 AND 60 THEN 1 ELSE 0 END)    AS lv_31_60,
           -- 进阶段人数
    SUM(CASE WHEN p.level > 60 THEN 1 ELSE 0 END)                 AS lv_60_up,
           -- 核心段人数
    SUM(CASE WHEN p.level IS NULL OR p.level = 0 THEN 1 ELSE 0 END) AS not_started
           -- 未进游戏人数：档案缺失（NULL）或等级为0
FROM user_register r
LEFT JOIN user_profile p ON r.user_id = p.user_id
WHERE r.register_time >= '2026-10-01'
  AND r.register_time <  '2026-11-01'
GROUP BY r.channel
ORDER BY total_users DESC;                                 -- 按渠道体量排序
```

结果解读：宽表一行一渠道，可直接贴周报；示例数据tiktok的2人中1人已达进阶段（17级），若tiktok的lv_60_up占比显著高于其他渠道，就是渠道质量差异的直接证据，支撑预算向高质量渠道倾斜。

### 5. 性能分析与优化

两种写法均为一次JOIN加一次聚合，数据量取决于统计周期的注册量，常规规模无性能风险。优化建议：（1）确保r.user_id与p.user_id两侧类型完全一致，避免隐式转换导致索引失效与JOIN错配；（2）user_profile若为按日快照分区表，需加「取最新分区」的过滤条件；（3）行转列写法只做一次GROUP BY且输出行数等于渠道数，聚合开销最小；（4）**【加分点】**更严谨的质量对比应使用「注册后第7天时的等级」而非当前等级快照——用当前快照会让注册早的玩家天然等级更高（存活偏差），同期群口径才公平，主动指出这一点能明显加分。

### 6. 面试延伸考点

**【面试高频】行转列（长表转宽表）怎么做，反过来呢？** 回答要点：行转列用SUM(CASE WHEN 条件 THEN 1 ELSE 0 END)计数或MAX(CASE WHEN 条件 THEN 值 END)取值，MySQL 8.0没有PIVOT语法；列转行用UNION ALL把多列拆成多行。

**【面试高频】这里为什么必须LEFT JOIN？** 回答要点：以注册为基准衡量渠道交付质量；INNER JOIN会静默丢掉未进游戏玩家，而那恰恰是渠道质量最差的部分，指标会系统性偏乐观。

**【加分点】等级分布能替代留存指标吗？** 回答要点：不能，等级是进度累积的存量口径，被时间长度污染（注册早必然等级高）；严谨对比要用「注册后N日到达等级」或直接用留存率，回答时点出存量与流量口径的区别。

### 7. 业务拓展思考

渠道×等级分布是渠道结算与素材优化的证据链：高等级占比持续偏低的渠道要在结算谈判时压价或砍预算，并与次留、7留、首充数据组成渠道质量评分卡；素材定向调整后观察等级分布是否右移，可验证定向效果。口径延展：等级段边界应对齐游戏的核心付费点与卡点（如31级解锁竞技场），让「进阶段占比」直接对应核心玩法触达率；不同品类也可用主城等级或战力分位数代替等级，让同一套SQL框架适配多款产品。
