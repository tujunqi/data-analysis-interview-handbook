## GAME-31 分渠道LTV与买量回本周期测算

### 1. 业务背景

买量投放经理（UA）每月初要与数据团队对一次账：上个月各渠道（抖音信息流、B站UP主、华为应用商店等）买来的新用户，首日、7日、30日分别贡献了多少人均充值（LTV），对照各渠道的CPA（单次获客成本），累计到第几天能"回本"。这份结论直接决定下月预算分配：回本周期在30天以内的渠道加投，60天以后才能回本的渠道降级观察，90天仍看不到头的渠道直接砍掉。手游行业买量预算动辄数百万，回本周期每差10天，现金流压力完全不同，因此这道题是游戏数据分析师面试中买量方向的必考题。

| 华为应用商店 | 2026-09 | 18.00 |

### 3. 解题思路

先钉死三个口径：第一，LTV口径用"累计人均充值收入"，不含广告变现（本题假设纯内购游戏）；首日LTV定义为注册当日（第0日），7日LTV为第0~6日，30日LTV为第0~29日，与买量平台结算习惯一致。第二，退款单从收入中剔除，按净额计算。第三，回本周期定义为"累计LTV首次大于等于CPA的生命周期天数"，找不到则返回NULL表示截至30日未回本。实现路径：先把订单流水压到"人×日"粒度降量，再挂渠道维表换算成"生命周期第N日"，按渠道×N日聚合出人均值后用窗口SUM做累计，最后条件聚合取出D0/D7/D30三个切片与回本日。**【避坑指南】** LTV分母必须是渠道全部新增（含未付费用户），若误用付费用户做分母会把LTV放大数倍，这也是面试官最爱挖的口径坑。

### 4. 参考解法

**解法一：多层CTE + cohort对齐 + 窗口累计（可输出任意第N日LTV与精确回本日）**

```sql
-- 解法一：cohort对齐 + 窗口累计，主推写法
WITH pay_daily AS (                                   -- ① 订单流水压到"人×日"粒度，先做一次大幅降量
    SELECT user_id,
          DATE(order_time) AS pay_date,
          SUM(amount)      AS pay_amt
    FROM orders
    WHERE status = '成功'                             -- 退款单不计入LTV收入
    GROUP BY user_id, DATE(order_time)
),
cohort_pay AS (                                       -- ② 挂渠道与注册日，换算成生命周期第N日
    SELECT a.channel,
          DATEDIFF(p.pay_date, a.install_date) AS day_n,   -- 第N日：0 = 注册首日
          p.user_id,
          p.pay_amt
    FROM pay_daily p
    JOIN ads_user a ON a.user_id = p.user_id
    WHERE p.pay_date >= a.install_date                -- 防脏数据：注册日之前的充值剔除
      AND p.pay_date <  a.install_date + INTERVAL 31 DAY   -- 本题只看30日窗口，提前裁剪
),
ch_day AS (                                           -- ③ 渠道×第N日：当日人均充值
    SELECT channel, day_n,
          SUM(pay_amt) / COUNT(DISTINCT user_id) AS arpu_n
    FROM cohort_pay
    GROUP BY channel, day_n
),
ch_ltv AS (                                           -- ④ 窗口累计：第N日累计LTV = D0..DN 人均之和
    SELECT channel, day_n,
          SUM(arpu_n) OVER (PARTITION BY channel ORDER BY day_n
                            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS ltv_cum
    FROM ch_day
)
SELECT c.channel,                                     -- 渠道名
      c.cpa_cost,                                     -- 当月CPA（元/人）
      ROUND(MAX(CASE WHEN l.day_n = 0  THEN l.ltv_cum END), 2) AS ltv_d0,   -- 首日LTV
      ROUND(MAX(CASE WHEN l.day_n = 6  THEN l.ltv_cum END), 2) AS ltv_d7,   -- 7日LTV（第0~6日）
      ROUND(MAX(CASE WHEN l.day_n = 29 THEN l.ltv_cum END), 2) AS ltv_d30,  -- 30日LTV（第0~29日）
      MIN(CASE WHEN l.ltv_cum >= c.cpa_cost THEN l.day_n + 1 END) AS payback_day -- 累计LTV首超CPA的天数
FROM channel_cost c
LEFT JOIN ch_ltv l ON l.channel = c.channel
GROUP BY c.channel, c.cpa_cost;
```

结果解读：若抖音信息流输出 `ltv_d30=38.5、payback_day=47`，说明该渠道30日尚未回本、按当前曲线约47天回本；B站若 `payback_day=21`，则是当月最优渠道，应优先加投。

**解法二：用户级条件聚合 + 区间自连接实现累计（不用窗口函数的兼容写法）**

```sql
-- 解法二：条件聚合定LTV + 区间自连接算累计，MySQL 5.7 也能跑
WITH user_ltv AS (                                    -- ① 用户级：三个窗口内累计充值
    SELECT a.user_id, a.channel,
          SUM(CASE WHEN DATEDIFF(o.order_time, a.install_date) < 1
                   THEN o.amount ELSE 0 END) AS amt_d0,    -- 首日（第0日）
          SUM(CASE WHEN DATEDIFF(o.order_time, a.install_date) < 7
                   THEN o.amount ELSE 0 END) AS amt_d7,    -- 7日（第0~6日）
          SUM(CASE WHEN DATEDIFF(o.order_time, a.install_date) < 30
                   THEN o.amount ELSE 0 END) AS amt_d30,   -- 30日（第0~29日）
          COUNT(o.order_id) AS pay_cnt
    FROM ads_user a
    LEFT JOIN orders o ON o.user_id = a.user_id AND o.status = '成功'
    GROUP BY a.user_id, a.channel
),
ch_ltv AS (                                           -- ② 渠道级人均：一次GROUP BY出三个LTV
    SELECT channel,
          COUNT(*)              AS uv,                -- 分母=全部新增，含未付费
          SUM(amt_d0)  / COUNT(*) AS ltv_d0,
          SUM(amt_d7)  / COUNT(*) AS ltv_d7,
          SUM(amt_d30) / COUNT(*) AS ltv_d30
    FROM user_ltv
    GROUP BY channel
),
ch_day AS (                                           -- ③ 渠道×第N日充值总额（不除人数）
    SELECT a.channel,
          DATEDIFF(DATE(o.order_time), a.install_date) AS day_n,
          SUM(o.amount) AS amt
    FROM orders o
    JOIN ads_user a ON a.user_id = o.user_id
    WHERE o.status = '成功'
      AND o.order_time < a.install_date + INTERVAL 30 DAY
    GROUP BY a.channel, DATEDIFF(DATE(o.order_time), a.install_date)
),
ch_cum AS (                                           -- ④ 区间自连接：s.day_n<=d.day_n 求和即累计
    SELECT d.channel, d.day_n,
          SUM(s.amt) / MAX(u.uv) AS ltv_cum           -- 除以渠道总新增 = 累计LTV
    FROM ch_day d
    JOIN ch_day s ON s.channel = d.channel AND s.day_n <= d.day_n
    JOIN (SELECT channel, COUNT(*) AS uv FROM ads_user GROUP BY channel) u
         ON u.channel = d.channel
    GROUP BY d.channel, d.day_n
)
SELECT l.channel, c.cpa_cost,
      ROUND(l.ltv_d0, 2) AS ltv_d0, ROUND(l.ltv_d7, 2) AS ltv_d7, ROUND(l.ltv_d30, 2) AS ltv_d30,
      MIN(CASE WHEN k.ltv_cum >= c.cpa_cost THEN k.day_n + 1 END) AS payback_day
FROM ch_ltv l
JOIN channel_cost c ON c.channel = l.channel
LEFT JOIN ch_cum k ON k.channel = l.channel
GROUP BY l.channel, c.cpa_cost, l.ltv_d0, l.ltv_d7, l.ltv_d30;
```

结果解读：两解法的 `payback_day` 应完全一致，可互为对账；解法二不用窗口，便于移植到老版本数仓，但第④步自连接是 O(D²) 行组合，必须放在"渠道×日"聚合之后的小结果集上做。

> Hive/Spark SQL 差异：Hive 的 `datediff(end_date, start_date)` 参数顺序与 MySQL 相反且只接受 date 类型；没有 `INTERVAL` 语法的全部形式，日期加法用 `date_add`；Hive 支持 `FULL OUTER JOIN`，可省去解法一中"LEFT JOIN + UNION ALL"式的并集模拟。生产上建议把 pay_daily 沉淀为按天分区的拉链式日汇总表，回本看板只查汇总层。

### 5. 性能分析与优化

解法一的代价集中在 orders×ads_user 的大join与两次聚合，窗口排序发生在聚合后的"渠道×日"小结果集上（每渠道约30行），代价可忽略；解法二的区间自连接行数为 O(D²)（30日约900行/渠道），同样可控，但若误把自连接放在用户明细级则是灾难级膨胀。优化建议：orders 按 `dt` 分区并只扫注册日±30天窗口的分区；为 orders 建 `(user_id, order_time)` 复合索引，覆盖 `amount、status` 形成覆盖索引避免回表；把 pay_daily 沉淀成每日预聚合表，回本报表只做渠道级二次聚合；channel_cost、ads_user 属于小表，Spark 下用 broadcast join 避免 shuffle。

### 6. 面试延伸考点

- **30日LTV只有这么大，怎么预估90日LTV？**
  回答要点：主流做法是用历史留存曲线与付费曲线拟合外推，常见幂函数 `LTV(t)=a*t^b` 拟合前30天再外推，或用"30日LTV/历史同型游戏30日占比"经验系数；必须声明外推置信度，并持续用真实数据回测修正系数。
- **CPA口径是按激活、注册还是付费回传？**
  回答要点：三种口径数值差异很大，对账前必须与投放平台统一；国内媒体平台多按激活计费、深度转化按回传事件计费，内部分析建议同时保留"激活CPA"与"付费CPA"两套口径。
- **退款和代充折扣怎么处理进LTV？**
  回答要点：LTV应按净额口径扣退款，且要区分"申请期退款"与"滞后退款"，滞后退款需按历史退款率回填；安卓渠道代充折扣则影响真实流水与道具经济，需单独标注。
- **为什么用注册日做cohort锚点而不是激活日？**
  回答要点：注册日更接近"用户可付费"的起点，且与归因表字段对齐；若产品存在长预下载（先装后注册），两口径会拉开差距，需在文档中固定一种。

### 7. 业务拓展思考

渠道LTV×回本周期表是买量业务的"总闸门"：它向上支撑月度预算分配与渠道商务谈判（用数据压价），向下可以拆到素材层级、达人层级做二次归因。联动动作上，回本慢但留存好的渠道可改投"事件回传出价"降低前置风险；回本快的渠道要同步盯大R占比，防止"低CPA+纯羊毛量"的虚假繁荣。口径延展上，可将LTV拆为内购LTV+广告LTV（混合变现），把回本周期拆为"回本率曲线"（累计LTV/CPA），对长期运营产品比单点回本天数更有解释力。

## GAME-32 留存曲线对比与渠道质量评估（含曲线平台期判定）

### 1. 业务背景

季度渠道评审会上，发行负责人要对比抖音、B站、华为商店三个渠道的新增留存曲线：哪些渠道是"量质兼备"（前期留存高且后期衰减慢），哪些是"前高后塌"（首周好看、第二周起断崖）。除了常规的次留/7留/30留三个点，这次评审新增一个要求：自动判定每个渠道的留存曲线从第几天进入"平台期"——即日留存降幅收敛到0.5个百分点以内、曲线趋平的日子。平台期越早，说明渠道用户与产品的长期匹配度越高，LTV长尾越值钱；这个指标将作为渠道评级的新维度写入采购合同。

### 2. 表结构说明

**表1：login 登录流水表（一人一日多行或去重后一人一日一行）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| channel | VARCHAR(32) | 用户注册渠道（随用户维度冗余） |
| login_date | DATE | 登录日期 |

示例数据：

| user_id | channel | login_date |
|---|---|---|
| u1001 | 抖音信息流 | 2026-09-01 |
| u1001 | 抖音信息流 | 2026-09-02 |
| u1001 | 抖音信息流 | 2026-09-05 |
| u1003 | B站UP主 | 2026-09-02 |
| u1004 | 华为应用商店 | 2026-09-03 |

### 3. 解题思路

口径先行：本题为"新增留存"——以每用户首登日为cohort锚点，第N日留存 = 注册后第N日仍登录的用户数 / 该渠道新增用户数；平台期定义为一个渠道留存率"日降幅"最后一次超过0.5个百分点的日子之后一天，从那天起曲线进入平缓段。实现路径分四层：先算每用户首登日与渠道；再cohort对齐生成"渠道×第N日回访人数"矩阵（0~30日）；除以渠道新增得留存率序列；然后用LAG求逐日降幅。平台期判定给两种写法：一是对降幅序列聚合"最后一个大降幅日"再加一；二是用反连接NOT EXISTS直接找"其后不再出现大降幅"的最早候选日。**【加分点】** 能主动指出留存率序列可能缺日（某天整渠道无人登录），LAG会跨日比较造成降幅失真，严谨做法是先补齐日历序列。

### 4. 参考解法

**解法一：cohort留存矩阵 + LAG降幅 + "最后一个大降幅日"定位平台期**

```sql
-- 解法一：窗口LAG求降幅，聚合定位平台期起点
WITH first_login AS (                                 -- ① 每用户的注册渠道与首登日
    SELECT user_id, channel, MIN(login_date) AS install_date
    FROM login
    GROUP BY user_id, channel
),
base AS (                                             -- ② 分母：各渠道新增人数
    SELECT channel, COUNT(*) AS uv
    FROM first_login
    GROUP BY channel
),
retain AS (                                           -- ③ cohort对齐：渠道×第N日回访人数（0~30日）
    SELECT f.channel,
          DATEDIFF(l.login_date, f.install_date) AS day_n,
          COUNT(DISTINCT l.user_id)              AS act_uv
    FROM first_login f
    JOIN login l
      ON l.user_id = f.user_id
      AND l.login_date BETWEEN f.install_date AND f.install_date + INTERVAL 30 DAY
    GROUP BY f.channel, DATEDIFF(l.login_date, f.install_date)
),
rate AS (                                             -- ④ 留存率 = 当日回访人数 / 新增人数
    SELECT r.channel, r.day_n, r.act_uv / b.uv AS ret
    FROM retain r
    JOIN base b ON b.channel = r.channel
),
chg AS (                                              -- ⑤ LAG求相邻日降幅（百分点）
    SELECT channel, day_n, ret,
          (LAG(ret) OVER (PARTITION BY channel ORDER BY day_n) - ret) * 100 AS drop_pp
    FROM rate
)
SELECT c.channel,
      COALESCE(                                                       -- 平台期起点 = 最后一个大降幅日的次日
          MAX(CASE WHEN chg.drop_pp >= 0.5 THEN chg.day_n END), 0
      ) + 1 AS plateau_from_day,
      ROUND(MAX(CASE WHEN chg.day_n = 7  THEN chg.ret END) * 100, 2) AS ret7_pct,
      ROUND(MAX(CASE WHEN chg.day_n = 30 THEN chg.ret END) * 100, 2) AS ret30_pct
FROM chg
GROUP BY c.channel;
```

结果解读：若抖音 `plateau_from_day=9、ret30=4.2%`，B站 `plateau_from_day=5、ret30=7.8%`，则B站曲线更早趋平且长尾更厚，属于"量质兼备"，值得给更高买量单价。

**解法二：反连接NOT EXISTS直接找"其后再无大降幅"的最早一天（无LAG写法）**

```sql
-- 解法二：自连接求降幅 + 反连接定位平台期，不依赖窗口函数
WITH first_login AS (
    SELECT user_id, channel, MIN(login_date) AS install_date
    FROM login GROUP BY user_id, channel
),
base AS (
    SELECT channel, COUNT(*) AS uv FROM first_login GROUP BY channel
),
rate AS (                                             -- 留存率序列（口径同解法一③④）
    SELECT f.channel,
          DATEDIFF(l.login_date, f.install_date) AS day_n,
          COUNT(DISTINCT l.user_id) / b.uv       AS ret
    FROM first_login f
    JOIN login l ON l.user_id = f.user_id
        AND l.login_date BETWEEN f.install_date AND f.install_date + INTERVAL 30 DAY
    JOIN base b ON b.channel = f.channel
    GROUP BY f.channel, DATEDIFF(l.login_date, f.install_date), b.uv
),
big_drop AS (                                         -- 自连接取前一日，筛出所有"大降幅日"
    SELECT r1.channel, r1.day_n
    FROM rate r1
    JOIN rate r2 ON r2.channel = r1.channel AND r2.day_n = r1.day_n - 1
    WHERE (r2.ret - r1.ret) * 100 >= 0.5
)
SELECT b.channel,
      MIN(cand.day_n) AS plateau_from_day             -- 最早一个"之后不再有大降幅"的日子
FROM base b
JOIN rate cand ON cand.channel = b.channel            -- 候选起点 = 矩阵中出现的每一天
WHERE NOT EXISTS (                                    -- 反连接：起点之后（含当天）无大降幅
    SELECT 1 FROM big_drop bd
    WHERE bd.channel = cand.channel AND bd.day_n >= cand.day_n
)
GROUP BY b.channel;
```

结果解读：反连接写法语义直白——"从某天起，往后再没有一天降幅超过0.5pp"，与解法一结果应一致；它把窗口排序换成了自连接+NOT EXISTS，在候选日很少（≤31天）时代价极低，是面试中展示"同一问题多种机制"的好素材。

> Hive/Spark SQL 差异：Hive 支持窗口 LAG 与 NOT EXISTS（hive.mapred.mode=strict 下子查询需加过滤），但自连接 rate 时同一表两次扫描，Spark 建议先缓存 rate 小结果集；大表 login 需按 `dt` 分区，30日窗口之外的分区直接裁剪。

### 5. 性能分析与优化

两种解法的共同大头是第③步 login 自join（首登表×登录流水），行数近似"新增用户×其30日内登录次数"。优化手段：先把 login 按 `login_date` 分区、cohort 窗口只扫最近35天分区；join 键 `(user_id, login_date)` 建复合索引；更彻底的做法是预聚合一张 `(channel, install_date, day_n, act_uv)` 的cohort日汇总表，评审查询只在这张几千行的表上算比率与降幅，毫秒级返回。反连接解法中 big_drop 与 rate 的自连接都发生在≤31行的粒度，可忽略；切勿在用户明细级做自连接。

### 6. 面试延伸考点

- **新增留存和活跃留存有什么区别？什么场景用哪个？**
  回答要点：新增留存只看新用户cohort，衡量获客质量与新手期体验；活跃留存包含老用户，衡量整体产品健康度。买量评估必须用新增留存，否则老用户会稀释渠道差异。
- **平台期阈值0.5pp是怎么定的？换成相对降幅行不行？**
  回答要点：绝对阈值直观但对不同留存水平渠道不公平——留存在20%与5%的渠道，同样0.5pp含义不同；可改用"日环比相对降幅<5%"或对留存率取对数后判斜率，阈值应结合历史渠道曲线分布校准。
- **渠道自然量混在里面，怎么剥离？**
  回答要点：用归因表（有渠道点击/曝光回传的用户）作为买量子集单独算留存，或用"非投放期/非投放地区"的自然量基线做差；无法完全剥离时要声明混合口径。
- **如果两个渠道留存曲线交叉了，怎么下结论？**
  回答要点：不能只报7留一个点，要看整条曲线与平台期位置；交叉通常意味着一个渠道前期买量质量高、另一个长尾好，结论应绑定买量目标（冲首周收入还是长期LTV）。

### 7. 业务拓展思考

留存曲线平台期指标把"渠道质量"从三个离散点升级为一条曲线的形状特征，可与LTV回本（GAME-31）拼成渠道评估双钻模型：回本周期定短期预算、平台期定长期单价。联动动作上，平台期晚且断崖的渠道，运营要分析其用户构成（是不是大量"下载即走"的泛流量），反馈投放端调整定向；平台期早的渠道适合承接内容型运营（社区、攻略）。口径延展上，可对平台期后再做"平台期留存水平"分箱，把渠道分为高平台+早收敛、高平台+晚收敛等四象限，形成更细的渠道画像。

## GAME-33 鲸鱼用户流水异动监控（滑动窗口周环比）

### 1. 业务背景

风控与VIP运营团队每天早上跑批一个"鲸鱼异动"监控：把近4周净流水（成功充值减退款）合计不低于5000元的用户定义为鲸鱼，监控其本周充值流水的周环比——环比下滑超过60%要触发挽留（鲸鱼沉默往往是流失前兆，客单价高值得客服一对一跟进），环比暴涨超过200%要触发核查（可能是盗刷、退款套利或代充工作室入侵，先冻结观察）。运营要的是一张"昨日命中清单"：用户ID、本周流水、上周流水、环比、预警类型，直接导给CRM系统执行。这道题考察滑动窗口与环比类指标的严谨写法。

### 2. 表结构说明

**表1：orders 充值订单表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | BIGINT | 订单号 |
| user_id | VARCHAR(32) | 用户ID |
| order_time | DATETIME | 下单时间 |
| amount | DECIMAL(10,2) | 订单金额（元） |
| status | VARCHAR(16) | 状态（成功/退款） |

示例数据：

| order_id | user_id | order_time | amount | status |
|---|---|---|---|---|
| 91001 | w2001 | 2026-10-05 21:10:00 | 648.00 | 成功 |
| 91002 | w2001 | 2026-10-12 20:05:00 | 328.00 | 退款 |
| 91003 | w2002 | 2026-10-11 13:22:00 | 98.00 | 成功 |
| 91004 | w2003 | 2026-10-13 23:47:00 | 648.00 | 成功 |
| 91005 | w2001 | 2026-10-19 22:31:00 | 128.00 | 成功 |

### 3. 解题思路

口径三件事：鲸鱼资格用"近4周净流水合计≥5000"，净流水=成功-退款；环比基期取上一周；预警阈值定为下滑超60%（本周≤上周×40%）与暴涨超200%（本周≥上周×3倍）。实现路径的最大陷阱是"缺周"：用户某周一分钱没充，订单表里就没有那一周，直接LAG会把"上上周"错当"上周"，环比全部错位。所以必须先构建"鲸鱼×周"的完整网格（笛卡尔积）再LEFT JOIN流水补零。解法一用窗口LAG在补齐后的网格上做环比；解法二用自连接相邻周加条件聚合，不依赖窗口函数，并顺带解决鲸鱼资格判定。**【避坑指南】** 上周流水为0时环比是无穷大，必须显式定义"上周为0且本周>0"归入暴涨核查而非报除零错误。

### 4. 参考解法

**解法一：周序列补齐 + LAG环比 + 范围窗口判鲸鱼资格**

```sql
-- 解法一：网格补齐防缺周 + 窗口LAG，主推写法（@cur_wk 为当前ISO周，如 202643）
WITH wk_amt AS (                                      -- ① 用户×ISO周 净流水（成功-退款）
    SELECT user_id,
          YEARWEEK(DATE(order_time), 1) AS wk,        -- mode=1：周一为一周开始
          SUM(CASE WHEN status = '成功' THEN amount ELSE -amount END) AS net_amt
    FROM orders
    GROUP BY user_id, YEARWEEK(DATE(order_time), 1)
),
whale AS (                                            -- ② 鲸鱼资格：近4周净流水合计≥5000
    SELECT user_id, SUM(net_amt) AS amt_4w
    FROM wk_amt
    WHERE wk BETWEEN @cur_wk - 3 AND @cur_wk
    GROUP BY user_id
    HAVING SUM(net_amt) >= 5000
),
wk_grid AS (                                          -- ③ 补齐周序列：鲸鱼×近5周网格，缺周补0
    SELECT w.user_id, g.wk, COALESCE(k.net_amt, 0) AS net_amt
    FROM whale w
    CROSS JOIN (SELECT DISTINCT wk FROM wk_amt
                WHERE wk BETWEEN @cur_wk - 4 AND @cur_wk) g
    LEFT JOIN wk_amt k ON k.user_id = w.user_id AND k.wk = g.wk
),
wk_lag AS (                                           -- ④ 网格上做LAG，环比才不会错位
    SELECT user_id, wk, net_amt,
          LAG(net_amt) OVER (PARTITION BY user_id ORDER BY wk) AS prev_amt
    FROM wk_grid
)
SELECT user_id,
      wk,
      net_amt                                         AS cur_amt,   -- 本周净流水
      prev_amt                                        AS prev_amt,  -- 上周净流水
      ROUND((net_amt - prev_amt) / NULLIF(prev_amt, 0) * 100, 1) AS wow_pct,
      CASE WHEN prev_amt > 0 AND net_amt <= prev_amt * 0.4 THEN '骤降预警'  -- 环比≤-60%
          WHEN net_amt > 0 AND net_amt >= prev_amt * 3      THEN '暴涨核查'  -- 环比≥+200%
      END AS alert_type
FROM wk_lag
WHERE wk = @cur_wk;                                   -- 只输出本周命中的清单
```

结果解读：输出如 `w2001, 本周1280, 上周4856, -73.6%, 骤降预警`，说明鲸鱼流水腰斩，CRM应推送专属回归礼包；`w2003, 本周6480, 上周0, NULL, 暴涨核查` 则要先过风控再谈庆祝。

**解法二：自连接相邻周 + 条件聚合（无窗口函数，兼容老引擎）**

```sql
-- 解法二：日期区间条件聚合 + 相邻周自连接，不依赖YEARWEEK连续性
WITH cur_prev AS (                                    -- ① 本周/上周流水：直接按日期区间条件聚合
    SELECT o.user_id,
          SUM(CASE WHEN DATE(o.order_time) >= @cur_date - INTERVAL 6 DAY
                    THEN CASE WHEN o.status='成功' THEN o.amount ELSE -o.amount END
                    ELSE 0 END) AS cur_amt,           -- 本周（近7天）
          SUM(CASE WHEN DATE(o.order_time) BETWEEN @cur_date - INTERVAL 13 DAY
                                        AND @cur_date - INTERVAL 7 DAY
                    THEN CASE WHEN o.status='成功' THEN o.amount ELSE -o.amount END
                    ELSE 0 END) AS prev_amt           -- 上周（8~14天前）
    FROM orders o
    WHERE DATE(o.order_time) >= @cur_date - INTERVAL 13 DAY
    GROUP BY o.user_id
),
whale AS (                                            -- ② 鲸鱼资格改用近28天净流水
    SELECT user_id
    FROM orders
    WHERE DATE(order_time) >= @cur_date - INTERVAL 27 DAY
    GROUP BY user_id
    HAVING SUM(CASE WHEN status='成功' THEN amount ELSE -amount END) >= 5000
)
SELECT cp.user_id, cp.cur_amt, cp.prev_amt,
      ROUND((cp.cur_amt - cp.prev_amt) / NULLIF(cp.prev_amt, 0) * 100, 1) AS wow_pct,
      CASE WHEN cp.prev_amt > 0 AND cp.cur_amt <= cp.prev_amt * 0.4 THEN '骤降预警'
          WHEN cp.cur_amt > 0 AND cp.cur_amt >= cp.prev_amt * 3      THEN '暴涨核查'
      END AS alert_type
FROM cur_prev cp
JOIN whale w ON w.user_id = cp.user_id
WHERE cp.cur_amt > 0 OR cp.cur_amt <> cp.prev_amt;    -- 排除无流水且无变化的噪声行
```

结果解读：解法二把"环比"翻译成两个互不重叠的日期区间求和，语义与周历解耦，天然规避YEARWEEK跨年（202643→202701无法减1）的坑；代价是窗口滑动改成固定7天窗，若周定义与自然周不一致需另行对齐。

> Hive/Spark SQL 差异：Hive 没有 YEARWEEK，用 `concat(year(dt), lpad(weekofyear(dt),2,'0'))` 自拼周键，注意跨年周；鲸鱼网格可用 `lateral view explode` 生成周序列；数据量大时建议把 wk_amt 沉淀为用户周流水表，监控SQL只扫5周分区。

### 5. 性能分析与优化

解法一的主要代价：wk_amt 全量订单聚合一次（可按周分区裁剪到近5周）；whale×周网格 CROSS JOIN 只有"鲸鱼数×5"行，很小。解法二对 orders 只扫14天分区、一次聚合，代价更低，但没有中间周序列，若要输出"连续3周下滑"这类多期模式就得扩展区间数。优化建议：orders 建 `(user_id, order_time)` 索引并按 `dt` 分区；把"用户×周净流水"固化为调度表 `dws_user_wk_pay`，监控与后续的异动归因都基于它；鲸鱼名单变化不大，可T-1物化，日批只算增量。**【面试高频】** 面试官常追问"为什么不直接LAG订单表"——答案就是缺周错位与窗口排序代价，先聚合成周粒度再LAG是标准范式。

### 6. 面试延伸考点

- **上周流水为0、本周为正，环比怎么报？**
  回答要点：数学上无穷大，业务上单独归为"新起量"类事件；报表显示NULL或"NEW"而不是报错，同时可辅助绝对值阈值（如本周>1000才核查）防止小金额噪声。
- **暴涨核查里怎么区分真付费与盗刷/退款套利？**
  回答要点：结合设备/IP聚集度、订单时间间隔规律性、退款率历史、支付渠道特征做二次画像；SQL层可输出"近24小时订单数、平均下单间隔、关联设备数"作为核查特征。
- **鲸鱼阈值5000定死合理吗？**
  回答要点：固定阈值受通胀与付费深度迁移影响，更稳健的是分位数法（如近4周流水Top 0.5%）或按游戏生命周期动态校准；阈值变动要保证监控口径可回溯。
- **怎么识别"连续N周下滑"而不是只看单周环比？**
  回答要点：在补齐周网格上用窗口判断 `net_amt <= LAG(net_amt) 且 LAG(net_amt) <= LAG(net_amt,2)` 的连续模式，或对每用户维护"连续下滑周数"累计窗口，这也是gaps-and-islands的反向应用。

### 7. 业务拓展思考

鲸鱼异动监控是"高价值用户运营"的雷达：骤降预警对接VIP客服挽留（专属礼包、电话回访），暴涨核查对接风控冻结，两者共享同一张底表但走完全不同的业务分支。可联动版本运营——大版本上线后的鲸鱼流水回落属于"内容消化完"的正常回落，应与真流失区分，因此监控规则可叠加版本日历做分层告警。口径延展上，周环比可升级为"相对个人基线的偏离度"（用该用户近12周流水中位数做基线），比固定比例更能适配鲸鱼之间巨大的付费节奏差异。

## GAME-34 抽卡概率与保底经济学验证

### 1. 业务背景

卡池下架后，数值策划与合规审计要联合复盘两件事：第一，卡池实际出货概率是否与公示概率一致——监管明确要求概率公示且真实，偏差过大有合规风险；第二，保底经济学验证——测算玩家平均多少抽能出一颗5星、80抽"满保底"（硬保底）的触发率是多少、10抽内就出货的"欧皇"占比多少，用于评估单位5星的期望钻石成本是否落在数值设计的目标区间（例如每颗5星期望成本62~68抽）。结论会影响下一个卡池的软保底参数（60抽后概率递增曲线）与保底继承规则。

### 2. 表结构说明

**表1：gacha_draw 抽卡记录表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| pool_id | VARCHAR(16) | 卡池ID |
| draw_seq | INT | 该用户在该池内的第几次抽取（从1递增） |
| draw_time | DATETIME | 抽卡时间 |
| item_rarity | TINYINT | 品质（5=五星 4=四星 3=三星） |
| is_up | TINYINT | 是否命中UP角色 |

示例数据：

| user_id | pool_id | draw_seq | draw_time | item_rarity | is_up |
|---|---|---|---|---|---|
| g3001 | P2026A | 1 | 2026-09-01 20:00:12 | 3 | 0 |
| g3001 | P2026A | 2 | 2026-09-01 20:00:15 | 4 | 0 |
| g3001 | P2026A | 3 | 2026-09-01 20:00:20 | 5 | 1 |
| g3001 | P2026A | 4 | 2026-09-01 20:00:26 | 3 | 0 |
| g3002 | P2026A | 1 | 2026-09-02 12:11:40 | 3 | 0 |

**表2：pool_declare 卡池公示参数表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| pool_id | VARCHAR(16) | 卡池ID |
| declared_p5 | DECIMAL(8,6) | 公示5星综合概率 |
| hard_pity | INT | 硬保底抽数（满多少抽必出5星） |

示例数据：

| pool_id | declared_p5 | hard_pity |
|---|---|---|
| P2026A | 0.016000 | 80 |
| P2026B | 0.012500 | 90 |

### 3. 解题思路

两个指标两类算法：综合概率验证是简单频率统计——各池5星出货次数/总抽数，与 declared_p5 求偏差；保底经济学则要算"相邻两颗5星的间隔抽数分布"，关键是给每颗5星找到"上一颗5星的序号"。解法一用窗口锚点法：在5星记录子集上按 `user_id, pool_id` 分区排序，LAG取上一颗的 draw_seq，差值即间隔，再聚合出均值、硬保底触发率；解法二用自连接：每颗5星去连接同池更早的所有5星取MAX序号，配合条件聚合输出间隔分布切片。**【加分点】** 能指出软保底（概率递增区）的数据特征——间隔分布会在60~80抽区间隆起，用直方图即可反向识别线上是否真的配置了递增曲线，而不只是查配置表。

### 4. 参考解法

**解法一：窗口锚点法验证概率与保底（主推）**

```sql
-- 解法一：LAG取“上一颗5星序号”，间隔=本次-上次
WITH pool_stat AS (                                   -- ① 各池实际出货频率
    SELECT pool_id,
          COUNT(*) AS total_draw,
          SUM(CASE WHEN item_rarity = 5 THEN 1 ELSE 0 END) / COUNT(*) AS real_p5,
          SUM(CASE WHEN item_rarity = 4 THEN 1 ELSE 0 END) / COUNT(*) AS real_p4
    FROM gacha_draw
    GROUP BY pool_id
),
five AS (                                             -- ② 只取5星行，LAG拿同池上一颗5星的序号
    SELECT user_id, pool_id, draw_seq,
          LAG(draw_seq) OVER (PARTITION BY user_id, pool_id ORDER BY draw_seq) AS prev_seq
    FROM gacha_draw
    WHERE item_rarity = 5
),
gap AS (                                              -- ③ 相邻5星间隔；首颗用自身序号（含新手保底）
    SELECT pool_id, draw_seq - COALESCE(prev_seq, 0) AS gap_n
    FROM five
)
SELECT s.pool_id,
      d.declared_p5,                                        -- 公示5星综合概率
      ROUND(s.real_p5, 5)                             AS real_p5,   -- 实际综合概率
      ROUND((s.real_p5 - d.declared_p5) * 100, 4)     AS p5_bias_pp,-- 偏差（百分点，合规审计关注）
      ROUND(AVG(g.gap_n), 1)                          AS avg_gap,   -- 平均每颗5星抽数
      ROUND(SUM(CASE WHEN g.gap_n >= d.hard_pity THEN 1 ELSE 0 END) / COUNT(g.gap_n), 4)
                                                      AS hard_pity_rate,  -- 满保底触发率
      ROUND(SUM(CASE WHEN g.gap_n <= 10 THEN 1 ELSE 0 END) / COUNT(g.gap_n), 4)
                                                      AS lucky10_pct      -- 10抽内出货占比
FROM pool_stat s
JOIN pool_declare d ON d.pool_id = s.pool_id
LEFT JOIN gap g ON g.pool_id = s.pool_id
GROUP BY s.pool_id, d.declared_p5, s.real_p5, d.hard_pity;
```

结果解读：若 `P2026A：declared 1.6%、real 1.61%、bias 0.01pp、avg_gap 63.2、pity_rate 6.8%`，说明概率公示可信、软保底把期望抽数压在目标区间内；若 pity_rate 高达20%，说明大量玩家触底，体验与口碑风险大。

**解法二：自连接找上一颗5星 + 条件聚合出间隔分布（无窗口写法）**

```sql
-- 解法二：自连接取“小于当前序号的最大5星序号”，再切片分布
WITH f AS (                                           -- 5星记录子集
    SELECT user_id, pool_id, draw_seq
    FROM gacha_draw
    WHERE item_rarity = 5
),
gap_join AS (                                         -- 当前5星 左连接 同池更早的所有5星
    SELECT f1.pool_id, f1.user_id, f1.draw_seq,
          COALESCE(MAX(f2.draw_seq), 0) AS prev_seq   -- MAX即“上一颗”，首颗记0
    FROM f f1
    LEFT JOIN f f2
      ON f2.user_id = f1.user_id
      AND f2.pool_id = f1.pool_id
      AND f2.draw_seq < f1.draw_seq
    GROUP BY f1.user_id, f1.pool_id, f1.draw_seq
)
SELECT g.pool_id,
      COUNT(*)                                          AS five_cnt,
      ROUND(AVG(g.draw_seq - g.prev_seq), 1)            AS avg_gap,
      ROUND(SUM(CASE WHEN g.draw_seq - g.prev_seq <= 10 THEN 1 ELSE 0 END) / COUNT(*), 4) AS bucket_01_10,
      ROUND(SUM(CASE WHEN g.draw_seq - g.prev_seq BETWEEN 11 AND 40 THEN 1 ELSE 0 END) / COUNT(*), 4) AS bucket_11_40,
      ROUND(SUM(CASE WHEN g.draw_seq - g.prev_seq BETWEEN 41 AND 60 THEN 1 ELSE 0 END) / COUNT(*), 4) AS bucket_41_60,
      ROUND(SUM(CASE WHEN g.draw_seq - g.prev_seq BETWEEN 61 AND 79 THEN 1 ELSE 0 END) / COUNT(*), 4) AS bucket_61_79, -- 软保底隆起区
      ROUND(SUM(CASE WHEN g.draw_seq - g.prev_seq >= 80 THEN 1 ELSE 0 END) / COUNT(*), 4) AS bucket_80_pity
FROM gap_join g
GROUP BY g.pool_id;
```

结果解读：五段分布直方图一眼看出软保底形状——若 `bucket_61_79` 明显高于 `bucket_41_60`，说明60抽后概率递增确实生效；全部间隔挤在 `bucket_80_pity` 则说明递增曲线没配对，玩家体验是"一路歪到保底"。

> Hive/Spark SQL 差异：抽卡日志日增千万行，Hive 下按 `dt` 分区、卡池下架后离线跑批；窗口 LAG 在 Hive 可用，自连接方案建议先对 f 子集做 `DISTRIBUTE BY user_id SORT BY draw_seq` 缓存；Spark SQL 可用 `collect_list` 之外的窗口方案，两者结果一致，注意 Hive 的整数除法需 `cast` 为 double。

### 5. 性能分析与优化

解法一在5星子集（约占抽数1.6%）上开窗，排序量很小，是首选；解法二的自连接复杂度为每用户每池 O(k²)（k=该池5星颗数），大R玩家一池几百颗5星时会到十万行级，需限制或接受离线跑批。优化建议：gacha_draw 按 `dt` 分区、`(pool_id, user_id, draw_seq)` 建聚簇/复合索引；概率验证部分可下沉为每日增量汇总 `(pool_id, dt, draws, p5_cnt, p4_cnt)`，审计只对小汇总表求比率；保底间隔分析需要用户级明细，无法完全预聚合，但可按月分区归档历史池。**【避坑指南】** 验证概率时不要只看全池平均——按"抽到第N抽的条件概率"切片才能暴露软保底配置错误，全池平均会掩盖局部异常。

### 6. 面试延伸考点

- **公示的“综合概率”和“基础概率”有什么区别？验证时用哪个？**
  回答要点：基础概率是每抽的独立概率，综合概率是把保底机制折算进去的全期望频率；玩家感知与监管口径都是综合概率，验证以综合概率为准，但诊断保底参数时要回到逐抽条件概率。
- **样本多大才能下“概率不合规”的结论？**
  回答要点：用二项分布/卡方检验思想——偏差是否超出 `sqrt(p(1-p)/n)` 的合理倍数；给出置信区间而不是单点比较，避免小样本池误判。
- **怎么从数据反向识别软保底曲线？**
  回答要点：对"距上次5星的抽数"分桶算条件出货率，观察60抽后是否逐抽抬升及斜率；如果条件概率在第70抽仍恒定，说明递增未生效。
- **歪了（UP未命中）怎么分析？**
  回答要点：统计5星中 is_up 占比是否接近公示的50%（或大保底机制下的100%），并分析"歪"玩家的后续抽取行为（是否继续抽），这关系到大保底机制的体验设计。

### 7. 业务拓展思考

保底经济学结论直接服务三个团队：数值组据此调软保底起点与递增斜率（把期望抽数控制在目标区间），合规组留存概率审计报告备查，运营组用"平均离保底还差几抽"设计定向礼包（比如第60抽未出货用户推送6折十连）。延展口径上，可计算"集齐全UP角色的期望成本"（几何分布叠加大保底），以及"歪的情绪成本"对流失的影响，把抽卡从概率问题升级为体验问题。

## GAME-35 关卡难度热力分析（通过率×流失率交叉分箱）

### 1. 业务背景

新版本上线一周，关卡策划要复盘主线1~100关的难度曲线：找出"又难又劝退"的双高关卡优先调参。单一通过率不够——有的关卡难但玩家越挫越勇，有的关卡不难却悄悄劝退了人。所以要把两维指标交叉：通过率（本关至少通过一次的用户/尝试用户）与"关卡流失率"（最后一次尝试本关后7日内不再登录的用户占比），做3×3交叉分箱（难度高/中/低 × 流失高/中/低），输出每一格的关卡清单。策划最关心"高难×高流失"格子里的关卡号，它们是下个热修的调参队列；而"高难×低流失"的关卡反而是设计得好的"心流关"。

### 2. 表结构说明

**表1：level_event 关卡尝试事件表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| level_id | INT | 关卡ID |
| attempt_time | DATETIME | 尝试时间 |
| is_pass | TINYINT | 本次尝试是否通过 |

示例数据：

| user_id | level_id | attempt_time | is_pass |
|---|---|---|---|
| p4001 | 12 | 2026-10-10 20:01:00 | 0 |
| p4001 | 12 | 2026-10-10 20:05:00 | 1 |
| p4001 | 13 | 2026-10-10 20:12:00 | 0 |
| p4002 | 12 | 2026-10-11 14:30:00 | 1 |
| p4002 | 13 | 2026-10-11 14:40:00 | 0 |

**表2：login 登录流水表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| login_date | DATE | 登录日期 |

示例数据：

| user_id | login_date |
|---|---|
| p4001 | 2026-10-10 |
| p4001 | 2026-10-13 |
| p4002 | 2026-10-11 |
| p4003 | 2026-10-12 |
| p4003 | 2026-10-20 |

### 3. 解题思路

口径先钉两个容易吵的点：通过率的分母是"尝试过该关的用户数"而不是尝试次数（避免肝帝刷次数拉高分母），分子是"曾通过该关的用户数"；关卡流失率的锚点是用户在该关的"最后一次尝试时间"，其后7日内无任何登录记为流失——注意是"任何登录"而不是"没打下一关"，两者含义不同。实现路径：先把事件压到"人×关"粒度（是否通过、最后尝试时间），聚合到关卡粒度算两个比率，再分箱交叉。分箱给两种写法：NTILE(3)数据驱动自动三等分，与业务经验阈值CASE分箱加条件聚合行转列输出9宫格矩阵。**【避坑指南】** NTILE分箱结果随版本波动，阈值口径不稳定，向策划汇报时要么固定历史阈值，要么声明"相对分箱"。

### 4. 参考解法

**解法一：NTILE自动分箱 + 排序定位双高关卡**

```sql
-- 解法一：两级聚合 + NTILE(3) 自动分箱，数据驱动
WITH lv_user AS (                                     -- ① 人×关 粒度：是否通过过、最后尝试时间
    SELECT level_id, user_id,
          MAX(CASE WHEN is_pass = 1 THEN 1 ELSE 0 END) AS is_pass,
          MAX(attempt_time)                            AS last_try
    FROM level_event
    WHERE attempt_time >= @ver_start                   -- 只看本版本窗口
    GROUP BY level_id, user_id
),
lv_stat AS (                                          -- ② 关卡粒度：通过率 + 7日流失率
    SELECT u.level_id,
          COUNT(*)                                     AS try_uv,
          SUM(u.is_pass) / COUNT(*)                    AS pass_rate,
          SUM(CASE WHEN NOT EXISTS (                   -- 最后尝试后7日内无登录 = 判定流失
                  SELECT 1 FROM login l
                  WHERE l.user_id = u.user_id
                    AND l.login_date > DATE(u.last_try)
                    AND l.login_date <= DATE(u.last_try) + INTERVAL 7 DAY)
              THEN 1 ELSE 0 END) / COUNT(*)            AS churn7_rate
    FROM lv_user u
    GROUP BY u.level_id
),
bin AS (                                              -- ③ NTILE各分3档：1=低 2=中 3=高
    SELECT level_id, try_uv, pass_rate, churn7_rate,
          NTILE(3) OVER (ORDER BY pass_rate)   AS pass_bin,    -- 通过率升序，1档最难过
          NTILE(3) OVER (ORDER BY churn7_rate) AS churn_bin    -- 流失率升序，3档最劝退
    FROM lv_stat
)
SELECT level_id, try_uv,
      ROUND(pass_rate * 100, 1)   AS pass_rate_pct,
      ROUND(churn7_rate * 100, 1) AS churn7_pct,
      CASE pass_bin  WHEN 3 THEN '高难' WHEN 2 THEN '中难' ELSE '低难' END AS diff_tag,
      CASE churn_bin WHEN 3 THEN '高流失' WHEN 2 THEN '中流失' ELSE '低流失' END AS churn_tag
FROM bin
ORDER BY churn_bin DESC, pass_bin DESC;               -- “高难×高流失”排在最前，即调参队列
```

结果解读：输出头部若是 `第38关 高难×高流失 通过率31% 流失率18%`，则是最高优先级调参对象；`第52关 高难×低流失` 属于良性挑战，动它前要谨慎。

**解法二：业务阈值CASE分箱 + 条件聚合行转列（输出3×3矩阵）**

```sql
-- 解法二：固定阈值分箱 + 条件聚合透视，输出策划习惯的9宫格
WITH lv_user AS (                                     -- 口径同解法一①
    SELECT level_id, user_id,
          MAX(CASE WHEN is_pass = 1 THEN 1 ELSE 0 END) AS is_pass,
          MAX(attempt_time) AS last_try
    FROM level_event
    WHERE attempt_time >= @ver_start
    GROUP BY level_id, user_id
),
lv_stat AS (                                          -- 口径同解法一②
    SELECT u.level_id,
          COUNT(*)          AS try_uv,
          SUM(u.is_pass) / COUNT(*) AS pass_rate,
          SUM(CASE WHEN NOT EXISTS (
                  SELECT 1 FROM login l
                  WHERE l.user_id = u.user_id
                    AND l.login_date > DATE(u.last_try)
                    AND l.login_date <= DATE(u.last_try) + INTERVAL 7 DAY)
              THEN 1 ELSE 0 END) / COUNT(*) AS churn7_rate
    FROM lv_user u
    GROUP BY u.level_id
),
tag AS (                                              -- 业务经验阈值分箱，口径跨版本稳定
    SELECT level_id, try_uv, pass_rate, churn7_rate,
          CASE WHEN pass_rate < 0.40 THEN '高难'
               WHEN pass_rate < 0.70 THEN '中难' ELSE '低难' END AS diff_tag,
          CASE WHEN churn7_rate >= 0.15 THEN '高流失'
               WHEN churn7_rate >= 0.05 THEN '中流失' ELSE '低流失' END AS churn_tag
    FROM lv_stat
)
SELECT SUM(diff_tag = '高难' AND churn_tag = '高流失') AS `高难_高流失`,   -- MySQL布尔式直接求和
      SUM(diff_tag = '中难' AND churn_tag = '高流失') AS `中难_高流失`,
      SUM(diff_tag = '低难' AND churn_tag = '高流失') AS `低难_高流失`,
      SUM(diff_tag = '高难' AND churn_tag = '中流失') AS `高难_中流失`,
      SUM(diff_tag = '中难' AND churn_tag = '中流失') AS `中难_中流失`,
      SUM(diff_tag = '低难' AND churn_tag = '中流失') AS `低难_中流失`,
      SUM(diff_tag = '高难' AND churn_tag = '低流失') AS `高难_低流失`,   -- 良性挑战区
      SUM(diff_tag = '中难' AND churn_tag = '低流失') AS `中难_低流失`,
      SUM(diff_tag = '低难' AND churn_tag = '低流失') AS `低难_低流失`
FROM tag;
```

结果解读：9宫格矩阵让"高难_高流失=7关、高难_低流失=12关"这类结构性结论一目了然——若高难关卡里一半在劝退人，说明难度曲线整体偏陡而非个别关卡问题，应调的是数值框架。

> Hive/Spark SQL 差异：Hive 支持 NTILE 与相关子查询性能较差，流失判定建议改成"用户末登表 LEFT JOIN"的写法（先算每用户 MAX(login_date)，再判断 `last_login <= last_try`）；9宫格透视在 Hive 中同样用条件聚合，布尔求和需改写为 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`。

### 5. 性能分析与优化

瓶颈在流失判定的相关子查询（NOT EXISTS逐行探测login）， lv_user 行数=用户×关卡，可能上千万行。优化：先物化 `user_last_login(user_id, MAX(login_date))` 小表，把NOT EXISTS改成LEFT JOIN后判断 `last_login <= DATE(last_try) OR last_login IS NULL`，一次hash join完成；level_event 按 `dt` 分区裁剪版本窗口，`(level_id, user_id)` 建复合索引加速两级聚合；更工程化的做法是把 lv_stat 沉淀为每日更新的关卡指标表，分箱与透视只在几千行的关卡粒度上做，NTILE与透视的代价都可忽略。**【面试高频】** "为什么分母用人数不用次数"几乎是必问题，答出"次数被重复尝试与肝帝稀释、人数才反映用户面"即可加分。

### 6. 面试延伸考点

- **流失归因到“本关”还是“本关+下一关”？怎么定？**
  回答要点：锚点选"最后一次尝试本关"，若用户打完A关就没再登录，也可能死在B关的加载/体验上；严谨做法对比"最后通过关"与"最后尝试关"的分布差异，把责任关卡定位到失败发生处。
- **同一用户多次流失边缘（弃坑又回来）怎么算？**
  回答要点：本题7日窗口口径下以"最后尝试"为准一人一票；若要研究反复弃坑，可对每次尝试做事件级标记，用生存分析处理多次事件。
- **通过率90%的关卡也可能有毒，怎么看？**
  回答要点：结合尝试次数分布（重复失败次数）与通过耗时，某些关"总能过但每次都要肝5次"同样伤体验，可加"平均尝试次数""失败后弃玩率"两个维度扩成热力矩阵。
- **NTILE和固定阈值分箱各自适用什么汇报场景？**
  回答要点：NTILE适合探索期快速看相对分布，固定阈值适合跨版本追踪与策划沟通（口径稳定），汇报文档建议固定阈值并在附录给出NTILE对照。

### 7. 业务拓展思考

关卡热力矩阵是策划调参的"作战地图"，9宫格可直接转成工单队列：高难_高流失进热修、中难_高流失观察一个版本、高难_低流失标为优秀设计进案例库。联动动作上，对卡点关可触发动态难度（连败后怪物数值微降）、推送友情助战与道具礼包；对高流失关可加"跳过券"做体验兜底。口径延展上，可按用户分层（免费/微氪/大R）分别出热力矩阵——同一关对付费玩家是付费点、对免费玩家是劝退点，分开看才能定 monetization 与难度权衡。

| 92005 | u2005 | 2026-09-24 22:00:00 | 328.00 | 退款 |

### 3. 解题思路

核心是"回流日"的机器可算定义：用户当天登录、且其前一次登录距今超过30天，该天即回流日；活动窗口内每人取最早回流日，避免一段沉睡期内多次登录重复计数。锚定回流日后，cohort方法复用：7日再留存 = 回流后1~7日内是否再登录（对login做限定区间的条件聚合），回流付费率 = 回流日后有无成功订单，回流前价值 = 活动窗口前的历史累计充值分档。实现路径给两条：LAG法（登录序列开窗取prev_date算间隔）与反连接法（NOT EXISTS判定"前30天无登录"），两法机制不同、结果应一致，可互为对账。**【避坑指南】** 全新用户首登没有"前一次登录"，必须显式排除，否则版本期的新增用户会混进回流口径，把再留存数据冲得虚高。

### 4. 参考解法

**解法一：LAG判定回流点 + cohort再锚定（主推）**

```sql
-- 解法一：登录序列LAG找回流日，再以回流日为锚算指标（@act_start/@act_end 为活动窗口）
WITH login_seq AS (                                   -- ① 登录序列：取与上次登录的间隔
    SELECT user_id, login_date,
          LAG(login_date) OVER (PARTITION BY user_id ORDER BY login_date) AS prev_date
    FROM login
),
rejoin AS (                                           -- ② 回流定义：间隔>30天的回归首日
    SELECT user_id, login_date AS rejoin_date
    FROM login_seq
    WHERE prev_date IS NOT NULL                       -- 排除全新用户首登
      AND DATEDIFF(login_date, prev_date) > 30
),
first_rejoin AS (                                     -- ③ 活动窗口内首次回流，一人一行
    SELECT user_id, MIN(rejoin_date) AS rejoin_date
    FROM rejoin
    WHERE rejoin_date BETWEEN @act_start AND @act_end
    GROUP BY user_id
),
pre_paid AS (                                         -- ④ 回流前历史累计充值（衡量沉睡前价值）
    SELECT o.user_id,
          SUM(CASE WHEN o.status = '成功' THEN o.amount ELSE 0 END) AS pre_amt
    FROM orders o
    WHERE o.order_time < @act_start
    GROUP BY o.user_id
),
rejoin_stat AS (                                      -- ⑤ 回流后7日再留存 + 渠道 + 付费标记
    SELECT f.user_id, f.rejoin_date,
          COALESCE(cb.callback_channel, '自然回流')   AS ch,
          MAX(CASE WHEN l.login_date > f.rejoin_date
                    AND l.login_date <= f.rejoin_date + INTERVAL 7 DAY
                  THEN 1 ELSE 0 END)                  AS retain7,
          MAX(CASE WHEN o.status = '成功'
                    AND o.order_time > f.rejoin_date THEN 1 ELSE 0 END) AS paid_after
    FROM first_rejoin f
    LEFT JOIN login l
      ON l.user_id = f.user_id
      AND l.login_date > f.rejoin_date
      AND l.login_date <= f.rejoin_date + INTERVAL 7 DAY       -- join即限定7日窗，避免全历史join
    LEFT JOIN orders o
      ON o.user_id = f.user_id
      AND o.order_time > f.rejoin_date
      AND o.status = '成功'
    LEFT JOIN callback cb
      ON cb.user_id = f.user_id AND cb.callback_date = f.rejoin_date
    GROUP BY f.user_id, f.rejoin_date, cb.callback_channel
)
SELECT r.ch,                                          -- 召回渠道
      COUNT(*)                                        AS rejoin_uv,
      ROUND(AVG(r.retain7), 4)                        AS retain7_rate,   -- 7日再留存
      ROUND(AVG(r.paid_after), 4)                     AS pay_rate,       -- 回流后付费率
      ROUND(AVG(CASE WHEN p.pre_amt >= 1000 THEN 1.0 ELSE 0 END), 4) AS whale_share, -- 沉睡大R占比
      ROUND(AVG(COALESCE(p.pre_amt, 0)), 1)           AS avg_pre_amt     -- 回流前人均充值
FROM rejoin_stat r
LEFT JOIN pre_paid p ON p.user_id = r.user_id
GROUP BY r.ch
ORDER BY rejoin_uv DESC;
```

结果解读：若广告渠道 `rejoin_uv=8200、retain7=22%、whale_share=31%`，推送渠道 `whale_share=6%`，则召回预算应向广告倾斜，推送改为"高价值沉默用户"精细化人群包。

**解法二：反连接NOT EXISTS判定回流（无窗口写法，机制不同）**

```sql
-- 解法二：对每个登录日做“前30天无登录”反连接判定，天然排除新用户
WITH rejoin AS (                                      -- ① 回流日 = 当天登录 且 前30天无登录 且 历史有登录
    SELECT b.user_id, b.login_date AS rejoin_date
    FROM login b
    WHERE b.login_date BETWEEN @act_start AND @act_end
      AND NOT EXISTS (                                -- 回流日前30天内没有登录
          SELECT 1 FROM login a
          WHERE a.user_id = b.user_id
            AND a.login_date <  b.login_date
            AND a.login_date >= b.login_date - INTERVAL 30 DAY
      )
      AND EXISTS (                                    -- 且历史确实登录过（排除首登）
          SELECT 1 FROM login a0
          WHERE a0.user_id = b.user_id AND a0.login_date < b.login_date
      )
),
first_rejoin AS (                                     -- ② 窗口内首次回流
    SELECT user_id, MIN(rejoin_date) AS rejoin_date
    FROM rejoin
    GROUP BY user_id
),
rejoin_stat AS (                                      -- ③ 指标计算与解法一⑤同口径
    SELECT f.user_id, f.rejoin_date,
          COALESCE(cb.callback_channel, '自然回流') AS ch,
          MAX(CASE WHEN l.login_date > f.rejoin_date
                    AND l.login_date <= f.rejoin_date + INTERVAL 7 DAY
                  THEN 1 ELSE 0 END) AS retain7,
          MAX(CASE WHEN o.status = '成功' AND o.order_time > f.rejoin_date
                  THEN 1 ELSE 0 END) AS paid_after
    FROM first_rejoin f
    LEFT JOIN login l ON l.user_id = f.user_id
        AND l.login_date > f.rejoin_date
        AND l.login_date <= f.rejoin_date + INTERVAL 7 DAY
    LEFT JOIN orders o ON o.user_id = f.user_id
        AND o.order_time > f.rejoin_date AND o.status = '成功'
    LEFT JOIN callback cb ON cb.user_id = f.user_id AND cb.callback_date = f.rejoin_date
    GROUP BY f.user_id, f.rejoin_date, cb.callback_channel
)
SELECT ch,
      COUNT(*)                 AS rejoin_uv,
      ROUND(AVG(retain7), 4)   AS retain7_rate,
      ROUND(AVG(paid_after), 4) AS pay_rate
FROM rejoin_stat
GROUP BY ch;
```

结果解读：反连接写法逐日判断"前30天空窗"，语义与业务定义原文一一对应，不依赖窗口排序，适合在MySQL 5.7或Hive老引擎落地；两法输出应逐行一致，可作为口径对账。

> Hive/Spark SQL 差异：login 全历史大表按 `dt` 分区后，反连接子查询需限定 `login_date <= @act_end` 的分区；Hive 支持 LAG 但全表开窗代价高，建议先 `GROUP BY user_id` 圈出"活动期活跃用户"小集合再回溯开窗；Spark 下 first_rejoin CTE 可 cache，供多指标复用。

### 5. 性能分析与优化

解法一的主要代价是对全量login按user_id分区开窗，先用 `login_date >= @act_start - 400 DAY` 做分区裁剪（30天阈值加合理回溯上限）可大幅降量；所有join都限定了日期区间，避免"一人全历史"的join膨胀；`(user_id, login_date)` 复合索引是两法共同前提，反连接的NOT EXISTS依赖它做index lookup。解法二逐行探测子查询，行数=活动期登录天数，在索引健全时可接受。工程化建议：把"用户回流日表"沉淀为活动期每日更新的dws表，再留存、付费归因、渠道归因全部基于它做轻量join；callback 归因表小表可broadcast。**【加分点】** 能主动提出"多次回流"的口径选择（活动归因取首次、行为研究取每次）并说明理由。

### 6. 面试延伸考点

- **回流30天阈值怎么定，有没有数据驱动的方法？**
  回答要点：看登录间隔分布的天然断裂带（如7天、30天处出现双峰），或用"间隔超过X天后回访概率趋近于0"的生存曲线拐点定阈值；阈值一旦变更，回流口径全变，需在指标文档固化并全量重刷历史。
- **回流再留存能和新增留存直接比大小吗？**
  回答要点：不能直接比——回流用户自带产品认知，通常再留存显著高于新用户；更有信息量的是纵向对比（回流再留存 vs 其回流前的历史留存）或按沉睡时长分层内部对比。
- **怎么剔除“本来就要回来”的自然回流？**
  回答要点：用活动前的自然回流率做同期基线，或用未触达用户做对照估算净增量；多渠道触达时要按"窗口内最后一次触达"归因，避免重复计功。
- **回流用户首日行为里最该盯什么？**
  回答要点：版本新内容触达率（有没有进新玩法）、资产恢复体验（装备/进度是否还在）、回归任务完成率；这些决定回流是"看一眼就走"还是"重新入坑"。

### 7. 业务拓展思考

回流分析的产出不止复盘报告，它同时是召回人群包的构建器："沉睡60天+历史大R+曾卡在主线X关"这类SQL条件直接生成下一轮推送名单。联动动作上，回流后3日是黄金干预期，可排"回归任务链+限时卡池+老友公会召回"组合承接；对召回后7日内又流失的用户要下钻卡点（版本口味不符、账号资产缩水、社交关系解体）。口径延展上，可定义"回流质量分"=再留存×付费率的加权替代单一回流人数KPI，防止运营为冲召回量把沉默用户无差别拉回领奖励。

## GAME-37 内购ARPU与广告eCPM混合变现拆解

### 1. 业务背景

超休闲转混合变现的产品开月度商业复盘会，商业化负责人要把当月总收入拆成两条线：内购线（充值流水）与广告线（激励视频/插屏/Banner的展示收益），并回答一个敏感问题：激励视频点位放量之后，"看广告的白嫖党"与"内购付费党"的人群结构有没有变化——广告收入是在做增量，还是在挤压内购？分析按四象限人群展开：纯内购党、纯广告党、混合党、零贡献党，分别统计人数占比、人均内购ARPU、人均广告ARPU与合计ARPU。结论直接决定广告位密度策略：如果混合党的内购ARPU明显低于纯内购党、且广告收益补不齐差额，就要收敛插屏点位、把激励视频改为玩家主动触发的奖励型设计。

### 3. 解题思路

### 4. 参考解法

**解法一：活跃底表 + 两次LEFT JOIN + 四象限条件聚合（主推）**

```sql
-- 解法一：底表驱动，天然覆盖零贡献党（@m_start/@m_end 为统计月首末日）
WITH active AS (                                      -- ① 底表：统计期活跃用户
    SELECT DISTINCT user_id
    FROM login
    WHERE login_date BETWEEN @m_start AND @m_end
),
iap AS (                                              -- ② 每人内购净收入（扣退款）
    SELECT user_id, SUM(amount) AS iap_amt
    FROM orders
    WHERE status = '成功'
      AND order_time >= @m_start AND order_time < @m_end + INTERVAL 1 DAY
    GROUP BY user_id
),
ads AS (                                              -- ③ 每人广告收益 = Σ(ecpm)/1000
    SELECT user_id, SUM(ecpm) / 1000 AS ad_amt
    FROM ad_watch
    WHERE watch_time >= @m_start AND watch_time < @m_end + INTERVAL 1 DAY
    GROUP BY user_id
),
seg AS (                                              -- ④ 挂上收入，打四象限标签
    SELECT a.user_id,
          COALESCE(i.iap_amt, 0) AS iap_amt,
          COALESCE(d.ad_amt, 0)  AS ad_amt,
          CASE WHEN COALESCE(i.iap_amt,0) > 0 AND COALESCE(d.ad_amt,0) > 0 THEN '混合党'
               WHEN COALESCE(i.iap_amt,0) > 0                              THEN '纯内购党'
               WHEN COALESCE(d.ad_amt,0)  > 0                              THEN '纯广告党'
               ELSE '零贡献党' END AS user_seg
    FROM active a
    LEFT JOIN iap i ON i.user_id = a.user_id
    LEFT JOIN ads d ON d.user_id = a.user_id
)
SELECT user_seg,
      COUNT(*)                                          AS uv,
      ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4)        AS uv_pct,      -- 窗口总计做分母算人群占比
      ROUND(SUM(iap_amt) / COUNT(*), 2)                 AS iap_arpu,    -- 人均内购贡献
      ROUND(SUM(ad_amt)  / COUNT(*), 2)                 AS ad_arpu,     -- 人均广告贡献
      ROUND((SUM(iap_amt) + SUM(ad_amt)) / COUNT(*), 2) AS total_arpu   -- 合并人均
FROM seg
GROUP BY user_seg
ORDER BY total_arpu DESC;
```

结果解读：若 `纯内购党 total_arpu=86、混合党=52、纯广告党=1.8` 且混合党规模连续两月扩大，就要做挤出验证——对比混合党"成为混合党前后"的内购ARPU变化。

**解法二：UNION ALL统一流水 + 一趟条件聚合（少一次大join）**

```sql
-- 解法二：两条变现流水纵向合并，一次GROUP BY用户完成聚合（注意零贡献党缺失）
WITH flow AS (                                        -- ① 结构对齐后UNION ALL，打流量类型标记
    SELECT user_id, '内购' AS flow_type, amount AS rev
    FROM orders
    WHERE status = '成功'
      AND order_time >= @m_start AND order_time < @m_end + INTERVAL 1 DAY
    UNION ALL
    SELECT user_id, '广告' AS flow_type, ecpm / 1000 AS rev
    FROM ad_watch
    WHERE watch_time >= @m_start AND watch_time < @m_end + INTERVAL 1 DAY
),
seg AS (                                              -- ② 一趟条件聚合同时算两种收入
    SELECT user_id,
          SUM(CASE WHEN flow_type = '内购' THEN rev ELSE 0 END) AS iap_amt,
          SUM(CASE WHEN flow_type = '广告' THEN rev ELSE 0 END) AS ad_amt
    FROM flow
    GROUP BY user_id
),
active AS (                                           -- ③ 活跃底表补齐分母
    SELECT DISTINCT user_id FROM login
    WHERE login_date BETWEEN @m_start AND @m_end
)
SELECT CASE WHEN s.iap_amt > 0 AND s.ad_amt > 0 THEN '混合党'
            WHEN s.iap_amt > 0              THEN '纯内购党'
            WHEN s.ad_amt  > 0              THEN '纯广告党'
            ELSE '零贡献党' END AS user_seg,
      COUNT(*)                                        AS uv,
      ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4)      AS uv_pct,
      ROUND(AVG(COALESCE(s.iap_amt, 0)), 2)           AS iap_arpu,
      ROUND(AVG(COALESCE(s.ad_amt, 0)), 2)            AS ad_arpu,
      ROUND(AVG(COALESCE(s.iap_amt,0) + COALESCE(s.ad_amt,0)), 2) AS total_arpu
FROM active a
LEFT JOIN seg s ON s.user_id = a.user_id
GROUP BY 1
ORDER BY total_arpu DESC;
```

结果解读：解法二对大流水表更友好（UNION ALL是纯并行窄操作），通过LEFT JOIN活跃底表把零贡献党补回分母，口径与解法一一致；面试中讲清"为什么必须补底表"即是亮点。

> Hive/Spark SQL 差异：Hive 支持 FULL OUTER JOIN，可用 `FULL JOIN + COALESCE(user_id)` 一次对齐两表；广告流水日增上亿行，ad_watch 按 `dt` 分区并预聚合 `(user_id, dt, ad_type, revenue)`，月度复盘只扫30个分区；Spark 中 UNION ALL 上下半区并行执行，通常比两次join更快。

### 5. 性能分析与优化

解法一的两次join都发生在"每人一行"的中间结果上，代价可控，大头是两条流水的全量聚合；解法二把两次聚合换成一次UNION ALL聚合加一次底表LEFT JOIN，大流水场景通常更快。优化建议：orders、ad_watch 均按 `dt` 分区并限定月窗口；ad_watch 建 `(user_id, watch_time)` 复合索引；把"用户月度双线收入表"沉淀为调度表，四象限拆解、环比趋势、挤出分析都基于它；Spark 下 active/iap/ads 小结果集用 broadcast join。**【避坑指南】** eCPM换算（÷1000）必须在明细层完成，若在日聚合后再除会把"千次收益"与"单次收益"口径混淆，系统性差一千倍——这是混合变现题最经典的数值翻车点。

### 6. 面试延伸考点

- **怎么验证“广告挤压内购”而不只是相关？**
  回答要点：个体内DID（同一用户成为混合党前后的内购ARPU对比）、广告点位灰度上线的实验组/对照组对比、控制版本内容差异；相关性（人群占比此消彼长）不等于挤压。
- **广告收入归因到用户时，eCPM用展示时点还是日均价？**
  回答要点：展示时点更精细但波动大且可能缺值，日均价稳定便于对账；两口径差异通常不大，但报表必须二选一固化，否则月度环比漂移。
- **ARPU、ARPPU、付费率的关系怎么用SQL自检？**
  回答要点：ARPU=ARPPU×付费率，同一条聚合SQL同时输出三者即可验证；所有指标分母统一为活跃用户口径，避免付费率用新增、ARPU用活跃的错配。
- **零贡献党为什么必须出现在商业报表里？**
  回答要点：它是广告变现场景下的"待激活资产"，其占比与转化趋势比绝对人数更重要；隐去它会让广告放量决策过度乐观。

### 7. 业务拓展思考

四象限拆解是广告位密度决策的仪表盘：纯广告党占比升且混合党内购ARPU下滑，就收敛插屏、把激励视频改成"纯奖励型"（玩家主动看换道具）；广告线健康则可继续放量并优化填充率。联动动作上，对零贡献党做"首充礼包+激励视频引导"组合干预，对纯广告党做轻度首充转化实验，对混合党控制广告频次上限保护付费体验。口径延展上，广告LTV按广告类型拆分（激励视频eCPM最高且最不伤体验），内购LTV按商品类型拆分（直充/礼包/月卡/战令），输出"变现组合"视角的优化路线图。

## GAME-38 新手7日任务完成度与长留分组对比

### 1. 业务背景

新手体验负责人要回答一个资源分配问题：完成7日新手任务不同进度的用户，30日留存与30日付费率差距有多大？如果"完成6~7个任务"的用户30日留存是"完成0~2个"的三倍以上，就要决定资源投向"任务提醒推送"（拉完成率）还是"任务奖励加码"（拉完成动机），并把全勤奖励、断点召回排进新手期运营日程。**【面试高频】** 这题的隐藏考点是幸存者偏差：任务完成度与留存互为因果——留下来的玩家自然做得多，SQL能算出相关性，但下业务结论必须声明因果方向；能主动提出"用注册后前3日完成度做先行指标"或"匹配同活跃水平用户再比"的候选人，会被面试官高看一眼。

### 3. 解题思路

三个口径先钉死：完成度只统计"注册后7日内完成"的任务数，防止玩家一个月后回来补做污染分组；分组边界用业务语义（0~2个=浅参与、3~5个=中参与、6~7个=全勤倾向）而非数据分位，保证跨月可比；30日留存定义为"注册日+30天当天是否登录"，30日付费率定义为"注册后30日内是否有成功充值"。实现路径：先建注册cohort表（每人首登日），再聚合每人7日内完成数并分组，最后算组级指标——解法一"指标下沉到用户"：每用户先算0/1标记再按组AVG，扩展性好；解法二"join聚合一次到底"：分组表直接join登录与订单明细，GROUP BY里用COUNT(DISTINCT CASE WHEN)同时出分子分母，链路最短。**【避坑指南】** 零完成用户在tasks表可能没有完成记录，分母必须来自注册cohort而不是任务表，否则低完成组被系统性漏掉。

### 4. 参考解法

**解法一：指标下沉到用户粒度再分组聚合（可扩展性强）**

```sql
-- 解法一：每用户先算好0/1指标，分组后直接AVG，语义最清晰
WITH usr AS (                                         -- ① 注册cohort：每人首登日
    SELECT user_id, MIN(login_date) AS reg_date
    FROM login
    GROUP BY user_id
),
task7 AS (                                            -- ② 严格限定“注册后7日内”完成的任务数
    SELECT t.user_id,
          COUNT(DISTINCT CASE WHEN t.is_finish = 1
                              AND DATE(t.finish_time) < u.reg_date + INTERVAL 7 DAY
                              THEN t.task_id END) AS done_cnt
    FROM tasks t
    JOIN usr u ON u.user_id = t.user_id
    GROUP BY t.user_id
),
grp AS (                                              -- ③ 完成度分3组（业务阈值，跨月可比）
    SELECT user_id,
          CASE WHEN done_cnt <= 2 THEN 'A_完成0-2个'
               WHEN done_cnt <= 5 THEN 'B_完成3-5个'
               ELSE 'C_完成6-7个' END AS done_grp
    FROM task7
),
r30 AS (                                              -- ④ 30日留存标记：注册+30天当天登录
    SELECT u.user_id,
          MAX(CASE WHEN l.login_date = u.reg_date + INTERVAL 30 DAY
                  THEN 1 ELSE 0 END) AS r30_flag
    FROM usr u
    JOIN login l ON l.user_id = u.user_id
    GROUP BY u.user_id
),
pay30 AS (                                            -- ⑤ 30日内付费标记
    SELECT DISTINCT o.user_id
    FROM orders o
    JOIN usr u ON u.user_id = o.user_id
    WHERE o.status = '成功'
      AND o.order_time < u.reg_date + INTERVAL 30 DAY
)
SELECT g.done_grp,
      COUNT(*)                                        AS uv,
      ROUND(AVG(COALESCE(r.r30_flag, 0)), 4)          AS retain30_rate,  -- 30日留存
      ROUND(AVG(CASE WHEN p.user_id IS NOT NULL THEN 1.0 ELSE 0 END), 4) AS pay30_rate, -- 30日付费率
      COUNT(*) / SUM(COUNT(*)) OVER ()                AS grp_share       -- 各组人数占比
FROM grp g
LEFT JOIN r30 r   ON r.user_id = g.user_id
LEFT JOIN pay30 p ON p.user_id = g.user_id
GROUP BY g.done_grp
ORDER BY g.done_grp;
```

结果解读：若输出 `A组留存8.1%/付费2.3%、C组留存41%/付费17%`，相关性强，但结论要谨慎表述——先看各组"注册前3日活跃天数"是否本就不同，必要时在同活跃分层内再比一次。

**解法二：join聚合一次性到底（无中间0/1表，链路最短）**

```sql
-- 解法二：分组表直接join明细，GROUP BY里同时出分子分母，笔试限时首选
WITH usr AS (                                         -- 注册cohort
    SELECT user_id, MIN(login_date) AS reg_date
    FROM login GROUP BY user_id
),
task7 AS (                                            -- 7日内完成数（口径同解法一②）
    SELECT t.user_id,
          COUNT(DISTINCT CASE WHEN t.is_finish = 1
                              AND DATE(t.finish_time) < u.reg_date + INTERVAL 7 DAY
                              THEN t.task_id END) AS done_cnt
    FROM tasks t JOIN usr u ON u.user_id = t.user_id
    GROUP BY t.user_id
),
grp AS (
    SELECT user_id,
          CASE WHEN done_cnt <= 2 THEN 'A_完成0-2个'
               WHEN done_cnt <= 5 THEN 'B_完成3-5个'
               ELSE 'C_完成6-7个' END AS done_grp
    FROM task7
)
SELECT g.done_grp,
      COUNT(DISTINCT g.user_id)                                          AS uv,
      COUNT(DISTINCT CASE WHEN l.login_date = u.reg_date + INTERVAL 30 DAY
                          THEN g.user_id END) / COUNT(DISTINCT g.user_id) AS retain30_rate, -- 分子分母同粒度
      COUNT(DISTINCT CASE WHEN o.user_id IS NOT NULL
                          THEN g.user_id END) / COUNT(DISTINCT g.user_id) AS pay30_rate
FROM grp g
JOIN usr u       ON u.user_id = g.user_id
LEFT JOIN login l ON l.user_id = g.user_id
        AND l.login_date BETWEEN u.reg_date AND u.reg_date + INTERVAL 30 DAY  -- join限定30日窗，防膨胀
LEFT JOIN (SELECT DISTINCT o.user_id                          -- 30日内成功充值用户
           FROM orders o JOIN usr u2 ON u2.user_id = o.user_id
           WHERE o.status = '成功'
             AND o.order_time < u2.reg_date + INTERVAL 30 DAY) o
  ON o.user_id = g.user_id
GROUP BY g.done_grp
ORDER BY g.done_grp;
```

结果解读：解法二把所有逻辑压进一层聚合，中间结果少、跑得快，是限时笔试的高效写法；缺点是再加指标（如7日留存）就要继续堆CASE，调试与复用不如解法一的分层CTE，面试可主动讲两种取舍。

> Hive/Spark SQL 差异：Hive 下带 COUNT(DISTINCT) 的多分组聚合可能退化为单 reducer，大表建议改"先按用户聚合标记、再AVG"的两段式（解法一结构）；login/orders 按注册月分区裁剪；usr、task7 中间结果在 Spark 中 cache 后供多指标复用。

### 5. 性能分析与优化

两解法的大头都是 tasks×usr 与 login 的join：任务表每人仅7行，量可控；login明细join必须加30日区间条件（解法二已内置），把join限制在每人≤31行。优化建议：`(user_id, login_date)`、`(user_id, task_day)` 复合索引；订单子查询已限定30日窗并先DISTINCT压缩；月度复盘场景把 grp 表物化为"新手完成度宽表"，后续所有"完成度×X"分析从它出发；分组阈值若要数据驱动，在物化层加版本号管理口径变更，避免历史报表漂移。**【加分点】** 能提出"完成度应配合完成时滞与断点位置一起看"——第几个任务流失最多，比总完成数更能指导改版。

### 6. 面试延伸考点

- **这个相关性怎么排除幸存者偏差？**
  回答要点：三层递进——用前3日完成度（更外生）替代7日完成度；按注册后3日活跃天数分层、在同层内比较；最终用A/B实验（随机发放任务提醒/加码奖励）验证因果，SQL只负责建立假设。
- **30日留存定义成“第30日当天活跃”还是“第22~30日间活跃”？**
  回答要点：前者严格但受单日波动影响，后者稳健但偏宽松；行业默认当天口径，改定义必须全量重算并留档，不能新旧混用。
- **分组边界为什么不用NTILE自动分箱？**
  回答要点：业务沟通需要稳定语义（"完成6-7个"），NTILE边界每月漂移导致跨月不可比；探索期可用NTILE辅助定阈值，正式口径用业务阈值。
- **任务完成度之外还该看什么新手期指标？**
  回答要点：完成顺序与断点、当天完成率（时滞）、关键行为（首次组队/首次抽卡）完成结构；这些都能从tasks表加窗口函数扩展，构成新手期行为画像。

### 7. 业务拓展思考

这题的产出物是"新手期关键行为清单"的雏形：找到与长留相关性最强且相对可控的行为（如"第2日完成首次组队"），立为北极星子指标，驱动三条线——策划改任务链设计、运营对断点用户推送召回、客服对高危用户人工干预。口径延展上，可把"任务完成度"换成任意候选行为（抽卡次数、加入公会、通过第X关）复用同一套分组对比框架，批量筛选aha moment；再把这些行为特征喂给流失预测模型，SQL产出即特征宽表，形成分析到模型的通路。

## GAME-39 公会社交绑定与留存交叉分析

### 1. 业务背景

社交系统策划在评估公会功能价值，为下个版本的资源分配提供依据：加入公会到底能不能提升留存？如果"活跃玩家才入会"的自选择假象成立，公会系统就不值这么多开发资源。分析要求三层递进：第一层，入会用户以首次入会日为锚的7日/30日留存；第二层，把公会按规模分箱（大/中/小），回答"什么样的公会最留人"，指导公会撮合算法与扶持资源分配；第三层，做一个更可信的个体内对比——同一用户"入会前的日活跃率"与"入会后的日活跃率"差值，削弱自选择偏差。结论将决定要不要强化公会任务、公会匹配是否按活跃度分层撮合、公会激励预算发给谁。

### 2. 表结构说明

**表1：guild_member 公会成员表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| guild_id | VARCHAR(16) | 公会ID |
| join_date | DATE | 入会日期 |
| quit_date | DATE | 退会日期（在会为NULL） |

示例数据：

| user_id | guild_id | join_date | quit_date |
|---|---|---|---|
| s5001 | G001 | 2026-08-02 | NULL |
| s5002 | G001 | 2026-08-03 | 2026-09-01 |
| s5002 | G002 | 2026-09-05 | NULL |
| s5003 | G003 | 2026-08-10 | NULL |
| s5004 | G003 | 2026-08-11 | 2026-08-20 |

**表2：login 登录流水表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| login_date | DATE | 登录日期 |

示例数据：

| user_id | login_date |
|---|---|
| s5001 | 2026-08-01 |
| s5001 | 2026-08-09 |
| s5001 | 2026-09-01 |
| s5002 | 2026-08-01 |
| s5003 | 2026-08-09 |

### 3. 解题思路

先处理两个口径：重复入会取"首次入会"做锚（ROW_NUMBER按join_date升序取第一条），退会为NULL视为在会至今（COALESCE兜到统计截止日）；公会规模用"历史累计入会人数"这个稳定口径。实现路径：解法一做"组间对比+规模分箱"——首次入会表join登录表算入会后7/30日留存标记，公会规模NTILE三分箱，输出"规模×留存"对比；解法二做"个体内对比"——对每个首次入会用户分别计算入会前（注册日至入会日前）与入会后（入会日至统计日）的日活跃率，输出活跃率提升量，并按"注册7日内即入会/7日后入会"分层控制混杂。**【加分点】** 能说明个体内对比仍不等于因果（入会时点可能与版本活动重合），并给出"叠加同期未入会用户的活跃率变化做双重差分"的升级方案。

### 4. 参考解法

**解法一：首次入会cohort + 公会规模分箱交叉（组间对比）**

```sql
-- 解法一：argmax取首次入会，规模分箱看“什么公会留人”（@stat_date 为统计截止日）
WITH ranked AS (                                      -- ① 每用户入会记录排序，取最早一次
    SELECT user_id, guild_id, join_date, quit_date,
          ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY join_date) AS rn
    FROM guild_member
),
join_first AS (                                       -- ② 首次入会锚点 + 在会区间终点
    SELECT user_id, guild_id, join_date AS j_date,
          COALESCE(quit_date, @stat_date) AS span_end   -- 退会空值兜底到统计日
    FROM ranked
    WHERE rn = 1
),
g_size AS (                                           -- ③ 公会规模：历史累计入会人数
    SELECT guild_id, COUNT(DISTINCT user_id) AS member_cnt
    FROM guild_member
    GROUP BY guild_id
),
g_bin AS (                                            -- ④ 规模三分箱（NTILE数据驱动）
    SELECT guild_id, member_cnt,
          CASE WHEN NTILE(3) OVER (ORDER BY member_cnt) = 1 THEN '小公会'
               WHEN NTILE(3) OVER (ORDER BY member_cnt) = 2 THEN '中公会'
               ELSE '大公会' END AS size_tag
    FROM g_size
),
ret AS (                                              -- ⑤ 入会后7/30日留存标记
    SELECT jf.user_id, jf.guild_id,
          MAX(CASE WHEN l.login_date = jf.j_date + INTERVAL 7 DAY  THEN 1 ELSE 0 END) AS r7,
          MAX(CASE WHEN l.login_date = jf.j_date + INTERVAL 30 DAY THEN 1 ELSE 0 END) AS r30
    FROM join_first jf
    JOIN login l ON l.user_id = jf.user_id
    GROUP BY jf.user_id, jf.guild_id
)
SELECT b.size_tag,
      COUNT(*)                                        AS uv,
      ROUND(AVG(r.r7), 4)                             AS retain7_rate,
      ROUND(AVG(r.r30), 4)                            AS retain30_rate,
      ROUND(AVG(b.member_cnt), 0)                     AS avg_member_cnt,
      ROUND(AVG(TIMESTAMPDIFF(DAY, jf.j_date, jf.span_end)), 1) AS avg_in_guild_days -- 平均在会天数
FROM ret r
JOIN join_first jf ON jf.user_id = r.user_id
JOIN g_bin b       ON b.guild_id = r.guild_id
GROUP BY b.size_tag
ORDER BY avg_member_cnt;
```

结果解读：若 `中公会 retain30=34%、大公会=29%、小公会=22%`，说明中等规模、关系密度高的公会最留人，撮合算法不必一味把新人塞进大公会。

**解法二：个体内对比——入会前活跃率 vs 入会后活跃率（削弱自选择）**

```sql
-- 解法二：同一用户前后两段活跃率配对比较，输出“入会提升量”
WITH join_first AS (                                  -- ① 首次入会（精简版）
    SELECT user_id, join_date AS j_date,
          COALESCE(quit_date, @stat_date) AS span_end
    FROM (SELECT user_id, join_date, quit_date,
                ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY join_date) AS rn
          FROM guild_member) t
    WHERE rn = 1
),
usr AS (                                              -- ② 注册日
    SELECT user_id, MIN(login_date) AS reg_date
    FROM login GROUP BY user_id
),
usr_span AS (                                         -- ③ 每用户：入会前/后 天数与活跃天数
    SELECT s.user_id,
          TIMESTAMPDIFF(DAY, u.reg_date, s.j_date)                     AS pre_days,  -- 入会前天数
          TIMESTAMPDIFF(DAY, s.j_date, s.span_end) + 1                 AS in_days,   -- 入会后台账天数
          SUM(CASE WHEN l.login_date <  s.j_date THEN 1 ELSE 0 END)    AS pre_active,  -- 入会前活跃天数
          SUM(CASE WHEN l.login_date BETWEEN s.j_date AND s.span_end
                  THEN 1 ELSE 0 END)                                   AS in_active   -- 入会后活跃天数
    FROM join_first s
    JOIN usr u ON u.user_id = s.user_id
    LEFT JOIN login l
      ON l.user_id = s.user_id
      AND l.login_date <= s.span_end                    -- join裁剪：只要入会前后的登录
    GROUP BY s.user_id, s.j_date, s.span_end, u.reg_date
)
SELECT CASE WHEN TIMESTAMPDIFF(DAY, reg_date, j_date) <= 7 THEN '注册7日内即入会'
            ELSE '注册7日后入会' END AS join_timing,    -- 入会早晚分层，控制老玩家混杂
      COUNT(*)                                            AS uv,
      ROUND(AVG(pre_active / NULLIF(pre_days, 0)), 4)     AS pre_act_rate, -- 入会前日活跃率
      ROUND(AVG(in_active / NULLIF(in_days, 0)), 4)       AS in_act_rate,  -- 入会后日活跃率
      ROUND(AVG(in_active / NULLIF(in_days, 0))
          - AVG(pre_active / NULLIF(pre_days, 0)), 4)     AS act_lift      -- 活跃率提升量
FROM usr_span
WHERE pre_days >= 1                                   -- 至少1天入会前数据才可比
GROUP BY 1;
```

结果解读：若 `act_lift=+0.21`（日活跃率从0.28升到0.49）且"注册7日内即入会"组提升更大，说明公会绑定在生命周期早期作用显著，应把公会引导前移到新手第3~5日。

> Hive/Spark SQL 差异：区间条件（BETWEEN）join 在大表上会膨胀，Hive/Spark 下先把 login 聚合为"用户×活跃天数"再拼接，或用 Spark 的范围join优化提示；TIMESTAMPDIFF 在 Hive 中用 `datediff` 替换；usr_span 的LEFT JOIN务必限定 `login_date <= span_end` 裁剪分区。

### 5. 性能分析与优化

解法一的ret步骤是 login×join_first 的join加聚合，量级=入会用户×其登录天数，应加"锚点后31天内"的日期区间条件把join压到每人≤31行；规模分箱发生在公会粒度（通常几千行）的NTILE，代价忽略。解法二最重的是usr_span对login的聚合join，务必在LEFT JOIN加 `l.login_date <= span_end` 条件，或预聚合"入会前活跃天数/入会后活跃天数"两张小表再拼。索引上 `(user_id, login_date)`、`(user_id, join_date)` 复合索引必备；公会粒度聚合表可broadcast。**【避坑指南】** 公会解散表现为大量quit_date同日，个体内对比会把"解散导致的活跃下滑"算到公会价值头上，需剔除解散公会成员或单独标注后再算提升量。

### 6. 面试延伸考点

- **“活跃玩家才入会”的自选择偏差，个体内对比能完全解决吗？**
  回答要点：不能完全——入会时点常伴随版本活动或好友邀请，本身是内生事件；升级方案是双重差分（同期未入会用户活跃率变化做基线）或按活跃水平匹配（PSM思想），定因果最终靠A/B（随机开放公会资格）。
- **为什么取“首次入会”而不是“当前是否在会”？**
  回答要点：首次入会是明确时点事件，可做cohort锚定与前后对比；"当前在会"是状态不是事件，锚点模糊导致留存口径不可复现。
- **公会留人靠规模还是活跃密度？**
  回答要点：规模只是代理变量，真正起作用的是好友数、组队次数等互动密度；应补公会日活跃人数、人均互动指标做分箱，规模结论需经密度变量检验。
- **退会用户怎么处理最严谨？**
  回答要点：退会日之后归入"未在会期"，并做反向验证——对比退会前后活跃率，若退会后活跃显著下滑，可进一步佐证公会贡献，同时要排除"因流失而退会"的反向因果。

### 7. 业务拓展思考

公会价值量化直接决定社交模块的资源优先级：若个体内提升显著，应推动公会任务、公会副本等绑定玩法加码，并把公会引导嵌入新手期；反之则要反思公会玩法是否只服务了少数头部公会。运营联动上，用"规模×活跃密度"给公会分级，对中腰部高活公会发扶持资源（专属活动、礼包），对僵尸公会做合服或清退。口径延展上，可把"公会"替换为师徒、好友、婚姻等任意社交关系复用同一框架，输出"社交深度—留存弹性"曲线，为整个社交系统的ROI排序提供依据。

## GAME-40 大R流失预警（付费频次+在线时长下滑双信号）

### 1. 业务背景

VIP运营团队每周一跑批"大R流失预警名单"：历史累计充值≥10000元的用户中，出现"付费频次下滑+在线时长下滑"双信号的标记为高危，由VIP客服24小时内一对一介入（专属礼包、电话回访）；只命中单信号的标记为中危，进观察池下周复查。为什么坚持双信号：只看付费会误伤"攒着等大版本再买"的正常节奏，只看时长会误伤"挂机搬砖党"；付费与时长同时走弱，流失概率才足够高，才值得消耗稀缺的VIP客服人力。输出名单字段：用户、本周/上周付费次数、本周/上周日均时长、命中信号与风险等级。这题是"窗口环比+多条件规则"的综合建模，也是游戏风控类SQL的典型范式。

### 2. 表结构说明

**表1：orders 充值订单表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| order_id | BIGINT | 订单号 |
| user_id | VARCHAR(32) | 用户ID |
| order_time | DATETIME | 下单时间 |
| amount | DECIMAL(10,2) | 金额（元） |
| status | VARCHAR(16) | 状态 |

示例数据：

| order_id | user_id | order_time | amount | status |
|---|---|---|---|---|
| 95001 | v6001 | 2026-10-06 21:00:00 | 648.00 | 成功 |
| 95002 | v6001 | 2026-10-08 20:30:00 | 328.00 | 成功 |
| 95003 | v6001 | 2026-10-15 22:10:00 | 6.00 | 成功 |
| 95004 | v6002 | 2026-10-07 19:00:00 | 1280.00 | 成功 |
| 95005 | v6002 | 2026-10-16 21:40:00 | 648.00 | 成功 |

**表2：user_daily 用户日行为汇总表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| stat_date | DATE | 统计日期 |
| online_minutes | INT | 当日在线分钟数 |
| pay_cnt | INT | 当日成功付费次数 |

示例数据：

| user_id | stat_date | online_minutes | pay_cnt |
|---|---|---|---|
| v6001 | 2026-10-14 | 95 | 0 |
| v6001 | 2026-10-15 | 88 | 1 |
| v6001 | 2026-10-20 | 20 | 0 |
| v6002 | 2026-10-15 | 130 | 0 |
| v6002 | 2026-10-20 | 125 | 1 |

### 3. 解题思路

口径三件套：大R=历史累计成功充值≥10000（全历史口径，物化成名单表）；本周/上周以监控日为锚取两个互不重叠的7天窗；双信号=付费频次环比降幅≥50%（且上周≥2次，防低基数误报）且日均时长环比降幅≥40%（且上周≥60分钟，防轻度用户噪声）。实现路径两条：解法一"双表窗口环比"——付费与时长各自按用户×周聚合后LAG取前值，按周对齐join，输出高危/中危分级；解法二"统一行为流水+条件聚合"——把订单与时长UNION成统一日粒度事件表，一次条件聚合同时算前后两窗，无窗口依赖，Hive与MySQL 5.7友好。**【避坑指南】** 用"周表LAG"时，用户整周未活跃会导致该周缺行，LAG取到的是更早一周、环比全部错位——必须以活跃周网格或日历网格为主架补零，这是环比类SQL最常翻车的地方。

### 4. 参考解法

**解法一：双表窗口环比 + 分级输出（主推）**

```sql
-- 解法一：付费/时长分别周聚合后LAG，按周对齐求双信号（@cur_date 为监控日）
WITH pay_wk AS (                                      -- ① 用户×周 成功付费次数
    SELECT user_id, YEARWEEK(DATE(order_time), 1) AS wk, COUNT(*) AS pay_cnt
    FROM orders
    WHERE status = '成功'
      AND DATE(order_time) >= @cur_date - INTERVAL 14 DAY
    GROUP BY user_id, YEARWEEK(DATE(order_time), 1)
),
dur_wk AS (                                           -- ② 用户×周 日均在线时长
    SELECT user_id, YEARWEEK(stat_date, 1) AS wk,
          SUM(online_minutes) / 7.0 AS avg_daily_min
    FROM user_daily
    WHERE stat_date >= @cur_date - INTERVAL 14 DAY
    GROUP BY user_id, YEARWEEK(stat_date, 1)
),
whale AS (                                            -- ③ 大R资格：历史累计成功充值≥10000
    SELECT user_id
    FROM orders
    WHERE status = '成功'
    GROUP BY user_id
    HAVING SUM(amount) >= 10000
),
act_grid AS (                                         -- ④ 活跃周网格：以出现过的(用户,周)为主架
    SELECT user_id, wk FROM pay_wk
    UNION
    SELECT user_id, wk FROM dur_wk
),
pay_cmp AS (                                          -- ⑤ 网格上补零后LAG，环比不错位
    SELECT g.user_id, g.wk,
          COALESCE(p.pay_cnt, 0) AS cur_cnt,
          LAG(COALESCE(p.pay_cnt, 0)) OVER (PARTITION BY g.user_id ORDER BY g.wk) AS prev_cnt
    FROM act_grid g
    LEFT JOIN pay_wk p ON p.user_id = g.user_id AND p.wk = g.wk
),
dur_cmp AS (                                          -- ⑥ 时长周环比
    SELECT user_id, wk, avg_daily_min,
          LAG(avg_daily_min) OVER (PARTITION BY user_id ORDER BY wk) AS prev_min
    FROM dur_wk
)
SELECT p.user_id,
      p.cur_cnt,  p.prev_cnt,
      ROUND(d.avg_daily_min, 1) AS cur_min,
      ROUND(d.prev_min, 1)      AS prev_min,
      CASE WHEN p.prev_cnt >= 2 AND p.cur_cnt <= p.prev_cnt * 0.5          -- 付费频次腰斩
            AND d.prev_min >= 60 AND d.avg_daily_min <= d.prev_min * 0.6    -- 时长下滑≥40%
          THEN '高危'
          WHEN (p.prev_cnt >= 2 AND p.cur_cnt <= p.prev_cnt * 0.5)
            OR (d.prev_min >= 60 AND d.avg_daily_min <= d.prev_min * 0.6)
          THEN '中危'
      END AS risk_level
FROM pay_cmp p
JOIN dur_cmp d ON d.user_id = p.user_id AND d.wk = p.wk
JOIN whale w   ON w.user_id = p.user_id
WHERE p.wk = YEARWEEK(@cur_date, 1);                  -- 只输出监控周的名单
```

结果解读：输出如 `v6001 本周付费1/上周3、日均时长20/88 → 高危`，进VIP客服24小时跟进队列；只掉时长的进中危观察池，下周复查是否恢复。

**解法二：统一行为流水 + 条件聚合前后两窗（无窗口，Hive/5.7友好）**

```sql
-- 解法二：订单与时长UNION成统一日粒度行为表，一次条件聚合算两个窗口
WITH act AS (                                         -- ① 统一行为事件表：付费与时长同构
    SELECT user_id, DATE(order_time) AS d, 1 AS pay_cnt, 0 AS online_min
    FROM orders
    WHERE status = '成功'
      AND DATE(order_time) >= @cur_date - INTERVAL 13 DAY
    UNION ALL
    SELECT user_id, stat_date, 0, online_minutes
    FROM user_daily
    WHERE stat_date >= @cur_date - INTERVAL 13 DAY
),
agg AS (                                              -- ② 压到用户×日
    SELECT user_id, d, SUM(pay_cnt) AS pay_cnt, SUM(online_min) AS online_min
    FROM act
    GROUP BY user_id, d
),
cmp AS (                                              -- ③ 条件聚合：本周 vs 上周
    SELECT user_id,
          SUM(CASE WHEN d >= @cur_date - INTERVAL 6 DAY
                  THEN pay_cnt ELSE 0 END)          AS cur_pay_cnt,
          SUM(CASE WHEN d <  @cur_date - INTERVAL 6 DAY
                  THEN pay_cnt ELSE 0 END)          AS prev_pay_cnt,
          SUM(CASE WHEN d >= @cur_date - INTERVAL 6 DAY
                  THEN online_min ELSE 0 END) / 7.0 AS cur_daily_min,
          SUM(CASE WHEN d <  @cur_date - INTERVAL 6 DAY
                  THEN online_min ELSE 0 END) / 7.0 AS prev_daily_min
    FROM agg
    GROUP BY user_id
),
whale AS (                                            -- ④ 大R资格（全历史，建议物化为维表）
    SELECT user_id FROM orders
    WHERE status = '成功'
    GROUP BY user_id HAVING SUM(amount) >= 10000
)
SELECT c.user_id, c.cur_pay_cnt, c.prev_pay_cnt,
      ROUND(c.cur_daily_min, 1)  AS cur_min,
      ROUND(c.prev_daily_min, 1) AS prev_min,
      CASE WHEN c.prev_pay_cnt >= 2 AND c.cur_pay_cnt <= c.prev_pay_cnt * 0.5
            AND c.prev_daily_min >= 60 AND c.cur_daily_min <= c.prev_daily_min * 0.6
          THEN '高危'
          WHEN (c.prev_pay_cnt >= 2 AND c.cur_pay_cnt <= c.prev_pay_cnt * 0.5)
            OR (c.prev_daily_min >= 60 AND c.cur_daily_min <= c.prev_daily_min * 0.6)
          THEN '中危'
      END AS risk_level
FROM cmp c
JOIN whale w ON w.user_id = c.user_id
WHERE c.cur_pay_cnt > 0 OR c.cur_daily_min > 0
   OR c.prev_pay_cnt > 0 OR c.prev_daily_min > 0;     -- 排除完全无行为的噪声行
```

结果解读：解法二把"环比"译成两个日期区间的条件求和，一条SQL无窗口依赖、调度简单；但"整周完全静默"的用户在近14天无任何行，会被WHERE滤掉，需要额外的"鲸鱼名单×活跃名单差集"兜底查询捞出——这本身就是最严重的流失信号。

> Hive/Spark SQL 差异：Hive 无 YEARWEEK，周键用 `year(stat_date)+weekofyear(stat_date)` 拼接或直接用日期区间（解法二天然规避）；user_daily 按 `stat_date` 日分区，监控只扫14个分区；whale 名单物化为维表并每周刷新，避免每次全量扫 orders；Spark 下 cmp×whale 走 broadcast join。

### 5. 性能分析与优化

解法一有两个按用户分区的窗口排序，排序代价=活跃用户数×周行数，先WHERE裁剪14天再开窗是标配；大R判定若每次全量扫orders则最贵，应把whale名单物化成周更维表。解法二一次聚合+一次join，代价结构最简单，适合高频调度。优化建议：orders `(user_id, order_time)` 复合索引并按月分区；user_daily 按 `stat_date` 日分区只扫14个分区；"用户×周付费次数/周时长"沉淀为周汇总表，预警SQL变成纯小表运算；规则增多时把阈值外置为规则表，SQL join规则表替代硬编码，运营可自助调参。**【面试高频】** "为什么阈值要配最小基数（上周≥2次付费、≥60分钟）"——低基数环比无意义，答出"防把正常波动当流失信号"即为加分。

### 6. 面试延伸考点

- **双信号阈值50%/40%怎么定才不是拍脑袋？**
  回答要点：用历史真流失大R回看其前两周信号分布，选precision/recall平衡点；没有标注时先用环比降幅的分位数（如P10）冷启动，再靠客服跟进反馈迭代阈值。
- **怎么把这条SQL升级成流失预测模型的特征工程？**
  回答要点：环比特征、连续下滑周数、最近付费间隔、大R等级等都是模型输入；SQL负责批量生产特征宽表，模型负责非线性组合打分，是上下游关系而非替代。
- **误报成本和漏报成本怎么权衡？**
  回答要点：VIP客服人力有限，误报浪费高价值触达甚至打扰用户，漏报损失真流失；阈值宁高勿低（高precision），漏报靠中危观察池与月度全量盘点兜底。
- **大R“攒着不买”和“要流失”在数据上怎么区分？**
  回答要点：看在线时长是否同步下滑、是否参与新版本活动、是否囤积未消耗优惠券；只停付费、行为不停的更可能是付费节奏问题——双信号机制正是为此设计。

### 7. 业务拓展思考

流失预警名单是CRM自动化的入口：高危自动触发客服工单与差异化礼包（按历史付费品类定制），中危进推送池，处理结果回写形成"预警-干预-回访"闭环，并用干预效果反哺阈值校准。可联动版本运营：大版本上线后的全体付费回落属正常消化，应临时屏蔽或降权告警，防止预警疲劳。口径延展上，双信号可扩为多维信号（社交行为骤停、公会退出、客服负反馈）加权成"流失风险分"，比二元规则更细腻；同时把口径从中R延展到腰部付费用户，构建全量付费用户的分层预警体系。

## GAME-41 版本内容消耗进度队列分析（内容空窗预警）

### 1. 业务背景

长草期预警会上，制作人要与运营、发行一起回答：当前版本的主线内容还能"喂饱"玩家多少天？把用户按主线进度分段，统计每日有多少玩家"追平了最新章节"（玩到了当前版本内容的尽头），并用近期的追赶速度外推——按当前速度，还剩多少"有内容可玩"的用户、能撑几天。一旦预测的"内容空窗日"早于下个版本上线日，就要立即排长草期活动（限时玩法、轮回活动、福利线）填坑，否则会出现DAU与付费双降的"长草滑坡"。这个分析把"内容消耗速度"变成可量化排期依据，是内容型游戏运营的核心报表之一。

### 2. 表结构说明

| V3.1 | 12 | 群星归位 | 2026-12-10 |

### 3. 解题思路

口径先行："追平"定义为玩家已通过当前版本开放的最高章节（本例为第9章，第10章尚未开放不计）；"剩余人数"=期内活跃过主线的人数减去已追平人数；"空窗天数"=剩余人数÷近7日平均每日追平人数，即按当前速度还能撑几天。实现路径：解法一在"日粒度"上做——先统计每日通过最新章节的人数，用窗口累计得历史累计追平人数、用滑动窗口（ROWS BETWEEN 6 PRECEDING AND CURRENT ROW）得近7日平均追赶速度，两者相除得剩余可玩天数；解法二在"用户粒度"上做——给每个用户算出"追平日"，构成追平cohort，再统计追平后7日的登录与活动参与情况，验证追平后是否真的"变咸鱼"，为空窗预警提供行为佐证。**【避坑指南】** 章节有分批开放节奏时，"最新章节"必须按日期动态取"当日已开放的最高章"，用固定MAX会高估追平人数。

### 4. 参考解法

**解法一：每日追平速度窗口累计 + 空窗天数外推（主推）**

```sql
-- 解法一：每日通过人数 → 累计与近7日速度 → 剩余天数外推（@cur_ver 当前版本，@stat_date 监控日）
WITH opened AS (                                      -- ① 截至监控日已开放的最高章节
    SELECT MAX(chapter_id) AS max_ch
    FROM contents
    WHERE version_id = @cur_ver
      AND release_date <= @stat_date                   -- 动态口径：只算已开放章节
),
daily_clear AS (                                      -- ② 每日通过最新章节的人数
    SELECT DATE(p.finish_time) AS d,
          COUNT(DISTINCT p.user_id) AS clear_uv
    FROM progress p
    CROSS JOIN opened o
    WHERE p.chapter_id = o.max_ch
    GROUP BY DATE(p.finish_time)
),
cum AS (                                              -- ③ 窗口累计：历史追平人数 + 近7日平均速度
    SELECT d, clear_uv,
          SUM(clear_uv) OVER (ORDER BY d) AS cum_uv,                     -- 全期累计追平人数
          AVG(clear_uv) OVER (ORDER BY d
              ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg7_speed     -- 近7日日均追平速度
    FROM daily_clear
),
stock AS (                                            -- ④ 内容总盘子：期内打过主线的人数
    SELECT COUNT(DISTINCT user_id) AS total_uv
    FROM progress
    WHERE DATE(finish_time) >= @ver_start             -- 本版本开服以来
)
SELECT c.d,                                           -- 监控日期
      c.cum_uv,                                       -- 累计已追平人数
      ROUND(s.total_uv - c.cum_uv) AS remaining_uv,   -- 估计仍有内容可玩的人数
      ROUND(c.avg7_speed, 1)       AS speed_7d,       -- 近7日日均追平速度
      ROUND((s.total_uv - c.cum_uv) / NULLIF(c.avg7_speed, 0), 1) AS days_to_empty -- 预计还能撑几天
FROM cum c
CROSS JOIN stock s
WHERE c.d >= @stat_date - INTERVAL 13 DAY             -- 看最近两周趋势
ORDER BY c.d;
```

结果解读：若输出最近一日 `remaining_uv=42000、speed_7d=3100、days_to_empty=13.5`，而下个版本13天后才上线，正好卡点；若 `days_to_empty=8`，则未来5天的长草缺口要立刻用活动填。

**解法二：用户级追平cohort + 追平后行为验证（佐证空窗伤害）**

```sql
-- 解法二：给每人算“追平日”，看追平后7日活跃是否断崖（@cur_ver/@stat_date 同上）
WITH opened AS (                                      -- ① 已开放最高章节
    SELECT MAX(chapter_id) AS max_ch
    FROM contents
    WHERE version_id = @cur_ver AND release_date <= @stat_date
),
user_prog AS (                                        -- ② 每用户最高章节
    SELECT user_id, MAX(chapter_id) AS max_ch_user
    FROM progress
    GROUP BY user_id
),
catch_up AS (                                         -- ③ 追平用户及其追平日
    SELECT p.user_id, MIN(DATE(p.finish_time)) AS catch_date
    FROM progress p
    CROSS JOIN opened o
    JOIN user_prog u ON u.user_id = p.user_id
    WHERE p.chapter_id = o.max_ch
      AND u.max_ch_user = o.max_ch                     -- 只算真正玩到尽头的用户
    GROUP BY p.user_id
),
after_7d AS (                                         -- ④ 追平后7日是否仍登录
    SELECT c.user_id, c.catch_date,
          MAX(CASE WHEN l.login_date > c.catch_date
                    AND l.login_date <= c.catch_date + INTERVAL 7 DAY
                  THEN 1 ELSE 0 END) AS active_after7
    FROM catch_up c
    LEFT JOIN login l ON l.user_id = c.user_id
        AND l.login_date > c.catch_date
        AND l.login_date <= c.catch_date + INTERVAL 7 DAY
    GROUP BY c.user_id, c.catch_date
)
SELECT DATE_FORMAT(a.catch_date, '%Y-%m-%d')          AS catch_date,   -- 按追平日分cohort
      COUNT(*)                                        AS catch_uv,
      ROUND(AVG(a.active_after7), 4)                  AS retain7_after_catch,  -- 追平后7日仍活跃率
      ROUND(1 - AVG(a.active_after7), 4)              AS stall_risk    -- 追平后沉默比例（长草风险）
FROM after_7d a
GROUP BY 1
ORDER BY 1 DESC
LIMIT 14;                                             -- 看最近两周追平cohort的沉默趋势
```

结果解读：若最近几日追平cohort的 `stall_risk` 从35%升到58%，说明"玩到头就沉默"正在加速发生，与解法一的剩余天数外推互相印证，空窗预警升级为红色。

> Hive/Spark SQL 差异：progress 按月分区后只扫版本窗口；窗口累计在 Hive 可用，注意 `ROWS BETWEEN` 的排序键唯一性（同一日多行时按日先聚合）；追平速度外推在生产上建议沉淀为每日快照表 `dws_content_queue(date, cum_uv, speed7, remaining, days_to_empty)`，预警看板直接读快照，避免每次现算。

### 5. 性能分析与优化

解法一的窗口都作用在"日粒度"聚合结果（每天一行）上，代价忽略不计；主要成本在 daily_clear 与 user_prog 两次对 progress 的聚合，按 `finish_time`/`dt` 分区裁剪到版本窗口即可。解法二多一次追平用户与login的join，务必像示例一样限定7日区间防止全历史join。优化建议：progress 建 `(chapter_id, finish_time)`、`(user_id, chapter_id)` 复合索引；"用户最高章节"沉淀为每日更新的用户进度表，追平判定变成长表过滤；contents 是小维表全程broadcast；预测外推逻辑（速度取近7日还是近14日、是否加权）放在调度脚本参数里，SQL保持口径纯净。**【加分点】** 能指出剩余人数的口径误差——期内活跃人数并非都在追主线，更精细的做法是只统计"距最高章节≤2章"的活跃用户作分母。

### 6. 面试延伸考点

- **追赶速度用近7日还是全期平均？各有什么问题？**
  回答要点：全期平均平滑但反应慢，版本初期用户涌入会高估速度；近7日灵敏但受周末与活动波动影响；生产上常两条都算并加权，或用近7日中位数抗异常。
- **多玩法并行（主线/活动关卡/肉鸽模式）时，“空窗”怎么定义？**
  回答要点：按玩法分别建模再取最长剩余天数做总余量，或给各玩法加权合成"内容丰富度指数"；核心是承认玩家可选替代内容，主线空窗不等于全局空窗。
- **追平后的用户都在干什么？SQL怎么验证？**
  回答要点：对追平cohort对比追平前后7日的玩法分布、体力消耗、活动参与率，看是转移到替代玩法还是整体沉默；这也是长草活动设计的依据。
- **怎么提前一个月预测空窗日而不只是监控？**
  回答要点：用历史版本追赶曲线的形状（用户进度分位数随时间的变化）做类比外推，或对"剩余人数"做时间序列拟合；把"进度分位数曲线"沉淀为版本复盘标配资产。

### 7. 业务拓展思考

内容消耗队列分析把"玩家什么时候玩完"变成可排期的数字：空窗缺口直接驱动轮回活动、限时玩法与福利线的上线排期，也可反向推动研发侧的内容产能节奏与版本间隔决策。联动动作上，对"距追平1~2章"的用户推送主线进度礼包做最后冲刺，对已追平用户第一时间引流到替代玩法或社交玩法（公会、PVP），把长草期变成社交沉淀期。口径延展上，可把"主线进度"换成体力消耗率、关卡解锁深度等任意内容度量，构建版本健康度仪表盘，让"内容空窗"从体感判断变成数据红线。

## GAME-42 工作室多账号识别（设备/IP/行为相似度规则）

### 1. 业务背景

风控团队发现新手奖励被批量薅取：疑似工作室在真机墙上批量注册账号，同步完成新手任务后集中提现或出售初始资源。识别要求三条线索：同一设备（或同一IP）短时间内注册多个账号；注册时间间隔高度规律（如整点、等间隔10分钟）；升级与任务完成轨迹高度雷同。产出物是一份"疑似工作室账号簇"清单（簇ID、簇内账号数、注册时间跨度、命中规则），交运营人工复核后决定封禁或延迟发放奖励。**【面试高频】** 这题的标准考法就是gaps-and-islands：把"同设备上间隔小于阈值的连续注册"归成一簇，是窗口函数高级应用的经典场景。

### 2. 表结构说明

**表1：users 注册信息表**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| register_time | DATETIME | 注册时间 |
| register_device | VARCHAR(64) | 注册设备指纹 |
| register_ip | VARCHAR(48) | 注册IP |
| channel | VARCHAR(32) | 注册来源渠道 |

示例数据：

| user_id | register_time | register_device | register_ip | channel |
|---|---|---|---|---|
| x8001 | 2026-10-10 08:00:05 | DEV-A | 1.2.3.4 | 自然流量 |
| x8002 | 2026-10-10 08:09:50 | DEV-A | 1.2.3.4 | 自然流量 |
| x8003 | 2026-10-10 08:18:30 | DEV-A | 1.2.3.4 | 自然流量 |
| x8004 | 2026-10-10 09:30:00 | DEV-B | 5.6.7.8 | 自然流量 |
| x8005 | 2026-10-11 22:01:00 | DEV-C | 9.9.9.9 | 抖音信息流 |

### 3. 解题思路

先定阈值与规则：同设备相邻注册间隔<10分钟视为"连号"；一个连号簇内账号数≥5判为疑似工作室；再叠加IP维度（同IP注册≥8个账号）与行为维度（注册时刻标准差<10分钟，说明程序化定时注册）形成多规则打分，总分≥2的账号进入复核名单。实现路径：解法一是标准gaps-and-islands——同设备按注册时间排序后LAG取相邻间隔，间隔≥10分钟（或首条）标记为"新簇起点"，对标记做窗口累计和生成簇ID，最后按簇聚合出账号数与时间跨度；解法二是多规则打分制——分别在设备、IP、注册时刻三个维度聚合出"命中名单"，再回表给每个账号算命中规则数，输出可解释的风险分。**【避坑指南】** 簇ID算法必须用"SUM(new_island)"的累计和重置逻辑，直接ROW_NUMBER会把整台设备的所有账号编成一簇，阈值切换（10分钟改30分钟）时全部历史簇ID会变，需在宽表固化快照。

### 4. 参考解法

**解法一：gaps-and-islands同设备连号分簇（主推）**

```sql
-- 解法一：LAG间隔 → 起点标记 → 累计和生成簇ID → 按簇聚合
WITH reg AS (                                         -- ① 同设备按注册时间排序，取相邻间隔
    SELECT user_id, register_device, register_time,
          LAG(register_time) OVER (PARTITION BY register_device ORDER BY register_time) AS prev_time
    FROM users
),
flagged AS (                                          -- ② 间隔≥10分钟（或首条）= 新簇起点
    SELECT user_id, register_device, register_time,
          CASE WHEN prev_time IS NULL
                    OR TIMESTAMPDIFF(MINUTE, prev_time, register_time) >= 10
              THEN 1 ELSE 0 END AS new_island
    FROM reg
),
island AS (                                           -- ③ 累计和=簇编号：每遇新起点+1
    SELECT user_id, register_device, register_time,
          SUM(new_island) OVER (PARTITION BY register_device ORDER BY register_time
                                ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS island_id
    FROM flagged
)
SELECT register_device,
      CONCAT(register_device, '-', island_id) AS cluster_id,      -- 簇ID=设备+序号
      COUNT(*)                                AS acct_cnt,        -- 簇内账号数
      MIN(register_time)                      AS first_reg,
      MAX(register_time)                      AS last_reg,
      ROUND(TIMESTAMPDIFF(SECOND, MIN(register_time), MAX(register_time))
            / NULLIF(COUNT(*) - 1, 0) / 60.0, 1) AS avg_gap_min       -- 平均注册间隔（分钟）
FROM island
GROUP BY register_device, island_id
HAVING COUNT(*) >= 5                                  -- 簇内≥5账号判为疑似工作室
ORDER BY acct_cnt DESC;
```

结果解读：输出如 `DEV-A 簇 12个账号、平均间隔8.9分钟`，配合整点/等间隔特征基本可定性工作室；单人换机（间隔数小时）不会成簇，误伤小。

**解法二：设备/IP/行为三规则打分制（可解释风险分）**

```sql
-- 解法二：三条独立规则聚合出命中名单，回表打分，输出可解释风险分
WITH dev_flag AS (                                    -- 规则①：同设备注册≥5个账号
    SELECT register_device
    FROM users
    GROUP BY register_device
    HAVING COUNT(*) >= 5
),
ip_flag AS (                                          -- 规则②：同IP注册≥8个账号
    SELECT register_ip
    FROM users
    GROUP BY register_ip
    HAVING COUNT(*) >= 8
),
regular_reg AS (                                      -- 规则③：注册时刻标准差<600秒 = 程序化定时注册
    SELECT register_device
    FROM users
    GROUP BY register_device
    HAVING COUNT(*) >= 3
       AND STDDEV_POP(TIME_TO_SEC(TIME(register_time))) < 600
),
scored AS (                                           -- 每账号命中几条规则
    SELECT u.user_id, u.register_device, u.register_ip, u.register_time,
          CASE WHEN d.register_device IS NOT NULL THEN 1 ELSE 0 END
        + CASE WHEN i.register_ip     IS NOT NULL THEN 1 ELSE 0 END
        + CASE WHEN r.register_device IS NOT NULL THEN 1 ELSE 0 END AS risk_score
    FROM users u
    LEFT JOIN dev_flag    d ON d.register_device = u.register_device
    LEFT JOIN ip_flag     i ON i.register_ip     = u.register_ip
    LEFT JOIN regular_reg r ON r.register_device = u.register_device
)
SELECT user_id, register_device, register_ip, risk_score
FROM scored
WHERE risk_score >= 2                                 -- 命中≥2条进入人工复核
ORDER BY risk_score DESC, register_time;
```

结果解读：`risk_score=3` 的账号三项全中，几乎可定性；`=2` 的进入复核；规则彼此独立，任何一条误判都不会单独导致误封，这是打分制相对单规则的鲁棒性优势。

> Hive/Spark SQL 差异：注册表按月分区后只扫近期数据；Hive 支持 LAG 与累计和窗口，注意 `STDDEV_POP` 需较新版本；生产上建议把设备/IP聚合规则下沉为每日增量任务（新注册即算分），实时链路用Flink复刻gaps逻辑；Spark 下 dev_flag/ip_flag 等小结果集broadcast回表打分。

### 5. 性能分析与优化

解法一的窗口按设备分区排序，排序量=注册行数，单次扫描可控；簇聚合发生在窗口结果上，无额外join。解法二有三次维度聚合+三次回表join，均是"聚合小表join明细大表"，把小表broadcast即可，避免明细表shuffle。优化建议：users 建 `(register_device, register_time)`、`(register_ip, register_time)` 复合索引，两个维度的聚合都能走索引扫描；行为相似度（升级速度、任务完成顺序的编辑距离/向量相似）计算昂贵，先由SQL规则筛出候选簇，再只对簇内账号做深度行为比对；风险分宽表按日快照固化，保证封禁审计可回溯。**【避坑指南】** 公用IP（校园、网吧、NAT出口）会大量误触发IP规则，生产上IP规则要配"IP下设备离散度"校验——多账号但设备各不相同且行为正常的IP应降权。

### 6. 面试延伸考点

- **为什么簇ID用“累计和重置”而不是ROW_NUMBER？**
  回答要点：ROW_NUMBER只给序号，不表达"相邻间隔是否断裂"；累计和以新簇起点为增量，天然把同设备的连续段归为同一编号，这是gaps-and-islands的标准解法。
- **怎么降低对正常用户的误伤？**
  回答要点：多规则交叉验证而非单规则封禁、家庭共享设备场景配行为校验、先"延迟发奖"等软措施再升级硬封禁、全流程留快照供申诉复核。
- **工作室换设备指纹怎么办？**
  回答要点：从静态指纹转向行为指纹——升级节奏、任务完成顺序、操作时间分布的相似度聚类（簇内两两相似度矩阵），SQL可先输出特征，相似度计算交给专门的算法链路。
- **怎么验证识别准确率？**
  回答要点：对已人工确认的封禁案例回测规则的precision/recall；对未被标记的抽样簇人工复核估算误报率；上线初期用"延迟发奖"灰度观察申诉率。

### 7. 业务拓展思考

工作室识别保护的不只是新手补贴：账号簇清单同时反哺经济系统（防初始资源抛售砸盘）、排行榜公平性（防代练占榜）与买量归因（工作室账号混入会污染渠道LTV）。联动动作上，对疑似簇统一"延迟发放奖励+提高提现门槛"，对确认簇封禁并回溯其关联渠道做投放反作弊扣量。口径延展上，可把"注册连号"扩展为"登录连号""充值连号"同一套gaps框架，形成设备/IP/支付账号多维图谱，簇与簇之间再连边，逼近关系网络分析。

## GAME-43 活动ROI与参与分层（按参与深度拆增量）

### 1. 业务背景

周年庆活动收官后，活动运营要交ROI复盘：活动总增量收入是多少、ROI（活动期增量收入÷活动成本）达不达标，更要紧的是回答"活动主要撬动了哪一层人"。按参与深度把活动期活跃用户分为四层——深参与（全勤+核心任务完成）、中参与（完成任务≥5个）、浅参与（仅登录领奖）、未参与（活跃但没碰活动），用"活动前7日人均收入 vs 活动期7日人均收入"的前后对比计算各层原始增量，再以未参与层作为同期基线扣除大盘自然增长，得到各层净增量（简化DID）。这决定下次活动的门槛设计：如果增量主要来自中参与层，说明"任务化参与"最有效，浅层领奖只是补贴老玩家。

### 2. 表结构说明

### 3. 解题思路

口径三件事：分层规则用业务语义（深=全勤、中=任务≥5、浅=仅参与、未参与=活动期活跃但无参与记录）；对比窗口取"活动前7日"与"活动期"两个互不重叠区间；净增量=该层(活动期人均-活动前人均) - 未参与层(活动期人均-活动前人均)，即以未参与层为同期基线的双重差分简化版。实现路径：解法一"条件聚合一次成型"——以分层表join订单，两条SUM(CASE WHEN区间)同列输出前后收入与各层净增量，未参与层基线用窗口或标量子查询引用；解法二"区段分别聚合再join"——活动前、活动期各聚一次合，再与分层表三表join，无长CASE、可读性好。**【避坑指南】** 未参与层不是随机对照组（不参与往往因为不活跃或低付费），DID结论要声明偏差方向，能提出"只用活动前收入水平相近的低活层做对照"更稳。

### 4. 参考解法

**解法一：条件聚合一次成型 + 未参与层作基线（主推）**

```sql
-- 解法一：分层+前后窗条件聚合，一条SQL输出各层净增量（@act_id/@act_start/@act_end 为活动参数）
WITH act_users AS (                                   -- ① 活动期活跃用户为底
    SELECT DISTINCT user_id
    FROM login
    WHERE login_date BETWEEN @act_start AND @act_end
),
seg AS (                                              -- ② 参与深度分层
    SELECT a.user_id,
          CASE WHEN ap.user_id IS NULL         THEN 'D_未参与'
               WHEN ap.is_full_attend = 1      THEN 'A_深参与'
               WHEN ap.task_cnt >= 5           THEN 'B_中参与'
               ELSE 'C_浅参与' END AS seg
    FROM act_users a
    LEFT JOIN activity_participation ap
      ON ap.user_id = a.user_id AND ap.activity_id = @act_id
),
rev AS (                                              -- ③ 前后两窗收入一次条件聚合
    SELECT p.user_id, p.seg,
          SUM(CASE WHEN o.order_time >= @act_start
                    THEN o.amount ELSE 0 END) AS rev_dur,          -- 活动期收入
          SUM(CASE WHEN o.order_time <  @act_start
                    AND o.order_time >= @act_start - INTERVAL 7 DAY
                    THEN o.amount ELSE 0 END) AS rev_pre           -- 活动前7日收入
    FROM seg p
    LEFT JOIN orders o
      ON o.user_id = p.user_id
      AND o.status = '成功'
      AND o.order_time >= @act_start - INTERVAL 7 DAY
      AND o.order_time <  @act_end + INTERVAL 1 DAY
    GROUP BY p.user_id, p.seg
)
SELECT seg,
      COUNT(*)                                        AS uv,
      ROUND(AVG(rev_pre), 2)                          AS arpu_pre,
      ROUND(AVG(rev_dur), 2)                          AS arpu_dur,
      ROUND(AVG(rev_dur) - AVG(rev_pre), 2)           AS raw_lift,    -- 各层原始增量
      ROUND( (AVG(rev_dur) - AVG(rev_pre))
           - (SELECT AVG(rev_dur) - AVG(rev_pre)      -- 减去未参与层基线 = 净增量(DID)
              FROM rev WHERE seg = 'D_未参与'), 2)    AS did_lift
FROM rev
GROUP BY seg
ORDER BY seg;
```

结果解读：若 `A_深参与 did_lift=118、B_中参与=64、C_浅参与=9、D_未参与基线=6`，说明增量由任务型参与驱动，下次活动应降低任务门槛、加大任务奖励，浅层签到礼包的边际效果有限。

**解法二：区段分别聚合再join（无长CASE，可读性优先）**

```sql
-- 解法二：活动前/活动期各聚一次，再与分层表拼接
WITH act_users AS (
    SELECT DISTINCT user_id FROM login
    WHERE login_date BETWEEN @act_start AND @act_end
),
seg AS (                                              -- 分层（同解法一②）
    SELECT a.user_id,
          CASE WHEN ap.user_id IS NULL    THEN 'D_未参与'
               WHEN ap.is_full_attend = 1 THEN 'A_深参与'
               WHEN ap.task_cnt >= 5      THEN 'B_中参与'
               ELSE 'C_浅参与' END AS seg
    FROM act_users a
    LEFT JOIN activity_participation ap
      ON ap.user_id = a.user_id AND ap.activity_id = @act_id
),
pre AS (                                              -- 活动前7日收入
    SELECT o.user_id, SUM(o.amount) AS rev_pre
    FROM orders o
    WHERE o.status = '成功'
      AND o.order_time >= @act_start - INTERVAL 7 DAY
      AND o.order_time <  @act_start
    GROUP BY o.user_id
),
dur AS (                                              -- 活动期收入
    SELECT o.user_id, SUM(o.amount) AS rev_dur
    FROM orders o
    WHERE o.status = '成功'
      AND o.order_time >= @act_start
      AND o.order_time <  @act_end + INTERVAL 1 DAY
    GROUP BY o.user_id
)
SELECT p.seg,
      COUNT(*)                                        AS uv,
      ROUND(AVG(COALESCE(pr.rev_pre, 0)), 2)          AS arpu_pre,
      ROUND(AVG(COALESCE(dr.rev_dur, 0)), 2)          AS arpu_dur,
      ROUND(AVG(COALESCE(dr.rev_dur,0)) - AVG(COALESCE(pr.rev_pre,0)), 2) AS raw_lift
FROM seg p
LEFT JOIN pre pr ON pr.user_id = p.user_id
LEFT JOIN dur dr ON dr.user_id = p.user_id
GROUP BY p.seg
ORDER BY p.seg;                                       -- 净增量=DID同解法一，可外层再包一层减基线
```

结果解读：解法二把"两个时间窗"翻译成两次独立聚合再拼接，SQL扁平易维护，适合活动参数频繁变化的调度场景；代价是三次join，规模上仍控制在用户粒度，可接受。

> Hive/Spark SQL 差异：Hive 下 orders 按 `dt` 分区，两个窗口只扫22个分区；seg 底表与两段收入均为用户粒度中间结果，Spark 中 broadcast join；活动成本、礼包发放成本通常在运营后台，可并入维表与 did_lift 相除直接产出ROI列。

### 5. 性能分析与优化

两解法的join都收敛在用户粒度（每层人数远小于订单流水），主要成本是orders两窗扫描与act_users去重；orders按 `dt` 分区裁剪到22天，`(user_id, order_time)` 复合索引加速user级聚合。解法一的单次条件聚合避免了两次聚合+join的shuffle，数据量大时更优；解法二的三次join在Spark下用broadcast化解。优化建议：把"用户活动参与分层"沉淀为活动期每日更新的宽表，复盘、A/B对比、跨活动横向比较都从它出发；未参与层基线若需更细（按活动前付费水平分层），预先物化"活动前7日用户收入分层表"再join，避免复杂子查询。**【加分点】** 能主动提出"活动虹吸检验"——活动后7日各层收入回落幅度，若深参与层回落最深，说明活动透支了未来付费，ROI要打折。

### 6. 面试延伸考点

- **未参与层不是随机对照组，DID结论怎么兜底？**
  回答要点：承认自选择偏差方向（不参与者往往更不活跃），可只用"活动前收入与活跃度相近的低活层"做对照，或按参与倾向做匹配；严谨结论靠随机化门槛/邀请制实验。
- **怎么识别“活动透支未来付费”（虹吸效应）？**
  回答要点：看活动结束后7~14日各层收入与付费率的回落深度，对比活动前基线；回落显著超过自然波动即虹吸，ROI核算要扣除这部分。
- **ROI的分母除了活动成本还应包含什么？**
  回答要点：礼包道具的边际成本（尤其是通缩型道具的经济成本）、开发人力折算、以及挤压其他活动收入的内部稀释，纯流水ROI会高估。
- **参与深度分层的边界怎么定才科学？**
  回答要点：先看任务完成数的自然断点（直方图）与各层人数规模，再对齐业务语义；边界一旦定下要跨活动复用，保证活动间可比。

### 7. 业务拓展思考

参与分层×净增量的框架是活动设计的"实验台"：哪一层贡献增量，就往哪一层加码——增量在中层则做任务线、在浅层则做签到与礼包直购、深参与层已饱和则控制强度防虹吸。联动动作上，把各层净增量与活动成本合成"分层ROI"，指导不同活动的目标人群与资源配比；对未参与层做定向邀请测试（发与不发对比）验证"不参与=没兴趣"还是"没看见"。口径延展上，可将收入增量换成留存增量、社交行为增量，评估活动的长期价值而不只是7日流水。

## GAME-44 赛季结算周期与DAU/付费节奏分析

### 1. 业务背景

竞技品类的运营在赛季复盤会上要刻画"赛季节奏"：把赛季内每一天对齐到"距赛季结算的剩余天数"，把多个赛季的DAU与付费率按剩余天数对齐后叠在一起比较，验证两个运营假设——"赛季末冲分带来付费小高峰"与"赛季初结算挫败导致DAU疲软"。如果假设成立，赛季末最后一周是限定礼包与冲分活动的黄金窗口，赛季初第一周则要排回流召回与保底福利对冲流失。这道题的核心是把"日历时间"转成"赛季相对时间"再聚合，考察对业务周期性数据的对齐建模能力，以及从已有日汇总表出发的轻量分析习惯。

### 2. 表结构说明

### 3. 解题思路

核心动作是"时间轴变换"：join赛季日历，把每个自然日换成两个相对坐标——距结算剩余天数（end_date - dt，0=结算日）与赛季内第几天；再按相对坐标跨赛季聚合，DAU取均值、付费率=付费用户/DAU、流水取均值，用"覆盖赛季数"列检验每格样本是否足够。实现路径两条：解法一直接join seasons表做剩余天数聚合，最直接；解法二演示"没有日历表时从数据反推赛季边界"——结算日的典型特征是次日DAU骤降（结算挫败+休赛），用LEAD找DAU降幅>25%的日子作结算日、次日为新赛季首日，再用窗口ROW_NUMBER定位"赛季内第N天"。**【避坑指南】** 跨赛季对比时各赛季时长不同，剩余天数轴要保留"该格覆盖了几个赛季"，样本不足的格子（如第85天）不能直接比较。

### 4. 参考解法

**解法一：join赛季日历按“剩余天数”对齐聚合（主推）**

```sql
-- 解法一：日汇总表join赛季日历，按“距结算剩余天数”跨赛季聚合
WITH d2s AS (                                         -- ① 每天挂上赛季与剩余天数
    SELECT r.dt,
          s.season_id,
          s.season_name,
          DATEDIFF(s.end_date, r.dt) AS days_left,    -- 剩余天数：0=结算日
          r.dau, r.pay_user_cnt, r.revenue
    FROM daily_report r
    JOIN seasons s
      ON r.dt BETWEEN s.start_date AND s.end_date     -- 落在某赛季区间内
)
SELECT days_left,
      COUNT(DISTINCT season_id)              AS season_cnt,   -- 覆盖赛季数（样本检验）
      ROUND(AVG(dau), 0)                     AS avg_dau,
      ROUND(AVG(pay_user_cnt) / NULLIF(AVG(dau), 0) * 100, 2) AS pay_rate_pct,  -- 平均付费率
      ROUND(AVG(revenue / NULLIF(dau, 0)), 2) AS arpu_daily   -- 日ARPU
FROM d2s
GROUP BY days_left
ORDER BY days_left DESC;                              -- 从赛季初一路看到结算日
```

结果解读：若曲线显示 `剩余7~1天 pay_rate=8.1%` 显著高于赛季中段的 `5.9%`，而 `剩余0~-1天（结算次日）DAU较峰值下滑18%`，两个假设同时成立，赛季末窗口与赛季初对冲策略都有了数据依据。

**解法二：从数据反推赛季边界（无日历表，窗口定位赛季内第N天）**

```sql
-- 解法二：用DAU断点反推结算日，再按“赛季内第N天”聚合（阈值需人工校准）
WITH edge AS (                                        -- ① 结算日特征：次日DAU骤降
    SELECT dt, dau,
          LEAD(dau) OVER (ORDER BY dt) AS next_dau
    FROM daily_report
),
season_start AS (                                     -- ② 骤降次日 = 新赛季首日（降幅>25%）
    SELECT DATE_ADD(dt, INTERVAL 1 DAY) AS season_start_date
    FROM edge
    WHERE next_dau IS NOT NULL
      AND next_dau < dau * 0.75
),
tagged AS (                                           -- ③ 每天归属第几个赛季（历史起点计数）
    SELECT r.dt, r.dau, r.pay_user_cnt, r.revenue,
          (SELECT COUNT(*) FROM season_start s
            WHERE s.season_start_date <= r.dt) AS season_no
    FROM daily_report r
),
pos AS (                                              -- ④ 窗口定位“赛季内第N天”
    SELECT season_no, dt,
          ROW_NUMBER() OVER (PARTITION BY season_no ORDER BY dt) AS day_n
    FROM tagged
    WHERE season_no >= 1
)
SELECT p.day_n,
      COUNT(DISTINCT p.season_no)                     AS season_cnt,
      ROUND(AVG(t.dau), 0)                            AS avg_dau,
      ROUND(AVG(t.pay_user_cnt) / NULLIF(AVG(t.dau), 0) * 100, 2) AS pay_rate_pct
FROM pos p
JOIN tagged t ON t.dt = p.dt
GROUP BY p.day_n
ORDER BY p.day_n;                                     -- 赛季内第1天起看疲软曲线
```

结果解读：解法二不依赖运营维护的日历表，适合日历缺失或赛季改期的场景；但它假设"结算日=DAU骤降日"，若大版本更新或事故同日发生会误判，必须人工校准边界后再固化。

> Hive/Spark SQL 差异：daily_report 按年/月分区即可全量扫；相关子查询（③的season_no计数）在Hive中性能差，改为 season_start LEFT JOIN + COUNT 聚合或窗口 `SUM(CASE WHEN...) OVER (ORDER BY dt)`；跨赛季聚合前先把 (dt, season_no, day_n, days_left) 物化为赛季日历宽表，一次维护反复使用。

### 5. 性能分析与优化

解法一是日汇总表（几百行/赛季）join小维表的纯聚合，代价可忽略；解法二的相关子查询逐日计数是唯一性能点，生产上改为窗口累计 `SUM(CASE WHEN is_season_start THEN 1 ELSE 0 END) OVER (ORDER BY dt)` 即O(n)。优化建议：把"日期→赛季/剩余天数/赛季内天数"映射固化为日历宽表（含赛季、节假日、版本日），所有节奏类报表共用；聚合粒度若要更稳，对剩余天数轴做平滑（3日移动平均）再输出；结算日前后样本做异常日标注（活动、事故日历join），防止单日异常拉偏均值。**【加分点】** 能提出"两个相对轴并用"——赛季内第N天看爬坡、剩余N天看冲刺，双轴透视一图讲清整个赛季生命周期。

### 6. 面试延伸考点

- **赛季初DAU下滑，怎么区分“结算挫败流失”和“内容真空”？**
  回答要点：看下滑人群结构——高段位玩家占比升=挫败流失，全量均匀下滑=内容真空；再对比"未打排位的休闲玩家"是否同步下滑做分离。
- **付费高峰归因冲分还是礼包？怎么拆？**
  回答要点：拆品类——排位保护卡、段位框类道具增长=冲分驱动，直充礼包增长=促销驱动；再对比"排位活跃用户与非排位用户"的付费率差。
- **多个赛季节奏曲线波动大怎么办？**
  回答要点：检查赛季时长与档期事件差异，做归一化（各赛季内分位数对齐）或剔除异常日；样本足够时给出置信区间而非单线。
- **跨赛季对比时赛季时长不一致怎么处理？**
  回答要点：相对轴天然解决长短不一，但要保留每格覆盖赛季数；也可统一截断到"标准赛季长度"（如60天）比较，超出部分单独说明。

### 7. 业务拓展思考

赛季节奏曲线是竞技品类运营的"潮汐表"：赛季末冲刺窗口排限定礼包与冲分活动、结算次日排保底福利与好友召回、赛季中段排玩法更新，把有限的运营资源对准节奏高点。联动动作上，与买量协同——赛季初的自然回流期配合召回买量性价比最高；与客服协同——结算挫败投诉高峰提前布防。口径延展上，可把DAU/付费率换成段位分布迁移矩阵（每赛季玩家段位流转）、赛季末离场名单的回流率，把"赛季周期性"从报表升级为跨赛季的玩家流动模型。

## GAME-45 跨版本用户迁移矩阵（版本A→B流转）

### 1. 业务背景

新版本上线30天后，版本分析师要输出"跨版本迁移矩阵"：以旧版本周期内最后一次活跃的客户端版本为"来源版本"，新版本上线后首周活跃的版本为"目标版本"，统计各来源版本用户的流向占比——多少直接升到2.0、多少滞留在1.5老版本、多少首周彻底未活跃（疑似流失或未强更），并对比各来源版本用户迁移后的30日留存差异，定位"迁移堵点"。结论直接驱动三个决策：对滞留老版本用户推强更（强制更新）灰度策略、对首周未活跃用户做召回、对迁移后留存骤降的来源版本做老服合并评估。这是版本运营与客户端发布团队联合复盘的标配分析。

### 2. 表结构说明

**表1：login 登录流水表（含版本号）**

| 字段名 | 类型 | 含义 |
|---|---|---|
| user_id | VARCHAR(32) | 用户ID |
| version_id | VARCHAR(16) | 客户端版本号 |
| login_date | DATE | 登录日期 |

示例数据：

| user_id | version_id | login_date |
|---|---|---|
| m1101 | 1.5 | 2026-09-20 |
| m1101 | 1.5 | 2026-09-28 |
| m1101 | 2.0 | 2026-10-01 |
| m1102 | 1.5 | 2026-09-25 |
| m1103 | 1.5 | 2026-09-22 |

（假设新版本2.0于2026-10-01上线）

### 3. 解题思路

口径三件事：来源版本=上线日前最后一次登录的版本（argmax问题）；目标版本=上线日后首周内第一次登录的版本（argmin问题），首周未登录记为"未迁移/疑似流失"；迁移后30日留存=迁移完成日起第30日是否仍活跃，作为迁移质量指标。实现路径：解法一用窗口ROW_NUMBER做双向argmax（上线日前按日期倒序取第一、上线日后按日期升序取第一），拼出"来源→目标"对后条件聚合透视成矩阵；解法二用条件聚合argmax写法（MAX(CASE WHEN 关键日期 THEN version)），不依赖窗口，Hive与老引擎友好，透视同为条件聚合行转列。**【避坑指南】** 同一天跨版本登录（当天上午1.5晚上2.0）会让argmax不唯一，生产上要用login_time时间戳而不是date做边界切分，面试时主动提出这一口径风险是明显加分项。

### 4. 参考解法

**解法一：窗口ROW_NUMBER双向argmax + 条件聚合透视矩阵（主推）**

```sql
-- 解法一：上线日前取最后版本、上线日后取首周首版本，透视成迁移矩阵（@v2_date=2026-10-01）
WITH uver AS (                                        -- ① 用户×版本×日期去重
    SELECT DISTINCT user_id, version_id, login_date
    FROM login
    WHERE login_date >= @v2_date - INTERVAL 90 DAY    -- 回溯90天足够覆盖“来源版本”
),
pre AS (                                              -- ② 上线日前最后一次登录的版本
    SELECT user_id, version_id,
          ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date DESC) AS rn
    FROM uver
    WHERE login_date < @v2_date
),
post AS (                                             -- ③ 上线日后首周第一次登录的版本
    SELECT user_id, version_id,
          ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn
    FROM uver
    WHERE login_date >= @v2_date
      AND login_date <  @v2_date + INTERVAL 7 DAY
),
pair AS (                                             -- ④ 拼出“来源→目标”版本对
    SELECT p.user_id,
          p.version_id AS from_ver,
          q.version_id AS to_ver                         -- NULL = 首周未活跃
    FROM (SELECT user_id, version_id FROM pre  WHERE rn = 1) p
    LEFT JOIN (SELECT user_id, version_id FROM post WHERE rn = 1) q
      ON q.user_id = p.user_id
)
SELECT from_ver,
      COUNT(*)                                                       AS total_uv,
      SUM(CASE WHEN to_ver = '2.0' THEN 1 ELSE 0 END)                AS to_20,   -- 已迁移
      SUM(CASE WHEN to_ver = '1.5' THEN 1 ELSE 0 END)                AS stay_15, -- 滞留老版本
      SUM(CASE WHEN to_ver IS NULL THEN 1 ELSE 0 END)                AS no_login,-- 首周未活跃
      ROUND(SUM(CASE WHEN to_ver = '2.0' THEN 1 ELSE 0 END) / COUNT(*), 4) AS migrate_rate -- 迁移率
FROM pair
GROUP BY from_ver
ORDER BY total_uv DESC;
```

结果解读：若 `1.5→2.0 迁移率62%、滞留30%、首周未活跃8%`，而滞留用户集中在某个渠道包未更新，就指向渠道包发布问题而非用户意愿，推动强更排期。

**解法二：MAX(CASE WHEN)条件聚合argmax + 全条件聚合（Hive/老引擎友好）**

```sql
-- 解法二：不依赖窗口，用“关键日期匹配”取边界版本，再透视矩阵
WITH bounds AS (                                      -- ① 每用户两个关键日期
    SELECT user_id,
          MAX(CASE WHEN login_date <  @v2_date THEN login_date END) AS last_old_date,
          MIN(CASE WHEN login_date >= @v2_date
                    AND login_date <  @v2_date + INTERVAL 7 DAY
                    THEN login_date END) AS first_new_date
    FROM login
    WHERE login_date >= @v2_date - INTERVAL 90 DAY
      AND login_date <  @v2_date + INTERVAL 7 DAY
    GROUP BY user_id
),
ver_pair AS (                                         -- ② 按关键日期回表取版本（argmax经典写法）
    SELECT b.user_id,
          MAX(CASE WHEN l.login_date = b.last_old_date THEN l.version_id END) AS from_ver,
          MAX(CASE WHEN l.login_date = b.first_new_date THEN l.version_id END) AS to_ver
    FROM bounds b
    JOIN login l ON l.user_id = b.user_id
    GROUP BY b.user_id
)
SELECT from_ver,
      COUNT(*)                                                        AS total_uv,
      SUM(CASE WHEN to_ver = '2.0' THEN 1 ELSE 0 END)                 AS to_20,
      SUM(CASE WHEN to_ver = '1.5' THEN 1 ELSE 0 END)                 AS stay_15,
      SUM(CASE WHEN to_ver IS NULL THEN 1 ELSE 0 END)                 AS no_login,
      ROUND(SUM(CASE WHEN to_ver = '2.0' THEN 1 ELSE 0 END) / COUNT(*), 4) AS migrate_rate
FROM ver_pair
GROUP BY from_ver
ORDER BY total_uv DESC;
```

结果解读：解法二与解法一结果一致，机制上是"关键日期+条件聚合"替代窗口排序，在Hive上免去全表排序；若需迁移后30日留存，在ver_pair基础上再join第30日登录标记按 `from_ver, to_ver` 分组即可——矩阵每格的留存差异正是"迁移堵点"定位的关键。

> Hive/Spark SQL 差异：login 按月分区，回溯90天+首周共约4个分区；窗口ROW_NUMBER在Hive可用但全用户排序代价高，解法二的MAX(CASE WHEN)是Hive下更稳的argmax范式；多渠道服版本号命名不一致（1.5-hw/1.5-mi）时先做版本归一化映射表再进矩阵，避免矩阵被版本后缀炸开。

### 5. 性能分析与优化

两解法的核心都是两次用户粒度聚合（bounds/pre+post），login明细扫描限制在约94天窗口内，分区裁剪是第一优化；`(user_id, login_date)` 复合索引支持解法二的日期匹配回表。解法一窗口按user_id分区排序，代价=活跃用户数×94天登录行数，可先用 `WHERE login_date >= 上线日-90天` 减量；解法二bounds→login的回表join是用户粒度二次扫描，Hive下可cache bounds。矩阵透视本身是6×6级小结果集，代价忽略。工程化建议：把 ver_pair 沉淀为"版本迁移快照表"（按版本上线批次固化），迁移率、堵点定位、迁移后留存全部基于快照做轻量计算，历史批次可复现。**【加分点】** 能指出"来源版本应为老服还是全服""渠道服延迟更新是否单列"两个口径决策，说明真正做过版本复盘。

### 6. 面试延伸考点

- **“最后活跃版本”和“设备可升级的最高版本”口径有什么差异？**
  回答要点：前者是行为事实，后者是能力边界；滞留用户要区分"没得升（渠道包未发）"和"不肯升（存储/兼容顾虑）"，前者找渠道、后者找产品，混在一起会归错因。
- **迁移后留存下降，是版本体验问题还是匹配池变化？**
  回答要点：对比同批用户迁移前后的对局匹配时长、段位分布与好友在线变化——匹配池被新版本稀释（老版本用户骤减）也会拉低体验，不一定是新版本内容问题。
- **同日跨版本登录怎么处理？**
  回答要点：边界切分用login_time时间戳而非date；仍不唯一时按"当日最后一次登录的版本"取值并在口径文档声明，保证可复现。
- **矩阵怎么扩展成“版本×渠道×机型”多维迁移分析？**
  回答要点：ver_pair 宽表加渠道、机型维度后按需GROUP BY CUBE（Spark/Hive）或逐维出表；维度爆炸时先聚焦"滞留率最高的渠道×机型组合"下钻。

### 7. 业务拓展思考

迁移矩阵是版本发布质量的"验收单"：迁移率与迁移后留存共同决定强更力度、老服合并名单与渠道包发布策略；堵点定位（某渠道滞留异常）可直接转化为渠道运营的跟进工单。联动动作上，对滞留用户定向推送"新版本亮点+更新礼包"，对迁移后30日留存低的来源版本人群做内容承接（回归指引、段位保护），对长期滞留的老版本考虑兼容性优化或关服合并。口径延展上，同一框架可复用于"大区/服务器迁移""账号系统迁移"等场景，把版本流转矩阵升级为通用的"状态迁移分析"方法论。
