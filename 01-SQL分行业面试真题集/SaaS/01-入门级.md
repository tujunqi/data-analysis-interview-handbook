## SAAS-01 每月新签客户数统计

### 1. 业务背景

SaaS公司的销售运营团队每周一要向管理层汇报"获客节奏"：本季度每个月新签了多少家客户？是否追平月度目标？这个结论由销售运营分析师（谁）在周会与月度经营会之前（何时）统计得出，用来评估市场投放与销售团队拓客的成效，并决定下月火力分配（为什么）。口径上，"新签客户"以合同表的签约日期为准，且同一客户同月签多份合同（如年度合同之外又增购席位）只能计一次；如果口径不统一，销售与市场团队就会为"新增归谁"扯皮。**【避坑指南】**面试官首先看你有没有"去重"意识：直接COUNT(*)在多合同场景下必然出错。

### 2. 表结构说明

contracts（合同表），记录客户与SaaS公司签订的订阅合同：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |
| plan_name | VARCHAR(50) | 订阅套餐：基础版/专业版/旗舰版 |
| sign_date | DATE | 签约日期 |
| start_date | DATE | 服务开始日期 |
| end_date | DATE | 服务到期日期 |
| contract_amount | DECIMAL(12,2) | 合同总金额（元） |
| mrr | DECIMAL(10,2) | 月度经常性收入MRR（元/月） |
| is_renewal | TINYINT | 是否续签合同：0新签/1续签 |
| renewal_status | VARCHAR(20) | 续约状态：pending待续约/negotiating谈判中/renewed已续约/churn_risk流失风险，新签合同为NULL |
| contract_status | VARCHAR(20) | 合同状态：active生效/expired已到期/terminated作废 |

示例数据（5行）：

| contract_id | account_id | plan_name | sign_date | start_date | end_date | contract_amount | mrr | is_renewal | renewal_status | contract_status |
|-------------|------------|-----------|-----------|------------|----------|-----------------|-----|------------|----------------|-----------------|
| 3001 | 101 | 专业版 | 2025-01-08 | 2025-01-10 | 2026-01-09 | 96000.00 | 8000.00 | 0 | NULL | active |
| 3002 | 102 | 旗舰版 | 2025-01-15 | 2025-01-16 | 2026-01-15 | 180000.00 | 15000.00 | 0 | NULL | active |
| 3003 | 101 | 专业版 | 2025-01-25 | 2025-01-25 | 2026-01-09 | 12000.00 | 1000.00 | 0 | NULL | active |
| 3004 | 103 | 基础版 | 2025-02-03 | 2025-02-05 | 2025-05-04 | 15000.00 | 5000.00 | 0 | NULL | active |
| 3005 | 104 | 旗舰版 | 2025-02-18 | 2025-02-20 | 2026-02-19 | 216000.00 | 18000.00 | 0 | NULL | active |

### 3. 解题思路

先定口径：统计2025年以来每月新签客户数。"新签客户"指该月内出现签约行为的去重客户数。示例中客户101在1月签了两份合同（年度合同+席位增购协议），必须只计1次，因此核心聚合是COUNT(DISTINCT account_id)而非COUNT(*)。时间边界选用sign_date（签约日）而不是start_date（服务开始日），因为经营汇报中"新签"看的是商业动作发生的时点，销售目标达成与提成核算都挂在签约月。实现路径分三步：第一，用WHERE限定sign_date范围；第二，用DATE_FORMAT(sign_date,'%Y-%m')把日期截断到月粒度；第三，按月分组去重计数并按月份排序输出。易错点有三：一是忘写DISTINCT导致多合同客户被重复计数；二是月份输出没有ORDER BY导致乱序；三是严格口径下应确认是否剔除terminated作废合同，面试时主动说明这一层判断是加分项。

### 4. 参考解法

**解法一：DATE_FORMAT按月分组 + COUNT(DISTINCT)去重计数**

```sql
-- 统计2025年以来每月新签客户数
SELECT
    DATE_FORMAT(sign_date, '%Y-%m') AS sign_month,   -- 将签约日期格式化为"年-月"字符串
    COUNT(DISTINCT account_id)      AS new_accounts  -- 去重统计客户数，同月多合同只计一次
FROM contracts
WHERE sign_date >= '2025-01-01'                     -- 限定统计起点为2025年初
  AND contract_status <> 'terminated'               -- 剔除作废合同，保证口径干净
GROUP BY DATE_FORMAT(sign_date, '%Y-%m')            -- 按签约月份分组
ORDER BY sign_month;                                -- 按月份升序，时间序列更直观
```

结果解读：1月虽有三笔签约（3001、3002、3003），但只涉及101、102两家客户，因此1月新签客户数为2；客户101当月的席位增购协议验证了"同月多合同只计一次"的口径。

**解法二：先在子查询中按"客户+月份"去重，再外层汇总**

```sql
-- 先把数据压缩到"客户×月份"粒度，外层再统计，方便扩展衍生指标
SELECT
    sign_month,                    -- 签约月份
    COUNT(*)       AS new_accounts, -- 每月去重后的客户数（子查询中每客户仅一行）
    SUM(month_mrr) AS new_mrr       -- 衍生指标：当月新签MRR合计
FROM (
    SELECT
        account_id,                                        -- 客户ID
        DATE_FORMAT(sign_date, '%Y-%m') AS sign_month,     -- 签约月份
        SUM(mrr)                        AS month_mrr       -- 该客户当月全部合同MRR之和（含增购）
    FROM contracts
    WHERE sign_date >= '2025-01-01'                        -- 限定统计起点
      AND contract_status <> 'terminated'                  -- 剔除作废合同
    GROUP BY account_id, DATE_FORMAT(sign_date, '%Y-%m')   -- 客户+月份唯一，完成去重
) t
GROUP BY sign_month             -- 外层按月汇总
ORDER BY sign_month;            -- 按月份升序输出
```

结果解读：子查询先把数据压到"客户×月份"粒度，外层顺势扩展出每月新签MRR等指标；与解法一结果一致，但为后续扩展留了口子，是更常见的工程化写法。

### 5. 性能分析与优化

解法一对contracts做一次扫描加临时表分组，WHERE条件是sign_date上的连续区间（可走索引），DATE_FORMAT只出现在SELECT与GROUP BY中，不影响索引命中；解法二多一层子查询分组，会多产生一个派生表（临时表），代价略高，但换来指标扩展性。可执行优化：一是为contracts建立覆盖索引 idx_sign_date_account(sign_date, account_id, mrr)，让两个解法都不必回表；二是统计范围明确时补上右边界（sign_date < '2026-01-01'）收窄扫描区间；三是数据量达到千万级时，改为T+1日粒度预聚合表（签约日、客户数、MRR），查询时再按月卷积，把线上查询从扫明细变成扫汇总。

### 6. 面试延伸考点

- **如果同月既有新签又有续约合同，怎么只统计"纯新签"？** 回答要点：加is_renewal=0过滤；更严谨的口径是取客户的首次签约月（可用窗口函数MIN(sign_date) OVER(PARTITION BY account_id)或客户维表上的first_sign_date字段），避免把老客复购误计为新客。
- **为什么用sign_date而不是start_date做口径？** 回答要点：新签反映商业动作时点，销售目标、提成、市场归因都按签约月核算；start_date是服务起算日，用于收入确认与交付排期，两者服务不同的管理目的。
- **COUNT(DISTINCT)在超大表上有什么问题？** 回答要点：去重需要内存或临时表，代价高；可改用预聚合、按月分区裁剪，或对精度要求不高的场景使用近似去重算法。
- **如何验证这个数是对的？** 回答要点：抽样核对个别多合同客户是否只计一次，与CRM系统报表、财务开票记录交叉对账，口径文档化。

### 7. 业务拓展思考

每月新签客户数是SaaS最上游的经营信号，直接联动两个动作：市场侧按来源拆分评估投放ROI，销售侧按月追平目标并调整人力部署。口径上可延展为新签MRR、新签客单价（合同额/客户数）、分行业/分区域新签结构，观察"量的增长是否伴随质的提升"。下游还可衔接客户成功团队的新客户交付排期——新签客户数决定未来30天的onboarding负荷，提前预警交付资源缺口。

## SAAS-02 各套餐客户数与MRR

### 1. 业务背景

产品与定价委员会每季度复盘套餐结构：基础版、专业版、旗舰版各沉淀了多少付费客户？各自贡献了多少MRR（月度经常性收入）？这份数据由商业分析师（谁）在季度定价复盘会前（何时）统计，用来判断低价套餐是否在"白送流量"、高价套餐是否增长乏力，进而决定套餐定价与包装调整（为什么）。MRR口径上只统计状态为active的生效合同，到期未续和作废合同不再贡献经常性收入。**【面试高频】**"MRR为什么只算生效合同"是SaaS面试的经典口径题，回答不出会直接暴露业务理解不足。

| sign_date | DATE | 签约日期 |
| start_date | DATE | 服务开始日期 |
| end_date | DATE | 服务到期日期 |
| contract_amount | DECIMAL(12,2) | 合同总金额（元） |
| mrr | DECIMAL(10,2) | 月度经常性收入MRR（元/月） |
| is_renewal | TINYINT | 是否续签合同：0新签/1续签 |
| renewal_status | VARCHAR(20) | 续约状态，新签合同为NULL |
| contract_status | VARCHAR(20) | 合同状态：active生效/expired已到期/terminated作废 |

### 3. 解题思路

先明确口径：按套餐分组，输出两个指标——去重客户数与MRR合计。客户数必须COUNT(DISTINCT account_id)，因为同一客户可能有增购合同；MRR直接SUM(mrr)，且只统计contract_status='active'的合同——expired（到期未续）与terminated（作废）合同不再贡献经常性收入。若希望更严格，还可以关联accounts排除已流失（churned）客户，避免历史合同残留干扰。实现路径：解法一只用合同表单表分组；解法二INNER JOIN客户表，同时排除流失客户并补充"户均MRR"（MRR合计/去重客户数）这一质量指标。易错点：一是忘记过滤合同状态导致MRR虚高；二是户均MRR的除数必须用去重客户数而不是COUNT(*)，否则多合同客户会把分母撑大。

### 4. 参考解法

**解法一：合同表单表GROUP BY，双指标聚合**

```sql
-- 按套餐统计生效合同的客户数与MRR合计
SELECT
    c.plan_name,                                   -- 套餐名称
    COUNT(DISTINCT c.account_id) AS account_cnt,   -- 去重客户数，防一客户多合同重复
    SUM(c.mrr)                   AS total_mrr      -- 该套餐MRR合计
FROM contracts c
WHERE c.contract_status = 'active'                 -- 只统计生效合同，到期/作废不计入MRR
GROUP BY c.plan_name                               -- 按套餐分组
ORDER BY total_mrr DESC;                           -- 按MRR贡献降序，快速定位收入支柱
```

结果解读：示例中专业版的合同4005已到期不计入，旗舰版虽只有1家客户却是MRR主力；基础版客户多但户均贡献低，符合典型的金字塔结构。

**解法二：JOIN客户表排除流失客户，并计算户均MRR**

```sql
-- 关联客户表，排除已流失客户后按套餐统计，并给出户均MRR质量指标
SELECT
    c.plan_name,                                          -- 套餐名称
    COUNT(DISTINCT c.account_id)        AS account_cnt,   -- 去重客户数
    SUM(c.mrr)                          AS total_mrr,     -- MRR合计
    ROUND(SUM(c.mrr) / COUNT(DISTINCT c.account_id), 0) AS avg_mrr -- 户均MRR，衡量套餐含金量
FROM contracts c
INNER JOIN accounts a ON a.account_id = c.account_id      -- 关联客户表校验客户状态
WHERE c.contract_status = 'active'                        -- 仅生效合同
  AND a.account_status <> 'churned'                       -- 排除已流失客户，剔除历史残留
GROUP BY c.plan_name
ORDER BY total_mrr DESC;
```

结果解读：流失客户205的专业版合同即便还剩active状态也会被剔除，避免"已流失却仍在贡献MRR"的口径矛盾；户均MRR可以直接对比各套餐的定价效率。

### 5. 性能分析与优化

解法一是单表扫描加分组，代价最低，为contracts建 (contract_status, plan_name, account_id, mrr) 复合索引可减少过滤与分组开销；解法二多一次JOIN，驱动表应是过滤后更小的合同结果集，MySQL会自动选择，但需保证accounts.account_id为主键（默认有索引）避免JOIN退化。进一步优化：MRR看板通常按月固定出数，建议建立每日MRR快照表（快照日、套餐、客户数、MRR），查询直接取最新快照，把实时聚合改为读预聚合；若套餐维度有限（3-5个），也可用条件聚合一次扫描输出所有套餐，减少分组次数。

### 6. 面试延伸考点

- **MRR和合同总金额（contract_amount）是什么关系？** 回答要点：MRR是月度经常性收入（订阅费/月），合同总额是整个合同期的一次性商业价值；ARR≈MRR×12；合同额可能包含一次性实施费，计入MRR会虚增经常性收入。
- **一个客户同时有多份生效合同，客户数和MRR分别怎么算？** 回答要点：客户数用DISTINCT去重；MRR应将多份合同相加（增购扩容属正常口径）；若要看"客户口径"的结构，需先按客户聚合到一行再分组。
- **为什么排除churned客户？** 回答要点：客户已流失但合同状态可能未及时同步为expired，做客户状态二次校验能兜住数据质量风险，这是真实数仓里常见的脏数据。
- **席位数变化对MRR有什么影响？** 回答要点：席位计费模式下MRR=席位数×单席月价，增购席位会产生新的增购合同或合同变更单，MRR随之上升，属于扩张收入（Expansion MRR）。

### 7. 业务拓展思考

套餐维度的客户数与MRR结构是定价策略的仪表盘：若基础版客户数占比高但MRR占比极低，说明免费/低价层沉淀了大量"饲料用户"，可推动升级引导或功能墙调整；若旗舰版续约率高且户均MRR上行，则验证高价打法可行。口径可延展为各套餐的新签MRR、扩张MRR与降级MRR，形成套餐迁移矩阵；联动动作上，可把低套餐高用量客户名单推给销售做升级外呼，把旗舰版客户交给专属客户成功经理维护。

## SAAS-03 月活跃用户数统计

### 1. 业务背景

客户成功团队每月初要交付"健康度报告"：每个客户上个月有多少终端用户真实使用了产品？月活跃用户数（MAU）是衡量产品是否被"用起来"的核心指标——签了约但没人用的客户，续约风险极高。该统计由数据分析师（谁）在每月初（何时）完成，供客户成功经理（CSM）按客户分层跟进：活跃骤降的客户触发挽回动作，活跃稳定的客户推动增购席位（为什么）。口径上，"活跃"= 当月产生过使用行为的去重用户；是否把"仅登录"算作活跃，需要与业务方确认。**【面试高频】**"活跃口径怎么定"几乎是必考追问，动手前先说清口径是标准动作。

### 2. 表结构说明

usage_logs（使用日志表），记录用户在产品内的行为流水：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| log_id | BIGINT | 日志ID，主键 |
| user_id | INT | 用户ID |
| account_id | INT | 所属客户ID |
| module_name | VARCHAR(50) | 使用功能模块：报表中心/商品管理/工单系统等 |
| action_type | VARCHAR(20) | 行为类型：login登录/query查询/export导出报表 |
| action_date | DATE | 行为日期 |

示例数据（5行）：

| log_id | user_id | account_id | module_name | action_type | action_date |
|--------|---------|------------|-------------|-------------|-------------|
| 50001 | 9001 | 101 | 报表中心 | login | 2025-06-01 |
| 50002 | 9001 | 101 | 报表中心 | export | 2025-06-03 |
| 50003 | 9002 | 101 | 商品管理 | login | 2025-06-05 |
| 50004 | 9003 | 102 | 报表中心 | query | 2025-06-20 |
| 50005 | 9001 | 101 | 报表中心 | login | 2025-07-01 |

### 3. 解题思路

先定口径：月活=统计月内产生过任意使用行为的去重用户数。时间边界用"左闭右开"写法（action_date >= 月初 AND action_date < 次月1日），比BETWEEN月初AND月末更稳——不必纠结MONTH函数的跨年问题，也不会漏掉月末最后一天的边界。实现路径：解法一单指标直接COUNT(DISTINCT user_id)；解法二用条件聚合一次扫描同时输出月活与各自然周活跃数，用于观察活跃在月内的分布——如果周活跃递减，说明客户月底基本没人用，是交付脱手的信号。易错点：一是忘了去重，同一用户当月多次行为会被重复计数；二是日期边界写成BETWEEN '2025-06-01' AND '2025-06-31'会因6月没有31日而报错或漏数；三是若业务定义"活跃"须排除纯登录，需加action_type过滤，动笔前要确认。

### 4. 参考解法

**解法一：日期范围过滤 + COUNT(DISTINCT)求月活**

```sql
-- 统计2025年6月的月活跃用户数（MAU）
SELECT
    COUNT(DISTINCT user_id) AS mau    -- 当月出现过的去重用户数即月活
FROM usage_logs
WHERE action_date >= '2025-06-01'     -- 月初（含当天）
  AND action_date <  '2025-07-01';    -- 左闭右开写法，天然覆盖到6月30日23:59
```

结果解读：6月内9001、9002、9003三个用户都有行为，月活为3；用户9001当月多条日志去重后只计一次，用户9001的7月1日记录被边界条件正确排除。

**解法二：条件聚合一次输出月活与各周活跃（活跃分布诊断）**

```sql
-- 一行输出：6月月活与各自然周活跃人数，观察活跃在月内的分布
SELECT
    COUNT(DISTINCT user_id) AS mau,                                        -- 整月去重活跃
    COUNT(DISTINCT CASE WHEN action_date BETWEEN '2025-06-01' AND '2025-06-07'
                        THEN user_id END) AS week1_active,                 -- 第1周活跃
    COUNT(DISTINCT CASE WHEN action_date BETWEEN '2025-06-08' AND '2025-06-14'
                        THEN user_id END) AS week2_active,                 -- 第2周活跃
    COUNT(DISTINCT CASE WHEN action_date BETWEEN '2025-06-15' AND '2025-06-21'
                        THEN user_id END) AS week3_active,                 -- 第3周活跃
    COUNT(DISTINCT CASE WHEN action_date BETWEEN '2025-06-22' AND '2025-06-30'
                        THEN user_id END) AS week4_active                  -- 第4周活跃
FROM usage_logs
WHERE action_date >= '2025-06-01'      -- 限定统计月
  AND action_date <  '2025-07-01';     -- 左闭右开边界
```

结果解读：CASE WHEN未命中的行返回NULL，COUNT(DISTINCT)天然忽略NULL，因此各周只统计各自区间内的用户；一次表扫描同时得到五个指标，周活跃对比月活能判断用户是"全月稳定使用"还是"只在月初露面"。

### 5. 性能分析与优化

usage_logs是典型的大流水表，解法一按日期范围扫描后去重，解法二同一次扫描做五次条件去重，CPU开销略高但省去多次扫表，整体优于跑五条SQL。优化建议：一是为usage_logs建 (action_date, user_id) 复合索引，或按action_date做_RANGE分区，让月度查询只扫一个分区；二是流水表通常上亿行，工程上普遍采用"按天预聚合"——先写 daily_active_user(统计日、客户、活跃用户数) 中间表，月活对天表去重或直接SUM近似，查询耗时从分钟级降到秒级；三是如需精确月活，可按月维护"月内活跃用户位图/集合"再计数。

### 6. 面试延伸考点

- **"活跃"应该怎么定义？登录算不算？** 回答要点：SaaS场景建议以有效业务行为（生成报表、导出、查询）为准，纯login可能包含自动心跳与误触；口径要写进指标字典并与客户成功团队对齐。
- **DAU/MAU是什么？说明什么问题？** 回答要点：粘性指标，比值越接近1说明用户几乎天天用；SaaS工具类产品该值天然低于社交产品，可按客户分层对比找异常。
- **如何把月活拆到客户维度？** 回答要点：GROUP BY account_id后COUNT(DISTINCT user_id)，再关联席位数为"席位活跃率=月活/已购席位"，这是客户健康分的核心输入。
- **日志表重复上报怎么办？** 回答要点：先按log_id或用户+模块+日期粒度去重（ROW_NUMBER或DISTINCT），与埋点团队确认上报语义，避免活跃虚高。

### 7. 业务拓展思考

月活是"交付价值是否落地"的试金石：签约只代表商业成功，活跃才代表客户真的在用，而持续使用是续约的前提。可延展的口径包括席位活跃率、核心功能渗透率（用过报表中心的客户占比）、活跃衰减预警（本月月活环比降幅超30%的客户名单）。联动动作上，客户成功经理对活跃下滑客户发起健康回访与培训排期，对高活跃客户推动增购席位与高级模块试用，把使用数据变成二次销售的线索池。

## SAAS-04 工单状态分布与解决率

### 1. 业务背景

交付与服务运营团队每周出"服务健康周报"：本周期内客户提交的工单处于什么状态分布？解决率是多少？有多少工单还压在手上？这份数据由服务运营分析师（谁）每周一（何时）统计，用来评估支持团队的负载与响应质量：open积压过多说明人手不足，pending过多说明客户响应拖了后腿，解决率下滑则预示客户不满与续约风险（为什么）。工单是SaaS交付质量的温度计，工单数据经常被面试官用来考察分组统计与占比计算。**【加分点】**能主动把"占比"算出来并解释各状态的业务含义，比只会COUNT(*)高一个层级。

### 2. 表结构说明

tickets（工单表），记录客户提交的服务请求：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| ticket_id | INT | 工单ID，主键 |
| account_id | INT | 提交工单的客户ID |
| ticket_type | VARCHAR(20) | 工单类型：consult咨询/fault故障/complaint投诉 |
| status | VARCHAR(20) | 状态：open处理中/pending待客户响应/resolved已解决/closed已关闭 |
| priority | VARCHAR(10) | 优先级：P0紧急/P1高/P2普通 |
| created_at | DATETIME | 工单创建时间 |
| resolved_at | DATETIME | 解决时间，未解决为NULL |

示例数据（5行）：

| ticket_id | account_id | ticket_type | status | priority | created_at | resolved_at |
|-----------|------------|-------------|--------|----------|------------|-------------|
| 6001 | 201 | fault | open | P1 | 2025-07-02 09:15:00 | NULL |
| 6002 | 202 | consult | resolved | P2 | 2025-07-03 14:30:00 | 2025-07-03 18:00:00 |
| 6003 | 203 | fault | pending | P0 | 2025-07-05 10:00:00 | NULL |
| 6004 | 201 | complaint | closed | P1 | 2025-07-08 16:45:00 | 2025-07-10 11:20:00 |
| 6005 | 204 | consult | open | P2 | 2025-07-09 11:05:00 | NULL |

### 3. 解题思路

先定口径：统计2025年7月以来创建的工单，按status分组输出工单数与占比，解决率=(resolved+closed)/总数。占比计算的核心是"分组计数除以总数"，总数可以用子查询获得，也可以在一次扫描里用窗口函数SUM(COUNT(*)) OVER()获得，入门阶段先用子查询，逻辑直白。实现路径：解法一按状态分组计数并除以总数得占比；解法二用CASE WHEN把四个状态转成一行四列（行转列），并顺带算解决率，适合直接贴进固定格式的周报表格。易错点：一是整数除法——COUNT(*)/COUNT(*)在MySQL里会截断为0或1，必须乘100.0或用ROUND转成小数；二是占比的分母要用同一过滤条件下的总数，内外WHERE不一致会导致占比加起来超过100%；三是resolved与closed在业务上都算"已完成"，口径要写清楚。

### 4. 参考解法

**解法一：GROUP BY分组计数 + 子查询提供总数算占比**

```sql
-- 统计7月以来各状态工单数量及占比
SELECT
    t.status,                                        -- 工单状态
    COUNT(*)                     AS ticket_cnt,      -- 该状态工单数
    ROUND(COUNT(*) * 100.0 /
          (SELECT COUNT(*) FROM tickets
            WHERE created_at >= '2025-07-01'), 2) AS pct -- 占比=分组数/同口径总数，乘100.0避免整数除法
FROM tickets t
WHERE t.created_at >= '2025-07-01'                   -- 与子查询保持同一过滤口径
GROUP BY t.status
ORDER BY ticket_cnt DESC;                            -- 按数量降序，最大问题状态排最前
```

结果解读：示例中open有2单、pending 1单、resolved与closed各1单，处理中占比40%；open积压占比高提示支持团队负载偏重，pending则要去催客户响应。

**解法二：CASE WHEN行转列，一行输出状态分布与解决率**

```sql
-- 行转列：一行输出工单状态分布，直接嵌入周报模板
SELECT
    COUNT(*) AS total_tickets,                                            -- 工单总数
    SUM(CASE WHEN status = 'open'     THEN 1 ELSE 0 END) AS open_cnt,     -- 处理中数量
    SUM(CASE WHEN status = 'pending'  THEN 1 ELSE 0 END) AS pending_cnt,  -- 待客户响应数量
    SUM(CASE WHEN status = 'resolved' THEN 1 ELSE 0 END) AS resolved_cnt, -- 已解决数量
    SUM(CASE WHEN status = 'closed'   THEN 1 ELSE 0 END) AS closed_cnt,   -- 已关闭数量
    ROUND(SUM(CASE WHEN status IN ('resolved', 'closed')
                   THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2)
                                        AS resolve_rate_pct               -- 解决率=(已解决+已关闭)/总数
FROM tickets
WHERE created_at >= '2025-07-01';     -- 统计周期
```

结果解读：五个状态指标压缩成一行，解决率52%左右波动即需关注；行转列写法适合状态枚举固定的场景，新增状态时需改SQL是它的代价。

### 5. 性能分析与优化

解法一会扫两遍tickets（主体一遍、子查询总数一遍，MySQL可能把子查询缓存为派生表只算一次，但计划上仍是一次聚合加一次关联）；解法二只扫一遍，单次聚合输出全部指标，效率更高，代价是SQL与状态枚举耦合。优化建议：一是为tickets建 (created_at, status) 复合索引，让时间过滤快速定位；二是工单状态变更频繁，可在数仓里做每日工单状态快照表，周报直接读快照，避免线上业务库被分析查询拖慢；三是若需按客户/类型下钻，把status与ticket_type做成维表映射而非硬编码枚举，降低维护成本。

### 6. 面试延伸考点

- **占比计算为什么必须乘100.0或用ROUND？** 回答要点：MySQL中两个整数相除默认按整数位截断（结果是0或1），乘100.0把分子转成小数才能得到正确百分比。
- **怎么统计平均解决时长？** 回答要点：AVG(TIMESTAMPDIFF(HOUR, created_at, resolved_at))，注意resolved_at为NULL的行TIMESTAMPDIFF返回NULL，AVG自动忽略，但要确认"未解决不参与均值"是否符合口径。
- **工单量突然暴涨，你从哪几个维度下钻？** 回答要点：按客户（是否个别客户集中爆发）、按类型（是否版本升级引发批量故障）、按模块（是否新功能有缺陷）、按时间（是否某天发布导致尖峰），先定位再归因。
- **pending状态过多说明什么？** 回答要点：等待客户补充信息的工单积压，要么是客户侧响应慢，要么是我方催办机制缺失，应区分对待而不是一刀切算支持团队效率。

### 7. 业务拓展思考

工单状态分布是客户成功的先行指标：工单长期未解决或P0故障频发的客户，续约概率显著下降，应把"高危工单客户清单"每周推送给CSM做前置干预。口径可延展为首响时长、解决时长分位数（P50/P90）、重复报障率（同一客户同一问题30天内多次提交），这些比单纯的解决率更能反映服务质量。再进一步，可以把工单数据与MRR关联，算"风险工单覆盖的MRR敞口"，让服务问题直接换算成收入风险，向管理层要资源时更有说服力。

## SAAS-05 试用中客户清单与剩余天数

### 1. 业务背景

SaaS的免费试用是签约前的关键窗口：客户成功与销售团队每天早上要拿到"试用中客户清单"，按试用剩余天数排序，优先跟进临期客户——剩余3天以内的客户必须当天触达，推动试用期内完成付费转化，否则窗口一过转化率断崖式下跌。这份数据由销售运营（谁）每个工作日晨会前（何时）导出，供一线销售与CSM按紧急度分工触达（为什么）。清单要素包括客户名称、试用起止日期与剩余天数，剩余天数用到期日减去当天动态计算。**【避坑指南】**试用结束日早于今天的"僵尸试用"是常见脏数据，不过滤会让销售白跑。

### 2. 表结构说明

accounts（客户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |
| account_name | VARCHAR(100) | 客户公司名称 |
| industry | VARCHAR(50) | 客户所属行业 |
| region | VARCHAR(50) | 客户所在区域 |
| owner_name | VARCHAR(30) | 负责该客户的客户经理 |
| account_status | VARCHAR(20) | 客户状态：trial试用中/paying付费中/churned已流失 |
| trial_start_date | DATE | 试用开始日期，未试用为NULL |
| trial_end_date | DATE | 试用结束日期，未试用为NULL |
| created_at | DATE | 客户建档日期 |

示例数据（5行，假设今天是2025-07-22）：

| account_id | account_name | industry | region | owner_name | account_status | trial_start_date | trial_end_date | created_at |
|------------|--------------|----------|--------|------------|----------------|------------------|----------------|------------|
| 301 | 惠民大药房 | 医药 | 华南 | 陈晓 | trial | 2025-07-01 | 2025-07-31 | 2025-06-25 |
| 302 | 蜀香餐饮集团 | 餐饮 | 西南 | 陈晓 | trial | 2025-07-10 | 2025-08-09 | 2025-07-05 |
| 303 | 迅风汽配 | 汽配 | 华东 | 赵磊 | trial | 2025-06-20 | 2025-07-20 | 2025-06-15 |
| 304 | 中原建材市场 | 建材 | 华中 | 赵磊 | paying | 2025-05-01 | 2025-05-31 | 2025-04-20 |
| 305 | 江南文旅集团 | 文旅 | 华东 | 孙倩 | trial | 2025-07-18 | 2025-08-17 | 2025-07-12 |

### 3. 解题思路

先定口径：清单=account_status为trial且试用尚未到期的客户；剩余天数=trial_end_date减去今天（CURDATE()），用DATEDIFF(结束日, 开始日)计算，注意MySQL的DATEDIFF是"前者减后者"，顺序写反会得到负数。边界处理上要加trial_end_date >= CURDATE()，把状态没更新但已过期的脏数据兜住。实现路径：解法一直接输出明细清单并按剩余天数升序——天数最少的排最前，销售从上往下打电话；解法二在明细之上用CASE WHEN把剩余天数分层为"3天内/7天内/14天内/14天以上"四档紧急度标签，方便晨会直接按档分工。易错点：一是DATEDIFF参数顺序；二是忘记CURDATE()是"运行当天"，SQL重跑结果会漂移，正式报表应传参固定统计日期；三是试用30天是常见配置，但不要把30写死在判断里，剩余天数必须动态算。

### 4. 参考解法

**解法一：DATEDIFF动态计算剩余天数，按紧迫度升序输出**

```sql
-- 试用中客户清单，按剩余天数升序（最紧急的排最前）
SELECT
    account_name,                                     -- 客户名称
    owner_name,                                       -- 负责客户经理，便于分派
    trial_start_date,                                 -- 试用开始日
    trial_end_date,                                   -- 试用结束日
    DATEDIFF(trial_end_date, CURDATE()) AS days_left  -- 剩余天数=结束日-今天，MySQL为前者减后者
FROM accounts
WHERE account_status = 'trial'                        -- 只看试用中的客户
  AND trial_end_date >= CURDATE()                     -- 兜底过滤已过期但状态未更新的脏数据
ORDER BY days_left ASC;                               -- 剩余天数少的排前面，销售按序触达
```

结果解读：示例统计日（2025-07-22）下客户303的试用已在7月20日到期会被过滤，301剩余9天、302剩余18天、305剩余26天；清单从上到下即销售外呼的优先顺序。

**解法二：CASE WHEN把剩余天数分层为紧急度标签**

```sql
-- 在清单基础上输出紧急度分层，晨会按档位分工
SELECT
    a.account_name,                                        -- 客户名称
    a.owner_name,                                          -- 负责客户经理
    DATEDIFF(a.trial_end_date, CURDATE()) AS days_left,    -- 剩余天数
    CASE
        WHEN DATEDIFF(a.trial_end_date, CURDATE()) <= 3  THEN 'A-紧急（3天内到期）'
        WHEN DATEDIFF(a.trial_end_date, CURDATE()) <= 7  THEN 'B-重要（7天内到期）'
        WHEN DATEDIFF(a.trial_end_date, CURDATE()) <= 14 THEN 'C-常规（14天内到期）'
        ELSE 'D-充裕（14天以上）'
    END AS urgency_level                                   -- 紧急度分层标签，CASE按序短路匹配
FROM accounts a
WHERE a.account_status = 'trial'                           -- 试用中
  AND a.trial_end_date >= CURDATE()                        -- 排除已过期
ORDER BY days_left ASC;                                    -- 越紧急越靠前
```

结果解读：分层标签让"谁今天必须被联系上一目了然"；A档客户建议由销售+CSM双人跟进，D档客户先做产品教育不急于逼单。

### 5. 性能分析与优化

accounts是客户维表，量级通常在几万到几十万，两解法都是全表扫描加过滤，代价可控；DATEDIFF与CURDATE()的运算只出现在SELECT和ORDER BY，不影响WHERE里account_status的索引命中。优化建议：一是为accounts建 (account_status, trial_end_date) 复合索引，试用客户通常只占客户总量的小部分，索引能显著缩小扫描范围；二是把该查询固化为每日晨会报表时，用带参数的统计日期替代CURDATE()，保证历史重跑结果一致（可复现性）；三是若清单要按客户经理分发给多人，可在SQL外层按owner_name排序，或直接在BI工具里做行级权限过滤。

### 6. 面试延伸考点

- **MySQL的DATEDIFF参数顺序是什么？和SQL Server一致吗？** 回答要点：MySQL是DATEDIFF(日期1, 日期2)=日期1减日期2；SQL Server是DATEDIFF(单位, 开始, 结束)，跨数据库迁移时极易写反，属于经典坑。
- **CURDATE()直接写进报表SQL有什么问题？** 回答要点：结果是"运行当天"，当天重跑多次结果一致但跨天不可复现；正式任务应传入业务日期参数，凌晨任务尤其要注意"跑的是昨天还是今天"。
- **试用到期前应该怎么安排触达？** 回答要点：分层节奏——开通第1天做激活引导、第15天检查使用深度、到期前3天进入成交冲刺、到期当天提供延长试用或折扣选项，每档对应不同动作。
- **如何衡量试用整体转化情况？** 回答要点：试用转付费率=试用且转付费客户数/同期到期试用客户数，分母只算"已到期"的试用，避免把还在试用期的新客算进流失。

### 7. 业务拓展思考

试用临期清单是SaaS最典型的"时间敏感型"运营数据，价值在于把有限的销售精力压在转化概率最高的窗口上。口径可延展为试用客户的使用深度（试用期间月活、核心功能是否被用过）——使用活跃的临期客户转化概率远高于"开通即沉睡"的客户，两者应有不同的跟进话术；还可以按行业和来源拆分试用转化率，反哺市场投放：某渠道试用多但转化差的，要在投放端降权。联动动作上，A档客户触发"销售+CSM"双人机制，到期未转化的客户进入培育池（nurture pool）等待二次激活。

## SAAS-06 线索来源分布与转化率

### 1. 业务背景

市场团队每季度要回答"钱花对地方了吗"：官网表单、百度SEM、行业展会、老客转介绍、短视频等各渠道带来多少线索？各自的付费转化率是多少？这份复盘由市场运营分析师（谁）在季度市场复盘会前（何时）统计，用来决定下季度预算在渠道间的再分配——线索量大但转化差的渠道要降权，线索少但转化高的渠道要加投（为什么）。转化率=线索中最终成为付费客户的比例，用0/1标记字段的均值即可算出。**【加分点】**主动提出"小样本渠道的转化率不可信"，并给出样本量下限的处理方式，是数据人判断力的直接体现。

### 2. 表结构说明

leads（线索表），记录市场渠道获取的销售线索及其转化结果：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| lead_id | INT | 线索ID，主键 |
| lead_name | VARCHAR(100) | 线索联系人/意向公司 |
| source | VARCHAR(30) | 来源渠道：官网表单/百度SEM/行业展会/老客转介绍/短视频 |
| owner_name | VARCHAR(30) | 跟进销售 |
| created_at | DATE | 线索创建日期 |
| converted_flag | TINYINT | 是否转化为付费客户：1是/0否 |

示例数据（5行）：

| lead_id | lead_name | source | owner_name | created_at | converted_flag |
|---------|-----------|--------|------------|------------|----------------|
| 2001 | 锦枫贸易-王总 | 官网表单 | 刘洋 | 2025-03-02 | 1 |
| 2002 | 朗顿教育-李老师 | 百度SEM | 刘洋 | 2025-03-05 | 0 |
| 2003 | 万象展览集团 | 行业展会 | 孙倩 | 2025-03-18 | 1 |
| 2004 | 优家家居 | 老客转介绍 | 孙倩 | 2025-04-01 | 1 |
| 2005 | 星动MCN | 短视频 | 刘洋 | 2025-04-12 | 0 |

### 3. 解题思路

先定口径：统计2025年以来各渠道的线索量、转化数与转化率。转化率的实现有两种等价写法：一是AVG(converted_flag)——0/1字段的算术平均值就是"1所占的比例"，这是SQL里最优雅的技巧之一；二是SUM(CASE WHEN converted_flag=1 THEN 1 ELSE 0 END)/COUNT(*)，更直白但啰嗦。渠道样本量差异极大（SEM可能几千条、展会可能几十条），小样本渠道的转化率会被个别线索放大，因此解法二加HAVING COUNT(*) >= 20做样本量下限过滤，这正是HAVING与WHERE分工的经典案例：WHERE过滤原始行，HAVING过滤聚合后的组。易错点：一是转化率直接用整数除法丢失小数；二是把SUM(converted_flag)当转化率（那只是转化数）；三是忘了HAVING只能用在GROUP BY之后，写在WHERE里会报错。

### 4. 参考解法

**解法一：AVG布尔值技巧直接求转化率**

```sql
-- 各渠道线索量与转化率
SELECT
    source,                                        -- 线索来源渠道
    COUNT(*)                        AS lead_cnt,   -- 线索总量
    SUM(converted_flag)             AS conv_cnt,   -- 转化数：1的和即转化成功的条数
    ROUND(AVG(converted_flag) * 100, 2) AS conv_rate_pct -- 0/1字段的均值即比例，乘100转百分数
FROM leads
WHERE created_at >= '2025-01-01'                   -- 统计2025年以来的线索
GROUP BY source                                    -- 按渠道分组
ORDER BY lead_cnt DESC;                            -- 先看量级排名，量是转化的前提
```

结果解读：示例中老客转介绍与展会各1条且全部转化，虽然转化率100%但样本只有1条，不能直接下"转介绍最优"的结论；看渠道要先比量、再比率、最后比样本可信度。

**解法二：SUM(CASE WHEN)显式求和 + HAVING过滤小样本渠道**

```sql
-- 转化率显式写法，并用HAVING过滤线索量过小的渠道
SELECT
    source,                                              -- 渠道
    COUNT(*) AS lead_cnt,                                -- 线索量
    SUM(CASE WHEN converted_flag = 1 THEN 1 ELSE 0 END)  AS conv_cnt, -- 命中转化记1求和
    ROUND(SUM(CASE WHEN converted_flag = 1 THEN 1 ELSE 0 END)
          * 100.0 / COUNT(*), 2)                         AS conv_rate_pct -- 转化率=转化数/总量
FROM leads
WHERE created_at >= '2025-01-01'                         -- WHERE过滤原始行
GROUP BY source
HAVING COUNT(*) >= 20                                    -- HAVING过滤聚合后的组：样本量>=20才参与比较
ORDER BY conv_rate_pct DESC;                             -- 按转化率降序，评估渠道质量
```

结果解读：HAVING把线索量不足20的渠道排除在排名之外，避免"3条线索转化2条=67%"这类统计噪音误导预算决策；这是WHERE与HAVING分工的标准示范。

### 5. 性能分析与优化

leads表量级通常在几十万级，两解法都是单表一次扫描加分组，差别仅在AVG与SUM(CASE WHEN)的表达式开销，几乎可忽略。优化建议：一是为leads建 (created_at, source, converted_flag) 复合索引，时间过滤可以直接走索引范围扫描，分组与聚合列被索引覆盖后无需回表；二是若该报表按周/按月固定刷新，建立"渠道×月"预聚合中间表，转化率在聚合时算好存列；三是converted_flag若存在NULL（未跟进完的线索），AVG会把NULL行从分母剔除，等于"只统计已定论的线索"，口径上要确认这是想要的结果，否则应补COALESCE(converted_flag, 0)或过滤created_at更早的批次。

### 6. 面试延伸考点

- **AVG(converted_flag)为什么能算转化率？** 回答要点：0/1标记列的均值=Σ1的数量/总行数，即布尔值的期望，等价于SUM/COUNT；这是数仓里处理标记列的标准技巧，简洁且少一层嵌套。
- **WHERE和HAVING的区别是什么？** 回答要点：WHERE在分组前过滤原始行（不能用聚合函数），HAVING在分组后过滤聚合结果（可以用聚合函数）；样本量过滤、"转化数大于N的渠道"这类需求只能用HAVING。
- **线索转化的归因口径怎么定？** 回答要点：一条线索可能先看SEM广告再通过官网表单留资，首触归因记SEM、末触归因记官网、多触点归因则要权重拆分；入门阶段先确认公司用哪种，口径不一致会让渠道对比全部失真。
- **线索量与线索质量怎么权衡？** 回答要点：单看量会奖励"便宜但劣质"的流量，单看率会奖励"少量精挑"的渠道，应结合CPL（单线索成本）、CAC（单获客成本）与线索到商机到签单的漏斗分层看。

### 7. 业务拓展思考

线索来源分布是市场预算的指挥棒，但要防止"唯转化率论"：转介绍转化率最高却受存量客户规模天花板限制，SEM能量大但成本高，健康的结构是多渠道组合。口径可延展为CPL、线索到商机的阶段转化率、以及按线索质量分级（MQL/SQL）后的分层转化率；还可以拉长时间窗看"慢转化"——展会线索常在90天后才签约，统计窗口太短会低估其价值。联动动作上，把高转化渠道的线索画像（行业、规模）反哺投放定向，把未转化线索按原因分类回流市场做再培育。

## SAAS-07 客户行业分布

### 1. 业务背景

销售策略团队制定年度行业打法时，需要先摸清存量客户盘子的行业结构：零售、制造、医药各占多少客户？哪些行业是基本盘、哪些是机会带？这份数据由销售运营（谁）在年度规划启动前（何时）统计，用来决定是否成立行业事业部、做哪类行业的标杆案例、以及市场内容往哪个行业倾斜（为什么）。听起来只是个GROUP BY，但生产环境的行业字段常有NULL（未录入）和空串（录入后清空），不清洗就会多出一组"空白"，分布表里出现一个无意义的空行。**【避坑指南】**GROUP BY会把NULL单独分一组但不显示分组名，业务方看不懂"这行空的算什么"，必须显式转成"未知"。

### 2. 表结构说明

accounts（客户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |
| account_name | VARCHAR(100) | 客户公司名称 |
| industry | VARCHAR(50) | 客户所属行业，可能为NULL（未录入）或空串（录入后清空） |
| region | VARCHAR(50) | 客户所在区域 |
| owner_name | VARCHAR(30) | 负责该客户的客户经理 |
| account_status | VARCHAR(20) | 客户状态：trial试用中/paying付费中/churned已流失 |
| trial_start_date | DATE | 试用开始日期，未试用为NULL |
| trial_end_date | DATE | 试用结束日期，未试用为NULL |
| created_at | DATE | 客户建档日期 |

示例数据（5行）：

| account_id | account_name | industry | region | owner_name | account_status | trial_start_date | trial_end_date | created_at |
|------------|--------------|----------|--------|------------|----------------|------------------|----------------|------------|
| 601 | 快达同城配送 | 物流 | 华北 | 周洁 | paying | NULL | NULL | 2024-03-10 |
| 602 | 优学在线教育 | 教育 | 华东 | 周洁 | paying | NULL | NULL | 2024-05-22 |
| 603 | 康泰医疗器械 | 医药 | 华南 | 吴凯 | paying | NULL | NULL | 2024-08-01 |
| 604 | 华贸进出口 | NULL | 华南 | 吴凯 | paying | NULL | NULL | 2024-09-12 |
| 605 | 绿源生鲜超市 | 零售 | 华东 | 周洁 | paying | NULL | NULL | 2024-10-30 |

### 3. 解题思路

先定口径：统计存量客户的行业分布，输出客户数与占比；行业字段为NULL或空串的一律归入"未知"组，而不是剔除——剔除会让分母缩水、占比失真，且掩盖了数据质量问题。清洗写法：NULL用COALESCE(industry,'未知')兜底，空串用NULLIF(TRIM(industry),'')先转NULL再兜底，两函数串联是处理"NULL+空串"混合脏值的标准组合拳。实现路径：解法一把清洗表达式同时写在SELECT与GROUP BY里（MySQL支持按列别名分组，但表达式写法兼容性更好）；解法二先用派生表（子查询）完成清洗，外层只负责分组统计，口径只写一遍、易维护，也更贴近数仓分层思想。易错点：一是只处理NULL忘了空串；二是把"未知"组从结果里删掉，导致占比加总不到100%；三是忘记按客户数排序，分布表无主次。

### 4. 参考解法

**解法一：COALESCE+NULLIF表达式清洗，直接分组**

```sql
-- 客户行业分布（NULL与空串统一归为"未知"）
SELECT
    COALESCE(NULLIF(TRIM(industry), ''), '未知')  AS industry_clean, -- TRIM去空格，NULLIF把空串转NULL，COALESCE兜底为"未知"
    COUNT(*)                                      AS account_cnt,    -- 各行业客户数
    ROUND(COUNT(*) * 100.0 /
          (SELECT COUNT(*) FROM accounts), 2)     AS pct             -- 占比，分母是全部客户而非仅有效行业
FROM accounts
GROUP BY COALESCE(NULLIF(TRIM(industry), ''), '未知')               -- 按清洗后的表达式分组
ORDER BY account_cnt DESC;                                          -- 按客户数降序，突出基本盘
```

结果解读：示例中物流、教育、医药、零售各1家，客户604的行业未录入归入"未知"；"未知"组的存在本身就是数据质量信号，应推动销售在CRM里补录。

**解法二：派生表先清洗，外层再分组统计**

```sql
-- 先在子查询里统一行业口径，外层只做统计，清洗逻辑只写一遍
SELECT
    t.industry_clean AS industry,                   -- 清洗后行业
    COUNT(*)         AS account_cnt,                -- 客户数
    ROUND(COUNT(*) * 100.0 /
          (SELECT COUNT(*) FROM accounts), 2) AS pct -- 占比（分母同解法一）
FROM (
    SELECT
        CASE WHEN industry IS NULL OR TRIM(industry) = ''
             THEN '未知'
             ELSE industry END AS industry_clean      -- CASE写法更显式：NULL与空串都归"未知"
    FROM accounts
) t
GROUP BY t.industry_clean        -- 外层按清洗列分组
ORDER BY account_cnt DESC;       -- 按客户数降序
```

结果解读：清洗逻辑集中在派生表里，后续要加"一级/二级行业映射"时只改子查询即可；两种解法结果一致，派生表写法在逻辑变复杂时优势明显。

### 5. 性能分析与优化

accounts维表量级小，两解法都是单次扫描加分组，性能差异可忽略；TRIM等函数作用在列上会使industry列上的普通索引失效，但对维表全量统计无所谓。优化建议：一是占比分母用窗口函数SUM(COUNT(*)) OVER()替代子查询，可少一次扫描（MySQL 8.0支持，可作为加分写法提及）；二是行业字段长期脏污的根治方案是在数仓建立行业维表并在ETL层完成映射，让分析SQL直接读标准化字段，而不是每条SQL重复清洗；三是若分布表要按月固定输出，加上统计月份列做成趋势快照表，观察各行业客户数的增长结构。

### 6. 面试延伸考点

- **GROUP BY遇到NULL会怎样？** 回答要点：NULL会被单独分成一组（GROUP BY认为NULL彼此相等），聚合函数COUNT(*)会计入NULL行、COUNT(列)则不计；业务展示时应显式转为"未知"并保留，而不是过滤掉。
- **COALESCE和IFNULL、NVL的区别？** 回答要点：三者都是取第一个非空值；IFNULL是MySQL的二元版本，COALESCE是SQL标准、支持多个参数，可移植性更好。
- **行业字段是自由文本（如"零售/零售业/超市"混写）怎么办？** 回答要点：建立行业维表做映射清洗，无法映射的进人工复核队列；源头治理靠CRM字段改成下拉枚举。
- **行业分布分析对销售组织设计有什么用？** 回答要点：客户密度高的行业适合行业专属打法与事业部制，密度低但增速高的行业适合标杆案例复制，分布数据是排兵布阵的输入。

### 7. 业务拓展思考

行业分布不只是饼图素材，它是"产品市场匹配度"的静态证据：某行业客户占比持续走高，说明产品价值主张在该行业成立，值得投入行业解决方案与案例营销。口径可延展为"行业×MRR贡献"（客户多不等于收入多）、"行业×续约率"（哪个行业客户留得住）、"行业×试用转化率"（哪个行业容易打动）；三者交叉能定位"高价值高留存"的黄金行业。联动动作上，向销售提供行业标杆案例包，向客户成功提供行业化最佳实践模板，让行业分布数据驱动从获客到交付的全链路资源倾斜。

## SAAS-08 合同金额区间统计

### 1. 业务背景

销售管理层复盘签约结构时关心一个问题：今年的合同是"多而小"还是"少而大"？小额单依赖广大的SMB（中小企业）销售团队走量，KA大单则由大客户团队长周期攻坚，两类订单的销售打法、考核周期完全不同。销售运营（谁）在月度经营分析会前（何时）把2025年签约合同按金额切成几个区间，统计各区间笔数与金额贡献，用来评估团队结构是否与订单结构匹配——比如KA团队签单占比持续偏低，就要复盘大客户策略（为什么）。这类"连续数值分箱统计"是CASE WHEN分组的最典型应用。**【面试高频】**"CASE WHEN能不能作为GROUP BY的分组依据"及其边界值写法，是考察基本功的高频点。

### 2. 表结构说明

contracts（合同表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |
| plan_name | VARCHAR(50) | 订阅套餐：基础版/专业版/旗舰版 |
| sign_date | DATE | 签约日期 |
| start_date | DATE | 服务开始日期 |
| end_date | DATE | 服务到期日期 |
| contract_amount | DECIMAL(12,2) | 合同总金额（元） |
| mrr | DECIMAL(10,2) | 月度经常性收入MRR（元/月） |
| is_renewal | TINYINT | 是否续签合同：0新签/1续签 |
| renewal_status | VARCHAR(20) | 续约状态，新签合同为NULL |
| contract_status | VARCHAR(20) | 合同状态：active生效/expired已到期/terminated作废 |

示例数据（5行）：

| contract_id | account_id | plan_name | sign_date | start_date | end_date | contract_amount | mrr | is_renewal | renewal_status | contract_status |
|-------------|------------|-----------|-----------|------------|----------|-----------------|-----|------------|----------------|-----------------|
| 8001 | 701 | 专业版 | 2025-01-12 | 2025-01-13 | 2026-01-12 | 42000.00 | 3500.00 | 0 | NULL | active |
| 8002 | 702 | 旗舰版 | 2025-02-06 | 2025-02-07 | 2026-02-06 | 256000.00 | 21000.00 | 0 | NULL | active |
| 8003 | 703 | 基础版 | 2025-03-15 | 2025-03-16 | 2026-03-15 | 28800.00 | 2400.00 | 0 | NULL | active |
| 8004 | 704 | 专业版 | 2025-04-22 | 2025-04-23 | 2026-04-22 | 96000.00 | 8000.00 | 0 | NULL | active |
| 8005 | 705 | 旗舰版 | 2025-05-18 | 2025-05-19 | 2026-05-18 | 135000.00 | 11500.00 | 1 | renewed | active |

### 3. 解题思路

先定口径：统计2025年签约、状态非作废的合同，按金额切成四档——小于5万（小额）、5万到10万（中额）、10万到20万（大额）、20万及以上（KA大单），输出各档笔数与金额合计。分箱用CASE WHEN实现，注意两点：一是边界语义，本例采用"左闭右开"（<50000、50000~99999.99），恰好5万的合同归哪档必须事先与业务确认并在口径文档写明；二是CASE WHEN从上到下短路匹配，条件顺序不能乱。实现路径：解法一在SELECT里生成区间标签并按同一表达式GROUP BY，输出规范的"一行一档"；解法二用行转列把四档压成一行四列，直接嵌入经营周报。MySQL支持GROUP BY列别名，两种写法都合法，但面试建议按表达式分组以示严谨。易错点：一是BETWEEN写法造成边界重叠或遗漏；二是忘记剔除terminated合同；三是行转列时漏写ELSE导致统计不准。

### 4. 参考解法

**解法一：CASE WHEN生成区间标签并按表达式分组**

```sql
-- 2025年签约合同按金额区间统计
SELECT
    CASE
        WHEN contract_amount <  50000 THEN 'A-小额（<5万）'
        WHEN contract_amount < 100000 THEN 'B-中额（5万-10万）'
        WHEN contract_amount < 200000 THEN 'C-大额（10万-20万）'
        ELSE 'D-KA大单（≥20万）'
    END AS amount_range,                 -- 金额区间标签，CASE从上到下短路匹配保证区间不重叠
    COUNT(*)            AS contract_cnt, -- 各区间合同笔数
    SUM(contract_amount) AS amount_sum   -- 各区间金额合计，看结构贡献
FROM contracts
WHERE sign_date >= '2025-01-01'         -- 只看2025年签约
  AND contract_status <> 'terminated'   -- 剔除作废合同
GROUP BY CASE
        WHEN contract_amount <  50000 THEN 'A-小额（<5万）'
        WHEN contract_amount < 100000 THEN 'B-中额（5万-10万）'
        WHEN contract_amount < 200000 THEN 'C-大额（10万-20万）'
        ELSE 'D-KA大单（≥20万）'
    END                                 -- 按同一CASE表达式分组（也可写GROUP BY amount_range，MySQL支持别名）
ORDER BY amount_range;                  -- 标签带A/B/C/D前缀，字符串排序即区间顺序
```

结果解读：示例5笔合同落入小额2笔、中额1笔、大额1笔、KA 1笔；金额合计上KA单笔贡献最大，是典型的"笔数少、金额重"结构，应关注KA交付资源是否匹配。

**解法二：行转列一行输出各区间合同数**

```sql
-- 行转列：一行输出四档合同数，直接嵌入经营周报表格
SELECT
    SUM(CASE WHEN contract_amount <  50000 THEN 1 ELSE 0 END)
                              AS small_cnt,   -- 小额单量，命中记1否则记0再求和
    SUM(CASE WHEN contract_amount >= 50000  AND contract_amount < 100000
                             THEN 1 ELSE 0 END) AS mid_cnt,    -- 中额单量，显式双边界防重叠
    SUM(CASE WHEN contract_amount >= 100000 AND contract_amount < 200000
                             THEN 1 ELSE 0 END) AS large_cnt,  -- 大额单量
    SUM(CASE WHEN contract_amount >= 200000 THEN 1 ELSE 0 END)
                              AS ka_cnt      -- KA大单量
FROM contracts
WHERE sign_date >= '2025-01-01'              -- 统计年份
  AND contract_status <> 'terminated';       -- 剔除作废合同
```

结果解读：行转列不产生分组，一次聚合出全部区间，适合固定版式报表；注意此处用">=下界 AND <上界"显式写边界，比BETWEEN（闭区间）更不易重叠，各列之和应等于合同总数，可用这个恒等式自检。

### 5. 性能分析与优化

两解法都是单表一次扫描，CASE WHEN只在内存里做表达式判断，本身不增加IO；区别在解法一有GROUP BY（多一步临时表分组+排序），解法二无分组、聚合常量输出，理论更快。优化建议：一是WHERE里的sign_date与contract_status可建复合索引 (contract_status, sign_date, contract_amount) 实现索引覆盖，避免回表；二是若区间定义经常调整（如年初调档位），把区间上下界做成区间维表（bin_table: 区间名、下界、上界），用JOIN ON amount BETWEEN 下界 AND 上界分箱，改区间不改SQL；三是签约量大的公司可按月预聚合区间统计，管理层看趋势时直接读汇总。

### 6. 面试延伸考点

- **CASE WHEN不写ELSE会怎样？** 回答要点：未命中返回NULL；在"SUM(CASE WHEN 条件 THEN 1 END)"里省略ELSE是安全的（NULL不参与求和），但写成"THEN 1 END"用于COUNT时容易误判，建议始终显式写ELSE 0。
- **为什么区间标签加A/B/C/D前缀？** 回答要点：纯中文标签按字符串排序会乱序，加序号前缀让ORDER BY直接得到区间顺序，是报表开发的小技巧；更好的做法是另存一列排序码。
- **CASE WHEN分箱和FLOOR取整分箱怎么选？** 回答要点：等宽区间可用FLOOR(amount/50000)数值分箱更简洁；业务区间通常不等宽且有语义（小额/KA），用CASE WHEN可读性更好。
- **怎么把区间统计做成趋势？** 回答要点：在GROUP BY里加上DATE_FORMAT(sign_date,'%Y-%m')，输出"月份×区间"矩阵，观察订单结构随时间的迁移，比如大单占比是否在提升。

### 7. 业务拓展思考

合同金额结构决定销售组织的形态：小额单占比高说明生意靠SMB规模化打法，重点在获客效率与标准化交付；KA单占比高则要建设大客户管理体系（专属客户成功、季度业务回顾）。口径可延展为"区间×毛利率"（大单通常含实施服务，毛利率结构不同）、"区间×续约率"（验证大单是否真的更留客）、"新签与续签分开的结构对比"。联动动作上，把小额高用量的客户筛出来交给销售做升级外呼推动向上迁移（upsell），把连续两期掉档的客户（如从中额降到小额续约）标记为降级风险，提前介入。

## SAAS-09 90天内到期合同清单

### 1. 业务背景

续约是SaaS收入的生命线：合同到期前90天是启动续约谈判的黄金窗口，太早客户没预算规划、太晚来不及走客户内部流程。销售运营（谁）每个工作日要产出"90天内到期合同清单"（何时），按到期日排序推给各客户经理，标出到期MRR——这份清单就是本季度的续约作战地图，直接服务于续约率目标（为什么）。清单只包含status为active且尚未到期的合同，并按"30/60/90天"分层标注续约优先级。**【面试高频】**日期边界写法（BETWEEN闭区间、CURDATE()+INTERVAL）与"到期日=今天"是否该纳入清单，是这类题最容易出错的地方。

### 2. 表结构说明

contracts（合同表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |
| plan_name | VARCHAR(50) | 订阅套餐：基础版/专业版/旗舰版 |
| sign_date | DATE | 签约日期 |
| start_date | DATE | 服务开始日期 |
| end_date | DATE | 服务到期日期 |
| contract_amount | DECIMAL(12,2) | 合同总金额（元） |
| mrr | DECIMAL(10,2) | 月度经常性收入MRR（元/月） |
| is_renewal | TINYINT | 是否续签合同：0新签/1续签 |
| renewal_status | VARCHAR(20) | 续约状态：pending待续约/negotiating谈判中/renewed已续约/churn_risk流失风险 |
| contract_status | VARCHAR(20) | 合同状态：active生效/expired已到期/terminated作废 |

示例数据（5行，假设今天是2025-08-25）：

| contract_id | account_id | plan_name | sign_date | start_date | end_date | contract_amount | mrr | is_renewal | renewal_status | contract_status |
|-------------|------------|-----------|-----------|------------|----------|-----------------|-----|------------|----------------|-----------------|
| 7001 | 401 | 专业版 | 2024-10-15 | 2024-10-16 | 2025-10-15 | 96000.00 | 8000.00 | 0 | pending | active |
| 7002 | 402 | 旗舰版 | 2024-08-01 | 2024-08-02 | 2025-09-01 | 200000.00 | 18000.00 | 0 | negotiating | active |
| 7003 | 403 | 基础版 | 2024-09-20 | 2024-09-21 | 2025-09-19 | 30000.00 | 2500.00 | 0 | churn_risk | active |
| 7004 | 404 | 专业版 | 2023-10-01 | 2023-10-02 | 2024-09-30 | 90000.00 | 7500.00 | 0 | NULL | expired |
| 7005 | 405 | 旗舰版 | 2024-11-01 | 2024-11-02 | 2025-10-31 | 240000.00 | 22000.00 | 0 | pending | active |

### 3. 解题思路

先定口径：清单=contract_status为active、到期日在[今天, 今天+90天]区间内的合同，输出合同要素、到期MRR与距到期天数，按到期日升序。日期条件的推荐写法是 end_date >= CURDATE() AND end_date < CURDATE() + INTERVAL 90 DAY，比BETWEEN更稳：BETWEEN是闭区间会把第90天当天重复计入，且对DATE类型虽然可用，但一旦字段变成DATETIME就会漏掉当天的时分秒部分。分层预警用CASE WHEN把天数切成"30天内高优先/31-60天中优先/61-90天低优先"。解法一仅用合同表输出最小清单；解法二JOIN客户表带上客户名称、客户经理与优先级标签，直接可分发到人。易错点：一是忘记过滤expired合同（已到期合同不该再出现在续约清单里）；二是DATEDIFF参数顺序；三是CURDATE()在跨天重跑时的可复现性问题。

### 4. 参考解法

**解法一：合同表单表过滤，输出最小可用清单**

```sql
-- 90天内到期合同清单（仅生效合同）
SELECT
    c.contract_id,                              -- 合同ID
    c.account_id,                               -- 客户ID
    c.plan_name,                                -- 订阅套餐标识
    c.end_date,                                 -- 到期日期
    c.mrr,                                      -- 到期MRR，即续约风险敞口
    DATEDIFF(c.end_date, CURDATE()) AS days_to_expire -- 距到期天数=到期日-今天
FROM contracts c
WHERE c.contract_status = 'active'              -- 仅生效合同，已到期/作废不进续约清单
  AND c.end_date >= CURDATE()                   -- 尚未到期（含今天到期）
  AND c.end_date <  CURDATE() + INTERVAL 90 DAY -- 到期日早于今天+90天，左闭右开防边界重复
ORDER BY c.end_date ASC;                        -- 越早到期越靠前
```

结果解读：示例中7004已到期被排除，7002、7003、7001、7005按到期先后排列；到期MRR合计就是"未来90天必须靠续约守住的收入盘子"。

**解法二：JOIN客户表带出责任人，并分层标注续约优先级**

```sql
-- 关联客户表输出可分发到人的续约清单，带优先级分层
SELECT
    a.account_name,                                 -- 客户名称
    a.owner_name,                                   -- 所属客户经理，续约第一责任人
    c.end_date,                                     -- 到期日
    c.mrr,                                          -- 到期MRR
    CASE
        WHEN DATEDIFF(c.end_date, CURDATE()) <= 30 THEN '30天内-高优先'
        WHEN DATEDIFF(c.end_date, CURDATE()) <= 60 THEN '31-60天-中优先'
        ELSE '61-90天-低优先'
    END AS priority_tag                             -- 续约优先级分层，CASE短路匹配
FROM contracts c
INNER JOIN accounts a ON a.account_id = c.account_id  -- 关联客户表取名称与责任人
WHERE c.contract_status = 'active'                    -- 仅生效合同
  AND c.end_date >= CURDATE()                         -- 未到期下界
  AND c.end_date <  CURDATE() + INTERVAL 90 DAY       -- 90天上界，左闭右开
ORDER BY c.end_date ASC, c.mrr DESC;                  -- 先按到期日，同期到期的MRR大的在前
```

结果解读：清单按人可分发、按层可分工——高优先档由客户经理本周内启动谈判，低优先档先做使用情况盘点；MRR排序让大额合同优先占用销售注意力。

### 5. 性能分析与优化

解法一单表过滤，理想索引是 (contract_status, end_date)，两个等值/范围条件都能命中同一索引，扫描范围被压缩到"active且90天内到期"的极小集合；解法二多一次JOIN，因contracts端结果集小、accounts按主键关联，成本增量很小。优化建议：一是把该查询固化为每日定时任务，输出日期参数化（传统计日期而非CURDATE()），保证失败重跑与历史补数的结果可复现；二是清单可以预落地为续约跟进表（到期日、客户、责任人、优先级、跟进状态），销售在CRM里更新跟进状态，分析侧追踪"清单转化漏斗"（触达→谈判→签约）；三是若合同量巨大，可按end_date分区，续约查询天然分区裁剪。

### 6. 面试延伸考点

- **为什么推荐" >= CURDATE() AND < CURDATE()+INTERVAL 90 DAY"而不是BETWEEN？** 回答要点：BETWEEN是双闭区间，DATE场景可用但与DATETIME混用时容易漏算当天时间部分或重复计入边界日；左闭右开区间是通用的稳妥写法，边界语义清晰。
- **CURDATE()+INTERVAL 90 DAY和DATE_ADD(CURDATE(), INTERVAL 90 DAY)是什么关系？** 回答要点：完全等价，前者是语法糖；跨数据库时DATE_ADD更通用，加分回答可提到SQL Server用DATEADD(day, 90, GETDATE())。
- **怎么算"90天内到期MRR占总MRR的比例"？** 回答要点：分子=清单MRR合计，分母=全部active合同MRR合计，两层子查询或窗口函数实现；该比例即短期续约收入风险敞口，超过一定阈值（如40%）说明收入结构过于集中在近期到期。
- **renewal_status已经在谈的客户还要出现在清单里吗？** 回答要点：要出现但应标注状态——已续约（renewed）的可以过滤，谈判中的要保留以跟踪进度，清单的价值是"未完成续约的合同的日历"。

### 7. 业务拓展思考

90天到期清单是SaaS续约管理的作战日历，价值在于把"被动的到期"变成"主动的节奏管理"。口径可延展为按客户经理的续约任务分派、按行业的到期MRR分布（某行业集中到期要提前备资源）、以及"到期MRR×历史续约率=预测续约收入"的滚动预测。联动动作上，高优先档触发"客户经理+CSM"联合复盘客户健康度（活跃、工单、NPS），带着使用数据去谈判比空谈感情有效得多；对churn_risk状态的合同，应在清单里置顶并升级管理层介入。

## SAAS-10 各功能模块开通客户数

### 1. 业务背景

SaaS公司除核心订阅外通常提供多个增值模块：报表中心、CRM、工单系统、开放API、BI看板等，模块增购（cross-sell）是扩张收入的重要来源。产品增长团队要回答：每个模块被多少客户开通了？哪些模块渗透率高、哪些是"无人问津的隐形库存"？这份增购策略复盘由产品运营与销售运营（谁）在季度增购分析前（何时）统计，用来设计模块推荐清单、包装增购套餐，并为销售产出"已开通A模块但尚未开通B模块"的目标客户名单（为什么）。注意"开通"只是商业动作，是否真的在用还需与使用数据交叉验证。**【加分点】**能主动区分"开通口径"与"使用口径"，并说明为什么两者必须分开统计。

### 2. 表结构说明

module_openings（模块开通表），记录客户开通各功能模块的历史：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| id | INT | 记录ID，主键 |
| account_id | INT | 客户ID |
| module_name | VARCHAR(50) | 功能模块名：报表中心/CRM/工单系统/开放API/BI看板 |
| opened_date | DATE | 开通日期 |
| seat_count | INT | 该次开通的模块席位数 |

accounts（客户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |

### 3. 解题思路

先定口径：按模块分组统计"开通客户数"，核心聚合是COUNT(DISTINCT account_id)——同一客户对同一模块可能有多条记录（先开通10席、半年后扩容再记一条），不去重会把客户数虚增；席位合计SUM(seat_count)则应把多条记录相加，因为扩容记录代表真实新增的席位。若要评估模块的近期动销，可加时间过滤只统计近90天新开通记录。实现路径：解法一单表按模块分组，输出去重客户数、席位合计与最早/最近开通日期，一次看清模块渗透与增长节奏；解法二JOIN客户表，把统计细化为"模块×行业"交叉，帮助发现某行业的增购偏好，为行业化增购话术提供依据，同时排除已流失客户避免脏数据。易错点：一是用COUNT(*)代替去重计数；二是JOIN后忘记过滤客户状态，把流失客户的开通记录也算进渗透率；三是开通不等于活跃，结论输出时要注明口径是"商业开通"而非"实际使用"。

### 4. 参考解法

**解法一：单表按模块分组，去重客户数与席位合计**

```sql
-- 各功能模块的开通客户数与席位体量
SELECT
    m.module_name,                                  -- 功能模块
    COUNT(DISTINCT m.account_id) AS account_cnt,    -- 开通客户数（去重：扩容/多记录只计一次）
    SUM(m.seat_count)            AS seat_total,     -- 席位合计（扩容记录相加才是真实席位数）
    MIN(m.opened_date)           AS first_opened,   -- 最早开通日，看模块上线后的渗透起点
    MAX(m.opened_date)           AS last_opened     -- 最近开通日，判断模块是否仍在动销
FROM module_openings m
GROUP BY m.module_name                            -- 按模块分组
ORDER BY account_cnt DESC;                        -- 按渗透客户数降序
```

结果解读：客户501对报表中心与CRM各有一条记录、客户502开通了报表中心与开放API，COUNT(DISTINCT)保证各自只被计一次；最近开通日与最早开通日的间隔能看出模块是"上线即火"还是"长期吃灰"。

**解法二：JOIN客户表，按"模块×行业"交叉统计近90天新开通**

```sql
-- 近90天各模块新开通客户数的行业分布，定位增购机会
SELECT
    m.module_name,                                   -- 功能模块
    a.industry,                                      -- 客户行业
    COUNT(DISTINCT m.account_id) AS account_cnt      -- 近90天新开通该模块的去重客户数
FROM module_openings m
INNER JOIN accounts a ON a.account_id = m.account_id   -- 关联客户表取行业
WHERE m.opened_date >= CURDATE() - INTERVAL 90 DAY     -- 只看近90天新开通记录，评估近期动销
  AND a.account_status <> 'churned'                    -- 排除已流失客户，避免脏数据干扰渗透率
GROUP BY m.module_name, a.industry                     -- 模块×行业交叉分组
ORDER BY m.module_name, account_cnt DESC;              -- 模块内按客户数降序
```

结果解读：交叉统计能发现"报表中心在零售行业增购集中"这类结构性机会，销售可按行业定制增购推荐话术；排除流失客户后，渗透率反映的是真实存量盘子的模块偏好。

### 5. 性能分析与优化

解法一是单表分组，量级小、代价低，为module_openings建 (module_name, account_id) 复合索引即可让分组与去重都在索引上完成；解法二多一次JOIN并带日期过滤，可建 (opened_date, account_id, module_name) 复合索引，让时间过滤与关联字段都被索引覆盖。优化建议：一是模块渗透是慢变化指标，按月快照存"模块×客户数×席位"表，复盘时直接读趋势而非现算；二是扩容记录造成的多条记录建议在ETL层做"客户×模块"最新状态表（含累计席位），分析SQL不再处理重复行；三是若要产出交叉销售名单（开通A未开通B），用条件聚合（每客户一行、各模块0/1标记）比模块自连接更高效，避免N×N的组合膨胀。

### 6. 面试延伸考点

- **COUNT(DISTINCT account_id)和COUNT(*)在这里差在哪？** 回答要点：一个客户可有多条开通记录（扩容、变更），COUNT(*)统计的是记录数会虚增客户数；去重计数才是"多少家客户开通了该模块"的真实答案。
- **开通了但没人用，怎么办？** 回答要点：关联usage_logs按模块统计近30天活跃用户，定义"僵尸模块"（开通超90天且零活跃）清单，交由CSM做激活培训或评估模块价值。
- **怎么产出"开通A模块但没开通B模块"的交叉销售名单？** 回答要点：按客户条件聚合出各模块0/1标记，再筛A=1且B=0的客户；比模块自连接更直观，也方便一次筛多组组合。
- **席位计费模式下模块开通对收入意味着什么？** 回答要点：模块MRR=开通席位×模块单价，席位合计即收入杠杆；渗透率提升直接翻译成扩张MRR，是净收入留存（NDR）的重要成分。

### 7. 业务拓展思考

模块渗透数据是增购收入的地图：渗透率高说明模块价值已被验证，应推动打包进更高阶套餐；渗透率低则要区分是"不知道"（触达问题）、"不需要"（定位问题）还是"不好用"（产品问题）。口径可延展为模块渗透率（开通客户数/付费客户总数）、开通到活跃的转化时滞、以及模块组合分析（开通CRM的客户中有多少也开通了报表中心）。联动动作上，把"高使用低渗透"的模块作为增购主打，把"开通即沉睡"的模块客户名单交给CSM做激活，让模块矩阵同时服务产品迭代与销售增购两条线。

## SAAS-11 客户经理名下客户与续约状态

### 1. 业务背景

销售 VP 每月要做"人盯事"的盘点：每个客户经理名下有多少在管客户？多少已经完成续约、多少还在谈判、多少亮了流失风险红灯？这份数据由销售运营（谁）在月度销售例会前（何时）统计，用来给客户经理排优先级、把高风险客户重新分配给更强的销售，并作为续约率考核的依据（为什么）。技术上这是一道经典的两表JOIN题：客户表存客户与责任人，合同表存续约状态，按客户经理聚合时既要数清客户，又要按续约状态做条件计数。**【面试高频】**"一个客户有多份合同时客户数会不会被JOIN放大"是该场景的核心陷阱，能否主动点破并给出两种防御写法，直接区分入门与合格。

### 3. 解题思路

先定口径：按客户经理分组，输出在管客户数、已续约客户数与流失风险客户数。"在管客户"取account_status为paying或trial的客户（试用客户虽无合同也是名下资产，用LEFT JOIN保留）；续约状态看客户当前合同的renewal_status。关键陷阱：客户902有两份合同（9102、9105），JOIN后该客户出现两行，直接COUNT(*)会把客户数从2数成3，必须COUNT(DISTINCT account_id)或先按客户预聚合。条件计数的写法：COUNT(DISTINCT CASE WHEN renewal_status='renewed' THEN account_id END)——命中才返回account_id，未命中返回NULL而COUNT忽略NULL，这正是"条件聚合"的入门标准式。实现路径：解法一LEFT JOIN+条件聚合一次完成；解法二先用子查询把合同表压到客户粒度（一客户一行），再JOIN客户表分组，客户数无需去重、逻辑更清晰。易错点：一是JOIN放大客户数；二是把LEFT JOIN写成INNER JOIN导致试用客户（无合同）丢失；三是CASE WHEN里THEN的是account_id而不是1（否则无法与DISTINCT配合按客户去重）。

### 4. 参考解法

**解法一：LEFT JOIN + 条件聚合（COUNT DISTINCT CASE WHEN）**

```sql
-- 各客户经理的在管客户数与续约状态分布
SELECT
    a.owner_name,                                                -- 客户经理
    COUNT(DISTINCT a.account_id)                AS account_cnt,  -- 在管客户数（去重，防多合同放大）
    COUNT(DISTINCT CASE WHEN c.renewal_status = 'renewed'
                        THEN a.account_id END)  AS renewed_cnt,  -- 有任一合同已续约的客户数
    COUNT(DISTINCT CASE WHEN c.renewal_status = 'churn_risk'
                        THEN a.account_id END)  AS risk_cnt       -- 有任一合同亮流失风险的客户数
FROM accounts a
LEFT JOIN contracts c ON c.account_id = a.account_id             -- 左连接：试用客户无合同也保留
WHERE a.account_status IN ('paying', 'trial')                    -- 在管客户=付费中+试用中
GROUP BY a.owner_name                                            -- 按客户经理分组
ORDER BY risk_cnt DESC, account_cnt DESC;                        -- 风险客户多的经理排前面，便于会上重点讨论
```

结果解读：王琳名下2家客户，其中902有流失风险合同且因两份合同在JOIN后出现两行——COUNT(DISTINCT)保证客户数仍为2；李强名下的试用客户904无合同也因LEFT JOIN被保留。

**解法二：子查询把合同压到客户粒度，再JOIN汇总**

```sql
-- 先按客户聚合续约标记（一客户一行），再按客户经理汇总，天然防重复计数
SELECT
    a.owner_name,                        -- 客户经理
    COUNT(*)             AS account_cnt, -- 客户数（派生表中每客户一行，无需再去重）
    SUM(t.has_renewed)   AS renewed_cnt, -- 已续约客户数：0/1标记直接求和
    SUM(t.has_risk)      AS risk_cnt     -- 风险客户数
FROM accounts a
INNER JOIN (
    SELECT
        account_id,                                                     -- 客户ID
        MAX(CASE WHEN renewal_status = 'renewed'
                 THEN 1 ELSE 0 END) AS has_renewed,                     -- 该客户任一合同已续约则记1
        MAX(CASE WHEN renewal_status = 'churn_risk'
                 THEN 1 ELSE 0 END) AS has_risk                         -- 任一合同有流失风险则记1
    FROM contracts
    GROUP BY account_id                                                 -- 压缩到客户粒度，一客户一行
) t ON t.account_id = a.account_id                                      -- 客户粒度关联，关系退化为一对一
WHERE a.account_status IN ('paying', 'trial')                           -- 在管客户
GROUP BY a.owner_name
ORDER BY risk_cnt DESC;                                                 -- 风险优先排序
```

结果解读：派生表先把"客户-合同"一对多压成"客户"一行，JOIN后关系变为一对一，客户数可以直接COUNT(*)；注意试用客户904因无合同被INNER JOIN排除，若要保留应改LEFT JOIN并在派生表侧允许NULL——这是与解法一的关键差异，面试要能主动指出。

### 5. 性能分析与优化

解法一先JOIN后聚合，JOIN的中间结果=客户数×各客户合同数，客户平均合同数少（1-3份）时开销可控；解法二先在contracts上做一次全量分组（派生表）再JOIN，多一步物化，但JOIN关系是一对一，后续聚合更轻。量级判断：accounts几十万、contracts百万级时两解法都在秒级。优化建议：一是给contracts建 (account_id, renewal_status) 复合索引，派生表的GROUP BY可以直接走索引；二是"客户经理-客户-续约状态"是典型的经理驾驶舱需求，建议按日预聚合出 owner_daily_summary 表，例会直接查询；三是若只关心风险客户，可把WHERE条件下推到子查询里只聚合churn_risk标记，减少派生表列数。

### 6. 面试延伸考点

- **为什么这里用LEFT JOIN而不是INNER JOIN？** 回答要点：LEFT JOIN保留没有任何合同的客户（如试用中客户），它们也是客户经理的考核资产；INNER JOIN会静默丢掉这部分人，导致"名下客户数"偏小，属于业务口径错误而非语法错误。
- **一个客户既有已续约合同又有流失风险合同，算什么？** 回答要点：按客户口径应看"当前主合同"的状态，或定义优先级（流失风险>已续约）取最坏状态；MAX聚合两个标记是把多份合同压成客户口径的常用手段，但要与业务确认规则。
- **续约率怎么算？** 回答要点：周期续约率=当期应续约客户中实际续约的数量/应续约总数；金额口径则用续约MRR/到期MRR，金额口径能反映"留下了大客户还是小客户"。
- **renewal_status这个字段的准确性怎么保障？** 回答要点：它是销售在CRM里手工维护的状态，天然滞后；分析前要检查空值率与更新时间分布，必要时用合同实际签约记录（新续签合同是否存在）反向校验。

### 7. 业务拓展思考

客户经理维度的续约状态分布是销售管理的"看板北极星"：它把抽象的续约率落到人、落到具体客户名单上，例会可以直接过名单而不是过平均数。口径可延展为"客户经理×续约MRR完成进度"（续约MRR/当期到期MRR）、"风险客户的健康度切片"（活跃下滑+工单积压+风险状态三重信号），以及客户交接时的名下资产快照。联动动作上，风险客户触发管理层介入机制与专属挽留方案，已续约客户由CSM无缝接手进入新一轮交付周期，让续约状态数据成为销售与客户成功之间真正的交接棒。

## SAAS-12 每月MRR合计与新增拆分

### 1. 业务背景

财务与经营管理层每月月初最关心MRR瀑布：本月新签带来了多少MRR？续签又带来多少？两者构成月度经常性收入的新增结构——新签MRR反映获客引擎的产出，续签MRR反映存量盘子的稳固度，此消彼长藏着完全不同的经营信号。这份月度复盘由经营分析岗（谁）在每月出账后（何时）统计，用于管理层的收入质量评估与下一阶段目标校准（为什么）。口径上，以签约月为时间轴，把当月生效合同的MRR按is_renewal拆成新签与续签两部分，并计算新签占比。**【加分点】**能说清"本月签约的MRR"与"本月末在管MRR（In-MRR）"是两个不同口径，并解释为什么入门题先用前者。

### 2. 表结构说明

contracts（合同表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |

| is_renewal | TINYINT | 是否续签合同：0新签/1续签 |
| renewal_status | VARCHAR(20) | 续约状态，新签合同为NULL |
| contract_status | VARCHAR(20) | 合同状态：active生效/expired已到期/terminated作废 |

示例数据（5行）：

| contract_id | account_id | plan_name | sign_date | start_date | end_date | contract_amount | mrr | is_renewal | renewal_status | contract_status |

### 3. 解题思路

先定口径：以sign_date所在月份为时间轴，统计每月"新增MRR"——本月所有生效签约合同（新签+续签）的MRR合计；再用is_renewal把新签与续签拆开，算新签占比。要强调口径边界：这里的"新增MRR"是"本月签约动作带来的MRR"，与财务口径的"本月末在管MRR"（所有在期合同之和）不是一回事——后者要按start_date <= 月末 AND end_date > 月末逐月判断，复杂度高一个量级，面试说清为什么先做前者即可。实现路径：解法一按月分组输出新签MRR、新签客户数与合同笔数，回答"获客引擎产出"；解法二用条件聚合把新签MRR与续签MRR拆成两列并算新签占比，回答"收入结构质量"。易错点：一是忘记剔除terminated合同；二是除法分母为零（某月只有续签时新签占比的分母仍非零，但稳健写法用NULLIF防炸）；三是月份格式不统一导致排序错乱，必须用'%Y-%m'固定格式。

### 4. 参考解法

**解法一：按月分组统计新增MRR与新签客户数**

```sql
-- 按签约月统计新增MRR与新签客户数（获客引擎产出视角）
SELECT
    DATE_FORMAT(sign_date, '%Y-%m')    AS sign_month,      -- 签约月份，固定"年-月"格式保证排序正确
    SUM(mrr)                           AS new_mrr,         -- 当月新增MRR合计（新签+续签全部签约动作）
    COUNT(DISTINCT account_id)         AS account_cnt,     -- 当月签约的去重客户数
    COUNT(*)                           AS contract_cnt     -- 当月签约合同笔数（与客户数相减可看复购强度）
FROM contracts
WHERE sign_date >= '2025-01-01'                            -- 统计起点
  AND contract_status <> 'terminated'                      -- 剔除作废合同，MRR口径才干净
GROUP BY DATE_FORMAT(sign_date, '%Y-%m')                   -- 按月分组
ORDER BY sign_month;                                       -- 按月升序形成时间序列
```

结果解读：示例数据下1月新增MRR 23000（2家客户2笔）、2月11500（2家2笔）、3月20000；contract_cnt与account_cnt的差异能提示哪些月份靠老客复购撑量。

**解法二：条件聚合拆分新签/续签MRR并计算新签占比**

```sql
-- 新签与续签MRR拆分（收入结构质量视角）
SELECT
    DATE_FORMAT(sign_date, '%Y-%m') AS sign_month,                 -- 签约月份
    SUM(CASE WHEN is_renewal = 0 THEN mrr ELSE 0 END) AS new_mrr,      -- 新签MRR：非续签合同的MRR求和
    SUM(CASE WHEN is_renewal = 1 THEN mrr ELSE 0 END) AS renewal_mrr,  -- 续签MRR：续签合同的MRR求和
    SUM(mrr)                                          AS total_mrr,  -- 合计MRR
    ROUND(SUM(CASE WHEN is_renewal = 0 THEN mrr ELSE 0 END) * 100.0
          / NULLIF(SUM(mrr), 0), 2)                 AS new_mrr_pct  -- 新签占比，NULLIF防止合计为0时除零报错
FROM contracts
WHERE sign_date >= '2025-01-01'                                   -- 统计起点
  AND contract_status <> 'terminated'                             -- 剔除作废合同
GROUP BY DATE_FORMAT(sign_date, '%Y-%m')                          -- 按月分组
ORDER BY sign_month;                                              -- 按月升序
```

结果解读：2月的新增里既有9000的续签又有2500的新签，新签占比21.7%，说明该月增长主要靠存量续约；若连续数月新签占比走低，即使总MRR持平也意味着获客引擎在减速。

### 5. 性能分析与优化

两解法都是单表扫描加按月分组，区别只在表达式复杂度，量级差异可忽略。优化建议：一是为contracts建 (sign_date, contract_status, is_renewal, mrr) 复合索引，时间范围过滤与状态过滤都走索引且覆盖聚合列；二是MRR月度统计是固定报表，建议按日落地"MRR事件流水"（签约日、合同、MRR、类型）预聚合表，月初直接读数，避免月初集中跑批压垮业务库；三是若需要与财务对账，可把终止/退费的负向MRR也纳入流水（mrr为负的记录），SUM后即为净新增MRR，一张表同时支撑毛新增与净新增两个口径。

### 6. 面试延伸考点

- **"本月新增MRR"和"本月末在管MRR"有什么区别？** 回答要点：前者是本月签约动作带来的增量（流量口径），后者是月末所有在期合同的存量合计（存量口径）；在管MRR要按月末时间点判断start_date与end_date的覆盖关系，常按日快照表维护。
- **续签MRR比原合同高，多出来的部分叫什么？** 回答要点：扩张MRR（Expansion MRR），来自席位增加或套餐升级；与之相对的降级是收缩MRR（Contraction），两者与流失MRR一起构成净MRR留存（NDR）的分子。
- **怎么算MRR流失（Churned MRR）？** 回答要点：当月到期未续合同的mrr合计；需要拿"到期合同"LEFT JOIN"续签合同"，没有续签动作的即流失，这是入门之后进阶的NOT EXISTS写法。
- **为什么新签占比下降也要警惕？** 回答要点：只靠续约撑收入的SaaS没有增长飞轮，新签占比是收入质量的先行指标，比绝对值更能预警增长失速。

### 7. 业务拓展思考

MRR月度瀑布是SaaS经营分析的核心叙事线：新签讲获客效率的故事，续签讲客户价值的故事，两者共同决定下季度收入指引。口径可延展为净新增MRR（毛新增-流失-收缩）、分区域/分行业的MRR结构、以及MRR增速与客户数增速的背离分析（客单价变化信号）。联动动作上，新签不及预期时市场与SDR团队复盘线索供给，续签不及预期时客户成功复盘交付质量；把每月MRR瀑布图贴进经营会材料，让"收入从哪来、丢在哪"成为全公司的共同语言。

## SAAS-13 客户数Top10行业排名

### 1. 业务背景

市场部策划年度行业营销日历时，需要先回答"我们最强的十个行业是谁"：按存量付费客户数给行业排名，取前10名作为重点行业投入内容营销与案例建设。这个排名由市场分析师（谁）在年度营销规划前（何时）统计，用于分配行业营销预算与销售行业专属培训资源（为什么）。看似只是"GROUP BY+排序+取前十"，但面试官常在这里考两个进阶点：一是并列名次怎么处理（RANK/DENSE_RANK/ROW_NUMBER的差异），二是"前10"之外的行业怎么合并呈现。**【面试高频】**窗口函数入门几乎必从TopN类题目切入，写法虽简单，三种排名函数的区别却常让候选人现场卡壳。

### 2. 表结构说明

accounts（客户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |
| account_name | VARCHAR(100) | 客户公司名称 |
| industry | VARCHAR(50) | 客户所属行业 |
| region | VARCHAR(50) | 客户所在区域 |
| owner_name | VARCHAR(30) | 负责该客户的客户经理 |
| account_status | VARCHAR(20) | 客户状态：trial试用中/paying付费中/churned已流失 |
| trial_start_date | DATE | 试用开始日期，未试用为NULL |
| trial_end_date | DATE | 试用结束日期，未试用为NULL |
| created_at | DATE | 客户建档日期 |

示例数据（5行）：

| account_id | account_name | industry | region | owner_name | account_status | trial_start_date | trial_end_date | created_at |
|------------|--------------|----------|--------|------------|----------------|------------------|----------------|------------|
| 701 | 快达同城配送 | 物流 | 华北 | 周洁 | paying | NULL | NULL | 2024-03-10 |
| 702 | 优学在线教育 | 教育 | 华东 | 周洁 | paying | NULL | NULL | 2024-05-22 |
| 703 | 康泰医疗器械 | 医药 | 华南 | 吴凯 | paying | NULL | NULL | 2024-08-01 |

| 705 | 绿源生鲜超市 | 零售 | 华东 | 周洁 | paying | NULL | NULL | 2024-10-30 |

### 3. 解题思路

先定口径：行业排名的分母是存量付费客户（account_status='paying'），行业为NULL或"未知"的记录不参与排名（营销无法对"未知"行业做动作），排序按客户数降序取前10。实现路径：解法一用GROUP BY统计各行业客户数，ORDER BY降序后LIMIT 10，这是最朴素的TopN写法，简洁但有两个局限——并列名次被随机截断（第10、11名客户数相同时取谁看运气），且拿不到名次列；解法二在GROUP BY之上叠DENSE_RANK() OVER (ORDER BY COUNT(*) DESC)窗口排名，外层取名次<=10，既保留并列（两家行业客户数相同并列第3），又输出名次列可直接进报表。易错点：一是窗口函数不能直接写在WHERE里（窗口在聚合后求值，必须包在子查询/CTE里再过滤）；二是LIMIT 10在并列时的随机性问题，面试要能主动指出；三是忘记过滤试用与流失客户导致排名被"未付费客户"污染。

### 4. 参考解法

**解法一：GROUP BY + ORDER BY + LIMIT 10**

```sql
-- 客户数Top10行业（朴素TopN写法）
SELECT
    industry,                     -- 行业
    COUNT(*)      AS account_cnt  -- 该行业付费客户数
FROM accounts
WHERE account_status = 'paying'   -- 只统计付费客户，试用与流失不进排名
  AND industry IS NOT NULL        -- 未录入行业的客户不参与排名
GROUP BY industry                 -- 按行业分组
ORDER BY account_cnt DESC         -- 按客户数降序
LIMIT 10;                         -- 取前10行，并列时截断哪一行是不确定的
```

结果解读：写法最短、最容易一次写对，适合快速探查；但第10名与第11名客户数并列时谁被留下取决于排序的稳定性，严谨报告场景要慎用。

**解法二：窗口函数DENSE_RANK排名后取前10（保留并列名次）**

```sql
-- 用DENSE_RANK给行业排名，外层取名次<=10，并列名次不丢失
SELECT
    industry,        -- 行业
    account_cnt,     -- 客户数
    rnk              -- 排名（并列不跳号）
FROM (
    SELECT
        industry,                                          -- 行业
        COUNT(*) AS account_cnt,                           -- 付费客户数
        DENSE_RANK() OVER (ORDER BY COUNT(*) DESC) AS rnk  -- 窗口排名：基于聚合结果排序，并列同名次且后续不跳号
    FROM accounts
    WHERE account_status = 'paying'                        -- 只统计付费客户
      AND industry IS NOT NULL                             -- 排除未录入行业
    GROUP BY industry                                      -- 先聚合出各行业客户数
) t
WHERE rnk <= 10                 -- 对名次过滤（窗口结果不能直接写进WHERE，必须包一层）
ORDER BY rnk, account_cnt DESC; -- 按名次输出，同名次内按客户数降序
```

结果解读：DENSE_RANK让客户数相同的行业并列同一名次且不产生名次空洞（如两个第3名后接第4名）；若业务希望"并列后跳号"则换RANK()，要求强制唯一名次则用ROW_NUMBER()——三者的取舍本身就是面试得分点。

### 5. 性能分析与优化

解法一是"分组聚合+TopN排序"，MySQL会对分组结果做排序（或用优先队列）再截断10行，行业基数小（几十个分组）时代价极低；解法二多一层窗口排序与派生表物化，开销略高但仍在毫秒级。优化建议：一是维表量小，通常无需索引优化，若accounts达到千万级，可建立 (account_status, industry) 复合索引先行过滤；二是行业排名属于低频缓变的报表，可按月快照存表，同时保留"上期名次"列以展示行业排名变动（升幅行业值得加投）；三是若常需要"Top10+其他"的完整饼图，可在解法二外再UNION一个"其他=总数-前十合计"，一次输出完整分布。

### 6. 面试延伸考点

- **ROW_NUMBER、RANK、DENSE_RANK三个函数的区别？** 回答要点：ROW_NUMBER强制唯一连续编号；RANK并列同名次但跳号（1、2、2、4）；DENSE_RANK并列不跳号（1、2、2、3）。取TopN时选哪个取决于业务是否接受并列与截断规则。
- **为什么窗口函数不能直接写在WHERE里？** 回答要点：SQL的逻辑执行顺序是FROM→WHERE→GROUP BY→聚合→窗口→ORDER BY→LIMIT，WHERE执行时窗口结果尚不存在，因此必须用子查询或CTE包一层再过滤。
- **客户数排名靠前的行业一定值得投吗？** 回答要点：还要看客单价与续约率——客户多但都是低价小单的行业，MRR贡献可能不如客户少但客单高的行业；正确姿势是"客户数+MRR+续约率"三表联排。
- **LIMIT 10和窗口排名在并列场景下结果会不同吗？** 回答要点：会。LIMIT硬截断第10行后的数据（并列者随机丢一个），窗口排名把并列者都保留（可能返回11行），对管理层汇报而言后者更公平且可解释。

### 7. 业务拓展思考

Top10行业排名是行业化打法的选靶依据，但"选靶"要同时看三个坐标：客户数（规模）、MRR贡献（含金量）、环比增速（势头）——客户数Top但增速停滞的行业是收割区，客户数小但增速快的行业是播种区，资源配置完全不同。口径可延展为"行业×区域"交叉排名（找到区域内的强势行业复制打法）、"行业Top10的客户集中度"（前三大客户占行业MRR比例过高则该行业根基不稳）。联动动作上，对Top行业配套标杆案例、行业专场活动与销售打单工具包；对排名快速上升的行业设立专项小组，把市场声量转化为签约动能。

### 3. 解题思路

先定口径："试用转付费名单"=trial_start_date非空（走过试用流程）且存在至少一份active生效合同（已付费）的客户；转化天数=该客户最早生效合同签约日（MIN(sign_date)）减trial_start_date。客户1305从未试用（trial_start_date为NULL）即使有合同也不算"试用转付费"；客户1304虽有一份合同但状态是terminated（作废），不算转化成功；客户1302有两份active合同（首签+增购），必须用MIN取首签日，否则转化天数被增购单拉长。实现路径：解法一INNER JOIN合同表过滤active并GROUP BY取MIN(sign_date)，优点是顺带算出转化天数；解法二用EXISTS子查询只判断"是否存在生效合同"，不取合同明细，语义直白且在只需名单时更高效。易错点：一是忘记按客户分组取MIN导致一人多行；二是把terminated合同也算进转化；三是混淆"客户状态=paying"与"存在生效合同"两个口径，前者依赖人工维护，后者以合同事实为准，分析应以合同事实为锚。

### 4. 参考解法

**解法一：INNER JOIN取首份生效合同，计算转化天数**

```sql
-- 试用转付费客户名单（附转化天数）
SELECT
    a.account_id,                                     -- 客户ID
    a.account_name,                                   -- 客户名称
    a.industry,                                       -- 行业
    a.owner_name,                                     -- 负责销售
    a.trial_start_date,                               -- 试用开始日
    MIN(c.sign_date)                    AS paid_sign_date,         -- 首份生效合同签约日=转化日
    DATEDIFF(MIN(c.sign_date), a.trial_start_date) AS convert_days -- 转化天数=转化日-试用开始日
FROM accounts a
INNER JOIN contracts c ON c.account_id = a.account_id   -- 关联合同表找付费证据
WHERE a.trial_start_date IS NOT NULL                    -- 只看走过试用流程的客户
  AND c.contract_status = 'active'                      -- 作废/到期合同不算转化证据
GROUP BY a.account_id, a.account_name, a.industry, a.owner_name, a.trial_start_date -- 客户粒度去重
ORDER BY convert_days ASC;                              -- 转化快的排前面，便于提炼可复制的打法
```

结果解读：示例中1301在试用开始26天后签约、1302在25天后签约（MIN正确跳过了6月的增购单）；转化天数短说明试用期内价值传达有效，可提炼该客户的激活路径做模板。

**解法二：EXISTS子查询判断付费事实，输出纯名单**

```sql
-- 用EXISTS判断"是否存在生效合同"，输出试用转付费名单
SELECT
    a.account_id,          -- 客户ID
    a.account_name,        -- 客户名称
    a.industry,            -- 行业
    a.owner_name,          -- 负责销售
    a.trial_start_date     -- 试用开始日
FROM accounts a
WHERE a.trial_start_date IS NOT NULL       -- 走过试用流程
  AND EXISTS (                             -- 相关子查询：逐行判断客户是否存在生效合同
        SELECT 1
        FROM contracts c
        WHERE c.account_id = a.account_id  -- 与外层客户关联
          AND c.contract_status = 'active' -- 存在即返回TRUE，找到一条就停止扫描
  )
ORDER BY a.trial_start_date;               -- 按试用开始日排列，观察批次效果
```

结果解读：EXISTS只关心"有没有"，不展开合同明细，名单场景下语义最清晰；与解法一的差异在于拿不到转化天数——需要周期指标时用JOIN，只要布尔判断时用EXISTS，这个取舍本身就是面试标准答案。

### 5. 性能分析与优化

解法一JOIN后聚合，中间结果是"试用客户×其全部合同"，因试用客户占比小且人均合同少，开销可控；EXISTS在MySQL 8.0中通常被优化器改写为半连接（semijoin），对大表"存在性判断"效率高，两解法在合理索引下都很快。优化建议：一是给contracts建 (account_id, contract_status, sign_date) 复合索引，EXISTS的探测与JOIN的关联都可直接命中索引；二是若名单要按周刷新，落地"试用-转化事件表"（试用开始日、转化日、天数、销售），同时支撑转化率、转化周期中位数等多个指标；三是统计"未转化名单"时用LEFT JOIN contracts ... IS NULL（须在ON里带contract_status='active'条件，写进WHERE会把LEFT JOIN退化成INNER JOIN），这是本题的自然延伸也是经典陷阱。

### 6. 面试延伸考点

- **JOIN和EXISTS该怎么选？** 回答要点：需要从子表取列或聚合（如首签日、转化天数）用JOIN；只做存在性判断用EXISTS，语义清晰且优化器可用半连接，不必担心一对多导致外层行数放大。
- **试用转付费率怎么算？分母是什么？** 回答要点：转化率=试用且已转付费客户数/已到期的试用客户总数；分母只算"试用期已结束"的客户，把还在试用期内的新客算进去会稀释转化率。
- **转化周期长说明什么问题？** 回答要点：可能是客户决策链长（B端需多角色审批）、试用期间价值未被验证（激活不足）或销售跟进缺位；应按转化天数分层对比试用期的活跃数据，定位卡在"没用起来"还是"没谈下来"。
- **怎么找"试用未转化"的客户做挽回？** 回答要点：LEFT JOIN+IS NULL反查无生效合同的试用客户，再按试用到期时间与试用活跃度排序，活跃高但未转化的客户是最优先挽回对象。

### 7. 业务拓展思考

试用转付费名单不只是一份战报，它是转化打法的提炼素材：把转化周期最短的一批客户的试用行为轨迹（先用了哪个模块、邀请了几个席位、看了几次报表）抽象成"高转化行为特征"，再把这些特征做成试用期的健康分模型，CSM就能在试用中期预判成败并精准介入。口径可延展为分行业/分渠道的转化率对比、转化客户的后续续约表现（转化快是否意味着留得住）、以及"延长试用"对转化率的影响评估。联动动作上，未转化的高活跃试用客户由销售48小时内跟进，低活跃客户先做产品培训再谈签约，让漏斗每一层都有对应动作。

### 1. 业务背景

### 3. 解题思路

先定口径：按客户所在区域（accounts.region）分组，统计付费客户数与生效合同的MRR、合同额合计；合同侧只取contract_status='active'。核心陷阱在数据形态：客户1503（华东）有两份生效合同，JOIN后华东区域该客户出现两行——客户数如果用COUNT(*)会虚增，必须COUNT(DISTINCT a.account_id)；而MRR与合同额本来就应把多份合同加总（1503的9000+2000=11000是正确的区域MRR），不需要去重。两个指标对"重复行"的态度完全相反，同一条SQL里要分别处理，这是本题的教学价值。实现路径：解法一直接JOIN后聚合，用DISTINCT与SUM分别处理；解法二先把contracts按客户预聚合到一行（消除一对多），再JOIN客户表按区域汇总，JOIN关系退化为标准一对一，是数仓里更稳妥的写法。易错点：一是INNER JOIN会丢掉没有生效合同的客户（如1505），客户数口径要确认是"全部付费客户"还是"有生效合同的付费客户"，两者都合法但必须说清；二是忘记过滤合同状态导致expired合同金额混入。

### 4. 参考解法

**解法一：直接JOIN聚合，客户数去重、金额直接SUM**

```sql
-- 各区域付费客户数与生效合同MRR/合同额
SELECT
    a.region,                                        -- 区域（取自客户表）
    COUNT(DISTINCT a.account_id)  AS account_cnt,    -- 客户数：必须去重，防一客户多合同被数多次
    SUM(c.mrr)                    AS total_mrr,      -- 生效合同MRR合计：多份合同本就应加总
    SUM(c.contract_amount)        AS amount_total    -- 生效合同金额合计
FROM accounts a
INNER JOIN contracts c ON c.account_id = a.account_id  -- 关联合同表取金额
WHERE a.account_status = 'paying'                      -- 只统计付费客户
  AND c.contract_status = 'active'                     -- 只统计生效合同，到期/作废不计
GROUP BY a.region
ORDER BY total_mrr DESC;                               -- 按MRR贡献降序，区域产出一目了然
```

结果解读：华东区域客户1503的两份合同MRR相加为11000、客户数仍计1家——同一条SQL里"客户数用DISTINCT、金额用SUM"是针对一对多JOIN的标准处理；华中客户1505因无生效合同被INNER JOIN排除，若要保留需改LEFT JOIN，口径上要向业务确认。

**解法二：合同表先按客户预聚合，再JOIN客户表汇总**

```sql
-- 先把合同按客户压成一行，再按区域汇总（防重复计数的稳妥写法）
SELECT
    a.region,                          -- 区域
    COUNT(*)            AS account_cnt,     -- 客户数：派生表每客户一行，直接COUNT即可
    SUM(t.account_mrr)  AS total_mrr,      -- 区域MRR合计
    SUM(t.account_amt)  AS amount_total    -- 区域合同额合计
FROM accounts a
INNER JOIN (
    SELECT
        account_id,                        -- 客户ID
        SUM(mrr)             AS account_mrr,  -- 该客户全部生效合同的MRR合计
        SUM(contract_amount) AS account_amt   -- 该客户全部生效合同的金额合计
    FROM contracts
    WHERE contract_status = 'active'       -- 仅生效合同
    GROUP BY account_id                    -- 压缩到客户粒度，一客户一行
) t ON t.account_id = a.account_id         -- 一对一关联，无行数放大风险
WHERE a.account_status = 'paying'          -- 只统计付费客户
GROUP BY a.region
ORDER BY total_mrr DESC;                   -- 按MRR降序
```

结果解读：派生表把"客户-合同"的一对多在JOIN之前消化掉，之后的一切聚合都不会被重复行污染，SQL语义更稳，是报表工程里推荐的防御性写法；结果与解法一一致，可互相验证。

### 5. 性能分析与优化

解法一JOIN的中间行数=客户数×人均合同数，客户平均合同少时代价小；解法二先对contracts全量按客户分组（一次扫描+分组），再与客户表做一对一JOIN，在"合同表很大而区域数很小"的场景下更稳，因为聚合把数据量先压小了。优化建议：一是给contracts建 (account_id, contract_status) 复合索引并INCLUDE mrr、contract_amount（MySQL用联合索引 (account_id, contract_status, mrr, contract_amount)），派生表聚合可索引覆盖；二是区域维度的经营报表应建立"区域×月"快照表（区域、客户数、MRR、合同额、环比），季度会直接读数；三是若区域层级要支持大区-省-市下钻，把region改为区域维表（region_id、大区、省、市），分析SQL关联维表而非硬编码字符串。

### 6. 面试延伸考点

- **为什么客户数要COUNT(DISTINCT)而MRR直接SUM？** 回答要点：一对多JOIN后客户维度被复制成多行，计数会重复、必须去重；金额类指标的业务口径本来就是"多份合同加总"，去重反而算错。判断标准是"指标在明细里是否可加"。
- **INNER JOIN丢掉了没有合同的客户，怎么办？** 回答要点：改LEFT JOIN保留全部付费客户，无合同客户的金额指标自然为NULL（可用COALESCE转0）；但要先与业务确认"区域客户数"是否包含无生效合同的付费客户，口径先行。
- **区域人效怎么算？** 回答要点：区域MRR/区域销售人数，或人均签约客户数；需要再关联销售人员的区域归属维表，注意年中调区的人按在职区间拆分归属。
- **两个解法结果一致，为什么还要写解法二？** 回答要点：解法二把复杂度前置消化（先聚合再JOIN），在多指标、多表、多层级的真实报表里更不容易被重复行坑到，属于防御性SQL思维，也是从"能跑"到"可靠"的分水岭。

### 7. 业务拓展思考

区域客户数与合同额是销售资源分配的基础盘：把区域MRR除以区域人数得到人效排名，再叠加区域市场的行业结构，就能回答"下一个销售编制应该给华东还是给西南"。口径可延展为区域×行业的MRR矩阵（找区域内的优势行业）、区域的新签与续签结构（区分"开拓型区域"与"收割型区域"）、以及区域客户集中度（某区域MRR高度依赖单一KA时风险极高）。联动动作上，对高人效区域加大编制与线索倾斜，对低人效区域先诊断是线索供给不足还是转化能力问题，避免简单用"压目标"代替归因。
