## SAAS-16 MRR环比变动的四因子拆分

### 1. 业务背景

财务BP（业务财务）每月初需要向管理层汇报净新增MRR（月度经常性收入）的构成。只报一个"net new MRR = 本月MRR - 上月MRR"是远远不够的：管理层要追问这个净增长是靠新客户贡献的，还是老客户加购扩容（扩张）撑起来的，又有多少被老客户降级（收缩）和流失吃掉了。四因子拆分（新增 New、扩张 Expansion、收缩 Contraction、流失 Churn）是SaaS董事会汇报的标准动作，直接决定下个月销售资源投在拉新还是客户成功团队投在留存上。**【面试高频】** MRR拆分是SaaS数据分析面试出现频率最高的口径题，几乎每场商业分析/BI岗终面都会以某种形式出现。

### 2. 表结构说明

表 `mrr_monthly`（客户月度MRR快照表）：客户流失当月仍留痕一条 mrr=0 的记录（口径约定）。

| 字段名 | 类型 | 含义 |
|--------|------|------|
| id | BIGINT | 快照记录ID，自增主键 |
| account_id | INT | 客户ID |
| stat_month | DATE | 月末快照日期（如2025-01-31） |
| mrr | DECIMAL(12,2) | 该客户当月MRR金额 |

示例数据：

| id | account_id | stat_month | mrr |
|----|-----------|------------|------|
| 1 | 1001 | 2025-01-31 | 8000.00 |
| 2 | 1001 | 2025-02-28 | 9500.00 |
| 3 | 1002 | 2025-01-31 | 12000.00 |
| 4 | 1002 | 2025-02-28 | 0.00 |
| 5 | 1003 | 2025-02-28 | 6000.00 |

（解释：1001从8000涨到9500属于扩张1500；1002从12000清零属于流失12000；1003二月首次出现属于新增6000。）

### 3. 解题思路

先定口径：以"客户×月份"快照为基本单位，对每个客户取上一个月的MRR（LAG），再按差值分类——上月无记录本月有记为"新增"；上月有本月清零记为"流失"；同月都有且本月更大记为"扩张"，更小记为"收缩"，相等记为"持平"不计入变动。实现路径：第一层CTE用 `LAG() OVER (PARTITION BY account_id ORDER BY stat_month)` 取上月值并打标签；第二层按月份 `GROUP BY` 后用条件聚合（SUM CASE）把四类变动金额分别加总，同时算出净新增用于对账。**【避坑指南】** 三个高频易错点：一是流失客户若在表中不留痕（直接缺行），LAG会错把流失月当成"上月无记录"，必须先和业务确认快照表是否留痕，不留痕要先用月份主轴补零；二是"新增"要排除首月快照的干扰（每个客户的第一条记录 prev_mrr 为NULL）；三是变动金额用绝对值汇总，流失金额应报正数（流失了多少），而不是负数。

### 4. 参考解法

**解法一：LAG窗口打标 + 条件聚合（推荐，适用于流失留痕的快照表）**

```sql
WITH mrr_flag AS (                            -- 第一步：为每条快照取上月MRR并打变动标签
    SELECT
        account_id,                           -- 客户ID
        stat_month,                           -- 月末快照日期
        mrr,                                  -- 本月MRR
        LAG(mrr) OVER (                       -- 窗口函数：取同客户上一条快照的MRR
            PARTITION BY account_id           -- 按客户分组，防止跨客户取值
            ORDER BY stat_month               -- 按月份排序，保证"上一条"即上月
        ) AS prev_mrr,                        -- 上月MRR，客户首月为NULL
        DATE_FORMAT(stat_month, '%Y-%m') AS ym -- 转成年月字符串便于输出
    FROM mrr_monthly
),
classified AS (                               -- 第二步：按口径把变动分成四类
    SELECT
        ym,                                   -- 统计月
        CASE
            WHEN prev_mrr IS NULL AND mrr > 0 THEN 'new'        -- 首次出现且有收入 → 新增
            WHEN prev_mrr = 0 AND mrr > 0 THEN 'new'            -- 流失客户回归 → 也记新增
            WHEN prev_mrr > 0 AND mrr = 0 THEN 'churn'          -- 有收入变零 → 流失
            WHEN mrr > prev_mrr THEN 'expansion'                -- 本月更大 → 扩张
            WHEN mrr < prev_mrr THEN 'contraction'              -- 本月更小 → 收缩
            ELSE 'flat'                                         -- 相等 → 持平不计
        END AS change_type,                   -- 变动类型标签
        ABS(mrr - COALESCE(prev_mrr, 0)) AS change_amt  -- 变动金额取绝对值，便于统一汇总
    FROM mrr_flag
)
SELECT
    ym,                                       -- 统计月
    SUM(CASE WHEN change_type = 'new'         THEN change_amt ELSE 0 END) AS new_mrr,         -- 新增MRR
    SUM(CASE WHEN change_type = 'expansion'   THEN change_amt ELSE 0 END) AS expansion_mrr,   -- 扩张MRR
    SUM(CASE WHEN change_type = 'contraction' THEN change_amt ELSE 0 END) AS contraction_mrr, -- 收缩MRR
    SUM(CASE WHEN change_type = 'churn'       THEN change_amt ELSE 0 END) AS churn_mrr,       -- 流失MRR
    SUM(CASE WHEN change_type IN ('new','expansion')     THEN change_amt ELSE 0 END)
      - SUM(CASE WHEN change_type IN ('churn','contraction') THEN change_amt ELSE 0 END) AS net_new_mrr  -- 净新增，用于与财务口径对账
FROM classified
GROUP BY ym
ORDER BY ym;
```

结果解读：每月一行四个变动因子，净新增 = 新增 + 扩张 - 收缩 - 流失。若扩张占比高说明增长由存量客户驱动、健康度高；若新增占大头而流失也在放大，说明增长依赖持续拉新，获客成本压力更大。

**解法二：月份主轴 + 客户全集补零（适用于流失不留痕的表）**

```sql
WITH RECURSIVE calendar AS (                  -- 递归CTE生成考察期内每个月末
    SELECT DATE '2025-01-31' AS month_end     -- 起始月：手动指定第一个月末
    UNION ALL
    SELECT month_end + INTERVAL 1 MONTH       -- 每次推进一个月（DATE加1月保持月末语义近似）
    FROM calendar
    WHERE month_end < DATE '2025-06-30'       -- 截止月，控制递归边界
),
clients AS (                                  -- 全量客户集合
    SELECT DISTINCT account_id FROM mrr_monthly
),
grid AS (                                     -- 客户×月份全组合（笛卡尔积）
    SELECT c.account_id, k.month_end
    FROM clients c CROSS JOIN calendar k
),
filled AS (                                   -- 把快照补齐到全组合，缺失月份按0处理
    SELECT
        g.account_id,                         -- 客户ID
        g.month_end,                          -- 月末日期
        COALESCE(m.mrr, 0) AS mrr             -- 左连接快照表，无记录视为0（解决流失不留痕）
    FROM grid g
    LEFT JOIN mrr_monthly m
        ON m.account_id = g.account_id        -- 同一客户
       AND m.stat_month = g.month_end         -- 同一个月末
),
prev_joined AS (                              -- 关联上月MRR
    SELECT
        f.month_end,                          -- 本月末
        f.mrr,                                -- 本月MRR
        p.mrr AS prev_mrr                     -- 上月MRR（缺失月份补0后恒有值）
    FROM filled f
    LEFT JOIN filled p
        ON p.account_id = f.account_id                                -- 同一客户
       AND p.month_end = f.month_end - INTERVAL 1 MONTH               -- 恰好上一个月
)
SELECT
    DATE_FORMAT(month_end, '%Y-%m') AS ym,                                            -- 统计月
    SUM(CASE WHEN prev_mrr = 0 AND mrr > 0 THEN mrr ELSE 0 END) AS new_mrr,           -- 新增：上月为0本月有
    SUM(CASE WHEN prev_mrr > 0 AND mrr > prev_mrr THEN mrr - prev_mrr ELSE 0 END) AS expansion_mrr,   -- 扩张差额
    SUM(CASE WHEN prev_mrr > 0 AND 0 < mrr AND mrr < prev_mrr THEN mrr - prev_mrr ELSE 0 END) AS contraction_mrr,  -- 收缩差额
    SUM(CASE WHEN prev_mrr > 0 AND mrr = 0 THEN prev_mrr ELSE 0 END) AS churn_mrr     -- 流失：按上月金额计
FROM prev_joined
GROUP BY ym
ORDER BY ym;
```

结果解读：主轴法不依赖"流失留痕"约定，口径更稳，且天然支持"任意一个月有多少客户在续"这类时点问题；代价是要构造客户×月份的网格。两法输出的四因子金额应完全一致，对不上就说明口径有洞。

### 5. 性能分析与优化

解法一只对快照表做一次窗口扫描，复杂度 O(N)，是最优路径；解法二先做递归生成月份、再做客户×月份的笛卡尔积和两次JOIN，复杂度 O(客户数×月份数)，客户量大时（如10万客户×24月=240万行）代价明显更高。优化建议：给 `mrr_monthly` 建复合索引 `(account_id, stat_month)` 并把 `mrr` 纳入索引形成覆盖索引，窗口排序可直接走索引避免filesort；解法二的月份主轴若固定使用（如每月报表），建议落地成物理月份维表 `dim_month` 而不是每次递归生成；若数据量继续膨胀，可把 `mrr_monthly` 按 `stat_month` 做分区，查询指定月份时做分区裁剪。

### 6. 面试延伸考点

- **净新增MRR和NDR（净收入留存率）是什么关系？** 回答要点：NDR =（期初客户在期末的MRR，含扩张/收缩/流失）/ 期初MRR，只看存量客户；净新增还包含新客贡献。NDR>100%说明存量扩张能覆盖流失，是SaaS最核心的健康指标。
- **如果流失客户当月不留痕，你的SQL会出什么问题？** 回答要点：LAG取到的是"上一次有收入的月份"而非紧邻上月，流失月会被误判为新增或持平，必须先构建月份主轴补零（即解法二）。
- **扩张和收缩要不要按"金额"和"席位"分别拆？** 回答要点：要。金额扩张可能来自单价提升（涨价）或席位增加（用量驱动），两者归因动作不同，业务上会再加一个维度拆开看。
- **为什么流失金额通常按"上月MRR"计而不是当月？** 回答要点：当月已清零，能代表客户流失前正常贡献水平的是上月值；部分公司用流失前三个月均值以平滑异常月。

### 7. 业务拓展思考

四因子拆分不只是财务汇报动作，它直接决定增长策略：新增占比高→投市场获客与渠道；扩张占比高→客户成功推动增购和交叉销售；收缩预警→销售运营要建立"降级客户清单"提前介入。口径上还可以延展出"按签约主体去重的Logo口径"与"按集团合并的母公司口径"两套并行，避免同一集团多个子公司签约导致Logo虚增。进阶方向是把四因子下沉到周粒度，配合订阅变更工单做实时监控，让客户成功在收缩发生的当周而非月末才知晓。

## SAAS-17 试用到付费转化率的渠道归因

### 1. 业务背景

市场部每月投放预算分配会上，增长分析师需要回答一个问题：官网SEO、信息流广告、渠道分销三个获客渠道带来的试用客户，谁的付费转化率最高？谁转化最快？这直接决定下季度市场预算往哪个渠道加码。口径上要看两个维度：转化率（转化的试用数/试用总数）和转化速度（试用开始到首次付费的平均天数），一个渠道可能转化率不高但转化极快、客单价高，同样值得投。**【面试高频】** 漏斗转化率是所有行业通用的面试题，SaaS语境下必须能说清"试用窗口"和"付费口径"两个边界。

### 2. 表结构说明

表 `trials`（试用记录表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| trial_id | INT | 试用记录ID，主键 |
| account_id | INT | 客户ID |
| channel | VARCHAR(50) | 获客渠道（官网SEO/信息流广告/渠道分销） |
| trial_start | DATE | 试用开始日期 |
| trial_end | DATE | 试用结束日期 |
| pay_date | DATE | 首次付费日期，未转化为NULL |
| plan_type | VARCHAR(20) | 付费版本，未转化为NULL |

示例数据：

| trial_id | account_id | channel | trial_start | trial_end | pay_date | plan_type |
|----------|-----------|---------|-------------|-----------|----------|-----------|
| 1 | 2001 | 官网SEO | 2025-03-01 | 2025-03-14 | 2025-03-10 | 标准版 |
| 2 | 2002 | 信息流广告 | 2025-03-03 | 2025-03-17 | NULL | NULL |
| 3 | 2003 | 渠道分销 | 2025-03-05 | 2025-03-19 | 2025-03-18 | 专业版 |
| 4 | 2004 | 官网SEO | 2025-03-06 | 2025-03-20 | NULL | NULL |
| 5 | 2005 | 信息流广告 | 2025-03-08 | 2025-03-22 | NULL | NULL |

辅助表 `orders`（订单表）：`order_id INT`、`account_id INT`、`order_type VARCHAR(20)`（新签/增购/续约）、`amount DECIMAL(12,2)`、`order_date DATE`。

### 3. 解题思路

先明确指标口径：转化率 = 已付费试用数 / 试用总数，分母是全部试用（含未结束的进行中试用，或只统计已结束试用，需与业务确认）；转化窗口约定为"试用开始后30天内产生首次新签付费订单"，超窗不算转化，防止试用三个月后才付费的老客户拉高当期转化率。实现路径有两条：若 `trials` 表自带 `pay_date` 冗余字段，直接条件聚合一步出结果；若要独立校验（防止冗余字段口径滞后），用 `trials LEFT JOIN orders` 并把"30天窗口内的新签订单"条件写在ON里，再按渠道数DISTINCT客户。**【避坑指南】** 最大易错点是LEFT JOIN的过滤条件写进WHERE而不是ON——一旦写进WHERE，未转化的试用（JOIN不上）会被整行过滤掉，分母变小、转化率虚高。另外转化天数 `DATEDIFF(pay_date, trial_start)` 的AVG只能对已转化样本计算，未转化样本的NULL会被AVG自动忽略，恰好符合需求，但要能主动说出这一点。

### 4. 参考解法

**解法一：条件聚合一步出结果（利用pay_date冗余字段）**

```sql
SELECT
    channel,                                             -- 获客渠道
    COUNT(*) AS trial_cnt,                               -- 试用总数（分母）
    SUM(pay_date IS NOT NULL) AS pay_cnt,                -- 已付费试用数（MySQL布尔表达式求和技巧）
    ROUND(AVG(pay_date IS NOT NULL) * 100, 2) AS cvr_pct, -- 转化率 = 付费样本占比
    ROUND(AVG(DATEDIFF(pay_date, trial_start)), 1) AS avg_days_to_pay,  -- 平均转化天数（NULL被AVG忽略，只剩已转化样本）
    ROUND(SUM(CASE WHEN pay_date IS NOT NULL THEN 1 ELSE 0 END) * 100.0
          / SUM(COUNT(*)) OVER (), 2) AS share_pct_of_payers       -- 该渠道付费客户占全部付费客户的比例
FROM trials
GROUP BY channel
ORDER BY cvr_pct DESC;                                   -- 转化率高的渠道排前面
```

结果解读：渠道分销虽然量可能小，但转化率和客单价往往最高；信息流广告量大但转化率通常垫底，要结合CAC（获客成本）一起看才能判断预算去向。

**解法二：LEFT JOIN订单表独立校验（口径可复用）**

```sql
SELECT
    t.channel,                                           -- 获客渠道
    COUNT(DISTINCT t.account_id) AS trial_cnt,           -- 试用客户数（分母，按客户去重）
    COUNT(DISTINCT o.account_id) AS pay_cnt,             -- 窗口内付费客户数（JOIN不上则为NULL，不计入）
    ROUND(COUNT(DISTINCT o.account_id) * 100.0
          / COUNT(DISTINCT t.account_id), 2) AS cvr_pct, -- 转化率
    ROUND(AVG(DATEDIFF(o.order_date, t.trial_start)), 1) AS avg_days_to_pay  -- 平均转化天数
FROM trials t
LEFT JOIN orders o
    ON o.account_id = t.account_id                       -- 同一客户
   AND o.order_type = '新签'                              -- 只认首次新签订单，增购续约不算转化
   AND o.order_date >= t.trial_start                      -- 付费不早于试用开始（防止历史客户重复试用）
   AND o.order_date <  t.trial_start + INTERVAL 30 DAY    -- 30天转化窗口（半开区间防边界重复）
GROUP BY t.channel
ORDER BY cvr_pct DESC;
```

结果解读：与解法一互相校验，两者差异通常来自pay_date冗余字段的更新滞后或转化窗口定义不同；面试中主动提出"双口径对账"是重要的加分项。

### 5. 性能分析与优化

解法一单表聚合，代价最低；解法二涉及JOIN，若 `orders` 表百万级，未带条件的JOIN会先产生大量中间行。优化建议：给 `orders` 建复合索引 `(account_id, order_type, order_date)`，使JOIN条件全部走索引，把每条试用记录的匹配降到近似常数级；`trials.channel` 基数很低（3~5个渠道），GROUP BY开销可忽略；若试用期数据量巨大（数百万），可先在子查询里对 `orders` 按 `account_id` 去重（取MIN(order_date)）再JOIN，避免COUNT(DISTINCT)在大中间结果上的开销；进一步可把30天窗口的判断改为在订单子查询里完成，减少JOIN后的行数。

### 6. 面试延伸考点

- **转化率分母要不要排除进行中的试用？** 回答要点：要区分"累计转化率"和"最终转化率"，进行中的试用还没到窗口终点，直接计入分母会低估转化率；严谨做法是只统计"试用开始超过30天"的样本（右删失处理）。
- **多触点渠道归因怎么做？** 回答要点：一个客户可能先点了广告又在官网注册，本题为末次触点归因；可用首次/末次触点、线性归因多口径对比，SQL上体现为渠道映射表与触点流水表的JOIN。
- **转化率和CAC如何联动决策？** 回答要点：转化率×客单价×留存时长 决定LTV，LTV/CAC>3才健康；转化率低的渠道若CAC也低，仍可能值得投。
- **如果渠道字段存在"未知/直接访问"占比很高怎么办？** 回答要点：先做归因补齐（UTM回填、反查referrer），再评估补齐前后转化率差异，避免决策建立在失真数据上。

### 7. 业务拓展思考

转化率结论要落到预算分配和市场动作上：对高转化低量的渠道（如分销）加大合作分成激励，对高量低转化的信息流要回到落地页与线索质量上做AB实验。口径延展上，可以按"渠道×客户规模×行业"三维切分转化率，识别"哪个渠道带来的是大客户"；再延展一步是试用时长与转化的关系（7天试用 vs 14天试用），为产品团队调整试用策略提供依据。长期看，渠道转化率应沉淀为周报核心指标，并接入线索评分模型做实时预警。

## SAAS-18 月度Logo Churn与金额Churn双口径

### 1. 业务背景

季度经营复盘会上，CFO要求客户成功运营负责人汇报月度流失情况，并明确要求两个口径分开：Logo Churn（流失客户数口径，反映丢了多少家客户）和金额Churn（流失MRR口径，反映丢了多少钱）。两者经常背离：丢掉3家小客户可能Logo流失率不低但金额流失很小；丢1家KA客户则金额流失巨大而Logo几乎无感。投资人和董事会看金额口径，运营团队用Logo口径监控服务覆盖，销售VP则关心流失的是哪些销售名下的客户。这个结论用来决定客户成功团队的编制投向与流失预警模型的优化优先级。**【加分点】** 能主动区分Logo与金额双口径，并说明分母取"上月末在续"而不是"当月均值"，是SaaS面试与其他行业拉开差距的关键。

### 2. 表结构说明

表 `contracts`（合同表）：一份合同代表一次签约生命周期。

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |
| mrr | DECIMAL(12,2) | 该合同的月度金额 |
| sign_date | DATE | 签约日期 |
| start_date | DATE | 合同生效日期 |
| end_date | DATE | 合同到期日期 |

示例数据：

| contract_id | account_id | mrr | sign_date | start_date | end_date |
|-------------|-----------|------|-----------|------------|-----------|
| 1 | 3001 | 10000.00 | 2024-02-01 | 2024-02-01 | 2025-01-31 |
| 2 | 3001 | 11000.00 | 2025-01-15 | 2025-02-01 | 2026-01-31 |
| 3 | 3002 | 5000.00 | 2024-03-10 | 2024-03-10 | 2025-03-09 |
| 4 | 3003 | 8000.00 | 2024-06-01 | 2024-06-01 | 2025-05-31 |
| 5 | 3004 | 3000.00 | 2025-01-10 | 2025-01-10 | 2025-04-09 |

（解释：3001在2025年1月提前续约，旧合同1月末到期、新合同2月生效，属于无缝续约，不能算流失；3002在2025年3月到期未续。）

### 3. 解题思路

先定口径：某客户在某月末"在续"指其至少一份合同覆盖该月末（start_date <= 月末 <= end_date）；"当月流失"指上月末在续而本月末不在续。Logo流失率 = 当月流失Logo数 / 上月末在续Logo数；金额流失率 = 流失客户MRR合计 / 上月末在续MRR合计。实现路径两条：解法一"时点快照法"，用递归CTE生成月末序列，JOIN合同表得到每月在续集合，再与下月集合反连接找流失者；解法二"事件法"，直接以 end_date 归属流失月，但必须剔除"到期后被续约"的合同（同一客户到期日附近有新合同生效）。**【避坑指南】** 三个坑：一是客户多份合同并存时Logo必须按account_id去重，直接数合同会把Logo口径变成合同口径；二是无缝续约的旧合同end_date不等于流失，事件法必须先剔除续约对；三是分母用"上月末"而非当月，否则月初流失的客户对当月分母贡献为0，流失率被放大。

### 4. 参考解法

**解法一：月末快照法（递归CTE月份主轴 + 反连接）**

```sql
WITH RECURSIVE months AS (                    -- 递归生成考察期内每个月末
    SELECT LAST_DAY(DATE '2024-12-01') AS month_end    -- 起点：2024年12月末
    UNION ALL
    SELECT LAST_DAY(month_end + INTERVAL 1 MONTH)      -- 下一个月末（LAST_DAY保证月末语义）
    FROM months
    WHERE month_end < LAST_DAY(DATE '2025-06-01')      -- 截止2025年6月末
),
onbook AS (                                   -- 每个月末"在续"的客户-MRR明细
    SELECT
        k.month_end,                          -- 月末时点
        c.account_id,                         -- 客户ID
        c.mrr                                 -- 合同MRR
    FROM months k
    JOIN contracts c                          -- 内连接：只保留覆盖月末的合同
      ON c.start_date <= k.month_end          -- 合同已生效
     AND c.end_date   >= k.month_end          -- 合同尚未到期（含当天）
),
snapshot AS (                                 -- 每月末的在续规模（Logo去重）
    SELECT
        month_end,                            -- 月末时点
        COUNT(DISTINCT account_id) AS logo_cnt,   -- 在续Logo数（多合同客户只算一次）
        SUM(mrr) AS mrr_total                 -- 在续MRR合计
    FROM onbook
    GROUP BY month_end
),
churned AS (                                  -- 找出"上月末在续、本月末缺席"的流失客户
    SELECT
        p.month_end,                          -- 流失发生的月（上月末时点所在月）
        COUNT(*) AS churn_logo,               -- 流失Logo数
        SUM(p.mrr) AS churn_mrr               -- 流失MRR（多合同客户需先汇总到客户级）
    FROM (
        SELECT month_end, account_id, SUM(mrr) AS mrr   -- 客户级MRR，防多合同重复计
        FROM onbook GROUP BY month_end, account_id
    ) p
    LEFT JOIN onbook c
        ON c.month_end = p.month_end + INTERVAL 1 MONTH   -- 下一个月末
       AND c.account_id = p.account_id                    -- 同一客户
    WHERE c.account_id IS NULL                            -- 下月末不在续 → 判定流失
    GROUP BY p.month_end
)
SELECT
    DATE_FORMAT(s.month_end, '%Y-%m') AS ym,               -- 统计月
    s.logo_cnt,                                            -- 本月末在续Logo数
    ch.churn_logo,                                         -- 当月流失Logo数
    LAG(s.logo_cnt) OVER (ORDER BY s.month_end) AS prev_logo_cnt,   -- 上月末Logo数（流失率分母）
    ROUND(ch.churn_logo * 100.0
          / NULLIF(LAG(s.logo_cnt) OVER (ORDER BY s.month_end), 0), 2) AS logo_churn_pct,   -- Logo月流失率
    ch.churn_mrr,                                          -- 当月流失MRR
    ROUND(ch.churn_mrr * 100.0
          / NULLIF(LAG(s.mrr_total) OVER (ORDER BY s.month_end), 0), 2) AS mrr_churn_pct    -- 金额月流失率
FROM snapshot s
JOIN churned ch ON ch.month_end = s.month_end               -- 只输出有流失发生的月份
ORDER BY s.month_end;
```

结果解读：月末快照法输出的流失率严格对应"期末在续基数"，是投资人尽调时的标准口径；Logo与金额两条流失率的背离本身就是分析结论（流失结构是大客户还是小客户）。

**解法二：事件法（以到期日归属流失月，先剔除续约对）**

```sql
WITH renewed_flag AS (                        -- 标记每份合同是否"被续约"（不算流失）
    SELECT
        c.contract_id,                        -- 合同ID
        EXISTS (                              -- 判断是否存在同一客户的后续合同
            SELECT 1
            FROM contracts n
            WHERE n.account_id = c.account_id          -- 同一客户
              AND n.contract_id <> c.contract_id       -- 不是自己
              AND n.start_date >= c.end_date - INTERVAL 30 DAY   -- 允许提前30天签续约
              AND n.start_date <= c.end_date + INTERVAL 90 DAY   -- 到期后90天内也算续约
        ) AS is_renewed                       -- 1=被续约，0=真流失或仍在履约
    FROM contracts c
)
SELECT
    DATE_FORMAT(c.end_date, '%Y-%m') AS churn_month,       -- 流失归属月：合同到期日所在月
    COUNT(DISTINCT c.account_id) AS churn_logo,            -- 流失Logo数（按客户去重，防多合同重复）
    SUM(c.mrr) AS churn_mrr                                -- 流失MRR合计
FROM contracts c
JOIN renewed_flag r ON r.contract_id = c.contract_id
WHERE r.is_renewed = 0                                      -- 剔除被续约的合同
  AND c.end_date BETWEEN DATE '2025-01-01' AND DATE '2025-06-30'   -- 考察期内的到期事件
GROUP BY churn_month
ORDER BY churn_month;
```

结果解读：事件法实现简单、流失月份归属直观（到期即流失），适合做流失客户清单下钻；但分母仍需另行计算上月末在续数，且归属月是"到期月"而非"缺席月"，与快照法可能有1个月错位，汇报时要统一口径。

### 5. 性能分析与优化

解法一的代价集中在：递归CTE生成月份（月数很少，可忽略）、合同表与月份轴JOIN（O(月数×合同数)）、onbook自反连接（O(在续明细²)的月内配对，实际由月份分割后并不大）；解法二的EXISTS相关子查询在合同表上逐行探测，合同量大时是主要瓶颈。优化建议：给 `contracts` 建复合索引 `(account_id, start_date, end_date)` 加速续约探测，再建 `(start_date, end_date)` 支撑时点JOIN的范围扫描；快照法中的 onbook 若按月反复使用，可物化为 `monthly_onbook` 中间表由ETL每日刷新；事件法中EXISTS可改写为LEFT JOIN + 派生表（按客户聚合出每份旧合同的下一份合同起始日），把相关子查询变成一次哈希JOIN。

### 6. 面试延伸考点

- **Gross MRR Churn Rate和Net MRR Retention有什么区别？** 回答要点：前者只减不增（纯流失+收缩的分母口径各异），后者把存量扩张加回来，NDR>100%时即使有流失整体仍在增长。
- **无缝续约但金额降了，算流失吗？** 回答要点：Logo口径不算流失、金额口径记为收缩（contraction），要在四因子拆分中体现而不是计入churn。
- **分母为什么用上月末在续而不是当月在续？** 回答要点：流失客户已不在当月分母中，用当月分母会让月初流失被放大、月末流失被低估，时点口径必须前移一个月。
- **如何处理"暂停服务但未退订"的客户？** 回答要点：定义宽限期规则（如暂停超60天记流失），SQL上以最后活跃/合同状态字段辅助判定，并保持口径文档化。

### 7. 业务拓展思考

双口径流失率的价值在于指导客户成功资源分配：金额流失集中在KA时，应把CSM高级资源绑定大客户并建立续约前90天的强制健康检查；Logo流失集中在SMB时，应推动自助化续约与信用卡自动扣款降低"被动流失"。口径延展上，可增加"复活客户（Resurrection）"独立统计流失客户回归率；联动动作上，把流失名单回流给销售做挽回（Win-back） campaign，并把流失原因（价格/功能/服务/倒闭）结构化沉淀，反哺产品定价与服务设计。

## SAAS-19 席位活跃率与月度活跃率透视

### 1. 业务背景

SaaS按席位（Seat）收费，客户买了100个席位但只有30个用户每月真的在用，意味着该客户大概率在下次续约时砍席位，甚至整体流失。续约前90天的客户健康评审会上，客户成功经理（CSM）需要每个客户的"席位活跃率"（当月有使用行为的席位数/购买席位数），并看最近三个月的活跃率趋势：持续走低的客户要提前干预（培训、重新分配席位），长期空置未分配的席位则建议客户减席或调整授权方式。这个结论直接用于续约前的席位谈判与客户健康分输入。**【面试高频】** "活跃/购买"比值类指标考察DISTINCT去重与半开区间时间过滤，是基础功底的试金石。

### 2. 表结构说明

表 `seat_license`（席位授权表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| seat_id | INT | 席位ID，主键 |
| account_id | INT | 客户ID |
| user_id | INT | 绑定用户ID，未分配为NULL |
| seat_type | VARCHAR(20) | 席位类型（标准/高级） |
| assigned_date | DATE | 分配日期 |

表 `usage_log`（用户使用日志表）：`user_id INT`、`event_date DATE`、`feature_name VARCHAR(50)`。

示例数据（seat_license）：

| seat_id | account_id | user_id | seat_type | assigned_date |
|---------|-----------|---------|-----------|---------------|
| 1 | 4001 | 9001 | 高级 | 2025-01-05 |
| 2 | 4001 | 9002 | 标准 | 2025-01-05 |
| 3 | 4001 | 9003 | 标准 | 2025-01-06 |
| 4 | 4001 | NULL | 标准 | NULL |
| 5 | 4002 | 9101 | 标准 | 2025-02-01 |

### 3. 解题思路

先定口径：某席位在某月"活跃"指其绑定的用户当月至少产生一条使用日志；席位活跃率 = 活跃席位数 / 购买席位数。注意两个边界：未分配席位（user_id为NULL）永远不活跃，统计时单独给出"空置席位数"更有业务价值；时间过滤用 `>= 月初 AND < 下月初` 的半开区间，避免月末23:59:59的边界遗漏。实现路径：解法一直接LEFT JOIN去重后的活跃用户集合，一次GROUP BY输出比率与空置明细；解法二先构建"席位×月份"主轴与活跃标记，再行转列输出每个客户近三个月的活跃率横切对比，方便CSM看趋势。**【避坑指南】** LEFT JOIN活跃集合时若不先对日志按user_id去重，会把JOIN放大后的多行算进COUNT，导致比率超过100%；COUNT(DISTINCT seat_id)是保底写法，但面试要能解释为什么会被放大。

### 4. 参考解法

**解法一：LEFT JOIN活跃用户集合 + 条件聚合（输出当月横切面）**

```sql
SELECT
    s.account_id,                                        -- 客户ID
    COUNT(DISTINCT s.seat_id) AS paid_seats,             -- 购买席位数（分母）
    COUNT(DISTINCT CASE WHEN a.user_id IS NOT NULL
                        THEN s.seat_id END) AS active_seats,          -- 活跃席位数（分子）
    ROUND(COUNT(DISTINCT CASE WHEN a.user_id IS NOT NULL THEN s.seat_id END) * 100.0
          / NULLIF(COUNT(DISTINCT s.seat_id), 0), 1) AS active_rate_pct,   -- 席位活跃率
    COUNT(DISTINCT CASE WHEN s.user_id IS NULL
                        THEN s.seat_id END) AS unassigned_seats,      -- 空置未分配席位数（单独给CSM看）
    COUNT(DISTINCT CASE WHEN s.user_id IS NOT NULL AND a.user_id IS NULL
                        THEN s.seat_id END) AS assigned_idle_seats    -- 已分配但整月未用的"僵尸席位"
FROM seat_license s
LEFT JOIN (
    SELECT DISTINCT user_id                              -- 先对日志按用户去重，减小JOIN规模
    FROM usage_log
    WHERE event_date >= DATE '2025-06-01'                -- 统计月起点
      AND event_date <  DATE '2025-07-01'                -- 半开区间，防月末边界重复或遗漏
) a ON a.user_id = s.user_id                             -- 席位 → 绑定用户 → 当月是否活跃
GROUP BY s.account_id
HAVING COUNT(DISTINCT s.seat_id) >= 10                   -- 席位过少的客户比率波动大，过滤小样本
ORDER BY active_rate_pct ASC;                            -- 活跃率最低的客户排前，CSM优先跟进
```

结果解读：活跃率低于50%的客户是续约高危名单；"僵尸席位"多说明客户存在按人数买单但实际用不满的问题，是谈判降席或转用量计费的信号。

**解法二：席位×月份主轴 + 行转列（输出近三月趋势）**

```sql
WITH act AS (                                 -- 各席位各月的活跃记录（先去重）
    SELECT DISTINCT
        s.account_id,                         -- 客户ID
        s.seat_id,                            -- 席位ID
        DATE_FORMAT(u.event_date, '%Y-%m') AS ym  -- 活跃发生的月份
    FROM seat_license s
    JOIN usage_log u ON u.user_id = s.user_id -- 内连接：只有真实使用才产生活跃记录
),
rate AS (                                     -- 客户×月份粒度的活跃率
    SELECT
        s.account_id,                         -- 客户ID
        DATE_FORMAT(m.month_first, '%Y-%m') AS ym,         -- 月份标签
        COUNT(DISTINCT s.seat_id) AS paid_seats,           -- 当月购买席位数
        COUNT(DISTINCT a.seat_id) AS active_seats          -- 当月活跃席位数（JOIN不上则为0）
    FROM seat_license s
    CROSS JOIN (                              -- 月份主轴：三个月各一行
        SELECT DATE '2025-04-01' AS month_first
        UNION ALL SELECT DATE '2025-05-01'
        UNION ALL SELECT DATE '2025-06-01'
    ) m
    LEFT JOIN act a
        ON a.account_id = s.account_id        -- 同一客户
       AND a.seat_id   = s.seat_id            -- 同一席位
       AND a.ym        = DATE_FORMAT(m.month_first, '%Y-%m')   -- 且活跃月份=主轴月份
    GROUP BY s.account_id, ym
)
SELECT
    account_id,                              -- 客户ID
    MAX(CASE WHEN ym = '2025-04' THEN ROUND(active_seats * 100.0 / NULLIF(paid_seats,0), 1) END) AS apr_rate,  -- 4月活跃率
    MAX(CASE WHEN ym = '2025-05' THEN ROUND(active_seats * 100.0 / NULLIF(paid_seats,0), 1) END) AS may_rate,  -- 5月活跃率
    MAX(CASE WHEN ym = '2025-06' THEN ROUND(active_seats * 100.0 / NULLIF(paid_seats,0), 1) END) AS jun_rate,  -- 6月活跃率
    MAX(paid_seats) AS paid_seats            -- 购买席位数（各月一般一致，取MAX兜底）
FROM rate
GROUP BY account_id
ORDER BY jun_rate DESC;                      -- 按最近月活跃率排序，快速定位恶化客户
```

结果解读：行转列后CSM一眼看出趋势——四月高、六月低的客户是"使用衰减型"高危，三个月都低的客户是"部署失败型"高危，干预动作完全不同。

### 5. 性能分析与优化

解法一的关键动作是把日志表先按user_id DISTINCT再JOIN，把亿级日志压缩成十万级用户集合后走小表JOIN大表；解法二多了月份主轴的CROSS JOIN，行数=席位数×3，仍在可控范围。优化建议：给 `usage_log` 建复合索引 `(user_id, event_date)`，让用户级时间过滤走范围扫描；如果日志表极大，推荐ETL预聚合出 `user_month_active`（user_id, ym）月度活跃表，查询时只面对去重后的结果；席位表规模小，无需特殊处理；避免在JOIN条件里对字段套函数（如 DATE_FORMAT(u.event_date,...) 放在ON里），应改为日期区间比较以便走索引，本例为教学演示保留了写法，生产上建议先物化月标签。

### 6. 面试延伸考点

- **活跃席位和活跃用户有什么区别？** 回答要点：一个用户可能对应多个席位（一人多席），席位口径按授权计量、用户口径按人头计量；按席位收费的公司必须以席位为分母，否则虚增活跃率。
- **为什么用半开区间而不是BETWEEN？** 回答要点：BETWEEN含两端，与相邻月产生重叠，且DATETIME字段BETWEEN月末容易漏掉23:59:59之后的事件；>=月初 AND <下月初 既不重也不漏。
- **如果客户买了席位但一直没分配，责任在谁？** 回答要点：这是交付/客户成功问题而非产品活跃问题，SQL要把"未分配"与"已分配未激活"分开统计，指向不同的干预动作。
- **如何把席位活跃率纳入健康分？** 回答要点：作为负向输入项加权（如活跃率<40%扣分），并区分趋势分（环比降幅）与水平分，避免一次性波动误判。

### 7. 业务拓展思考

席位活跃率的业务价值在于把"纸面合同"翻译成"真实使用"，是续约谈判和增购建议的核心依据：高活跃+满席使用是增购扩容的最佳时机，低活跃+大量空置则要主动建议调整采购模式（转用量计费）以免客户在续约时大面积砍席。口径延展上，可以细化到"核心功能席位"（如高级席位的专属功能是否被使用），以及管理员账号与普通账号分开统计；联动动作上，把低活跃席位名单接入客户成功的自动化触达（邮件培训、在线课程），并把趋势数据作为续约报价折扣授权的输入条件。

## SAAS-20 功能使用率Top/Bottom排行

### 1. 业务背景

产品运营负责人每季度做功能盘点：全公司几十个功能模块，哪些功能客户"离不开"（使用率高，是价值锚点），哪些功能"建了没人用"（使用率垫底，要么重做要么下线）。盘点会需要一张Top3/Bottom3排行表，使用率定义为"当月至少使用过一次该功能的在续客户数 / 当月在续客户总数"，按客户维度而非用户维度统计，因为付费决策在客户层面。这个结论决定产品路线图优先级：高使用率功能是续约话术里的价值证据，Bottom功能则进入"优化/下线/重新定位"评审。**【加分点】** 能说明为什么用"客户数"而非"事件数"做分子（防止高频噪声功能霸榜），体现对SaaS B端口径的理解。

### 2. 表结构说明

表 `feature_usage`（客户功能使用月度汇总表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| id | BIGINT | 记录ID，主键 |
| account_id | INT | 客户ID |
| feature_name | VARCHAR(50) | 功能名称 |
| stat_month | VARCHAR(7) | 统计月份（如2025-06） |
| use_days | INT | 当月使用天数 |

表 `accounts`（客户主表）：`account_id INT`、`account_name VARCHAR(100)`、`status VARCHAR(20)`（在续/已流失/试用中）、`segment VARCHAR(20)`。

示例数据（feature_usage）：

| id | account_id | feature_name | stat_month | use_days |
|----|-----------|--------------|------------|----------|
| 1 | 5001 | 报表中心 | 2025-06 | 22 |
| 2 | 5001 | 自动化流程 | 2025-06 | 5 |
| 3 | 5002 | 报表中心 | 2025-06 | 18 |
| 4 | 5003 | API集成 | 2025-06 | 12 |
| 5 | 5002 | 移动端审批 | 2025-06 | 1 |

### 3. 解题思路

先定口径：分子 = 当月 use_days >= 1 的 DISTINCT account_id 数；分母 = accounts 表中 status='在续' 的客户总数（口径固定为期末在续，避免试用客户稀释）。实现路径：解法一用两层CTE，第一层算分母（一行），CROSS JOIN 引入分子计算；第二层对使用率开两个反向 ROW_NUMBER 窗口（一正一反），外层筛出 Top3 与 Bottom3 后 UNION 输出；解法二用标量子查询作分母、NTILE(4)四分位看整体分布，Top/Bottom 等价于第一与第四分位。**【避坑指南】** 三个易错点：一是分子用SUM(use_days)会把"少数客户狂用"误判为高使用率，必须数客户数；二是 ROW_NUMBER 并列时只保留一条，若业务要求并列都进榜应改用RANK，两种写法要能说清差别；三是分母若误把"已流失""试用中"算进去，使用率被系统性低估。

### 4. 参考解法

**解法一：双窗口ROW_NUMBER正反排序取Top3/Bottom3**

```sql
WITH denom AS (                               -- 分母：当月在续客户总数（一行）
    SELECT COUNT(*) AS active_clients
    FROM accounts
    WHERE status = '在续'                     -- 口径：期末在续客户
),
feat AS (                                     -- 分子：各功能的使用客户数与使用率
    SELECT
        f.feature_name,                       -- 功能名
        COUNT(DISTINCT f.account_id) AS used_clients,   -- 使用该功能的客户数（关键：按客户去重）
        ROUND(COUNT(DISTINCT f.account_id) * 100.0
              / d.active_clients, 1) AS usage_rate      -- 使用率 = 分子/分母
    FROM feature_usage f
    CROSS JOIN denom d                       -- 分母只有一行，笛卡尔引入即可
    WHERE f.stat_month = '2025-06'           -- 统计月
      AND f.use_days >= 1                    -- 至少使用过1天才算使用
    GROUP BY f.feature_name
),
ranked AS (                                   -- 正反两个排序窗口
    SELECT
        feature_name,                         -- 功能名
        used_clients,                         -- 使用客户数
        usage_rate,                           -- 使用率
        ROW_NUMBER() OVER (ORDER BY usage_rate DESC, used_clients DESC) AS rk_top,  -- 从高到低排（并列时客户多者在前）
        ROW_NUMBER() OVER (ORDER BY usage_rate ASC,  used_clients ASC)  AS rk_low   -- 从低到高排
    FROM feat
)
SELECT
    CASE WHEN rk_top <= 3 THEN 'TOP3' ELSE 'BOTTOM3' END AS rank_type,   -- 榜单类型
    feature_name,                            -- 功能名
    used_clients,                            -- 使用客户数
    usage_rate                               -- 使用率
FROM ranked
WHERE rk_top <= 3 OR rk_low <= 3              -- 两个榜单各取前3
ORDER BY rank_type DESC, usage_rate DESC;     -- TOP在前并按使用率降序
```

结果解读：TOP3功能进入续约话术与价格锚点；BOTTOM3功能进入季度评审，结合功能定位（战略型/收费型/获客型）决定是优化还是下线，而非一律砍掉。

**解法二：标量子查询分母 + NTILE四分位看整体分布**

```sql
SELECT
    feature_name,                            -- 功能名
    used_clients,                            -- 使用客户数
    usage_rate,                              -- 使用率
    NTILE(4) OVER (ORDER BY usage_rate) AS usage_quartile   -- 按使用率均分四组：1=最低档，4=最高档
FROM (
    SELECT
        f.feature_name,                      -- 功能名
        COUNT(DISTINCT f.account_id) AS used_clients,   -- 使用客户数
        ROUND(COUNT(DISTINCT f.account_id) * 100.0
              / (SELECT COUNT(*) FROM accounts WHERE status = '在续'), 1) AS usage_rate  -- 标量子查询作分母
    FROM feature_usage f
    WHERE f.stat_month = '2025-06'
    GROUP BY f.feature_name
) t
ORDER BY usage_rate DESC;                    -- 使用率从高到低
-- 取Top/Bottom时在外层再包一层：WHERE usage_quartile IN (1, 4)
```

结果解读：NTILE把所有功能切成四档，比只看首尾3个更能反映整体分布（例如尾部功能普遍低于5%时说明是系统性问题而非个别功能问题），外层加一行过滤即可退化为Top/Bottom榜单。

### 5. 性能分析与优化

两种解法的主体都是对 feature_usage 按功能聚合，代价主要在 COUNT(DISTINCT account_id) 的去重上；解法二的标量子查询在MySQL 8.0中会被优化为一次性执行的常量，代价可忽略，但若优化器版本旧可能逐行执行，这也是推荐解法一CROSS JOIN写法的原因。优化建议：给 `feature_usage` 建复合索引 `(stat_month, feature_name, account_id)`，使按月按功能的分组直接走索引有序扫描；若功能数多、月度明细大，建议ETL预聚合出"功能×月×客户数"的中间表；当需要连续多个月的功能趋势时，把 WHERE stat_month 的等值过滤改为IN多个月并加月份到GROUP BY，一次扫描产出多月数据，避免每个功能单查一遍。

### 6. 面试延伸考点

- **ROW_NUMBER、RANK、DENSE_RANK取TopN时有什么差别？** 回答要点：三者处理并列的方式不同——ROW_NUMBER强制唯一、RANK并列跳号、DENSE_RANK并列不跳号；使用率相同的功能用RANK可能并列进榜导致榜单超过3个，需与业务确认。
- **为什么分子用客户数而不是调用次数？** 回答要点：调用次数受埋点抖动和自动化任务影响大，客户渗透率才反映功能价值；两者结合可再加"户均使用天数"看深度。
- **Bottom功能一定该下线吗？** 回答要点：不一定，要区分战略功能（如安全合规，使用少但影响投标）、收费功能与长尾功能，结合客户反馈与收入贡献判断。
- **如何排除"误触"使用？** 回答要点：设置最小使用阈值（如use_days>=3或单次时长>=30秒），并做阈值敏感性分析确认结论稳健。

### 7. 业务拓展思考

功能使用率排行是产品与商业化联动的枢纽：TOP功能沉淀为续约案例库和定价依据，BOTTOM功能进入季度评审决定投入产出。口径延展上，可增加"功能采用率曲线"（开通后N周内首次使用的客户占比）识别引导流程问题；按客户分层（KA/SMB）分别看排行，会发现同一功能在两个客群中的价值完全不同。联动动作上，把TOP3功能的使用数据推送给CSM做健康分正向输入，把Bottom名单交给产品经理做用户访谈排期，并将使用率变化与NPS评论交叉验证，避免只看数字做下线决策。
## SAAS-21 销售漏斗阶段转化与停留周期

### 1. 业务背景

销售运营（RevOps）负责诊断销售漏斗效率。CRM中每个商机都会留下阶段流转流水（新建→需求确认→方案报价→商务谈判→成单/输单），销售VP月度经营会上要两个核心结论：每个阶段向下一阶段的推进率（卡在哪个环节最多）、每个阶段的平均停留天数（哪个环节拖最久）。比如"方案报价→商务谈判"停留长达45天，可能是报价审批链路太长；"需求确认"阶段大量输单，可能是SDR给的线索质量差。这些结论用来决定：是否增配售前资源、是否调整阶段定义、以及对滞留商机设置强制推进或关闭规则。**【面试高频】** 漏斗+时间差是窗口函数LEAD/自连接的经典综合题，重点考察"下一阶段怎么取"。

### 2. 表结构说明

表 `opportunity_stage_log`（商机阶段流转流水表）：每进入一个阶段记一条。

| 字段名 | 类型 | 含义 |
|--------|------|------|
| id | BIGINT | 流水ID，自增主键 |
| opportunity_id | INT | 商机ID |
| stage | VARCHAR(20) | 进入的阶段（新建/需求确认/方案报价/商务谈判/成单/输单） |
| entered_at | DATETIME | 进入该阶段的时间 |

示例数据：

| id | opportunity_id | stage | entered_at |
|----|---------------|-------|------------|
| 1 | 6001 | 新建 | 2025-03-03 09:00:00 |
| 2 | 6001 | 需求确认 | 2025-03-07 14:00:00 |
| 3 | 6001 | 方案报价 | 2025-03-20 10:30:00 |
| 4 | 6001 | 商务谈判 | 2025-04-10 16:00:00 |
| 5 | 6001 | 成单 | 2025-04-25 11:00:00 |

（解释：商机6001依次经过四个销售阶段后在4月25日成单；终态阶段"成单/输单"没有下一阶段。）

### 3. 解题思路

先定口径：某阶段"进入次数"为该阶段流水的条数（同一商机可能多次进入同一阶段，回退是正常销售行为）；"推进到成单率"= 该阶段的下一阶段为'成单'的次数 / 该阶段进入次数；"平均停留天数"= 离开该阶段的时间减进入时间，终态阶段（成单/输单）无离开时间，须从均值中剔除。实现路径：解法一用LEAD窗口在同一商机的流水上取下一阶段与下一阶段时间，一次扫描完成；解法二用自连接+相关子查询取"同商机之后最早的一条"作对照，展示不依赖窗口的写法。**【避坑指南】** 三个易错点：一是自连接若只写 `s2.entered_at > s1.entered_at` 不取MIN，一个商机后续有N条流水就产生N倍膨胀，聚合全部失真；二是停留时间用TIMESTAMPDIFF(DAY,...)按自然日取整，若要精确小时应说明单位口径；三是多次回退的商机"直接成单率"只统计相邻推进，整体转化率另算，两个口径不能混。

### 4. 参考解法

**解法一：LEAD窗口取下一阶段（推荐）**

```sql
WITH seq AS (                                 -- 第一步：为每条流水找到同商机的下一条
    SELECT
        opportunity_id,                       -- 商机ID
        stage,                                -- 当前进入的阶段
        entered_at,                           -- 进入时间
        LEAD(stage) OVER (                    -- 窗口取下一阶段的名称
            PARTITION BY opportunity_id       -- 按商机分组
            ORDER BY entered_at               -- 按时间排序
        ) AS next_stage,                      -- 下一阶段（终态为NULL）
        LEAD(entered_at) OVER (
            PARTITION BY opportunity_id
            ORDER BY entered_at
        ) AS next_time                        -- 离开当前阶段的时间（=进入下一阶段的时间）
    FROM opportunity_stage_log
),
stay AS (                                     -- 第二步：算出每段停留
    SELECT
        stage,                                -- 阶段
        next_stage,                           -- 推进到哪个阶段
        TIMESTAMPDIFF(DAY, entered_at, next_time) AS stay_days   -- 停留天数（自然日）
    FROM seq
)
SELECT
    stage,                                    -- 阶段名
    COUNT(*) AS enter_cnt,                    -- 进入次数（含回退重进）
    SUM(next_stage = '成单') AS to_won_cnt,    -- 推进到成单的次数
    ROUND(SUM(next_stage = '成单') * 100.0 / COUNT(*), 1) AS stage_win_pct,   -- 该阶段直接成单率
    ROUND(AVG(CASE WHEN next_stage IS NOT NULL THEN stay_days END), 1) AS avg_stay_days,  -- 平均停留天数（终态NULL被AVG剔除）
    MAX(CASE WHEN next_stage IS NOT NULL THEN stay_days END) AS max_stay_days    -- 最长滞留天数，用于发现卡点
FROM stay
GROUP BY stage
ORDER BY FIELD(stage, '新建', '需求确认', '方案报价', '商务谈判', '成单', '输单');   -- 按漏斗顺序输出
```

结果解读：按漏斗顺序一张表看清"哪里卡人、哪里卡时间"；若某阶段直接成单率异常高而中间阶段被跳过，通常意味着阶段定义流于形式，是CRM流程治理信号。

**解法二：自连接 + 相关子查询取紧邻下一阶段（不依赖窗口）**

```sql
SELECT
    s1.stage,                                 -- 当前阶段
    COUNT(*) AS enter_cnt,                    -- 进入次数
    SUM(s2.stage = '成单') AS to_won_cnt,      -- 推进到成单次数
    ROUND(SUM(s2.stage = '成单') * 100.0 / COUNT(*), 1) AS stage_win_pct,   -- 阶段成单率
    ROUND(AVG(TIMESTAMPDIFF(DAY, s1.entered_at, s2.entered_at)), 1) AS avg_stay_days  -- 平均停留天数
FROM opportunity_stage_log s1
LEFT JOIN opportunity_stage_log s2            -- 自连接：同商机的"下一条"流水
    ON s2.opportunity_id = s1.opportunity_id  -- 同一商机
   AND s2.entered_at > s1.entered_at          -- 严格晚于当前进入时间
   AND s2.entered_at = (                      -- 且是所有后续里最早的一条，防止一对多膨胀
       SELECT MIN(s3.entered_at)
       FROM opportunity_stage_log s3
       WHERE s3.opportunity_id = s1.opportunity_id   -- 同一商机
         AND s3.entered_at > s1.entered_at           -- 之后发生的
   )
GROUP BY s1.stage
ORDER BY FIELD(s1.stage, '新建', '需求确认', '方案报价', '商务谈判', '成单', '输单');
```

结果解读：与解法一结果应完全一致；这种写法在窗口函数不可用（旧版本数据库）或面试官明确要求"不用窗口"时是标准替代方案，代价是相关子查询逐行探测。

### 5. 性能分析与优化

解法一单表一次扫描加窗口排序，复杂度 O(N log N)（按商机会话分组排序），是首选；解法二对每行执行相关子查询取MIN，最坏 O(N²)，流水表到十万行以上会明显变慢。优化建议：给 `opportunity_stage_log` 建复合索引 `(opportunity_id, entered_at)`，两个解法都依赖这个排序键——解法一避免filesort，解法二让MIN子查询走索引范围扫描变快；若按阶段周期分析是固定报表，建议ETL层用LEAD预计算 `stage_stay` 明细表（含next_stage、stay_days），查询层只做GROUP BY；回退频繁的场景可在子查询中限定 `s3.entered_at < s1.entered_at + INTERVAL 180 DAY` 防御异常数据导致的极端扫描。

### 6. 面试延伸考点

- **整体漏斗转化率（首阶段到成单）怎么算？** 回答要点：与相邻阶段转化率不同，整体转化率=成单商机数/创建商机数，用商机粒度去重（一个商机只算一次），可与相邻转化率相乘交叉验证但通常不相等（存在跳阶段与回退）。
- **如何识别"僵尸商机"？** 回答要点：当前所处阶段停留天数超过该阶段P90停留时长的商机，用窗口或与阶段均值表JOIN判定，输出清单给销售经理强制处置。
- **阶段停留时长的口径为什么中位数可能比均值好？** 回答要点：停留时长右偏严重（少数商机滞留半年），均值被拉高，MEDIAN可用窗口计数法或PERCENT_RANK近似实现。
- **回退（阶段倒流）要不要算进转化率？** 回答要点：相邻口径下每次进入独立统计会重复计数，商机口径下要取每个商机的最高到达阶段，两种口径服务不同分析目的，汇报需注明。

### 7. 业务拓展思考

漏斗诊断的价值在于把"业绩不好"拆成可执行的具体动作：转化率卡点指向线索质量与售前能力，停留卡点指向流程与审批效率。口径延展上，可按商机金额分层（大单/小单）分别看漏斗，大单通常在商务谈判阶段停留更久、需要管理层介入机制；按销售个人维度下钻，能识别需要辅导的对象。联动动作上，把滞留商机清单自动推送给销售经理并接入AI推荐下一步动作；将阶段流转数据与市场活动归因交叉，评估哪些活动带来的商机推进更快，反哺市场预算分配。

## SAAS-22 续约率与续约金额率

### 1. 业务背景

SaaS的商业模型建立在"订阅续约"上：新签一次性，续约才是复利。季度董事会要求汇报两个指标：续约率（到期合同中被续约的比例，Logo口径）和续约金额率（续约新合同ACV合计 / 到期旧合同ACV合计，金额口径，能反映涨价或降级）。销售运营用这个结论做三件事：给销售团队定续约配额与佣金系数、识别续约风险客户名单、评估定价调整对续约的影响。比如续约率90%但金额续约率只有75%，说明大量客户在缩规模续约，比整体流失更值得警惕。**【加分点】** 能主动定义"续约判定窗口"（到期前后多少天内的同客户新合同算续约）并解释为什么需要它，是本题的核心区分点。

### 2. 表结构说明

表 `contracts`（合同表，含新签与续约产生的所有合同）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | INT | 合同ID，主键 |
| account_id | INT | 客户ID |
| acv | DECIMAL(12,2) | 合同年度金额 |
| sign_date | DATE | 签约日期 |
| start_date | DATE | 合同生效日期 |
| end_date | DATE | 合同到期日期 |

示例数据：

| contract_id | account_id | acv | sign_date | start_date | end_date |
|-------------|-----------|------|-----------|------------|-----------|
| 1 | 7001 | 120000.00 | 2024-03-01 | 2024-03-01 | 2025-02-28 |
| 2 | 7001 | 132000.00 | 2025-02-10 | 2025-03-01 | 2026-02-28 |
| 3 | 7002 | 60000.00 | 2024-05-15 | 2024-05-15 | 2025-05-14 |
| 4 | 7003 | 90000.00 | 2024-01-20 | 2024-01-20 | 2025-01-19 |
| 5 | 7004 | 45000.00 | 2024-08-01 | 2024-08-01 | 2025-07-31 |

（解释：7001旧合同2月末到期、新合同3月生效且金额上涨10%，属于金额扩张的续约；7002到期但考察截止时未见续约。）

### 3. 解题思路

先定口径：到期合同 = end_date 早于等于考察截止日的合同（旧合同）；判定续约 = 同一客户在旧合同到期日前30天（允许提前签）至到期日后90天（允许短暂断档）窗口内存在新合同生效。续约率 = 被续约的到期合同数 / 到期合同总数；金额续约率 = 被续约旧合同对应的新合同ACV合计 / 到期旧合同ACV合计。实现路径：解法一用窗口 `LEAD(start_date)`/`LEAD(acv)` 按客户按生效日排序，对每份合同判断"下一份是否落在窗口内"；解法二用自连接+MIN(start_date)子查询定位续约合同，不依赖窗口。**【避坑指南】** 四个坑：一是同一客户同一天多份新合同会导致JOIN一对多放大，需用MIN或ROW_NUMBER取唯一；二是金额续约率的分子必须取新合同ACV、分母取旧合同ACV，写反了含义完全不同；三是窗口口径（30/90天）必须与业务对齐并写进文档；四是未到期合同不能进分母，否则续约率被稀释。

### 4. 参考解法

**解法一：LEAD窗口判定续约（推荐）**

```sql
WITH ordered AS (                             -- 第一步：每份合同找到"同客户的下一份合同"
    SELECT
        contract_id,                          -- 合同ID
        account_id,                           -- 客户ID
        acv,                                  -- 本合同年度金额
        start_date,                           -- 本合同生效日
        end_date,                             -- 本合同到期日
        LEAD(start_date) OVER (               -- 下一份合同的生效日
            PARTITION BY account_id
            ORDER BY start_date, contract_id  -- 按生效日排序，contract_id做并列tiebreak
        ) AS next_start,
        LEAD(acv) OVER (
            PARTITION BY account_id
            ORDER BY start_date, contract_id
        ) AS next_acv                         -- 下一份合同的金额
    FROM contracts
),
flagged AS (                                  -- 第二步：打续约标签
    SELECT
        contract_id,                          -- 合同ID
        account_id,                           -- 客户ID
        acv,                                  -- 旧合同金额（金额续约率分母）
        end_date,                             -- 到期日
        next_start,                           -- 下一份合同生效日
        next_acv,                             -- 新合同金额（金额续约率分子）
        CASE
            WHEN next_start IS NOT NULL
             AND DATEDIFF(next_start, end_date) BETWEEN -30 AND 90   -- 生效日在到期前30天~后90天窗口内
            THEN 1 ELSE 0
        END AS is_renewed                     -- 续约标记：1=被续约
    FROM ordered
)
SELECT
    COUNT(*) AS expired_cnt,                                        -- 到期合同总数（分母）
    SUM(is_renewed) AS renewed_cnt,                                 -- 被续约合同数
    ROUND(AVG(is_renewed) * 100, 1) AS logo_renewal_rate_pct,       -- 续约率（Logo口径）
    ROUND(SUM(CASE WHEN is_renewed = 1 THEN next_acv ELSE 0 END) * 100.0
          / NULLIF(SUM(acv), 0), 1) AS amount_renewal_rate_pct      -- 金额续约率 = 新ACV合计/旧ACV合计
FROM flagged
WHERE end_date <= DATE '2025-09-30'                               -- 只统计考察截止日前已到期的合同
ORDER BY NULL;                                                    -- 单行输出
```

结果解读：若Logo续约率与金额续约率差距大（如90% vs 75%），说明"缩量续约"普遍，是涨价过猛或用量不足的信号；金额续约率>100%说明净扩张续约，是定价权强的表现。

**解法二：自连接 + MIN子查询定位续约合同（不依赖窗口）**

```sql
SELECT
    COUNT(*) AS expired_cnt,                                        -- 到期合同数
    SUM(n.contract_id IS NOT NULL) AS renewed_cnt,                  -- 有续约的合同数
    ROUND(AVG(n.contract_id IS NOT NULL) * 100, 1) AS logo_renewal_rate_pct,      -- 续约率
    ROUND(SUM(CASE WHEN n.contract_id IS NOT NULL THEN n.acv ELSE 0 END) * 100.0
          / NULLIF(SUM(o.acv), 0), 1) AS amount_renewal_rate_pct    -- 金额续约率
FROM contracts o
LEFT JOIN contracts n                              -- 自连接：为每份旧合同找续约新合同
    ON n.account_id = o.account_id                 -- 同一客户
   AND n.contract_id <> o.contract_id              -- 不是自己
   AND n.start_date = (                            -- 取窗口内最早生效的一份，保证一一对应
       SELECT MIN(n2.start_date)
       FROM contracts n2
       WHERE n2.account_id = o.account_id          -- 同一客户
         AND n2.contract_id <> o.contract_id       -- 排除自身
         AND n2.start_date >= o.end_date - INTERVAL 30 DAY   -- 允许提前30天签
         AND n2.start_date <= o.end_date + INTERVAL 90 DAY   -- 到期后90天内仍算续约
   )
WHERE o.end_date <= DATE '2025-09-30'              -- 到期合同才进分母
GROUP BY NULL;                                     -- 汇总为一行
```

结果解读：与解法一互为校验；此写法的好处是把续约合同本身JOIN了出来，可以直接带上新合同的字段（签约人、折扣、版本）做续约质量下钻，窗口法要再多一层回JOIN。

### 5. 性能分析与优化

解法一一次扫描加窗口排序，O(N log N)；解法二的相关子查询逐行找MIN，合同表大了以后是主要瓶颈，但借助 `(account_id, start_date)` 索引可以把每次探测降为索引范围查找，十万级合同仍可接受。优化建议：复合索引 `(account_id, start_date, contract_id)` 是两个解法共同的命脉，务必建立；若续约判定是高频报表，建议ETL预生成 `contract_renewal_map`（旧合同ID→新合同ID映射表），业务查询只做简单JOIN；金额续约率涉及SUM两个方向，可把窗口法的flagged结果物化，供"续约率×销售团队×产品线"多维下钻复用；注意同一客户同日多合同的防御，生产上应先用ROW_NUMBER去重再判定。

### 6. 面试延伸考点

- **GRR（Gross Revenue Retention）和金额续约率的区别？** 回答要点：GRR上限100%，不含扩张，只看存量能否保住；金额续约率若把同客户增购算进去可超100%，接近NRR概念，汇报时必须声明口径。
- **提前续约（到期前3个月签）算谁的当期业绩？** 回答要点：收入确认按合同起始期，业绩归属按签约期，两个时间轴要分开建模，SQL中体现为sign_date与start_date双字段。
- **多年度合同怎么算续约率？** 回答要点：可按"合同"到期计算，也可拆成年度义务（每次周年日算一次续约决策点），口径不同结论不同，需提前对齐。
- **续约率和流失率能互相推导吗？** 回答要点：月度上近似互补但严格不成立——存在断档超过宽限期的"迟续约"与复活客户，跨期核对要留出入账时间窗。

### 7. 业务拓展思考

续约双口径是收入预测（Renewal Forecast）的底层输入：把未来两个季度到期合同按历史续约率加权，即可滚动预测基线收入，再叠加Pipeline修正。业务联动上，续约率低的销售分区应启动客户成功前置介入（到期前90天健康检查）；金额续约率低于Logo续约率时，定价团队要复盘涨价幅度与折扣策略。口径延展上，可拆分"自动续约（信用卡扣款）"与"人工续约"两类，前者反映产品黏性、后者反映销售能力；进一步把续约金额率分解为"价格变动×席位变动×版本变动"三因子，定位缩量续约的真实原因。

## SAAS-23 客户健康分多源合成

### 1. 业务背景

客户成功团队（CSM）按人头覆盖上百个客户，不可能平均用力，需要一个量化的"健康分"把客户分成健康/观察/高危三档，让CSM把时间花在高危客户上。健康分由三个数据源合成：产品活跃度（近30天活跃天数，权重40%）、功能广度（当月使用的功能模块数，权重30%）、服务压力（未解决工单数，反向指标，权重30%）——用得勤、用得广、投诉少的是健康客户；某项骤降就是流失前兆。每月1号客户成功总监用健康分名单做资源排布：高危客户48小时内CSM必须触达，观察客户进入培育队列。**【面试高频】** 多源数据合成类题目考察CTE分层能力与归一化处理，"负向指标怎么进加权"是必问点。

### 2. 表结构说明

表 `usage_daily`（客户日活跃表）：`account_id INT`、`active_date DATE`（该客户当日有登录即有一条，按客户×日去重）。

表 `tickets`（工单表）：`ticket_id INT`、`account_id INT`、`created_date DATE`、`status VARCHAR(20)`（open待解决/resolved已解决）。

表 `feature_usage`（功能使用月度汇总）：`account_id INT`、`feature_name VARCHAR(50)`、`stat_month VARCHAR(7)`。

示例数据（usage_daily）：

| account_id | active_date |
|-----------|-------------|
| 8001 | 2025-09-02 |
| 8001 | 2025-09-03 |
| 8002 | 2025-09-05 |
| 8003 | 2025-09-01 |
| 8003 | 2025-09-02 |

示例数据（tickets）：

| ticket_id | account_id | created_date | status |
|-----------|-----------|--------------|--------|
| 1 | 8001 | 2025-09-10 | resolved |
| 2 | 8002 | 2025-09-12 | open |
| 3 | 8002 | 2025-09-20 | open |
| 4 | 8003 | 2025-09-15 | open |
| 5 | 8001 | 2025-09-18 | open |

### 3. 解题思路

先定口径：三个原始指标分别是近30天活跃天数（usage_daily按客户COUNT DISTINCT日期）、未解决工单数（tickets中status='open'）、功能广度（feature_usage当月DISTINCT功能数）。由于三者量纲不同（天数0~30、工单0~N、功能0~M），合成前必须归一化：用min-max把每个指标压到0~1，其中工单是负向指标，取 (1 - 归一值) 反向处理。健康分 = 40×活跃分 + 30×功能分 + 30×工单反向分，再按阈值分级（>=70健康、40~69观察、<40高危）。实现路径：解法一四层CTE（三个聚合层+客户全集层）→ 窗口归一化层 → 打分层 → 分级输出；解法二把max/min放到一个汇总CTE里CROSS JOIN实现归一化，不依赖窗口。**【避坑指南】** 三个坑：一是NULLIF防除零（所有客户活跃天数相同时max=min）；二是客户全集必须三表UNION，只从usage_daily出发会漏掉"当月零活跃但投诉中"的最危险客户；三是工单为0的客户其负向分应得满分，直接用归一化值不取反会把零投诉客户判成最差。

### 4. 参考解法

**解法一：多层CTE + 窗口归一化（推荐）**

```sql
WITH usage_agg AS (                           -- 指标一：近30天活跃天数
    SELECT account_id, COUNT(DISTINCT active_date) AS active_days
    FROM usage_daily
    WHERE active_date >= DATE '2025-09-01'    -- 统计月起点
      AND active_date <  DATE '2025-10-01'    -- 半开区间
    GROUP BY account_id
),
ticket_agg AS (                               -- 指标二：未解决工单数（负向）
    SELECT account_id, COUNT(*) AS open_tickets
    FROM tickets
    WHERE status = 'open'                     -- 只算未解决的
    GROUP BY account_id
),
feature_agg AS (                              -- 指标三：当月功能广度
    SELECT account_id, COUNT(DISTINCT feature_name) AS feature_cnt
    FROM feature_usage
    WHERE stat_month = '2025-09'
    GROUP BY account_id
),
base AS (                                     -- 客户全集 + 三指标拼接（缺失补0）
    SELECT
        a.account_id,                         -- 客户ID（来自三表UNION的全集）
        COALESCE(u.active_days, 0) AS active_days,
        COALESCE(t.open_tickets, 0) AS open_tickets,
        COALESCE(f.feature_cnt, 0) AS feature_cnt
    FROM (SELECT account_id FROM usage_daily
          UNION SELECT account_id FROM tickets          -- UNION自带去重，得到客户全集
          UNION SELECT account_id FROM feature_usage) a
    LEFT JOIN usage_agg   u ON u.account_id = a.account_id
    LEFT JOIN ticket_agg  t ON t.account_id = a.account_id
    LEFT JOIN feature_agg f ON f.account_id = a.account_id
),
norm AS (                                     -- min-max归一化到0~1
    SELECT
        account_id,                           -- 客户ID
        (active_days  - MIN(active_days)  OVER ()) /
            NULLIF(MAX(active_days)  OVER () - MIN(active_days)  OVER (), 0) AS s_act,    -- 活跃分（正向）
        (feature_cnt  - MIN(feature_cnt)  OVER ()) /
            NULLIF(MAX(feature_cnt)  OVER () - MIN(feature_cnt)  OVER (), 0) AS s_feat,   -- 功能分（正向）
        (open_tickets - MIN(open_tickets) OVER ()) /
            NULLIF(MAX(open_tickets) OVER () - MIN(open_tickets) OVER (), 0) AS s_tick    -- 工单分（负向，越大越差）
    FROM base
),
scored AS (                                   -- 加权合成
    SELECT
        account_id,                           -- 客户ID
        ROUND(40 * COALESCE(s_act, 0)         -- 活跃权重40
            + 30 * COALESCE(s_feat, 0)        -- 功能广度权重30
            + 30 * (1 - COALESCE(s_tick, 0)), -- 工单反向：1-归一值，零工单得满分
            1) AS health_score                -- 健康分0~100
    FROM norm
)
SELECT
    account_id,                              -- 客户ID
    health_score,                            -- 健康分
    CASE WHEN health_score >= 70 THEN '健康'
         WHEN health_score >= 40 THEN '观察'
         ELSE '高危' END AS health_level     -- 三档分级，阈值与CSM服务SLA绑定
FROM scored
ORDER BY health_score ASC;                   -- 高危排前，供CSM按序触达
```

结果解读：高危档名单是CSM当周的救火清单；健康分分布整体左移（全员偏低）时优先排查是数据问题（埋点断更、工单积压）还是产品问题。

**解法二：极值汇总CTE + CROSS JOIN归一化（不依赖窗口）**

```sql
WITH base AS (                                -- 与解法一相同的三源拼接（此处省略聚合CTE，逻辑一致）
    SELECT
        a.account_id,
        COALESCE(u.active_days, 0)  AS active_days,
        COALESCE(t.open_tickets, 0) AS open_tickets,
        COALESCE(f.feature_cnt, 0)  AS feature_cnt
    FROM (SELECT account_id FROM usage_daily
          UNION SELECT account_id FROM tickets
          UNION SELECT account_id FROM feature_usage) a
    LEFT JOIN (SELECT account_id, COUNT(DISTINCT active_date) AS active_days
               FROM usage_daily WHERE active_date >= '2025-09-01' AND active_date < '2025-10-01'
               GROUP BY account_id) u ON u.account_id = a.account_id
    LEFT JOIN (SELECT account_id, COUNT(*) AS open_tickets
               FROM tickets WHERE status = 'open' GROUP BY account_id) t ON t.account_id = a.account_id
    LEFT JOIN (SELECT account_id, COUNT(DISTINCT feature_name) AS feature_cnt
               FROM feature_usage WHERE stat_month = '2025-09' GROUP BY account_id) f ON f.account_id = a.account_id
),
stats AS (                                    -- 一行汇总三个指标的极值
    SELECT
        MAX(active_days)  AS max_act,  MIN(active_days)  AS min_act,
        MAX(feature_cnt)  AS max_ft,   MIN(feature_cnt)  AS min_ft,
        MAX(open_tickets) AS max_tk,   MIN(open_tickets) AS min_tk
    FROM base
)
SELECT
    b.account_id,                            -- 客户ID
    ROUND(40 * (b.active_days - s.min_act) / NULLIF(s.max_act - s.min_act, 0)   -- 活跃归一加权
        + 30 * (b.feature_cnt - s.min_ft) / NULLIF(s.max_ft - s.min_ft, 0)   -- 功能归一加权
        + 30 * (1 - (b.open_tickets - s.min_tk) / NULLIF(s.max_tk - s.min_tk, 0)),  -- 工单反向加权
        1) AS health_score
FROM base b CROSS JOIN stats s                -- 极值表只有一行，笛卡尔接入
ORDER BY health_score ASC;
```

结果解读：与窗口法结果一致；这种写法把归一化参数集中在一处，便于把权重和极值口径做成配置表（比如改用P5/P95截尾极值抗异常点）。

### 5. 性能分析与优化

两种解法的主体代价都是三次聚合加一次拼接，瓶颈在客户全集UNION后的三次LEFT JOIN；窗口归一化（解法一）只需一次排序，CROSS JOIN极值（解法二）为O(1)接入，两者差异不大。优化建议：给 `usage_daily` 建 `(active_date, account_id)` 或按月分区的索引，把时间过滤变成范围扫描；`tickets` 建 `(status, account_id)` 复合索引让open工单过滤走索引；健康分是月度批任务，推荐把三个聚合结果物化到 `account_health_feature` 宽表，由调度任务每日增量刷新，查询层只做加权与分级；若客户数十万以上，UNION全集可改为以客户维表 `accounts` 为基准LEFT JOIN三源，语义更清晰且少一次UNION去重排序。

### 6. 面试延伸考点

- **为什么用min-max而不是z-score归一化？** 回答要点：健康分要落在一个稳定可解释的0~100区间，min-max直观；但极值敏感，可改用分位数截尾（P5/P95）或z-score+线性压缩，需说明选择理由。
- **工单数是不是越多越不健康？** 回答要点：不一定，主动提工单可能是深度使用信号；更精细的是"重复开单率""升级投诉率"，口径上区分服务问题与使用问题。
- **健康分阈值70/40怎么定？** 回答要点：不应拍脑袋，用历史流失客户回溯健康分分布，取流失前一个月分布的P25作为高危线，并用混淆矩阵验证命中率。
- **负向指标还有哪些常见处理方式？** 回答要点：取反归一（本题）、设置扣分上限（防止一个极端工单拖垮全分）、独立为"风险标记"不进加权，按业务解释力选择。

### 7. 业务拓展思考

健康分是客户成功从"被动救火"转向"主动经营"的基础设施：高危档触发48小时SLA触达、观察档进入自动培育（培训邮件、最佳实践推送）、健康档识别为增购与转介绍候选。口径延展上，可引入趋势项（活跃天数环比降幅比绝对值更早预警）、发起人角色覆盖度（决策层账号是否活跃）等；权重本身也应按客群AB测试校准。联动动作上，健康分作为续约报价折扣的授权输入（低分不给大折扣续约）、作为流失预警模型的核心特征，并回流给销售做挽回优先级排序。

## SAAS-24 开通到首次核心功能使用的激活时长

### 1. 业务背景

SaaS交付团队有个共识：客户开通后越早用上"核心功能"（如报表中心、自动化流程、API集成），续约概率越高，这就是"激活时刻（Aha Moment）"理论。交付经理每周要review新开通客户的"激活时长"（开通日到首次使用核心功能的天数），分桶看分布：7天内激活的算部署顺利，30天以上没激活的进入"部署救援"流程，一直没用核心功能的则标记为交付失败风险。这个结论用来优化实施排期、决定是否安排现场培训，也是客户成功接手时的第一份风险清单。**【加分点】** 能把"未使用"作为一种结果单独成桶（而不是丢给NULL消失），体现分析完整性。

### 2. 表结构说明

表 `accounts`（客户开通记录）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |
| account_name | VARCHAR(100) | 客户名称 |
| activated_at | DATE | 开通日期（合同生效、账号开通） |
| plan | VARCHAR(20) | 版本（标准版/专业版/旗舰版） |

表 `usage_log`（功能使用明细）：`account_id INT`、`user_id INT`、`feature_name VARCHAR(50)`、`event_date DATE`。

示例数据（accounts）：

| account_id | account_name | activated_at | plan |
|-----------|--------------|--------------|------|
| 8101 | 星辰科技 | 2025-06-02 | 专业版 |
| 8102 | 蓝海贸易 | 2025-06-05 | 标准版 |
| 8103 | 云图传媒 | 2025-06-10 | 旗舰版 |
| 8104 | 恒基制造 | 2025-06-15 | 专业版 |
| 8105 | 中科信息 | 2025-06-20 | 标准版 |

### 3. 解题思路

先定口径：激活时长 = DATEDIFF(首次核心功能使用日, 开通日)；核心功能清单白名单 ('报表中心','自动化流程','API集成') 由产品定义，不能用全部功能代替；结果分四桶：7天内激活、8-30天、30天以上、未使用。实现路径：解法一在accounts LEFT JOIN usage_log后用 `MIN(CASE WHEN feature_name IN (...) THEN event_date END)` 条件聚合，一次查询同时输出明细与分桶；解法二先在子查询/CTE里对usage_log过滤白名单并按客户取MIN，再LEFT JOIN回accounts，扫描行数更少。**【避坑指南】** 两个坑：一是必须LEFT JOIN而非INNER JOIN，否则"从未使用核心功能"的客户整行消失，而这恰恰是最重要的风险名单；二是MIN要作用于CASE过滤后的日期而不是先MIN再过滤；如果日志表有脏数据（event_date早于activated_at的补录数据），DATEDIFF会出现负数，要在CASE里显式处理或与业务确认补录口径。

### 4. 参考解法

**解法一：LEFT JOIN + 条件聚合（明细与分桶一次完成）**

```sql
SELECT
    a.account_id,                            -- 客户ID
    a.account_name,                          -- 客户名称
    a.activated_at,                          -- 开通日
    MIN(CASE WHEN u.feature_name IN ('报表中心', '自动化流程', 'API集成')
             THEN u.event_date END) AS first_core_date,     -- 首次核心功能使用日（无则为NULL）
    DATEDIFF(MIN(CASE WHEN u.feature_name IN ('报表中心', '自动化流程', 'API集成')
                       THEN u.event_date END), a.activated_at) AS days_to_first_use,  -- 激活时长（天）
    CASE
        WHEN MIN(CASE WHEN u.feature_name IN ('报表中心', '自动化流程', 'API集成')
                      THEN u.event_date END) IS NULL THEN '未使用'   -- 从未用核心功能 → 交付失败风险
        WHEN DATEDIFF(MIN(CASE WHEN u.feature_name IN ('报表中心', '自动化流程', 'API集成')
                           THEN u.event_date END), a.activated_at) <= 7 THEN '7天内激活'   -- 部署顺利
        WHEN DATEDIFF(MIN(CASE WHEN u.feature_name IN ('报表中心', '自动化流程', 'API集成')
                           THEN u.event_date END), a.activated_at) <= 30 THEN '8-30天'     -- 正常偏慢
        ELSE '30天以上'                      -- 激活迟缓 → 部署救援名单
    END AS activation_bucket                 -- 激活分桶
FROM accounts a
LEFT JOIN usage_log u
    ON u.account_id = a.account_id           -- 左连接：保证从未使用核心功能的客户也在结果里
GROUP BY a.account_id, a.account_name, a.activated_at
ORDER BY days_to_first_use DESC NULLS FIRST; -- MySQL 8.0中NULL在DESC排序时天然排最前，未使用客户置顶
```

结果解读：置顶的"未使用"与"30天以上"客户构成当周部署救援清单；整体分桶分布则回答"我们的实施流程平均几天让客户用起来"。

**解法二：先聚合首次使用再JOIN（扫描量更小）**

```sql
WITH first_use AS (                          -- 先把日志收窄到核心功能并取每客户最早一天
    SELECT
        account_id,                          -- 客户ID
        MIN(event_date) AS first_core_date   -- 首次核心功能使用日
    FROM usage_log
    WHERE feature_name IN ('报表中心', '自动化流程', 'API集成')   -- 白名单先过滤，大幅减少扫描
    GROUP BY account_id
),
bucketed AS (                                -- 关联开通表并分桶
    SELECT
        a.account_id,                        -- 客户ID
        DATEDIFF(f.first_core_date, a.activated_at) AS days_to_first_use,   -- 激活时长
        CASE WHEN f.first_core_date IS NULL THEN '未使用'
             WHEN DATEDIFF(f.first_core_date, a.activated_at) <= 7  THEN '7天内激活'
             WHEN DATEDIFF(f.first_core_date, a.activated_at) <= 30 THEN '8-30天'
             ELSE '30天以上' END AS activation_bucket       -- 分桶标签
    FROM accounts a
    LEFT JOIN first_use f ON f.account_id = a.account_id   -- 左连接保全量新客
    WHERE a.activated_at >= DATE '2025-06-01'              -- 只看本季度开通客户，避免老客户干扰
)
SELECT
    activation_bucket,                       -- 分桶
    COUNT(*) AS client_cnt,                  -- 客户数
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS pct,   -- 占比（窗口求总分母）
    ROUND(AVG(days_to_first_use), 1) AS avg_days   -- 该桶平均激活天数（未使用桶为NULL）
FROM bucketed
GROUP BY activation_bucket
ORDER BY FIELD(activation_bucket, '7天内激活', '8-30天', '30天以上', '未使用');   -- 按激活快慢排序
```

结果解读：分桶汇总比明细更适合进周报——若"7天内激活"占比逐月上升说明实施流程在改善；"未使用"占比是交付质量的红线指标。

### 5. 性能分析与优化

解法一把全部日志JOIN进来做条件聚合，日志量千万级时中间结果大；解法二先在子查询里把日志收窄到三个核心功能，通常能砍掉90%以上扫描量，是大数据量下的首选。优化建议：给 `usage_log` 建复合索引 `(feature_name, account_id, event_date)`，白名单过滤+按客户分组可直接走索引；若核心功能清单会变化，把它落成配置维表 `core_features` 再JOIN，改清单不改SQL；开通客户量大时给 `accounts.activated_at` 建索引支撑时间范围过滤；进一步可在ETL层预计算 `account_first_core_use`（客户级首次核心使用日），激活时长分析退化为一次轻量JOIN。

### 6. 面试延伸考点

- **"首次使用核心功能"和"首次登录"哪个是更好的激活指标？** 回答要点：登录是浅行为、核心功能是价值行为，激活口径应绑定Aha Moment；两者差值（登录了但没用到核心功能）本身就是引导流程的问题清单。
- **DATEDIFF出现负数说明什么？** 回答要点：存在使用日志早于开通日的数据（灰度试用、补录、时钟问题），要先和业务确认口径再决定是取0、剔除还是修复开通日期。
- **如何验证激活时长与续约的相关性？** 回答要点：按激活分桶统计后续续约率/流失率做对比（本题30题同思路），必要时做生存分析（Cox回归），SQL负责出分组对比，建模交给Python/R。
- **多用户客户怎么算"首次"？** 回答要点：任意用户首次使用即可，但更严格口径可要求"管理员之外的业务用户"使用，防止实施顾问代操作的假激活。

### 7. 业务拓展思考

激活时长是交付质量的先行指标，直接预测首年续约：把"未使用/30天以上"名单接入交付周会闭环，7天激活率纳入实施团队考核。口径延展上，可按核心功能分别统计首次使用时长，发现"哪个功能最容易成为第一个Aha"；按版本/行业分层看激活差异，为实施SOP分层（旗舰版驻场、标准版自助）提供依据。联动动作上，激活超期的自动触发实施救援工单、CSM提前介入；把激活数据反馈给产品团队优化新手引导（Onboarding Checklist），形成"实施-产品-客户成功"三方的共同指标。

## SAAS-25 KA与SMB客户群多指标对比

### 1. 业务背景

SaaS公司通常同时服务KA（大客户，销售驱动、定制化交付）和SMB（中小客户，市场驱动、自助化服务）两个客群，商业模式完全不同。季度战略会上，商业分析师要给管理层一张"客群对比表"：两个客群的客户数、MRR贡献占比、户均MRR、流失率、月均活跃天数。结论用于回答"资源往哪边投"——KA户均产出高但交付重、流失一单伤筋动骨；SMB量大但流失率高，靠自助化压成本。如果数据显示KA贡献80%收入但活跃度反而低于SMB，就是强烈的预警信号（大客户买了不用）。**【面试高频】** "分组对比+行转列"是条件聚合的综合应用题，考察能否用一条SQL产出汇报级宽表。

### 2. 表结构说明

表 `accounts`（客户主表）：`account_id INT`、`account_name VARCHAR(100)`、`segment VARCHAR(10)`（KA/SMB）、`seats INT`（购买席位数）。

表 `contract_current`（客户当前合同状态快照）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID |
| mrr | DECIMAL(12,2) | 当前MRR |
| status | VARCHAR(20) | 在续/已流失 |
| start_date | DATE | 合同生效日 |

表 `usage_daily`（客户日活跃）：`account_id INT`、`active_date DATE`。

示例数据（accounts）：

| account_id | account_name | segment | seats |
|-----------|--------------|---------|-------|
| 9001 | 华信集团 | KA | 500 |
| 9002 | 迅捷物流 | SMB | 15 |
| 9003 | 恒安保险 | KA | 300 |
| 9004 | 麦芽设计 | SMB | 8 |
| 9005 | 天润零售 | SMB | 20 |

示例数据（contract_current）：

| account_id | mrr | status | start_date |
|-----------|------|--------|------------|
| 9001 | 80000.00 | 在续 | 2023-05-01 |
| 9002 | 2400.00 | 在续 | 2024-11-01 |
| 9003 | 52000.00 | 在续 | 2024-02-01 |
| 9004 | 1600.00 | 已流失 | 2024-08-01 |
| 9005 | 3000.00 | 在续 | 2025-01-15 |

### 3. 解题思路

先定指标口径：客户数按segment计数；MRR贡献占比 = 该客群MRR合计/总MRR；户均MRR = 客群MRR合计/客群客户数；流失率 = 该客群status='已流失'客户数/客群客户数；月活跃天数 = 近30天COUNT DISTINCT active_date的户均值。实现路径：解法一用条件聚合（SUM/AVG CASE WHEN segment='KA'）把两个客群横向铺开成一行宽表，一条SQL直达汇报格式；解法二先GROUP BY segment输出纵向长表，再用UNION ALL把每行指标转成"指标名|KA值|SMB值"的透视格式，更易扩展多客群。**【避坑指南】** 三个坑：一是AVG(CASE WHEN...)里不满足条件返回NULL，AVG自动忽略NULL，恰好得到组内均值，但SUM(CASE WHEN)必须补ELSE 0否则流失率分子分母错位；二是除法分母要NULLIF防除零；三是活跃天数LEFT JOIN不到的客户（当月零活跃）COALESCE补0，否则户均活跃被高估。

### 4. 参考解法

**解法一：条件聚合一行宽表（直接输出汇报格式）**

```sql
SELECT
    COUNT(*) AS all_clients,                                          -- 客户总数
    SUM(a.segment = 'KA') AS ka_cnt,                                  -- KA客户数（布尔求和）
    SUM(a.segment = 'SMB') AS smb_cnt,                                -- SMB客户数
    ROUND(SUM(CASE WHEN a.segment = 'KA' THEN c.mrr ELSE 0 END) * 100.0
          / NULLIF(SUM(c.mrr), 0), 1) AS ka_mrr_share_pct,            -- KA的MRR贡献占比
    ROUND(AVG(CASE WHEN a.segment = 'KA' THEN c.mrr END), 0) AS ka_avg_mrr,    -- KA户均MRR（AVG忽略NULL即组内均值）
    ROUND(AVG(CASE WHEN a.segment = 'SMB' THEN c.mrr END), 0) AS smb_avg_mrr,  -- SMB户均MRR
    ROUND(SUM(a.segment = 'KA'   AND c.status = '已流失') * 100.0
          / NULLIF(SUM(a.segment = 'KA'), 0), 1) AS ka_churn_pct,     -- KA流失率
    ROUND(SUM(a.segment = 'SMB'  AND c.status = '已流失') * 100.0
          / NULLIF(SUM(a.segment = 'SMB'), 0), 1) AS smb_churn_pct,   -- SMB流失率
    ROUND(AVG(CASE WHEN a.segment = 'KA' THEN COALESCE(u.act_days, 0) END), 1) AS ka_avg_active_days,   -- KA月均活跃天数
    ROUND(AVG(CASE WHEN a.segment = 'SMB' THEN COALESCE(u.act_days, 0) END), 1) AS smb_avg_active_days   -- SMB月均活跃天数
FROM accounts a
JOIN contract_current c ON c.account_id = a.account_id             -- 客户→当前合同状态
LEFT JOIN (
    SELECT account_id, COUNT(DISTINCT active_date) AS act_days     -- 近30天活跃天数
    FROM usage_daily
    WHERE active_date >= DATE '2025-09-01'
      AND active_date <  DATE '2025-10-01'
    GROUP BY account_id
) u ON u.account_id = a.account_id;                                -- LEFT JOIN：零活跃客户保留
```

结果解读：一行看完两客群画像；重点看"MRR占比 vs 客户数占比"的错位程度（收入集中度）和"流失率×户均MRR"的期望损失对比。

**解法二：GROUP BY长表 + UNION ALL透视（客群可扩展）**

```sql
WITH by_seg AS (                              -- 先按客群聚合成纵向长表
    SELECT
        a.segment,                            -- 客群
        COUNT(*) AS clients,                  -- 客户数
        SUM(c.mrr) AS mrr_total,              -- MRR合计
        ROUND(AVG(c.mrr), 0) AS avg_mrr,      -- 户均MRR
        ROUND(SUM(c.status = '已流失') * 100.0 / COUNT(*), 1) AS churn_pct,   -- 流失率
        ROUND(AVG(COALESCE(u.act_days, 0)), 1) AS avg_active_days            -- 户均月活跃天数
    FROM accounts a
    JOIN contract_current c ON c.account_id = a.account_id
    LEFT JOIN (
        SELECT account_id, COUNT(DISTINCT active_date) AS act_days
        FROM usage_daily
        WHERE active_date >= DATE '2025-09-01' AND active_date < DATE '2025-10-01'
        GROUP BY account_id
    ) u ON u.account_id = a.account_id
    GROUP BY a.segment
)
SELECT '客户数' AS metric,                            -- 指标名
       MAX(CASE WHEN segment = 'KA' THEN clients END) AS ka_value,      -- KA列
       MAX(CASE WHEN segment = 'SMB' THEN clients END) AS smb_value     -- SMB列
FROM by_seg
UNION ALL
SELECT 'MRR合计',                                     -- 逐行转置
       MAX(CASE WHEN segment = 'KA' THEN mrr_total END),
       MAX(CASE WHEN segment = 'SMB' THEN mrr_total END)
FROM by_seg
UNION ALL
SELECT '户均MRR',
       MAX(CASE WHEN segment = 'KA' THEN avg_mrr END),
       MAX(CASE WHEN segment = 'SMB' THEN avg_mrr END)
FROM by_seg
UNION ALL
SELECT '流失率%',
       MAX(CASE WHEN segment = 'KA' THEN churn_pct END),
       MAX(CASE WHEN segment = 'SMB' THEN churn_pct END)
FROM by_seg
UNION ALL
SELECT '月均活跃天数',
       MAX(CASE WHEN segment = 'KA' THEN avg_active_days END),
       MAX(CASE WHEN segment = 'SMB' THEN avg_active_days END)
FROM by_seg;
```

结果解读：指标名做行、客群做列，新增第三客群（如中型市场）时只需在by_seg里多一个取值，UNION段不用动；对比解法一，这种写法在指标多、客群多的场景更易维护。

### 5. 性能分析与优化

两种解法主体相同：一次三表JOIN加GROUP BY，代价集中在usage_daily的时间范围聚合；UNION ALL透视只是对几行的轻量重组，可忽略。优化建议：`usage_daily` 建 `(active_date, account_id)` 复合索引或按月分区，让30天窗口走范围扫描；`contract_current` 以account_id为主键即可点查；若对比是固定月报，把客户级活跃天数物化成 `account_month_active` 后，主查询退化为两表JOIN；客群维度若由多字段组合（segment×行业×版本），推荐解法二的"先长后转"结构，避免条件聚合里出现指数级的CASE组合；注意JOIN顺序，先用contract_current过滤掉已流失（如只看在续）再做活跃JOIN可减小中间结果。

### 6. 面试延伸考点

- **KA和SMB的流失率能直接比较吗？** 回答要点：不能只看数值，SMB基数大波动大、KA一单流失影响巨大，应同时看流失率与流失金额占比；统计上还要注意小样本区间的置信度。
- **如果想看两个客群的续约率差异，表结构要怎么调整？** 回答要点：把contract_current换成合同全量表，按SAAS-22的续约判定逻辑先算客户级续约标记，再按segment聚合。
- **MRR贡献占比用什么做分母？** 回答要点：全量在续客户MRR合计；若要剔除已流失客户需声明口径，否则流失客户金额拉低总盘会虚增KA占比。
- **活跃天数之外还有什么客群对比维度？** 回答要点：席位活跃率、功能广度、工单量/百席位、NPS、交付周期，形成客群画像雷达图而非单指标比较。

### 7. 业务拓展思考

客群对比结论直接牵动组织与定价：KA贡献集中但服务成本高，要评估CSM人效与定制交付的边际收益；SMB流失率高则要推动自助化（在线开通、信用卡扣款、自动化续约）摊薄服务成本。口径延展上，可引入"户均收入/服务成本"看两客群的真实毛利结构，而非只看收入；按客群分别设定健康分权重与预警阈值。联动动作上，SMB中的高活跃头部客户可识别为"KA潜力池"交给销售跟进升级；KA中的低活跃客户则进入客户成功重点干预，两条腿走路改善客群结构。
## SAAS-26 增购扩容订单分析

### 1. 业务背景

SaaS收入增长有两条腿：拉新签和存量增购（Upsell）。增购指老客户在合同期内追加席位、升级版本或购买新模块，是NDR超过100%的主要来源，且获客成本几乎为零。销售运营总监每月要分析增购订单的三个问题：月度增购金额及占总订单金额的比例（存量经营健康度）、客户从新签到首次增购的平均间隔（客户价值兑现周期）、以及"连续增购"客户占比（有多少客户买了又买，是扩张型客户的标志）。这个结论决定客户成功与销售的配合机制——增购商机由CSM挖出来交给AE跟进，还是CSM直接持有。**【面试高频】** "订单类型结构 + 客户级时间间隔"的组合题，考察LAG窗口与条件聚合的配合。

### 2. 表结构说明

表 `orders`（订单表，含新签、增购、续约三类）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | INT | 订单ID，主键 |
| account_id | INT | 客户ID |
| order_type | VARCHAR(10) | 订单类型（新签/增购/续约） |
| amount | DECIMAL(12,2) | 订单金额（年化） |
| seats | INT | 订单席位数（增购时为新增席位） |
| order_date | DATE | 签单日期 |

示例数据：

| order_id | account_id | order_type | amount | seats | order_date |
|----------|-----------|------------|--------|-------|------------|
| 1 | 9501 | 新签 | 60000.00 | 20 | 2024-06-01 |
| 2 | 9501 | 增购 | 30000.00 | 10 | 2024-11-15 |
| 3 | 9501 | 增购 | 15000.00 | 5 | 2025-03-20 |
| 4 | 9502 | 新签 | 45000.00 | 15 | 2024-09-10 |
| 5 | 9502 | 续约 | 49500.00 | 15 | 2025-09-09 |

（解释：9501一年内两次增购，属于典型扩张型客户；9502只按期续约，是稳定但未扩张客户。）

### 3. 解题思路

先定口径：月度趋势层看增购订单数、增购金额、增购金额占总订单金额的比例；客户间隔层定义"首次增购间隔"= 该客户第一笔增购日期 - 第一笔新签日期（只统计有新签历史的客户）；"连续增购"用LAG看上一笔订单类型，上一笔也是增购即复购扩张。实现路径：解法一用条件聚合出月度趋势（LAG套在SUM聚合上算环比），再用客户级条件聚合算首次增购间隔；解法二用 `LAG() OVER (PARTITION BY account_id ORDER BY order_date)` 给每笔订单标记"上一笔是什么、隔了多久"，一次扫描区分首笔增购与连续增购。**【避坑指南】** 三个坑：一是增购占比的分母是"全部订单金额（含续约）"还是"新签+增购"必须声明口径，含续约会稀释比例；二是窗口LAG在PARTITION BY account_id内排序后，同日多单要加order_id做tiebreak，否则顺序不稳定；三是"首次增购间隔"必须排除从未新签的客户（如并购承接的客户直接产生增购单），否则NULL参与AVG被忽略反而造成样本口径不明。

### 4. 参考解法

**解法一：条件聚合出月度趋势 + 客户级首购间隔**

```sql
-- 第一部分：月度增购趋势
SELECT
    DATE_FORMAT(order_date, '%Y-%m') AS ym,                          -- 月份
    COUNT(*) AS total_orders,                                        -- 全部订单数
    SUM(order_type = '增购') AS upsell_cnt,                           -- 增购订单数
    SUM(CASE WHEN order_type = '增购' THEN amount ELSE 0 END) AS upsell_amount,   -- 增购金额
    ROUND(SUM(CASE WHEN order_type = '增购' THEN amount ELSE 0 END) * 100.0
          / NULLIF(SUM(amount), 0), 1) AS upsell_amount_pct,         -- 增购金额占比（分母=全部订单，口径需声明）
    SUM(CASE WHEN order_type = '增购' THEN seats ELSE 0 END) AS upsell_seats,     -- 增购席位数（扩张的量纲证据）
    SUM(CASE WHEN order_type = '增购' THEN amount ELSE 0 END)
      - LAG(SUM(CASE WHEN order_type = '增购' THEN amount ELSE 0 END))
        OVER (ORDER BY DATE_FORMAT(order_date, '%Y-%m')) AS upsell_mom_diff          -- 增购金额环比差（窗口套聚合，MySQL 8.0支持）
FROM orders
GROUP BY ym
ORDER BY ym;
```

```sql
-- 第二部分：客户从新签到首次增购的间隔
WITH firsts AS (                                 -- 每个客户的两个"第一次"
    SELECT
        account_id,                              -- 客户ID
        MIN(CASE WHEN order_type = '新签' THEN order_date END) AS first_sign,     -- 首次新签日
        MIN(CASE WHEN order_type = '增购' THEN order_date END) AS first_upsell    -- 首次增购日
    FROM orders
    GROUP BY account_id
)
SELECT
    COUNT(*) AS signed_clients,                              -- 有新签历史的客户数
    SUM(first_upsell IS NOT NULL) AS upsell_clients,         -- 其中发生过增购的客户数
    ROUND(SUM(first_upsell IS NOT NULL) * 100.0 / COUNT(*), 1) AS upsell_client_pct,   -- 增购客户渗透率
    ROUND(AVG(DATEDIFF(first_upsell, first_sign)), 1) AS avg_days_to_upsell,   -- 平均首购间隔（未增购客户NULL被AVG忽略）
    MAX(DATEDIFF(first_upsell, first_sign)) AS max_days_to_upsell              -- 最长间隔，用于识别"突然想起来的"客户
FROM firsts
WHERE first_sign IS NOT NULL;                    -- 只统计有新签历史的客户，口径干净
```

结果解读：增购金额占比逐月上升说明存量经营策略奏效；首购间隔的均值配合分布（可用分位数细化）帮助CSM判断"新签后第几个月是增购黄金窗口"。

**解法二：LAG窗口识别首笔增购与连续增购**

```sql
WITH seq AS (                                    -- 每笔订单带上"上一笔"信息
    SELECT
        account_id,                              -- 客户ID
        order_type,                              -- 本笔订单类型
        amount,                                  -- 本笔金额
        order_date,                              -- 本笔日期
        LAG(order_type) OVER (                   -- 上一笔订单类型
            PARTITION BY account_id
            ORDER BY order_date, order_id        -- 按日期排序，order_id防同日并列
        ) AS prev_type,
        LAG(order_date) OVER (
            PARTITION BY account_id
            ORDER BY order_date, order_id
        ) AS prev_date                           -- 上一笔订单日期
    FROM orders
)
SELECT
    COUNT(*) AS upsell_cnt,                                  -- 增购订单总数
    SUM(amount) AS upsell_amount,                            -- 增购总金额
    ROUND(AVG(DATEDIFF(order_date, prev_date)), 1) AS avg_interval_from_prev,   -- 距上一单的平均间隔
    SUM(prev_type = '新签') AS first_upsell_cnt,              -- 新签后首笔增购（首购型扩张）
    SUM(prev_type = '增购') AS repeat_upsell_cnt,             -- 连续增购（复购型扩张，最强扩张信号）
    ROUND(SUM(prev_type = '增购') * 100.0 / COUNT(*), 1) AS repeat_upsell_pct   -- 连续增购占比
FROM seq
WHERE order_type = '增购';                       -- 只看增购单在订单序列中的上下文
```

结果解读：连续增购占比高说明存在一批"越买越多"的扩张型客户，应作为标杆案例复制其成功路径；间隔均值则提示CSM在合适的时间点主动发起增购沟通。

### 5. 性能分析与优化

解法一两条查询各扫一遍订单表，订单表通常是三张业务表中最小的（相对日志表），代价可控；解法二一次扫描加窗口排序，O(N log N)。优化建议：给 `orders` 建 `(account_id, order_date, order_id)` 复合索引支撑窗口排序，另建 `(order_type, order_date)` 支撑按类型的趋势过滤；若订单量到达百万级且分析维度多，建议ETL出 `account_order_seq`（客户订单序列+上一单信息）宽表；月度趋势查询注意GROUP BY ym后ORDER BY ym使用索引输出；窗口套聚合（LAG(SUM(...))）在MySQL 8.0合法但可读性差，面试中建议先在CTE里聚合、外层再开窗口，两层结构更清晰也不易出错。

### 6. 面试延伸考点

- **增购金额占比的分母应该是什么？** 回答要点：三种口径（占总订单、占新签+增购、占期初MRR）回答不同问题——存量经营健康度、拉新与挖潜的平衡、NDR构成，汇报必须注明，面试主动区分是加分项。
- **增购和续约涨价怎么区分？** 回答要点：续约合同金额上涨属于价格/条款变动，应记入续约扩张而非增购订单；SQL上用订单类型字段严格区分，若CRM录入不规范要做数据清洗规则。
- **如何预测下季度增购金额？** 回答要点：用历史首购间隔分布×新签客户队列（cohort）滚动预估，叠加健康分调节系数；SQL负责出cohort级历史转化，预测建模在分析层完成。
- **席位数和金额增购方向不一致说明什么？** 回答要点：可能存在折扣或版本升级（席位少金额多），要交叉检查两列，异常组合指向数据质量问题或特殊商务条款。

### 7. 业务拓展思考

增购分析的核心价值是找到"什么时候、对什么客户、推什么"：首购间隔集中在第4-6个月的客户群，说明第3个月就该启动增购商机培育；连续增购客户的共性（行业、版本、使用特征）反哺ICP（理想客户画像）。口径延展上，可拆分"席位增购/版本升级/新模块"三类增购的产品线归因；按CSM维度统计增购贡献，作为客户成功团队商业化能力的考核依据。联动动作上，把增购商机自动推送CRM并带出使用数据佐证（席位活跃率100%、席位不够用），让CSM的扩张沟通从"卖东西"变成"帮你解决不够用的问题"。

## SAAS-27 NPS分层与客户规模交叉分析

### 1. 业务背景

每季度客户成功团队发起NPS调研，回收后不能只报一个总分的NPS值——管理层真正要知道的是"哪类客户在贬损我们"。把客户按席位规模分成SMB（<20席）、中型（20-100席）、KA（>100席）三档，与NPS三档人群（推荐者9-10分、中立者7-8分、贬损者0-6分）做交叉：如果KA客群的贬损率显著高于SMB，说明服务大客户的交付或支持体系出了问题，要立刻排查；如果SMB全是推荐者但KA贬损，资源投向完全不同。这张交叉表用于决定客户成功的服务分层策略与NPS回访名单（贬损客户72小时内电话回访）。**【加分点】** 能同时输出各桶NPS值（推荐者占比-贬损者占比）并解释NPS是"差值"而非平均分，是基本功扎实的体现。

### 2. 表结构说明

表 `nps_survey`（NPS调研回收表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| survey_id | INT | 调研回收ID，主键 |
| account_id | INT | 客户ID |
| score | TINYINT | NPS评分0-10 |
| survey_month | VARCHAR(7) | 调研月份（如2025-09） |
| comment | VARCHAR(500) | 开放评论文本 |

表 `accounts`（客户主表）：`account_id INT`、`account_name VARCHAR(100)`、`seats INT`。

示例数据（nps_survey）：

| survey_id | account_id | score | survey_month | comment |
|-----------|-----------|-------|--------------|---------|
| 1 | 9601 | 9 | 2025-09 | 报表功能很好用 |
| 2 | 9602 | 6 | 2025-09 | 工单响应太慢 |
| 3 | 9603 | 8 | 2025-09 | 整体满意 |
| 4 | 9604 | 3 | 2025-09 | 系统经常卡顿 |
| 5 | 9605 | 10 | 2025-09 | 客户成功很专业 |

### 3. 解题思路

先定口径：NPS分层用固定阈值（9-10推荐者、7-8中立者、0-6贬损者），客户规模分桶按席位数切三档；每个规模桶内计算三档人群占比及桶级NPS=(推荐者占比-贬损者占比)。注意两点：一个客户多次回收只取最新一次（防重复计数），分母是有效样本数。实现路径：解法一用条件聚合直接输出宽表交叉表（行=规模桶，列=三档占比+NPS值），一步到位；解法二先按"规模×人群"两维GROUP BY出长表，再用 `SUM(cnt) OVER (PARTITION BY 规模桶)` 窗口计算桶内占比，结构更通用。**【避坑指南】** 三个坑：一是"去重取最新"若用MAX(survey_month)字符串比较在YYYY-MM格式下成立，但若混入不同格式日期会错，建议用ROW_NUMBER按回收时间排序取第一条；二是NPS是占比差不是评分均值，AVG(score)是常见的口径错误；三是低样本桶（如回收<10份的KA）占比波动大，要给样本量列让读者自行判断置信度。

### 4. 参考解法

**解法一：条件聚合直接输出交叉宽表（推荐汇报格式）**

```sql
WITH latest AS (                              -- 每个客户只保留最近一次回收
    SELECT
        survey_id,                            -- 回收ID
        account_id,                           -- 客户ID
        score,                                -- 评分
        ROW_NUMBER() OVER (                   -- 同一客户多次回收取最新一次
            PARTITION BY account_id
            ORDER BY survey_month DESC, survey_id DESC   -- 月份新者优先，ID做并列tiebreak
        ) AS rn
    FROM nps_survey
    WHERE survey_month = '2025-09'            -- 本季调研
)
SELECT
    CASE WHEN a.seats < 20  THEN 'SMB(<20席)'
         WHEN a.seats <= 100 THEN '中型(20-100席)'
         ELSE 'KA(>100席)' END AS size_bucket,             -- 客户规模分桶
    COUNT(*) AS resp_cnt,                                  -- 有效样本数（供判断置信度）
    ROUND(SUM(n.score >= 9) * 100.0 / COUNT(*), 1) AS promoter_pct,            -- 推荐者占比
    ROUND(SUM(n.score BETWEEN 7 AND 8) * 100.0 / COUNT(*), 1) AS passive_pct,  -- 中立者占比
    ROUND(SUM(n.score <= 6) * 100.0 / COUNT(*), 1) AS detractor_pct,           -- 贬损者占比
    ROUND((SUM(n.score >= 9) - SUM(n.score <= 6)) * 100.0 / COUNT(*), 1) AS nps  -- 桶级NPS = 推荐者占比 - 贬损者占比
FROM latest n
JOIN accounts a ON a.account_id = n.account_id             -- 关联客户主表拿席位数
WHERE n.rn = 1                                             -- 只留最新一次
GROUP BY size_bucket
ORDER BY nps DESC;                                         -- NPS最高的客群排前，快速定位口碑分层
```

结果解读：KA桶NPS显著低于SMB时优先排查KA交付与专属支持链路；贬损者名单（score<=6）直接导出给CSM做72小时回访。

**解法二：两维长表 + SUM OVER组内占比（结构通用）**

```sql
WITH latest AS (                              -- 与解法一相同的去重逻辑
    SELECT account_id, score,
           ROW_NUMBER() OVER (PARTITION BY account_id
                              ORDER BY survey_month DESC, survey_id DESC) AS rn
    FROM nps_survey
    WHERE survey_month = '2025-09'
),
tagged AS (                                   -- 打上两个维度标签
    SELECT
        CASE WHEN a.seats < 20  THEN 'SMB'
             WHEN a.seats <= 100 THEN '中型'
             ELSE 'KA' END AS size_bucket,    -- 规模桶
        CASE WHEN n.score >= 9 THEN '推荐者'
             WHEN n.score >= 7 THEN '中立者'
             ELSE '贬损者' END AS nps_group   -- NPS三档
    FROM latest n
    JOIN accounts a ON a.account_id = n.account_id
    WHERE n.rn = 1
),
cross_tab AS (                                -- 两维交叉计数
    SELECT size_bucket, nps_group, COUNT(*) AS cnt
    FROM tagged
    GROUP BY size_bucket, nps_group
)
SELECT
    size_bucket,                              -- 规模桶（行）
    nps_group,                                -- NPS分层（行）
    cnt,                                      -- 样本数
    ROUND(cnt * 100.0 / SUM(cnt) OVER (PARTITION BY size_bucket), 1) AS pct_within_bucket  -- 桶内占比（窗口求组内分母）
FROM cross_tab
ORDER BY FIELD(size_bucket, 'SMB', '中型', 'KA'),
         FIELD(nps_group, '推荐者', '中立者', '贬损者');   -- 按业务顺序输出
```

结果解读：3×3九宫格每个格子一个占比，是交互式BI看板最易接入的结构；桶级NPS可在该结果上再包一层透视（推荐者占比-贬损者占比）获得，两解法口径完全等价。

### 5. 性能分析与优化

两种解法主体都是一次JOIN加GROUP BY，回收表量级通常在万级，性能压力很小；ROW_NUMBER去重是最贵的部分，走 `(account_id, survey_month)` 索引可避免filesort。优化建议：给 `nps_survey` 建复合索引 `(account_id, survey_month DESC, survey_id DESC)`（MySQL 8.0支持降序索引）；规模分桶阈值若会调整（如把中型上界从100改为200），建议把阈值放配置维表 `segment_dim`，SQL用JOIN分桶而不是硬编码CASE；若要做"连续多季NPS趋势"，把survey_month放进GROUP BY并配合窗口环比，一次扫描出多季数据；评论文本字段不在本查询SELECT中列出，避免大字段拖慢传输。

### 6. 面试延伸考点

- **NPS是平均值吗？怎么用SQL算？** 回答要点：不是，NPS=推荐者占比-贬损者占比，取值-100~100；用条件聚合两个SUM相减，常见错误是AVG(score)再线性映射。
- **回收率偏低会怎么扭曲结论？** 回答要点：愤怒或极度满意的客户更愿意响应，样本自选择偏差可能高估两端占比；应报告回收率，必要时对比响应者与全量客户的流失率差异。
- **贬损者回访的优先级怎么排？** 回答要点：不只按分数，按"贬损×客户规模×续约临近度"排序，KA+贬损+90天内到期是最高优先级，SQL可三元排序输出。
- **中立者为什么重要？** 回答要点：中立者是转化推荐者或滑向贬损的摇摆人群，量最大且最容易被忽视，运营上用产品改进公告与成功案例激活。

### 7. 业务拓展思考

NPS交叉表的价值在于把"口碑"翻译成"服务资源配置"：KA贬损率高时优先补交付与支持SLA，SMB贬损集中时优化自助帮助与产品稳定性。口径延展上，可把NPS与健康分、续约结果做三表关联，验证"NPS对续约的预测力"（通常贬损者的续约率显著更低），让NPS从满意度装饰变成流失预警输入；评论开放文本可结合关键词统计（分词后TOP词频）定位具体痛点。联动动作上，贬损者名单进入CSM回访SLA、推荐者名单进入转介绍与案例邀请流程，让调研形成闭环而不是一发问卷了之。

## SAAS-28 客户月度使用天数分布

### 1. 业务背景

产品运营在月度产品复盘上要回答"客户到底用得多勤"：不是看总调用次数（容易被几个自动化脚本刷高），而是看"每个客户当月有多少天至少用了一次产品"的分布。分布形态直接决定运营策略：如果大量客户集中在1-4天的低频桶，说明客户是"每周看一眼报表"的浅使用，粘性弱、续约靠惯性；如果高频桶（20天以上）占比高，说明产品已进入工作流，是涨价和增购的底气。运营还要看分布逐月移动方向——整体从低频桶向高频桶迁移是最健康的信号。这个结论用于设定活跃分层运营策略与续约预警。**【面试高频】** COUNT DISTINCT + 分桶分布是"先聚合再分桶"的两层聚合题，考察对聚合顺序的理解。

### 2. 表结构说明

表 `usage_log`（客户使用日志，已按客户×日×功能去重汇总）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| id | BIGINT | 日志ID，主键 |
| account_id | INT | 客户ID |
| event_date | DATE | 使用日期 |
| feature_name | VARCHAR(50) | 使用的功能 |

示例数据：

| id | account_id | event_date | feature_name |
|----|-----------|------------|--------------|
| 1 | 9701 | 2025-09-01 | 报表中心 |
| 2 | 9701 | 2025-09-01 | 移动端审批 |
| 3 | 9701 | 2025-09-03 | 报表中心 |
| 4 | 9702 | 2025-09-02 | 自动化流程 |
| 5 | 9702 | 2025-09-02 | API集成 |

（解释：9701在9月1日用了两个功能，但活跃天数只算1天——同日多行为必须去重，这正是本题的口径要点。）

### 3. 解题思路

先定口径：客户月活跃天数 = 当月 DISTINCT event_date 的数量（同一客户同一天无论用多少功能只算1天）；分桶为固定业务阈值：低频1-4天、中频5-11天、高频12-19天、极高频20天以上。关键结构：先按客户聚合出天数（第一层GROUP BY），再对天数分桶统计客户数与占比（第二层GROUP BY）——聚合顺序不能颠倒，直接对原始日志分桶会数成"日志数"而不是"客户数"。实现路径：解法一两层CTE+CASE分桶，占比用 `COUNT(*) / SUM(COUNT(*)) OVER ()` 窗口求；解法二把分桶阈值落成维表 `bucket_dim` 用区间JOIN，阈值可配置、复用性强。**【避坑指南】** 两个坑：一是忘记DISTINCT date，同日多功能客户被多算天数，低频客户被系统性推高；二是分桶边界要互斥且完备（1-4、5-11、12-19、20+无缝覆盖1到31），写 BETWEEN 加 OR 时容易漏边界，推荐维表区间JOIN从结构上消灭这个风险。

### 4. 参考解法

**解法一：两层CTE + CASE固定分桶（推荐）**

```sql
WITH days AS (                                -- 第一层：客户粒度的当月活跃天数
    SELECT
        account_id,                           -- 客户ID
        COUNT(DISTINCT event_date) AS active_days   -- 关键：按日期去重，同日多行为只算1天
    FROM usage_log
    WHERE event_date >= DATE '2025-09-01'     -- 统计月起点
      AND event_date <  DATE '2025-10-01'     -- 半开区间，天然覆盖整月
    GROUP BY account_id
),
bucketed AS (                                 -- 第二层：把天数映射到业务分桶
    SELECT
        account_id,                           -- 客户ID
        CASE WHEN active_days <= 4  THEN '低频(1-4天)'
             WHEN active_days <= 11 THEN '中频(5-11天)'
             WHEN active_days <= 19 THEN '高频(12-19天)'
             ELSE '极高频(20天以上)' END AS freq_bucket,   -- 阈值互斥且完备
        active_days                           -- 保留原值，桶内还能看均值
    FROM days
)
SELECT
    freq_bucket,                              -- 分桶
    COUNT(*) AS client_cnt,                   -- 客户数
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS pct,   -- 占比（窗口对分组结果求总分母）
    ROUND(AVG(active_days), 1) AS avg_days    -- 桶内平均天数，展示桶内密度
FROM bucketed
GROUP BY freq_bucket
ORDER BY FIELD(freq_bucket, '低频(1-4天)', '中频(5-11天)', '高频(12-19天)', '极高频(20天以上)');   -- 按频次从低到高
```

结果解读：低频桶占比高说明产品未进入客户日常工作流，续约靠惯性；对比上月分布可看客群迁移方向，是活跃度运营的北极星视图。

**解法二：分桶维表 + 区间JOIN（阈值可配置）**

```sql
WITH days AS (                                -- 同解法一：客户级活跃天数
    SELECT
        account_id,
        COUNT(DISTINCT event_date) AS active_days
    FROM usage_log
    WHERE event_date >= DATE '2025-09-01'
      AND event_date <  DATE '2025-10-01'
    GROUP BY account_id
)
SELECT
    b.bucket_name,                            -- 桶名（来自维表）
    COUNT(d.account_id) AS client_cnt,        -- 落入该桶的客户数（LEFT JOIN保住空桶）
    ROUND(COUNT(d.account_id) * 100.0
          / NULLIF((SELECT COUNT(*) FROM days), 0), 1) AS pct,   -- 占比：分母=全部有日志客户
    b.sort_no                                 -- 维表自带排序号，输出顺序可配置
FROM bucket_dim b                             -- 分桶维表：bucket_name/min_days/max_days/sort_no
LEFT JOIN days d
    ON d.active_days BETWEEN b.min_days AND b.max_days      -- 天数落在桶区间即归入，边界由维表统一管理
GROUP BY b.bucket_name, b.sort_no
ORDER BY b.sort_no;
```

结果解读：维表法把分桶规则从SQL里解耦——运营想改成"5天一档"只改维表数据，不动代码；LEFT JOIN维表还能让空桶也出现在结果里，避免分布图缺柱。

### 5. 性能分析与优化

两种解法的第一层聚合相同，代价在日志表的 DISTINCT 去重与GROUP BY；解法二的区间JOIN规模极小（4行维表），哈希连接开销可忽略。优化建议：给 `usage_log` 建 `(event_date, account_id)` 复合索引（或按月分区），让整月过滤走范围扫描；日志量大时ETL预聚合出 `account_month_active_days`（客户×月×活跃天数），本查询退化为对聚合表的轻量分桶；注意索引顺序——若常按月查整月，event_date放前列；若常按客户查个人轨迹，account_id放前列，两张索引按查询模式取舍。占比计算用 `SUM(COUNT(*)) OVER ()` 避免再扫一遍，标量子查询分母在MySQL 8.0也只执行一次，两种写法均可。

### 6. 面试延伸考点

- **为什么看活跃天数而不是活跃次数？** 回答要点：次数易被自动化调用和重复刷新灌水，天数更接近"使用习惯"的度量；两者配合可区分"人工高频"与"脚本高频"。
- **分桶边界怎么定才合理？** 回答要点：参考工作日月均22天、周活跃5天的业务节律，让桶对应"每月一次/每周一次/每天使用"的业务语义，而不是机械等宽切分。
- **月活跃天数和DAU/MAU有什么关系？** 回答要点：DAU/MAU是产品整体粘性比，客户月活跃天数分布是B端客户粒度的粘性分布，后者能定位"哪些客户粘性差"，更适合SaaS运营。
- **如何处理月中新开通客户？** 回答要点：月中开通的天数天然偏低，要么按"开通后可用天数"归一化（活跃天数/可用天数），要么把首月客户单独成桶，避免拉低整体分布。

### 7. 业务拓展思考

天数分布是活跃分层运营的底座：低频桶客户触发"激活旅程"（功能引导邮件、使用技巧推送），高频桶客户进入"深度经营"（增购、标杆案例邀约）。口径延展上，可区分"工作日活跃"与"周末活跃"识别使用场景（办公刚需 vs 临时查看）、按核心功能分别算天数分布定位"为哪个功能而来"；跨月视角可做活跃天数迁移矩阵（本月低频→下月高频的比例），量化运营动作的真实拉动。联动动作上，把分布结果同步给CSM作为健康分活跃项的原始依据，并把连续两月滑入低频桶的客户自动生成续约预警工单。

## SAAS-29 销售代表业绩与转化排名

### 1. 业务背景

季度末销售运营要做销售排行榜，但只按签单金额排名会冤枉好人：有的销售金额高是因为分到了大区好线索，有的销售赢率高但单子小。一张合格的业绩排名表要并列多个维度：成单金额（产出）、成单数与赢率（效率）、平均成单周期（节奏），并给出三种排名——金额RANK（允许并列跳号）、赢率DENSE_RANK（并列不跳号）、金额四分位NTILE（把团队分成头部/中上/中下/尾部四档便于差异化管理）。管理层用它决定：谁是标杆复制经验、谁进入绩效辅导、配额下季度怎么调。**【面试高频】** 三个排名窗口函数的语义差异（并列怎么处理）是本题的必考点。

### 2. 表结构说明

表 `sales_reps`（销售代表表）：`rep_id INT`、`rep_name VARCHAR(50)`、`region VARCHAR(30)`（所属大区）、`hire_date DATE`。

表 `opportunities`（商机表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| opportunity_id | INT | 商机ID，主键 |
| owner_id | INT | 归属销售ID |
| amount | DECIMAL(12,2) | 商机金额 |
| stage | VARCHAR(10) | 状态（成单/输单/进行中） |
| created_date | DATE | 商机创建日 |
| close_date | DATE | 结单日期（进行中为NULL） |

示例数据（opportunities）：

| opportunity_id | owner_id | amount | stage | created_date | close_date |
|----------------|----------|--------|-------|--------------|------------|
| 1 | 101 | 120000.00 | 成单 | 2025-01-10 | 2025-03-15 |
| 2 | 101 | 30000.00 | 输单 | 2025-02-01 | 2025-03-01 |
| 3 | 102 | 80000.00 | 成单 | 2025-01-20 | 2025-02-28 |
| 4 | 103 | 60000.00 | 成单 | 2025-02-05 | 2025-04-10 |
| 5 | 103 | 90000.00 | 进行中 | 2025-03-01 | NULL |

### 3. 解题思路

先定口径：只统计考察期内已结单的商机（输单+成单）计算赢率，进行中商机不计入赢率分母但要单独列"在途金额"；成单周期 = close_date - created_date，只对成单商机求均值。实现路径：解法一先按销售聚合（CTE），再在外层开三个排名窗口（RANK/DENSE_RANK/NTILE）输出；解法二演示"窗口聚合替代GROUP BY"技巧——在明细行上用 `SUM(...) OVER (PARTITION BY rep_id)` 直接算聚合值再DISTINCT，适合还要保留明细的混合查询。**【避坑指南】** 三个坑：一是赢率分母必须剔除"进行中"，否则进度慢的销售赢率被稀释；二是无商机的新人LEFT JOIN后amount为NULL，SUM(CASE)会返回NULL，要COALESCE补0；三是RANK与DENSE_RANK的差别必须能口述——并列第2时RANK下一位是3、DENSE_RANK下一位是2，排行榜用哪个要和业务确认。

### 4. 参考解法

**解法一：CTE聚合 + 三窗口排名（标准做法）**

```sql
WITH perf AS (                                -- 第一步：销售粒度业绩聚合
    SELECT
        r.rep_id,                             -- 销售ID
        r.rep_name,                           -- 姓名
        r.region,                             -- 大区
        COUNT(o.opportunity_id) AS total_closed,                    -- 已结单商机数（含输单）
        SUM(o.stage = '成单') AS won_cnt,                            -- 成单数
        COALESCE(SUM(CASE WHEN o.stage = '成单' THEN o.amount END), 0) AS won_amount,  -- 成单金额（新人补0）
        ROUND(SUM(o.stage = '成单') * 100.0
              / NULLIF(COUNT(o.opportunity_id), 0), 1) AS win_rate_pct,   -- 赢率：分母=已结单，进行中不进入
        ROUND(AVG(CASE WHEN o.stage = '成单'
                       THEN DATEDIFF(o.close_date, o.created_date) END), 1) AS avg_cycle_days,  -- 平均成单周期
        COALESCE(SUM(CASE WHEN o.stage = '进行中' THEN o.amount END), 0) AS pipeline_amount  -- 在途金额（未来弹药）
    FROM sales_reps r
    LEFT JOIN opportunities o
        ON o.owner_id = r.rep_id              -- 左连接：零商机销售也出现在榜上
       AND o.stage IN ('成单', '输单', '进行中')
    GROUP BY r.rep_id, r.rep_name, r.region
)
SELECT
    *,                                        -- 聚合指标全保留
    RANK() OVER (ORDER BY won_amount DESC) AS amount_rank,        -- 金额排名：并列跳号（2,2,4）
    DENSE_RANK() OVER (ORDER BY win_rate_pct DESC) AS winrate_rank,  -- 赢率排名：并列不跳号（2,2,3）
    NTILE(4) OVER (ORDER BY won_amount DESC) AS amount_quartile,  -- 金额四分位：1=尾部…4=头部（按窗口内行数均分）
    RANK() OVER (PARTITION BY region ORDER BY won_amount DESC) AS region_rank      -- 大区内排名，供区域经理使用
FROM perf
ORDER BY amount_rank;                         -- 按总金额排名输出
```

结果解读：金额榜与赢率榜交叉看——金额高但赢率低的销售靠大单硬扛、效率有隐患；头部四分位（amount_quartile=4）进入标杆经验萃取，尾部进入辅导计划。

**解法二：窗口聚合替代GROUP BY（明细与汇总混合查询）**

```sql
SELECT DISTINCT                               -- 窗口在明细行上算，DISTINCT收拢到销售粒度
    rep_name,                                 -- 姓名
    region,                                   -- 大区
    won_amount,                               -- 成单金额（窗口聚合值）
    ROUND(won_cnt * 100.0 / NULLIF(total_closed, 0), 1) AS win_rate_pct,   -- 赢率（外层再除，窗口里不便做比率）
    RANK() OVER (ORDER BY won_amount DESC) AS amount_rank    -- 金额排名
FROM (
    SELECT
        r.rep_name,                           -- 姓名
        r.region,                             -- 大区
        SUM(CASE WHEN o.stage = '成单' THEN o.amount ELSE 0 END)
            OVER (PARTITION BY r.rep_id) AS won_amount,      -- 窗口聚合：每行都带同销售合计
        SUM(o.stage = '成单') OVER (PARTITION BY r.rep_id) AS won_cnt,   -- 窗口求成单数
        COUNT(o.opportunity_id) OVER (PARTITION BY r.rep_id) AS total_closed  -- 窗口求结单总数
    FROM sales_reps r
    LEFT JOIN opportunities o ON o.owner_id = r.rep_id       -- 左连接保住无单销售
) t
ORDER BY amount_rank;
```

结果解读：结果与解法一一致；这种写法适合"既要明细行又要汇总列"的场景（比如每笔成单旁标注销售累计业绩），单独排名时不如CTE清晰，面试要能说清两种结构的适用边界。

### 5. 性能分析与优化

解法一一次JOIN加GROUP BY再加窗口排序，窗口都定义在聚合后的少量行上（销售数级别），排序代价可忽略；解法二的窗口聚合在JOIN后的明细行上执行，明细多时窗口PARTITION开销高于GROUP BY，仅推荐用于明细+汇总混合需求。优化建议：给 `opportunities` 建 `(owner_id, stage, close_date)` 复合索引，让按销售的聚合直接走索引分组；考察期过滤（close_date范围）应在JOIN前用派生表先过滤，减小JOIN规模；销售排行榜若按周刷新，可把perf层物化为 `rep_quarter_perf`；RANK窗口的ORDER BY列（won_amount）若能保留在聚合结果的索引/物化中，可避免额外排序；注意LEFT JOIN中把stage过滤写在ON而非WHERE，否则零商机销售被WHERE过滤掉，榜单缺人。

### 6. 面试延伸考点

- **RANK、DENSE_RANK、ROW_NUMBER在并列时的行为差异？** 回答要点：值相同时候选名次分别为并列跳号、并列不跳号、强制唯一；奖金只发给前3名时用ROW_NUMBER会武断打破并列，用RANK可能超过3人，需业务规则补充（如按金额小数位或创建时间tiebreak）。
- **为什么赢率要用已结单做分母？** 回答要点：进行中商机胜负未定，计入分母会让大量在途的销售赢率虚低；分析"预测赢率"时可按历史阶段转化率给在途商机加权。
- **NTILE四分位在行数不能整除时怎么分？** 回答要点：多出的行从第一组开始依次多分一个，组间行数差最多1；NTILE适合粗分层，不要求名次精确。
- **大区之间怎么公平比较？** 回答要点：看大区内排名（本题region_rank）与人均产出而非绝对金额，并控制线索分配质量；可按大区PARTITION再算份额与赢率。

### 7. 业务拓展思考

多维排名的价值是让激励与辅导有的放矢：金额头部+赢率尾部的销售可能是"大单依赖型"，需要拓宽漏斗；赢率高+金额低的适合带新人或接高难度小单。口径延展上，可加入"新签vs续约"拆分——续约单多的销售榜单虚高，要分别排名；加入时间衰减（本月业绩权重高于上月）反映当前状态。联动动作上，四分位结果对接激励方案（头部加速提成、尾部绩效改进计划PPIP），大区排名进入区域经理例会；把排名变化（环比升跌）作为动态视角，识别势头下滑的头部销售及时干预。

## SAAS-30 试用行为与转化率的分组对比

### 1. 业务背景

增长团队在优化试用（Trial）体验时需要一个关键证据：试用初期的哪些行为与最终付费转化强相关？比如"注册后前3天完成'创建项目/邀请成员/连接数据源'等关键行为的客户，转化率是否显著更高？"如果验证成立，Product-Led Growth（PLG）策略就应把资源压在引导新试用客户尽快完成这些动作（Onboarding Checklist），而不是泛泛地群发提醒邮件。分析师需要按"前3天关键行为次数"分桶（0次/1-2次/3-5次/6次以上），输出每桶的试用数、转化数、转化率及与大盘的差值，形成行为-转化对照表。**【加分点】** 能主动声明"相关不等于因果"（高频行为可能是高意愿的结果），并提出用AB实验验证引导动作的真实增量，是从SQL执行者到增长分析师的思维方式跃迁。

### 2. 表结构说明

表 `trial_accounts`（试用客户表）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | INT | 客户ID，主键 |
| channel | VARCHAR(50) | 获客渠道 |
| trial_start | DATE | 试用开始日 |
| trial_end | DATE | 试用结束日 |
| converted | TINYINT | 是否转化付费（1=是，0=否） |

表 `trial_events`（试用行为日志）：`account_id INT`、`event_date DATE`、`event_type VARCHAR(30)`（创建项目/邀请成员/连接数据源/浏览帮助文档/...）。

示例数据（trial_accounts）：

| account_id | channel | trial_start | trial_end | converted |
|-----------|---------|-------------|-----------|-----------|
| 9801 | 官网SEO | 2025-09-01 | 2025-09-14 | 1 |
| 9802 | 信息流广告 | 2025-09-02 | 2025-09-16 | 0 |
| 9803 | 渠道分销 | 2025-09-03 | 2025-09-17 | 1 |
| 9804 | 官网SEO | 2025-09-04 | 2025-09-18 | 0 |
| 9805 | 渠道分销 | 2025-09-05 | 2025-09-19 | 1 |

### 3. 解题思路

先定口径：行为窗口 = 试用开始日的前3个自然日（trial_start <= event_date < trial_start+3天）；关键行为白名单 = ('创建项目','邀请成员','连接数据源')，由增长团队定义（浏览文档属于浅行为，不计入）；分桶 = 0次/1-2次/3-5次/6次以上；每桶输出试用数、转化数、转化率、与大盘转化率的差值。实现路径：解法一LEFT JOIN行为日志（窗口与白名单条件全放ON）后按客户聚合行为数，CASE分桶再条件聚合出转化率，大盘转化率用独立标量子查询；解法二用窗口 `SUM(...) OVER (PARTITION BY account_id)` 在明细行上累计行为数，DISTINCT收拢到客户粒度再分桶，展示窗口聚合思路并顺带踩一遍"明细转客户粒度必须去重"的坑。**【避坑指南】** 三个坑：一是行为JOIN会把一条试用复制成N行，SUM(converted)会被重复计入，必须先收拢到客户粒度或对converted用MAX；二是与大盘差值若用 `AVG(converted) OVER ()` 会得到"各组转化率的均值"而不是整体转化率（分组后的窗口是对组行求均值），要用独立子查询算加权大盘；三是LEFT JOIN行为条件写进WHERE会把零行为试用滤掉。

### 4. 参考解法

**解法一：JOIN聚合行为数 + CASE分桶 + 条件聚合（推荐）**

```sql
WITH early_act AS (                           -- 试用粒度：前3天关键行为计数
    SELECT
        t.account_id,                         -- 客户ID
        t.converted,                          -- 是否转化
        COUNT(e.event_type) AS key_actions    -- 前3天关键行为次数（JOIN不上为0）
    FROM trial_accounts t
    LEFT JOIN trial_events e
        ON e.account_id = t.account_id        -- 同一试用客户
       AND e.event_date >= t.trial_start      -- 行为不早于试用开始（防历史数据混入）
       AND e.event_date <  t.trial_start + INTERVAL 3 DAY   -- 只取前3天窗口（半开区间）
       AND e.event_type IN ('创建项目', '邀请成员', '连接数据源')   -- 关键行为白名单，条件全部放ON里
    GROUP BY t.account_id, t.converted
),
bucketed AS (                                 -- 行为数分桶
    SELECT
        converted,                            -- 是否转化
        CASE WHEN key_actions = 0 THEN '0次'
             WHEN key_actions <= 2 THEN '1-2次'
             WHEN key_actions <= 5 THEN '3-5次'
             ELSE '6次及以上' END AS action_bucket         -- 行为量分桶
    FROM early_act
)
SELECT
    action_bucket,                            -- 行为分桶
    COUNT(*) AS trial_cnt,                    -- 试用客户数
    SUM(converted) AS converted_cnt,          -- 转化数
    ROUND(AVG(converted) * 100, 1) AS cvr_pct,                     -- 桶内转化率
    ROUND((AVG(converted) - (SELECT AVG(converted) FROM trial_accounts)) * 100, 1) AS vs_overall_pct  -- 与大盘差（大盘用独立子查询，加权正确）
FROM bucketed
GROUP BY action_bucket
ORDER BY FIELD(action_bucket, '0次', '1-2次', '3-5次', '6次及以上');   -- 按行为量升序，观察转化率单调性
```

结果解读：若转化率随行为量单调上升（如0次桶5%、1-2次桶18%、6次以上桶45%），即可向增长团队建议把Onboarding Checklist的完成门槛设为3次关键行为，并推入AB实验验证。

**解法二：窗口累计行为数 + DISTINCT收拢（展示另一种结构）**

```sql
WITH joined AS (                              -- 明细级：试用×行为（无行为也保留）
    SELECT
        t.account_id,                         -- 客户ID
        t.converted,                          -- 是否转化
        CASE WHEN e.event_type IS NOT NULL THEN 1 ELSE 0 END AS is_key   -- 单行是否为关键行为
    FROM trial_accounts t
    LEFT JOIN trial_events e
        ON e.account_id = t.account_id
       AND e.event_type IN ('创建项目', '邀请成员', '连接数据源')          -- 白名单过滤
       AND e.event_date <  t.trial_start + INTERVAL 3 DAY                 -- 前3天窗口
),
counted AS (                                  -- 窗口在明细行上累计每客户的行为数
    SELECT
        account_id,                           -- 客户ID
        converted,                            -- 是否转化（每行重复出现）
        SUM(is_key) OVER (PARTITION BY account_id) AS key_actions   -- 窗口求该客户总行为数
    FROM joined
),
acct AS (                                     -- 收拢到客户粒度：一行一客户
    SELECT DISTINCT
        account_id,
        converted,
        key_actions                           -- 不去重的话SUM(converted)会被行为行数放大，这是本解法的核心坑
    FROM counted
)
SELECT
    CASE WHEN key_actions = 0 THEN '0次'
         WHEN key_actions <= 2 THEN '1-2次'
         WHEN key_actions <= 5 THEN '3-5次'
         ELSE '6次及以上' END AS action_bucket,             -- 分桶
    COUNT(*) AS trial_cnt,                    -- 试用数
    SUM(converted) AS converted_cnt,          -- 转化数
    ROUND(AVG(converted) * 100, 1) AS cvr_pct,             -- 桶内转化率
    ROUND((SELECT AVG(converted) * 100 FROM trial_accounts), 1) AS overall_cvr_pct  -- 大盘转化率并列输出便于对照
FROM acct
GROUP BY action_bucket
ORDER BY FIELD(action_bucket, '0次', '1-2次', '3-5次', '6次及以上');
```

结果解读：与解法一完全等价；它演示了"窗口累计+DISTINCT收拢"的结构，代价是中间多了一层明细展开，面试中主动说明"为什么DISTINCT一步不能少"即可转化为加分点。

### 5. 性能分析与优化

解法一的行为计数在JOIN后GROUP BY完成，日志按 (account_id, event_date) 过滤后规模可控；解法二多一层明细展开与窗口PARTITION，行为多的客户中间行数多，总体略逊于解法一。优化建议：给 `trial_events` 建复合索引 `(account_id, event_date, event_type)`，JOIN条件三字段全覆盖；白名单可落成配置维表 `key_event_dim`，增长团队调整关键行为定义时无需改SQL；若试用客户量数十万且常做此类分组，把"前3天行为数"物化为试用宽表字段（ETL在试用结束后回填），查询退化为单表分桶；大盘转化率的子查询对 trial_accounts 全表AVG，可用窗口 `AVG(converted) OVER ()` 的替代写法但注意它算的是"组均值"——正确做法是保留独立子查询，或先算全局SUM/COUNT再JOIN。

### 6. 面试延伸考点

- **转化率随行为量上升，能说明行为导致转化吗？** 回答要点：不能，高意愿客户既更活跃又更可能付费，属于自选择偏差；要下结论需AB实验（随机推送引导）或工具变量/倾向得分匹配，SQL结论只是提出假设。
- **`AVG(converted) OVER ()` 在GROUP BY之后算出的是什么？** 回答要点：是各桶转化率的简单平均（对分组结果行求均值），不是加权大盘转化率；各桶样本量差异大时两者偏差明显，这是窗口函数位置（聚合后执行）的经典陷阱。
- **行为窗口为什么定3天而不是整个试用期？** 回答要点：越早的行为越有引导价值且未受后期运营动作污染；整窗行为与转化关系更强但指导性弱，可两个窗口都跑做敏感性对比。
- **分桶阈值0/1-2/3-5/6+怎么定？** 回答要点：参考行为分布的分位数（P25/P50/P75）保证各桶样本均衡，且桶数足够支持显著性对比；阈值本身可做敏感性分析。

### 7. 业务拓展思考

行为-转化对照表是PLG产品增长循环的起点：把验证有效的关键行为固化进Onboarding Checklist，配自动化触达（未完成第2天发提醒、第3天升级人工触达），并用AB实验持续校准阈值。口径延展上，可按渠道分桶看"哪个渠道的试用客户更愿意行动"、按行为组合（做齐三类行为 vs 只做一种）识别最优行为序列；把分桶结果与试用期时长、版本（免费版/付费试用）交叉，定位体验断点。联动动作上，高行为低转化组指向定价或支付流程问题，低行为组指向激活引导问题——同一张对照表喂给产品、增长、CSM三个团队的不同的行动清单。
