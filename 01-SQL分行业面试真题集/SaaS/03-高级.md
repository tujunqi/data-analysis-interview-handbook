## SAAS-31 净收入留存率（NRR）计算与扩张/收缩/流失分解

### 1. 业务背景

某B端SaaS公司的CFO要在季度董事会汇报净收入留存率（NRR）——这是SaaS估值体系的核心指标，NRR持续大于100%意味着存量客户自身就能驱动增长。RevOps分析师需要在每季度初，基于客户MRR月末快照计算本季度NRR，并拆分出扩张（增购席位/升级档位）、收缩（降级/缩减席位）、流失（整体退订）三类贡献，供管理层判断增长主要靠拉新还是靠存量经营，并决定下季度销售与客户成功（CS）的资源配比。**【面试高频】** NRR的分母必须是期初存量客户，混入期内新签客户是本题型最常见的口径陷阱。

### 2. 表结构说明

表一：mrr_snapshot（客户月度MRR快照表，每月1号落一条快照）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| snapshot_month | DATE | 快照月份（每月1号） |
| mrr | DECIMAL(12,2) | 当月月度经常性收入 |
| plan_name | VARCHAR(50) | 当前定价档位 |

示例数据：

| account_id | snapshot_month | mrr | plan_name |
|------------|----------------|---------|----------|
| A001 | 2024-01-01 | 5000.00 | 专业版 |
| A001 | 2024-04-01 | 8000.00 | 企业版 |
| A002 | 2024-01-01 | 3000.00 | 专业版 |
| A002 | 2024-04-01 | 1500.00 | 基础版 |
| A003 | 2024-01-01 | 2000.00 | 基础版 |

（A003在2024-04-01无记录，代表整体流失；A004为2024-02新签客户，不进本季NRR分母）

表二：mrr_change_log（MRR变动事件流水表，每次增减购/流失记录一条）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| log_id | BIGINT | 流水ID |
| account_id | VARCHAR(32) | 客户账户ID |
| change_date | DATE | 变动生效日期 |
| change_type | VARCHAR(20) | 变动类型：expansion扩张/contraction收缩/churn流失/new新签 |
| delta_mrr | DECIMAL(12,2) | MRR变动额（流失为负值） |

示例数据：

| log_id | account_id | change_date | change_type | delta_mrr |
|--------|------------|-------------|-------------|-----------|
| 9001 | A001 | 2024-02-15 | expansion | +3000.00 |
| 9002 | A002 | 2024-03-01 | contraction | -1500.00 |
| 9003 | A003 | 2024-02-01 | churn | -2000.00 |
| 9004 | A004 | 2024-02-10 | new | +6000.00 |
| 9005 | A001 | 2024-03-20 | expansion | +500.00 |

### 3. 解题思路

第一步先锁口径：NRR =（期初存量客户在期末的MRR合计）÷（期初存量客户MRR合计），分母固定为"2024-01-01快照中出现的客户集合"，期内新签客户（如A004）绝不进入分母。第二步做客户级配对：以1月1日快照为左表，LEFT JOIN 4月1日快照，流失客户（A003）右侧为NULL，用COALESCE补0；再按"期末对比期初"打分类标签：变大记扩张、变小记收缩、变0记流失。第三步按分类聚合MRR变动额与占比，并输出整体NRR。事件法则是反向思路：期初MRR加上季度内所有expansion/contraction/churn流水（剔除new），应精确等于期末MRR，可与快照法互为对账。**【避坑指南】** 若误用INNER JOIN配对，流失客户会被静默剔除，NRR直接虚高约2～5个百分点。

### 4. 参考解法

**解法一：月末快照配对法（LEFT JOIN + 分类聚合）**

```sql
WITH pair AS (                              -- 步骤1：期初与期末快照按客户配对
    SELECT
        s0.account_id,                      -- 以期初快照为基准的客户ID
        s0.mrr  AS mrr_start,               -- 期初MRR，构成NRR分母
        COALESCE(s1.mrr, 0) AS mrr_end      -- 期末MRR；流失客户无记录，补0计入
    FROM mrr_snapshot s0
    LEFT JOIN mrr_snapshot s1               -- LEFT JOIN保证流失客户不被丢掉
        ON  s1.account_id    = s0.account_id
        AND s1.snapshot_month = DATE '2024-04-01'
    WHERE s0.snapshot_month = DATE '2024-01-01'
),
classified AS (                             -- 步骤2：给每个客户打留存分类标签
    SELECT
        account_id, mrr_start, mrr_end,
        CASE
            WHEN mrr_end = 0            THEN 'churned'      -- 期末MRR归零视为整体流失
            WHEN mrr_end > mrr_start    THEN 'expansion'    -- 收入增长记为扩张
            WHEN mrr_end < mrr_start    THEN 'contraction'  -- 收入下降记为收缩
            ELSE 'flat'                                     -- 收入持平
        END AS move_type
    FROM pair
)
SELECT
    move_type,                                          -- 留存分类
    COUNT(*)                      AS acct_cnt,          -- 该类客户数
    SUM(mrr_start)                AS mrr_start_sum,     -- 该类客户期初MRR合计
    SUM(mrr_end - mrr_start)      AS mrr_delta,         -- 该类客户收入变动额
    ROUND(SUM(mrr_end) / SUM(mrr_start) * 100, 2) AS end_over_start_pct  -- 该类期末/期初比
FROM classified
GROUP BY move_type
UNION ALL
SELECT
    'TOTAL_NRR',                                        -- 汇总行：整体NRR
    COUNT(*),
    SUM(mrr_start),
    SUM(mrr_end - mrr_start),
    ROUND(SUM(mrr_end) / SUM(mrr_start) * 100, 2)       -- NRR = 期末合计 ÷ 期初合计
FROM classified;
```

结果解读：若扩张类合计+300万、收缩类-80万、流失类-120万、期初合计1000万，则NRR=110%，扩张掩盖了流失，公司应把CS资源优先投向流失集中的客群。

**解法二：事件流水法（变动日志聚合，可与快照法对账）**

```sql
WITH base AS (                              -- 步骤1：期初MRR总额（NRR分母）
    SELECT SUM(mrr) AS mrr_start
    FROM mrr_snapshot
    WHERE snapshot_month = DATE '2024-01-01'
),
base_accts AS (                             -- 步骤2：期初存量客户名单（限定流水范围）
    SELECT account_id
    FROM mrr_snapshot
    WHERE snapshot_month = DATE '2024-01-01'
),
moves AS (                                  -- 步骤3：季度内存量客户的变动流水分类汇总
    SELECT
        SUM(CASE WHEN change_type = 'expansion'   THEN delta_mrr ELSE 0 END) AS exp_delta,  -- 扩张贡献
        SUM(CASE WHEN change_type = 'contraction' THEN delta_mrr ELSE 0 END) AS con_delta,  -- 收缩拖累
        SUM(CASE WHEN change_type = 'churn'       THEN delta_mrr ELSE 0 END) AS churn_delta -- 流失拖累
    FROM mrr_change_log
    WHERE change_date >= DATE '2024-01-01'
      AND change_date <  DATE '2024-04-01'
      AND account_id IN (SELECT account_id FROM base_accts)   -- 只统计期初存量客户，剔除新签
)
SELECT
    b.mrr_start,                                        -- 期初MRR
    m.exp_delta, m.con_delta, m.churn_delta,            -- 三类变动贡献
    ROUND((b.mrr_start + m.exp_delta + m.con_delta + m.churn_delta)
          / b.mrr_start * 100, 2) AS nrr_pct            -- NRR = (期初+净变动) ÷ 期初
FROM base b CROSS JOIN moves m;
```

结果解读：事件法天然输出了扩张/收缩/流失三个分项金额，是与财务口径对账的首选；当两种解法的NRR出现差异时，通常意味着流水漏记或快照落表延迟。

> Hive/Spark SQL差异：数据量达千万级快照时，Hive中DATE字面量建议写成'2024-01-01'字符串或to_date()；两表JOIN时小表（期初快照）可开启MapJoin广播，避免Shuffle；Spark SQL可直接用coalesce与窗口，语义一致。

### 5. 性能分析与优化

解法一只扫描两个月份的快照分区（若按snapshot_month做RANGE分区），JOIN键account_id上建立联合索引(account_id, snapshot_month)可走索引连接，代价约为2倍客户数的扫描+一次哈希JOIN。解法二扫描变动流水表，流水行数通常远大于快照（高频增减购场景可达快照的10倍以上），但可用change_date分区裁剪+change_type索引把无关流水过滤在扫描层；IN子查询会被优化器改写为半连接（semi-join）。优化建议：①快照表按月分区并预聚合成"客户×月"粒度，禁止在查询层对日明细实时汇总；②将期初客户名单物化为临时表，避免IN子查询重复执行；③每月例行预计算NRR分子分母宽表，董事会查询退化为单表读。

### 6. 面试延伸考点

- **GRR与NRR的区别是什么？为什么董事会两个都要看？** 回答要点：GRR（总收入留存）剔除扩张、只含收缩与流失、数学上限100%，衡量保客能力；NRR包含扩张、可以超过100%，衡量存量内生增长力。两个一起看能区分"守得住"和"长得动"。
- **客户期内先降级又升级，快照法和事件法结果一致吗？** 回答要点：期末NRR一致，但快照法只看两端、路径被抹平；事件法能还原中间波动，适合做过程归因与客户健康度分析。
- **新客户什么时候才计入NRR？** 回答要点：严格口径下期内新签永远不进当期分母，通常从下一个年度周期（或满一个记账期）开始进入存量池，防止新签拉高留存指标掩盖流失。
- **如果部分客户按年付费、MRR如何摊？** 回答要点：年ACV/12折算MRR，注意签约与确认收入时点差异，快照口径应与财务确认口径对齐。

### 7. 业务拓展思考

NRR分解结果可直接驱动经营动作：扩张占比高说明增购通道健康，销售团队应继续做交叉销售与向上销售；收缩集中说明部分客户在"缩席位过冬"，CS要复盘是预算削减还是功能未被用起来；流失集中则需要前置预警（见SAAS-32）并做流失访谈。口径上还可按客群切片：分行业、分获客渠道、分客户规模的NRR矩阵，识别哪类客户留存最好，反哺ICP（理想客户画像）与定价策略；进一步可计算按客户数口径的Logo Retention，与收入口径交叉验证"少而大"的流失风险。

## SAAS-32 流失预警高危客户名单（使用率下滑+工单激增双信号）

### 1. 业务背景

客户成功（CS）团队每周一召开风险客户评审会，但人力有限，每周只能深度干预10～15家客户。RevOps需要在会前产出一份高危名单：筛选"连续3个月席位使用率下滑"且"当月工单量环比翻倍"的客户——用得越来越少、抱怨越来越多，是B端SaaS续约前最经典的流失前兆组合。CS主管依据名单排定干预优先级：谁先由CSM打电话、谁给商务折扣、谁升级为技术专案，这份名单的准确率直接影响下季度GRR与续约金额。**【面试高频】** "双信号取交集"的口径必须落在同一个自然月上，跨月对齐是常见错误。

### 2. 表结构说明

表一：usage_monthly（客户月度席位使用快照表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| stat_month | DATE | 统计月份（每月1号） |
| active_seats | INT | 当月活跃席位数（当月有登录行为的用户数） |
| purchased_seats | INT | 购买席位数 |

示例数据：

| account_id | stat_month | active_seats | purchased_seats |
|------------|------------|--------------|-----------------|
| A100 | 2024-06-01 | 80 | 100 |
| A100 | 2024-07-01 | 60 | 100 |
| A100 | 2024-08-01 | 40 | 100 |
| A100 | 2024-09-01 | 30 | 100 |
| A200 | 2024-09-01 | 95 | 100 |

表二：tickets（工单表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| ticket_id | BIGINT | 工单ID |
| account_id | VARCHAR(32) | 客户账户ID |
| created_date | DATE | 工单创建日期 |
| priority | VARCHAR(10) | 优先级：P0/P1/P2/P3 |

示例数据：

| ticket_id | account_id | created_date | priority |
|-----------|------------|--------------|----------|
| 5001 | A100 | 2024-09-03 | P1 |
| 5002 | A100 | 2024-09-05 | P2 |
| 5003 | A100 | 2024-09-12 | P1 |
| 5004 | A100 | 2024-09-20 | P0 |
| 5005 | A200 | 2024-09-08 | P3 |

### 3. 解题思路

先明确两个信号口径：信号一"连续3个月使用率下滑"定义为使用率（active_seats/purchased_seats）本月<上月且上月≤上上月，即至少连续两段下行；信号二"工单激增"定义为当月工单量≥上月2倍且绝对量不低于3单（防止1→2单的噪声误报）。实现路径：①CTE算月度使用率；②用LAG取前两月使用率，窗口内直接判断连续下滑；③工单按客户×月聚合后用LAG算环比；④两信号在同一月份上INNER JOIN取交集并限定观察月。易错点：①工单表的日期是日粒度，必须先对齐到月首再JOIN，否则粒度不一致；②purchased_seats可能为0（试用客户），要NULLIF防除零；③只用等号比较"下滑"会漏掉平台期，口径要和业务方确认是严格递减还是非递增。**【加分点】** 主动提出给双信号加绝对阈值与时间衰减权重，说明候选人有误报治理意识。

### 4. 参考解法

**解法一：多层CTE + LAG窗口判连续下滑**

```sql
WITH seat_rate AS (                         -- 步骤1：月度席位使用率
    SELECT
        account_id,
        stat_month,
        ROUND(active_seats / NULLIF(purchased_seats, 0), 4) AS usage_rate  -- 使用率，NULLIF防除零
    FROM usage_monthly
    WHERE stat_month >= DATE '2024-06-01'   -- 限定窗口月，减少扫描量
),
rate_trend AS (                             -- 步骤2：取前两月使用率
    SELECT
        account_id,
        stat_month,
        usage_rate,
        LAG(usage_rate, 1) OVER (           -- 同客户按月排序取上月使用率
            PARTITION BY account_id ORDER BY stat_month) AS rate_lag1,
        LAG(usage_rate, 2) OVER (           -- 取上上月使用率
            PARTITION BY account_id ORDER BY stat_month) AS rate_lag2
    FROM seat_rate
),
decline AS (                                -- 步骤3：标记"连续三个月走低"的账户月份
    SELECT
        account_id,
        stat_month,
        usage_rate,
        CASE WHEN rate_lag2 IS NOT NULL     -- 必须有完整三个月数据才可判定
              AND usage_rate < rate_lag1    -- 本月低于上月
              AND rate_lag1 <= rate_lag2    -- 上月不高于上上月（允许平台期）
             THEN 1 ELSE 0 END AS is_decline
    FROM rate_trend
),
ticket_month AS (                           -- 步骤4：工单聚合到客户×月
    SELECT
        account_id,
        CAST(DATE_FORMAT(created_date, '%Y-%m-01') AS DATE) AS stat_month,  -- 对齐月首，与使用率表同粒度
        COUNT(*) AS ticket_cnt
    FROM tickets
    GROUP BY account_id,
             CAST(DATE_FORMAT(created_date, '%Y-%m-01') AS DATE)
),
ticket_trend AS (                           -- 步骤5：工单量环比
    SELECT
        account_id,
        stat_month,
        ticket_cnt,
        LAG(ticket_cnt) OVER (              -- 上月工单量
            PARTITION BY account_id ORDER BY stat_month) AS ticket_prev
    FROM ticket_month
)
SELECT
    d.account_id,                                                       -- 高危客户ID
    d.usage_rate,                                                       -- 当月使用率
    t.ticket_cnt,                                                       -- 当月工单量
    t.ticket_prev,                                                      -- 上月工单量
    ROUND(t.ticket_cnt / NULLIF(t.ticket_prev, 0), 2) AS ticket_surge   -- 工单激增倍数
FROM decline d
JOIN ticket_trend t                                         -- 双信号按客户+月份对齐取交集
    ON  t.account_id = d.account_id
    AND t.stat_month = d.stat_month
WHERE d.is_decline = 1                                      -- 信号一：连续三月使用率下滑
  AND t.ticket_cnt >= 2 * t.ticket_prev                     -- 信号二：工单环比至少翻倍
  AND t.ticket_cnt >= 3                                     -- 绝对量下限，滤除小样本噪声
  AND d.stat_month = DATE '2024-09-01';                     -- 只产出最新观察月名单
```

结果解读：输出形如A100（使用率0.30、工单4单、环比2.0倍）的客户清单，即CS评审会的介入名单；若名单超过15家，可按"使用率降幅×工单倍数"乘积排序取Top N。

**解法二：自连接三月份快照法（替代LAG窗口）**

```sql
SELECT
    u0.account_id,                                  -- 客户ID
    u0.stat_month,                                  -- 观察月
    u0.usage_rate,                                  -- 当月使用率
    u1.usage_rate AS rate_prev1,                    -- 上月使用率
    u2.usage_rate AS rate_prev2,                    -- 上上月使用率
    t.ticket_cnt,                                   -- 当月工单量
    t.ticket_prev                                   -- 上月工单量
FROM (
    SELECT account_id, stat_month,
           ROUND(active_seats / NULLIF(purchased_seats, 0), 4) AS usage_rate
    FROM usage_monthly
    WHERE stat_month = DATE '2024-09-01'            -- 本月快照
) u0
JOIN (
    SELECT account_id, stat_month,
           ROUND(active_seats / NULLIF(purchased_seats, 0), 4) AS usage_rate
    FROM usage_monthly
    WHERE stat_month = DATE '2024-08-01'            -- 上月快照
) u1 ON u1.account_id = u0.account_id
JOIN (
    SELECT account_id, stat_month,
           ROUND(active_seats / NULLIF(purchased_seats, 0), 4) AS usage_rate
    FROM usage_monthly
    WHERE stat_month = DATE '2024-07-01'            -- 上上月快照
) u2 ON u2.account_id = u0.account_id
JOIN (                                              -- 工单环比在派生表内完成
    SELECT account_id, ticket_cnt,
           LAG(ticket_cnt) OVER (PARTITION BY account_id ORDER BY stat_month) AS ticket_prev
    FROM (
        SELECT account_id,
               CAST(DATE_FORMAT(created_date, '%Y-%m-01') AS DATE) AS stat_month,
               COUNT(*) AS ticket_cnt
        FROM tickets
        GROUP BY account_id,
                 CAST(DATE_FORMAT(created_date, '%Y-%m-01') AS DATE)
    ) tm
) t ON  t.account_id = u0.account_id
   AND t.stat_month = u0.stat_month
WHERE u0.usage_rate < u1.usage_rate                 -- 本月低于上月
  AND u1.usage_rate <= u2.usage_rate                -- 上月不高于上上月
  AND t.ticket_cnt >= 2 * t.ticket_prev
  AND t.ticket_cnt >= 3;
```

结果解读：自连接版逻辑更直白、便于在只支持低版本SQL的BI工具中落地，且每段子查询各扫一个月分区；但月份窗口变化时需要改三处日期，工程上不如LAG版本易维护。

> Hive/Spark SQL差异：工单表在Hive中通常是亿级分区表，务必按created_date分区裁剪只读近3个月；LAG窗口在Spark中会产生单分区排序，客户数极大时可先按account_id分桶（bucketBy）再开窗，避免数据倾斜。

### 5. 性能分析与优化

解法一的窗口函数需要按account_id分区排序，代价为O(N log N)的排序，且两个LAG共用同一窗口规范时MySQL只需一次排序；解法二的三次自连接各扫描一个月分区，JOIN三次的哈希构建与探测开销高于窗口方案，在客户数百万级时差距明显。优化建议：①usage_monthly建立(account_id, stat_month)联合索引或按stat_month分区，让LAG输入天然有序；②工单月度聚合结果物化为tickets_monthly汇总表，把"日明细全扫"降为"月汇总小表"；③双信号可拆成两条独立流水线各自预计算，最后只对"本月高危池"（数千行）做JOIN，避免大表之间直接相交；④名单查询是典型周任务，建议入调度并物化结果表供看板直读。

### 6. 面试延伸考点

- **为什么用"连续3个月下滑"而不是单月下滑？** 回答要点：单月下滑受季节、假期、单项目结束影响，噪声大；连续多月下行才有趋势意义，能显著压误报，但会牺牲部分时效性，需权衡。
- **双信号之外还能加哪些信号维度？** 回答要点：关键决策人离职/账号停用、API调用量骤降、NPS变差、发票逾期、支持满意度下滑、活跃管理员数减少等，信号越多越准但要控制可解释性。
- **如何评估这份预警名单的效果？** 回答要点：以"名单内客户随后90天的实际流失率/续约率对比名单外"做验证，或回溯历史计算召回率与精确率，形成预警模型的A/B迭代。
- **工单激增也可能是深度使用的标志，如何区分？** 回答要点：结合工单类型（咨询类vs故障类）、优先级分布与是否伴随使用率下滑联合判断，故障类+使用下滑才是真风险。

### 7. 业务拓展思考

高危名单是CS资源的指挥棒：名单输出后可自动派发工单给对应CSM、按ARR（年经常性收入）加权排序实现"高风险高价值优先"。口径上可延展为流失概率评分（把各信号logistic加权），或按续约日临近程度分层——距到期90天内的客户信号权重加倍。与销售侧联动时，预警名单可与增购名单（SAAS-43）互斥复核，避免CSM在客户濒临流失时还在推销增购造成体验伤害；长期看，预警名单的干预闭环数据（干预与否、干预方式、结果）又能反哺DID实验（SAAS-37），形成完整的客户健康管理飞轮。

## SAAS-33 按签约季度Cohort收入留存矩阵

### 1. 业务背景

SaaS公司的投资人尽调与经营复盘都要求出"签约季度Cohort收入留存矩阵"：横轴是签约后的第N个季度，纵轴是签约季度，格子里的数字是该cohort客户在N个季度后的MRR相对签约当季MRR的百分比。CFO用它回答三个问题：新客质量是否在变好（新cohort曲线是否更高）、流失与降级的拐点发生在签约后第几个季度（决定CS资源前置的时点）、扩张能否让曲线"上翘"超过100%。产品与CS团队据此设定onboarding目标（例如签约后两个季度内MRR留存不低于85%）。**【加分点】** 能主动说明矩阵必须以"签约季度"而非"注册季度"对齐，且基期取签约当季末快照。

### 2. 表结构说明

表一：contracts（合同表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | BIGINT | 合同ID |
| account_id | VARCHAR(32) | 客户账户ID |
| signed_date | DATE | 签约日期 |
| acv | DECIMAL(12,2) | 合同年合同价值 |
| status | VARCHAR(20) | 合同状态：生效中/已到期/已解约 |

示例数据：

| contract_id | account_id | signed_date | acv | status |
|-------------|------------|-------------|---------|--------|
| C1001 | A001 | 2023-01-15 | 60000.00 | 生效中 |
| C1002 | A002 | 2023-04-20 | 36000.00 | 生效中 |
| C1003 | A003 | 2023-04-05 | 24000.00 | 已解约 |
| C1004 | A004 | 2023-07-10 | 48000.00 | 生效中 |
| C1005 | A001 | 2024-01-05 | 96000.00 | 生效中 |

表二：mrr_snapshot（客户月度MRR快照表，同SAAS-31口径）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| snapshot_month | DATE | 快照月份（每月1号） |
| mrr | DECIMAL(12,2) | 当月月度经常性收入 |
| plan_name | VARCHAR(50) | 当前定价档位 |

示例数据：

| account_id | snapshot_month | mrr | plan_name |
|------------|----------------|---------|----------|
| A001 | 2023-03-01 | 5000.00 | 专业版 |
| A001 | 2023-06-01 | 5000.00 | 专业版 |
| A001 | 2023-12-01 | 8000.00 | 企业版 |
| A002 | 2023-06-01 | 3000.00 | 专业版 |
| A002 | 2023-09-01 | 0.00 | 基础版 |

### 3. 解题思路

先定口径：①cohort用客户首份合同的签约季度（MIN(signed_date)取季度），防止续约合同把老客户误划入新cohort；②基期MRR取签约当季末（季度末月快照）的客户MRR合计，而非签约日当天（月中签约当月MRR不满额）；③期数偏移q_offset =（观察季度-签约季度）的季度差，用年差×4+季差计算；④留存率 = 该cohort在offset期的MRR合计 ÷ 该cohort基期MRR合计，流失客户自然体现为合计下降。实现路径：CTE算cohort → 关联季度末快照并计算offset → 按cohort×offset聚合成"长表" → 条件聚合透视成"宽表矩阵"。易错点：续约合同混入cohort划分、把月快照全量拿来做基期（应只取季度末月）、留存率按客户平均而非按MRR加权；另外季末最后几天签约的客户其签约季末快照可能尚未落表，需约定以"签约后首个季度末"为基期兜底，避免这类客户被静默剔除。**【避坑指南】** MIN(signed_date)一定要按客户分组后再取，直接对合同表求季度会把续约合同当新客。

### 4. 参考解法

**解法一：多层CTE + 条件聚合透视（宽表矩阵）**

```sql
WITH cohort AS (                            -- 步骤1：客户的首签季度（cohort键）
    SELECT
        account_id,
        CONCAT(YEAR(MIN(signed_date)), 'Q', QUARTER(MIN(signed_date))) AS cohort_q
                                            -- 首份合同签约季度，形如 2023Q1
    FROM contracts
    GROUP BY account_id
),
q_mrr AS (                                  -- 步骤2：季度末月（3/6/9/12月）快照的MRR
    SELECT
        s.account_id,
        s.snapshot_month,
        s.mrr,
        CONCAT(YEAR(s.snapshot_month), 'Q', QUARTER(s.snapshot_month)) AS qtr
    FROM mrr_snapshot s
    WHERE MONTH(s.snapshot_month) IN (3, 6, 9, 12)   -- 只取季度末月快照作为该季收盘MRR
      AND s.account_id IN (SELECT account_id FROM cohort)
),
aligned AS (                                -- 步骤3：计算相对签约季度的期数偏移
    SELECT
        c.cohort_q,
        q.account_id,
        (YEAR(q.snapshot_month)
            - CAST(SUBSTRING_INDEX(c.cohort_q, 'Q', 1) AS UNSIGNED)) * 4
        + (QUARTER(q.snapshot_month)
            - CAST(SUBSTRING_INDEX(c.cohort_q, 'Q', -1) AS UNSIGNED)) AS q_offset,
                                            -- 年差×4 + 季差 = 相隔季度数
        q.mrr
    FROM q_mrr q
    JOIN cohort c ON c.account_id = q.account_id
),
cohort_mrr AS (                             -- 步骤4：cohort × 期数 的MRR合计（长表）
    SELECT
        a.cohort_q,
        a.q_offset,
        SUM(a.mrr) AS mrr_sum
    FROM aligned a
    GROUP BY a.cohort_q, a.q_offset
),
cohort_base AS (                            -- 步骤5：各cohort的基期（offset=0）MRR
    SELECT cohort_q, mrr_sum AS base_mrr
    FROM cohort_mrr
    WHERE q_offset = 0
)
SELECT
    m.cohort_q,                                             -- 签约季度
    cb.base_mrr,                                            -- 基期MRR合计
    MAX(CASE WHEN m.q_offset = 0 THEN ROUND(m.mrr_sum / cb.base_mrr * 100, 1) END) AS `当季`,
    MAX(CASE WHEN m.q_offset = 1 THEN ROUND(m.mrr_sum / cb.base_mrr * 100, 1) END) AS `+1季`,
    MAX(CASE WHEN m.q_offset = 2 THEN ROUND(m.mrr_sum / cb.base_mrr * 100, 1) END) AS `+2季`,
    MAX(CASE WHEN m.q_offset = 4 THEN ROUND(m.mrr_sum / cb.base_mrr * 100, 1) END) AS `+4季`,
    MAX(CASE WHEN m.q_offset = 8 THEN ROUND(m.mrr_sum / cb.base_mrr * 100, 1) END) AS `+8季`
                                            -- 条件聚合把长表透视成矩阵
FROM cohort_mrr m
JOIN cohort_base cb ON cb.cohort_q = m.cohort_q
GROUP BY m.cohort_q, cb.base_mrr
ORDER BY m.cohort_q;
```

结果解读：理想输出形如2023Q1行"100.0 / 92.3 / 105.1 / 108.4 / 112.0"——先降后升说明客户在踩过onboarding磨合期后开始增购；若新cohort的同列数值系统性低于老cohort，则说明近两年新客质量在变差。

**解法二：长表输出 + 窗口环比（供BI热力图直接消费）**

```sql
WITH cohort_mrr AS (                        -- 步骤1：复用解法一前四步得到长表
    SELECT a.cohort_q, a.q_offset, SUM(a.mrr) AS mrr_sum
    FROM (
        SELECT
            c.cohort_q,
            (YEAR(q.snapshot_month)
                - CAST(SUBSTRING_INDEX(c.cohort_q, 'Q', 1) AS UNSIGNED)) * 4
            + (QUARTER(q.snapshot_month)
                - CAST(SUBSTRING_INDEX(c.cohort_q, 'Q', -1) AS UNSIGNED)) AS q_offset,
            q.mrr
        FROM (
            SELECT account_id, snapshot_month, mrr
            FROM mrr_snapshot
            WHERE MONTH(snapshot_month) IN (3, 6, 9, 12)   -- 季度末月快照
        ) q
        JOIN (
            SELECT account_id,
                   CONCAT(YEAR(MIN(signed_date)), 'Q', QUARTER(MIN(signed_date))) AS cohort_q
            FROM contracts
            GROUP BY account_id
        ) c ON c.account_id = q.account_id
    ) a
    GROUP BY a.cohort_q, a.q_offset
),
enriched AS (                               -- 步骤2：窗口补齐基期MRR与环比
    SELECT
        cohort_q,
        q_offset,
        mrr_sum,
        FIRST_VALUE(mrr_sum) OVER (         -- 取同一cohort内最早的MRR合计作基期
            PARTITION BY cohort_q ORDER BY q_offset) AS base_mrr,
        LAG(mrr_sum) OVER (                 -- 上一期MRR合计，用于逐季变动
            PARTITION BY cohort_q ORDER BY q_offset) AS prev_mrr
    FROM cohort_mrr
)
SELECT
    cohort_q,                               -- 签约季度
    q_offset,                               -- 相隔季度数
    ROUND(mrr_sum / base_mrr * 100, 1) AS retention_pct,    -- 相对基期的留存率
    ROUND((mrr_sum - prev_mrr) / NULLIF(prev_mrr, 0) * 100, 1) AS qoq_pct
                                            -- 相邻两季的环比变化，定位拐点
FROM enriched
ORDER BY cohort_q, q_offset;
```

结果解读：长表（cohort_q, q_offset, retention_pct, qoq_pct）可直接喂给BI工具画热力图；qoq_pct列能让面试官看到你不仅会"留存"，还会定位"拐点在签约后第几季"。

> Hive/Spark SQL差异：Hive不支持QUARTER的旧版本可改用(floor((month-1)/3)+1)；快照表亿级数据时，先在ETL层按"仅季度末月"预过滤落成季度快照表（数据量降为1/3），矩阵查询变成纯小表透视；透视列很多时Spark可用pivot语法替代MAX(CASE WHEN)。

### 5. 性能分析与优化

两种解法的主体成本都在步骤2～3：快照表按账户JOIN合同聚合结果，快照表若有3年×12月×10万客户≈3600万行，只取季度末月可先裁剪到1200万行；条件聚合透视本身是单表GROUP BY，代价低。优化建议：①mrr_snapshot按snapshot_month RANGE分区，查询里显式给出季度末月清单以触发分区裁剪；②cohort键（客户首签季度）属于慢变属性，建议物化为account_cohort维表，省去每次对合同表的MIN聚合；③矩阵列固定（如只展示+0～+12季），可在调度里把长表预展开成宽表物化，看板查询零计算；④若需要全量季度offset透视，Spark SQL用pivot比几十个MAX(CASE WHEN)更利于Catalyst优化。

### 6. 面试延伸考点

- **矩阵应该按"签约季度"还是"首次付费季度"对齐？** 回答要点：以业务动作为准——销售签约制公司用签约季度、PLG试用转化模式用首付费月；关键是全员统一并写进口径文档。
- **新cohort数据还不满4个季度，矩阵右侧空格怎么处理？** 回答要点：空格是"尚未发生"不是"流失"，展示时用灰色区分，并避免用不完整cohort做同比结论。
- **留存矩阵上翘（>100%）说明什么？如何拆解上翘来源？** 回答要点：扩张超过流失+收缩，可再拆为增购/升级/加产品的金额贡献，与NRR分项对齐。
- **如果要看客户数口径的cohort留存，查询要怎么改？** 回答要点：把SUM(mrr)改为COUNT(DISTINCT account_id)，口径从收入留存变成Logo留存，两者背离时说明流失集中在小客户或大客户。

### 7. 业务拓展思考

Cohort矩阵是SaaS经营质量的"心电图"：新cohort曲线走低时，市场团队要复盘获客渠道质量（是否大量薅羊毛型客户），销售要复盘折扣与承诺是否过度；拐点列（qoq）能帮CS定位干预窗口——若普遍在签约后第2季度出现收缩，onboarding资源就应前置到第1季度。口径可延展为"按签约金额分层"的cohort（大客/中客/长尾分开看），或"按行业"的cohort矩阵识别垂直行业留存优势；进一步与获客成本（CAC）结合，可以算出各cohort的回本周期与LTV/CAC，把留存分析升级为单位经济模型分析。

## SAAS-34 功能采用深度与续约率分组分析

### 1. 业务背景

产品与CS团队长期争论：功能采用广度到底能不能预测续约？数据团队需要给出量化证据。业务问题来自CS主管：在客户续约评审会上，CSM需要一个直观分级——过去90天用过多少个核心功能模块的客户，其续约率与平均ACV分别是多少？如果"深度采用（5个功能以上）"客户续约率显著高于"零采用"客户，CS就把"推动客户多用功能"写进续约前90天的标准动作（playbook）；反之若相关性弱，则要警惕把资源押错方向。该分析也是PLG（产品驱动增长）团队衡量PQA（产品合格账户）口径的基础。**【面试高频】** 采用深度必须按"续约事件前90天"的回看窗口对齐，而不是取客户历史全期，否则存在未来信息泄漏。

| 7003 | A003 | 2024-08-31 | 0 | 24000.00 |
| 7004 | A004 | 2024-10-31 | 1 | 48000.00 |
| 7005 | A005 | 2024-10-15 | 1 | 60000.00 |

### 3. 解题思路

第一步定指标口径：每个续约事件的"采用深度"=该客户在续约日前90天窗口内使用过的互不重复核心功能数（COUNT DISTINCT feature_name），用回看窗口避免把续约后才发生的使用算进来；第二步分箱：0个记"未采用"、1～2个记"浅度"、3～4个记"中度"、5个及以上记"深度"；第三步按箱聚合续约率（AVG(is_renewed)）与平均ACV，观察单调性。实现上有两条路：解法一是JOIN+GROUP BY的CTE主线，简单稳健；解法二进一步计算采用数与是否续约的皮尔逊相关系数，用矩公式在SQL里直接量化相关强度，并输出散点聚合明细。易错点：①LEFT JOIN后COUNT DISTINCT在零采用客户上得NULL，要COALESCE为0再分箱，否则该箱直接消失；②一个客户多年多次续约会生成多条续约事件，样本相互关联，结论要按"事件"还是"客户"口径讲清楚；③核心功能清单应由产品口径先定，避免把登录、浏览类弱功能算进深度。**【避坑指南】** 忘记COALESCE零采用客户，分箱结果里永远看不到最关键的"0个功能"组，续约率对比直接失真。

### 4. 参考解法

**解法一：CTE回看窗口 + 分箱 + 条件聚合**

```sql
WITH adopt AS (                             -- 步骤1：为每个续约事件对齐前90天采用深度
    SELECT
        r.renewal_id,
        r.account_id,
        r.is_renewed,
        r.acv,
        COUNT(DISTINCT f.feature_name) AS feature_cnt   -- 90天窗口内去重功能数
    FROM renewals r
    LEFT JOIN feature_usage f               -- LEFT JOIN保证零采用客户也保留
        ON  f.account_id = r.account_id
        AND f.used_date >= r.renewal_date - INTERVAL 90 DAY   -- 回看窗口起点
        AND f.used_date <  r.renewal_date                     -- 窗口终点（不含续约日当天）
    GROUP BY r.renewal_id, r.account_id, r.is_renewed, r.acv
),
binned AS (                                 -- 步骤2：采用深度分箱
    SELECT
        renewal_id, is_renewed, acv,
        COALESCE(feature_cnt, 0) AS feature_cnt,        -- 零采用补0
        CASE
            WHEN COALESCE(feature_cnt, 0) = 0 THEN 'A-未采用(0个)'
            WHEN COALESCE(feature_cnt, 0) <= 2 THEN 'B-浅度(1-2个)'
            WHEN COALESCE(feature_cnt, 0) <= 4 THEN 'C-中度(3-4个)'
            ELSE 'D-深度(5个及以上)'
        END AS depth_bin
    FROM adopt
)
SELECT
    depth_bin,                                          -- 采用深度分箱
    COUNT(*)                     AS event_cnt,          -- 续约事件数
    SUM(is_renewed)              AS renewed_cnt,        -- 续约成功数
    ROUND(AVG(is_renewed) * 100, 1) AS renew_rate_pct,  -- 续约率
    ROUND(AVG(acv), 0)           AS avg_acv,            -- 平均合同金额
    ROUND(SUM(is_renewed * acv) / SUM(acv) * 100, 1) AS acv_weighted_rate
                                                        -- 按金额加权的续约率
FROM binned
GROUP BY depth_bin
ORDER BY depth_bin;
```

结果解读：若四箱续约率依次为42%/61%/78%/91%，呈明显单调上升，即支持"采用深度驱动续约"的假设，CS应把功能引导写入续约前playbook；若金额加权率低于客户数口径率，说明流失集中在小客户。

**解法二：嵌套派生表 + 皮尔逊相关系数（量化相关强度）**

```sql
SELECT
    COUNT(*)                            AS n,               -- 样本数（续约事件数）
    ROUND(AVG(x), 2)                    AS avg_feature,     -- 平均采用功能数
    ROUND(AVG(y) * 100, 1)              AS renew_rate_pct,  -- 总体续约率
    ROUND(
        (SUM(x * y) - SUM(x) * SUM(y) / COUNT(*))                   -- 协方差项
        / (SQRT(SUM(x * x) - SUM(x) * SUM(x) / COUNT(*))            -- x的标准差项
           * SQRT(SUM(y * y) - SUM(y) * SUM(y) / COUNT(*)))         -- y的标准差项
        , 3)                            AS pearson_corr     -- 皮尔逊相关系数
FROM (
    SELECT
        r.renewal_id,
        COUNT(DISTINCT f.feature_name) AS x,                -- x=采用功能数
        r.is_renewed                   AS y                 -- y=是否续约(0/1)
    FROM renewals r
    LEFT JOIN feature_usage f
        ON  f.account_id = r.account_id
        AND f.used_date >= r.renewal_date - INTERVAL 90 DAY
        AND f.used_date <  r.renewal_date
    GROUP BY r.renewal_id, r.is_renewed
) t;
```

结果解读：相关系数若为0.62，说明采用深度与续约有较强正相关，但相关不等于因果——可能是"健康客户本来就爱用功能"，结论要配合SAAS-37式的干预实验才能上升到因果表述，这是回答时的加分表述。

> Hive/Spark SQL差异：feature_usage是典型的大表（日均千万行），Hive下先按回看窗口谓词做分区裁剪（used_date动态分区）；COUNT(DISTINCT)在Hive中会强制单Reducer，大样本时应改为"先GROUP BY account_id, feature_name去重、再COUNT"两阶段聚合；Spark SQL可开启skew join优化。

### 5. 性能分析与优化

解法一的代价核心在renewals与feature_usage的区间JOIN：feature_usage若为亿级日明细，直接JOIN会产生大范围Shuffle。优化建议：①先把feature_usage预聚合为"客户×月×功能"粒度的小表（月度百万行级），回看窗口JOIN降到90行/客户；②renewals按renewal_date分区，只读本期续约事件；③JOIN键account_id上建索引，续约事件表小、可作Build侧走哈希JOIN；④解法二的矩公式只需一趟聚合，代价低于分箱方案，可作为看板上"相关性健康度"指标的固定查询；若样本量极大，先抽样或按月分片再合并计算（协方差与方差均可分片累加）。

### 6. 面试延伸考点

- **为什么用90天回看窗口？窗口取多长合适？** 回答要点：90天覆盖一个季度经营节奏且贴近续约决策期；窗口过短样本稀疏、过长稀释信号，可用不同窗口跑敏感性分析选择。
- **续约率高就代表功能有用吗？如何反驳"相关非因果"？** 回答要点：健康客户自选择偏差、大客户资源多既买得多也用得多；规范做法是干预实验（强制引导部分客户采用某功能，对比DID）。
- **分箱边界怎么定才不武断？** 回答要点：参考业务playbook的可操作性（0/浅/中/深对应不同动作），或用NTILE分位数分箱后观察单调性再归并为业务友好的边界。
- **多次续约的客户怎么处理？** 回答要点：可按"客户最新一次续约"去重（ROW_NUMBER取rn=1），或按事件口径保留并说明样本相关性，两种口径都汇报。

### 7. 业务拓展思考

采用深度与续约的相关性一旦确认，就可以产品化：把分箱写进客户健康分模型，CS按"深度不足+临近续约"自动生成任务清单，推动客户在续约前90天完成2个新功能采用。产品侧可用同一口径评估新功能上线价值——上线后客户采用深度分布是否右移、对应cohort续约率是否改善。口径延展上，可把"功能数"换成"关键动作数"（如完成首次集成、导入历史数据）、按角色细分（管理员采用vs普通成员采用），甚至区分广度（用了几个）与深度（用得多频繁），为PLG团队提供PQA评分与增长实验的统一底座。

## SAAS-35 销售管线加权预测（阶段×概率×金额）

### 1. 业务背景

季度中期（Q3第6周），销售VP要向CFO提交本季度新增签约额预测，用于收入指引与人力调配。CRM里Open管线的每个商机都带有销售自报的金额、阶段与赢单概率，但销售自报概率普遍乐观（"Optimism Bias"），直接SUM(amount×probability)会系统性高估。RevOps需要给出两版预测： naive版（自报概率加权）与校准版（用公司历史各阶段的真实胜率替换自报概率），并按阶段拆分展示，指出哪类阶段的管线水分最大，进而推动销售运营把阶段推进标准（Stage Exit Criteria）落到CRM。**【加分点】** 能主动提出"自报概率与历史胜率的偏差"（乐观度差距）是预测校准的关键。

### 2. 表结构说明

表一：opportunities（商机管线表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| opp_id | BIGINT | 商机ID |
| account_id | VARCHAR(32) | 客户账户ID |
| stage | VARCHAR(20) | 当前阶段：线索确认/需求验证/方案报价/商务谈判 |
| amount | DECIMAL(12,2) | 预计合同金额 |
| probability | INT | 销售自报赢单概率（0-100） |
| expected_close_date | DATE | 预计签约日期 |
| is_closed | TINYINT | 是否已关单：1已关/0在管线 |

示例数据：

| opp_id | account_id | stage | amount | probability | expected_close_date | is_closed |
|--------|------------|-------|--------|-------------|---------------------|-----------|
| 8001 | B001 | 方案报价 | 120000.00 | 60 | 2024-11-20 | 0 |
| 8002 | B002 | 商务谈判 | 200000.00 | 80 | 2024-11-05 | 0 |
| 8003 | B003 | 线索确认 | 80000.00 | 20 | 2024-12-10 | 0 |
| 8004 | B004 | 需求验证 | 150000.00 | 40 | 2024-11-30 | 0 |
| 8005 | B005 | 商务谈判 | 90000.00 | 90 | 2024-11-15 | 0 |

表二：stage_benchmarks（阶段历史基准表，由历史赢单数据统计得到）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| stage | VARCHAR(20) | 商机阶段 |
| hist_win_rate | DECIMAL(5,4) | 历史进入该阶段的商机最终赢单率 |
| avg_days_to_close | INT | 该阶段到关单的平均天数 |

示例数据：

| stage | hist_win_rate | avg_days_to_close |
|-------|---------------|-------------------|
| 线索确认 | 0.1500 | 90 |
| 需求验证 | 0.3200 | 65 |
| 方案报价 | 0.5500 | 40 |
| 商务谈判 | 0.7800 | 18 |

### 3. 解题思路

先明确预测口径：只统计is_closed=0且expected_close_date落在本季度（2024-10-01至2024-12-31）的Open商机；naive加权额=SUM(amount×自报概率)；校准加权额=SUM(amount×该阶段历史胜率)。两版对比后按阶段拆分，计算每个阶段的"乐观度差距"（自报加权-历史加权），找出水分最大的阶段。实现路径：解法一用GROUP BY+ROLLUP一次输出分阶段小计与总计；解法二JOIN基准表做校准并引入"滑期风险因子"（预计签约日越靠季末、被推迟到下季的概率越高，给时间衰减系数），更贴近实战。易错点：①probability字段是0-100整数不是小数，加权时除以100；②已关单商机若状态维护不及时会混入管线，可用expected_close_date早于今天且仍Open的"僵尸商机"检查兜底；③大单占比高时均值不稳定，应同时输出加权额的中位数口径或按单笔封顶。**【避坑指南】** 忘记过滤is_closed=0，会把已赢单金额重复计入预测。

### 4. 参考解法

**解法一：自报概率加权 + ROLLUP分阶段汇总**

```sql
SELECT
    COALESCE(stage, '【全部合计】')         AS stage,      -- 阶段；ROLLUP行用合计标签
    COUNT(*)                                AS opp_cnt,    -- 商机数
    SUM(amount)                             AS pipeline_amount,    -- 管线名义金额
    ROUND(SUM(amount * probability / 100), 0) AS weighted_amount
                                            -- naive加权预测 = Σ(金额×自报概率)
FROM opportunities
WHERE is_closed = 0                                        -- 只看在管线的Open商机
  AND expected_close_date BETWEEN DATE '2024-10-01'
                             AND DATE '2024-12-31'         -- 预计签约落在本季度
GROUP BY stage WITH ROLLUP                                 -- 分阶段小计 + 总计行
ORDER BY GROUPING(stage), weighted_amount DESC;            -- 总计行排最前（GROUPING=1）
```

结果解读：假设输出商务谈判加权32万、方案报价26万、需求验证19万、线索确认2.4万、合计79.4万——VP可直接对照季度目标判断缺口；若某阶段商机数极少但金额巨大，要提示单点风险。

**解法二：历史胜率校准 + 滑期风险因子（JOIN基准表）**

```sql
SELECT
    o.stage,                                                -- 商机阶段
    b.hist_win_rate,                                        -- 历史真实胜率
    o.self_rate,                                            -- 阶段内平均自报概率
    ROUND(o.naive_amt, 0)   AS naive_amt,                   -- 自报概率加权额
    ROUND(o.calib_amt, 0)   AS calib_amt,                   -- 历史胜率加权额
    ROUND(o.naive_amt - o.calib_amt, 0) AS optimism_gap     -- 乐观度差距（水分）
FROM (
    SELECT
        stage,
        AVG(probability) AS self_rate,                      -- 该阶段平均自报概率
        SUM(amount * probability / 100) AS naive_amt,       -- naive加权额小计
        SUM(amount * b.hist_win_rate                        -- 校准加权：金额×历史胜率
                  * CASE                                    -- 滑期风险因子：签约日越靠季末越可能滑出本季
                        WHEN expected_close_date <  DATE '2024-12-01' THEN 1.00
                        WHEN expected_close_date <  DATE '2024-12-15' THEN 0.85
                        ELSE 0.65
                    END) AS calib_amt
    FROM opportunities o
    JOIN stage_benchmarks b ON b.stage = o.stage            -- 关联历史基准
    WHERE o.is_closed = 0
      AND o.expected_close_date BETWEEN DATE '2024-10-01' AND DATE '2024-12-31'
    GROUP BY o.stage
) o
JOIN stage_benchmarks b ON b.stage = o.stage;               -- 再关联一次取胜率用于展示
```

结果解读：若商务谈判阶段乐观度差距为正、线索确认阶段为负（销售在早期反而保守），运营可针对性要求谈判期商机补充决策链信息，并把季末商机单独做"滑期名单"跟进。

> Hive/Spark SQL差异：商机表百万行级不算大，但集团多BU场景下可按bu_id分区并行；WITH ROLLUP在Hive中语法不同（Hive 2.3+支持GROUP BY ... WITH ROLLUP，Spark用GROUPING SETS替代）；CASE WHEN滑期因子在两平台通用。

### 5. 性能分析与优化

两版查询都是单表（或一小表JOIN）聚合，扫描量=Open商机数，通常几万到几十万行，代价本身很低；关键风险在JOIN stage_benchmarks是广播小表，代价可忽略。优化建议：①opportunities对(is_closed, expected_close_date)建联合索引，过滤Open+本季直接走索引范围；②历史胜率基准表由离线任务每日更新，避免查询时实时扫描历史关单商机（那才是真正的大计算：要扫全量Closed-Won/Lost）；③ROLLUP输出适合直接落预测看板；④若需按周滚动预测，把"Open管线快照"每周一物化，支持预测准确度的回测（预测vs实际）而不被后续商机状态更新污染。

### 6. 面试延伸考点

- **自报概率和历史胜率哪个更可信？什么时候混用？** 回答要点：历史胜率更稳定但滞后于打法变化；大客户直销可信任资深销售自报，规模化销售用校准值；可输出两版区间给CFO做承诺与stretch目标。
- **如何处理"僵尸商机"（预计签约日已过但仍Open）？** 回答要点：先跑数量与金额占比，超阈值则把其expected_close_date重置规则纳入CRM治理，预测时对僵尸商机打折或剔除。
- **为什么还要乘滑期因子？** 回答要点：预计签约日在季末的商机实际大量滑到下季，时间分布修正让周滚动预测更准；因子可由历史"预计vs实际签约月差"统计得出。
- **如何评估预测质量？** 回答要点：留存每周快照做回测，用MAPE/WMAPE衡量预测偏差，并把偏差归因到阶段漏斗转化率的变化。

### 7. 业务拓展思考

加权预测不止服务于收入指引：按阶段拆出的"水分榜"是销售运营改进阶段定义（Stage Exit Criteria）的依据——水分最大的阶段说明该阶段的进入门槛形同虚设。校准胜率可进一步按行业、客户规模、渠道伙伴分层，形成更细的胜率矩阵；预测区间（P50/P90）可衔接财务的收入确认与费用投放节奏。与SAAS-45联动：续约商机与新增商机应分池预测，两者的赢单率与周期结构完全不同；长期可将管线加权额、转化率、周期一起构成销售漏斗健康仪表盘，指导是"补线索"还是"推阶段"的资源决策。
## SAAS-36 定价档位迁移对MRR的净影响分析

定价委员会每半年复盘一次档位（Plan）策略，核心疑问是：客户在档位之间的迁移到底是净升级还是净降级？哪一对档位迁移（如企业版→专业版）流失的MRR最多？2024年公司刚完成一次提价与新档位上线，CFO要求量化本次定价调整对MRR的结构性影响，用以决定是否推出中间档位或调整年付折扣。RevOps分析师需要基于档位迁移流水，按月统计升级/降级/同级迁移的笔数与MRR净变动，并下钻到"迁移对"（from_plan→to_plan）粒度，为定价与包装（Pricing & Packaging）决策提供证据。**【面试高频】** 迁移流水自身的数据质量（上一次迁移后的MRR应等于下一次迁移前的MRR）是本题的隐藏考点。

### 3. 解题思路

第一步定分类口径：升级=mrr_after>mrr_before、降级=mrr_after<mrr_before、同级迁移=相等（如月付转年付，属"名义同级但实为折扣迁移"）；净影响=SUM(mrr_after-mrr_before)。第二步按月×分类聚合输出趋势，识别提价后的降级潮；第三步下钻迁移对：GROUP BY from_plan, to_plan，找出负向金额最大的档位对，供定价委员会设计"缓冲档位"。解法二从数据质量切入：用LAG按账户时间序列校验mrr_before是否等于上一条mrr_after，揪出漏记的迁移事件（如直接退订又重签），防止净影响被低估；同时结合plans.tier把"MRR下降但tier上升"的异常迁移（定价调整导致）单独标记。易错点：①同为"升级"定义，按金额比较与按tier比较可能矛盾，须与业务确认主口径；②年付折扣迁移不应计入降级流失，要单独归入"付费方式迁移"。**【加分点】** 主动提出用tier校验金额方向的合理性，体现对定价结构本身的理解。

### 4. 参考解法

**解法一：迁移分类聚合 + 档位对下钻**

```sql
WITH moves AS (                             -- 步骤1：打迁移分类标签
    SELECT
        change_id,
        account_id,
        change_date,
        from_plan,
        to_plan,
        mrr_after - mrr_before AS mrr_delta,            -- 单笔MRR变动
        CASE
            WHEN mrr_after > mrr_before THEN '升级'
            WHEN mrr_after < mrr_before THEN '降级'
            ELSE '同级迁移'                             -- 金额相同（如月付转年付前的对等迁移）
        END AS move_type
    FROM plan_changes
    WHERE change_date >= DATE '2024-07-01'              -- 提价上线后的观察期
)
SELECT
    DATE_FORMAT(change_date, '%Y-%m') AS ym,            -- 迁移月份
    move_type,                                          -- 升级/降级/同级迁移
    COUNT(*)                    AS move_cnt,            -- 迁移笔数
    SUM(mrr_delta)              AS net_mrr_delta,       -- 该类净MRR影响
    ROUND(AVG(ABS(mrr_delta)), 0) AS avg_abs_delta      -- 单笔平均变动幅度
FROM moves
GROUP BY DATE_FORMAT(change_date, '%Y-%m'), move_type
UNION ALL
SELECT
    '【汇总-迁移对TOP】',                               -- 第二段：负向影响最大的档位对
    CONCAT(from_plan, ' → ', to_plan) AS move_type,     -- 档位对标签
    COUNT(*),
    SUM(mrr_delta),
    ROUND(AVG(ABS(mrr_delta)), 0)
FROM moves
GROUP BY CONCAT(from_plan, ' → ', to_plan)
HAVING SUM(mrr_delta) < 0                                 -- 只看净流出（负向）的迁移对
ORDER BY net_mrr_delta;
```

结果解读：若2024-08出现降级净流出峰值且"企业版→专业版"贡献最大，说明新定价的企业版门槛过高把中等客户挤下去了，定价委员会可考虑增设中间档或对年付放宽条件。

**解法二：LAG流水自洽校验 + tier交叉验证**

```sql
WITH seq AS (                               -- 步骤1：账户内按时间排列迁移链
    SELECT
        account_id,
        change_id,
        change_date,
        from_plan,
        to_plan,
        mrr_before,
        mrr_after,
        LAG(mrr_after) OVER (               -- 取该客户上一条迁移的"迁移后MRR"
            PARTITION BY account_id ORDER BY change_date) AS prev_after,
        LAG(to_plan) OVER (                 -- 上一条迁移的目标档位
            PARTITION BY account_id ORDER BY change_date) AS prev_to_plan
    FROM plan_changes
),
audit AS (                                  -- 步骤2：数据质量审计
    SELECT
        account_id, change_id, change_date,
        from_plan, to_plan, mrr_before, mrr_after,
        CASE
            WHEN prev_after IS NOT NULL
             AND ABS(mrr_before - prev_after) > 0.01
            THEN '断裂-疑似漏记'                        -- 迁移前MRR对不上上一条的迁移后MRR
            WHEN prev_after IS NOT NULL
             AND prev_to_plan <> from_plan
            THEN '断裂-档位名不一致'                    -- 上一条终点档位与本次起点不符
            ELSE 'OK'
        END AS audit_flag
    FROM seq
)
SELECT
    a.audit_flag,                                       -- 审计结论
    a.change_id,
    a.account_id,
    a.change_date,
    a.from_plan,
    a.to_plan,
    b.tier AS from_tier,                                -- 起点档位层级
    c.tier AS to_tier,                                  -- 终点档位层级
    a.mrr_after - a.mrr_before AS mrr_delta,            -- 金额变动
    CASE WHEN (a.mrr_after - a.mrr_before) > 0 AND c.tier <= b.tier
          THEN '金额升但档位未升-定价调整嫌疑'          -- tier与金额方向矛盾，提示提价/折扣因素
         ELSE '' END AS cross_check                     -- 交叉验证结论
FROM audit a
LEFT JOIN plans b ON b.plan_name = a.from_plan
LEFT JOIN plans c ON c.plan_name = a.to_plan
ORDER BY a.audit_flag, a.account_id, a.change_date;
```

结果解读："断裂-疑似漏记"事件说明迁移流水不完整，净影响被低估，应先回补流水（或以快照法对账）再下业务结论；"金额升但档位未升"集中出现时，正对应本次提价造成的同档变相涨价。

> Hive/Spark SQL差异：迁移流水若来自多端埋点合并（亿级），Hive下先按change_date分区过滤观察期；LAG窗口在Spark中注意account_id倾斜（个别大客户迁移上百次），可先加盐或按account_id分桶；ABS容差比较在浮点存储时建议改用DECIMAL。

### 5. 性能分析与优化

解法一是纯单表过滤聚合，扫描量=观察期内迁移笔数，代价最低；解法二的窗口按account_id分区排序，代价O(N log N)，且两次JOIN plans字典表都是几十行的广播小表。优化建议：①plan_changes对(change_date)分区、(account_id, change_date)建联合索引，窗口排序可直接利用索引序；②迁移事件通常不多（月均千级），两版查询都适合直连生产库实时跑；真正的大表是背后的订阅计费明细，应在ETL层先抽象出"迁移事件"这一层，查询层永远不碰原始账单；③审计类查询可固化为每日数据质量任务，产出断裂事件清单自动派给计费系统负责人；④给(mrr_before, mrr_after)加CHECK式校验在写入端（计费系统）落库时执行，源头治数。

### 6. 面试延伸考点

- **升级/降级的判定用金额还是档位tier？** 回答要点：分析目的优先——收入影响看金额、包装健康度看tier；两者矛盾时（金额升tier降）要单独归因为定价或折扣变化，避免污染分类。
- **月付转年付的折扣迁移算不算降级？** 回答要点：MRR下降但合同价值与现金流改善，应单列"付费方式迁移"维度，用年化ACV与MRR双口径同时汇报。
- **如何区分"客户主动降级"和"系统自动降级"（如试用期结束回落）？** 回答要点：迁移事件需带来源字段（人工/系统/合同到期），口径上剔除系统自动迁移再评估客户真实意愿。
- **如果迁移流水缺失，怎么补齐分析？** 回答要点：用月度MRR快照的逐月差分反推迁移事件（金额对不上即视为有未记录变更），与SAAS-31的快照-事件对账思想一致。

### 7. 业务拓展思考

档位迁移矩阵（from_plan×to_plan的迁移人数与金额热力图）是Pricing & Packaging迭代的标准输入：若"企业版→专业版"持续净流出，可设计"高级专业版"承接溢出需求；若"基础版→专业版"升级顺畅，则说明包装梯度合理。迁移分析还能与客户分层交叉——大客户的降级往往伴随满意度问题，应触发CS介入而非仅商务处理；长尾客户的降级则可能是自然淘洗。口径延展上可引入"迁移弹性"（提价幅度对应的降级率变化）作为下次调价的量化依据，并跟踪迁移后客户的6个月留存，判断"留下来的是不是更健康的客户"。

## SAAS-37 客户成功干预效果评估（简化DID）

### 1. 业务背景

CS团队在2024年7月对一批"健康分偏低"的客户启动了专项干预（专属CSM接管+技术健康检查），希望证明干预有效以争取明年预算。但直接对比干预前后客户MRR会高估效果（时间趋势、季节性混杂），直接对比干预组与对照组会低估效果（选择偏差：干预组本来就是高风险客户）。RevOps采用简化双重差分（DID）：选取同期未干预的相似客户作对照组，用"干预组前后变化 - 对照组前后变化"剔除共同趋势，得到净效应。分析结论将决定该干预项目是扩大规模、维持试点还是终止。**【面试高频】** 平行趋势假设与"干预组/对照组前后窗口对齐"是DID题的两个必问点。

### 2. 表结构说明

表一：cs_experiment（干预分组表）

| grp | VARCHAR(10) | 分组：treatment干预组/control对照组 |
| intervene_date | DATE | 干预生效日（对照组填其配对客户的假想干预日） |

示例数据：

| account_id | grp | intervene_date | health_score |
|------------|-----|----------------|--------------|
| A001 | treatment | 2024-07-15 | 58.00 |
| A003 | treatment | 2024-07-15 | 61.00 |
| A010 | control | 2024-07-15 | 57.50 |
| A012 | control | 2024-07-20 | 60.00 |
| A015 | treatment | 2024-07-25 | 55.00 |

表二：mrr_monthly（客户月度MRR表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| stat_month | DATE | 统计月份（每月1号） |
| mrr | DECIMAL(12,2) | 当月MRR |

示例数据：

| account_id | stat_month | mrr |
|------------|------------|---------|
| A001 | 2024-04-01 | 5000.00 |
| A001 | 2024-10-01 | 6200.00 |
| A010 | 2024-04-01 | 4800.00 |

### 3. 解题思路

先定口径：①前后窗口各取干预日前3个月与干预日后3个完整月（干预当月剔除，避免"半干预"月份污染）；②每客户的前值=窗口内MRR均值（比取单月更稳健），后值同理；③DID=（干预组后均值-前均值）-（对照组后均值-前均值），分子分母都用客户级数据聚合，等价于双向固定效应回归在两期两组下的简化式。解法一用条件聚合在-panel长表上一次算出两组pre/post与DID；解法二先在客户粒度算出每家的delta，再汇总两组——好处是能输出delta分布（中位数、截尾均值），防止个别异常客户拉偏均值。易错点：①对照组也要有"假想干预日"才能时间对齐；②干预当月必须剔除；③客户流失导致post窗口MRR为0要保留（干预失败的代价），不能INNER JOIN掉。**【避坑指南】** 若把post窗口的流失客户INNER JOIN丢弃，干预效果会被系统性高估。

### 4. 参考解法

**解法一：面板长表 + 条件聚合一步DID**

```sql
WITH panel AS (                             -- 步骤1：构建"客户×月份"面板并标记前后期
    SELECT
        e.account_id,
        e.grp,                                          -- treatment / control
        m.stat_month,
        m.mrr,
        CASE
            WHEN m.stat_month <  e.intervene_date
             AND m.stat_month >= e.intervene_date - INTERVAL 3 MONTH
            THEN 'pre'                                  -- 干预前3个月
            WHEN m.stat_month >= e.intervene_date + INTERVAL 1 MONTH
             AND m.stat_month <= e.intervene_date + INTERVAL 3 MONTH
            THEN 'post'                                 -- 干预后3个完整月（干预当月剔除）
        END AS period_flag
    FROM cs_experiment e
    JOIN mrr_monthly m ON m.account_id = e.account_id
    WHERE m.stat_month BETWEEN e.intervene_date - INTERVAL 3 MONTH
                           AND e.intervene_date + INTERVAL 3 MONTH
)
SELECT
    grp,                                                -- 分组
    COUNT(DISTINCT account_id) AS acct_cnt,             -- 组内客户数
    ROUND(AVG(CASE WHEN period_flag = 'pre'  THEN mrr END), 0) AS avg_mrr_pre,
                                                        -- 前期平均MRR
    ROUND(AVG(CASE WHEN period_flag = 'post' THEN mrr END), 0) AS avg_mrr_post,
                                                        -- 后期平均MRR
    ROUND(AVG(CASE WHEN period_flag = 'post' THEN mrr END)
        - AVG(CASE WHEN period_flag = 'pre'  THEN mrr END), 0) AS delta
                                                        -- 组内前后差（一重差分）
FROM panel
GROUP BY grp;
-- DID = treatment行delta - control行delta，可在外层再包一层查询自动相减
```

结果解读：若treatment delta=+400、control delta=+50，则DID=+350元/客户/月，即干预带来的净月收入提升；乘以客户数与12即年化效应，用于和干预人力成本比较ROI。

**解法二：客户级delta先行 + 分布稳健汇总**

```sql
WITH cust_delta AS (                        -- 步骤1：客户粒度的前后差
    SELECT
        e.account_id,
        e.grp,
        AVG(CASE WHEN m.stat_month <  e.intervene_date
                  AND m.stat_month >= e.intervene_date - INTERVAL 3 MONTH
                 THEN m.mrr END) AS mrr_pre,            -- 前3个月均值
        AVG(CASE WHEN m.stat_month >= e.intervene_date + INTERVAL 1 MONTH
                  AND m.stat_month <= e.intervene_date + INTERVAL 3 MONTH
                 THEN m.mrr END) AS mrr_post,           -- 后3个月均值（流失客户为0）
        AVG(CASE WHEN m.stat_month >= e.intervene_date + INTERVAL 1 MONTH
                  AND m.stat_month <= e.intervene_date + INTERVAL 3 MONTH
                 THEN m.mrr END)
      - AVG(CASE WHEN m.stat_month <  e.intervene_date
                  AND m.stat_month >= e.intervene_date - INTERVAL 3 MONTH
                 THEN m.mrr END) AS delta               -- 客户级一重差分
    FROM cs_experiment e
    LEFT JOIN mrr_monthly m ON m.account_id = e.account_id
        AND m.stat_month BETWEEN e.intervene_date - INTERVAL 3 MONTH
                              AND e.intervene_date + INTERVAL 3 MONTH
    GROUP BY e.account_id, e.grp
)
SELECT
    grp,                                                -- 分组
    COUNT(*)                        AS acct_cnt,        -- 客户数（含流失，LEFT JOIN保住）
    ROUND(AVG(delta), 0)            AS mean_delta,      -- 平均delta
    ROUND(SUM(CASE WHEN delta >= 0 THEN 1 ELSE 0 END) / COUNT(*) * 100, 1) AS positive_pct,
                                                        -- delta为正的客户占比（改善面）
    ROUND(SUM(delta), 0)            AS total_delta,     -- 组内总效应（金额口径）
    COUNT(CASE WHEN mrr_post = 0 OR mrr_post IS NULL THEN 1 END) AS churned_cnt
                                                        -- 后窗口流失客户数
FROM cust_delta
GROUP BY grp
ORDER BY grp;
```

结果解读：两组客户级delta并排后，DID=两组mean_delta之差；positive_pct与churned_cnt能揭示效应的构成——若干预组均值提升全靠2家大客户、流失面却更大，结论要谨慎表述为"结构性改善但尾部风险上升"。

> Hive/Spark SQL差异：面板JOIN在客户百万级时，Spark下cs_experiment作广播小表；AVG(CASE WHEN)条件聚合两平台通用；若正式建模可改用Spark的双向固定效应回归（或导出面板给Python做event-study），SQL层负责数据准备。

### 5. 性能分析与优化

两版查询都限定在干预日±3月的窄窗口内扫描mrr_monthly，扫描量=组内客户数×7个月，通常很小；JOIN键account_id走索引即可。优化建议：①mrr_monthly对stat_month分区，查询窗口谓词触发裁剪；②cs_experiment表小（千级），可作Build侧；③若评估多批次干预，把"客户×月份×前后期标记"物化为统一面板表，多批次实验共享；④解法二多一次GROUP BY客户，代价略高于解法一，但输出分布信息更丰富，看板场景建议物化解法二的客户级delta表，DID与分布指标都从它派生。

### 6. 面试延伸考点

- **平行趋势假设是什么？如何用SQL验证？** 回答要点：干预前两组MRR走势应平行；做法是取干预前6个月，按月算两组均值差，检查差值是否稳定（可画pre-period trend图或跑前期差分的t检验）。
- **对照组怎么选才公平？** 回答要点：按健康分、行业、规模、签约时长做匹配（如最近邻匹配）或倾向得分匹配（PSM）；本题为简化DID，至少要剔除明显不可比的客群。
- **干预当月为什么要剔除？** 回答要点：当月只有部分天数被干预、且干预动作本身短期扰动使用行为，混入会稀释效应估计。
- **如果干预组与对照组规模悬殊怎么办？** 回答要点：报告加权DID与分层结果，或对对照组抽样到可比规模；更重要的是检查效应是否在子组间一致（异质性分析）。

### 7. 业务拓展思考

DID结论直接决定CS干预项目的规模化路径：净效应显著为正时，把干预成本（CSM人力/客户）与年化收入效应比较算ROI，再决定扩容到全部高危客户；不显著时先检查执行保真度（干预是否真的落地）再谈放弃。口径可延展为多期event-study（逐月画效应动态，看干预效果是衰减还是累积），或把结果变量从MRR换成活跃席位、工单量、功能采用深度，构建多维证据链；与SAAS-32的预警名单、SAAS-34的采用深度联动后，可形成"识别高危→分组干预→量化效果→迭代策略"的完整客户成功运营闭环。

## SAAS-38 Onboarding漏斗流失节点定位

### 1. 业务背景

PLG（产品驱动增长）模式下，新客户自助注册后的Onboarding完成度直接决定激活率与首续约率。增长团队定义了标准激活漏斗五步：S1注册并完成引导→S2导入业务数据→S3邀请团队成员→S4配置第三方集成→S5完成首次核心业务流程。产品负责人需要知道：每一步的到达率与步间转化率是多少？流失最严重的"卡点"在哪一步？新客户从注册到S5平均要花几天，卡点步骤的耗时是否异常拉长？这些结论决定PM优先优化哪个引导页、CS优先对哪类客户人工介入。**【加分点】** 能同时输出"转化率"与"步间耗时"两个维度，说明候选人理解漏斗不仅有流失还有摩擦。

### 2. 表结构说明

onboarding_events（引导完成事件表，完成某步才有记录，未完成无记录）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| event_id | BIGINT | 事件ID |
| account_id | VARCHAR(32) | 客户账户ID |
| step_code | VARCHAR(5) | 步骤编码：S1~S5 |
| step_name | VARCHAR(50) | 步骤名称 |
| step_order | INT | 步骤顺序号 |
| completed_at | DATETIME | 完成时间 |

示例数据：

| event_id | account_id | step_code | step_name | step_order | completed_at |
|----------|------------|-----------|-----------|------------|---------------------|
| 3001 | C001 | S1 | 注册引导 | 1 | 2024-09-01 10:05:00 |
| 3002 | C001 | S2 | 导入数据 | 2 | 2024-09-02 14:30:00 |
| 3003 | C001 | S3 | 邀请成员 | 3 | 2024-09-02 15:00:00 |
| 3004 | C002 | S1 | 注册引导 | 1 | 2024-09-03 09:00:00 |
| 3005 | C002 | S2 | 导入数据 | 2 | 2024-09-06 11:20:00 |

（C001未完成S4/S5，C002未完成S3~S5，均无对应记录）

### 3. 解题思路

先定口径：①到达率=完成该步的账户数÷进入漏斗（完成S1）的账户数；②步间转化=完成第i+1步的账户数÷完成第i步的账户数（用DISTINCT account_id计数，防止重复事件）；③步间耗时=同一账户完成i+1步与i步的时间差中位数/均值（JOIN相邻步骤取时间对）。实现路径有两条：解法一用条件聚合一次扫描把五步计数横向展开，再用UNION ALL或窗口转成漏斗行；解法二用"逐步LEFT JOIN链"（S1 LEFT JOIN S2 LEFT JOIN ...），天然支持在链条上顺带算每步的完成耗时分布。易错点：①事件表可能存在乱序完成或重复完成事件，计数前要用账户×步骤去重（或取MIN(completed_at)为首次完成）；②到达率与步间转化分母不同，展示时必须标注口径，否则汇报时会被质疑数字对不上；③注册时间跨度要限定观察cohort（如近90天注册账户），防止老账户混入。**【避坑指南】** 不去重直接COUNT(*)会把重复触发事件算成多次到达，漏斗全盘虚高。

### 4. 参考解法

**解法一：条件聚合一次展开 + 窗口算步间转化**

```sql
WITH acct_step AS (                         -- 步骤1：账户×步骤去重，取首次完成时间
    SELECT
        account_id,
        step_code,
        MIN(completed_at) AS first_done     -- 重复完成取首次，保证计数与耗时口径一致
    FROM onboarding_events
    WHERE completed_at >= DATE '2024-07-01' - INTERVAL 90 DAY   -- 观察期内完成的
    GROUP BY account_id, step_code
),
funnel AS (                                 -- 步骤2：条件聚合横向展开五步计数
    SELECT
        COUNT(DISTINCT CASE WHEN step_code = 'S1' THEN account_id END) AS s1_cnt,
        COUNT(DISTINCT CASE WHEN step_code = 'S2' THEN account_id END) AS s2_cnt,
        COUNT(DISTINCT CASE WHEN step_code = 'S3' THEN account_id END) AS s3_cnt,
        COUNT(DISTINCT CASE WHEN step_code = 'S4' THEN account_id END) AS s4_cnt,
        COUNT(DISTINCT CASE WHEN step_code = 'S5' THEN account_id END) AS s5_cnt
    FROM acct_step
),
long_funnel AS (                            -- 步骤3：转成漏斗长表（步骤名+到达数）
    SELECT 'S1 注册引导' AS step, 1 AS step_order, s1_cnt AS reach_cnt FROM funnel
    UNION ALL SELECT 'S2 导入数据', 2, s2_cnt FROM funnel
    UNION ALL SELECT 'S3 邀请成员', 3, s3_cnt FROM funnel
    UNION ALL SELECT 'S4 配置集成', 4, s4_cnt FROM funnel
    UNION ALL SELECT 'S5 首次核心流程', 5, s5_cnt FROM funnel
)
SELECT
    step,                                               -- 步骤名
    reach_cnt,                                          -- 到达账户数
    ROUND(reach_cnt / FIRST_VALUE(reach_cnt) OVER (ORDER BY step_order) * 100, 1)
        AS overall_conv_pct,                            -- 相对S1的整体到达率
    ROUND(reach_cnt / LAG(reach_cnt) OVER (ORDER BY step_order) * 100, 1)
        AS step_conv_pct,                               -- 相对上一步的步间转化率
    FIRST_VALUE(reach_cnt) OVER (ORDER BY step_order) - reach_cnt
        AS lost_from_prev                               -- 相对上一步的流失账户数
FROM long_funnel
ORDER BY step_order;
```

结果解读：若S2→S3步间转化只有48%（其余步骤均在75%以上），"邀请成员"就是头号卡点——协作类SaaS未邀请成员意味着单兵使用、续约风险高，PM应优先重做邀请引导并给CS配置人工陪跑名单。

**解法二：逐步LEFT JOIN链 + 步间耗时分布**

```sql
WITH acct_step AS (                         -- 步骤1：同解法一，账户×步骤首次完成时间
    SELECT account_id, step_code, MIN(completed_at) AS first_done
    FROM onboarding_events
    GROUP BY account_id, step_code
),
s AS (                                      -- 步骤2：把每步拆成独立子查询便于JOIN
    SELECT account_id, first_done AS t1 FROM acct_step WHERE step_code = 'S1'
),
s2 AS (
    SELECT account_id, first_done AS t2 FROM acct_step WHERE step_code = 'S2'
),
s3 AS (
    SELECT account_id, first_done AS t3 FROM acct_step WHERE step_code = 'S3'
),
s4 AS (
    SELECT account_id, first_done AS t4 FROM acct_step WHERE step_code = 'S4'
),
s5 AS (
    SELECT account_id, first_done AS t5 FROM acct_step WHERE step_code = 'S5'
)
SELECT
    COUNT(s.account_id)                                     AS s1_cnt,   -- 完成S1
    COUNT(s2.account_id)                                    AS s2_cnt,   -- 完成S2
    COUNT(s3.account_id)                                    AS s3_cnt,
    COUNT(s4.account_id)                                    AS s4_cnt,
    COUNT(s5.account_id)                                    AS s5_cnt,
    ROUND(AVG(TIMESTAMPDIFF(HOUR, s.t1, s2.t2)), 1)         AS avg_h_1to2,  -- S1→S2平均耗时(小时)
    ROUND(AVG(TIMESTAMPDIFF(HOUR, s2.t2, s3.t3)), 1)        AS avg_h_2to3,  -- S2→S3平均耗时
    ROUND(AVG(TIMESTAMPDIFF(HOUR, s3.t3, s4.t4)), 1)        AS avg_h_3to4,
    ROUND(AVG(TIMESTAMPDIFF(HOUR, s4.t4, s5.t5)), 1)        AS avg_h_4to5,
    ROUND(SUM(CASE WHEN s5.account_id IS NOT NULL THEN 1 ELSE 0 END)
          / COUNT(s.account_id) * 100, 1)                   AS end_to_end_pct  -- 全漏斗完成率
FROM s
LEFT JOIN s2 ON s2.account_id = s.account_id             -- LEFT JOIN链保留只完成部分步骤的账户
LEFT JOIN s3 ON s3.account_id = s2.account_id            -- 顺序链：完成S3必先完成S2
LEFT JOIN s4 ON s4.account_id = s3.account_id
LEFT JOIN s5 ON s5.account_id = s4.account_id;
```

结果解读：若S2→S3平均耗时只有3小时但S3→S4耗时超过5天，说明"配置集成"是高摩擦步骤，转化率低的同时耗时也长，优化收益最大；end_to_end_pct是增长团队对外汇报的北极星指标之一。

> Hive/Spark SQL差异：事件表十亿级时按completed_at分区裁剪；账户×步骤去重可用ROW_NUMBER() OVER (PARTITION BY account_id, step_code ORDER BY completed_at)取rn=1代替MIN；Spark下五个步骤子查询可合并为一次pivot，减少五遍扫描。

### 5. 性能分析与优化

解法一只扫描一次事件表（条件聚合），代价=O(N)加DISTINCT计数成本；解法二的五步子查询在无下推优化时可能扫五遍表，这是最大差异。优化建议：①事件表对(completed_at)分区、(account_id, step_code)建联合索引；②先物化acct_step去重小表（账户×步骤，行数=账户数×平均完成步数，通常百万级以内），两条解法都从它出发，重复扫描被消除；③解法二在MySQL中五个子查询同一表时，优化器可复用物化临时表，但仍建议显式CTE化；④漏斗是高频看板查询，按注册cohort周粒度预计算结果表；⑤若需支持任意步骤组合的漏斗（自助分析），改用Spark的窗口序号法（对账户内事件排序打step序列号再匹配）扩展性更好。

### 6. 面试延伸考点

- **漏斗必须严格有序吗？乱序完成怎么算？** 回答要点：标准漏斗要求有序（完成S5前必先S4）；乱序事件先与业务确认是否允许跳步，允许跳步时用"到达型漏斗"（只数到达不数顺序）。
- **到达率低就是产品问题吗？** 回答要点：可能混入非目标客户注册（学生/竞品调研）、渠道质量差异；应按渠道拆分漏斗后再下结论。
- **如何处理"完成但耗时极长"的账户？** 回答要点：单列超时阈值（如7天未完成S2视为事实流失），把"慢激活"单独分层运营，与"未激活"区别对待。
- **如何验证Onboarding改版有效果？** 回答要点：按注册cohort前后对比或A/B实验，用同口径漏斗指标做DID，防止流量结构变化混杂。

### 7. 业务拓展思考

漏斗定位的卡点应转化为产品与CS的联合动作：S3"邀请成员"卡点可触发自动化邮件与CSM人工邀请话术包，S4"集成"卡点可上线预置模板降低配置成本；整体漏斗完成率可作为PLG团队的季度OKR。口径延展上，可把漏斗与续约数据连接（完成S5的账户首续约率对比未完成者），把"激活"定义为与收入结果强相关的口径而非任意步骤；进一步按行业/规模/来源渠道拆分漏斗，识别哪类客群天然卡在哪一步，把onboarding资源（模板、文档、人工陪跑）按客群定向投放，实现激活率的结构性提升。

## SAAS-39 多产品线交叉持有与NRR关系

### 1. 业务背景

公司从单一CRM产品扩展出工单、BI三条产品线，战略目标是通过交叉销售提升客户粘性与NRR。CEO在战略会上追问：持有多条产品线的客户，其NRR是否显著高于单产品客户？"多持有→更留存"到底是粘性效应还是"好客户本来就什么都买"的选择效应？RevOps需要按客户在期初持有的产品线数量分组，计算各组下一季度的NRR，并补充两条产品线两两组合的交叉矩阵，为交叉销售优先级（先推工单还是先推BI）提供证据。**【面试高频】** 分组必须用期初快照的持有数，若用期末持有数会产生幸存者偏差，NRR对比全部失真。

### 2. 表结构说明

subscriptions（客户×产品线×月度订阅表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| product_line | VARCHAR(30) | 产品线：CRM/工单/BI |
| snapshot_month | DATE | 快照月份（每月1号） |
| mrr | DECIMAL(12,2) | 该产品线当月MRR |
| seats | INT | 该产品线席位数 |

示例数据：

| account_id | product_line | snapshot_month | mrr | seats |
|------------|--------------|----------------|---------|-------|
| A001 | CRM | 2024-01-01 | 5000.00 | 50 |
| A001 | 工单 | 2024-01-01 | 2000.00 | 30 |
| A001 | CRM | 2024-04-01 | 6000.00 | 60 |
| A001 | 工单 | 2024-04-01 | 2500.00 | 35 |
| A002 | CRM | 2024-01-01 | 3000.00 | 20 |

（A002在2024-04-01无任何记录，代表整体流失；A002未持工单/BI）

### 3. 解题思路

第一步定口径：①分组键=期初（2024-01-01）快照中COUNT(DISTINCT product_line)，分单产品/双产品/三产品三组；②各组NRR=期末（2024-04-01）该组客户MRR合计（含已持有各产品线之和，流失客户计0）÷期初该组MRR合计；③补充口径：新购产品线带来的MRR属于扩张，会被自然计入，无需剔除。第二步交叉矩阵：自连接期初快照（a.product_line<b.product_line去重组合），统计每对产品线的共同持有客户数与其NRR。第三步给结论加限定：这是相关性证据，"粘性效应"要靠干预实验（先推某产品线的客户 vs 未推客户）确认。易错点：①SUM MRR时要按账户×产品线聚合到账户级再分组，避免一条订阅行算一次客户数；②期末快照用INNER JOIN会丢掉流失客户；③交叉矩阵要防重复对（CRM+工单 与 工单+CRM）。**【避坑指南】** 用期末持有数分组是本题最经典的错误，面试官常以此判断候选人有没有"幸存者偏差"意识。

### 4. 参考解法

**解法一：期初定组 + LEFT JOIN期末算分组NRR**

```sql
WITH start_side AS (                        -- 步骤1：期初快照聚合到客户级并定组
    SELECT
        account_id,
        SUM(mrr) AS mrr_start,                          -- 期初该客户全部产品线MRR
        CASE
            WHEN COUNT(DISTINCT product_line) = 1 THEN 'A-单产品'
            WHEN COUNT(DISTINCT product_line) = 2 THEN 'B-双产品'
            ELSE 'C-三产品及以上'
        END AS hold_bin                                 -- 按期初持有产品线数分箱
    FROM subscriptions
    WHERE snapshot_month = DATE '2024-01-01'
    GROUP BY account_id
),
end_side AS (                               -- 步骤2：期末快照聚合到客户级
    SELECT
        account_id,
        SUM(mrr) AS mrr_end                             -- 期末全部产品线MRR
    FROM subscriptions
    WHERE snapshot_month = DATE '2024-04-01'
    GROUP BY account_id
)
SELECT
    g.hold_bin,                                         -- 交叉持有分组（期初口径）
    COUNT(*)                       AS cust_cnt,         -- 客户数
    SUM(g.mrr_start)               AS mrr_start,        -- 组内期初MRR
    COALESCE(SUM(e.mrr_end), 0)    AS mrr_end,          -- 组内期末MRR（流失计0）
    ROUND(COALESCE(SUM(e.mrr_end), 0) / SUM(g.mrr_start) * 100, 1) AS nrr_pct,
                                                        -- 组级NRR
    SUM(CASE WHEN e.mrr_end IS NULL THEN 1 ELSE 0 END) AS churned_cnt
                                                        -- 完全流失客户数
FROM start_side g
LEFT JOIN end_side e ON e.account_id = g.account_id     -- LEFT JOIN保住流失客户
GROUP BY g.hold_bin
ORDER BY g.hold_bin;
```

结果解读：若三组NRR分别为105%/118%/128%，与"多持有更留存"一致，可进一步看churned_cnt是否随持有数递减；但要向CEO说明这是相关性，需要交叉销售实验来验证因果。

**解法二：产品线两两组合矩阵（自连接去重对）**

```sql
WITH start_side AS (                        -- 步骤1：期初客户×产品线明细（客户级聚合前置）
    SELECT DISTINCT
        account_id,
        product_line
    FROM subscriptions
    WHERE snapshot_month = DATE '2024-01-01'
      AND mrr > 0                                        -- 有效持有才计入组合
),
pair AS (                                   -- 步骤2：自连接生成两两组合，按字典序去重
    SELECT
        a.account_id,
        a.product_line AS line_a,
        b.product_line AS line_b
    FROM start_side a
    JOIN start_side b
        ON  b.account_id = a.account_id
        AND b.product_line > a.product_line              -- 字典序去重，防(工单,CRM)重复对
),
pair_nrr AS (                               -- 步骤3：每个"客户对组合"的期初/期末MRR
    SELECT
        p.line_a,
        p.line_b,
        COUNT(*)                       AS cust_cnt,      -- 该组合共同持有客户数
        SUM(COALESCE(s0.mrr_sum, 0))   AS mrr_start,     -- 组合客户期初总MRR
        SUM(COALESCE(s1.mrr_sum, 0))   AS mrr_end        -- 组合客户期末总MRR
    FROM pair p
    LEFT JOIN (SELECT account_id, SUM(mrr) AS mrr_sum
               FROM subscriptions
               WHERE snapshot_month = DATE '2024-01-01'
               GROUP BY account_id) s0 ON s0.account_id = p.account_id
    LEFT JOIN (SELECT account_id, SUM(mrr) AS mrr_sum
               FROM subscriptions
               WHERE snapshot_month = DATE '2024-04-01'
               GROUP BY account_id) s1 ON s1.account_id = p.account_id
    GROUP BY p.line_a, p.line_b
)
SELECT
    line_a,                                             -- 产品线A
    line_b,                                             -- 产品线B
    cust_cnt,                                           -- 共同持有客户数
    ROUND(mrr_end / mrr_start * 100, 1) AS nrr_pct,     -- 该组合客户NRR
    mrr_end - mrr_start             AS nrr_delta        -- 净MRR变化额
FROM pair_nrr
ORDER BY cust_cnt DESC;
```

结果解读：若"CRM+BI"组合客户数最少但NRR最高，且"CRM+工单"客户基数大，交叉销售优先级可定为"规模上先做工单渗透、利润上主攻BI"，用矩阵同时回答渗透率与留存质量两个维度。

> Hive/Spark SQL差异：订阅表按月分区时两版查询都只读两个月分区；自连接在Spark下两边都是小结果集（DISTINCT账户×产品线），可broadcast join；Hive中DISTINCT+JOIN可先GROUP BY account_id, product_line压实。产品线数量增长后，pair矩阵改用GROUPING SETS或CTE展开全部组合。

### 5. 性能分析与优化

解法一扫描两个月分区并做两次客户级GROUP BY加一次JOIN，代价与客户数线性相关，索引(subscriptions: snapshot_month, account_id)或分区裁剪即可满足。解法二的自连接在"账户×产品线"去重结果上进行，行数=持有关系数（通常客户数的1.5倍以内），代价可控；但两条对全表MRR的子查询s0/s1各扫一个月分区，与解法一重复。优化建议：①把"客户×月"的MRR合计与持有组合预物化为account_product_month宽表，两版查询都变成小表运算；②自连接前给组合表加(line_a, line_b)索引；③产品线多时组合呈C(n,2)增长，矩阵输出应限制在主流组合或用"持有数分组+Top组合"两级展示；④NRR分母口径（期初有记录且mrr>0）要在文档固化，防止与财务口径打架。

### 6. 面试延伸考点

- **为什么分组必须用期初持有数？** 回答要点：期末持有数会被"流失掉的单产品客户"与"中途加购变多产品"双向扭曲，产生幸存者偏差，把相关性往"多产品更留存"方向高估。
- **如何设计实验验证"粘性效应"而非"选择效应"？** 回答要点：对同质客户随机/准随机分配交叉销售触达（先推工单），对比被触达与未触达客户的NRR做DID；或用倾向得分匹配控制"好客户"混杂。
- **新购产品线的MRR算扩张还是新客收入？** 回答要点：同一账户内加购属扩张，计入NRR分子；独立新账户才是新签。交叉销售的天花板就用NRR里的扩张项衡量。
- **如果交叉持有客户NRR更高但客单也更高，怎么解读？** 回答要点：说明持有数与客户规模混杂，应分组内再按MRR分层或做回归控制，否则结论可能是"大客户效应"。

### 7. 业务拓展思考

交叉持有矩阵是交叉销售路线图（Land & Expand）的核心证据：矩阵中"共同持有少但组合NRR高"的组合是最佳扩张标的，销售团队据此设计捆绑报价与试用策略；矩阵还能反向暴露产品孤岛——某产品线鲜少与CRM共存的客户群，提示集成能力或定位问题。口径延展上，可把持有数换成"功能模块数"细化到产品内部，或跟踪"首次交叉购买"事件后的留存变化（事件研究法），量化每多持有一条产品线带来的留存增量，支撑LTV模型与定价打包（bundle）策略。

## SAAS-40 大客户收入集中度与单点依赖识别

### 1. 业务背景

CFO在准备投资人材料时最怕被问到一个问题："你们最大客户的收入占比是多少？"B端SaaS若Top5客户贡献超过30%收入，或单一客户超过15%，估值会被显著打折（单点依赖风险）。RevOps需要基于生效中的合同ACV计算：①收入集中度曲线（客户按ACV降序的累计占比）；②Top5/Top10占比与HHI（赫芬达尔-希希曼指数，份额平方和，越大越集中）；③单点依赖客户清单（占比≥15%即触发红色预警），供管理层制定大客户分散化与中客户培育策略。**【面试高频】** 累计占比必须用窗口函数（SUM OVER ORDER BY），面试官借此区分"会排序"与"懂分布"的候选人。

### 2. 表结构说明

contracts（客户合同表，取status='生效中'的合同）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | BIGINT | 合同ID |
| account_id | VARCHAR(32) | 客户账户ID |
| account_name | VARCHAR(100) | 客户名称 |
| industry | VARCHAR(30) | 客户行业 |
| acv | DECIMAL(14,2) | 年合同价值 |
| status | VARCHAR(20) | 合同状态：生效中/已到期/已解约 |

示例数据：

| contract_id | account_id | account_name | industry | acv | status |
|-------------|------------|--------------|----------|-----------|--------|
| C2001 | D001 | 华信集团 | 金融 | 3000000.00 | 生效中 |
| C2002 | D002 | 联科科技 | 制造 | 1500000.00 | 生效中 |
| C2003 | D002 | 联科科技 | 制造 | 600000.00 | 生效中 |
| C2004 | D003 | 天润零售 | 零售 | 900000.00 | 生效中 |
| C2005 | D004 | 星澜教育 | 教育 | 200000.00 | 生效中 |

（D002有两份生效合同，客户级ACV需先SUM）

### 3. 解题思路

先定口径：①客户级ACV=该客户所有status='生效中'合同的ACV合计；②集中度指标三件套：Top N占比（Top5、Top10）、HHI=Σ(客户份额²)，份额用小数、HHI取0~10000分制便于汇报；③单点依赖阈值=任一客户份额≥15%标记红色。实现路径：解法一用ROW_NUMBER排名+SUM OVER窗口累计占比，一条查询输出集中度曲线明细；解法二用CROSS JOIN总表（或窗口取总额）算份额，再做平方和聚合得HHI，并用条件聚合输出Top5/Top10与红色预警客户数，适合直接落汇报看板。易错点：①客户有多份合同必须先聚合到客户级再排名，否则同一客户占两个名次；②HHI必须在份额归一（除以总额）后再平方求和，忘记归一会得到天文数字；③超大客户名单展示要脱敏（投资人材料场景）。**【加分点】** 能补充"按行业拆分HHI"提示集中度可能被单一行业系统性放大。

### 4. 参考解法

**解法一：排名 + 窗口累计占比（集中度曲线）**

```sql
WITH acct_acv AS (                          -- 步骤1：合同聚合到客户级
    SELECT
        account_id,
        SUM(acv) AS acv_sum                             -- 客户级生效合同ACV合计
    FROM contracts
    WHERE status = '生效中'
    GROUP BY account_id
),
ranked AS (                                 -- 步骤2：排名与累计占比
    SELECT
        account_id,
        acv_sum,
        ROW_NUMBER() OVER (ORDER BY acv_sum DESC) AS rnk,   -- 按ACV降序排名
        SUM(acv_sum) OVER (ORDER BY acv_sum DESC
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_acv,
                                            -- 累计ACV（必须用ROWS框架防同值并列重复）
        SUM(acv_sum) OVER ()              AS total_acv    -- 全体客户ACV总额
    FROM acct_acv
)
SELECT
    rnk,                                                -- 收入排名
    account_id,                                         -- 客户ID
    acv_sum,                                            -- 客户ACV
    ROUND(acv_sum / total_acv * 100, 2)  AS share_pct,  -- 单客占比
    ROUND(cum_acv / total_acv * 100, 2)  AS cum_share_pct,  -- 累计占比（集中度曲线）
    CASE
        WHEN acv_sum / total_acv >= 0.15 THEN '红色-单点依赖'
        WHEN acv_sum / total_acv >= 0.05 THEN '黄色-重点观察'
        ELSE ''
    END AS risk_flag                                    -- 风险分级
FROM ranked
ORDER BY rnk
LIMIT 20;                                               -- 展示Top20即可看清曲线头部
```

结果解读：若Top1占比18%（红色）、Top5累计41%，CFO需在投资人材料中主动披露分散化计划；集中度曲线前10%客户贡献超过70%，说明中腰部客户培育是下一阶段增长重点。

**解法二：份额平方聚合算HHI + Top N条件聚合（汇报口径）**

```sql
WITH acct_acv AS (                          -- 步骤1：客户级ACV
    SELECT account_id, SUM(acv) AS acv_sum
    FROM contracts
    WHERE status = '生效中'
    GROUP BY account_id
),
total AS (                                  -- 步骤2：总额（供CROSS JOIN归一）
    SELECT SUM(acv_sum) AS total_acv FROM acct_acv
),
share AS (                                  -- 步骤3：客户份额
    SELECT
        a.account_id,
        a.acv_sum,
        a.acv_sum / t.total_acv AS share               -- 归一化份额（0~1）
    FROM acct_acv a
    CROSS JOIN total t
),
ranked AS (                                 -- 步骤4：排名用于Top N判定
    SELECT account_id, acv_sum, share,
           ROW_NUMBER() OVER (ORDER BY acv_sum DESC) AS rnk
    FROM share
)
SELECT
    ROUND(SUM(share * share) * 10000, 0)            AS hhi_score,
                                            -- HHI = Σ份额²，万分制（美国司法部口径参考）
    ROUND(SUM(CASE WHEN rnk <= 5  THEN share ELSE 0 END) * 100, 1) AS top5_share_pct,
                                            -- Top5占比
    ROUND(SUM(CASE WHEN rnk <= 10 THEN share ELSE 0 END) * 100, 1) AS top10_share_pct,
                                            -- Top10占比
    SUM(CASE WHEN share >= 0.15 THEN 1 ELSE 0 END)  AS red_flag_cnt,
                                            -- 单点依赖（≥15%）客户数
    COUNT(*)                                        AS active_acct_cnt,
    ROUND(1 / NULLIF(SUM(share * share), 0), 0)     AS effective_accounts
                                            -- 等效客户数=1/HHI(小数制)，直观表达"相当于几个客户撑着"
FROM ranked;
```

结果解读：若HHI=620、等效客户数≈16，即公司收入实际只相当于16个等量客户在支撑，抗风险弱；Top5=41%配合红色客户1家，可推导出"未来两年把Top5压到30%以下"的量化目标。

> Hive/Spark SQL差异：合同表百万行以下两版都是轻查询；集团多实体场景按entity_id分区后CROSS JOIN总额仍可broadcast；HHI这类全局聚合在Hive中只有一个Reducer，可先在Spark中按account_id分桶聚合份额再求平方和；窗口累计在Hive中同样支持SUM OVER ORDER BY，但注意Hive 2.x对ROWS框架的兼容性。

### 5. 性能分析与优化

两版主体都是"合同表过滤聚合→客户级小表→窗口/聚合"，扫描量=生效合同行数，通常几十万级，代价极低。风险点与优化：①窗口SUM OVER ORDER BY需要一次全局排序，客户数百万级时注意排序内存，可先按acv_sum建索引或分桶；②解法二的CROSS JOIN total是把一行总额广播到每行，代价可忽略，但若写成子查询标量出现在SELECT里且表很大，部分旧版本优化器会重复计算，应显式物化total；③集中度是月度汇报指标，建议把acct_acv与ranked结果物化入仓，看板直接读；④若要历史趋势（HHI逐月变化），改为按snapshot_month循环或用窗口PARTITION BY月份一次算出，避免12次查询；⑤展示层务必做客户名脱敏与权限隔离。

### 6. 面试延伸考点

- **HHI和Top N占比哪个更好？各适用什么场景？** 回答要点：Top N直观但对排名边界敏感（第5、6名互换影响大）；HHI利用全分布信息、对尾部敏感，适合做监管/投资口径；汇报用Top N、分析用HHI，等效客户数（1/HHI）是很好的转译。
- **份额应该按ACV还是按确认收入算？** 回答要点：ACV前瞻、反映签约结构；确认收入反映当期实际；集中度风险通常看未来12个月可确认收入，两者都可算并交叉验证。
- **如何降低集中度？SQL层面还能提供什么证据？** 回答要点：定位高集中行业/渠道（按industry拆份额）、识别"可复制大客户画像"的中客户候选名单（与Top1画像相似但ACV中等），支撑培育策略。
- **大客户流失对集中度指标的冲击如何预警？** 回答要点：把SAAS-32的流失预警信号与份额≥10%的客户做交集，触发大客户健康度专属看板。

### 7. 业务拓展思考

集中度分析不应止于风险披露：等效客户数与HHI趋势可写进公司OKR，倒逼销售结构从"大客户依赖"转向"金字塔结构"；按行业拆分的份额矩阵能发现"金融客户占60%"这类行业集中风险，与宏观经济敏感性叠加评估。联动销售侧，可对Top20客户设置高管赞助（Executive Sponsor）机制与专属CS；对Top1依赖客户，合同续约提前量（SAAS-45）与流失预警双通道监控。口径延展上，可计算"剔除最大客户后的NRR与增速"——投资人常问"去掉最大客户你还增长吗"，这条口径是估值对话中的关键弹药。
## SAAS-41 API调用量异动客户识别（流失或扩张信号）

### 1. 业务背景

API优先的SaaS产品（数据服务/开放平台类）中，客户的API调用量是最实时、最难造假的"用脚投票"指标：调用量骤降往往领先于流失决策，而持续倍增则是扩大配额、升级套餐的扩张信号。平台运营团队每天要产出一份"异动客户名单"，分"骤降-流失风险"与"骤增-扩张商机"两个方向，分别推送给CS团队（挽回）与销售团队（扩容报价）。单日环比噪声太大（周末效应、批处理周期），必须用"近7日日均 vs 前7日日均"的双段均值对比来定义异动，并叠加绝对量门槛过滤长尾小客户。**【加分点】** 能说明为什么用双段均值而非单日环比，体现对信号噪声的工程理解。

### 2. 表结构说明

api_daily（客户×日期API调用量表，由网关日志ETL而来）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| account_id | VARCHAR(32) | 客户账户ID |
| call_date | DATE | 调用日期 |
| call_cnt | BIGINT | 当日API调用次数 |
| success_rate | DECIMAL(5,4) | 当日调用成功率 |

示例数据：

| account_id | call_date | call_cnt | success_rate |
|------------|------------|----------|--------------|
| E001 | 2024-09-24 | 520000 | 0.9980 |
| E001 | 2024-09-25 | 480000 | 0.9975 |
| E001 | 2024-10-01 | 90000 | 0.9800 |
| E002 | 2024-09-24 | 120000 | 0.9990 |
| E002 | 2024-10-01 | 950000 | 0.9995 |

（E001调用量走低疑似流失信号，E002近期调用量跳升疑似扩张信号）

### 3. 解题思路

先定口径：①基期=观察日前第8~14天（前7日）、当期=观察日前6天至当天（近7日），各算日均，剔除未满7天数据的新客（快照天数不足直接排除，防误报）；②异动定义：骤降=近7日日均≤前7日日均×50%且前7日日均≥1000（有意义的基数）；骤增=近7日日均≥前7日日均×250%且近7日日均≥10000（绝对量门槛防小客户噪声）；③输出观察日快照名单并保留两个方向的日均数值供人工复核。实现路径两条：解法一用窗口AVG的ROWS框架一次算出双段均值，扫表一遍；解法二用两次自连接区间聚合（观察日往前取7天、再取第8~14天）在GROUP BY中求均值，兼容不支持窗口的旧引擎。易错点：①窗口框架必须用ROWS而不是RANGE，RANGE会按值并列扩展窗口；②缺数日期（客户当天零调用也可能没有日志行）会造成7日均值的分母不齐，严格做法要日历补零；③新客户无前7日数据时avg_prev_7d为NULL，比值判断要显式排除。**【避坑指南】** 用RANGE BETWEEN 6 PRECEDING时日期缺行会把窗口扩到9~10天，双段均值全部失真。

### 4. 参考解法

**解法一：窗口ROWS双段均值（一遍扫描）**

```sql
WITH daily AS (                             -- 步骤1：观察期内的日调用明细
    SELECT account_id, call_date, call_cnt
    FROM api_daily
    WHERE call_date BETWEEN DATE '2024-09-18' AND DATE '2024-10-01'
                                            -- 覆盖前7日+近7日共14天
),
roll AS (                                   -- 步骤2：窗口计算双段均值
    SELECT
        account_id,
        call_date,
        call_cnt,
        AVG(call_cnt) OVER (
            PARTITION BY account_id ORDER BY call_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)   AS avg_7d,
                                            -- 近7日均值（含当天）
        AVG(call_cnt) OVER (
            PARTITION BY account_id ORDER BY call_date
            ROWS BETWEEN 13 PRECEDING AND 7 PRECEDING)  AS avg_prev_7d,
                                            -- 前7日均值（往前第7~13天）
        COUNT(call_cnt) OVER (
            PARTITION BY account_id ORDER BY call_date
            ROWS BETWEEN 13 PRECEDING AND 7 PRECEDING)  AS prev_days_cnt
                                            -- 前7日实有天数，校验窗口完整性
    FROM daily
),
snap AS (                                   -- 步骤3：截取观察日快照
    SELECT *
    FROM roll
    WHERE call_date = DATE '2024-10-01'
)
SELECT
    account_id,                                         -- 异动客户
    ROUND(avg_prev_7d, 0) AS avg_prev_7d,               -- 前7日日均
    ROUND(avg_7d, 0)      AS avg_7d,                    -- 近7日日均
    ROUND(avg_7d / NULLIF(avg_prev_7d, 0), 2) AS ratio, -- 变动倍数
    CASE
        WHEN avg_prev_7d >= 1000
         AND avg_7d <= avg_prev_7d * 0.5
            THEN '骤降-流失风险'                        -- 方向一：基数足够且腰斩
        WHEN avg_7d >= 10000
         AND avg_7d >= avg_prev_7d * 2.5
            THEN '骤增-扩张商机'                        -- 方向二：绝对量过阈且倍增
        ELSE NULL
    END AS signal_type                                  -- 异动方向标签
FROM snap
WHERE prev_days_cnt = 7                                 -- 前7日数据完整，排除新客/缺数客户
  AND (
        (avg_prev_7d >= 1000 AND avg_7d <= avg_prev_7d * 0.5)
     OR (avg_7d >= 10000 AND avg_7d >= avg_prev_7d * 2.5)
  );                                                    -- 只保留触发双方向阈值之一者
```

结果解读：名单按方向分两栏推送——"骤降-流失风险"给CS按流失预警流程处置（优先核对是否客户侧迁移了调用），"骤增-扩张商机"给销售评估配额扩容与套餐升级报价；ratio列供复核人员判断信号强度。

**解法二：双区间自连接聚合（兼容无窗口引擎）**

```sql
WITH obs AS (                               -- 步骤1：观察日清单（此处取单日，可扩展多日）
    SELECT DISTINCT account_id, call_date
    FROM api_daily
    WHERE call_date = DATE '2024-10-01'
),
agg AS (                                    -- 步骤2：自连接区间聚合双段均值
    SELECT
        o.account_id,
        o.call_date,
        AVG(CASE WHEN d.call_date >  o.call_date - INTERVAL 7 DAY
                 THEN d.call_cnt END)              AS avg_7d,
                                            -- 近7日：观察日前6天至当天
        AVG(CASE WHEN d.call_date <= o.call_date - INTERVAL 7 DAY
                  AND d.call_date >  o.call_date - INTERVAL 14 DAY
                 THEN d.call_cnt END)              AS avg_prev_7d,
                                            -- 前7日：往前第7~13天
        COUNT(CASE WHEN d.call_date <= o.call_date - INTERVAL 7 DAY
                   AND d.call_date >  o.call_date - INTERVAL 14 DAY
                   THEN 1 END)                     AS prev_days_cnt
                                            -- 前7日实有天数，校验窗口完整性
    FROM obs o
    JOIN api_daily d
        ON  d.account_id = o.account_id
        AND d.call_date >  o.call_date - INTERVAL 14 DAY  -- 一次JOIN覆盖14天
        AND d.call_date <= o.call_date
    GROUP BY o.account_id, o.call_date
)
SELECT
    account_id,
    ROUND(avg_prev_7d, 0) AS avg_prev_7d,
    ROUND(avg_7d, 0)      AS avg_7d,
    ROUND(avg_7d / NULLIF(avg_prev_7d, 0), 2) AS ratio,
    CASE
        WHEN avg_prev_7d >= 1000 AND avg_7d <= avg_prev_7d * 0.5
            THEN '骤降-流失风险'
        WHEN avg_7d >= 10000 AND avg_7d >= avg_prev_7d * 2.5
            THEN '骤增-扩张商机'
        ELSE NULL
    END AS signal_type
FROM agg
WHERE prev_days_cnt = 7                                 -- 前7日数据完整，排除新客/缺数客户
  AND (
        (avg_prev_7d >= 1000 AND avg_7d <= avg_prev_7d * 0.5)
     OR (avg_7d >= 10000 AND avg_7d >= avg_prev_7d * 2.5)
  );
```

结果解读：解法二与解法一结果等价；其优势是每个客户只聚合一次、无全局排序，在Redshift/旧Hive等引擎上更稳；劣势是14天区间的JOIN扇出为14倍行数，观察日增多时扫描量线性放大。

> Hive/Spark SQL差异：api_daily是平台最大的事实表之一（日增数亿行），必须按call_date分区裁剪只读14天；窗口版在Spark中按account_id重分区排序，客户数千万级时建议预分桶；Hive的AVG窗口用ROWS框架需1.2+版本；若日历缺行严重，先与日历维表LEFT JOIN补零再开窗。

### 5. 性能分析与优化

解法一全流程=一次14天分区扫描+窗口双AVG（同一窗口规范只排一次序），代价约为O(N log N)（N=14天×活跃客户数）；解法二JOIN扇出14倍再GROUP BY，代价≈14N的聚合输入，但在无窗口引擎上反而更优。优化建议：①api_daily按call_date分区是硬前提，查询永远显式给日期范围；②日粒度明细先ETL成"客户×日"预聚合表（若源头是网关日志明细，绝不在查询层扫原始日志）；③异动检测是每日例行任务，把roll层物化为"客户×日双段均值"表，名单查询退化为单日过滤；④阈值参数（0.5/2.5/绝对门槛）外置成配置表，便于A/B调参；⑤对反复异动的客户做"信号冷却期"（30天内不重复推送），减少CS团队的名单疲劳。

### 6. 面试延伸考点

- **为什么用双段7日均值而不是单日环比或周环比？** 回答要点：单日环比受周末与批处理周期影响噪声大；双段7日均值对齐星期效应、平滑突发，同时保留一周粒度的时效性。
- **客户当天零调用但表里没有行，窗口会怎样？** 回答要点：ROWS框架按行数计数会"借用"更早的数据，均值被高估；规范做法是与日历维表LEFT JOIN补零，保证每客户每天一行。
- **骤增一定是商机吗？如何排伪？** 回答要点：可能是爬虫、重试风暴（success_rate下降可佐证）、客户内部跑批迁移；要结合成功率、调用端IP多样性、配额水位联合判断。
- **如何验证调用量骤降对流失的预测力？** 回答要点：回溯历史，统计"触发骤降信号后60/90天内实际流失率"对比未触发组，算提升度（lift），并优化阈值使F1最大化。

### 7. 业务拓展思考

API异动名单是把"产品使用遥测"变成增长与挽留两个业务引擎的入口：骤降名单接入CS流失干预流程（SAAS-32双信号可与之取交集提高精度），骤增名单接入销售PQA商机池并自动预估扩容报价（按调用量弹性映射席位数）。口径可延展为"调用量基线模型"（按客户自身的周周期拟合基线、用残差检测异动，替代固定阈值），或分接口权重（核心接口调用权重更高）；长期看，调用量、席位活跃（SAAS-43）、功能广度（SAAS-34）三路信号融合成客户健康分，是SaaS客户成功平台的标准架构。

## SAAS-42 年度合同月摊销MRR波动归因

### 1. 业务背景

SaaS公司大量签年度合同（先收钱、按月确认MRR），财务与业务两侧都需要一张"月度摊销MRR"报表：每份年合同把total_value按合同月数平均摊到覆盖的每个自然月。CFO发现2024年6月MRR环比突然下跌4%，要求数据团队把波动归因拆开：是新签不足（新增摊销贡献减少）、到期未续（老合同摊销退出）、还是续约降价（续约合同比上期低）？归因结论决定管理层动作——签单端提速、续约挽留加码，还是定价复盘。**【面试高频】** 区间展开（合同×月份）是本题的核心技能：把"一段合同"转成"逐月多行"再聚合，同时归因必须以"上月存在、本月是否存在"的合同集合差分来拆分新增与退出。

### 2. 表结构说明

contracts（合同表，含起止日期与类型）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| contract_id | BIGINT | 合同ID |
| account_id | VARCHAR(32) | 客户账户ID |
| start_date | DATE | 合同起始日 |
| end_date | DATE | 合同结束日（含当月摊销） |
| total_value | DECIMAL(14,2) | 合同总金额 |
| deal_type | VARCHAR(20) | 合同类型：新签/续约 |

示例数据：

| contract_id | account_id | start_date | end_date | total_value | deal_type |
|-------------|------------|------------|----------|-------------|-----------|
| C3001 | F001 | 2024-01-10 | 2024-12-31 | 120000.00 | 新签 |
| C3002 | F002 | 2023-07-01 | 2024-06-30 | 96000.00 | 新签 |
| C3003 | F002 | 2024-07-01 | 2025-06-30 | 72000.00 | 续约 |
| C3004 | F003 | 2023-10-15 | 2024-09-30 | 60000.00 | 新签 |
| C3005 | F004 | 2024-06-01 | 2025-05-31 | 96000.00 | 新签 |

（C3003续约金额低于C3002，即典型的"续约降价"场景；C3002到期后若未续约则为流失退出）

### 3. 解题思路

先定口径：①月摊销额=total_value÷合同覆盖月数，月数用PERIOD_DIFF(年月(end), 年月(start))+1计算（不足整月按整月近似，口径与财务对齐即可）；②某月的摊销MRR=该月覆盖的所有合同摊销额之和，"覆盖"判定用"月首落在[start_date, end_date]内"；③波动归因：本月摊销MRR-上月摊销MRR=本月新进入合同的摊销贡献-本月退出的合同的上月摊销贡献（存续合同摊销额固定、贡献为零），新进入按deal_type拆成"新签贡献/续约贡献"。实现路径：解法一用递归CTE生成月骨架再JOIN合同区间，一条查询展开全年；解法二用实体日历维表+区间重叠条件JOIN，并用LAG做逐月差分与归因分类。易错点：①归因比较的是"合同集合"而非"金额表"逐行相减，必须按合同ID对齐两月；②到期合同当月仍要摊销（end_date当月计入），否则退出月会被重复计损；③续约合同若是新contract_id，按"上月消失+本月出现"会同时记退出与进入，这正是需要的口径（退出按老合同、进入按新合同）。**【避坑指南】** 区间JOIN条件写成"月首≥start且月首≤end"时，end在月中也会整月计入，须与财务确认是整月摊还是按天比例摊。

### 4. 参考解法

**解法一：递归CTE月骨架 + 区间展开聚合**

```sql
WITH RECURSIVE months AS (                  -- 步骤1：递归生成2024年月序列骨架
    SELECT DATE '2024-01-01' AS month_start
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH
    FROM months
    WHERE month_start < DATE '2024-12-01'   -- 递归到12月为止（12个月，安全上限内）
),
spread AS (                                 -- 步骤2：合同×月份区间展开
    SELECT
        m.month_start,
        c.contract_id,
        c.deal_type,
        c.total_value / (
            PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM c.end_date),
                        EXTRACT(YEAR_MONTH FROM c.start_date)) + 1
        ) AS monthly_mrr                    -- 月摊销额 = 总金额 ÷ 覆盖月数（含首尾月）
    FROM contracts c
    JOIN months m
        ON m.month_start BETWEEN DATE_FORMAT(c.start_date, '%Y-%m-01')
                              AND DATE_FORMAT(c.end_date, '%Y-%m-01')
                                            -- 月首落在合同区间内即视为该月覆盖
)
SELECT
    month_start,                                        -- 自然月
    ROUND(SUM(monthly_mrr), 0)                      AS amortized_mrr,
                                                    -- 该月摊销MRR合计
    ROUND(SUM(CASE WHEN deal_type = '新签' THEN monthly_mrr ELSE 0 END), 0) AS from_new,
                                                    -- 其中新签合同摊销贡献
    ROUND(SUM(CASE WHEN deal_type = '续约' THEN monthly_mrr ELSE 0 END), 0) AS from_renewal
                                                    -- 其中续约合同摊销贡献
FROM spread
GROUP BY month_start
ORDER BY month_start;
```

结果解读：输出全年逐月摊销MRR曲线，能直观看到6月下滑的总量与结构（新签vs续约占比变化）；下一步用解法二做严格的逐月归因差分。

**解法二：日历维表 + LAG逐月集合差分归因**

```sql
WITH spread AS (                            -- 步骤1：同解法一展开为"月×合同"明细
    SELECT
        m.month_start,
        c.contract_id,
        c.deal_type,
        c.total_value / (
            PERIOD_DIFF(EXTRACT(YEAR_MONTH FROM c.end_date),
                        EXTRACT(YEAR_MONTH FROM c.start_date)) + 1
        ) AS monthly_mrr
    FROM contracts c
    JOIN dim_month m                        -- 实体日历维表（ETL维护的月序列）
        ON m.month_start BETWEEN DATE_FORMAT(c.start_date, '%Y-%m-01')
                              AND DATE_FORMAT(c.end_date, '%Y-%m-01')
),
monthly AS (                                -- 步骤2：月度汇总
    SELECT
        month_start,
        SUM(monthly_mrr) AS total_mrr
    FROM spread
    GROUP BY month_start
),
joined AS (                                 -- 步骤3：逐月对比（LAG取上月总量）
    SELECT
        month_start,
        total_mrr,
        LAG(total_mrr) OVER (ORDER BY month_start) AS prev_mrr
    FROM monthly
),
attr_in AS (                                -- 步骤4a：新进入合同贡献（本月有、上月无）
    SELECT
        cur.month_start,
        SUM(cur.monthly_mrr) AS in_flow     -- 本月新出现的合同（新签进入或续约换约进入）
    FROM spread cur
    LEFT JOIN spread prev
        ON  prev.contract_id = cur.contract_id
        AND prev.month_start = cur.month_start - INTERVAL 1 MONTH
    WHERE prev.contract_id IS NULL          -- 上月不存在 => 本月新进入
    GROUP BY cur.month_start
),
attr_out AS (                               -- 步骤4b：退出合同损失（上月有、本月无）
    SELECT
        prev.month_start + INTERVAL 1 MONTH AS month_start,
                                            -- 退出损失归属到"消失"的那个月
        SUM(prev.monthly_mrr) AS out_flow   -- 上月还在摊、本月消失的合同摊销额
    FROM spread prev
    LEFT JOIN spread cur
        ON  cur.contract_id = prev.contract_id
        AND cur.month_start = prev.month_start + INTERVAL 1 MONTH
    WHERE cur.contract_id IS NULL           -- 本月不存在 => 合同退出（到期未续/解约）
    GROUP BY prev.month_start + INTERVAL 1 MONTH
)
SELECT
    j.month_start,                                  -- 月份
    ROUND(j.total_mrr, 0)          AS mrr_now,      -- 本月摊销MRR
    ROUND(j.prev_mrr, 0)           AS mrr_prev,     -- 上月摊销MRR
    ROUND(j.total_mrr - j.prev_mrr, 0) AS net_delta,-- 净变动
    ROUND(COALESCE(a.in_flow, 0), 0)  AS new_in_flow,  -- 新增贡献（新签+续约进入）
    ROUND(COALESCE(o.out_flow, 0), 0) AS churn_out,    -- 退出损失（到期未续/解约）
    ROUND((j.total_mrr - j.prev_mrr)
          - (COALESCE(a.in_flow, 0) - COALESCE(o.out_flow, 0)), 0) AS residual
                                                    -- 残差=存续合同摊销变化（应为0，非0说明有中途改单）
FROM joined j
LEFT JOIN attr_in  a ON a.month_start = j.month_start
LEFT JOIN attr_out o ON o.month_start = j.month_start
ORDER BY j.month_start;
```

结果解读：6月净变动若为-40万，其中out_flow=-52万（C3002等合同到期退出）、in_flow=+12万，即"到期未续为主因"，管理层动作应指向续约挽留与到期前90天启动续约（联动SAAS-45）；residual列长期非零则提示计费系统有中途改单未走合同流程。

> Hive/Spark SQL差异：递归CTE在Hive中不可用，月骨架必须用实体dim_month维表或sequence/generate_series（Spark 2.4+支持explode(sequence(...)))；区间JOIN在合同百万级时为非等值JOIN，Spark下需开启broadcast nested loop前先按年过滤压缩右表；建议ETL层固化"月×合同摊销"宽表，查询层只做归因聚合。

### 5. 性能分析与优化

两版主体都是"合同×月"展开：合同1万条×12月=12万行的小计算，真正要防的是合同量达到百万级、跨多年摊销时展开行数膨胀（百万×36=3600万）。优化建议：①展开前先按观察年过滤合同区间（end_date≥年初 AND start_date≤年末），把无关合同挡在JOIN之前；②dim_month维表小（几十行），任何引擎都可broadcast；③归因差分需要对spread表自JOIN一次（按contract_id+相邻月），先把spread物化为临时表避免重复展开；④"月×合同摊销"是经典的快照型事实表，建议每日/每月增量落入数仓，报表查询不再展开区间；⑤合同中途改单（金额变更）应生成新版本行（SCD2），否则residual无法解释。

### 6. 面试延伸考点

- **按月均摊和按天比例摊哪个对？** 回答要点：财务确认收入常按天比例（或直线法），业务报表常用整月均摊；关键是与财务对账口径写进文档，两套数字并行时明确各自用途。
- **归因里的"退出"如何进一步拆成到期未续/提前解约/降级？** 回答要点：给退出合同关联终止原因字段与后续合同匹配（同账户90天内新签视为续接），拆分可控流失与非可控流失。
- **为什么存续合同对环比波动贡献为零？** 回答要点：均摊口径下存续合同每月摊销额恒定，只有合同集合的进出才改变总量；若按天摊或按阶梯摊则存续合同也会贡献变化。
- **如何从该表推导"未来12个月已锁定MRR"？** 回答要点：对未到期合同的剩余月份摊销求和即合同负债侧的可视MRR，是预测基线，叠加管线加权（SAAS-35）即成收入预测。

### 7. 业务拓展思考

摊销MRR归因表把财务口径的收入波动翻译成业务语言：新签贡献弱→市场与SDR提效；续约进入低于退出→续约价格与挽留问题；提前解约突出→产品或服务危机。归因可继续下钻到客户分层与销售区域，形成"哪块板漏水"的精确打击；与SAAS-45的续约窗口分析联动，可验证"提前90天启动续约是否减少退出"。口径延展上，可加"合同负债（递延收入）余额"曲线观察现金流与确认收入的剪刀差，或按deal_type拆新签里多少来自老客户加购（扩张型新签），把NRR（SAAS-31）与摊销MRR两套口径接成完整的收入故事线。

## SAAS-43 席位使用率分箱与增购概率

### 1. 业务背景

销售运营与定价团队发现：席位型SaaS的增购（Upsell）几乎都发生在使用率高位区间——当客户活跃用户数逼近购买席位数时，管理员才会发起加购；而使用率长期低于40%的客户增购概率极低、甚至有降级风险。CS与销售需要一个量化分箱：把客户按当月席位使用率（活跃用户÷购买席位）分成四箱，统计各箱次月的增购率，验证"使用率驱动增购"的假设并定出触发线（如使用率≥90%进入自动加购提醒流程）。该结论还直接用于定价实验：能否在客户触顶时推送按需弹性席位包。**【面试高频】** 分箱统计的口径要在"账户×月"面板上做前瞻对齐（本月分箱、次月观察增购），任何同期对齐都会引入反向因果。

| 4105 | G006 | 2024-09-12 | +15 | +4000.00 |

### 3. 解题思路

先定口径：①使用率=active_users÷seats_purchased（seats_purchased为0的试用客户剔除）；②分箱：<40%记A、40%~70%记B、70%~90%记C、≥90%记D，边界来自业务经验（90%是管理员"挤着用"的心理阈值）；③增购=次月（9月）发生delta_seats>0的增购事件；④各箱增购率=发生增购的客户数÷该箱客户数，同时输出平均MRR增量衡量商机质量。实现路径：解法一以8月面板为分箱基表、增购月名单做LEFT JOIN，条件聚合输出；解法二完全用窗口LEAD在面板内完成"次月席位是否增加"的判定，不需要JOIN事件表（席位变化本身就是增购的痕迹），并可顺带输出月度转移矩阵（8月箱→9月箱的使用率迁移）。易错点：①8月已触顶且9月才增购的客户，9月使用率反而下降，若用9月分箱会错分到低箱；②LEAD判定"席位增加"要对比次月与本月seats_purchased，防止降级客户误判；③同月多次增购去重。**【加分点】** 提出用使用率转移矩阵检验分箱稳定性，是面板数据思维的体现。

### 4. 参考解法

**解法一：分箱基表 + 增购名单LEFT JOIN（JOIN法）**

```sql
WITH base AS (                              -- 步骤1：8月面板计算使用率
    SELECT
        account_id,
        seats_purchased,
        active_users,
        ROUND(active_users / NULLIF(seats_purchased, 0), 4) AS util_rate
                                            -- 使用率，NULLIF防试用客户除零
    FROM license_monthly
    WHERE stat_month = DATE '2024-08-01'
      AND seats_purchased > 0               -- 剔除0席位试用客户
),
binned AS (                                 -- 步骤2：使用率分箱
    SELECT
        account_id,
        CASE
            WHEN util_rate < 0.40 THEN 'A-低于40%'
            WHEN util_rate < 0.70 THEN 'B-40%至70%'
            WHEN util_rate < 0.90 THEN 'C-70%至90%'
            ELSE 'D-90%及以上'
        END AS util_bin,
        util_rate
    FROM base
),
ups AS (                                    -- 步骤3：次月增购客户名单（去重）
    SELECT DISTINCT account_id
    FROM upsell_events
    WHERE delta_seats > 0                   -- 只算加购，剔除减席位的调整
      AND upsell_date BETWEEN DATE '2024-09-01' AND DATE '2024-09-30'
)
SELECT
    b.util_bin,                                         -- 使用率分箱（8月口径）
    COUNT(*)                     AS acct_cnt,           -- 该箱客户数
    COUNT(u.account_id)          AS upsold_cnt,         -- 次月发生增购的客户数
    ROUND(COUNT(u.account_id) / COUNT(*) * 100, 1) AS upsell_rate_pct,
                                                        -- 分箱增购率
    ROUND(AVG(b.util_rate) * 100, 1) AS avg_util_pct    -- 该箱平均使用率（校验分箱质量）
FROM binned b
LEFT JOIN ups u ON u.account_id = b.account_id          -- LEFT JOIN保留未增购客户
GROUP BY b.util_bin
ORDER BY b.util_bin;
```

结果解读：若四箱增购率为3%/8%/22%/38%，单调且D箱是A箱的12倍，"触顶驱动加购"假设成立，可把"使用率≥90%"设为自动加购提醒与CS跟进的触发线。

**解法二：LEAD前瞻窗口 + 使用率转移矩阵（窗口法）**

```sql
WITH panel AS (                             -- 步骤1：面板排序并取次月状态
    SELECT
        account_id,
        stat_month,
        seats_purchased,
        ROUND(active_users / NULLIF(seats_purchased, 0), 4) AS util_rate,
        LEAD(seats_purchased) OVER (        -- 次月购买席位数，用于判定是否发生增购
            PARTITION BY account_id ORDER BY stat_month) AS seats_next,
        LEAD(ROUND(active_users / NULLIF(seats_purchased, 0), 4)) OVER (
            PARTITION BY account_id ORDER BY stat_month) AS util_next
                                            -- 次月使用率，用于转移矩阵
    FROM license_monthly
    WHERE seats_purchased > 0
),
aug AS (                                    -- 步骤2：截取8月行为分箱基期
    SELECT
        account_id,
        seats_purchased,                    -- 基期席位数（与次月对比判增购）
        seats_next,
        util_next,
        CASE
            WHEN util_rate < 0.40 THEN 'A-低于40%'
            WHEN util_rate < 0.70 THEN 'B-40%至70%'
            WHEN util_rate < 0.90 THEN 'C-70%至90%'
            ELSE 'D-90%及以上'
        END AS util_bin,
        CASE
            WHEN util_next IS NULL THEN 'E-次月流失'    -- 次月无面板行=客户消失
            WHEN util_next < 0.40 THEN 'A-低于40%'
            WHEN util_next < 0.70 THEN 'B-40%至70%'
            WHEN util_next < 0.90 THEN 'C-70%至90%'
            ELSE 'D-90%及以上'
        END AS util_bin_next
    FROM panel
    WHERE stat_month = DATE '2024-08-01'
)
SELECT
    util_bin,                                           -- 8月使用率分箱
    COUNT(*)                                        AS acct_cnt,
    SUM(CASE WHEN seats_next > seats_purchased THEN 1 ELSE 0 END) AS upsold_cnt,
                                            -- 次月席位数大于本月 => 发生增购
    ROUND(SUM(CASE WHEN seats_next > seats_purchased THEN 1 ELSE 0 END)
          / COUNT(*) * 100, 1)                      AS upsell_rate_pct,
                                            -- 分箱增购率（前瞻口径）
    SUM(CASE WHEN util_next IS NULL THEN 1 ELSE 0 END) AS churned_cnt
                                            -- 次月消失的客户数（分箱流失对照）
FROM aug
GROUP BY util_bin
ORDER BY util_bin;
-- 将GROUP BY改为 util_bin, util_bin_next 并做二维交叉计数，即得"8月箱→9月箱"使用率转移矩阵
```

结果解读：窗口版不依赖事件表（适合事件埋点缺失的场景，席位变动即增购痕迹）；把util_bin×util_bin_next做完整交叉聚合即得转移矩阵——若D箱次月大多仍在D箱，说明触顶是持续状态、加购意愿真实，若D箱大量掉到A箱，则触顶是脉冲式假象。

> Hive/Spark SQL差异：面板表亿级行时按stat_month分区裁剪；LEAD窗口在Spark下按account_id重分区，客户数千万级建议先分桶；MySQL中窗口无排序索引时会产生文件排序，大面板建议在ETL层物化util_rate列与次月快照。

### 5. 性能分析与优化

解法一=基期单月过滤（分区裁剪）+增购月名单聚合+一次JOIN，都是小结果集，代价最低；解法二需对整个面板开窗（所有月份参与排序），代价是全面板排序O(N log N)，明显更高。优化建议：①license_monthly对(account_id, stat_month)建联合索引，窗口输入接近索引序；②把"次月席位与使用率"用窗口物化进面板宽表（ETL每日追加），查询层不再开窗；③增购名单可从upsell_events换成"月度席位差分"，避免埋点缺失；④分箱边界做成参数表，支持定价实验里做敏感性分析；⑤若扩展到"触顶后N个月内增购"的生存分析口径，建议预计算每客户首次触顶月与首次增购月的间隔表。

### 6. 面试延伸考点

- **为什么分箱用8月、增购观察9月？同期对齐会怎样？** 回答要点：同期对齐会引入反向因果（增购后席位变大、使用率被动走低被错分到低箱），前瞻对齐才能解释"使用率→增购"的先后关系。
- **分箱边界如何定更科学？** 回答要点：先看使用率分布（NTILE五等分）与增购率的单调区间，再归并成业务可执行的整数边界；边界要配合产品触发动作的粒度。
- **使用率高也可能是不健康（席位买多了用不满），如何区分？** 回答要点：区分"触顶型高使用率"（活跃≈购买，增购信号）与"萎缩型低使用率"（活跃绝对值下滑，流失信号），结合SAAS-32的连续下滑信号交叉判断。
- **增购率高的箱位一定该推弹性席位包吗？** 回答要点：还要看客单与毛利结构、弹性包对年费客户的收入平滑影响，用实验验证 elasticity 再全量。

### 7. 业务拓展思考

分箱结论可直接产品化为"触顶自动提醒"：使用率≥90%时向管理员推送加购引导、向CS推送跟进任务，把被动等续约变成主动经营；对长期<40%的箱位则反向启动"席位瘦身"挽留方案（降配保客），避免到期一次性流失。口径延展上，可把席位换成存储量/API配额/报表张数等资源型指标通用化该框架；与SAAS-34功能广度、SAAS-41调用量信号加权成健康分后，可构建"增购概率×客户价值"的二维商机矩阵，指导销售按优先级分配资源，并用增购事件的转化率回测持续迭代分箱边界。

## SAAS-44 账户多联系人激活广度与续约

### 1. 业务背景

协作型SaaS的调研结论是：激活广度（一个客户账户内有多少比例的注册用户真正活跃）比单点深度使用更能预测续约——只有一两个人在用的账户，关键员工一离职客户就流失。CS团队要为续约评审会准备账户级"激活广度"报表：统计每个客户近30天的活跃用户数、激活广度（活跃÷注册）、管理员是否活跃三个指标，并按广度分箱对比续约率，验证"广度驱动续约"，同时产出"广度低但即将续约"的干预名单。**【面试高频】** 激活广度的分母（注册用户）是慢变字段，分子（近30天活跃）是时变字段，两层聚合的结构是本题的SQL核心；管理员活跃作为单独维度是B端SaaS特有的口径。

### 2. 表结构说明

### 3. 解题思路

先定口径：①用户级"近30天活跃"=在续约日前30天内有活跃日志；②账户级激活广度=近30天活跃用户数÷账户在职用户数（status='在职'，剔除已删除用户防止广度被虚低）；③管理员活跃=账户内任一在职admin在近30天活跃；④按广度分箱（0~25%、25%~50%、50%~75%、75%~100%）对比续约率。实现路径：解法一是经典三层聚合——用户层标记活跃→账户层聚合广度与管理员标志→分箱关联续约结果；解法二用窗口函数在"用户×活跃标记"的行集上直接PARTITION BY account_id完成COUNT聚合，把三层压成两层，并顺带输出活跃用户数与管理员数的明细列便于核对。易错点：①活跃日志要按user_id DISTINCT后再对账户计数，一日多次会话不能重复计人；②LEFT JOIN活跃日志时未活跃用户的COUNT会变NULL，要用COUNT(DISTINCT CASE WHEN ... THEN user_id END)显式计数；③分母必须过滤status='在职'，否则离职员工的注册记录拉低广度制造假信号。**【避坑指南】** 直接用总注册数做分母会让"人员流失型客户"看起来广度极低，混淆"没人用"与"人走了"两类问题。

### 4. 参考解法

**解法一：三层聚合（用户层→账户层→分箱层）**

```sql
WITH user_flag AS (                         -- 步骤1：用户级近30天活跃标记
    SELECT
        u.user_id,
        u.account_id,
        u.role,
        CASE WHEN a.user_id IS NOT NULL THEN 1 ELSE 0 END AS is_active_30d
                                            -- 续约前30天内有活跃日志记为1
    FROM users u
    LEFT JOIN (
        SELECT DISTINCT user_id             -- 日志去重：一人一天只算一次
        FROM user_active_log
        WHERE active_date BETWEEN DATE '2024-10-01' AND DATE '2024-10-30'
    ) a ON a.user_id = u.user_id
    WHERE u.status = '在职'                 -- 分母只含在职用户
),
acct_breadth AS (                           -- 步骤2：账户级聚合广度与管理员标志
    SELECT
        account_id,
        COUNT(*)                          AS active_user_cnt,   -- 在职用户总数
        SUM(is_active_30d)                AS active_cnt,        -- 近30天活跃数
        SUM(is_active_30d) / COUNT(*)     AS breadth_rate,      -- 激活广度
        MAX(CASE WHEN role = 'admin' AND is_active_30d = 1
                 THEN 1 ELSE 0 END)       AS admin_active_flag  -- 管理员是否活跃
    FROM user_flag
    GROUP BY account_id
),
binned AS (                                 -- 步骤3：广度分箱
    SELECT
        account_id,
        admin_active_flag,
        CASE
            WHEN breadth_rate <= 0.25 THEN 'A-0%至25%'
            WHEN breadth_rate <= 0.50 THEN 'B-25%至50%'
            WHEN breadth_rate <= 0.75 THEN 'C-50%至75%'
            ELSE 'D-75%至100%'
        END AS breadth_bin
    FROM acct_breadth
)
SELECT
    b.breadth_bin,                                      -- 激活广度分箱
    COUNT(*)                     AS acct_cnt,           -- 账户数
    SUM(b.admin_active_flag)     AS admin_active_cnt,   -- 管理员活跃的账户数
    ROUND(AVG(r.is_renewed) * 100, 1) AS renew_rate_pct,-- 分箱续约率
    ROUND(AVG(r.acv), 0)         AS avg_acv             -- 平均续约金额
FROM binned b
JOIN renewals r ON r.account_id = b.account_id          -- 关联续约结果
GROUP BY b.breadth_bin
ORDER BY b.breadth_bin;
```

结果解读：若D箱续约率92%、A箱仅38%，且管理员不活跃的账户续约率再低15个百分点，则"广度+管理员活跃"双口径成立，CS应优先对"低广度+管理员不活跃+临近续约"账户做培训与高层沟通。

**解法二：窗口函数两层压缩 + 明细核对列**

```sql
WITH joined AS (                            -- 步骤1：用户×活跃标记的行集
    SELECT
        u.account_id,
        u.user_id,
        u.role,
        CASE WHEN a.user_id IS NOT NULL THEN 1 ELSE 0 END AS is_active_30d
    FROM users u
    LEFT JOIN (
        SELECT DISTINCT user_id
        FROM user_active_log
        WHERE active_date BETWEEN DATE '2024-10-01' AND DATE '2024-10-30'
    ) a ON a.user_id = u.user_id
    WHERE u.status = '在职'
),
acct AS (                                   -- 步骤2：窗口一次算出账户级多列
    SELECT DISTINCT
        account_id,
        COUNT(*) OVER (PARTITION BY account_id)                     AS active_user_cnt,
        SUM(is_active_30d) OVER (PARTITION BY account_id)           AS active_cnt,
        SUM(CASE WHEN role = 'admin' AND is_active_30d = 1
                 THEN 1 ELSE 0 END) OVER (PARTITION BY account_id)  AS admin_active_cnt
                                            -- 账户内活跃管理员数
    FROM joined
)
SELECT
    CASE
        WHEN a.active_cnt / a.active_user_cnt <= 0.25 THEN 'A-0%至25%'
        WHEN a.active_cnt / a.active_user_cnt <= 0.50 THEN 'B-25%至50%'
        WHEN a.active_cnt / a.active_user_cnt <= 0.75 THEN 'C-50%至75%'
        ELSE 'D-75%至100%'
    END AS breadth_bin,                                 -- 激活广度分箱
    COUNT(*)                                        AS acct_cnt,
    SUM(CASE WHEN a.admin_active_cnt > 0 THEN 1 ELSE 0 END) AS admin_active_cnt,
    ROUND(AVG(r.is_renewed) * 100, 1)               AS renew_rate_pct,
    MIN(a.active_cnt)                               AS min_active_users,
                                            -- 该箱最小活跃用户数（核对离群账户）
    MAX(a.active_cnt)                               AS max_active_users
FROM acct a
JOIN renewals r ON r.account_id = a.account_id
GROUP BY breadth_bin
ORDER BY breadth_bin;
```

结果解读：窗口版把"用户层标记"与"账户层聚合"合并在一个行集上完成，列出的min/max活跃用户数便于发现"超大账户拉高箱均值"的问题；工程上与解法一等价，选择取决于团队SQL风格与可维护性。

> Hive/Spark SQL差异：活跃日志是最大的表（日活千万×365天），必须按active_date分区裁剪只读30天；users×日志去重JOIN后COUNT(DISTINCT)在Hive会退化单Reducer，先对(user_id, active_date)去重可规避；Spark下建议对user_active_log按user_id分桶，与users维表JOIN免Shuffle。

### 5. 性能分析与优化

两版成本主体都在活跃日志的30天分区扫描与去重JOIN：日志若为年累计百亿行，30天窗口也有百亿分之一量级（数亿行），去重DISTINCT是关键成本。优化建议：①预聚合"用户×日活跃"为"用户×月活跃"位图表（或bitmap/roaring bitmap），账户级广度变成位图与运算，彻底摆脱大JOIN；②users维表对status过滤先行，缩小JOIN右表；③JOIN键user_id两表都建索引/分桶；④续约评审名单是周任务，把acct_breadth物化并追加历史快照，还能顺带输出广度的逐月趋势（广度下滑也是流失信号，可与SAAS-32合并进健康分）；⑤解法二的DISTINCT account_id去重是窗口聚合后的必要步骤，别忘了它，否则账户会按用户数重复输出。

### 6. 面试延伸考点

- **激活广度的分母用注册数还是席位数？** 回答要点：席位数对应付费口径、注册数对应真实人口；扩容销售场景用"活跃÷购买席位"（SAAS-43），续约风险场景用"活跃÷在职注册"，两个口径用途不同要并行。
- **管理员活跃为什么单列？** 回答要点：管理员掌握配置、账号开通与续约决策链，其流失往往是组织级流失的前兆；也可扩展为"决策人活跃"。
- **广度低就一定该干预吗？** 回答要点：要区分客群——设计部门3人小团队天然广度低但黏性高；应分客群建基线，对比同规模账户的相对广度而非绝对值。
- **如何把广度做成时序指标？** 回答要点：按月物化账户广度快照，输出广度的环比变化与连续下滑标记，融入流失预警（SAAS-32）与健康分模型。

### 7. 业务拓展思考

激活广度是"账户级PLG"的核心运营抓手：低广度+临近续约名单触发CSM启动多人培训、部门推广计划与管理员沟通；高广度账户则是增购（SAAS-43）与NPS调研的优质池。产品侧可依据卡点设计"邀请激励"（邀请成员解锁功能）拉升广度；销售侧在续约谈判时用广度数据讲故事（"贵司120人注册仅15人活跃，价值未兑现"）既是风险披露也是扩容铺垫。口径延展上可引入"关键角色广度"（财务、IT、业务三类角色分别的活跃覆盖），或用协同网络分析识别"单点依赖账户"（活跃集中在一人），把人因风险量化进客户健康分。

## SAAS-45 合同到期续约窗口与赢单率时间关系

### 1. 业务背景

续约是SaaS收入的基本盘，但续约商机"什么时候启动"差异极大：到期前90天启动给足技术评估与预算周期，临期30天才启动则容易因客户流程走不完而丢单或被迫延期。销售运营需要回答：续约商机从创建到合同到期日的"提前期"分窗后（≤30/31-60/61-90/>90天），各窗的赢单率、平均成交周期、以及"赢单但签约日晚于到期日"（服务断档）的占比各是多少？结论将固化为续约SOP——提前多少天必须创建续约商机，并对迟到商机设置自动升级告警。**【面试高频】** 提前期=DATEDIFF(到期日, 商机创建日)，分窗后必须只统计已关单商机，否则赢单率分母被在途商机稀释。

### 2. 表结构说明

renewal_opps（续约商机表）

| 字段名 | 类型 | 含义 |
|--------|------|------|
| opp_id | BIGINT | 商机ID |
| account_id | VARCHAR(32) | 客户账户ID |
| contract_end_date | DATE | 原合同到期日 |
| opp_created_date | DATE | 续约商机创建日 |
| close_date | DATE | 关单日期（未关单为NULL） |
| is_won | TINYINT | 关单结果：1赢单/0输单（未关单为NULL） |
| amount | DECIMAL(12,2) | 续约金额 |

示例数据：

| opp_id | account_id | contract_end_date | opp_created_date | close_date | is_won | amount |
|--------|------------|-------------------|------------------|------------|--------|---------|
| 9001 | J001 | 2024-12-31 | 2024-10-02 | 2024-12-20 | 1 | 120000.00 |
| 9002 | J002 | 2024-12-31 | 2024-12-15 | NULL | NULL | 80000.00 |
| 9003 | J003 | 2024-11-30 | 2024-09-01 | 2024-11-15 | 1 | 96000.00 |
| 9004 | J004 | 2024-11-30 | 2024-11-10 | 2024-12-25 | 1 | 60000.00 |
| 9005 | J005 | 2024-10-31 | 2024-08-15 | 2024-10-20 | 0 | 45000.00 |

（9004赢单但签约晚于到期日，即服务断档案例；9002在途不进赢单率分母）

### 3. 解题思路

先定口径：①提前期=DATEDIFF(contract_end_date, opp_created_date)，负值表示商机创建时合同已到期（红线案例，单独成窗）；②只分析close_date非空的已关单商机，赢单率=SUM(is_won)÷COUNT(*)；③平均成交周期=AVG(DATEDIFF(close_date, opp_created_date))且只对赢单商机算；④断档率=赢单且close_date>contract_end_date的商机÷赢单商机，衡量交付连续性风险。实现路径：解法一在内层派生表算提前期，外层CASE分窗后条件聚合一次输出全部指标；解法二用NTILE(4)按提前期分位对比胜率（免除人为边界），并用窗口SUM OVER按提前期排序输出"累计赢单率曲线"，回答"提前期越长胜率是否单调越高"的趋势问题。易错点：①未关单商机必须剔除，但要汇报其占比（在途占比过高说明管道健康度差）；②分窗边界要覆盖负提前期（临期后启动）；③赢单周期与输单周期分开统计，混算会拉低均值误导SOP。**【避坑指南】** 忘记过滤未关单商机，赢单率被在途商机摊薄，四个窗口的数字全部失真。

### 4. 参考解法

**解法一：提前期分窗 + 条件聚合（SOP口径）**

```sql
SELECT
    CASE
        WHEN lead_days <  0  THEN '0-过期后启动'        -- 商机创建晚于到期日，红线案例
        WHEN lead_days <= 30 THEN '1-临期30天内启动'
        WHEN lead_days <= 60 THEN '2-31至60天启动'
        WHEN lead_days <= 90 THEN '3-61至90天启动'
        ELSE '4-90天以上启动'
    END AS lead_bin,                                    -- 提前期分窗
    COUNT(*)                                        AS closed_cnt,
                                                    -- 已关单商机数（分母）
    SUM(is_won)                                     AS won_cnt,
    ROUND(AVG(is_won) * 100, 1)                     AS win_rate_pct,
                                                    -- 窗口赢单率
    ROUND(AVG(CASE WHEN is_won = 1
                   THEN DATEDIFF(close_date, opp_created_date) END), 0) AS avg_cycle_won,
                                                    -- 赢单商机平均成交周期（天）
    ROUND(SUM(CASE WHEN is_won = 1 AND close_date > contract_end_date
                   THEN 1 ELSE 0 END)
          / NULLIF(SUM(is_won), 0) * 100, 1)        AS service_gap_pct,
                                                    -- 赢单但晚于到期日的断档占比
    SUM(CASE WHEN is_won = 1 THEN amount ELSE 0 END) AS won_amount
                                                    -- 窗口赢单金额
FROM (
    SELECT
        opp_id, contract_end_date, opp_created_date, close_date, is_won, amount,
        DATEDIFF(contract_end_date, opp_created_date) AS lead_days
                                                    -- 提前期=到期日-商机创建日
    FROM renewal_opps
    WHERE close_date IS NOT NULL                    -- 只统计已关单商机
      AND is_won IS NOT NULL
) t
GROUP BY lead_bin
ORDER BY lead_bin;
```

结果解读：若四窗赢单率依次为55%/72%/86%/91%、断档率集中在"临期30天"窗（赢单也大多晚于到期日），即可把"到期前60天必须创建续约商机"写入SOP，并对临期窗商机设自动升级。

**解法二：NTILE分位 + 累计赢单率曲线（趋势口径）**

```sql
WITH closed AS (                            -- 步骤1：已关单商机与提前期
    SELECT
        opp_id, amount, is_won,
        DATEDIFF(contract_end_date, opp_created_date) AS lead_days
    FROM renewal_opps
    WHERE close_date IS NOT NULL AND is_won IS NOT NULL
),
quantiled AS (                              -- 步骤2：按提前期分四分位
    SELECT
        lead_days,
        is_won,
        NTILE(4) OVER (ORDER BY lead_days) AS lead_quartile
                                            -- 提前期短的排前，Q1=最临期启动
    FROM closed
),
quartile_stat AS (                          -- 步骤3：分位胜率对比
    SELECT
        CONCAT('Q', lead_quartile) AS quartile,
        MIN(lead_days)             AS min_lead_days,    -- 该分位提前期下界
        MAX(lead_days)             AS max_lead_days,    -- 上界
        COUNT(*)                   AS cnt,
        ROUND(AVG(is_won) * 100, 1) AS win_rate_pct
    FROM quantiled
    GROUP BY lead_quartile
)
SELECT quartile, min_lead_days, max_lead_days, cnt, win_rate_pct
FROM quartile_stat
ORDER BY min_lead_days;

-- 累计赢单率曲线（趋势口径）：按提前期逐笔累计，回答"越早启动是否越稳赢"
WITH closed AS (
    SELECT
        DATEDIFF(contract_end_date, opp_created_date) AS lead_days,
        is_won
    FROM renewal_opps
    WHERE close_date IS NOT NULL AND is_won IS NOT NULL
)
SELECT
    lead_days,                                          -- 提前期（天）
    ROUND(SUM(is_won) OVER (ORDER BY lead_days
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
        / COUNT(*) OVER (ORDER BY lead_days
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) * 100, 1)
        AS cum_win_rate_pct                             -- 到该提前期为止的累计赢单率
FROM closed
ORDER BY lead_days;
```

结果解读：NTILE版免除人为分窗边界，若Q1（最晚启动）胜率系统性低于Q4且分位边界（如Q1≤45天）清晰，可直接反推SOP阈值；累计曲线若呈单调上升，说明"越早启动越接近稳赢"，若中段反而凹陷，则提示过早启动的商机容易被搁置，需要中途激活机制。

> Hive/Spark SQL差异：商机表十万级为小表；DATEDIFF在Hive中参数顺序为datediff(end, start)且只支持日期字符串，注意与MySQL的参数序差异；NTILE与累计窗口在Spark通用；若商机与合同分表存储，先按account_id+到期月做派生对齐再算提前期，避免JOIN扇出。

### 5. 性能分析与优化

两版都是单表过滤+窗口/GROUP BY，扫描量=已关单商机数，代价极低；窗口NTILE与SUM OVER各需一次按lead_days的全排序，可合并窗口规范减少排序次数。优化建议：①renewal_opps对(close_date, contract_end_date)建联合索引，过滤已关单+年份直接走索引；②提前期字段建议ETL时物化成列（lead_days），查询层免函数计算且便于索引与分窗统计；③赢单率趋势是月度经营指标，把分窗统计物化入看板；④若要扩展到"提前期×客户规模×区域"多维分析，预聚合按维度上卷，避免多维GROUP BY重复扫描；⑤在途商机监控（close_date IS NULL且距到期<30天）单独做成告警查询，是SOP落地的执行抓手。

### 6. 面试延伸考点

- **为什么赢单率分母只含已关单商机？在途商机怎么处理？** 回答要点：在途商机结果未知，混入分母会摊薄赢单率；应单独监控在途占比与老化（创建超90天未关单），必要时用快照回测修正。
- **提前期长赢单率就一定高吗？会不会有混杂？** 回答要点：存在选择效应——健康客户续约被动提前启动；可按客户健康分分层对比，或比较"同一客户不同年度的启动时间变化"控制客户因素。
- **断档率（赢单但晚于到期）为什么重要？** 回答要点：服务断档触发合同间隙的法律与收入确认问题，也伤害客户体验；它是"启动太晚"的直接代价，比输单更隐蔽。
- **如何把结论固化为流程？** 回答要点：按分位边界设定"到期前N天未创建商机即告警"，并用A/B验证SOP上线后分窗赢单率与断档率的改善。

### 7. 业务拓展思考

续约窗口分析是续约SOP的数据底座：把"提前90天自动创建续约商机、60天健康检查、30天未关单升级"固化为系统自动流转，能把赢单率与断档率同时改善；分窗数据还可与续约折扣挂钩——临期启动的商机往往被迫用大折扣换时间，提前启动则保住价格。联动SAAS-42的摊销MRR，续约断档会直接表现为下月MRR的退出缺口，形成财务可感知的风险传导链；口径延展上，可引入"续约周期vs原合同周期""续约金额保持率"，与NRR（SAAS-31）互补，最终构成"续约启动-过程-结果-财务影响"的完整续约漏斗仪表盘。
