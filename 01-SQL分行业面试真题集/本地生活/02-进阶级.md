## LL-16 新客首单补贴ROI：补贴成本与次日留存

### 1. 业务背景

外卖平台拉新团队每月投入千万级预算对新客首单进行补贴（新客立减、首单红包）。市场负责人在月度复盘中要回答：花在新客首单上的每一元补贴，换回了多少"次日仍愿意再下单"的有效新客？分析师需要按渠道、按城市汇总新客首单的补贴总成本，并追踪这批新客在次日（T+1 自然日）是否再次完成订单，计算"次日留存GMV ÷ 补贴成本"作为补贴ROI的核心口径。该结论直接决定下个月各渠道的预算分配：ROI 高的渠道加大投放，ROI 低的渠道收缩。用户产生首单与复购订单，商家提供供给，骑手履约质量（超时、洒漏）会间接压低次日留存，平台则在链路中支付补贴。

### 2. 表结构说明

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 下单用户ID |
| channel_id | INT | 拉新渠道ID（101应用商店/102信息流/103地推） |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单实付金额（用户实际支付） |
| subsidy_amount | DECIMAL(10,2) | 平台补贴金额（平台承担部分） |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（5行）：

| order_id | user_id | channel_id | pay_time | order_amount | subsidy_amount | status |
|----------|---------|------------|----------|--------------|----------------|--------|
| 10001 | 5001 | 101 | 2026-09-01 11:23:00 | 35.80 | 8.00 | completed |
| 10002 | 5002 | 102 | 2026-09-01 12:05:00 | 28.00 | 8.00 | completed |
| 10003 | 5003 | 101 | 2026-09-03 18:40:00 | 52.30 | 10.00 | canceled |
| 10004 | 5004 | 103 | 2026-09-05 09:12:00 | 19.90 | 6.00 | completed |
| 10005 | 5001 | 101 | 2026-09-02 12:10:00 | 30.00 | 0.00 | completed |

### 3. 解题思路

先钉死三个口径边界。①首单定义：以该用户**最早一笔"已完成"订单的支付时间**为准，不能轻信 is_new_user_order 类标记字段（可能被刷单污染或状态回刷）；取消单未产生真实履约，不计入首单，其补贴也未真实消耗。②次日留存定义：首单支付日为 D，在 D+1 自然日（当日 00:00 至 23:59:59）内再次出现已完成订单即记为留存，注意是"自然日"而非"严格满24小时"，两种口径会让结果差出几个百分点，面试时要先声明。③ROI = 次日留存用户产生的GMV ÷ 首单补贴总成本，分母只算平台承担的补贴。实现路径：先 CTE 圈出每个用户的首单（用户×最早完成支付时间），再判断次日是否存在复购订单，最后按渠道聚合。**【避坑指南】** 判断次日复购时若直接对 pay_time 包 DATE 函数比较，会导致索引失效，应改写成 pay_time 的左闭右开区间。

### 4. 参考解法

解法一：CTE 圈定首单 + EXISTS 判定次日复购（可读性好，逻辑直白）。

```sql
WITH first_orders AS (            -- 第一步：圈定每位用户的真实新客首单
    SELECT o.user_id,
           o.channel_id,                                -- 首单所在渠道（归因口径）
           DATE(o.pay_time)      AS first_pay_date,     -- 首单支付自然日 D
           o.subsidy_amount      AS subsidy,            -- 首单平台补贴
           o.order_amount        AS first_gmv           -- 首单GMV
    FROM orders o
    JOIN (SELECT user_id, MIN(pay_time) AS min_pay      -- 每用户最早完成支付时间
          FROM orders
          WHERE status = 'completed'                    -- 只认完成单，取消单不算首单
          GROUP BY user_id) f
      ON o.user_id = f.user_id                          -- 回关联取首单明细行
     AND o.pay_time  = f.min_pay
),
next_day_flag AS (                -- 第二步：逐个首单用户判断 T+1 是否复购
    SELECT fo.*,
           CASE WHEN EXISTS (       -- EXISTS 短路扫描，命中一行即返回
               SELECT 1 FROM orders o2
               WHERE o2.user_id = fo.user_id
                 AND o2.status = 'completed'
                 AND o2.pay_time >= fo.first_pay_date + INTERVAL 1 DAY  -- D+1 00:00
                 AND o2.pay_time <  fo.first_pay_date + INTERVAL 2 DAY  -- D+2 00:00，左闭右开
           ) THEN 1 ELSE 0 END      AS is_retained        -- 次日留存标记
    FROM first_orders fo
)
SELECT channel_id                                      AS 渠道ID,
       COUNT(*)                                        AS 新客首单数,
       ROUND(SUM(subsidy), 2)                          AS 补贴总成本,
       SUM(is_retained)                                AS 次日留存人数,
       ROUND(SUM(is_retained) / COUNT(*), 4)           AS 次日留存率,
       ROUND(SUM(CASE WHEN is_retained = 1
                      THEN first_gmv END)
             / NULLIF(SUM(subsidy), 0), 2)             AS 补贴ROI   -- 除零保护
FROM next_day_flag
GROUP BY channel_id;
```

结果解读：ROI 大于 1 说明次日留存订单的 GMV 已覆盖该渠道补贴成本，可继续放量；ROI 明显低于其他渠道的（如地推）往往混入羊毛党，应收缩预算并叠加反作弊标记。

解法二：窗口函数一次扫描法（MIN 窗口取首单时间，聚合到人，免自连接）。

```sql
WITH user_orders AS (             -- 第一步：窗口并行求出每个用户的最早完成支付时间
    SELECT user_id, channel_id, pay_time, subsidy_amount, order_amount, status,
           MIN(CASE WHEN status = 'completed' THEN pay_time END)
               OVER (PARTITION BY user_id)              AS first_pay_time  -- 按用户分组求最小完成支付时间
    FROM orders
),
user_tag AS (                     -- 第二步：按用户聚合出渠道、补贴、次日行为
    SELECT user_id,
           MAX(CASE WHEN pay_time = first_pay_time
                    THEN channel_id END)               AS channel_id,     -- 只取首单行的渠道
           MAX(CASE WHEN pay_time = first_pay_time
                    THEN subsidy_amount END)           AS subsidy,        -- 只取首单行的补贴
           SUM(CASE WHEN status = 'completed'
                     AND DATE(pay_time) = DATE(first_pay_time) + INTERVAL 1 DAY
                    THEN order_amount ELSE 0 END)      AS next_day_gmv,   -- 次日复购订单GMV合计
           MAX(CASE WHEN status = 'completed'
                     AND DATE(pay_time) = DATE(first_pay_time) + INTERVAL 1 DAY
                    THEN 1 ELSE 0 END)                 AS retained        -- 次日是否留存
    FROM user_orders
    WHERE first_pay_time IS NOT NULL                   -- 剔除从未有过完成单的用户
    GROUP BY user_id                                   -- 一行 = 一个新客
)
SELECT channel_id                        AS 渠道ID,
       COUNT(*)                          AS 新客数,
       ROUND(SUM(subsidy), 2)            AS 补贴总成本,
       ROUND(AVG(retained), 4)           AS 次日留存率,
       ROUND(SUM(next_day_gmv)
             / NULLIF(SUM(subsidy), 0), 2) AS 补贴ROI
FROM user_tag
GROUP BY channel_id;
```

结果解读：窗口方案把"找首单"和"判次日"压缩进用户分区的一次排序扫描，用户量越大相对自连接越划算；两法结果一致时可交叉验证口径无误。

### 5. 性能分析与优化

解法一的代价集中在两处：内层 GROUP BY 全量聚合（约一次哈希聚合），以及 EXISTS 触发的半连接探测（若 orders 上有 (user_id, status, pay_time) 复合索引则每用户为一次索引下探，代价 O(N·logN)；没有索引则可能退化为逐行扫描，风险最大）。解法二需要按 user_id 做一次窗口排序（O(N·logN)），但全程单表单次扫描，无回表与二次关联，大数据量下通常更优。可执行优化：①为 orders 建 (user_id, status, pay_time) 复合索引，同时服务首单聚合与 EXISTS 探测；②渠道分析先按 channel_id 分区或预过滤缩小扫描面；③若为常态化月报，可把"用户首单表"落成日更中间表，查询时只对增量计算；④ROI 类比率在展示层保留成本明细，避免 round 掩盖除零异常。

### 6. 面试延伸考点

- **如果口径改成7日留存，SQL怎么改？** 要点：把次日区间条件改为 `pay_time BETWEEN first + INTERVAL 1 DAY AND first + INTERVAL 8 DAY`；若要输出 D1~D7 留存矩阵，工程上常用"日期偏移 = DATEDIFF(复购日, 首单日)"打标后按偏移天数透视。
- **羊毛党会怎么扭曲ROI，如何在SQL层先做识别？** 要点：同设备/同收货地址多账号、首单后长期沉默、补贴金额占比异常高；可先用规则标记黑名单（如自连接同地址多首单），再从分母剔除。
- **ROI分母要不要包含商家承担的补贴？** 要点：平台视角只计平台补贴，商家视角或行业视角需叠加商家承担部分；先明确决策方视角，再定口径，避免汇报时数字打架。

### 7. 业务拓展思考

补贴ROI不应只看次日，可延展为 D1/D7/D30 留存曲线下的"新客生命周期GMV"，用 LTV/CAC 视角替代单日ROI，评估补贴的真实回收周期。结论可直接联动运营动作：对高ROI渠道追加预算并复制素材，对低ROI渠道改用"留资立减"等后置激励；对次日未留存的新客，可在 T+1 午餐时段定向推无门槛券做二次唤起。口径延展上，还可按商圈/品类拆分ROI，识别"补贴敏感型供给"（如茶饮奶茶类新客复购快），把补贴从全量撒网改为品类定向。

## LL-17 商家月动销率统计：在营商家中有订单的占比

### 1. 业务背景

城市BD（商务拓展）团队每月按商圈考核商家健康度，核心指标是商家动销率：当月有已完成订单的在营商家数 ÷ 当月在营商家总数。动销率低的商圈说明存在大量"僵尸供给"——挂着门面但不出单，既稀释流量分发效率，也拉低用户体验。区域负责人需要按月、按区域输出动销率及动销商家明细，用于决定BD拜访优先级（优先激活还是优先清退）。难点在于"在营"的口径：商家有上线日期与可能的下线日期，月中上线、月中下线都会改变分母；同时历史区域划分发生过调整，同比时必须固定区域版本，否则动销率的变化会被误读为经营变化。用户在此链路里只与动销商家成交，商家产出订单，平台负责口径定义与考核。

### 2. 表结构说明

merchants 商家表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| merchant_id | BIGINT | 商家ID，主键 |
| merchant_name | VARCHAR(64) | 商家名称 |
| region_id | INT | 所属区域ID（按当前划分） |
| online_date | DATE | 上线日期 |
| offline_date | DATE | 下线日期，NULL表示在营 |

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| merchant_id | BIGINT | 商家ID |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（merchants，5行）：

| merchant_id | merchant_name | region_id | online_date | offline_date |
|-------------|---------------|-----------|-------------|--------------|
| 9001 | 老王麻辣烫 | 11 | 2025-03-01 | NULL |
| 9002 | 蜀香冒菜 | 11 | 2026-06-15 | NULL |
| 9003 | 快乐柠檬 | 12 | 2025-08-20 | 2026-07-10 |
| 9004 | 张记烧烤 | 12 | 2025-01-05 | NULL |
| 9005 | 米饭食堂 | 13 | 2026-07-25 | NULL |

示例数据（orders，5行）：

| order_id | merchant_id | pay_time | order_amount | status |
|----------|-------------|----------|--------------|--------|
| 20001 | 9001 | 2026-07-03 11:50:00 | 32.00 | completed |
| 20002 | 9004 | 2026-07-04 19:20:00 | 88.50 | completed |
| 20003 | 9001 | 2026-08-06 12:10:00 | 28.00 | canceled |
| 20004 | 9004 | 2026-08-08 18:40:00 | 45.00 | completed |
| 20005 | 9002 | 2026-09-02 11:30:00 | 26.50 | completed |

### 3. 解题思路

口径先行：①分母"当月在营商家"= 上线日期早于当月月末 且（未下线 或 下线日期不早于当月月初），月中上线的商家计入当月分母；②分子"动销商家"= 当月存在 status='completed' 订单的商家，取消单不计入，避免刷单虚调动销；③统计月取 2026-07 至 2026-09 三个月做趋势。实现路径上，难点是分母不能只从订单表反推（无订单商家会丢失），必须以商家表为全集：先造出月份列表（递归CTE），与商家表按"当月在营"条件做非等值JOIN生成"月×商家"全集格，再左连接当月完成订单聚合结果判动销。**【加分点】** 用递归CTE动态生成月份维表，比硬编码 UNION ALL 更工程化。易错点：用 INNER JOIN 订单表导致零单商家整月消失；下线边界用 `>` 还是 `>=` 造成月末下线商家归属摇摆；区域划分变更期未固定版本。

### 4. 参考解法

解法一：递归CTE造月份 + 预聚合动销结果后 LEFT JOIN（两段聚合相除，性能友好）。

```sql
WITH RECURSIVE months AS (        -- 第一步：递归生成2026-07至2026-09每月月初日期
    SELECT DATE '2026-07-01' AS month_start
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH           -- 每次加一个月
    FROM months
    WHERE month_start < '2026-09-01'                -- 递归终止条件
),
alive AS (                        -- 第二步：展开"月×在营商家"全集格（分母来源）
    SELECT mo.month_start, m.merchant_id
    FROM months mo
    JOIN merchants m
      ON m.online_date < mo.month_start + INTERVAL 1 MONTH          -- 上线早于当月月末
     AND (m.offline_date IS NULL                                    -- 未下线
          OR m.offline_date >= mo.month_start)                      -- 或下线不早于当月月初
),
sold AS (                         -- 第三步：预聚合每月每个有完成订单的商家
    SELECT o.merchant_id,
           DATE_FORMAT(o.pay_time, '%Y-%m-01') AS month_start          -- 对齐到月初与months关联
    FROM orders o
    WHERE o.status = 'completed'
      AND o.pay_time >= '2026-07-01' AND o.pay_time < '2026-10-01'
    GROUP BY o.merchant_id, DATE_FORMAT(o.pay_time, '%Y-%m-01')
)
SELECT a.month_start                                  AS 统计月,
       COUNT(*)                                       AS 在营商家数,
       COUNT(s.merchant_id)                           AS 动销商家数,   -- LEFT JOIN未命中的s列为NULL，COUNT忽略NULL
       ROUND(COUNT(s.merchant_id) / COUNT(*), 4)      AS 动销率
FROM alive a
LEFT JOIN sold s
       ON s.merchant_id = a.merchant_id
      AND s.month_start = a.month_start
GROUP BY a.month_start
ORDER BY a.month_start;
```

结果解读：以示例数据推断，9005、9002 月中上线会进入上线当月的分母，9003 下线后不再计入后续月份分母，动销率会随商家结构波动，解读时需同步披露分母变化。

解法二：月×商家全集格上逐格 EXISTS 标记，AVG 求动销率（一格一判断，可自然扩展到区域粒度）。

```sql
WITH RECURSIVE months AS (        -- 月份维表，与解法一相同
    SELECT DATE '2026-07-01' AS month_start
    UNION ALL
    SELECT month_start + INTERVAL 1 MONTH FROM months WHERE month_start < '2026-09-01'
)
SELECT mo.month_start                                   AS 统计月,
       COUNT(*)                                         AS 在营商家数,
       ROUND(AVG(                                       -- 每格动销为1/0，均值即动销率
           CASE WHEN EXISTS (                           -- 逐格判断该商家当月是否有完成订单
               SELECT 1 FROM orders o
               WHERE o.merchant_id = m.merchant_id
                 AND o.status = 'completed'
                 AND o.pay_time >= mo.month_start                       -- 当月起点
                 AND o.pay_time <  mo.month_start + INTERVAL 1 MONTH    -- 当月终点，左闭右开
           ) THEN 1 ELSE 0 END), 4)                     AS 动销率
FROM months mo
JOIN merchants m
  ON m.online_date < mo.month_start + INTERVAL 1 MONTH
 AND (m.offline_date IS NULL OR m.offline_date >= mo.month_start)
GROUP BY mo.month_start
ORDER BY mo.month_start;
```

结果解读：AVG(0/1标记) 与"分子除分母"在数学上等价，但该写法保留了"每格一个判断"的语义，往 SELECT 里加 region_id 即可平滑升级为区域粒度动销率，适合探查阶段。

### 5. 性能分析与优化

解法一将订单侧收敛为预聚合结果（每月每商家一行）再 JOIN，JOIN 规模 = 在营格数，且 sold 子查询可走 (merchant_id, status, pay_time) 复合索引做松散扫描，三倍的月份规模通常很小；解法二对每个"月×商家"格执行一次相关子查询，格数 = 月数×商家数，若商家十万级则探测次数巨大，依赖索引且仍可能劣化，更适合小范围探查而非例行报表。优化建议：①orders 建 (merchant_id, status, pay_time) 复合索引；②alive 与 sold 的 JOIN 键统一为 (merchant_id, month_start) 两列，避免隐式转换；③若历史区域划分变更，按业务方冻结的"区域版本日期"过滤 merchants，或引入 region_snapshot 表；④例行化时可每月落一张动销结果表，报表只读结果。

### 6. 面试延伸考点

- **如果只要本月动销率，不需要月份维表，还能怎么写？** 要点：直接以 merchants 为全集 LEFT JOIN 当月完成订单聚合结果，`COUNT(DISTINCT o.merchant_id)/COUNT(DISTINCT m.merchant_id)`，注意两个 COUNT 都要 DISTINCT。
- **为什么分母不能用订单表出现的商家数？** 要点：幸存者偏差——零单商家在订单表中不存在，用它当分母会把动销率系统性高估。
- **月中上线的商家算不算当月分母，两种口径差在哪？** 要点：计入则分母更大、动销率更低，反映真实供给利用效率；不计入则只看存量商家，适合评估BD激活老商家的效果，需按汇报目的选择并标注。

### 7. 业务拓展思考

动销率是"供给利用率"的体检表，可与商家生命周期联动：对上线 4 周内零动销的新商家触发冷启干预（流量券包、运营诊断电话），对连续 2 个月零动销的老商家进入清退评估。口径延展上，可定义"深度动销"（月订单≥30单才算动销）区分陪跑商家与真实产出商家；也可结合区域维度做动销率×单商家平均单量的四象限，指导BD在不同商圈之间调配拜访人力。区域划分变更期的同比，建议输出双版本口径（新划/旧划）并排展示，避免误读。

## LL-18 配送时长P50/P90分区域统计：定位长尾区域

### 1. 业务背景

配送运营团队每周按区域复盘履约时效。平均配送时长会被极端值绑架，行业通行做法是看分位数：P50 反映典型体验，P90 反映最差 10% 用户的体验下限。区域经理需要拿到各区域配送时长的 P50 与 P90，对 P90 明显偏高的区域启动专项：要么加骑手运力，要么调整调度参数（顺路单上限、取餐等待时长），要么治理出餐慢的商家。这里的配送时长是"多段耗时"的总和：骑手接单→到店→取餐→送达，全程时长 = 送达时间 - 接单时间；但商家出餐慢和骑手在途慢是两类责任，分析时先统一口径算全程，后续再按分段拆解归因。用户是时效的直接感知方，商家影响出餐段，骑手决定在途段，平台用分位数指标驱动调度决策。

### 2. 表结构说明

deliveries 配送单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| delivery_id | BIGINT | 配送单ID，主键 |
| order_id | BIGINT | 关联订单ID |
| region_id | INT | 配送区域ID |
| rider_id | BIGINT | 接单骑手ID |
| accept_time | DATETIME | 骑手接单时间 |
| arrive_shop_time | DATETIME | 骑手到店时间 |
| pickup_time | DATETIME | 骑手取餐时间 |
| deliver_time | DATETIME | 送达时间 |
| status | VARCHAR(16) | 配送状态：delivered已送达 / canceled已取消 / exception异常单 |

示例数据（5行）：

| delivery_id | order_id | region_id | rider_id | accept_time | arrive_shop_time | pickup_time | deliver_time | status |
|-------------|----------|-----------|----------|-------------|------------------|-------------|--------------|--------|
| 30001 | 40001 | 21 | 701 | 2026-09-15 11:32:00 | 11:40:00 | 11:52:00 | 2026-09-15 12:03:00 | delivered |
| 30002 | 40002 | 21 | 702 | 2026-09-15 11:35:00 | 11:47:00 | 12:05:00 | 2026-09-15 12:26:00 | delivered |
| 30003 | 40003 | 22 | 703 | 2026-09-15 11:36:00 | 11:42:00 | 11:55:00 | 2026-09-15 12:08:00 | delivered |
| 30004 | 40004 | 22 | 703 | 2026-09-15 11:40:00 | NULL | NULL | NULL | canceled |
| 30005 | 40005 | 21 | 704 | 2026-09-15 11:44:00 | 11:55:00 | 12:20:00 | 2026-09-15 12:58:00 | delivered |

（示例表中时间列省略了相同日期前缀的写法仅为排版简洁，实际为完整 DATETIME。）

### 3. 解题思路

口径与边界：①样本过滤只保留 status='delivered' 的配送单，取消单没有送达时间，异常单（如洒漏重派）混入会污染分位；②时长 = TIMESTAMPDIFF(秒, accept_time, deliver_time)/60，即接单到送达的全程分钟数，负值或超过240分钟的记录属脏数据需剔除；③P50/P90 采用"最近秩"近似：升序排列后取第 ⌈0.5·N⌉ 与 ⌈0.9·N⌉ 名的值，与教科书插值分位略有差异，面试时声明近似口径即可；④MySQL 8.0 没有内置 PERCENTILE_CONT 聚合函数，必须用窗口函数模拟。实现路径：CTE 洗出有效样本与时长 → 窗口按区域分区内排序编号 → 条件聚合取出目标秩。**【面试高频】** "MySQL里怎么算分位数"几乎每场数据岗面试都会出现，ROW_NUMBER 与 PERCENT_RANK 两种模拟法都要会手写。

### 4. 参考解法

解法一：ROW_NUMBER + 计数窗口，取最近秩（最经典、可迁移性最强的写法）。

```sql
WITH valid AS (                   -- 第一步：洗出有效样本并计算全程时长（分钟）
    SELECT region_id,
           TIMESTAMPDIFF(SECOND, accept_time, deliver_time) / 60.0 AS dur  -- 秒差转分钟，保留小数
    FROM deliveries
    WHERE status = 'delivered'                        -- 只要送达单
      AND accept_time IS NOT NULL AND deliver_time IS NOT NULL
      AND deliver_time > accept_time                  -- 剔除时间倒挂的脏数据
      AND TIMESTAMPDIFF(MINUTE, accept_time, deliver_time) <= 240  -- 剔除超4小时异常
),
ranked AS (                       -- 第二步：区域内按时长升序编号，并保留分区总数
    SELECT region_id, dur,
           ROW_NUMBER() OVER (PARTITION BY region_id ORDER BY dur) AS rn,  -- 升序秩
           COUNT(*)     OVER (PARTITION BY region_id)              AS cnt -- 分区样本量
    FROM valid
)
SELECT region_id                                        AS 区域ID,
       cnt                                              AS 样本数,
       MAX(CASE WHEN rn = CEIL(cnt * 0.5) THEN dur END) AS P50分钟,   -- 第⌈N/2⌉名即中位数
       MAX(CASE WHEN rn = CEIL(cnt * 0.9) THEN dur END) AS P90分钟,   -- 第⌈0.9N⌉名即P90
       ROUND(MAX(CASE WHEN rn = CEIL(cnt * 0.9) THEN dur END)
           / NULLIF(MAX(CASE WHEN rn = CEIL(cnt * 0.5) THEN dur END), 0), 2) AS 尾部比P90÷P50
FROM ranked
GROUP BY region_id, cnt;
```

结果解读：尾部比（P90÷P50）越大说明该区域长尾越严重，P50 尚可但尾部比高的区域优先查调度拥堵与出餐慢商家，而非盲目加人。

解法二：PERCENT_RANK 百分位窗口，取"百分位首次越过目标线"的时长（一次排序同时出任意分位）。

```sql
WITH valid AS (                   -- 同解法一，先洗样本
    SELECT region_id,
           TIMESTAMPDIFF(SECOND, accept_time, deliver_time) / 60.0 AS dur
    FROM deliveries
    WHERE status = 'delivered'
      AND deliver_time > accept_time
      AND TIMESTAMPDIFF(MINUTE, accept_time, deliver_time) <= 240
),
pr AS (                           -- 第二步：计算每条记录在区域内的百分位秩
    SELECT region_id, dur,
           PERCENT_RANK() OVER (PARTITION BY region_id ORDER BY dur) AS pct  -- (秩-1)/(N-1)，落在0~1
    FROM valid
)
SELECT region_id,
       MIN(CASE WHEN pct >= 0.5 THEN dur END) AS P50分钟,   -- 百分位首次≥0.5的最小时长=上中位
       MIN(CASE WHEN pct >= 0.9 THEN dur END) AS P90分钟,   -- 百分位首次≥0.9的最小时长=P90
       COUNT(*)                               AS 样本数
FROM pr
GROUP BY region_id;
```

结果解读：PERCENT_RANK 法把"取哪个分位"参数化，想再加 P95 只需一行 CASE，适合做分位矩阵；结果与最近秩法可能有 ±1 个样本位的差异，属口径近似范围内。

### 5. 性能分析与优化

两种解法都要按 (region_id, dur) 排序一次，代价同为 O(N·logN)，差异在输出形态：解法一的 COUNT 窗口无 ORDER BY，可与 ROW_NUMBER 共享同一次排序；解法二的 MIN(CASE) 需要全分区扫到尾部才能确定最小百分位，但省了样本量窗口。可执行优化：①deliveries 建 (status, region_id, accept_time) 索引，先按状态与时间收窄扫描；②时长计算放到 CTE 后，外层不再重复 TIMESTAMPDIFF；③区域数多、周期长时可预聚合到"区域×日"粒度落表，但注意分位数不可跨粒度直接平均，日表需保留原始秩分布或按样本加权；④超大数据量改用抽样或专门的近似分位算法（如 t-digest 类实现），面试提到这点是明确加分项。

### 6. 面试延伸考点

- **P90和"平均时长"分别适合什么决策场景？** 要点：均值对骑手考核与整体成本敏感，P90对体验兜底与差评防控敏感；P50与P90组合能区分"普遍慢"与"长尾慢"。
- **怎么把全程P90拆解为出餐段与在途段？** 要点：分别对 (accept→pickup) 与 (pickup→deliver) 两段套用同一分位框架，比较哪段贡献了长尾，再决定治理商家出餐还是加运力。
- **MySQL 8.0为什么没有PERCENTILE_CONT，PG/Oracle里有怎么办？** 要点：MySQL仅提供窗口模拟；跨方言可写 `PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY dur)`，面试中说出方言差异体现广度。

### 7. 业务拓展思考

分位时效可以直接接入调度策略：对 P90 超标的区域动态上调配送费与冲单奖励，吸引骑手向缺口区域迁移；对出餐段 P90 高的商家推送"出餐慢"标签并降低其派单优先级。口径延展上，可按"时段×区域"二维出分位矩阵（午高峰的 P90 才是真正的压力测试），或用"承诺送达时间达成率"补充用户视角——用户感知的是"比承诺晚了多少"，而不是绝对时长。长期看，把 P90 目标写进骑手排班与商家准入，比事后复盘更能形成闭环。

## LL-19 用户复购周期与30天复购率：发券时机的数据依据

### 1. 业务背景

用户增长团队负责外卖主站的老客经营，核心假设是：复购券应该在"用户即将复购但还没下单"的时间窗投放，因此必须先量化用户的复购周期分布与30天复购率。运营负责人每月要回答三个问题：本月有多少活跃用户产生了30天内复购（复购率）？复购用户平均隔多少天回来（复购周期）？复购周期在不同品类结构上是否不同（例如正餐用户比茶饮用户周期更长）？这些结论直接决定 CRM 定向券的投放时机（如第3、7、14天触达）与券面门槛。用户产生订单行为，平台定义口径并运营触达，商家承接复购供给；若商家供给不稳，复购率下滑会被误判为券效问题，因此口径解读时需联动供给侧。取数窗口为 2026-09-01 至 2026-10-31，观察月为9月。

### 2. 表结构说明

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| biz_type | VARCHAR(16) | 品类：外卖/闪购/到店 |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（5行）：

| order_id | user_id | biz_type | pay_time | order_amount | status |
|----------|---------|----------|----------|--------------|--------|
| 50001 | 8001 | 外卖 | 2026-09-02 12:01:00 | 33.00 | completed |
| 50002 | 8001 | 外卖 | 2026-09-06 19:20:00 | 28.50 | completed |
| 50003 | 8002 | 闪购 | 2026-09-03 10:15:00 | 56.00 | completed |
| 50004 | 8002 | 闪购 | 2026-10-20 11:00:00 | 41.00 | completed |
| 50005 | 8003 | 外卖 | 2026-09-15 18:30:00 | 47.20 | canceled |

### 3. 解题思路

口径与边界：①观察人群 = 9月内有过至少一笔**已完成**订单的用户（活跃用户）；②复购定义 = 用户首单（此处取9月内首单）之后 30 个自然日内再次出现已完成订单，取"首单→复购单"这一对订单计算周期，而不是相邻任意两单，保证人人只贡献一个周期、口径可加总；③平均复购周期 = 复购用户（复购日-首单日）的均值，30天复购率 = 复购用户数 ÷ 活跃用户数；④取数必须覆盖到10月底，否则9月末首单用户的30天窗口被截断，复购率被低估。实现路径：先给每用户打上首单时间，再找"晚于首单且在30天窗口内"的最早订单作为复购单，两层聚合出结果。**【避坑指南】** 若直接把9月之后的订单截掉，9月25日首单用户的复购几乎不可能被观察到——窗口截断是复购类指标最常见的翻车点。

### 4. 参考解法

解法一：窗口 MIN 打首单标 + 条件聚合找复购单（一次扫描用户订单序列）。

```sql
WITH user_orders AS (             -- 第一步：窗口为每个用户并行求出首单支付时间
    SELECT user_id, pay_time,
           MIN(pay_time) OVER (PARTITION BY user_id) AS first_pay  -- 用户分区内最早支付时间
    FROM orders
    WHERE status = 'completed'                        -- 复购只认完成单
      AND pay_time >= '2026-09-01' AND pay_time < '2026-11-01'  -- 窗口覆盖9月+10月防截断
),
user_tag AS (                     -- 第二步：按用户聚合出首单与30天内的复购单
    SELECT user_id,
           MIN(first_pay)                                  AS first_pay,   -- 用户首单
           MIN(CASE WHEN pay_time > first_pay                        -- 晚于首单
                     AND pay_time < first_pay + INTERVAL 30 DAY      -- 且在30天窗口内
                    THEN pay_time END)                       AS repurchase_time  -- 最早复购单
    FROM user_orders
    GROUP BY user_id
    HAVING MIN(first_pay) < '2026-10-01'              -- 首单必须落在9月（观察月），10月新客剔除
)
SELECT COUNT(*)                                        AS 活跃用户数,
       COUNT(repurchase_time)                          AS 复购用户数,   -- NULL不计数
       ROUND(AVG(DATEDIFF(repurchase_time, first_pay)), 1) AS 平均复购周期天,
       ROUND(COUNT(repurchase_time) / COUNT(*), 4)     AS 复购率30天
FROM user_tag;
```

结果解读：若平均复购周期约4天，说明外卖高频场景下第3-5天是券触达黄金窗口；复购率环比下滑时应先看供给（动销商家数）再怪券效。

解法二：两段聚合 + 自连接找复购单（不依赖窗口函数的经典写法，兼容老版本思路）。

```sql
WITH first_t AS (                 -- 第一步：先聚合出9月内每个用户的首单时间
    SELECT user_id, MIN(pay_time) AS first_pay
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-09-01' AND pay_time < '2026-10-01'   -- 首单定义在观察月内
    GROUP BY user_id
),
repurchase AS (                   -- 第二步：回表找每用户30天窗口内的最早后续订单
    SELECT f.user_id, f.first_pay,
           MIN(o.pay_time)        AS repurchase_time
    FROM first_t f
    JOIN orders o
      ON o.user_id = f.user_id
     AND o.status = 'completed'
     AND o.pay_time >  f.first_pay                          -- 严格晚于首单
     AND o.pay_time <  f.first_pay + INTERVAL 30 DAY        -- 30天复购窗口
    GROUP BY f.user_id, f.first_pay
)
SELECT COUNT(*)                                        AS 活跃用户数,
       (SELECT COUNT(*) FROM repurchase)               AS 复购用户数,
       ROUND((SELECT AVG(DATEDIFF(repurchase_time, first_pay)) FROM repurchase), 1) AS 平均复购周期天,
       ROUND((SELECT COUNT(*) FROM repurchase) / COUNT(*), 4) AS 复购率30天
FROM first_t;
```

结果解读：自连接法的复购集合是显式的中间表，便于继续下钻"复购用户的品类结构"；缺点是活跃用户与复购用户来自两个结果集，需用标量子查询拼装，可读性略逊。

### 5. 性能分析与优化

解法一按 user_id 排序一次完成，窗口 MIN 无需回表，整体一次扫描 + 一次聚合，代价 O(N·logN)；解法二先 GROUP BY 全量聚合一次，再以 first_t（用户级，行数远小于订单表）驱动 JOIN 回 orders，JOIN 时若 orders 有 (user_id, status, pay_time) 索引则每次探测为一次范围扫描，总体也很快，但多一轮回表。可执行优化：①orders 建 (user_id, status, pay_time) 复合索引，两个解法同时受益；②时间条件保持左闭右开区间，避免对 pay_time 包函数；③若用户量大，可先按 biz_type 拆分口径分别输出（正餐/茶饮复购周期差异大，混算会掩盖发券时机差异）；④例行化后建议落"用户月活跃宽表"，把首单时间固化为字段。

### 6. 面试延伸考点

- **"相邻订单间隔"和"距首单间隔"两种复购周期口径有什么区别？** 要点：前者用 LEAD 算每对相邻订单差、反映节奏分布；后者人人一个周期、便于汇总与归因；汇报时必须写清用的哪种。
- **复购率算到多少算健康？怎么设目标？** 要点：分行业基准（外卖周复购天然高、闪购月度更低），且应与自身历史环比而非绝对值比较；也可以按用户分层（新老客）分别设目标。
- **窗口截断问题除了拉长取数窗口还能怎么处理？** 要点：使用"已成熟用户"口径（首单日 ≤ 统计日-30天的用户）计算复购率，或者对未满窗口用户单独标注"观察中"不计入分母。

### 7. 业务拓展思考

复购周期分布是 CRM 触达策略的底座：可以输出周期直方图（1-3天/4-7天/8-14天/15-30天四桶），对每桶配置不同的券面额与推送时刻，把"平均触达"升级为"分位触达"。结论还能与供给联动：复购率低的商圈优先排查动销与出餐时效，避免把供给问题误治成营销问题。口径延展上，可引入"跨品类复购"（外卖用户30天内转向闪购）单独统计，衡量平台品类渗透；也可以把30天窗口替换为用户历史个人周期（个性化复购窗口），做真正的一人一策。

## LL-20 商家评分分桶与订单量对比：验证高分等于高单量

### 1. 业务背景

平台供给治理团队想验证一个直觉假设：评分高的商家单量也高，因此值得把流量扶持与改造资源优先投给"接近高分但还没上分"的商家。分析师需要把商家按评分分桶（低于3.5分、3.5-3.9、4.0-4.4、4.5-5.0四档），统计每档的商家数、月户均订单量，并与全体商家户均单量对比得出指数（分桶户均 ÷ 全体户均）。如果指数随评分单调上升，假设成立，"提分拉动单量"的资源策略有了依据；如果不单调（例如3.5-3.9档反而最高），则要警惕评分与单量互为因果或被区域混杂。用户用脚投票产生订单，商家的服务决定评分，平台需要用干净的对比数据决定资源投放。统计月为2026年9月，评分为9月末快照。

### 2. 表结构说明

merchants 商家表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| merchant_id | BIGINT | 商家ID，主键 |
| merchant_name | VARCHAR(64) | 商家名称 |
| rating | DECIMAL(2,1) | 商家评分（1.0~5.0，月末快照） |
| region_id | INT | 所属区域ID |

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| merchant_id | BIGINT | 商家ID |
| pay_time | DATETIME | 支付时间 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（merchants，5行）：

| merchant_id | merchant_name | rating | region_id |
|-------------|---------------|--------|-----------|
| 9001 | 老王麻辣烫 | 4.8 | 11 |
| 9002 | 蜀香冒菜 | 4.2 | 11 |
| 9003 | 快乐柠檬 | 3.4 | 12 |
| 9004 | 张记烧烤 | 4.5 | 12 |
| 9005 | 米饭食堂 | 3.8 | 13 |

示例数据（orders，5行）：

| order_id | merchant_id | pay_time | status |
|----------|-------------|----------|--------|
| 60001 | 9001 | 2026-09-01 11:50:00 | completed |
| 60002 | 9001 | 2026-09-01 19:20:00 | completed |
| 60003 | 9003 | 2026-09-02 12:10:00 | completed |
| 60004 | 9004 | 2026-09-03 18:40:00 | canceled |
| 60005 | 9002 | 2026-09-03 11:30:00 | completed |

### 3. 解题思路

口径与边界：①单量只统计 status='completed' 的9月订单，按商家收敛为"户均月单量"；②评分取月末快照，若商家当月评分大幅波动，快照时点选择必须前后一致，否则出现"用结果解释结果"的幸存者偏差（低分商家可能是被差评打下去的高单量商家）；③分桶边界用左闭右开 [3.5,4.0) 等固定业务阈值，另用 NTILE 四分位分桶做稳健性对照；④对比基准是全体商家户均单量，产出"分桶指数"，剔除总量波动干扰。实现路径：CTE 算每商家订单数 → JOIN 商家表打分桶 → 分桶聚合 → 聚合后开窗口算全体均值。**【加分点】** 长尾商家（月单量个位数）会把均值拉偏，可同时给出分桶中位数（仍用 LL-18 的分位近似框架）作为稳健性检验，面试中主动提这点会显著加分。

### 4. 参考解法

解法一：固定业务阈值分桶 + 聚合后窗口算全体均值（指数对比）。

```sql
WITH mo AS (                      -- 第一步：每商家9月完成订单数
    SELECT o.merchant_id,
           COUNT(*)               AS ord_cnt
    FROM orders o
    WHERE o.status = 'completed'
      AND o.pay_time >= '2026-09-01' AND o.pay_time < '2026-10-01'
    GROUP BY o.merchant_id
),
bucketed AS (                     -- 第二步：关联评分并按业务阈值打分桶标签
    SELECT CASE WHEN m.rating <  3.5 THEN '01_<3.5'
                WHEN m.rating <  4.0 THEN '02_3.5-3.9'
                WHEN m.rating <  4.5 THEN '03_4.0-4.4'
                ELSE '04_4.5-5.0' END      AS rating_band,   -- 标签前缀数字保证排序正确
           mo.ord_cnt
    FROM mo
    JOIN merchants m ON m.merchant_id = mo.merchant_id
),
agg AS (                          -- 第三步：分桶聚合出档位商家数与户均单量
    SELECT rating_band,
           COUNT(*)          AS merchant_cnt,
           AVG(ord_cnt)      AS avg_orders
    FROM bucketed
    GROUP BY rating_band
)
SELECT rating_band                            AS 评分分档,
       merchant_cnt                           AS 商家数,
       ROUND(avg_orders, 1)                   AS 户均月单量,
       ROUND(AVG(avg_orders) OVER (), 1)      AS 全体户均单量,      -- 对聚合结果再开窗口
       ROUND(avg_orders / NULLIF(AVG(avg_orders) OVER (), 0), 2) AS 单量指数   -- 分桶/全体
FROM agg
ORDER BY rating_band;
```

结果解读：若单量指数随分档单调上升（如 0.4 → 0.8 → 1.2 → 1.9），支持"高分≈高单量"；若在某一档出现倒挂，需要先检查该档是否混入低单量新商家。

解法二：NTILE 四分位分桶做稳健性对照（数据驱动分组，验证阈值分桶结论是否稳定）。

```sql
WITH mo AS (                      -- 每商家订单数，同解法一
    SELECT o.merchant_id, COUNT(*) AS ord_cnt
    FROM orders o
    WHERE o.status = 'completed'
      AND o.pay_time >= '2026-09-01' AND o.pay_time < '2026-10-01'
    GROUP BY o.merchant_id
),
nt AS (                           -- 按评分升序均分四组：Q1最低分组 ~ Q4最高分组
    SELECT NTILE(4) OVER (ORDER BY m.rating) AS rating_quartile,   -- 四分位编号1~4
           mo.ord_cnt,
           m.rating
    FROM mo
    JOIN merchants m ON m.merchant_id = mo.merchant_id
)
SELECT CONCAT('Q', rating_quartile)           AS 评分四分位组,
       MIN(rating)                            AS 组内最低分,       -- 展示组边界帮助解读
       MAX(rating)                            AS 组内最高分,
       COUNT(*)                               AS 商家数,
       ROUND(AVG(ord_cnt), 1)                 AS 户均月单量,
       ROUND(AVG(AVG(ord_cnt)) OVER (), 1)    AS 全体户均单量      -- 聚合套窗口：对分桶均值求全体均值
FROM nt
GROUP BY rating_quartile
ORDER BY rating_quartile;
```

结果解读：四分位分组强制每组样本均衡，若 Q1→Q4 户均单量仍单调上升，则说明结论不依赖人为阈值，汇报时两法并排展示说服力最强。

### 5. 性能分析与优化

两法的主体代价都是"订单表按商家聚合一次 + 与商家表按主键JOIN + 一次排序分桶"，规模受商家数而非订单数驱动，均属轻量。差异点：CASE 分桶只做一次条件表达式，NTILE 需按 rating 全量排序（O(M·logM)，M=商家数），商家百万级时排序成本可见但可接受。可执行优化：①orders 建 (merchant_id, status, pay_time) 索引让订单聚合走索引扫描；②评分快照若来自 reviews 实时计算，应预先物化到 merchants 表，避免查询时实时聚合评分；③输出可加区域维度变成"区域×分档"矩阵，注意此时"全体均值"窗口要改按区域分区（PARTITION BY region_id），否则跨区域比较失真；④对月单量为0的商家是否入桶要先声明——本口径只含当月有完成单的商家，若要含零单商家需改为以 merchants 为全集 LEFT JOIN。

### 6. 面试延伸考点

- **评分与单量的相关性如何量化，相关等于因果吗？** 要点：可算皮尔逊/斯皮尔曼相关系数（SQL内用聚合公式实现），但高评分可能既是单量高的原因也是结果（口碑飞轮），严格归因需要双重差分或对照实验。
- **为什么不用平均分而要分桶？** 要点：分桶把连续关系离散化便于运营落地（每档一套动作），且能暴露非线性（如4.5以上单量跃迁的"门槛效应"）。
- **评分低但单量高的商家说明什么？** 要点：可能是低价走量、供给稀缺（写字楼独一份），这类商家是"提分潜力股"，治理动作应该是帮扶而非处罚。

### 7. 业务拓展思考

分桶对比结论可直接产品化为"评分成长通道"：给 3.5-4.4 档商家推送差评归因报告与整改清单，配合流量倾斜实验，观察提分后单量指数是否如假设抬升。指标口径可延展为"评分变化弹性"——用评分变动0.1分前后的单量变化率（联动 LL-27 的事件前后对比）量化提分ROI；也可加入差评率、退款率构成服务分，避免单一评分被刷分行为操纵。区域维度上，分桶应控区域做分层对比，防止高评分区域集中在高消费城区造成的辛普森悖论。
## LL-21 满减梯度与客单价对比：满减真的推高了客单吗

### 1. 业务背景

外卖平台营销团队在9月投放了三档满减：满20减4、满35减6、满50减8，由平台与商家按比例分摊。营销负责人的疑问是：不同满减梯度的订单客单价分别是多少？与不使用满减的订单相比，满减是否真的把客单价抬上来了，还是只是给"本来就要买够20元"的用户发了补贴？分析师需要按梯度输出客单价、订单量占比，并计算每档订单金额距门槛的平均差额——如果某档订单金额紧密聚集在门槛上方一点，说明大量用户是"凑单"到门槛的，满减确实在改变购物篮；如果订单金额远高于门槛，说明满减更多是价格转移。用户为凑单而加购，商家承担部分让利并可能上调标价，平台据此决定下期梯度设置。统计范围为2026年9月完成订单。

### 2. 表结构说明

promotions 满减活动表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| promo_id | INT | 活动ID，主键 |
| promo_name | VARCHAR(32) | 梯度名称（满20减4等） |
| threshold_amount | DECIMAL(10,2) | 满减门槛金额 |
| discount_amount | DECIMAL(10,2) | 优惠金额 |
| start_date | DATE | 活动开始日 |
| end_date | DATE | 活动结束日 |

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| merchant_id | BIGINT | 商家ID |
| promo_id | INT | 使用的满减活动ID，NULL为未用券 |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额（优惠前原价口径） |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（promotions，5行中的3档+补充）：

| promo_id | promo_name | threshold_amount | discount_amount | start_date | end_date |
|----------|------------|------------------|-----------------|------------|----------|
| 1 | 满20减4 | 20.00 | 4.00 | 2026-09-01 | 2026-09-30 |
| 2 | 满35减6 | 35.00 | 6.00 | 2026-09-01 | 2026-09-30 |
| 3 | 满50减8 | 50.00 | 8.00 | 2026-09-01 | 2026-09-30 |
| 4 | 满80减15 | 80.00 | 15.00 | 2026-09-01 | 2026-09-30 |

示例数据（orders，5行）：

| order_id | user_id | merchant_id | promo_id | pay_time | order_amount | status |
|----------|---------|-------------|----------|----------|--------------|--------|
| 70001 | 8001 | 9001 | 2 | 2026-09-01 11:50:00 | 36.50 | completed |
| 70002 | 8002 | 9002 | 1 | 2026-09-01 12:05:00 | 22.00 | completed |
| 70003 | 8003 | 9003 | NULL | 2026-09-02 09:30:00 | 15.80 | completed |
| 70004 | 8004 | 9004 | 3 | 2026-09-02 18:40:00 | 51.00 | completed |
| 70005 | 8005 | 9001 | 2 | 2026-09-03 11:20:00 | 60.00 | canceled |

### 3. 解题思路

口径与边界：①订单金额取"优惠前原价"（order_amount），这样才能观察满减是否抬高了购物篮；若用折后实付价，客单价会被优惠直接拉低，结论反转；②只统计 completed 订单，取消单凑单失败不产生真实行为；③对比基准是 promo_id IS NULL 的无满减订单，需注意无券订单与用券订单的用户结构差异（大额自然单不可能是满减单），解读时声明混杂；④"距门槛平均差额" = 订单金额 - 该档门槛，是判断凑单强度的关键副指标。实现路径：订单表 LEFT JOIN 活动表（必须 LEFT，保住无券订单做基准）后，既可按梯度 GROUP BY 输出长表，也可条件聚合成一行宽表。**【避坑指南】** 订单可能同时叠加红包等其他优惠，若要纯化满减效应，需先剔除叠加其他平台优惠的订单，否则满减组客单价被污染。

### 4. 参考解法

解法一：LEFT JOIN 后按梯度 GROUP BY 输出长表（含凑单强度副指标）。

```sql
WITH ord AS (                     -- 第一步：订单关联活动，无券订单保留为基准
    SELECT o.order_id,
           o.order_amount,
           COALESCE(p.promo_name, '无满减')            AS promo_name,   -- 无券订单打统一标签
           p.threshold_amount                           AS threshold     -- 无券时为NULL
    FROM orders o
    LEFT JOIN promotions p ON p.promo_id = o.promo_id   -- LEFT保证无券订单不丢
    WHERE o.status = 'completed'
      AND o.pay_time >= '2026-09-01' AND o.pay_time < '2026-10-01'
)
SELECT promo_name                                   AS 满减梯度,
       COUNT(*)                                     AS 订单量,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS 订单量占比pct,  -- 聚合后窗口算占比
       ROUND(AVG(order_amount), 2)                  AS 客单价,       -- 优惠前原价口径
       ROUND(AVG(order_amount - COALESCE(threshold, order_amount)), 2) AS 距门槛平均差额
       -- 无券订单用自身金额做差恒为0，有券订单差额越大说明凑单越弱
FROM ord
GROUP BY promo_name
ORDER BY promo_name;
```

结果解读：若"满20减4"档距门槛平均差额只有2元左右，说明大量订单贴线凑单，满减在真实改变购物篮；差额大则多为价格转移，可考虑提高门槛或改为满减券包。

解法二：条件聚合一行车转列，四档客单价并排，方便汇报页直接引用。

```sql
SELECT ROUND(AVG(CASE WHEN o.promo_id IS NULL THEN o.order_amount END), 2) AS 无满减客单价,
       ROUND(AVG(CASE WHEN p.promo_name = '满20减4' THEN o.order_amount END), 2) AS `满20减4客单价`,
       ROUND(AVG(CASE WHEN p.promo_name = '满35减6' THEN o.order_amount END), 2) AS `满35减6客单价`,
       ROUND(AVG(CASE WHEN p.promo_name = '满50减8' THEN o.order_amount END), 2) AS `满50减8客单价`,
       ROUND(AVG(CASE WHEN o.promo_id IS NOT NULL THEN o.order_amount END)
           - AVG(CASE WHEN o.promo_id IS NULL THEN o.order_amount END), 2)        AS 用券vs无券差额,
       COUNT(*)                                                                   AS 总完成订单量
FROM orders o
LEFT JOIN promotions p ON p.promo_id = o.promo_id
WHERE o.status = 'completed'
  AND o.pay_time >= '2026-09-01' AND o.pay_time < '2026-10-01';
-- AVG自动忽略NULL：每个CASE只对命中该档的订单取金额，其余行贡献NULL不进均值
```

结果解读：宽表一行读出全部梯度对比，"用券vs无券差额"直接回答"满减是否抬了客单"；若差额接近0，说明用券订单客单与自然单无异，满减主要在补贴存量。

### 5. 性能分析与优化

两法主体都是一次订单表扫描 + 一次按主键的 LEFT JOIN，promo_id 上的索引能把 JOIN 变成索引查找；解法一多了 GROUP BY 的哈希聚合，解法二单次扫描带条件聚合，代价更低且只回一行。可执行优化：①orders 建 (status, pay_time) 或 (promo_id, status, pay_time) 复合索引，先按状态与时间裁剪数据；②活动表极小（几行），JOIN 成本可忽略，但若活动按商家维度配置（每商家独立梯度），活动表会膨胀到百万行，此时应把活动主键与门槛冗余进订单快照表，避免大表JOIN；③梯度数量动态变化时，CASE 硬编码行转列不可维护，生产上建议用 GROUP_CONCAT 拼长表或交给 BI 工具做透视，面试可提"SQL做定长透视、工具做动态透视"的分工。④若需观察凑单金额分布而非均值，对 (order_amount - threshold) 做分桶直方图比均值更有解释力。

### 6. 面试延伸考点

- **怎么剥离"满减抬高客单"与"高客单用户更爱用满减"的选择偏差？** 要点： observational 数据只能控混杂（同商家、同用户、同时段对比），严格结论要靠随机化实验——对部分用户隐藏某档满减做对照。
- **客单价上升但平台毛利下降，怎么综合评估满减ROI？** 要点：看增量GMV的毛利能否覆盖补贴（边际分析），而非只看客单价；需要构建"有无满减"反事实对照。
- **满减和折扣券哪个对客单影响大，如何设计对比？** 要点：满减引导凑单（门槛效应），折扣券按比例引导加件；对比时要统一补贴预算口径，否则比的是预算不是机制。

### 7. 业务拓展思考

把"距门槛差额"分布接进推荐链路：差额在1-5元区间的用户，在购物车页推荐凑单商品（卤蛋、饮料），既能提升体验又能吃满补贴效率。口径延展上，可统计"凑单商品渗透率"（订单中因凑单新增的商品件数占比），衡量满减对连带消费的带动；也可以按商家参与度分层，观察"商家承担比例"与商家动销/退出的关系，防止高让利把优质中小商家挤出平台。长期建议把满减梯度设置做成持续实验机制，用边际补贴效率（每元补贴带来的增量GMV）替代单一客单价评估。

## LL-22 区域运力缺口（单骑比）：午高峰调度预警

### 1. 业务背景

外卖调度中心在午高峰（11:00-14:00）需要实时盯盘各区域的运力供需：单骑比 = 区域每小时完成订单量 ÷ 该区域在线骑手数。行业经验认为单骑比超过2.0进入预警（骑手持续满载、出餐后无人取），超过2.5属于严重缺口，会出现爆单压单、超时率飙升与骑手违章提速，最终同时伤害用户体验与骑手安全。调度运营每小时要输出一张"区域×小时"的单骑比与缺口等级表，对严重缺口区域立即触发动作：周边区域调度补骑手、上线高峰补贴、临时缩小配送范围。用户在高峰期下单最怕超时，商家怕压单出不了餐，骑手怕无限堆单，平台用单骑比这张表平衡三方。本题为盘后复盘口径，取2026-09-18午高峰三小时数据。

### 2. 表结构说明

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| region_id | INT | 收货地址所属区域ID |
| create_time | DATETIME | 订单创建（支付）时间 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

rider_online_logs 骑手在线心跳表（每小时每骑手每区域一行）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| rider_id | BIGINT | 骑手ID |
| region_id | INT | 心跳上报时所在区域ID |
| snap_time | DATETIME | 心跳聚合时间（整点快照） |

示例数据（orders，5行）：

| order_id | region_id | create_time | status |
|----------|-----------|-------------|--------|
| 80001 | 31 | 2026-09-18 11:05:00 | completed |
| 80002 | 31 | 2026-09-18 11:20:00 | canceled |
| 80003 | 32 | 2026-09-18 12:10:00 | completed |
| 80004 | 31 | 2026-09-18 12:30:00 | completed |
| 80005 | 33 | 2026-09-18 13:15:00 | completed |

示例数据（rider_online_logs，5行）：

| rider_id | region_id | snap_time |
|----------|-----------|-----------|
| 701 | 31 | 2026-09-18 11:00:00 |
| 702 | 31 | 2026-09-18 11:00:00 |
| 703 | 32 | 2026-09-18 11:00:00 |
| 701 | 31 | 2026-09-18 12:00:00 |
| 704 | 33 | 2026-09-18 12:00:00 |

### 3. 解题思路

口径与边界：①分母是在线骑手数而非注册骑手数，来源是心跳表的 COUNT(DISTINCT rider_id)，同一骑手跨区域心跳要按其心跳所在区域计入（简化口径：快照所在区域），面试时声明该近似；②分子取 completed 订单按 create_time 归小时（也有口径用接单时间，需与调度系统对齐）；③缺口等级阈值 2.0/2.5 由调度经验给出，SQL 中参数化成 CASE 即可；④某区域某小时没有骑手心跳时单骑比无穷大，必须显式处理 NULL 与 0。实现路径：订单侧与骑手侧各自按"区域×小时"预聚合，再按两键 JOIN，最后计算比值与等级。**【避坑指南】** NULL 参与除法结果为 NULL，NULL 与阈值比较结果仍为 NULL，会静默漏进 ELSE 分支被判成"健康"——这是运力看板最经典的翻车点，必须先 COALESCE 再比较。

### 4. 参考解法

解法一：双源预聚合 CTE + JOIN，显式处理无骑手格（推荐的标准写法）。

```sql
WITH ord AS (                     -- 第一步：订单侧按区域×小时聚合完成单量
    SELECT region_id,
           DATE_FORMAT(create_time, '%Y-%m-%d %H:00:00') AS stat_hour,  -- 截断到小时
           COUNT(*) AS order_cnt
    FROM orders
    WHERE status = 'completed'                        -- 只统计真实履约的单
      AND create_time >= '2026-09-18 11:00:00'
      AND create_time <  '2026-09-18 14:00:00'        -- 午高峰三小时，左闭右开
    GROUP BY region_id, stat_hour
),
rider AS (                        -- 第二步：骑手侧按区域×小时去重计在线人数
    SELECT region_id,
           DATE_FORMAT(snap_time, '%Y-%m-%d %H:00:00') AS stat_hour,
           COUNT(DISTINCT rider_id) AS online_riders         -- 同骑手多条心跳去重
    FROM rider_online_logs
    WHERE snap_time >= '2026-09-18 11:00:00'
      AND snap_time <  '2026-09-18 14:00:00'
    GROUP BY region_id, stat_hour
)
SELECT o.region_id                                     AS 区域ID,
       o.stat_hour                                     AS 统计小时,
       o.order_cnt                                     AS 完成单量,
       COALESCE(r.online_riders, 0)                    AS 在线骑手数,
       ROUND(o.order_cnt / NULLIF(r.online_riders, 0), 2) AS 单骑比,   -- 除零保护，NULL显示为NULL
       CASE WHEN COALESCE(r.online_riders, 0) = 0 THEN '无运力-严重缺口'   -- 先处理零骑手
            WHEN o.order_cnt / r.online_riders >= 2.5  THEN '严重缺口'
            WHEN o.order_cnt / r.online_riders >= 2.0  THEN '预警'
            ELSE '健康' END                            AS 运力状态
FROM ord o
LEFT JOIN rider r
       ON r.region_id = o.region_id
      AND r.stat_hour = o.stat_hour
ORDER BY o.stat_hour, 单骑比 DESC;                      -- 每小时内缺口最大的排最前
```

结果解读：输出直接可贴进调度复盘会，"无运力-严重缺口"格优先处理；单骑比健康但超时率仍高的区域，问题多半出在商家出餐而非运力。

解法二：订单聚合为主表，在线骑手数用相关子查询作标量列（不建骑手CTE的紧凑写法）。

```sql
WITH ord AS (                     -- 订单侧聚合，同解法一
    SELECT region_id,
           DATE_FORMAT(create_time, '%Y-%m-%d %H:00:00') AS stat_hour,
           COUNT(*) AS order_cnt
    FROM orders
    WHERE status = 'completed'
      AND create_time >= '2026-09-18 11:00:00'
      AND create_time <  '2026-09-18 14:00:00'
    GROUP BY region_id, stat_hour
)
SELECT t.region_id                                     AS 区域ID,
       t.stat_hour                                     AS 统计小时,
       t.order_cnt                                     AS 完成单量,
       (SELECT COUNT(DISTINCT r.rider_id)              -- 相关子查询：逐行回骑手表数人
          FROM rider_online_logs r
         WHERE r.region_id = t.region_id
           AND DATE_FORMAT(r.snap_time, '%Y-%m-%d %H:00:00') = t.stat_hour) AS 在线骑手数
FROM ord t;
-- 得到基础表后再包一层计算单骑比与缺口等级，避免标量子查询重复执行两次
SELECT x.*,
       ROUND(x.order_cnt / NULLIF(x.在线骑手数, 0), 2)  AS 单骑比,
       CASE WHEN COALESCE(x.在线骑手数, 0) = 0 THEN '无运力-严重缺口'
            WHEN x.order_cnt / x.在线骑手数 >= 2.5     THEN '严重缺口'
            WHEN x.order_cnt / x.在线骑手数 >= 2.0     THEN '预警'
            ELSE '健康' END                            AS 运力状态
FROM (
    -- 上面那段查询在此处内联，形成 先取数、后算比的分层结构
) x
ORDER BY x.stat_hour, 单骑比 DESC;
```

结果解读：标量子查询版结构更贴近"主指标+补充列"的即席查询习惯，适合临时取数；但其逐行探测特性不适合大范围例行运行。

### 5. 性能分析与优化

解法一两个 CTE 各自聚合到"区域×小时"极小的中间粒度，JOIN 行数 = 区域数×小时数（几十行级别），是典型的小表 JOIN，代价集中在两个源表的扫描与聚合；rider_online_logs 若有 (region_id, snap_time) 索引可直接走索引聚合。解法二的相关子查询对订单聚合结果每行探测一次骑手表，虽然行数少时差异不大，但每行都要对 DATE_FORMAT 结果比较——骑手表的 snap_time 索引会被函数包裹破坏，可能退化为全扫。可执行优化：①骑手心跳条件改写为 `r.snap_time >= t.stat_hour AND r.snap_time < t.stat_hour + INTERVAL 1 HOUR` 的范围形式保住索引；②两表都按日期分区，查询带分区裁剪条件；③若要覆盖全天24小时与更多日期，把解法一的 JOIN 改为两张预聚合表 JOIN 并落中间表；④进阶方向是把心跳表改为"在线区间表"(online_start, online_end) 后用区间重叠计算真实在岗时长，能区分"在线但憋单"与"在线且饱和"。

### 6. 面试延伸考点

- **单骑比健康但平均履约时长恶化，可能是什么原因？** 要点：商家出餐慢、楼层/写字楼下单难、恶劣天气拉长在途、骑手在线但被长距离单占用；单骑比只度量"人均单量"，不度量空间与流程摩擦。
- **如果要预测未来1小时的缺口而不是盘后复盘，SQL角色怎么变？** 要点：SQL负责构建特征（历史同时段单骑比、天气、节假日、订单前置期），预测交给模型；分析师要能说明特征表怎么取。
- **骑手跨区域游走如何影响分母？** 要点：按心跳快照归区域会重复计数或漏计，更严谨用"在线区间×接单区域"加权分摊；口径要在看板脚注声明。

### 7. 业务拓展思考

单骑比看板可升级为"缺口预测-补偿"闭环：预测到某区域午高峰单骑比超2.0，提前30分钟通过周边区域众包骑手补贴调度进入，同时对该区域订单动态延长承诺送达时间，避免超时率被动恶化。口径延展上，可把分母从"在线人数"换成"有效运力分钟数"（在线时长×饱和度折扣），更贴近真实承载力；也可对等级阈值做分区域校准（写字楼区与居民区的健康单骑比不同）。与商家侧联动，严重缺口区域可临时对出餐慢商家降权派单，先保供给链路通畅。

## LL-23 团购券核销率按品类：到店团购的转化体检

### 1. 业务背景

到店团购业务中，用户在平台购买代金券/套餐券，到店后出示核销。品类运营（餐饮、丽人、休闲娱乐）每月复盘各品类的核销率：到期核销率 = 已核销券数 ÷（已核销 + 过期未核销）券数。核销率低的品类说明"买了不来"，可能意味着套餐吸引力造假、门店服务缩水或有效期太短，用户钱花了体验没发生，直接伤害复购与信任。品类负责人根据核销率决定选品策略：低核销品类的招商标准收紧（审核套餐使用规则），高核销品类追加流量。同时要区分"实时核销率"（含未到期券，必然偏低）与"到期核销率"（状态已收敛，才可横向比较）。用户购买并核销，商家提供履约，平台定义口径并管理招商。

### 2. 表结构说明

coupons 团购券表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| coupon_id | BIGINT | 券ID，主键 |
| deal_id | BIGINT | 关联团购单（deal）ID |
| user_id | BIGINT | 购买用户ID |
| sold_time | DATETIME | 购买（售出）时间 |
| expire_time | DATETIME | 有效期截止时间 |
| verify_time | DATETIME | 到店核销时间，NULL为未核销 |
| status | VARCHAR(20) | 状态：valid未到期 / verified已核销 / unused_expired过期未核销 / refunded已退款 |

deals 团购单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| deal_id | BIGINT | 团购单ID，主键 |
| deal_name | VARCHAR(128) | 团购套餐名称 |
| category | VARCHAR(16) | 品类：餐饮/丽人/休闲娱乐 |
| merchant_id | BIGINT | 商家ID |

示例数据（coupons，5行）：

| coupon_id | deal_id | user_id | sold_time | expire_time | verify_time | status |
|-----------|---------|---------|-----------|-------------|-------------|--------|
| 90001 | 101 | 8001 | 2026-06-03 12:00:00 | 2026-08-03 | 2026-06-10 19:00:00 | verified |
| 90002 | 102 | 8002 | 2026-06-05 18:30:00 | 2026-08-05 | NULL | unused_expired |
| 90003 | 101 | 8003 | 2026-06-10 11:00:00 | 2026-08-10 | 2026-06-18 12:10:00 | verified |
| 90004 | 103 | 8004 | 2026-06-12 20:00:00 | 2026-08-12 | NULL | refunded |
| 90005 | 102 | 8005 | 2026-09-20 14:00:00 | 2026-11-20 | NULL | valid |

示例数据（deals，5行）：

| deal_id | deal_name | category | merchant_id |
|---------|-----------|----------|-------------|
| 101 | 双人火锅套餐 | 餐饮 | 9001 |
| 102 | 精剪洗吹套餐 | 丽人 | 9002 |
| 103 | 密室逃脱双人票 | 休闲娱乐 | 9003 |
| 104 | 自助烤肉单人券 | 餐饮 | 9004 |
| 105 | 皮肤管理体验券 | 丽人 | 9005 |

### 3. 解题思路

口径与边界：①统计对象限定"状态已收敛"的券：verified 与 unused_expired，已退款券未产生到店履约预期、未到期券（valid）结局未定，两者都不能进分母，否则未到期券越多核销率被压得越低，跨品类比较全部失真；②取数范围限定6-8月售出的券，保证到统计日（9月底）基本都已到期收敛；③分子只算 verify_time 非空的核销券；④退款率作为伴随指标一并列出，退款异常高的品类要先洗数据再谈核销。实现路径：明细上做条件聚合（一次扫描出各状态计数）最直接；也可先按 deal 预聚合再 JOIN 品类维表，方便复用 deal 粒度的中间结果。**【加分点】** 主动区分"到期核销率"与"实时核销率"两个口径，并说明例行报表应固定用前者做跨期比较。

### 4. 参考解法

解法一：明细级条件聚合，一次扫描出全部状态计数与核销率。

```sql
SELECT d.category                                        AS 品类,
       COUNT(*)                                          AS 售出券数,
       SUM(o.status = 'verified')                        AS 已核销券数,     -- 布尔表达式求和=计数
       SUM(o.status = 'unused_expired')                  AS 过期未核销数,
       SUM(o.status = 'refunded')                        AS 退款券数,
       ROUND(SUM(o.status = 'refunded') / COUNT(*), 4)   AS 退款率,
       ROUND(SUM(o.status = 'verified')
             / NULLIF(SUM(o.status IN ('verified', 'unused_expired')), 0), 4) AS 到期核销率
       -- 分母只含状态已收敛的券，未到期(valid)与退款(refunded)均不进分母
FROM coupons o
JOIN deals d ON d.deal_id = o.deal_id
WHERE o.sold_time >= '2026-06-01' AND o.sold_time < '2026-09-01'  -- 已过主售卖期，状态基本收敛
GROUP BY d.category
ORDER BY 到期核销率;
```

结果解读：若丽人品类核销率显著低于餐饮，通常是"冲动购买+预约门槛"导致，运营动作是缩短有效期、上线自动预约提醒，而不是简单降价。

解法二：两层预聚合——先按 deal 收敛，再 JOIN 品类维表汇总（中间结果可复用）。

```sql
WITH deal_stat AS (               -- 第一步：团购单粒度先收敛状态计数
    SELECT deal_id,
           SUM(status = 'verified')                       AS verified_cnt,
           SUM(status = 'unused_expired')                 AS expired_cnt
    FROM coupons
    WHERE sold_time >= '2026-06-01' AND sold_time < '2026-09-01'
    GROUP BY deal_id
)
SELECT d.category                              AS 品类,
       SUM(s.verified_cnt)                     AS 已核销券数,
       SUM(s.verified_cnt + s.expired_cnt)     AS 已收敛券数,
       ROUND(SUM(s.verified_cnt)
             / NULLIF(SUM(s.verified_cnt + s.expired_cnt), 0), 4) AS 到期核销率
FROM deal_stat s
JOIN deals d ON d.deal_id = s.deal_id
GROUP BY d.category
ORDER BY 到期核销率;
```

结果解读：deal 粒度中间表可直接复用到"单团购核销率Top榜"，一次计算多处使用；与解法一结果完全一致，差异在工程形态而非口径。

### 5. 性能分析与优化

解法一对 coupons×deals 做一次 JOIN 后聚合，JOIN 规模为券量级（百万级），主键 JOIN 成本可控；解法二先在 coupons 上聚合（扫描同样不可省），但 JOIN 发生在收敛后（deal 数远小于券数），JOIN 阶段更轻，且中间结果可落表复用，适合多报表共用的场景。可执行优化：①coupons 建 (sold_time, status) 或 (deal_id, status) 复合索引；②状态判定如果历史上存在"状态与 verify_time 不一致"的脏数据，加一道一致性校验（verify_time 非空但状态非 verified 的行数应为0）；③若券量巨大且按月例行，可按月分区或按月增量落"券状态日快照表"；④退款有滞后性，统计日前几天的批次退款率会虚低，可在口径中加"售出后N天才纳入统计"的成熟期规则。

### 6. 面试延伸考点

- **为什么不用"核销数/售出数"这个更直观的公式？** 要点：未到期券分母未收敛，会随统计日选择剧烈波动，且新售卖多的品类被系统性低估；到期口径才可跨品类、跨期比较。
- **如何判断某品类核销率下滑是选品问题还是有效期问题？** 要点：按有效期长度分层对比核销率，控制品类后看有效期效应；再看售出-核销间隔分布，若间隔集中在末期说明有效期卡太紧。
- **核销率和复购（再次购买同品类券）有什么关系，怎么一起看？** 要点：核销是履约转化，复购是价值放大；可构建"购买→核销→再购"三步漏斗，定位卡点在哪一步。

### 7. 业务拓展思考

核销率应成为招商与选品的准入指标：对连续两期核销率低于品类均值的 deal 降权曝光，对高核销 deal 给"放心购"标签并追加流量。口径延展上，可计算"核销时距"（售出到核销的天数分布）反推有效期设计，用"提前到期提醒"减少 unused_expired；也可引入"到店转化漏斗"（浏览→购买→核销→评价），把核销率放进全链路看，避免只优化单点。与商家联动，核销率异常低的商家可触发履约暗访，防止套餐到店加价等伤害体验的行为。

## LL-24 月活跃用户下单频次分层：券包策略的用户底座

### 1. 业务背景

用户运营团队每月对活跃用户做频次分层：当月完成1单的"新客/低频层"、2-3单的"成长层"、4-5单的"高潜层"、6单及以上的"忠实层"。分层是券包与权益策略的底座——低频层发无门槛券促二单，成长层用满减券拉频次，忠实层转会员权益提留存。运营负责人需要每层的人数、人数占比与单量占比：如果忠实层只占10%人数却贡献50%单量，资源就该向保层防流失倾斜；如果成长层向高潜层的升级率下滑，说明中间权益断层。同时频次分层是"行为分层"，要与"价值分层"（客单价/金额）交叉才能定券面额。用户产生订单，平台做分层与权益设计，商家承接各层用户的消费。统计月为2026年9月，口径为当月 completed 订单。

### 2. 表结构说明

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| biz_type | VARCHAR(16) | 品类：外卖/闪购/到店 |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（5行）：

| order_id | user_id | biz_type | pay_time | order_amount | status |
|----------|---------|----------|----------|--------------|--------|
| 100001 | 8001 | 外卖 | 2026-09-01 11:50:00 | 33.00 | completed |
| 100002 | 8001 | 外卖 | 2026-09-03 19:20:00 | 28.50 | completed |
| 100003 | 8001 | 外卖 | 2026-09-06 12:10:00 | 35.00 | canceled |
| 100004 | 8002 | 闪购 | 2026-09-05 10:15:00 | 56.00 | completed |
| 100005 | 8003 | 外卖 | 2026-09-08 18:30:00 | 47.20 | completed |

### 3. 解题思路

口径与边界：①活跃用户 = 当月至少一笔 completed 订单的用户，取消单完全剔除（若取消单计入频次，刷单与犹豫单都会污染分层）；②分层边界为业务约定：1单 / 2-3单 / 4-5单 / ≥6单，边界必须左闭右闭且不重不漏，写 CASE 时按升序短路判断；③输出三组数：每层人数、人数占比、单量占比，单量占比是资源分配的真正依据；④分层粒度是"月"，跨月要重算（用户层别会迁移），如果要做层别迁移矩阵需要按月快照。实现路径：先收敛到用户粒度计数，再打层标签，最后聚合+窗口算占比；另一路用 INTERVAL+ELT 函数分桶并转成一行宽表。**【加分点】** 提出"单量占比与人数占比的比值"（单量集中度）作为忠实层价值量的速读指标。

### 4. 参考解法

解法一：用户粒度计数 + CASE 分层 + 窗口占比（长表输出，最通用）。

```sql
WITH ucnt AS (                    -- 第一步：收敛到用户粒度，统计9月完成单量
    SELECT user_id, COUNT(*) AS ord_cnt
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-09-01' AND pay_time < '2026-10-01'
    GROUP BY user_id
),
layered AS (                      -- 第二步：按业务边界打层标签（升序短路，不重不漏）
    SELECT CASE WHEN ord_cnt = 1            THEN '01_1单(低频)'
                WHEN ord_cnt <= 3           THEN '02_2-3单(成长)'
                WHEN ord_cnt <= 5           THEN '03_4-5单(高潜)'
                ELSE '04_6单及以上(忠实)' END        AS freq_layer,
           ord_cnt
    FROM ucnt
)
SELECT freq_layer                                     AS 频次分层,
       COUNT(*)                                       AS 人数,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2)    AS 人数占比pct,
       ROUND(SUM(ord_cnt) * 100.0 / SUM(SUM(ord_cnt)) OVER (), 2) AS 单量占比pct,
       ROUND(SUM(ord_cnt) * 1.0 / COUNT(*), 1)        AS 层内人均单量
FROM layered
GROUP BY freq_layer
ORDER BY freq_layer;
-- SUM(COUNT(*)) OVER ()：先对分层数出人数，再开全表窗口求总人数，聚合套窗口的固定范式
```

结果解读：典型外卖分布是低频层人数占比最高但单量占比低，忠实层反之；单量占比除以人数占比即为各层的单量集中度，大于1的层是收入基本盘。

解法二：INTERVAL+ELT 函数分桶 + 条件聚合一行宽表（函数分桶 + 行转列组合技）。

```sql
WITH ucnt AS (                    -- 用户粒度完成单量，同解法一
    SELECT user_id, COUNT(*) AS ord_cnt
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-09-01' AND pay_time < '2026-10-01'
    GROUP BY user_id
),
lv AS (                           -- INTERVAL(n,2,4,6)：n<2返回0，<4返回1，<6返回2，否则3
    SELECT ELT(INTERVAL(ord_cnt, 2, 4, 6) + 1,
               '1单', '2-3单', '4-5单', '6单及以上')  AS freq_layer,   -- ELT按1起下标取标签
           ord_cnt
    FROM ucnt
)
SELECT COUNT(*)                                   AS 活跃用户数,
       SUM(freq_layer = '1单')                    AS `低频_人数`,     -- 布尔求和做行转列
       ROUND(SUM(freq_layer = '1单') / COUNT(*) * 100, 2) AS `低频_占比pct`,
       SUM(freq_layer = '2-3单')                  AS `成长_人数`,
       ROUND(SUM(freq_layer = '2-3单') / COUNT(*) * 100, 2) AS `成长_占比pct`,
       SUM(freq_layer = '4-5单')                  AS `高潜_人数`,
       ROUND(SUM(freq_layer = '4-5单') / COUNT(*) * 100, 2) AS `高潜_占比pct`,
       SUM(freq_layer = '6单及以上')              AS `忠实_人数`,
       ROUND(SUM(freq_layer = '6单及以上') / COUNT(*) * 100, 2) AS `忠实_占比pct`
FROM lv;
```

结果解读：一行宽表直接嵌入月报摘要页；分层数多时行转列会急剧变宽，可只保留占比列或交由 BI 透视。

### 5. 性能分析与优化

两法主体都是一次订单表扫描 + GROUP BY 用户（这是本查询最大开销，订单千万级时哈希聚合内存与落盘需关注）+ 一次轻量聚合输出。CASE 与 INTERVAL 都是行内表达式，不产生额外代价差异；解法二聚合输出只有一行，几乎可忽略。可执行优化：①orders 建 (status, pay_time) 复合索引或按月分区，把扫描裁剪到单月；②若常态月报，预聚合"用户×月单量表"落表，分层查询只扫用户级数据（量级缩小一个数量级）；③INTERVAL 函数分桶边界必须升序书写，写错顺序不会报错但结果错乱，代码评审要重点看；④跨月迁移矩阵用两个月快照 FULL JOIN（MySQL用 LEFT JOIN + UNION 模拟），此时用户粒度中间表复用价值最大。

### 6. 面试延伸考点

- **如何构建"上月层别→本月层别"的迁移矩阵？** 要点：两月各自分层后按 user_id JOIN，行=上月层、列=本月层做行转列计数；重点关注忠实层流出率与低频层升级率。
- **频次分层和价值分层（GMV分层）冲突时怎么定策略？** 要点：做二维交叉分层（频次×客单），识别"高频低客单"（提客单）与"低频高客单"（提频次）两类错配人群，券策略完全不同。
- **为什么取消单要剔除，什么情况下反而要研究取消单？** 要点：分层度量的是有效消费行为，取消单剔除；但取消率本身是体验指标，异常取消集中在某些层时提示券策略引发羊毛行为。

### 7. 业务拓展思考

频次分层是生命周期运营的坐标系：每月输出迁移矩阵后，可对"忠实层流出用户"触发挽回券包，对"低频层 stuck 用户"排查供给与配送体验而非继续发券。口径延展上，可把自然月改为"滚动28天"消除月度天数差异，也可按品类拆分层别（外卖高频、闪购中频、到店低频，混在一个口径里分层会失真）。进一步与商家联动：忠实层用户的常购商家清单可用于"商家失联预警"——当忠实层的常购商家下线时，该用户流失概率显著上升，可提前推替代商家。

## LL-25 准时率按区域×时段矩阵：履约质量的差格定位

### 1. 业务背景

履约质量周会上，运营负责人要一张"区域×时段"的准时率矩阵：行是配送区域，列是早高峰/午高峰/下午/晚高峰/夜宵五个时段，格子是"送达时间 ≤ 承诺送达时间"的订单占比。矩阵的用途是定位"差格"——例如 A 区整体健康但晚高峰准时率跌破85%，说明是晚高峰运力或特定商家出餐问题，而不是区域整体能力问题，治理动作因此完全不同。准时率的分母是当时段已送达订单，分子是其中准时送达的订单；承诺送达时间由平台按历史时效动态给出，因此准时率也隐含了承诺算法的松紧，解读时要和平均超时分钟数一起看。用户感知的是"是否迟到"，商家影响出餐段，骑手决定在途段，平台用矩阵把责任定位到最小治理单元。

### 2. 表结构说明

deliveries 配送单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| delivery_id | BIGINT | 配送单ID，主键 |
| order_id | BIGINT | 关联订单ID |
| region_id | INT | 配送区域ID |
| accept_time | DATETIME | 骑手接单时间 |
| promise_time | DATETIME | 平台承诺送达时间 |
| deliver_time | DATETIME | 实际送达时间 |
| status | VARCHAR(16) | 配送状态：delivered已送达 / canceled已取消 / exception异常单 |

示例数据（5行）：

| delivery_id | order_id | region_id | accept_time | promise_time | deliver_time | status |
|-------------|----------|-----------|-------------|--------------|--------------|--------|
| 110001 | 120001 | 41 | 2026-09-15 11:32:00 | 2026-09-15 12:05:00 | 2026-09-15 11:58:00 | delivered |
| 110002 | 120002 | 41 | 2026-09-15 17:40:00 | 2026-09-15 18:20:00 | 2026-09-15 18:35:00 | delivered |
| 110003 | 120003 | 42 | 2026-09-15 11:50:00 | 2026-09-15 12:25:00 | 2026-09-15 12:20:00 | delivered |
| 110004 | 120004 | 42 | 2026-09-15 21:10:00 | 2026-09-15 21:50:00 | 2026-09-15 21:45:00 | delivered |
| 110005 | 120005 | 41 | 2026-09-15 12:05:00 | 2026-09-15 12:40:00 | NULL | canceled |

### 3. 解题思路

口径与边界：①准时判定 deliver_time <= promise_time，只统计 delivered 单，取消单与异常单剔除；②时段按 accept_time 的小时划分：早高峰7-9点、午高峰10-13点、下午14-16点、晚高峰17-20点、夜宵21-23点，边界含两端；③矩阵形态：区域为行、时段为列，用条件聚合行转列实现，AVG 对 NULL 自动忽略的特性能让"不在该时段的订单"自然不进均值，是行转列最干净的写法；④某格订单量过小时准时率波动大，应伴随输出样本量，样本不足的格子标注低置信。实现路径：先在 CTE 里完成状态过滤与准时标记、小时提取，再按区域聚合。**【面试高频】** "AVG(CASE WHEN ...) 里 ELSE 不写会怎样"是行转列的经典追问——答案是 ELSE NULL，AVG 忽略 NULL，恰好是我们想要的"分时段隔离"效果。

### 4. 参考解法

解法一：条件聚合行转列，直接输出宽表矩阵（汇报页即用形态）。

```sql
WITH dv AS (                      -- 第一步：洗样本并打准时标记、提取接单小时
    SELECT region_id,
           HOUR(accept_time) AS hr,                                -- 取接单小时0~23
           CASE WHEN deliver_time <= promise_time THEN 1 ELSE 0 END AS is_ontime  -- 准时=1
    FROM deliveries
    WHERE status = 'delivered'                        -- 只要送达单
      AND accept_time >= '2026-09-15' AND accept_time < '2026-09-22'  -- 周维度窗口
)
SELECT region_id                                        AS 区域ID,
       ROUND(AVG(CASE WHEN hr BETWEEN 7  AND 9  THEN is_ontime END), 4) AS `早高峰准时率`,
       ROUND(AVG(CASE WHEN hr BETWEEN 10 AND 13 THEN is_ontime END), 4) AS `午高峰准时率`,
       ROUND(AVG(CASE WHEN hr BETWEEN 14 AND 16 THEN is_ontime END), 4) AS `下午准时率`,
       ROUND(AVG(CASE WHEN hr BETWEEN 17 AND 20 THEN is_ontime END), 4) AS `晚高峰准时率`,
       ROUND(AVG(CASE WHEN hr BETWEEN 21 AND 23 THEN is_ontime END), 4) AS `夜宵准时率`,
       COUNT(*)                                               AS 总样本量
FROM dv
GROUP BY region_id
ORDER BY region_id;
-- 每个CASE不带ELSE：非该时段订单得到NULL，AVG自动忽略，分母即该时段样本数
```

结果解读：矩阵中低于0.85的格子即为差格；横向看同一区域不同时段可识别时段性缺口，纵向看同一时段跨区域可识别结构性弱区。

解法二：时段维表 + 区域全集 CROSS JOIN 后 LEFT JOIN 订单，长表输出且保证矩阵无缺格。

```sql
WITH slots AS (                   -- 第一步：时段维表（起止小时含两端）
    SELECT '早高峰' AS slot_name, 7  AS h1, 9  AS h2
    UNION ALL SELECT '午高峰', 10, 13
    UNION ALL SELECT '下午',   14, 16
    UNION ALL SELECT '晚高峰', 17, 20
    UNION ALL SELECT '夜宵',   21, 23
),
regions AS (                      -- 第二步：区域全集（保证无单区域也出现在矩阵里）
    SELECT DISTINCT region_id FROM deliveries
),
stat AS (                         -- 第三步：区域×时段全集格，左连接命中的订单算准时率
    SELECT r.region_id, s.slot_name,
           ROUND(AVG(CASE WHEN d.deliver_time <= d.promise_time
                          THEN 1 ELSE 0 END), 4) AS ontime_rate,   -- 未命中格AVG(NULL)=NULL
           COUNT(d.delivery_id)              AS sample_cnt         -- 只数命中的配送单
    FROM regions r
    CROSS JOIN slots s                                   -- 区域×时段笛卡尔全集
    LEFT JOIN deliveries d
           ON d.region_id = r.region_id
          AND d.status = 'delivered'
          AND HOUR(d.accept_time) BETWEEN s.h1 AND s.h2  -- 命中该时段
          AND d.accept_time >= '2026-09-15' AND d.accept_time < '2026-09-22'
    GROUP BY r.region_id, s.slot_name
)
SELECT region_id                                   AS 区域ID,
       slot_name                                   AS 时段,
       COALESCE(ontime_rate, -1)                   AS 准时率,      -- 无单格用-1占位，BI里映射为'无数据'
       sample_cnt                                  AS 样本量,
       CASE WHEN sample_cnt < 30 THEN '样本不足' ELSE '可信' END AS 置信标记
FROM stat
ORDER BY region_id, slot_name;
```

结果解读：长表形态适合入库与 BI 再透视，CROSS JOIN 保证某区域某时段零订单时格子依然存在（显示无数据），避免宽表法"缺列缺行"造成矩阵误读。

### 5. 性能分析与优化

解法一一次扫描 deliveries 后按区域聚合，代价 O(N)；CASE 行转列在内存中完成，无额外 JOIN。解法二多出 slots×regions 的笛卡尔集（区域数×5，量级很小），但 LEFT JOIN 的 ON 条件里对 accept_time 包了 HOUR 函数，索引 (region_id, status, accept_time) 只能用到前缀，时段过滤退化为区域内的行扫描；改进写法是把订单先按 (region_id, HOUR) 预聚合再与维表 JOIN，或把时段起止转成左闭右开时间区间后用范围条件。可执行优化：①deliveries 建 (region_id, status, accept_time) 复合索引并按周分区；②样本过滤提前到 CTE，避免在 JOIN 后重复判断状态；③准时标记 is_ontime 可物化进表（写入时计算），查询省去时间比较；④矩阵例行化后按"区域×时段×日"落表，周会数据直接读结果表。

### 6. 面试延伸考点

- **承诺送达时间本身由算法给出，准时率高一定代表体验好吗？** 要点：承诺给得宽松，准时率虚高但用户等待变长；应同时监控"承诺时长"与"实际时长"两个分布，防止用承诺换准时率。
- **商家出餐慢导致的迟到怎么从准时率里剥离？** 要点：把 (accept→pickup) 出餐段超时的订单单独标记，输出"剔除出餐责任的骑手准时率"，责任分离后再考核。
- **矩阵里样本量小的格子怎么处理？** 要点：显示但标低置信，或做经验贝叶斯收缩（向区域整体均值收缩），避免小样本极端值触发误动作。

### 7. 业务拓展思考

准时率矩阵是运力调度与承诺算法联调的仪表盘：对差格区域，动作依次是查运力单骑比（联动 LL-22）、查出餐慢商家、最后才调承诺算法参数。口径延展上，可输出"准时率+平均超时分钟"双指标矩阵（准时率85%但平均超时仅2分钟与平均超时15分钟的治理优先级完全不同），也可把时段颗粒细化到30分钟档以捕捉高峰尖刺。长期看，准时率应与取消率、差评率构成履约质量三件套，任何一项异常都触发同区域交叉下钻，形成从指标到动作的固定链路。
## LL-26 外卖+闪购跨品类连带分析：一屏多用是否成立

### 1. 业务背景

平台战略团队想验证"超级平台"假设：用户是否因为一个App既能点外卖又能买闪购（超市便利/鲜花药品即时零售）而提高了整体使用价值。增长负责人需要三个数字：9月活跃用户中来自外卖的用户规模、其中"同一自然日既点外卖又下闪购"的同日连带用户占比（强连带），以及"月内两个品类都买过"的期间连带用户占比（弱连带）；同时对比连带用户与纯外卖用户的人均消费（ARPU），评估跨品类用户的溢价。结论决定首页Feed是否上闪购卡片、是否推"外卖+闪购联合券"。用户产生跨品类行为，商家与骑手分品类履约，平台做交叉供给运营。若同日连带占比可观，说明即时零售场景天然互通，交叉引流有杠杆；若只有弱连带，则更多靠长期品类教育。

### 2. 表结构说明

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| biz_type | VARCHAR(16) | 品类：外卖 / 闪购 / 到店 |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（5行）：

| order_id | user_id | biz_type | pay_time | order_amount | status |
|----------|---------|----------|----------|--------------|--------|
| 130001 | 8001 | 外卖 | 2026-09-01 11:50:00 | 33.00 | completed |
| 130002 | 8001 | 闪购 | 2026-09-01 20:10:00 | 45.50 | completed |
| 130003 | 8002 | 外卖 | 2026-09-02 12:05:00 | 28.00 | completed |
| 130004 | 8003 | 闪购 | 2026-09-02 15:30:00 | 61.00 | canceled |
| 130005 | 8003 | 到店 | 2026-09-08 18:40:00 | 128.00 | completed |

### 3. 解题思路

口径与边界：①只统计 completed 订单，取消单不构成有效品类行为；②两类连带口径分开：期间连带 = 月内两种品类都有完成单的用户；同日连带 = 存在某个自然日两种品类都下单的用户，后者更严格、更接近"一次会话多场景"；③分母：外卖连带率用"外卖用户数"做分母，ARPU 对比时连带组与纯外卖组必须互斥（否则重复计算）；④粒度收敛是本题主线：先收敛到"用户×日×品类"去重粒度再判断，否则订单明细直接 JOIN 会产生笛卡尔积式重复计数。实现路径：CTE 去重收敛 → HAVING/自连接判连带 → 聚合对比。**【避坑指南】** 直接 `FROM orders a JOIN orders b ON a.user_id=b.user_id` 会在多订单用户上爆炸出 O(N²) 中间结果，且不去重的 COUNT 是错的——先 GROUP BY 收敛是跨品类分析的第一动作。

### 4. 参考解法

解法一：收敛到用户×日×品类后，用户级条件聚合判定期间连带并对比 ARPU。

```sql
WITH ud AS (                      -- 第一步：收敛到 用户×日×品类 粒度，消除订单重复
    SELECT user_id,
           DATE(pay_time)  AS dt,                      -- 自然日
           biz_type,
           SUM(order_amount) AS amt                    -- 该用户该日该品类消费额
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-09-01' AND pay_time < '2026-10-01'
    GROUP BY user_id, DATE(pay_time), biz_type
),
user_flag AS (                    -- 第二步：用户级打品类标记，算月消费额
    SELECT user_id,
           MAX(biz_type = '外卖') AS has_wm,           -- MySQL布尔表达式参与MAX得0/1
           MAX(biz_type = '闪购') AS has_sg,
           SUM(amt)               AS month_amt
    FROM ud
    GROUP BY user_id
)
SELECT COUNT(*)                                                  AS 月活跃用户数,
       SUM(has_wm)                                               AS 外卖用户数,
       SUM(has_wm = 1 AND has_sg = 1)                            AS 期间连带用户数,
       ROUND(SUM(has_wm = 1 AND has_sg = 1) / NULLIF(SUM(has_wm), 0), 4) AS 外卖用户期间连带率,
       ROUND(AVG(CASE WHEN has_wm = 1 AND has_sg = 1 THEN month_amt END)
             / NULLIF(AVG(CASE WHEN has_wm = 1 AND has_sg = 0 THEN month_amt END), 0), 2) AS 连带vs纯外卖ARPU倍数
       -- 分子分母两组用户互斥：连带组(双品类) 对 纯外卖组(仅外卖)
FROM user_flag;
```

结果解读：期间连带率与ARPU倍数双高，说明跨品类用户价值显著，但这是相关性——是否推联合券要看实验增量。

解法二：用户×日×品类自连接，判定"同日跨品类"强连带（检验场景即时互通性）。

```sql
WITH ud AS (                      -- 同解法一，先收敛到 用户×日×品类
    SELECT user_id,
           DATE(pay_time) AS dt,
           biz_type
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-09-01' AND pay_time < '2026-10-01'
    GROUP BY user_id, DATE(pay_time), biz_type
),
wm AS (                           -- 外卖用户全集（分母）
    SELECT COUNT(DISTINCT user_id) AS cnt
    FROM ud WHERE biz_type = '外卖'
)
SELECT COUNT(DISTINCT a.user_id)                     AS 同日连带用户数,
       ROUND(COUNT(DISTINCT a.user_id) / NULLIF(MAX(w.cnt), 0), 4) AS 外卖用户同日连带率
FROM ud a                                            -- 外卖侧
JOIN ud b                                            -- 闪购侧
  ON a.user_id = b.user_id
 AND a.dt     = b.dt                                 -- 同一自然日
 AND a.biz_type = '外卖'
 AND b.biz_type = '闪购'
CROSS JOIN wm w;                                     -- 只为取出分母一行
```

结果解读：同日连带率若明显低于期间连带率，说明跨品类多为"不同天各买各的"，交叉推荐应主打场景唤醒（晚餐时段推便利店商品）而非同一会话内硬凑。

### 5. 性能分析与优化

两法第一步相同：GROUP BY (user_id, dt, biz_type) 收敛，扫描订单表一次，是主要开销；收敛后中间结果通常比订单明细小一到两个数量级。解法一只在收敛结果上聚合，代价可忽略；解法二的自连接在"用户×日"内做外卖×闪购配对，若用户单日多订单未先收敛会平方级爆炸，收敛后规模可控但仍应限制品类对数（本题只看外卖×闪购一对）。可执行优化：①orders 建 (status, pay_time) 或 (user_id, status, pay_time) 索引并按月分区；②收敛 CTE 结果物化落表，同日/期间/ARPU三个查询共用；③若扩展到三个品类两两连带，先算"用户×日"的品类集合（GROUP_CONCAT DISTINCT），再按集合字符串判定，避免 k×(k-1) 次自连接；④ARPU对比对异常大额订单敏感，可加99分位截尾（联动LL-18分位框架）。

### 6. 面试延伸考点

- **期间连带率高就说明品类互相带动吗？怎么验证因果？** 要点：可能只是高活跃用户天然买得多（选择偏差）；用联合券做A/B实验，对比实验组品类渗透率提升才是因果证据。
- **如果要下钻"外卖→闪购"的方向性连带（谁带着谁），怎么算？** 要点：对每个用户取首次外卖日与首次闪购日，比较先后（DATEDIFF符号），输出"外卖先行用户中N天内下闪购的比例"，形成品类迁移漏斗。
- **到店品类要不要纳入连带分析？** 要点：到店频次低、周期长，直接同日口径几乎测不到，应放宽为周/月窗口并单独解读；混在一个口径里会稀释结论。

### 7. 业务拓展思考

连带分析直接服务于流量分配与联合营销：同日连带强的时段（晚餐前后）在首页穿插闪购卡片，联合券按"外卖满减+闪购立减"组合发放，用补贴撬动第二品类首单。口径延展上，可构建品类迁移矩阵（月度首品类×次品类），量化"外卖是闪购的入口"这一命题；也可按城市分层看连带率，验证供给密度（闪购前置仓覆盖）对连带的约束——连带率低的城市先补供给再谈营销。对商家侧，连带用户聚集的商圈可招商"餐饮+便利"组合供给，提升骑手顺路单比例。

## LL-27 商家评分变化前后订单对比：评分下滑的单量代价

### 1. 业务背景

供给治理团队发现一批商家在9月初评分明显下滑（例如4.8掉到4.2，多因出餐慢、缺斤短两引发差评）。运营负责人要回答：评分下滑后，这些商家的单量与好评率发生了多大变化？如果后四周日均单量较前四周显著下跌，说明评分已经真实影响流量分配与用户选择，治理动作（联系整改、临时流量降权、要求出餐提速）就有明确优先级；若单量几乎不变，说明商家靠低价或稀缺性维持需求，治理应更温和。分析师以"评分变化日"为锚点，对比前后各28天的日均完成订单量与好评订单占比。用户用评分决定是否下单，商家是整改对象，平台需要干净的前后对比支撑治理决策。评分变动记录来自评分系统的事件日志。

### 2. 表结构说明

rating_change_log 评分变动日志表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| merchant_id | BIGINT | 商家ID |
| change_date | DATE | 评分变动生效日期 |
| old_rating | DECIMAL(2,1) | 变动前评分 |
| new_rating | DECIMAL(2,1) | 变动后评分 |

orders 订单表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| merchant_id | BIGINT | 商家ID |
| pay_time | DATETIME | 支付时间 |
| is_good_review | TINYINT | 该单评价是否好评：1好评 / 0中差评（未评价计0） |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（rating_change_log，5行）：

| merchant_id | change_date | old_rating | new_rating |
|-------------|-------------|------------|------------|
| 9001 | 2026-09-05 | 4.8 | 4.2 |
| 9002 | 2026-09-08 | 4.6 | 4.4 |
| 9003 | 2026-09-10 | 4.3 | 4.6 |
| 9004 | 2026-09-12 | 4.9 | 4.1 |
| 9005 | 2026-09-15 | 4.0 | 3.5 |

示例数据（orders，5行）：

| order_id | merchant_id | pay_time | is_good_review | status |
|----------|-------------|----------|----------------|--------|
| 140001 | 9001 | 2026-08-20 11:50:00 | 1 | completed |
| 140002 | 9001 | 2026-09-01 12:05:00 | 1 | completed |
| 140003 | 9001 | 2026-09-20 18:40:00 | 0 | completed |
| 140004 | 9002 | 2026-09-03 11:30:00 | 1 | completed |
| 140005 | 9001 | 2026-09-25 11:20:00 | 0 | canceled |

### 3. 解题思路

口径与边界：①只分析"评分下滑"事件（new_rating < old_rating），评分上调商家是对照组不是治理对象，混入会稀释效应；②对比窗口 = 变化日前28天 vs 后28天，窗口太短受星期内周期扰动，太长混入其他事件；③指标：日均完成订单量（各除以28）与好评订单占比（is_good_review 均值，声明未评价计0的口径）；④订单取数窗口必须覆盖所有事件的窗口并集（约8月初至10月初），且要在 JOIN 条件内做窗口过滤，防止事件间互相串窗。实现路径：事件表为驱动表，订单按商家 JOIN 后用 DATEDIFF 判前后段；既可先按日预聚合再对比（大表友好），也可明细直连一次算完。**【加分点】** 主动指出"前后对比"不是因果——同期可能有季节性或平台流量波动，严谨做法是引入同商圈未变动商家做双重差分对照。

### 4. 参考解法

解法一：订单先按商家×日预聚合，再 JOIN 事件表分段对比（大表友好的两层结构）。

```sql
WITH chg AS (                     -- 第一步：筛选评分下滑事件
    SELECT merchant_id, change_date
    FROM rating_change_log
    WHERE new_rating < old_rating                     -- 只看下滑，上调作对照另算
),
daily AS (                        -- 第二步：订单收敛到 商家×日 粒度
    SELECT merchant_id,
           DATE(pay_time)     AS dt,
           COUNT(*)           AS ord_cnt,             -- 当日完成单量
           AVG(is_good_review) AS good_rate         -- 当日好评占比（未评价计0）
    FROM orders
    WHERE status = 'completed'
      AND pay_time >= '2026-08-01' AND pay_time < '2026-10-04'  -- 覆盖全部事件的±28天窗口
    GROUP BY merchant_id, DATE(pay_time)
)
SELECT c.merchant_id                                            AS 商家ID,
       ROUND(SUM(CASE WHEN d.dt >=  c.change_date - INTERVAL 28 DAY
                       AND d.dt <   c.change_date
                      THEN d.ord_cnt END) / 28.0, 1)            AS 前四周日均单量,
       ROUND(SUM(CASE WHEN d.dt >=  c.change_date
                       AND d.dt <   c.change_date + INTERVAL 28 DAY
                      THEN d.ord_cnt END) / 28.0, 1)            AS 后四周日均单量,
       ROUND(AVG(CASE WHEN d.dt >=  c.change_date - INTERVAL 28 DAY
                       AND d.dt <   c.change_date
                      THEN d.good_rate END), 4)                 AS 前四周好评率,
       ROUND(AVG(CASE WHEN d.dt >=  c.change_date
                       AND d.dt <   c.change_date + INTERVAL 28 DAY
                      THEN d.good_rate END), 4)                 AS 后四周好评率
FROM chg c
JOIN daily d ON d.merchant_id = c.merchant_id
GROUP BY c.merchant_id;
```

结果解读：后四周日均单量相对前四周的跌幅超过两成即可判定"评分已伤单量"，整改优先级最高；好评率同步下滑说明体验问题在持续发生，而非一次性事件。

解法二：明细直连事件表，行转列一次算完前后指标（一商家一行，嵌报告最方便）。

```sql
WITH chg AS (                     -- 评分下滑事件
    SELECT merchant_id, change_date, old_rating, new_rating
    FROM rating_change_log
    WHERE new_rating < old_rating
)
SELECT c.merchant_id,
       c.old_rating                                            AS 变动前评分,
       c.new_rating                                            AS 变动后评分,
       ROUND(COUNT(CASE WHEN o.pay_time <  c.change_date
                         THEN o.order_id END) / 28.0, 1)       AS 前四周日均单量,
       ROUND(COUNT(CASE WHEN o.pay_time >= c.change_date
                         THEN o.order_id END) / 28.0, 1)       AS 后四周日均单量,
       ROUND(AVG(CASE WHEN o.pay_time <  c.change_date
                      THEN o.is_good_review END), 4)           AS 前四周好评率,
       ROUND(AVG(CASE WHEN o.pay_time >= c.change_date
                      THEN o.is_good_review END), 4)           AS 后四周好评率
FROM chg c
LEFT JOIN orders o                                   -- LEFT：无单商家也保留，单量显示0
       ON o.merchant_id = c.merchant_id
      AND o.status = 'completed'
      AND o.pay_time >= c.change_date - INTERVAL 28 DAY   -- 窗口过滤写进JOIN条件
      AND o.pay_time <  c.change_date + INTERVAL 28 DAY   -- 防止事件窗口互相串数据
GROUP BY c.merchant_id, c.old_rating, c.new_rating;
```

结果解读：窗口条件放在 JOIN ON 里而非外层 WHERE，配合 LEFT JOIN 才能保住"变化后零订单"的商家行——若误写进 WHERE，LEFT JOIN 会退化成 INNER JOIN，极端商家被静默丢弃。

### 5. 性能分析与优化

解法一先把订单表收敛成"商家×日"（行数从订单级降到商家×天数级），与事件表 JOIN 的规模很小，适合订单量大、事件多的生产场景；代价是多一次全量 GROUP BY。解法二直接明细 JOIN，少一层聚合，但 JOIN 的中间结果是"事件×窗口内订单"明细，事件多、窗口宽时中间结果膨胀，且每个商家要在 orders 里做两段范围扫描。可执行优化：①orders 建 (merchant_id, status, pay_time) 复合索引，两法的 JOIN/聚合都能走索引范围；②rating_change_log 建 (merchant_id) 或 (change_date) 索引；③一商家多次评分变动时，解法二会一行一事件地重复计算重叠窗口，需先按商家取"最近一次下滑事件"去重（ROW_NUMBER 取 rn=1）；④滚动对比可参数化为任意 N 天，输出"前N日日均、后N日日均、变化率"三列模板，便于治理看板复用。

### 6. 面试延伸考点

- **单量下跌一定能归因于评分下滑吗？怎么设计更可信的对照？** 要点：引入同商圈、同品类、评分未变的商家做平行对照，用双重差分（前后差值再相减）剔除大盘季节性；再不行就做恢复实验（临时提升曝光看单量弹性）。
- **好评率口径里"未评价计0"合理吗？** 要点：会低估好评率，应改为"好评数/有评价订单数"并另报评价率；两个口径都要展示，防止"好评率降了"其实是"评价率降了"。
- **评分下降与单量下降谁先发生？** 要点：看两类事件的时间先后（评分是结果，单量是反馈，也可能是单量先跌导致差评占比被动升高），用逐日曲线而不是28天粗对比判断传导顺序。

### 7. 业务拓展思考

该对比模板可固化为"商家健康预警"：评分下滑事件自动触发前后单量对比，跌幅超阈值的商家进入治理队列，整改后跟踪"恢复曲线"评估治理有效性。口径延展上，可把对比指标从单量扩展到退款率、配送差评率，定位下滑根因（出餐慢还是品控差）；也可输出"评分-单量弹性"（评分每降0.1分的单量跌幅中位数）作为流量分配模型的输入。对平台而言，治理的终点不是处罚而是恢复：把整改后的评分回升商家重新扶回原流量位，形成"预警-治理-恢复"闭环。

## LL-28 每个骑手单均配送时长与单量排名：评优与培训名单

### 1. 业务背景

运力运营团队每月评选"区域骑行标兵"：在每个配送区域内，按骑手的单均配送时长（接单到送达）升序排名，前三名进入评优名单并获得冲单奖励加成；同时设立参评门槛——当月完成单量不足60单的骑手不参与排名（样本太少，单均时长波动大，排名无意义）。这份名单也用于反向管理：排名垫底的骑手进入培训队列，重点辅导路线规划与批量取送。单量冠军与时长冠军往往不是同一人（冲单型跑得多但每单慢，稳健型单均快但量少），因此名单必须同时展示两项指标，由运营人工定夺。用户感知骑手时效，骑手是被考核者，区域是公平性单元（不同区域路况差异大，必须区域内排名而非全局排名），平台用排名牵引行为。

### 2. 表结构说明

riders 骑手表：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| rider_id | BIGINT | 骑手ID，主键 |
| rider_name | VARCHAR(32) | 骑手姓名（虚构） |

### 3. 解题思路

口径与边界：①样本只取 delivered 单，时长 = accept_time 到 deliver_time 的分钟数，脏数据（倒挂、超4小时）剔除；②参评门槛：月完成单量 ≥ 60，先过滤再排名，避免低样本骑手凭三两快单霸榜；③排名按区域分区内、单均时长升序，用 RANK（并列同名次有跳号）；④同时输出完成单量，方便运营在"快而少"与"稍慢但量大"之间权衡；⑤面试中必须能说清 RANK/DENSE_RANK/ROW_NUMBER 三者在并列值时的行为差异，并说明评优场景选哪个、为什么。实现路径：CTE 按骑手聚合单量与单均时长 → HAVING 过门槛 → 窗口排名；对照写法用相关子查询数"比我快的人数"实现 TopN。**【面试高频】** "不用窗口函数怎么写分组TopN"是十年经典考题，相关子查询法必须会。

### 4. 参考解法

解法一：骑手级聚合 + RANK 窗口排名（标准解法，附三种排名函数差异注释）。

```sql
WITH rider_stat AS (              -- 第一步：按骑手聚合9月有效单量与单均时长
    SELECT d.rider_id,
           r.region_id,
           COUNT(*)                                                        AS done_cnt,
           AVG(TIMESTAMPDIFF(SECOND, d.accept_time, d.deliver_time) / 60.0) AS avg_min  -- 单均分钟
    FROM deliveries d
    JOIN riders r ON r.rider_id = d.rider_id
    WHERE d.status = 'delivered'                        -- 只要送达单
      AND d.accept_time >= '2026-09-01' AND d.accept_time < '2026-10-01'
      AND d.deliver_time > d.accept_time                -- 剔除时间倒挂脏数据
      AND TIMESTAMPDIFF(MINUTE, d.accept_time, d.deliver_time) <= 240  -- 剔除超长异常
    GROUP BY d.rider_id, r.region_id
    HAVING COUNT(*) >= 60                               -- 参评门槛：月单量不少于60单
)
SELECT rider_id                                        AS 骑手ID,
       region_id                                       AS 区域ID,
       ROUND(avg_min, 1)                               AS 单均时长分钟,
       done_cnt                                        AS 完成单量,
       RANK()       OVER (PARTITION BY region_id ORDER BY avg_min ASC) AS rk_rank,   -- 并列同名次、跳号 1,1,3
       DENSE_RANK() OVER (PARTITION BY region_id ORDER BY avg_min ASC) AS rk_dense,  -- 并列同名次、不跳号 1,1,2
       ROW_NUMBER() OVER (PARTITION BY region_id ORDER BY avg_min ASC) AS rn         -- 强制唯一 1,2,3
FROM rider_stat;
-- 评优取前三：评优允许并列用RANK；若必须恰好三人则用ROW_NUMBER再按完成单量做次级排序
```

结果解读：结果同时保留三种名次便于讨论规则；实际发榜时以 rk_rank ≤ 3 过滤，"快而少"与"稍慢但量大"的骑手可通过单量列人工校准。

解法二：相关子查询实现分组TopN（不用窗口函数的经典写法，面试常考）。

```sql
WITH rider_stat AS (              -- 同解法一：骑手级聚合 + 门槛过滤
    SELECT d.rider_id,
           r.region_id,
           COUNT(*)                                                         AS done_cnt,
           AVG(TIMESTAMPDIFF(SECOND, d.accept_time, d.deliver_time) / 60.0) AS avg_min
    FROM deliveries d
    JOIN riders r ON r.rider_id = d.rider_id
    WHERE d.status = 'delivered'
      AND d.accept_time >= '2026-09-01' AND d.accept_time < '2026-10-01'
      AND d.deliver_time > d.accept_time
      AND TIMESTAMPDIFF(MINUTE, d.accept_time, d.deliver_time) <= 240
    GROUP BY d.rider_id, r.region_id
    HAVING COUNT(*) >= 60
)
SELECT * FROM (
    SELECT t.rider_id,
           t.region_id,
           ROUND(t.avg_min, 1)                            AS 单均时长分钟,
           t.done_cnt                                     AS 完成单量,
           (SELECT COUNT(*) + 1                           -- "比我更快的人数"+1 就是我的名次
              FROM rider_stat s
             WHERE s.region_id = t.region_id              -- 同区域才参与比较
               AND s.avg_min < t.avg_min)                 -- 严格小于：并列者同名次，等价RANK
             AS rk
    FROM rider_stat t
) x
WHERE x.rk <= 3                                          -- 每区域前三名
ORDER BY x.region_id, x.rk;
```

结果解读：子查询里 `COUNT(*)+1` 的计法与 RANK() 在并列时行为一致；把 `<` 改成 `<=` 再 DISTINCT 可模拟 DENSE_RANK，这套对应关系面试时讲清楚非常加分。

### 5. 性能分析与优化

解法一聚合后一次窗口排序，代价 O(M·logM)（M=过门槛骑手数，通常远小于订单量）；解法二对每个骑手执行一次相关子查询，复杂度 O(M²) 量级，M=几百尚可，M=几万会明显劣化，且优化器难以把相关子查询重写为 JOIN。可执行优化：①deliveries 建 (rider_id, status, accept_time) 复合索引，聚合走索引范围扫描；②riders.region_id 建索引加速 JOIN；③解法二可改写为自 JOIN 聚合（rider_stat s JOIN rider_stat t ON 同区域 AND s.avg_min < t.avg_min，GROUP BY t）把逐行探测变成一次哈希连接，代价降到 O(M·logM)；④月度例行化时把 rider_stat 落表，再在结果表上做排名，两句都变轻；⑤门槛（60单）与名次（Top3）都应做成参数，防止写死在SQL里。

### 6. 面试延伸考点

- **RANK、DENSE_RANK、ROW_NUMBER 在并列时分别怎么表现，评优该用哪个？** 要点：RANK 并列跳号、DENSE_RANK 并列不跳号、ROW_NUMBER 唯一；评优允许并列荣誉用 RANK，涉及固定名额奖金（只发三人）用 ROW_NUMBER 并补次级排序键。
- **单均时长排名公平吗？怎么修正区域与时段差异？** 要点：不同区域路况、楼宇密度不同，可改用"相对值"——骑手单均时长相对区域同时段中位数的比值或z分数排名，消除环境差异。
- **门槛会不会把新骑手系统性挡在评优外？** 要点：会；可增设"新锐奖"按入职不满3月骑手单独排名，或用"前N单的单均时长"单独评估新人成长斜率。

### 7. 业务拓展思考

排名不止于评优：把区域 Top10% 骑手的路线特征（顺路单占比、批次取单数）提炼成培训教材，对垫底10%做定向辅导，比单纯奖惩更能改善整体时效。口径延展上，可加入"高峰时段单均时长"单独排名（高峰能力才是稀缺能力），或用"承诺时间达成率"替代绝对时长，让排名与用户体验直接挂钩。对平台调度，快骑手的接单模式可反哺派单策略（如给稳健型骑手更多顺路批次），把个人优势放大为系统效率。

## LL-29 新商家冷启期表现追踪：上线后4周曲线分型

### 1. 业务背景

商家成长团队对新上线商家执行"冷启追踪"标准动作：以商家上线日为 D0，追踪此后第1周（D0~D6）、第2周（D7~D13）、第3周（D14~D20）、第4周（D21~D27）的完成订单量与GMV，形成4周成长曲线。曲线形态决定运营动作：第1周高、逐周下滑的"高开低走"型说明冷启流量给了但承接不住（评分、出餐、缺货问题），要立即做履约诊断；逐周爬坡的"低开稳升"型说明自然增长健康，可追加流量放大。区域负责人每周要看本区域新商家的整批表现（按上线月分群），因此报表既要能输出单个商家的四周明细，也要能一键汇总到区域粒度。用户在冷启期被冷启流量触达，商家承接流量，平台调配冷启资源并评估ROI。

### 2. 表结构说明

| 字段名 | 类型 | 含义 |

| merchant_id | BIGINT | 商家ID，主键 |

| region_id | INT | 所属区域ID |
| biz_type | VARCHAR(16) | 品类：外卖/闪购/到店 |
| online_date | DATE | 上线日期（D0） |

| order_id | BIGINT | 订单ID，主键 |
| merchant_id | BIGINT | 商家ID |
| pay_time | DATETIME | 支付时间 |
| order_amount | DECIMAL(10,2) | 订单金额 |
| status | VARCHAR(16) | 订单状态：completed已完成 / canceled已取消 |

示例数据（merchants，5行）：

| merchant_id | merchant_name | region_id | biz_type | online_date |
|-------------|---------------|-----------|----------|-------------|

| 9102 | 鲜果切配送 | 11 | 闪购 | 2026-08-12 |

| order_id | merchant_id | pay_time | order_amount | status |
|----------|-------------|----------|--------------|--------|
| 160001 | 9101 | 2026-08-06 11:50:00 | 32.00 | completed |
| 160002 | 9101 | 2026-08-20 19:20:00 | 45.00 | completed |
| 160003 | 9102 | 2026-08-13 10:15:00 | 56.00 | completed |
| 160004 | 9103 | 2026-08-21 18:40:00 | 38.50 | canceled |
| 160005 | 9104 | 2026-09-25 09:30:00 | 22.00 | completed |

### 3. 解题思路

口径与边界：①冷启周定义：第k周 = DATEDIFF(订单日, 上线日) 落在 [7(k-1), 7k-1]，即第1周含上线当天（部分当天即有单），第4周到 D27 为止；②只统计 completed 订单，GMV 用 order_amount；③追踪对象为8月上线商家（保证上线满4周，窗口截断问题已消除，若追踪"最近上线"商家需标注未满周为"观察中"）；④商家中途下线或改区域不影响归因（按上线时快照）。实现路径两条：明细上按 DATEDIFF 条件聚合并行转列（一商家一行四周对比，最直观）；或造"商家×周索引"全集格再 LEFT JOIN（无单周显示0，曲线不断点），并可用 ROLLUP 汇总到区域。**【避坑指南】** 直接按"订单日期所在自然周"分周会把不同上线日的商家对不齐，必须用"距上线日的偏移周"，这是同期群分析的核心纪律。

### 4. 参考解法

解法一：DATEDIFF 条件聚合 + 行转列，一商家一行四周对比（并 ROLLUP 汇总）。

```sql
WITH new_m AS (                   -- 第一步：8月上线的商家（上线已满4周）
    SELECT merchant_id, region_id, online_date
    FROM merchants
    WHERE online_date >= '2026-08-01' AND online_date < '2026-09-01'
)
SELECT COALESCE(CAST(n.merchant_id AS CHAR), '汇总')     AS 商家ID,   -- ROLLUP汇总行标记
       SUM(CASE WHEN DATEDIFF(o.pay_time, n.online_date) BETWEEN 0  AND 6
                THEN o.order_amount ELSE 0 END)          AS 第1周GMV,  -- 含上线当天
       SUM(CASE WHEN DATEDIFF(o.pay_time, n.online_date) BETWEEN 7  AND 13
                THEN o.order_amount ELSE 0 END)          AS 第2周GMV,
       SUM(CASE WHEN DATEDIFF(o.pay_time, n.online_date) BETWEEN 14 AND 20
                THEN o.order_amount ELSE 0 END)          AS 第3周GMV,
       SUM(CASE WHEN DATEDIFF(o.pay_time, n.online_date) BETWEEN 21 AND 27
                THEN o.order_amount ELSE 0 END)          AS 第4周GMV,
       SUM(CASE WHEN DATEDIFF(o.pay_time, n.online_date) BETWEEN 0 AND 6 THEN 1 ELSE 0 END)
                                                              AS 第1周单量
FROM new_m n
LEFT JOIN orders o
       ON o.merchant_id = n.merchant_id
      AND o.status = 'completed'
      AND o.pay_time >= n.online_date                          -- 不计入上线前的历史单
      AND o.pay_time <  n.online_date + INTERVAL 28 DAY        -- 只看4周冷启窗口
GROUP BY n.merchant_id WITH ROLLUP;                            -- 末行自动汇总全部商家
```

结果解读：宽表逐行扫一眼即可分型——第1周远高于第4周为高开低走需履约诊断，逐周抬升为健康爬坡可加流量；汇总行给出8月上线批次整体曲线。

解法二：商家×周索引全集格 LEFT JOIN，长表输出且无单周补0（曲线不断点）。

```sql
WITH RECURSIVE wk AS (            -- 第一步：周索引维表 0~3 对应第1~4周
    SELECT 0 AS idx
    UNION ALL
    SELECT idx + 1 FROM wk WHERE idx < 3
),
new_m AS (                        -- 8月上线商家，同解法一
    SELECT merchant_id, region_id, online_date
    FROM merchants
    WHERE online_date >= '2026-08-01' AND online_date < '2026-09-01'
),
grid AS (                         -- 第二步：商家×周 全集格，保证无单周也在结果里
    SELECT n.merchant_id, n.region_id, n.online_date, w.idx
    FROM new_m n CROSS JOIN wk w
)
SELECT g.merchant_id                                   AS 商家ID,
       g.region_id                                     AS 区域ID,
       CONCAT('第', g.idx + 1, '周')                    AS 冷启周,
       COUNT(o.order_id)                               AS 完成单量,   -- 无单周=0
       ROUND(COALESCE(SUM(o.order_amount), 0), 2)      AS GMV,
       CASE WHEN COUNT(o.order_id) = 0 THEN '断档周' ELSE '正常' END AS 周状态
FROM grid g
LEFT JOIN orders o
       ON o.merchant_id = g.merchant_id
      AND o.status = 'completed'
      AND o.pay_time >= g.online_date + INTERVAL g.idx * 7 DAY        -- 第idx周起点（0起算）
      AND o.pay_time <  g.online_date + INTERVAL (g.idx + 1) * 7 DAY  -- 第idx周终点
GROUP BY g.merchant_id, g.region_id, g.idx
ORDER BY g.merchant_id, g.idx;
```

结果解读：长表天然兼容 BI 折线图（x=周、y=单量），无单周被显式记为0并打"断档周"标签——断档常常是商家关店或断货的信号，宽表法会把它误显示为普通低值。

### 5. 性能分析与优化

解法一扫描订单一次 + 按商家聚合，条件聚合无 JOIN 放大，代价 O(N)；解法二多出"商家×4"的 grid（小表），LEFT JOIN 时每个格子在 orders 上做一段范围探测，若有 (merchant_id, status, pay_time) 索引则高效，否则反复扫描大表。可执行优化：①orders 建 (merchant_id, status, pay_time) 复合索引是本题最关键的一刀；②DATEDIFF 计算放在 JOIN 条件中基于两列日期做范围比较（`pay_time >= online_date + INTERVAL idx*7 DAY`），不要对 pay_time 包函数，保住索引；③批次大时把"上线日+4周偏移"算成起止日期常量再 JOIN，避免每行重复日期运算；④若要长期追踪到8周以上，把周索引维表扩展并物化"商家×周"日快照表，报表直接读。⑤上线商家若按月数千级增长，解法一 ROLLUP 在明细级聚合即可，不建议在明细上先算周标签再二次聚合。

### 6. 面试延伸考点

- **如果要对比不同上线月份批次的冷启曲线，怎么组织数据？** 要点：把上线月份作为同期群（cohort）维度，输出"上线月×偏移周"矩阵；注意早期批次已满4周而最新批次未满，要标注成熟度或只对比已成熟周。
- **第1周表现好能预测第4周吗？怎么量化？** 要点：算第1周与第4周单量的相关系数或分箱条件均值（第1周分五档看第4周均值），强相关则第1周即可分流干预资源。
- **冷启流量是平台给的，怎么区分自然增长与流量效果？** 要点：用未获冷启资源的同品类新商家做对照，或平台按规则随机分配冷启流量后做实验对比；SQL负责产出分组与指标。

### 7. 业务拓展思考

四周曲线分型可直接接进商家成长SOP：高开低走型48小时内触发履约诊断（评分、出餐时长、缺货率三查），低开稳升型自动进入"流量加码"池，断档周商家转人工外呼。口径延展上，可把追踪窗延到8周观察留存形态，或加入"首单用户复购率"衡量冷启带来的用户质量而非单量泡沫；也可以按品类分别建立基准曲线（咖啡快取与正餐餐馆的成长斜率天然不同），让"低于基准"而非"低于均值"成为干预触发线。对平台而言，冷启ROI要算总账：冷启流量成本 vs 商家4周GMV与后续留存贡献。

## LL-30 各时段取消率分布与异常时段识别：凌晨单的真相

### 1. 业务背景

体验团队周度排查订单取消率的小时分布，识别"异常时段"。真实案例是凌晨0-1点取消率显著高于白天：深夜运力真空、商家打烊但页面仍可下单、用户下单后等不到接单主动取消。取消率的口径必须先钉死：分母是"有支付行为"的订单（未支付流失属于漏斗上游，不算取消），分子是支付后取消的单（用户取消、骑手取消、商家取消三类），超时未支付单独状态不计入。异常判定规则：该小时取消率 > 全天加权平均取消率 × 1.5。识别出的异常时段触发定向动作：0-1点收缩营业中商家曝光、给夜间值班骑手补贴、或把深夜承诺送达时间拉长。用户在深夜期待确定性，商家控制营业时间，骑手决定接单意愿，平台用取消率发现三方预期的错配。

### 2. 表结构说明

orders 订单表（含完整状态机）：

| 字段名 | 类型 | 含义 |
|--------|------|------|
| order_id | BIGINT | 订单ID，主键 |
| user_id | BIGINT | 用户ID |
| region_id | INT | 区域ID |
| pay_time | DATETIME | 支付时间，NULL表示未支付 |
| cancel_time | DATETIME | 取消时间，未取消为NULL |
| cancel_role | VARCHAR(16) | 取消发起方：user/rider/merchant，未取消为NULL |
| status | VARCHAR(20) | 终态：completed / user_cancel / rider_cancel / merchant_cancel / timeout_unpaid超时未支付 |

示例数据（5行）：

| order_id | user_id | region_id | pay_time | cancel_time | cancel_role | status |
|----------|---------|-----------|----------|-------------|-------------|--------|
| 170001 | 8001 | 51 | 2026-09-15 00:20:00 | 2026-09-15 00:45:00 | user | user_cancel |
| 170002 | 8002 | 51 | 2026-09-15 08:30:00 | NULL | NULL | completed |
| 170003 | 8003 | 52 | 2026-09-15 12:05:00 | 2026-09-15 12:10:00 | merchant | merchant_cancel |
| 170004 | 8004 | 51 | NULL | NULL | NULL | timeout_unpaid |
| 170005 | 8005 | 52 | 2026-09-15 18:40:00 | NULL | NULL | completed |

### 3. 解题思路

口径与边界：①分母 = pay_time 非空且 status ≠ 'timeout_unpaid' 的订单（已完成或支付后取消）；②分子 = status IN ('user_cancel','rider_cancel','merchant_cancel')，三类取消先合计，定位根因时再按 cancel_role 拆；③时段按 pay_time 的小时（0-23），因为取消率随"下单时点"的供给环境变化；④异常判定阈值 = 全天加权平均取消率（SUM取消/SUM支付）×1.5，注意与"各小时取消率的简单平均"不同——简单平均给深夜小单量时段过高权重，会把2单取消1单的时段误判为异常。实现路径：先按小时聚合出各时段取消率，再与全天均值比较打标；全天均值既可用第二段 CTE 算（加权），也可聚合后开窗口（简单平均），两法恰好展示这个口径差异。**【面试高频】** "聚合结果上再开窗口"（AVG(聚合列) OVER ()）是 MySQL 8.0 高频考点，本题是最佳演练场景。

### 4. 参考解法

解法一：小时聚合 CTE + 加权全天均值 CTE，CROSS JOIN 比较打标（口径最严谨）。

```sql
WITH hr AS (                      -- 第一步：按下单小时聚合支付单量与取消单量
    SELECT HOUR(pay_time) AS hr,
           COUNT(*)                                            AS paid_cnt,   -- 有支付行为的单
           SUM(status IN ('user_cancel', 'rider_cancel', 'merchant_cancel'))
                                                               AS cancel_cnt  -- 支付后取消的单
    FROM orders
    WHERE pay_time IS NOT NULL                          -- 只看有支付行为的订单
      AND status <> 'timeout_unpaid'                    -- 未支付流失不算取消分母
      AND pay_time >= '2026-09-15' AND pay_time < '2026-09-16'
    GROUP BY HOUR(pay_time)
),
day_avg AS (                      -- 第二步：全天加权平均取消率 = 总取消/总支付
    SELECT SUM(cancel_cnt) * 1.0 / NULLIF(SUM(paid_cnt), 0) AS avg_rate
    FROM hr
)
SELECT h.hr                                            AS 小时,
       h.paid_cnt                                      AS 支付单量,
       h.cancel_cnt                                    AS 取消单量,
       ROUND(h.cancel_cnt / NULLIF(h.paid_cnt, 0), 4)  AS 时段取消率,
       ROUND(d.avg_rate, 4)                            AS 全天加权取消率,
       CASE WHEN h.cancel_cnt / NULLIF(h.paid_cnt, 0) > 1.5 * d.avg_rate
            THEN '异常时段' ELSE '正常' END            AS 判定
FROM hr h
CROSS JOIN day_avg d                                   -- 全天均值只有一行，笛卡尔挂上即可
ORDER BY h.hr;
```

结果解读：凌晨0-1点若被标"异常时段"，配小单量提示（paid_cnt 个位数）需谨慎——样本不足时阈值法会误报，可加 paid_cnt >= 30 的置信条件。

解法二：聚合后直接开窗口算"各时段取消率的简单平均"，同层完成判定（展示口径差异）。

```sql
WITH hr AS (                      -- 按小时聚合，同解法一
    SELECT HOUR(pay_time) AS hr,
           COUNT(*)                                            AS paid_cnt,
           SUM(status IN ('user_cancel', 'rider_cancel', 'merchant_cancel')) AS cancel_cnt
    FROM orders
    WHERE pay_time IS NOT NULL
      AND status <> 'timeout_unpaid'
      AND pay_time >= '2026-09-15' AND pay_time < '2026-09-16'
    GROUP BY HOUR(pay_time)
)
SELECT hr                                             AS 小时,
       paid_cnt                                       AS 支付单量,
       cancel_cnt                                     AS 取消单量,
       ROUND(cancel_cnt / NULLIF(paid_cnt, 0), 4)     AS 时段取消率,
       ROUND(AVG(cancel_cnt * 1.0 / NULLIF(paid_cnt, 0)) OVER (), 4) AS 简单平均取消率,
       -- 窗口开在聚合结果上：先每行算出时段取消率，再对24行求无权平均
       CASE WHEN cancel_cnt * 1.0 / NULLIF(paid_cnt, 0)
                 > 1.5 * AVG(cancel_cnt * 1.0 / NULLIF(paid_cnt, 0)) OVER ()
            THEN '异常时段' ELSE '正常' END           AS 判定
FROM hr
ORDER BY hr;
```

结果解读：简单平均会被深夜等小单量时段的极端率拉高，导致全天均值虚高、异常判定偏松；两种口径并排输出，恰好向面试官展示"对什么平均"的口径意识。

### 5. 性能分析与优化

两法主体都是一次订单表扫描 + GROUP BY 小时（24组，聚合极轻），差异只在均值来源：解法二把窗口放在聚合结果上，24行开窗几乎零成本，且少一次 CTE；解法一多一段 day_avg 聚合，但加权口径正确性更高。可执行优化：①orders 按 pay_time 建索引或按日分区，查询带日期范围裁剪；②status 的枚举判断可配合 (status, pay_time) 索引，但注意函数 HOUR(pay_time) 出现在 GROUP BY 不影响扫描裁剪（裁剪靠 WHERE 里的范围条件）；③长期监控时按日预聚合"小时×日"取消率落表，周报跨周趋势直接聚合结果表；④阈值1.5可改成"分位数法"（取消率高于P75的时段为异常），对单量波动更稳健，实现可复用 LL-18 的分位框架；⑤若取消原因里有结构化原因码，分子应排除"用户改地址"等非体验类取消，避免污染异常判定。

### 6. 面试延伸考点

- **取消率上升，怎么拆解到取消方与原因？** 要点：按 cancel_role 与原因码二维下钻，输出"小时×取消方"矩阵；用户取消多为等待不耐，骑手取消多为距离/报酬，商家取消多为缺货打烊，动作完全不同。
- **全天加权平均和简单平均的取消率差很多说明什么？** 要点：说明取消率与单量相关（小单量时段极端），应改用加权口径或分位数法，并检查小样本时段是否该合并。
- **未支付流失要不要算进"取消"？** 要点：不属于支付后取消，但属于"下单意向流失"，应放入独立漏斗（曝光→下单→支付）单独监控，混入取消率会掩盖支付环节问题。

### 7. 业务拓展思考

异常时段识别应长成"自动巡检+归因"链路：判定异常后自动下钻取消方构成与同小时运力（联动 LL-22 单骑比）、营业中商家数，把"取消率高"翻译成"深夜运力真空"或"商家打烊未关店"等可执行结论。口径延展上，可引入"取消挽回率"（取消后推送挽留券再次下单的比例）衡量止损效果；也可按"承诺送达超时后取消"单独统计，把体验型取消与意愿型取消分开。对深夜时段，结构化动作包括：收缩曝光、延长承诺时间、设置深夜专属运力补贴，三招组合把取消率压回正常水位。
