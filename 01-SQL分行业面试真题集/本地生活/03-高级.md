## LL-31 外卖订单量环比下滑的多维归因拆解

### 1. 业务背景

外卖平台的城市运营负责人在周一例会前发现：上周平台订单量环比下降 8%。他需要数据分析师在会前回答两个问题：这 8% 的降幅究竟来自哪些区域、哪些品类、哪些时段的组合；其中多少是雨天等天气造成的短期自然波动、多少是真实的结构性下滑。前者无需干预，后者则要立刻排查商家供给、补贴力度或竞对动作。归因结论直接决定本周运营资源投到哪个片区、哪个品类，是本地生活运营分析中最典型的高频决策场景。

### 2. 表结构说明

| order_id | BIGINT | 订单ID，全局唯一 |
| region_id | INT | 区域ID（城市下的一级片区） |
| category_id | INT | 品类ID（1=美食正餐 2=甜点饮品 3=生鲜果蔬 4=超市便利） |
| order_time | DATETIME | 下单时间 |
| pay_amount | DECIMAL(10,2) | 用户实付金额 |
| order_status | VARCHAR(20) | 订单状态（completed=完成，canceled=取消） |

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| region_id | INT | 区域ID |
| dt | DATE | 日期 |
| weather_type | VARCHAR(10) | 天气类型（sunny/cloudy/rain/snow） |

### 3. 解题思路

先定口径：对比期为本周（2026-10-19 起）与上周（2026-10-12 起），只统计 completed 订单；归因粒度取"区域×品类×时段"三维组合，时段切成午高峰/晚高峰/其余三段。核心口径是贡献度的可加分解：单元格贡献 = 本期单量 − 上期单量，对整体降幅的贡献率 = 该差值 ÷ 上期总单量，这样全部单元格贡献率之和恰好等于整体环比变化，结论可以直接汇报"某组合拖累了几个百分点"。实现路径：CTE 打期标签 → 聚合到单元格 → 条件聚合行转列对齐两期 → 除以整体基数并排序。易错点：a) 忘记过滤取消单引入噪声；b) 某单元格上期为 0 时环比无穷大，要用 NULLIF 防护；c) 用"占比变化"冒充贡献度会因基数不同而误判；d) 天气维度叠加后组合数爆炸，应先一维下钻再二次下钻。

### 4. 参考解法

**解法一：多层 CTE + 可加贡献分解（推荐，口径最直观）**

```sql
WITH tagged AS (                          -- 步骤1：圈定两周明细并打上期数标签
    SELECT region_id, category_id, order_time,
           CASE WHEN order_time >= '2026-10-19' THEN 'cur'   -- 本周记为 cur
                ELSE 'prev' END AS period_tag                -- 上周记为 prev
    FROM orders
    WHERE order_time >= '2026-10-12'                         -- 只扫两周数据，控制扫描量
      AND order_status = 'completed'                         -- 口径：仅完成单参与归因
),
cell AS (                                   -- 步骤2：聚合到 区域×品类×时段×期数
    SELECT region_id, category_id,
           CASE WHEN HOUR(order_time) BETWEEN 10 AND 13 THEN 'lunch_peak'
                WHEN HOUR(order_time) BETWEEN 16 AND 20 THEN 'dinner_peak'
                ELSE 'other' END AS time_slot,
           period_tag,
           COUNT(*) AS order_cnt
    FROM tagged
    GROUP BY region_id, category_id,
             CASE WHEN HOUR(order_time) BETWEEN 10 AND 13 THEN 'lunch_peak'
                  WHEN HOUR(order_time) BETWEEN 16 AND 20 THEN 'dinner_peak'
                  ELSE 'other' END,
             period_tag
),
pv AS (                                     -- 步骤3：条件聚合行转列，两期对齐到同一行
    SELECT region_id, category_id, time_slot,
           SUM(CASE WHEN period_tag = 'cur'  THEN order_cnt ELSE 0 END) AS cur_cnt,
           SUM(CASE WHEN period_tag = 'prev' THEN order_cnt ELSE 0 END) AS prev_cnt
    FROM cell
    GROUP BY region_id, category_id, time_slot
),
total AS (                                  -- 步骤4：整体基数，作为贡献率的统一分母
    SELECT SUM(cur_cnt) AS total_cur, SUM(prev_cnt) AS total_prev FROM pv
)
SELECT p.region_id, p.category_id, p.time_slot,
       p.prev_cnt, p.cur_cnt,
       p.cur_cnt - p.prev_cnt AS delta_cnt,                                    -- 该单元格单量净变化
       ROUND((p.cur_cnt - p.prev_cnt) / t.total_prev * 100, 2) AS contrib_pct,  -- 对整体环比的贡献率
       ROUND((p.cur_cnt - p.prev_cnt) / NULLIF(p.prev_cnt, 0) * 100, 2) AS cell_growth_pct -- 单元格自身环比
FROM pv p CROSS JOIN total t
ORDER BY contrib_pct ASC;                    -- 负贡献最大的排最前，即主要拖累来源
```

结果解读：所有单元格 contrib_pct 之和恰等于整体环比 -8%，按升序即可直接读出拖累最大的组合，例如"101 片区×甜点饮品×午高峰贡献 -3.2pp"，运营可据此定向排查。

**解法二：嵌套派生表 + 结构占比×组内增速分解（区分盘子与结构）**

```sql
SELECT c.region_id, c.category_id, c.time_slot,
       c.prev_cnt / t.total_prev AS prev_share,                                  -- 上期结构占比 s_i
       c.cur_cnt / NULLIF(c.prev_cnt, 0) - 1 AS cell_growth,                     -- 组内增速 g_i
       ROUND((c.prev_cnt / t.total_prev)
             * (c.cur_cnt / NULLIF(c.prev_cnt, 0) - 1) * 100, 2) AS contrib_pct  -- s_i × g_i = 对整体增速的贡献
FROM (                                            -- 内层派生表：两期单元格一次聚合完成
    SELECT region_id, category_id,
           CASE WHEN HOUR(order_time) BETWEEN 10 AND 13 THEN 'lunch_peak'
                WHEN HOUR(order_time) BETWEEN 16 AND 20 THEN 'dinner_peak'
                ELSE 'other' END AS time_slot,
           SUM(order_time >= '2026-10-19') AS cur_cnt,   -- MySQL技巧：布尔表达式为1/0，求和即计数
           SUM(order_time <  '2026-10-19') AS prev_cnt
    FROM orders
    WHERE order_time >= '2026-10-12' AND order_status = 'completed'
    GROUP BY region_id, category_id,
             CASE WHEN HOUR(order_time) BETWEEN 10 AND 13 THEN 'lunch_peak'
                  WHEN HOUR(order_time) BETWEEN 16 AND 20 THEN 'dinner_peak'
                  ELSE 'other' END
) c
CROSS JOIN (                                      -- 第二层派生表：整体两期基数
    SELECT SUM(order_time >= '2026-10-19') AS total_cur,
           SUM(order_time <  '2026-10-19') AS total_prev
    FROM orders
    WHERE order_time >= '2026-10-12' AND order_status = 'completed'
) t
ORDER BY contrib_pct ASC;
```

结果解读：恒等式"整体环比 = Σ(结构占比 × 组内增速)"成立，该写法把每组拖累拆成"结构份额×自身降幅"，能区分"大盘在涨但该组份额被稀释"与"组自身塌方"两类原因。

> **Hive/Spark SQL 差异**：生产订单表按天分区，两期对比应写 `dt BETWEEN '2026-10-12' AND '2026-10-25'` 触发分区裁剪；Hive 中布尔求和需改写为 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`；数据量大时建议先按天落"区域×品类×时段"聚合中间表再做归因。

### 5. 性能分析与优化

解法一通过 CTE 只扫一遍两周明细，聚合两次（cell 与 pv 层），代价约为 O(两周订单数)；解法二的嵌套派生表会使 orders 被扫描两次（单元格层与整体基数层各一次），大表下代价更高。可执行优化：1) orders 按 dt 做range分区并只取两周分区，扫描量直接减一个量级；2) 在 (order_status, order_time) 上建复合索引辅助过滤，在 (region_id, category_id) 上建索引辅助分组；3) 归因若为周例行任务，预聚合"日×区域×品类×时段"汇总表，把查询从亿行级降到万行级；4) MySQL 8.0 中被多次引用的 CTE 只物化一次，优于重复派生表。

### 6. 面试延伸考点

- **如果还要叠加天气维度，归因表会膨胀到什么程度？怎么控制？** 要点：三维组合已有数千格，加天气后按"区域×日"先关联 weather_daily 再聚合成四维，更稳妥的做法是先做一维下钻定位异常层，再只对异常切片做二次下钻。
- **取消率这类比率指标也能这样加总分解吗？** 要点：不能，比率不可直接相加，要用固定基数法或"结构×比率"分解，见 LL-41。
- **为什么用单量而不用 GMV 做归因？** 要点：跟随决策目标——运力排班看单量、财务复盘看 GMV；两者结论可能相反，正式汇报应双指标并行。
- **如何判断 -8% 是否超出自然波动区间？** 要点：用历史同期方差或置信区间做显著性判断，波动在噪声带内不必过度归因。

### 7. 业务拓展思考

该归因框架可固化为每周例行"异动看板"：环比波动超过阈值（如 ±5%）自动触发多维下钻。结论可直接联动动作——天气贡献占比高，则提前配置恶劣天气运力补贴与配送费动态调价（见 LL-38）；某品类结构性下滑，则联动品类运营检查供给数量、排序权重与竞对比价。口径上可继续延展：把 GMV 异动拆成"单量×客单价"乘法分解，把单量异动拆成"新客×老客"，形成三层归因树；也可叠加显著性检验避免对噪声过度反应。

## LL-32 不同补贴档位新客的7日留存对比

### 1. 业务背景

增长运营团队在新城市做拉新，新人首单立减分三档：5 元、10 元、15 元，档位由策略按用户特征分配。财务质疑高档补贴"买来的用户质量差"，要求分析师回答：三档新客在 7 日留存率、7 日内人均复购 GMV 上是否有实质差异？如果 15 元档留存并不比 10 元档高，就应把预算从高档位挪向性价比更优的档位，或转投后期复购激励。这一"补贴档位 vs 用户质量"的评估结论，直接决定下季度拉新预算在档位间的分配，是本地生活补贴 ROI 体系的基础环节。

### 2. 表结构说明

new_user_coupons（新客首单补贴记录表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| first_order_dt | DATE | 首单日期（成为新客的日期） |
| subsidy_tier | TINYINT | 补贴档位（5/10/15 元） |
| subsidy_amount | DECIMAL(5,2) | 实际补贴金额 |
| channel | VARCHAR(20) | 获客渠道 |

orders（订单表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| order_dt | DATE | 下单日期 |
| pay_amount | DECIMAL(10,2) | 实付金额 |
| order_status | VARCHAR(20) | 订单状态 |

| 10002 | 2026-10-01 | 5 | 5.00 | 应用商店 |

| 10004 | 2026-10-03 | 10 | 10.00 | 抖音信息流 |

| 700104 | 10003 | 2026-10-02 | 48.00 | completed |
| 700105 | 10004 | 2026-10-09 | 33.50 | completed |

### 3. 解题思路

口径先行：7 日留存 = 首单后第 1~7 天（不含首单当天）内至少有 1 笔完成单的新客占比；人均复购 GMV = 档位内新客在 7 日窗口复购实付金额之和 ÷ 档位新客数。三个易踩的坑：1) 分母必须是全部新客而非有复购用户，否则留存率虚高；2) 观察窗必须封口——只统计首单日期距今 ≥8 天的 cohort，近期新客窗口未走完会造成右删失、低估留存；3) 首单本身不计入复购。实现路径：先取新客名单与首单日期，再与订单表按"同用户 + 时间窗"连接判定复购，最后按档位条件聚合。两种写法分别采用"LEFT JOIN 时间窗 + 布尔均值聚合"与"先算留存名单再左连回人群表"，后者中间结果更小。

### 4. 参考解法

**解法一：LEFT JOIN 时间窗 + 条件聚合（可同时算留存与复购GMV）**

```sql
WITH cohort AS (                              -- 步骤1：新客名单（窗口封口，排除右删失）
    SELECT user_id, first_order_dt, subsidy_tier
    FROM new_user_coupons
    WHERE first_order_dt <= DATE_SUB('2026-10-25', INTERVAL 8 DAY)  -- 首单距今至少8天
),
rebuy AS (                                    -- 步骤2：左连7日窗口内的完成单
    SELECT c.user_id, c.subsidy_tier,
           MAX(o.order_id IS NOT NULL) AS is_retain,          -- 连接命中即视为留存
           COALESCE(SUM(o.pay_amount), 0) AS rebuy_gmv        -- 窗口内复购实付金额
    FROM cohort c
    LEFT JOIN orders o
           ON o.user_id = c.user_id
          AND o.order_dt > c.first_order_dt                   -- 首单当天不算复购
          AND o.order_dt <= DATE_ADD(c.first_order_dt, INTERVAL 7 DAY)  -- 7日窗口右边界
          AND o.order_status = 'completed'
    GROUP BY c.user_id, c.subsidy_tier
)
SELECT subsidy_tier AS tier,
       COUNT(*) AS new_users,                                 -- 分母=该档全部新客
       ROUND(AVG(is_retain) * 100, 2) AS retain_7d_pct,       -- 布尔均值即留存率
       ROUND(SUM(rebuy_gmv) / COUNT(*), 2) AS avg_rebuy_gmv   -- 人均7日复购GMV
FROM rebuy
GROUP BY subsidy_tier
ORDER BY subsidy_tier;
```

结果解读：若输出显示 5/10/15 元档留存率分别为 22%/24%/25%，说明高补贴对留存的边际拉动有限，而 15 元档多花的 5 元/人可用于更优渠道或复购券。

**解法二：留存名单法（EXISTS 语义，先小后大）**

```sql
WITH retained AS (                            -- 步骤1：先求"7日内有复购"的小名单
    SELECT DISTINCT n.user_id                 -- DISTINCT 压成用户粒度
    FROM new_user_coupons n
    JOIN orders o
      ON o.user_id = n.user_id
     AND o.order_dt > n.first_order_dt                       -- 复购起点：首单之后
     AND o.order_dt <= DATE_ADD(n.first_order_dt, INTERVAL 7 DAY)
     AND o.order_status = 'completed'
)
SELECT n.subsidy_tier AS tier,
       COUNT(*) AS new_users,                                 -- 人群表为主表，分母不丢人
       COUNT(r.user_id) AS retained_users,                    -- 命中名单人数
       ROUND(AVG(r.user_id IS NOT NULL) * 100, 2) AS retain_7d_pct
FROM new_user_coupons n
LEFT JOIN retained r ON r.user_id = n.user_id
WHERE n.first_order_dt <= DATE_SUB('2026-10-25', INTERVAL 8 DAY)
GROUP BY n.subsidy_tier
ORDER BY n.subsidy_tier;
```

结果解读：留存名单粒度小、左连后聚合快，适合人群表很大而订单表按 user_id 分桶的场景；缺点是这一写法不直接给出复购 GMV，需要再补一个聚合窗口。

> **Hive/Spark SQL 差异**：Hive 对相关子查询支持弱，留存判定优先用解法一的 LEFT JOIN 或 `LEFT SEMI JOIN`；生产中新客表与订单表应按 user_id 分桶（CLUSTERED BY）以避免 shuffle；cohort 建议落在以 first_order_dt 为分区的日增表上。

### 5. 性能分析与优化

解法一 join 后的中间行数约为"新客数 × 窗口内订单数"，再聚合两次；解法二先以 DISTINCT 压缩出小名单再 join，中间结果显著更小，但订单表必须有 (user_id, order_dt) 索引才能高效探测。优化建议：1) 两表均按 user_id 分区/分桶，join 前完成裁剪；2) 用"用户×日"粒度的订单汇总表替代明细表做留存判定；3) 长期方案是建立 cohort 日增表（首单日期为分区键），留存率随窗口到期逐日回填；4) 避免在 join 条件里对列做函数运算（如 DATE(order_dt)），防止索引失效。

### 6. 面试延伸考点

- **留存窗口为什么从"首单后第1天"起算而不是含首单当天？** 要点：首单是"被补贴激活"的动作，留存衡量的是"无强激励下是否回来"，混入首单会系统性高估。
- **如何排除补贴吸引来的羊毛党？** 要点：叠加设备指纹去重、收货地址聚集度、券核销与退款时序等特征剔除异常，或与自然流入用户留存基线对比。
- **档位不是随机分配时，直接对比有什么偏差？** 要点：选择偏差——高意向用户更可能领到高档券，需 DID 或倾向得分匹配校正，参见 LL-36。
- **7日留存之外还应看什么？** 要点：30日留存、LTV（见 LL-43）与补贴回收期，避免"高留存低价值"的假阳性。

### 7. 业务拓展思考

留存档位对比可延展为"补贴边际效率曲线"：每多投 1 元补贴带来多少增量留存用户，进而求最优档位；观察周期也可从 7 日拉长到 30 日、90 日，结合 LTV 判断长期质量差异。运营联动上：对"低档位高留存"人群追加复购券而非更高首单补贴；对"高补贴低留存"档位收缩预算，把费用挪向渠道质量更优的投放；若某档位留存高但 GMV 低，则应转向客单价提升策略（凑单、满减阶梯）而非继续加码拉新。

## LL-33 配送时长与30日复购率的分箱边际关系

### 1. 业务背景

体验策略团队想回答一个经典问题：配送时长每上一个台阶（30 分钟内 / 30-45 / 45-60 / 60 以上），用户的 30 日复购率下降多少？边际损失在哪一档突然放大？这决定"全链路时效目标"定在哪一档最划算——把全部订单压进 30 分钟成本极高，但如果 45-60 档的复购率断崖式下跌，就值得对长时效订单定向补贴骑手或限流远单。该结论由数据分析团队输出给物流策略与产品，用于制定履约 SLA 与运力预算的取舍。

### 2. 表结构说明

deliveries（配送单表，虚构，含用户与下单时间，复购判定直接在本表内完成）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 下单用户ID |
| order_dt | DATETIME | 下单时间 |
| promise_minutes | INT | 承诺送达时长（分钟） |
| actual_minutes | INT | 实际送达时长（分钟） |
| rider_id | BIGINT | 接单骑手ID |

deliveries 示例数据：

| order_id | user_id | order_dt | promise_minutes | actual_minutes | rider_id |
| --- | --- | --- | --- | --- | --- |
| 880001 | 201 | 2026-09-01 11:20:00 | 35 | 28 | 5001 |
| 880002 | 202 | 2026-09-01 18:35:00 | 40 | 52 | 5002 |
| 880003 | 203 | 2026-09-02 12:10:00 | 35 | 66 | 5003 |
| 880004 | 201 | 2026-09-15 19:02:00 | 40 | 38 | 5002 |
| 880005 | 204 | 2026-09-20 11:45:00 | 35 | 33 | 5001 |

### 3. 解题思路

口径：配送时长按 actual_minutes 切四箱（≤30 / 30-45 / 45-60 / >60）；30 日复购 = 该订单之后 30 天内同用户至少再有 1 笔订单。产出两张表：各箱复购率，以及相邻箱之间的"边际降幅"（用 LAG 对排序后的分箱求一阶差分），边际陡降的箱位就是时效红线的落点。易错点：a) 分箱边界要左闭右开并统一，避免 45 分钟同时落入两箱；b) 复购判定要与"本单"对齐——从每单往后看 30 天，而不是把用户所有订单两两配对后混淆方向；c) 老客与新人混算会引入偏差，可加"首单后 N 单"限定；d) 相关子查询逐行执行慢，大表应改自连接或窗口。

### 4. 参考解法

**解法一：分箱 + 相关子查询 EXISTS 判复购 + LAG 求边际**

```sql
WITH base AS (                            -- 步骤1：圈定观察期订单并切分时长箱
    SELECT order_id, user_id, order_dt,
           CASE WHEN actual_minutes <= 30 THEN 'a_le_30'
                WHEN actual_minutes <= 45 THEN 'b_30_45'
                WHEN actual_minutes <= 60 THEN 'c_45_60'
                ELSE 'd_gt_60' END AS dur_bin       -- 左闭右开，边界不重不漏
    FROM deliveries
    WHERE order_dt >= '2026-08-01' AND order_dt < '2026-09-30'  -- 留出30日复购观察窗
),
flag AS (                                 -- 步骤2：逐单判定30日内是否有复购
    SELECT b.*,
           EXISTS (SELECT 1 FROM deliveries o        -- 同用户后续订单
                   WHERE o.user_id = b.user_id
                     AND o.order_dt >  b.order_dt
                     AND o.order_dt <= DATE_ADD(b.order_dt, INTERVAL 30 DAY)) AS rep_30d
    FROM base b
),
agg AS (                                  -- 步骤3：按箱聚合复购率
    SELECT dur_bin, COUNT(*) AS order_cnt, AVG(rep_30d) AS rep_rate
    FROM flag
    GROUP BY dur_bin
)
SELECT dur_bin, order_cnt,
       ROUND(rep_rate * 100, 2) AS rep_pct,                 -- 该箱复购率
       ROUND((rep_rate - LAG(rep_rate) OVER (ORDER BY dur_bin)) * 100, 2) AS marginal_drop_pp
                                                            -- 相邻箱边际降幅（负值即每慢一档掉几个点）
FROM agg
ORDER BY dur_bin;
```

结果解读：若 30 分钟内档复购率 34%、30-45 档 33%、45-60 档 29%、60 以上档 21%，边际在 60 分钟档骤降 8 个百分点，说明时效红线应设在 60 分钟，资源优先压超时高危单。

**解法二：自连接配对判复购（避免相关子查询，大表友好）**

```sql
WITH base AS (                            -- 步骤1：同解法一的分箱
    SELECT order_id, user_id, order_dt,
           CASE WHEN actual_minutes <= 30 THEN 'a_le_30'
                WHEN actual_minutes <= 45 THEN 'b_30_45'
                WHEN actual_minutes <= 60 THEN 'c_45_60'
                ELSE 'd_gt_60' END AS dur_bin
    FROM deliveries
    WHERE order_dt >= '2026-08-01' AND order_dt < '2026-09-30'
),
pair AS (                                 -- 步骤2：自连接找"后单落在前单30日内"的配对
    SELECT b.order_id, b.dur_bin
    FROM base b
    JOIN deliveries o
      ON o.user_id = b.user_id
     AND o.order_dt >  b.order_dt                       -- 只看本单之后的订单
     AND o.order_dt <= DATE_ADD(b.order_dt, INTERVAL 30 DAY)
    GROUP BY b.order_id, b.dur_bin                      -- 一单多条复购压成一行
)
SELECT b.dur_bin,
       COUNT(*) AS order_cnt,                           -- 全部订单为分母
       ROUND(COUNT(p.order_id) / COUNT(*) * 100, 2) AS rep_pct  -- 命中配对即为复购
FROM base b
LEFT JOIN pair p ON p.order_id = b.order_id
GROUP BY b.dur_bin
ORDER BY b.dur_bin;
```

结果解读：LEFT JOIN 后按箱统计命中率，等价于 EXISTS 语义但把逐行探测变成一次 hash join，亿级配送表下耗时通常能降一个量级；结果口径与解法一完全一致，可互为校验。

> **Hive/Spark SQL 差异**：Hive 不支持 SELECT 中的相关 EXISTS 子查询，必须用解法二的自连接或窗口写法；自连接前把两份 base 落临时表并按 user_id 分桶，可把 shuffle 从全量降为同桶对齐；30 日窗口也可用 `o.order_dt <= date_add(b.order_dt, 30)`。

### 5. 性能分析与优化

解法一的相关子查询对每行做一次索引探测，行数越大代价线性放大，适合百万级以内；解法二两次扫描 + 一次 hash join + 一次分组，适合千万级以上，但 pair 层自连接若不加 user_id 等值条件会退化为笛卡尔积，必须防止。优化建议：1) deliveries 在 (user_id, order_dt) 上建复合索引，既服务复购探测也服务自连接；2) 先按月分区裁剪，只扫观察期与复购窗并集；3) 分箱结果可预聚合为"日×箱"中间表供例行报表；4) 若仅需复购率，可用用户级"下次下单时间"字段（LEAD 计算后物化）替代两两配对，把 O(订单×订单) 降为 O(订单)。

### 6. 面试延伸考点

- **为什么用 EXISTS 而不是 COUNT 复购单数？** 要点：复购是 0/1 事件，用 EXISTS 语义可在连接前去重，避免一单多复购把分母权重放大。
- **分箱边界怎么定才科学？** 要点：等频与业务断点结合，10 分钟粒度先看分布再合并，且箱内样本量要足够支撑比率稳定。
- **复购率下降就一定是时效造成的吗？** 要点：存在混杂——远单/恶劣天气既拉长时效又影响体验，需控制品类、距离、天气做分层或回归（见 LL-38）。
- **相关子查询和自连接各在什么场景占优？** 要点：小结果集+强索引用相关子查询省内存；大表靠自连接/窗口批量算，Hive 里只能后者。

### 7. 业务拓展思考

该分箱边际曲线是履约 SLA 定价的基础：把边际降幅换算成 GMV 损失，再对比"缩短 1 分钟的运力成本"，就能解出最优时效目标与超时赔付额度。联动动作包括：对 45 分钟以上订单做骑手顺路加价与远单限流，对超时高危订单提前弹窗安抚或发放无门槛券止损。口径可延展为"准点率 × 复购"的弹性、分品类时效敏感度（奶茶对时效远比超市便利敏感），以及与 LL-34 的运力缺口联动，识别"缺口大且时效敏感"的双高时段。

## LL-34 骑手运力缺口滑动预警（滚动单量 vs 在线骑手）

### 1. 业务背景

调度运营需要在午高峰前预判运力缺口：当"滚动 1 小时待配送单量 ÷ 当时在线骑手数"超过 1.5 时，配送超时率会显著抬升，必须提前 30-60 分钟通过冲单奖、上线奖励把骑手拉上线，或在商家端开启出餐限流。预警逻辑要求每 30 分钟输出一次各时段的滚动单量、在线骑手数与人均负荷，并标记超阈值时段。这道题考察把"时间区间数据"（订单事件流、骑手上下线区间）对齐到统一时间轴的能力，是调度类数据分析的核心 SQL 模式。

### 2. 表结构说明

orders（订单事件表，虚构，仅保留待配送相关状态）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| created_at | DATETIME | 下单时间 |
| order_status | VARCHAR(20) | 状态（待接单/配送中/已完成/已取消） |

rider_online（骑手上下线区间表，虚构，offline_ts 为空表示仍在线）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| rider_id | BIGINT | 骑手ID |
| city_id | INT | 城市ID |
| online_ts | DATETIME | 上线时间 |
| offline_ts | DATETIME | 下线时间（NULL=仍在线） |

orders 示例数据：

| order_id | created_at | order_status |
| --- | --- | --- |
| 660001 | 2026-10-25 10:35:00 | 已完成 |
| 660002 | 2026-10-25 11:05:00 | 配送中 |
| 660003 | 2026-10-25 11:40:00 | 待接单 |
| 660004 | 2026-10-25 12:10:00 | 待接单 |
| 660005 | 2026-10-25 12:25:00 | 配送中 |

rider_online 示例数据：

| rider_id | city_id | online_ts | offline_ts |
| --- | --- | --- | --- |
| 5001 | 1 | 2026-10-25 09:50:00 | 2026-10-25 14:00:00 |
| 5002 | 1 | 2026-10-25 10:30:00 | NULL |
| 5003 | 1 | 2026-10-25 11:20:00 | 2026-10-25 12:00:00 |
| 5004 | 1 | 2026-10-25 12:15:00 | NULL |
| 5005 | 1 | 2026-10-25 10:00:00 | 2026-10-25 10:40:00 |

### 3. 解题思路

先定义口径：滚动单量 = 截至某 30 分钟刻度的"过去 1 小时"内创建且状态属于待接单/配送中的订单数；在线骑手 = 上线时间 ≤ 刻度 < 下线时间（或未下线）的骑手数；运力缺口预警 = 滚动单量 ÷ 在线骑手 > 1.5。实现有两条路：a) 递归 CTE 生成完整 30 分钟时间轴，订单侧用相关子查询/范围统计滚动计数，骑手侧用"在线区间覆盖刻度"的区间判定——优点是时间轴无空洞；b) 先把订单落到 30 分钟桶，再用窗口 `ROWS BETWEEN 1 PRECEDING AND CURRENT ROW` 两桶求和近似 1 小时滚动，骑手侧把在线时长切成桶内人·分钟除以 30 得平均在线人数——优点是大表下无需逐刻度探测。易错点：区间判定漏掉"仍在线"（offline 为 NULL）、滚动窗口把边界单算重或算漏、桶有空洞导致滑动窗口错位。

### 4. 参考解法

**解法一：递归 CTE 时间轴 + 区间覆盖判定（时间轴完整，逻辑最直白）**

```sql
WITH RECURSIVE slots AS (                 -- 步骤1：生成当天每30分钟一个刻度
    SELECT TIMESTAMP('2026-10-25 10:00:00') AS slot_start
    UNION ALL
    SELECT slot_start + INTERVAL 30 MINUTE
    FROM slots
    WHERE slot_start < TIMESTAMP('2026-10-25 21:30:00')   -- 覆盖午晚两大高峰
),
order_load AS (                           -- 步骤2：每刻度的滚动1小时待配送单量
    SELECT s.slot_start,
           (SELECT COUNT(*)
            FROM orders o
            WHERE o.created_at >  s.slot_start - INTERVAL 1 HOUR  -- 左开右闭防重
              AND o.created_at <= s.slot_start
              AND o.order_status IN ('待接单','配送中')) AS rolling_orders
    FROM slots s
),
rider_supply AS (                         -- 步骤3：每刻度统计在线骑手数
    SELECT s.slot_start,
           COUNT(r.rider_id) AS online_riders
    FROM slots s
    LEFT JOIN rider_online r
           ON r.online_ts <= s.slot_start                              -- 上线早于刻度
          AND (r.offline_ts IS NULL OR r.offline_ts > s.slot_start)    -- 未下线或下线晚于刻度
    GROUP BY s.slot_start
)
SELECT o.slot_start,
       o.rolling_orders,
       r.online_riders,
       ROUND(o.rolling_orders / NULLIF(r.online_riders, 0), 2) AS orders_per_rider,  -- 人均负荷
       CASE WHEN o.rolling_orders / NULLIF(r.online_riders, 0) > 1.5
            THEN 'ALERT' ELSE 'OK' END AS alert_flag                    -- 缺口预警标记
FROM order_load o
JOIN rider_supply r USING (slot_start)
ORDER BY o.slot_start;
```

结果解读：输出逐刻度的负荷曲线，11:30-12:30 连续出现 ALERT 即为午高峰缺口时段，调度可提前在 11:00 触发上线奖励。

**解法二：时间桶 + 窗口滑动（大表友好，接近 Hive 生产写法）**

```sql
WITH order_bucket AS (                    -- 步骤1：订单先落30分钟桶
    SELECT FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(created_at) / 1800) * 1800) AS bucket_start,
           COUNT(*) AS ord_cnt
    FROM orders
    WHERE created_at >= '2026-10-25 09:00:00'
      AND created_at <  '2026-10-25 22:00:00'
      AND order_status IN ('待接单','配送中')
    GROUP BY bucket_start
),
rolling AS (                              -- 步骤2：当前桶+前一桶 = 滚动1小时单量
    SELECT bucket_start,
           SUM(ord_cnt) OVER (ORDER BY bucket_start
                              ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS rolling_orders
    FROM order_bucket
),
slots AS (                                -- 步骤3：从订单桶取有效刻度（注意：空桶会缺失）
    SELECT DISTINCT bucket_start FROM order_bucket
),
supply AS (                               -- 步骤4：骑手在线区间与桶求交，折算平均在线人数
    SELECT s.bucket_start,
           SUM(TIMESTAMPDIFF(MINUTE,
                 GREATEST(r.online_ts, s.bucket_start),
                 LEAST(COALESCE(r.offline_ts, '2026-10-25 22:00:00'),
                       s.bucket_start + INTERVAL 30 MINUTE))) / 30.0 AS avg_online_riders
    FROM slots s
    JOIN rider_online r
      ON r.online_ts < s.bucket_start + INTERVAL 30 MINUTE              -- 区间与桶相交
     AND COALESCE(r.offline_ts, '2026-10-25 22:00:00') > s.bucket_start
    GROUP BY s.bucket_start
)
SELECT ro.bucket_start,
       ro.rolling_orders,
       ROUND(sp.avg_online_riders, 1) AS online_riders,
       ROUND(ro.rolling_orders / NULLIF(sp.avg_online_riders, 0), 2) AS orders_per_rider,
       CASE WHEN ro.rolling_orders / NULLIF(sp.avg_online_riders, 0) > 1.5
            THEN 'ALERT' ELSE 'OK' END AS alert_flag
FROM rolling ro
LEFT JOIN supply sp USING (bucket_start)
ORDER BY ro.bucket_start;
```

结果解读：用"人·分钟 ÷ 30"折算平均在线人数，能刻画骑手中途上下线的部分时段贡献；缺点是刻度取自订单桶，某刻度完全无订单时会缺行，正式看板需补齐时间轴。

> **Hive/Spark SQL 差异**：Hive 无递归 CTE，时间轴要用日历维度表或 `sequence()` + `explode` 生成；`FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(ts)/1800)*1800)` 是通用的 30 分钟分桶写法；在线人数折算同样适用，注意 timestampdiff 需换成 `unix_timestamp` 差值除以 60。

### 5. 性能分析与优化

解法一的滚动单量用相关子查询逐刻度探测订单表，刻度数 × 探测代价，适合刻度少、索引健全（created_at 上的 B+ 树）的场景；解法二把订单先聚合到桶再窗口滑动，订单表只扫一遍，代价集中在一次排序（窗口 ORDER BY bucket_start），大表下明显更优。优化建议：1) orders 按 created_at 分区（日/小时），预警只扫当天分区；2) rider_online 在 (online_ts, offline_ts) 建索引或按城市分区，区间 join 前先按 city_id 过滤；3) 骑手供给可预聚合为"城市×30分钟在线人分钟"表，与订单桶表直接对齐；4) 生产中把滚动单量改为流式累计（Flink），SQL 只负责离线回溯校准阈值。

### 6. 面试延伸考点

- **滚动 1 小时为什么用"左开右闭"边界？** 要点：避免边界分钟的事件在相邻刻度被重复计入，保证滚动序列可加且无重算。
- **在线骑手数用"时点数"还是"人·分钟"？各适合什么决策？** 要点：时点数适合并发接单能力评估，人·分钟适合运力供给总量与成本核算；预警常用时点数，结算用人·分钟。
- **如果某 30 分钟完全没有订单，滑动窗口会怎样？** 要点：解法二会缺桶导致"前桶"错位，需用完整时间轴 LEFT JOIN 补零后再开窗。
- **如何把预警升级为"提前 30 分钟预测"？** 要点：用历史同周期负荷做基线预测（同昨/上周同时段），叠加实时偏差修正，SQL 输出预测缺口表。

### 7. 业务拓展思考

运力缺口预警是调度域"供需匹配"指标的雏形，可延展出分商圈/分品类粒度、雨天修正系数（恶劣天气骑手在线意愿下降而订单上升，见 LL-38），以及"缺口成本"货币化：缺口单量 × 超时赔付率 × 客单 GMV 损失，与拉骑手上线的补贴成本直接比较，形成 ROI 化的调度决策。联动动作包括冲单奖阶梯、跨商圈调度、商家出餐限流和用户端配送费动态调价；口径上还可拆"接单意愿"（在线但拒单率）与"真实运力"，避免在线人数虚高掩盖供给质量下滑。
## LL-35 商家曝光-转化公平性四象限矩阵

### 1. 业务背景

本地生活平台的流量是稀缺资源：首页推荐位、频道排序、搜索卡片每天要分配给几十万商家，BD（商务拓展）与运营团队经常收到商家投诉"不给曝光所以没单"，而流量团队又发现部分商家"给了曝光也没单"。平台运营负责人（谁）在月度流量分配复盘中，需要一张**曝光量×转化效率**的四象限矩阵（何时/什么）：横轴看商家拿到的曝光分位，纵轴看"曝光→下单"的转化分位，把商家切进"高效高量/高效低量/低效高量/低效低量"四象限（为什么）——高效低量（hidden gem）应该加权流量，低效高量要治理内容与头图，低效低量先诊断供给质量，高效高量维持并保护。这张矩阵是流量分配"公平性与效率"双重目标的量化底座，也是回答商家"为什么我没单"的标准工具。

### 2. 表结构说明

表名：merchant_expo_order（商家月度曝光与转化汇总表，由行为日志按月聚合预生成）

| 字段名 | 类型 | 含义 |
|---|---|---|
| merchant_id | BIGINT | 商家ID |
| stat_month | CHAR(7) | 统计月（如 2025-06） |
| category | VARCHAR(20) | 主营品类：美食/甜点/超市/到店综合 |
| expo_cnt | BIGINT | 当月曝光次数（推荐+搜索+频道） |
| order_user_cnt | BIGINT | 当月通过曝光进入并下单的去重用户数 |
| gmv | DECIMAL(18,2) | 当月GMV（元） |

示例数据：

| merchant_id | stat_month | category | expo_cnt | order_user_cnt | gmv |
|---|---|---|---|---|---|
| 20001 | 2025-06 | 美食 | 158000 | 4300 | 512000.00 |
| 20002 | 2025-06 | 美食 | 92000 | 210 | 24500.00 |
| 20003 | 2025-06 | 甜点 | 12000 | 980 | 88000.00 |
| 20004 | 2025-06 | 超市 | 305000 | 1200 | 190000.00 |
| 20005 | 2025-06 | 到店综合 | 6500 | 12 | 3600.00 |

（20003 是典型 hidden gem：曝光很低但转化效率高；20004 是低效高量的典型。）

### 3. 解题思路

先定口径：**转化效率 = order_user_cnt / expo_cnt**（每次曝光带来的下单用户数，即"曝光→下单"的端到端效率；不直接用 GMV 是因为品类客单价差异会污染效率信号）。矩阵构建分三步：第一，先过滤样本——剔除曝光量过低（如 <1000 次）的商家，避免"3 次曝光 1 单"的偶然高效率污染分位（**【避坑指南】** 小样本分位是这类矩阵最常见的翻车点）；第二，分别对曝光量与转化率做分位——曝光量用降序 `NTILE(4)` 或 `PERCENT_RANK` 切"高/低"，转化率同样切"高/低"，注意转化率并列值多（很多商家为 0）时分位会抖动，业务上应叠一个绝对门槛（如 order_user_cnt ≥ 30）后再分位；第三，二维组合打四象限标签并输出各象限的商家数与 GMV 占比，供运营直接圈人。两条实现路径：解法一用两层 `NTILE` 窗口一步切四象限；解法二用 `PERCENT_RANK + CASE` 阈值显式分层，便于把分位阈值固化成可复用的运营规则。

### 4. 参考解法

**解法一：双层 NTILE 一步切象限（简洁版）**

```sql
WITH base AS (                        -- 第一层：样本清洗，剔除小样本商家
    SELECT merchant_id, category,
           expo_cnt,
           order_user_cnt,
           order_user_cnt / expo_cnt AS cvr      -- 曝光→下单转化效率
    FROM merchant_expo_order
    WHERE stat_month = '2025-06'
      AND expo_cnt >= 1000                        -- 小样本剔除，防偶然高效率
      AND order_user_cnt >= 30                    -- 绝对单量门槛，稳定分位
),
quadrant AS (                        -- 第二层：双维分位
    SELECT merchant_id, category, expo_cnt, order_user_cnt, cvr,
           NTILE(4) OVER (ORDER BY expo_cnt DESC)        AS expo_tier,  -- 曝光量降序四分位，1=最高
           NTILE(4) OVER (ORDER BY cvr DESC)             AS cvr_tier    -- 转化率降序四分位，1=最高
    FROM base
)
SELECT CASE
         WHEN expo_tier <= 2 AND cvr_tier <= 2 THEN 'A_高效高量_维持保护'  -- 量足效率高
         WHEN expo_tier  > 2 AND cvr_tier <= 2 THEN 'B_高效低量_加权流量'  -- hidden gem
         WHEN expo_tier <= 2 AND cvr_tier  > 2 THEN 'C_低效高量_治理内容'  -- 曝光浪费
         ELSE                                        'D_低效低量_诊断供给'
       END AS quadrant,                                   -- 四象限标签
       COUNT(*)                AS merchant_cnt,           -- 象限内商家数
       SUM(gmv) / 10000        AS gmv_wan,                -- 象限GMV（万元）
       ROUND(AVG(cvr), 6)      AS avg_cvr                 -- 象限平均转化效率
FROM quadrant
GROUP BY quadrant
ORDER BY quadrant;
```

结果解读：B 象限（高效低量）通常商家数最少但平均 CVR 最高，是流量加权的首选池；C 象限如果 GMV 占比反常地高，说明平台流量在向低效商家集中，公平性预警。

**解法二：PERCENT_RANK + 显式阈值（规则固化版）**

```sql
WITH base AS (                          -- 同解法一的样本清洗
    SELECT merchant_id, category, expo_cnt, order_user_cnt,
           order_user_cnt / expo_cnt AS cvr
    FROM merchant_expo_order
    WHERE stat_month = '2025-06'
      AND expo_cnt >= 1000
      AND order_user_cnt >= 30
),
pct AS (                                -- 百分位化：PERCENT_RANK∈[0,1]，越大越靠前
    SELECT merchant_id, category, expo_cnt, order_user_cnt, cvr,
           PERCENT_RANK() OVER (ORDER BY expo_cnt) AS expo_pct,   -- 曝光百分位
           PERCENT_RANK() OVER (ORDER BY cvr)      AS cvr_pct     -- 效率百分位
    FROM base
)
SELECT CASE
         WHEN expo_pct >= 0.5 AND cvr_pct >= 0.5 THEN 'A_高效高量_维持保护'  -- 双前50%
         WHEN expo_pct <  0.5 AND cvr_pct >= 0.5 THEN 'B_高效低量_加权流量'
         WHEN expo_pct >= 0.5 AND cvr_pct <  0.5 THEN 'C_低效高量_治理内容'
         ELSE                                                     'D_低效低量_诊断供给'
       END AS quadrant,
       COUNT(*)          AS merchant_cnt,
       ROUND(COUNT(*) / SUM(COUNT(*)) OVER (), 4) AS merchant_share,  -- 商家数占比（全量分母）
       SUM(gmv)/10000    AS gmv_wan
FROM pct
GROUP BY quadrant
ORDER BY quadrant;
-- PERCENT_RANK 的价值：阈值0.5写死在规则里，运营口径可跨月复用、可对外解释；
-- NTILE 的价值：强制等分，适合"必须切四份"的场合。两者取其一，不要混用口径。
```

### 5. 性能分析与优化

解法一与解法二复杂度同阶：两个开窗各需一次全量排序（expo_cnt 一次、cvr 一次），百万级商家下排序是主要成本；两者都先在 base 里收窄到有效样本，扫描量可控。优化点：①**预聚合前置**——merchant_expo_order 本身应是数仓按"月×商家"预聚合的 DWS 表，绝不在明细日志上直接开窗（原始曝光日志按月可达百亿行）；②**减少一次排序**——若只需要四象限标签，可把 cvr 分位改为基于均值的绝对规则（如 cvr ≥ 全站 P50 的近似值存配置表），把两次开窗降为一次；③索引方面，DWS 表按 (stat_month, category) 分区/索引，`WHERE stat_month` 触发分区裁剪；④若输出要按品类分别出矩阵（不同品类 CVR 基线差异大），应在开窗里加 `PARTITION BY category`，避免美食与到店综合同台分位导致象限失真——这是业务正确性问题，比性能更重要。

### 6. 面试延伸考点

- **为什么转化率分位前要设绝对单量门槛？** 要点：小样本商家的 CVR 方差极大（1/3 与 300/900 同为 33%），分位会被噪声主导；先按"可靠样本"（order_user_cnt≥30）过滤，再分位才稳定。
- **曝光高但转化低的商家，一定是"低效"吗？** 要点：要区分"流量给了错误人群"（平台问题）与"商家承接差"（商家问题），可叠加点击率拆解——曝光→点击低是内容/头图问题，点击→下单低是价格/评价/供给问题；四象限是诊断入口，不是结论本身。
- **不同品类的 CVR 基线差异很大，矩阵怎么调整？** 要点：开窗加 `PARTITION BY category` 分品类内部排名，或对 CVR 做品类内标准化（相对全品类均值的倍数），避免跨品类比较。
- **这张矩阵和推荐系统的流量分配是什么关系？** 要点：矩阵是离线治理视角（月度复盘、规则化干预），线上分配是实时策略（pCTR/pCVR 预估）；矩阵产出的 hidden gem 名单会作为新商家冷启流量包与探索流量的输入。

### 7. 业务拓展思考

曝光-转化公平性矩阵把"流量该给谁"从主观分配变成可量化规则：B 象限加权曝光、C 象限治理头图与评分、D 象限诊断供给，A 象限保护体验，直接进流量分配策略与 BD 拜访队列。延展方向：把横轴换成"GMV 贡献"可得收入公平性视角；把时间维度拉长做象限迁移矩阵（上月 B → 本月 A 的晋级率），衡量冷启扶持的真实效果；再叠加"投诉率/履约超时率"作护栏，防止加权流量把差体验商家推上去。对平台而言，这张矩阵是"效率与公平"这对矛盾的第一个可讨论的量化基准，也是商家治理会上最常用的一页 PPT。

## LL-36 会员红包活动的增量GMV估算（简化DID）

### 1. 业务背景

会员运营团队在 8 个试点城市上线"会员红包周"活动（连续 7 天向会员发放无门槛红包），其余城市保持原样作为对照。财务要求回答：活动期这些城市 GMV 涨了多少是红包带来的"净增量"，而不是大盘自然上涨？这决定活动是全量推广、继续测试还是叫停。直接对比试点城市活动前后的 GMV 会把大盘增长、季节因素全部算成红包功劳，必须引入未受干预的对照城市做双重差分（DID），净增量结论直接决定下一个亿级预算的走向。

### 2. 表结构说明

city_daily_gmv（城市日粒度经营表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| dt | DATE | 日期 |
| city_id | INT | 城市ID |
| gmv | DECIMAL(14,2) | 当日GMV |
| order_cnt | INT | 当日订单量 |

ab_city_group（城市分组表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| city_id | INT | 城市ID |
| group_tag | VARCHAR(10) | 分组（treat=试点发红包，control=对照） |

city_daily_gmv 示例数据：

| dt | city_id | gmv | order_cnt |
| --- | --- | --- | --- |
| 2026-10-06 | 1 | 1,250,000.00 | 38,500 |
| 2026-10-13 | 1 | 1,420,000.00 | 43,800 |
| 2026-10-06 | 2 | 860,000.00 | 26,100 |
| 2026-10-13 | 2 | 895,000.00 | 27,300 |
| 2026-10-19 | 1 | 1,380,000.00 | 42,600 |

ab_city_group 示例数据：

| city_id | group_tag |
| --- | --- |
| 1 | treat |
| 2 | control |
| 3 | treat |
| 4 | control |
| 5 | treat |

### 3. 解题思路

DID 口径：净增量 = 试验组前后差 − 对照组前后差，隐含假设是"没有红包时两组会走出平行趋势"。先定观察窗：活动期 2026-10-13~10-19（post），活动前一周 10-06~10-12（pre），两组各 7 天对齐以消除周内效应。指标建议用"城市日均 GMV"而不是总 GMV，避免两组城市数不同带来的规模差。实现路径：a) 四格表法——按 组×前后 聚合出四个均值，一次 CROSS JOIN 行转列后相减；b) 城市级个体差分法——先给每个城市算前后差值，再对两组差值求均值比较，附带看组内离散度以判断稳健性。易错点：前后期长度不一致、城市数不等却直接比总量、忘记验证平行趋势（活动前两周两组增速应接近）、活动期间同时有其他营销叠加造成污染。

### 4. 参考解法

**解法一：DID 四格表（2×2 行转列，汇报最直观）**

```sql
WITH base AS (                                -- 步骤1：拼接分组标签并圈定前后各7天
    SELECT g.group_tag,                       -- treat=红包试点城市
           CASE WHEN s.dt BETWEEN '2026-10-13' AND '2026-10-19'
                THEN 'post' ELSE 'pre' END AS phase,          -- 活动期/活动前
           s.city_id, s.gmv
    FROM city_daily_gmv s
    JOIN ab_city_group g ON g.city_id = s.city_id
    WHERE s.dt BETWEEN '2026-10-06' AND '2026-10-19'          -- 前后各一周，长度对齐
),
cell AS (                                     -- 步骤2：聚合出四格的"城市日均GMV"
    SELECT group_tag, phase,
           ROUND(SUM(gmv) / 7.0 / COUNT(DISTINCT city_id), 2) AS avg_city_daily_gmv
    FROM base
    GROUP BY group_tag, phase
)
SELECT MAX(CASE WHEN group_tag='treat'   AND phase='pre'  THEN avg_city_daily_gmv END) AS t_pre,
       MAX(CASE WHEN group_tag='treat'   AND phase='post' THEN avg_city_daily_gmv END) AS t_post,
       MAX(CASE WHEN group_tag='control' AND phase='pre'  THEN avg_city_daily_gmv END) AS c_pre,
       MAX(CASE WHEN group_tag='control' AND phase='post' THEN avg_city_daily_gmv END) AS c_post,
       ROUND(
           (MAX(CASE WHEN group_tag='treat'   AND phase='post' THEN avg_city_daily_gmv END)
          - MAX(CASE WHEN group_tag='treat'   AND phase='pre'  THEN avg_city_daily_gmv END))
         - (MAX(CASE WHEN group_tag='control' AND phase='post' THEN avg_city_daily_gmv END)
          - MAX(CASE WHEN group_tag='control' AND phase='pre'  THEN avg_city_daily_gmv END)), 2)
           AS did_increment                    -- 净增量 = 试验组前后差 - 对照组前后差
FROM cell;
```

结果解读：假设输出 t_pre=120 万、t_post=135 万、c_pre=95 万、c_post=99 万，则净增量 = 15 − 4 = 11 万元/城市日，即红包带来约 11 万的城市日增量 GMV，可进一步对比红包成本算活动 ROI。

**解法二：城市级个体差分（保留分布信息，稳健性更好）**

```sql
WITH base AS (                                -- 步骤1：同解法一，拼分组与前后期标签
    SELECT g.group_tag,
           CASE WHEN s.dt BETWEEN '2026-10-13' AND '2026-10-19' THEN 'post' ELSE 'pre' END AS phase,
           s.city_id, s.gmv
    FROM city_daily_gmv s
    JOIN ab_city_group g ON g.city_id = s.city_id
    WHERE s.dt BETWEEN '2026-10-06' AND '2026-10-19'
),
city_pair AS (                                -- 步骤2：每城市分别算前后两周日均GMV
    SELECT city_id, group_tag,
           SUM(CASE WHEN phase='post' THEN gmv END) / 7.0 AS post_avg,
           SUM(CASE WHEN phase='pre'  THEN gmv END) / 7.0 AS pre_avg
    FROM base
    GROUP BY city_id, group_tag
),
city_delta AS (                               -- 步骤3：城市个体差分
    SELECT city_id, group_tag, post_avg, pre_avg,
           post_avg - pre_avg AS delta
    FROM city_pair
)
SELECT group_tag,
       COUNT(*) AS city_cnt,                  -- 组内城市数（样本量提示）
       ROUND(AVG(delta), 2) AS avg_delta,     -- 组平均前后差，两组相减即DID
       ROUND(MIN(delta), 2) AS min_delta,     -- 组内最小差（看是否有负增长城市）
       ROUND(MAX(delta), 2) AS max_delta      -- 组内最大差（看是否被个别大城拉爆）
FROM city_delta
GROUP BY group_tag;
```

结果解读：试验组平均 delta 减对照组平均 delta 仍是 DID 估计，但 min/max 揭示组内一致性——若某试点城市 delta 为负，说明红包在供给不足的城市无效，全量推广前要按城市特征分层。

> **Hive/Spark SQL 差异**：城市日表按 dt 分区，取前后两周直接分区裁剪；`SUM(CASE WHEN phase='post' THEN gmv END)` 在 Hive 中写法相同；若城市数上千，可在解法二基础上加 `percentile_approx(delta, 0.5)` 看中位数差分以抵抗离群城市。

### 5. 性能分析与优化

解法一在 cell 层完成全部分组，之后只有 4 行的行转列，代价集中在 base 的 join 与一次聚合；解法二多一层城市粒度聚合，中间结果 2×城市数 行，几乎无额外开销。优化建议：1) ab_city_group 很小时 MySQL 会选它做驱动表，给 city_id 建主键/唯一索引即可；2) city_daily_gmv 按 dt 分区并只扫两周分区，按 city_id 建索引加速 join；3) 例行化后可预聚合"城市×周"粒度表，DID 退化为一行四列；4) 若要评估置信度，城市数太少（<8）时不宜用 t 检验，应改置换检验或扩大试验城市数。

### 6. 面试延伸考点

- **DID 成立的核心假设是什么？如何用 SQL 验证？** 要点：平行趋势——取活动前 3~4 周，逐周比较两组增速差是否稳定在 0 附近，SQL 上做"期数×分组"的分组均值序列。
- **为什么用城市日均而不是总 GMV？** 要点：两组城市数可能不同，总量比较混入规模效应；日均（或人均）把口径拉平，是处理效应的正确载体。
- **活动期恰逢竞对大促怎么办？** 要点：若竞对大促只覆盖部分城市，会把污染算进处理效应，需剔除被覆盖城市或用三重差分（DDD）。
- **红包成本怎么并入结论？** 要点：净增量 GMV × 毛利率 与 红包核销金额比较，再叠加会员长期留存价值，避免只看短期收支。

### 7. 业务拓展思考

DID 框架可平移到几乎所有"城市级 A/B"场景：配送费调价、新首页改版灰度、品类补贴。结论联动动作明确——净增量为正且 ROI 达标则全量推广，反之排查红包核销漏斗（领取未使用、使用了未复购）。口径延展上，可把 GMV 换成新客数、会员开卡数等北极星指标；可延长 post 窗口观察"活动后回落"，估算净增量的衰减曲线，判断红包培育的是长期习惯还是一次性薅羊毛；还可按会员等级分层做 DID，识别哪一层用户对红包最敏感，实现差异化发券。

## LL-37 用户品类偏好季度迁移矩阵

### 1. 业务背景

品类运营总监在季度复盘中提出：用户的主消费品类正在迁移吗？比如上一季度主买"甜点饮品"的用户，这一季度有多大比例转向"美食正餐"？迁移矩阵能揭示品类的此消彼长是"拉新"还是"存量互搏"，直接决定品类营销打法——若是互搏，应对流失品类做挽留券而非继续加码拉新；若是外部流入，则应扩大新品类供给。分析师需要以用户为单位，取每季度订单量最大的品类作为"主品类"，构建 Q2→Q3 的迁移矩阵并找出最大的流入/流出品类对。

### 2. 表结构说明

orders（订单表，虚构，本题只需要用户、日期、品类三列）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| order_dt | DATE | 下单日期 |
| category_id | INT | 品类ID（1=美食正餐 2=甜点饮品 3=生鲜果蔬 4=超市便利） |
| pay_amount | DECIMAL(10,2) | 实付金额 |

orders 示例数据：

| order_id | user_id | order_dt | category_id | pay_amount |
| --- | --- | --- | --- | --- |
| 550001 | 301 | 2026-04-10 | 2 | 22.00 |
| 550002 | 301 | 2026-07-08 | 1 | 45.00 |
| 550003 | 302 | 2026-05-21 | 2 | 18.50 |
| 550004 | 302 | 2026-08-02 | 2 | 20.00 |
| 550005 | 303 | 2026-06-15 | 4 | 33.00 |

### 3. 解题思路

口径：主品类 = 用户当季订单量最大的品类（并列时取 ID 小者保证可复现）；迁移对 = 同一用户相邻两季主品类组合（Q2 主品类 → Q3 主品类），品类不变的用户可单独统计为"留存"，变了的是"迁移"。实现路径：a) 用户×季度×品类聚合 → ROW_NUMBER 取主品类 → LAG 取上季主品类 → 过滤目标季度后聚合成矩阵；b) 主品类表自连接，连接条件为"同用户、季度序号 +1"（用 年×4+季度 把季度转成连续整数，规避字符串比较）。易错点：LAG 按季度字符串排序在跨年时会乱（Q1'27 < Q4'26），必须用整数季度序号或年季联合排序；两季都有消费才构成迁移对，只在一季消费的用户要剔除或归入"新客/流失"桶；季度并列主品类的 tie-breaking 要写明。

### 4. 参考解法

**解法一：多层 CTE + LAG 序列化（推荐，扩展到多季度容易）**

```sql
WITH uq AS (                                  -- 步骤1：用户×季度×品类 聚合单量
    SELECT user_id,
           CONCAT(YEAR(order_dt), '-Q', QUARTER(order_dt)) AS qtr,  -- 季度标签
           YEAR(order_dt) * 4 + QUARTER(order_dt) AS qidx,          -- 整数季度序号，跨年不乱序
           category_id,
           COUNT(*) AS order_cnt
    FROM orders
    WHERE order_dt >= '2026-01-01'
    GROUP BY user_id, qtr, qidx, category_id
),
main_cat AS (                                 -- 步骤2：每用户每季度取单量最大的主品类
    SELECT user_id, qtr, qidx, category_id,
           ROW_NUMBER() OVER (PARTITION BY user_id, qidx
                              ORDER BY order_cnt DESC, category_id) AS rn  -- 并列时按品类ID稳定破平
    FROM uq
),
seq AS (                                      -- 步骤3：LAG 取该用户上季度主品类
    SELECT user_id, qtr, category_id AS to_cat,
           LAG(category_id) OVER (PARTITION BY user_id ORDER BY qidx) AS from_cat
    FROM main_cat
    WHERE rn = 1
)
SELECT from_cat AS from_category,             -- 流出品类（上季主品类）
       to_cat   AS to_category,               -- 流入品类（本季主品类）
       COUNT(*) AS user_cnt,                  -- 迁移用户数
       ROUND(COUNT(*) / SUM(COUNT(*)) OVER () * 100, 2) AS pct_of_flows  -- 占全部迁移流比例
FROM seq
WHERE qtr = '2026-Q3'                         -- 只看 Q3 的流入结构
  AND from_cat IS NOT NULL                    -- 排除 Q3 新客（无上季主品类）
GROUP BY from_cat, to_cat
ORDER BY user_cnt DESC;
```

结果解读：矩阵中"2→1"（甜点饮品→美食正餐）若以最高占比出现，说明饮品用户在向正餐升级，应把正餐拉新券替换为饮品用户的正餐尝鲜券。

**解法二：主品类表自连接相邻季度（不依赖窗口的等价写法）**

```sql
WITH uq AS (                                  -- 步骤1：聚合（整数季度序号防跨年乱序）
    SELECT user_id,
           YEAR(order_dt) * 4 + QUARTER(order_dt) AS qidx,
           category_id,
           COUNT(*) AS order_cnt
    FROM orders
    WHERE order_dt >= '2026-01-01'
    GROUP BY user_id, qidx, category_id
),
main_cat AS (                                 -- 步骤2：只保留主品类行
    SELECT user_id, qidx, category_id
    FROM (
        SELECT user_id, qidx, category_id,
               ROW_NUMBER() OVER (PARTITION BY user_id, qidx
                                  ORDER BY COUNT(*) DESC, category_id) AS rn
        FROM uq
        GROUP BY user_id, qidx, category_id   -- 窗口在聚合结果上执行
    ) t
    WHERE rn = 1
)
SELECT a.category_id AS from_category,
       b.category_id AS to_category,
       COUNT(*)       AS user_cnt
FROM main_cat a                               -- 上季主品类
JOIN main_cat b                               -- 本季主品类
  ON b.user_id = a.user_id
 AND b.qidx  = a.qidx + 1                     -- 相邻季度：序号+1 即下一季
GROUP BY a.category_id, b.category_id
ORDER BY user_cnt DESC;
```

结果解读：自连接版与 LAG 版结果一致；qidx+1 的等值连接让优化器走 hash join，在用户量大、季度多的场景比窗口排序更省内存，且天然排除只有单季消费的用户。

> **Hive/Spark SQL 差异**：Hive 写法完全兼容（QUARTER 需 2.0+，低版本用 `(month(dt)-1) DIV 3 + 1` 替代）；订单表按 user_id 分桶后，自连接与窗口都能避免全量 shuffle；季度很长（如 24 个季度）时建议把迁移对落成拉链表增量维护。

### 5. 性能分析与优化

两解法都要先做用户×季度×品类的全量聚合，这是最大开销；其后解法一多一次按 qidx 的分区排序（LAG），解法二多一次按 user_id+qidx 的 hash join。优化建议：1) orders 按 dt 分区裁剪后，聚合输入已限定在观察季度；2) (user_id, order_dt) 复合索引或按 user_id 分桶可同时加速两条路径；3) 把"用户×季度主品类"物化为月更表，迁移矩阵变成对主品类表的轻量连接；4) 若只需 TopN 迁移对，可在聚合后先按 user_cnt 过滤再窗口计算占比，减少排序数据量。

### 6. 面试延伸考点

- **为什么主品类按订单量而不是 GMV 取？** 要点：订单量代表"频次习惯"，GMV 代表"钱包份额"；两者口径要写清楚，本题为频次口径，财务口径应换 GMV 重算并对比差异。
- **LAG 用季度字符串排序会有什么问题？** 要点：`2026-Q1` 与 `2025-Q4` 按字典序会颠倒，必须用 年×4+季度 的整数序号或 (year, quarter) 双键排序。
- **如何区分"品类迁移"和"品类流失"？** 要点：迁移对之外单独统计"上季活跃、本季无单"用户为流失桶，与迁入新品类的用户分开看，动作完全不同（召回 vs 交叉推荐）。
- **矩阵能否升级为转移概率表？** 要点：行内归一化（该流出品类用户中迁往各品类的比例），即马尔可夫转移矩阵，可用于多步预测品类结构演化。

### 7. 业务拓展思考

迁移矩阵是品类战略的基础仪表盘：持续追踪可发现结构性趋势（如夜宵品类吃掉下午茶份额），提前调整供给招商方向。联动动作上——大迁移对触发定向交叉券（LL-42 的推荐位承接）、流失品类启动供给丰富度专项与价格力对标；口径可延展为"主商圈迁移"（用户搬家/换工作地识别）、"价格带迁移"（消费升级/降级监测），以及把季度粒度细化到月观察迁移速度，为品类预算的节奏分配提供依据。

## LL-38 恶劣天气GMV弹性测算

### 1. 业务背景

定价与补贴团队需要回答：下雨、下雪天外卖 GMV 会涨多少？涨幅是否足以覆盖恶劣天气下骑手运力成本上升？这决定"天气动态调价"策略——雨天是否加收配送费、给商家多少天气补贴、给骑手多少天气奖励。测算口径是"天气弹性"：恶劣天气日相对正常天气日的 GMV 提升幅度。直接拿雨天全平台均值比晴天均值会被大城市淹没（大城市订单多、且未必多雨），也忽略持续降雨期间的自然增长趋势，需要城市内配对与邻接日对照两种口径互相校验。

### 2. 表结构说明

city_weather_daily（城市日天气表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| dt | DATE | 日期 |
| city_id | INT | 城市ID |
| weather_type | VARCHAR(10) | 天气（sunny/cloudy/rain/snow） |

city_daily_metrics（城市日经营表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| dt | DATE | 日期 |
| city_id | INT | 城市ID |
| gmv | DECIMAL(14,2) | 当日GMV |
| order_cnt | INT | 当日订单量 |

city_weather_daily 示例数据：

| dt | city_id | weather_type |
| --- | --- | --- |
| 2026-10-20 | 1 | sunny |
| 2026-10-21 | 1 | rain |
| 2026-10-22 | 1 | rain |
| 2026-10-21 | 2 | cloudy |
| 2026-10-22 | 2 | snow |

city_daily_metrics 示例数据：

| dt | city_id | gmv | order_cnt |
| --- | --- | --- | --- |
| 2026-10-20 | 1 | 1,200,000.00 | 37,000 |
| 2026-10-21 | 1 | 1,392,000.00 | 42,500 |
| 2026-10-22 | 1 | 1,452,000.00 | 44,000 |
| 2026-10-21 | 2 | 780,000.00 | 24,000 |
| 2026-10-22 | 2 | 858,000.00 | 26,200 |

### 3. 解题思路

两种口径：a) 城市内配对均值——每个城市分别算"恶劣天气日均 GMV ÷ 正常天气日均 GMV − 1"，再对城市求平均。先在城市内做比值再平均，避免 GMV 大城市主导结果（对冲辛普森悖论）；b) LAG 邻接日对照——每个恶劣天气日与其前一个正常天气日配对，算当日相对前日的变化再平均。邻接日对照能吸收大盘增长趋势与部分周内效应，但会把周中/周末错配引入噪声，可叠加"同周几"约束。易错点：a) 全平台直接比均值会因城市规模权重失真；b) 连续多天雨天时"前一日也是雨天"，不构成对照对，必须限定前一日为正常天气；c) 弹性要用 GMV 还是单量？两者要分开看——单量弹性更纯粹，GMV 弹性混入客单价变化；d) 样本不足的城市（无雨天或无晴天）要剔除。

### 4. 参考解法

**解法一：城市内配对均值再平均（对冲城市规模权重）**

```sql
WITH j AS (                                   -- 步骤1：天气与经营按 城市+日期 对齐
    SELECT w.city_id, w.dt, w.weather_type, s.gmv
    FROM city_weather_daily w
    JOIN city_daily_metrics s
      ON s.city_id = w.city_id AND s.dt = w.dt
    WHERE w.dt BETWEEN '2026-09-01' AND '2026-10-24'
),
city_ratio AS (                               -- 步骤2：城市内部先算两类天气的日均GMV
    SELECT city_id,
           AVG(CASE WHEN weather_type IN ('rain','snow') THEN gmv END)  AS bad_avg,
           AVG(CASE WHEN weather_type IN ('sunny','cloudy') THEN gmv END) AS good_avg
    FROM j
    GROUP BY city_id
)
SELECT COUNT(*) AS city_cnt,                                       -- 参与测算的城市数
       ROUND(AVG(bad_avg / NULLIF(good_avg, 0) - 1) * 100, 2) AS elasticity_pct,  -- 城市级弹性均值
       ROUND(SUM(bad_avg) / SUM(good_avg) - 1, 4) AS pooled_ratio  -- 池化比值作对照（会被大城市主导）
FROM city_ratio
WHERE good_avg > 0;                           -- 剔除无正常天气样本的城市
```

结果解读：elasticity_pct 是每个城市"自己和自己比"的平均弹性，pooled_ratio 故意并列输出以暴露口径差异——两者差距大说明大城市雨天效应异于中小城市，应分层汇报。

**解法二：LAG 邻接日对照（吸收趋势与周内效应的准实验口径）**

```sql
WITH j AS (                                   -- 步骤1：同解法一对齐天气与GMV
    SELECT w.city_id, w.dt, w.weather_type, s.gmv
    FROM city_weather_daily w
    JOIN city_daily_metrics s
      ON s.city_id = w.city_id AND s.dt = w.dt
    WHERE w.dt BETWEEN '2026-09-01' AND '2026-10-24'
),
seq AS (                                      -- 步骤2：按城市时间排序，LAG 取前一日状态
    SELECT city_id, dt, weather_type, gmv,
           LAG(weather_type) OVER (PARTITION BY city_id ORDER BY dt) AS prev_weather,
           LAG(gmv)          OVER (PARTITION BY city_id ORDER BY dt) AS prev_gmv
    FROM j
)
SELECT ROUND(AVG(gmv / NULLIF(prev_gmv, 0) - 1) * 100, 2) AS day_over_prev_pct,  -- 恶劣日相对前一日涨幅
       COUNT(*) AS valid_pairs                 -- 有效对照对数量（样本量提示）
FROM seq
WHERE weather_type IN ('rain', 'snow')        -- 今日为恶劣天气日
  AND prev_weather IN ('sunny', 'cloudy');    -- 前一日为正常天气，才构成对照
```

结果解读：只保留"正常日→恶劣日"的转换对，涨幅天然剔除了趋势项；若该口径结果低于解法一，说明部分弹性其实是持续增长趋势，调价策略应以更保守的邻接口径为准。

> **Hive/Spark SQL 差异**：两表均按 dt 分区，join 前分区裁剪；LAG 的 PARTITION BY city_id ORDER BY dt 在 Hive 中一致，注意大表按 city_id 分桶可省一次 shuffle；样本极多时可用 `percentile_approx(day_ratio, ARRAY[0.25,0.5,0.75])` 输出弹性分布而非单点均值。

### 5. 性能分析与优化

解法一是一次 join + 一次分组，代价 O(城市×天数)；解法二在 join 基础上多一次 (city_id, dt) 窗口排序，排序粒度为城市内时间序列。两者都轻。优化建议：1) city_daily_metrics 以 (city_id, dt) 为唯一键建聚簇/唯一索引，join 走等值匹配；2) 天气表可预铺成"城市×日"全量维度表（缺失日补 unknown），避免 join 丢行；3) 例行化时预聚合"城市×天气类型×周"中间表，弹性周报退化为简单比值；4) 结论做显著性判断时在城市层做 bootstrap，避免伪复制（把日样本当独立样本高估显著性）。

### 6. 面试延伸考点

- **为什么先在城市内做比值再平均，而不是全平台比值？** 要点：全平台比值按城市规模隐式加权，弹性被大城市主导；城市内比值再平均是"每个城市等权"，更能代表典型城市的天气效应。
- **连续降雨第二天还算"恶劣天气效应"吗？** 要点：邻接对照口径中前一日也是雨天则被剔除，避免把趋势当效应；配对口径里它仍算恶劣日均，两个口径差异本身就是洞察。
- **怎么把弹性换算成调价策略？** 要点：弹性×正常日 GMV = 预期增量，对比雨天运力加价与骑手补贴成本，增量毛利覆盖成本才启动动态加价。
- **GMV 弹性和单量弹性不一致说明什么？** 要点：雨天客单价变了（囤货型大单），策略上应区分"运力承接"与"客单运营"两个动作。

### 7. 业务拓展思考

天气弹性可延展为分品类弹性矩阵——生鲜果蔬囤货弹性最高、甜点饮品几乎不受影响，据此在雨天动态调整品类流量分配与补贴投向；也可与 LL-34 联动，构建"雨天运力缺口预测"，提前一天按天气预报预调度骑手。口径延展包括：温度区间替代天气类型做连续变量弹性、空气质量（雾霾）对到店 vs 外卖的结构性影响、以及"天气效应衰减曲线"（降雨持续第几天后弹性回落），为动态调价的启用/退出阈值提供依据。

## LL-39 商圈POI流量-进店-下单漏斗分层

### 1. 业务背景

到店业务的平台侧运营管理着数千个商圈 POI（门店页）。每个 POI 的用户旅程是"列表页曝光 → 点击进店 → 下单"，两层转化率反映不同问题：曝光进店率低通常是头图、评分、起送价等"门面"问题；进店下单率低是套餐、价格力、评价内容问题。团队需要按曝光规模把 POI 分成头部/腰部/尾部三层，分别计算各层漏斗转化率并定位瓶颈层——头部 POI 是流量分配的大盘基本盘，尾部 POI 中"高转化低曝光"的则应加权扶持。结论用于流量分配策略与 POI 运营专项的立项排序。

### 2. 表结构说明

poi_funnel_daily（POI 日粒度漏斗表，虚构，UV 口径已由上游预聚合）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| dt | DATE | 日期 |
| poi_id | BIGINT | 门店POI ID |
| biz_circle_id | INT | 所属商圈ID |
| expo_uv | INT | 曝光UV（在列表页被展示的去重用户数） |
| enter_uv | INT | 进店UV（点击进入门店页的去重用户数） |
| order_uv | INT | 下单UV（当日下单的去重用户数） |

poi_funnel_daily 示例数据：

| dt | poi_id | biz_circle_id | expo_uv | enter_uv | order_uv |
| --- | --- | --- | --- | --- | --- |
| 2026-10-24 | 8001 | 11 | 12,000 | 2,400 | 360 |
| 2026-10-24 | 8002 | 11 | 8,000 | 640 | 160 |

| 2026-10-24 | 8004 | 12 | 900 | 90 | 18 |
| 2026-10-24 | 8005 | 13 | 5,000 | 1,500 | 525 |

### 3. 解题思路

口径：近 30 天聚合每个 POI 的 expo/enter/order UV，漏斗两段转化率 = enter/expo 与 order/enter；分层用曝光 UV 的 NTILE(3)（头部/腰部/尾部），也可以用 PERCENT_RANK 阈值。产出三件事：各层漏斗、每个 POI 的瓶颈诊断标签（与全量基准比较，两段转化率低于基准 40% 分别标记"曝光-进店瓶颈"或"进店-下单瓶颈"）、以及"高转化低曝光"潜力名单。易错点：a) UV 不能跨日直接相加再当 UV 用——本表是日 UV，跨期求和是"人次口径"，严格 UV 需上游按期去重，本题按业务惯例说明后使用人次口径；b) 分层按"期曝光总量"而非日均，避免 POI 上下线天数不同造成偏差；c) 尾部 POI 单期样本小，转化率波动大，应设最小样本阈值。

### 4. 参考解法

**解法一：NTILE 三层分层漏斗（直接产出分层大盘）**

```sql
WITH agg AS (                                 -- 步骤1：近30天POI级漏斗聚合
    SELECT poi_id, biz_circle_id,
           SUM(expo_uv)  AS expo,
           SUM(enter_uv) AS enter,
           SUM(order_uv) AS ord
    FROM poi_funnel_daily
    WHERE dt >= DATE_SUB('2026-10-25', INTERVAL 30 DAY)
    GROUP BY poi_id, biz_circle_id
    HAVING SUM(expo_uv) >= 3000               -- 最小样本阈值，滤掉长尾噪声POI
),
tiered AS (                                   -- 步骤2：按曝光规模分三层
    SELECT *,
           CASE NTILE(3) OVER (ORDER BY expo DESC)
                WHEN 1 THEN 'head'             -- 头部：曝光前1/3
                WHEN 2 THEN 'waist'            -- 腰部
                ELSE 'tail' END AS poi_tier    -- 尾部
    FROM agg
)
SELECT poi_tier,
       COUNT(*) AS poi_cnt,                                       -- 层内POI数
       SUM(expo) AS total_expo,
       ROUND(SUM(enter) / SUM(expo) * 100, 2) AS expo_to_enter_pct,  -- 漏斗第一段
       ROUND(SUM(ord)   / SUM(enter) * 100, 2) AS enter_to_order_pct, -- 漏斗第二段
       ROUND(SUM(ord)   / SUM(expo) * 100, 2) AS end_to_end_pct    -- 端到端转化
FROM tiered
GROUP BY poi_tier
ORDER BY total_expo DESC;
```

结果解读：典型结论是"尾部曝光进店率高于头部但端到端最低"或相反——各层短板不同，分层运营专项才能对症下药，而不是一刀切优化头图。

**解法二：基准偏差法逐 POI 瓶颈诊断 + 潜力名单（运营可执行）**

```sql
WITH agg AS (                                 -- 步骤1：POI级近30天聚合（同解法一）
    SELECT poi_id, biz_circle_id,
           SUM(expo_uv)  AS expo,
           SUM(enter_uv) AS enter,
           SUM(order_uv) AS ord
    FROM poi_funnel_daily
    WHERE dt >= DATE_SUB('2026-10-25', INTERVAL 30 DAY)
    GROUP BY poi_id, biz_circle_id
    HAVING SUM(expo_uv) >= 3000
),
benchmark AS (                                -- 步骤2：全量基准（两段转化率+平均曝光）
    SELECT SUM(enter) / SUM(expo) AS base_enter_rate,
           SUM(ord)   / SUM(enter) AS base_order_rate,
           AVG(expo) AS avg_expo,
           SUM(ord) / SUM(expo) AS base_e2e
    FROM agg
),
diag AS (                                     -- 步骤3：逐POI与基准比较打诊断标签
    SELECT a.poi_id, a.biz_circle_id, a.expo, a.enter, a.ord,
           CASE
             WHEN a.enter / a.expo < b.base_enter_rate * 0.6
              AND a.ord / a.enter >= b.base_order_rate * 0.8 THEN 'expo_gate'   -- 进得来店的人会买：门面不行
             WHEN a.enter / a.expo >= b.base_enter_rate * 0.8
              AND a.ord / a.enter <  b.base_order_rate * 0.6 THEN 'order_gate'  -- 进店不下单：套餐价格力问题
             WHEN a.expo < b.avg_expo * 0.5
              AND a.ord / a.expo > b.base_e2e * 2 THEN 'hidden_gem'             -- 高转化低曝光：潜力股
             ELSE 'normal'
           END AS diag_tag
    FROM agg a CROSS JOIN benchmark b         -- 基准只有一行，笛卡尔积安全
)
SELECT diag_tag,
       COUNT(*) AS poi_cnt,
       SUM(expo) AS total_expo                 -- 各诊断桶的流量占比，用于排专项优先级
FROM diag
GROUP BY diag_tag
ORDER BY total_expo DESC;
```

结果解读：expo_gate 桶流量占比最高说明大盘主要浪费在"列表页门面"，应优先推头图与评分治理；hidden_gem 名单（个数少但转化数倍于大盘）直接交给 BD 加权扶持。

> **Hive/Spark SQL 差异**：日漏斗表按 dt 分区；NTILE 与基准 CROSS JOIN 写法通用；POI 数十万级时建议按 biz_circle_id 分桶，诊断 SQL 改为先算商圈内基准再全局基准双层对比，避免跨商圈可比性问题。

### 5. 性能分析与优化

两解法的主体都是一次 30 天聚合（O(POI×30) 行输入）；解法一多一次 NTILE 排序，解法二多一次一行基准的 CROSS JOIN，开销均可忽略。瓶颈在输入表行数。优化建议：1) poi_funnel_daily 按 dt 分区裁剪到 30 天；2) (poi_id, dt) 唯一索引/分桶，聚合走本地预聚合；3) 把"POI×30天漏斗"物化为周更中间表，分层与诊断直接基于该表；4) NTILE 分层要求全局排序，POI 千万级时改用 expo 的分位数截断值（如先算 1/3 分位阈值）再 CASE 分层，可并行执行。

### 6. 面试延伸考点

- **跨日 UV 相加是什么口径？什么时候可以接受？** 要点：相加后是"人次"而非去重 UV；漏斗分子分母同口径相除时偏差可接受，但汇报必须注明，严格 UV 要上游按期去重。
- **为什么按曝光分层而不是按 GMV 分层？** 要点：本题诊断的是"流量分配效率"，曝光是投入侧变量；若做商家价值分层则应按 GMV/单量，口径服务于问题。
- **尾部 POI 样本少导致转化率不稳怎么办？** 要点：设最小曝光阈值、拉长观察窗至 60~90 天、或用贝叶斯平滑（向全局基准收缩）后再排序。
- **NTILE 和 PERCENT_RANK 各适合什么场景？** 要点：NTILE 强制等量切桶，受并列值影响；PERCENT_RANK 按分数切，业务阈值（前 20%）明确时更直观。

### 7. 业务拓展思考

漏斗分层可继续下探一层：把"进店-下单"拆成"加购/凑单/支付"细漏斗，定位是套餐吸引力还是支付环节流失；也可按商圈聚合诊断，识别系统性短板商圈（BD 覆盖不足 vs 供给同质化）。联动动作：hidden_gem 名单进入流量加权与 BD 拜访队列；expo_gate 桶推进头图 A/B 与评分治理；order_gate 桶联动套餐改造与价格力对标。口径延展上，可将曝光公平性（LL-35 的四象限）与漏斗瓶颈合并成"流量效率双维看板"，成为到店运营周会的固定决策依据。

## LL-40 商家生命周期阶段识别（gaps-and-islands）

### 1. 业务背景

商家运营团队管理数十万在营商家，不同阶段需要完全不同的运营动作：上线初期（爬坡期）要流量扶持与开店辅导；爆发期要保供给、保时效，避免爆单压垮履约；衰退期要在彻底流失前用补贴与诊断工具促活。分析师需要把每个商家上线以来的日单量序列自动划分为生命周期阶段，输出"当前处于什么阶段、每个阶段起止日期"，供 CRM 分层触达。技术上等价于：识别"日单量显著高于该商家自身均值"的连续区段（连续高单量段 = 爆发期），这正是 gaps-and-islands 的经典应用。

### 2. 表结构说明

merchants（商家主表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| merchant_id | BIGINT | 商家ID |
| launch_dt | DATE | 平台上线日期 |
| category_id | INT | 主营品类ID |

merchant_daily（商家日单量表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| merchant_id | BIGINT | 商家ID |
| dt | DATE | 日期 |
| order_cnt | INT | 当日有效订单量 |

merchants 示例数据：

| merchant_id | launch_dt | category_id |
| --- | --- | --- |
| 4001 | 2026-05-01 | 1 |
| 4002 | 2026-03-15 | 2 |
| 4003 | 2026-06-01 | 1 |
| 4004 | 2026-01-10 | 4 |
| 4005 | 2026-08-01 | 3 |

merchant_daily 示例数据：

| merchant_id | dt | order_cnt |
| --- | --- | --- |
| 4001 | 2026-10-20 | 12 |
| 4001 | 2026-10-21 | 45 |
| 4001 | 2026-10-22 | 52 |
| 4001 | 2026-10-23 | 48 |
| 4002 | 2026-10-22 | 5 |

### 3. 解题思路

口径设计：以商家自身历史日均单量为基准（窗口 AVG 计算，避免跨商家比较），日单量 ≥ 日均×1.5 记为"高单量日"；连续 ≥7 个高单量日构成"爆发段"（消除断续噪声）。阶段划分规则：上线后 30 天内为爬坡期；命中爆发段的日期为爆发期；最近 14 天滑动均值 < 日均×0.5 为衰退期；其余为稳定期。gaps-and-islands 实现：对高单量标记按商家分区、按日期排序生成行号，`日期 − 行号天` 的差值在连续段内恒定，该差值即为分段键，MIN/MAX 即得段起止。易错点：a) 日期序列有断档（商家歇业日）时"连续"被自然打断，要决定断档是否重置区段；b) 日均基准包含爆发期本身会抬高阈值，可改用中位数或剔除极值；c) ROW_NUMBER 必须在 (商家, 高单量标记) 双分区上取，否则差值法失效；d) 上线不足 30 天的新商家样本不足，单列"观察期"不强行归段。

### 4. 参考解法

**解法一：gaps-and-islands 连续区段识别（经典差值法）**

```sql
WITH md AS (                                  -- 步骤1：附上商家自身日均单量基准
    SELECT d.merchant_id, d.dt, d.order_cnt,
           AVG(d.order_cnt) OVER (PARTITION BY d.merchant_id) AS avg_cnt  -- 历史日均（含爆发期，见思路备注）
    FROM merchant_daily d
),
flag AS (                                     -- 步骤2：打高单量标记
    SELECT merchant_id, dt, order_cnt, avg_cnt,
           CASE WHEN order_cnt >= avg_cnt * 1.5 THEN 1 ELSE 0 END AS is_burst
    FROM md
),
grp AS (                                      -- 步骤3：差值法构造连续段键
    SELECT merchant_id, dt, order_cnt, is_burst,
           DATE_SUB(dt, INTERVAL ROW_NUMBER() OVER (
               PARTITION BY merchant_id, is_burst             -- 双分区是差值法成立的关键
               ORDER BY dt) DAY) AS grp_key                   -- 连续日期段内该键恒定
    FROM flag
),
streak AS (                                   -- 步骤4：折叠出每个连续段
    SELECT merchant_id, is_burst, grp_key,
           MIN(dt) AS seg_start,
           MAX(dt) AS seg_end,
           COUNT(*) AS seg_days
    FROM grp
    GROUP BY merchant_id, is_burst, grp_key
),
burst_rank AS (                               -- 步骤5：取每个商家最长的爆发段
    SELECT merchant_id, seg_start, seg_end, seg_days,
           ROW_NUMBER() OVER (PARTITION BY merchant_id
                              ORDER BY seg_days DESC, seg_start) AS rn
    FROM streak
    WHERE is_burst = 1
)
SELECT merchant_id,
       seg_start  AS burst_start,             -- 爆发期起点
       seg_end    AS burst_end,               -- 爆发期终点
       seg_days   AS burst_days,
       CASE WHEN seg_days >= 7 THEN 'valid_burst' ELSE 'noise' END AS burst_flag  -- 连续≥7天才算有效爆发
FROM burst_rank
WHERE rn = 1;
```

结果解读：输出每个商家最长爆发段；valid_burst 的商家进入"爆发期保供给"名单，noise 的说明只是偶发爆单，无需调度干预。

**解法二：滑动均值 + 状态机切点（输出完整阶段序列）**

```sql
WITH md AS (                                  -- 步骤1：关联上线日期并算两个基准
    SELECT d.merchant_id, m.launch_dt, d.dt, d.order_cnt,
           AVG(d.order_cnt) OVER (PARTITION BY d.merchant_id) AS avg_cnt,          -- 全期日均
           AVG(d.order_cnt) OVER (PARTITION BY d.merchant_id ORDER BY dt
                                  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7 -- 7日滑动均值
    FROM merchant_daily d
    JOIN merchants m ON m.merchant_id = d.merchant_id
),
staged AS (                                   -- 步骤2：逐日打阶段标签
    SELECT merchant_id, dt, order_cnt, ma7, avg_cnt,
           CASE
             WHEN dt < DATE_ADD(launch_dt, INTERVAL 30 DAY) THEN 'ramp'     -- 上线30天内=爬坡期
             WHEN ma7 >= avg_cnt * 1.5 THEN 'burst'                          -- 滑动均值高企=爆发期
             WHEN ma7 <  avg_cnt * 0.5 AND dt >= DATE_SUB('2026-10-25', INTERVAL 14 DAY)
                  THEN 'decline'                                             -- 近期塌方=衰退期
             ELSE 'stable' END AS stage
    FROM md
),
chg AS (                                      -- 步骤3：LAG 找阶段切换点
    SELECT merchant_id, dt, stage,
           LAG(stage) OVER (PARTITION BY merchant_id ORDER BY dt) AS prev_stage
    FROM staged
)
SELECT merchant_id,
       dt AS stage_change_dt,                 -- 阶段切换发生的日期
       stage AS new_stage                     -- 切入的新阶段
FROM chg
WHERE prev_stage IS NULL OR prev_stage <> stage   -- 首日与每次状态变化都是里程碑
ORDER BY merchant_id, dt;
```

结果解读：每个商家的阶段切换时间线（如 4001：9-20 爬坡→10-20 爆发）可直接喂给 CRM 触发"爆发期保供给""衰退期促活"两类工单；与解法一互验，状态机版还能捕捉衰退。

> **Hive/Spark SQL 差异**：两版窗口语法 Hive 均支持；日单量表按 dt 分区后仍需全商家扫描，建议按 merchant_id 分桶（bucket 64/128）让窗口在桶内完成；日均基准受爆发期污染的问题，可用 `percentile_approx` 求商家中位数替代 AVG，Spark 中实现更方便。

### 5. 性能分析与优化

解法一需要两次窗口排序（ROW_NUMBER 与爆发段排名），解法二需要三个窗口（全期均值、滑动均值、LAG），均为商家内排序，代价 O(日行数 × log 商家内行数)。优化建议：1) merchant_daily 按 merchant_id 分桶/聚簇，窗口排序在桶内完成，避免全量 shuffle；2) 日表按 dt 分区裁剪观察期；3) 把"商家×日均/滑动均值"物化为日更中间表，阶段识别退化为轻量 CASE；4) 长尾商家（历史 <30 天）可先过滤再开窗，减少排序输入；5) 差值法中 DATE_SUB(dt, INTERVAL rn DAY) 已是纯行内计算，无需额外优化。

### 6. 面试延伸考点

- **差值法的数学原理是什么？** 要点：连续日期依次加 1，行号也依次加 1，二者相减在连续段内为常数；段一旦断开差值跳变，因此可作为分组键折叠区段。
- **日期断档（歇业日无记录）会怎样？** 要点：差值法把断档视为区段终结，符合"连续高单量"的业务定义；若要容忍 1 天歇业，可先补日历轴再标记。
- **日均基准被爆发期抬高导致漏检怎么办？** 要点：改用中位数、截尾均值或"上线前 30 天均值"做基准，阈值也应结合品类做归一。
- **这套阶段划分如何验证有效性？** 要点：回测——用 T 时点识别的阶段预测 T+30 的流失/爆单，看分组的区分度（AUC 或分组差异）。

### 7. 业务拓展思考

生命周期阶段识别是商家分层运营的引擎：爬坡期配"流量冷启包"，爆发期触发运力与备货预警（联动 LL-34），稳定期做利润与品质经营，衰退期启动诊断回访与定向补贴。口径延展上：把单量换成 GMV/评分可构建多维阶段；把切换点做生存分析可量化"从上线到爆发的平均时长"，反向指导冷启资源投入周期；识别出的"第二次爆发"（大促复现能力）还可作为商家质量分特征，回流到流量分配模型（联动 LL-35）。
## LL-41 晚高峰取消率异动定位（分渠道分时段）

### 1. 业务背景

客服负责人发现上周五晚高峰取消投诉集中爆发，整体取消率从前一周同期的 6.2% 升到 9.8%。取消率是比率指标，不能像单量那样把环比差直接加总——各渠道×各时段的单量结构也在变，某渠道单量占比上升会机械推高整体取消率。分析师需要回答：异动主要来自哪个渠道（App/小程序/第三方）哪个时段？各单元格对整体取消率上涨各贡献了几个百分点？其中多少是"结构效应"（单量结构变化）、多少是"率效应"（单元格自身取消率恶化）？结论决定是修 App 端产品问题、处理第三方渠道供给质量，还是补运力。

### 2. 表结构说明

orders（订单表，虚构，含渠道与取消原因）：

| channel | VARCHAR(20) | 下单渠道（app/miniapp/third_party） |
| order_time | DATETIME | 下单时间 |
| order_status | VARCHAR(20) | 状态（completed/user_cancel/merchant_cancel/platform_cancel） |
| cancel_reason | VARCHAR(50) | 取消原因（仅取消单有值） |

orders 示例数据：

| --- | --- | --- | --- | --- |

| 770005 | app | 2026-10-16 19:15:00 | user_cancel | 下错单 |

### 3. 解题思路

口径：对比对象为相邻两个周五的 16:00-20:59 晚高峰；取消率 = 用户取消单 ÷ 总单量（商家/平台取消另口径复盘）。比率指标分解两种经典做法：a) 固定基数法——单元格贡献 = (本期取消数 − 上期取消数) ÷ 上期总单量，所有单元格贡献之和等于整体取消率变化（按百分点），可直接排序定位；b) 结构×率效应法——把整体取消率写成 Σ(单元格单量占比 × 单元格取消率)，变化拆成"占比变化 × 上期率"（结构效应）与"本期占比 × 率变化"（率效应），回答"是渠道结构变了还是质量恶化了"。易错点：a) 直接比较各单元格取消率的环比而不看单量权重，会把低单量单元格的噪声放大；b) 前后期"总单量"基数不一致导致贡献不可加，固定基数法必须统一用上期总单量；c) 取消原因要与取消率交叉看，定位是体验问题还是运力问题。

### 4. 参考解法

**解法一：固定基数法贡献分解（可加、可排序，汇报首选）**

```sql
WITH base AS (                                -- 步骤1：圈定两个周五晚高峰明细并打期标签
    SELECT channel, order_id,
           CASE WHEN DATE(order_time) = '2026-10-16' THEN 'cur' ELSE 'prev' END AS period_tag,
           CASE WHEN order_status = 'user_cancel' THEN 1 ELSE 0 END AS is_cancel  -- 口径：用户取消
    FROM orders
    WHERE order_time >= '2026-10-09' AND order_time < '2026-10-17'      -- 覆盖两个周五
      AND HOUR(order_time) BETWEEN 16 AND 20                            -- 晚高峰口径
),
pv AS (                                       -- 步骤2：渠道×期数 聚合单量与取消数
    SELECT channel, period_tag,
           COUNT(*) AS ord_cnt,
           SUM(is_cancel) AS cancel_cnt
    FROM base
    GROUP BY channel, period_tag
),
aligned AS (                                  -- 步骤3：行转列，两期对齐
    SELECT channel,
           SUM(CASE WHEN period_tag='cur'  THEN ord_cnt END)    AS cur_ord,
           SUM(CASE WHEN period_tag='prev' THEN ord_cnt END)    AS prev_ord,
           SUM(CASE WHEN period_tag='cur'  THEN cancel_cnt END) AS cur_cancel,
           SUM(CASE WHEN period_tag='prev' THEN cancel_cnt END) AS prev_cancel
    FROM pv
    GROUP BY channel
),
total AS (                                    -- 步骤4：上期整体单量，作统一固定基数
    SELECT SUM(prev_ord) AS prev_total FROM aligned
)
SELECT a.channel,
       ROUND(a.prev_cancel / NULLIF(a.prev_ord, 0) * 100, 2) AS prev_rate_pct,  -- 上期取消率
       ROUND(a.cur_cancel  / NULLIF(a.cur_ord, 0) * 100, 2) AS cur_rate_pct,   -- 本期取消率
       ROUND((a.cur_cancel - a.prev_cancel) / t.prev_total * 100, 2) AS contrib_pp,
       -- 固定基数贡献：该渠道取消数增量 ÷ 上期总单量，所有渠道之和=整体取消率变化
       a.cur_ord - a.prev_ord AS ord_delta       -- 单量变化，辅助判断是否伴随结构异动
FROM aligned a CROSS JOIN total t
ORDER BY contrib_pp DESC;
```

结果解读：若 third_party 贡献 +2.6pp、app 贡献 +0.9pp，则异动主因是第三方渠道，联合其取消原因分布（"骑手久等不来"居多）指向运力而非产品问题。

**解法二：结构×率效应分解（回答"结构还是质量"）**

```sql
WITH base AS (                                -- 步骤1：同解法一构造明细
    SELECT channel, order_id,
           CASE WHEN DATE(order_time) = '2026-10-16' THEN 'cur' ELSE 'prev' END AS period_tag,
           CASE WHEN order_status = 'user_cancel' THEN 1 ELSE 0 END AS is_cancel
    FROM orders
    WHERE order_time >= '2026-10-09' AND order_time < '2026-10-17'
      AND HOUR(order_time) BETWEEN 16 AND 20
),
pv AS (                                       -- 步骤2：渠道级两期单量与取消数
    SELECT channel,
           SUM(CASE WHEN period_tag='cur'  THEN 1 ELSE 0 END) AS cur_ord,
           SUM(CASE WHEN period_tag='prev' THEN 1 ELSE 0 END) AS prev_ord,
           SUM(CASE WHEN period_tag='cur'  THEN is_cancel ELSE 0 END) AS cur_cancel,
           SUM(CASE WHEN period_tag='prev' THEN is_cancel ELSE 0 END) AS prev_cancel
    FROM base
    GROUP BY channel
),
tot AS (                                      -- 步骤3：两期整体单量
    SELECT SUM(cur_ord) AS total_cur, SUM(prev_ord) AS total_prev FROM pv
)
SELECT p.channel,
       ROUND(((p.cur_ord / t.total_cur) - (p.prev_ord / t.total_prev))
             * (p.prev_cancel / NULLIF(p.prev_ord, 0)) * 100, 2) AS struct_effect_pp,
       -- 结构效应：单量占比变化 × 上期取消率（占比升且本身取消率高，机械推高整体）
       ROUND((p.cur_ord / t.total_cur)
             * (p.cur_cancel / NULLIF(p.cur_ord, 0) - p.prev_cancel / NULLIF(p.prev_ord, 0)) * 100, 2) AS rate_effect_pp
       -- 率效应：本期占比 × 该渠道取消率变化（真实质量恶化）
FROM pv p CROSS JOIN tot t
ORDER BY rate_effect_pp DESC;
```

结果解读：每个渠道的变化被拆成两块——struct_effect_pp 大说明是渠道单量结构漂移（如第三方补贴拉来更多单），rate_effect_pp 大说明该渠道体验真恶化；两者之和近似整体取消率变化，运营据此选择"调结构"还是"修质量"。

> **Hive/Spark SQL 差异**：订单表按 dt 分区后取两天分区，扫描极小；`SUM(CASE WHEN ... )` 写法 Hive 通用；渠道数少时也可用 `GROUPING SETS ((channel, period_tag), (period_tag), ())` 一次产出单元格与整体层，避免 CROSS JOIN。

### 5. 性能分析与优化

两解法主体都是两天明细的分组聚合（O(两期晚高峰订单数)），解法二多一层两行 tot 的 CROSS JOIN，可忽略。优化建议：1) orders 按 dt 分区，两个周五只扫 2 个分区；2) (order_time, channel) 复合索引或 (dt, channel) 分桶可加速分组；3) 若取消率监控是例行任务，预聚合"日×渠道×小时"的单量/取消数中间表，异动定位退化为对数千行的比率分解；4) 注意 HOUR(order_time) 上的过滤会阻止索引裁剪，分区键仍是 dt；5) 渠道字典表若含已下线渠道，需 INNER JOIN 过滤避免空渠道行。

### 6. 面试延伸考点

- **为什么取消率不能像单量一样直接加总环比差？** 要点：比率是加权平均，分母（单量结构）变化会污染分子效应；可加分解必须固定基数或做结构×率拆分。
- **固定基数法与结构×率法各回答什么问题？** 要点：前者回答"谁拖累了几个百分点"（定位排序），后者回答"是结构漂移还是质量恶化"（归因性质），汇报时通常先前者后后者。
- **如何排除天气/竞对等混杂因素？** 要点：对比历史多个周五的取消率分布判断异常程度，叠加天气表（LL-38）做同口径对照，或扩大对照时段。
- **取消原因字段缺失率高怎么办？** 要点：原因多为事后填写，先看"骑手未取到""商家超时"这类系统侧结构化标签，缺失部分单列，不可用多数填充误导结论。

### 7. 业务拓展思考

取消率异动定位可沉淀为例行监控：对"渠道×时段"格子设取消率与贡献率双阈值告警，自动附上固定基数分解报告。联动动作：率效应高的渠道推进产品/运力修复（如第三方渠道骑手接单激励），结构效应高则评估该渠道的补贴与供给质量是否匹配；对"骑手久等不来"主导的取消，联动 LL-34 的运力缺口预警在高峰前补调。口径延展上可拆"支付前取消/支付后取消""骑手接单前/后取消"两段漏斗，分别指向决策犹豫与履约问题，把一个比率指标做成可行动的诊断体系。

## LL-42 跨品类交叉购买与推荐位效率

### 1. 业务背景

推荐运营想评估首页"看了再买"推荐位的真实价值：买过甜点饮品的用户有多少会在 30 天内首次购买美食正餐/生鲜果蔬？点击过推荐位的用户，其跨品类购买率是否显著高于未点击用户？前者（交叉购买矩阵）刻画品类间的自然关联强度，用于供给组合与推荐策略；后者（推荐位点击组 vs 未点击组）用于评估推荐位效率。两者结合可回答"推荐位是在创造新需求，还是只加速了本来就会发生的购买"——这决定推荐位流量配比与坑位结算方式。

### 2. 表结构说明

orders（订单表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单ID |
| user_id | BIGINT | 用户ID |
| order_dt | DATE | 下单日期 |
| category_id | INT | 品类ID（1=美食正餐 2=甜点饮品 3=生鲜果蔬 4=超市便利） |

reco_events（推荐位事件表，虚构，用户日粒度已去重）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户ID |
| event_dt | DATE | 事件日期 |
| slot_id | INT | 推荐位坑位ID |
| event_type | VARCHAR(10) | 事件类型（expo=曝光，click=点击） |

orders 示例数据：

| order_id | user_id | order_dt | category_id |
| --- | --- | --- | --- |
| 330001 | 601 | 2026-09-01 | 2 |
| 330002 | 601 | 2026-09-15 | 1 |
| 330003 | 602 | 2026-09-03 | 2 |
| 330004 | 603 | 2026-09-05 | 4 |
| 330005 | 602 | 2026-09-28 | 3 |

reco_events 示例数据：

| user_id | event_dt | slot_id | event_type |
| --- | --- | --- | --- |
| 601 | 2026-09-02 | 5 | expo |
| 601 | 2026-09-02 | 5 | click |
| 602 | 2026-09-04 | 5 | expo |
| 603 | 2026-09-06 | 7 | expo |
| 604 | 2026-09-06 | 7 | click |

### 3. 解题思路

两个产出、两条路径：a) 交叉购买矩阵——以用户为单位取"首购品类"与"首购后 30 日内购买的其他品类"，按 (首购品类 × 次购品类) 计数并做行内占比，得到自然交叉率；b) 推荐位效率——把用户标记为"点击过推荐位/只曝光未点击"，对比两组的跨品类购买率。必须向业务声明：b 是描述性对比而非因果，点击组本就是高意向人群（自选择偏差），严谨结论需 A/B 或倾向得分匹配。易错点：a) 首购品类要用 MIN(order_dt) 关联取当日品类，注意首日多单多品类的破平规则；b) "次购"要排除首购品类本身才算跨品类；c) 30 日窗口未走完的 cohort 要封口；d) 连接推荐位事件时把 expo/click 混为一谈会高估点击规模。

### 4. 参考解法

**解法一：首购品类 × 30日跨品类矩阵（自连接购后序列）**

```sql
WITH first_order AS (                         -- 步骤1：每用户首购日期
    SELECT user_id, MIN(order_dt) AS f_dt
    FROM orders
    WHERE order_dt < '2026-10-01'             -- cohort 封口：留足30日观察窗
    GROUP BY user_id
),
first_cat AS (                                -- 步骤2：首购日期当天的品类（首日多品类取ID最小者）
    SELECT o.user_id, MIN(o.category_id) AS f_cat
    FROM orders o
    JOIN first_order f ON f.user_id = o.user_id AND f.f_dt = o.order_dt
    GROUP BY o.user_id
),
cross_pair AS (                               -- 步骤3：首购后30日内购买的其他品类
    SELECT fc.f_cat, o.category_id AS s_cat,
           COUNT(DISTINCT fc.user_id) AS user_cnt
    FROM first_cat fc
    JOIN orders o
      ON o.user_id = fc.user_id
     AND o.order_dt >  (SELECT f_dt FROM first_order f WHERE f.user_id = fc.user_id)  -- 晚于首购
     AND o.order_dt <= DATE_ADD((SELECT f_dt FROM first_order f WHERE f.user_id = fc.user_id),
                                INTERVAL 30 DAY)
     AND o.category_id <> fc.f_cat            -- 排除同品类，只看跨品类
    GROUP BY fc.f_cat, o.category_id
)
SELECT f_cat AS from_category,                -- 首购品类
       s_cat AS to_category,                  -- 30日内新购品类
       user_cnt,
       ROUND(user_cnt / SUM(user_cnt) OVER (PARTITION BY f_cat) * 100, 2) AS row_share_pct
       -- 行内占比：该首购品类用户中迁往此品类的比例（矩阵读法：按行看）
FROM cross_pair
ORDER BY f_cat, row_share_pct DESC;
```

结果解读：若"2→1"（甜点→正餐）行占比最高，说明甜点是正餐的天然入口，正餐推荐位应优先对甜点首购人群投放；行内占比即品类间"自然交叉率"基线。

**解法二：LAG 序列化跨品类标记 + 点击组对比（描述性效率口径）**

```sql
WITH seq AS (                                 -- 步骤1：用户订单按时间排序，LAG 取上一单品类
    SELECT user_id, order_dt, category_id,
           LAG(category_id) OVER (PARTITION BY user_id ORDER BY order_dt, order_id) AS prev_cat
    FROM orders
    WHERE order_dt < '2026-10-01'
),
user_flag AS (                                -- 步骤2：用户级标记——是否跨品类、是否点击过推荐位
    SELECT s.user_id,
           MAX(CASE WHEN s.prev_cat IS NOT NULL
                     AND s.category_id <> s.prev_cat THEN 1 ELSE 0 END) AS has_cross,
           MAX(CASE WHEN r.event_type = 'click' THEN 1 ELSE 0 END) AS clicked
    FROM seq s
    LEFT JOIN (SELECT DISTINCT user_id          -- 只取点击过的人群，DISTINCT 防多坑位重复
               FROM reco_events WHERE event_type = 'click') r
           ON r.user_id = s.user_id
    GROUP BY s.user_id
)
SELECT clicked,
       COUNT(*) AS users,                                        -- 两组人数
       ROUND(AVG(has_cross) * 100, 2) AS cross_buy_pct           -- 组内跨品类购买率
FROM user_flag
GROUP BY clicked
ORDER BY clicked;
```

结果解读：若点击组跨品类率 38%、未点击组 22%，说明推荐位点击与跨品类强相关，但需声明这是相关非因果——点击者本可能就是高意向用户，应推动随机化实验再下结论。

> **Hive/Spark SQL 差异**：LAG 与窗口聚合 Hive 通用；推荐位事件表体量大，先 `WHERE event_type='click'` 过滤并按 user_id 分桶再 join；相关子查询写法（解法一）在 Hive 中需改写为 first_cat 与 first_order 的 JOIN 后再连 orders，三层 join 建议中间结果落临时表。

### 5. 性能分析与优化

解法一涉及三层连接（首购日期 → 首购品类 → 跨品类配对），相关子查询在 MySQL 中每行探测，用户千万级时代价高，宜改写为 join 并给 orders 建 (user_id, order_dt) 索引；解法二主体是一次分区窗口排序 + 一次小名单 join，代价更低。优化建议：1) 推荐位事件先按 event_type 过滤压成小表再 join；2) 首购信息（首购日期、首购品类）物化为用户属性表，供多场景复用；3) 交叉矩阵按月例行化时只增量计算新 cohort；4) 避免对 order_dt 做函数包装导致索引失效；5) 大表下把"用户首单后 30 日订单"用范围 join + 分组去重，替代逐行 EXISTS。

### 6. 面试延伸考点

- **点击组 vs 未点击组的差异能说明推荐位有效吗？** 要点：不能直接说明因果，存在自选择偏差；需 A/B 实验、DID 或按活跃度/消费力匹配后的对比，SQL 结论只能作为假设。
- **为什么次购要排除首购品类？** 要点：本题衡量"跨品类"创造，混入同品类复购会把留存当作交叉，口径失真；留存另见 LL-32。
- **矩阵读法是按行还是按列？** 要点：行内占比回答"首购 A 的人去哪了"，列占比回答"B 的增量从哪来"，两个读法服务不同决策。
- **首日多单多品类怎么破平？** 要点：必须写明规则（订单时间最早者、金额最大者或品类 ID 最小者），否则结果不可复现，面试中主动提规则意识是加分项。

### 7. 业务拓展思考

交叉矩阵是推荐与品类组合的底座：高关联品类对用于推荐位选品与"凑单场景"设计，低关联对提示品类隔离展示。联动动作——对"甜点→正餐"入口人群定向正餐新人券；对点击未转化人群做推荐位创意迭代；把自然交叉率与点击组提升幅度合并成"推荐位增量创造率"指标，纳入坑位结算。口径延展：把品类换成商圈/价格带可评估"跨商圈引流"；把 30 日窗口做 7/14/30 敏感性分析可刻画关联的时间衰减，为再营销触达节奏提供依据。

## LL-43 用户LTV分档与获客渠道ROI

### 1. 业务背景

市场投放团队每月花数千万元在抖音信息流、应用商店、地推等渠道上获客，各渠道 CAC（单客获客成本）差异巨大。CMO 要求回答：哪个渠道买来的用户"值"？口径是 90 日 LTV（新客注册后 90 天累计 GMV）与渠道 ROI（LTV ÷ CAC），并辅以 LTV 分档结构——有的渠道 CAC 便宜但都是一次性羊毛用户，有的 CAC 贵却带来高价值客。结论直接决定下月预算在渠道间的增减，以及哪些渠道需要从"按激活结算"改为"按留存结算"。

### 3. 解题思路

口径：90 日 LTV = 用户在 [获客日, 获客日+90天] 内 completed 订单实付金额之和，只统计获客日距今 ≥90 天（最好再加缓冲月）的 cohort，保证窗口封口；渠道 ROI = 渠道人均 LTV ÷ 渠道人均 CAC；分档用 NTILE(4) 按用户 LTV 四分位（高/中高/中/低价值），并输出帕累托曲线（按 LTV 降序的累计 GMV 占比）看头部集中度。易错点：a) 忘记窗口封口，把注册不满 90 天的用户算进来会系统性低估 LTV；b) LTV 应含首单，窗口左边界是获客日当天；c) ROI 分母用人均 CAC，若渠道是打包采购价需先摊到人；d) 只看均值会被头部 whale 拉爆，必须配中位数与分档结构；e) canceled 单不计入。

### 4. 参考解法

**解法一：多层 CTE 渠道 ROI 排名（主口径，直接支持预算决策）**

```sql
WITH gmv90 AS (                               -- 步骤1：每新客90日窗口内累计GMV
    SELECT a.user_id, a.channel, a.cac,
           COALESCE(SUM(o.pay_amount), 0) AS ltv_90      -- 未复购用户补0，不能丢
    FROM user_acquisition a
    LEFT JOIN orders o
           ON o.user_id = a.user_id
          AND o.order_dt >= a.acquire_dt                                 -- 含首单当天
          AND o.order_dt <  DATE_ADD(a.acquire_dt, INTERVAL 90 DAY)      -- 右开边界
          AND o.order_status = 'completed'
    WHERE a.acquire_dt <= DATE_SUB('2026-10-25', INTERVAL 120 DAY)       -- 窗口封口再留30天缓冲
    GROUP BY a.user_id, a.channel, a.cac
),
ch AS (                                       -- 步骤2：渠道级聚合
    SELECT channel,
           COUNT(*) AS new_users,
           ROUND(AVG(ltv_90), 2) AS avg_ltv_90,                 -- 人均90日LTV
           ROUND(AVG(ltv_90 > 0) * 100, 2) AS pay_user_pct,     -- 布尔均值=付费率
           ROUND(AVG(cac), 2) AS avg_cac,                       -- 人均获客成本
           ROUND(AVG(ltv_90) / NULLIF(AVG(cac), 0), 2) AS roi   -- 渠道ROI
    FROM gmv90
    GROUP BY channel
)
SELECT channel, new_users, avg_ltv_90, pay_user_pct, avg_cac, roi,
       RANK() OVER (ORDER BY roi DESC) AS roi_rank                  -- ROI 排名，预算增减依据
FROM ch
ORDER BY roi_rank;
```

结果解读：若 douyin_feed ROI 2.1、ground_promo 0.8，则地推预算应压缩，且 ROI>1.5 的渠道可申请追加投放；付费率列可识别"便宜但低质"的渠道。

**解法二：NTILE 分档 + 帕累托累计占比（看结构而非只看均值）**

```sql
WITH gmv90 AS (                               -- 步骤1：用户级90日LTV（同解法一）
    SELECT a.user_id, a.channel, a.cac,
           COALESCE(SUM(o.pay_amount), 0) AS ltv_90
    FROM user_acquisition a
    LEFT JOIN orders o
           ON o.user_id = a.user_id
          AND o.order_dt >= a.acquire_dt
          AND o.order_dt <  DATE_ADD(a.acquire_dt, INTERVAL 90 DAY)
          AND o.order_status = 'completed'
    WHERE a.acquire_dt <= DATE_SUB('2026-10-25', INTERVAL 120 DAY)
    GROUP BY a.user_id, a.channel, a.cac
),
tiered AS (                                   -- 步骤2：LTV四分位分档 + 全局帕累托
    SELECT user_id, channel, ltv_90,
           NTILE(4) OVER (ORDER BY ltv_90 DESC) AS ltv_q,        -- 按 LTV 降序切四档：1=最高档
           SUM(ltv_90) OVER (ORDER BY ltv_90 DESC)               -- 降序累计LTV
             / SUM(ltv_90) OVER () AS cum_ltv_share              -- 累计占比（帕累托曲线）
    FROM gmv90
)
SELECT channel,
       ltv_q,                                                 -- LTV 分档
       COUNT(*) AS users,
       ROUND(AVG(ltv_90), 2) AS avg_ltv,
       ROUND(MAX(cum_ltv_share) * 100, 2) AS cum_share_pct    -- 档末累计GMV占比（只对档内最大值有意义）
FROM tiered
GROUP BY channel, ltv_q
ORDER BY channel, ltv_q;
```

结果解读：帕累托列的全局视角可读出"前 25% 用户贡献约 70% GMV"的集中度；渠道×分档矩阵则显示哪些渠道的头部分档占比更高——头部占比高的渠道即使 CAC 贵也可能更值得投。

> **Hive/Spark SQL 差异**：NTILE/累计窗口 Hive 通用；用户千万级时先按 channel 分桶，帕累托排序在桶内仍需全局窗口，数据更大时改 Spark `percentile_approx` 或抽样估计；cohort 建议落为 acquire_dt 分区的日增表，90 日到期自动补算。

### 5. 性能分析与优化

两解法主体都是"用户×订单"范围 join + 聚合，join 后行数 = 新客 × 90 日窗口订单数，是最大开销；解法二多两个全局窗口排序（NTILE 与累计和）。优化建议：1) 两表按 user_id 分桶/分区，join 走同桶对齐；2) orders 在 (user_id, order_dt) 建复合索引；3) 用"用户×日"GMV 汇总表替代明细订单参与 join；4) cohort 表按 acquire_dt 分区并只取已封口月份，避免扫描活跃用户；5) 帕累托只需全局前若干档时可先 `WHERE ltv_90 >= 阈值` 再开窗，减少排序输入。

### 6. 面试延伸考点

- **为什么必须"窗口封口"后再算 LTV？** 要点：不满 90 天的用户 LTV 天然偏小，混入会低估且低估程度随时间变化， cohort 封口是 LTV 类指标的第一纪律。
- **LTV 均值、中位数、分档结构各看什么？** 要点：均值决定 ROI 总账，中位数代表典型用户，分档识别"头部集中"与"虚假繁荣"；三口径背离时以结构优先。
- **ROI>1 就应该加预算吗？** 要点：还要看边际 ROI（加量后新客质量稀释）、回收周期与现金流，以及渠道饱和曲线，滚动 cohort 的 LTV 逐月爬升情况。
- **如何验证渠道归因可信？** 要点：关注归因窗口与 last-click 偏差，交叉对比 MMP 归因与自归因，防止渠道作弊刷量抬高 LTV。

### 7. 业务拓展思考

LTV 分档可反哺产品与 CRM：高价值档用户做会员深度运营（联动 LL-36 的红包策略），低价值档识别羊毛特征后降低券投放。口径延展：把 GMV 换成毛利口径的 LTV（GMV×毛利率−补贴成本）更贴近财务真相；做 90/180/365 日多窗口 LTV 外推曲线支持更长周期投放决策；与 LL-32 的补贴档位、LL-42 的交叉购买特征组合成"获客质量评分卡"，把单渠道 ROI 升级为"渠道×人群×素材"三维矩阵，指导精细化出价。

## LL-44 商家流失预警双信号模型

### 1. 业务背景

商家流失（停业、转投竞对）前通常有前置信号：订单量连续下滑（可能已在竞对平台经营）与评分下滑（经营投入意愿降低）。商家运营团队希望每周产出一份预警名单：最近一周订单量环比下滑超 30%，且近 30 天评分较前 30 天下降超过 0.3 的在营商家。BD 会对名单逐一回访挽留——提前两周触达的挽留成功率是流失后召回的三倍，因此预警的时效与准确率都直接是钱。分析师需要用 SQL 把两个信号计算出来并取交集，同时控制误报（新商家、季节性商家天然波动大）。

### 2. 表结构说明

merchant_daily（商家日单量表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| merchant_id | BIGINT | 商家ID |
| dt | DATE | 日期 |
| order_cnt | INT | 当日有效订单量 |

reviews（商家评价表，虚构）：

| 字段名 | 类型 | 含义 |
| --- | --- | --- |
| review_id | BIGINT | 评价ID |
| merchant_id | BIGINT | 商家ID |
| review_dt | DATE | 评价日期 |
| score | DECIMAL(2,1) | 评分（1.0~5.0） |

merchant_daily 示例数据：

| merchant_id | dt | order_cnt |
| --- | --- | --- |
| 4001 | 2026-10-13 | 50 |
| 4001 | 2026-10-20 | 28 |
| 4001 | 2026-10-24 | 22 |
| 4002 | 2026-10-13 | 80 |
| 4002 | 2026-10-24 | 85 |

reviews 示例数据：

| review_id | merchant_id | review_dt | score |
| --- | --- | --- | --- |
| 91001 | 4001 | 2026-09-10 | 4.8 |
| 91002 | 4001 | 2026-10-20 | 4.2 |
| 91003 | 4001 | 2026-10-22 | 4.0 |
| 91004 | 4002 | 2026-09-15 | 4.6 |
| 91005 | 4002 | 2026-10-23 | 4.7 |

### 3. 解题思路

口径：信号一（单量）——近 7 天订单量 ÷ 前 7 天订单量 < 0.7，且前 7 天订单量 ≥ 最低样本阈值（如 ≥21 单，防小基数误报）；信号二（评分）——近 30 天平均评分 − 前 30 天平均评分 < −0.3，且两个窗口都有足量评价（如 ≥5 条）。两信号 INNER JOIN 取交集为预警名单，输出单量保留率与评分降幅便于 BD 排序。实现两条路：a) 条件聚合双 CTE——各自按 CASE 切窗口聚合，再按商家 join，逻辑直白；b) 周序列 + LAG/LEAD——把单量聚合成周粒度后用窗口取上周/下周，能识别"连续两周下滑"的更强信号，评分同理按周序列对比。易错点：a) 无评价商家在 AVG(CASE) 下两窗口为 NULL，join 后会整商家丢失或误报，要显式处理；b) 窗口边界（> 还是 >=）必须前后一致；c) 新上线商家历史不足，需排除上线 <60 天者；d) 周粒度用 YEARWEEK(dt,1) 保证周一为一周起点且跨年正确。

### 4. 参考解法

**解法一：条件聚合双 CTE + 信号交集（逻辑最直白）**

```sql
WITH vol AS (                                 -- 步骤1：单量信号——近7天 vs 前7天
    SELECT merchant_id,
           SUM(CASE WHEN dt >  DATE_SUB('2026-10-25', INTERVAL 7 DAY)
                    THEN order_cnt END) AS w_cur,     -- 近7天单量
           SUM(CASE WHEN dt <= DATE_SUB('2026-10-25', INTERVAL 7 DAY)
                    THEN order_cnt END) AS w_prev     -- 前7天单量
    FROM merchant_daily
    WHERE dt > DATE_SUB('2026-10-25', INTERVAL 14 DAY)  -- 两周窗口一次扫描
    GROUP BY merchant_id
    HAVING w_prev >= 21                       -- 样本阈值：周均≥3单/天，防小基数误报
       AND w_cur / w_prev < 0.7               -- 信号一：单量保留率<70%
),
score AS (                                    -- 步骤2：评分信号——近30天 vs 前30天
    SELECT merchant_id,
           AVG(CASE WHEN review_dt >  DATE_SUB('2026-10-25', INTERVAL 30 DAY)
                    THEN score END) AS s_cur,
           AVG(CASE WHEN review_dt <= DATE_SUB('2026-10-25', INTERVAL 30 DAY)
                    THEN score END) AS s_prev,
           COUNT(*) AS review_cnt              -- 评价量，用于稳健性提示
    FROM reviews
    WHERE review_dt > DATE_SUB('2026-10-25', INTERVAL 60 DAY)
    GROUP BY merchant_id
    HAVING s_prev IS NOT NULL AND s_cur IS NOT NULL   -- 两窗口都有评价才可比
       AND s_prev - s_cur > 0.3               -- 信号二：评分降幅>0.3
)
SELECT v.merchant_id,
       ROUND(v.w_cur / v.w_prev * 100, 1) AS vol_retain_pct,  -- 单量保留率
       ROUND(s.s_prev - s.s_cur, 2)       AS score_drop,      -- 评分降幅
       s.review_cnt,                                        -- 评价量（置信度参考）
       'high_risk' AS risk_tag
FROM vol v
INNER JOIN score s ON s.merchant_id = v.merchant_id   -- 双信号同时命中才进名单
ORDER BY vol_retain_pct ASC;                  -- 单量掉得最狠的优先回访
```

结果解读：名单按单量保留率升序即 BD 回访优先级；若名单里出现大量低评价量商家，应提高 review_cnt 阈值重跑，避免被一两条差评带偏。

**解法二：周序列 + LAG/LEAD 识别"连续两周下滑"（更强、更稳的信号）**

```sql
WITH vol_wk AS (                              -- 步骤1：单量聚合成周粒度（周一为一周起点）
    SELECT merchant_id, YEARWEEK(dt, 1) AS week_id,
           SUM(order_cnt) AS week_ord
    FROM merchant_daily
    WHERE dt > DATE_SUB('2026-10-25', INTERVAL 28 DAY)  -- 取最近4周
    GROUP BY merchant_id, YEARWEEK(dt, 1)
),
vol_seq AS (                                  -- 步骤2：窗口取上周与下周，判断连续下滑
    SELECT merchant_id, week_id, week_ord,
           LAG(week_ord)  OVER (PARTITION BY merchant_id ORDER BY week_id) AS prev_wk,
           LEAD(week_ord) OVER (PARTITION BY merchant_id ORDER BY week_id) AS next_wk
    FROM vol_wk
),
vol_signal AS (                               -- 步骤3：本周边际下滑+下周边际下滑=连续下滑
    SELECT DISTINCT merchant_id
    FROM vol_seq
    WHERE prev_wk IS NOT NULL AND next_wk IS NOT NULL
      AND week_ord < prev_wk * 0.7            -- 本周 < 上周70%
      AND next_wk < week_ord                  -- 下周继续降（趋势确认）
),
score_wk AS (                                 -- 步骤4：评分同样周粒度化
    SELECT merchant_id, YEARWEEK(review_dt, 1) AS week_id, AVG(score) AS wk_score
    FROM reviews
    WHERE review_dt > DATE_SUB('2026-10-25', INTERVAL 60 DAY)
    GROUP BY merchant_id, YEARWEEK(review_dt, 1)
),
score_seq AS (                                -- 步骤5：LAG 取上周评分
    SELECT merchant_id, week_id, wk_score,
           LAG(wk_score) OVER (PARTITION BY merchant_id ORDER BY week_id) AS prev_score
    FROM score_wk
),
score_signal AS (                             -- 步骤6：周环比降幅>0.3 视为评分恶化
    SELECT DISTINCT merchant_id
    FROM score_seq
    WHERE prev_score IS NOT NULL AND wk_score < prev_score - 0.3
)
SELECT v.merchant_id
FROM vol_signal v
INNER JOIN score_signal s ON s.merchant_id = v.merchant_id;   -- 双信号交集即预警名单
```

结果解读：连续两周单量下滑的确认信号比单周对比误报少，适合作为正式预警；单周剧烈下滑可另设"观察名单"，避免 BD 资源被噪声消耗。

> **Hive/Spark SQL 差异**：YEARWEEK 在 Hive 中可用 `yearweek(dt)`（Hive 2.2+）或 `concat(year(dt), lpad(weekofyear(dt),2,'0'))` 替代；LAG/LEAD 语法一致；大表按 merchant_id 分桶后窗口免 shuffle，条件聚合版可用 GROUPING SETS 一次产出多窗口。

### 5. 性能分析与优化

解法一两次窗口聚合（单量 14 天、评分 60 天）+ 一次商家级 join，join 规模为"命中信号一的商家数"，通常很小；解法二多两层窗口排序（周序列），但输入已是周粒度小表，代价不大。优化建议：1) merchant_daily 按 dt 分区只扫 14/28 天，reviews 按 review_dt 分区扫 60 天；2) (merchant_id, dt) 主键/分桶保证聚合走本地；3) 周聚合结果（商家×周单量、商家×周评分）物化为例行中间表，预警 SQL 变成对小表的窗口查询；4) 信号阈值（0.7、0.3、样本阈值）应配置化并按品类分层校准，避免 SQL 硬编码；5) JOIN 前两信号各先 DISTINCT 压缩，防历史数据重复行导致名单重复。

### 6. 面试延伸考点

- **为什么单量信号要设"前7天≥21单"的样本阈值？** 要点：周单量 10→3 也是下滑 70%，但对小商家是自然波动；样本阈值控制统计噪声，是预警系统精度与召回的平衡。
- **评分窗口用均值还是加权均值？** 要点：近 30 天评价数差异大时，简单均值会被低样本窗口主导；可按评价量加权或要求双窗口最低条数。
- **如何评估预警模型的效果？** 要点：回测名单商家在 T+30 的实际流失率与全体基线比较（lift），并在准确率/召回率间按 BD 人力容量选阈值。
- **连续下滑用 LAG/LEAD 和自连接区间哪个好？** 要点：语义等价，周序列+LAG 只扫一遍且可读性更好；自连接区间适合不规则观察窗，但要注意 join 膨胀。

### 7. 业务拓展思考

双信号框架可扩展为多信号评分卡：加入"商家登录商家版 App 频次下降""参加平台活动次数减少""改价频率异常"等行为信号，用简单加权分或后续接入模型输出流失概率分。联动动作：高危名单触发 BD 48 小时内回访、定向"经营诊断报告"推送与返佣补贴；观察名单进自动化触达。口径延展：把流失定义精确化（连续 N 天 0 单/主动关店）作为标签反向校准阈值；按品类与城市分层预警，识别系统性流失（商圈拆迁、品类退潮）与个体流失，二者的应对完全不同。

| 5003 | 2026-10-20 | 450 | 30 |

### 3. 解题思路

口径：cohort = 2026-09 月入职骑手；周龄 tenure_week = (工作日期 − 入职日期) DIV 7，第 0 周即入职首周；周留存率 = 该周龄仍出勤的骑手数 ÷ cohort 总人数（不要求连续出勤，"该周至少出勤 1 天"即可）；人均日单量 = 该周总完单 ÷ 该周出勤人·日，衡量爬坡强度。两个实现要点：a) 出勤表只在出勤日有行，周留存天然"跳过"缺勤周，但若某周整体无人出勤，聚合会缺行，严谨曲线要用"cohort × 周轴"全组合补零；b) 人均日单量的分母是出勤人·日而非 7 天，避免把缺勤日摊薄。易错点：a) 用工作日期的 MIN 当入职日会在骑手入职当天未出勤时偏移 cohort 起点，必须用 onboard 表；b) 入职不满 8 周的骑手，其高周龄格子观察未完整，cohort 应按"入职距今 ≥8 周"封口；c) 兼职与全职混算会扭曲爬坡曲线，需先按出勤强度分层。

### 4. 参考解法

**解法一：cohort 周龄聚合（简洁，适合快速出数）**

```sql
WITH cohort AS (                              -- 步骤1：新人骑手名单（窗口封口）
    SELECT rider_id, onboard_dt
    FROM rider_onboard
    WHERE onboard_dt BETWEEN '2026-09-01' AND '2026-09-30'   -- 9月cohort
      AND onboard_dt <= DATE_SUB('2026-10-25', INTERVAL 56 DAY)  -- 入职≥8周，高周龄格子才完整
),
tenure AS (                                   -- 步骤2：每条出勤记录换算成周龄
    SELECT c.rider_id,
           DATEDIFF(s.work_date, c.onboard_dt) DIV 7 AS tenure_week,  -- 0=入职第1周
           s.order_cnt, s.online_minutes
    FROM cohort c
    JOIN rider_shifts s ON s.rider_id = c.rider_id
),
wk AS (                                       -- 步骤3：按周龄聚合留存与产出
    SELECT tenure_week,
           COUNT(DISTINCT rider_id) AS active_riders,   -- 该周至少出勤1天的骑手
           SUM(order_cnt) AS total_orders,
           COUNT(*) AS active_days                      -- 出勤人·日数
    FROM tenure
    GROUP BY tenure_week
)
SELECT w.tenure_week,
       ROUND(w.active_riders / c.cohort_size * 100, 2) AS retention_pct,        -- 周留存率曲线
       ROUND(w.total_orders / NULLIF(w.active_days, 0), 1) AS avg_daily_orders, -- 人均日单量爬坡曲线
       c.cohort_size
FROM wk w
CROSS JOIN (SELECT COUNT(*) AS cohort_size FROM cohort) c
ORDER BY w.tenure_week;
```

结果解读：典型形态是留存率第 2~3 周掉最快、人均日单量在第 5~6 周接近成熟水平；激励资源应压在流失陡峭的周次，保底工资至少覆盖到爬坡达标周。

**解法二：递归 CTE 周轴补零 + 窗口累计（曲线无断点，口径最严谨）**

```sql
WITH RECURSIVE week_axis AS (                 -- 步骤1：生成0~8周龄完整周轴
    SELECT 0 AS w
    UNION ALL
    SELECT w + 1 FROM week_axis WHERE w < 8
),
cohort AS (                                   -- 步骤2：封口后的新人名单
    SELECT rider_id, onboard_dt
    FROM rider_onboard
    WHERE onboard_dt BETWEEN '2026-09-01' AND '2026-09-30'
      AND onboard_dt <= DATE_SUB('2026-10-25', INTERVAL 56 DAY)
),
grid AS (                                     -- 步骤3：cohort×周轴全组合，作为补零骨架
    SELECT c.rider_id, c.onboard_dt, a.w
    FROM cohort c CROSS JOIN week_axis a
),
filled AS (                                   -- 步骤4：左连出勤记录，缺勤周补0
    SELECT g.rider_id, g.w,
           COALESCE(SUM(s.order_cnt), 0) AS ord,          -- 该周总单量（缺勤=0）
           MAX(CASE WHEN s.work_date IS NOT NULL THEN 1 ELSE 0 END) AS is_active
    FROM grid g
    LEFT JOIN rider_shifts s
           ON s.rider_id = g.rider_id
          AND DATEDIFF(s.work_date, g.onboard_dt) DIV 7 = g.w   -- 出勤日映射到周龄
    GROUP BY g.rider_id, g.w
)
SELECT f.w AS tenure_week,
       ROUND(SUM(f.is_active) * 100.0 / (SELECT COUNT(*) FROM cohort), 2) AS retention_pct,
       -- 分母恒为 cohort 总数，某周无人出勤也会输出0%而非缺行
       ROUND(SUM(f.ord) / NULLIF(SUM(CASE WHEN f.is_active = 1 THEN 1 END), 0), 1) AS avg_weekly_orders,
       SUM(f.is_active) AS active_riders
FROM filled f
GROUP BY f.w
ORDER BY f.w;
```

结果解读：补零后留存曲线在低周龄出现 0%/接近 0% 的"断崖"，正是流失集中周；`avg_weekly_orders` 为周口径，除以该周实际出勤天数即可换算人均日单量，两者口径要在报表中注明。

> **Hive/Spark SQL 差异**：Hive 无递归 CTE，周轴可用日历维度表或 `posexplode(sequence(0,8))` 生成；`DATEDIFF(...) DIV 7` 写作 `floor(datediff(work_date, onboard_dt)/7)`；cohort×周轴的 CROSS JOIN 在 Hive 中直接支持，建议先按 rider_id 分桶减少 join shuffle。

### 5. 性能分析与优化

解法一是一次 join + 一次分组，代价 O(cohort 出勤行数)；解法二多一个 9 倍膨胀的 grid（cohort 人数 × 9 周）与一次 join，cohort 十万级时 grid 约百万行，仍可接受。优化建议：1) rider_shifts 按 (rider_id, work_date) 建复合索引或按月分区，join 与周龄映射都走等值/范围条件；2) 周龄可在写入时预计算成列（tenure_week），查询免函数计算；3) 例行化后预聚合"骑手×周"粒度表（周出勤天数、周单量），cohort 报表变成对小表聚合；4) cohort 封口条件放 WHERE 最前，先裁剪再 join；5) 多 cohort 并看时按 onboard 月份分组输出，避免一次全量扫描所有历史骑手。

### 6. 面试延伸考点

- **为什么留存分母用 cohort 总数而不是"上周仍在职人数"？** 要点：前者是 cohort 留存（可跨 cohort 比较、单调下降），后者是期间留存（循环流动），两者曲线形态与用途不同，混用是常见口径事故。
- **骑手入职当天没出勤，用 MIN(work_date) 当入职日会怎样？** 要点：cohort 起点被推迟、周龄整体偏移，正确做法是用入职登记表的 onboard_dt 作为锚点。
- **人均日单量的分母为什么是出勤人·日而不是天数×人数？** 要点：前者衡量"在岗效率"，后者把缺勤摊进去衡量"粘性产出"；爬坡看前者，激励设计两者都要。
- **兼职骑手会怎么污染爬坡曲线？** 要点：兼职出勤少、单量低，混算会压低曲线；应按周出勤天数分层（如 ≥4 天为全职口径）分别输出。

### 7. 业务拓展思考

两条曲线可直接转成运营节奏：留存陡降周次前置投放"满 X 单奖励"与师徒绑定；爬坡达标周次决定新人保底工资退出点与冲单奖梯度。口径延展：留存可拆"主动注销/超 14 天不出勤"两类流失；爬坡可对比不同城市、不同骑手来源（专送/众包）的达标速度；把周龄曲线与接单距离、拒单率叠加，可诊断流失原因是"收入不及预期"还是"体验受挫"，进而分别调整派单策略与新人保护期规则，形成"招聘—留存—爬坡"全链路运力供给模型。
