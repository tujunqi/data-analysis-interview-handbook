## 一、SQL类（Q1-Q9）

### Q1：窗口函数和GROUP BY有什么区别？什么场景必须用窗口函数？

**【考察点】** SQL理解深度的第一试金石。

**【低分避坑】** 只会说"窗口函数更高级"；说不出"行数变化"这个本质差异。

**【高分框架】** 一句话本质 + 行数对比 + 三个典型必用场景 + 执行顺序细节。

**【完整参考答案】**
"本质区别是**输出行数**：GROUP BY把每组压成一行，明细信息丢失；窗口函数**每一行都保留**，把组内计算结果作为额外列附在每行上。三个必须用窗口函数的场景：①**组内排名**（每个类目销量Top3——需要保留商品明细再排名）；②**组内对比**（每单金额和所属用户平均单价的差——用聚合窗口SUM/AVG() OVER()广播组统计值）；③**偏移与滑动**（环比用LAG、7日滑动均值用ROWS BETWEEN——这些GROUP BY根本做不到）。
执行顺序上，窗口函数在GROUP BY/HAVING**之后**、ORDER BY之前执行，所以不能直接写在WHERE里，要先套一层子查询或CTE再过滤——比如'取每个部门工资前3'必须先RANK再外层WHERE rn<=3。"

**【加分延伸】** 提"窗口函数让SQL具备表达'行间关系'的能力，等价于Pandas的transform/groupby.shift"。

### Q2：RANK、DENSE_RANK、ROW_NUMBER有什么区别？取"销量前3的商品"该用哪个？

**【考察点】** 排名函数细节 + "并列"业务语义。

**【低分避坑】** 三者混用；不知道"前3"有歧义（恰好3条 vs 含并列）。

**【高分框架】** 并列时的编号差异（1,1,3 / 1,1,2 / 1,2,3）→ "前N"的两种业务语义 → 选型结论。

**【完整参考答案】**
"三个函数都排序编号，区别在**并列处理**：ROW_NUMBER强制唯一（1,2,3,4），RANK并列同名次但跳号（1,1,3），DENSE_RANK并列且不跳号（1,1,2,3）。
'销量前3的商品'要先问业务语义：**'要恰好3条'**（哪怕第3、4名并列也只取3条）用ROW_NUMBER；**'并列都要'**（销量并列第3的商品都算Top3，可能返回4条）用DENSE_RANK。业务报表一般倾向后者——'宁多勿漏'，尤其涉及奖金/榜单时漏掉并列冠军是事故。如果用RANK取 rn<=3 还会出现'前3返回5条'的意外（1,1,3,3…），所以**选型时必须先想清楚并列语义**。"

**【加分延伸】** NTILE(4)分四分位（RFM打分常用）；"取每个类目TopN用PARTITION BY类目"，全表排名不写PARTITION BY。

### Q3：手写SQL：一张订单表有重复记录，怎么去重只保留每个订单的最新一条？

**【考察点】** 去重的三种写法与适用条件（手写高频题）。

**【低分避坑】** 只会 `SELECT DISTINCT *`（只能去完全相同的行，去不了"业务键重复内容不同"）；忘记处理并列时间戳。

**【高分框架】** 场景区分：完全重复→DISTINCT/GROUP BY；业务键重复→窗口法/MAX(id)回表法；给出代码与各自适用性。

**【完整参考答案】**

```sql
-- 场景：order_id 重复（多次状态流转/重复导出），保留 update_time 最新的那条

-- 写法一：窗口函数（推荐，逻辑最清晰）
WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY order_id              -- 每个订单一组
               ORDER BY update_time DESC, id DESC -- 最新优先；id DESC 兜底同一秒的并列，保证结果确定
           ) AS rn
    FROM orders
)
SELECT * FROM ranked WHERE rn = 1;
-- 优点：一次扫描完成；rn=1 保证每组恰好一条（不会因并列返回多行）

-- 写法二：GROUP BY 取最大id再回表（老版本MySQL无窗口函数时用）
WITH latest AS (
    SELECT MAX(id) AS max_id        -- 假设id自增且与时间正相关：每组业务键取最大id
    FROM orders
    GROUP BY order_id
)
SELECT o.* FROM orders o
JOIN latest l ON o.id = l.max_id;
-- 优点：兼容旧版本；注意依赖"id与时间同向"的假设，如果可能乱序要改取MAX(update_time)对应行

-- 写法三：NOT EXISTS 反连接（保留"不存在更新的记录"的行）
SELECT o.* FROM orders o
WHERE NOT EXISTS (
    SELECT 1 FROM orders newer
    WHERE newer.order_id = o.order_id
      AND newer.update_time > o.update_time      -- 有比它新的就不选它
);
-- 并列时间会返回多条，如需唯一要再加 tie-breaker 条件
```

**【加分延伸】** 提"窗口法在大表上可能触发排序，若表有 (order_id, update_time) 联合索引可减少排序"；提"MySQL 8.0 的 `WITH` CTE 让多层逻辑可读"。

### Q4：手写SQL：找出连续3天都有登录的用户。说说你的思路和代码。

**【考察点】** "连续问题"套路（gaps-and-islands），校招笔试压轴常客。

**【低分避坑】** 想用自连接三层嵌套（能写但复杂易错）；忘记先按天去重（同日多次登录会干扰）。

**【高分框架】** 核心技巧=**日期减去行号得到"分组键"**：连续日期减去递增行号结果相同，同键即连续段。

**【完整参考答案】**
"思路三步：①按用户×日期去重（一天只留一行）；②对每个用户的日期排序编号；③**用日期减去编号**——连续的日期减去连续的编号会得到同一个'基准日'，这个基准日就是连续段的分组键；按用户+基准日分组计数≥3即连续3天。"

```sql
WITH login_d AS (                              -- 第1步：一人一天一行
    SELECT DISTINCT user_id, DATE(login_time) AS dt
    FROM user_login
),
ranked AS (                                    -- 第2步：组内按日期编号
    SELECT user_id, dt,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY dt) AS rn
    FROM login_d
),
seg AS (                                       -- 第3步：日期-行号=连续段键
    SELECT user_id, dt, rn,
           DATE_SUB(dt, INTERVAL rn DAY) AS grp_key   -- 连续日期 => 同一grp_key
    FROM ranked
)
SELECT user_id, MIN(dt) AS streak_start, MAX(dt) AS streak_end, COUNT(*) AS days
FROM seg
GROUP BY user_id, grp_key
HAVING COUNT(*) >= 3;                          -- 连续段天数≥3即为所求
```

**【加分延伸】** 该模式通吃"连续签到最长天数"（取MAX(days)）、"连续N月消费"；补充另一解法：`LAG` 比较 `dt = 上一天+1` 打断点再累计——两种都会更显功力。

### Q5：手写SQL：计算每个渠道用户的次日留存率。

**【考察点】** 留存SQL（全库最高频手写题）。

**【低分避坑】** 分子分母口径不一致（分子含老用户）；JOIN条件写错方向；渠道维度在JOIN后丢失。

**【高分框架】** 三步：新用户表（首登日+渠道）→ 左连次日登录 → 分渠道聚合算比率。

**【完整参考答案】**

```sql
WITH first_login AS (                    -- 第1步：每个用户的首次登录日与注册渠道
    SELECT u.user_id,
           MIN(l.dt) AS first_dt,        -- 首次登录日
           u.channel                     -- 渠道从用户表取（避免登录表无渠道字段）
    FROM users u
    JOIN user_login l ON u.user_id = l.user_id
    GROUP BY u.user_id, u.channel
),
day1 AS (                                -- 第2步：命中"首登次日"的登录记录
    SELECT f.user_id, f.first_dt, f.channel
    FROM first_login f
    JOIN user_login l
      ON l.user_id = f.user_id
     AND l.dt = DATE_ADD(f.first_dt, INTERVAL 1 DAY)   -- 次日留存：精确命中第1天
)
SELECT f.channel,                                   -- 按渠道汇总
       COUNT(DISTINCT f.user_id) AS new_users,      -- 分母：当日新增用户数
       COUNT(DISTINCT d.user_id) AS retained,       -- 分子：次日仍登录的用户数
       ROUND(COUNT(DISTINCT d.user_id) / COUNT(DISTINCT f.user_id), 4) AS day1_rate
FROM first_login f
LEFT JOIN day1 d                                    -- LEFT JOIN：没人次日登录的渠道也要出0
  ON d.user_id = f.user_id
GROUP BY f.channel
ORDER BY day1_rate DESC;
```

"易错点三个：①分子分母都要DISTINCT去重；②必须LEFT JOIN，否则'次留0%'的渠道整行消失；③渠道字段要在第一步就带上，JOIN后再分组。"

**【加分延伸】** 滚动留存改法（`BETWEEN first_dt+1 AND first_dt+7`）；大表优化："先把用户×首登日×渠道预聚合成轻表再JOIN"。

### Q6：讲讲MySQL中JOIN的执行原理。为什么"小表驱动大表"？

**【考察点】** JOIN底层原理（区分背题与理解）。

**【低分避坑】** 只会背"小表驱动大表"不知道为什么；说不出三种JOIN算法。

**【高分框架】** Nested Loop（内循环次数=驱动表行数×被驱动表每次查找成本）→ 所以驱动表要小、被驱动表关联键要有索引 → Block Nested Loop 与 8.0.18+ Hash Join。

**【完整参考答案】**
"MySQL的JOIN主要三种算法：**Simple Nested Loop**——双重循环逐行匹配，最慢；**Index Nested Loop**——外层（驱动表）每取一行，到内层表**通过索引**查匹配行，把'全表扫'变成'索引点查'，这是最理想的形态，所以要求**被驱动表的关联字段有索引**；**Block Nested Loop / Hash Join**——没有可用索引时，把驱动表的一批行放进join buffer，内层表每扫一遍完成一批匹配（8.0.18起用Hash Join替代，小表建哈希表，大表探测）。
'小表驱动大表'的原因：驱动表行数决定**外层循环次数**，每循环一次就要到内层查一次——驱动表1万行×点查 vs 大表1000万行×点查，成本差100倍。所以LEFT JOIN时左表是驱动表，写SQL要让过滤后更小的表当驱动侧；另外用EXPLAIN看驱动顺序（第一行表），确认优化器选择符合预期。"

**【加分延伸】** 提"大表JOIN先预聚合缩小再JOIN"（改变驱动集大小）；提"JOIN键类型不一致会让索引失效（隐式转换）"。

### Q7：WHERE和HAVING的区别？SQL的完整执行顺序是什么？

**【考察点】** SQL基本功（几乎每场技术面都问）。

**【低分避坑】** 只答"WHERE过滤行HAVING过滤组"，不背执行顺序；不知道WHERE不能有聚合函数的原因。

**【高分框架】** 执行顺序六步 + 各步可用的东西 + 一个体现顺序的陷阱（SELECT别名在WHERE里不可用、窗口函数在HAVING后）。

**【完整参考答案】**
"执行顺序：**FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**。WHERE在分组前逐行过滤，所以**不能用聚合函数**（此时还没分组），且看不到SELECT里定义的别名（SELECT还没执行）；HAVING在分组后过滤组，可以用聚合函数。两个常见陷阱：①`WHERE rank_col <= 3` 报错——窗口函数排在HAVING之后，比WHERE更晚，必须套子查询；②`WHERE ym = '2024-06'` 如果ym是SELECT里用DATE_FORMAT造的别名会报错，要在WHERE里写原始表达式或套子查询。理解顺序之后，很多'为什么这个别名用不了'的问题都会自己推理出来。"

**【加分延伸】** 提"能下推到WHERE的条件不要放HAVING"（先过滤减少分组数据量，性能更好）。

### Q8：手写SQL：行转列。把"用户-月份-消费额"长表转成"用户为行、月份为列"的宽表。

**【考察点】** 条件聚合（CASE WHEN + GROUP BY）实现PIVOT。

**【低分避坑】** 忘记SUM包裹（CASE WHEN返回多行）；动态列问题不知道怎么答。

**【高分框架】** 条件聚合标准写法 + 为什么SUM + 动态列的说明（SQL没有原生PIVOT，动态列要靠程序拼接SQL或数仓函数）。

**【完整参考答案】**

```sql
-- 长表：user_spend(user_id, ym, amount) → 宽表：每用户一行，1-6月各一列
SELECT user_id,
       SUM(CASE WHEN ym = '2024-01' THEN amount ELSE 0 END) AS m01,  -- 命中该月的金额求和
       SUM(CASE WHEN ym = '2024-02' THEN amount ELSE 0 END) AS m02,
       SUM(CASE WHEN ym = '2024-03' THEN amount ELSE 0 END) AS m03,
       SUM(CASE WHEN ym = '2024-04' THEN amount ELSE 0 END) AS m04,
       SUM(CASE WHEN ym = '2024-05' THEN amount ELSE 0 END) AS m05,
       SUM(CASE WHEN ym = '2024-06' THEN amount ELSE 0 END) AS m06
FROM user_spend
GROUP BY user_id;
-- 原理：每个用户分组内，每行按ym判断是否属于该列，SUM把命中行加总、未命中记0
-- 写 ELSE 0 而不是省略：省略时非命中行返回NULL，SUM会忽略NULL，结果一样但语义更显式
```

"补充：SQL标准里没有动态PIVOT——列名固定才能这么写；月份不定时，工程上要么在BI/程序层做透视（Pandas pivot / PowerBI矩阵），要么用存储过程动态拼接。面试答到'条件聚合是万能底座，动态列交给外层工具'即可。"

**【加分延伸】** 反向"列转行"用UNION ALL或JSON_TABLE；Hive里直接有 `CASE WHEN` 同款，另有 `collect_list` 等聚合。

### Q9：一条SQL很慢，你的排查和优化思路是什么？

**【考察点】** 系统性调优思维（开放题，考框架）。

**【低分避坑】** 只会说"加索引"；没有排查顺序。

**【高分框架】** 三层排查：**看执行计划（EXPLAIN）→ 看写法（JOIN膨胀/函数失效/SELECT *）→ 看数据架构（预聚合/分区/物化）**。

**【完整参考答案】**
"我按三层排查。**第一层看EXPLAIN**：type是否ALL（全表扫描）——力争到range/ref；key是否用上了预期索引；rows预估扫描量；Extra里出现 Using filesort / Using temporary 是危险信号（通常排序或去重没吃到索引），Using index 是覆盖索引的好信号。**第二层审写法**：①索引列上是否有函数或运算（`DATE(create_time)=...` 会让索引失效，改写成范围条件）；②隐式类型转换（字符串列传数字）；③JOIN是否膨胀——先检查关联键唯一性，一对多时先聚合再JOIN；④SELECT * 改成所需列，给覆盖索引留机会；⑤大偏移的LIMIT分页改'游标分页'（WHERE id > 上页最大id）。**第三层看架构**：如果单表千万级以上，写法优化有限——把常用口径做成**预聚合表**（数仓DWS层）、按时间分区裁剪、或上缓存/物化。最后我会说：优化的第一步永远是**确认这条SQL的业务必要性**——很多慢SQL的正确解法是'这个需求换个方式出数'。"

**【加分延伸】** 提 `SHOW PROFILE`/慢查询日志定位；提"COUNT(DISTINCT)大表改GROUP BY"（Hive场景）。

## 二、Excel类（Q10-Q12）

### Q10：VLOOKUP有哪些局限？分别怎么解决？

**【考察点】** Excel函数体系（校招Excel环节必考第一题）。

**【低分避坑】** 只说"有时候查不到"；说不出结构性局限。

**【高分框架】** 四大局限逐条+解法：①只能从左往右查→INDEX+MATCH/XLOOKUP；②硬编码列号易错位→MATCH动态列/XLOOKUP；③无内置容错→IFERROR/XLOOKUP第四参数；④近似匹配要求升序+容易误用→区间表规范。

**【完整参考答案】**
"VLOOKUP有四个结构性局限。**①只能向右查**：查找值必须在区域第一列，返回列在它右边——按姓名反查工号这种'向左查'做不到，解法是INDEX+MATCH（MATCH找行、INDEX取值，方向任意）或直接XLOOKUP。**②列号硬编码**：第三个参数写死3，维表插一列全表错位，解法是用MATCH动态算列号：`VLOOKUP(A2, 区域, MATCH("商品名", 表头区域, 0), 0)`。**③没有内置容错**：查不到返回#N/A，要包IFERROR；XLOOKUP第四参数直接给默认值更干净。**④匹配模式易误用**：默认省略第四参数是近似匹配（要求区域升序，否则结果不可预测）——这是无数'VLOOKUP结果乱'事故的根源，日常一律显式写FALSE/0做精确匹配；近似匹配只用于提成区间、税率表这类阶梯匹配。最后补一句选型：2021/M365环境我直接用XLOOKUP，四个问题全解。"

**【加分延伸】** #N/A排查三步（TRIM去不可见空格→类型统一→确认区域首列）；XLOOKUP搜索模式-1找"最近一条记录"。

### Q11：用透视表算毛利率，为什么有人算出来的结果是错的？

**【考察点】** "平均的平均"陷阱（Excel面试的区分度题）。

**【低分避坑】** 不知道陷阱是什么；不知道计算字段是解法。

**【高分框架】** 错误做法：源数据逐行算毛利率→透视表求和/平均（逐行平均≠总毛利率）；正确做法：计算字段（先汇总分子分母再相除）；推广到所有比率型指标。

**【完整参考答案】**
"错误出在**'平均的平均'**：如果先在源数据每行算出毛利率（每单的毛利/该单销售额），再在透视表里对'毛利率'这一列求平均，得到的是'各单毛利率的简单平均'——单笔小单和单笔大单权重相同，和真实的总毛利率（总毛利/总销售额）不一致，大单占比高的类目会被明显扭曲。
正确做法是用**透视表计算字段**：`分析→字段和集→计算字段`，定义 `毛利率 = 毛利 / 销售额`——计算字段在**汇总层**先算总毛利和总销售额再相除，口径才是对的。推广一下：所有比率型指标（转化率、达成率、留存率）都必须'先加总分子分母、再相除'，任何'对比率求平均'的口径都要警惕。这个题的通用版本叫'**比率指标不可加也不可直接平均**'，和数仓里'余额不能按时间SUM'是同族陷阱。"

**【加分延伸】** DAX视角："PowerBI里用DIVIDE(SUM(毛利),SUM(销售额))的度量值天然是汇总层计算，从机制上避免这个坑"。

### Q12：不写VBA，怎么用函数做"多条件求和与计数"？至少说出三种写法。

**【考察点】** 条件聚合函数熟练度。

**【低分避坑】** 只会说SUMIFS；说不出老版本兼容方案与透视表方案。

**【高分框架】** ①SUMIFS/COUNTIFS（直给）；②SUMPRODUCT（老版本/复杂逻辑）；③透视表（拖拽）；④（进阶）SUM+FILTER动态数组。

**【完整参考答案】**
"四种写法：**①SUMIFS/COUNTIFS**：`=SUMIFS(金额区, 渠道区,"抖音", 日期区,">="&月初, 日期区,"<"&下月初)`，注意SUMIFS的求和区在第一参数（和SUMIF相反）；**②SUMPRODUCT**：`=SUMPRODUCT((渠道区="抖音")*(金额区))`——兼容老版本，且支持更灵活的逻辑（条件相乘=AND、相加=OR），加权平均类需求只有它能优雅实现；**③透视表**：拖维度+值筛选，多条件场景最不容易错，配合切片器还能交互；**④动态数组**（M365）：`=SUM(FILTER(金额区,(渠道区="抖音")*(日期区>=月初)*(日期区<下月初)))`。选型：简单条件用SUMIFS；要跨版本兼容或逻辑复杂用SUMPRODUCT；给人看和自查用透视表。"

**【加分延伸】** 通配符 `"*手机*"` 模糊匹配；文本型数字会让条件匹配失败（分列转数值）。

## 三、统计学类（Q13-Q18）

### Q13：用大白话解释p值。p=0.03意味着什么？不是什么？

**【考察点】** 统计学第一高频题（考察是否真懂p值）。

**【低分避坑】** 说"有3%的概率是错的"或"两组有差异的概率97%"——两大经典误读；只背定义不会业务翻译。

**【高分框架】** 标准定义 + 正确翻译 + 两个"不是" + 一句业务话术收尾。

**【完整参考答案】**
"标准定义：**在'两组没有差异'（原假设）成立的前提下，观察到当前差异或更极端差异的概率**。p=0.03的正确翻译是：如果新版本其实没有任何效果，纯靠运气出现'现在这么大的提升'，机会只有3%——这个运气概率低到我们更愿意相信'效果是真的'，所以拒绝原假设。
但p=0.03**不是**：①'新版本有97%的概率有效'（频率学派里原假设没有'为真的概率'这个概念）；②'效果很大'（p值和效应量、样本量都有关，样本量够大时微小的差异也会显著）。所以我汇报时除了p值，一定同时给**提升幅度和置信区间**——p值回答'是不是真的'，效应量回答'有多大值不值'，两个问题要分开答。"

**【加分延伸】** 主动补"0.05是约定不是魔法线，还要结合业务成本"；提"p-hacking"（反复切分人群直到显著）作为反面警示。

### Q14：什么是置信区间？为什么95%置信区间不是"真值有95%的概率在区间里"？

**【考察点】** 频率学派vs贝叶斯的边界（校招高区分度题）。

**【低分避坑】** 直接答"真值95%概率落在区间内"（这是贝叶斯可信区间的说法，不是频率学派置信区间）。

**【高分框架】** 正确定义（重复抽样视角）+ 为什么容易误解 + 业务上怎么用（CI比p值信息更多）。

**【完整参考答案】**
"95%置信区间的严格定义是**'用同样的抽样和构造方法反复做，长期来看95%的区间会盖住真值'**——95%说的是**构造方法的可靠性**，不是某一个具体区间里真值的概率。因为频率学派认为真值是固定的数（只是未知），区间是随机的，所以'真值落在区间内'不是随机事件，不能赋概率。
业务上我更看重CI的三个用法：①**CI整体在0右侧⇒显著**，等价于p<0.05但信息更全；②**CI宽度反映不确定性**——区间很宽说明样本不足，要延长实验；③**CI下界**可以对照'最小可接受提升'做决策（下界3%>成本线2%，放心上线）。所以我做AB汇报的标准格式是'提升+X%，95%CI[a, b]'，比单独一个p值有用得多。"

**【加分延伸】** 提"贝叶斯可信区间才是'参数有95%概率在区间内'，两者哲学不同但大样本下数值接近"；提"CI不覆盖0但幅度小于业务成本的案例"。

### Q15：AB实验的样本量怎么计算？哪些因素影响它？

**【考察点】** 样本量公式与直觉（技术面常要求现场算）。

**【低分避坑】** 记不住公式结构（四个要素：α、β、基线方差、效应量）；说不出"相对提升越小样本越大得越快"的直觉。

**【高分框架】** 公式 + 各参数含义与常用值 + 数字例子 + 定性直觉（平方反比）。

**【完整参考答案】**
"两比例比较的每组样本量：**n = (z_α/2 + z_β)² × [p₁(1−p₁)+p₂(1−p₂)] / (p₁−p₂)²**。参数：α取0.05（z≈1.96），功效1−β取0.8（z_β≈0.84），两项z之和平方≈7.85；p₁是基线转化率，p₂是期望的新转化率，差值Δ=p₁−p₂是**绝对**提升。
举例：基线10%，想检测1pp（10%→11%）的提升，n=7.85×(0.09+0.0979)/0.0001≈14750人/组。三个直觉规律：①**效应量在分母且平方**——想检测的效应减半，样本量翻4倍；②**基线越低方差项越小**，但Δ通常也更小，总体还是更难测；③**α和β越严格样本越大**。实操中我按公式算完再乘1.1-1.2倍余量，并保证实验时长覆盖至少一个完整周（消除星期效应）。"

**【加分延伸】** 提"均值类指标（客单价）样本量公式用方差σ²替代p(1-p)"；提"缩短实验的现实手段：提高MDE、用更灵敏的代理指标、方差缩减技术（CUPED，点到为止）"。

### Q16：第一类错误和第二类错误在AB测试里分别对应什么业务后果？你会怎么权衡？

**【考察点】** 两类错误的业务化表达（考统计概念是否落地）。

**【低分避坑】** 只会背"弃真/取伪"定义，说不出业务后果；不知道权衡手段。

**【高分框架】** 定义+AB语境化（α=上线无效改动，β=错过有效改动）→ 成本不对称分析 → 权衡手段（样本量/α调整/顺序决策）。

**【完整参考答案】**
"第一类错误α是**假阳性**：实验显示有效、实际无效，我们上线了一个没用的改动——代价是开发资源浪费，更糟的是无效改动可能悄悄伤害体验。第二类错误β是**假阴性**：改动真有效但实验没测出来，我们错过了提升——代价是机会成本。业务上两类错误并不对称：互联网改动的假阳性代价（回滚一次）通常低于假阴性代价（错过增长），所以α=0.05、功效80%的标准是合理的；但在高风险场景（如金融风控规则、医疗）权衡会反转——风控宁可漏放不可错杀，假阳性的成本极高。
权衡手段：唯一'双赢'的是**加大样本量**（同时降α和β）；样本固定时调α会反向影响β；实操里我还会用**顺序决策**降低两类错误的总成本——小流量试探+达标放量+护栏熔断，把错误在早期截住。"

**【加分延伸】** 提"AA测试可以实证α（对照组vs对照组的显著率应≈5%）"；提"多重检验校正Bonferroni"。

### Q17：AB实验结果不显著，你的处理流程是什么？（技术面版）

**【考察点】** 实验健康度检查清单（和业务面Q27相比，技术面版本要更"工程化"）。

**【低分避坑】** 直接说"延长实验时间"；漏掉SRM和AA检查。

**【高分框架】** 四查：①健康度（SRM样本比失配/AA/埋点）→ ②功效（样本量是否达标，看CI）→ ③异质性（分人群是否被平均）→ ④决策（延长/止损/沉淀）。

**【完整参考答案】**
"我的处理按四查走。**一查实验健康度**：SRM检查——设计5:5分流，实际样本比例是否偏离（卡方检验，比如48:52以上偏离要警惕分流bug或用户选择性退出）；AA测试——两组跑同版是否误报显著；埋点完整性——实验组功能数据上报率是否和对照一致。健康度有问题，结论作废，修复重跑。**二查功效**：对照实验前的样本量设计，确认是否收集够；如果没收集够，看置信区间——CI很宽（如[-1%,+4%]）说明'还没测出来'，延长或加流量；CI很窄但跨0（如[-0.3%,+0.3%]）说明'效应即使存在也很小'，可以止损。**三查异质性**：分新老客/渠道/平台看有没有方向相反的显著效应互相抵消——有就从'上不上'变成'对谁上'的定向决策。**四做决策并沉淀**：真无效应就下线，把结论（含CI）写进实验记录库——实验库是团队最重要的隐性资产，防止三个月后有人重复做同一个实验。"

**【加分延伸】** SRM检查的具体方法（观测比与期望比的卡方拟合）；提"新奇效应检查：按天看效应是否衰减"。

### Q18：什么是辛普森悖论？AB测试为什么能避免它？观察数据怎么办？

**【考察点】** 悖论题（统计理解 + 实验设计联系）。

**【低分避坑】** 只能讲定义讲不出数字例子；说不出"为什么AB能免疫"。

**【高分框架】** 数字案例（分组好、整体反转）→ 成因（混杂变量与分组分配相关）→ AB免疫的原因（随机化切断混杂）→ 观察数据的防御（分层/标准化/权重检查）。

**【完整参考答案】**
"辛普森悖论是'**每个分组里A都更好，合并后B反而更好**'的现象。数字例子：转化率上，iOS里A版6%>B版5%，安卓里A版4%>B版3%，但整体A=4.6%<B=4.4%——因为B把70%流量分到了高转化的iOS，A只分了30%，结构权重压倒了组内优势。
**AB测试为什么免疫**：随机分流保证两组在'渠道'这个混杂变量上的分布几乎一致（大样本下），结构效应被随机化抹平，剩下的差异就是处理效应。这也解释了为什么AB要求随机化单元正确、样本量足够。
**观察数据（非实验）怎么办**：三道防线——①**强制分层看数**：任何整体结论先按关键混杂维度（渠道/人群/时段）分层复验，分层结论与整体相反时以分层为准；②**标准化**：用统一权重重新加权各层（如都按iOS:安卓=50:50加权），消除结构差异；③**检查分配机制**：先问'这个分组是怎么形成的'——如果是自选择（用户自己选的版本），结论天然不可信，要往准实验设计（匹配/DID）上靠。"

**【加分延伸】** 历史案例（伯克利录取性别歧视案）；提"分析习惯：看到整体指标先看结构占比，是防御辛普森的本能"。

## 四、数仓类（Q19-Q20）

### Q19：数仓为什么要分层？不分层会怎样？

**【考察点】** 数仓第一必考题（考是否理解数据生产线）。

**【低分避坑】** 背得出五层名字说不出"为什么"；举不出不分层的具体乱象。

**【高分框架】** 五层一句话带过 → 重点讲四条理由（复用解耦/职责清晰/血缘追溯/屏蔽变化）→ 不分层的三个真实乱象 → 结合自己的经历。

**【完整参考答案】**
"先一句话定位分层：**ODS原样接入、DWD明细清洗、DWS轻度汇总、ADS面向应用，DIM维度横切**。分层的原因四条：**①复用与解耦**：'用户×天'这种汇总算一次，所有报表复用，不用每张报表都从亿级明细重算——省算力且口径统一；**②职责清晰**：清洗逻辑只写在DWD层，改口径知道去哪改，出问题知道去哪查；**③血缘可追溯**：ADS数字有问题，顺着ADS→DWS→DWD→ODS逐层核对，像函数调用栈；**④屏蔽上游变化**：业务库改表结构只影响ODS→DWD的映射，下游无感。
不分层的真实乱象我见过三个：①同一个'GMV'五张表五个口径，开会先吵架；②一条临时需求直接在明细上写SQL出报表，三个月后没人敢动那个任务（血缘断了）；③上游加个字段，十几张下游报表集体报错。所以我的总结是：**分层是用一点存储和步骤，换质量、效率和口径的唯一性**。"

**【加分延伸】** 讲自己项目里"我在DWD层做了清洗、在ADS层出指标"的对应经历；提"分层粒度要克制：DWS只建高频复用的，不贪多"。

### Q20：事实表和维度表的区别？账户余额能直接SUM吗？

**【考察点】** 维度建模基本功 + 半可加性（组合考，第二个问题区分度极高）。

**【低分避坑】** 只说"事实表存数字维度表存名字"；对余额SUM答"能"或不知道。

**【高分框架】** 定义对照（事件vs主体、外键+度量vs属性、行数差异）→ 三种事实表类型一句带过 → 可加性三分类 → 余额的正确处理（期末快照/日均）。

**【完整参考答案】**
"事实表记录**发生的事件**，一行=一次业务动作（一笔订单、一次支付），字段=外键+度量值，亿行级持续增长；维度表描述**事件的主体与环境**（用户、商品、日期），字段=描述属性，十万行级相对稳定。事实表按形态分三种：事务事实表（一笔一行）、周期快照（每天拍一次状态）、累积快照（一个流程一行、里程碑时间逐步更新）。
**余额不能直接SUM**——它属于**半可加度量**：跨账户、跨地区可以加（全平台总余额有意义），但**按时间求和无意义**（1号余额100、2号余额100，加起来200什么都不是）。正确处理两种：**期末快照**——每天存一行当日余额，取期初/期末值；**日均余额**——对计息等场景按天平均。同族的还有库存量。总结成可加性三分类：完全可加（销售额）、半可加（余额、库存）、不可加（比率类——必须先加总分子分母再除）。这道题我把它当作'能不能正确处理状态类数据'的试金石，真实数仓里做错会直接导致资金类报表失真。"

**【加分延伸】** 提SCD2（维度历史用生效日期多行保留）；提"退化维度：订单号直接放事实表"。
